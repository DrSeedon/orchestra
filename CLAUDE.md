## Что это
Свой оркестратор AI-агентов. Оркестратор управляет воркерами через MCP tools.
Каждый worker = CLI-сессия (Claude или Codex-бэкенд) в отдельном git worktree.
Dashboard = FastAPI + HTMX + SSE.

## Стек
- Python 3.12+, FastAPI, Jinja2, SSE
- `claude-agent-sdk` — SDK для Claude Code sessions
- External stdio MCP server (FastMCP) — tools как отдельный процесс
- SQLite — sessions, logs, inbox, jobs
- `git worktree` — изоляция работников

## Принципы
- Persistent client per session (connect once, `query()` injects mid-turn via stdin)
- External MCP (no in-process deadlocks)
- Workers communicate via HTTP callback, not MCP inject
- Proxy — см. секцию «🔌 ПРОКСИ» ниже (источник истины = .env HTTPS_PROXY)
- Фронтенд (JS/CSS/HTML) обновляется без рестарта; Python-код требует рестарта для загрузки, но это не разрешение на него
- `sudo systemctl` для `orchestra`/`telegram-bot-api` доступен технически, но это НЕ authorization: `restart/stop/start` — только по явной команде текущего юзера; `status` остаётся read-only. Рестарт прерывает active turns
- После разрешённого рестарта SQLite-сессии и idle workers восстанавливаются; активные turns прерываются
- **НЕ обновлять VPS самостоятельно** — git pull, systemctl restart на VPS делает только юзер вручную. Не пушить и не деплоить на VPS без команды
- **Remotes:** `origin` (github.com/DrSeedon/orchestra) — наш публичный, держать актуальным. Всё, что НЕ `origin`, — чужое: не трогать никогда, ни push, ни pull, ни ветки. Список смотреть командой (`git remote -v`), а не по памяти: на 11.08.2026 чужих remote в репозитории нет
- **TG /restart** — команда в TG группе для рестарта Orchestra
- **Воркеры могут общаться друг с другом** через `send_message(to="worker-name")`. Пример: backend воркер добавил endpoint → пишет frontend-opus чтобы тот добавил кнопку. Оркестратор не нужен как посредник для координации между воркерами

## 🔌 ПРОКСИ (единственный источник истины = .env)
- **`.env` `HTTPS_PROXY`/`HTTP_PROXY` = ЕДИНСТВЕННЫЙ источник.** Нет DB, нет hot-switch, нет кеша статусов
- Один прокси везде: systemd EnvironmentFile → `os.environ` → наследуют все (Orchestra + CLI агенты + MCP subprocess). Рассинхрон невозможен by design
- **Сменить прокси:**
  ```
  1. Отредактируй HTTPS_PROXY И HTTP_PROXY в .env (оба!)
  2. sudo systemctl restart orchestra
  ```
  Всё. Живой прокси найти: `bash scripts/check-proxies.sh` (диагностика — покажет живой и впишет в .env; рестарт — руками)
- **Дашборд:** только индикатор активного (из `os.environ`, read-only) + кнопка Check (проверить живость on-demand). Кнопки «выбрать/активировать» НЕТ — переключение только через .env
- `proxy_manager.py` — read-only: `list_proxies()` + `check_all()`. НЕ мутирует env, НЕ пишет в DB
- SSH-туннели (`ssh_tunnel.py`) поднимают локальные порты к VPS. `HTTPS_PROXY` указывает на нужный порт. Мёртвые VPS не спамят реконнектом (health-gate + backoff)
- **TG bot** (telegram-bot-api) — через proxychains (`/etc/proxychains4.conf`), C++ бинарник не читает .env. Обычно socks5 Contabo (12345). **ВАЖНО**: при смене прокси обновлять ОБА файла: `/etc/proxychains4.conf` И `~/.proxychains/proxychains.conf` — user-config имеет приоритет

## AI Efficiency (design principle)
Orchestra automates humans — but the AI agents themselves must be optimized too.
Every feature should minimize agent overhead: fewer tool calls, less context waste, less repetition.

**Design for AI, not humans:**
- If an agent does the same 3 tool calls every time → automate into 1 MCP tool or server-side logic
- If agents waste context reading the same files → pre-inject via system prompt or worktree setup
- If a pattern causes context rot (agent re-reads, re-explains, loops) → fix the root cause, don't add more instructions
- Measure cost-per-task, not just "does it work". $2 task done in 3 tool calls > $8 task done in 30 tool calls
- Prompt engineering = agent optimization. Shorter, clearer prompts = fewer confused retries = less $ burned
- Every new feature ask: "does this reduce total agent tool calls/tokens across typical workflows?"

**Anti-patterns to avoid:**
- Agent reads entire file when it needs 5 lines → give it grep/line-range hints
- Agent asks orchestrator for permission it could decide itself → expand decision tree
- Agent retries failed command 5 times → fail fast, report, let orchestrator decide
- Two agents duplicate work because they don't know about each other → worker-to-worker communication
- Agent spends 20 tool calls on setup that could be pre-configured → inject at spawn time

## Agent Determinism (design principle)
Агенты должны быть ПРЕДСКАЗУЕМЫМИ. Один путь, один маршрут, минимум свободы.

**Правила проектирования промптов и тулов:**
- **1 задача = 1 workflow.** Не давать агенту 3 способа сделать одно и то же — он выберет худший. Один оптимальный маршрут, жёстко прописанный
- **Минимум тулов.** Каждый лишний тул = развилка где агент может свернуть не туда. Давать ТОЛЬКО те тулы которые нужны для конкретной роли
- **Decision tree > свобода.** Вместо "реши сам" — чёткое дерево решений: если X → делай A, если Y → делай B. Агент не должен "думать" о стратегии
- **Fail loud, не fail creative.** Ошибку маршрутизировать по контракту BUGS ниже; не обходить молча. СТОП — только когда безопасно продолжить нельзя
- **Нет импровизации в проде.** Агент следует промпту буквально. Если промпт не покрывает ситуацию — спросить оркестратора, а не выдумывать

**При разработке новых ролей/промптов:**
- Тестировать: "может ли агент пойти не тем путём?" Если да — сузить промпт
- Каждый edge case в промпте = потенциальная развилка. Лучше 3 конкретных правила чем 1 "умное" обобщение
- Логировать когда агент отклоняется от ожидаемого пути → добавлять guardrails

## Баг-репорты от агентов (инбокс, НЕ BUGS.md)
- `report_bug(title, description)` — только сбои платформы Orchestra (MCP, сессии, worktree, TG, dashboard, model routing); писать сразу, даже если найден обход
- Баг кода текущего проекта → `docs/tasks/<id>/` + сообщение оркестратору, НЕ `report_bug`
- **Репорты живут вне рабочего дерева** — поэтому не пачкают checkout и не блокируют мержи. Трекнутый `BUGS.md` — только указатель, туда никто не пишет с 01.08.2026
- **При старте корневой Orchestra-сессии** — чекни инбокс: `GET /api/report_bug` (или баннер «🐛 Новые bug reports» на дашборде). Worker получает нужный контекст через задачу/промпт
- **Чистка**: разобранный репорт — удалить его файл из `records/` в инбоксе (путь и условия — в `BUGS.md`). TODO.md — done items удалять, держать компактным

## ⚡ PROCESS RULES (оркестратор)
- **КРАТКОСТЬ — не лей воду.** Юзер видит логи tool-вызовов. НЕ пересказывай что сделал ("Спавнил X", "Проверю что закоммитилось") — он это видит. НЕ дублируй статус по 2-3 раза за ответ. НЕ объясняй очевидное ("безобидно, всё чисто").
- **Сделал → одна фраза** (что + результат). Панчлайны/таблицы/резюме — ТОЛЬКО для реального итога или решения, НЕ на рутину (спавн, merge, "жду воркера", "как вернётся покажу").
- **Не отчитывайся о промежуточном** — "жду Codex", "воркер работает" = шум. Юзер узнает из авто-репортов/логов. Пиши когда есть РЕЗУЛЬТАТ или нужно РЕШЕНИЕ юзера.
- Панчлайн-аналогия из глобального промпта — на ИТОГ сессии/крупное решение, не на каждый чих.
- **ВСЕ воркеры ВСЕХ проектов — МОЯ ответственность.** Воркеры в kesha-tg-bot, polus, seedon и любом другом проекте управляются Orchestra. Баги воркеров (status-desync, зацикливание, idle-while-running) — разбираю Я, не делегирую проектному оркестратору. Проектный оркестратор (kesha-tg-bot, polus-orchestrator) — это разработчик проекта, НЕ менеджер воркеров.
- 📝 RULE: Когда пользователь говорит «все воркеры» без явного списка других проектов → действовать только в своём контуре и разбирать чужие логи своим read-only воркером, не рассылать распоряжения чужим оркестраторам.
- **НЕ убивать full-cycle воркеров после merge.** Full-cycle на гейте ("awaiting approval to plan/implement") = ЖДЁТ продолжения. merge → оставить idle, НЕ kill. Если воркер написал "STOP на гейте" — он ЖИВОЙ и ждёт следующую фазу. Условия самого kill'а живут ТОЛЬКО в модуле `worker-lifecycle` (`lifecycle=one-shot` + финальный DONE + успешный merge + idle + чистый WIP) и здесь намеренно не повторяются. Замер: #175 — эта строка требовала «kill только одноразовых» по ИМЕНИ (`impl-*`, `fix-*`), модуль — по маркеру `lifecycle`; агент выполнил более точное правило и формально нарушил `CLAUDE.md`.
- **Задал воркеру `owned_dirs` → включи туда и `docs/workers/<имя>.md`.** Иначе обязательная проверка личной памяти упирается в границу владения: воркер либо теряет урок, либо нарушает границу, чтобы его записать. Замер: 11.08.2026 за один день четверо (#175, #176, #177, #186) уперлись в это, трое молча потеряли урок, один написал и предупредил.
- **Задача появилась → сразу в работу; параллельность — средство, а не цель.** Спавн оправдан независимостью работы, а не наличием свободной модели. Работу, которую тянет один воркер, не делить на двоих — но по причине связности, а НЕ из-за цены спавна. **Прежняя оценка «≈$4 за холодный старт» была завышена в 6–13 раз и отменена (#178, 11.08.2026): холодный старт = 49–62K токенов = $0.31–0.62; $4 — это стоимость всей короткой сессии, а не входа в неё.** Настоящий драйвер расхода — round-trip'ы: ≈$0.13 на tool-вызов, показатель 1.05, R=0.935, и 68% суммы — `cache_read`, то есть перечитывание контекста на каждом вызове. Из этого следует обратное прежнему: бояться надо длинных болтливых сессий, а не лишнего воркера. Но независимую задачу НЕ ставить в очередь и не ждать освобождения: один файл на двоих — не повод откладывать, развести по непересекающимся участкам, перед мержем `check_conflict`, при конфликте — cherry-pick на свежую ветку от main. Очередь оправдана только когда две задачи правят одни и те же строки.

## ✅ ПРОВЕРЬ ПЕРЕД РАБОТОЙ (все агенты, не только оркестратор)
Четыре правила про одно: убедись в предпосылке, пока она стоит копейки, а не после сделанной работы.
- **Задача описывает симптом («сломано», «ловил N раз») → сперва `git log -S"<символ>" main -- <файл>` и чтение ТЕКУЩЕГО кода, потом планирование правки.** Постановка задачи стареет: баг мог быть смержен вчера. Замер: воркер получил #114 «report_bug пачкает дерево», проверил первым делом — фикс уже в main три дня как, `pkill` из проекта исчез. Работа не начата, ход не потрачен.
- **В задании указан путь файла → `git check-ignore -v <путь>` ДО начала работы, не на коммите.** Игнор находится за секунду на старте и стоит потерянного хода в конце. Замер: артефакт #134 был написан целиком в `artifacts/`, который полгода как в `.gitignore` — обнаружилось при попытке коммита.
- **Намерил улучшение на фиксированной выборке → сперва померь СОБСТВЕННЫЙ ШУМ метрики (split-half на своей же выборке), потом сравнивай прирост с ним. Шум считай ТОЛЬКО по до-периоду:** пул «до+после» втягивает сам эффект в оценку шума и делает вывод «эффекта нет» неоправданно лёгким (замер #188 — на объединённом пуле правило проходило как сработавшее, на до-периоде не проходит). Прирост меньше медианного шума = нет прироста, а не «слабый эффект». Замер: #135, лучший арм ΔMRR +0.031 при медианном шуме метрики 0.105 — втрое меньше. Внедрили бы шум и потом объясняли, почему поиск стал странный.
- **Собрал список на УДАЛЕНИЕ по снимку состояния → пересчитай его по свежим данным непосредственно перед удалением.** Список устаревает между сбором и исполнением, и устаревает в опасную сторону: в снимке нет того, что появилось после него. Пересчёт делай В ТОЙ ЖЕ команде, что удаляет, и отказывайся от прохода при любом расхождении с ожидаемым множеством и при пустом реестре. Замер: #188 — в снимке было 103 живых агента, через час 107, и по старому списку под удаление попадал файл памяти существующего агента; при исполнении список пересчитался и совпал, но это установила проверка, а не удача.

**Проверка и доказательства (самый частый источник ошибок)**
- Агент «сделал» работу, а её нет → напечатал tool call текстом вместо вызова → проверять артефакт, а не рассказ
- Диагноз/поправка о коде — гипотеза: трассируй до КОНЦА, смотри ВЕТКУ строки, а не первую подтверждающую. Поправка бывает права про дефект и неверна про место (роль терялась не на компакте, а на реконнекте)
- Проверка, дающая одинаковый вывод при успехе и провале, — не проверка (`systemctl show -p OOMScoreAdjust` печатает `infinity` всегда; ground truth — `/proc/<pid>/oom_score_adj`). **Хуже, когда инструмент проверки молча вырождается в «не найдено»: `grep` по испорченному (двоичному) файлу отвечает пустотой, и пустой ответ читается как «строки нет» — то есть врёт в ту же сторону, что и сама ошибка.** Замер: #189, два фоновых прогона писали в один `/tmp`-файл и перемололи его; лечится уникальным путём на каждый прогон и проверкой, что файл вообще текстовый. **Тот же класс — ждать ОТСУТСТВИЯ незавершённой работы как признака завершения: «очередь пуста» одинаково верно при «всё сделано» и при «никто не начинал».** Ждать надо положительный признак выполненного. **И третий вид того же: греп МАРКЕРА без границы слова — подстрока матчится внутри длинных слов и подделывает срабатывание.** Замер: #219 — проверка изоляции клона искала `grep -i 'FACTS'`, поймала «arti**facts**» в девяти старых сообщениях коммитов и объявила 9 родственных файлов на чистом клоне. Здесь она провалилась ГРОМКО, но тот же шаблон так же легко врёт молча в обратную сторону — а гоняли его на каждом клоне за прогон. Маркер грепать якорно: точный путь, граница слова, уникальная строка. Замер: #189 — три воркера были архивированы, `get_all_sessions()` архивных не отдаёт, поток выходил первой строкой, и 767 записей из 3339 за сутки (23%) не обрабатывались вовсе, а проверка на пустую очередь это одобряла
- **Проверяешь живость бэкенда через прокладку (прокси, CDN, reverse proxy, релей) → assert'ь на БАЙТ, который может произвести только бэкенд (редирект авторизации, заголовок приложения, известное тело), а не на «код ответа + латентность»: их подделывает любая прокладка.** Замер 12.08.2026, три раза за одно расследование: `HTTPS_PROXY` дал TCP-коннект «к удалённому IP» за 0.14 мс (физически невозможно); «404 за 287 мс → ориджин жив» оказалось собственной страницей nginx-релея в 162 байта; «200 за 210 мс» — снова ответ релея за себя. **Тесты**
- Тест, читающий ЖИВОЕ состояние (квота, время, нагрузка), — не тест: `test_compact_logs_preamble_as_user_message` был зелёным всё утро и покраснел на 100% 5h-окна, потому что `compact()` отказывает под лимитом, а гард не был замокан

- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap на диске) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов. Зеркально: спящий процесс с гигабайтами не виден в CPU-топе
- `/tmp` на ноуте — **tmpfs, то есть RAM**: 1.6 ГБ «файлов» физически занимали оперативку, за которую в тот же момент дрались агенты. Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корневой раздел забит на 99%, свободно 3.3 ГБ)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx` и НЕ `maps`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт и потянет перекачку
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
