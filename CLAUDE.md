## Что это
Свой оркестратор AI-агентов. Оркестратор управляет воркерами через MCP tools.
Каждый worker = CLI-сессия (Claude или Codex-бэкенд) в отдельном git worktree.
Dashboard = FastAPI + HTMX + SSE.

## Стек
- Python 3.12+, FastAPI, Jinja2, SSE
- `claude-agent-sdk` — SDK для Claude Code sessions
- External stdio MCP server (FastMCP) — tools как отдельный процесс
- SQLite — sessions, logs, inbox, jobs
- `git worktree` — изоляция работников

## Принципы
- Persistent client per session (connect once, `query()` injects mid-turn via stdin)
- External MCP (no in-process deadlocks)
- Workers communicate via HTTP callback, not MCP inject
- Proxy — см. секцию «🔌 ПРОКСИ» ниже (источник истины = .env HTTPS_PROXY)
- Фронтенд (JS/CSS/HTML) обновляется без рестарта; Python-код требует рестарта для загрузки, но это не разрешение на него
- `sudo systemctl` для `orchestra`/`telegram-bot-api` доступен технически, но это НЕ authorization: `restart/stop/start` — только по явной команде текущего юзера; `status` остаётся read-only. Рестарт прерывает active turns
- После разрешённого рестарта SQLite-сессии и idle workers восстанавливаются; активные turns прерываются
- **НЕ обновлять VPS самостоятельно** — git pull, systemctl restart на VPS делает только юзер вручную. Не пушить и не деплоить на VPS без команды
- **Remotes:** `origin` (github.com/DrSeedon/orchestra) — наш публичный, держать актуальным. Всё, что НЕ `origin`, — чужое: не трогать никогда, ни push, ни pull, ни ветки. Список смотреть командой (`git remote -v`), а не по памяти: на 11.08.2026 чужих remote в репозитории нет
- **TG /restart** — команда в TG группе для рестарта Orchestra
- **Воркеры могут общаться друг с другом** через `send_message(to="worker-name")`. Пример: backend воркер добавил endpoint → пишет frontend-opus чтобы тот добавил кнопку. Оркестратор не нужен как посредник для координации между воркерами

## 🔌 ПРОКСИ (единственный источник истины = .env)
- **`.env` `HTTPS_PROXY`/`HTTP_PROXY` = ЕДИНСТВЕННЫЙ источник.** Нет DB, нет hot-switch, нет кеша статусов
- Один прокси везде: systemd EnvironmentFile → `os.environ` → наследуют все (Orchestra + CLI агенты + MCP subprocess). Рассинхрон невозможен by design
- **Сменить прокси:**
  ```
  1. Отредактируй HTTPS_PROXY И HTTP_PROXY в .env (оба!)
  2. sudo systemctl restart orchestra
  ```
  Всё. Живой прокси найти: `bash scripts/check-proxies.sh` (диагностика — покажет живой и впишет в .env; рестарт — руками)
- **Дашборд:** только индикатор активного (из `os.environ`, read-only) + кнопка Check (проверить живость on-demand). Кнопки «выбрать/активировать» НЕТ — переключение только через .env
- `proxy_manager.py` — read-only: `list_proxies()` + `check_all()`. НЕ мутирует env, НЕ пишет в DB
- SSH-туннели (`ssh_tunnel.py`) поднимают локальные порты к VPS. `HTTPS_PROXY` указывает на нужный порт. Мёртвые VPS не спамят реконнектом (health-gate + backoff)
- **TG bot** (telegram-bot-api) — через proxychains (`/etc/proxychains4.conf`), C++ бинарник не читает .env. Обычно socks5 Contabo (12345). **ВАЖНО**: при смене прокси обновлять ОБА файла: `/etc/proxychains4.conf` И `~/.proxychains/proxychains.conf` — user-config имеет приоритет

## AI Efficiency (design principle)
Orchestra automates humans — but the AI agents themselves must be optimized too.
Every feature should minimize agent overhead: fewer tool calls, less context waste, less repetition.

**Design for AI, not humans:**
- If an agent does the same 3 tool calls every time → automate into 1 MCP tool or server-side logic
- If agents waste context reading the same files → pre-inject via system prompt or worktree setup
- If a pattern causes context rot (agent re-reads, re-explains, loops) → fix the root cause, don't add more instructions
- Measure cost-per-task, not just "does it work". $2 task done in 3 tool calls > $8 task done in 30 tool calls
- Prompt engineering = agent optimization. Shorter, clearer prompts = fewer confused retries = less $ burned
- Every new feature ask: "does this reduce total agent tool calls/tokens across typical workflows?"

**Anti-patterns to avoid:**
- Agent reads entire file when it needs 5 lines → give it grep/line-range hints
- Agent asks orchestrator for permission it could decide itself → expand decision tree
- Agent retries failed command 5 times → fail fast, report, let orchestrator decide
- Two agents duplicate work because they don't know about each other → worker-to-worker communication
- Agent spends 20 tool calls on setup that could be pre-configured → inject at spawn time

## Agent Determinism (design principle)
Агенты должны быть ПРЕДСКАЗУЕМЫМИ. Один путь, один маршрут, минимум свободы.

**Правила проектирования промптов и тулов:**
- **1 задача = 1 workflow.** Не давать агенту 3 способа сделать одно и то же — он выберет худший. Один оптимальный маршрут, жёстко прописанный
- **Минимум тулов.** Каждый лишний тул = развилка где агент может свернуть не туда. Давать ТОЛЬКО те тулы которые нужны для конкретной роли
- **Decision tree > свобода.** Вместо "реши сам" — чёткое дерево решений: если X → делай A, если Y → делай B. Агент не должен "думать" о стратегии
- **Fail loud, не fail creative.** Ошибку маршрутизировать по контракту BUGS ниже; не обходить молча. СТОП — только когда безопасно продолжить нельзя
- **Нет импровизации в проде.** Агент следует промпту буквально. Если промпт не покрывает ситуацию — спросить оркестратора, а не выдумывать

**При разработке новых ролей/промптов:**
- Тестировать: "может ли агент пойти не тем путём?" Если да — сузить промпт
- Каждый edge case в промпте = потенциальная развилка. Лучше 3 конкретных правила чем 1 "умное" обобщение
- Логировать когда агент отклоняется от ожидаемого пути → добавлять guardrails

## Баг-репорты от агентов (инбокс, НЕ BUGS.md)
- `report_bug(title, description)` — только сбои платформы Orchestra (MCP, сессии, worktree, TG, dashboard, model routing); писать сразу, даже если найден обход
- Баг кода текущего проекта → `docs/tasks/<id>/` + сообщение оркестратору, НЕ `report_bug`
- **Репорты живут вне рабочего дерева** — поэтому не пачкают checkout и не блокируют мержи. Трекнутый `BUGS.md` — только указатель, туда никто не пишет с 01.08.2026
- **При старте корневой Orchestra-сессии** — чекни инбокс: `GET /api/report_bug` (или баннер «🐛 Новые bug reports» на дашборде). Worker получает нужный контекст через задачу/промпт
- **Чистка**: разобранный репорт — удалить его файл из `records/` в инбоксе (путь и условия — в `BUGS.md`). TODO.md — done items удалять, держать компактным

## ⚡ PROCESS RULES (оркестратор)
- **КРАТКОСТЬ — не лей воду.** Юзер видит логи tool-вызовов. НЕ пересказывай что сделал ("Спавнил X", "Проверю что закоммитилось") — он это видит. НЕ дублируй статус по 2-3 раза за ответ. НЕ объясняй очевидное ("безобидно, всё чисто").
- **Сделал → одна фраза** (что + результат). Панчлайны/таблицы/резюме — ТОЛЬКО для реального итога или решения, НЕ на рутину (спавн, merge, "жду воркера", "как вернётся покажу").
- **Не отчитывайся о промежуточном** — "жду Codex", "воркер работает" = шум. Юзер узнает из авто-репортов/логов. Пиши когда есть РЕЗУЛЬТАТ или нужно РЕШЕНИЕ юзера.
- Панчлайн-аналогия из глобального промпта — на ИТОГ сессии/крупное решение, не на каждый чих.
- **ВСЕ воркеры ВСЕХ проектов — МОЯ ответственность.** Воркеры в kesha-tg-bot, polus, seedon и любом другом проекте управляются Orchestra. Баги воркеров (status-desync, зацикливание, idle-while-running) — разбираю Я, не делегирую проектному оркестратору. Проектный оркестратор (kesha-tg-bot, polus-orchestrator) — это разработчик проекта, НЕ менеджер воркеров.
- 📝 RULE: Когда пользователь говорит «все воркеры» без явного списка других проектов → действовать только в своём контуре и разбирать чужие логи своим read-only воркером, не рассылать распоряжения чужим оркестраторам.
- **НЕ убивать full-cycle воркеров после merge.** Full-cycle на гейте ("awaiting approval to plan/implement") = ЖДЁТ продолжения. merge → оставить idle, НЕ kill. Если воркер написал "STOP на гейте" — он ЖИВОЙ и ждёт следующую фазу. Условия самого kill'а живут ТОЛЬКО в модуле `worker-lifecycle` (`lifecycle=one-shot` + финальный DONE + успешный merge + idle + чистый WIP) и здесь намеренно не повторяются. Замер: #175 — эта строка требовала «kill только одноразовых» по ИМЕНИ (`impl-*`, `fix-*`), модуль — по маркеру `lifecycle`; агент выполнил более точное правило и формально нарушил `CLAUDE.md`.
- **Задал воркеру `owned_dirs` → включи туда и `docs/workers/<имя>.md`.** Иначе обязательная проверка личной памяти упирается в границу владения: воркер либо теряет урок, либо нарушает границу, чтобы его записать. Замер: 11.08.2026 за один день четверо (#175, #176, #177, #186) уперлись в это, трое молча потеряли урок, один написал и предупредил.
- **Задача появилась → сразу в работу; параллельность — средство, а не цель.** Спавн оправдан независимостью работы, а не наличием свободной модели. Работу, которую тянет один воркер, не делить на двоих — но по причине связности, а НЕ из-за цены спавна. **Прежняя оценка «≈$4 за холодный старт» была завышена в 6–13 раз и отменена (#178, 11.08.2026): холодный старт = 49–62K токенов = $0.31–0.62; $4 — это стоимость всей короткой сессии, а не входа в неё.** Настоящий драйвер расхода — round-trip'ы: ≈$0.13 на tool-вызов, показатель 1.05, R=0.935, и 68% суммы — `cache_read`, то есть перечитывание контекста на каждом вызове. Из этого следует обратное прежнему: бояться надо длинных болтливых сессий, а не лишнего воркера. Но независимую задачу НЕ ставить в очередь и не ждать освобождения: один файл на двоих — не повод откладывать, развести по непересекающимся участкам, перед мержем `check_conflict`, при конфликте — cherry-pick на свежую ветку от main. Очередь оправдана только когда две задачи правят одни и те же строки.

## ✅ ПРОВЕРЬ ПЕРЕД РАБОТОЙ (все агенты, не только оркестратор)
Четыре правила про одно: убедись в предпосылке, пока она стоит копейки, а не после сделанной работы.
- **Задача описывает симптом («сломано», «ловил N раз») → сперва `git log -S"<символ>" main -- <файл>` и чтение ТЕКУЩЕГО кода, потом планирование правки.** Постановка задачи стареет: баг мог быть смержен вчера. Замер: воркер получил #114 «report_bug пачкает дерево», проверил первым делом — фикс уже в main три дня как, `pkill` из проекта исчез. Работа не начата, ход не потрачен.
- **В задании указан путь файла → `git check-ignore -v <путь>` ДО начала работы, не на коммите.** Игнор находится за секунду на старте и стоит потерянного хода в конце. Замер: артефакт #134 был написан целиком в `artifacts/`, который полгода как в `.gitignore` — обнаружилось при попытке коммита.
- **Намерил улучшение на фиксированной выборке → сперва померь СОБСТВЕННЫЙ ШУМ метрики (split-half на своей же выборке), потом сравнивай прирост с ним. Шум считай ТОЛЬКО по до-периоду:** пул «до+после» втягивает сам эффект в оценку шума и делает вывод «эффекта нет» неоправданно лёгким (замер #188 — на объединённом пуле правило проходило как сработавшее, на до-периоде не проходит). Прирост меньше медианного шума = нет прироста, а не «слабый эффект». Замер: #135, лучший арм ΔMRR +0.031 при медианном шуме метрики 0.105 — втрое меньше. Внедрили бы шум и потом объясняли, почему поиск стал странный.
- **Собрал список на УДАЛЕНИЕ по снимку состояния → пересчитай его по свежим данным непосредственно перед удалением.** Список устаревает между сбором и исполнением, и устаревает в опасную сторону: в снимке нет того, что появилось после него. Пересчёт делай В ТОЙ ЖЕ команде, что удаляет, и отказывайся от прохода при любом расхождении с ожидаемым множеством и при пустом реестре. Замер: #188 — в снимке было 103 живых агента, через час 107, и по старому списку под удаление попадал файл памяти существующего агента; при исполнении список пересчитался и совпал, но это установила проверка, а не удача.
- **Считаешь отношение или скорость из счётчика с ОКРУГЛЁННЫМИ значениями (целые проценты, округлённые метрики) → проверь, не отбираешь ли интервалы по условию на ту же величину, которую считаешь.** Отбор «беру интервалы, где числитель вырос» завышает результат тем сильнее, чем слабее сигнал; мерь средний знаменатель в отброшенных против оставшихся. Замер: #186 — завышение 60–150%, по-разному в разных сегментах, поймано только внешним ревью. **Проверяешь ГИПОТЕЗУ против такого счётчика → строй фальсификатор на отрезке ПОСЛЕ наблюдённого перехода, а не на суммарной дельте за прогон:** начальная дробь внутри бакета неизвестна, поэтому суммарная дельта совместима с обеими гипотезами, а отрезок после шага начинается от известной границы. Замер: #199 — один шаг счётчика за 15.1 млн токенов не различал гипотезы вовсе, а те же данные от момента шага (8.7 млн токенов без движения) отвергли одну однозначно.
- **Строишь стенд, где агент НЕ ДОЛЖЕН знать ответ (ретроспективный реплей, слепой прогон, «реши задачу, которая уже решена») → поднимай его вне worktree основного репозитория, клоном с `--no-local`, и докажи недостижимость ответа, а не предполагай её.** `spawn_worker` в worktree того же репо даёт ОБЩИЙ object store: смерженная реализация физически доступна воркеру, даже если её нет в его ветке и в рабочем дереве. Дыра невидима в результатах — прогон выглядит успешным и просто оказывается завышенным. Замер: #210, первая пара прогонов потеряна целиком, улика в `docs/tasks/210/contaminated-run-evidence.txt`.
- **Добираешь прогоны в ячейку замера ПОСЛЕ того, как раскрыл ключ слепого судейства → помечай их exploratory навсегда и считай отдельно, а не доливай в подтверждающую выборку.** Замер: #184 — автор сам поймал за собой два таких повтора и разделил их; никто, кроме него, этого бы не увидел, а выводы держались бы на выборке, куда доливали уже зная ответ.
- **Эффект правки промпта/правила померен на фиксированном наборе заданий → прогони 1-2 задания из ДАЛЁКОЙ предметной области, прежде чем объявлять эффект.** Однородный набор мерит не правку, а тему. Замер: #119, на пяти технических заданиях правка выглядела как «палитра стала разнообразной», а на первом же бытовом старая версия дала то же улучшение сама — часть прироста была свойством выборки.
- **Числа в сравнительной таблице отчёта («у них N, у нас M») берутся из выполненной команды, а не из впечатления от чтения.** Замер: #119, самопроверка вскрыла 3 ошибки в 3 проверенных строках, и все три сдвигали картину в сторону вывода автора. **То же и про ОБРАЗЕЦ «как это будет выглядеть»: он собирается одним прогоном, все строки одного происхождения.** Строка из вывода упавшего теста, вставленная в образец рядом с настоящими, читается как поведение прода и уезжает пользователю — замер: #189, в образце оказалось `0 действий · $0.01` из тестовой фикстуры на двух строках без единого тула.

Замер: #167 — правка `_log` попала в близнеца `_submit_db_write` выше по файлу; маркер `grep -c` показал 1 и не спас, потому что искомая строка есть в обоих методах.
- **Мутируешь ОДИН файл, чтобы доказать, что проверка ловит пропажу → прогони ещё и СОСТАВНУЮ мутацию «пропало здесь И появилось в общем слое» (base, шаблон, родительский конфиг).** Одиночная мутация зелёная у обеих проверок — и у честной, и у той, что просто ищет строку в итоговой сборке, — поэтому она не отличает «ловит пропажу инструкции» от «ловит отсутствие строки где угодно». - **Мутационная проверка НЕ покраснела на функции с несколькими признаками или fallback → добавь случай, где остальные признаки помочь не могут, и повтори мутацию.** Зелёный прогон означает лишь, что запасная ветка подменила основную. Замер за один день у двух разных агентов: мутация по `tg_bridge` прошла незамеченной (тест держался на fallback), в #151 две мутации пережили тесты, стоявшие не на том seam. **Тест, написанный ПОД конкретную находку, сам по себе её не проверяет — прогоняй мутацию и по нему.** Замер: #186 — тест написан ровно под подсказанную ревьюером мутацию `ORDER BY id DESC`, и мутация всё равно выжила: на фикстуре пара `60 → 0` с одинаковым `ts` даёт один ответ в обе стороны. Понадобилась фикстура, которая порядок действительно различает. Три способа получить зелёный прогон на дефектной реализации, все замерены в #186 за одну задачу: симметричная фикстура (одинакова в обе стороны), одинаковый формат на обеих сторонах сравнения (ломается только СМЕСЬ форматов), гонка через `asyncio.gather` (исход решает планировщик). Плюс: **тест, который при регрессии ЗАВИСАЕТ, а не падает, — дефектный**, такой однажды заскипают.
- **Тест приколочен к дословному argv / тексту кода / имени вызова → сперва `git log -S"<строка>"` и вопрос «изменилось ПОВЕДЕНИЕ или только ФОРМА?».** Форма → переписать тест на поведенческий, НЕ подгонять строку: подгонка дешевле и оставляет тест хрупким до следующего рефакторинга. Замер: #154, тест требовал дословное `AbortSignal.timeout(30000)`, а #58 перевёл бюджет в параметр — поведение сохранено, прод-код чинить было нечего.

И мерь то, что защищает, а не то, что исполняется: идиому взяли 20 прогонов из 20, а работу потеряла четверть — «соблюдение 100%, защита 75%».
- **Жалоба юзера на скорость → сперва померь ДЕЙСТВИЕ из его дословной формулировки, и только потом загрузку страницы.** Замер: сутки чинили первую загрузку, пока жалобы были «переключаю воркера и долго тупит» и «при переключении проектов лагают»; переключение проекта стоит 1205 мс главного потока и 883 КБ против 1590 мс у всей загрузки — дороже всего, что мы правили, и не мерилось ни разу (#57).
- **Цикл умеет ПЕРЕИГРЫВАТЬ вход после сбоя (откат курсора, ретрай, at-least-once очередь) → флаг «уже обработано» гасить ПОСЛЕ фактического сайд-эффекта, не в момент обнаружения события; тестом закрывать оба направления — потерю и дубль.** Гашение при обнаружении теряет эффект именно на повторе, то есть под нагрузкой, когда он нужнее всего. Замер: #158, тег юзера гасился на строке `turn ended`, а `_TgDeliveryOverloaded` откатывал курсор и переигрывал пачку — на повторе флаг уже false, уведомление молча исчезало в длинных ходах.
- **Задача обосновывает работу словами «такого ещё нет» / «инструкции нет» → до планирования `grep -ril "<тема>" docs/ ~/.claude/skills/` и проверка СУЩЕСТВОВАНИЯ каждого артефакта, на который велено сослаться.** Постановку пишет тот, кто сам мог не проверить. Замер: #159 — инструкция на 564 строки лежала в `docs/`, а 2 из 3 скиллов, на которые велено ссылаться, не существовали; обе проверки стоили одной команды, без них вышел бы расходящийся дубль и две ссылки в пустоту.

Замер: #165 — один дословный прогон разом подтвердил три утверждения текста и до того поймал сниппет, начинавшийся с `-d` без `curl`; в тот же день скилл утверждал «историю диалога не везём», пока `copy_transcript` её вёз.

## 🪤 Грабли (то, на чём уже спотыкались)

Формат: симптом → причина → что делать. Хроника — в `docs/archive/sessions/`.
Разделы идут в порядке, в котором на них напарываются: сначала то, что бьёт каждый день
(проверка чужой работы, воркеры), в конце — редкое (деплой, железо).

**Проверка и доказательства (самый частый источник ошибок)**
- Агент «сделал» работу, а её нет → напечатал tool call текстом вместо вызова → проверять артефакт, а не рассказ
- Диагноз/поправка о коде — гипотеза: трассируй до КОНЦА, смотри ВЕТКУ строки, а не первую подтверждающую. Поправка бывает права про дефект и неверна про место (роль терялась не на компакте, а на реконнекте)
- Проверка, дающая одинаковый вывод при успехе и провале, — не проверка (`systemctl show -p OOMScoreAdjust` печатает `infinity` всегда; ground truth — `/proc/<pid>/oom_score_adj`). **Хуже, когда инструмент проверки молча вырождается в «не найдено»: `grep` по испорченному (двоичному) файлу отвечает пустотой, и пустой ответ читается как «строки нет» — то есть врёт в ту же сторону, что и сама ошибка.** Замер: #189, два фоновых прогона писали в один `/tmp`-файл и перемололи его; лечится уникальным путём на каждый прогон и проверкой, что файл вообще текстовый. **Тот же класс — ждать ОТСУТСТВИЯ незавершённой работы как признака завершения: «очередь пуста» одинаково верно при «всё сделано» и при «никто не начинал».** Ждать надо положительный признак выполненного. Замер: #189 — три воркера были архивированы, `get_all_sessions()` архивных не отдаёт, поток выходил первой строкой, и 767 записей из 3339 за сутки (23%) не обрабатывались вовсе, а проверка на пустую очередь это одобряла
- Находка/чужой красный тест протухают между пакетами → сверяй с ТЕКУЩИМ файлом И с main, а не со своей веткой: `git stash` докажет «красное не моё», но не покажет, что фикс уже есть в main (замер: 2 из 12). **Зеркальная ошибка (#189): проверять «текущий код» в ГЛАВНОМ чекауте, работая в ветке.** Ветка отрезана от своей базы и свежих колонок/функций из main не содержит — «чинить нечего» оказалось верным про main и ложным про своё дерево. Сверяться надо с ОБОИМИ и явно говорить, про какое дерево утверждение
- Эвал/судья назначил фикс → открой СЫРЫЕ флагнутые выходы и фикстуру, прежде чем чинить: находка может быть артефактом стенда (замер: 3 из 5 флагов ложные — судья физически не видел живой Read)
- **Задача называет N точек, куда поставить проверку → сперва грепни ВСЕХ вызывающих общий лист и сверь со списком, а не гейти названные точки.** Замер: #154, три названные точки оказались 11 реальными вызовами `manager.send`, и среди необойдённых был вход из Telegram; заодно выяснилось, что гейтить общий лист нельзя — по одной из веток идёт доставка `[Background job FAILED]`, и блокировка съела бы уведомление
- **Вывел признак «данных не было» из ФОРМЫ записи и собрался чистить по нему историю → сперва посчитай ложные срабатывания на строках, где данные ТОЧНО были.** Замер: #150, признак «пустой `resets_at` + нулевой процент» пометил бы 161 честную строку (так выглядит настоящий ответ про только что сброшенное окно) против 78 настоящих подделок — снёс бы вдвое больше правды, чем лжи
- **«Исполняется ли этот тест вообще» проверяется мутацией его ПРЕДУСЛОВИЯ (логин, фикстура, доступность сервера), а не ассерта.** Сломанный ассерт доказывает лишь, что строка сравнения жива; сломанное предусловие показывает, кто на самом деле входил в тело. Замер: #145, 16 тестов молча скипались на включённом auth и печатались зелёными — после починки мутация неверного пароля покраснила ровно те же 16, один в один
- **Добавляешь в прод переменную окружения или флаг, гейтящий СУЩЕСТВУЮЩЕЕ поведение → сперва запинь значение фикстурой в тестах, которые ходят по загейченному пути, и только потом пиши тесты на сам флаг.** Симптом ловится одной командой: `grep -rn "<VAR>" tests/` даёт совпадения только в тестах самого флага. Замер: #122 добавил `AUTO_COMPACT_ENABLED` и 74 строки тестов на него, три старых теста стали читать `.env` машины — в main на боевой конфигурации `3 failed, 148 passed`
- **Посчитал агрегат по истории (сумма расхода, число событий, суммарный процент) → сперва сверь его с ФИЗИЧЕСКИМ потолком периода, а не с ожиданием.** Число, которого не может быть, вскрывает грязные строки за одну команду. Замер: #162, сумма недельного расхода дала 6.2 лимита за 4.7 недели — невозможно; так нашлись 70 строк с фальшивыми нулями, на которых оценка курса ошибалась на 40%

Замер: #140, греп насчитал 81 вхождение против 6 настоящих — регулярка ловила строку внутри чужих полей

Тест дешёвый из-за асимметрии: один случай непослушания опровергает «останавливает» окончательно, один случай послушания не доказывает ничего. Рантайм инжектит инструкцию, а исполняет её агент.

Замер: #175 — `cache_read <= input` верно в 330/330 codex-строк и лишь в 36/1402 claude-строк (у Anthropic cached НЕ входит в `input_tokens`, у OpenAI входит); из-за пропущенной проверки отчёт заявил «Codex втрое хуже держит контекст, 48% против 97%», после пересчёта — 93.5% против 97.3%, и рекомендация развернулась. **То же и при ДЕЛЕНИИ одной метрики на другую: сперва проверь, порождены ли числитель и знаменатель одним счётчиком — одинаковая единица измерения этого не гарантирует.** Замер: #189 — «63% косметики выброшено» получилось делением счётчика очереди на длину журнала; счётчик суммировал уже склеенные события, то есть совокупности разные, и процент пришлось снять целиком.

- `asyncio.wait_for(..., timeout=0.1)` в тестах = флак по wall-clock → на загруженной машине падал случайный тест в `tests/test_tg_bridge.py`, в одиночку зелёный 6/6. Таймаут против зависания не должен подрабатывать перф-ассертом. Массовый случай (21 место) вычищен, на 11.08.2026 осталось 1 — правило держим, чтобы не завелось снова
- Тест «падает в фулле, зелёный изолированно» → не спеши звать order-dependence: общий конфиг мог измениться параллельно (`can_spawn: []` из чужой ветки дал 409 в обоих). Сверь commit обоих прогонов
- Переносишь спавн/IO на новую функцию → грепни тесты на СТАРОЕ имя seam и перенаправь моки. Переставший перехватывать monkeypatch не падает, а молча пускает тест в реальную систему (замер: сьют 5× за прогон запускал НАСТОЯЩИЙ `sh -c`). Зелёный тест проверяй мутацией
- Тест падает у тебя, но не на CI (или наоборот) → сравнивай `env` обоих окружений РАНЬШЕ файлов репозитория. `EnvironmentFile` в systemd-юните кладёт переменные в процесс агента, и «в чекауте нет `.env`» этого не отменяет: чистый клон main без `.env` давал те же 401, потому что `DASHBOARD_*` пришли из юнита, а `load_dotenv()` в lifespan затянул файл обратно
- Тест приколочен к дословному argv/тексту ошибки → ломается от смены ФОРМЫ вызова, а не поведения. Печатай фактическую последовательность вызовов, прежде чем править матчер (замер: 4 таких за день, в т.ч. страж, ронявший третий зонд из-за перехода на `--quiet`)
- Тест меряет ВЕС или РАЗМЕР → проверяй мутацией на фикстуре, которая сжимается как живые данные: `"строка " * 3000` жмётся в 293 раза против 5.1 у настоящего текста и делает такой тест зелёным при сломанном коде (#65)
- **Тест сверяет ТЕКСТ (промпт, шаблон, конфиг) и выводит проверяемые куски из самого же источника → он слеп к переносу строки внутри проверяемой фразы.** Клаузы, извлечённые из уже переформатированного файла, находятся в собранном результате как ни в чём не бывало; правило при этом молча потеряно. Страхует только РУЧНОЙ якорь на цельную фразу. Замер: #210 — перенос сработал дважды за одну реализацию (`already green | at review time`, `never | weaken it to fit`), оба раза ловил якорный тест, ни разу — вычитка глазами
- Браузерную проверку начинай с ожидания символа, которого НЕТ в main → иначе она зеленеет на старом коде. Замер: шесть скриптов проверяли main, дыра жила сутки
- Проверка агрегирует собранное на лету (`all(...)`/`any(...)` по списку из DOM, файлов, логов) → первым делом гард на непустоту списка: пустой сбор печатает зелёное, ничего не проверив. **Тест доказывает, что текст НЕ протёк в чужой промпт/артефакт → якоря извлекай из файла-ИСТОЧНИКА (все его пункты), а не выписывай 2-3 фразы руками:** ручные якоря остаются зелёными на копии соседнего пункта того же блока. Замер: #203 — первая версия теста была зелёной на контрпримере Codex (копия пункта про Opus без тегов)

**Git, файлы, деплой**
- merge воркера не проходит на ровном месте → инжектированные `.claude/skills/` дёргают дерево → исключать через git common-dir `info/exclude`, не `.gitignore`. НО `info/exclude` бессилен против ОТСЛЕЖИВАЕМЫХ файлов — правила игнорирования не применяются к индексу: в репо, который версионирует свои `.claude/skills/*/SKILL.md` (seedon, 14 файлов), инъекция = модификация трекнутого файла, дерево грязное навсегда. Правило общее: платформа НИКОГДА не пишет поверх файла, который репозиторий трекает (`workspace.tracked_paths`) — как и зеркало `AGENTS.md`. Untracked-копии (`.env`) при спавне сами попадают в `info/exclude`
- В `.gitignore` строка `workers/` глотает и `docs/workers/` → нужен `!docs/workers/` (строки 9-10, не «почистить»): иначе воркер молча теряет личную память или делает `git add -f`
- SHA в инструкции отката: `--is-ancestor` доказывает достижимость, но НЕ откатываемость → прогони `git revert --no-commit` на скретче + `--abort`. В hot-path доке лежал до-squash SHA, а рабочий давал конфликт
- Документируешь период → два прохода: `git log main` по датам (НЕ своя ветка, НЕ присланный список — моя цифра «93 коммита» потеряла 7) + `docs/tasks/<id>/report.md` по каждому id: счётчик не покажет ОТОЗВАННЫЕ и отрицательные результаты, а они и есть суть
- Цена переноса репо = `du -sh .git` + `ls-files` + `remote -v`, НЕ `du -sh` каталога: untracked даёт 10-20× завышение (Parsing: 91 ГБ каталог, 7.5 МБ история). `remote -v` ловит репы без удалёнки
- Деплой в каталог с `User=` в юните → сперва `find <dir> ! -user <юзер>`: чужие владельцы не мешают чтению и запуску, падает только ЗАПИСЬ в `.git`, посреди деплоя. `chown -R` со снимком прав
- Надо, чтобы агент ЗАБЫЛ устаревшее → `UPDATE sessions SET session_id=''` при ОСТАНОВЛЕННОМ сервисе, НЕ `compact_worker`: компакт просит сессию законспектировать саму себя, устаревшие убеждения переезжают без исходника. Инструмент против симптома — сперва прочти, что он делает с ПРИЧИНОЙ
- Правишь файл, который в проекте СОБИРАЕТСЯ скриптом (CHANGELOG, зеркала, оглавления) → сперва `git log --oneline -3 -- <файл>` и грепни `scripts/` на его имя: владелец файла мог смениться посреди твоей задачи, и узнаешь ты об этом конфликтом мержа с уже сделанной работой
- Правишь фронт в worktree → на живом :8888 его НЕ проверить: статика идёт из основного чекаута, симптом — «функции просто нет». Проверять подменой файла через Playwright `page.route`, а факт применения правки — `typeof <новый символ>` в рантайме

**Чужая машина (ноут юзера — рабочий, не стенд)**
- Тяжёлые прогоны только последовательно и под потолком памяти: `systemd-run --user --scope -p MemoryMax=2G`, одна модель за раз с выгрузкой, `nice -n 15`, не больше 2-3 параллельных. `nice` НЕ защищает от вытеснения по ПАМЯТИ — дважды за сутки выдавили чужое обучение сети (RSS рос 3.5→4.2 ГиБ), а ONNX-бенчмарки грели CPU до 93°C и уронили чужой preflight. Потолок — в ПОСТАНОВКУ задачи, не в напоминание вдогонку
- Гейт свободной памяти считать по `MemAvailable` из `/proc/meminfo`, НЕ по `free`: при page cache они расходятся в 2-3 раза
- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap на диске) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов. Зеркально: спящий процесс с гигабайтами не виден в CPU-топе
- `/tmp` на ноуте — **tmpfs, то есть RAM**: 1.6 ГБ «файлов» физически занимали оперативку, за которую в тот же момент дрались агенты. Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корневой раздел забит на 99%, свободно 3.3 ГБ)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx` и НЕ `maps`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт и потянет перекачку
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
