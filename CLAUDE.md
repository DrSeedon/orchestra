## Что это
Свой оркестратор AI-агентов: оркестратор управляет воркерами через MCP tools, каждый worker = CLI-сессия (Claude / Codex / Grok) в отдельном git worktree. Dashboard = FastAPI + HTMX + SSE.
**Стек:** Python 3.12+, FastAPI, Jinja2, SSE; `claude-agent-sdk`; external stdio MCP server (FastMCP) как отдельный процесс; SQLite (sessions, logs, inbox, jobs); `git worktree` для изоляции.

## Архитектура
```
Оркестратор (FastAPI :8888)
├── Dashboard (HTMX + SSE) — http://localhost:8888, auth: cookie session (login/password из .env)
├── SQLite — sessions, logs, inbox, jobs, tasks, payments
├── External MCP Server (app/mcp_stdio.py) — tools для CLI; auth по INTERNAL_TOKEN
├── Auth middleware — cookie OR internal token
├── Session Manager — spawn/stop/archive/compact
├── Task Manager (app/tm.py) — CRUD, priorities, payments, YouGile sync
├── TG Bridge (app/tg_bridge.py) — bidirectional, topics, voice transcription
└── Workers — CLI-сессия (Claude/Codex/Grok) + свой git worktree + MCP (Orchestra + scope .mcp.json)
```
Deployed: localhost:8888 (dev) + VPS клиента (auth enabled)

## Принципы
- Persistent client per session (connect once, `query()` injects mid-turn via stdin)
- External MCP (no in-process deadlocks); workers communicate via HTTP callback, not MCP inject
- Воркеры общаются друг с другом напрямую через `send_message(to="worker-name")` — оркестратор не нужен как посредник
- Фронтенд (JS/CSS/HTML) обновляется без рестарта; Python-код требует рестарта для загрузки, но это не разрешение на него
- `sudo systemctl` для `orchestra`/`telegram-bot-api` доступен технически, но это НЕ authorization: `restart/stop/start` — только по явной команде текущего юзера, `status` read-only. Рестарт прерывает active turns; после него SQLite-сессии и idle workers восстанавливаются. **Настоящая цена рестарта — не 2.38 убитого хода, а задержка выката: медиана 3.3 ч, p75 22.9 ч (#220)**
- **НЕ обновлять VPS самостоятельно** — git pull и рестарт на VPS делает только юзер вручную
- **Remotes:** `origin` (github.com/DrSeedon/orchestra) — наш публичный, держать актуальным. Всё, что НЕ `origin`, — чужое: не трогать никогда. Список смотреть командой `git remote -v`, а не по памяти
- **TG /restart** — команда в TG группе для рестарта Orchestra

## 🔌 ПРОКСИ (владелец = отдельный AI Proxy Manager)
- **Единственный владелец маршрута и SSH-туннелей — `ai-proxy-manager.service`.** Ранбук: `~/.claude/docs/ai-proxy-manager.md`; UI: `http://127.0.0.1:18109`; стабильный gateway: `http://127.0.0.1:12339`

- Default route — Contabo. Автоматический failover и балансировка по IP запрещены; switch вручную проверяет ChatGPT backend и рвёт активные соединения
- `PROXY_LIST`, `scripts/check-proxies.sh`, `proxy_manager.py` и старая панель Orchestra больше не являются источниками истины и не должны менять маршрут
- Положительный health-check = JSON от ChatGPT backend. `403 text/html` от Cloudflare означает только доступность CDN и не считается рабочим AI-маршрутом
- **TG bot** (telegram-bot-api) — через proxychains, C++ бинарник не читает `.env`. При смене прокси обновлять ОБА файла: `/etc/proxychains4.conf` И `~/.proxychains/proxychains.conf` (user-config имеет приоритет)

## AI Efficiency + Agent Determinism (design principles)
Orchestra автоматизирует людей — но и самих агентов надо оптимизировать. Мерить цену задачи, а не «работает ли»: $2 за 3 вызова > $8 за 30.
- Одни и те же 3 вызова каждый раз → один MCP-тул или серверная логика; агенты перечитывают одни файлы → инжектить при спавне; паттерн вызывает context rot → чинить причину, а не добавлять инструкции
- Антипаттерны: читает файл целиком ради 5 строк (дать grep/диапазон); спрашивает разрешение, которое мог решить сам; ретраит 5 раз вместо fail fast; два агента дублируют работу (worker-to-worker); 20 вызовов на setup, который можно преднастроить
- **Детерминизм: 1 задача = 1 workflow** (три способа → агент выберет худший). Минимум тулов: лишний тул = развилка. Decision tree вместо «реши сам». Fail loud, не fail creative. Промпт не покрывает ситуацию → спросить оркестратора, а не выдумывать. Проектируя роль, спрашивать «может ли агент пойти не тем путём?» — да → сузить

## ⚡ PROCESS RULES (оркестратор)
- **Краткость, формат отчётов и «не отчитываться о промежуточном» живут в `pipelines/default/prompts/base.md` (`<communication-style>`) и `roles/orchestrator.md`** — там владелец, здесь копии намеренно нет.
- **ВСЕ воркеры ВСЕХ проектов — МОЯ ответственность.** Воркеры в kesha-tg-bot, polus, seedon и любом другом проекте управляются Orchestra. Баги воркеров (status-desync, зацикливание, idle-while-running) разбираю Я. Проектный оркестратор — это разработчик проекта, НЕ менеджер воркеров.
- 📝 RULE: Когда пользователь говорит «все воркеры» без явного списка других проектов → действовать только в своём контуре и разбирать чужие логи своим read-only воркером, не рассылать распоряжения чужим оркестраторам.
- **НЕ убивать full-cycle воркеров после merge.** Full-cycle на гейте («awaiting approval to plan/implement») = ЖДЁТ продолжения → оставить idle. Условия самого kill'а живут ТОЛЬКО в модуле `worker-lifecycle` (`lifecycle=one-shot` + финальный DONE + успешный merge + idle + чистый WIP) и здесь намеренно не повторяются. Замер: #175 — прежняя формулировка по ИМЕНИ (`impl-*`, `fix-*`) противоречила модулю, агент выполнил более точное правило и формально нарушил `CLAUDE.md`.
- **Задал воркеру `owned_dirs` → включи туда и `docs/workers/<имя>.md`.** Иначе обязательная проверка личной памяти упирается в границу владения. Замер: 11.08 за день четверо (#175, #176, #177, #186) уперлись в это, трое молча потеряли урок.
- **Задача появилась → сперва класс по `<approval-gate>` (модуль `orchestration`), а не сразу спавн.** Реализация начинается по слову юзера; сам себе работу оркестратор не заводит. Прежняя формулировка «появилась → сразу в работу» отменена юзером 19.08 — он платит за каждого воркера и требует быть в курсе каждой правки.
- **АПРУВ ПОЛУЧЕН → параллельность как средство, а не цель.** Спавн оправдан независимостью работы, а не наличием свободной модели. **Оценка «≈$4 за холодный старт» ОТМЕНЕНА как завышенная в 6–13 раз (#178): холодный старт = 49–62K токенов = $0.31–0.62.** Настоящий драйвер расхода — round-trip'ы: ≈$0.13 на tool-вызов, R=0.935, и 68% суммы — `cache_read`. Бояться надо длинных болтливых сессий, а не лишнего воркера. Апрувленную независимую задачу НЕ ставить в очередь: один файл на двоих — развести по непересекающимся участкам, перед мержем `check_conflict`, при конфликте cherry-pick на свежую ветку от main. Очередь оправдана только когда две задачи правят одни и те же строки.

## ✅ ПРОВЕРЬ ПЕРЕД РАБОТОЙ (все агенты, не только оркестратор)
Одно про всё: убедись в предпосылке, пока она стоит копейки, а не после сделанной работы.
Доказательство каждого пункта — `docs/kb/evidence-methods.md`.
- **Задача описывает симптом («сломано», «ловил N раз») → сперва `git log -S"<символ>" main -- <файл>` и чтение ТЕКУЩЕГО кода, потом планирование:** постановка стареет, баг мог быть смержен вчера (#114 — фикс лежал в main три дня)
- **В задании указан путь файла → `git check-ignore -v <путь>` ДО начала работы, не на коммите** (#134 — артефакт целиком написан в `.gitignore`-каталоге)
- **Autoincrement `id` — порядок ВСТАВКИ, а не порядок событий, если запись идёт через пул потоков или очередь. Сопоставляешь парные события → сортируй по `ts`** (#340 — у 4 266 из 42 661 пар `id` результата меньше `id` вызова, `ts` верен в 42 661 из 42 661; проход по `id` давал 79% всех висяков)
- **Метрика зависит от нагрузки машины (время, тики, любой wall-clock) → мерь ветки ВПЕРЕМЕЖКУ A/B/A/B и печатай `loadavg` рядом с каждым замером:** блочный порядок подмешивает тренд нагрузки в пользу той ветки, что мерили в тишине (#230 — «4 красных из 6 против 0 из 7» после чередования превратилось в отсутствие эффекта)
- **Выбрал ПОРОГ по замеру → до прода три проверки** (все три завалил `deficit > 14`, #314): (1) пересчитай сетку МЕЛКО вокруг точки — в четырёх часах от неё знак разделения инвертируется; (2) прогони метрику по ВСЕМ снимкам с ПРОДОВЫМ правилом базы — офлайн-калибровка ложно срабатывала в 7 окнах из 7; (3) смотри ОБЕ половины матрицы ошибок и журналируй ВСЕ оценки с `revision` порога — «0 ложных» при n=0 это «не измерено»
- **Называешь версию библиотеки/рантайма, на которой работает ПРОД → спрашивай её интерпретатором из `ExecStart` юнита (или из `/proc/<pid>/`), а НЕ тем `python3`, что первым в PATH** (#197 — системный дал 1.0.0, боевой venv 1.1.0; я на этом расхождении выдал воркеру ложную находку как дефект, ревьюер её снял). Проверка на живом процессе точнее, чем на venv: `ls /proc/<pid>/root/.../site-packages/<pkg>-*.dist-info`.
- **Намерил улучшение на фиксированной выборке → померь СОБСТВЕННЫЙ ШУМ метрики (split-half) и ТОЛЬКО по до-периоду:** пул «до+после» втягивает эффект в оценку шума (#188). Прирост меньше медианного шума = нет прироста (#135 — ΔMRR +0.031 при шуме 0.105)
- **Меряешь эффект СРАВНЕНИЕМ ДВУХ ПРОГОНОВ (до/после, main против ветки) → сперва прогони «до против до» на ОДНОМ И ТОМ ЖЕ коде и сравни разброс с ожидаемым эффектом** (#197 — `test_dashboard_polling_equivalent_twelve_minutes` сравнивал main сам с собой и объявлял регрессию 2 раза из 3, `before_total` гулял 1456–2242 на неизменном коде). Шум больше эффекта → метрика негодна, считай величину детерминированно (по расписанию), а прогон не используй вовсе. Отличие от правила выше: там фиксированная выборка и split-half, здесь парный прогон.
- **Собрал список на УДАЛЕНИЕ по снимку → пересчитай его по свежим данным В ТОЙ ЖЕ команде, что удаляет, и откажись от прохода при любом расхождении и при пустом реестре** (#188 — за час 103 агента стали 107, под удаление попадал файл памяти живого агента)
- **Считаешь отношение из счётчика с ОКРУГЛЁННЫМИ значениями → проверь, не отбираешь ли интервалы по условию на ту же величину, которую считаешь** (#186 — завышение 60–150%). **Проверяешь ГИПОТЕЗУ против такого счётчика → фальсификатор на отрезке ПОСЛЕ наблюдённого перехода, а не на суммарной дельте** (#199)
- **Строишь стенд, где агент НЕ ДОЛЖЕН знать ответ (слепой прогон, ретроспективный реплей) → поднимай его вне worktree основного репозитория, клоном с `--no-local`, и докажи недостижимость ответа:** общий object store делает смерженную реализацию физически доступной, и прогон просто выглядит успешным (#210 — первая пара прогонов потеряна целиком)
- **Добираешь прогоны в ячейку ПОСЛЕ раскрытия ключа слепого судейства → помечай их exploratory навсегда и считай отдельно** (#184)
- **Эффект правки промпта/правила померен на фиксированном наборе заданий → прогони 1-2 задания из ДАЛЁКОЙ предметной области, прежде чем объявлять эффект:** однородный набор мерит тему, а не правку (#119 — на бытовом задании старая версия дала то же улучшение сама)
- **Текст отчёта обязан совпадать с тем, что реально считала команда — и по ЧИСЛУ, и по ОБЛАСТИ.** Числа берутся из выполненной команды, а не из впечатления (#119 — 3 ошибки в 3 проверенных строках, все в пользу автора); фильтр, подмножество, знаменатель называются дословно тем же, каким считал (#314 — две подмены области, обе поймало только внешнее ревью). Образец «как это будет выглядеть» собирается ОДНИМ прогоном (#189). Сам `print` про фильтр — не доказательство фильтра: грепни, применён ли он в коде (#345)
- **Правило в промпте/скилле диктует синтаксис ВНЕШНЕГО стандарта (CSS/HTTP/SQL/формат файла) → проверь синтаксис одним прогоном, прежде чем следовать дословно; расхождение отдай владельцу файла** (#123 — скилл предписывал `light-dark()` с обратным порядком аргументов)
- **Мутируешь по тексту строки → сперва `grep -c "<строка>"` по ФАЙЛУ; >1 → целься уникальным якорем,** иначе мутант уедет в чужой метод и «тест не ловит дефект» будет ложью (#167)
- **Мутируешь ОДИН файл, чтобы доказать, что проверка ловит пропажу → прогони ещё и СОСТАВНУЮ мутацию «пропало здесь И появилось в общем слое» (base, шаблон, родительский конфиг):** одиночная зелена и у честной проверки, и у той, что просто ищет строку в итоговой сборке (#198)
- **Сузил или ИНВЕРТИРОВАЛ условие срабатывания фичи → перепроверь НЕГАТИВНЫЕ тесты вопросом «может ли этот тест ещё покраснеть?»:** после инверсии он часто проходит ВАКУУМНО (#241)
- **Тест утверждает ОТСУТСТВИЕ строки в ЖИВОМ контейнере (чат, журнал, страница прода) → якорь на СВОЙ узел, а не на весь контейнер:** продовые данные содержат ровно ту строку, ради которой заведена задача (#270)
- **Мутационная проверка НЕ покраснела на функции с несколькими признаками или fallback → добавь случай, где остальные признаки помочь не могут, и повтори мутацию** (#151). **Тест, написанный ПОД конкретную находку, сам её не проверяет — прогоняй мутацию и по нему** (#186; там же три способа получить зелёный прогон на дефектной реализации: симметричная фикстура, одинаковый формат на обеих сторонах сравнения, гонка через `asyncio.gather`). **Тест, который при регрессии ЗАВИСАЕТ, а не падает, — дефектный**
- **Тест приколочен к дословному argv / тексту кода / имени вызова → сперва `git log -S"<строка>"` и вопрос «изменилось ПОВЕДЕНИЕ или только ФОРМА?».** Форма → переписать тест на поведенческий, НЕ подгонять строку: подгонка оставляет его хрупким до следующего рефакторинга; печатай фактическую последовательность вызовов, прежде чем править матчер (#154 — тест требовал дословное `AbortSignal.timeout(30000)`, а #58 перевёл бюджет в параметр: прод-код чинить было нечего)
- **Назначаешь абсолютный порог приёмки ДО прогона → выводи его из пилота и измеренного шума, а не из круглого числа; и мерь то, что защищает, а не то, что исполняется** (#77 — реальный эффект Δ+0.50 при p=0.0039 провалил взятый с потолка критерий 0.80)
- **Жалоба юзера на скорость → сперва померь ДЕЙСТВИЕ из его дословной формулировки, потом загрузку страницы** (#57 — сутки чинили первую загрузку, а переключение проекта стоило 1205 мс и не мерилось ни разу)
- **Цикл умеет ПЕРЕИГРЫВАТЬ вход после сбоя (откат курсора, ретрай, at-least-once) → флаг «уже обработано» гасить ПОСЛЕ фактического сайд-эффекта; тестом закрывать оба направления — потерю и дубль** (#158)
- **Задача обосновывает работу словами «такого ещё нет» → до планирования `grep -ril "<тема>" docs/ ~/.claude/skills/` и проверка СУЩЕСТВОВАНИЯ каждого артефакта, на который велено сослаться** (#159 — инструкция на 564 строки уже лежала в `docs/`, 2 из 3 названных скиллов не существовали)
- **Зеркальный случай: утверждаешь «в системе УЖЕ ЕСТЬ X», опираясь на СВОЙ прошлый тикет → грепни production-вызывающего, а не определение** (#216 — «доверенный серверный task_class» оказался enum с нулём вызывающих)

## 🪤 Грабли (то, на чём уже спотыкались)

Формат: **триггер → действие** + якорь замера (число, `#задача`). Доказательство — как мерили,
чем поймали, во что верили до этого — в базе знаний: `docs/kb/evidence-methods.md` (проверки и
замеры), `docs/kb/test-oracles.md` (тесты и общий рантайм), `docs/kb/codex-runtime.md` (Codex,
модели, ревью), `docs/kb/repo-ops.md` (git, деплой, дубли, воркеры). Хроника — `docs/archive/sessions/`.

**Проверка и доказательства (самый частый источник ошибок)**
- Агент «сделал» работу, а её нет → напечатал tool call текстом вместо вызова → проверять артефакт, а не рассказ
- **`sudo` под `NoNewPrivileges=yes` отбит, отказ уходит в stderr → в конвейере остаётся ПУСТОТА, читаемая как «ничего не найдено».** Убедись, что источник ЧИТАЕТСЯ (`sudo -n true` отдельной строкой, `2>&1`), прежде чем трактовать пустоту как содержимое; врёт всегда в сторону «проблемы нет» (18.08 — два случая за день)
- **Проверяешь, СДЕЛАНА ли работа → ищи символ или путь (`git log -S'<символ>' main`, `git cat-file -e main:<файл>`) плюс `worker_wip`, а НЕ номер задачи в заголовках коммитов и НЕ отчёт воркера:** при squash заголовок берётся от ПЕРВОГО коммита ветки (#323 — 4 из 9 задач по заголовкам не нашлись бы). Зеркально: `git rev-list --count main..<ветка>` == 0 = «ветку сбросили», а не «работы не было»
- **Отличаешь СВОЙ процесс от чужого по переменной окружения → прочитай `/proc/<pid>/environ` предполагаемого ЧУЖОГО:** дочерний шелл наследует всё, не наследуется только ТОЖДЕСТВО pid (#324)
- Диагноз о коде — гипотеза: трассируй до КОНЦА, смотри ВЕТКУ строки, а не первую подтверждающую. Поправка бывает права про дефект и неверна про место
- **Проверка, дающая одинаковый вывод при успехе и провале, — не проверка:** `systemctl show -p OOMScoreAdjust` печатает `infinity` всегда, ground truth — `/proc/<pid>/oom_score_adj`
- **Строка ЛОГА печатается безусловно, а поведение рядом ветвится по условию → это самоподтверждение, а не журнал.** Текст-доказательство обязан ветвиться тем же условием, что и поведение (#230 — лог «its turn keeps running» при пустом `active_turn_id` у всех трёх «подтверждающих»)
- **Инструмент молча вырождается в «не найдено» и врёт в сторону ошибки:** `grep` по испорченному двоичным мусором файлу отвечает пустотой (#189 — два фоновых прогона писали в один `/tmp`-файл; лечится уникальным путём на прогон)
- **«Очередь пуста» одинаково верно при «всё сделано» и при «никто не начинал» → ждать надо положительный признак выполненного** (#189 — 767 записей из 3339 за сутки не обрабатывались, проверка на пустую очередь это одобряла)
- **Грепаешь МАРКЕР → якорно: точный путь, граница слова, уникальная строка** (#219 — `grep -i 'FACTS'` поймал «arti**facts**» и объявил 9 родственных файлов на чистом клоне)
- **Регексп по тексту, длину СТРОКИ которого ты не контролируешь (чужой HTML, ответ API, дамп `strings`, минифицированный бандл), — только `grep -aboF 'литерал' файл | head -20`,** контекст резать питоном по байтовому смещению: `.{0,N}…{0,M}` и альтернация дают катастрофический бэктрекинг по ДЛИНЕ СТРОКИ. 18.08 — три агента в трёх проектах за вечер, по ~5.6 ГБ RSS; при `OOMScoreAdjust=800` ядро убьёт оркестратор, а не греп
- **Проверяешь живость бэкенда через прокладку (прокси, CDN, релей) → assert'ь на БАЙТ, который может произвести только бэкенд**, а не на «код ответа + латентность»: их подделывает любая прокладка (12.08 — три ложных подтверждения подряд при ориджине по 20 000 мс). Два `Host` на одном IP = два РАЗНЫХ vhost

- Тест падает у тебя, но не на CI → сравнивай `env` обоих окружений РАНЬШЕ файлов репозитория: `EnvironmentFile` в юните кладёт переменные в процесс агента (чистый клон main без `.env` давал те же 401)
- Тест меряет ВЕС или РАЗМЕР → проверяй мутацией на фикстуре, которая сжимается как живые данные: `"строка " * 3000` жмётся в 293 раза против 5.1 у настоящего текста (#65)
- **Тест сверяет ТЕКСТ (промпт, шаблон, конфиг) и выводит проверяемые куски из самого же источника → он слеп к переносу строки внутри фразы.** Страхует только РУЧНОЙ якорь на цельную фразу (#210 — перенос сработал дважды, оба раза ловил якорный тест, ни разу вычитка)
- Браузерную проверку начинай с ожидания символа, которого НЕТ в main → иначе она зеленеет на старом коде (шесть скриптов проверяли main, дыра жила сутки)
- Проверка агрегирует собранное на лету (`all(...)`/`any(...)` по списку из DOM, файлов, логов) → гард на непустоту списка: пустой сбор печатает зелёное. **Тест доказывает, что текст НЕ протёк в чужой промпт → якоря извлекай из файла-ИСТОЧНИКА (все его пункты), а не выписывай 2-3 фразы руками** (#203)

**Чужая машина (ноут юзера — рабочий, не стенд)**
- Тяжёлые прогоны только последовательно и под потолком памяти: `systemd-run --user --scope -p MemoryMax=2G`, одна модель за раз, `nice -n 15`, не больше 2-3 параллельных. `nice` НЕ защищает от вытеснения по ПАМЯТИ — дважды за сутки выдавили чужое обучение сети. Потолок — в ПОСТАНОВКУ задачи, не в напоминание вдогонку
- Гейт свободной памяти считать по `MemAvailable` из `/proc/meminfo`, НЕ по `free`: при page cache они расходятся в 2-3 раза
- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов
- `/tmp` на ноуте — **tmpfs, то есть RAM** (1.6 ГБ «файлов» занимали оперативку). Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корень забит на 99%)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
