## Что это
Свой оркестратор AI-агентов: оркестратор управляет воркерами через MCP tools, каждый worker = CLI-сессия (Claude / Codex / Grok) в отдельном git worktree. Dashboard = FastAPI + HTMX + SSE.
**Стек:** Python 3.12+, FastAPI, Jinja2, SSE; `claude-agent-sdk`; external stdio MCP server (FastMCP) как отдельный процесс; SQLite (sessions, logs, inbox, jobs); `git worktree` для изоляции.

## Архитектура
```
Оркестратор (FastAPI :8888)
├── Dashboard (HTMX + SSE) — http://localhost:8888, auth: cookie session (login/password из .env)
├── SQLite — sessions, logs, inbox, jobs, tasks, payments
├── External MCP Server (app/mcp_stdio.py) — tools для CLI; auth по INTERNAL_TOKEN
├── Auth middleware — cookie OR internal token
├── Session Manager — spawn/stop/archive/compact
├── Task Manager (app/tm.py) — CRUD, priorities, payments, YouGile sync
├── TG Bridge (app/tg_bridge.py) — bidirectional, topics, voice transcription
└── Workers — CLI-сессия (Claude/Codex/Grok) + свой git worktree + MCP (Orchestra + scope .mcp.json)
```
Deployed: localhost:8888 (dev) + VPS клиента (auth enabled)

## Принципы
- Persistent client per session (connect once, `query()` injects mid-turn via stdin)
- External MCP (no in-process deadlocks); workers communicate via HTTP callback, not MCP inject
- Воркеры общаются друг с другом напрямую через `send_message(to="worker-name")` — оркестратор не нужен как посредник
- Фронтенд (JS/CSS/HTML) обновляется без рестарта; Python-код требует рестарта для загрузки, но это не разрешение на него
- `sudo systemctl` для `orchestra`/`telegram-bot-api` доступен технически, но это НЕ authorization: `restart/stop/start` — только по явной команде текущего юзера, `status` read-only. Рестарт прерывает active turns; после него SQLite-сессии и idle workers восстанавливаются. **Настоящая цена рестарта — не 2.38 убитого хода, а задержка выката: медиана 3.3 ч, p75 22.9 ч (#220)**
- **НЕ обновлять VPS самостоятельно** — git pull и рестарт на VPS делает только юзер вручную
- **Remotes:** `origin` (github.com/DrSeedon/orchestra) — наш публичный, держать актуальным. Всё, что НЕ `origin`, — чужое: не трогать никогда. Список смотреть командой `git remote -v`, а не по памяти
- **TG /restart** — команда в TG группе для рестарта Orchestra

## 🔌 ПРОКСИ (единственный источник истины = .env)
- **`.env` `HTTPS_PROXY`/`HTTP_PROXY` = ЕДИНСТВЕННЫЙ источник.** Нет DB, нет hot-switch, нет кеша статусов. Один прокси везде: systemd EnvironmentFile → `os.environ` → наследуют все (Orchestra + CLI агенты + MCP subprocess), рассинхрон невозможен by design
- **Сменить прокси:** отредактируй `HTTPS_PROXY` И `HTTP_PROXY` в `.env` (оба!) → `sudo systemctl restart orchestra`. Живой прокси найти: `bash scripts/check-proxies.sh` (диагностика, впишет в `.env`; рестарт — руками)
- **Дашборд:** только индикатор активного (из `os.environ`, read-only) + кнопка Check. Кнопки «выбрать/активировать» НЕТ. `proxy_manager.py` read-only: `list_proxies()` + `check_all()`, НЕ мутирует env и НЕ пишет в DB
- SSH-туннели (`ssh_tunnel.py`) поднимают локальные порты к VPS, `HTTPS_PROXY` указывает на нужный порт. Мёртвые VPS не спамят реконнектом (health-gate + backoff)
- **TG bot** (telegram-bot-api) — через proxychains, C++ бинарник не читает `.env`. При смене прокси обновлять ОБА файла: `/etc/proxychains4.conf` И `~/.proxychains/proxychains.conf` (user-config имеет приоритет)

## AI Efficiency + Agent Determinism (design principles)
Orchestra автоматизирует людей — но и самих агентов надо оптимизировать. Мерить цену задачи, а не «работает ли»: $2 за 3 вызова > $8 за 30.
- Одни и те же 3 вызова каждый раз → один MCP-тул или серверная логика; агенты перечитывают одни файлы → инжектить при спавне; паттерн вызывает context rot → чинить причину, а не добавлять инструкции
- Антипаттерны: читает файл целиком ради 5 строк (дать grep/диапазон); спрашивает разрешение, которое мог решить сам; ретраит 5 раз вместо fail fast; два агента дублируют работу (worker-to-worker); 20 вызовов на setup, который можно преднастроить
- **Детерминизм: 1 задача = 1 workflow** (три способа → агент выберет худший). Минимум тулов: лишний тул = развилка. Decision tree вместо «реши сам». Fail loud, не fail creative. Промпт не покрывает ситуацию → спросить оркестратора, а не выдумывать. Проектируя роль, спрашивать «может ли агент пойти не тем путём?» — да → сузить

**Чужая машина (ноут юзера — рабочий, не стенд)**
- Тяжёлые прогоны только последовательно и под потолком памяти: `systemd-run --user --scope -p MemoryMax=2G`, одна модель за раз, `nice -n 15`, не больше 2-3 параллельных. `nice` НЕ защищает от вытеснения по ПАМЯТИ — дважды за сутки выдавили чужое обучение сети (RSS рос 3.5→4.2 ГиБ), а ONNX-бенчмарки грели CPU до 93°C. Потолок — в ПОСТАНОВКУ задачи, не в напоминание вдогонку
- Гейт свободной памяти считать по `MemAvailable` из `/proc/meminfo`, НЕ по `free`: при page cache они расходятся в 2-3 раза
- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap на диске) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов
- `/tmp` на ноуте — **tmpfs, то есть RAM**: 1.6 ГБ «файлов» физически занимали оперативку. Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корневой раздел забит на 99%)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
