## Что это
Свой оркестратор AI-агентов: оркестратор управляет воркерами через MCP tools, каждый worker = CLI-сессия (Claude / Codex / Grok) в отдельном git worktree. Dashboard = FastAPI + HTMX + SSE.
**Стек:** Python 3.12+, FastAPI, Jinja2, SSE; `claude-agent-sdk`; external stdio MCP server (FastMCP) как отдельный процесс; SQLite (sessions, logs, inbox, jobs); `git worktree` для изоляции.

## Архитектура
```
Оркестратор (FastAPI :8888)
├── Dashboard (HTMX + SSE) — http://localhost:8888, auth: cookie session (login/password из .env)
├── SQLite — sessions, logs, inbox, jobs, tasks, payments
├── External MCP Server (app/mcp_stdio.py) — tools для CLI; auth по INTERNAL_TOKEN
├── Auth middleware — cookie OR internal token
├── Session Manager — spawn/stop/archive/compact
├── Task Manager (app/tm.py) — CRUD, priorities, payments, YouGile sync

└── Workers — CLI-сессия (Claude/Codex/Grok) + свой git worktree + MCP (Orchestra + scope .mcp.json)
```
Deployed: localhost:8888 (dev) + VPS клиента (auth enabled)

## Принципы
- **ХРАНИМ СМЫСЛ, УДАЛЯЕМ ВЫВОДИМОЕ (решение юзера 01.09.2026, его формулировка: «максимально все данные сохраняем для логирования и прочего, информация не должна теряться, но лишней информации и дублей нельзя делать и мертвого мусора… то, что можно восстановить — удалять, ну типа как с формулами в физике»).** Два требования одновременно, и они не противоречат друг другу: НИ ОДИН факт, урок или доказательство не теряется — и при этом на диске не лежит ничего, что можно получить заново. Проверка перед тем, как что-то сохранить или оставить: **«это выводимо из другого источника?»** Да → удалить, оставив источник. Нет → сохранить, и сохранить один раз. Отсюда следствия: копия — всегда дефект, а не подстраховка (у копии заводится второй владелец, и она расходится с оригиналом); пересобираемый артефакт (venv, индекс, проекция, кеш) не бэкапится и не хранится по числу потребителей; сырьё, из которого уже извлечён смысл, удаляется вместе с извлечением, а не «на всякий случай» — иначе греп находит мусор наравне с правдой и агент не может отличить. Архив допустим только там, где извлечение смысла принципиально неполно, и тогда он ОДИН и явно помечен как архив.
- Persistent client per session (connect once, `query()` injects mid-turn via stdin)
- External MCP (no in-process deadlocks); workers communicate via HTTP callback, not MCP inject
- Воркеры общаются друг с другом напрямую через `send_message(to="worker-name")` — оркестратор не нужен как посредник
- Фронтенд (JS/CSS/HTML) обновляется без рестарта; Python-код требует рестарта для загрузки, но это не разрешение на него
- **РЕСТАРТ ДЕЛАЕТСЯ БЕЗ СПРОСА И БЕЗ ОГЛЯДКИ НА ЧУЖИЕ ХОДЫ (решение юзера 28.08.2026, дословно: «если рестарт или какая-то инфраструктурная дичь НИКОГДА НЕ ВМЕШИВАТЬСЯ В РАБОТУ ДРУГИХ ОРКЕСТРАТОРОВ И ПРОЕКТОВ, ЕСЛИ НУЖЕН РЕСТАРТ НЕ СПРАШИВАЕШЬ РЕСТАРТИШЬ И ВСЕ, ТЕБЕ ПОХУЙ НА НИХ И ВСЕХ ИХ ТАМ САМИ РАЗБУДЯТ АЛГОРИТМЫ ПОСЛЕ РЕСТАРТА»).** Нужен рестарт — рестартишь. Не ждёшь чужой ход, не смотришь, кто сейчас `running`, не пишешь чужим оркестраторам «сейчас будет рестарт», не просишь закончить, не спрашиваешь разрешения ни у них, ни у юзера. Прерванные ходы поднимает сама платформа: SQLite-сессии и idle workers восстанавливаются, агентов будят алгоритмы. Прежняя формулировка («по явной команде юзера, кроме аварии класса A» + `list_agents` перед рестартом + ожидание DONE) ОТМЕНЕНА целиком — именно это ожидание 26.08 держало 15 минут `restart_pending` у всех проектов и всё равно кончилось отменой. `sudo systemctl status` — read-only и бесплатен. **Цена рестарта — не 2.38 убитого хода, а задержка выката: медиана 3.3 ч, p75 22.9 ч (#220)**: ждать дороже, чем рестартовать.
- **В чужие проекты и к чужим оркестраторам по поводу инфраструктуры не лезть вообще.** Инфраструктура общая и моя; «предупредить, согласовать, попросить подождать» — это не вежливость, а вмешательство в их работу и трата их ходов. Сообщение чужому оркестратору законно, только если он сам спросил или ему адресован результат ЕГО задачи.
- **НЕ обновлять код VPS самостоятельно** — `git pull`/выкат новой версии делает юзер вручную. На рестарт это НЕ распространяется: рестарт мой и без спроса (правило ниже)

## AI Efficiency + Agent Determinism (design principles)
Orchestra автоматизирует людей — но и самих агентов надо оптимизировать. Мерить цену задачи, а не «работает ли»: $2 за 3 вызова > $8 за 30.
- Одни и те же 3 вызова каждый раз → один MCP-тул или серверная логика; агенты перечитывают одни файлы → инжектить при спавне; паттерн вызывает context rot → чинить причину, а не добавлять инструкции
- Антипаттерны: читает файл целиком ради 5 строк (дать grep/диапазон); спрашивает разрешение, которое мог решить сам; ретраит 5 раз вместо fail fast; два агента дублируют работу (worker-to-worker); 20 вызовов на setup, который можно преднастроить
- **Детерминизм: 1 задача = 1 workflow** (три способа → агент выберет худший). Минимум тулов: лишний тул = развилка. Decision tree вместо «реши сам». Fail loud, не fail creative. Промпт не покрывает ситуацию → спросить оркестратора, а не выдумывать. Проектируя роль, спрашивать «может ли агент пойти не тем путём?» — да → сузить

## 🧷 `search_memory` НЕ УБИРАТЬ (26.08.2026, прямое требование юзера)
**`search_memory` остаётся MCP-тулом и остаётся в промптах, пока юзер не скажет обратное.** Дословно 26.08: «Серч мемори не убирай пока что». Снятие `@mcp.tool()` с него — блокер мержа, а не деталь реализации.

Причина механическая: `modules/memory-search.md` объявляет его ОБЯЗАТЕЛЬНЫМ шагом («Mandatory pre-work order»). Убрать тул, оставив требование в промпте, — значит послать каждого агента КАЖДОГО проекта звать несуществующее на обязательном шаге. Это зеркало аварии 25.08, где промпт требовал ещё не включённый `knowledge`.

**Поправка 30.08 (#419): ТУЛ жив, а МЕХАНИЗМ под ним выключен — это разные вещи, и правило выше соблюдено.** При `RAG_ENABLED=false` `search_memory` не падает и не исчезает: он отвечает «семантический поиск выключен (RAG_ENABLED=false)» и подставляет готовую команду `rg` (`app/mcp_stdio.py:3033`, ветка `"RAG disabled" in e.message`). Обязательный шаг промпта при этом выполняется штатно — агент получает не ошибку, а маршрут. Отсюда общее правило на любое выключение фичи, на которую ссылается промпт: **гасить надо реализацию, оставляя точку входа, которая честно называет причину и даёт замену.** Удалять точку входа можно только вместе с требованием в промпте, и в этом порядке: сперва промпт, потом тул.

Проверка перед мержем любой правки, трогающей память агентов, — две команды, обе обязаны быть непустыми:
- `git show main:app/mcp_stdio.py | grep -B1 '^async def search_memory' | grep -c '@mcp.tool()'` → 1
- `git show main:.orchestra/pipelines/default/prompts/modules/memory-search.md | grep -c search_memory` → ≥1

Расходятся → не мержить. Замер 26.08 (#361): воркер снял декоратор, потому что этого требовал T5 его же оракула; оракул и живой промпт оказались двумя владельцами одной мысли и разошлись. Чинить в таком случае ОРАКУЛ, а не прод: удаление совместимого `search_memory` — отдельный тикет ПОСЛЕ gen3, а не побочный эффект чужой задачи.

## 🚦 Промпты агентов меняются ПОСЛЕДНИМИ, а не первыми (25.08.2026, требование юзера)
**Правило: правка промптов, обязывающая агентов пользоваться новой возможностью, выкатывается ТОЛЬКО после того, как live-owner этой возможности отвечает успехом на реальный запрос из реального агентского контура.** Не «код смержен», не «тесты зелёные», не «сервис поднят» — успешный ответ на живой вызов тем же путём, которым пойдёт агент.

Причина в асимметрии: код с неработающей фичей просто лежит и никому не мешает, а промпт с требованием звать неработающую фичу **ломает всех агентов всех проектов сразу**, включая тех, кто про эту фичу не знает и в ней не нуждается. Радиус поражения промпта — весь парк, радиус поражения мёртвого кода — ноль.

Замер: 25.08 `knowledge` был вписан в 5 prompt-owner файлов до включения сервиса. Чужой оркестратор (COG-second-brain) получил `503 knowledge_not_configured` на обязательном шаге и завёл баг-репорт платформы; правило пришлось выкатывать откатом, возвращая `search_memory`. Порядок обязан быть обратный: сервис → живой запрос успешен → потом промпты.

Практика на такой выкат:
- Гейт на промптовую правку — только положительный признак: успешный ответ live-owner на запрос из настоящего агентского контура. Отсутствие ошибки признаком не является.
- Пока гейт не пройден, новая возможность существует как ОПЦИЯ (агент может позвать, если она есть), но никогда как ОБЯЗАННОСТЬ.
- Не проходит гейт → откатывается ПРОМПТ, а не сервис: код остаётся в репозитории и доезжает позже.
- Тот же порядок для любой внешней зависимости в промпте: MCP-тул, эндпоинт, скилл, файл. Промпт, ссылающийся на то, чего ещё нет, — это отложенная авария у всех сразу.

## 🧭 Архитектуру ОБСУЖДАЕМ с юзером до реализации, а не показываем результат (30.08.2026)

Отдельно: **тул обязан упрощать то, что без него потребовало бы много кода.** Если агент может получить то же самое обычным чтением файла или грепом, тул не нужен — он не «интерфейс ради интерфейса». Я выдал воркеру как факт «ревью — обязательный гейт мержа» и «`CLAUDE.md` весит 171 419 байт»; обе цифры он проверил и обе оказались неверны: `grep -c review app/merge_operations.py` → **0** (единственное совпадение — константа `REVIEW_WARNINGS_OUTSIDE_MERGE`, то есть код прямо говорит, что ревью ВНЕ мержа), `wc -c CLAUDE.md` → **189 851**. Ревью принуждается промптами пяти файлов, квитанции пишутся в `review_receipts` и на пути мержа НЕ читаются вовсе. Цена ошибки уже реализовалась: формулировка «ревью стоит гейтом на мерже» ушла в отправленный промо-текст и в рамку #505. Практика: любое утверждение вида «X принуждается системой» проверяется грепом ПО ПРИНУЖДАЮЩЕМУ пути (merge/gate/hook), а не по промпту, где оно написано; расхождение возвращается заказчику как находка, а не переписывается из задания.
- **Краткость, формат отчётов и «не отчитываться о промежуточном» живут в `.orchestra/pipelines/default/prompts/base.md` (`<communication-style>`) и `roles/orchestrator.md`** — там владелец, здесь копии намеренно нет.
- **Поднимаешь цитату юзера про конкретный продукт или интерфейс до ОБЩЕГО правила → проверь обобщённую формулировку в проекте, где этого интерфейса нет вовсе.** Потеряла предмет или ввела новый предмет, которого в цитате не было, — значит это правило проекта, а не парка. Замер 01.09 (#428), два случая подряд за одну задачу: «я смотрю дашборд на ПК» я обобщил до «как агенту отчитываться» — юзер снял («нет это я про оркестру только говорю»); и приписал ему свою же фразу «внимание юзера дорого» как его ценность. Оба раза обобщение звучало шире цитаты и вводило предмет, которого в ней не было. - **Разовое «делай как считаешь нужным» НИКОГДА не поднимается в промпт как правило — только конечным перечнем классов решений с исключениями** (решение юзера 01.09, дословно: «это хуевый промпт он перезатирать будет все удали»). Причина механическая, а не про область действия: формулировка вида «решай сам» не ДОБАВЛЯЕТ агенту свободы, она ОТМЕНЯЕТ соседние правила, потому что любой конфликт агент разрешает ею в свою пользу — она сильнее всего, что стоит рядом, и тем сильнее, чем длиннее промпт. Разрешение на автономию выражается списком: вот эти обратимые локальные решения принимаются без спроса, всё прочее — вопрос. Замер: фраза была сказана дважды как разовая делегация конкретной задачи (#428, V20), ресёрч поднял её в реестр ценностей, юзер снял. ## ✅ ПРОВЕРЬ ПЕРЕД РАБОТОЙ (все агенты, не только оркестратор)
- **Правка опирается на запись в базе знаний или в этом файле → проверь ИСПОЛНЕНИЕ у владельца состояния, а не факт записи.** Минимальный набор: конфиг (`.env` и его mtime), `/proc/<MainPID>/environ` живого процесса, строка в журнале при старте, контрольный вызов самой функции. Замер 02.09.2026: с 30.08 здесь стояло «семантический поиск выключен, `RAG_ENABLED=false` в `.env`» — на деле в `.env` всё это время `true`, процесс поднят с ним, `data/vec.db` растёт, а `search_memory` возвращает настоящую гибридную выдачу. Я записал НАМЕРЕНИЕ как исполненный факт и месяц читал его как состояние; поймал воркер, которому эта запись была выдана основанием для правки ПУБЛИЧНОГО README. Отсюда же вторая ловушка того разбора: боевой интерпретатор `/opt/orchestra/runtimes/…/bin/python` содержит пакеты, которых нет в `.venv` репозитория — проверка «стоит ли зависимость» не по тому интерпретатору даёт ложное «нет».
Одно про всё: убедись в предпосылке, пока она стоит копейки, а не после сделанной работы.
Доказательство каждого пункта — `.orchestra/kb/evidence-methods.md`.
- **Задача описывает симптом («сломано», «ловил N раз») → сперва `git log -S"<символ>" main -- <файл>` и чтение ТЕКУЩЕГО кода, потом планирование:** постановка стареет, баг мог быть смержен вчера (#114 — фикс лежал в main три дня)
- **В задании указан путь файла → `git check-ignore -v <путь>` ДО начала работы, не на коммите** (#134 — артефакт целиком написан в `.gitignore`-каталоге)
- **Фильтруешь по времени колонку с ISO-timestamp (`2026-09-01T18:34:03+00:00`) → НИКОГДА не сравнивай её с `datetime('now','-N hours')`: SQLite отдаёт строку с ПРОБЕЛОМ вместо `T`, а `'T' > ' '` в ASCII, поэтому на той же дате условие `ts > datetime(...)` пропускает ВСЕ строки суток.** Отказ тихий и всегда в сторону завышения: запрос выглядит как «за 3 часа», а отдаёт «за сегодня». Замер 02.09 (#437): мой запрос дал 142 хода / 458 176 выходных токенов «за 3 часа», правильный питоновский ISO-cutoff — 85 / 271 347, то есть завышение в 1.7 раза; на этом я успел объявить юзеру несуществующую «нестыковку чувствительности втрое» и отзывать её. Правильно: считать границу в Python (`datetime.now(timezone.utc) - timedelta(hours=3)).isoformat()`) и передавать параметром, либо сравнивать через `datetime(ts)` с обеих сторон. Проверка за один вызов: печатай `min(ts)` выборки рядом с результатом — если он старше заявленного окна, фильтр не сработал.
- **Autoincrement `id` — порядок ВСТАВКИ, а не порядок событий, если запись идёт через пул потоков или очередь. Сопоставляешь парные события → сортируй по `ts`** (#340 — у 4 266 из 42 661 пар `id` результата меньше `id` вызова, `ts` верен в 42 661 из 42 661; проход по `id` давал 79% всех висяков)
- **Реконструируешь ПРОШЛОЕ состояние хранилища, чтобы объяснить сбой → якорь берётся по timestamp самого СБОЯ (строка ошибки в логе), а не по `created_at` операции, задачи или сессии.** Операция создаётся раньше, чем падает, и за этот зазор состояние успевает измениться — снимок по `created_at` описывает не тот момент и оправдывает или обвиняет невиновного. Замер #426: привязка к `operation.created_at` дала неверную картину и была снята ревью; перепривязка к точным timestamp падающих логов показала, что в снимках на момент отказа задач #399/#400/#410 в canonical не было (`target_matches=0` при 246–248 других состояний), а сейчас есть — то есть дефект условный, а не постоянный, и общий финализатор переделывать было не нужно
- **Метрика зависит от нагрузки машины (время, тики, любой wall-clock) → мерь ветки ВПЕРЕМЕЖКУ A/B/A/B и печатай `loadavg` рядом с каждым замером:** блочный порядок подмешивает тренд нагрузки в пользу той ветки, что мерили в тишине (#230 — «4 красных из 6 против 0 из 7» после чередования превратилось в отсутствие эффекта)
- **Выбрал ПОРОГ по замеру → до прода три проверки** (все три завалил `deficit > 14`, #314): (1) пересчитай сетку МЕЛКО вокруг точки — в четырёх часах от неё знак разделения инвертируется; (2) прогони метрику по ВСЕМ снимкам с ПРОДОВЫМ правилом базы — офлайн-калибровка ложно срабатывала в 7 окнах из 7; (3) смотри ОБЕ половины матрицы ошибок и журналируй ВСЕ оценки с `revision` порога — «0 ложных» при n=0 это «не измерено»
- **Называешь версию библиотеки/рантайма, на которой работает ПРОД → спрашивай её интерпретатором из `ExecStart` юнита (или из `/proc/<pid>/`), а НЕ тем `python3`, что первым в PATH** (#197 — системный дал 1.0.0, боевой venv 1.1.0; я на этом расхождении выдал воркеру ложную находку как дефект, ревьюер её снял). Проверка на живом процессе точнее, чем на venv: `ls /proc/<pid>/root/.../site-packages/<pkg>-*.dist-info`.
- **Намерил улучшение на фиксированной выборке → померь СОБСТВЕННЫЙ ШУМ метрики (split-half) и ТОЛЬКО по до-периоду:** пул «до+после» втягивает эффект в оценку шума (#188). Прирост меньше медианного шума = нет прироста (#135 — ΔMRR +0.031 при шуме 0.105)
- **Меряешь эффект СРАВНЕНИЕМ ДВУХ ПРОГОНОВ (до/после, main против ветки) → сперва прогони «до против до» на ОДНОМ И ТОМ ЖЕ коде и сравни разброс с ожидаемым эффектом** (#197 — `test_dashboard_polling_equivalent_twelve_minutes` сравнивал main сам с собой и объявлял регрессию 2 раза из 3, `before_total` гулял 1456–2242 на неизменном коде). Шум больше эффекта → метрика негодна, считай величину детерминированно (по расписанию), а прогон не используй вовсе. Отличие от правила выше: там фиксированная выборка и split-half, здесь парный прогон.
- **Собрал список на УДАЛЕНИЕ по снимку → пересчитай его по свежим данным В ТОЙ ЖЕ команде, что удаляет, и откажись от прохода при любом расхождении и при пустом реестре** (#188 — за час 103 агента стали 107, под удаление попадал файл памяти живого агента)
- **Считаешь отношение из счётчика с ОКРУГЛЁННЫМИ значениями → проверь, не отбираешь ли интервалы по условию на ту же величину, которую считаешь** (#186 — завышение 60–150%). **Проверяешь ГИПОТЕЗУ против такого счётчика → фальсификатор на отрезке ПОСЛЕ наблюдённого перехода, а не на суммарной дельте** (#199)
- **Строишь стенд, где агент НЕ ДОЛЖЕН знать ответ (слепой прогон, ретроспективный реплей) → поднимай его вне worktree основного репозитория, клоном с `--no-local`, и докажи недостижимость ответа:** общий object store делает смерженную реализацию физически доступной, и прогон просто выглядит успешным (#210 — первая пара прогонов потеряна целиком)
- **Добираешь прогоны в ячейку ПОСЛЕ раскрытия ключа слепого судейства → помечай их exploratory навсегда и считай отдельно** (#184)
- **Эффект правки промпта/правила померен на фиксированном наборе заданий → прогони 1-2 задания из ДАЛЁКОЙ предметной области, прежде чем объявлять эффект:** однородный набор мерит тему, а не правку (#119 — на бытовом задании старая версия дала то же улучшение сама)
- **Текст отчёта обязан совпадать с тем, что реально считала команда — и по ЧИСЛУ, и по ОБЛАСТИ.** Числа берутся из выполненной команды, а не из впечатления (#119 — 3 ошибки в 3 проверенных строках, все в пользу автора); фильтр, подмножество, знаменатель называются дословно тем же, каким считал (#314 — две подмены области, обе поймало только внешнее ревью). Образец «как это будет выглядеть» собирается ОДНИМ прогоном (#189). Сам `print` про фильтр — не доказательство фильтра: грепни, применён ли он в коде (#345)
- **Правило в промпте/скилле диктует синтаксис ВНЕШНЕГО стандарта (CSS/HTTP/SQL/формат файла) → проверь синтаксис одним прогоном, прежде чем следовать дословно; расхождение отдай владельцу файла** (#123 — скилл предписывал `light-dark()` с обратным порядком аргументов)
- **Мутируешь по тексту строки → сперва `grep -c "<строка>"` по ФАЙЛУ; >1 → целься уникальным якорем,** иначе мутант уедет в чужой метод и «тест не ловит дефект» будет ложью (#167)
- **Мутируешь ОДИН файл, чтобы доказать, что проверка ловит пропажу → прогони ещё и СОСТАВНУЮ мутацию «пропало здесь И появилось в общем слое» (base, шаблон, родительский конфиг):** одиночная зелена и у честной проверки, и у той, что просто ищет строку в итоговой сборке (#198)
- **Сузил или ИНВЕРТИРОВАЛ условие срабатывания фичи → перепроверь НЕГАТИВНЫЕ тесты вопросом «может ли этот тест ещё покраснеть?»:** после инверсии он часто проходит ВАКУУМНО (#241)
- **Тест утверждает ОТСУТСТВИЕ строки в ЖИВОМ контейнере (чат, журнал, страница прода) → якорь на СВОЙ узел, а не на весь контейнер:** продовые данные содержат ровно ту строку, ради которой заведена задача (#270)
- **Мутация не покраснела → СПЕРВА докажи ассертом внутри теста, что он дошёл до проверяемого состояния, и только потом пиши «код защищён другим слоем».** Пустой тест и защищённый код выглядят одинаково — оба зелёные. Замер #453: проверка gitlink пережила мутацию, потому что `git add -A` молча снимал из индекса запись о submodule; тест доходил до коммита, ничего не проверив. После ассерта на предусловие (`assert "160000" in git diff --cached --raw`) та же мутация краснеет. Отличие от правила ниже: там выживает КОД из-за нескольких признаков, здесь пуст ТЕСТ.
- **Мутационная проверка НЕ покраснела на функции с несколькими признаками или fallback → добавь случай, где остальные признаки помочь не могут, и повтори мутацию** (#151). **Тест, написанный ПОД конкретную находку, сам её не проверяет — прогоняй мутацию и по нему** (#186; там же три способа получить зелёный прогон на дефектной реализации: симметричная фикстура, одинаковый формат на обеих сторонах сравнения, гонка через `asyncio.gather`). **Тест, который при регрессии ЗАВИСАЕТ, а не падает, — дефектный**
- **Тест приколочен к дословному argv / тексту кода / имени вызова → сперва `git log -S"<строка>"` и вопрос «изменилось ПОВЕДЕНИЕ или только ФОРМА?».** Форма → переписать тест на поведенческий, НЕ подгонять строку: подгонка оставляет его хрупким до следующего рефакторинга; печатай фактическую последовательность вызовов, прежде чем править матчер (#154 — тест требовал дословное `AbortSignal.timeout(30000)`, а #58 перевёл бюджет в параметр: прод-код чинить было нечего)
- **Назначаешь абсолютный порог приёмки ДО прогона → выводи его из пилота и измеренного шума, а не из круглого числа; и мерь то, что защищает, а не то, что исполняется** (#77 — реальный эффект Δ+0.50 при p=0.0039 провалил взятый с потолка критерий 0.80)
- **Жалоба юзера на скорость → сперва померь ДЕЙСТВИЕ из его дословной формулировки, потом загрузку страницы** (#57 — сутки чинили первую загрузку, а переключение проекта стоило 1205 мс и не мерилось ни разу)
- **Цикл умеет ПЕРЕИГРЫВАТЬ вход после сбоя (откат курсора, ретрай, at-least-once) → флаг «уже обработано» гасить ПОСЛЕ фактического сайд-эффекта; тестом закрывать оба направления — потерю и дубль** (#158)
- **Задача обосновывает работу словами «такого ещё нет» → до планирования `grep -ril "<тема>" docs/ ~/.claude/skills/` и проверка СУЩЕСТВОВАНИЯ каждого артефакта, на который велено сослаться** (#159 — инструкция на 564 строки уже лежала в `docs/`, 2 из 3 названных скиллов не существовали)
- **Зеркальный случай: утверждаешь «в системе УЖЕ ЕСТЬ X», опираясь на СВОЙ прошлый тикет → грепни production-вызывающего, а не определение** (#216 — «доверенный серверный task_class» оказался enum с нулём вызывающих)

## 🪤 Грабли (то, на чём уже спотыкались)

Формат: **триггер → действие** + якорь замера (число, `#задача`). Доказательство — как мерили,
чем поймали, во что верили до этого — в базе знаний: `.orchestra/kb/evidence-methods.md` (проверки и
замеры), `.orchestra/kb/test-oracles.md` (тесты и общий рантайм), `.orchestra/kb/codex-runtime.md` (Codex,
модели, ревью), `.orchestra/kb/repo-ops.md` (git, деплой, дубли, воркеры). Хроника — `.orchestra/archive/sessions/`.

**Проверка и доказательства (самый частый источник ошибок)**
- Агент «сделал» работу, а её нет → напечатал tool call текстом вместо вызова → проверять артефакт, а не рассказ
- **`transport_timeout: ReadTimeout` от MCP-тула означает НЕИЗВЕСТНОСТЬ, и исход разный по тулам → проверяй состояние в БД, не повторяй вслепую и не считай сделанным вслепую.** Замер 28.08 в двух проектах: `task_create` — задача создана 6 раз из 6 (мои #414, #417 плюс 4 у seedon), `spawn_worker` — воркер создан, `switch_worker_branch` — ветка переключена, но `send_message` — доставки НЕ БЫЛО (новой строки в `message_deliveries` не появилось вовсе), и текст отказа честно говорит `ambiguous`. Поэтому правило «раз таймаут, значит выполнилось» неверно, а слепой повтор `task_create` создаёт ВТОРУЮ задачу с новым номером и разводит ветки и привязки. Где смотреть: `sessions` — спавн и переключение, `tm_tasks` — задача, `message_deliveries` — доставка. Причина чинится в #395 (идемпотентный `request_key` + `GET /api/tm/task-create-requests/{request_key}`). **Уточнение 31.08 (dev-lead): у ЧТЕНИЯ повтор законен — оно идемпотентно; `task_get` после двух таймаутов подряд отдал карточку с третьего вызова за секунду. Опасен повтор только на ПИШУЩИХ вызовах, где он создаёт дубль.**
- **Платформа отчитывается не о том, что произошло, а о том, что вернул последний слой** (формулировка dev-lead, 31.08, по трём случаям за день): `stop_worker` печатает «interrupted and set to idle» при живом ходе; `resolve_merge_operation` печатает «was not resolved» поверх УСПЕШНО снятой блокировки (успешный ответ собирается копией исходного результата операции, а у UNKNOWN там лежит `error`); `ReadTimeout` печатает отказ поверх выполненной операции. Отсюда рабочее следствие: **«тул сказал отказ» и «состояние не изменилось» — РАЗНЫЕ утверждения, и второе проверяется своим источником** — `data/orchestra.db`, `worker_wip`, содержимое `main`. Цена пропуска замерена: dev-lead объявил тёплый воркер (ctx 56%) непригодным и оплатил холодный старт нового, хотя `worker_wip` в тот момент отвечал `clean`.
- **`sudo` под `NoNewPrivileges=yes` отбит, отказ уходит в stderr → в конвейере остаётся ПУСТОТА, читаемая как «ничего не найдено».** Убедись, что источник ЧИТАЕТСЯ (`sudo -n true` отдельной строкой, `2>&1`), прежде чем трактовать пустоту как содержимое; врёт всегда в сторону «проблемы нет» (18.08 — два случая за день)
- **Проверяешь, СДЕЛАНА ли работа → ищи символ или путь (`git log -S'<символ>' main`, `git cat-file -e main:<файл>`) плюс `worker_wip`, а НЕ номер задачи в заголовках коммитов и НЕ отчёт воркера:** при squash заголовок берётся от ПЕРВОГО коммита ветки (#323 — 4 из 9 задач по заголовкам не нашлись бы). Зеркально: `git rev-list --count main..<ветка>` == 0 = «ветку сбросили», а не «работы не было»
- **Отличаешь СВОЙ процесс от чужого по переменной окружения → прочитай `/proc/<pid>/environ` предполагаемого ЧУЖОГО:** дочерний шелл наследует всё, не наследуется только ТОЖДЕСТВО pid (#324)
- Диагноз о коде — гипотеза: трассируй до КОНЦА, смотри ВЕТКУ строки, а не первую подтверждающую. Поправка бывает права про дефект и неверна про место
- **Проверка, дающая одинаковый вывод при успехе и провале, — не проверка:** `systemctl show -p OOMScoreAdjust` печатает `infinity` всегда, ground truth — `/proc/<pid>/oom_score_adj`
- **Строка ЛОГА печатается безусловно, а поведение рядом ветвится по условию → это самоподтверждение, а не журнал.** Текст-доказательство обязан ветвиться тем же условием, что и поведение (#230 — лог «its turn keeps running» при пустом `active_turn_id` у всех трёх «подтверждающих»)
- **Инструмент молча вырождается в «не найдено» и врёт в сторону ошибки:** `grep` по испорченному двоичным мусором файлу отвечает пустотой (#189 — два фоновых прогона писали в один `/tmp`-файл; лечится уникальным путём на прогон)
- **«Очередь пуста» одинаково верно при «всё сделано» и при «никто не начинал» → ждать надо положительный признак выполненного** (#189 — 767 записей из 3339 за сутки не обрабатывались, проверка на пустую очередь это одобряла)
- **Сверяешь ЦИТАТУ грепом → сперва нормализуй типографику: `’` против `'`, `“”` против `"`, неразрывный пробел и длинное тире.** Греп по дословной цитате из чужого текста молча отвечает «не найдено», и это читается как «цитата выдумана», хотя она на месте. Замер 03.09.2026 (воркер seedon на сплошном аудите атрибуций): из 59 фрагментов 44 совпали, три оказались настоящими искажениями источника, и ОДНО ложное «не найдено» дал апостроф `don’t` вместо `don't`. Практика: искать по куску без апострофов и кавычек либо прогонять обе стороны через нормализацию, а вывод «источник не подтверждает» делать только после этого.
- **Грепаешь МАРКЕР → якорно: точный путь, граница слова, уникальная строка** (#219 — `grep -i 'FACTS'` поймал «arti**facts**» и объявил 9 родственных файлов на чистом клоне)
- **Регексп по тексту, длину СТРОКИ которого ты не контролируешь (чужой HTML, ответ API, дамп `strings`, минифицированный бандл), — только `grep -aboF 'литерал' файл | head -20`,** контекст резать питоном по байтовому смещению: `.{0,N}…{0,M}` и альтернация дают катастрофический бэктрекинг по ДЛИНЕ СТРОКИ. 18.08 — три агента в трёх проектах за вечер, по ~5.6 ГБ RSS; при `OOMScoreAdjust=800` ядро убьёт оркестратор, а не греп
- **Проверяешь живость бэкенда через прокладку (прокси, CDN, релей) → assert'ь на БАЙТ, который может произвести только бэкенд**, а не на «код ответа + латентность»: их подделывает любая прокладка (12.08 — три ложных подтверждения подряд при ориджине по 20 000 мс). Два `Host` на одном IP = два РАЗНЫХ vhost
- **Переписываешь ОБЩУЮ историю (`push --force`, чистка секретов) → согласуй с другими контурами ДО и проверь ОБА направления: «секретов нет» И «чужие коммиты на месте» (`git merge-base --is-ancestor <их SHA> <новая история>`)** — 12.08 проверяли только первое, чужой коммит исчез
- Находка/чужой красный тест протухают между пакетами → сверяй с ТЕКУЩИМ файлом И с main; зеркально — не проверяй «текущий код» в ГЛАВНОМ чекауте, работая в ветке (#189). Говорить явно, про какое дерево утверждение
- Эвал/судья назначил фикс → открой СЫРЫЕ флагнутые выходы и фикстуру перед починкой: 3 из 5 флагов были артефактом стенда
- **Греп вернул список файлов, и ты пишешь «этого нигде нет» → открой первые N по УБЫВАНИЮ числа совпадений** (#238 — файл с дословной искомой строкой стоял ВТОРЫМ в собственном выводе автора)
- **Два агента НЕЗАВИСИМО увидели одно изменение окружения → проверь общее изменяемое состояние вне worktree** (user-конфиг, env, системный бинарь) и сними подозреваемый ключ как разрешающий контроль (#251 — вывод «модели плавают у провайдера» отозван: чужой ключ в общем `~/.grok/config.toml`). Правку вне своего worktree объявляй явно — в диффе её нет
- **Пишешь «единственный» / «seam один» → `grep -rn` ДО того, как предложение дописано; задача называет N точек — грепни ВСЕХ вызывающих** (#219 — греп дал 11 вместо «одного»; #154 — три названные оказались 11)
- **Проверка ПОЛНОТЫ, опознающая вызовы по форме `<объект>.метод(...)`, слепа к прямому импорту той же функции — и это не гипотеза, а замер.** Сканер #433 признавал только `manager.send*`/`session.send*` и не видел ни квалифицированного, ни импортированного напрямую `accept_message_delivery`; из-за этого мимо обязательного поля прошли ДВЕ живые точки записи (`app/routes/portfolio.py:342`, `app/portfolio_watchdog.py:188`), причём вторую не знал никто, пока детектор не починили. Порядок обязателен и он же доказательство: **сперва чини детектор и убедись, что он КРАСНЕЕТ на непочиненном коде, потом чини найденное.** Детектор, дополненный после починки вызовов, не доказывает ничего. И мутация делается по КАЖДОЙ найденной точке отдельно: одна общая не покажет, что сканер видит обе.
- **Вывел признак «данных не было» из ФОРМЫ записи и чистишь по нему историю → посчитай ложные срабатывания на строках, где данные ТОЧНО были** (#150 — 161 честная строка против 78 подделок)
- **«Исполняется ли тест вообще» проверяется мутацией его ПРЕДУСЛОВИЯ (логин, фикстура, доступность сервера), а не ассерта** (#145 — 16 тестов молча скипались и печатались зелёными)
- **Добавляешь флаг/переменную окружения, гейтящую СУЩЕСТВУЮЩЕЕ поведение → запинь значение фикстурой в тестах, идущих по загейченному пути.** Симптом: `grep -rn "<VAR>" tests/` совпадает только в тестах самого флага (#122 — `3 failed` на боевой конфигурации)
- **Посчитал агрегат по истории → сверь с ФИЗИЧЕСКИМ потолком периода, а не с ожиданием** (#162 — 6.2 лимита за 4.7 недели вскрыли 70 строк с фальшивыми нулями, курс ошибался на 40%)
- **Копия ЖИВОЙ SQLite ради доказательства — только `sqlite3.Connection.backup`, никогда `cp`:** при WAL свежие записи лежат в `-wal` (#155 — по `cp` механизм публично объявлен несработавшим, `backup()` показал обратное)
- Проверяешь чужую цифру о содержимом данных → разбирай их же парсером (`json.loads` + обход), а не грепом, и первой подозревай СВОЮ быструю проверку (#140 — 81 против 6)
- **Нужна модель/рантайм агента В ПРОШЛОМ → строки `model change:` из `logs` (или `turn_usage` по дням), а НЕ `sessions.model`** (там сегодняшнее состояние, переписывающее историю задним числом), **и считай по КОЛОНКЕ модели, не по имени агента** (#176, #219)
- **Правка цепляется к МНОЖЕСТВУ call sites → пересчитай их в `main` через `git show main:<файл>` и предпочти хук на ПЕРЕХОД состояния списку точек** (#269 — в ветке три точки, в `main` четыре)
- **Работа отложена в ОЧЕРЕДЬ, которую разгребает событие жизненного цикла (старт, коннект, деплой) → грепни всех, кто снимает условие постановки, и сравни с вызывающими дренаж** (#269 — три точки постановки при единственном дренаже в `lifespan`)
- **Защита стоит middleware на ТРАНСПОРТЕ (HTTP-роуты, RPC) → грепни ВНУТРИПРОЦЕССНЫХ вызывающих** (#269 — TG-мост кладёт сообщение прямо в сессию мимо HTTP-гейта)

**Чужая машина (ноут юзера — рабочий, не стенд)**
- **`systemd-run --user` в контуре агента НЕ РАБОТАЕТ и изоляцией не является (проверено 31.08, #422).** Отвечает `Failed to connect to user scope bus: $DBUS_SESSION_BUS_ADDRESS and $XDG_RUNTIME_DIR not defined` — у агентского процесса нет пользовательской шины. Хуже того, при попытке использовать его как песочницу сеть остаётся доступной И основной `.env` читается, то есть прогон дотягивается до БОЕВЫХ кред (наш класс аварий: 16–18.08 два `uvicorn` в worktree подняли второй TG-мост с боевым токеном). Рабочая изоляция — `bwrap`: `bwrap --ro-bind / / --unshare-net --dev /dev …` даёт `NETWORK_DENIED`, проверено обоими плечами. Прогон, которому нужен секрет, получает его ЯВНО одной переменной, а не наследованием `.env` целиком. Ограничение памяти для тяжёлых прогонов задавать иначе (`ulimit -v`, `nice -n 15`), одна модель за раз, не больше 2-3 параллельных. `nice` НЕ защищает от вытеснения по ПАМЯТИ — дважды за сутки выдавили чужое обучение сети. Потолок — в ПОСТАНОВКУ задачи, не в напоминание вдогонку
- Гейт свободной памяти считать по `MemAvailable` из `/proc/meminfo`, НЕ по `free`: при page cache они расходятся в 2-3 раза
- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов
- `/tmp` на ноуте — **tmpfs, то есть RAM** (1.6 ГБ «файлов» занимали оперативку). Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корень забит на 99%)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
