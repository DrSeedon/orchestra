# #276 — отвергнутые варианты различения «вопрос» vs «DONE»

Решение оркестратора 14.08.2026: **вариант 1**. Уже в main (`637029cd`,
исходный коммит ветки `1526225c`). Этот файл — чтобы не писать заново то, что
выглядит очевидным.

Инцидент: веер `Orchestra-orchestrator-8cee08b4`. Барьер снялся по факту
`send_message`, трое из четырёх ещё работали. Живой MCP-тул
`send_message(to, message)` **не передаёт** `message_kind` (проверено:
`app/mcp_stdio.py:937`, в JSON только `message`/`sender`/`scope`). Поэтому
«терминально при kind ∈ {done,failed,timeout,killed}» на агентском маршруте
даёт «никогда» — закрытие только дедлайном или концом хода.

Самообъявляемый kind ребёнком отвергнут отдельно: принуждение через промпт
не работает (#198 бюджет ×8 при прямой инструкции, #216, #227 запрет модели
нарушен 1/1).

## Принято: вариант 1

Конец хода (`fire_auto_report` на idle, не `WAITING` от bg job) терминален.
`send_message` в середине хода — нет, по построению, не по доверию к kind.

AC-2 («ребёнок спросил и закончил ход, ожидая ответа») **снят как недостижимый**:
заблокированный и закончивший работу неотличимы (idle + `_did_report` + пустой
ящик). Компенсация организационная: исполнителям велено не задавать вопросы
«на всякий случай».

## Вариант 2 — ОТВЕРГНУТ (не реализовывался)

Конец хода терминален **только если в этом ходе не было `send_message`**.

Ломает основной сценарий #231: честный DONE через тул перестал бы закрывать
веер. Ребёнок, который отчитался как просили в постановке веера, оставался бы
pending до дедлайна. Лечение хуже болезни.

## Вариант 3 — ОТВЕРГНУТ (не реализовывался)

Новый примитив «жду ответа» по образцу `AgentStatus.WAITING` у bg jobs.

Без самообъявления не заводится: отличить «жду ок» от DONE нечем. С
самообъявлением — снова промпт, который у нас не принуждается. Распознаватель
по тексту (`DONE` в теле) — вторая копия правды, сознательно запрещён.

Не писать вариант 3 заново, пока не появится состояние, которое ребёнок себе
не назначает.
