### 1.3 Равные `ts` — ноль, и что будет, если появятся

На моём (более свежем) снимке:

| проверка | результат |
|---|---|
| групп `(session_id, ts)` с >1 строкой | **0 из 179 763** |
| то же только по `tool`/`tool_result` | **0** |
| строк с пустым/NULL `ts` | 0 |
| пар с `result.ts == call.ts` | 0 из 43 264 |

Если равные `ts` появятся (например, кто-то начнёт писать `ts` секундной точности),
тайбрейк `(ts, id)` возвращает сравнение к `id`, то есть к исходному дефекту. Прогон
(`/tmp/rev340_eqts.py`) показывает, ЧЕМ именно это кончится:

```
equal ts, inverted ids, more rows after: statuses=['ambiguous','unresolved'] blocking=0
equal ts, inverted ids, call is last event: statuses=['ambiguous','pending'] blocking=1
equal ts, natural id order:                statuses=['completed']           blocking=0
```

То есть равные `ts` дают **не возврат вечного замка, а разъехавшуюся пару**: половинки
поедут как `ambiguous` + `unresolved`, гейт промолчит. Заблокирует только если такой вызов
окажется последней строкой снимка, и снимется первой же следующей строкой лога. Деградация
мягкая — это в пользу правки, но стоит знать, что тайбрейк не защищает, а лишь детерминирует.

### 1.4 Поправка к §1 отчёта: «0 из 42 661» — методическая, вывод устоял

**86 групп `(session_id, tool_use_id)` имеют больше одной строки `tool`**:

| сессия | рантайм | групп | вызовов |
|---|---|---|---|
| `grok-impl` | grok-4.5 | 82 | 164 |
| `plan-quota-controller` | codex | 2 | 4 |
| `fix-spawn-delivery`, `feat-landings-209` | codex | по 1 | по 2 |

Все 82 «инверсии» — из одной grok-сессии, где один и тот же `call-…` висит на РАЗНЫХ
вызовах (разные `tool_name`). Вывод автора («порядок `ts` верен») от этого не страдает:
настоящих инверсий `ts` в честных парах по-прежнему ноль. Но у факта есть следствие в коде,

(до неё осиротевший эффект блокировал вечно, теперь уедет как `unresolved`) — но при разборе
следующего инцидента с Grok об этом надо помнить. *suggestion*

## 2. Шов «что считать блокирующим»: контрпример СУЩЕСТВУЕТ, но на данных не наблюдается

### 2.1 Инвариант в комментарии кода эмпирически ложен

`runtime_history.py:437-440` утверждает дословно: *«A call the transcript continued past can
never become completed: its turn is over, so no result row will ever arrive for it»*.
Проверка по всей живой истории (сопоставление в порядке `ts`, как в правке):

| факт | число |
|---|---|
| пар вызов↔результат | 43 096 |
| **пар, между которыми в логе есть хоть одна строка** | **4 615 (10.7%)** |
| из них: между вызовом и его результатом успел прийти результат ДРУГОГО вызова | **1 863 (140 сессий)** |
| типы вклинившихся строк | `tool` 4 428, `tool_result` 4 297, `subagent_start/end` 3 711, **`user_message` 152**, `text` 113, `status` 98 |

То есть «после вызова есть строка» НЕ доказывает, что ход закончился: в 10.7% случаев
результат вызова приходил ПОСЛЕ посторонних строк. Механизмов два, оба измеренные:
**параллельная пачка вызовов** (модель шлёт Read+Grep+Bash одним сообщением, быстрые
возвращаются раньше долгого) и **сообщение, вклиненное в живой ход** (152 строки
`user_message` внутри интервала вызов→результат — штатный режим Orchestra).

Оба контрпримера прогнаны против нового кода (`/tmp/rev340_eqts.py`):

```
parallel batch, in-flight call not last (sibling result after it):
    statuses=['unresolved','completed'] blocking=0 unresolved=1
in-flight call + injected user_message after it:
    statuses=['unresolved'] blocking=0 unresolved=1
```

Долгий `Bash`, который в этот момент РЕАЛЬНО исполняется, классифицируется как «результата
уже не будет» и пропускается. Это ровно тот случай, про который спрашивала постановка:
строки после вызова появились по ДРУГОЙ причине.

### 2.2 Почему это всё-таки не блокер: два независимых ограничителя

**(1) Гейт `RUNNING`.** `app/session.py:4292` отказывает раньше: `if self.status ==
AgentStatus.RUNNING: return {"ok": False, "error": "cannot change model while running"}`.
Пока статус честен, снимок посреди живого хода не берётся вовсе. Известная щель одна и она
задокументирована: `app/session.py:1007` — при усыновлении живого CLI без сохранённого
`active_turn_id` статус ставится `IDLE`, хотя ход продолжается (замер #230 в `CLAUDE.md`:
три агента с пустым `active_turn_id`). В этой щели контрпример 2.1 достижим.

**(2) Строгий предикат ничего бы не изменил — на данных.** Я собрал альтернативу, которую
подсказывает собственная форензика автора (§2.1 отчёта): блокировать вызов, пока после него
не встретилась строка, ДОКАЗЫВАЮЩАЯ смерть хода (`status: turn ended…`, `⏹️ stopped`,
маркер рестарта). Прогон обоих правил по всей истории:

```
сессий с >=1 непарным вызовом (сопоставление по ts): 191
непарных вызовов всего:                              1 162
сессий, блокируемых ПРАВИЛОМ АВТОРА (вызов — последняя строка): 2
сессий, блокируемых строгим предикатом (нет turn-end после вызова): 2
вызовов, отпущенных правилом автора БЕЗ доказательства конца хода: 0
```

Ноль. Оба правила блокируют одни и те же две сессии. Значит выбранное «есть хоть одна
строка после» на реальных данных совпадает со строгим «ход доказанно закончился», и
удорожать правку ради 2.1 незачем. **Рекомендация — не менять предикат, а исправить
комментарий:** он обещает инвариант, которого нет, и следующий агент построит на нём вывод.
Формулировка по факту: «после вызова есть строки → его ход почти наверняка закончился;
исключение — параллельная пачка и вклиненное сообщение, достижимые только при снимке
посреди живого хода, который отсекает гейт RUNNING». *suggestion*

### 2.3 Две оставшиеся заблокированными сессии — проверил поимённо

`review-337-opus` (claude-opus-5, **status=idle**, последняя строка — незакрытый `Bash` от
`2026-08-18T15:33:01`) и `rev340-opus` (я сам, `running`, снимок пойман посреди `Bash`).

например ответом на сообщение») закрывает вопрос без кода. *suggestion*

## 4. BLOCKING: журнальная строка про `unresolved` на нормальном пути НЕ пишется

**Файл:** `app/session.py:1879` (ранний `return`) против `app/session.py:1906-1913` (warning).

`_prepare_runtime_handoff` вызывает `prepare_runtime_handoff_snapshot(..., build_record)`.
При успешной ПЕРВОЙ подготовке `build_record` возвращает и запись, и готовый
`PreparationResult`, поэтому строка 1879 `if result is not None: return result` выходит из
функции **до** блока с `logger.warning`. Код с журналом достижим только когда
`prepare_runtime_handoff_snapshot` нашёл УЖЕ СУЩЕСТВУЮЩУЮ запись (`db.py:2286-2291`,
идемпотентный повтор с тем же `idempotency_key`).

Проба (`tests/test_zz_rev340_probe.py`, мой файл в скретч-копии, авторские тесты не трогались;
фикстуры импортированы из его же файла, `caplog` на логгер `app.session`):

```
FIRST  prepare: ok= True unresolved= 1 warning_logged= False
REPLAY prepare: ok= True unresolved= 1 warning_logged= True
1 passed
```

**Сценарий отказа конкретными данными.** `direct-research` едет с 28 эффектами `unresolved`,
`feat-review-council` — с 15 (числа из §5 отчёта). Оператор зовёт `change_worker_model` один
раз, получает `ok: True`, и НИ ОДНА из 43 записей нигде не всплывает: в журнале пусто,
`unresolved_effects` не читает ни один потребитель (`grep` даёт только два присваивания и
тесты), в ответе API поля нет. Второго вызова с тем же `idempotency_key` в штатной работе не
бывает — то есть предупреждение не сработает никогда.

Почему это блокер, а не suggestion: правка СОЗНАТЕЛЬНО расширяет класс пропускаемого
(1 162 вызова, из них 39 «убитых рестартом», где сайд-эффект мог остаться недоделанным), и
собственный комментарий автора называет журнал единственным компенсирующим контролем —
`app/session.py:1908`: *«The journal entry is the whole resolution path»*. Контроля нет.
Это прямое нарушение «fail loud» и пункта «не потерять запись о реально незавершённом
сайд-эффекте».

**Чинится тремя строками:** посчитать `unresolved` внутри `build_record` рядом с
`classify_handoff_effects` (строка 1820, где оно уже посчитано) и написать warning там же,
либо перенести блок выше строки 1879. Оракул — проба выше: warning обязан появляться на
ПЕРВОЙ подготовке. Дополнительно стоит положить `unresolved_effects` в успешный ответ
`change_model`, чтобы оператор видел цифру, а не только сервер-лог.
