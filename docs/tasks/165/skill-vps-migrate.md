# Переезд проекта на VPS Contabo

## Purpose
Довести проект с ноутбука до работающего оркестратора на общем сервере, не сломав чужие
боевые агенты, которые там уже живут.

## When to Invoke
- «как мне переехать на VPS», «перенести проект на сервер», «хочу копию на сервере»
- проекту нужна работа **без включённого ноутбука**: мониторинг, кроны, ответы в TG 24/7
- надо завести оркестратора проекта на сервере
- **НЕ сюда:** обновление самой Orchestra на её сервере; общение с уже живущими там
  агентами — для этого скилл `vps-orchestra`

## Pre-Flight Check

**1. Спроси владельца сервера ДО начала.** Не «можно ли переезжать вообще», а «нужен ли
VPS этому проекту». Сервер общий, и на нём чужие **боевые** агенты — рестарт Orchestra
рвёт активные ходы всех сразу.

**2. Убедись, что переезд вообще нужен.** Если проект и так разрабатывают при живом ноуте,
переезд даёт только вторую копию, которая начнёт расходиться с первой. Не переезжай по инерции.

**3. Запушь `main` на ноутбуке.** VPS тянет из `origin`, а не с твоей машины:
```bash
git rev-list --count origin/main..main    # должно быть 0
```
Не ноль → сперва пуш, иначе на сервер приедет вчерашний код.

**4. Оцени размер репозитория по `.git`, а не по каталогу:**
```bash
du -sh .git && git count-objects -vH
```
`du -sh` всей папки врёт в 10–20 раз (считает venv и артефакты). Нет `git remote -v` —
переезжать нечему, сперва заведи репозиторий.

## Что переезжает, а что нет

Ты **не** переносишь свою память и контекст. Сессия на VPS — новая сессия того же проекта:
тот же код, тот же `CLAUDE.md`, **пустая история диалога**.

- **Личная память агента подхватывается по совпадению ИМЕНИ** (`docs/workers/<имя>.md`) —
  назовёшь агента иначе, память не найдётся.
- **НО имя выбирается по тому, останется ли оригинал жив.** Контуры — независимые базы, и
  `send_message(to="имя")` резолвится внутри ОДНОГО инстанса Orchestra.
  - **Переезд** (на ноуте агента не остаётся) → имя то же, память подхватится сама.
  - **Дубль** (оба живут одновременно) → имя ОБЯЗАНО отличаться (`<имя>-vps`), иначе два разных
    агента под одним именем путают адресацию при каждой пересылке. Ценой того, что
    `docs/workers/<исходное-имя>.md` придётся положить в скоуп на VPS руками — одна операция
    против постоянной путаницы.
- **Историю диалога везти не надо и вредно** — переезжает рецепт (промпт, роль, файлы), а не
  транскрипт. Штатный путь (раздел 4) историю не везёт вовсе: транскрипт, логи, inbox и
  статистика субагентов остаются на ноуте. Это не потеря, а ровно то, что абзацем выше
  названо вредным. Единственное исключение — сноска про `migrate_agent.py` в разделе 4.
- Всё, что знаешь и не записал в файлы, при переезде теряется → **до переезда** запиши в
  `CLAUDE.md` и `docs/` то, что копия должна знать.

## Process Flow

### 1. Вход на сервер
```bash
ssh root@158.220.127.161
su -s /bin/bash kesha
```
Флаг `-s` обязателен: `su - kesha` **зависнет**, спросив пароль, которого у `kesha` нет.

**Золотое правило:** пакеты ставим от root, **всё остальное — под `kesha`**. Иначе получишь
каталог с разъехавшимися владельцами, который читается и запускается нормально, а падает
только на записи в `.git` — посреди деплоя, через месяц. Проверка:
```bash
find /home/kesha/projects/<name> ! -user kesha | wc -l   # должно быть 0
```

### 2. Клон проекта
```bash
cd /home/kesha/projects
git clone <репозиторий> <name>
```
Строго `/home/kesha/projects/<name>`. Не в `/opt` (там системное: боты, прокси) и не в корень
домашней папки. Remote — по SSH (`git@github.com:...`), ключ к GitHub на сервере уже есть.

Зависимости — под `kesha`. Для Python: `uv sync`. **Проверь свои extras:** `uv sync` без
`--extra` молча удалит пакеты, поставленные с флагом, а конфиг продолжит их обещать.
Проверяй фактом (`python -c "import <пакет>"`), а не отчётом установщика.

### 3. `.env` — прокси ВЫКЛЮЧИТЬ
**Прокси на VPS не нужен.** Сервер в Германии, `api.anthropic.com` отвечает напрямую —
проверено замером с самого сервера, без прокси-переменных:
```
api.anthropic.com/v1/messages → 405 за 0.053s
```
(`405 Method Not Allowed` на голом GET = ответ самого API: TLS и HTTP дошли.)

Копируешь `.env` с ноутбука — **закомментируй строки прокси**, иначе процесс будет стучаться
в несуществующий локальный порт и падать по таймауту:
```bash
# HTTPS_PROXY=http://127.0.0.1:12334
# HTTP_PROXY=http://127.0.0.1:12334
```
Права `600`, владелец `kesha`, в git не коммитить.

**Аутентификация — подписка.** На сервере логин через `claude login` (oauth).
`ANTHROPIC_API_KEY` не заводить и не копировать — отдельный ключ проекту не нужен.

**Порты.** Реестра `~/ports.md` на VPS нет (он только на ноутбуке). Свободный смотри через
`ss -tlnp`, свой сразу запиши в `CLAUDE.md` проекта — иначе следующий переехавший займёт тот же.

### 4. Оркестратор проекта — БЕЗ рестарта

Оркестратор заводится на **живом** сервере одним HTTP-вызовом. Рестарт не нужен и окна на
общем сервере ловить не надо: `POST /api/sessions` идёт через процесс Orchestra, а не мимо
него, поэтому сессия сразу живёт в памяти, а не только в БД.

Так переезжает всё, кроме истории диалога: строка сессии со всеми ~20 полями, MCP, личная
память, `CLAUDE.md`, worktree воркеров. Остаются на ноуте транскрипт, логи, inbox — то самое
«прошлое», которое везти и не надо.

**1. Имя и модель.** Имя — по правилу из «Что переезжает» (переезд → то же; дубль →
`<имя>-vps`). Модель пинить с `[1m]`: голый `claude-opus-5` даёт 200k контекста вместо 1M —
потеряешь 800k молча. Имя здесь важнее, чем кажется: `docs/workers/<имя>.md` подхватывается
**по совпадению имени в момент создания**. Ошибся именем — память молча не подхватится, а
сессия будет выглядеть здоровой.

**2. Файлы должны лежать на месте ДО вызова.** Клон (раздел «2. Клон проекта») уже принёс `CLAUDE.md` и
`docs/workers/<имя>.md`, если они закоммичены. Не закоммичены — положи руками сейчас, потом
поздно: память вшивается в промпт при создании, а `CLAUDE.md` агент читает с диска.
```bash
ls /home/kesha/projects/<name>/CLAUDE.md /home/kesha/projects/<name>/docs/workers/<имя>.md
git -C /home/kesha/projects/<name> remote -v      # нормальный клон, а не свалка от rsync
```

**3. Смержи работу воркеров ДО переезда.** Незамерженные ветки не доедут. Имя ветки платформа
считает сама (`task-<par>/<имя>` при `task_id`, иначе `feat/<slug>/<имя>`): не совпадёт —
заведёт новую от базовой, и коммиты воркера останутся в стороне, **а worktree при этом будет
выглядеть совершенно здоровым**. Молчаливая потеря работы, которую заметят через неделю.
Мержи на ноуте, переезжай с чистым `main`.

**4. Создай оркестратора на живом сервере.** Локальный `mcp__orchestra__spawn_worker` сюда НЕ
годится: он создаст агента в ЛОКАЛЬНОМ инстансе, инстансы независимы. Транспорт — `curl` с
кукой; **куку получи по скиллу `vps-orchestra`** (там же, почему зеркало `orc.seedon.ru`, а не
прямой адрес, и почему пароль не хранится в файлах).
```bash
curl -sk --noproxy '*' -b /tmp/orc-cookie.txt --max-time 30 \
  -X POST "https://orc.seedon.ru/api/sessions" \
  -H "Content-Type: application/json" \
  -d '{
    "name":"<проект>-orchestrator",
    "scope":"/home/kesha/projects/<name>",
    "cwd":"/home/kesha/projects/<name>",
    "model":"claude-opus-5[1m]",
    "is_orchestrator":true,
    "role":"orchestrator",
    "description":"lifecycle=persistent — оркестратор проекта <name>",
    "mcp_servers":{}
  }'
```
Ответ `201` с `id` — строка создана. Это ещё не приёмка, см. шаг 7.

`mcp_servers` — сюда сразу свои MCP (websearch, pandoc и т.п.) в формате `.mcp.json`. Отдельной
операции «прописать MCP» нет и не нужно: платформа сохранит их в `mcp_servers_custom` и
подмешает к вшитому `orchestra`. Не нужны — оставь `{}`.

`tg_topic` не передавай: корневому оркестратору платформа включает его сама. В группе появится
новый топик — это штатно, а не сбой.

**5. Воркеров, скорее всего, заводить не надо** — их спавнит уже переехавший оркестратор по
мере задач. Если всё же нужен сразу: тот же эндпоинт, но ПОСЛЕ оркестратора (воркер ищет
родителя среди существующих) и с четырьмя добавками к телу запроса: `"role":"worker"`,
`"use_worktree":true`, `"repo_path"` = каталог проекта, `"parent_name"` = имя оркестратора.
Git worktree и ветку платформа создаст сама — клонировать и линковать руками не надо.

**6. Погаси исходную сессию на ноуте.** Обязательный шаг, а не уборка «когда-нибудь». На этом
пути нет гейта `assert_idle` из скрипта — ничто, кроме тебя, не мешает одному агенту жить на
двух хостах и расходиться. Оставишь обоих живыми — сам же потом не разберёшь, чей `docs/`
свежее. Гасить только после успешной приёмки (шаг 7).

**7. Приёмка — ответом, а не кодом 201.** `201` доказывает только, что строка создана. Живая
она или мёртвая, показывает единственная проверка: агент отвечает.
```bash
curl -sk --noproxy '*' -b /tmp/orc-cookie.txt --max-time 25 \
  -X POST "https://orc.seedon.ru/api/sessions/<проект>-orchestrator/send" \
  -H "Content-Type: application/json" \
  -d '{"message":"<рабочая задача из раздела 6>","scope":"/home/kesha/projects/<name>"}'
```
Формулировку задачи бери из раздела «6. Приёмка» — там же критерий, почему общий ответ
считается провалом.

> **Сноска: когда всё-таки нужен `scripts/migrate_agent.py`.** Ровно один случай — надо, чтобы
> копия проснулась **с памятью диалога** (клонирование конкретной живой сессии, а не переезд
> проекта). Скрипт везёт транскрипт и дочерние строки, но пишет в БД мимо процесса, поэтому
> требует `systemctl restart orchestra` — а он рвёт активные ходы **всех** агентов сервера.
> Тогда: скрипт запускает кто-то снаружи (гейт `assert_idle` считает тебя `running`, пока ты
> отвечаешь), а рестарт не лови сам — попроси владельца совместить с плановым. Для обычного
> переезда проекта это анти-цель: копия должна начать с чистой головы.

### 5. Хендофф — файлом, не сообщением
Написать копии текст в чат **не работает**: сообщение сгорит на первом компакте. Пиши файл в
репозиторий проекта (`docs/HANDOFF-to-vps.md`) и ссылку **первой строкой** в `CLAUDE.md`.

Что писать — не пересказ коммитов (их видно в `git log`), а то, чего нет в файлах: решения и
**причины отказов** от альтернатив, факты, которые выглядят иначе, чем называются, что сломано
и чинить не надо, незакрытые вопросы с критерием проверки.

### 6. Приёмка
Не «сервис создался», а «работает и делает своё». Каждая проверка должна давать **разный
вывод при успехе и провале**:
```bash
systemctl is-active <юнит>                                    # active
journalctl -u <юнит> --since "5 min ago" | grep -iE "traceback|error|critical"   # пусто
git rev-parse --short HEAD                                    # ожидаемый коммит
find /home/kesha/projects/<name> ! -user kesha | wc -l        # 0
```

**Главная проверка для оркестратора — не викторина, а рабочая задача с проверяемым
результатом:** «прочитай хендофф, сделай X, отчитайся id». Одним ходом проверяется чтение
файлов, живой MCP и способность довести до артефакта. Формулируй так, чтобы **общий ответ
считался провалом**: «ответ уровня „был баг с контекстом“ = файлы не прочитаны, переезд не
состоялся». Иначе получишь пересказ вопроса вместо знания.

## Ограничения сервера

Памяти 24 ГБ, свободно обычно ~18 ГБ, swap 16 ГБ, диск 247 ГБ свободно — то есть **дело не в
дефиците**. Осторожность нужна по другой причине: **сервер общий, на нём чужие боевые
агенты**. Тяжёлую нагрузку (бенчмарки, ML-модели, полные прогоны) согласовывай с владельцем
независимо от того, что показывает `free`. Потолок памяти для своих прогонов:
```bash
systemd-run --scope -q -p MemoryMax=3G --uid=kesha --gid=kesha nice -n 15 <команда>
```
`sudo -n -u kesha systemd-run --scope` не работает (`Interactive authentication required`) —
запускай scope от root с `--uid`/`--gid`.

## Error Handling

| Симптом | Причина | Что делать |
|---|---|---|
| `su - kesha` висит | у `kesha` нет пароля | `su -s /bin/bash kesha` |
| `uv: command not found` под `kesha` | нет в `PATH` | `/home/kesha/.local/bin/uv` или `.venv/bin/python` |
| `ModuleNotFoundError: app` | heredoc через ssh из `/tmp` | запускать из каталога Orchestra |
| таймауты к API | скопирован `.env` с прокси ноутбука | закомментировать `HTTPS_PROXY`/`HTTP_PROXY` |
| `git fetch` падает через месяц | поработали от root | `find ! -user kesha`, `chown` со снимком прав |
| `detected dubious ownership` | каталог `kesha`, ssh под root | `git config --global --add safe.directory <путь>` |
| скилл с ноутбука мёртв на сервере | хардкод `/mnt/data/...` | грепать пути перед использованием |
| `403 cwd not in allowed paths` | `cwd` вне разрешённых корней Orchestra | держать проект в `/home/kesha/projects/<name>`; `.git`/`.env`/`.claude` в пути запрещены |
| `409 worker '<имя>' already exists` | сессия с таким именем в этом скоупе уже есть | не пересоздавать — либо другое имя (`<имя>-vps`), либо гасить старую |
| агент создан, но память не подхватилась | `docs/workers/<имя>.md` не было на диске в момент создания | положить файл и **пересоздать** сессию — задним числом не вошьётся |

**Любой деструктивный шаг** (`systemctl stop/restart`, `UPDATE`, `chown -R`, `git reset`) —
сперва скажи владельцу, что и зачем, и дождись подтверждения. Разрешение на переезд ≠
разрешение на любые операции на общем сервере.

Застрял — пиши `Orchestra-orchestrator`, он этот путь прошёл целиком.
