# #427 — успешный мерж объявляется PARTIAL из-за служебного счётчика

Разбор баг-репорта kesha-tg-bot-orchestrator от 01.09.2026 (операция
`82fcf78b-e1e5-412b-8b41-07baf575d697`, задача #33 проекта kesha-tg-bot).

## Что произошло

Мерж дошёл до commit point: `main` получил `e198fe8`, приёмка зелёная (`70 passed`),
дерево воркера чистое. Дальше финализация вернула
`RuntimeError: canonical task finalization failed: task update failed`, операция стала
`PARTIAL` и заблокировала воркера до ручного `resolve_merge_operation`.

Сохранённый payload операции показывает, что обновление статуса **применилось**:

```json
"task_status": {"ok": false, "error": "task update failed",
 "result": {"ok": true, "new_status": "done", "updated": ["status"],
            "shadow_match": false,
            "projection_debt": {"mismatches":
              {"sync_revision": {"canonical": 2, "legacy": 3}}}}}
```

То есть внутренний результат — `ok: true`, статус выставлен. Отказ произвёл гейт
`_apply_finalization_task_update` (`app/tm.py:1205-1217`): он принимает расхождение
двух хранилищ ровно одного вида —

```python
replay_match = (result.get("shadow_match") is False
                and set(mismatches) == {"updated"}
                and result.get("new_status") == status)
```

`{"sync_revision"}` в это исключение не входит, поэтому применённое обновление
объявляется провалом, а сообщение вырождается в дефолт `"task update failed"` —
причина в тексте не называется вовсе.

## Почему это не единичный случай

`sync_revision` — служебный счётчик, и он расходится у трети задач, причём в ОБЕ
стороны (значит это не однонаправленный дрейф от второй двери записи):

| | задач |
|---|--:|
| `sync_revision` совпадает | 180 |
| **расходится** | **89 (33%)** |

Примеры: kesha-tg-bot #19 legacy=3 / canonical=4, #2 legacy=1 / canonical=2,
#33 legacy=4 / canonical=2.

Мержи за неделю (с 25.08): 147 операций, из них 11 `PARTIAL`, и **2 из 11 упали именно
на этом сравнении** при `ok: true` внутри.

## Связь с #426

Репортёр связал отказ с задержкой записи (#426, 18–21 с). Связи нет: в payload видно, что
запись успела и вернула `ok: true` — валит не таймаут, а сравнение полей. #426 остаётся
отдельным дефектом.

## Кандидаты на фикс (не выбраны)

- Исключить `sync_revision` из полей, по которым считается `shadow_match` для финализации:
  поле легаси-синхронизации не описывает содержимое задачи.
- Либо, если совпадение обязано держаться, найти вторую точку записи — но расхождение в
  обе стороны против этой версии.
- Отдельно: `detail` в `app/tm.py:1211` обязан называть конкретное расхождение, а не
  дефолт `"task update failed"` — сейчас причина видна только в сыром payload операции.
