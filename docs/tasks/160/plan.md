# #160 — план: сохранить признак прерванности через рестарт

Scope: ТОЛЬКО первый дефект (потеря признака «был прерван»). `_pending_messages` (F4) —
отдельная задача, в этот коммит не входит.

## Ключевое уточнение к research.md (проверено при планировании)

`session.stop()` имеет **ровно одного вызывающего** — `shutdown_all` (`manager.py:1759`).
Пользовательский стоп идёт другим путём: `routes/sessions.py:549` → `manager.stop_worker`
(`:939`) → `session.interrupt()` (`session.py:1163`), который ставит `_manually_interrupted`
и НЕ трогает `stop()`.

Следствие: различать два случая ВНУТРИ `stop()` не нужно — `stop()` и есть путь
выключения сервера. Правка сводится к тому, чтобы `stop()` не затирал `running`, а
переводил его в устойчивый признак прерванности. Это проще, чем предполагал research.md,
и не требует нового флага в сигнатуре.

## Решение

Использовать существующую колонку `status` со значением `interrupted` — отдельный
терминальный статус для «сервер выключился, пока агент работал».

Почему не новая колонка: `status` уже персистится, уже читается стартом, уже
мигрируется. Новая колонка = миграция + второй источник правды о состоянии агента
(грабля «одна мысль = один owner»). Почему не `running`: старт обязан различать
«процесс жив и работает» от «процесс мёртв, ход оборван» — оставить `running` в БД
значило бы врать дашборду в окне до `auto_resume_all`.

### T1 — `stop()` сохраняет прерванность
- Files: `app/session.py:1718-1726`
- `stop()` пишет `AgentStatus.INTERRUPTED` вместо `IDLE`, ЕСЛИ на входе `status == RUNNING`.
  Иначе (idle/waiting — агент честно закончил) — прежний `IDLE`. Это и есть fail-closed в
  обе стороны на уровне записи.
- Новый член `AgentStatus.INTERRUPTED = "interrupted"`.
- AC:
  - сессия в `RUNNING` после `stop()` → в БД `interrupted`
  - сессия в `IDLE` после `stop()` → в БД `idle` (признак НЕ появляется у того, кто закончил)
- blocked-by: none

### T2 — `auto_resume_all` будит по новому признаку
- Files: `app/manager.py:1646-1704`
- `was_running` читает `status IN ('running','interrupted')` — `running` остаётся ради
  hard-kill (арм B, сейчас единственный работающий путь; ломать его нельзя).
- Строка сброса (`:1661`) добавляет `interrupted` в список нормализуемых в `idle`.
- Восстановление (`:1655`) добавляет `interrupted` в `status IN (...)`, иначе сессия
  вообще не попадёт в `resumable`.
- AC:
  - арм A (graceful): `restart notices sent: 0` → `1`
  - арм B (hard kill): по-прежнему `1` — регрессии нет
  - агент, честно закончивший ход до рестарта, пинка НЕ получает
- blocked-by: T1

### T3 — статус не течёт в UI как незнакомое значение
- Files: проверить словари статусов (`app/static/js/*`, шаблоны, `_display_status`)
- `interrupted` живёт в БД доли секунды (до `:1661`), но грабля «словари статусов
  продублированы в двух местах» требует проверки, что незнакомое значение не ломает
  рендер, если старт упал между записью и нормализацией.
- AC: `interrupted` либо отображается осмысленно, либо не встречается в путях рендера
- blocked-by: T1

## Тесты (порядок обязателен: RED → GREEN → мутация)

`tests/test_manager.py`, новый класс `TestRestartWake`:
1. `test_graceful_restart_wakes_interrupted_worker` — арм A, КРАСНЫЙ до фикса
2. `test_hard_kill_restart_wakes_worker` — арм B, зелёный до и после (защита от регрессии)
3. `test_idle_worker_not_woken_after_restart` — обратная сторона fail-closed:
   честно закончивший ход пинка не получает

Мутация: откат `app/session.py` через `git show <commit>^:app/session.py`, подтверждение
маркером `grep -c INTERRUPTED` (в откаченной версии = 0), прогон → тест 1 обязан покраснеть.
НЕ `git stash`.

Асинхрон: готовый набор прогнать 4 раза подряд.

## Что НЕ трогать
- `_pending_messages` (F4) — отдельная задача
- `interrupt()` — пользовательский стоп работает корректно, не в scope
- фильтр `session_id IS NOT NULL` — известный отдельный риск (mid-compact), не причина #160
- живой сервис — не рестартить
