# #33 — дубли запросов при загрузке дашборда

Вторая половина жалобы «долго грузит». Причину каждого дубля искал перехватом `fetch`
со стеком вызова (`page.add_init_script` до загрузки страницы), поэтому ниже не гипотезы,
а имена функций.

## Причины — их действительно три разных

### 1. Шторм панели задач на проигрывании истории (главный)

```
/api/tm/tasks — 8×
   +  655 мс  window ← loadTasks ← addChatEntry ← _renderHistory
   +  687 мс  window ← loadTasks ← addChatEntry ← _renderHistory
   … ещё шесть таких же за 250 мс
/api/tm/payments/status — 8×   (те же стеки)
```

`addChatEntry` при отрисовке строки с вызовом `task_create` / `task_update` /
`payment_receive` дёргает `loadTasks()` — обновить панель. Для ЖИВОГО вызова это верно,
но при отрисовке истории те же строки — прошлое, и каждая из них перезагружала панель
целиком. Восемь пар запросов за 250 мс на одном заходе.

Два отягчающих обстоятельства:
- **`_tasksTabActive` не проверялся**: в замере панель задач была закрыта, а девять
  полных загрузок всё равно уходили. Трафик ради невидимого элемента.
- **#32 усилил дефект**: страница чата выросла с 20 строк до 100, то есть в пять раз
  больше исторических строк, каждая из которых могла попасть в этот `if`. Мой же вчерашний
  фикс сделал этот баг заметным — честно записываю.

Починка: флаг `_replayingHistory` (владелец — `_renderHistory`, `_completeChatPage`,
`loadMoreLogs`), и побочный эффект выполняется только вне проигрывания.

### 2. `/api/tm/payments/status` — 404 c 14.05, спрашивался в каждом круге опроса

Роут отвечает `{"error":"No client specified and no client found for project scope"}`
со статусом 404, потому что к этому проекту не привязан клиент. Панель задач опрашивается
каждые 5 секунд → двенадцать 404 в минуту и столько же красных строк в консоли.

**Решение: помним scope, для которого клиента нет, и больше не спрашиваем.** Конфигурация
не меняется на ходу, поэтому один вопрос на scope за загрузку страницы достаточно.

Почему не серверный вариант (отдавать 200 с `{"client": null}`, раз «клиента нет» — это
нормальное состояние, а не ошибка): он честнее по смыслу, но (а) требует рестарта, чтобы
вступить в силу, то есть до рестарта ничего не чинит; (б) меняет контракт для второго
потребителя — MCP-тула `payment_status` (`app/mcp_stdio.py:1546`), которого задача не
касается; (в) 404 на «ресурса для этого проекта не существует» — защитимая семантика.
Если владелец захочет серверный вариант — это одна строка в `app/routes/tm.py`, но тогда
надо править и MCP-тул.

### 3. `/api/models` ×4 и `/api/orchestrators` ×4 — это НЕ дубли

```
/api/models        +19 мс api ← loadModels ← HTMLDocument     (инициализация)
                 +3030 мс window ← _heartbeatProbe            (каждые 3 с)
/api/orchestrators +20 мс api ← loadOrchestrators ← HTMLDocument
                  +476 мс api ← refreshSessions               (каждые 3 с)
```

- **`/api/orchestrators` в `refreshSessions` нужен логически**: по свежему списку
  считается, что в ЧУЖОЙ вкладке закончился ход, и ставится метка непрочитанного
  (`_orchestratorTurnFinished`). Убрать — потерять метки. Оставлен, объяснение здесь.
- **`/api/sessions`, `/api/stats`, `/api/sessions/<agent>/context` по 3×** — это круг
  опроса раз в 3 с, а не повтор в одном проходе. Не трогал.

**Но одну цену стоит записать: heartbeat тянет 4.7 КБ каждые 3 секунды ради статуса
и одного заголовка.** `_heartbeatProbe` бьёт в `/api/models` (#15 выбрал его, потому что
там едет `X-Orchestra-Build`) и читает только `r.status` и заголовок — тело в 4.7 КБ
выбрасывается. Это 1.57 КБ/с постоянного фона на канале, где у юзера 15–80 КБ/с.

Не чинил здесь, и вот почему: правильная правка — разрешить методу HEAD
(`methods=["GET", "HEAD"]`), тело тогда не поедет вовсе. Проверено: сейчас
`HEAD /api/models` → **405**. Значит клиентская правка «слать HEAD» в окне до рестарта
получала бы 405 без заголовка версии и молча ломала баннер #15 — ровно тот класс, который
мы чинили в #22 и #29. Это отдельная задача с бэкендом и рестартом.

## Замеры до/после

**Окно замера: от логина до 9-й секунды**, свежий профиль браузера. Окно указываю явно,
потому что оно определяет цифру: каждые 3 с идёт круг опроса (`/api/sessions`,
`/api/stats`, `/api/orchestrators`, `/api/models`, `/context`), и на более длинном окне
общее число запросов растёт линейно, а разница «до/после» остаётся той же.

Независимая проверка perf (`de9505f`, окно 10 с после `load`, три захода подряд):

```
main сейчас         cold/warm1/warm2:  46 / 46 / 45 запросов, tm/tasks 9, payments 9
ветка 934d491:                         28 / 28 / 27 запросов, tm/tasks 0, payments 0
```

Его 28 и мои 23 — одна и та же величина в разных окнах. Совпадает главное: всплеск
исчезает во всех трёх плечах, включая заходы с тёплым зеркалом.

**Через nginx, домен — то, что видит юзер** (`transferSize` из Resource Timing, то есть
сжатые байты по проводу):

| | запросов | по проводу |
|---|---:|---:|
| до | 41 | 196 КБ |
| после | **23** | **169 КБ** |
| разница | −18 (−44%) | −27 КБ (−14%) |

Что ушло: `/api/tm/tasks` 9× / 25.1 КБ → 1×, `/api/tm/payments/status` 9× / 3.4 КБ → 1×.

**Локально, мимо nginx** (несжатые тела; помечаю как локальные — по договорённости после
расхождения с perf):

| | запросов | байт |
|---|---:|---:|
| до | 41 | 725 КБ |
| после | 24 | 654 КБ |

Разница в общих байтах меньше, чем в запросах, потому что вес забирают две крупные
однократные загрузки: `/api/logs/sync` 111 КБ (холодное зеркало, один раз на браузер) и
`/api/sessions/<agent>/logs` 33 КБ (страница чата). В обычном сеансе с тёплым зеркалом
первой нет вовсе, и доля убранных дублей в остатке заметно выше.

### Оговорка о методе: `page.route` выключает кеш браузера

perf указал на это, и оговорка касается всех моих проверок фронта, потому что подмена
`app.js` через `page.route` — мой основной способ проверить ветку на живом сервере.
Включённый перехват отключает HTTP-кеш целиком: статика перекачивается в каждом заходе,
а подменённый файл приезжает несжатым. Значит из таких прогонов **достоверны число
запросов и поведение, но не байты статики и не тайминги**.

Мои цифры выше это не задевает: я считал `transferSize` только по записям `/api/`, а
ответы API динамические и не кешируются, поэтому перехват на них не влияет. Направление
разницы тем более безопасно: «после» мерилось С перехватом (кеш выключен), «до» — без
него, то есть если бы кеш и играл роль, он завышал бы «после», а оно и так меньше.

Тайминг главного потока этим способом мерить нельзя вовсе — perf проверит его после
мержа в main, без подмены, против опоры 871/1186 мс из #32.

## Проверка, что фича не сломана

```
вкладка задач открыта, 13 с опроса: {'tm/tasks': 3, 'tm/payments/status': 1}
scope без клиента запомнен:         ['/home/kesha/orchestra']
после ЖИВОГО task_update:           {'tm/tasks': 1}
```

- Три круга опроса дали три загрузки задач (это собственный таймер панели, 5 с) и **один**
  запрос платежей вместо трёх.
- Живая строка `task_update` по-прежнему обновляет панель — подавлено только проигрывание
  истории.
- Флаг `_replayingHistory` после отрисовки равен `false` (не течёт).
- При закрытой вкладке задач запросов к `/api/tm/` теперь ноль (было девять).

  выставляют `_replayingHistory` (через `try/finally`, иначе исключение в отрисовке
