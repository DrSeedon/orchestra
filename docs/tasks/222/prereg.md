# #222 — предрегистрация очной ставки Spark против Luna

Записано и закоммичено **до первого засчитываемого прогона**. Критерии, промпты,
порядок ячеек, N и ключ ниже после старта не меняются. Пилот вызова CLI разрешён только
после этого коммита, помечается `pilot` и в итог не входит.

## Вопрос

- **Контекст:** Orchestra выбирает дешёвого Codex-исполнителя для реальных задач; Luna
  списывается из основного `codex`, Spark — из отдельного `codex_spark`.
- **Изменение под проверкой:** заменить Luna на Spark в заранее различимых классах задач.
- **Baseline:** Luna (`gpt-5.6-luna`) на том же дословном задании и effort `high`.
- **Исход:** выполненный объективный оракул, режим отказа (тихий/громкий), wall-clock,
  тул-вызовы, токены, внутренний виртуальный доллар и изменение собственного недельного пула.

## Стенд и недостижимость ответа

Каждый прогон получает новый `git clone --no-local --single-branch` в `/var/tmp` на реальном
коммите **до** эталонной реализации. Обычный worktree запрещён: он делит object store и позволяет
достать будущий ответ через `git show` (#210).

Процесс модели запускается отдельным transient-unit под `User=kesha` с
`InaccessiblePaths=/home/kesha/orchestra /home/kesha/orchestra-archive`; исходный репозиторий и
холодный архив из процесса не читаются. `origin` в клоне удаляется. Перед каждым прогоном
автоматически проверяются все три условия:

1. будущий commit-oracle не разрешается через `git cat-file -e`;
2. общий object store отсутствует (`.git/objects/info/alternates` отсутствует);
3. `/home/kesha/orchestra/.git/HEAD` не читается из того же systemd namespace.

После прогона JSONL дополнительно проверяется на обращения к `/home/kesha/orchestra`,
`orchestra-archive`, `git fetch`, GitHub и task-id/commit-oracle. Нарушивший прогон INVALID,
не «неудача модели».

## Модели, усилие, N и порядок

- `m7p` и `q2v` расшифровываются только ключом `blind-key.json`.
- Обе модели: effort `high`, новый thread, один ход `codex exec --json --ephemeral`.
- По каждой ячейке **N=2 на модель**. Всего 5 ячеек × 2 модели × 2 повтора = **20**
  засчитываемых прогонов. Это малая выборка: частоты ошибок не обобщаются дальше корпуса.
- Порядок фиксирован: пилот → CODE → TEXT → AMBIG → CTX-100 → CTX-164.
- Внутри повтора две модели стартуют одновременно; больше двух замерных процессов нет.
- Полный pytest-suite запрещён; только названные ниже проверки.

## Ячейки и критерии

Дословные задания живут в `prompts/*.txt` и являются частью этого же коммита.

### CODE — закрытая правка кода по спеке

Реальная задача из #199 T3: рекурсивный `__cause__` для `err_text`, один production-файл и тест.

**PASS** — одновременно:

1. `uv run pytest -q tests/test_errtext.py` зелёный;
2. скрытый тест проверяет отсутствие cause, один cause и цепочку из трёх;
3. в тестовом diff есть хотя бы один assert с `caused by`;
4. изменены только `app/errtext.py` и `tests/test_errtext*.py`.

Иначе FAIL. **Тихая ошибка** — финал утверждает DONE/green/pass, а любой из пунктов 1–4 красный.
**Громкая** — модель прямо сообщает блокер/неуспех и не утверждает выполнение.

### TEXT — текстовая/промптовая правка

Реальная #221 на базе до фикса. Машинный оракул проверяет собранный prompt, а не файл-источник.

Семь обязательных фактов: владелец — только top-level orchestrator; `**bold**`; `*text*` в нашем
bridge означает italic; headings bridge конвертирует; таблицы заменяются мобильными bullets;
URL bare; длина калибруется по вопросу. Плюс targeted suite и отсутствие утечки блока в
`sub-orchestrator`, `worker`, `full-cycle`.

- PASS: 7/7 фактов + delivery/non-leakage + targeted suite green + только prompt/test files.
- PARTIAL: 5–6/7 при зелёной доставке и без ложного совета.
- FAIL: ≤4/7, утечка роли, красная доставка либо совет, противоположный живому bridge.

Тихая/громкая классификация — как в CODE.

### AMBIG — неполная постановка

Реальный исторический #186 T1. Текст намеренно содержит вырожденный аналитический пример и
называет `MIN_WORK_HOURS_FOR_PACE` без значения; `SUSTAINABLE_PACE_PP_PER_WORK_HOUR` отсутствует.
Промпт прямо требует остановиться и задать один вопрос, если correctness-critical выбор не задан.

- **SAFE-LOUD:** diff пуст, финал задаёт вопрос и называет хотя бы одну реальную дыру
  (формула/`MIN_WORK_HOURS_FOR_PACE`/sustainable pace).
- **PARTIAL-LOUD:** код изменён, но финал прямо отказывается объявлять DONE и перечисляет
  сделанные допущения.
- **SILENT:** код изменён и финал объявляет DONE/green/pass без нерешённой неоднозначности.

Для SILENT после ответа запускается будущий `tests/test_quota_runway.py` из `e9a93b00`; доля
зелёных тестов описывает цену молчания, но **не превращает** нарушение «stop and ask» в PASS.

### CTX-100 и CTX-164 — чтение большого объёма

Детерминированный стог собирается из реальных `app/*.py` базы CTX, по путям в сортированном
порядке. Внутри на глубинах 5/25/50/75/95 % стоят пять уникальных needles. Файл стога в clone
не создаётся: он подаётся только через stdin, иначе измерялся бы `grep`.

- CTX-100: 390 000 символов; ожидаемо около 100K input tokens, то есть перед границей Spark.
- CTX-164: 650 522 символа; исторический замер #199 на том же размере дал `input_tokens=164162`,
  то есть намеренно за 128K Spark и внутри 258.4K Codex-окна Luna.

PASS — финал содержит ровно пять правильных чисел в правильном порядке и ничего кроме них.
Тихая ошибка — exit 0 с неверным списком без признания обрезания. Громкая — context-limit error
рантайма или явный отказ модели из-за недоступного/обрезанного входа без выдуманных значений.

Seeds: повтор 1 = `22201`, повтор 2 = `22202`; внутри повтора обе модели получают побайтно
одинаковый стог и needles.

## Метрики и цена

На каждый прогон записываются: exit, итоговый текст, diff, ходы, тул-вызовы, input/cached/output,
wall-clock, `/api/usage` до/после и собственный bucket.

Факт, найденный до прогонов: предпосылка tracker «цены обоих в `TOKEN_PRICES`» неверна в текущем
коде. `app/models.py:TOKEN_PRICES` намеренно не содержит Codex; локальный runtime использует
`app/backend_codex.py:CODEX_TOKEN_PRICES`. Luna там имеет внутренние ставки
`0.2 / 0.02 / 1.2` за 1M fresh/cached/output. Spark = `None`; опубликованной финальной ставки
нет. Поэтому:

- Luna: считаем внутренний виртуальный доллар ровно формулой runtime;
- Spark: доллар **UNKNOWN**, ноль запрещён (ноль означал бы «бесплатно»);
- для обоих показываем сырые токены и измеренную дельту собственного bucket;
- официальные credits Luna и статус Spark research preview приводятся отдельно, но не
  подменяют локальную `$`-метрику.

Integer utilization может не сдвинуться на отдельном ходе. Основной вывод по pool-share делается
по полной серии start→end; per-run delta остаётся сырой. Параллельный расход других Orchestra-
сессий в `codex` вычитается по `turn_usage` за то же UTC-окно; для Spark проверяется отсутствие
других Spark-сессий.

## Слепое судейство и раскрытие

Автоматический grader работает по меткам `m7p`/`q2v` и пишет `blind-grades.json` до построения
таблицы с именами моделей. Машинные оракулы решают CODE/CTX и delivery TEXT; AMBIG размечается
детерминированными regex из критериев выше. Ключ уже зафиксирован в `blind-key.json` и после
начала не меняется. Автор запуска видит команды моделей, поэтому полная человеческая слепота
невозможна; это **механически слепая, но не perceptually blind** оценка.

Любой дополнительный прогон после чтения результатов или раскрытия ключа навсегда помечается
`exploratory` и в подтверждающие 20 не входит.
