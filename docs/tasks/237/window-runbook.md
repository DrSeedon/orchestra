# #237 — ранбук окна: от мержа до доказательства бесшовности

Всё готово заранее, чтобы в момент рестарта ничего не сочинять. Порядок:
вердикт `review237-opus` → мерж → **A** → гейт активации → спавн субъекта → **B** → шесть
признаков. Критерии предрегистрированы в `activation-check.md` и не меняются после результата.

## 🔴 Прочитать первым: после мержа рестарт ЖДЁТ Claude-агентов

Это прямое следствие того, что мы построили, а не дефект: живой ход на рантайме, который
нельзя передать, **блокирует** рестарт вместо того, чтобы быть разорванным
(`_blocking_runtimes()` в `app/routes/system.py`).

Замер по живой БД на момент подготовки:

```
('claude', 'running', 6)   ← каждый из них блокирует рестарт B
('claude', 'idle',    5)
('claude', 'waiting', 3)
('codex',  'idle',   29)   ← ни одного живого Codex-хода
```

Следствия, которые надо знать заранее:

1. **Пока идёт ход любого Claude/Opus-агента, `/api/restart` не пошлёт сигнал.** Он дренирует
   их до `_DRAIN_DEADLINE_S` (900 с) и при истечении **отменяет рестарт** с `ok: False`.
2. **Оркестратор сам — Claude-сессия и сам в `running`, когда отдаёт команду.** Рестарт
   произойдёт не в момент вызова, а после того, как его ход закончится и остальные освободятся.
   Это нормально: приём новых ходов уже закрыт, поэтому очередь сходится, а не растёт.
3. Если за 15 минут кто-то не освободился — рестарт отменён, оба гейта открыты обратно,
   ничего не сломано. Повторить в затишье (у тебя для этого уже стоит слежка).

Практически: **B запускать в затишье по не-Codex агентам.** Иначе получишь честный `ok: False`
и решишь, что механизм сломан, хотя он ровно этим и занят — не режет чужой ход.

Рестарта **A** это не касается: он исполняет старый код и режет всех, как и раньше.

## Шаг 2 — гейт активации после рестарта A

`scripts/cli-inventory.py` появляется в `/home/kesha/orchestra` **вместе с мержем первого
поезда**. До мержа команды ниже падают с `No such file or directory` — громко и безвредно, но
знать стоит: репетировать их заранее надо из worktree, а не из главного чекаута.

```bash
cd /home/kesha/orchestra
# ДО сигнала A:
python3 scripts/cli-inventory.py snapshot > /home/kesha/orchestra-scratch/237/pre-A-inventory.txt
wc -l < /home/kesha/orchestra-scratch/237/pre-A-inventory.txt   # НЕ ноль, иначе см. ниже

# ПОСЛЕ A:
python3 scripts/cli-inventory.py check /home/kesha/orchestra-scratch/237/pre-A-inventory.txt
```

Вывод `check` заканчивается строкой `checked N entries, M still alive`; `M = 0` и код
возврата `0` → гейт пройден. Каждая строка `UNRESOLVED` — провал активации, а не мелочь:
после #258 неопознанный сирота не убивается и будет копиться молча. Гасить такие отдельно, с
доказательством identity, а не по совпадению pid.

**Пустой снимок — это ОТКАЗ, а не «сирот нет».** Ноль строк означает, что инвентарь ничего не
увидел, и тогда `check` не сделает ни одной итерации: `M = 0` получится по построению, при
любом числе выживших. Проверять именно `wc -l`, до рестарта, когда исправить ещё можно.

<details><summary>Почему здесь скрипт, а не строчка в markdown (это уже ломалось)</summary>

Прежняя версия шага искала `pgrep -f 'codex app-server'`. Такой подстроки в argv нет —
реальная строка `node /usr/bin/codex -c … -c … app-server --stdio`. Живой замер на этой
машине: шаблон дал **1 совпадение, и это был собственный bash проверяющего**, при 40 живых
процессах (20 CLI). То есть снимок вышел бы пустым, сверка не сделала бы ни одного шага, и
«сирот нет» было бы напечатано, ни разу на них не посмотрев.

Скрипт матчит argv ПО ХВОСТУ `("app-server", "--stdio")` — та же форма, которую проверяет
`terminate_cli_process` перед сигналом, — и потому не ловит ни свой bash (его последний
аргумент это текст скрипта), ни чужие команды с похожим текстом.

Проверено на живой машине, все три плеча:

| плечо | вход | результат |
|---|---|---|
| разрешающее | 40 живых процессов | 40 × `UNRESOLVED`, `exit=1` |
| отрицательное | несуществующий pid | `0 still alive`, `exit=0` |
| подделка | живой pid + чужой starttime | `0 still alive`, `exit=0` |

Разрешающее плечо здесь обязательно: без него «ноль сирот» не отличить от «проверка слепа».
</details>

Подтверждение, что загрузился НОВЫЙ код (поведением, а не фактом старта): в журнале после
первого же рестарта должны появляться имена нового формата `agent.<uuid>.stdin`, а не
`agent:<uuid>:stdin`.

## Шаг 4 — разрешающее плечо (ОБЯЗАТЕЛЬНО до сигнала B)

Без него отсутствие обрыва означало бы «ход и не начинался».

```bash
cd /home/kesha/orchestra                                       # скрипт приезжает с мержем
S=/home/kesha/orchestra-scratch/237/liveB
W=/home/kesha/orchestra/worktrees/home-kesha-orchestra/seamless237

cat $S/started.txt                                             # ждём STARTED
sqlite3 'file:/home/kesha/orchestra/data/orchestra.db?mode=ro' \
  "SELECT name,status,backend_type FROM sessions WHERE name='seamless237';"

systemctl show orchestra -p MainPID --value > $S/mainpid-before-B.txt   # база для признака 1

PID=$(python3 scripts/cli-inventory.py snapshot | awk '$3=="node"{print $1}' \
      | while read p; do [ "$(readlink /proc/$p/cwd 2>/dev/null)" = "$W" ] && echo "$p"; done)
if [ "$(echo $PID | wc -w)" = 1 ]; then
  echo "$PID $(python3 scripts/cli-inventory.py snapshot | awk -v p=$PID '$1==p{print $2}')" \
    > $S/subject-identity.txt
  cat $S/subject-identity.txt
else
  echo "ОТКАЗ: субъект не опознан однозначно (нашлось '$PID') — B НЕ ЗАПУСКАТЬ"
fi
```

Требуется одновременно: `STARTED` на диске, `status=running`, `backend_type=codex` и непустой
`subject-identity.txt` из двух чисел. **Нет файла — B не запускать:** без identity признак 2
шага 6 нечем сверять, и замер выродится в «посмотрели и не поняли».

<details><summary>Почему identity берётся из `/proc`, а не из `sessions.cli_pid` (это ломалось)</summary>

Прежняя версия требовала «непустой `cli_pid`». Колонка пишется РОВНО одним вызовом —
`save_handover_state` (`db.py:2782` ← `manager.py:2233`), то есть **только в ходе передачи, уже
после сигнала**. Живой замер: 46 сессий, непустых `cli_pid` — **ноль**.

Ночью это давало один из двух исходов, оба плохие: либо оператор встаёт на шаге 4 и теряет
окно затишья, либо пишет `PID=0`, и тогда признак 2 (`/proc/0/stat`) печатает пустоту при ЛЮБОМ
исходе — центральный признак замера превращается в вечное ложное «CLI не выжил».

Тот же факт записан правильно в суточном блоке ниже, где по нему проверка сознательно
выброшена. Применено к одному месту и не применено к другому — внутри одного документа.

`node`-процесс пары и есть `backend.pid`: его родитель — python-процесс uvicorn (проверено:
`ppid=3325645`), а единственный ребёнок — настоящий бинарь codex. Именно его целит
`terminate_cli_process`.

Проверено на живой машине, оба плеча:

| плечо | вход | результат |
|---|---|---|
| разрешающее | `feat-runtime-switch`, `quota-policy`, `quota-routing` | ровно 1 pid у каждого (`3356830`, `3358048`, `3360284`) |
| отрицательное | worktree Claude-агента (codex-процесса нет) | 0 pid → ветка `ОТКАЗ` |

</details>

Успех — только когда сошлись **все шесть**. Совпадение pid без совпадения starttime не
считается: номера переиспользуются.

## Что успехом НЕ считается

`NFileDescriptorStore=2`, сменившийся MainPID сам по себе, отсутствие ошибок, пустая очередь,
«сессия восстановилась и стоит idle» — последнее и есть сегодняшнее поведение при обрыве.

## Если A прошёл, а B запустить долго не удаётся

Штатное промежуточное состояние. Действие: **ничего не делать, ждать следующего затишья.**
Откатывать нечего и незачем.

**Как называть это состояние — дословно:** «механизм АКТИВИРОВАН, но НЕ ДОКАЗАН».

- Можно говорить: код загружен, гейт активации пройден, старые CLI убраны, сирот нет.
- **Нельзя говорить юзеру «бесшовность работает»** — до зелёного B это утверждение ничем не
  подкреплено. Единственное, что доказано без B, — что мы больше не режем ход Claude/Grok,
  потому что рестарт теперь на них останавливается. Про Codex без B не известно ничего.
- Формулировка для юзера, если он спросит раньше времени: «выкачено и активировано; проверка
  на живом ходе ждёт тихого окна, до неё бесшовность не подтверждена».

**Что реально изменилось сразу после A, даже без B** (знать, чтобы не удивиться ночью):
рестарт стало ТРУДНЕЕ сделать. `/api/restart` ждёт освобождения всех не-Codex агентов до
900 с и при истечении отменяется. Это не поломка, это цена гарантии.

**Аварийный выход, если рестарт нужен немедленно, а агенты заняты:** ручной
`sudo systemctl restart orchestra`. Он обходит оба гейта — то есть не дренирует мутирующий
HTTP, не делает транзакцию атомарной и не умеет ответить «нельзя».

Чего он при этом **не** делает — не рвёт Codex-ходы: SIGTERM идёт в graceful shutdown, а тот
зовёт `shutdown_all()` → передачу дескрипторов (механизм #230). Ранее здесь было написано
обратное; утверждение снято после ревью, подробности и цена — `## Operational limitation` в
`report.md`. Пользоваться, когда простой дороже риска, и потом обязательно сверить исход
последнего мутирующего вызова вручную.

**Проверка, что промежуточное состояние не деградирует** (раз в сутки достаточно):

```bash
cd /home/kesha/orchestra
systemctl show orchestra -p NFileDescriptorStore --value   # ждём 0 при отсутствии передач
python3 scripts/cli-inventory.py count
sqlite3 'file:/home/kesha/orchestra/data/orchestra.db?mode=ro' \
  "SELECT COUNT(*) FROM sessions WHERE finished_at IS NULL AND backend_type='codex';"
```

**Главный триггер — `survived_a_restart > 0`, пока B не пройден.** Это CLI с `ppid=1`, то есть
процесс, чей родитель умер. Рестарт A исполняет СТАРЫЙ код и передач не делает, значит до
успешного B любой такой процесс — сирота по определению, и одной штуки достаточно, чтобы это
был инцидент. После успешного B смысл меняется на противоположный: там будут жить именно
пережившие, и число станет ожидаемым.

Второй, слабый: **`clis` ≤ числа живых codex-сессий** — у сессии не бывает двух CLI. Слабый
потому, что срабатывает только при накоплении: сегодня `clis=20` при 29 сессиях, то есть он
промолчит про первые девять сирот. Держим как грубую сетку, а не как основную.

Замер сегодня: `processes=40 clis=20 survived_a_restart=0` при 29 живых сессиях — норма по
обоим. Любое срабатывание — в `## First activation` (`report.md`).

Два числа в выводе `count` намеренно разные: **один CLI это ДВА процесса** (обёртка
`node /usr/bin/codex` и настоящий бинарь под ней), поэтому сравнивать с сессиями надо
`clis`, а не `processes`.

**Чего здесь СОЗНАТЕЛЬНО нет — проверки по `sessions.cli_pid`.** Она напрашивается и была бы
генератором ложных тревог: колонка пишется только при передаче (`save_handover_state`,
`db.py:2792`), поэтому в покое она нулевая у всех. Живой замер: 40 процессов против **0**
непустых `cli_pid` — проверка «у каждого CLI есть сессия-владелец» объявила бы сиротами все
сорок. По той же причине неверна и прежняя формулировка этого шага («сверить число процессов
с числом сессий»): 20 CLI против 29 сессий — нормальное состояние, а не расхождение.

Срок ожидания не ограничен: B ничего не чинит, он только доказывает. Затишье наступит само,
когда Codex-пул сбросится 20.08 и часть воркеров уедет обратно с Opus на Sol/Luna.

## Если B провалился

Ход разорван — то есть ровно сегодняшнее поведение, нового риска нет. Единственное, что
требует действий: выживший, но неопознанный CLI → в unresolved-list, гасить отдельно с
доказательством identity. Субъект `seamless237` — `lifecycle=one-shot`, после DONE и проверки
его можно убирать.
