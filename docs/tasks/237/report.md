## Сменившие смысл ассерты

`tests/test_hot_apply.py` кодировал контракт #220 «дедлайн безусловен → рестарт всё равно
режет ход и отчитывается числом разорванных». #237 T3 меняет исход на противоположный, и оба
утверждения одновременно верны быть не могут. Переписаны, а не подогнаны:

- `test_t3_drain_deadline_is_unconditional_and_reports_cut_turns` →
  `..._and_names_the_blocking_turns`: `kill` вызывался ровно раз → не вызывается вовсе;
  `cut_turns == 1` → `cut_turns == 0` и `cut_names` называет заблокировавшего.
- `test_t3_drain_outcome_is_persisted_before_the_signal`: проверяемое свойство (запись до
  сигнала) прежнее; сессия заменена с занятой на свободную, иначе сигнала не будет вовсе и
  проверять станет нечего. `("record", 1)` → `("record", 0)`.
- `test_t3_broken_recorder_does_not_cancel_the_signal`: то же — свободная сессия.

## Найдено не оракулами

1. **uvloop переиспользует номер закрытого дескриптора.** Закрытие детских концов ДО
   привязки своих давало `os.fstat` на уже переиспользованном номере (`fd 13 → /dev/null`).
   Замерено пробой, не выведено. Порядок изменён: сперва привязка, потом закрытие — заодно
   при сбое привязки CLI получает EOF, а не виснет.
2. **Момент освобождения дескриптора определял планировщик.** `transport.close()` только
   планирует закрытие; `teardown_owned_pipes` сделан асинхронным и ждёт его.
3. **Сторож не откатывал подготовленный флот** (pre-mortem). Рестарт, не случившийся после
   успешной подготовки, оставлял агентов живыми, но ГЛУХИМИ навсегда, а их дескрипторы
   копились в systemd до исчерпания store. Закрыто охранником.
4. **Провал рестарта до планирования задачи оставлял гейт ходов закрытым** — та же болезнь,
   что в #220 ловил полный сьют. Закрыто охранником.
5. **Предсуществующий дефект изоляции тестов:** фикстура `tests/test_system_restart.py`
   возвращала только приём ходов, но не приём мутирующего HTTP, который `restart_server()`
   тоже закрывает. Ронял `test_fd_adopt.py::test_t6_real_middleware_...`. Воспроизведено на
   чистом `main` (`git stash`), то есть не моя регрессия; починено здесь.

### Раунд 2: код APPROVED, блокер оказался в РАНБУКЕ

**Единственный блокер — команда инвентаря в ранбуке, и он опаснее любого из трёх кодовых**,

## First activation

Первый рестарт исполняет ещё СТАРЫЙ загруженный Python, поэтому нового workflow в нём нет:
он по построению прерывающий. Это ожидаемо и заранее принято.

- До сигнала снять инвентарь каждого живого CLI: `(pid, /proc starttime, argv)`.
- `NFileDescriptorStore` в этот момент `0` — усыновить существующие процессы невозможно.
- После старта нового поколения каждый CLI из инвентаря должен быть **reaped**. Совпавший
  живой identity — не «мелочь», а провал активации: после #258 неопознанный сирота
  НЕ убивается (сигнал только через pidfd с доказанной identity), поэтому он останется жить
  молча. Такие процессы вносятся в явный unresolved-list и гасятся оператором отдельно,
  с доказательством identity, а не по совпадению pid.
- Проверка после активации: старых CLI нет; новые Codex-сессии поднимаются; мост и HTTP
  живы; повторный mid-turn рестарт — только на мини-Orchestra.

## Operational limitation

Ручной `sudo systemctl restart orchestra` в обход `/api/restart` обходит ОБА гейта. Кодом это
не закрывается — systemd подчиняется оператору, а не приложению.

**Поправка после ревью (S3).** Раньше здесь стояло, что при ручном рестарте «активные
Codex-ходы рвутся, потому что дескрипторы никто не передал». **Это неверно**, и оператор
принимал бы решение по ложной модели. SIGTERM → graceful shutdown uvicorn → lifespan →
`manager.shutdown_all()` (`app/main.py:303`) → `_hand_over_backend` для каждой сессии: то есть
дескрипторы передаются и CLI переживает. Это механизм #230, и раннер T4 проверяет именно его.

Настоящая цена ручного рестарта другая и меньше:

1. **Нет дренажа мутирующего HTTP** — незавершённый вызов теряет ответ при совершённом
   эффекте (максимум измеренного — `merge_worker`, 90.2 с). Единственное последствие,
   требующее ручной сверки.
2. **Нет атомарности и поздней проверки** — передача идёт по сессии за раз, часть может
   передаться, часть нет, и никто не откатит.
3. **Агент с незавершённым JSON-RPC запросом останавливается по-старому:** `quiesce`
   отказывает fail-closed, `_hand_over_backend` возвращает False, сессия уходит в `stop()`.
4. **Никто не скажет «нельзя»** — `/api/restart` умеет ответить отказом, `systemctl` нет.

Итог для оператора: рестарт делать через эндпоинт; если ручной всё же выполнен — сверить
исход последнего мутирующего вызова вручную, а не считать его выполненным.

## Ограничение на машине с работающим systemd-scope (S2)

На этом VPS путь неактивен (живая проба: `scope_ok = False`, `/run/user/1001/bus`
отсутствует), поэтому здесь дефект спящий. **Но на контуре, где у пользователя есть linger**
(ноутбук — `docs/HANDOFF-from-laptop.md`), Codex спавнится через `systemd-run --scope`,
дескрипторы остаются `PIPE`, `fd_in`/`fd_out` — `None`.

Тогда цепочка НЕ деградирует в старое поведение, а жёстко ломает рестарт:
`_hand_over_backend` → False → `prepare_restart_handover` → `ok: False` → `_abort_restart`.
То есть **`/api/restart` не отработает никогда, пока занят хоть один Codex-агент**, тогда как
до #237 он бы отработал, отрезав ход. Размен осознанный (не резать ход важнее, чем уметь
рестартовать), но на такой машине первый поезд фактически выключен и требует отдельного
решения: либо адоптировать scope-запуск, либо блокировать рестарт по имени агента с внятным
сообщением, а не отказом транзакции без объяснения.
