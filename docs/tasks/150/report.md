# #150 — сборщик usage писал нули вместо «данных нет»

## 1. Где подставлялся ноль

**`app/routes/system.py:972`** (до правки):

```python
fh = (anthropic_data or {}).get("five_hour") or {}      # :967
sd = (anthropic_data or {}).get("seven_day") or {}      # :968
usage_save_snapshot(
    fh.get("utilization", 0), sd.get("utilization", 0), # :972  ← вот он
    ...
```

Запрос к anthropic упал → `anthropic_data = None` → `fh` и `sd` пустые словари →
`.get("utilization", 0)` отдаёт **0**, и он ложится в колонки `usage_snapshots.five_hour_pct`
и `seven_day_pct`, где ноль читается как «квота не израсходована».

Строка при этом писалась: `providers` непуст (в JSON уже клался честный
`{"status": "unavailable", "error": ...}`), поэтому `if not providers: return` не срабатывал.

Второе тихое место — `except PermissionError` (`:910`): при 401 текст ошибки не сохранялся
вовсе, и если обновление токена не помогало, отказ оставался безымянным даже в JSON.

Третье — журнала не было ни у одного провайдера: причина отказа жила только внутри строки БД.

## 2. Что теперь

- `fh.get("utilization")` без дефолта → `None` → в колонке **NULL**.
- **Строку оставляем.** В ней живут `codex`/`grok` в `provider_usage` и локально посчитанные
  `total_cost_usd`/`active_agents` — от молчания anthropic они не пострадали. Пропуск строки
  выбросил бы честные данные трёх источников из-за отказа одного.
  Агрегаты SQLite (`AVG`, `MAX`) строки с NULL пропускают сами, потребитель у колонок ровно
  один — `_usage_providers_from_row`.
- `_usage_providers_from_row` (`app/db.py:1734`): окно не собирается, если pct `NULL`.
  Иначе наружу уехало бы `utilization: null`, а фронт превратил бы его в 0 (`Number(null)` = 0)
  — тот же ноль, просто на слой ниже.
- `logger.warning("usage snapshot: %s asked and did not answer — %s", provider_id, error)`
  в уже существующей ветке «спросили, но не ответил» — с классом исключения, для всех трёх
  провайдеров сразу.
- `PermissionError` записывает причину сразу и очищает её, только если повтор с новым токеном
  удался.

Сигнатура `usage_save_snapshot` — `float | None` (`app/db.py:1716`).

## 3. Счёт по истории — 184 строки с двумя нулями

Всего снимков 7583.

| категория | строк | период | признак |
|---|---|---|---|
| **заведомо фальшивые** | **78** | 03.08 23:30 – 06.08 22:02 | `provider_usage.anthropic.status == "unavailable"` в той же строке |
| **недоказуемые** | **106** | 09.07 17:57 – 20.07 05:42 | `provider_usage = '{}'` — колонки старой схемы, независимого признака нет |

78 фальшивых доказаны **независимым полем той же строки**, а не косвенным признаком: сборщик
сам записал, что источник спросили и он не ответил.

### Почему 106 старых строк трогать нельзя

Напрашивался признак «пустой `resets_at` при нулевом pct = источник молчал». Он **неверен**:

```
строк с provider_usage:                    1111
из них anthropic ОТВЕТИЛ (есть окна):      1033
из них five_hour_resets_at пустой:          161
из них five_hour_pct == 0:                  161   ← все до единой
```

То есть «нулевой pct с пустым `resets_at`» — это ровно то, как выглядит **настоящий** ответ про
только что сброшенное 5-часовое окно. Признак пометил бы 161 честную строку как подделку.
Из 106 старых строк 36 имеют непустой `resets_at`, 70 — пустой, и разделить их нечем.

**Предложение: мигрировать только 78 доказанных, 106 оставить как есть.** Данные не тронуты,
жду решения.

### Поправка к постановке задачи

- «`total_cost_usd` заморожена на `1900.453` → источник не отвечал» — совпадение.
  `total_cost_usd` считается ЛОКАЛЬНО (`sum(s.cost_usd for s in manager.sessions.values())`,
  `system.py:969`) и к провайдеру отношения не имеет. За 06.08 с 12:00 до 24:00 в 143 снимках
  26 различных значений, диапазон 1841.56–1923.47; ночью оно стояло потому, что ходов не было.
  Доказательство подделки — `status: "unavailable"`, оно точное и не зависит от нагрузки.
- «семидневный счётчик обнулился и вернулся к 69%» — верно для КОЛОНОК. В `provider_usage`
  тех же строк anthropic честно помечен `unavailable` с пустым списком окон, поэтому на графике
  разрыв уже сейчас: `_historyProviders` (`usage.js:389`) при непустом `row.providers` берёт JSON
  и до колонок не доходит. Врали именно колонки — и всё, что считает по ним.

## 5. Что уехало фронту

Сообщено воркеру `frontend`: в строках `/api/usage/history` поля `five_hour_pct` и
`seven_day_pct` теперь бывают `null`. Фолбэк `_historyProviders` (`app/static/js/usage.js:389-400`)
делает `Number(row.five_hour_pct) || 0` — на `null` это даст 0 и нарисует пол. Механика разрыва
у них уже есть (`gapMs = _sparkStepMin * 1.5 * 60000`, `usage.js:529-541`): точки просто не
будет, и линия разорвётся сама.

## Известная соседняя странность (не чинил, вне задачи)

Фолбэк по колонкам отбрасывает окно при `pct == 0` и пустом `resets_at` — то есть настоящий
ноль сброшенного окна на старых строках (`provider_usage='{}'`) в график не попадает.
Условие досталось от прежнего кода; менять его — значит менять отрисовку истории, о чём не просили.
