# #50 — план: очередь фактов о недоставке, доезжающая в контекст со следующим сообщением

Граница, на которой стоит вся политика #30: **в контекст едет ФАКТ («такое-то событие
не доставлено»), а не исходное сообщение.** Ретрая нет ни в каком виде.

## Поправка к собственному исследованию: точек отправки ТРИ, а не две

Требование «проверить на обоих рантаймах» сразу дало результат ещё до реализации.
Кроме двух путей из research.md есть третий, и он как раз Codex-овский:

| # | путь | строка | когда |
|---|---|---|---|
| 1 | mid-turn inject | `app/session.py:652` | агент RUNNING, рантайм умеет инъекцию (Claude) |
| 2 | обычный старт хода | `app/session.py:756` | агент IDLE/WAITING |
| 3 | **флаш очереди сообщений** | `app/session.py:1045` | рантайм НЕ умеет инъекцию (Codex): сообщение легло в `_pending_messages`, потом уходит одним `backend.send(combined)` |

`_flush_pending` зовёт `backend.send` НАПРЯМУЮ, мимо `send()`. Врезка только в `send()`
означала бы, что на Codex факт не доезжает никогда — ровно тот класс ошибки, о котором
предупреждал оркестратор.

**Про обёртку `<current-user-message>`:** она появляется не от рантайма, а от
`runtime_handoff` (`app/session.py:741`) — при смене рантайма прошлый диалог цитируется, а
текущее сообщение заворачивается. Факт врезается в `message` ДО сборки `outbound_message`,
то есть оказывается ВНУТРИ `<current-user-message>`. Это осознанно: факт адресован агенту
сейчас, он часть текущего сообщения, а не часть процитированного прошлого. Так же ведёт
себя существующая инъекция промпта.

## Tickets

### T1 — durable очередь с потолком и видимым сжатием
- Files: `app/db.py`, `tests/test_undelivered_queue.py`
- Что делает: таблица `undelivered_facts` (`session_id`, `dedupe_key`, `text`, `created_at`,
  `delivered_at`) + `enqueue_fact()`, `peek_facts()`, `ack_facts()`.
  - **Дедупликация**: `UNIQUE(session_id, dedupe_key)` — повторная недоставка того же
    события не кладёт вторую строку (обновляет время, не плодит).
  - **Потолок**: 20 недоставленных фактов на сессию. Переполнение НЕ отбрасывается молча:
    старые сворачиваются в одну строку «и ещё N событий, см. журнал» — в задаче про
    молчаливые потери молчаливое отбрасывание было бы смешно.
  - Очередь durable: переживает рестарт, в отличие от `_pending_messages` (P1 из #35).
- AC:
  - два `enqueue_fact` с одним `dedupe_key` → в очереди одна строка;
  - 25 фактов → `peek_facts` отдаёт 20 плюс явную строку про свёрнутые 5;
  - `ack_facts` гасит ровно переданные ключи, остальные остаются;
  - записи переживают переоткрытие БД (проверяется новым соединением, а не памятью).
- blocked-by: none

### T2 — врезка во ВСЕ три точки и гашение строго после доставки
- Files: `app/session.py` (652, 756, 1045), `tests/test_undelivered_queue.py`
- Что делает: один приватный помощник `_attach_pending_facts(message) -> (text, keys)`,
  вызываемый во всех трёх точках; `ack_facts(keys)` — ТОЛЬКО после возврата из
  `backend.send`. Формат блока:
  ```
  [Orchestra platform note: пока тебя не было, до тебя не дошло 2 события. Это факты,
  а не повтор сообщений — исходные сообщения НЕ пересылались.]
  - 06:12 автоотчёт воркера «perf» не доставлен: RuntimeError: …
  - 06:20 уведомление о баг-репорте «…» не доставлено: …
  ---
  <исходное сообщение>
  ```
- AC:
  - **отказ `backend.send` (управляемая подмена бэкенда, а не живой сбой): факты остаются
    в очереди** — без этого правило «гасим по факту доставки» остаётся заявлением;
  - успешная отправка гасит их же и второй раз не приписывает;
  - **mid-turn inject** (RUNNING + Claude-подобный рантайм): факт виден в payload
    `backend.send`;
  - **флаш очереди** (Codex-подобный рантайм, `mid_turn_inject=False`): факт виден в
    `combined`, ушедшем в `backend.send`;
  - при `runtime_handoff` факт оказывается ВНУТРИ `<current-user-message>`;
  - сбой самой очереди (например, БД недоступна) не мешает отправке сообщения —
    сообщение важнее факта.
- blocked-by: T1

### T3 — три производителя ставят факт в очередь
- Files: `app/manager.py` (`_record_undelivered_auto_report`), `app/notify.py`
  (`report_undelivered`, `_record_undelivered_bug`), тесты
- Что делает: там, где сегодня пишется только строка в историю сессии, дополнительно
  кладётся факт в очередь адресата. Ключи дедупликации: `record_id` у баг-репорта,
  `job_id` у пробуждения/bg-job, `session_id+turn` у автоотчёта.
  Запись в историю остаётся: её читает человек в дашборде, очередь — агент.
- AC:
  - живой сценарий: недоставка автоотчёта → следующая успешная отправка тому же
    оркестратору → **в payload `backend.send` виден факт** (печатать payload, а не строку БД);
  - повторная недоставка того же события не удваивает запись;
  - для каждого из трёх производителей есть свой тест.
- blocked-by: T2

## Чего план НЕ делает

- не вводит ретраев (исходные сообщения не пересылаются никогда);
- не трогает `_pending_messages` — это отдельная сущность с отдельным P1 (#35), сливать их
  в этой задаче нельзя: у них разный смысл (сообщение vs факт о недоставке);
- не делает TG-зеркало (вариант C) — по решению оркестратора остаётся запасным;
- не меняет внешний вид записи в дашборде (это #51 у фронтенда).

## Вердикта Codex нет

Codex недоступен до 08.08. Самокритика:

1. **Врезка в `send()` — общий рантайм, и три точки вместо одной увеличивают риск.**
   Помощник обязан быть тривиальным и не бросать: любой сбой очереди не должен мешать
   доставке сообщения. Это записано в AC, но проверить я смогу только подменой БД.
2. **Потолок 20 — цифра из головы**, а не из замера: сколько фактов реально копится за
   инцидент, я не измерял (недоставки редки по построению). Если окажется мало — увидим
   по строке про свёрнутые события, она для этого и нужна.
3. **Ключ дедупликации у автоотчёта самый слабый**: `session_id+turn` — если ход не имеет
   стабильного id, ключ придётся строить из времени, и тогда два быстрых автоотчёта
   подряд дадут две записи. Проверю на реализации; если стабильного id нет, скажу прямо.
