Миграция отправки почты: провайдер A → провайдер B

Шесть недель, шесть фаз, ни одного шага, который нельзя откатить за пять минут. Ключ ко всему — DNS правим аддитивно (обе подписи живут одновременно), а трафик переключаем флагом в конфиге. Поэтому откат никогда не ждёт TTL. Раскатка идёт ступенями 1 → 100 % по хэшу пользователя, каждая ступень открывается только зелёными метриками, а не календарём.

01 Что не обсуждается

Четыре решения приняты до начала работ. Если по ходу захочется их нарушить — это не оптимизация, это отказ от плана: возвращайся к постановщику.

Инвариант 1

Переключает флаг, а не DNS

Источник правды — MAIL_PROVIDER со значениями old, new, split:N. Читается из конфига без передеплоя. DNS в переключении не участвует вообще.

Инвариант 2

DNS только добавляем

SPF получает второй include, DKIM — второй селектор. Записи старого провайдера не трогаем до фазы 5. Половина катастроф в таких миграциях — это удалённая на день раньше строчка.

Инвариант 3

Ключ идемпотентности на каждом письме

message_key = hash(template_id, user_id, event_id), таблица sent_messages с уникальным индексом. Это единственная защита от дублей в момент, когда очередь старого провайдера ещё дренится, а новый уже шлёт.

Инвариант 4

Отписки живут у нас, а не у провайдера

Своя таблица — источник правды, провайдерский suppression list — вторая линия обороны. Провайдер меняется, юридическое обязательство перед пользователем — нет.

03 Фазы · чек-лист исполнителя

07 Аварийный откат

Выполняет дежурный, без согласований и без созвона. Разбор — после, не до. Ошибочный откат стоит одного потерянного дня графика; несделанный — репутации домена на месяцы.

  1. 0:00Переключить флаг: MAIL_PROVIDER=old. Деплой не нужен, DNS не трогаем.
  2. 0:02Убедиться по дашборду, что доля исходящих через B упала до нуля. Не упала — фасад читает конфиг из кеша, перезапустить воркеры отправки.
  3. 0:05Дать очереди B дренироваться самой. Не чистить руками — письма в ней уже приняты, повторная отправка через A даст дубли.
  4. 0:15Снять срез: сколько писем ушло через B за инцидент, кому, с какими событиями. Это выборка для разбора и для ответа поддержке.
  5. 1:00Написать в поддержку провайдера B, если причина на их стороне (лимиты, блок IP, отказ SMTP). Тикет заводится сразу — время ответа больше нашего.
  6. +1 деньРазбор: какой гейт пропустил проблему. Гейт не был проверен — чиним процесс; гейт был зелёным — чиним гейт. Возврат на ступень ниже той, где сломалось.

DNS-записи при откате не меняются никогда. Они аддитивны и валидны для обоих провайдеров — в этом вся суть инварианта 2.

08 Так не делать

  • Переключать трафик сменой DNSОткат превращается в ожидание TTL у чужих резолверов. Часы вместо минут — и это в момент, когда письма уже не доходят.
  • Сплитить случайно на каждом письмеОдин пользователь получает письма от двух отправителей вперемешку: рвётся цепочка в почтовике, часть писем уходит в «Промоакции». Сплит только по стабильному хэшу user_id.
  • Начинать раскатку с массовых рассылокХудший engagement на непрогретом IP. Начинают с транзакционных писем, которые открывают почти все.
  • Удалять SPF-include старого провайдера в день переключенияВ его очереди ещё лежат письма. Они уйдут без валидной SPF — прямиком в спам. Ждать 60 дней.
  • Мигрировать без переноса suppression-листа«У нас есть свои отписки» — есть, но у провайдера накоплены ещё и жёсткие отказы за годы. Отправка по ним — быстрый путь к блокировке.
  • Считать доставку по ответу API202 Accepted означает «принял в очередь», а не «доставил». Метрика приёмки — только событие delivered из вебхука.
  • Оставлять два кода отправки «на всякий случай» навсегдаВторая реализация фасада удаляется на фазе 5. Незадействованный путь отправки перестаёт тестироваться и через полгода не работает — но выглядит как страховка.
