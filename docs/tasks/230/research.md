# #230 — можно ли рестартовать Orchestra, не прервав ни одного хода

Фаза 1 (research). Живой сервис не рестартился ни разу. Все прогоны — на отдельных
одноразовых systemd-юнитах (`orchestra-fdtest*`, `orchestra-sockact`, `orchestra-portbind`),
скрипты в `/home/kesha/orchestra-scratch/230/`.

## Question

### Context
Один процесс `uv run uvicorn app.main:app` (PID 3044780 на момент замера). Агентские CLI —
его прямые дети: замерено 6 живых (2 × `node /usr/bin/codex … app-server --stdio`,
4 × `/usr/bin/claude --output-format stream-json`). Юнит `orchestra.service` **не задаёт
`KillMode`** → действует дефолт `control-group`, то есть SIGTERM уходит всему cgroup.
Транспорт — stdio-пайпы, владелец пайпа = сервер.

### Change under test
Рестарт супервизора не прерывает ни один активный ход. Агент доигрывает ход в своём
процессе; новые инструменты, промпты и конфиг получает на следующем ходу.

### Baseline
Сегодня рестарт убивает активные ходы (#220 F5: 2.38 хода за рестарт).

### Outcome (measurable)
1. Переживает ли РЕАЛЬНЫЙ агентский процесс `systemctl restart` супервизора, и доезжает ли
   результат его хода до НОВОГО поколения супервизора.
2. Сколько данных теряется на стыке (в байтах и в событиях хода).
3. Что ещё ломается, когда агент остался жив, а супервизор перезапустился.
4. Цена в коде и что останется требующим настоящего перерыва.

## Findings

### F1 — Реальный агентский процесс переживает `systemctl restart`, и результат его хода доезжает до нового поколения. CONFIRMED для СЫРОГО транспорта; PARTIAL для продового пути (правка после ревью)

Механизм: `KillMode=process` (не убивать детей) + **systemd FD store** (`FileDescriptorStoreMax=`,
`sd_notify FDSTORE=1` с передачей FD через `SCM_RIGHTS`). Store держит дупликаты наших концов
пайпов, поэтому смерть супервизора не даёт CLI ни сигнала, ни EOF; новое поколение получает те
же FD через `$LISTEN_FDS`/`$LISTEN_FDNAMES` и продолжает читать тот же поток.

Почему нужны обе половины: сегодня агента убивают ДВА независимых механизма — cgroup-SIGTERM
(снимается `KillMode=process`) и EOF на закрытом пайпе (снимается FD store). Закрыть один и
считать задачу решённой нельзя.

**Codex, реальный ход** (`fdtest4.py`, юнит `orchestra-fdtest4`, `codex-cli 0.146.0`,
`gpt-5.6-luna`). Ход: одна shell-команда `touch m4-start && sleep 90 && touch m4-done`, затем
ответ модели. Рестарт сделан, когда `m4-start` уже существовал, а `sleep 90` шёл:

```
1786539211.019 gen1 turn_id=019ff608-f901-7740-8965-eb337690b410
1786539211.185 gen1 EVENT turn/started {"threadId": "019ff608-…", "status": "inProgress"
1786539223.122 gen1 marker_start=True — now idling until systemd stops me
1786539231.112 gen1 SIGTERM -> exit, codex untouched
1786539231.213 gen2 REATTACH fds={'codexstdout': 3, 'codexstdin': 4} codex_pid=3064808 alive=True
               thread=019ff608-… turn=019ff608-f901-… leftover_bytes=0
1786539351.235 gen2 events_after_restart=10 distinct=['account/rateLimits/updated',
               'item/commandExecution/terminalInteraction', 'item/completed',
               'item/started', 'thread/tokenUsage/updated']  marker_done=True
```
Передача поколения — **101 мс**. Процесс Codex жив, тот же `thread`/`turn`, 10 событий ТОГО ЖЕ
хода прочитаны новым процессом, shell-команда довелась до конца (`m4-done`).

**Claude, реальный ход** (`fdtest5.py`, `claude-sonnet-5[1m]`, `--output-format stream-json
--input-format stream-json`). Тот же сценарий, рестарт во время `sleep 90`:

```
1786539619.916 gen1 SIGTERM -> exit, claude untouched
1786539620.005 gen2 REATTACH fds={'claudestdout': 3, 'claudestdin': 4} claude_pid=3067671 alive=True
1786539675.886 gen2 EVENT system/task_notification … "status": "completed"
1786539678.344 gen2 EVENT result/success {"is_error": false, "duration_ms": 95934, …}
```
Передача — **89 мс**. Итоговое событие хода (`result/success`, `is_error: false`, ход длиной
95.9 с) получено ПОСЛЕ рестарта тем поколением, которое этот ход не начинало. Именно этот кадр
сегодня и теряется вместе с ходом.

**Граница этого замера (сужено после ревью).** Подтверждено: CLI выживает, поток не рвётся,
терминальный кадр хода доезжает до нового процесса. НЕ подтверждено: что этот кадр принимает
продовый путь Orchestra. Оба зонда читают сырой провод, а не наш стек: Claude-зонд запущен с
`--permission-mode bypassPermissions`, тогда как прод работает с
`permission_mode="default", can_use_tool=_make_auto_approve(...)` (`backend_claude.py:277`) —
то есть двунаправленный control-канал SDK зонд не задействовал вовсе (см. F10). У Codex
финальный `turn/completed` в этом прогоне не пришёл: получены `item/completed` и ещё 9 событий,
а `m4-done` доказывает завершение shell-команды, не хода. Поэтому «ход доигрывается» верно про
процесс и про поток и остаётся НЕДОКАЗАННЫМ про завершение хода в учёте Orchestra.

Дополнительно измерено на стенде-заменителе (`fdtest.py`): ребёнок переехал на `ppid=1`, остался
в cgroup `0::/system.slice/orchestra-fdtest.service`, ответил новому поколению
(`pong 2 for hello-from-gen2 ppid=1`). Порядок FD в `LISTEN_FDNAMES` **не совпадает с порядком
отправки** (отправлял stdin, stdout — вернулось `['childstdout', 'childstdin']`), поэтому
привязка только по `FDNAME`, не по позиции.

### F2 — Store переживает и КРАШ супервизора, но не переживает `stop`. CONFIRMED (измерено)

`fdtest3.py`, четыре поколения подряд:
- два `systemctl restart` подряд — оба раза реаттач, `child_alive=True`;
- `systemctl kill -s SIGKILL --kill-whom=main` (эмуляция краша) + `Restart=always` → gen4
  подхватил живого ребёнка: `gen=4 REATTACH … child_alive=True`. То есть при крахе агенты
  тоже выживают — supervisor не успевает ничего сделать, а FD держит systemd, не он.
- полный `stop` (или провалившийся старт, который systemd доводит до stop) освобождает store.
  Точная формулировка (сужена после ревью): `stop` ВЫБРАСЫВАЕТ сохранённые дескрипторы и не
  даёт никакой непрерывности. Смерть ребёнка при этом наблюдалась у ПИШУЩЕГО ребёнка —
  `BrokenPipeError: [Errno 32] Broken pipe` в `child2.py`, — и это следствие записи в закрытый
  пайп. Молчащий CLI записи не делает, EPIPE не получает и после `stop` может остаться жить в
  cgroup (как и его MCP-дети). Это вопрос не непрерывности, а УБОРКИ, и он не проверен.

Практический вывод: сохраняются **restart и краш**, не сохраняются **stop и ребут**.
`FileDescriptorStorePreserve` по умолчанию = `restart`, systemd на машине — 255 (`255.4-1ubuntu8.17`),
то есть нужная версия есть (опция появилась в 254).

Цена краша отдельно: SIGKILL'нутое поколение не успевает записать, докуда дочитало. В замере
`GAP_FROM_PREV_GEN=378` строк — это то, что оно прочитало из пайпа и не зафиксировало. В проде
эти события пишутся в БД по мере поступления, поэтому реальная потеря — последнее незаписанное
событие, а не 378; но нулевой её назвать нельзя.

### F3 — При ШТАТНОМ рестарте поток не теряет байт; при крахе теряет прочитанное-но-незаписанное. CONFIRMED в границах стенда (сужено после ревью)

`fdtest3.py` + `child3.py`, непрерывный поток строк со счётчиком:
- медленный писатель: gen1 дочитал до `seq 341`, gen2 начал с `342` → `GAP_FROM_PREV_GEN=0`;
- быстрый писатель (без sleep): **156 365 734 байта за 3 с**, gen1 закончил на `seq 730681`,
  gen2 начал с `730682` → `GAP=0`, и на следующем рестарте снова `GAP=0`;
- при этом ребёнок в момент стыка упирается в заполненный пайп: `worst_write=0.123s`. То есть
  агент на время передачи блокируется на запись и продолжает сам, без потерь.

Что ТЕРЯЕТСЯ: байты, уже вычитанные умирающим процессом в СВОЙ буфер. В прогонах стенда
`leftover_bytes=0`, но это артефакт стенда (строки по 208 байт < PIPE_BUF, запись атомарна);
в реальном прогоне Codex я поймал `leftover_bytes=149`. При ШТАТНОМ выключении лечится
переносом остатка буфера в состояние (в стенде так и сделано, поле `leftover` в `state4.json`),
при SIGKILL перенести его нечем — там теряется всё прочитанное и незаписанное (F2, 378 строк).

Границы, снятые с этой находки после ревью:
- **`0.123 с` — свойство стенда, а не приложения.** Это задержка записи при заполненном пайпе на
  МОЁМ стыке в 100 мс. У Orchestra стык длится десятки секунд (F4), значит CLI упирается в
  заполненный пайп на всё это время. Верхней границы для приложения этот замер не даёт.
- **Настоящая семантика — «не более одного раза», и потери, а не дубли.** Пайп не умеет
  перечитывание: кадр, вычитанный мёртвым поколением, из пайпа исчез, откатить курсор некуда.
  Поэтому опасное окно — «кадр прочитан, побочный эффект (лог, usage, уведомление) ещё не
  записан»: такой кадр пропадает молча. **У САМОГО ПАЙПА механизма переигрывания нет**, поэтому
  на транспортном слое дублирование невозможно — переигрывать нечего. Ревью этот довод приняло,
  но справедливо потребовало сузить формулировку: «дубли невозможны» верно ПРО ПАЙП и неверно
  про систему целиком — дублировать можно САМО ДЕЙСТВИЕ инструмента, если добавить ретрай
  неопределённого HTTP-вызова (F11), и можно переиграть байты кривой передачей остатка буфера.
  Что из этого следует для фазы 2: границу «прочитал → записал» сузить до одного кадра и мерить
  SIGKILL именно на ней.

### F4 — Живой агент вскрывает дыру, которой сегодня нет: HTTP-окно рестарта. CONFIRMED (замер + A/B)

Сегодня это не больно, потому что агенты всё равно мертвы. Как только они живы, их tool-вызовы
(все 34 `/api/...` пути из `app/mcp_stdio.py`) попадают в окно недоступности API.

Настоящий рестарт сегодня (журнал, 12.08):
```
14:23:38 systemd[1]: Stopping orchestra.service …
14:24:33 systemd[1]: Stopped orchestra.service
14:24:33 systemd[1]: Started orchestra.service
14:24:36 первый обслуженный запрос нового PID 3044780
```
То есть **55 с между «Stopping» и «Stopped»** и **58 с до первого обслуженного запроса нового
процесса**. Уточнение после ревью: момент, когда СТАРЫЙ слушатель перестал принимать
соединения, я не зондировал — журнал его не показывает, а uvicorn закрывает сокет где-то внутри
этих 55 с. Поэтому «58 с недоступности API» — это верхняя оценка, а доказанная величина —
«окно измеряется десятками секунд, а не секундами». Для вывода этого достаточно: даже нижняя
правдоподобная оценка на два порядка больше моего стендового стыка в 100 мс.

A/B на стенде, клиент стучит каждые 0.2 с, по два рестарта в каждом плече:
| плечо | запросов | 200 | отказов |
|---|---|---|---|
| socket activation (`ListenStream=127.0.0.1:8899`, `Accept=no`, `uvicorn --fd 3`) | 90 | 90 | **0** (худшая задержка 275 мс) |
| порт биндит приложение (как сейчас) | 60 | 56 | **4** (`CURL_FAIL 7` — connection refused) |

Отказы в контроле собраны на юните, который стартует меньше секунды. У Orchestra окно на два
порядка больше, поэтому **обязательным является требование, а не механизм**: пока супервизор
поднимается, tool-вызов живого агента не должен получить отказ — иначе «ход не прерван»
превращается в «ход не прерван, но его tool-вызов упал». Socket activation — единственный
механизм, ЗАМЕРЕННЫЙ здесь (90/90), но не единственный возможный: ретрай в шиме и передача
слушателя новому процессу не опровергнуты и не проверены. И сам он не безграничен: backlog
конечен, у вызывающего свой таймаут, а замер сделан на тривиальном ASGI-приложении, а не на
реальном старте Orchestra.

### F5 — Существующий механизм scope у Codex на этом VPS инертен. CONFIRMED (измерено)

`backend_codex.py:98-160` умеет запускать CLI в собственном user-scope
(`systemd-run --user --scope`), и это выглядит как готовая защита от cgroup-kill. На этой машине
он выключен:
```
loginctl show-user kesha → Failed to get user: User ID 1001 is not logged in or lingering
systemctl is-active user@1001.service → inactive
```
`_codex_scope_support()` требует `Linger=yes` и живой user-bus → возвращает False, и все 6 живых
CLI лежат в `0::/system.slice/orchestra.service` (проверено по `/proc/<pid>/cgroup`).
Следствие: рассчитывать на него нельзя, но включить (`loginctl enable-linger kesha`) — дешёвая
альтернатива `KillMode=process` для половины задачи. Вторую половину (EOF на пайпе) он не решает.

### F6 — Claude-сессию можно подхватить без форка SDK. CONFIRMED (чтение установленного кода)

`claude-agent-sdk 0.2.114`, `/home/kesha/orchestra/.venv/lib/python3.12/site-packages/claude_agent_sdk/`:
- `ClaudeSDKClient.__init__(self, options: ClaudeAgentOptions | None = None, transport: Transport | None = None)`
  — `client.py:68-72`, параметр публичный;
- `connect` использует его дословно: `if self._custom_transport: self._transport = self._custom_transport`
  — `client.py:187-195`;
- `Transport` (ABC, `_internal/transport/__init__.py:8`) требует ровно 6 методов: `connect`,
  `write`, `read_messages`, `close`, `is_ready`, `end_input` — все сантехнические;
- весь жизненный цикл процесса заперт в `SubprocessCLITransport` (`self._process` встречается в
  11 местах одного файла: 535, 692, 695, 699, 702, 706, 708, 716, 732, 734, 813), снаружи его
  никто не трогает.

То есть транспорт поверх унаследованных FD — это один класс на ~6 методов, без патча SDK.
**Уточнение о статусе: это установленная возможность API, а не проверенный прогон.** Сквозной
прототип «SDK поверх унаследованного FD» я не запускал; проверен сырой провод CLI (F1).

### F7 — Socket-маршрут у Codex существует, но нашему протоколу не отвечает. CONFIRMED (прогон) + LIKELY (объяснение)

`codex app-server --help` действительно предлагает `--listen unix://PATH` и `ws://IP:PORT`.
Прогон: сокет создан (`srw------- probe.sock`), соединение принято, я отправил ровно тот
`initialize`, который отправляет наш `backend_codex.py`, — и получил `RECV: b''`, то есть
сервер закрыл соединение, не ответив. В stderr только предупреждение про bubblewrap.

Косвенное объяснение (LIKELY, из `--help`, не из кода): у control-сокета иное кадрирование —
для него существует отдельный переходник `codex app-server proxy --sock <SOCKET_PATH>`
(«Proxy stdio bytes to the running app-server control socket»), а `codex app-server daemon`
управляет ОДНИМ локальным демоном (`start|restart|stop|version`), в справке которого нет ни
слова про переживание отключения клиента, про несколько клиентов и про idle-timeout.
Плюс архитектурная цена: один общий демон на всех агентов ломает изоляцию per-session (свой
`cwd` он принимает, но env, прокси, `CODEX_HOME` и UID — свойства процесса демона).

Вывод: для Codex дешёвый маршрут — FD store поверх СУЩЕСТВУЮЩЕГО stdio-спавна (измерено, F1),
а не смена транспорта. Маршрут `daemon`+`proxy` не закрыт — он **непроверен**, и проверять его
надо прогоном `proxy`, а не рассуждением.

### F8 — Цена ниже, чем у (D), но ДОЛГОВЕЧНОЕ состояние ≠ состояние ХОДА. UNCERTAIN (оценка, и ревью нашло в ней дыру)

Ключ, который меняет арифметику #220: сегодняшний рестарт УЖЕ пересобирает все объекты сессий
(`manager._load_from_db`, `manager.py:1488`) и переподключает бэкенды (`auto_resume_all`,
`manager.py:1791`). Значит вариант (D) («разнести сессии и веб-слой») решал задачу, которая
частично уже решена: не хватает ровно одного — не убивать и не пересоздавать CLI, а **принять
уже живой процесс**.

**Где это рассуждение ломается (находка ревью, проверена в коде и принята).** Из БД
восстанавливается ДОЛГОВЕЧНОЕ состояние, а состояние ИДУЩЕГО ХОДА не восстанавливается ничем —
более того, оно сегодня осознанно стирается. Дословно из `auto_resume_all`:
```
c.execute("UPDATE sessions SET status='idle' "
          "WHERE status IN ('running', 'interrupted', 'waiting')")
```
То есть текущий рестарт не «теряет ход случайно», а ЗАБЫВАЕТ его по построению. Живёт только в
питоне и в БД отсутствует как минимум это: у Codex — futures незавершённых запросов
(`_pending_requests`), задача-читатель, `_active_turn_id`, состояние компакта; у Claude — клиент
SDK и его приёмник, карты преобразования, `pending_control_responses` (F10); у сессии —
`_listen_task`, итератор `events()`, накопленный вывод, признак «кому принадлежат эти байты».
Новый процесс сможет РАЗОБРАТЬ байты, но обязан ещё решить, какому ходу они принадлежат,
опубликовать и записать их, закрыть ход, обновить usage и статус, вызвать `on_idle` и не
запустить конкурирующий ход.

Отсюда честная переоценка: фраза «новой сериализации не требуется» **неверна** и снята. Верно
другое: не требуется сериализовать 101 поле и 63 атрибута сессии (это и так делает БД), а
требуется НОВЫЙ, отдельно спроектированный контракт восстановления ХОДА. Мою оценку «≈550 строк»
поэтому считать нижней границей без доказательства: она получена до того, как этот контракт был
назван, и до сквозного прототипа мерить нечего.

Инвентарь (собран замерными детьми, правила счёта заданы дословно):
- внешних обращений к живым объектам сессий — **33** (`manager.py` 13, `routes/system.py` 6,
  `routes/sessions.py` 5, `tg_bridge.py` 4, `routes/subagent.py` 3, `merge_operations.py` 1,
  `db.py` 1). Они остаются в одном процессе с реестром → переделывать НЕ надо (в отличие от (D));
- `live_broker` — **17** мест, все внутрипроцессные; он просто стартует пустым, и это уже
  документированное поведение (`live_broker.py:1-8`: «The final DB-persisted 'text' log is always
  authoritative on reload/reconnect»);
- `AgentSession` — 101 поле dataclass + 63 различных атрибута, присваиваемых вне блока полей.
  **Из этого инвентаря НЕЛЬЗЯ заключать, что всё восстанавливается: часть 63 атрибутов живёт
  только в памяти (перечислены ниже в этой же находке).** Сколько именно полей реально
  восстанавливает `_load_from_db`, надо посчитать по его коду — этой цифры у меня нет, и до неё
  инвентарь не доказывает ничего про восстановимость;
- процессы порождают 4 рантайма (`backend_codex.py:479`, `backend_claude.py` через SDK,
  `backend_grok.py:296`, `backend_opencode.py:215`); живых в проде два.

Оценка объёма (моя, не замер): модуль FD-store (~80 строк), adopt-путь в двух рантаймах
(~60 Codex + ~100 Claude через custom transport), реанимация состояния хода и итератора
`events()` (~150), путь выключения «сохранить FD и не убивать детей» (~60), юниты
`orchestra.service` + `orchestra.socket` (~15 строк конфига), сборщик сирот (~80).
Итого **≈550 строк плюс тесты**. Это заметно меньше, чем транспорт + IPC вместо `live_broker` +
распределённый реестр, которые требовал (D).

### F9 — MCP-процессы едут с CLI. CONFIRMED (измерено). Что «инструменты меняются на следующем ходу» — НЕ доказано (понижено после ревью)

Родители живых `app/mcp_stdio.py` — сами CLI, не Orchestra:
```
mcp=3045203 ppid=3045132 parent=/usr/bin/claude --output-format stream-json
mcp=3046460 ppid=3045147 parent=/usr/lib/node_modules/@openai/codex/…
```
Отсюда три следствия. MCP-сервер переживает рестарт вместе со своим CLI (его никто не трогает).
Тела инструментов живут в супервизоре за HTTP и обновляются рестартом сами. Замороженным
остаётся только код самого шима и СПИСОК инструментов — то есть ровно то, что чинится
пересозданием CLI. Особый случай из #215/#217 (новый обязательный аргумент в шиме против старого
процесса) закрывается тем же пересозданием.

**Чего этот замер НЕ доказывает (принято от ревью).** Родительство доказывает только, кто с кем
умирает. Вторая половина цели юзера — «инструменты и промпты подменяются на следующем ходу» —
требует АТОМАРНОГО протокола на границе хода, которого сейчас нет ни в одном виде:
дождаться достоверного завершения хода → не дать очереди и вклиниваниям стартовать на СТАРОМ CLI
→ дочитать его вывод → погасить и убрать старый CLI вместе с MCP-детьми → поднять новый CLI и
возобновить тот же диалог → и только теперь отпустить очередь. Первый же шаг этого протокола —
«достоверное завершение хода» — у Codex в моём прогоне не наблюдался (F1), то есть у одного из
двух живых рантаймов граница хода пока не подтверждена наблюдением. Это обязательный предмет
прототипа фазы 2, а не следствие F9.

### F10 — Обратный канал: живой CLI может СПРОСИТЬ супервизора посреди хода, и в окне рестарта спросить некого. CONFIRMED в коде, НЕ измерено (находка ревью, я её пропустил)

Все мои зонды читали поток в одну сторону, и это скрыло целый класс отказа. Провод CLI ↔
супервизор двунаправленный: у Claude SDK есть control-канал с ожиданием ответа —
`pending_control_responses: dict[str, anyio.Event]` (`_internal/query.py:114`),
`_handle_control_request` / `control_response` (`query.py:236-257`), а решение о разрешении
инструмента отдаёт наш ПИТОНОВСКИЙ колбэк: `permission_mode="default",
can_use_tool=_make_auto_approve(self._is_orchestrator)` (`backend_claude.py:277`).

Значит: если переживший рестарт CLI посреди хода запросит разрешение на инструмент, отвечать
будет некому до того момента, как новое поколение полностью поднимет клиента SDK и заберёт
транспорт. **Что при этом происходит с ходом — ЖДЁТ или падает — UNKNOWN, и моя первая
формулировка «он ЖДЁТ» была домыслом.** Проверено в установленном SDK: входящие control-запросы
обрабатываются через `_inflight_requests` (`query.py:126,240`) БЕЗ таймаута на этой стороне;
единственный найденный таймаут смотрит в противоположную сторону — `initialize_timeout: float =
60.0` (`query.py:83`) для ИСХОДЯЩИХ запросов. Значит ограничение по времени, если оно есть,
живёт в CLI/протоколе, а не в SDK, и установить его можно только прогоном. Ждать пришлось бы не
100 мс из моего стенда, а всё окно старта Orchestra (F4, десятки секунд). Socket activation здесь не помогает вовсе: этот трафик
идёт по stdio, а не по HTTP.

Почему мой замер этого не увидел: Claude-зонд запущен с `--permission-mode bypassPermissions`,
то есть ровно та ветка, где вопрос не задаётся. Проверять надо ходом, который ГАРАНТИРОВАННО
спросит разрешение уже после рестарта. Это обязательный тест фазы 2 и первый кандидат на то,
чтобы обрушить весь замысел: если у control-канала есть свой таймаут короче окна старта, ход
не «доиграется», а упадёт — и именно на самой частой операции (вызов инструмента).

### F11 — Socket activation спасает НОВЫЕ соединения, но не начатый tool-вызов. CONFIRMED по механизму, НЕ измерено (вторая находка ревью, я её пропустил)

Дыра в моём же выводе F4. Socket activation сохраняет слушающий сокет, поэтому новые соединения
ждут в backlog. Она НЕ переносит уже УСТАНОВЛЕННОЕ соединение и не сохраняет питоновский
обработчик, который его обслуживал. Сценарий: MCP-шим живого агента вызвал `/api/...`, сервер
принял запрос, побочный эффект уже совершён, — и рестарт убивает обработчик до того, как ответ
дошёл до шима. Агент видит упавший или НЕОПРЕДЕЛЁННЫЙ tool-вызов: он не знает, случилось ли
действие.

Почему это больно именно у нас: инструментов 77, и среди них заведомо неидемпотентные —
`spawn_worker`, `merge_worker`, `payment_receive`, `task_create`. Ретрай такого вызова может
выполнить действие ВТОРОЙ раз (второй мерж, второй воркер), а отсутствие ретрая обрывает ход,
несмотря на то что CLI и его пайп целы. То есть «ноль обрывов» недостижимо одной сохранностью
процесса: нужен либо дренаж незавершённых HTTP-запросов перед выключением, либо контракт
идемпотентности/сверки на стороне тулов. Это ещё один обязательный предмет фазы 2, и он
пересекается с уже сделанным дренажом из #220: там дренаж ждал тишины ХОДОВ, здесь нужен дренаж
незавершённых ЗАПРОСОВ.

Смежная граница, о которой пишет `feat-fan-research` (#231): недоставленное сообщение в ящике
сессии — та же самая очередь на границе хода. Ответ «где физически лежит недоставленное и
переживает ли оно смерть процесса» обязан быть ОДИН для рестарта, для ящика и для флага
«не будить», иначе у одной мысли появится второй owner. Оттуда же метрика, которую нельзя
потерять молча: 23.9% ходов сегодня склеивают ≥1 лишнее сообщение (931 за окно 03–12.08),
и это бесплатный эффект mid-turn инъекции; если граница доставки сдвинется, долю склеенных
надо мерить до и после. Плюс 93.5% ходов — это пробуждения, то есть цена границы хода
умножается почти на все ходы.

## Вердикт фазы (после ревью)

**Главный результат: снят физический риск, который делал цель недостижимой.** Процессная
граница, которую просил юзер, УЖЕ существует: ход физически живёт в CLI, а не в питоне. Замерено,
что при `KillMode=process` + systemd FD store реальные Codex и Claude переживают рестарт, поток
хода не рвётся, а терминальный кадр Claude-хода доезжает до нового поколения.

**Точная формулировка про (D) (сужена ревью во втором раунде).** Замер опровергает утверждение
«сохранить пайпы можно только вынеся сессии в отдельные процессы». Он НЕ опровергает другое
утверждение — «отдельный процесс на стороне сессии нужен, чтобы сохранить колбэки и состояние
хода»: именно оно осталось живым после F8, F10 и F11. Поэтому честно так: FD-store — рабочий
кандидат, который, ПОХОЖЕ, позволяет обойтись без (D), и решается это не аргументом, а
фальсификаторами фазы 2 (F10 — таймаут control-канала, F11 — неопределённый tool-вызов,
F8 — контракт восстановления хода). Если хоть один из трёх скажет «нужен живой процесс на стороне
сессии», (D) вернётся в игру уже как ответ на РЕАЛЬНУЮ причину, а не ради экономии 23.3% правок.

**Но «ни одного прерванного хода» этим ещё не доказано, и обещать это сейчас нельзя.** Доказана
непрерывность транспорта. Не доказано: приём хода продовым путём Orchestra (F1), достоверное
завершение хода у Codex (F1/F9), поведение обратного канала разрешений в окне рестарта (F10),
восстановление состояния хода в питоне (F8), поведение на 13 сессиях и на реальном старте (F4).
Честная формулировка результата: **это архитектура, у которой снят главный физический риск, и
которой нужен сквозной прототип фазы 2 плюс явно очерченный конверт поддержки** — что гарантируем
при штатном рестарте, что при крахе, что при `stop` и ребуте, что при переполнении store, что при
провале старта и несовместимости версий.

## Ответы на шесть пунктов постановки

**1. Граница процессов.** Её не надо проводить заново: она уже есть и проходит по CLI. В
супервизоре остаются HTTP, дашборд, TG-мост, реестр, БД, `live_broker`. В процессе агента
остаётся то, что и так там: сам CLI, его MCP-дети, его рабочие подпроцессы. Переносить
`AgentSession` в отдельный процесс НЕ нужно — этого требовал (D), и именно этого можно не делать.

**2. Кто владеет процессом агента.** Владельцем FD становится systemd (FD store), владельцем
процесса — cgroup юнита при `KillMode=process`. Отдельный юнит на агента и `systemd-run --scope`
не нужны; scope-путь к тому же инертен (F5). Сирот убирает сборщик на старте: сверить store и
реестр в БД, принять известных, добить неизвестных — с правилом fail-closed из #220 (при ПУСТОМ
реестре проход не выполняется). Отдельная улика, что сироты видимы: журнал сам пишет
`Found left-over process … in control group while starting unit. Ignoring.`

**3. Как супервизор находит живые процессы.** Не pid-файлами: `$LISTEN_FDS` + `$LISTEN_FDNAMES`
приносят сами FD, а имя FD несёт идентификатор сессии. PID нужен только для диагностики и
сверки. Порядок FD не гарантирован (F1) — ключ только имя.

**4. Падение, зависание, двойной запуск.** Падение супервизора — агенты выживают (F2), а
незаписанные события теряются (мера — F2). Падение CLI — как сегодня: EOF на пайпе, статус в
БД. Зависание CLI — существующий `HibernateManager._process_runtime_dead`
(`session_hibernate.py`) уже опирается на процесс и listener, а не на тишину. Двойной запуск —
единственный настоящий новый риск: два поколения, читающих один пайп, разорвут поток пополам;
защита обязана быть конструктивной (адоптировать только то, что пришло через `$LISTEN_FDS`
своего юнита, и отказываться, когда процесс запущен руками из чекаута).

**5. Подмена инструментов и промптов «на следующем ходу».** Граница хода уже существует и уже
используется: `assemble_prompt` из #220 пересобирает промпт при переинжекте. Инструменты
меняются пересозданием CLI на границе хода (F9). То есть эта половина задачи почти вся
сделана; трудная половина — не прервать ТЕКУЩИЙ ход, и она решается F1+F4.

**6. Что останется требующим настоящего перерыва.** `systemctl stop` и ребут машины (F2) —
принципиально, потому что store живёт до конца юнита. Обновление самого CLI — доедет до агента
на его следующем ходу, что и есть требуемая семантика. Правка кода adopt/FD-store — самая
опасная категория: ошибка в ней теряет агентов, поэтому её выкат честнее делать при пустом
поле. Группа A из #220 (интерпретатор, нативные расширения, форма живых объектов) никуда не
делась, но перестаёт стоить ходов: процесс перезапускается целиком, а ходы этого не замечают.

## Counter-evidence и чем это может развалиться

- **Против моего же вывода F1:** «переживает» проверено на ходах, где работа шла в SHELL-команде
  (`sleep 90`). Ход, который в момент стыка ждёт ОТВЕТА МОДЕЛИ по сети, я не проверял отдельно;
  доводов, почему он должен вести себя иначе, у меня нет, но и замера нет.
- **Против «ничего не теряется»:** нулевой GAP получен на строках короче PIPE_BUF. Реальные
  JSON-строки CLI бывают крупнее 4 КиБ, и тогда возможна разорванная строка на стыке; один
  такой остаток (149 байт) я уже наблюдал. Это чинится переносом остатка, но означает, что
  «потерь нет» без такого переноса — неверно.
- **Против «крах тоже безопасен» (F2):** выжил ПРОЦЕСС, а не учёт. Поколение, убитое SIGKILL,
  не записало 378 прочитанных строк. Обещать «краш бесплатен» нельзя.
- **Против дешевизны (F8):** оценка объёма — моя, а не замер; такой архитектуры не существует,
  мерить нечего. Ровно этой оговоркой в #220 сопровождалась оценка (D), и она оказалась
  недооценкой не объёма, а ЦЕЛИ.
- **Против socket activation как решённого вопроса:** 90/90 получены на тривиальном ASGI-
  приложении. Реальное приложение стартует секунды, и очередь backlog не бесконечна: при
  достаточном числе висящих запросов часть всё равно отвалится по своему таймауту. Нужен
  замер на реальном старте, его нет.
- **Против меня, в пользу (D):** если когда-нибудь понадобится менять код супервизора, НЕ
  прерывая ход, — FD store этого не даёт (процесс супервизора всё равно новый, а ход живёт в
  CLI, что как раз и требуется). Случай, где (D) действительно нужен, — тот, где состояние хода
  живёт В ПИТОНЕ, а не в CLI. Сегодня это не наш случай, и это следует перепроверять, если
  появится рантайм без своего процесса.

## Affected files, risks, edge cases (если фаза 2 будет одобрена)

Файлы: `/etc/systemd/system/orchestra.service` (+ новый `orchestra.socket`), `app/main.py`
(инициализация из унаследованного сокета, lifespan-выключение), новый модуль FD-store,
`app/backend_codex.py` (adopt вместо спавна), `app/backend_claude.py` (custom `Transport`),
`app/manager.py` (`auto_resume_all`/`_load_from_db` — принять живое вместо реконнекта, сборщик
сирот), `app/session.py` (реанимация `events()`/статуса хода).

Риски по убыванию:
0. обратный канал без отвечающего в окне рестарта (F10) — самый вероятный убийца замысла;
1. двойной читатель одного пайпа (расщепление потока) — конструктивная защита обязательна;
2. утечка FD и сирот в cgroup: они считаются в `MemoryMax=12G` и невидимы для `systemctl`;
3. `FileDescriptorStoreMax` надо считать от числа сессий × 2 (сегодня 6 живых CLI → 12 FD, но
   на 13 сессиях уже 26); при переполнении store молча не примет FD — нужен громкий отказ;
4. правка, которая ломает adopt, теряет агентов не в тестах, а в проде;
5. окно, где сессия уже адоптирована, но статус в БД ещё старый.

## Открытые вопросы (не установлено этой фазой)

Первые четыре — обязательные предметы прототипа фазы 2; без них «ноль обрывов» остаётся гипотезой.

1. **Обратный канал разрешений в окне рестарта (F10).** Ход, который заведомо спросит разрешение
