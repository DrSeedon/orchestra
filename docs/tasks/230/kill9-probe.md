# T3 — проба на `kill -9`: ОТРИЦАТЕЛЬНЫЙ результат с названным механизмом

Критерии предрегистрированы ДО прогона (`/home/kesha/orchestra-scratch/230b/T3-preregistered.md`)
и здесь не переписаны. Проба ставилась на стенде `orchestra-237` (порт 18888, свой клон, своя
БД); боевой `orchestra.service` не затрагивался.

## Что проверялось

Цель 2 юзера: живучесть агента как ЕГО свойство, а не следствие того, что сервер успел
попрощаться. Поэтому удар — именно `kill -9` по супервизору, при котором штатная передача
дескрипторов не выполняется вовсе.

## Разрешающее плечо (снято до удара)

| признак | значение |
|---|---|
| `STARTED` на диске | есть, через 14 с после отправки задания |
| статус сессии | `running` |
| `NFileDescriptorStore` | `2` |
| CLI Grok | pid **4037129**, starttime **88786193**, `ppid=4033404` (= MainPID стенда) |
| MainPID стенда | `4033404` |

Задание задавало длительность стенными часами (`sleep 150`), удар нанесён внутри интервала —
иначе быстрый рантайм успевает закончить ход до сигнала (на этом уже сгорал прогон в #237).

## Результат: ЧАСТИЧНО, и это провал по предрегистрированным критериям

**Пункт 1 выполнен: CLI пережил `kill -9`.** Дословно из журнала systemd:

```
orchestra-237.service: Main process exited, code=killed, status=9/KILL
orchestra-237.service: Unit process 4037129 (node) remains running after unit stopped.
orchestra-237.service: Unit process 4037136 (grok) remains running after unit stopped.
```

То есть `KillMode=process` работает: смерть супервизора сама по себе агента не убивает.

**Пункт 4 провален: усыновление не состоялось, и CLI умер вскоре после.** Дословно:

```
Found left-over process 4037129 (node) in control group while starting unit. Ignoring.
Resumed worker: probe237-grok
Failed to resume worker probe237-grok: Pipe transport is only for pipes, sockets and character devices
```

Через 12 с после удара `4037129` и `4037136` мертвы. `NFileDescriptorStore` остался `2` —
дескрипторы этого агента в store не добавились.

## Механизм (установлен, а не предположен)

**Только Codex создаёт СВОИ пайпы.** `grep -ln "attach_owned_pipes" app/backend_*.py` →
`backend_codex.py`, `backend_jsonrpc.py`. Grok спавнится обычным путём
(`app/backend_grok.py:331-334`: `create_subprocess_exec(..., stdin=PIPE, stdout=PIPE)`), поэтому
его `fd_in`/`fd_out` берутся из asyncio-транспорта через `get_extra_info`.

Такой дескриптор не является тем концом пайпа, который можно отдать и потом принять: новое
поколение получило из store нечто, на что `connect_read_pipe` отвечает `Pipe transport is only
for pipes, sockets and character devices`. Усыновление провалилось, читателя у CLI не стало, и
он завершился.

Это ровно тот класс, который #237 уже описал для uvloop (`get_extra_info("pipe") → None`), но в
новом обличье: здесь первое звено вернуло не пустоту, а **непригодный** дескриптор, и потому
`publish_backend_fds` отработал «успешно», ничего не защитив.

## Что это значит для T2

T2 даёт независимость от аварии **только рантайму с parent-owned пайпами**, то есть сегодня
только Codex. Для Grok правка публикует то, что принять нельзя. Формулировка «дескрипторы у
systemd с момента спавна» верна буквально и недостаточна по существу: важно не «положили», а
«положили то, что можно принять».

Проверить это на Codex сейчас нельзя: его ходы заблокированы недельной квотой
(`weekly_quota_blocked`, 97% при пороге 95%), а поднять CLI без хода штатного способа нет.

## Что нужно сделать (не входит в текущие тикеты)

**T6 — дать Grok parent-owned пайпы**, как у Codex (`attach_owned_pipes` в `connect`). После
этого повторить эту же пробу без изменения критериев. До T6 пункт приёмки 2 остаётся
закрытым только для Codex и недоказанным даже для него.

## Границы

- Проба выполнена один раз на одном рантайме; повторов не было.
- Состояние store до пробы (`2`) принадлежало прошлому усыновлению стенда, а не этому агенту.
- Стенду выдана копия `~/.grok/auth.json` в его изолированный `HOME`
  (`/home/kesha/orchestra-scratch/237/home/.grok/`); пользовательский файл не изменялся
  (mtime до и после — `2026-08-13 16:09`).

Дословно из журнала нового поколения: `[probe237-grok] adopted a live CLI; its turn keeps
running`. Ошибки `Failed to resume` больше нет — то есть T6 закрыл ровно тот дефект, ради
которого делался: в store теперь лежит то, что можно принять обратно.

## Что провалено: пункты 5 и 6

Финального файла нет, статус остался `running`, CLI позже умер. Причина — в журнале, через
4 секунды после усыновления:

```
[probe237-grok] adopted a live CLI; its turn keeps running
[probe237-grok] listen task exited without exception (silent death), status=AgentStatus.IDLE
[probe237-grok] releasing adopted CLI at the turn boundary so new tools and prompt take effect
[probe237-grok] grok turn started
```

**Механизм.** Grok — рантайм `per_turn` (`runtime_registry.py:329`): его цикл событий живёт
только внутри хода, созданного `send()`. У принятого бэкенда счётчик активных промптов равен
нулю, поэтому `events()` завершается немедленно — «silent death», — ход считается законченным,
статус падает в IDLE, и обновление на границе хода (#237 T9) штатно отпускает усыновлённый
CLI. Дальше начинается новый ход, а старый процесс убивается.

Это ровно тот дефект, который для Codex закрывался в #237 T5 возобновлением
`_turn_event_loop` при усыновлении. Для Grok такого возобновления нет.

## Вывод

**Пункт приёмки 2 остаётся НЕ доказанным ни для одного рантайма.** Для Grok осталось одно
недостающее звено, и оно названо: восстановить у принятого бэкенда признак идущего промпта и
возобновить цикл событий, как сделано для Codex. Это T7; до него прогон 2 засчитывается как
FAIL по предрегистрированным критериям, а не как «почти получилось».

Порядок находок сам по себе показателен: T2 «положили дескрипторы» → T6 «положили то, что
можно принять» → T7 «принятое кто-то читает до конца хода». Каждый предыдущий шаг рапортовал
успех, пока следующий не был сделан.

Журнал повторяет прогон 2 дословно: `adopted a live CLI; its turn keeps running` → через 4 с

## Что это означает: T7 необходим, но не достаточен

Оракул T7 зелёный и мутацией проверен: `events()` действительно перестал выходить на первом
событии, когда счётчик восстановлен. На живом пути этого не хватило, значит слушатель
завершается по ДРУГОЙ ветке, а не по «нечего слушать».

`active_turn_id` в БД при этом непуст (`f860380018c14efa9982378b1f7811f8`), то есть счётчик
должен был встать в 1 — эта гипотеза проверена и **не** объясняет прогон 3.

**Следующий кандидат, названный но НЕ проверенный:** `_read_stdout` в своём `finally`
безусловно кладёт `_process/exited`, а `events()` на этом событии выходит (`backend_grok.py`,
ветка `if message.get("method") == "_process/exited": return`). У принятого бэкенда
`self._proc is None`, поэтому `returncode` вычисляется как `None`, но событие всё равно
публикуется. Если читатель завершился по любой причине — например, увидел EOF, — ход будет
объявлен законченным, хотя CLI жив. Проверять это следующим шагом; до проверки — гипотеза.

## Состояние пункта приёмки 2

По-прежнему **НЕ доказан**. Достигнуто и стабильно воспроизводится: агент переживает
`kill -9` супервизора и принимается новым поколением с совпадающей identity (пункты 1, 3, 4 —
три прогона подряд). Не достигнуто: доигрывание хода после аварии (пункты 5, 6).

## Цепочка целиком (четыре ступени, каждая рапортовала успех)

1. **положили дескрипторы** (T2) — `store_fds` отработал, защиты нет;
2. **положили ПРИГОДНЫЕ дескрипторы** (T6) — принять обратно было нельзя
   (`Pipe transport is only for pipes, sockets and character devices`);
3. **есть кому читать принятое** (T7) — слушатель выходил на первом же событии;
4. **читатель не сообщает о смерти, которой не было** — открыто.

Новый оттенок к правилу из `research-method.md`: звено может вернуть не пустоту, а
**непригодное значение**. Тогда промежуточная проверка зелёная, а конечный эффект не наступает.
