## Findings

### suggestion — T1 всё ещё позволяет «купить» третий раунд тривиальным скриптом

План определяет исполняемость не свойством основного предмета ревью, а наличием результата запуска:

> «артефакт считается исполняемым не по факту, что к нему приложен скрипт, а по факту, что **ревьюер его запустил** — то есть в выводе ревью есть число прогнанных тестов или вывод скрипта.»

Это не закрывает заявленную лазейку, а переносит её на один шаг. Автор прозы может приложить тривиальный скрипт и прямо попросить ревьюера запустить его. После запуска в выводе появится число тестов или вывод скрипта, и `plan.md` формально станет «исполняемым».

Критерий должен классифицировать предмет, который исправляется между раундами. Если меняется только `plan.md`/`research.md`, предмет остаётся прозой независимо от запуска вспомогательного валидатора. Три раунда оправданы, только когда объект исправлений сам является кодом/диффом/исполняемым артефактом либо находка относится к поведению проверяемого кода.

### suggestion — T3 не закрывает риск для роли `orchestrator`

План сам утверждает:

> «Скилл — единственный файл, который читают все три роли, запускающие ревью»

Но T3 добавляет обязанность загрузки только в два файла:

> «`pipelines/default/prompts/roles/full-cycle.md:73`»

и:

> «`pipelines/default/prompts/roles/worker.md`, блок `<before-done>`»

При этом `orchestrator` действительно получает скилл:

> `skills: [html-artifacts, vps-deploy, codex-debate, grill-me, orchestra-agents]`

Если предохранитель зависит от явной обязанности загрузить скилл, такая обязанность нужна всем трём запускающим ревью ролям либо в одном общем owner, который гарантированно присутствует у всех. Иначе для `orchestrator` остаётся ровно признанный планом риск отсутствия правила в контексте.

### suggestion — T4 проверяет старый, более слабый критерий доказательства

T2 требует:

> «либо число прогнанных тестов, либо **дословную строку из артефакта, которой не было в тексте запроса**»

Но T4 AC проверяет другое:

> «`docs/tasks/177/codex-review-plan.md` существует и содержит `file:line` либо число тестов»

Таким образом, голый `file:line`, который T2 специально признаёт недостаточным, снова становится достаточным в T4. Это внутреннее противоречие плана. T4 должен применять критерий T2 дословно: число реально прогнанных тестов либо цитата, отсутствовавшая в запросе и подтверждённая `grep -F`.

Дополнительно тестовое число само по себе слабее цитаты: оно доказывает запуск команды, но не обязательно чтение предмета ревью. Для ревью чистой прозы применима именно цитата.

### suggestion — семантика загрузки по триггеру не доказана разрешённым кодом

Механизм копирования подтверждён дословно:

> `"""Copy resolved pipeline skills into <path>/<home_dir>/skills/ as native CLI skills.`

И адреса подтверждены:

> ``Claude discovers skills in `.claude/skills/`, Codex in `.codex/skills/` ``

Фактическое назначение пути:

> `dest = wt / home_dir / "skills" / sname / "SKILL.md"`

Но вывод «следовательно, скилл подгружается только по триггеру описания» из этой функции не следует. Более того, код прямо говорит:

> `whether a CLI actually discovers this directory is not something we detect`

Следовательно:

- копирование в нативные каталоги — подтверждено;
- безусловного включения содержимого скилла в системный контекст эта функция не делает;
- description-trigger loading — правдоподобная характеристика CLI, но данными разрешённых файлов не доказана;
- риск плана не опровергнут и остаётся реальным.

Есть также предусмотренные кодом случаи, когда инъекция пропускается, например:

> `if rels[sname] in tracked:`

и:

> `skipped.append(f"tracked_skill:{sname}")`

В первом случае CLI читает версию репозитория; при иных `skipped` гарантия доставки может отсутствовать. Поэтому фраза плана «разойтись нечему» слишком сильная: числа не дублируются, но обязанность и доступность owner всё ещё могут разойтись.

### question — следует ли T3 охватывать orchestrator или общий prompt?

Это требует решения автора плана. По `pipeline.yaml` распределение дословно такое:

- `orchestrator`:

  > `skills: [html-artifacts, vps-deploy, codex-debate, grill-me, orchestra-agents]`

- `sub-orchestrator`:

  > `skills: [orchestra-agents]`

- `worker`:

  > `skills: [html-artifacts, codex-debate]`

- `full-cycle`:

  > `skills: [html-artifacts, codex-debate]`

Исходное утверждение полностью верно. Но из него следует, что обязанность загрузки должна покрыть `orchestrator`, если он действительно входит в заявленные «три роли, запускающие ревью».

### Подтверждение дыры worker

В `worker.md` слово `round` отсутствует. Ограничения числа повторов ревью также нет. Самое близкое требование:

> `Touched shared runtime (message delivery, sessions, queues, locks, DB migrations)? → codex_review is MANDATORY regardless of diff size, and its findings are fixed before you report DONE`

Оно требует провести ревью и исправить находки, но не ограничивает количество раундов. Поэтому утверждение плана верно: изменение только `full-cycle.md` дыру обычного worker не закрывает.
