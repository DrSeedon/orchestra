# #37 — серверная половина: `HEAD /api/models`

## Что сделано

`@router.head("/api/models")` (`app/routes/system.py`) — статус 200, пустое тело, тот же
заголовок `X-Orchestra-Build`, что у GET. Отдельный обработчик, а не `methods=["GET","HEAD"]`
на существующем: при общем маршруте тело GET'а всё равно вычислялось бы целиком (`MODELS`,
`provider_metadata_payload()`, `is_proxy_connected()`) и выбрасывалось транспортом. Здесь не
вычисляется ничего, кроме `build_id()`.

Тело GET, его набор ключей и заголовок GET не тронуты — контракт с живым клиентом цел.

Проверка — не «метод разрешён», а «заголовок тот же»:
`test_head_carries_same_build_header_with_empty_body` сравнивает `X-Orchestra-Build` у HEAD
и GET **в одном прогоне** и требует пустое тело. Обе мутации красные:
- убрать маршрут HEAD → 405;
- оставить маршрут, убрать заголовок → падает на сравнении с GET.

Вторая и есть смысл теста: без неё зелёный «метод разрешён» прикрыл бы молча онемевший баннер.

## Замер `/api/models` — цифра в задаче завышена в 6.3 раза

Задача исходит из «4.7 КБ каждые 3 с = 1.57 КБ/с». 4732 B — это размер **несжатого** тела.
На боевом пути nginx его жмёт:

```
$ curl --compressed https://orchestra.seedon.ru/api/models
content-encoding: gzip
size_download = 747 B          (заголовки ответа — ещё 162 B)
```

| | по проводу | на 3 с | в секунду |
|---|---|---|---|
| GET сейчас | 747 B тела + 162 B заголовков ≈ **909 B** | 909 B | **≈ 300 B/с** |
| HEAD после правки | ~162 B заголовков + `X-Orchestra-Build` ≈ **190 B** | 190 B | ≈ 63 B/с |

Экономия — **≈ 240 B/с на вкладку**, а не 1.5 КБ/с. Правку это не отменяет (она в три строки
и строго лучше), но при канале 15–80 КБ/с речь про 0.3–1.6 % полосы, а не про 2–10 %.
Дальше решать не мне: если исходной целью было «разгрузить канал юзера», порядок величины
другой, и приоритет клиентской половины стоит пересчитать по этой цифре.

## Что `/api/models` тащит лишнего (форму НЕ менял)

Разбор тела, 4732 B несжатого:

```
models             4254 B  (12 моделей)
provider_metadata   852 B  (5 провайдеров)
proxy_connected       5 B
```

Внутри `models` по полям, суммарно по всем 12:

```
capabilities    2430 B   ← 57 % всего массива
context_length   315 B
id               279 B
name             278 B
provider         274 B
runtime          243 B
backend          243 B   ← побайтовый дубликат runtime ("backend": spec.runtime)
price_*          168 B
```

Два наблюдения:
1. **`capabilities` повторяется у каждой модели, а различных блобов всего 3** — по числу
   рантаймов (`{"event_stream": "per_turn", "hibernate": true, …}`, 8 полей). 12 копий трёх
   значений — 2430 B вместо ~600 B. Ключ дедупликации уже лежит в самом ответе: `runtime`.
2. **`backend` — дубликат `runtime` по построению** (`"backend": spec.runtime`, `system.py:357`),
   то есть каждая модель везёт одно и то же значение дважды.

### После рестарта — что тут можно сделать отдельной задачей

Обе правки меняют форму ответа, а значит ломают живого клиента до рестарта — не трогал.
Когда рестарт пройдёт и клиент с сервером снова совпадут, тут лежит:

1. **`capabilities` вынести в словарь верхнего уровня** `capabilities_by_runtime` и оставить
   в модели только `runtime` как ключ: 2430 B → ~600 B, то есть **−1.8 КБ несжатого,
   ≈40 % тела**. Ключ дедупликации уже есть в самом ответе, новых полей не нужно.
2. **`backend` убрать** — это `"backend": spec.runtime` (`app/routes/system.py:357`), то есть
   каждая модель везёт одно и то же значение дважды. Сначала грепнуть фронт: поле читается
   живым клиентом, и снимать его можно только вместе с клиентской правкой.

Оговорка, без которой цифра врёт: **в сжатом виде выигрыш будет заметно меньше**, чем 1.8 КБ.
Именно на этих дубликатах gzip и берёт свой коэффициент 6.3 (4732 → 747 B); убрав их из
тела, мы отбираем у него самую сжимаемую часть. Ожидать стоит десятков-сотни байт по проводу,
а не полутора килобайт — и решать, стоит ли того смена контракта, надо по этой цифре, а не по
несжатой. Мерить после правки тем же способом: `curl --compressed` через боевой хост.

## Порядок применения

Правка серверная и обратно совместимая: до рестарта живой сервер продолжает отвечать на HEAD
405, клиент по-прежнему ходит GET'ом и работает. Клиентскую половину включать **только после
рестарта** — иначе heartbeat начнёт получать 405, не найдёт `X-Orchestra-Build` и баннер
версии из #15 замолчит.

Проверка после рестарта:
```bash
curl -sI -H "Authorization: Bearer $INTERNAL_TOKEN" -X HEAD http://127.0.0.1:8888/api/models \
  | grep -i x-orchestra-build      # должен быть непустым и совпадать с GET
```
