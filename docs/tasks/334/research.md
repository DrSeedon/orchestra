## Question

**Контекст:** у нас одновременно оплачены Claude Max 20× ($200/мес) и ChatGPT Pro 20× ($200/мес).
Обе подписки жжём одной и той же нагрузкой (Orchestra: длинные контексты, высокая доля
`cache_read`, много параллельных агентов).

**Сравниваемое:** сколько API-эквивалентных долларов работы отдаёт недельный пул каждой подписки.
**Базис сравнения:** равные деньги — $200 против $200.
**Измеримый исход:** `$ API-эквивалента / 1 процентный пункт утилизации пула` и `$ за неделю`
при утилизации 100%.

Ответ должен стоять на нашей телеметрии; цены с сайтов провайдеров — только рамка.

## Главный результат

| | Claude Max 20× | ChatGPT Pro 20× (Codex) |
|---|---|---|
| Цена подписки | $200/мес | $200/мес |
| **Недельный пул, API-экв.** | **≈$2 850** | **≈$2 400–2 600** |
| $ за 1 п.п. пула | ≈$28.5 | ≈$24–26 |
| Выходных токенов за неделю | ≈11.8 М | ≈13.2 М |
| Наблюдений | 2 окна, оба до 100% | 1 окно, до 99% |
| Действует ли промо-акция | **ДА, +50% до 19.08.2026** [1] | нет активных промо [7] |
| **Пул БЕЗ промо (расчёт)** | **≈$1 900/нед** | ≈$2 400–2 600/нед |

Точность цифр — две значащие. Интервал у Codex — это размах МЕТОДА (три способа счёта, см. F2),
а не доверительный интервал: собственный разброс окон Codex неизвестен, окно наблюдалось одно.
У Claude воспроизводимость между двумя окнами высокая (F1), но это тоже не доверительный
интервал. Сравнивать эти две неопределённости как однотипные нельзя.

**Вердикт:**

- **Сегодня (до 19.08 включительно) впереди Claude Max 20×: ≈$2 850 против ≈$2 400–2 600, то есть
  на 10–20%.** Честная формулировка — «паритет с небольшим перевесом Claude», а не «Claude круче»:
  перевес сопоставим с неопределённостью стороны Codex.
- **С 20.08, когда истекает промо-акция Anthropic, перевес переходит к ChatGPT Pro: ≈$2 400–2 600
  против ≈$1 900, то есть Codex даёт примерно в 1.3 раза больше** API-эквивалентных долларов
  и примерно в 1.7 раза больше выходных токенов за те же $200.

Множитель «1.3» намеренно дан одной значащей цифрой: он получается делением на промо-коэффициент,
известный только как «+50%». Промо на +40% или +60% сдвигает эту цифру на ∓10% — сильнее, чем все
остальные поправки вместе взятые.

В пересчёте на месяц: Claude сейчас ≈$12 000 API-эквивалента за $200 (≈60×), с 20.08 ≈$8 200 (41×);
Codex Pro ≈$10 000–11 000 (≈52×). Обе подписки выгоднее API в десятки раз — вопрос только в том,
какая выгоднее.

### F1 — Claude: недельный пул $2 847, воспроизведён на двух окнах с точностью 0.13% · CONFIRMED
*Тир 1: собственное измерение по двум машинам, двум окнам и двум независимым источникам.*

Недельное окно Anthropic фиксировано по вторникам 07:00 UTC (в `usage_snapshots` восемь дат
подряд с интервалом ровно 7 суток). Счётчик, который мы читаем, — аккаунтный, а не машинный:
в сыром ответе провайдера (`data/usage_cache.json`) это `limits[1]` с `kind: "weekly_all"`,
`scope: null`.

Обе машины — VPS и ноутбук — работают под **одним** `accountUuid`
`8de190c8-81b7-472b-a458-1624d609e136`, тариф `default_claude_max_20x` (проверено чтением
`~/.claude.json` на обеих). Значит числитель обязан включать обе.

Расход, накопленный к моменту, когда счётчик впервые показал 100%
(W_A — 09.08 07:25:18 UTC, W_B — 15.08 10:01:52 UTC, моменты взяты из `usage_snapshots`):

| Окно | VPS | Ноутбук | **Пул** | Выходных токенов |
|---|---|---|---|---|
| W_A 04.08 → 09.08 07:25 | $2 077.76 | $767.18 | **$2 844.94** | 12.12 М |
| W_B 11.08 → 15.08 10:02 | $2 547.66 | $300.94 | **$2 848.60** | 11.53 М |
| расхождение | 22.6% | — | **0.13%** | 5.1% |

**Это и есть положительный контроль, что ноутбук ест ТОТ ЖЕ пул.** Два независимых окна дают
размер пула, сходящийся до 0.13%; по одному только VPS те же окна расходятся на 22.6%. Добавление
постороннего расхода не могло бы схлопнуть дисперсию — если бы этот расход шёл в другой пул.

Метод: `~/.claude/projects/*/*.jsonl`, поле `message.usage` каждого assistant-сообщения,
цены из единственного владельца `TOKEN_PRICES` (`app/models.py`: Opus 5 = $5/$25 за 1 М), кеш по
тарифу Anthropic (read 10%, write 125%). Один и тот же скрипт прогнан на обеих машинах.

Две обязательные оговорки метода:

- **Дедупликация по `message.id` обязательна: наивная сумма завышает почти вдвое** — множитель
  1.98× на W_A и 1.73× на W_B (8 572 повторных сообщения из 21 140 — это счёт по W_B). Claude Code
  при resume переписывает прежний транскрипт в новый файл, и usage считается второй раз.
- **Пересечение `message.id` между машинами — ноль** (проверено `comm -12` по обоим окнам:
  0 и 0 при 4 485 / 2 025 идентификаторах ноутбука). Сложение машин не создаёт дублей.

Сверка с `turn_usage` (третий источник, только VPS и только Orchestra): диск $2 269.79 против
БД $2 379.87 за W_B — расхождение 4.6%. **Это согласие ничего не доказывало о полноте** — см.
F9 и RULE в конце.

Расход после насыщения счётчика пренебрежим: за оба окна после отметки 100% прошло 7 ходов на
$7.82 и $5.67 (0.45% и 0.24% пула) — пул действительно блокирует работу, а не течёт дальше.

### F2 — Codex Pro: недельный пул $2 524–2 630 · CONFIRMED, точность ниже, чем у Claude
*Тир 1: счётчик пула дошёл до 99%; вторая машина учтена оценкой.*

Окно Codex — **скользящее**, стартует от первого использования: в `usage_snapshots` `resets_at`
сдвигается вслед за `now+7d`, пока утилизация 0, и замирает с первым расходом. Текущее окно
заякорено 16.08 07:26 UTC (`resets_at: 2026-08-23T07:26:39Z`, `window_minutes: 10080`,
`plan_type: pro`), на момент замера — 99%. Сброса внутри окна нет, утилизация монотонна.

Аккаунт OpenAI у VPS и ноутбука тоже **один**: `chatgpt_account_id`
`0bd9b907-7945-4714-94f9-eabc4d573e9b`, `chatgpt_plan_type: pro` (прочитано из `id_token` в
`~/.codex/auth.json` на обеих машинах). Ноутбук в этом окне работал: 14 rollout-файлов.

| Источник | $ | Выход |
|---|---|---|
| VPS, `turn_usage`, Spark исключён (авторитетный источник) | $2 212.39 · 1 241 ход | 11.89 М |
| VPS, реконструкция по `~/.codex/sessions/**`, по событиям | $2 077 | 11.39 М |
| Ноутбук, та же реконструкция по событиям | $259 · 14 rollout'ов | 1.14 М |
| **Итого на 99 п.п.** | **$2 336 – $2 472** | 13.0–13.2 М |

**Три способа счёта и почему разброс именно такой:**

1. **Наивный «последний кумулятив на файл» — отвергнут.** Он давал на VPS $1 618.90, и в ревизии 2
   из этого был выведен поправочный коэффициент 1.367, перенесённый на ноутбук ($286 → $391).
   **Коэффициент неверен и снят.** Причина недобора не в парсере: финального `token_count` нет
   всего у 5 файлов из 268. Настоящая причина — сессии Orchestra переоткрываются сутками, а файл
   лежит в каталоге даты СОЗДАНИЯ, поэтому отбор файлов по дате теряет расход, сделанный внутри
   окна в старых файлах (найдено ревьюером, ~80% разрыва). Это свойство ПОПУЛЯЦИИ сессий машины
   (на VPS воркеры живут сутками, на ноутбуке 14 интерактивных сессий), а не парсера, и переносить
   его между машинами нельзя: на ноутбуке наивный метод не недобирает, а слегка перебирает.
2. **По событиям (принят).** Разности кумулятива `total_token_usage` с фильтром по времени
   СОБЫТИЯ, а не по имени файла. Один скрипт на обеих машинах: VPS $2 077 (24 211 событий,
   270 файлов), ноутбук $259 (2 393 события). Method-matched отношение к `turn_usage` на
   VPS = **×1.065**, то есть вклад ноутбука в единицах авторитетного источника ≈ **$276**.
3. **Оценщик по показаниям самого счётчика (контроль устойчивости).** В каждом `token_count`
   лежит `rate_limits.primary.used_percent` — то же поле, что в `usage_snapshots`
   (`resets_at 1787469999` совпадает на обеих машинах). Суммируя расход двух машин между двумя
   показаниями счётчика, получаем оценку без границ окна и без нормировки 99 → 100:

   | отрезок | 10→90 | 20→80 | 10→50 | 50→90 | 5→95 | 0→99 | 30→70 | 40→99 |
   |---|---|---|---|---|---|---|---|---|
   | $/п.п. | 26.07 | 26.53 | 26.10 | 26.05 | 26.04 | 24.97 | 27.87 | 25.58 |

   Медиана **$26.06/п.п.**, размах $24.97–27.87 (±6%). Это первая внутренняя проверка
   устойчивости на стороне Codex вообще: восемь перекрывающихся отрезков одного окна согласуются
   в пределах ±6%.

**Итог: недельный пул Codex Pro ≈ $2 400–2 600**, точечно ≈$2 500. Нижняя граница — счёт по
событиям на обеих машинах, верхняя — авторитетный `turn_usage` плюс оценщик по счётчику.
Величина имеет две значащие цифры, не больше.

Это НЕ экстраполяция недели: счётчик недельный и мы дошли до 99% его. Экстраполируется только
последний процентный пункт; способ 3 не экстраполирует и его.

### F3 — Замер Claude завышен промо-акцией Anthropic, истекающей 19.08.2026 · LIKELY
*Тир 2: первоисточник — справка Anthropic, дословно. LIKELY, а не CONFIRMED, потому что
абсолютный размер лимита не наблюдаем в принципе.*

Дословно из справки Anthropic [1]:

> From May 13, 2026 through August 19, 2026, your weekly usage limit in Claude Cod[e]…
> After August 19, 2026, weekly usage limits in Claude Code return to their standard levels.
> There's no change to your plan or billing.

Оба измеренных окна целиком лежат внутри промо-периода, наша нагрузка — на 100% Claude Code,
то есть ровно тот лимит, который поднят. Значит «100% пула» в наших замерах = 1.5 стандартного
лимита, и стандартный уровень = измеренное / 1.5: **$1 898/нед, $18.98 за п.п.**

Что удалось проверить в пользу деления на 1.5: в сыром ответе провайдера наш счётчик —
единственный недельный аккаунтный (`weekly_all`, `scope: null`), отдельного бакета под промо
нет. Что проверить нельзя: **`limit_dollars: null`** — провайдер не отдаёт абсолютный лимит,
поэтому «÷1.5» останется допущением и после 20.08.

**Два честных ограничения вердикта:**

1. Промо продлевали дважды (13.07 → 19.07 → 19.08). Третье продление возможно, и тогда переход
   к перевесу Codex просто сдвинется. Вердикт «с 20.08» — это прогноз при отсутствии продления,
   а не наблюдённый факт.
2. **Фальсификатор, дешёвый и обязательный к прогону:** первое полное окно после 20.08
   (25.08 07:00 → 01.09 07:00) при том же способе счёта должно отдать ≈$1 900, а не ≈$2 850.
   Не упало — вывод неверен и снимается.

### F4 — «prolite → pro» 16.08 — это апгрейд плана $100 → $200 · CONFIRMED
*Тир 1 (наш замер отношения) + тир 3 (два независимых источника про смысл идентификатора).*

В `usage_snapshots` `codex.plan_type` меняется `prolite → pro` в **2026-08-16T07:15:41Z**, новое
окно якорится в 07:26 того же утра. Замеренное отношение размера пула (только VPS, оба плана
считаны одинаково, поэтому отношение устойчиво к поправке F2):

| Окно | план | утилизация | $ | $/п.п. |
|---|---|---|---|---|
| 11.08 00:28 → 12.08 18:08 | prolite | 92% | $522.16 | 5.68 |
| 13.08 03:36 → 14.08 17:00 | prolite | 97% | $575.75 | 5.94 |
| 16.08 07:26 → 18.08 09:11 | **pro** | 99% | $2 212.39 | **22.35** |

Отношение pro/prolite = **3.76× и 3.93×**. Опубликованное отношение тарифов Pro 20× к Pro 5× —
ровно **4.00×** [4][5]. Идентификатор `prolite` = $100-й тариф ChatGPT Pro 5×, `pro` = $200-й
Pro 20× — подтверждено issue в самом репозитории `openai/codex` (декодер планов ломался на
`"prolite"` при даунгрейде 20× → 5× и восстановлении обратно) [4].

**Следствие, важнее самого факта:** до 16.08 мы сравнивали $200-й Claude со $100-м OpenAI.
Все прежние цифры по Codex ($5.39/п.п. из #219, $6.00 из #215, «≈$600 недельный пул») — это
характеристики $100-го плана. Запись в `CLAUDE.md` («пул вырос вчетверо») по числу верна, но
причину называет неполно: это не подарок провайдера и не изменение цен, а покупка вдвое более
дорогого тарифа.

Перекрёстная валидация способа счёта: модель кредитов из прежних замеров (15 000 кредитов/нед
при 25 кредитах за $ ⇒ ≈$600/нед на prolite) при ×4 предсказывает $2 400/нед на pro. Измерено
$2 524–2 630 — расхождение 5–9%.

### F5 — Одноимённые счётчики вложены по-разному; проверено на всех строках · CONFIRMED
*Тир 1: проверка по всем строкам каждой группы, подтверждена независимо ревьюером.*

За период с 01.08, строки с `input_tokens > 0`:

| runtime | строк | `cache_read ≤ input` | `cache_read > input` |
|---|---|---|---|
| claude | 2 625 | 29 | **2 596** |
| codex | 2 111 | **2 111** | 0 |

У OpenAI `cache_read` **входит** в `input_tokens`, у Anthropic — **нет**. Причина видна в коде:
`_codex_cost` (`app/backend_codex.py:181-194`) вычитает `cached` и `cache_write` из `input`,
прежде чем применить полную цену.

Практическое следствие: «свежий вход» для Codex считается как `input − cache_read − cache_create`,
для Claude — как есть. Без поправки вход Codex завышается в ~32 раза (3.51 млрд против 108 М).

### F8 — Пул Claude списывается пропорционально ДОЛЛАРАМ, а не выходным токенам · LIKELY
*Тир 1. **Вывод ревизии 1 был противоположным и отозван. Сила вывода в ревизии 2 была завышена
и понижена до LIKELY в ревизии 3.***

Ревизия 1 утверждала обратное — что предиктором расхода работают выходные токены, а разброс 22%
между двумя 100%-ными неделями есть собственный шум метрики. Причина ошибки: в числителе стояла
одна машина из двух. После включения второй (F1):

| | доллары | выходные токены |
|---|---|---|
| W_A (VPS+ноутбук, до сатурации) | $2 844.94 | 12.12 М |
| W_B (VPS+ноутбук, до сатурации) | $2 848.60 | 11.53 М |
| **разброс** | **0.13%** | 5.1% |

**«В 39 раз точнее» — артефакт агрегирования, и на нём настаивать нельзя.** При n = 2 верхняя
95%-граница на σ составляет ≈16 выборочных с.к.о. (χ², 1 степень свободы), то есть наблюдённые
0.13% совместимы с истинным разбросом до ≈1.5%. Разрешающий тест поставлен ревьюером на отрезках
ВНУТРИ окон по показаниям счётчика (n = 8 вместо 2, обе машины):

| | коэф. вариации | размах |
|---|---|---|
| $ на п.п. | **11.9%** | 22.89–32.38 (×1.41) |
| выходных токенов на п.п. | 20.1% | 78.3–148.9 (×1.90) |

Направление подтверждается и на бо́льшей выборке, но преимущество долларов — **×1.7, а не ×39**.
Есть и прямой контрпример, где метрики расходятся в разные стороны: отрезок W_A 30→50 даёт
$25.73/п.п. при 148.9 К токенов/п.п., отрезок W_B 50→70 — $32.06/п.п. при 103.1 К, то есть
доллары +25% при токенах −31%.

*(Эти восемь отрезков посчитаны ревьюером; автор их независимо не воспроизводил — отсюда LIKELY,
а не CONFIRMED. Направление вывода при этом совпадает с независимо проверенным F1.)*

Итого: недельный пул Anthropic ведёт себя **скорее как долларовый бюджет по списочным ценам**,
чем как бюджет выходных токенов — тот же принцип, что у Codex (25 кредитов за доллар, F4).

**Практические следствия:**

- Утверждение ревизии 2 «собственный шум метрики — 0.13%, поэтому разницы в 10% значимы»
  **снято**. Значимость разрыва в 10% ограничена не разбросом Claude, а НЕИЗВЕСТНЫМ разбросом
  окон Codex, — что прямо соответствует оговорке в вердикте.
- Экономить пул Claude переходом на модель с меньшим выходом, вероятно, бессмысленно —
  списывается цена. Экономит уменьшение перечитывания контекста (F7) и уход на более дешёвую
  модель.

**Механизм ошибки, а не сам факт:** автор сверил `turn_usage` с логами CLI на диске, получил
согласие 4.6% и принял его за доказательство полноты числителя. Оба источника описывали **одного
и того же потребителя** — VPS. Согласие двух источников на одном потребителе не говорит ничего о
существовании второго. Ошибка при этом попала ровно в заявленный вывод (H3 «пулы примерно
равны»), то есть в сторону автора — что и обязана была искать внешняя проверка.

📝 **RULE (предложение в `CLAUDE.md`):** когда метрика делит измеренную величину на показания
счётчика, у которого могут быть другие потребители (общая квота, лимит аккаунта, счётчик
внешнего сервиса) → перечисли ВСЕХ потребителей счётчика и докажи, что числитель их покрывает,
прежде чем делить; согласие двух источников на ОДНОМ потребителе полноты не доказывает.
Признак второго потребителя ищется по идентификатору аккаунта, а не по каталогам своей машины.
Замер: #334 — сверка «диск против БД» сошлась на 4.6% при пропуске 12–37% пула, и пропуск
выдавался за «собственный шум метрики 22%».

## Counter-evidence и то, что замер НЕ показывает

**Против вывода:**

1. **Окно Codex Pro наблюдалось один раз.** Диапазон $2 400–2 600 отражает разброс МЕТОДОВ счёта,
   а собственный разброс окон Codex неизвестен. Частично это закрыто оценщиком по показаниям
   счётчика (F2, способ 3): восемь перекрывающихся отрезков ОДНОГО окна согласуются в пределах
   ±6%, — но это внутриоконная устойчивость, а не разброс между окнами. У Claude два окна.
2. **Привязка промо к нашему счётчику не проверена прогоном** (F3, LIKELY), а абсолютный лимит
   провайдер не отдаёт (`limit_dollars: null`). Если акция поднимает не этот счётчик, деление на
   1.5 неправомерно и перевес Claude сохранится после 19.08.
3. **Промо могут продлить в третий раз.** Тогда «с 20.08» не наступит.
4. **API-эквивалент — не деньги.** Ни один из этих долларов не заплачен. Единица зависит от
   списочных цен ($5/$25 Opus 5 против $5/$30 Sol); провайдер поменяет прайс — цифра поедет,
   хотя ни пул, ни работа не изменятся.
5. **Профиль зафиксирован, а не варьировался.** 65–68% суммы — `cache_read` (F7). Замера на
   коротких контекстах с низкой долей кеша у нас нет. Но F8 снижает риск этой оговорки: раз оба
   пула списываются пропорционально цене, ранжирование не должно зависеть от профиля так сильно,
   как считала ревизия 1.
6. **Веб-ChatGPT невидим** (F9) — единственная односторонняя неопределённость, играет против
   Codex.

**Чего замер не показывает вовсе:**

- **Качество моделей.** Здесь не сравниваются Opus 5 и Sol по результату. Доллар API-эквивалента
  у них разный по полезности, и данных об этом тут нет.
- **Доступность в момент нужды.** Пул, выжигаемый за 49 часов, оставляет 5 дней без инструмента.
  Близость недельных сумм этого не компенсирует.
- **Боль от исчерпания.** Действующее правило в `CLAUDE.md` выбирает порядок пулов по асимметрии
  ПОСЛЕДСТВИЯ (стена Claude = работать нечем; стена Codex = откат на Opus и продолжаем), а не по
  цене. **Этот замер даёт цену и не является основанием пересматривать то правило.** Фактом,
  позволяющим его пересмотреть, было бы измерение последствия: сколько часов работы реально
  встало при каждом виде стены. Такого измерения здесь нет.

**Что этот замер меняет по факту:**

- Списать прежние цифры Codex ($5.39 / $6.00 за п.п.) как относящиеся к $100-му тарифу (F4).
  Актуальная — **≈$25/п.п.**
- Ожидать сокращения недельного пула Claude примерно на треть с 20.08 и не искать причину в
  собственной нагрузке (F3).
- При планировании недели исходить из ≈$2 500 Codex и ≈$2 850 → ≈$1 900 Claude (до / после 19.08).
- **Любой замер пула впредь считать по обеим машинам** — иначе повторится ошибка ревизии 1.
- **Оценщик по `rate_limits.primary.used_percent` (F2, способ 3) — лучший из имеющихся
  инструментов замера пула Codex:** он не зависит ни от границ окна, ни от нормировки на 100%,
  ни от отбора файлов по датам. Стоит переиспользовать в следующих замерах вместо сумм по окну.
