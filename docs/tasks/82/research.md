# #82 — исследование: имя агента используется как идентификатор в трёх слоях, а переименование чинит один

## Вопрос

- **Контекст:** `rename_worker` меняет имя сессии; живой MCP-подпроцесс агента получил своё имя
  через env при коннекте.
- **Что проверяется:** правда ли, что после переименования умолчание «я сам» указывает на
  несуществующую сессию, и какой из двух предложенных фиксов (перезапуск MCP-подпроцесса против
  резолва «я сам» из БД) закрывает класс.
- **Базовая линия:** текущее поведение — env заморожен, БД переименована.
- **Измеримый исход:** для каждого пути класса — что именно возвращает СЕРВЕР на устаревшее имя
  (громкий отказ / тихая потеря) и что стоит каждый из фиксов.

## Гипотезы и их фальсификаторы

| # | Гипотеза | Фальсификатор | Итог |
|---|---|---|---|
| H1 | env `WORKER_NAME` заморожен при коннекте, переименование его не трогает → все умолчания «я сам» врут | найдётся хук в `rename_session`, пересобирающий MCP-конфиг, ИЛИ сервер резолвит имя с алиасом | **подтверждена** |
| H2 | Подпроцесс пересоздаётся достаточно часто (каждый ход/компакт), поэтому окно рассинхрона узкое | env живых процессов совпадает с временем старта сессии, а не хода | **опровергнута** (env заморожен на всё время коннекта) |
| H3 | Класс ограничен четырьмя местами из репорта | грепом найдутся другие потребители `WORKER_NAME`/`PARENT_NAME` | **опровергнута** — их около десяти |
| H4 | Достаточно починить env (любым из двух способов) | найдётся путь, где устаревшее имя лежит в БД, а не в env | **опровергнута** — таких путей три |

## Находки

### F1 — механизм подтверждён: env ставится один раз, у переименования хука нет — CONFIRMED
`_make_mcp_config` (`app/manager.py:390-400`) кладёт `WORKER_NAME`/`PARENT_NAME`/`ORCHESTRA_SCOPE`
в env MCP-подпроцесса; `app/mcp_stdio.py:38-39` читает их один раз при импорте.
`rename_session` (`app/routes/sessions.py:613-670`) обновляет: строку `sessions`, `system_prompt`,
ветку git, `session.name` в памяти и TG-топик. Пересборки `mcp_servers` и дисконнекта бэкенда там
нет ни одного.
Замер на живой машине: у всех 8 живых MCP-подпроцессов `WORKER_NAME` соответствует времени
СТАРТА процесса (16:46–16:54), то есть env замораживается на весь коннект, а не на ход.
*Тир: чтение исходника + прямое наблюдение процессов.*

### F3 — адресация по устаревшему имени падает ГРОМКО — CONFIRMED замером
Изолированная БД + `TestClient` (`/tmp/probe82.py`, живую БД не трогал):
```
P2  POST /api/bg/jobs   target_name=ghost  → 404 {"error":"session 'ghost-name' not found in scope"}
P3  POST /api/sessions/ghost/progress      → 404 {"error":"not found"}
P4  POST /api/sessions/ghost/send          → 404 {"error":"agent 'ghost-name' not found. Available: "}
P5  POST /api/report_bug reporter=ghost    → 200 (репорт принят, репортёр — призрак)
```
То есть исходный симптом (`bg_create`) — это как раз ГРОМКАЯ половина класса: агент видит отказ
сразу и может исправиться. Severity репорта здесь завышен.
*Тир: прямое измерение.*

### F4 — тест-лок: залипает, но не так, как описано в репорте — CONFIRMED замером
```
acquire(old-name) → (True, None)
release(new-name) → False            ← держателем считается old-name
acquire(new-name) → (False, 'old-name')   ← BUSY, держатель — имя, которого нет ни у кого
release(old-name) → True
```
(`app/db.py:1810-1838`: `DELETE ... WHERE scope=? AND holder=?` — сравнение по строке имени.)

**Уточнение к постановке:** пока живёт ТОТ ЖЕ MCP-подпроцесс, он берёт и отдаёт лок под одним и
тем же устаревшим именем — то есть отдаёт нормально. Лок становится неснимаемым только если между
`acquire` и `release` подпроцесс переподключился (компакт, гибернация, рестарт сервиса) и получил
новое имя. Зато отказ громкий: следующий претендент видит `BUSY — held by 'old-name'`, а такого
агента в `list_agents` нет, и снять лок может ровно одна строка — старое имя.
*Тир: прямое измерение + исходник.*

### F5 — тихий и самый вредный путь: bg-джоб будит по ИМЕНИ, хотя id лежит рядом — CONFIRMED
`app/bg_jobs.py:518`: `session = await self._session_manager.ensure_loaded(target_name, target_scope)`;
не нашли → `logger.warning(f"bg_job {job_id}: target {target_name} not found")` (`:521`) и всё.
При этом в строке джоба хранится `target_session_id` (`bg_jobs` PRAGMA: `target_session_id`,
`target_name`, `target_scope`, `created_by_name`) — и на срабатывании он НЕ используется.

Почему это хуже лока: этим же механизмом `codex_review` (`app/mcp_stdio.py:1993`) будит агента по
завершении ревью, а инструкция тула прямо предписывает закончить ход и ждать пробуждения.
Переименованный агент уходит в idle и не просыпается никогда; единственный след — строка в
журнале сервиса. Громкого отказа нет ни у кого.
*Тир: чтение исходника + схема живой БД.*

### F6 — имя работает как внешний ключ в трёх слоях, переименование чинит один — CONFIRMED
1. **env MCP-подпроцесса** — `WORKER_NAME`, `PARENT_NAME` (F1);
2. **строки в БД**: `sessions.parent_name` (рядом лежит `parent_id`), `bg_jobs.target_name` (рядом
   `target_session_id`), `test_lock.holder` (id нет вовсе);
3. **адресация HTTP** — `/api/sessions/{name}/...`.

Живая БД: у восьми воркеров `parent_name` заполнен именем родителя И `parent_id` его же id.
`rename_session` обновляет только собственную строку сессии — значит **после переименования
РОДИТЕЛЯ его дети сохраняют старое `parent_name`**, а авто-репорт адресуется по
`last_task_sender or parent_name` (`app/session_turns.py:186-187`, `app/bg_jobs.py:509-510`).
Это второй, независимый от env дефект того же класса.
*Тир: чтение исходника + запрос к живой БД в режиме read-only.*

### F7 — worktree остаётся по старому пути, и это безвредно — LIKELY
`rename_session` не трогает `worktree_path`; каталог создаётся из имени при спавне
(`workspace.create_worktree`, `wt_dir / name`). Грепом по `app/routes/`, `app/manager.py` не нашёл
ни одного места, где путь ВЫЧИСЛЯЕТСЯ из имени заново — везде читается сохранённый путь. Значит
рассинхрон «каталог зовётся старым именем» — косметика и повод для путаницы у человека, но не
поломка. Ветка git при этом переименовывается (`git branch -m`, `:658`).
LIKELY, а не CONFIRMED: проверено грепом по основным модулям, а не исполнением на живом
переименовании.

### F8 — ни один из двух предложенных вариантов не закрывает класс в одиночку — CONFIRMED
- **Вариант «перезапустить MCP-подпроцесс»** чинит слой 1 целиком. Прецедент в этом же файле:
  `change_orchestrator_scope` (`app/manager.py:965-1025`) уже делает ровно это для
  `ORCHESTRA_SCOPE` — `_disconnect_backend()`, пересборка `mcp_servers`, ленивый реконнект,
  `session_id` сохраняется. Но слоя 2 (F5, F6) он не касается вовсе.
- **Вариант «резолвить „я сам“ из БД»** в лоб дороже, чем кажется: `mcp_stdio` намеренно ходит
  только по HTTP и не имеет доступа к БД, поэтому «резолв на каждый вызов» = лишний round-trip
  на КАЖДЫЙ тул. Дешёвая его форма — положить в env неизменяемый `ORCHESTRA_SESSION_ID` и слать
  его РЯДОМ с именем, а сервер пусть предпочитает id. Это аддитивно: старый сервер новое поле
  игнорирует и работает как сегодня.
- Слой 2 не лечится ни тем, ни другим: там устаревшее имя лежит в БД. Лечится либо
  «предпочитать сохранённый id в момент использования» (`bg_jobs` — одна строка, id уже есть),
  либо «обновлять ссылающиеся строки при переименовании» (`sessions.parent_name`).

## Контр-доводы

- **Против моей же оценки F4:** без переподключения между `acquire` и `release` лок отдаётся
  нормально, то есть «худший исход» требует совпадения двух условий. Я оставляю F5 выше F4
  именно поэтому: F5 срабатывает всегда и молча.
- **Против варианта с реконнектом:** он обрывает живой ход, если агент в этот момент работает,
  и убивает кеш промпта. Для Codex это дорого — по проектной доке (`CLAUDE.md`) TTL кеша ≈30 мин
  и 10× штраф на холодную. LIKELY: цифру не перемерял сегодня, взял из доки.
- **Против «просто запретить переименование живых»:** переименование — дешёвая операция
  оркестратора, запрет ударит по рабочему сценарию; и он не чинит слой 2.

## Риски и края

- **Окно мерж→рестарт:** `app/mcp_stdio.py` подхватывается новым процессом сразу, `app/routes/`
  живёт в памяти systemd до рестарта. Любая правка контракта MCP↔роут обязана быть аддитивной:
  новое поле рядом со старым, сервер предпочитает новое, старый сервер игнорирует.
- **Переименование во время хода** — дисконнект оборвёт ход; нужна либо отложенная пересборка,
  либо отказ при `status=running`.
- **Гонка имён:** `UNIQUE` на имени есть (`sqlite3.IntegrityError` → 409), но старое имя сразу
  освобождается — его может занять другой агент, и тогда устаревшая ссылка укажет на ЧУЖУЮ
  живую сессию. Это единственный сценарий класса, где промах не громкий и не тихий, а неверный.

## Что осталось непроверенным

Живое переименование ТЕСТОВОГО воркера со сквозным прогоном путей. Механизм и последствия
доказаны кодом, процессами и измерением на изолированной БД, но end-to-end на живом агенте
требует спавна одноразового воркера. Не делал: юзер только что закрыл линию правок из-за лимитов,
а спавн — это ход модели. Готов выполнить по команде.
