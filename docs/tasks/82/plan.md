# #82 — план: имя перестаёт быть идентификатором там, где оно им быть не может

## Решение и его граница

Слоёв три (research F6), и лечить их надо разными средствами — одно средство на все три даст
второй механизм поверх первого, ровно как в #80.

| Слой | Кто владелец истины | Средство |
|---|---|---|
| env MCP-подпроцесса | текущее имя сессии | пересобрать env при переименовании (T2) |
| ссылки, сохранённые РАНЬШЕ (bg-джобы, тест-лок, `parent_name` детей) | неизменяемый `session_id` | предпочитать сохранённый id в момент использования (T1, T3) |
| адресация HTTP `/api/sessions/{name}` | текущее имя | ничего не меняем — после T2 имя верное |

**Почему НЕ делаем `ORCHESTRA_SESSION_ID` рядом с именем на всех десяти вызовах** (направление 1
от оркестратора, он просил обосновать, а не исполнить): после T2 env содержит ВЕРНОЕ имя, значит
«я сам» в момент вызова уже не врёт. Слать id рядом с именем на каждый вызов — это второй
механизм, делающий работу первого, и он ничего не добавляет ни в одном сценарии, кроме окна
«переименовали посреди хода» — а там все затронутые пути отдают громкий 404 (research F3), кроме
тест-лока, который получает id отдельно в T3. Цена отказа честная: в этом окне часть вызовов
агента упадёт с 404 вместо того, чтобы отработать. Считаю, что громкий отказ в узком окне дешевле
постоянного дублирования идентичности в каждом контракте — и заметно дешевле в поддержке.

**Важный факт, ограничивающий объём T2:** `session.mcp_servers` в БД не хранится — при загрузке
сессии он строится заново из `db_row["name"]` (`manager.py:1411`). Значит незагруженная
(гибернированная, после рестарта) сессия чинится сама, и трогать надо ТОЛЬКО живой коннект.

## Про край с переиспользованием имени

Проверил, как просил оркестратор: **предпочтение id закрывает его везде, где id есть или
добавляется**. Старое имя освобождается сразу; если его займёт другой агент, то
- bg-джоб после T1 будит по `target_session_id` → чужую сессию не разбудит;
- тест-лок после T3 сравнивает держателя по `holder_session_id` → чужой лок не снимет
  (сегодня — снял бы: `DELETE ... WHERE holder=?` по строке имени);
- `parent_name` после T3 обновляется у детей → ребёнок не приаттачится к чужому родителю.

**Остаточный риск, который кодом не закрывается:** имя, уже уехавшее в ТЕКСТ чужого контекста
(`[from:old-name]` в сообщении, которое собеседник прочитал), после переиспользования укажет на
другого живого агента. Это не чинится — только предупреждением в доке: **не переиспользовать
освободившееся имя, пока живы агенты, успевшие его увидеть.**

## Tickets

### T1 — bg-джоб будит по сохранённому id, имя остаётся для человека
- Files: `app/bg_jobs.py` (`_trigger`/`ensure_loaded` call site ~`:509-530`), `app/manager.py`
  (id-вариант загрузки поверх `db.get_session`), тесты
- Что делает: срабатывание берёт `target_session_id` из строки джоба (он там уже есть и сегодня
  не используется), имя оставляем только для логов и текста. Это самостоятельный дефект: id лежал
  рядом и до появления `rename_worker`.
  Сессия по id не найдена → лог обязан назвать И id, И имя (сегодня печатает только имя).
- AC:
  - джоб, созданный до переименования, будит воркера ПОСЛЕ переименования;
  - джоб с `target_session_id`, указывающим на архивную/удалённую сессию, не будит никого и пишет
    в лог id + имя;
  - имя цели, занятое ДРУГИМ агентом, не будит этого другого агента;
  - **фолбэка на имя НЕ делаем**: в живой БД `SELECT COUNT(*), SUM(target_session_id='')
    FROM bg_jobs` → `25 | 0`, строк без id нет ни одной. Пустой id → громкая запись в лог и
    отказ будить, а не тихий возврат к имени (иначе чиненный путь останется рабочим обходом).
- blocked-by: none

### T2 — переименование пересобирает MCP-идентичность живого коннекта
- Files: `app/routes/sessions.py` (`rename_session`), `app/manager.py` (метод рядом с
  `change_orchestrator_scope`), `app/session_turns.py` (`handle_turn_end`), тесты
- Что делает: повторяет уже работающий прецедент `change_orchestrator_scope`
  (`manager.py:965-1025`): `session.mcp_servers = _make_mcp_config(new_name, …)` +
  `_disconnect_backend()` + `_persist()`; бэкенд лениво переподключается на следующем `send`,
  `session_id` сохраняется → контекст цел.
  **Сессия занята ходом** — дисконнект оборвал бы живой ход, поэтому пересборка откладывается до
  конца хода (флаг + вызов в `handle_turn_end`). Отказывать в переименовании работающего воркера
  не будем: имя нужно человеку сейчас, а идентичность процесса подождёт до конца хода.
  Незагруженная сессия не требует ничего (см. факт выше) — записать это комментарием, чтобы
  следующий не «чинил» несуществующее.
- AC:
  - переименование ИДЛОВОГО загруженного воркера → `mcp_servers.orchestra.env.WORKER_NAME` равен
    новому имени, `session_id` не изменился;
  - переименование РАБОТАЮЩЕГО воркера → ход не оборван, пересборка происходит на конце хода;
  - переименование незагруженной сессии → дисконнекта нет вовсе, а после загрузки env верный;
  - `PARENT_NAME` детей переименованного родителя пересобирается тем же путём (иначе слой env
    починен только наполовину);
  - тест мутацией: без пересборки env остаётся старым.
- blocked-by: none

### T3 — ссылки в БД перестают указывать на имя
- Files: `app/db.py` (`test_lock`: колонка `holder_session_id` + сравнение по ней;
  миграция аддитивная), `app/routes/system.py` (эндпоинты лока), `app/mcp_stdio.py`
  (`acquire_test_lock`/`release_test_lock` шлют id), `app/routes/sessions.py` (`rename_session`
  обновляет `parent_name` детей), тесты
- Что делает: две независимые правки одного слоя.
  1. **Тест-лок**: держатель определяется по `holder_session_id`; имя хранится и показывается
     человеку. Освобождение проверяет id, а не строку. Старые строки без id (лок, взятый до
     обновления) сравниваются по имени — иначе в окне мерж→рестарт живой лок станет неснимаемым.
  2. **`sessions.parent_name` детей** переименованного родителя обновляется в той же транзакции,
     что и само переименование. `parent_id` уже верный и не трогается — именно он доказывает,
     каких детей обновлять.
- AC:
  - лок взят, воркер переименован, подпроцесс переподключился → `release_test_lock` снимает лок;
  - лок взят агентом A, имя A занято агентом B → B не снимает лок A;
  - `test_lock_status` показывает АКТУАЛЬНОЕ имя держателя, а не то, под которым брали;
  - лок, взятый старым сервером (строка без `holder_session_id`), снимается по имени;
  - после переименования родителя у всех его детей `parent_name` = новое имя, `parent_id` не
    изменился; авто-репорт ребёнка доходит.
- blocked-by: none

### T4 — живой сквозной прогон на одноразовом воркере + документирование worktree
- Files: `docs/tasks/82/live-rename.md` (протокол и сырой вывод), `docs/tasks/82/report.md`
- Что делает: спавн одноразового воркера на Haiku в ЭТОМ проекте, переименование, прогон всех
  десяти путей из таблицы research F2 (не четырёх), затем `kill_worker`. Чужих агентов не
  трогаем. Наблюдение по worktree фиксируется в отчёте как СОЗНАТЕЛЬНО не чинимое: путь нигде
  не вычисляется из имени заново, поэтому это косметика, а не поломка.
- AC:
  - все десять путей прогнаны и записаны сырым выводом, а не пересказом;
  - до правок воспроизведены оба тихих отказа (непробуждение bg-джоба, лок) — иначе прогон
    ничего не доказывает;
  - после правок: те же десять путей проходят;
  - воркер убит, `worker_wip` чист.
- blocked-by: T1, T2, T3

## Порядок и почему такой

T1 первым: он единственный чинит ТИХИЙ отказ и не зависит ни от чего. T2 и T3 независимы друг от
друга и от T1. T4 последним — он проверяет всё вместе на живом агенте.

## Аддитивность (окно мерж→рестарт)

- `app/mcp_stdio.py` подхватывается новым процессом сразу, `app/routes/` живёт до рестарта:
  MCP начинает слать `holder_session_id`, старый роут его игнорирует и работает по имени —
  сегодняшнее поведение. Новых ОБЯЗАТЕЛЬНЫХ полей запроса не вводим.
- Миграция `test_lock` — только `ALTER TABLE ADD COLUMN`, пустое значение читается как «строка
  от старого сервера, сравнивать по имени».
- `bg_jobs.target_session_id` уже существует — схему не трогаем.

## Чего план НЕ делает

- не вводит `ORCHESTRA_SESSION_ID` во все контракты (обоснование выше);
- не запрещает переименование работающего воркера;
- не переносит worktree и не переименовывает его каталог;
- не трогает `/api/sessions/{name}` — адресация по имени остаётся, после T2 имя верное.

## Вердикта Codex нет

Codex недоступен до 08.08. Самокритика:

1. **Отказ от id-в-каждом-контракте — решение, а не факт.** Оно держится на том, что окно
   «переименовали посреди хода» короткое, а отказы в нём громкие. Если окажется, что renaming
   на ходу — частый сценарий, вернуться придётся именно сюда.
2. **Отложенная пересборка в `handle_turn_end` добавляет состояние сессии.** Это лишний флаг,
   который может рассинхрониться (переименовали дважды за ход, ход упал с ошибкой). В AC заложил
   оба случая, но признаю: это самая хрупкая часть плана.
3. **T3 меняет схему живой БД.** `ALTER TABLE ADD COLUMN` безопасен, но если лок держат в момент
   миграции, поведение определяется веткой «строка без id» — её обязательно проверить тестом,
   иначе получим ровно тот неснимаемый лок, который чиним.
