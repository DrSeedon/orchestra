### T1 — bg-джобы будят по неизменяемому id
Путей оказалось не один, а **пять**: `_trigger`, `_fire_cron`, `_fire_cron_command`,
`_timeout_notify`, `_fail_notify`. Последние два — это ровно то, чем `codex_review`
сообщает о таймауте и падении, то есть переименованный агент не узнавал ни об успехе, ни
о провале своего же ревью. Все пять переведены на один `_load_job_target`.
**Фолбэка на имя нет намеренно**: в живой БД `SELECT COUNT(*), SUM(target_session_id='')
FROM bg_jobs` → `25 | 0`. Пустой id → громкая запись в лог и отказ будить.

### T2 — переименование пересобирает MCP-идентичность
`manager.refresh_identity` повторяет прецедент `change_orchestrator_scope`: конфиг
пересобирается СРАЗУ, живой бэкенд гасится на границе хода.
Три требования оркестратора выполнены и покрыты тестами:
1. **идемпотентность** — два переименования за ход дают один перезапуск (флаг булев);
2. **упавший ход флаг не съедает** — `_apply_pending_identity_restart` вызывается в начале
   СЛЕДУЮЩЕГО хода, а если коннекта не станет вовсе, новый бэкенд и так строится из уже
   пересобранного `mcp_servers`;
3. в тесте оба случая: `test_restart_happens_on_turn_boundary_not_inside_a_live_turn`
   сперва проверяет, что в `RUNNING` бэкенд НЕ гасится, потом — что после падения хода
   гасится ровно один раз.

**Факт, сокративший работу и достойный отдельной строки:** `session.mcp_servers` в БД не
хранится, при загрузке он строится заново из `db_row["name"]` (`manager.py:1456`). Значит
гибернированные сессии и всё после рестарта чинятся сами — трогать надо только живой
коннект. Не «чинить» это.

### T3 — ссылки в БД перестали указывать на имя
- **Тест-лок**: держатель сравнивается по `holder_session_id`. `ORCHESTRA_SESSION_ID`
  добавлен в env MCP — это единственное место, где id ушёл в контракт, и оно оправдано:
  id **неизменяем**, поэтому корректен даже в окне, пока env хранит старое имя.
  Строка без id (лок старого сервера) сравнивается по имени — иначе живой лок стал бы
  неснимаемым в окне мерж→рестарт.
- **`sessions.parent_name` детей** обновляется по неизменяемому `parent_id`, живым детям
  пересобирается `PARENT_NAME`. Чужие дети с тем же именем родителя не трогаются.

## Что сделано НЕ так, как предлагали

**`ORCHESTRA_SESSION_ID` не ушёл во все десять контрактов** (направление оркестратора,
принято его же согласие): после пересборки env имя в момент вызова верное, значит id рядом
с именем был бы вторым механизмом поверх первого. Цена: в окне «переименовали посреди хода»
часть вызовов агента упадёт с 404. Отказ громкий и виден сразу — это осознанный размен.

**Worktree не чиним.** Каталог остаётся по старому имени (подтверждено живым прогоном),
ветка git переименовывается. Путь читается из строки БД и нигде не вычисляется из имени
заново — это косметика и путаница для человека, а не поломка. **Следующему, кто захочет
это «починить»: не надо, переименование каталога worktree сломает пути живых процессов
ради красоты в `ls`.**

## Граница, которая закрывается не кодом

Имя, уже уехавшее в ТЕКСТ чужого контекста (`[from:old-name]` в прочитанном сообщении),
после переиспользования укажет на другого живого агента. Правило для оркестратора:
**не переиспользовать освободившееся имя, пока живы агенты, успевшие его увидеть.**

## Вердикта Codex нет

Codex недоступен до 08.08. Самокритика:

1. **Половина «после» живьём не проверена** — правки не в памяти сервера. Протокол в
   `live-rename.md` воспроизводим дословно, прогнать после мержа и рестарта.
2. **`_identity_stale` — состояние в памяти сессии.** Переживает падение хода, но не
   падение процесса; там его страхует пересборка `mcp_servers` при загрузке. Слабое место —
   если появится путь, поднимающий бэкенд мимо `send()`, флаг останется непрочитанным.
3. **`_same_lock_holder` сравнивает по имени, когда id нет хоть у одной стороны.** Это
   сознательная уступка окну мерж→рестарт, но она же оставляет старому серверу возможность
   снять лок чужим совпавшим именем. Уступка временная: после рестарта id есть у всех.
