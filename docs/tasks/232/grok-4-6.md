## 1. CLI установлен, логин не выполнялся

```
sudo npm i -g @xai-official/grok      # 3 packages, 20s
grok --version                        # grok 1.0.3 (1a29d5bc12)
command -v grok                       # /usr/bin/grok -> ../lib/node_modules/@xai-official/grok/bin/grok
```

Видно из PATH под `kesha` без обёрток. npm-пакет — лаунчер: настоящий бинарник (165 МБ)
скачался в `~/.grok/bin/grok-1.0.3`, симлинк `~/.grok/bin/grok` на него. Оба пути ведут в одно,
поэтому резолвер `backend_grok.py:21` (`GROK_BIN` → `which` → `~/.grok/bin/grok`) даёт один
и тот же бинарник по любой ветке.

**Версия скакнула 0.2.112 → 1.0.3.** Всё, что замерено в #95, снято на 0.2.x — формы событий,
имена полей квоты и поведение `--agent-profile` нужно перепроверить на первом живом ходе, а не
считать перенесёнными.

`data/grok-home/` не существует и создавать его руками не надо: `ensure_grok_home()`
(`backend_grok.py:101`) делает каталог и **симлинк** `data/grok-home/auth.json` →
`~/.grok/auth.json` при первом коннекте. Отсюда требование к логину: заходить надо
**пользователем `kesha` на этом VPS**, чтобы креды легли именно в `~/.grok/auth.json`.

### Измерено до логина

## 2. Grok 4.6 по первоисточникам

Пересланное юзером сверено с `x.ai/news/grok-4-6`, `docs.x.ai/developers/pricing`,
`docs.x.ai/developers/models` и разбором Artificial Analysis. Три утверждения из четырёх
подтвердились, одно — неполно, и неполнота бьёт ровно по нам.

| Утверждение из пересказа | Первоисточник | Вердикт |
|---|---|---|
| AA Intelligence Index 61, вровень с Sol | x.ai: «matches GPT-5.6 Sol on the Artificial Analysis Intelligence Index»; AA: 61, +5 к 4.5 | **ВЕРНО** |
| Обошёл Sol в CursorBench / FrontierCode / AA-Briefcase | 69.9 vs 67.2 · 61.3 vs 60.6 · 1577 vs 1502 | **ВЕРНО, но не полно** (см. ниже) |
| Цена та же, $2/$6 | x.ai: «Pricing starts at $2 per million input tokens and $6 per million output» | **ВЕРНО ЗАГОЛОВОЧНО, ЛОЖНО ДЛЯ НАС** |
| Доступен в Grok Build, Cursor, Grok Bot, API; первую неделю ×2 лимиты | x.ai: «available today in Cursor and Grok Build… also in the API and other partners»; «2x included usage inside Grok Build and Cursor for the first week» | **ВЕРНО**, но удвоение — только Grok Build и Cursor, **не API** |

**Что пересказ опускает.** Лидерство над Sol в трёх бенчах верно, но в двух из трёх 4.6 позади
Fable 5 Max (CursorBench 69.9 против 70.5; FrontierCode 61.3 против 63.6), а сам Cursor ранее
признавал, что снимок его кодовой базы попадал в обучающие данные Grok — то есть CursorBench
для этой пары читается с поправкой. Проигрышные строки в пересказе отсутствуют целиком:
**DeepSWE 65.9 против 73 у Sol** и **Terminal-Bench v3.0 26% против 34.6% у Sol** — последнее
и есть худшая строка модели.

Значение Terminal-Bench для нас непропорционально его весу в индексе: это ближайший публичный
прокси к тому, чем занят наш воркер — длинный агентный цикл в шелле с тулами. Композит 61
набран не там, где мы работаем.

Отдельно у AA есть цифра, которая говорит в пользу Grok сильнее любого бенча: задача решается
за ~53 хода и ~0.5 млрд входных токенов против ~103 ходов и ~2.0 млрд у Opus 5. Наш собственный
профиль расхода (68% `cache_read`, ≈$0.13 за tool-вызов) — ровно про число round-trip'ов, так что
эта ось для нас важнее интеллекта. Но это **их** замер на **их** харнессе, перенос на Orchestra
не доказан.

### 2a. Удвоение выше 200k — НЕ убрано, и кэш подорожал

`docs.x.ai/developers/pricing`, сверено 13.08.2026:

| | <200k in / cached / out | ≥200k in / cached / out |
|---|---|---|
| grok-4.5 | $2.00 / **$0.30** / $6.00 | $4.00 / **$0.60** / $12.00 |
| grok-4.6 | $2.00 / **$0.50** / $6.00 | $4.00 / **$1.00** / $12.00 |

Дословно там же: «Requests whose prompt reaches the listed token threshold are billed at the
higher rate for all tokens in the request». Порог — на **запрос**, не на ход.

Порог сохранён. Заголовочные $2/$6 совпадают с 4.5 действительно — а **ставка кэша выросла
с $0.30 до $0.50, то есть на 67%, и ровно на 67% в обоих тарифах** (0.30→0.50 и 0.60→1.00).
Для нас это не деталь: у нас `cache_read` — 97.9% всех prompt-токенов (30 суток, claude-рантайм:
5.955 млрд `cache_read` против 3.94 млн `input` и 125 млн `cache_create`). Компонент, который
подорожал, и есть весь наш счёт.

Отсюда: **на профиле Orchestra 4.6 дороже 4.5 примерно в 1.6 раза при одинаковом заголовке.**
Отношение тариф-независимо, поэтому оно устойчиво; абсолют — сценарий с названным допущением.

**Сценарий** (30 суток claude-объёма, перенесённого на xAI по прямому биллингу, допущение —
что доля `cache_read` при переносе рантайма сохранится, а она НЕ замерена):
$1 899 на 4.5 против $3 091 на 4.6 в нижнем тарифе; $3 798 против $6 182 в верхнем.

Оговорка та же, что и в фазе 1: наш `turn_usage` агрегирует токены **за ход**, а тариф считается
**за запрос**. Доля ходов с агрегатом ≥200k — 91.7% claude (2010/2193) и 85.6% codex (517/604),
семантика кэша учтена по рантаймам раздельно (`cache_read ≤ input` верно в 604/604 строк codex
и лишь в 50/2193 claude). Но **вывести из этого долю запросов ≥200k нельзя** — наши данные не
той гранулярности. Закрывается одним авторизованным тяжёлым ходом.

**Всё это касается только API-маршрута.** По подписке счёт идёт в `modelCalls`, а не в токенах,
и тариф не применяется вовсе. Значение раздела — цена отката, если подписочный маршрут не
взлетит, и она за месяц выросла.

### 2b. Лимиты подписки — НЕ ЗАКРЫТО, и закрывается только логином

Вопрос был: 20 000 `modelCalls`/мес у SuperGrok — это про 4.5 или про весь аккаунт, и как
считается 4.6.

Ответа нет и по открытым источникам не будет. Что установлено:

- **Единственный авторитетный источник — сам аккаунт.** В #95 цифры взяты из `GET /v1/billing`
  на `cli-chat-proxy.grok.com` (`used` / `monthlyLimit` / `billingPeriodStart|End`), то есть
  из CLI под кредами, а не из документации. Публично xAI разбивку по моделям не публикует.
- `docs.x.ai/grok-build/usage-limits` → **HTTP 404**, такой страницы нет.
- Поиск даёт только SEO-обзоры, которые противоречат друг другу в разы (100 / 400 / 1000
  сообщений в день у одного и того же автора) и слова `modelCalls` не знают вовсе. Опираться
  на них нельзя ни в одну сторону.
- Косвенно за «пул общий на аккаунт»: сторонние обзоры сходятся, что с июня 2026 xAI перешёл на
  один общий пул на Chat / Imagine / Voice / Build вместо подневных на продукт. Это вторичка —
  гипотеза, а не факт.

**Как закрыть, после логина, за один прогон:** снять `GET /v1/billing` до и после хода на 4.5,
затем то же на 4.6 (если он вообще появится в `grok models`), и сравнить приращение `used`.
Одинаковое приращение при одном `monthlyLimit` = пул общий и модель не влияет; разные лимиты
или отдельные счётчики вылезут прямо в ответе.

## 3. Правило допуска — под третий пул

Прежний черновик (`retriever-only`) писался под гипотезу «Grok — источник X-доступа и больше
ничего». Под отдельный пул он неверен: экономит ресурс, которого не жалко.

### Что изменилось в постановке

**Пул не дефицитен.** 20 000 `modelCalls`/мес против нашего суммарного объёма 2 719 ходов за
30 суток по всем рантаймам — это **7.4× всей нашей работы**, и период календарно-месячный, без
5h/7d окон (§7.0 полевого гида). Нормировать нечего.

**Оговорка, которая одна способна это перевернуть:** соответствие «1 ход = 1 `modelCall`»
замерено в #95 только на лёгких ходах (2 хода → +2, 3 → +4, 3 → +3). На тяжёлом ходе с
десятками tool-вызовов оно может не выполняться. Если один такой ход стоит десятки
`modelCalls`, запас 7.4× исчезает. **Это первое, что меряется после логина**, и до замера
любые слова про ёмкость — гипотеза.

Отсюда разворот вопроса: Codex-пул нормируем **по расходу**, потому что он дефицитен.
Grok-пул нормировать по расходу не нужно — его надо нормировать **по классу работы**, потому
что дефицитна не ёмкость, а пригодность.

### Что ограничивает на самом деле

1. **Контекст 500k** против Claude `[1m]`. Наши длинные воркер-сессии живут дольше этого окна.
2. **Terminal-Bench 26%** — худшая строка модели совпадает с профилем нашего основного цикла.
3. **Рантайм не проверен на 1.0.3** — версия сменила мажор, замеры #95 сняты на 0.2.x.

### Черновик правила

**Допускается:**

- **A. Ретривер.** Единственная способность, которой у нас доказуемо нет: `WebFetch` по
  `x.com` даёт HTTP 402, `site:x.com` даёт ноль. Контракт прежний и жёсткий — **URL +
  дословный фрагмент + таймстамп, без пересказа**. Пересказ — это уже суждение, а способность
  Grok к X-поиску сама по себе UNCERTAIN (`toolOverrides` в дампе #95 обещает
  `x_keyword_search`/`x_semantic_search`, живьём не проверено).
- **B. Ограниченный одноходовый анализ.** Вход фиксирован и заведомо меньше 500k, выход — один
  ответ: разбор дифа, таблица, классификация, сверка артефакта. Класс, где «1 ход = 1
  `modelCall`» работает в нашу пользу и где запас пула превращается в реальную пропускную
  способность.
- **C. Широкий веер дешёвых детей.** В #219 одиннадцать детей стоили $1.21 против $47.66 у
  координатора; в #231 дорогими оказывались дети с веб-запросами. Пул, который не жалко,
  ровно под эту фигуру: параллельность за счёт третьего счётчика, пока Claude и Codex держат
  дорогую сторону.

**Запрещается:**

- **Длинный агентный цикл реализации** — full-cycle роли, долгоживущие воркеры, код с
  десятками round-trip'ов. Основание не «он глупее», а три названные выше границы, из которых
  первая (500k) — арифметическая.

**Где правило должно жить — в коде, не в промпте.** Проверка по критерию из `CLAUDE.md`:
забыли правило → Grok не используется → деградация в сегодняшнее поведение, безвредно.
Применили слишком широко → воркер уезжает в запрещённый класс, упирается в 500k посреди
задачи, работа теряется — то есть происходит запрещённое действие. Одно направление отказа
вредное ⇒ промпт не годится. Плюс прямой замер: в #227 прямой запрет модели в промпте не
сработал 1/1 — Terra была заспавнена агентом, который этот запрет читал. Значит гейт
на выбор `model="grok"` — в маршрутизации/манифесте.

**Правило вступает в силу только после приёмочного прогона** по §8 полевого гида (состав MCP,
доставка промпта, один `turn_end` на ход, бакет SuperGrok, сходимость стоимости) — на 1.0.3
заново, и с замером `modelCalls` на тяжёлом ходе.
