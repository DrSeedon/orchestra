Фаза 1. Всё ниже — замеры по живой БД (`data/orchestra.db`, копия `/tmp/o77.db`, снимок

## Вопрос

- **Контекст**: правила поведения агентов Orchestra живут в `CLAUDE.md` (проектный +
  глобальный `~/.claude/CLAUDE.md`) и в промптах ролей `pipelines/default/prompts/`.
- **Проверяемое утверждение (гипотеза оркестратора)**: правило, сформулированное через
  СИТУАЦИЮ («при мутационной проверке»), не срабатывает, потому что рефлекс запускается
  КОМАНДОЙ («checkout»); правило-шаг исполняется, правило-напоминание — нет.
- **Базовая линия**: сегодняшние формулировки в `CLAUDE.md:163-164` и в модулях промптов.
- **Измеримый исход**: доля исполнения правила по логам — сколько раз агент оказывался в

### H1 опровергнута — с двух сторон

**Сторона «команда не спасает».** `rm -rf` — самый сильный из возможных вариантов формы:
абсолютный запрет, привязанный к дословной команде, набранный жирным первым пунктом
раздела «Безопасность» в глобальном `CLAUDE.md`. Замер: **45 нарушений**. Правило в
контексте точно есть — `dev-lead` 03.08 08:26 переписал его дословно в системный промпт
спавнимого воркера (`log id 2125`: «`rm -rf` запрещён (только `trash`/`rm -i`)»), и в тот
же день сам вызвал `rm -rf`.

Отдельно проверил, что глобальный `~/.claude/CLAUDE.md` вообще доезжает до воркеров (в
`sessions.system_prompt` его нет — его подкладывает сам Claude Code): правило «лесенка
перед тем как писать код» существует ТОЛЬКО там и цитируется четырьмя воркерами
(`perf`, `frontend`, `feat-charts`, `back`); правило про VPN «Ёжик» — тоже оттуда,
цитирует `perf`. Файл доезжает.

Почему оно мертво — видно в тех же данных, и это H5 + «мальчик, который кричал волк»:
- `which trash` на этом хосте — **пусто**. Предписанная замена физически отсутствует;
- цели вызовов: `rm -rf scratch7 && mkdir scratch7`, `rm -rf lockprobe && git clone`,
  `rm -rf /tmp/sbx62` — почти всегда каталог, созданный этим же агентом минуту назад.
  Запрет сформулирован шире своего смысла и в подавляющем большинстве срабатываний
  неправ. Правило, которое неправо 9 раз из 10, перестаёт читаться и в десятый.

**Сторона «ситуация не мешает».** memory gate сформулирован ровно через ситуацию
(«перед первым `Read`/`Grep` для задач вида исследование/диагностика/…») — и исполняется
на позиции 2 из сотен вызовов у 14 из 20 сессий: сразу после `pwd`, как и написано.

Вывод: **форма триггера не предсказывает исполнение.** Оба полюса заняты обеими формами.

### H3 уточнена, а не подтверждена

`Memory: …` — это именно напоминание («Before every DONE report, workers MUST ask»), но
оно даёт **видимый токен в артефакте, который читает приёмщик**: 91%. А посылка «CHANGELOG
не пишется никогда» **не подтвердилась**: 0 из 8 — это личный счёт одного воркера
(feat-instant, `docs/tasks/52/research.md`), при этом за те же двое суток `CHANGELOG.md`
получил 15 коммитов от других агентов (`#12 #13 #19 #21 #28 #34 #37 #49 #53 #55 #62 #69 #9`
и др.), ≈25% задач. Правильная формулировка: напоминание исполняется **ненадёжно и
по-разному у разных агентов**, а не «никогда». Это поправка к посылке задачи.

## Замер 2 — что на самом деле произошло в трёх инцидентах

Все три воспроизведены по логам. Форма одна и та же:

1. агент правит файл `F` (`Edit`/скриптом) — **не коммитит**;
2. пишет ОДНУ bash-команду: мутировать `F` → прогнать тест → откатить `F`;
3. откат — `git checkout … F`;
4. незакоммиченная правка в `F` исчезает вместе с мутацией.

| Агент | id | Команда (сокращено) | Что потеряно |
|---|---|---|---|
| perf | 9650 | `…мутация…; pytest …; git checkout app/mcp_stdio.py 2>/dev/null \|\| true` | `_codex_bin()` + 4 вызова, восстанавливал руками (9655) |
| feat-charts | 10603 / 12208 | `git checkout app/prompting.py && echo "откат подтверждён"` | правка в `#55` (`scripts/migrate_agent.py`) |
| feat-instant | 10218 | `for i in 1 2 3; do pytest…; done; …мутация…; git checkout HEAD -- app/manager.py` | импорт + 2 замены в `manager.py`, восстанавливал руками (10234) |

**17 из 59** bash-вызовов с `git checkout` были составлены в ОДНОЙ команде с мутацией.
То есть отдельного момента принятия решения об откате не существует: клауза отката
пишется как хвост рецепта, до того как мутация вообще выполнилась.

Всего по контуру: **51 эпизод мутационной проверки** у 8 агентов; откат через
`git checkout` — **21 эпизод**, через `git show …:file >` — 8, через `cp .bak` — 3.
`git checkout` — доминирующая идиома отката, а не оговорка одного воркера.

### Ключевое наблюдение: соседние строки, одна команда, разная судьба

`CLAUDE.md:163` и `CLAUDE.md:164` — соседние строки одного списка:

```
163  Зелёная проверка на АСИНХРОННОМ коде ничего не доказывает → прогони её ещё 3 раза подряд…
164  Мутационная проверка на УЖЕ ЗАКОММИЧЕННОМ фиксе → откатывай файл через `git show <commit>^:<file>`…
```

Команда feat-instant (`id 10218`) исполняет **строку 163 буквально** —
`for i in 1 2 3; do pytest…; done` — и в той же строке шелла нарушает **строку 164**.
Один агент, одна секунда, один контекст, соседние строки правил.

Это закрывает H2 (доставка): дело не в том, что правила не было в контексте. И это же
показывает, чем 163 отличается от 164:

- **163 просит сделать БОЛЬШЕ того, что агент и так делает сейчас** — повторить прогон.
  Действие помещается внутрь той же команды, не требует ни состояния, ни проверки условия.
- **164 требует действия в ПРОШЛОМ** (коммит) и в другом инструменте. В момент, когда
  агент пишет команду, исполнить правило уже невозможно — можно только вернуться назад.

## Замер 3 — эксперимент: предписанная замена так же разрушительна (H4)

Правило 164 предлагает `git show <commit>^:<file>`. Проверил, спасает ли это,
в чистом репозитории `/tmp/r77` (сценарий инцидента: незакоммиченная правка + мутация
поверх неё + откат):

```
git checkout -- f.py         → фикс на месте: 0
git checkout HEAD -- f.py    → фикс на месте: 0
git show HEAD:f.py > f.py    → фикс на месте: 0
cp/mv .bak                   → фикс на месте: 1
```

**Все три git-отката уничтожают незакоммиченную правку одинаково.** Замена, которую
предписывает действующее правило, не безопаснее запрещаемой команды. Следствие, важное
для решения: **переписать правило как запрет на команду нельзя — редиректить не на что.**
Безопасен только откат из копии, сделанной ДО мутации.

Заодно это объясняет текст правила: `git show <commit>^:<file>` в нём — рецепт того, как
мутацию **вносят** (взять до-фиксовую версию файла), а шаг **отката** правило не
описывает вовсе. Агент закрывает дыру идиоматичным обратным действием — `git checkout`.

## Диагноз

Правило исполняется, когда его действие **помещается внутрь шага, который агент уже
составляет**, и не требует ни проверки условия, ни состояния, созданного раньше.
Правило не исполняется, когда для его соблюдения нужно сначала что-то оценить
(«грязное ли дерево») или что-то сделать в другой момент времени («сперва закоммить»).

| Признак правила | Исполнение по замерам |
|---|---|
| действие внутри текущего шага, замена 1:1, условия нет | 91–100% (`Co-Authored-By`, `send_message`, push, строка 163, `Memory:`) |
| шаг в фиксированной точке, ничем не занятой | 70–95% (memory gate) |
| требует оценить условие ИЛИ действия в прошлом | ≈4% и три потери работы (`rm -rf`, строка 164) |
| предписанное действие в этой среде не работает | 1–4% (`UV_CACHE_DIR=/mnt/data`, `trash`) |

Три названных случая ложатся в одну строку таблицы, но по разным причинам:
`git checkout` — «нужно действие в прошлом»; CHANGELOG — «действие вне текущего артефакта,
никто не проверяет»; смена владельца файла в #52 — привычка, пойманная **маркером в самом
файле**, то есть тем же принципом «подсказка в точке действия».

Порядок фаз в промпте работает ПРОТИВ строки 164 и это не метафора:
`pipelines/default/prompts/roles/full-cycle.md`, Phase 3 — `1. Implement` → `2. self-verify AC`
→ `3. Test` → `5. Commit`; `git-workflow.md` — «ALWAYS commit before reporting DONE».
Коммит закреплён в КОНЦЕ, мутационная проверка живёт на шагах 2–3. Правило «мутируй только
закоммиченное» требует от агента нарушить порядок, заданный его же промптом. Плюс сама
инструкция «проверяй мутацией» есть ТОЛЬКО в `CLAUDE.md`: в `pipelines/` слова «мутация»
нет ни разу (`grep -rn "мутац\|mutation" pipelines/` → одно совпадение, про `external
mutation` в скилле деплоя).

(feat-charts `id 8051`, feat-instant `id 12710`)

## Уверенность по находкам

- **CONFIRMED** — форма триггера (команда/ситуация) не предсказывает исполнение.
  Прямой замер обоих полюсов: `rm -rf` 4% против memory gate 70–95%.
- **CONFIRMED** — правило было в контексте в момент нарушения. Соседние строки 163/164 в
  одной bash-команде; агент цитирует правило в том же ходу (`perf`, `id 9654`).
- **CONFIRMED** — предписанная действующим правилом замена (`git show …:file >`) уничтожает
  незакоммиченную работу так же, как `git checkout`. Воспроизводимый эксперимент.
- **CONFIRMED** — `git checkout` как откат мутации это норма контура, а не оговорка:
  21 эпизод из 51, четыре разных агента; 17 откатов написаны в одной команде с мутацией.
- **LIKELY** — предложенная форма («бэкап внутри той же команды») будет исполняться:
  опирается на замеренный класс правил и на то, что агенты сами к ней приходят,
  но прямого A/B нет.
- **REFUTED** — «шаг-напоминание не исполняется никогда»: CHANGELOG ≈25% (14 задач из 56),
  0 из 8 — личный счёт одного воркера.
- **UNCERTAIN** — доля потерь среди 21 отката. Точно известны 3; остальные 18 признаны
  безопасными по отсутствию жалоб, а не по реконструкции состояния дерева.

## Контр-доводы (что говорит против моего вывода)

1. **`rm -rf` — слабое доказательство «запрет не работает»**: у него два независимых
   дефекта (нет `trash` на хосте; запрет шире смысла). Возможно, безусловный запрет по
   команде работал бы при исполнимой замене. Ответ: ровно поэтому вывод сформулирован не
   «запреты не работают», а «нужна доступная замена 1:1 без проверки условия» — и в этом
   классе замер 100% (`Co-Authored-By`, `git push`, `SendMessage`).
