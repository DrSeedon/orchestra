# #131 — План: подготовка VPS + оркестратор для работы над Orchestra

Ревизия 2 (2026-08-03). Скоуп сужен решениями юзера: **миграции контура больше нет**.
Основано на `research.md` + замерах OOM/памяти этой фазы.

**ВСЕ команды выполняет юзер (или оркестратор по его команде). Агент на VPS только читал.**

## Решения юзера, определяющие скоуп

1. Соседство с ботом Кеши — ОК.
2. Группа B остаётся на ноуте — ОК.
3. **Переносится ТОЛЬКО оркестратор**, для работы над проектом Orchestra. Группа A целиком НЕ переносится.
4. **Воркеры не переносятся вообще.** Все 85 сессий остаются на ноуте.
5. Swap делаем. Приоритет памяти: **tinyproxy и бот Кеши выживают, Orchestra умирает первой.**

**ВЫЧЕРКНУТО из ревизии 1** (не делать): клонирование группы A, пересоздание 33 сессий,
`compact_worker` перед переносом, перенос локальной БД, правка `GITHUB_REPO_SCOPE_MAP`.

## Остаётся ровно четыре шага

Swap → приоритеты памяти → обновление кода до main → оркестратор на VPS.

### Поправка к вводным оркестратора
`systemctl show -p OOMScoreAdjust` печатает `infinity` **у всех** юнитов — это артефакт
отображения, а не реальное значение. Ground truth — `/proc/<pid>/oom_score_adj`, и там у
всех процессов **`0`**, то есть дефолт. Вывод «настройки пусты» верен, но проверять надо
через `/proc`, иначе после настройки не отличить успех от неудачи.

### Ключевая поправка: самый жирный процесс — НЕ Orchestra
Посылка «вероятнее всего OOM выберет Orchestra как самый жирный» **неверна**:
бот Кеши 1446 МБ против Orchestra 142 МБ, то есть в 10 раз больше. При текущем раскладе
OOM-killer скорее убьёт **защищаемый** сервис. Это усиливает необходимость шага 2:
без явных приоритетов дефолт работает **против** требования юзера, а не случайно за него.

### Наследование дочерними процессами — ПРОВЕРЕНО, работает
Крит-вопрос оркестратора («наследуют ли CLI-агенты и MCP настройку юнита»). Проверено на
живом примере — `kesha-bot-vps` спавнит ровно такое же дерево, что будет у Orchestra:
```
247289  adj=0  python3
248579  adj=0  claude          <- CLI-агент
248607  adj=0  python
248613  adj=0  workspace-mcp   <- MCP-сервер
```
Все потомки лежат в cgroup юнита и несут `oom_score_adj`, унаследованный от него
(`fork()` копирует значение, systemd ставит его главному процессу). Значит:
- `OOMScoreAdjust=` в юните **дойдёт** до `claude`/MCP-процессов — защита сработает на жирных потомках;
- `MemoryMax=`/`MemoryHigh=` применяются к **cgroup целиком**, то есть считают Orchestra
  вместе со всеми воркерами разом. Это именно то, что нужно.

## Шаг 1 — swap 4 ГБ

Зачем: `swap=0` при 7.9 ГБ и боте с пиком 2.3 ГБ. Без swap любой всплеск = мгновенный
OOM-kill вместо деградации.

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```
Отдельно — снизить агрессивность вытеснения (дефолт 60 слишком охотно свопит):
```bash
echo 'vm.swappiness=10' | sudo tee /etc/sysctl.d/99-swap.conf
sudo sysctl -w vm.swappiness=10
```

**Проверка:** `free -h` → `Swap: 4.0Gi`; `swapon --show` → `/swapfile`.
**Откат:** `sudo swapoff /swapfile && sudo rm /swapfile` + убрать строку из `/etc/fstab` и
удалить `/etc/sysctl.d/99-swap.conf`.

## Шаг 2 — приоритеты памяти

Механизм выбран так: **`OOMScoreAdjust` решает, КОГО убить при глобальной нехватке**
(это и есть требование юзера), **`MemoryHigh` тормозит Orchestra до того**, как дойдёт до
убийства, а **`MemoryMax` — жёсткий потолок**, чтобы разросшийся воркер не съел хост.

Почему не только `MemoryMax` на Orchestra: слишком жёсткий потолок = она падает сама под
нагрузкой (риск, названный оркестратором). Поэтому пара `MemoryHigh` (мягкий тормоз,
throttling+reclaim, НЕ убивает) + `MemoryMax` (потолок заметно выше) — граница ищется
между ними, а не одним числом.

Числа от замеров: Orchestra без воркеров = 158 МБ пик. Свободно 5666 МБ. Боту нужно до
2.3 ГБ. Оставляем боту и системе запас, Orchestra отдаём `MemoryHigh=2G` / `MemoryMax=3G` —
это ~13× её текущего пика, то есть места на несколько воркеров хватит, а хост не утонет.

### 2.1 Orchestra — жертва номер один
```bash
sudo systemctl edit orchestra
```
```ini
[Service]
OOMScoreAdjust=800
MemoryHigh=2G
MemoryMax=3G
ManagedOOMPreference=avoid
```
`OOMScoreAdjust=800` (не 1000: 1000 гарантирует убийство даже при копеечном потреблении;
800 надёжно ставит её первой в очереди, оставляя ядру право на здравый смысл).

### 2.2 tinyproxy — самый защищаемый
```bash
sudo systemctl edit tinyproxy
```
```ini
[Service]
OOMScoreAdjust=-900
ManagedOOMPreference=omit
```
Обоснование приоритета: он раздаёт ноуту прокси `:12343`; его смерть отрезает запасной
сетевой путь **на ноутбуке**. Ест 9 МБ — защита ничего не стоит.

### 2.3 Бот Кеши и telegram-bot-api — защищаемые
```bash
sudo systemctl edit kesha-bot-vps      # OOMScoreAdjust=-500
sudo systemctl edit telegram-bot-api   # OOMScoreAdjust=-700
```
```ini
[Service]
OOMScoreAdjust=-500
```
Боту `-500`, а не `-900`: он реально жирный (пик 2.3 ГБ), и если течёт именно он —
полная неприкосновенность утопит хост целиком. `telegram-bot-api` (14 МБ) — `-700`,
без него бот всё равно не работает.

### 2.4 Применить
```bash
sudo systemctl daemon-reload
sudo systemctl restart tinyproxy            # 9 МБ, рестарт мгновенный
# orchestra рестартуется в шаге 3 вместе с обновлением кода — отдельно не дёргать
```
**Бота Кеши и telegram-bot-api не рестартовать** — `OOMScoreAdjust` для них применится при
их следующем рестарте. Ронять живого бота ради настройки не нужно; до тех пор защищает
`OOMScoreAdjust=800` на Orchestra, которого достаточно (она и так уходит первой).

**Откат шага 2:** `sudo systemctl revert orchestra tinyproxy kesha-bot-vps telegram-bot-api`
+ `daemon-reload`. Дроп-ины лежат отдельными файлами и не трогают исходные юниты; у
`orchestra` уже есть `environment.conf` — `systemctl edit` создаст **отдельный**
`override.conf`, существующий дроп-ин не пострадает.

Останавливать обязательно: иначе `-wal` снимется неконсистентно.

```bash

```

Миграция БД пройдёт сама при старте (`init_db()` добавит `turn_usage`, `tool_errors`,

**Старые опусы** — три сессии на VPS сидят на Opus 4.6/4.8. Править **при остановленном

```bash
uv run python - <<'EOF'

c = sqlite3.connect("data/orchestra.db")
c.execute("UPDATE sessions SET model='claude-opus-5[1m]' WHERE model LIKE 'claude-opus-4%'")

```
Пинить именно `[1m]` — голый алиас даёт 200K контекста вместо 1M.

```bash
sudo systemctl start orchestra
```
**Проверка:** `systemctl is-active orchestra` → `active`; `journalctl -u orchestra -n 50`
без трейсбеков; `curl -s -o /dev/null -w "%{http_code}\n" https://orchestra.seedon.ru/` → `302`;
повторить SELECT — модели должны остаться `claude-opus-5[1m]` (если откатились, сервис не был остановлен).

**Откат шага 3:** `sudo systemctl stop orchestra` → `git checkout 41c7dc4` → вернуть оба

Откат — `checkout` на коммит + восстановление файлов, не `revert`, поэтому конфликтов нет;
убедиться только, что `41c7dc4` в истории после `fetch`.

## Как убедиться, что приоритеты РЕАЛЬНО работают (не «настроено», а проверено)

`systemctl show -p OOMScoreAdjust` **не годится** — печатает `infinity` независимо от
настройки. Проверять только по `/proc`.

### Проверка A — значения дошли до процессов
```bash
for u in orchestra tinyproxy kesha-bot-vps telegram-bot-api; do
  echo "--- $u ---"
  cat /sys/fs/cgroup/system.slice/$u.service/cgroup.procs 2>/dev/null | while read p; do
    printf "  %-8s adj=%-6s %s\n" "$p" "$(cat /proc/$p/oom_score_adj)" "$(tr -d '\0' < /proc/$p/comm)"
  done
done
```
Ожидается: orchestra → `800` у **всех** процессов включая `uv` и `uvicorn`; tinyproxy → `-900`.
У бота и telegram-bot-api останется `0` до их рестарта — это ожидаемо (шаг 2.4).

### Проверка B — наследование живыми агентами (главное)
Смысл в том, что защита обязана дойти до `claude`/MCP, а не только до `uvicorn`.
После шага 4 заспавнить одного воркера и повторить проверку A: в cgroup появятся процессы
`claude` и MCP — **у них тоже должно быть `800`**.
Это прямой аналог уже измеренного дерева `kesha-bot-vps`, где `claude` и `workspace-mcp`
корректно унаследовали `adj` от юнита.

### Проверка C — лимиты применились к cgroup
```bash
cat /sys/fs/cgroup/system.slice/orchestra.service/memory.high   # 2147483648
cat /sys/fs/cgroup/system.slice/orchestra.service/memory.max    # 3221225472
```

### Проверка D — счётчик срабатываний под нагрузкой
```bash
cat /sys/fs/cgroup/system.slice/orchestra.service/memory.events
```
`high` растёт → Orchestra упирается в мягкий лимит (норма, это троттлинг).
`oom_kill` растёт → потолок мал, поднять `MemoryMax` до 4G.
Смотреть после первой реальной нагрузки с воркерами.

### Чего НЕ делать
Не устраивать «боевую проверку» через `stress`/форк-бомбу на живом хосте: там бот Кеши и
прокси, который держит запасной канал ноутбука. Проверок A–D достаточно: они показывают,
что значения дошли, а `memory.events` покажет реальное поведение под настоящей нагрузкой.

## Порядок и почему он такой

1. **Swap** — первым: страховка на случай, если что-то пойдёт не так на следующих шагах.
2. **Приоритеты** — до обновления: если новый код окажется прожорливее, защита уже стоит.
3. **Код + БД** — здесь единственный рестарт Orchestra (совмещён с применением дроп-ина).
4. **Оркестратор** — последним, когда хост подготовлен.

Полный откат всего: шаг 4 → остановить сессию; шаг 3 → `git checkout 41c7dc4` + БД из бэкапа;
шаг 2 → `systemctl revert`; шаг 1 → `swapoff`. Шаги независимы, откатываются в любом порядке.

## Риски

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| `MemoryMax=3G` мал для нескольких воркеров | Средняя | Orchestra убита своим же лимитом | Проверка D: `oom_kill` в `memory.events` → поднять до 4G |
| Бот Кеши течёт до 2.3 ГБ пика при активной Orchestra | Средняя | Давление на память | swap 4G + `MemoryHigh` тормозит Orchestra заранее |
| `OOMScoreAdjust` бота не применён (без рестарта) | Высокая (ожидаемо) | Бот не защищён явно | Достаточно `800` на Orchestra; применится при след. рестарте бота |
| `uv.lock` конфликтует при pull | Высокая | Обновление встало | `git stash` до pull (шаг 3) |
| `sessions.model` откатывается после старта | Высокая | Опусы остались 4.6/4.8 | Править при остановленном сервисе, перепроверить SELECT |
| Два контура разъезжаются по коду Orchestra | Средняя | Конфликты мержа | Один проект — один контур; синхронизация только через `origin` |

## Открытый вопрос

Оркестратор на VPS будет вести **тот же репозиторий Orchestra**, что и локальный контур.
Нужна договорённость, кто ведёт `main`: иначе две ветки разработки одного проекта начнут
конфликтовать. Предложение — на VPS работать только в отдельных ветках задач и мержить
через `origin`. Решение за юзером.
