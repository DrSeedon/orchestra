# Замер: блокируют ли «фоновые» задачи рантайма ход агента

Повод: юзер 28.08.2026 — «эти бг таски они не в фоне нихуя, замораживают клауди пока
не доработают». Гипотеза юзера подтвердилась полностью.

## Метод

Источник — таблица `logs` в `data/orchestra.db`, read-only снимок. Считались пары
`subagent_start` / `subagent_end`, спаренные по `id=<token>` из поля `content`.
Длительность — разница `ts` между парой. «Агент работал внутри окна» = существует строка
той же `session_id` с `type in ('tool','text')`, чей `logs.id` строго между id старта и
id конца.

Окно выборки для блокировки: `ts > 2026-08-28T10:00`. Окно для длительностей: неделя,
`ts > 2026-08-21`.

## Что изменило в системе

1. `pipelines/default/prompts/base.md` — правило: команда дольше ~60 с идёт через
   `bg_create(type="run")`. Порог выбран по распределению: он трогает 11% задач и не
   задевает 385 коротких, у которых медиана 3.5 с.
2. `app/static/js/chat.js` + `style.css` — часы на живой плашке («⏳ идёт 1:05»,
   пульсация, снятие на финише). Причина: между start и end событий нет вообще,
   поэтому иного признака жизни у интерфейса не существует.

## Границы

- Выборка — только наш контур, только `task_type=local_bash`.
- «Пустое окно» доказывает отсутствие ЗАПИСАННЫХ действий, а не отсутствие мышления
  модели. Для вывода о блокировке этого достаточно: инструментов агент не звал.
- Порог 60 с выбран по распределению длительностей, а не подобран экспериментом; при
  накоплении данных его стоит пересчитать.
