   `": "`, который выводился при пустом сообщении. Предложенный фикс не тронул
   бы эту строку. Два разных дефекта под одним симптомом.
2. **Правило существовало в кодовой базе четырежды**, независимо и уже
   разошедшись:

| Копия | Отличие (= накопленный дрейф) |

## Дефект 2 — решение и обоснование

Выбран вариант **(б) логировать факт потери**, не тихое гашение.

`logs.session_id` объявлен как `REFERENCES sessions(id) ON DELETE CASCADE` —
значит у записи для мёртвой сессии нет дома **by design** и восстанавливать
нечего. Но тихое гашение дало бы «проверку, одинаковую при успехе и провале»:
следующий FK-сбой по ДРУГОЙ причине (битая миграция, гонка при архивации) снова
ушёл бы в никуда.

Способ взят у близнеца-писателя телеметрии из ЭТОГО ЖЕ класса
(`session.py:1765-1780`), который уже делал `done.result()` правильно. Один файл,
два способа — теперь один.

```
ДО    : asyncio печатает 'Future exception was never retrieved' —
        без имени агента, без типа записи, без содержимого
ПОСЛЕ : '[Orchestra-orchestrator] log write lost (error): IntegrityError:
         FOREIGN KEY constraint failed | connect failed: TimeoutError'
```

## Дефект 3 — это была ПОЛОМКА, не шум

Гипотеза «пустой pipeline у оркестратора — норма, чинить ложную тревогу»
**опровергнута** четырьмя независимыми свидетельствами:

1. Код сам объявляет пустое значение легаси-маркером: `pipeline.py:470`
   («пусто/корневой оркестратор → DEFAULT_PIPELINE») и `manager.py:1354`
   («Old rows (migrated) store pipeline='' → normalize»).
2. Измерение: `get_role('', 'orchestrator')` → `FileNotFoundError`;
   `get_role('default','orchestrator').skills` → 5 скиллов.
3. Живой диск: в `.claude/skills/` корня лежал один `codex-debate` от 5 июня;
   `grill-me`, `html-artifacts`, `orchestra-agents`, `vps-deploy` отсутствовали.
4. Живая БД: единственная НЕархивная сессия с пустым pipeline — корневой
   `Orchestra-orchestrator` (остальные 26 в архиве).

**Root cause — тот же класс, что у дефектов 1 и 2:** одно значение читалось
двумя способами внутри ОДНОЙ функции `_load_from_db`. Строка 1357 нормализовала
`'' → 'default'` и отдавала промпту (поэтому промпт был верный), строка 1408
клала в `AgentSession` сырой `db_row`. `_refresh_skills` читал сырое и падал.

Чинится нормализацией у источника, а не подавлением warning у потребителя:
правка потребителя оставила бы вторую копию логики ждать следующего читателя.

```
ДО    (pipeline='')        → 0 скиллов + 'skill refresh failed: pipeline name is empty'
ПОСЛЕ (pipeline='default') → 5: codex-debate, grill-me, html-artifacts,
                                orchestra-agents, vps-deploy
```

Спавн новых сессий не затронут — там уже используется нормализованная переменная.

## Риски и что осталось

- **Рестарта не было** — правки `app/routes/` и `app/manager.py` доедут до
  живого сервиса только при следующем перезапуске (делает юзер). `app/mcp_stdio.py`
  подхватывается немедленно; контракт MCP↔route не менялся (только текст внутри
  конверта), поэтому окно до рестарта безопасно. Проверено: `mcp_stdio`
  запускается отдельным процессом как СКРИПТ и импортирует `app.errtext` штатно
  (`PYTHONPATH` из `runtime_env`).
- **Дефект 3 меняет данные:** при первом `_persist` корневой сессии `pipeline`
  переедет `'' → 'default'` в БД. Де-факто необратимо для этой строки; согласовано
  с оркестратором — `default` там и так подразумевается везде.
- **`limit_wake` envelope:** поле `error` теперь содержит класс (`'boom'` →
  `'ValueError: boom'`). Проверено, что потребители только показывают строку или
  проверяют на истинность, не парсят.
- **НЕ измерено:** влияние отсутствовавших 4 скиллов на КАЧЕСТВО работы
  оркестратора. Установлен только факт отсутствия файлов. Утверждать «работал
  хуже» без замера я не могу.

## Урок (в этот отчёт, отдельного retro-файла нет)

Все три дефекта — один класс: **одна мысль, два владельца.** Правило про класс
исключения жило в `CLAUDE.md` и в 4+11 копиях кода; `done.result()` — в двух
методах одного класса; нормализация pipeline — в двух строках одной функции.
Везде расхождение возникло не при написании, а при последующей правке ОДНОЙ из
копий. Симптом всегда выглядел как «мелкий баг форматирования», а причиной было
отсутствие владельца.
