## Задания (одинаковые дословно, порядок фиксирован T1 → T2 → T3)

### T1 — найти дефект (реальный код `app/session_cost.py`, внесена одна правка)
Из `CostTracker.apply_turn_result` удалён блок сброса базы при смене `session_id`:
```python
if sid and sid != s.session_id:
    s._last_cost = 0.0
    s._last_cost_cached = 0.0
    s._context_cost = 0.0
```
Промпт: «В этом файле ровно один дефект, внесённый правкой. Назови строку и последствие».

**Критерий PASS (обе части обязательны):**
1. указано, что при смене `session_id` не сбрасывается накопительная база `_last_cost`
   (или эквивалентно: пропал сброс базы для нового session_id);
2. названо последствие: разность `new_cost - _last_cost` становится отрицательной,
   `max(0, …)` обнуляет её → расход хода недосчитывается (нули) после компакта/новой сессии,
   пока новая накопительная сумма не перерастёт старую.
Только (1) без (2) → PARTIAL. Указание другого места как главного дефекта → FAIL.

### T2 — объяснить участок (реальный код `app/backend_codex.py`, без правок)
Даны `_codex_cost` и `_read_rollout_context`. Три вопроса:
- (a) что вернёт `_codex_cost` для модели, которой нет в `CODEX_TOKEN_PRICES`;
- (b) `input_tokens=1000, cached_input_tokens=1500` — сколько токенов посчитается по
  свежей ставке и почему;
- (c) почему `_read_rollout_context` читает события `token_count`, а не `turn.completed.usage`.

**Критерий PASS — все три верны:** (a) `0.0`; (b) свежих 0, кешированные подрезаны до 1000
(`min(cached, input)`); (c) `turn.completed.usage` — накопительный итог по треду, он не может
показать текущее занятое окно. Две из трёх → PARTIAL.

### T3 — правка с тестом (реальный код `app/errtext.py` + его тесты)
Задание: `err_text` должен дописывать причину из `__cause__` рекурсивно, формат строго
`"<база> (caused by <err_text(cause)>)"`; при `__cause__ is None` поведение прежнее.
Требуется: правка модуля + новый файл теста; существующие тесты обязаны остаться зелёными.

**Критерий PASS — все три:**
1. `python3 -m pytest` в каталоге прогона зелёный на выданных тестах;
2. модель создала свой файл теста, и он собирается и проходит;
3. проходит мой скрытый тест (`/tmp/b199/hidden_t3.py`, написан ДО прогонов):
   - `err_text(ValueError("boom")) == "ValueError: boom"`;
   - причина одна → `"ValueError: boom (caused by TimeoutError)"`;
   - цепочка из трёх → `"A: x (caused by B: y (caused by TimeoutError))"`;
   - `err_text(TimeoutError()) == "TimeoutError"`.
Любой пункт не выполнен → FAIL (частичных нет: правка либо работает, либо нет).

## Отдельная гипотеза про пул (главный вопрос задачи)

Наш доллар — реконструкция по ценам за токен. Сколько списывает из недельного пула сам
провайдер — считает он. Совпадают ли — не проверялось никогда.

- **H1 (списание пропорционально цене).** Тогда наш доллар — честный прокси пула, и Luna
  дешевле Sol во столько же раз, во сколько дешевле её токен (25× по входу, 25× по выходу).
  Предсказание: 1 п.п. пула = **$6.2 наших долларов** для ЛЮБОЙ модели пула.
- **H2 (списание по сырым токенам).** Тогда наш доллар врёт: Luna при в 25 раз меньшей цене
  съедает пул как Sol. Предсказание: 1 п.п. = **≈8.3 млн токенов** для любой модели.

Разделяющий замер: калибровка Sol уже есть по 2 976 живым событиям текущего окна
(0 → 43 %, $6.24/п.п., шаги 4.8–7.6). Для Luna гоню контролируемый расход свежим входом
(случайный текст, чтобы не попасть в кеш) объёмом ~2.5 млн токенов. Под H1 это ≈0.08 п.п.
(незаметно), под H2 ≈0.3 п.п. — уже различимо, а при добавке до ~8 млн токенов H2 обязана
дать целый шаг счётчика, которого H1 не даёт. Параллельный расход других агентов вычитаю
по их же rollout'ам за тот же интервал.
**Falsifier H1:** Luna даёт шаг счётчика раньше, чем накопит $6.2.
**Falsifier H2:** Luna накопила ≥8.3 млн токенов, а счётчик не сдвинулся.
Порог принятия назначен здесь и после прогона не двигается.
