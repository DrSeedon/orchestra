# #223 — `full-cycle` отдаёт реализацию закрытых тикетов дешёвому исполнителю

Дата замера: 2026-08-12. Фаза 1; код и промпты не менялись.

## Прямой ответ

**Делегирование уже почти собрано из существующих правил, но Phase 3 не соединяет их.**
`full-cycle` уже пишет и коммитит красный оракул, уже получает `model-routing`, уже имеет
`can_spawn: ["*"]`; дочерняя роль `worker` уже получает запрет писать себе acceptance test.
При этом Phase 3 дословно велит самому `full-cycle` идти по тикетам и реализовывать их, а в
собранном prompt нет ни одного шага передачи тикета ребёнку [1][2][3]. Значит в границах #223
нужна правка текста роли и delivery-тест, а не новый runtime в `app/`.

**Сравнение «Luna $0.13 против координации родителя $7.45 = проигрыш в 59 раз» наблюдаемо, но
не является причинной ценой делегирования.** Первый ход родителя `$6.579` был смешанным:
классификация корпуса, постройка стенда и оракула существовали бы и в baseline, а постановка
срезов и спавн — нет; отделить их цены из `turn_usage` нельзя. Два следующих хода, вызванных
сообщениями ребёнка, стоили `$0.874` и `$0.877`. Это не чистая фиксированная «цена открыть
глаза»: в каждом родитель ещё сделал содержательную работу и вывел 4.7–6.6K токенов. Честная
формулировка — **наблюдённая стоимость message-triggered parent turn**, на 99.4–99.6 % состоящая
из `cache_read`. Один такой turn стоил примерно как семь полных Luna-срезов по `$0.127` [5].

**Что остаётся от 6–10 % после координации — пока не измерено на едином знаменателе.** Сценарный
расчёт даёт полезную границу, но не новый агрегат: у одного Opus-тикета `B=$14.48`, строковая
прокси переносимой доли `q=35 %` даёт `qB≈$5.07`; Luna research-срез `$0.127` + один
message-triggered parent turn `$0.877` оставляют `$4.06`. Эти числа смешивают один
implementation ticket, долю строк, research-ребёнка и parent turn другой фазы. Поэтому 6–10 %
из #210 остаются исходным **UNCERTAIN порядком величины до координации**, а остаток обязан
измерить первый живой Phase 3 rollout; пересчитывать их в 4.8–8.0 % нельзя [4][5].

**Текущая политика покрывает не весь failure-контракт #223.** `model-routing` разрешает сразу
выбрать Sol для закрытого, но сложного тикета. Если тикет пошёл Luna, красная команда или
недоказанный AC уже означают одну попытку и немедленную передачу Sol без повторной Luna.
Clarification, `WIP/STOP` и изменённый oracle пока не названы тем же failure-классом — это новая
политика, которую Phase 2 обязана закрепить. `oracle: none` не делегируется вообще и остаётся у
дорогого `full-cycle` [1][2].

**Барьер сейчас не существует.** #219 измерил требования, но не реализовал интерфейс; в текущем
коде `send_message` прямо обещает новый turn, а сообщение idle/waiting-сессии переводит её в
`RUNNING` [6][7]. Немедленную правку #223 это не блокирует: действующий `model-routing` и Phase 3
уже требуют один закрытый тикет за раз. Координация с #219 в Phase 2 сняла первоначальный вывод
о запрете параллельности: без барьера каждый ребёнок сверх первого стоит ещё один parent turn,
но независимые тикеты от этого не становятся некорректными; конфликтующие по строкам тикеты
сериализуются независимо от барьера. A/B #223 остаётся последовательным, чтобы не смешивать
эффекты делегирования и fan-out. Второй механизм #223 не проектирует.

## Вопрос (Шаг 0)

- **Контекст:** дорогой `full-cycle` владеет исследованием, планом, красным оракулом и длинным
  контекстом; Phase 3 сейчас исполняется тем же агентом.
- **Проверяемое изменение:** для тикета с reviewed + committed RED-командой `full-cycle`
  передаёт реализацию дочерней роли `worker`, выбранной существующим `model-routing`; сам
  сохраняет владение оракулом и принимает результат.
- **Baseline:** тот же `full-cycle` сам реализует каждый тикет.
- **Измеримый исход:** (а) оракул не изменён ребёнком; (б) та же команда red до передачи и green
  после; (в) все невыразимые командой AC доказаны; (г) не больше одной дешёвой попытки; (д)
  дополнительная стоимость сообщений родителю не съедает переносимую дорогую работу.

## Findings

### F1. Делегируемость уже имеет однозначный машинно наблюдаемый признак

**CONFIRMED — current primary source + delivery tests.** Тикет делегируем, когда его `Test`
называет reviewed, committed RED behavioural test либо RED delivery check и точную команду.
`oracle: none — reason` никогда не делегируется. Уже зелёная или отсутствующая команда означает
сломанный оракул и STOP до реализации [1][3].

Важно сохранить квалификатор **RED**: наличие произвольной тестовой команды недостаточно.
Красный результат обязан быть missing behaviour, не collection/import error [1].

### F2. В Phase 3 отсутствует ровно соединяющий шаг

**CONFIRMED — current primary source + assembled prompt measurement.** Phase 3 выбирает тикет,
сама запускает red и дальше описывает тест/ревью/commit/report так, будто реализация остаётся в
том же worktree. Слова `delegate the ticket` в собранном prompt нет. Одновременно
`pipeline.yaml` уже даёт `full-cycle` `can_spawn: ["*"]`, а `model-routing` отправляет обычную
закрытую работу Luna, сохраняя существующее исключение Sol для ожидаемо сложной [1][2].

Соседний блок `<parallelism>` говорит «research/data gathering only — never split code
implementation this way». Он относится к fan-out, но буквальная модель может прочитать его как
общий запрет делегировать код. Phase 3 должна явно различить: **один ticket executor — да;
параллельное дробление одного тикета — нет** [1].

### F3. Guard исполнителя доезжает, но immutable-oracle запрет отсутствует

**CONFIRMED для доставки; LIKELY для текстовой дыры.** `worker.md` и собранный worker-prompt
содержат `Never author the acceptance test ... do not write the check yourself`; тест #210
проверяет источник, доставку и не-утечку [1][3]. Значит Luna-исполнитель это правило получает.

Но текущий текст не говорит дословно `do not edit/delete/rename/weaken the received test`.
Формально «не author» не запрещает править уже полученный файл. Поэтому immutable-oracle guard
обязан жить в worker-facing `worker.md`, повторяться в payload конкретного тикета, а приёмка
родителя обязана проверить diff/hash тестового файла. Оставлять `worker.md` необязательным нельзя:
иначе защита зависит от полноты каждого динамического task-текста.

### F4. Контракт передачи может быть полностью текстовым

**LIKELY — составлен из уже исполняемых первичных правил; прямой пилот именно нового prompt ещё
не запускался.** Родитель передаёт одному `worker`:

- текст одного тикета целиком: `Files`, `Test`, `AC`, `blocked-by`;
- commit красного оракула, точную команду, exit != 0 и первую падающую assertion-строку;
- дословный запрет менять, удалять, переименовывать, скипать или ослаблять полученный oracle;
- требование одного terminal report с commit, exact command output и доказательством AC.

Родитель до спавна сам повторяет red. После terminal report он проверяет чистый committed WIP,
что oracle byte/diff unchanged, принимает только green той же команды + доказанные оставшиеся
AC, затем мержит и повторяет named command и соседний regression check. Результат ребёнка —
улика, не приёмка самим ребёнком.

Нормальная работа не должна слать progress-сообщения родителю. Досрочное прерывание допустимо
только при трёх исключениях из #219: выход за границы; ложная предпосылка; блокировка без ответа.
Такой сигнал завершает дешёвую попытку, а не открывает многоходовый диалог [6].

### F5. Existing route покрывает test/AC failure; остальные failure-классы добавляет #223

**CONFIRMED для red/AC; новая policy для остальных исходов.** `model-routing` дословно говорит
`On failure escalate, never retry`, red/недоказанный AC → Sol и «do not send it back to Luna».
Там же `Closed work goes to the worker role, never to full-cycle`, но Sol разрешён сразу для
закрытой сложной работы [2]. Поэтому:

- parent сначала применяет `model-routing`: обычный closed ticket → Luna, сложный, который Luna
  ожидаемо не потянет → Sol сразу;
- у Luna уже ровно одна попытка при красной команде или недоказанном AC; тот же тикет уходит
  Sol-роли `worker` и не возвращается Luna;
- Phase 2 должна явно приравнять clarification, `WIP/STOP` и изменённый oracle к провалу дешёвой
  попытки; сегодня источник этой политики — #223, не существующий текст `model-routing`;
- `full-cycle` сам делает только `oracle: none`, потому что это по определению не закрытая работа.

### F6. Message-triggered parent turn дороже ребёнка; чистый остаток экономии неизвестен

**CONFIRMED для наблюдённых turn costs; UNCERTAIN для чистой надбавки и экономии.** Один
message-triggered terminal turn `$0.877` стоил 6.9 раза больше Luna-среза `$0.127`. Exception
turn + terminal turn дали `$1.751`; четыре исторических веера #219 показывают средний parent
turn `$1.62–4.43` [5][6]. Ни одно число не отделяет пустой wake от содержательной реакции.

Сценарий на несовпадающих измерениях (`qB=$5.07`) — только sensitivity analysis:

| сценарий одного тикета | `L + parent turn(s)` | остаётся от `qB` | доля сценарной выгоды |
|---|---:|---:|---:|
| 1 terminal message-triggered turn | $1.004 | $4.064 | 80 % |
| exception turn + terminal turn | $1.878 | $3.190 | 63 % |
| 1 исторический дорогой parent turn ($4.43) | $4.557 | $0.511 | 10 % |
| 2 дорогих parent turns по $4.43 | $8.987 | **−$3.919** | схема убыточна |

Таблица не переносится на популяцию и не обновляет headline 6–10 %. Она показывает только, что
один observed turn совместим с положительной экономикой, а два дорогих — уже нет. Отсюда
нагрузочный invariant: **ровно одно обычное сообщение ребёнка на тикет; любое дополнительное —
только исключение**. Первый живой rollout обязан измерить baseline и делегированный Phase 3 на
едином тикете, включая все parent turns.

### F7. Барьер экономит turns при N>1, но не является условием корректности

**CONFIRMED для отсутствия; LIKELY для границы применения.** `send_message` сейчас триггерит
turn; idle/waiting parent становится running. Сервер умеет склеить уже одновременно
очередившиеся сообщения в один turn, но не держит реестр N детей до их общего завершения [7].

#219 требует положительный terminal token от каждого ребёнка, failed token, абсолютный deadline,
server-side manifest путей и «барьер по completion, interrupt по исключению». Это спецификация,
не доступный tool/API [6]. Пока её нет, существующие правила «ONE ticket at a time» не создают
веер, поэтому последовательному A/B #223 барьер ничего не экономит. Независимые тикеты можно
параллелить и без него: это добавляет примерно один отдельный parent turn на каждого ребёнка
сверх первого, а не создаёт correctness failure. Конфликтующие по строкам тикеты сериализуются
по конфликту, а не из-за отсутствия барьера. Это Phase 2 correction после прямой координации с
владельцем #219; первоначальный запрет из принятой Phase 1 отозван.

При обычном завершении ребёнок обязан явно отправить `DONE`; при упавшем turn runtime уже шлёт
родителю auto-report со `stop_reason` и `Turn failed before an explicit report` [7]. Но
`fire_auto_report` намеренно подавляется при manual interrupt/stop, а доказательства terminal
token для внешнего `kill` в прочитанном пути нет. Поэтому prompt-only контракт покрывает
`DONE`, explicit `WIP/STOP` и failed-turn auto-report, но **не обещает** положительный token при
любом `timeout/killed`. Начальная доставка не молчит: `spawn_worker` отправляет task до успешного
ответа и возвращает parent delivery error синхронно. Неохваченным остаётся ребёнок, вручную
остановленный или убитый уже после принятой задачи; это failure gap до общего барьера #219 [7].

## Counter-evidence и ограничения

- **Message-triggered turns измерены у research-parent на 20–21 % context, не у поздней
  Phase 3.** Исторические `$1.62–4.43` показывают, что `$0.87` — не потолок; ни один замер не
  отделяет чистый wake от работы реакции [6].
- **6–10 % — только исходный порядок величины до измеренной координации.** Сценарий `$4.06`
  смешивает разные фазы и одну строковую прокси; новый агрегат из него не выводится [4][5].
- **Барьерный результат #219 — отрицательный по качеству research (2 из 14 находок).** Это не
  контрпример реализации: у Phase 3 есть committed red oracle, которого у открытого research не
  было. Но это предупреждение не поручать Luna синтез/приёмку [6].
- **Оракул может быть неполным.** Green подтверждает только то, что сильная сторона сумела
  выразить до спавна; Codex review плана и non-test AC остаются обязательными [1][4].
- **Запрет в `worker.md` семантически не равен immutable oracle.** Нужен и точный текст задачи,
  и независимая parent-проверка diff/hash; один prompt guard недостаточен [1][3].
- **Последовательность A/B #223 — ограничение замера, не общая политика.** Независимую работу
  можно параллелить без барьера ценой дополнительных parent turns; в этом rollout тикеты идут
  по одному, чтобы измерять делегирование, а не делегирование вместе с fan-out [1][2][6].
- **Manual stop/kill не доказан как положительный terminal outcome.** Failed turn auto-report
  существует, но manual interrupt его подавляет; без runtime-барьера нельзя обещать N-из-N
  завершение для всех классов смерти ребёнка [7].

## Затрагиваемые файлы и риски следующей фазы

- `pipelines/default/prompts/roles/full-cycle.md` — обязательный production-файл: явный Phase 3
  decision/dispatch/accept/escalate flow и устранение двусмысленности блока parallelism.
- `tests/test_default_pipeline.py` — delivery oracle: source → assembled `full-cycle` prompt;
  исполнительский запрет → assembled `worker`; отсутствие шага в orchestrator/sub-orchestrator;
  составная мутация «удалить из full-cycle + посадить якорь в base».
- `pipelines/default/prompts/roles/worker.md` — обязательный production-файл: дословный запрет
  менять/удалять/переименовывать/скипать/ослаблять полученный oracle; текущий `Never author`
  этого не гарантирует.
- `pipelines/default/prompts/modules/model-routing.md`, `pipeline.yaml`, `app/` — **не менять**:
  владелец выбора модели, red/AC escalation и capability уже существуют; остальные failure-классы
  добавляет `full-cycle.md`; barrier отсутствует и находится вне границ #223.

Edge cases для плана:

1. test missing/already green до спавна → STOP, ребёнка не создавать;
2. `oracle: none` → выполнить на дорогой стороне, никогда не маскировать причиной ради дешёвого
   routing;
3. ребёнок изменил oracle или не показал exact command → reject без merge, Sol escalation;
4. ребёнок задал уточняющий вопрос → тикет оказался не closed; дешёвую попытку закончить, не
   вести Luna по шагам;
5. green named command, но verbatim non-test AC не доказан → failure, не acceptance;
6. explicit `WIP/STOP` или failed-turn auto-report → Sol escalation; manual stop/kill без
   сообщения — известная runtime-дыра, не выдумывать положительный token;
7. после merge parent повторяет exact command; зелёный вывод ребёнка сам по себе не артефакт
   приёмки;
8. A/B #223 → вести последовательно; для иной независимой работы отсутствие barrier означает
   дополнительную цену parent turns, а не запрет; не имитировать барьер ожиданием тишины или
   polling.
