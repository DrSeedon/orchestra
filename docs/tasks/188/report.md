## T4 — 17 файлов мёртвой памяти

Удалено скриптом, который сам снимает свежую копию БД, сам пересчитывает список и падает при
любом расхождении. Вывод фактического прогона:

```
guards passed: db=108 arch=314 live=36 files=45
removed 17
```

Проверка **точного множества**, а не количества:

```
deleted lines: 17 | all under docs/workers/: True
set equality with EXPECTED: True
anything else changed: nothing
```

Живые не задеты:

```
memory files remaining: 28
live agents whose memory file survived: 14
```

Удалённые (78 426 байт): `audit-worktree`, `docs-changelog`, `feat-freshness`, `fix-bugsmd`,
`fix-merge-branch-drift`, `fix-silent-errors`, `fix-tg-mention`, `fix-wake-after-restart`,
`memory-research`, `merge-contours`, `migrate-vps`, `rag-max`, `research-compact-prompt`,
`research-embeddings`, `research-memory`, `research-merge`, `skill-migrate-norestart`.

**Почему пересчёт непосредственно перед удалением обязателен.** За время между Фазой 1 и Фазой 3
живая БД выросла со 103 имён до 108, а `docs/workers/` — с 38 файлов до 45. По списку Фазы 1
под удаление попал бы `tg-readability.md`, чей агент к тому моменту уже существовал. Список,
собранный по снимку, устаревает к моменту удаления.

**Четыре guard'а до арифметики множеств** (`db`, `arch`, `live`, `files` на непустоту) плюс
положительная проверка `EXPECTED & (db|arch|live)` — потому что при пустом `db` разность
множеств может СОВПАСТЬ с ожидаемой, если все имена нашлись в архиве, и скрипт снёс бы файлы,
не имея ни одного подтверждения жизни. В первой редакции плана я это место обосновал неверно
(«пустой реестр сам уронит по `!=`»), ревью поймало.
