# #259 — аудит понятности дашборда

Дата замера: 13.08.2026. Основной сценарий — десктоп.

## Что проверено

Живой дашборд открыт Playwright в Chromium при `1920×1080`, scale 1, выбран
`Orchestra-orchestrator` в scope `/home/kesha/orchestra`. В момент снимка в правой
панели было 23 видимых агента: 9 `running`, 1 `waiting`, 13 `idle`. В чате — 82
верхнеуровневых узла и 27 элементов инструментов. Ошибок страницы не было.

## Проход по экрану глазами нового человека

- **Верхняя полоса.** Лимиты Claude/Codex/Grok читаются как отдельные шкалы и дают
  нужный ежедневный сигнал — это удачная часть интерфейса. Рядом `9 active · 156
  total` двусмысленно: в текущем scope видны 23 агента, а слово `total` не объясняет,
  что 156 — другой охват. Исправлять это сейчас не обязательно: точный scope-summary
  безопаснее добавить над правым деревом, не трогая недавно починенный бар.
- **Левая панель.** Репозиторий показан как файловое дерево и требует технического
  контекста, но структура предсказуема. Это не главный источник жалобы.
- **Центр.** Пользовательские сообщения, итоги агентов, lifecycle и сырые результаты
  инструментов идут в одном потоке. Именно здесь интерфейс перестаёт объяснять, что
  произошло, и иногда сообщает неверную связь вызова с результатом.
- **Правая панель.** Данные полны, но имя выбранного агента обрезается, scope
  переносится на несколько строк, а стоимость визуально сильнее статуса. Для
  ежедневной работы это терпимо; для ответа «кто требует внимания» — недостаточно.
- **Иконки управления.** Несколько действий объясняются только hover-title. Это
  вторичный риск: на десктопе подсказка доступна, а добавление подписей отнимет место.
  В предлагаемый пакет не входит.

## Находки

### 1. Результаты параллельных инструментов приклеиваются к чужим карточкам

Это не косметический дефект: интерфейс сообщает неверный смысл.

Живые строки журнала идут так:

```text
99084 tool        task_create   tool_use_id=A
99085 tool        list_agents   tool_use_id=B
99086 tool_result task_create   tool_use_id=A
99087 tool_result list_agents   tool_use_id=B

99137 tool        task_create   tool_use_id=C
99138 tool        worker_wip    tool_use_id=D
99139 tool_result task_create   tool_use_id=C
```

В DOM результат `99086` показан внутри узла `99085`: карточка называется
`Agents`, но содержит JSON созданной задачи #257. Аналогично результат `99139`
показан внутри `worker_wip` `99138` и выглядит как будто это его ответ.

Причина локализована в compact-renderer: `app/static/js/app.js:4018-4020`
ищет просто последний `[data-compact-tool]`. `payload.tool_use_id` там не
используется, хотя обычный renderer ниже по файлу сопоставляет результат по id.

### 2. Compact mode обходит уже существующие понятные карточки задач

Вместо результата действия человек видит внутреннюю схему:

```text
par / id / title / project / price_rub / status / description /
assignee / priority / task_id
```

Поля `id` и `task_id` дублируются, `par` требует знания внутреннего контракта,
`price_rub: 0` занимает место без пользы, а состояние `new` не переведено в
операционное действие. При этом обычный renderer уже умеет показывать заголовок
`#N: title`, приоритет, состояние и описание (`app/static/js/app.js:5247-5263`).
Compact mode проходит раньше и до этой ветки не доходит.

История подтверждает расхождение владельцев: compact renderer появился 10.05
(`0d710a30`), а полные карточки задач добавлены 01.08 (`2a8925ff`) только в обычную
ветку. Значит проблема не в отсутствии formatter-а, а в двух путях рендера.

`list_agents` в compact mode сводится к `📎 N items`. Это не отвечает на нужные
вопросы: сколько работает, кто ждёт, есть ли сломанные.

### 3. Панель агентов богата данными, но не даёт порядка внимания

У каждого агента одновременно показаны имя, статус, модель, cache-age, стоимость,
контекст и прогресс. Все данные полезны по отдельности, но на списке из 23 строк
статус конкурирует с телеметрией. Чтобы найти единственного `waiting`, надо
просмотреть дерево; отдельного числа `broken` и быстрого фильтра нет.

Сохранять надо именно текущие status/model/context данные. Не хватает не ещё одной
метрики, а короткого ответа сверху: `9 работают · 1 ждёт · 0 сломано` и пути к
строкам, требующим внимания.

### 4. Служебный жизненный цикл разрывает содержательный разговор

Строки `turn ended (...)` и `waiting for bg jobs` занимают самостоятельные строки
между сообщением пользователя и итогом агента. Они выглядят почти как сообщения,
хотя человеку обычно нужен только текущий исход. Критические статусы — rate limit,
disconnect, failed, broken — нельзя прятать; штатный жизненный цикл можно свернуть
в одну раскрываемую строку.

## Предлагаемый пакет

### P0. Исправить корреляцию результата в compact mode

Искать карточку по `tool_use_id`, как уже делает обычный renderer. При отсутствии
парной карточки результат не приклеивать к последнему вызову: показать отдельный
`Result without matching call`. Приёмочный тест — два параллельных вызова A/B и
результаты в обратном порядке; каждый результат остаётся у своего вызова.

Польза: очень высокая. Риск: низкий, изменение локально в compact renderer.

### P1. Показать задачи и список агентов операционными карточками

Для `task_create/update/get/list` переиспользовать существующий task formatter и
показывать действие первым:

```text
Задача #258 создана · Critical · New
orphan sweep убивает по устаревшему PID…
[описание, свернуто]
```

Для `list_agents`:

```text
Агенты · 23 всего
9 работают · 1 ждёт · 0 сломано
Требует внимания: Orchestra-orchestrator — waiting
```

Сырые данные остаются под раскрытием `Технические детали`, а не исчезают.

Польза: очень высокая. Риск: низкий–средний; только известные структурированные
инструменты, остальные продолжают использовать общий renderer.

### P2. Добавить в панель агентов строку внимания и фильтры

Над деревом: `Все 23`, `Работают 9`, `Ждут 1`, `Сломаны 0`. Если есть waiting или
broken, первым показывать компактный блок `Требует внимания`, но само дерево и
порядок родитель→дети не менять. Это сокращает поиск проблемы без удаления
model/cache/cost/context.

Польза: высокая. Риск: средний; фильтр должен сохранять предков совпавших детей,
иначе потеряется контекст дерева.

### P3. Свернуть штатные status-строки, аварии оставить громкими

Последовательность `turn ended` + `waiting for bg jobs` показать одной строкой
`Ход завершён · ждёт 2 фоновые задачи`, детали — по клику. `rate limit`,
`disconnect`, `failed`, `broken` остаются отдельными цветными сообщениями.

Польза: средняя. Риск: низкий, если whitelist штатных строк узкий.

## Что сознательно не предлагается

- Не менять верхнюю полосу лимитов Claude/Codex/Grok: она ценна и только что
  исправлена.
- Не убирать статусы, модель, контекст или стоимость из карточек агентов.
- Не делать общий «умный» парсер свободного текста всех инструментов.
- Не перестраивать чат, виртуализацию или конвейер доставки.
- Не делать мобильный редизайн; проверить лишь отсутствие горизонтальной поломки.
