# #17 — отчёт: у системы появился путь, который сводит запомненную личность воркера с живым git

## Что сделано

Введено одно понятие — **класс дрейфа личности**. Раньше существовало «совпало» и «отказ»;
теперь есть третье состояние: расхождение безобидно, оно принимается и записывается.

| класс | условие | поведение |
|---|---|---|
| `SAME` | ветка и HEAD те же | как раньше, в тексте ответа молчание |
| `BENIGN_ADVANCE` | та же ветка, пин — предок живого HEAD | сливается живой HEAD; оба SHA и класс уходят в результат и в текст ответа |
| `FATAL` | другая ветка, не-потомок, неизвестный пин, git недоступен | отказ с причиной словами |

Формулировки `FATAL`: `branch changed: X → Y`,
`history rewritten: <pinned> is not an ancestor of <actual> (rebase/amend/reset)`,
`pinned commit <sha> unknown to repository`, `cannot inspect worker identity: …`.
Безликое «worker HEAD changed» из пути мержа исчезло.

## Тикеты

- **T1** — классификатор + мерж принимает продвижение ветки воркера. Перечитывание стоит
  после `_wait_for_merge_idle` и **под lifecycle-локом**: это последний момент, когда воркер
  уже ничего не допишет. Durable-контракт не ослаблен — пин уезжает в результат вместе с
  фактическим HEAD, повтор операции по-прежнему отдаёт записанное.
- **T2** — «уже на этой ветке» разведено на три исхода: база содержится → успех
  `state="already_on_branch"` при неподвижном HEAD; просят другую базу → отказ, называющий обе;
  грязное дерево → прежний отказ (проверка стоит выше по коду и не тронута).
- **T3** — **кода не потребовалось**, и это главный результат тикета. Оба вызывающих
  (`routes/sessions.py:1162`, `manager.py:775`) уже писали наблюдаемую личность в БД при
  `ok` — не хватало ровно того, что `ok` никогда не был истиной в этой ветке. T2 замкнул
  петлю: ремонт успешен → БД догоняет → мерж проходит. Проверено тестом, не рассуждением.

### Мутация: тесты обязаны краснеть на коде «до»

Откат файлов через `git show <commit>^:<file>` (не `git stash` — он бы застэшил пустоту):

```
T1: откат app/workspace.py + app/routes/sessions.py → 7 failed, 1 passed
    (на старом коде мерж отвечал: worker HEAD changed before merge: expected …, found …)
T2: откат app/workspace.py                          → 3 failed, 9 passed
```

Единственный тест, зелёный по обе стороны, — «смена ветки во время ожидания»: её старый код
тоже отвергал, только другим сообщением. Оставлен намеренно как страж поведения.

## Совместимость MCP ↔ роут в окне до рестарта

Требование: `app/mcp_stdio.py` подхватывается немедленно, `app/routes/` живёт в памяти до
рестарта — новый MCP будет говорить со старым роутом.

- Никаких новых полей ЗАПРОСА не добавлено: контракт вызова не менялся вовсе.
- В ответ поля только **добавлены** (`git.head_drift`, `git.worker_head_pinned`).
  Старый роут их не пришлёт — новый MCP печатает прежний текст, потому что фраза про дрейф
  висит на условии `head_drift == "BENIGN_ADVANCE"`, а не на присутствии ключа.
- Sentinel-значений нет: отсутствие поля и `SAME` ведут к одному и тому же поведению.
- Обратно: новый роут + старый MCP — лишние ключи игнорируются, как и раньше.

## Отступления от плана

1. Оба воспроизведения лежат в **одном новом файле** `tests/test_identity_drift.py`, а не
   разнесены по `test_merge_operations.py` / `test_workspace.py` / `test_manager.py`, как
   обещал план. Причина: обоим нужен настоящий git-репозиторий, а `test_merge_operations.py`
   построен на выдуманных путях (`/worktree`) — тесты в нём не о git, и тащить туда реальный
   репозиторий значило бы смешать два разных стенда.
2. План обещал переписать `tests/test_workspace.py:1300` («worker HEAD changed»). Не
   потребовалось: сверка внутри `merge_worktree_to_main` осталась нетронутой как последняя
   линия обороны на время самой git-работы, и её текст прежний. Переписан другой тест —
   `test_same_branch_is_rejected_without_mutation` → `..._is_idempotent_success_without_mutation`:
   его исходная суть (дерево не мутирует) сохранена, изменилось только ожидание `ok`.
3. T3 не потребовал кода (см. выше).

## Вердикта Codex нет

Codex недоступен до 08.08 — ревью не запрашивалось ни по одному тикету. Самокритика:

**Чего именно не хватило ревью на пути доставки сообщений (T3) — первый кандидат на 08.08.**
`_auto_switch_before_delivery` вызывается из `send()` под `_lifecycle_lock`, и после T2
ветка «git уже в требуемом состоянии» впервые в жизни возвращает `ok=True` вместо исключения.
Проверить это живьём я не могу: имя ветки там генерируется от `time()`, поэтому «уже на этой
ветке» в авто-switch недостижимо по построению — то есть мой тест на эту ветку кода не
попадает вовсе, а рассуждение о её безопасности ничем не подкреплено. Ревьюеру я бы задал
ровно один вопрос: существует ли путь, на котором авто-switch получает УЖЕ занятое имя
ветки (совпадение секунды при двух доставках подряд, восстановление после рестарта с тем же
`adhoc-*`), и не превращает ли T2 прежнее громкое падение в тихое «ничего не делаю».

**Второе.** `BENIGN_ADVANCE` расширяет сливаемое за пределы принятого при приёме операции.
Контракт соблюдён формально (класс и оба SHA — в результате и в тексте), но политики
«мержим только принятое состояние» у нас нет; если она появится, T1 пересматривается.

**Третье.** «Потомок = безобидно» опирается на аргумент «отказ ничего не защищает, потому что
повторный `merge_worker` сольёт то же самое». Аргумент верен ровно до тех пор, пока повтор
дешёв. Если появится ручное подтверждение мержа, посылка отвалится.
