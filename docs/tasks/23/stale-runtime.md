## 2. Где расходятся версии и опасно ли это

Проверял по коду и живыми запросами, не по описаниям задач.

### 2.1 `usage.js` (новый) ↔ `/api/usage/history` (старый) — СЛОМАНО СЕЙЧАС

Единственное реальное расхождение, и оно видно юзеру.

`#13` сменил ФОРМУ ответа: было `[...]`, стало `{step_minutes, rows, oldest_ts}`.
Живой сервер отдаёт старую форму — проверено запросом:

```
$ curl -s -H "Authorization: Bearer $TOK" "http://127.0.0.1:8888/api/usage/history?hours=1"
[{"id":6584,"ts":"2026-08-03T15:46:08...
```

Живой `usage.js:340`: `if (!Array.isArray(history?.rows)) throw new Error('ответ без rows: …')`.

Юзер видит в тултипе usage: «История не загрузилась — Error: ответ без rows: [{"id":6584,…».
То есть спарклайн мёртв, но врать про «Collecting data…» перестал — работа #10 тут отработала
правильно, отказ громкий и с причиной. **Чинится только рестартом**, откатывать `usage.js`
ради окна не стоит: рестарт всё равно нужен по десятку других причин.

### 2.2 Баннер новой версии (#15 T2) — инертен, ложных срабатываний нет

`app.js:5934` берёт `X-Orchestra-Build` с `/api/models`; живой сервер заголовка не шлёт
(проверено `curl -D -`). Условие `if (serverBuild && _pageBuild && serverBuild !== _pageBuild)`
защищено с обеих сторон, поэтому баннер просто не появится.

Шаблон: `data-build="{{ build_id() if build_id is defined else '' }}"` — страж `is defined`
спасает от 500, потому что в живом процессе `build_id` не зарегистрирован. Проверено:
`GET /` → **200**, `data-build=""`; `GET /login` → **200**. Это ровно то окно, ради которого
страж и писался.

Заметить стоит асимметрию: `static_url()` в шаблоне такого стража НЕ имеет. Сейчас это
безопасно (функция в живом процессе есть, приехала до старта), но любой следующий Jinja-глобал
без `is defined` уронит дашборд в окне между мержем и рестартом — шаблоны-то живые.

### 2.2a Уже открытые вкладки баннер не увидят — и это надо сказать юзеру словами

Наблюдение `frontend` (#22), подтверждаю по коду. Страница, отрисованная СТАРЫМ сервером,
получила `data-build=""`. Баннер показывается только при непустых обеих сторонах
(`serverBuild && _pageBuild`). Значит после рестарта открытая вкладка о новой версии не узнает
никогда — она будет тихо работать на старом JS с новым API.

Практический вывод для момента рестарта: **попросить юзера перезагрузить вкладку руками**.
Расчёт «увидит баннер и обновит» на ЭТОТ раз не сработает; со следующего рестарта — заработает.

### 2.2b Проверено и НЕ подтвердилось: `/api/logs/sync`

`frontend` сообщил, что маршрута нет и клиентское зеркало журнала отключается по 404.
Проверил на живом сервисе — **200**:


Маршрут есть и в `main`, и в загруженной версии (`git grep "logs/sync" 569075f -- app/` →
`app/routes/sessions.py:358`), то есть приехал ДО старта сервиса. Причина расхождения — база
сравнения: у коллеги за точку старта взят `1de71b7` (по датам коммитов), а фактически было
`569075f` (по reflog). В чеклист пункт не берём.

### 2.2c Маршрутная поверхность цела — расходится только ФОРМА ответов

Дополнено после #28 по замеру `frontend`: все 27 беспараметрических GET-маршрутов из
`tests/route_surface_snapshot.json` прогнаны по живому серверу — отсутствующих **ноль**,
единственный 404 (`/api/tm/payments/status`) прикладной и к рестарту отношения не имеет.

Практический вывод для чеклиста: проверять **не наличие путей, а форму ответов**. Реальных
пар «новый клиент ↔ старый сервер» остаётся две — §2.1 (`usage.js`) и §2.2 (`build_id`).

### 2.3 MCP (новый) ↔ роуты (старые) — безопасно

- `#16`: тул читает `result.get("index")` и печатает долг индекса, только если ключ есть.
  Старый роут ключа не отдаёт → строки нет. Протестировано на всех трёх комбинациях.
- `#8/#17`: тул читает `git.get("head_drift")` — старый роут поля не шлёт, примечание про
  «воркер закоммитил после приёма операции» не печатается. Данные при этом не искажаются.
- `#11`: правка целиком внутри MCP (ожидание исхода 90 с), роут не трогали. Работает у тех
  воркеров, чей MCP стартовал после 16:05.

Обратного направления — «новый MCP шлёт роуту поле, которого тот не знает» — сегодня нет:
все правки контракта аддитивны и односторонние (сервер → тул).

### 2.4 Что просто не работает до рестарта, без расхождения

- **#16 целиком инертен.** Живой бэкфилл — старый: prune последним, `fetchall` по логам,
  без срезов. Значит 17 фантомов в индексе всё ещё отдаются `search_memory` как текущие файлы,
  и это самый неприятный пункт: агент строит решение на удалённом файле.
- **#15 T3 инертен**: TG-мост всё ещё поднимается на критическом пути старта. Парадокс окна —
  ПРЕДСТОЯЩИЙ рестарт уже пойдёт по новому коду, то есть первым же и починится.

Порядок: сначала то, что докажет, что процесс вообще поднялся правильно, потом пофично.
Всё read-only.

```bash
cd /home/kesha/orchestra
PID=$(ss -lptnH 'sport = :8888' | grep -o 'pid=[0-9]*' | cut -d= -f2)
TOK=$(grep -m1 '^INTERNAL_TOKEN=' .env | cut -d= -f2- | tr -d '"')
```

**1. Процесс тот, что нужно, и код свежий**
```bash
ps -o pid,lstart,etimes -p $PID          # старт позже последнего мержа
find app -name '*.py' -newermt "$(ps -o lstart= -p $PID)" | grep . && echo "ЕСТЬ ФАЙЛЫ НОВЕЕ ПРОЦЕССА"
```
Вывод последней команды должен быть ПУСТЫМ. Непустой = снова разъехались.

**2. TG-мост уходит с критического пути (долг #15 T3)**
```bash
journalctl -u orchestra -n 200 -o short-iso | grep -E "Application startup complete|TG bridge|TG Bridge"
```
Ждём: `Application startup complete` **раньше**, чем `TG bridge: ready`. Если `TG Bridge started`
снова стоит ДО `Application startup complete` — правка не приехала. Плюс `TG bridge: starting in
background` обязан появиться: он на INFO и виден только после фикса логирования (#16), так что
эта строка проверяет сразу две задачи.

**3. Лимиты cgroup — по `/sys/fs/cgroup`, не по `systemctl show`**
```bash
CG=/sys/fs/cgroup/system.slice/orchestra.service
grep . $CG/memory.high $CG/memory.max $CG/memory.current
awk '/^high /{print "throttle events:", $2}' $CG/memory.events
awk '/^pgscan_direct/{print "direct reclaim:", $2}' $CG/memory.stat
```
Ждём `memory.high=8589934592`, `memory.max=12884901888`. `systemctl show` печатает значение и
при успехе, и при провале — это не проверка. Счётчик `high` смотреть в динамике: два замера с
интервалом 15 с, прирост должен быть около нуля (до подъёма лимитов было +2254 за 15 с).

**4. Сессии и воркеры вернулись**
```bash
curl -s -H "Authorization: Bearer $TOK" localhost:8888/api/sessions | python3 -c "import json,sys; r=json.load(sys.stdin); s=r if isinstance(r,list) else r.get('sessions',[]); print(len(s),'сессий'); [print(' ',x['name'],x.get('status')) for x in s[:20]]"
journalctl -u orchestra -n 300 -o cat | grep -iE "auto_resume|restored|hydrat" | tail
```
Ждём: воркеры на месте и в `idle`, а не потерянные. Сверить с `list_agents` до рестарта.

**5. Бэкфилл делает дешёвое первым и говорит об этом**
```bash
journalctl -u orchestra -f -o short-iso | grep -E "RAG (service|scheduled|backfill)"
```
Ждём в таком порядке:
`RAG service initialized` → `RAG scheduled backfill accepted scope=…` →
`RAG backfill_files[…] pruned 17 deleted files` (это должно прийти В ПЕРВЫЕ СЕКУНДЫ прогона,
до какого-либо эмбеддинга) → далее `indexed/updated N files` → `backfill_scope[…]: … still pending`.
Если строк нет вообще — не приехал фикс логирования; если `pruned` приходит через минуты —
не приехала перестановка порядка.

Прямая проверка результата, без ожидания логов:
```bash

```
Было 315 при 401 файле на диске. После первого прогона число не должно включать удалённые пути:
```bash

  | while read p; do [ -e "$p" ] || echo "ФАНТОМ: $p"; done
```

## 4. Что стоит знать про сам момент рестарта

- Ходы агентов четырёх проектов рвутся — это цена, не побочный эффект.
- MCP-процессы воркеров переживают рестарт сервера, но их версия останется прежней до
  реконнекта воркера. То есть после рестарта разъезд «сервер новый / MCP старый» сохранится,
  только зеркально нынешнему. Полностью выравнивается по мере переподключения воркеров.
- Первый бэкфилл после старта будет самым дорогим за день: 109 файлов в долге, ~1.28 с на
  чанк. С новыми лимитами cgroup это больше не создаёт стоек HTTP, но CPU займёт.
