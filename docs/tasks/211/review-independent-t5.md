## 1. Порядок фиксации хешей и откат по шагам — ЗАКРЫТО

`installed.sha256` теперь пишется в `record_expected_hashes` из хешей ИСТОЧНИКОВ и вызывается
до первого `atomic_install` (`install_hook:194-199`). Дыра, которую я нашёл в прошлый раз
(install умер между двумя `atomic_install` → `installed.sha256` нет → откат падает на `awk`
уже ПОСЛЕ того, как увёл оба файла), закрыта в двух местах сразу:
- файл существует до любой замены;
- на всякий случай чтение теперь защищено — `[[ -f "$STATE_DIR/installed.sha256" ]]` перед
  `awk`, пустой `expected` даёт громкий выход через `restore_claims`.

Новых дыр от перестановки не нашёл, и вот почему прошёл каждый шаг:

| падение на шаге | состояние после |
|---|---|
| install умер до/во время первой замены | destination нетронут; откат принимает его веткой `claim_matches_saved` (`cmp` с бэкапом), `restore_one` выходит по `[[ -n "$claim" ]] \|\| return 0` — исходное состояние сохранено |
| `validate_restore_hook` упал (битый бэкап) | выход ДО единого `mv` — система не тронута вовсе. Порядок «проверить, потом менять» здесь правильный |
| `claim_and_verify_install` упал на index 1 | `restore_claims` возвращает claim index 0 на место; итерация по `DESTINATIONS` с `${CLAIMS[$index]:-}` больше не разъезжается по индексам |
| `restore_one` упал после `atomic_restore_noreplace` | destination уже восстановлен корректно, остаётся только инертный claim-файл |

**Остаточное (suggestion, не блокер):** в `rollback_hook:245-247` цикл `restore_one` не имеет
компенсации. Оба destination уводятся в claim ещё в `claim_and_verify_install`, поэтому падение
внутри `restore_one(0)` (например `atomic_restore_noreplace` вернул 1 → `set -e`) оставляет
index 1 заклеймленным без попытки восстановления и без `restore_claims`. Контракт «откат
возвращает исходное состояние на каждом шаге» на этом пути по-прежнему не выполняется.

Понижаю до suggestion осознанно, а не из вежливости: конкретный блокер, о котором я отчитался,
закрыт и проверен; остаток деградирует в безопасную сторону (оба файла отсутствуют →
по замеру из первого вердикта это «как сегодня»), оригинал цел в `$STATE_DIR/backup/`,
и выход громкий.

## 2. `bash -n` на shell-стороне — ЗАКРЫТО, планка держится

Проверка стоит на обоих путях, ведущих к `/etc/orchestra/claude-env.sh`:

  Индекс 0 — это именно `.sh`; systemd-`.conf` под `bash -n` не гоняется, что правильно;
- `validate_restore_hook:229-236` — `bash -n "$STATE_DIR/backup/hook"` при `state=present`,
  вызывается ПЕРВОЙ строкой `rollback_hook`, до claim.

Второй пункт закрывает ровно то, на что я указывал: раньше откат возвращал в этот путь
произвольный предсуществовавший файл без единой проверки.

Прогнал сам:
```
bash -n deploy/orchestra-claude-env.sh   → rc=0
bash -n <мой битый образец из первого вердикта> → rc=2, syntax error near unexpected token '('
```
То есть guard ловит именно тот класс порчи, которым я в прошлый раз положил Bash у агента.

**Путей, по которым скрипт САМ кладёт непроверенный файл в destination, не нашёл.** Единственный
непроверяемый файл, который может там оказаться, — тот, что уже лежал живым до запуска:
`restore_claims` возвращает на место содержимое, взятое с того же destination. Это status quo
ante, а не привнесённая скриптом порча.

**Остаточное (suggestion):** `bash -n` — проверка синтаксиса, не смысла, и она защищает моменты
install и restore, но не после них. Система по-прежнему в одной внешней порче
`/etc/orchestra/claude-env.sh` от полного отказа Bash у всех агентов, и ничто это не сторожит.
Вне объёма этой правки, но планку «худший исход — как сегодня» держит только до тех пор,
пока файл никто не трогает снаружи.

## 3. Одно ли правило no-clobber на весь файл — НЕТ

Опровергаю. Осталась одна голая строка: `rollback_hook:251` — `mv "$STATE_DIR" "$archive"`,
без `-T` и без `-n`. Остальные пять `mv` приведены к no-clobber либо намеренно форсированы:

| строка | вызов | статус |
|---|---|---|
| 49 | `mv -f "$temporary" "$destination"` | по замыслу — атомарная установка поверх |
| 57 | `mv -Tn "$temporary" "$destination"` | ✔ |
| 112 | `mv -Tn "$claim" "$destination"` | ✔ |
| 153 | `mv -Tn "$destination" "$claim"` | ✔ |
| 223 | `mv -Tn "$claim" "$removed"` | ✔ моя прошлая suggestion принята |
| **251** | `mv "$STATE_DIR" "$archive"` | **голый** |

Сценарий: `$archive` = `rollback-<...>Z` с точностью до СЕКУНДЫ. Если каталог с таким именем
уже есть, голый `mv` не падает, а кладёт `deploy-state` ВНУТРЬ него. Проверил:
```
mv mvt/state mvt/arch  →  mvt/arch/state/f
```
Потери данных нет, но раскладка архива молча меняется. Закрывается тем же `-Tn`.

**Отдельно, и это следствие моей же прошлой suggestion:** перевод строки 223 на `mv -Tn` сделал
частично упавший откат неповторяемым. При повторе `restore_one` восстанавливает destination
корректно, а затем упирается в уже существующий `$STATE_DIR/removed/$key`, отказывается
перезаписать и выходит с «Could not archive claimed file without overwriting retained data».
Это правильный размен для проекта с fail loud — громко и без разрушения вместо тихой
перезаписи, — но означает, что после частичного отката оператор обязан руками разобрать
`$STATE_DIR/removed/`, иначе повтор не пройдёт никогда. Стоит одной строки в runbook.
