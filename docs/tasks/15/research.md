# #15 — мгновенное восстановление дашборда после рестарта

## Ответ коротко

**Менять — да, но не там, где болит по ощущениям.** Перезагрузка страницы после возврата
сервера действительно не нужна, и её главное заявленное достоинство — «гарантированно
приводит клиента в согласованное состояние, включая новую версию фронта» — **измерением не
подтверждается**: после `location.reload()` браузер берёт весь JS из кеша, не спрашивая
сервер. Старый JS против нового бэкенда у нас происходит уже сегодня, молча.

При этом главный источник задержки — вообще не перезагрузка и не старт сервиса, а то,
**сколько клиент не замечает, что сервер вернулся**: медиана 23 с, худший случай 159 с
против 4–14 с самого старта.

## Вопрос

- **Контекст.** Дашборд открыт весь день, сервис перезапускается по несколько раз в день.
  Канал юзера через VPN, HTTP/2, TTFB 0.31–0.35 с.
- **Что проверяем.** Нужна ли перезагрузка страницы после возврата сервера, или хватает
  переподключения потока и досинхронизации дельты (которая после #8 уже есть).
- **База сравнения.** Нынешнее поведение: 2 неудачных heartbeat → оверлей → опрос раз в 2 с →
  `location.reload()`.
- **Измеримый исход.** Время от «сервер снова принимает запросы» до «дашборд пригоден к
  работе», разложенное на обнаружение и восстановление. Плюс цена самого старта сервиса.

## Находки

### F1. Клиент не замечает возврат сервера от 2 до 159 секунд. CONFIRMED

От строки `Application startup complete` до первого `GET /` от браузера юзера
(10 рестартов, `journalctl`, реальный клиент):

```
 1.7 с   2.6 с   14.5 с   15.7 с   20.7 с   25.1 с   75.0 с   111.4 с   151.2 с   159.4 с
```
Медиана ≈ 23 с. Уложились в 3 с только 2 раза из 10.

Для сравнения: сам старт сервиса в тех же прогонах — 4.3–13.9 с. **Клиент теряет больше,
чем сервер.**

### F2. В эти секунды клиент просто перестаёт слать запросы. LIKELY

`access.log` вокруг рестарта 13:27 (тот же реальный клиент):

```
13:27:19 … 13:27:37   502 каждые ~2-3 с — heartbeat и опрос работают
13:27:51              последние ответы старого процесса
   ← ТИШИНА 22 секунды: ни одного запроса, хотя страница открыта ↑
13:28:13              GET /  — страница сама перезагрузилась
13:27:57.66           сервер принимал запросы уже здесь (за 15.7 с до этого)
```

Оверлей ребута опрашивает `/api/models` раз в 2 с, heartbeat — раз в 3 с. Ни один из них
не выполнился 22 секунды подряд. Объяснение, которое я **не смог проверить**: скрытая
вкладка тормозит JS-таймеры (в headless воспроизвести не удалось — `document.hidden`
остаётся `false`, а `Page.setWebLifecycleState: frozen` через CDP принимается, но
`visibilityState` не меняется и таймеры идут штатно, 6 срабатываний за 20 с).

Механизм остаётся UNCERTAIN, но **на решение это не влияет**: чем бы ни была вызвана
тишина, JS-таймер — неподходящий детектор, а нужное событие (`visibilitychange`) приходит
ровно тогда, когда юзер возвращается к вкладке.

### F3. `location.reload()` НЕ доставляет новую версию фронта. CONFIRMED

Контролируемый опыт (Playwright через nginx, тот же контекст): холодная загрузка, затем
`reload`, и сверка с тем, что увидел сервер.

```
браузер после reload:  app.js  transferSize=0, decodedBodySize=355107
сервер за то же время: GET /                 200
                       (запроса /static/js/app.js НЕТ ВООБЩЕ)
```

То есть перезагружается только HTML; весь JS берётся из кеша **без ревалидации**. Если бы
сервер поднялся с новым фронтом, юзер продолжил бы работать на старом и не узнал бы об этом.

Причина — отсутствие правил кеширования. Замер заголовков через nginx: ни на одном из 13
статических файлов и на `/` **нет `Cache-Control`**, только `ETag` и `Last-Modified`, а по
ним браузер применяет эвристическую свежесть и может не спрашивать сервер вовсе.

**Поправка к постановке:** «#9 дал версионирование статики с `immutable`» — не выполнено.
Коммит `b9b744c` («#9: версия в URL статики + правила кеширования») существует, но лежит на
ветке `adhoc-747628/frontend` и **в `main` не влит** (`git merge-base --is-ancestor` → нет),
`static_url` в `main` не встречается, живой сервер отдаёт статику без `Cache-Control`.

### F4. Но иногда reload всё-таки тянет всё заново — и это дорого. CONFIRMED

Тот же рестарт 13:27, реальный клиент, после автоперезагрузки:

```
13:28:13-14  GET / + 13 статических файлов — ВСЕ с кодом 200 (не 304)
```
Объём: 389 КБ на проводе, 1300 КБ после распаковки (замер через nginx).

Итого у перезагрузки два режима, и **оба плохи для её оправдания**: либо JS берётся из кеша
и новая версия не доезжает (F3), либо всё качается заново и это 389 КБ на узком канале.
Какой из них сработает — зависит от состояния кеша, то есть от везения.

### F5. Сама перезагрузка дёшева. CONFIRMED (на сервере)

Playwright через nginx, «чат на экране»:

| | холодная загрузка | reload #1 | reload #2 |
|---|---|---|---|
| время до истории на экране | 12 мс* | 594 мс | 507 мс |
| статики с сети | 389 КБ | **0 КБ** (13 файлов из кеша) | 0 КБ |
| `DOMContentLoaded` | 1436 мс | 271 мс | 223 мс |

\* холодная цифра не показательна: чат отрисовался из зеркала #8 ещё до `load`.

На канале юзера будет дороже, но порядок тот же: **перезагрузка стоит меньше секунды и не
является узким местом.** H1 опровергнута.

### F6. Родной ретрай EventSource не лучше нынешней схемы. REFUTED (моя гипотеза)

Контролируемый опыт: свой SSE-сервер, убит на 6 с, поднят снова. Время до первого события
после возврата:

```
родной ретрай (onerror не закрываем)   3021 мс   (onerror сработал 3 раза)
close + setTimeout(2000), как сейчас   2054 мс   (onerror сработал 4 раза)
```

В видимой вкладке нынешняя схема уже возвращается за ~2 с. Значит производственные 20–159 с
(F1) объясняются не схемой переподключения, а тем, что таймеры не идут (F2).

Первый заход этого опыта провалился и это стоит записать: `srv.shutdown()` у
`ThreadingHTTPServer` перестаёт принимать новые соединения, но **живой SSE-поток не рвёт** —
`onerror` не сработал ни разу, обе схемы «не заметили» падения. Рвёт только убийство
процесса.

### F7. Старт сервиса: 4.3–13.9 с, и вся дисперсия в одном промежутке. CONFIRMED

`journalctl -o short-precise`, 4 разобранных рестарта:

| рестарт | старт → bootstrap | **bootstrap → «TG Bot using LOCAL API»** | TG → complete | всего |
|---|---|---|---|---|
| 13:27 | 0.41 с | **3.62 с** | 0.26 с | 4.30 с |
| 13:13 | 0.37 с | **3.89 с** | 0.07 с | 4.32 с |
| 11:19 | 0.92 с | **8.37 с** | 0.50 с | 9.79 с |
| 08:29 | 0.49 с | **13.38 с** | 0.07 с | 13.94 с |

В первом промежутке успевают `load_dotenv`, `init_db`, `refresh_models`,
`manager.auto_resume_all()` и `ensure_bootstrap` — меньше секунды на всё.
Во втором, по коду `lifespan` (`app/main.py:60-65`): `start_background_tasks`,
`bg_manager.restore_from_db()`, **ленивый `from app.tg_bridge import start_bridge`** и сам
`start_bridge`.

Замер импортов (отдельные процессы):
```
import app.tg_bridge   4051 мс
  из них aiogram       3718 мс  (холодный, отдельным процессом)
import app.main         866 мс  (это ДО «Started server process»)
import app.bg_jobs       70 мс
import app.bootstrap      1 мс
```

**Минимальный наблюдавшийся промежуток (3.62 с) практически равен цене импорта aiogram.**
То есть пол старта задаёт один ленивый импорт внутри `lifespan`, а uvicorn начинает
принимать запросы только после его завершения (в журнале `Uvicorn running on…` идёт **после**
`Application startup complete`). Всё это время nginx отвечает 502 — проверено:
`upstream prematurely closed connection` в `error.log` и 502 в `access.log`.

Полная недоступность ≈ 0.9 с (импорт `app.main`) + 4.3–13.9 с (`lifespan`) ≈ **5–15 с**.

### F8. Что именно надо восстановить, если не перезагружать страницу. CONFIRMED (по коду)

| состояние | кто восстановит | комментарий |
|---|---|---|
| поток SSE | `connectSSE()` уже переподключается с `after_id` | есть |
| дельта истории | `_storeSync()` из #8, один gzip-запрос | на простое было 931 Б |

| атрибуты из Jinja на `<body>`: `data-currency`, `data-hide-thinking`, `data-auth-enabled`, `data-client-name` | **никто** | меняются только вместе с конфигом; протухнут до настоящей перезагрузки |

Первый пункт из «никто» — единственный реальный риск варианта «не перезагружать», и он
решается тем, что при восстановлении чат перерисовывается целиком через `_showChatFor`,
а оптимистичные пузыри сбрасываются.

## Ответ на вопрос постановки про риск «старый JS против нового бэкенда»

Разбираю честно, потому что именно на нём держится оправдание `reload`.

1. **Риск существует уже сегодня и не защищён.** F3: после перезагрузки JS берётся из кеша
   без обращения к серверу. `Cache-Control` нет ни на статике, ни на HTML. Значит
   `location.reload()` даёт согласованность *состояния клиента*, но не *версии клиента*.
2. **Отказ от перезагрузки этот риск не увеличивает.** Он ровно тот же: и там и там
   исполняется JS, загруженный при первом открытии вкладки.
3. **Чинится он не перезагрузкой, а двумя вещами:** версионированными URL (это #9, не влит)
   и явным сигналом версии, по которому клиент понимает, что бэкенд уехал вперёд.
4. Поэтому «риск перевешивает, менять не надо» — **не тот вывод**. Правильный: менять, и
   заодно сделать этот риск громким вместо молчаливого.

## Варианты и цена

### A. Не менять
Цена 0. Медиана 23 с до возвращения дашборда, худший случай 159 с; заявленная гарантия
свежего фронта не выполняется (F3). Старт сервиса 5–15 с остаётся.

### B. Восстановление на месте вместо перезагрузки (рекомендую)
Вместо `location.reload()` — сброс оптимистичного состояния, `_storeSync()`, `_showChatFor()`
и переподключение потока; плюс попытка восстановления на `visibilitychange`, то есть ровно в
момент, когда юзер вернулся к вкладке.
- Выигрыш: вместо «до 159 с опроса + полная перезагрузка» — один круг в момент возврата
  к вкладке. Вся механика уже написана в #8, новых сущностей не появляется.
- Цена: ~40 строк в `app.js` (зона 5745–5800, теперь моя). Риск один и named: оптимистичные
  пузыри, которые перезагрузка выбрасывала бесплатно.
- Не лечит: атрибуты из Jinja (F8) — они меняются только при смене конфига.

### C. Сигнал версии фронта
Сервер отдаёт идентификатор сборки статики в `/api/models` (его и так дёргает heartbeat
раз в 3 с — нового запроса не появляется). Клиент запоминает тот, с которым загрузился;
при несовпадении показывает баннер «сервер обновился, обновите страницу».
- Выигрыш: молчаливое расхождение версий становится громким.
- Цена: ~15 строк (сервер + клиент).
- **Важно:** автоматически перезагружать по этому сигналу **нельзя, пока не влит #9** —
  без версионированных URL перезагрузка вернёт тот же закешированный JS (F3), и клиент
  зациклится на баннере. Поэтому здесь именно баннер, а не автодействие.

### D. Снять aiogram с критического пути старта
`start_bridge` уходит в `asyncio.create_task` после завершения `lifespan`, с явным
логированием отказа.
- Выигрыш: −4 с из 5–15 с недоступности (F7), в лучшем случае старт 4.3 → ~0.7 с.
- Цена: ~5 строк в `app/main.py`. Риск: polling TG стартует на несколько секунд позже,
  команды из TG в это окно задержатся (Telegram их не теряет, но `/restart` из TG будет
  выглядеть залипшим). `stop_bridge` при выключении должен пережить «ещё не поднялся».
- Оставшуюся дисперсию (8.4 и 13.4 с) это не объясняет и не лечит — там, судя по всему,
  холодный дисковый кеш; отдельно не копал.

**Рекомендация: B + C + D.** B даёт основной выигрыш, D дёшев и независим, C закрывает
дыру, которая существует уже сегодня и которую B сам по себе не трогает.

## Контрдоводы

- **В видимой вкладке сегодня всё и так неплохо.** F6: возврат за ~2 с. Все случаи 20–159 с
  — это вкладка не на переднем плане. Если юзер смотрит на дашборд в момент рестарта,
  разницы он почти не заметит. Ценность B — для случая «перезапустил и ушёл».
- **Перезагрузка даёт чистое JS-состояние даром.** Никаких утечек, зависших замыканий,
  полуприменённого DOM. Восстановление на месте обязано быть аккуратным с оптимистичным
  состоянием — это класс ошибок, которого у перезагрузки не бывает в принципе.
- **Механизм тишины (F2) не доказан.** Я утверждаю «таймеры не идут», опираясь на
  производственный лог, но воспроизвести троттлинг не смог. Если причина другая (например,
  сеть юзера, а не браузер), то `visibilitychange` может и не спасти — тогда B даст выигрыш
  меньше обещанного. Проверяется только на его машине.
- **D меняет порядок старта.** Сегодня «сервер принимает запросы» означает «TG-мост уже
  поднят». После D это перестанет быть правдой, и любой код, который на это молча
  рассчитывает, сломается. Я такого не нашёл, но искал по `lifespan`, а не по всему проекту.
- **Против моей же F3.** Возможно, в реальных условиях юзера кеш ведёт себя иначе, чем в
  моём headless-прогоне: F4 показывает, что у него все 13 файлов пришли с кодом 200. Тогда
  перезагрузка версию всё-таки обновляет, и её оправдание частично возвращается. Но цена
  тогда — 389 КБ на узком канале, и вывод «менять» не меняется, меняется только аргумент.

## Риски и края

- Оптимистичные сообщения при восстановлении на месте — единственный путь потерять или
  задвоить сообщение. Обязателен явный сброс.
- Если рестарт совпал с активным ходом агента, `streamBubble` останется черновиком без
  финала; перерисовка чата из зеркала это чинит, но только если чат перерисовывается
  целиком, а не дополняется.
- Сигнал версии обязан быть дешёвым: он поедет в `/api/models` раз в 3 с.
- D нельзя делать «тихо»: отказ `start_bridge` в фоне должен быть громким, иначе TG умрёт
  молча и это заметят через часы.

## Что стоит снять с ноутбука юзера

Одна цифра, которой у меня нет и не может быть с сервера: **действительно ли таймеры
останавливаются в его браузере, когда вкладка не на переднем плане** (F2).

Команда для юзера: открыть дашборд, в DevTools → Console вставить и **сразу переключиться
на другое окно минимум на минуту**, затем вернуться и прислать вывод:

```js
(() => { const t0 = performance.now(); let n = 0, last = t0, gaps = [];
  const id = setInterval(() => { const now = performance.now();
    gaps.push(Math.round(now - last)); last = now; n++;
    if (now - t0 > 90000) { clearInterval(id);
      console.log('RESULT ' + JSON.stringify({ticks: n, ms: Math.round(now - t0),
        maxGapMs: Math.max(...gaps), hidden: document.hidden})); } }, 3000); })();
```
Ожидание без троттлинга: ~30 срабатываний, `maxGapMs` ≈ 3000. Если `maxGapMs` окажется
десятками секунд — F2 подтверждена, и B работает ровно так, как обещано.
