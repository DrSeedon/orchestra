# Приёмка #38 — первый кадр рисует 20 строк, остальные 80 после кадра

## Как снято

Парные плечи в одном окне, чередование `main → #38 → main → #38 …`, **6 пар**, каждое плечо —
три захода подряд (пустой профиль → F5 → F5). Обе версии `app.js` подменяются через
route-перехват, то есть **завышены одинаково**: подмена вырубает HTTP-кеш браузера, статика
перекачивается в каждом заходе. Поэтому здесь читаются ТОЛЬКО парные разницы, не абсолюты.

- main: `git show main:app/static/js/app.js` (md5 3ee2368c…)
- #38: `adhoc-817540/frontend` `692c6e1` (md5 e3e793be…)
- Вход: `https://orchestra.seedon.ru` (nginx, HTTP/2, gzip). Браузер — на самом VPS, RTT≈0.
- loadavg на прогонах 3.0–5.2; сырое — `browser-ab{1..6}-{main,38}.json`.
- **Одна пара (ab6) выброшена**: там внешний CDN застопорил загрузку на 16.8 с (см. ниже).
  Выброс объявлен по признаку `domContentLoaded > 5 с`, не по «некрасивому» числу.

## Результат (5 пар, медиана парных разниц)

| | 2-й заход (warm1) | 3-й заход (warm2) |
|---|---|---|
| **первый контент чата** | −4 мс (эффекта нет) | **−406 мс** (4 из 5 пар в минус) |
| LCP | −28 мс | **−424 мс** |
| вся сотня строк на экране | +18 мс | **+164 мс** |
| суммарно длинные задачи | +106 мс | +223 мс |

**Вердикт: делает ровно то, что заявлено, на третьем и последующих заходах.** Первый экран
приходит на ~0.4 с раньше — это больше, чем всё, что осталось выжать из сети на этом плече
(там её уже ноль). Цена честная и её надо назвать вслух: полная сотня строк дорисовывается
на ~0.16 с позже, а суммарной работы главного потока становится БОЛЬШЕ на ~0.2 с — приём
не уменьшает работу, а переставляет её за первый кадр.

На втором заходе эффекта нет — как frontend и предсказывал: там 80 строк всё равно едут
с сервера, и переставлять нечего.

Разброс между повторами одной и той же версии сопоставим с эффектом (main warm2: 1155–2730 мс),
поэтому вывод держится на ПАРНОЙ схеме и знаке разниц (4 из 5), а не на разнице медиан.

## Побочная находка, крупнее всего замеренного

`app/templates/dashboard.html:29`:
```html
<script src="https://cdn.jsdelivr.net/npm/chart.js@4/dist/chart.umd.min.js"></script>
```
Единственная внешняя зависимость страницы — и она **без `defer`/`async`, то есть блокирует
разбор документа и `DOMContentLoaded`**. В одном заходе из двенадцати этот запрос отвечал
**16.8 с**, и на столько же уехало ВСЁ: `domContentLoaded` 17.3 с, список агентов 17.6 с,
чат 17.9 с. Ни к #38, ни к серверу это отношения не имеет.

С VPS jsdelivr обычно быстрый: 8 замеров подряд — 63–72 мс, 208 КБ raw / 70 КБ gzip. То есть
стопор — не «CDN лежит», а хвост распределения, который случается и на прямом канале дата-центра.
У юзера канал другой и до jsdelivr, вероятно, хуже.

Почему этого не видно в обычных замерах: файл кешируется, и со второго захода запрос не
уходит. Он бьёт по первому заходу и по каждому, где кеш промахнулся.

Это кандидат в прямые причины жалобы «долго грузит», и он дешевле любой оптимизации рендера:
положить chart.js рядом с остальными вендорными библиотеками (`app/static/css/vendor/`, где
уже лежат tailwind, marked, purify, highlight) и раздавать со своего домена.
