## Подход одной фразой

Тулы перестают быть сообщениями. На ход появляется одна косметическая строка `⚙️`,
которая правится на месте и держит внутри свёрнутый список действий, а на границе хода
уходит короткий надёжный якорь `━━━`. Всё остальное (`💬`, `👤`, `📨`, `❌`) не меняется.

## Что меняется, по файлам

### `app/tg_bridge.py` — новые форматтеры

Рядом с прочими форматтерами, перед `_send_expandable`:

| функция | что делает | границы |
|---|---|---|
| `_tool_line(tool_name, body)` | одна строка действия: значок + команда/цель | ≤ 70 знаков, всегда одна строка |
| `_result_mark(result, is_error)` | хвост строки: `2.1 КБ ✓` или `✗ SyntaxError` | ≤ 20 знаков |
| `_progress_text(actions, seconds)` | тело `⚙️`: заголовок + последние 40 строк | ≤ 3500 знаков |
| `_turn_anchor(actions, seconds, cost)` | текст якоря | **жёстко ≤ 300 знаков** |

### `app/tg_bridge.py` — `stream_logs` (2988–3295)

- `t == "tool"` → больше НЕ `_send_expandable` и НЕ `_send_diff_image`. Кладёт
  `_tool_line(...)` в состояние хода, просит обновить `⚙️`.
- `t == "tool_result"` → больше НЕ картинка, НЕ `_edit_tool_with_result`, НЕ отдельное
  сообщение. Находит свою строку действия, дописывает `_result_mark(...)`, просит обновить
  `⚙️`. Ветка «`Read` вернул картинку» ОСТАЁТСЯ: это настоящий файл, который агент смотрел,
  а не машинерия (8 вызовов за сутки).
- `t == "status"`:
  - `turn ended` → финализация: последняя правка `⚙️` + якорь;
  - `message steered into active Codex turn` и `waiting for bg jobs` → строкой действия
    внутри `⚙️` (`↪ сообщение вошло в текущий ход`, `⏸ жду фоновые задачи`);
  - всё остальное (`codex turn=… started`, `precompact timer …`, `codex compacting context`)
    не отправляется вовсе.
- `t in ("text", "user_message", "error")` → без изменений.

**Названный размен:** «сообщение вошло в текущий ход» перестаёт быть отдельным сообщением и
становится строкой в косметическом `⚙️`. Если `⚙️` дропнут очередью, юзер не увидит
подтверждения, что его реплика подхвачена. Терпимо, потому что ответ агента на эту реплику
придёт надёжным `💬`. Если на практике будет мешать — сделать этот один статус надёжным
(33 сообщения в сутки), это правка одной строки.

### Состояние хода — идемпотентное по `log.id`

Живёт в локальных переменных `stream_logs`. Ключевое: `_TgDeliveryOverloaded` **откатывает
курсор** (`tg_bridge.py:3281-3287`) и переигрывает уже обработанные строки. Поэтому состояние
не может быть «списком, в который дописывают»:

```
_turn_actions: dict[int, str]        # log.id → строка действия, повтор ПЕРЕЗАПИСЫВАЕТ
_action_by_tool_id: dict[str, int]   # tool_use_id → log.id действия
_turn_started: float
_anchor_sent_for: int | None         # log.id строки `turn ended`, по которой якорь уже ушёл
_progress_msg_id: int | None         # разрешённый message_id ⚙️, не Future
_progress_last_edit: float
_progress_last_text: str
```

Повторное применение той же строки журнала даёт тот же результат: действие перезаписывается
по своему `log.id`, результат — по `log.id` своего вызова, якорь по уже отработанному
`turn ended` второй раз не уходит.

### Правка `⚙️` — как коалесцировать, не трогая политику очереди

`_tg_edit_message_safe` сейчас не принимает `telemetry_key`, и каждая правка получает
уникальный ключ (`tg_bridge.py:1787`). Нужен ОДИН аддитивный параметр — новый ключ
коалесцирования, без изменения самой очереди:

1. `_tg_edit_message_safe(..., telemetry_key=("progress", thread_id, orch_name))` —
   параметр прокидывается в существующий `_tg_call_safe`, логика очереди не меняется.
2. Ключ правок **отличается** от ключа отправки `⚙️`. Иначе коалесцирование заменит
   `call_factory` элемента-отправки, и правка будет ждать `Future` подменённой отправки.
3. Правка ставится в очередь только после того, как `message_id` РАЗРЕШЁН: `stream_logs`
   ждёт результат отправки `⚙️` один раз и дальше держит `int`. Не разрешился (косметику
   дропнули) → правок нет вовсе, ход закончится якорем.
4. Не чаще одной правки в 5 с на топик и **никогда с тем же текстом** — иначе
   `message is not modified` жжёт бюджет.

### Зеркала

`config["mirrors"]` сейчас пуст (проверено в `data/tg_bridge.json`), код инертен.
Контракт: зеркало получает ТОЛЬКО финальный якорь одним `_mirror_send`. Ни потока действий,
ни правок, ни второго `message_id` — заводить хранение handle для зеркала не будем.

### Чего НЕ трогаем

- политику очереди (`_tg_dispatch_chat`, полосы, TTL, правила коалесцирования) — инцидент
  с `important=True` жил именно там; добавляем только параметр `telemetry_key` в
  `_tg_edit_message_safe`;
- `app/session.py`, бэкенды, схему БД — после перебазирования `tool_use_id` уже пишется;
- `send_file` / `send_chart` / фото от юзера / полосу картинок.

## Лимиты Telegram на правку — что нашёл и что из этого следует

- Официальная FAQ даёт только про отправку: в группу бот не может слать больше
  20 сообщений в минуту [1].
- Про правки в официальной доке чисел НЕТ. Ближайшее известное — дословно из документации
  grammY (строка 68 сырого исходника): «bots can only do up to 20 message edits in a minute
  per group chat», со ссылкой на tdlibchat и оговоркой, что лимиты могут измениться [2].
- Правки тратят тот же бюджет: лимиты считают исходящие вызовы API [2].
- `message is not modified` — ошибка, которую надо не допускать, а не ловить [1][2].

Отсюда: 1 правка / 5 с на топик (худший ход в замере — 157 тулов → ≤ 12 правок в минуту,
запас к известным 20), коалесцирование в очереди, отказ от правки с неизменившимся текстом.

## Риски

| риск | что делаем |
|---|---|
| `⚙️` не доехало (косметика дропнута) | `message_id` не разрешился → правок нет, ход всё равно закрывается надёжным якорем |
| якорь разрастётся и `_formatted_chunks` порежет его на пачку надёжных отправок | жёсткий потолок 300 знаков + тест на 157 действиях |
| откат курсора при перегрузке переигрывает строки | состояние идемпотентно по `log.id`, якорь помнит свой `turn ended` |
| рестарт `stream_logs` посреди хода | курсор встаёт на последнюю строку (`tg_bridge.py:3012`), середина хода не восстанавливается: `⚙️` и якорь покажут только увиденный хвост. Принимаем осознанно, закрепляем тестом |
| старые строки без `tool_use_id` | привязка к САМОМУ СТАРОМУ незакрытому действию (FIFO), нет незакрытых — результат молча игнорируется |
| проверить на живом боте нельзя до общего рестарта | всё проверяется заглушкой и стендом `replay.py`; замер «после» — тем же стендом, что базовая линия |

## Что поправил раунд 1 Codex-ревью

- **blocking, принят полностью:** «`tool_use_id` уже пишется» — правда про `main`, ложь про
  мою ветку. Отсюда предусловие о перебазировании и зависимость T3.
- **blocking, принят:** коалесцирование правок технически не обеспечено —
  `_tg_edit_message_safe` не принимает ключ, а общий ключ с отправкой опасен. Появился
  раздел про аддитивный параметр, отдельный ключ и разрешение `message_id` до правок.
- **blocking, принят:** откат курсора при `_TgDeliveryOverloaded` переигрывает строки поверх
  состояния хода. Состояние переделано на идемпотентное по `log.id`, у якоря появилась
  память о своём `turn ended`, в AC T2 добавлен мутационный тест.
- **suggestion, принят:** рестарт `stream_logs` посреди хода — записан в риски как
  осознанно принятая частичность плюс тест.
- **suggestion, принят частично:** глушить ВСЕ статусы нельзя. Два пользовательских
  (`message steered`, `waiting for bg jobs`) переехали строкой в `⚙️`, размен назван вслух.
- **suggestion, принят:** тест давления на надёжную полосу при одновременных завершениях.
- **suggestion, принят:** для строк без `tool_use_id` — FIFO вместо «последней незакрытой».
- **suggestion, принят:** AC T5 перечисляет все удаляемые символы, зависимость от T4 убрана.
- **question, отвечено:** зеркало получает только финальный якорь, отдельный handle не заводим.
