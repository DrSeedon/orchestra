# #71 — исследование: чем весит `/api/orchestrators` и откуда второй вызов

## Вопрос

- **Контекст**: ответ `/api/orchestrators` — 21 490 байт по проводу (56 323 распакованных,
  5 записей). У юзера ответы крупнее ~15 КБ доезжают примерно в половине попыток.
- **Проверяемое утверждение**: вес можно снять, не перестраивая ответ.
- **Измеримый исход**: сколько байт по проводу даёт каждое поле и остаётся ли ответ
  в надёжном конверте (≤15 КБ) после снятия.

## Замер 1: одно поле — 92.8% провода

Метод из #65 — пережатие живого ответа без каждого поля (gzip -6, как отдаёт nginx):

```
база: 21 345 б gzip, 56 752 распакованных

19800 б gzip   92.8%  system_prompt              (распакованных 50 780)
  178 б gzip    0.8%  id
  127 б gzip    0.6%  description
   98 б gzip    0.5%  last_turn_ts
   83 б gzip    0.4%  created_at
   59 б gzip    0.3%  total_cache_read_tokens
   …остальные 50 полей — суммарно меньше 3%
```

Снятие ОДНОГО поля даёт **19.8 КБ из 21.3 КБ**: ответ становится ~1.5 КБ — не «в полтора
раза меньше», а в четырнадцать, и это глубоко внутри надёжного конверта. Требуемые ~7 КБ
закрываются с запасом, структура ответа не меняется.

**Вывод: читателей поля в этом ответе нет.** Это не «вроде никто не использует» — это шесть
проверенных потребителей, у каждого назван набор полей.

## Замер 3: второй вызов на первой загрузке — причина найдена

Трассировка вызывающего (врезка в `window.fetch`, стек в консоль):

```
+0.36 с  at api <- at loadOrchestrators
+0.85 с  at api <- at refreshSessions
итого вызовов: 2
```

Причина не в двух местах кода, а в **начальном значении дросселя**: `app.js:5788`
`let _orchFreshAt = 0`, а условие — `Date.now() - _orchFreshAt >= 15000`. При старте
`_orchFreshAt` равен нулю, поэтому первый же `refreshSessions` (через 0.5 с после
`loadOrchestrators`) считает данные протухшими и тянет их заново.

Дальше дроссель работает: за 20 секунд наблюдения всего 3 вызова (0.30 / 0.72 / 18.64 с),
то есть прежнего спама раз в 3 с уже нет — его кто-то снял до меня (комментарий на
`app.js:5817` про «1.1 МБ в минуту»).

**Правка на одну строку и она во фронте:** проставлять `_orchFreshAt = Date.now()` в
`loadOrchestrators()` после успешного ответа — тогда первый `refreshSessions` не дублирует
только что полученное. Файл `app/static/js/app.js` — территория frontend, сам не трогаю.

## Риски

1. **`to_dict()` общий**: если убирать поле в нём, пострадают другие потребители
   (`/api/sessions/{name}` отдаёт `to_dict()` и промпт там может быть нужен). Резать надо
   в РОУТЕ `/api/orchestrators`, а не в источнике.
2. **Строки из БД** (`get_all_sessions`) и активные сессии (`to_dict`) — два разных пути,
   поле надо снять в обоих, иначе останется у половины записей.
3. **Внешние потребители API** вне репозитория (если кто-то ходит в эндпоинт руками) не
   проверяемы — но эндпоинт внутренний, авторизация по токену.

## Чего я НЕ проверял

- Не проверял, как ведёт себя ответ при большем числе оркестраторов (сейчас 5). Доля
  `system_prompt` должна расти, но замер только на текущих данных.
- Не мерил доставку через посредника до машины юзера — цифры про 15 КБ взяты из описания
  задачи.
- Не смотрел, нет ли других эндпоинтов с тем же полем в списочных ответах (например
  `/api/sessions`) — это соседняя задача #65.
