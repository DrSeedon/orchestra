# #78 — исследование: base64-картинки в журнале, и почему рекомендованный способ надо поправить

## Вопрос

- **Контекст**: 52 строки журнала с base64 держат ~43% всех байт логов; у большинства есть
  парный `Read` с `file_path`, но рабочая копия воркера после мержа сносится.
- **Проверяемое утверждение** (оценка frontend): копировать ФАЙЛ в своё хранилище при
  записи строки (`app/session.py:1022`), уборка блобов в такт retention логов.
- **Измеримый исход**: доля байт журнала, вес худшего ответа истории, судьба картинки после
  удаления рабочей копии.

## Оценку перепроверил своим замером — цифры сходятся

| что | оценка frontend | мой замер (живая БД, read-only) |
|---|---|---|
| доля тяжёлых строк в байтах логов | 9.6 МБ = 43.4% | 10.79 МБ = **43.6%** (топ-52) |
| все ли они `tool_result` | 51 из 52 | **52 из 52** |
| парный `file_path` | 51 | **50** (у двух парной строки `tool` нет) |
| файл жив | 33 из 51 | **32 из 50** |

Расхождения в пределах суток роста БД. Вывод оценки подтверждён независимо: **ссылка на
файл протухает у 36% строк уже сейчас**, и это не случайность, а штатное поведение —
рабочие копии сносятся после мержа.

Мой первый запрос по шаблону `LIKE '%data:image%'` нашёл 0.5% байт и был бы ложным
опровержением: тело хранится как **python-repr словаря**
`{'type': 'image', 'source': {'type': 'base64', 'data': 'iVBOR…', 'media_type': 'image/png'}}`,
без префикса `data:image`. Искать надо по ВЕСУ, а не по форме.

## Поправка к направлению: копировать надо не файл, а то, что уже в руках

В точке записи (`app/session.py:1022`, `self._log("tool_result", event.content)`) **пути к
файлу нет** — он в ПРЕДЫДУЩЕЙ строке журнала (`tool` с `Read: {...}`). Чтобы «скопировать
файл», придётся идти назад по журналу за парной строкой, и это не сработает для двух строк
из пятидесяти двух, у которых парной строки нет вовсе.

При этом **тело картинки в этот момент уже в руках** — это и есть `event.content`. Значит
дешевле и надёжнее: раскодировать base64 и записать БАЙТЫ в блоб-хранилище, а в журнал
положить ссылку. Тогда:
- покрытие 52 из 52, а не 50 из 52;
- независимость от судьбы рабочей копии по построению (мы не ссылаемся на чужой файл);
- на диске байты, а не base64 — это ещё −25% к объёму (base64 раздувает на треть).

Это не спор с направлением, а его уточнение: хранилище то же, точка та же, меняется
источник данных для копии.

## Главное препятствие: retention логов НЕ СУЩЕСТВУЕТ, и это решение владельца

Требование «уборка блобов в такт retention логов» описывает механизм, которого нет:

```python
# app/db.py:1192
def cleanup_old_logs(days: int = 7) -> int:
    """REMOVED by owner decision — agent history is research data, never delete it.
    …"""
    raise RuntimeError("cleanup_old_logs is disabled: agent logs must never be deleted…")
```

То же в `app/manager.py:440`: «log retention REMOVED by owner decision». То есть «в такт
retention» = «никогда», а требование «retention обязателен в этой же задаче» прямо
сталкивается с решением владельца, что история не удаляется.

Разрешить это должен оркестратор. Вижу три честных варианта:

| вариант | что значит | цена |
|---|---|---|
| **A. Блоб живёт, пока жива строка** | удаление блоба только вместе со строкой журнала (то есть никогда) | рост есть, но в 1.33 раза медленнее нынешнего (байты вместо base64) и вне SQLite |
| B. Отдельная политика для блобов | картинки старше N суток удаляются, в журнале остаётся пометка | история теряет картинки — тот самый тихий класс, который мы чиним весь день; пометка делает потерю громкой |
| C. Инвентарь без удаления | сухой прогон «что можно удалить и почему», решение человека | ноль автоматики, но и ноль тихих потерь; так сделано в #27 для веток |

Мой выбор — **A + C**: блоб не переживает свою строку, а роста хватает надолго (см. цифры
ниже); инвентарь показывает, когда пора звать человека. Заводить «хранилище, о котором
никто не помнит» я не собираюсь — но и удалять историю молча тоже.

**Цифры для решения**: сейчас в БД 24.7 МБ логов за 8 суток, из них 10.8 МБ — картинки.
В блоб-хранилище те же картинки займут ~8.1 МБ (base64 → байты). При нынешнем темпе это
~1 МБ картинок в сутки; 39 МБ файл БД на диске 254 ГБ свободных.

## Старые 52 строки: мигрировать

Причина — не эстетика, а вес ответа истории: пока строки лежат как есть, любой запрос
истории такой сессии тащит их целиком. Миграция разовая, обратимая (блоб + ссылка) и
проверяемая: содержимое картинки не теряется, потому что байты берутся из самой строки,
а не из файла на диске. Если оркестратор решит иначе — старые строки продолжат работать,
клиент обязан уметь оба формата.

## Риски

1. **`logs` неизменяемы по инварианту** (`db.py:974`: «ни одного UPDATE»). Миграция старых
   строк этот инвариант нарушает — либо явно его пересматривать, либо мигрировать «в
   сторону» (новая строка + пометка), либо не мигрировать вовсе. Это решение уровня
   оркестратора, я его не приму молча.
2. **Клиент должен уметь оба формата** одновременно, иначе история сломается в момент
   выката.
3. **Блоб без строки — мусор, строка без блоба — дыра.** Нужен инвентарь, который видит обе
   стороны, иначе получим третий стор без читателя.
