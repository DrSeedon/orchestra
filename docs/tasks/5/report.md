# #5 — вставка картинки: долгая загрузка и запертый ввод

Жалоба юзера: «картинки вставляю пиздец долго грузят, можно ли ускорить или параллельно,
типа чтобы дальше писать текст можно было пока загружается картинка».

Оказалось две независимые проблемы, и та, на которую не жаловались, серьёзнее.

## 1. Замер: из чего складывалось время

| фаза | что показал замер |
|---|---|
| чтение файла в браузере | **статьи расхода нет.** `item.getAsFile()` отдаёт готовый Blob из буфера, уходит `FormData`-ом. Никакого FileReader/base64 в этом пути не было — гипотезу сняли до оптимизаций |
| сеть, аплоад | **всё время здесь.** С машины юзера 53–82 КБ/с: 753 КБ = 14–16 с, 1.7 МБ = 21–32 с |
| сервер | доли секунды: `read()` в память, md5, запись, `_cleanup_uploads` (в каталоге 1 файл при лимите 1 ГБ) |
| перерисовка | превью после аплоада качало **ту же картинку обратно**: `transferSize` 683 116 Б на 666 КБ файл |

Отдельно всплыло при замере с ноута: файлы тяжелее 1 МБ не доходили вообще —
`413 Request Entity Too Large` от **nginx** (`client_max_body_size` по умолчанию 1 МБ).
Лимит поднят оркестратором до 20 МБ. Тело такого ответа — HTML, а не JSON; это учтено
в обработчике ошибок (см. п. 3) и проверено отдельным прогоном.

**Вывод: упор в канал, а не в сервер и не в клиентский код.** Ускорить можно только одним
способом — отправить меньше байтов.

## 2. Главное, о чём не просили: терялся набранный текст

```js
const oldText = input.value;
input.value = oldText + '\n⏳ uploading image...';   // textarea захвачена
await fetch('/api/upload', …);                       // юзер печатает
input.value = oldText + '\n' + data.path;            // ← набранное стёрто
```

Ввод не «блокировался» — он затирался по возврату fetch. То есть ровно то, о чём юзер просил
(«чтобы дальше писать текст можно было»), выглядело работающим, а результат печати пропадал.
На канале 53 КБ/с окно потери — 15–30 секунд печати.

Замер до/после, сценарий «печатаю во время загрузки» (`/tmp/test_paste.py`):

| | ДО (`9423131`) | ПОСЛЕ |
|---|---|---|
| текст, набранный во время загрузки | **потерян** | сохранён |
| поле по окончании | `текст до вставки\n/path` | `текст до вставки допечатал во время загрузки\n/path` |
| каретка | уезжала в конец | остаётся на месте |

Теперь `input.value` только **дописывается** и только после ответа сервера; позиция каретки
восстанавливается (`setSelectionRange`), потому что присваивание `value` уводит её в конец.

## 3. Ошибка больше не молчит

Было: `catch { input.value = oldText; }` — ни слова юзеру. А при JSON-ответе без `path`
(400 «file too large») не срабатывал и catch: в поле навсегда оставалось `⏳ uploading image...`.

Проверены все четыре ветки (`/tmp/test_413.py`):

| случай | что видит юзер | вечный ⏳ | текст |
|---|---|---|---|
| nginx 413, тело HTML | `Upload failed — …: Error: HTTP 413` | нет | цел |
| приложение 400, JSON | `Upload failed — …: Error: file too large (max 10MB)` | нет | цел |
| обрыв соединения | `Upload failed — …: TypeError: Failed to fetch` | нет | цел |
| 200 без `path` | `Upload failed — …: Error: server returned no file path` | нет | цел |

Класс исключения печатается намеренно: у `TimeoutError` и части сетевых ошибок `message`
пустой, и без класса получилось бы `Upload failed — ` без объяснения.

## 4. Отправка, пока картинка не долетела

Было: сообщение уходило без картинки, а её путь потом дописывался в уже очищенное поле —
осиротевшей строкой к следующему сообщению.

Стало: `sendChat` дожидается всей незавершённой работы с файлом (`_trackUpload` — от сжатия
до ответа сервера), кнопка на это время показывает `⏳`, поле ввода остаётся живым: всё,
что допечатают за время ожидания, попадёт в то же сообщение. Ожидание конечно — таймаут 60 с.

Проверено (`/tmp/test_send_during.py`): Send нажат через 120 мс после вставки →
```
аплоадов в полёте на момент Send: 1
ушло агенту: {"message":"посмотри скрин\n/home/kesha/orchestra/data/uploads/f5bd99f17c8b.webp"}
картинка в сообщении: True | текст в сообщении: True | кнопка вернулась: 'Send'
```

## 5. Меньше байтов: WebP вместо PNG

Проверено на настоящем retina-скриншоте дашборда (2880×1800, снят с `device_scale_factor=2`):

| формат | размер | во сколько раз | PSNR |
|---|---|---|---|
| исходный PNG | 667 КБ | — | — |
| PNG, перекодированный браузером | 898 КБ | **хуже** | lossless |
| WebP lossless (`quality: 1`) | 750 КБ | **хуже** | lossless |
| **WebP q=0.9** | **354 КБ** | **1.9×** | 38.6 дБ |
| WebP q=0.8 | 264 КБ | 2.5× | 37.6 дБ |

Два неожиданных результата: браузерный PNG-энкодер **раздувает** файл, а WebP lossless в
Chromium крупнее исходного PNG (у Pillow на тех же картинках он, наоборот, в 1.9–2.3× меньше —
разная «усидчивость» энкодеров). Поэтому lossless-путь отброшен, взят q=0.9.

**Читаемость:** кропы 1:1 области с мелким текстом (оригинал / q=0.9 / q=0.8) сложены в
`readability.png` — текст неотличим, в том числе для vision-модели, которая эти скриншоты
и читает. Именно поэтому q=0.9 взят без колебаний: запас есть даже до q=0.8.

Итог по трафику: 683 КБ → 354 КБ. На канале юзера 53–82 КБ/с это 8.3–12.9 с → 4.3–6.7 с.

Ограничители: только для вставки из буфера (дропнутый файл юзер выбрал сам — его формат не наш);
файлы меньше 100 КБ не трогаем; если WebP получился не меньше оригинала — шлём оригинал;
любая ошибка кодирования → уходит оригинал (в консоль с классом ошибки, не в UI: аплоад-то удался).

## Что осталось незакрытым

- **Время кодирования на машине юзера не измерено.** На этом VPS замер недостоверен: LA 11–19,
  разброс 405 мс … 13.7 с на одной и той же картинке. Ориентир из спокойного момента —
  ~400 мс на 1.6 МП, то есть ~1.1 с на retina-скриншот 5.2 МП. Экономия 4–6 с это окупает,
  но проверить надо на ноуте: вставить скриншот и посмотреть `performance` вокруг кодирования.
- **Двойной перегон превью не убран.** После сжатия обратно качается 354 КБ, а скачивание у
  юзера быстрое; при этом картинка и так видна сразу — во время загрузки показывается сам файл
  из памяти браузера (`createObjectURL`, ноль сети). Замена финального превью на тот же
  objectURL требует протаскивания ссылки через `showImagePreview` и ручного `revokeObjectURL`
  в трёх местах удаления — на фоне 354 КБ по быстрому каналу не стоит того. Цифра для решения:
  `GET /uploads/…` = 45 мс на localhost, `transferSize` = размер файла целиком.
- **Формат стал `.webp`.** Claude-агенты читают webp штатно; для других рантаймов не проверено.
  Если где-то не прочитается — лечится сменой `image/webp` на `image/jpeg` в `_compressScreenshot`
  (одна строка), ценой ~1.1× худшего сжатия.
- **53–82 КБ/с — подозрительно мало** даже для асимметричного домашнего канала (≈0.5 Мбит/с).
  Стоит померить аплоад с той же машины на сторонний хост: если там столько же — это канал,
  если больше — упор в тракт до дашборда, и тогда экономия байтов лечит симптом, а не причину.
