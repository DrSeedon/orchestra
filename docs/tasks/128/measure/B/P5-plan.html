Миграция транзакционной и рассылочной почты на нового провайдера

Сервис на 40 000 пользователей. Переезд делается постепенным переключением доли трафика через фича-флаг, а не «в ночь с субботы на воскресенье»: репутация нового отправителя строится неделями, и единственный способ не сжечь доставляемость — прогрев с откатом на каждом шаге. Пять этапов, у каждого — вход, выход, порог остановки и способ откатиться меньше чем за 5 минут.

Как это устроено

Один интерфейс отправки, флаг доли, две ветки провайдера

Код не знает, какой провайдер сейчас работает. Он пишет письмо в собственную таблицу outbox, получает свой message_id, и уже отправщик решает по флагу, куда уйдёт конкретное письмо. Обратный поток (доставлено / отбилось / жалоба) от обоих провайдеров сводится в один обработчик и ложится рядом с исходной записью — это и есть ответ на вопрос «доехало ли».

Пунктир — обратный поток событий. Сплошной акцент — путь, который мы наращиваем. Приглушённая ветка — старый провайдер: он остаётся живым до конца Э4 и весь этот срок обслуживает свою долю трафика.

Этапы

Пять этапов: делаем — рискуем — откатываемся — проверяем

0

Инвентаризация и базовая линия

Неделя 1 · кода не трогаем

Делаем

  • Список всех мест отправки: бэкенд, cron, админка, CRM, сторонние интеграции. Grep по SDK старого провайдера и по SMTP-хосту в конфигах
  • Реестр шаблонов: где лежат, на каком движке (Handlebars / Liquid / свои), какие переменные
  • Экспорт списков подавления: hard bounces, жалобы, отписки — полностью, с датами
  • Снимок метрик за 30 дней: delivered, bounce, complaint, open — это baseline, с ним сравниваем всё дальше

Риск

  • Забытый отправитель всплывает после отключения старого аккаунта — письма молча пропадают
  • API старого провайдера отдаёт suppression list страницами и обрезает историю глубже N месяцев

Проверка выхода

  • Сумма писем по найденным отправителям сходится со счётчиком провайдера за неделю, расхождение < 2 %
  • Файл подавлений выгружен, число строк совпадает с цифрой в интерфейсе провайдера
Откат и артефакты этапа

Откат не нужен — этап только читает. Артефакты: docs/mail/inventory.md, suppression-YYYY-MM-DD.csv, дашборд baseline-метрик со ссылкой в тикете.

1

Абстракция отправки и outbox

Недели 1-2 · трафик 100 % на старом

Делаем

  • Единый интерфейс EmailSender.send(msg), две реализации, выбор — по флагу доли
  • Таблица outbox: свой message_id, получатель, тип письма, провайдер, статус, время. Ключ идемпотентности — чтобы ретрай не удвоил письмо
  • Один обработчик вебхуков на оба провайдера, статусы пишутся в outbox
  • Раскатка с флагом 0 %: код нового провайдера в проде, но не отправляет

Риск

  • Двойная отправка при переключении флага в момент ретрая — лечится ключом идемпотентности, а не «аккуратностью»
  • Различия API: у провайдеров разные лимиты размера, вложений, заголовков и формат ошибок 4xx/5xx

Проверка выхода

  • При флаге 0 % метрики не изменились относительно baseline — рефакторинг ничего не сломал
  • В outbox есть запись на каждое отправленное письмо; сверка с дашбордом старого провайдера за сутки
  • Тест: два одновременных вызова с одним ключом → одна отправка
Откат

Флаг уже стоит на 0 % — откат это откат релиза бэкенда обычным способом. Отдельный аварийный тумблер mail.provider.force=old, читается на каждой отправке, меняется без деплоя.

2

Домены, DNS, перенос подавлений

Неделя 2 · трафик 100 % на старом

Делаем

  • Верификация домена у нового провайдера: свой DKIM-селектор, чтобы не столкнуться со старым
  • SPF: добавляем include нового, старый не убираем. Считаем DNS-lookup'ы — лимит 10, за ним permerror
  • TTL всех почтовых записей опускаем до 300 c за сутки до первого переключения
  • Импорт списка подавления из Э0 в новый аккаунт — до первой отправки
  • DMARC rua на свой адрес, отчёты читаются глазами всю миграцию

Риск

  • Самый дорогой отказ плана: подавления не переехали → шлём по мёртвым адресам и тем, кто жаловался → всплеск жалоб → новый аккаунт блокируют в первые дни
  • Превышение 10 DNS-lookup в SPF ломает аутентификацию обоих потоков сразу
  • При p=reject опечатка в DKIM = письма отбиваются, а не падают в спам

Проверка выхода

  • Тестовое письмо на почтовые ящики: SPF=pass, DKIM=pass, DMARC=pass в исходном заголовке
  • Валидатор SPF показывает число lookup < 10
  • Число адресов в подавлении нового аккаунта = числу из выгрузки Э0 ± 0
  • DMARC-отчёты за 48 ч не содержат неизвестных источников
Откат и проверки DNS одной командой 
dig +short TXT example.com | grep spf1
dig +short TXT sel1._domainkey.example.com
dig +short TXT _dmarc.example.com

# после отправки тестового — в исходнике письма ждём три pass:
# Authentication-Results: spf=pass dkim=pass dmarc=pass

Откат: удалить include нового провайдера из SPF. При TTL 300 c изменение расходится за 5 минут; старый поток при этом не затронут вообще, потому что его запись всё это время оставалась на месте.

3

Прогрев: рампа 1 → 5 → 25 → 50 → 100 %

Недели 3-6 · главный этап

Делаем

  • Порядок типов писем: сперва транзакционные активным пользователям (их открывают — репутация растёт быстрее), затем сервисные уведомления, массовые рассылки — последними
  • Шаг рампы держим минимум 48 часов, через выходные не переключаем
  • Ежедневный отчёт: bounce, complaint, spam rate в Google Postmaster и Яндекс.Почтовом офисе
  • Seed-адреса на 8-12 почтовых системах, проверяем не «доставлено», а папку

Риск

  • Рампа быстрее, чем растёт репутация → троттлинг у Gmail/Mail.ru, задержки в часы, письма в «Промоакции»
  • Рассылка на 40 000 в момент, когда доля уже 50 %, — это разовый всплеск в 20 000 писем с молодого IP
  • Разные шаблонизаторы: письмо уходит с неподставленными {{ }}

Порог остановки

  • Жалобы ≥ 0,10 % — стоп немедленно, не «понаблюдаем»
  • Hard bounce ≥ 2 % — стоп
  • Spam rate в Postmaster ≥ 0,10 % — откат на шаг назад
  • Delivered ниже baseline более чем на 0,5 п. п. — откат на шаг назад
Рампа и стоп-кран

Каждое переключение — отдельная запись в журнале миграции: время, кто, какая доля, метрики на момент. Стоп-кран один: mail.provider.force=old. Возврат к прежней доле после отката — не раньше, чем через 72 часа и только с объяснённой причиной отката, иначе следующий шаг повторит ту же ошибку.

4

Стабилизация и отключение старого

+30 дней после 100 %

Делаем

  • 30 дней старый аккаунт живой и оплаченный: вебхуки принимаем, отправку не шлём
  • Домен трекинга ссылок старого провайдера не гасим — по ссылкам из уже отправленных писем ещё кликают
  • Финальная выгрузка новых подавлений со старой стороны и досыл в новый аккаунт
  • После 30 дней: убираем include старого из SPF, возвращаем TTL, удаляем вторую реализацию и мёртвый флаг

Риск

  • Ранняя отписка от старого тарифа → теряем вебхуки о жалобах по отправленному ранее и не заносим людей в подавление
  • Домен трекинга отключён вместе с аккаунтом → битые ссылки в письмах последних недель, а виноватым выглядит новый провайдер

Проверка выхода

  • 7 суток подряд метрики не хуже baseline при 100 % трафика
  • В outbox нет записей с провайдером «старый» за последние 30 дней
  • Grep по коду: SDK и ключи старого провайдера отсутствуют; ключи отозваны
Точка невозврата

До удаления include из SPF откат стоит одно переключение флага. После — откат означает повторную правку DNS и ожидание распространения. Поэтому чистку SPF и удаление кода делаем отдельным релизом после 30 дней тишины, а не «заодно» в день выхода на 100 %.

Проверка доставки

Как убеждаемся, что письма доехали, а не «отправились»

Ответ провайдера 202 Accepted не значит ничего: письмо принято к отправке, а не доставлено. Четыре независимых источника — если они расходятся, верим худшему.

Откат

Три уровня отката, от самого дешёвого

< 1 мин

Флаг доли

Ставим mail.provider.force=old. Весь новый трафик уходит на старого провайдера, деплой не нужен. Покрывает почти всё: всплеск жалоб, рост bounce, падение доставляемости, ошибки API нового провайдера.

~5 мин

DNS

Убираем include нового провайдера из SPF. Нужен только если проблема в аутентификации, а не в отправке. Работает быстро, пока TTL = 300 c — вернуть его обратно на сутки/неделю можно лишь после Э4.

часы

Откат релиза

Только при дефекте в самом слое отправки (дубли, потеря писем, порча шаблонов). Требует внимания к outbox: письма, отправленные новой версией, должны остаться с корректными статусами.

Правило одно: откат делает дежурный без согласования, разбор — после. Порог из Э3 достигнут → откатываемся, а потом обсуждаем; репутация отправителя восстанавливается неделями, а решение «понаблюдать ещё день» стоит именно этих недель.

Границы

Чего в этом плане нет

  • Смена домена отправителя. Мы меняем провайдера, домен остаётся прежним. Смена домена — отдельная миграция со своим прогревом, совмещать нельзя
  • Переезд входящей почты (MX, поддержка, ответы пользователей) — здесь не рассматривается, MX-записи не трогаем вообще
  • Перенос истории отправок из интерфейса старого провайдера. Если история нужна для поддержки — это отдельная задача до отключения аккаунта
  • Переписывание шаблонов под новый движок оценивается отдельно после реестра из Э0: объём зависит от того, совпадают ли шаблонизаторы

Числа сроков и объёмов — расчётные, пересчитываются после заполнения блока «Перед стартом». Проверено: 40 000 получателей — единственная цифра, заданная постановкой.
