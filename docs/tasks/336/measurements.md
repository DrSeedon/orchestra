## 3. Схема батчей из #322 в проде ещё ни разу не исполнялась

Сохранённые выходы показывают деление **`[12, 2]`** (#290, 06:46 и 07:27) и **`[9, 12]`** (#248,
08:42) — это код #317, а не `[5,5,4]` из #322. Причина: `bf70e3ad` (#322) смержен 18.08 09:26,
а ни одной операции с `n > 12` после этого времени в БД нет. Питон-код подхватывается только
рестартом, и на момент разбора живой сервер (`ExecMainStartTimestamp=18.08 17:36`) уже нёс #322,
но проверить его было не на чем.

То есть вывод «балансировка не укладывается» (research.md §3) относится к схеме, которая
работала бы впервые — и по числам не смогла бы.

## 5. Стоимость не является функцией числа файлов

Из тех же 178 операций, гейты с настоящим вердиктом: `n=1` стоит от **1.3 с** до **149.5 с**,
`n=7` — от **58.3 с** до **167.3 с**, `n=6` — от 46.9 с до 162.4 с.

Один и тот же файл `tests/test_merge_test_gate.py` в пяти прогонах:
**14.3 / 15.8 / 18.4 / 25.8 / 149.5 с — разброс 10.5×** без содержательных изменений в файле.

Доминирующий член — конкурентная загрузка машины. Отсюда: **балансировать батчи по количеству
файлов — мерить не ту величину**, и любой фиксированный потолок рано или поздно будет пробит.
Значит отказ по времени обязан быть информативным; это не украшение, а единственное, что
работает при непробиваемо-правильном бюджете, которого не существует.

## 6. Различие «красное против не успели» уже печатается — и выбрасывается

Главная находка. Сохранённый выход #248 (`batch_inconclusive`, 21 файл):

```

..............FF........................................................ [ 47%]
.........................................FFFF
batch 2/2 ... reason=timeout
..........................................................FF............ [  8%]
.............F...........................F...........F.................. [ 17%]
```

Девять `F` — настоящая краснота, о которой pytest успел сообщить до убийства. Гейт доложил
`INCONCLUSIVE`, то есть «повтори» — а повторять было нечего.

Сохранённый выход #329 за те же 180 с — сплошные точки, **ни одного `F`**: набор зелёный,
просто не доехал.

Данные для различения лежали в `output` обоих отказов и никем не читались.

## 7. Прогон: что переживает убийство по таймауту

`-q` при убийстве даёт безымянные точки, а при убийстве в фазе сбора — **0 символов**
(замерено: kill на 6 с по `tests/test_default_pipeline.py`).

Проверка режимов на файле с зелёным, красным и висящим тестом (`/tmp/336probe`, kill на 10 с):

```
test_probe.py::test_a_ok PASSED                                          [ 25%]
test_probe.py::test_b_red FAILED                                         [ 50%]
test_probe.py::test_c_slow
```

Есть всё нужное: имя, вердикт **до** убийства, и имя теста, на котором прервались (строка без
вердикта).

Арифметика флагов — проверена прогоном, потому что неочевидна и ломается «улучшением»:

| флаги | verbosity | потестовые строки |
|---|---|---|
| `-q` | −1 | нет, точки |
| `-q -v` | 0 | **нет**, точки |
| `-q -vv` | +1 | **да** |
| `-v` | +1 | да |

Выбран `-q -vv`: даёт тот же режим, что `-v`, но сохраняет `argv[:4] == [python, -m, pytest, -q]`,
на который стоит существующий тест `test_pytest_argv_has_no_exitfirst`. Гвардой на эту арифметику
стоит `test_argv_verbosity_really_prints_per_test_lines` — настоящий pytest, не мок; мутация
`-vv` → `-v` красит его (проверено).

## 8. Проверки, которых требовал оркестратор

### `-m "not live_probe"` в `addopts`

| проверка | результат |
|---|---|
| `pytest -m live_probe tests/` — CLI обязан ПЕРЕОПРЕДЕЛЯТЬ, а не складываться | **3/3214 собрано** (3211 deselected) — переопределяет |
| обычный `pytest tests/` | 3211/3214 собрано, 3 deselected |
| командой гейта `-m "not live_probe"` | 3211/3214 — **число совпадает** |

`-m` — опция одного значения, побеждает последняя; CLI идёт после `addopts`. Оба требования
выполнены.

Побочно: CI (`.github/workflows/ci.yml:19`) зовёт `uv run pytest -q --timeout=30` без фильтра
маркеров — теперь живые пробы снимаются и там.

### Пер-тестовый `--timeout`

Механизм проверен прогоном (`/tmp/336timeout`, `--timeout=8`), причём на обоих видах зависания:

```
FAILED test_hang.py::test_hangs_on_subprocess - Failed: Timeout (>8.0s) from ...
FAILED test_hang.py::test_hangs_on_sleep     - Failed: Timeout (>8.0s) from pytes...
2 failed, 1 passed in 16.81s
```

Зависший тест становится **именованным падением с трейсбеком, и прогон продолжается** —
ровно то, чего не хватало. Блокирующий `subprocess.run` прерывается наравне с `time.sleep`.

Значение НЕ выбрано намеренно: слишком низкое даёт ложную красноту, то есть тот же класс отказа,
который задача чинит. CI уже держит `--timeout=30`, но CI-машина не знает нагрузки 15+, при
которой один файл здесь идёт 260–283 с. Для выбора нужен прогон с `--durations` по полному
сьюту, а он требует `test_lock` (занят `feat-hot-reload`). Предлагаю мерить и вносить отдельно —
угадывать это число нельзя.

## 9. Итоговый бюджет (вариант А, разрешён оркестратором)

`budget_for(n) = min(1200, 180 + 150 × n)`, происхождение каждого числа записано рядом с
константами в `app/merge_test_gate.py`, чтобы через месяц оно не стало вторым безродным 180:

| источник | число | как получено |
|---|---|---|
| ПОЛ 330 с (`n=1`) | 219.5 с | самый дорогой одиночный файл (`test_manager`, под нагрузкой 283 с) × 1.5. Батч не может быть меньше файла |
| ШАГ 150 с/файл | среднее ≈68 с | среднее по замеренным файлам с двойным запасом (медиана 33 с, хвост тяжёлый) |
| ПОТОЛОК 1200 с | 682 с | худший правдоподобный набор (manager+frontend+db+session+mcp_stdio+tg_bridge) × 1.5 |

Кривая и покрытие наблюдённых отказов:

| набор | бюджет | измеренная стоимость | запас |
|---|---|---|---|
| #329, 6 файлов | 1080 с | 456 / 465 / 593 с | 1.8–2.4× |
| #290, 14 файлов | 1200 с | ≥ 682 с (сумма одиночных) | 1.76× |
| 1 файл | 330 с | до 283 с (`test_manager` под нагрузкой) | 1.17× |

Потолок нужен именно потому, что запас не может быть гарантирован: разброс одного и того же
файла 10.5× (§5). Поэтому бюджет — первый контур, а информативный отказ (§6–7) — второй, и он
работает как раз тогда, когда первый пробит.

### Что переписано в тесте и чем это доказано

`test_large_mapped_subset_runs_all_files_in_bounded_batches` вшивал прежний бюджет литералами
(`== [60.0, 60.0, 60.0]`, `36.82 + 240.0 > DEFAULT_TIMEOUT_SECONDS`) — то есть морозил не
поведение, а константу, пришедшую из чужой подсистемы. Заменён на
`test_large_mapped_subset_reaches_a_verdict_at_measured_file_costs`: стоимости файлов взяты из
замера (`test_manager` 283 с, `test_frontend` 148 с), проверяется, что батч ограничен, каждый
файл прогнан, бюджет растёт с размером набора и вмещает самый дорогой одиночный файл, а вердикт
выдан.

| мутация | ожидание | результат |
|---|---|---|
| `budget_for` → `return BASE_TIMEOUT_SECONDS` (бюджет перестал зависеть от набора) | КРАСНЫЙ — это настоящий дефект | `1 failed` |
| `PER_FILE 150 → 200`, `MAX 1200 → 900` (только литералы) | ЗЕЛЁНЫЙ — тест про поведение, не про число | `1 passed` |

Обе откачены с `touch`, повторные прогоны зелёные (24 passed).
