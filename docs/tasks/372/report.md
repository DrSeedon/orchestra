# #372 — аудит деградации VPS при одновременной работе Codex

Дата замера: 2026-08-23. Инцидент: примерно 13:00–13:24 CEST (18:00–18:24 по времени пользователя). Дерево: `1f0a526d3a74`. Диагностика read-only; сервис не перезапускался и конфигурация не менялась.

## Вердикт

Прокси не был узким местом: Codex на этом VPS вообще не использует HTTP(S)-proxy. Его живые сокеты шли напрямую по IPv6 через `eth0` в `chatgpt.com`/Cloudflare. Канал, CPU и RAM имели большой запас.

Наблюдались две независимые причины двух разных симптомов:

1. Длинные ходы воркеров создавали сами задания: `xhigh`, контекст 92–93% и 51–71 tool round-trip за ход. У двух остановленных длинных ходов только 41–63 с заняли сами инструменты, а измеренные ожидания следующего ответа модели — 489–781 с. Один inference-gap достиг 241 с.
2. Дашборд ломал собственный HTTP-канал: `_conditional()` возвращает `JSONResponse(None, status_code=304)`. Клиент успевает увидеть `304`, затем сервер падает с `RuntimeError: Response content longer than Content-Length` и закрывает соединение. За окно наблюдения было около 62 таких запросов. Это соответствует браузерным `signal timed out`, но не объясняет длительность модельных ходов.

Диск испытывал вторичную нагрузку от работы агентов (до 69% util и 15% iowait), но не был главным временем в длинных ходах: `await` оставался 1.4–1.9 мс, а tool execution занимал лишь 4–5% общей длительности двух худших ходов.

## Что на самом деле означали «примерно 20 Codex-процессов»

В cgroup Orchestra было 10 загруженных Codex-сессий. На каждую живут два процесса: Node launcher и native `codex`; поэтому `ps` показывает около 20 процессов даже при idle. Отдельно у каждой сессии есть MCP-процесс.

По журналу реальный максимум одновременных provider-turn на VPS за день — 4, не 20. До остановки длинные ходы одновременно шли у `ai-table-worker`, `partner-call-prep` и ещё 1–2 сессий. После остановки не-оркестраторов `vmstat` показал 98–99% CPU idle и практически нулевой дисковый поток.

## Измерения

### Сеть и прокси

- В `.env`, окружении живого Orchestra и окружении Codex нет `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`.
- Живые Codex TCP-соединения: прямые IPv6-сокеты к адресу `chatgpt.com` через `eth0`; маршрут не содержит tunnel/proxy hop.
- Контрольный `chatgpt.com`: 1 параллельный запрос — 0.081 с; 4 — максимум 0.101 с; 12 — максимум 0.153 с, ошибок 0.
- 10 МБ с Cloudflare: 34.0 MB/s.
- Во время инцидента `eth0`: 1.0–1.7 MB/s, 0 RX/TX errors, 0 drops.
- First-output latency не выросла содержательно с конкуренцией: median 12.7 с при 1–2 активных ходах против 13.4 с при 3–4. Сами задания разные, поэтому это контроль отсутствия крупной деградации, а не точный benchmark.

### VPS

- 8 CPU. В 13:10/13:20/13:30 idle: 60.3% / 86.8% / 80.7%; load-1: 2.35 / 1.00 / 1.58.
- `MemAvailable` около 17.9 GB из 24.6 GB; swap-in/out 0.
- Диск `sda`: 34–69% util, 20–111 MB/s reads, 4.5–15% CPU iowait, `await` 1.37–1.86 мс.
- После остановки воркеров: 98–99% CPU idle, диск 0–0.2% util на коротком повторном срезе.

### Два длинных хода

`ai-table-worker`:

- 1170 с до принудительной остановки;
- 6.44M cumulative input tokens, контекст 93%;
- 71 tool calls: 56 Bash, 9 WebSearch, 4 memory search, остальные 2;
- 68 измеренных tool-result пар: 62.9 с суммарно;
- ожидание модели после старта/tool-result: 781.4 с суммарно, максимум одного gap 241.1 с.

`partner-call-prep`:

- 1022 с до принудительной остановки;
- 6.35M cumulative input tokens, контекст 92%;
- 51 tool call: 38 Bash, 12 WebSearch, 1 memory search;
- 49 tool-result пар: 40.8 с суммарно;
- ожидание модели после старта/tool-result: 488.6 с суммарно, максимум 100.6 с;
- на 14-й минуте начался native compact.

9 из 10 загруженных Codex-сессий запущены с `model_reasoning_effort=xhigh`; одна — `high`.

## Отдельный дефект дашборда

Текущий код: `app/routes/sessions.py:221-236`, `_conditional()`; строка 235 создаёт JSON-тело `null` для статуса, которому тело запрещено. Контроль:

1. authenticated GET `/api/sessions` → `200`, ETag;
2. повтор с `If-None-Match` → клиент получает `304`, 0 bytes;
3. журнал немедленно получает `RuntimeError: Response content longer than Content-Length` и `Unhandled exception on GET /api/sessions`.

Локальный обычный `/api/sessions` после остановки воркеров: median 0.114 с; через `https://orc.seedon.ru`: 0.400 с. Значит публичный путь добавляет примерно 0.2–0.3 с, но сам по себе не даёт двухсекундный таймаут. Повторный crash/close HTTP/1.1 соединения — измеренный механизм, который объясняет каскадные browser timeouts при нескольких параллельных запросах и SSE.

Подан platform bug: `/api/sessions 304 sends body and crashes ASGI connection after response headers`.

## Что исправлять

Приоритет 0: заменить 304 на настоящий пустой `Response(status_code=304, headers=...)` и добавить тест, который проверяет не только статус/пустое тело клиента, но и отсутствие ASGI exception/закрытия соединения.

Приоритет 1: не лечить это лимитом «не больше N воркеров» — измеренный максимум уже был 4. Для длительности ходов сокращать round-trip и не отдавать открытые исследовательские задания воркерам с 90%+ контекста. Конкретный красный флаг — 50+ tool calls за один ход; это важнее числа загруженных CLI.

Приоритет 1: пересмотреть автоматический `xhigh` для механических/закрытых задач. В этом инциденте 9 из 10 живых Codex-сессий были `xhigh`; сеть доставляла ответ за десятки миллисекунд, минуты уходили внутри model loop.

Приоритет 2: отдельно профилировать источник больших последовательных чтений, если после исправления 304 и сокращения ходов интерактивность всё ещё деградирует. Текущих данных достаточно назвать диск вторичным давлением, но недостаточно честно назначить конкретный процесс-виновник в прошлом окне.

## Ограничения вывода

- Исторический sysstat имеет шаг 10 минут; он доказывает отсутствие общей CPU/RAM/network saturation, но не исключает краткий секундный spike.
- Provider wait включает сеть и inference. Прямая трасса, отсутствие drops/errors, стабильная first-output latency при concurrency 1–4 и контроль 12 соединений исключают крупный сетевой вклад; разделить hidden reasoning и provider queue без серверной телеметрии OpenAI нельзя.
- Сравнение first-output по concurrency наблюдательное: задания и размеры контекста различались.
