# #337 — Agent Reach: даёт ли она нам то, чего у нас нет

Дата: 2026-08-18. Фаза 1 (research + живые пробы на нашем VPS). Реализации нет, ничего не установлено.

## Вопрос

- **Контекст:** юзер прислал форвард про утилиту Agent Reach — «ставит и настраивает агенту
  инструменты доступа к платформам»; автор форварда заменил ей самописные парсеры.
- **Изменение под проверкой:** поставить Agent Reach на этот VPS.
- **Baseline:** то, что у нас есть сейчас — встроенный `WebSearch`, `curl` + `r.jina.ai`,
  скиллы `reddit-reader`/`youtube-reader`, Grok 4.5 native X (незакрытая #261), `gh` CLI.
- **Решающий исход:** появляется ли источник, которого у нас сейчас НЕТ, и/или закрывается ли
  #261 «Поиск по X как ТУЛ» — при цене (авторизация, общие конфиги, риск), которую мы готовы платить.

## Гипотезы и фальсификаторы

- **H1: Agent Reach закрывает #261 (доступ к поиску по X).**
  Ложна, если её X-путь требует того, чего у нас нет на headless VPS (кука живого аккаунта,
  десктопный браузер) — или если он менее надёжен, чем уже проверенный Grok.
  → **REFUTED**, F3.
- **H2: Agent Reach обходит блокировку Reddit, про которую наш скилл пишет категорично.**
  Ложна, если её собственная документация признаёт ту же блокировку.
  → **REFUTED в заявленной форме**, но нашёлся ДРУГОЙ обход (F5) — не тот, что предполагала H2.
- **H3: главная ценность — сами бэкенды.**
  Ложна, если бэкенды доступны нам напрямую без установки Agent Reach.
  → **REFUTED**, F6: ценность — в СПИСКЕ выбора, а не в коде; забрать список можно без установки.
- **H4: установка идёт через `curl | bash` (наш глобальный стоп-фактор).**
  → **REFUTED**, F1.

## Findings

### F1. Установка — `pipx`/`pip`, не `curl | bash`. Стоп-фактор снят, но заменяется другим

Первоисточник (`docs/install.md`, шаг 1) даёт дословно [1]:

```
pipx install https://github.com/Panniantong/agent-reach/archive/main.zip
# или, при PEP 668:
python3 -m venv ~/.agent-reach-venv && source ~/.agent-reach-venv/bin/activate
pip install https://github.com/Panniantong/agent-reach/archive/main.zip
```

`curl | bash` в репозитории нет. Зато рекламируемый способ установки — не команда, а
**инструкция агенту**: «帮我安装 Agent Reach: <raw URL docs/install.md>» (README, строки 78-80) [2].
То есть агент скачивает markdown и исполняет из него команды. Функционально это тот же класс
доверия, что `curl | bash`, только исполнителем выступает LLM. У нас это управляемо: команды
из F1 можно выполнить руками и не отдавать агенту.

`agent-reach install` **по умолчанию систему не меняет** — только проверяет окружение;
изменения происходят при явном `--system`, есть `--dry-run` (README «安全性», строки 250-257) [2].
Это подтверждено кодом: `sudo` в `agent_reach/cli.py` **не встречается ни разу**
(`grep -n sudo ar-cli.py` → пусто), а `_install_system_deps()` зовёт `apt-get` напрямую [3].
На нашем VPS под `NoNewPrivileges=yes` такой `apt-get` от агента просто не пройдёт;
`gh` и `node`/`npm` у нас уже стоят (проверено: `/home/kesha/.local/bin/gh`, `/usr/bin/node`).

**CONFIRMED — tier 2 (первоисточник) + tier 1 (чтение кода).**

### F2. Что она физически делает с общими файлами — это и есть главная цена

`--system` копирует свой скилл в **каждый существующий** каталог скиллов
(`agent_reach/cli.py:541-568`) [3]:

```python
skill_dirs = [
    (os.path.expanduser("~/.agents/skills"), "Agent"),
    (os.path.expanduser("~/.config/opencode/skills"), "OpenCode"),
    (os.path.expanduser("~/.openclaw/skills"), "OpenClaw"),
    (os.path.expanduser("~/.claude/skills"), "Claude Code"),
]
```

`~/.claude/skills` у нас существует → туда лягут `SKILL.md` (6 802 Б) плюс семь
`references/*.md` (22 794 Б суммарно; замерено `stat -c%s`). Это ровно тот класс правки,
на котором мы уже горели: чужой агент поправил общий `~/.grok/config.toml` и молча сломал
выдачу моделей у двух других (#251). Скилл читают **все агенты всех проектов** на этом VPS,
и правка не видна ни в одном `git diff`.

Хуже, что скилл написан на захват маршрутизации. Дословно из его frontmatter [4]:

> MUST USE when user wants to 调研/research/搜索/search/查/找/look up anything on the internet
> […] Also MUST USE when user mentions any platform or shares any URL/链接

Это прямо конфликтует с нашими `reddit-reader`, `youtube-reader` и с правилом
«`WebSearch` первым, `sonar` для однофразовых ответов» из `~/.claude/CLAUDE.md`. Наш принцип
«1 задача = 1 workflow» нарушается: у агента появляется второй способ сделать то же самое,
причём помеченный `MUST USE`.

Плюс `--system` пишет MCP-конфиг через `mcporter … --scope home` (install.md, строки 229, 304) [1]
и `~/.agent-reach/config.yaml` для кук.

Удаление честное: `agent-reach uninstall` чистит `~/.agent-reach/`, скилл-файлы и MCP-конфиг,
есть `--dry-run` (README, строки 277-291) [2].

**CONFIRMED — tier 1: прочитанный код + замеренные размеры файлов.**

### F3. #261 она НЕ закрывает. X-поиск требует куки живого аккаунта и сам помечен нестабильным

Матрица из README, строка 113 [2]: Twitter/X «装好即用» (без конфига) = **чтение одного твита**;
«配置后解锁» = поиск, таймлайн, лонгриды. Конфиг — это кука.

Гайд `setup-twitter.md` дословно [5]:

> twitter-cli 是免费开源工具（pipx 安装），但需要你的 Twitter 账号 cookie。
> […] 3. 点击 Cookie-Editor 图标 → Export → Header String

и далее `export TWITTER_AUTH_TOKEN=… TWITTER_CT0=…`. То есть нужен залогиненный десктопный
браузер с расширением Cookie-Editor и ручной экспорт — на headless VPS сам этот шаг невозможен,
его делает юзер на своей машине.

Три отдельных предупреждения, все из первоисточника:

1. **Риск бана аккаунта.** README, строки 262-266 [2]: «使用 Cookie 登录的平台（Twitter、小红书等），
   通过脚本/API 调用**存在被平台检测并封号的风险**。请务必使用**专用小号**».
2. **Именно VPS-IP — отдельный фактор риска.** Скилл `references/social.md`, дословно [4]:
   «**IP 风控**: 不要在 VPS/数据中心 IP 上频繁调用 […] 有封号风险。使用住宅代理或本地环境».
3. **Ровно нужная нам команда помечена нестабильной.** `social.md` кладёт
   `twitter search "query"` в раздел «可能不稳定的命令» с пояснением «Twitter 频繁改 GraphQL 端点，
   可能 404», и даёт цепочку ретраев из четырёх шагов [4]. Стабильными названы `feed`,
   `tweet URL`, `article`, `user-posts` — то есть чтение по известной ссылке, не поиск.

Апстрим `public-clis/twitter-cli`: 2 852 звезды, последний push **2026-05-07** — три месяца без
изменений (GitHub API, замер 18.08.2026). Это тот самый класс «одноплатформенные CLI разом
встали в марте 2026», который сам проект называет причиной своей маршрутизации.

Сравнение с уже проверенным у нас путём (#251/#261): Grok 4.5 native X дал **18/18** успешных
X-обращений, exact permalink 4/6, медиана 34.6 с, ноль ненулевых exit'ов — **без куки, без
чужого аккаунта, без риска бана, в рамках подписки** [6].

Отдельно: остаточные блокеры #261 — это НЕ «нет доступа к X». Последний раунд ревью плана
оставил ровно два блокирующих замечания, оба про строгость оракула [7]:
mismatched-`threshold` конверт `available` проходит приёмку, и оракул не проверяет, что
candidate/canonical URL вообще принадлежат X (`https://attacker.invalid/status/<тот же id>`
прошёл бы). Ни одно из двух Agent Reach не касается: они про наш валидатор, а не про источник.

**CONFIRMED (REFUTED H1) — tier 2: три независимых места первоисточника + tier 1: метаданные
апстрима.**

### F4. Reddit: Agent Reach подтверждает наш вывод, а не опровергает его. Измерено

Наш скилл `reddit-reader` утверждает категорично: «Reddit блокирует ВСЕ серверные запросы
(curl, JSON API, headless browser)». Проверка на этой машине, 18.08.2026 15:2x UTC:

| проба | результат |
|---|---|
| `curl https://www.reddit.com/r/ClaudeAI/top.json?limit=1` | **HTTP 403**, тело `<title>Blocked</title>` |
| `curl https://r.jina.ai/https://www.reddit.com/r/ClaudeAI/comments/…` | Jina вернула HTTP 200, **содержимое** = `Warning: Target URL returned error 403: Forbidden` / «You've been blocked by network security» |
| Exa MCP `web_fetch_exa` на тот же URL | `CRAWL_HTTP_403` |

Три независимых серверных пути — три отказа. Agent Reach говорит то же самое своими словами,
README строка 115 [2]: «—（没有零配置路径：匿名接口已被封）», и `social.md` [4]:
«**Reddit 没有零配置路径**：匿名 `.json` 端点已被封（403），官方 API 自 2025-11 起人工审批基本不批».

Её рабочие пути для Reddit: OpenCLI с **десктопным** браузерным логином (у нас нет десктопа)
либо `rdt-cli` + кука, и README отдельно указывает, что на сервере нужен резидентный прокси
(~$1/мес), потому что «Reddit 在 VPS IP 上更容易 403» [2].

**CONFIRMED (H2 REFUTED в заявленной форме) — tier 1: три собственных измерения, согласуются
с tier 2.**

### F5. Настоящая находка по Reddit пришла с другой стороны: индекс Exa отдаёт тело поста, бесплатно

Agent Reach подключает полнотекстовый поиск через MCP Exa (`config/mcporter.json`:
`{"exa": {"baseUrl": "https://mcp.exa.ai/mcp"}}`, ключа нет) [8]. Проверено с нашего VPS
напрямую, без установки Agent Reach:

- `initialize` → HTTP 200, `serverInfo: {"name":"exa-search-server","version":"3.2.1"}`, ключ не
  спрашивается;
- `tools/list` → `web_search_exa`, `web_fetch_exa`;
- `web_search_exa("Agent Reach github Panniantong")` → HTTP 200, 6 930 Б, реальные результаты.

Ключевой прогон — `web_search_exa` по reddit-запросу (сырьё:
`docs/tasks/337/exa-rdsearch.txt`). Первый результат вернул **тело поста**, не только заголовок:

> How is it possible to hit a full weekly limit in a few hours? […] I'm a Claude Pro subscriber
> […] My weekly limit reset today at 10:00 AM. A few hours later […] I was already being told I
> had consumed my entire weekly limit

То есть у нас появляется бесплатный путь к содержимому Reddit там, где скилл утверждает, что
остался только Perplexity. Границы честные и видны в том же сырье: это **индекс, не живой
краул** — второй результат в той же выдаче отдал закешированный снимок страницы-заглушки
(«'ve been blocked by network security» + мусорные base64-обрывки). Свежий пост, которого нет
в индексе, так не прочитается, и `web_fetch_exa` живьём даёт `CRAWL_HTTP_403` (F4).

**CONFIRMED для существования пути (tier 1, свой прогон); UNCERTAIN для покрытия** — измерен
один запрос, доля индексированных постов не мерилась.

### F7. Zero-config путь к X через Jina Reader на нашем IP сейчас не работает

Единственный беcкуковый X-путь Agent Reach — Jina Reader (`web.py → Jina Reader`, README
строка 231) [2]. Проба с нашего VPS, два раза с интервалом ~7 минут, дословный ответ:

```
HTTP=403
{"code":403,"name":"AbuseAlleviationError","status":40305,
 "message":"Anonymous access to domain x.com blocked until Tue Aug 18 2026 16:16:53 GMT+0000
 due to previous abuse found on https://x.com/jaynitx: DDoS attack suspected: Too many requests"}
```

Блок доменный и **на анонимный пул целиком** — не про нас лично и по формулировке временный
(до 16:16 UTC того же дня). Но это ровно тот режим отказа, который делает канал непригодным для
автоматики: он выключается действиями посторонних. Reddit через Jina в тот же момент проходил
на уровне транспорта (HTTP 200) и падал на уровне цели (403 от Reddit) — то есть сама Jina
живая, отрезан именно домен `x.com`. Платный/ключевой тариф Jina эту квоту поднимает, но это уже
не «zero config».

Контрольная проба того же момента: `publish.twitter.com/oembed` (наш независимый верификатор
X-ссылок из #261) с этого же IP работает — HTTP 200 с реальным телом твита. Значит канал
проверки #261 жив, а мёртв именно чужой ридер.

**CONFIRMED — tier 1: две пробы + положительный контроль.**

### F8. YouTube — единственный источник, где у Agent Reach есть реальный прирост, и он не доказан

Наш `youtube-reader` даёт метаданные через oEmbed; в нём есть шаг 3 «скачать аудио `yt-dlp` +
Deepgram», то есть транскрипция у нас платная и с внешним ключом. Agent Reach ставит `yt-dlp`
и берёт **готовые субтитры** (README строка 109, «字幕提取 + 视频搜索», без конфига) [2] — это
дешевле и точнее, чем ASR по аудио.

Что измерено на нашем IP:

- страница `youtube.com/watch` грузится нормально: HTTP 200, 1 424 022 Б, `captionTracks`
  присутствует, маркера бот-гейта `Sign in to confirm` — 0;
- **но** наивный запрос по извлечённому `baseUrl` дорожки вернул `HTTP=200, bytes=0`.

Ноль байт при коде 200 — это ровно тот класс проверки, что даёт одинаковый ответ при успехе и
провале, поэтому вывода «субтитры недоступны» из него не делаю. Современный `timedtext` требует
дополнительных параметров (po_token), которые и умеет `yt-dlp`. Значит: **гипотеза
правдоподобна, но НЕ проверена**, и проверяется она ровно одним прогоном `yt-dlp` (см. эксперимент).

Побочно: `youtube-reader` содержит устаревшее — прокси `127.0.0.1:12334` в каждой команде,
хотя по `CLAUDE.md` этих туннелей на VPS не существует. Здесь YouTube открывается напрямую.

`yt-dlp` у нас **не установлен** (`command -v yt-dlp` → пусто).

**LIKELY для прироста, UNCERTAIN для работоспособности — tier 1 измерил только доступность
страницы, не извлечение субтитров.**

### F9. Остальные источники: паритет или недостижимы

- **Веб-чтение.** У неё `web.py → Jina Reader`. У нас `curl https://r.jina.ai/<url>` уже прописан
  в `CLAUDE.md` как штатный обход 403. **Разницы нет.**
- **GitHub.** `github.py → gh CLI`. `gh` установлен. **Разницы нет.**
- **RSS.** `rss.py → feedparser`. У нас `feedparser` не стоит (`ImportError`), но это `pip install`
  в одну строку, а не источник, к которому нет доступа. **Разница ≈ ноль.**
- **LinkedIn.** Публичные страницы — Jina Reader (доступно нам и так). Детали профилей —
  `mcp-server-linkedin`, и install.md дословно требует десктоп [1]:
  «浏览器弹出后手动登录 LinkedIn […] 无桌面的服务器需在 VNC 等可见桌面中运行同一条登录命令».
  **На headless VPS недостижимо.**
- **Instagram / Facebook.** Только OpenCLI с сессией десктопного Chrome (README строки 116-117) [2].
  **На headless VPS недостижимо.**
- **B站, 小红书, V2EX, 雪球, 小宇宙.** Китайские площадки; в наших задачах не фигурируют.

## Counter-evidence — что говорит ПРОТИВ моего вердикта

1. **Главный довод форварда я не опроверг.** Его автор хвалит не возможности, а то, что
   «самописные парсеры периодически отваливались». Ценность Agent Reach — сопровождение выбора
   бэкендов (`yt-dlp` → `bili-cli` при бане B站, ротация умерших CLI в марте 2026). Если мы
   заберём `yt-dlp` и Exa руками, мы забираем **сегодняшний** список и остаёмся сами себе
   мейнтейнером, когда он протухнет. Это реальная, не выдуманная цена моей рекомендации.
2. **Мои измерения — срез одного дня.** Блок Jina на `x.com` истекает 18.08 16:16 UTC; на
   следующий день zero-config чтение твита может работать. Вывод F7 верен как «канал
   выключается посторонними», но неверен как «канал мёртв».
3. **Покрытие Exa я померил одним запросом.** F5 доказывает существование пути, а не его
   надёжность. Один удачный reddit-запрос — не основание переписывать `reddit-reader`.
4. **Против моего «X не закрывается» есть сильный аргумент, который я обязан назвать:**
   `twitter-cli` возвращает **структурированный ответ API**, а Grok возвращает **текст модели**.
   Вся сложность #261 (валидатор из четырёх признаков, oEmbed-верификация, запрет публиковать
   неподтверждённый текст модели) существует ровно потому, что модель может сочинить ссылку.
   У CLI этой проблемы нет по построению. То есть при наличии куки-аккаунта `twitter-cli` дал
   бы **лучший provenance**, чем наш путь. Я всё равно рекомендую не брать — но по цене
   (аккаунт + бан-риск + VPS-IP + нестабильность команды), а не потому, что путь плох.

## Вердикт

**НЕ БРАТЬ Agent Reach как продукт. ВЗЯТЬ ЧАСТЯМИ два её выбора, напрямую и без установки.**

- **Не брать** саму утилиту: единственное, что она добавляет сверх своих бэкендов, — это
  установщик и `SKILL.md` с `MUST USE`-описанием в общий `~/.claude/skills/`, читаемый всеми
  агентами всех проектов (F2). Цена — конфликт маршрутизации с нашими скиллами и правилом
  «1 задача = 1 workflow», плюс невидимая в `git diff` правка общего состояния, на которой мы
  уже горели (#251). Прироста, оправдывающего это, нет: половина её каналов у нас уже есть,
  половина недостижима без десктопа.
- **Взять часть 1 — Exa MCP.** `https://mcp.exa.ai/mcp`, без ключа, проверено живьём с этого VPS
  (F5). Добавляется строкой в `.mcp.json` Orchestra. Даёт воркерам семантический поиск и текст
  страниц там, где сейчас у них только встроенный `WebSearch`; побочно — путь к телу
  reddit-постов из индекса.
- **Взять часть 2 (после проверки) — `yt-dlp` для субтитров YouTube.** `pipx install yt-dlp`,
  никаких общих конфигов. Даёт `youtube-reader` то, чего у него нет: содержание видео без
  платного ASR (F8).
- **#261 не закрывается и не меняется.** Её остаточные блокеры — про строгость нашего оракула
  (mismatched `threshold`; candidate/canonical URL не проверяются на принадлежность X) [7], а не
  про доступ к X. Agent Reach ни одного из двух не касается. Grok-маршрут остаётся.
- **Пересмотреть решение, если** юзер готов завести **отдельный расходный X-аккаунт** и снимать
  с него куку руками. Тогда `twitter-cli` становится осмысленным ВТОРЫМ источником для #261 —
  с лучшим provenance, чем текст модели (см. counter-evidence 4). Это решение юзера, не моё.

## Дешёвый эксперимент (один, ~5 минут, ничего общего не трогает)

**E1 — субтитры YouTube через `yt-dlp` с нашего IP.** Единственная непроверенная часть вердикта.

```bash
pipx install yt-dlp    # или: uvx yt-dlp ...  — без установки в систему
yt-dlp --write-auto-sub --sub-lang en --skip-download \
       -o '/home/kesha/orchestra/data/yt-probe/%(id)s' \
       'https://www.youtube.com/watch?v=<видео с речью на английском>'
```

- **Успех** = на диске появился непустой `.vtt` (> 1 КБ), внутри читаемые реплики, exit 0.
- **Провал** = ненулевой exit, пустой файл, либо `Sign in to confirm you're not a bot` —
  тогда YouTube требует куку/po_token и с нашего IP путь закрыт, пункт «взять часть 2» отменяется.
- Файл кладётся в `data/`, **не в `/tmp`** (по `CLAUDE.md` — проверить `findmnt /tmp`).
- Отрицательный результат так же полезен, как положительный: он закрывает F8 окончательно.

**Не предлагаю эксперимент по X через `twitter-cli`** — он невозможен без куки живого аккаунта,
то есть без решения юзера. Это не «дорого», это заблокировано на входе.
