# #95 — источник данных о квоте SuperGrok

**Вердикт: ЕСТЬ, но это НЕ 7d-окно.** Найдены два независимых источника. Оба дают реальные
числа, оба проверены измерением. Ни один не повторяет семантику Claude/Codex (скользящее
7-дневное окно) — у Grok это **календарный месяц** и **мгновенный остаток**.

Всё ниже снято на живом аккаунте 2026-07-28, grok 0.2.112, `tier: 4` в JWT.

---

## Источник A — `GET /v1/billing` (месячный расход)

```
https://cli-chat-proxy.grok.com/v1/billing
Authorization: Bearer <JWT из ~/.grok/auth.json>
x-grok-client-version: 0.2.112
x-grok-client-identifier: grok-cli
x-grok-client-surface: grok-build
```

Сырой ответ (полностью, `/tmp/grok-billing-raw.json`):

```json
{"config": {
  "monthlyLimit": {"val": 20000},
  "used": {"val": 474},
  "onDemandCap": {"val": 0},
  "billingPeriodStart": "2026-07-01T00:00:00+00:00",
  "billingPeriodEnd":   "2026-08-01T00:00:00+00:00",
  "history": [
    {"billingCycle": {"year": 2026, "month": 6}, "includedUsed": {"val": 0},
     "onDemandUsed": {"val": 0}, "totalUsed": {"val": 0}},
    {"billingCycle": {"year": 2026, "month": 5}, ...},
    {"billingCycle": {"year": 2026, "month": 4}, ...}
  ]}}
```

### Что такое `used` — ИЗМЕРЕНО, не угадано

Единица не документирована, поэтому мерил дельтой. Три независимых прогона:

| прогон | ходов | токенов | Δ`used` |
|---|---|---|---|
| 1 | 2 | 47 332 | +2 |
| 2 | 3 | 95 114 | +4 |
| 3 | 3 | — | **+3** |

Третий прогон снимал `usage.modelCalls` из `turn_completed` и сравнивал напрямую:
`modelCalls = [1, 1, 1]`, сумма 3, **дельта billing = 3 → MATCH**.

**`used` = число модель-вызовов (`modelCalls`) за расчётный месяц.** Не токены, не доллары,
не ходы: во втором прогоне 3 хода дали 4 вызова (внутри хода бывает больше одного), и
счётчик показал именно 4. Ходы и вызовы совпадают не всегда — считать надо `modelCalls`.

**Лаг ~20 секунд.** Сразу после хода дельта 0; на отметке 20 с появляется полное значение и
дальше не меняется (проверено на 0/20/40/70 с). Для дашборда: опрос чаще чем раз в ~30 с
бессмысленен.

### Что отсюда собирается

| нужно для панели | есть? | как получить |
|---|---|---|
| % использования | **да** | `used / monthlyLimit * 100` = 474/20000 = **2.4%** |
| момент сброса | **да** | `billingPeriodEnd` (ISO с таймзоной) |
| длительность окна | **да, но месяц** | `billingPeriodEnd − billingPeriodStart` (календарный, 28–31 д.) |
| прогресс окна | **да** | доля прошедшего от начала до конца периода |
| отклонение темпа | **да** | сравнение доли расхода с долей прошедшего времени |
| **7d-окно** | **НЕТ** | у Grok его не существует, см. «Чего нет» |

## Источник B — заголовки `x-ratelimit-*` на инференсе

На `POST /v1/chat/completions` (успешный, 200) приходят:

```
x-ratelimit-limit-tokens:     53000000
x-ratelimit-remaining-tokens: 53000000
x-ratelimit-limit-requests:   8300
x-ratelimit-remaining-requests: 8300
```

Это **мгновенный остаток**, отдельный от месячного счётчика. Ограничения находки:
- **окно неизвестно** — заголовков `x-ratelimit-reset-*` в ответе НЕТ, длительность нигде не
  заявлена. Сколько времени восстанавливаются 8300 запросов — не измерено.
- на момент замера оба счётчика были в максимуме (`remaining == limit`), то есть просадку
  наблюдать не удалось и связь «расход → падение remaining» **не подтверждена**.
- заголовки приходят на прямой HTTP-вызов; **ACP-транспорт их не пробрасывает** — через
  `grok agent stdio` мы их не видим.

## Чего НЕТ (проверено, не предположение)

- **7-дневного или иного скользящего окна.** У Claude — 5h/7d, у Codex — primary/secondary.
  У Grok расчётный период — календарный месяц (`billingPeriodStart/End` = 1-е число).
  Приводить месяц к «7d» на дашборде можно только пересчётом темпа, и это будет НАША
  производная величина, а не то, что заявляет провайдер.
- **Команды в CLI.** В `grok --help` нет ничего про usage/limits; в ACP `availableCommands`
  только `compact, always-approve, context, session-info, deep-research, workflow, goal`.
- **Метода ACP.** Аналога `account/rateLimits/read` (как у Codex) в потоке нет; сам CLI за
  время работы ходит только в `/v1/models` (проверено `--debug-file`).
- **Прочих эндпоинтов.** Перебраны `/usage /limits /rate_limits /rate-limits /subscription
  /subscriptions /me /account /quota /usage/limits /credits` на `cli-chat-proxy.grok.com/v1`
  и `api.x.ai/v1` — везде 404. Существуют только `/models` и `/billing`.

## Подводные камни для реализации

1. **Токен живёт ~12 часов и протухает.** У меня первый заход дал сплошные 401 именно
   поэтому. В `auth.json` есть `refresh_token` и `expires_at`; обновление делает сам CLI при
   любом вызове. Дашборд не должен обновлять токен сам — безопаснее дёргать через CLI или
   реагировать на 401 как на «нет данных», а не рисовать ноль.
2. **Без `x-grok-client-version` инференс отвечает 426 Upgrade Required.** Для `/v1/billing`
   этот заголовок не обязателен, но лучше слать всегда — версия зашита в поведение прокси.
3. **`used` лагает ~20 с.** Значение сразу после хода занижено.
4. **Аккаунт командный** (`team_id` в JWT, `onDemandCap: 0`). На другом аккаунте форма
   ответа может отличаться — считать поля опциональными, отсутствие → «нет данных».
5. **Не показывать 0 как факт.** Если запрос не удался, панель должна говорить «нет данных»,
   как уже делает карточка SuperGrok («Лимиты провайдера недоступны — значения не подменены
   нулями»).

## Что это даёт для §7.1 «форма терминального исчерпания»

**Частично закрывает, но не полностью.** Теперь есть, чем предсказать приближение к лимиту:
`used / monthlyLimit` и `remaining_requests`. Это позволяет предупредить ДО упора.

Но сама **форма ошибки при нуле по-прежнему не наблюдалась**: на момент замера расход 480 из
20000 (2.4%), остаток по заголовкам полный. Чтобы закрыть §7.1 окончательно, нужен реальный
упор — тогда сработает уже готовое дословное логирование `Grok raw error payload:`.

Ожидаемое место ошибки — HTTP 429 на инференсе (`rate_limited` встречается в бинарнике как
`error_type`), но это **гипотеза**, а не замер.
