# Grok Build как рантайм Orchestra — полевой гид

Парный документ к `codex-field-guide.md`. Пишется для того, кто вернётся сюда через полгода
и не помнит ничего. Всё ниже — результат замеров на живом CLI (задача #95, `docs/tasks/95/`),
а не пересказ документации: вендорский README на этом рантайме врал дважды.

Версия, на которой всё измерено: **grok 0.2.112**, модель **grok-4.5** (рантайм-лейбл
`grok-4.5-build`), подписка **SuperGrok**.

⚠️ На VPS с 13.08.2026 стоит **grok 1.0.3** — сменился мажор. Всё ниже снято на 0.2.x и
на 1.0.3 **не перепроверено**: формы событий, имена полей и поведение `--agent-profile`
считать гипотезами до приёмки по §8.

---

## 0. Главное за две минуты

- Рантайм называется `grok`, модель `grok-4.5`, провайдер `x-ai`, контекст **500 000**.
- Спавн: `spawn_worker(model="grok", ...)`. Алиасы: `grok`, `grok4.5`, `grok-build`.
- Транспорт — **ACP** (Agent Client Protocol, JSON-RPC 2.0 по stdio), процесс
  `grok agent stdio`. Ближайший аналог — `codex app-server`, не headless-CLI.
- Зачем он вообще: **отдельный пул квоты**. Это единственная причина. По качеству он не
  заменяет ни Opus, ни Sol.
- **Registry-only на сегодня**: рантайм выбирается явно указанием модели, в `pipeline.yaml`
  роли за ним не закреплены.

## 1. Что должно стоять и где логин

```bash
sudo npm i -g @xai-official/grok   # официальный пакет; curl|bash не использовать
grok --version                     # на VPS: grok 1.0.3 (1a29d5bc12)
grok login --oauth                 # ТОЛЬКО так; кладёт креды в ~/.grok/auth.json
grok models                        # должен ответить "You are logged in with grok.com"
```

**`--device-auth` НЕ использовать** (замер 14.08.2026, `CLAUDE.md` — единственный владелец правила):
он выдаёт токен БЕЗ `refresh_token`, тот живёт около суток, и по истечении CLI САМ удаляет
`~/.grok/auth.json` — выглядит как «файл пропал», хотя это штатное истечение. `--oauth` даёт
`refresh_token` + `expires_at` и продлевается сам. Живость проверять командой `grok models`,
а не наличием файла.

npm-пакет — лаунчер: настоящий бинарник (~165 МБ) уезжает в `~/.grok/bin/grok-<версия>`,
`/usr/bin/grok` — симлинк на пакет. Обе ветки резолвера ведут в один файл.

**Логин делает человек и только под тем юзером, под которым Orchestra запускает воркеров
(`kesha`)** — `ensure_grok_home()` симлинкует `data/grok-home/auth.json` на `~/.grok/auth.json`
этого юзера. Каталог `data/grok-home/` создаётся сам на первом коннекте, руками не готовить.

Всё через прокси: в шелле есть функция `grok`, которая делает `orchestra_proxy_load`.
Если зовёшь бинарник напрямую (`~/.grok/bin/grok`) — прокидывай `HTTPS_PROXY` сам,
источник истины прежний: `HTTPS_PROXY` в `.env` Orchestra.

Бинарник ищется в порядке: `GROK_BIN` из окружения → `shutil.which("grok")` → `~/.grok/bin/grok`.
Явная переменная бьёт PATH намеренно — посторонний `grok` в PATH не должен молча выигрывать
у настройки.

## 2. Изоляция: почему у воркеров свой GROK_HOME

Orchestra запускает грок-воркеров с `GROK_HOME=data/grok-home` (в `.gitignore`), а не с
пользовательским `~/.grok`. Причина не косметическая:

Grok **самостоятельно подхватывает** MCP-серверы из `~/.claude.json`, `.mcp.json`,
`~/.grok/config.toml`, проектных `.grok/config.toml` и плагинов — и **транслирует их env**
в нотификации `_x.ai/mcp/servers_updated`. Так в артефакт задачи однажды утёк живой
`OPENROUTER_API_KEY` стороннего сервиса.

Передача `session/new.mcpServers` **не замещает** обнаруженное, а **мерджится** с ним
(замер: передал только `orchestra` — поднялось `{orchestra, websearch, mcp-pandoc}`;
передал пустой список — всё равно два чужих). Единственный работающий тумблер —
`[compat.claude] mcps = false`, и он читается **только из user-конфига**; тот же ключ в
проектном `.grok/config.toml` игнорируется. Править `~/.grok/config.toml` нельзя — это
личный файл человека.

Отсюда конструкция:
- `data/grok-home/config.toml` — наш конфиг с выключенным claude/cursor-compat MCP;
- `data/grok-home/auth.json` — **симлинк** на пользовательский, чтобы refresh токена был общим,
  а не протухал в приватной копии;
- каталог **стабильный, не временный** — там же лежит session store, от него зависит резюм.

Поверх этого на коннекте проверяется фактический состав серверов: чужой → `GrokMcpIsolationError`,
воркер **не стартует**. Гарантию поведения самого grok мы не контролируем, поэтому проверяем
результат.

## 3. Чем отличается от claude и codex на практике

| | claude | codex | **grok** |
|---|---|---|---|
| Транспорт | SDK-сессия | app-server JSON-RPC | **ACP JSON-RPC (stdio)** |
| Системный промпт | параметр SDK | `developerInstructions` | **только файл `--agent-profile`** |
| Инъекция в идущий ход | да | `turn/steer` | **нет — очередь, N посылок = N `turn_end`** |
| `usage` в конце хода | за ход | **кумулятивный за тред** | **за ход** |
| Стоимость | считаем сами | считаем сами | **рантайм отдаёт `costUsdTicks`** |
| Контекст | из API | скрести rollout-файл | **`_meta.totalTokens` в каждом чанке** |
| Резюм | `session_id` | thread id | `session/load` по `(cwd, sessionId)` |

Практические следствия, на которых легко обжечься:

- **Системный промпт доходит ТОЛЬКО через `--agent-profile`** (временный `.md` с YAML-frontmatter).
  ACP-поля `systemPrompt`, `_meta.systemPrompt`, `instructions` принимаются и **молча
  игнорируются** — воркер поедет вообще без промпта, и никто не заметит.
- **Мид-тёрн сообщение не рулит ходом.** Оно попадает в нативную очередь и исполняется
  ОТДЕЛЬНЫМ ходом. Поэтому `mid_turn_inject=False`, а цикл событий завершается по опустевшей
  очереди, а не по первому `prompt_complete`.
- **Одобрение тулов берётся из предложенного списка.** Реальные id — `allow-once` /
  `reject-once`. Выдуманный `allow` не совпадал ни с чем, агент читал это как «ничего не
  выбрано» и **отменял ход целиком**: вывод команды уже получен, а `turn_end` приходит
  `ok=False stop=interrupted`. Снаружи — «воркер загадочно бросает задачи», без строчки ошибки.
- **Резюм переживает смену ветки** в том же worktree (проверено `main` → `feature/x`), но
  привязан к пути: тот же id из другого cwd → `Path not found` → фолбэк в новую сессию с
  громким предупреждением.

## 4. Деньги и контекст

Стоимость берётся из рантайма: `costUsdTicks × 1e-10` USD. Сходится **в ноль** с формулой

```
cost_usd = ((input − cachedRead)·$2 + cachedRead·$0.30 + output·$6) / 1e6
```

на четырёх замеренных ходах — но **все четыре были короче 200k, и формула верна только для
этого тарифа** (третья ловушка). Три ловушки:

- **Ставка кэша — $0.30/M, а не $0.50**, как пишут все вторичные источники. Рантайм прав.
- **Цены Grok намеренно НЕ лежат в общем `TOKEN_PRICES`.** `routes/system.py:_cost_cached_for()`
  пересчитывает историю для всего, что есть в этом словаре, по claude-эвристике кэша
  (cache_read = 10% от input). У Grok это 15%, и на реальном ходе эвристика завышает
  стоимость на **+27.6%**. Пока модели в словаре нет — функция отдаёт сохранённое значение.
  Не «зарегистрируй заодно цены как у всех».
- **Выше 200k тариф удваивается: $4 / $0.60 / $12** за 1M (input / cached / output) против
  $2 / $0.30 / $6 ниже порога. Источник — `docs.x.ai/developers/pricing`, сверено 12.08.2026
  (#232), **живьём подтверждено 13.08.2026 (#251)**: в однозначных single-batch A/B ходах
  token-компонент `costUsdTicks` согласуется с плоским тарифом при prompt `<200k` и с
  удвоенным при `≥200k`. Это не разрешает пересчитывать fallback по агрегату multi-call хода:
  тариф применяется к отдельному request, а ACP отдаёт только turn aggregate.
  Практический смысл: 500 000 контекста — преимущество платное, а не бесплатное. Класс задач
  «извлечение из большого объёма» уходит за порог по построению и стоит вдвое — то есть
  единственное окно, которым Grok выигрывает у Sol/Luna (258k), оплачивается двойной ставкой
  ровно там, где оно нужно.
  **Конфликт источников:** OpenRouter на `x-ai/grok-4.5` даёт плоские $2/$6 и порог не
  упоминает вовсе. Для прямого биллинга xAI верить docs.x.ai — он владелец биллинга, а
  OpenRouter перепродавец со своей ценовой политикой.
- **grok-4.6 (вышел 12.08.2026) — заголовок тот же, кэш дороже на 67%.** По
  `docs.x.ai/developers/pricing`, сверено 13.08.2026 (#232): `<200k` — $2 / **$0.50** / $6,
  `≥200k` — $4 / **$1.00** / $12. Заголовочные in/out совпадают с 4.5 в точности, порог
  никуда не делся, а ставка кэша выросла $0.30 → $0.50 (и $0.60 → $1.00), то есть на 67% в
  обоих тарифах. Оба тарифа 4.6 подтверждены живыми ходами #251. Значение: при одинаковом
  token-профиле cache-heavy ход 4.6 дороже 4.5; точный межмодельный расход по 18 ходам НЕ
  сравнивать, пока нет account billing truth (см. §7.6). Формулу проверки сначала подставлять
  со ставкой **своей** модели, а не «как у Grok».

`reasoningTokens` — **подмножество** `outputTokens`, сверху не биллится. Не складывать.

Знаменатель `context_pct` берётся из рантайма (`totalContextTokens`), а не из нашей
константы: константа и рантайм сейчас совпадают (500 000), и это способно спрятать поломку
механизма — тесты специально разводят значения.

## 5. Карта: где чинить, когда сломается

| Симптом | Куда смотреть |
|---|---|
| Не коннектится, падает на старте, ошибки протокола, события не те | `app/backend_grok.py` |
| Воркер поднялся не с тем набором MCP / промпт не доехал / не тот эффорт | `app/backend_grok.py` (`_mcp_server_configs`, `_write_agent_profile`, `connect`) |
| Модель ушла не на тот рантайм, нет в выпадашке, не тот контекст/провайдер | `app/models.py` (`MODELS`, `BACKENDS`, `ALIASES`, `_infer_backend`, `_infer_provider`) |
| Не собирается бэкенд, не те capabilities, MCP-набор собран неверно | `app/runtime_registry.py` (`_grok_factory`, `register_runtime`) |
| Расходы упали не в тот пул, не тот TTL кэша, cold-starts врут | `app/usage_analytics.py` (`_PROVIDER_RULES`, `_provider_case`, `_cache_ttl_case`) |
| Карточка провайдера, цвет, фильтр агентов, cache-grid | `app/static/js/analytics.js` (`_PROVIDER_META`, `_PROVIDER_CAPACITY_KEY`) |
| Цвет модели / короткое имя | ничего не трогать: фронт data-driven, `_PROVIDER_COLORS['x-ai']` + label из API |

## 6. Правило для СЛЕДУЮЩЕГО рантайма

Новый рантайм расширяет **контракт общего кода**, а не только добавляет файл.

Фактура: после мержа грок-фабрики `runtime_registry` начал звать `get_role(pipeline, role)`.
У legacy-сессий `pipeline` пуст → `load_pipeline('')` кидал `ValueError`, а фабрики ловили
только `FileNotFoundError` → **лёг `send` у 34 живых сессий**. Тесты не поймали: в фикстурах
`pipeline` заполнен всегда, в проде — нет.

Правила, выведенные из этого:

1. **Добавил вызов общей функции в фабрику — проверь её на РЕАЛЬНЫХ значениях из живой БД**
   (read-only копия), а не на фикстурах. Замер по 330 сессиям: `pipeline` пуст у 27,
   `profile` у 316, `task_id` у 243, `base_branch` — **у всех 330**, `cwd` формально заполнен,
   но каталога нет у 248.
2. **Лови класс исключения, а не тот, что попался.** Фабрика ловила `FileNotFoundError`,
   а прилетал `ValueError` из валидации имени.
3. **`ELSE claude` — всегда баг.** Любой хвост «всё остальное = существующий провайдер»
   при добавлении рантайма тихо приписывает ему чужой пул, чужой TTL и чужую квоту. Ищи
   такие хвосты в SQL, в тернарах фронта и в дефолтных ветках политик.
4. **Ищи ВТОРУЮ копию.** В этой задаче одна и та же бинарность жила в трёх местах
   (`_PROVIDER_SQL`, inline-CASE, порог cold-start) и в трёх тернарах фронта.

## 7. Реестр непроверенного

Незакрытый вопрос без инструкции проверки превращается в фольклор. Здесь — всё, что помечено
UNCERTAIN, и **как именно** это проверить, когда появится возможность.

### 7.0 Данные о квоте — НАЙДЕНЫ (см. `docs/tasks/95/quota-source.md`)
Источник есть: `GET /v1/billing` на `cli-chat-proxy.grok.com` даёт `used` / `monthlyLimit` /
`billingPeriodStart|End`, где **`used` = число `modelCalls`** (измерено сверкой: 3 вызова →
дельта 3), с лагом ~20 с. Плюс заголовки `x-ratelimit-*` на инференсе — мгновенный остаток,
но **без окна сброса** и без наблюдённой просадки. **7d-окна у Grok нет**: расчётный период —
календарный месяц. Полные сырые ответы, замеры и подводные камни — в `quota-source.md`.

### 7.1 Форма терминального исчерпания квоты — НЕИЗВЕСТНА
- **Почему не закрыто:** исчерпать SuperGrok в ходе задачи не удалось; на момент замеров
  расход 480 из 20 000 (2.4%). §7.0 даёт возможность ПРЕДСКАЗАТЬ приближение к лимиту, но не
  показывает форму ошибки при нуле. Ожидаемое место — HTTP 429 на инференсе (`rate_limited`
  есть в бинарнике как `error_type`), но это гипотеза, а не замер.
- **Что сделано вместо:** паттерн не выдуман. Неопознанная ошибка остаётся `error` и падает
  громко; сырой payload логируется **дословно** (`logger.error`, до 4000 символов) и в потоке
  ошибок, и при провале `session/prompt`.
- **Как проверить:** дождаться первого реального упора в лимит → достать из лога строку
  `Grok raw error payload:` целиком → сопоставить с `_classify_error` в `backend_grok.py` →
  добавить ветку `rate_limit` по РЕАЛЬНОМУ полю (код/тип), а не по подстроке сообщения.
- **Чего не делать:** копировать классификацию Codex «по аналогии». У Codex терминальный
  лимит ловится в error handler по своим полям — это не переносится.

### 7.2 `type: "http"` для url-MCP — ПРОВЕРЕНО (форма params)
- **Замер 15.08.2026, grok 0.2.112:** bare `{"name", "type":"http", "url"}` →
  `session/new` **Invalid params** (валит весь connect, как у COG-second-brain с
  `agentic-jobs`). `headers` **обязан** быть массивом (пустой `[]` ок). Dict `headers:{}`
  — тоже Invalid params. То же для `type: "sse"`.
- **Orchestra:** `_mcp_server_configs()` всегда шлёт `headers` list-of-pairs
  (`_headers_to_acp`). Авторизованный http-MCP: `headers: {"Authorization": "Bearer …"}`
  в `.mcp.json` → `[{name, value}, …]`.
- **Не закрыто:** доходит ли remote http-MCP до `status=ready` и видны ли тулы — отдельно
  от формы params; connect больше не падает на Invalid params.

### 7.3 TTL кэша — НЕ ИЗМЕРЕН
- **Почему не закрыто:** xAI TTL не документирует, рантайм его не сообщает, а замер требует
  часов wall-clock (фоновый пробник не переживает конец хода агента).
- **Что сделано вместо:** `cache_policy_for_runtime("grok")` помечен `approximate=True` —
  дашборд рисует «≈» вместо обещания точности. Значение 3600 — справочное.
- **Как проверить:** сделать ход, подождать N минут, сделать второй ход в ТОЙ ЖЕ сессии и
  посмотреть `cachedReadTokens` в `turn_completed.usage`. Ноль → кэш истёк. Бинарным поиском
  по N (10/20/40/60 мин) граница находится за несколько итераций. Запускать надо не фоновым
  процессом агента, а cron-джобой (`bg_create(type="cron")`) или отдельным скриптом.

### 7.4 Мелочи, не влияющие на работу
- `_MODEL_SHORT` в `tg_bridge.py` не содержит `grok-4.5` — фолбэк и так даёт читаемое имя.
- Grok обёртывает MCP-тулы в мета-слой `search_tool` → `use_tool`, поэтому в событиях
  сначала виден `use_tool`, а конкретное имя (`orchestra__list_agents`) приходит апдейтом.

### 7.5 `grok-4.6` в Grok Build — ПОДТВЕРЖДЕНО
- **Живой замер** (grok 1.0.3, подписка grok.com, 13.08.2026): `grok models` вернул
  `grok-4.6 (default)` и `grok-4.5`; 18/18 headless-ходов на обеих моделях завершились.
- `[features] remote_fetch = false` выключает онлайн-каталог и оставляет статический fallback
  только с 4.5. Это однажды выглядело как «4.6 исчезла у провайдера», но одинаковый результат
  во всех worktree создал общий user-config; после удаления ключа 4.6 вернулась немедленно.
- Доступность модели в живом каталоге и проверенный route в Orchestra — разные состояния:
  registry разрешает runtime/provider, а `grok models` отвечает, доступна ли модель аккаунту
  сейчас. Статический registry не должен обещать живую доступность.

### 7.6 `modelCalls` и account billing на текущей подписке — ТОЧНОЙ ЦИФРЫ НЕТ
- В #251 18 ходов с 113 completed X-вызовами и 19 X batch-id отдали суммарно
  `modelCalls=18`. Это поле само по себе не доказывает расход пула: один ход с двумя batch
  10+8 вернул один `turn_completed`, а published cost-формула разошлась на $0.05.
- Старый замер #95 `monthlyLimit=20 000` относился к другому аккаунту/тарифу. На текущем
  X Premium+ `GET /v1/billing` 13.08.2026 вернул `monthlyLimit=0, used=0`; unified billing log
  даёт только округлённые `creditUsagePercent=8.0` и недельное окно, без числителя.
- Поэтому billing delta снять нельзя, ёмкость третьего пула в ходах сейчас **UNKNOWN**.
  Не переносить 20 000 на этот аккаунт и не суммировать `modelCalls` как provider truth.

## 8. Что смотреть на первом живом прогоне

Рантайм может **правдоподобно притворяться работающим**. Ниже — конкретные сигналы, где
искать и чему именно не верить.

**Сначала — три места, где он соврёт убедительнее всего:**

1. **Ход завершился `ok=False stop=interrupted`, хотя тул отработал.** Это НЕ «модель
   передумала». Так выглядит несовпадение одобрения тулов. Смотреть: были ли `tool_use` и
   `tool_result` ДО `turn_end`. Если да, а ход «прерван» — сломан approval, а не модель.
2. **Воркер отвечает бодро и по делу, но игнорирует правила проекта.** Проверять не тон, а
   факт доставки промпта: спроси у него что-то, что есть ТОЛЬКО в системном промпте (роль,
   ограничения). Общая грамотность ответа ничего не доказывает — промпт мог не доехать молча.
3. **Стоимость выглядит правдоподобной.** Она правдоподобна всегда. Сверять надо не «похоже
   на правду», а арифметику: `costUsdTicks × 1e-10` против
   `((in−cached)·2 + cached·CACHED + out·6)/1e6` — **но только если запрос короче 200k**.
   `CACHED` берётся по МОДЕЛИ: `0.30` для grok-4.5, `0.50` для grok-4.6 (§4). Выше порога
   удваивать все три ставки (`4 / 0.60 / 12` и `4 / 1.00 / 12` соответственно), иначе честный
   биллинг прочитается как сломанный. Расхождение на СВОЁМ тарифе = сломанный биллинг, а не шум.

**Дальше по списку, в порядке убывания цены ошибки:**

| Что смотреть | Где | Красный флаг |
|---|---|---|
| Состав MCP | лог коннекта, событие `grok mcp ready · N tools` | в наборе есть что-то кроме наших; или `GrokMcpIsolationError` — значит изоляция не сработала |
| Доставка промпта | ответ воркера на вопрос про его роль | отвечает как «просто Grok» |
| Тулы реально исполняются | `tool_result` с именем `orchestra__*` | только `search_tool`/`use_tool` без результата |
| Ровно один `turn_end` на ход | лог событий | два `turn_end` подряд = двойной учёт стоимости |
| Бакет расходов | дашборд → карточка **SuperGrok** | расходы появились у Claude Max, а карточки SuperGrok нет |
| Контекст | `context_pct` в дашборде | знаменатель не 500 000 |
| Резюм после рестарта | `session_id` до и после | id сменился молча (должно быть предупреждение о потере истории) |
| Прерывание | `stop_reason=interrupted` по `interrupt()` | ход продолжает стримить после прерывания |

**Отдельно про квоту:** первый же реальный упор в лимит — это не поломка, а **ценные данные**.
Достать из лога `Grok raw error payload:` и передать в §7.1. Не чинить «по аналогии».

**Порог для решения о роли в пайплайне.** Прогон засчитывается, если одновременно:
состав MCP чистый, промпт доехал, тулы отработали, ровно один `turn_end` на ход, расходы
в бакете SuperGrok, стоимость сходится с арифметикой. Любой пункт мимо — это баг рантайма,
а не «модель так решила».

## Грабли Grok (перенесено из CLAUDE.md 2026-07-30 — файл упёрся в лимит Codex 32 768 байт)

**Grok** (full guide + unverified-registry: `docs/grok-field-guide.md`)
- Worker drops tasks with no error, `turn_end ok=False stop=interrupted` while `tool_result` already arrived → tool approval, not the model: option ids come from the offer (`allow-once`); an invented `allow` reads as "nothing selected" and cancels the turn

- Runtime prices with a cached tier must NOT go into shared `TOKEN_PRICES` → `_cost_cached_for()` reprices history with Claude's cache heuristic (+27.6% on a measured turn)
