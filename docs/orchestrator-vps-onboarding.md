# Как оркестратору переехать на VPS

Инструкция для оркестраторов проектов, которые хотят иметь свою рабочую копию на общем VPS.
Написана по следам реального переезда Orchestra-orchestrator (задача #131, 3 августа 2026) —
все грабли ниже настоящие, на каждой кто-то уже постоял.

**Сервер:** `158.220.127.161` (Contabo, Германия). Дашборд: `https://orchestra.seedon.ru`.

---

## 0. Сначала пойми, нужно ли тебе это

Переезд имеет смысл, если твоему проекту нужно, чтобы работа шла **без включённого ноутбука
Максима**: мониторинг, крон-задачи, долгие прогоны, ответы в TG круглосуточно.

Если проект — разработка, которую и так ведут при живом ноуте, переезд не даст ничего,
кроме второй копии, которая начнёт расходиться с первой. **Не переезжай по инерции.**

**Ресурсы общие и конечные.** На сервере 8 ГБ памяти, из них ~2.4 ГБ свободно, и там уже живут
бот Кеши (1.5 ГБ), второй мозг, прокси и Orchestra. Каждый новый оркестратор — минус от этого
остатка. Диска 127 ГБ свободно, он не проблема; проблема — память.

**Спроси Максима до начала.** Не «можно ли», а конкретно: нужен ли этому проекту VPS и
готов ли он отдать под него память. Ответ «делай» на общий вопрос ≠ разрешение на твой проект.

---

## 1. Что вообще значит «клонировать себя»

Важно понимать, чего НЕ произойдёт. Ты не переносишь свою память и не копируешь контекст.
Сессия на VPS — **новая сессия того же проекта**: тот же промпт, тот же код, тот же
`CLAUDE.md`, но пустая история диалога.

Всё, что ты знаешь и не записал в файлы, при переезде теряется. Поэтому:

> **Перед переездом запиши в `CLAUDE.md` и `docs/` всё, что твоя копия должна знать.**
> Файлы переезжают. Контекст — нет.

Это не недостаток процедуры, а её суть. Проверено на моём же переезде: старая сессия на VPS
была от 7 июля, и главной задачей оказалось не «перенести знания», а **заставить её забыть
устаревшие** (см. шаг 6).

## 2. Доступ

```bash
ssh root@158.220.127.161
```

Ключ у Максима уже настроен. Дальше — **сразу под юзера сервисов**:

```bash
su -s /bin/bash kesha
```

`su - kesha` **зависнет**, спросив пароль: у `kesha` пароля нет. Флаг `-s` от root пароля не
требует. Это первая грабля, на ней спотыкаются все.

### Золотое правило сервера

> Ставить пакеты — от root. Всё остальное — под `kesha`.

Клонирование, git, конфиги, логины, запуск — под тем юзером, под которым systemd запускает
сервис. Иначе получишь каталог с разъехавшимися владельцами, который **читается и запускается
нормально, а падает только на записи в `.git`, посреди деплоя**. У нас так умер `git fetch`
через месяц после того, как кто-то поработал от root: 3021 файл принадлежал root при
`User=kesha` в юните.

Проверка до git-операций в чужом каталоге:

```bash
find /path/to/project ! -user kesha | wc -l   # должно быть 0
```

## 3. Куда класть код

```
/home/kesha/projects/<имя-проекта>
```

Там уже лежит `dnd-game-master`. Не клади в `/opt` (там системные вещи: бот Кеши, второй мозг,
прокси) и не в корень домашней папки.

```bash
su -s /bin/bash kesha
cd /home/kesha/projects
git clone <твой-репозиторий> <имя-проекта>
```

**Оцени размер репозитория ДО клонирования** — по `.git`, а не по каталогу:

```bash
du -sh .git && git count-objects -vH
```

`du -sh` всей папки врёт в 10–20 раз: считает untracked-мусор, venv и артефакты. Реальный
пример: каталог 91 ГБ, история 7.5 МБ.

Нет удалёнки (`git remote -v` пусто) — переезжать нечему, сперва заведи репозиторий.

## 4. Зависимости

Python-проекты:

```bash
cd /home/kesha/projects/<имя>
uv sync
```

**Проверь свои extras.** `uv sync` без `--extra` **молча удалит** пакеты, которые ставились с
флагом. У нас так пропал RAG: в `.env` стояло `RAG_ENABLED=true`, а `sqlite-vec` больше не было —
конфиг обещал то, чего нет. Если у проекта есть опциональные группы:

```bash
uv sync --extra <группа>
```

Проверять фактом, а не отчётом установщика:

```bash
python -c "import sqlite_vec; print('OK', sqlite_vec.__version__)"
```

Node-проекты — глобальные пакеты от root (`npm install -g ...`), локальные под `kesha`.

## 5. Окружение и прокси

**Прокси на VPS не нужен.** Сервер в Германии, `api.anthropic.com` и `api.openai.com`
отвечают напрямую. Все правила про `HTTPS_PROXY=127.0.0.1:1234x` и Hiddify относятся ТОЛЬКО
к ноутбуку Максима — этих туннелей здесь физически нет.

Если копируешь `.env` с ноутбука — **закомментируй строки прокси**, иначе процесс будет
стучаться в несуществующий локальный порт и падать по таймауту:

```bash
# HTTPS_PROXY=http://127.0.0.1:12340
# HTTP_PROXY=http://127.0.0.1:12340
```

**Порты.** Занятые смотри через `ss -tlnp`, свой выбирай свободный и сразу записывай — иначе
следующий переехавший займёт тот же. Реестр `~/ports.md` живёт на ноутбуке, на VPS его нет:
свой порт укажи в `CLAUDE.md` проекта.

**Секреты.** `.env` не коммитить, права `600`, владелец `kesha`. Токены с ноутбука не
дублировать без нужды — если сервису нужен свой, попроси у Максима отдельный.

## 6. Сессия оркестратора на VPS

> **Сначала прочитай этот врез — он экономит весь остальной раздел.**
>
> Есть готовый скрипт `scripts/migrate_agent.py` (в репозитории Orchestra). Он делает UPSERT
> строки сессии и вдобавок переносит транскрипт, `logs`/`inbox`/`subagents`, worktrees воркеров
> и scope-файлы. **Работает и когда сессии на целевом хосте нет вовсе** — тогда просто создаёт.
>
> Первая версия этой инструкции про него умалчивала (я при переезде #131 делал руками и не знал,
> что он существует с 6 июля) — из-за чего два оркестратора полезли править `sqlite` вручную.
> **Ручной путь ниже — только для случая «сессия уже есть и она протухла».** Для переезда с
> ноутбука бери скрипт.

### 6а. Штатный путь — `migrate_agent.py`

```bash
uv run python scripts/migrate_agent.py --name <ТВОЁ-ИМЯ> \
  --from maxim@localhost --to root@158.220.127.161 \
  --from-orchestra /mnt/data/Projects/Python/orchestra --to-orchestra /home/kesha/orchestra \
  --from-scope <путь-на-ноуте> --to-scope /home/kesha/projects/<имя> --dry-run
```

Убери `--dry-run`, когда вывод устроит.

**Оркестратор не может мигрировать сам себя.** Гейт `assert_idle` (строка 144) считает `running`
всех агентов твоей стороны, включая тебя: пока ты отвечаешь — ты `running`, а закончив ход,
запустить скрипт уже некому. Запускает кто-то снаружи — юзер руками или твой воркер (он
отдельный процесс, к тому моменту ты уже `idle`). Гейт проверяет только сторону `--from`;
чужие агенты на VPS в него не попадают.

**Целевой каталог должен быть нормальным git-клоном с `origin`.** Скрипт делает git-операции
(`migrate_git`); на свалке от `rsync` с пустым `.git` он упадёт или намусорит. Сперва клон,
потом миграция.

**Рестарт нужен, но не тобой и не сразу.** Скрипт пишет в БД и в конце сам печатает: «restart
Orchestra — `auto_resume_all` will replay transcripts». Строка появится сразу, сессия поднимется
при ближайшем рестарте. `systemctl restart orchestra` рвёт активные ходы **всех** агентов на
сервере — не лови окно сам, доложи `Orchestra-orchestrator`, он совместит с плановым.

После успеха — **погаси исходную сессию** (`kill_worker`/архив). Один `session_id`, живой на двух
хостах, — это расхождение, которое потом никто не распутает.

### 6б. Ручной путь — только для протухшей сессии

Проверь, нет ли твоей сессии там уже:

```bash
python3 -c "
import sqlite3
c = sqlite3.connect('/home/kesha/orchestra/data/orchestra.db')
for r in c.execute(\"select name, model, substr(session_id,1,8), status from sessions where status!='archived'\"):
    print(r)
"
```

Заметь: колонки `turns` в схеме нет, а `sqlite3` как команды на сервере не установлено —
только через Python.

### Если сессия есть и она старая

Это опаснее пустой: она не «не знает нового», она **помнит устаревшее** и будет действовать
по нему уверенно. Лечится сбросом истории, **не компактом**:

```bash
sudo systemctl stop orchestra     # обязательно ДО правки

python3 -c "
import sqlite3
c = sqlite3.connect('/home/kesha/orchestra/data/orchestra.db')
c.execute(\"update sessions set session_id='' where name='ТВОЁ-ИМЯ'\")
c.execute(\"update sessions set model='claude-opus-5[1m]' where name='ТВОЁ-ИМЯ'\")
c.commit()
print('rows:', c.total_changes)
"

sudo systemctl start orchestra
```

Три вещи, каждая из которых уже кого-то укусила:

1. **`WHERE name='ТВОЁ-ИМЯ'`, никаких масок вроде `model LIKE 'claude-opus-4%'`** — заденешь
   чужие сессии. На живом сервере рядом с тобой работают другие.
2. **Только при остановленном сервисе.** Живой сервер перезаписывает поля сессии из памяти,
   и твой `UPDATE` молча откатится. После рестарта — перепроверь `SELECT`.
3. **Не `compact_worker`.** Компакт просит сессию законспектировать саму себя: устаревшие
   убеждения переезжают в конспект, но уже без исходника для перепроверки. Становится хуже,
   а выглядит как решение.

**Модель пинить с `[1m]`.** Голый `claude-opus-5` даёт 200k контекста вместо 1M — теряешь
800k молча.

### Если сессии нет вовсе, а скрипт применить нельзя

Сюда попадаешь, только если у проекта нечего переносить (нет истории на ноуте) и нужна чистая
сессия. **Руками `INSERT` в `sqlite` — нельзя**, по трём причинам:

1. **Автосоздание не сработает.** `bootstrap.py:100 _ensure_orchestrator()` создаёт оркестратора
   только если в базе нет **ни одного** (`has_orch` → skip). На VPS он уже есть, так что
   бутстрап пройдёт мимо тебя, сколько ни рестартуй.
2. **Живой сервер держит сессии в памяти** (`manager.py:1447 auto_resume_all`). Строка, вставленная
   в живую базу, серверу неизвестна, в дашборде не появится, а при следующей записи из памяти
   может быть затёрта — тот же механизм, из-за которого `UPDATE` при живом сервисе откатывается.
3. **Полей больше, чем кажется.** `db.py:618 save_session()` проставляет около двадцати умолчаний
   (`context_pct`, `total_turns`, `template_hash`, `cost_usd_cached`, `backend_type`, `parent_id`,
   `pipeline`, `profile`…). Список из семи «очевидных» колонок пройдёт `INSERT` без ошибки и
   упадёт позже, в чужом месте и без связи с причиной.

Правильно — вызвать тот же код, что создавал всех остальных:

```bash
su -s /bin/bash kesha
cd /home/kesha/orchestra
uv run python - <<'PYEOF'
import uuid
from datetime import datetime, timezone
from app.db import get_all_sessions, save_session
from app.models import resolve_model, backend_for_model

NAME  = "<проект>-orchestrator"
SCOPE = "/home/kesha/projects/<проект>"
MODEL = resolve_model("claude-opus-5[1m]")

assert not any(s["name"] == NAME for s in get_all_sessions()), "already exists"

save_session({
    "id": str(uuid.uuid4()), "name": NAME, "scope": SCOPE, "cwd": SCOPE,
    "model": MODEL, "system_prompt": "", "status": "idle", "session_id": None,
    "cost_usd": 0, "worktree_path": "", "branch": "",
    "is_orchestrator": 1, "role": "orchestrator", "color": "",
    "created_at": datetime.now(timezone.utc).isoformat(), "finished_at": None,
    "backend_type": backend_for_model(MODEL),
})
print("created:", NAME, MODEL)
PYEOF
```

Поля скопированы 1:1 из `bootstrap.py:_ensure_orchestrator` — это тот же код, что создавал
существующих оркестраторов.

**Две засады среды** (обе словлены на живом переезде kesha-tg-bot):

- **`uv` не в `PATH` под `su -s /bin/bash kesha`** → `uv: command not found`. Лежит в
  `/home/kesha/.local/bin/uv`. Либо полный путь, либо просто
  `/home/kesha/orchestra/.venv/bin/python` — результат тот же.
- **Heredoc через `ssh` не доедет** → `ModuleNotFoundError: No module named 'app'`: скрипт
  исполняется не из каталога Orchestra. Клади файл прямо в `/home/kesha/orchestra/`, запускай
  оттуда и сразу удаляй. Из `/tmp` не работает — пакет `app` не находится.

**`system_prompt=""` — не копируй чужой.** Полный промпт роли рантайм собирает сам из поля
`role` (`manager.py:492 ROLE_SYSTEM_PROMPT`), а `system_prompt` из БД лишь **добавляется сверху**
как оверлей. Скопируешь чужой — получишь двойную личность.

**`resolve_model()` и `backend_for_model()` вызывать, а не писать строкой** — иначе модель и
рантайм разъедутся, а `[1m]` пинится именно внутри `resolve_model`.

Сервис при этом останавливать **не нужно**: `save_session` — штатная запись, сессия подхватится
при ближайшем рестарте.

> **Общий признак неверного пути:** если правка требует останавливать общий сервис ради одной
> строки — почти наверняка ты выбрал не тот путь. Перед любым `systemctl stop orchestra`
> проверь, кого порвёшь: `select name, status from sessions where status='running'`.

## 7. Systemd (если проекту нужен постоянный сервис)

Юнит-файлы — в `/etc/systemd/system/`, дроп-ины — отдельными файлами, чтобы не затирать чужое:

```bash
mkdir -p /etc/systemd/system/<юнит>.service.d/
# писать файлом, НЕ systemctl edit — он откроет редактор в ssh и подвесит сессию
```

Обязательно `User=kesha` и `EnvironmentFile=` с путём к `.env` — не хардкодь секреты в юните.

**Приоритет памяти.** Сервер общий, памяти мало. Расставлено осознанно:

| Сервис | `OOMScoreAdjust` | Логика |
|---|---|---|
| tinyproxy | −900 | умрёт последним, через него ходит трафик |
| telegram-bot-api | −700 | инфраструктура |
| kesha-bot-vps | −500 | боевой бот |
| orchestra | **800** | умрёт первой, переживаемо |

Новому сервису ставь положительное значение (умирает раньше инфраструктуры) и лимиты памяти:

```ini
[Service]
OOMScoreAdjust=800
MemoryHigh=2G
MemoryMax=3G
```

`MemoryHigh`/`MemoryMax` применяются **на лету**, без рестарта. `OOMScoreAdjust` — только при
рестарте процесса.

**Проверять факт, а не флаг:**

```bash
cat /proc/$(systemctl show -p MainPID --value <юнит>)/oom_score_adj
```

`systemctl show -p OOMScoreAdjust` печатает `infinity` всегда — при успехе и при провале
одинаково. Проверка, дающая один и тот же вывод в обоих случаях, проверкой не является.

## 8. Ветки и синхронизация

**`main` ведёт ноутбук.** На VPS — только ветки задач. Синхронизация через GitHub.

Отсюда неочевидное следствие, на котором мой переезд встал: **VPS тянет из `origin`, а не с
ноутбука**. Если локальный `main` не запушен, на сервер приедет вчерашний код, и твоя «свежая
копия» будет без сегодняшнего дня.

Перед `git pull` на VPS убедись, что пушить нечего:

```bash
# на ноутбуке
git rev-list --count origin/main..main    # должно быть 0
```

Не ноль — сперва пуш, потом переезд.

## 9. Проверки после запуска

Не «сервис создался», а «работает и делает своё». Каждая проверка должна давать **разный
вывод при успехе и провале**:

```bash
systemctl is-active <юнит>                     # active
journalctl -u <юнит> --since "5 min ago" | grep -iE "traceback|error|critical"   # пусто
cat /proc/$(systemctl show -p MainPID --value <юнит>)/oom_score_adj              # твоё число
curl -s -o /dev/null -w "%{http_code}\n" https://<твой-домен>/                   # 200/302
git rev-parse --short HEAD                     # ожидаемый коммит
```

**Главная проверка для оркестратора — задать своей копии вопрос, на который невозможно
ответить старыми знаниями.** Не «ты живой?», а что-то из свежих правил или сегодняшнего
состояния сервера. Если ответил по делу — переезд состоялся. Если общими словами — сессия
не перечитала контекст.

## 10. Точка отката

Снимай **до** первого деструктивного шага, не после:

```bash
cp data/<база>.db ~/backup-<задача>-<проект>.db
cp data/<база>.db-wal ~/backup-<задача>-<проект>.db-wal   # WAL отдельно, в нём свежие записи
cp .env ~/backup-<задача>.env
git rev-parse HEAD > ~/backup-<задача>-commit.txt
find <каталог> ! -user kesha -printf '%u %g %p\n' > ~/backup-<задача>-owners.txt
```

Последняя строка — если собираешься делать `chown -R`. Без снимка владельцев откат
пофайлово невозможен, только наугад.

## 11. Порядок работы

Переезд — не один заход, а последовательность с проверкой на каждом шаге:

1. Согласовать с Максимом (память, необходимость)
2. Запушить `main` на ноутбуке
3. Клонировать под `kesha`, поставить зависимости, проверить extras
4. `.env` без прокси, порт свободный
5. Systemd с `User=kesha`, приоритетом памяти и лимитами
6. Сессия: сброс истории при остановленном сервисе, модель с `[1m]`
7. Проверки фактами + контрольный вопрос копии
8. Записать в `CLAUDE.md` проекта: что теперь живёт на VPS, порт, юнит, что рестарт рвёт
   активные ходы агентов

**Каждый деструктивный шаг** (`systemctl stop`, `UPDATE`, `chown -R`, `git reset`) — сперва
скажи Максиму, что и зачем, и дождись подтверждения. Он сегодня разрешил конкретный переезд,
а не любые операции на общем сервере.

## 12. Грабли одним списком

- `su - kesha` виснет без пароля → `su -s /bin/bash kesha`
- Работа от root в каталоге с `User=kesha` → `git fetch` умрёт через месяц, а не сейчас
- `du -sh` каталога вместо `.git` → завышение в 10–20 раз
- `uv sync` без `--extra` → молча сносит пакеты, конфиг продолжает обещать их наличие
- `.env` с ноутбука → прокси в несуществующий порт
- `UPDATE` по маске модели → зацепишь чужие сессии
- `UPDATE` при живом сервисе → молча откатится
- `compact_worker` вместо сброса `session_id` → устаревшие убеждения консервируются
- Модель без `[1m]` → 200k вместо 1M контекста
- `systemctl show -p OOMScoreAdjust` → `infinity` всегда, ground truth в `/proc`
- `systemctl edit` в ssh → откроет редактор и подвесит сессию
- Незапушенный `main` → на VPS приедет вчерашний код
- Рестарт Orchestra → рвёт активные ходы всех агентов, включая чужих
- Ручной `INSERT` сессии → `bootstrap` пройдёт мимо, живой сервер затрёт, полей не хватит
- Скопированный чужой `system_prompt` → двойная личность (роль собирается рантаймом, это оверлей)
- `uv` не в `PATH` под `su -s /bin/bash kesha` → `/home/kesha/orchestra/.venv/bin/python`
- Heredoc через `ssh` из `/tmp` → `No module named 'app'`, запускать из каталога Orchestra
- Попытка мигрировать себя скриптом → `assert_idle` считает тебя `running`, нужен кто-то снаружи
- Целевой каталог — свалка от `rsync` с пустым `.git` → `migrate_git` упадёт, сперва чистый клон
