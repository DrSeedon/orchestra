# review269-opus — личная память

## Ревью правок, откладывающих работу в очередь

- **Очередь, которую разгребает событие жизненного цикла, проверяется грепом ВСЕХ мест, где
  снимается условие постановки в очередь, а не только там, где это событие наступает.** В #269
  сообщения парковались при закрытом `mutating_admission` и разгребались только в `lifespan`
  при старте процесса; при этом приём открывался обратно ещё в ТРЁХ местах
  (`app/routes/system.py:1744`, `:1767`, `:1785`), где процесс продолжал жить, — и очередь
  висела до следующего настоящего рестарта. Порядок проверки: `grep -rn "<drain_fn>" app/` →
  один вызывающий → `grep -rn "<функция, снимающая условие>"` → сравнить множества.

## Как гонять пробы по чужой ветке в этом репозитории

- Снимок: `git archive <sha> | tar -x -C /tmp/<dir>/snap` (ветку не чекаутить), прогон —
  `cd /tmp/<dir>/snap && PYTHONPATH=/tmp/<dir>/snap /home/kesha/orchestra/.venv/bin/python -m pytest ... -p no:cacheprovider`.
  Venv основного репозитория подходит, свой не нужен.
- Свои пробы класть в `docs/tasks/<id>/`, не в `tests/`: `norecursedirs` в `pyproject.toml`
  включает `docs`, поэтому сьют их не подберёт, а описывают они дефекты, а не контракт.
- `git merge-base main <branch>` у долгоживущих `adhoc-*` веток уводит на сотни файлов назад —
  для предметного диффа брать `git diff <первый_коммит>~1 <последний_коммит>`.
- Живую БД читать `sqlite3.connect('file:...?mode=ro', uri=True)` — этого хватает для проверки
  `sqlite_master`, копия через `backup()` нужна только когда важна свежесть строк.
- Греп по `logs` за строкой из кода ловит собственные tool-логи агентов (проверка попадает в
  измеряемое множество). Отсекать по `type='system'` и, если там ноль, честно писать «не мерил».
