# fix-silent-errors — личная память

## Мутация: целься по УНИКАЛЬНОМУ якорю, а не по строке кода
Замер (#167): мутировал `_log` заменой по тексту — попал в близнеца
`_submit_db_write`, который идёт в файле ВЫШЕ и содержит те же строки.
Мутант не применился к нужной функции, тест остался зелёным, и это выглядело
как «тест не ловит дефект». Маркер `grep -c` показал `1` и НЕ спас: строка
неспецифична, она есть в обоих методах.
- Перед мутацией: `grep -c "<строка>"` — если >1, строка НЕ годится как якорь.
- Целься по уникальному фрагменту (комментарий, соседняя строка) или по номеру
  строки через `lines[N]` с `assert` на содержимое.
- Питоновский `.replace(a, b, 1)` без `assert s.count(a)==1` — это лотерея.

## Прежде чем чинить «по списку из задачи» — отрендерь строку
Замер (#167): в задаче было «в трёх местах печатать `type(e).__name__`». В
третьем месте класс УЖЕ печатался, а дефектом был разделитель `": "` при пустом
`str(e)`. Исполнил бы буквально — починил бы 2 из 3 и отчитался за 3.
Один `uv run python -c` с дословным рендером текущего кода закрыл вопрос за
минуту и дал готовую таблицу ДО/ПОСЛЕ для приёмки.

## Ищешь «все копии» — греп по имени переменной обязателен
Замер (#167): первый греп нашёл 4 копии правила, я закоммитил. Самопроверка
после коммита нашла ещё 11: паттерн покрывал `str(e)`/`str(exc)`/`str(error)`,
но не `str(task_error)`, `str(persist_error)`, `str(quarantine_error)`.
→ Ищи по ФОРМЕ выражения (`or type(`), а не по именам переменных.

## Локальное
- Запуск скретч-скрипта: файл класть В ВОРКТРИ, не в `/tmp` — `sys.path[0]` это
  каталог скрипта, и `import app` из `/tmp` падает даже под `uv run` из корня.
- Своя БД для теста: `ORCHESTRA_DB_PATH=/mnt/data/tmp<id>/x.db` (не `/tmp` —
  там tmpfs = чужая RAM).
- Живую БД смотреть только по копии: `cp data/orchestra.db /tmp/x.db` — сервис
  работает, юзер на нём сидит.
