# bench-grok — личная память

## Доступ к ноутбуку Максима без `run_on_laptop`

Скилл `laptop-access` предписывает `mcp__kesha__run_on_laptop`, но **этого MCP у воркеров
Orchestra нет** — он у бота Кеши. Прямой путь через тот же обратный туннель:

```bash
ssh -p 2222 -i ~/.ssh/tunnel_laptop -o BatchMode=yes maxim@127.0.0.1 '<команда>'
```

Юзер именно `maxim` (не `kesha` — под ним отказ по ключу), хост `maxim-911aird`, ключ
`~/.ssh/tunnel_laptop` (комментарий `kesha-bot-to-laptop`). Туннель держит systemd-юнит
`ssh-tunnel-vps` со стороны ноута; порт слушает `127.0.0.1:2222` на VPS. Ноут спит →
туннель мёртв, так и говорить, а не гадать.
Ограничений на метасимволы, в отличие от `run_on_laptop`, тут нет — можно пайпы и heredoc.

Проверять наличие туннеля до попытки: `ss -ltnp | grep :2222`.

## Наш веб-стек и X/Twitter (замер 12.08.2026)

- `WebFetch` по `x.com/<user>/status/<id>` → **HTTP 402 Payment Required**. Пост по ссылке не
  прочитать вообще. Это самый быстрый способ доказать пробел — одна команда.
- `site:x.com` в `WebSearch` → 0 результатов с домена.
- Пермалинк X изредка всплывает в обычной выдаче сам, если пост попал в общий индекс.
  Поэтому «мы не достаём X» в абсолютной форме — неверно, проверял.

## Урок методики, за который поймало ревью

Мерил «умеет ли инструмент» двумя открытыми discovery-запросами, получил ноль и объявил
неспособность. Ноль на открытом запросе мерит **формулировку**, а не индекс. Спасает
положительный контроль: взять объект, который ТОЧНО существует, и попробовать достать его
адресно. У меня контр-пример нашёлся в собственном транскрипте — пермалинк, который я сам же
до этого получил в выдаче.

Перед «инструмент не умеет X» — адресный прогон по заведомо существующему объекту.

## Анонс модели: сверять не только то, что в пересказе, но и то, чего в нём нет (13.08.2026)

Пересказ анонса Grok 4.6 был честен построчно — три утверждения из четырёх подтвердились
первоисточником дословно. Врал он **умолчаниями**, и оба умолчания били по нам:

- «Обошёл Sol в трёх бенчах» — верно, но проигрышные строки не названы вовсе, а худшая из них
  (Terminal-Bench 26% против 34.6%) — ближайший прокси к тому, чем занят наш воркер.
- «Цена та же, $2/$6» — заголовок совпадает в точности, а ставка **кэша** выросла $0.30 → $0.50.
  У нас `cache_read` — 97.9% prompt-токенов, то есть подорожал весь счёт при неизменном
  заголовке.

Практика: сверять анонс по трём осям, а не по одной — (1) подтверждается ли сказанное,
(2) какие строки той же таблицы **пропущены**, (3) какой компонент цены совпадает с профилем
**нашего** расхода, а не с заголовком. Заголовочная цена описывает не наш режим ни разу.

Сопутствующее: считая долю ходов ≥200k, чуть не сложил `input + cache_read` у codex, где
`cache_read` уже входит в `input` (604/604 строк). Правило из `CLAUDE.md` про одноимённые
счётчики срабатывает и на своих же данных, а не только при сравнении провайдеров.

## Скрипт из `docs/tasks/` может импортировать `app` не из своего worktree

При запуске `python docs/tasks/N/probe.py` первым в `sys.path` становится каталог скрипта, а
не корень worktree. На этой машине editable-install подхватил `app` из main: production-arm
telemetry probe внезапно увидел старый `_build_env` и честно покраснел на чужом коде.

Экспериментальному скрипту, который импортирует проект, сначала вычислять repo root из
`Path(__file__)` и вставлять его в `sys.path` **до** `from app...`; затем positive/negative
плечи обязаны пройти из одного запуска. `cwd` команды сам по себе Python-import не чинит.

## Независимая проверка X permalink без API-ключа

`publish.twitter.com/oembed?omit_script=1&url=<x-url>` различает заведомо существующий пост
(HTTP 200 + canonical URL/author/HTML) и несуществующий `id=1` (HTTP 404). Старый
`cdn.syndication.twimg.com/tweet-result` непригоден: обоим объектам отдаёт `HTTP 200 {}`.
Для long-form oEmbed режет body многоточием, поэтому им проверять identity и публиковать только
возвращённый fragment; полный текст модели он не подтверждает.

## Persistent bg run и внешний расход

`BgJobManager.restore_from_db()` переисполняет command активного `run` после рестарта. Если
command тратит внешний пул, одного `success_file` недостаточно: до spawn нужен атомарный
`O_CREAT|O_EXCL` marker. Готовый валидный artifact можно переиспользовать; marker без artifact
означает `outcome unknown` и обязан запрещать повторный расход.
