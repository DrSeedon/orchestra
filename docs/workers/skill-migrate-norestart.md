# skill-migrate-norestart — личная память

## Проверка промпта сессии — только из БД, не из API

`GET /api/sessions/{name}` режет `system_prompt` до 500 символов (`to_dict`). Проверка
«подхватилась ли личная память / вшилось ли X в промпт» по ответу API даёт ОДИНАКОВЫЙ
результат при успехе и провале — то есть не является проверкой. Один раз уже увело в вывод
«память не подхватилась», который оказался ложным.

Ground truth:
```bash
sqlite3 data/orchestra.db "SELECT system_prompt FROM sessions WHERE name='<имя>'" > /tmp/p.txt
grep -c "<маркер>" /tmp/p.txt
```

Заодно: колонки `mcp_servers` в таблице `sessions` НЕТ — есть только `mcp_servers_custom`,
эффективный конфиг собирается в рантайме (`_make_mcp_config`). `SELECT mcp_servers` падает с
`no such column`, и это легко принять за «MCP не переносится».

## Приёмка документации = прогнать записанную в ней команду дословно

Правил скилл/инструкцию с командами — не сдавай, пока не выполнил ОТТУДА скопированное тело
запроса на живой системе. Так поймал у себя за один прогон три вещи разом: тело валидно,
роль выставляется, `tg_topic` включается сам (то есть утверждение в тексте верно).
Отдельно этим же способом ловятся обрывки: сниппет, начинающийся с `-d '{...}'` без `curl`,
выглядит в редакторе нормально и не работает у читателя.

## Заведение сессии Orchestra без рестарта

`POST /api/sessions` идёт ЧЕРЕЗ процесс (`manager.create_session`), поэтому сессия сразу в
памяти и рестарт не нужен. Ручной `INSERT` в sqlite — мимо процесса, живой сервер о строке не
знает. Различающая проверка «живая или мёртвая»: отправить сообщение и дождаться ответа;
код `201` сам по себе не доказывает ничего.

Порядок при заведении: файлы (`CLAUDE.md`, `docs/workers/<имя>.md`) должны лежать на диске ДО
вызова — память вшивается в промпт в момент создания и по совпадению ИМЕНИ, задним числом не
подхватится.

## Скретч на этой машине

`/tmp` — tmpfs (= RAM других агентов). Скретч-каталоги класть на `/mnt/data/...`, убирать
через `gio trash` (`trash` в PATH нет, `rm -rf` запрещён).
