# fix-bugsmd — личная память

## Задачу с симптомом «X сломан» начинать с проверки, не сломан ли X ещё

На #114 симптом был описан подробно и убедительно («сработало ПЯТЬ раз за сегодня»), но фикс
уже лежал в `main` (`4b7814b`), а описание симптома протухло. Первым делом —
`git log -S"<имя функции>" main -- <файл>` и чтение ТЕКУЩЕГО кода, только потом планирование
правки. Стоило бы полдня переписывания уже смерженной фичи.

Заодно: `docs/tasks/<id>/` мог остаться от прошлого захода (там лежали `research.md` +
`plan.md` на 350 строк от упавшего по квоте full-cycle воркера). Проверять этот каталог до
старта — там половина ответа.

## `uv run pytest` в этом репо переписывает `uv.lock`

После прогона `git status` показывает ` M uv.lock` (+809/−892) — это мой собственный тул
испачкал дерево, а не чужая правка. Перед DONE: `git checkout -- uv.lock`. Иначе сам создашь
ровно ту грязь, из-за которой падают мержи.

## Локальный инбокс баг-репортов — не в `/var/lib/orchestra`

Локальный systemd-юнит Orchestra не содержит `StateDirectory` (она только в
`deploy/orchestra.service.template`, а это VPS-юнит для `/opt/orchestra`). Поэтому
`_bug_state_root()` уходит в fallback: **`~/.local/state/orchestra/bug-inbox/`**.
Искать репорты там.
