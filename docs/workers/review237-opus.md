# review237-opus — личная память

## Как ревьюить чужую ветку, не трогая ни её, ни свою

`git checkout <ветка>` не сработает: ветка занята worktree автора (`fatal: already used by
worktree at ...`). Чекать код из своей ветки нельзя — она отрезана от его правок.

Рабочий приём (проверено на #237):
```bash
D=/tmp/rev<id>-$$ && mkdir -p $D
git archive <ветка> | tar -x -C $D          # снимок БЕЗ .git — коммитить туда нечем
cd $D && /home/kesha/orchestra/.venv/bin/python -m pytest tests/<файл> -q
```
Венв берётся репозиторный, `app` импортируется из cwd. Для голых скриптов (не pytest) нужен
`PYTHONPATH=$D`. Мутации и пробы делать ТАМ: чужое дерево цело, моя ветка чистая, а `rm -rf`
не нужен (и запрещён).

## Что реально ловит дефекты в таких ревью

Не чтение диффа, а проба, которая строит **настоящий объект** вместо двойника из оракула.
Три блокера в #237 нашлись так: `CodexBackend` на настоящих `os.pipe()`, настоящий
`SessionManager`, настоящий uvloop + `create_subprocess_exec`. Каждый оракул, который был
зелен на этом же месте, оказался зелен из-за двойника, чьё состояние прод не производит
(тест сам выставлял флаг, который реализация снимает).

Второй по силе приём — **мутация ради проверки ОРАКУЛА, а не кода**: отключить подозрительную
строку и посмотреть, заметит ли сьют. «15 оракулов зелены под мутацией» — это готовая улика в
отчёт, сильнее любого рассуждения о покрытии.

## Проверка констант-таймаутов

Когда правка добавляет НОВОЕ ожидание под уже существующий сторож — сравнить бюджеты числами и
прочитать КОММЕНТАРИЙ у старой константы. В #237 сторож (120 с) обосновывался дренажом HTTP
(90 с), а T3 подсунул под него ожидание 900 с; комментарий остался прежним и сам выдал разрыв.
