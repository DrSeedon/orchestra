# subscription-decision — личная память

## Квоты и окна (проверял сам, #190)

- **Недельное окно Anthropic — КАЛЕНДАРНОЕ, не скользящее.** `seven_day_resets_at` стоит
  фиксированной точкой (вторник 07:00 UTC) всю неделю и прыгает ровно на 7 суток:
  `28.07 07:00 → 04.08 07:00 → 11.08 07:00`. Расход из окна не «вытекает» по мере
  старения → «сколько ходов выбирают пул» считается честно.
  **У Codex окно наоборот скользящее** — его `resets_at` ползёт. Не переносить поведение
  одного провайдера на другого: на этом Codex-ревью построило ложную находку про мой пул.
- **`codex_review` не попадает в `turn_usage` вообще.** Это bg job с `codex exec`
  (`app/mcp_stdio.py:2035`), а не ход агента. Токены ревью живут ТОЛЬКО в
  `/tmp/codex_review_<worker>_<slug>.jsonl`, событие `type: "turn.completed"` → `usage`.
  Файл перетирается `rm -f` при каждом новом запуске того же slug → выборка тает,
  и цифра, посчитанная по ним, дрейфует между прогонами. Нужна стабильная — фиксировать
  сразу, а не пересчитывать позже.
- Абсолютных долларов у Anthropic нет: `limit_dollars`/`used_dollars`/`remaining_dollars`
  = `null` на подписке Max. Только целые проценты. Всё абсолютное — через `turn_usage`,
  который начинается 03.08.2026 и раньше не существует.

## Метод, который сработал

- Возражение «границы окна выбраны удобно» закрывается не чувствительностью к сдвигу
  (сужение окна механически уменьшает счёт), а **обогащением**: доля события внутри окна
  против доли времени окна. У меня 24% времени вмещали 76% работы = ×3.1 — это возражение
  снимает, а сдвиг границ не снимал.
- Когда меряешь спрос в периоде, где система упиралась в потолок, спрос **занижен**
  (цензура сверху). Считать темп по НЕзаблокированным часам — но тогда нельзя добавлять
  сверху работу, ушедшую на другой рантайм внутри блокировки: это двойной счёт.
