# back — память воркера

- **Проверка, дающая один и тот же вывод в разных режимах, — не проверка.** Ловил трижды:
  стенд с незакавыченным `|` оставил живой uvicorn, и залипший инстанс отвечал за следующие
  режимы; grep-проба по меткам не находила их нигде. Лечение: в каждом режиме держать строку,
  которая ОБЯЗАНА отличаться, и перед стартом убеждаться, что порт свободен, а процесс жив.
- **Тест, приколоченный к ДЕТАЛИ реализации, ломается от смены формы, а не поведения.**
  За день — четыре случая: имя seam (`is_auth_enabled`→`is_owner_mode`, 5 моков перестали
  перехватывать и стали читать живой env), дословный argv (`show-ref` + `--quiet` сбил счётчик
  вызовов, и инжект сбоя молча не сработал), текст заглушки, склейка сообщения об ошибке.
  Прежде чем править матчер — распечатай РЕАЛЬНУЮ последовательность вызовов (временная копия
  теста + print), иначе не отличишь «ослабил проверку» от «сдвинулся номер».
- **Мутационная проверка закоммиченного фикса — только `git show <commit>^:<file> > <file>`.**
  `git stash push <file>` на чистом дереве не сохраняет ничего, прогон идёт по фикшенному коду
  и даёт ложное «тесты ловят баг» (7/7 passed вместо настоящих 3 failed), а следующий
  `stash pop` целится в ЧУЖОЙ стэш. Убедись `grep -c`, что откат произошёл, и что вернул.
  И проверь, что тест ВООБЩЕ различает версии: если фикс — «ждать дольше / делать больше
  попыток», заглушка обязана требовать БОЛЬШЕ попыток, чем мог старый код. Мой тест на
  ожидание мержа зеленел на до-фиксовой версии, потому что отдавал готовность со 2-го
  опроса, а старый бюджет допускал три.
  **Правка ещё НЕ закоммичена — этот приём её УНИЧТОЖАЕТ:** `git show HEAD:<file> > <file>`
  затирает рабочую версию, а `git checkout <file>` после прогона возвращает HEAD, а не твою
  строку. Потерял правку ровно так. Для некоммитнутого: `cp <file> /tmp/keep` перед откатом.

- **`py-spy --gil` систематически ЗАНИЖАЕТ всё, что блокирует loop через SQLite:** модуль
  `sqlite3` отпускает GIL на времени выполнения запроса. В #21 GIL-профиль отдал `get_all_sessions`
  21.7 % и не показал `get_last_turn_map` вовсе, а обычный wall-clock (`py-spy record` без `--gil`)
  дал ей **55 % всего профиля** — она и была расходом. Вопрос «кто держит интерпретатор» и вопрос
  «кто держит event loop» — РАЗНЫЕ, и второй меряется wall-clock'ом. Подтверждать вторым прибором:
  прямой тайминг запроса на read-only копии живой БД (`file:...?mode=ro`, `uri=True`).
- **`git show-ref --verify` БЕЗ `--quiet` даёт exit 128 и на отсутствующую ветку** — ровно как
  на `dubious ownership`, то есть по `returncode` «нет ветки» и «git отказал» неразличимы.
  `--quiet` делает `exit 1` значащим. Эталон в `app/workspace.py` — `_inspect_branch_ref`.
- **Окружение агента на этом VPS НЕ чистое:** юнит подаёт `EnvironmentFile=.env`, поэтому
  `DASHBOARD_USER`, `OWNER_MODE`, `INTERNAL_TOKEN` уже лежат в `os.environ`. «В чекауте нет
  `.env`» этого не отменяет — проверял чистым клоном main, 401 остался. Смотри `env | grep`.
- **`app/db.py:DB_PATH` вычисляется НА ИМПОРТЕ.** Выставить `ORCHESTRA_DB_PATH` после импорта
  `app.db` (в общем прогоне он импортирован рано) = молча работать по БОЕВОЙ базе. Из-за этого
  отказался поднимать тестовый инстанс дашборда в фикстуре.
- **`api()` во фронте имеет ОБЩИЙ таймаут 5 с** и бросает на `!resp.ok`. Тяжёлым ответам нужен
  свой `signal`: `/api/usage/history?hours=8760` — 4.29 МБ и 1–2 с только генерации, впритык.
  Падение пряталось за `catch {}` и выглядело вечным «Collecting data...». Чинишь «пустую
  панель» — измерь РАЗМЕР и ВРЕМЯ ответа, а не только содержимое.
- **Мои Bash-процессы живут в cgroup `system.slice/orchestra.service`** — вместе с живым
  сервером и всеми 17 процессами, под `MemoryHigh=2G`. «Безобидный бенчмарк в /tmp» отъедает
  память у прода и сам вызывает стойки, которые меряет. Перед тяжёлым прогоном: `cat
  /proc/self/cgroup`, снять `memory.events` до и после, тяжёлое — отменяемой bg-джобой.
- **Прежде чем винить GIL, аллокатор или ONNX — прочитай лимиты cgroup.** `pgscan_kswapd=0`
  при огромном `pgscan_direct` = весь реклейм ПРЯМОЙ, то есть процесс синхронно встаёт чистить
  память; это и есть стойки. `memory.events` считает `high` отдельно от `max`, поэтому
  `oom_kill=0` НЕ значит «с памятью нормально»: у нас 300+ срабатываний мягкого лимита в
  секунду при 20 ГБ свободных на машине.
- **A/B: сначала разброс ВНУТРИ плеча, потом разница МЕЖДУ плечами.** Плечо OFF дало 1516 и
  3079 мс/чанк — 2× внутри себя, больше межплечевой разницы. По одному прогону на плечо я бы
  «доказал» любой знак эффекта. Два прогона на плечо в чередующемся порядке — минимум.
- **Утверждение про свежесть индекса проверяется sha, а не поиском.** Сверка `files.sha256`
  из `vec.db` с sha файлов на диске за 0.3 с даёт полную картину (пропущено / устарело /
  фантомы), тогда как пробный `search_memory` показывает только то, что попало в top-K.
- **Чинишь молчаливый обман — проверь, не завёл ли второй.** Фильтр «не отдавать файл, которого
  нет на диске» при недоступном корне scope опустошал бы выдачу целиком, и это была бы такая же
  тихая ложь, только наоборот. Правило: предикат по внешнему ресурсу применять, только если сам
  ресурс доступен; иначе «нет объекта» неотличимо от «нет доступа».
- **В Orchestra один процесс обслуживает НЕСКОЛЬКО scope** (на VPS их четыре в одной БД).
  Любое модульное состояние — счётчики, кеши, статусы — обязано быть словарём по scope.
  Общий `_last_pending` показал бы агенту долг чужого проекта, и заметить это он бы не смог.
- **«Какой код в живом процессе» — по `git reflog` + mtime файлов, НЕ по датам коммитов.**
  `pull --rebase` переписывает даты коммиттера: по ним выходило, что #9 приехал после старта
  сервиса, а живой сервер его код исполнял. Ground truth: `git reflog --date=format:...` даёт
  HEAD на момент старта, `find app -name '*.py' -newermt "<startup>"` — что переписано после.
  Момент старта — из журнала (`Application startup complete`), не из `ps` родителя.
- **В Orchestra фронт живой, бэк замороженный.** Jinja `auto_reload` и статика читаются с
  диска при каждом запросе, Python — один раз при старте. В окне между мержем и рестартом
  браузер получает НОВЫЙ js/html поверх СТАРОГО API. Любой новый Jinja-глобал без
  `is defined` в этом окне роняет дашборд в 500; любая смена формы ответа API ломает панель.
- **Сменил сигнатуру функции, которую тесты подменяют заглушкой, — прогон ПОВИСНЕТ, а не
  упадёт.** Добавил `session_name` в `backfill_scope`; async-заглушки принимали только `scope`,
  `TypeError` проглотил обработчик внутри планировщика, и тест навсегда завис на
  `Event.wait()`. Симптом — пять зелёных точек и тишина. Меняешь сигнатуру seam → сразу
  `grep "def fake_"` по тестам, а зависший прогон читай как несовпадение сигнатуры, а не как
  дедлок в проде. **Сформулировал это правило — и следующим же коммитом в него попал:**
  `blocked_backfill(_scope)` в `tests/test_api.py` остался стоять и блокировал всем полный
  прогон сутки. Правило работает только как ШАГ, а не как знание: сменил сигнатуру →
  до коммита `grep -rn "def fake_\|def blocked_\|def stub_" tests/` **и прогнать те файлы,
  которые её мокают** (мой прогон #28 их не включал — оттуда и дыра).

- **«Никто не зовёт» ≠ «никому не нужен».** Перед удалением роута смотри не только КТО ЕГО
  ЗОВЁТ, но и КТО ЧИТАЕТ ЕГО ДАННЫЕ и не рекламирует ли его строка в ответе соседнего роута.
  `GET /api/report_bug` вызывающего кода не имел вовсе — и был единственным читателем стора
  `~/.local/state/orchestra/bug-inbox/records/` (0600, вне git — так задумано), куда `POST`
  кладёт каждый репорт отдельным файлом. **`BUGS.md` репозитория с 01.08 не пополняется:**
  всё новое лежит там, 7 репортов на момент проверки. Плюс `POST` возвращает агенту дословно
  `Read: /api/report_bug` (`mcp_stdio.py:1418`) — удаление сделало бы из этого ссылку на 404.

- **CHANGELOG.md пишется РУКАМИ.** Автосборка из отчётов задач (#52) существовала полдня и
  отменена (`497db45`): `docs/tasks/*/report.md` содержат пути, IP, имена клиентов, а CHANGELOG

- **Правку текста делай Edit-инструментом, а не `python - <<EOF` с `str.replace` по вычисленной
  строке.** В #122 я выбрал строку фильтром «содержит X, не содержит Y», промахнулся на другую и

- **Тесты чанкера на КОРОТКИХ секциях врут.** Секция короче `MD_MIN_MERGE = 250` символов
  сливается с соседней, поэтому дописывание меняет ТЕКСТ соседнего чанка, а не только его
  позицию — мой тест на переиспользование эмбеддингов (#73) падал именно на этом, а не на коде.
  Для чанкерных тестов секции строить длиннее 250 символов, иначе проверяешь слияние, а не то,
  что хотел. Цена элемента меряется в ЧАНКАХ, не в килобайтах: 2.2 с/чанк, батчинг не помогает.

- **Долг индексации RAG сперва РАЗЛОЖИ по каталогам, потом ускоряй.** В #63 94 % долга (459 из
  490) оказались `data/bench138/` — чужим бенчмарк-корпусом под `.gitignore`, который обходчик

- **RAG-бэкфилл не логирует прогресс — только `start` и финальную строку.** Дедлайн

  5 файлов + 100 логов ≈ до 290 с → до ~10 минут тишины в journald при живом прогоне. Пустой

  `/api/memory/reindex`), а не «логи сломаны». Жив ли прогон — смотреть
  `py-spy dump --pid <pid> | grep -A6 rag-w_0` (видно и слой: `backfill_files` против логов);
  `COUNT(*) FROM logs_indexed` растёт СТУПЕНЯМИ по срезу, ноль за минуту — ещё не «встало».

- **Трафик считать ПО ПРОВОДУ, а не по `len(body)`:** дашборд стоит за nginx, и он жмёт JSON.
  `/api/models` — 4732 B тела и **747 B** на проводе (+162 B заголовков), коэффициент 6.3.

- **Добавил маршрут → обнови `tests/route_surface_snapshot.json`.** `test_routes_surface`
  сравнивает `(path, methods)` со снимком и краснеет на ЛЮБОМ новом маршруте. Снимок
  регенерируется тем же кодом, что в тесте (`json.dumps(surface, indent=1, ensure_ascii=False)`);
  перед перезаписью распечатай симметричную разницу — в снимке не должно ПРОПАСТЬ ничего.

- **Слой, округливший большое число, опознаётся по ФОРМАТУ текста, а не по коду.** Для
  `1917704623170653147` (> 2^53): JS печатает `1917704623170653200` (кратчайшая round-trip
  запись double), Python — либо `1.9177046231706532e+18` (`json.dumps` float'а), либо
  `1917704623170653184` (`int(float(x))`, точное значение double). Три разных текста одного и
  того же double → по строке в БД видно, чей это `JSON.stringify`. И помни: **Python
  `json.loads` без `parse_int` разбирает целое ТОЧНО** (int произвольной точности), то есть
  Python-слой целые ID не портит в принципе — виноват всегда кто-то другой.
  Разбор — `docs/tasks/129/research.md`.

- **Чтобы увидеть, что CLI РЕАЛЬНО шлёт MCP-серверу, поднимай свой stdio MCP-сервер на 45 строк**

  'mcp_servers.probe.args=["..."]'`. Стенд проверяется handshake'ом (`initialize` от
  `codex-mcp-client`) ещё до ответа модели — то есть годность стенда видна, даже если квота
  потом откажет. У Codex квота отдельная от Claude: `You've hit your usage limit ... try again at`.
- **Цена рекурсивного обхода JSON меряется в ЭЛЕМЕНТАХ контейнеров, а не в байтах.** Реальный

- **Признак «данных не было», выведенный из формы записи, проверяй на строках, где данные ТОЧНО

- **Стенограмму сессии Claude режет штатная `fork_session` из SDK — руками JSONL не трогать.**
  `from claude_agent_sdk import fork_session, get_session_messages`;
  `fork_session(sid, directory=<cwd>, up_to_message_id=<uuid>)` создаёт НОВЫЙ файл сессии со
  свежими UUID, источник не трогает (проверил на живой: 1571 запись → форк 1067, отравленных
  0). `get_session_messages(sid, directory=...)` даёт список с `uuid`/`message` для выбора точки
  среза. Файлы лежат в `~/.claude/projects/<путь-с-дефисами>/<session_id>.jsonl`.
  **Смены `s.session_id` НЕДОСТАТОЧНО:** клиент CLI persistent между ходами и держит старую
  стенограмму, `_ensure_backend` возвращает живой backend не глядя на id. Нужен
  `s._spawn_bg(s._disconnect_backend())` — иначе откат остаётся записью в журнале.
