# fix-tg-mention — личная память

## Флаг «уже обработано» в цикле, который умеет ПЕРЕИГРЫВАТЬ вход

`stream_logs` (`app/tg_bridge.py`) при `_TgDeliveryOverloaded` откатывает курсор
(`last_id = current_log_previous_id`) и читает пачку заново. Любое состояние,
погашенное в момент «событие замечено», на повторе уже ложно → работа теряется молча.

Правило: гасить флаг ПОСЛЕ фактического сайд-эффекта (отправки), не при обнаружении.
И проверять ОБА направления — потерю и дубль: откат курсора не переигрывает строки
с `id <= last_id`, поэтому дубля обычно нет, но это надо доказывать тестом, а не считать.

## Где в Orchestra искать «конец хода агента»

Разметки «финальное сообщение» на строке `text` НЕТ. Единственная durable-граница —
строка журнала `type='status'`, `content LIKE 'turn ended%'` (пишется в
`app/session_turns.py:314`, после текста). Событие `turn_end` из `AgentEvent` в таблицу
`logs` не попадает — на него в мосте опираться нельзя.

Живой замер по `data/orchestra.db` (10 дней, 1415 ходов оркестраторов):
4777 из 6161 строк `text` — промежуточные. Любая эвристика «последний text» = тег на 78% мусора.

## Полосы доставки TG

`_tg_send_safe(important=True)` — надёжная полоса с ретраями; `important=False` может
быть молча дропнута. Приоритет ЦЕЛОГО класса сообщений не флипать (был инцидент с
lock contention). Нужно надёжно доставить одно новое сообщение — слать его отдельно
своим `important=True`, не поднимая класс.

## Читать живую БД перед проектированием

`cp data/orchestra.db /tmp/x.db` + sqlite3 отвечает на «сколько таких случаев на самом деле»
за минуту. Замер убил два очевидных варианта решения (тег на каждом `text`; придержать
текст до границы — p99 задержки 26 с, max 320 с) ДО написания кода.
