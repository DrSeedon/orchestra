Orchestra — Git Workflow

Как агенты работают в параллельных ветках без конфликтов  ·  Руководство для PM

1

Как это работает сейчас

🗺️
Общий поток: от репозитория до мержа
💡
Каждый воркер — это агент Claude в отдельной папке со своей веткой. Они работают параллельно и не мешают друг другу, пока не наступает момент мержа.
📋
Пошаговый процесс
  1. 1
    Оркестратор создаёт воркер
    Указывает task_id — автоматически создаётся ветка task-49/backend-opus и изолированная папка (worktree). Файлы проекта (CLAUDE.md, .env) копируются туда же.
  2. 2
    Агент работает в своём worktree
    Claude делает коммиты прямо в свою ветку — wip: trying approach, fix: typo, feat: add endpoint. Никто другой эту ветку не трогает.
  3. 3
    Предварительная проверка конфликтов
    Перед мержем Orchestra симулирует объединение (git merge-tree) без изменения реального кода. Если конфликты есть — сообщит заранее, не сломав ничего.
  4. 4
    Глобальный лок → squash merge
    Только один мерж происходит в каждый момент времени (файловый лок). Все шумные «рабочие» коммиты агента сворачиваются в один чистый коммит на main с привязкой к задаче #49.
  5. 5
    Очистка или следующая задача
    Worktree удаляется, либо воркер переключается на следующую задачу (switch_worker_branch) — ему создаётся новая ветка от обновлённого main.
2

Что меняет squash merge

🎯
Проблема: AI-агенты делают много «черновых» коммитов — wip: try A, revert, fix typo. Если мержить их все в main, история становится нечитаемой. Squash merge сворачивает всё это в один осмысленный коммит.
❌ До: merge commit
История в main:
a1b2c3d Merge branch 'task-49/backend'
7f3e1a2 wip: trying approach 3
6c2d9b1 revert: approach 2 broken
5b1c8a0 fix: typo in endpoint
4a0b7z9 wip: auto-save
3f9a6y8 try: different SQL query
2e8b5x7 #49: add user endpoint
1d7a4w6 prev task...
⚠️ 6 мусорных коммитов агента попали в main. Через месяц — непонятно что было, когда и зачем.
✅ После: squash merge
История в main:
a1b2c3d #49: add user endpoint
task-49/backend-opus (6 commits squashed)
1d7a4w6 prev task...
✅ Один коммит = одна задача. История читается. git bisect работает. Ссылка #49 сохранена.
Полная рабочая история агента не удаляется — она остаётся в ветке refs/agents/task-49 для аудита, просто не засоряет main.
🔄
Как работает squash технически
✅
Преимущества squash
  • 📖
    История main читается как книга — один коммит на фичу/задачу
  • 🔍
    git bisect работает быстро — нет «мусорных» промежуточных состояний
  • 🔗
    Привязка #49 в одном месте — легко найти что изменилось по задаче
  • 🕵️
    Полная рабочая история агента сохраняется в refs/agents — аудит всегда доступен
⚡
Когда оставлять merge commit
Squash — умолчание. Merge commit нужен только если:
  • 📋
    Аудиторские требования — нужна полная история каждого шага в main
  • 🔧
    Отладка сложного рефакторинга — важно видеть каждый промежуточный шаг прямо в main
Флаг: merge_worker(strategy="merge")
3

Изоляция воркеров: worktrees

🏗️
Worktree — это отдельная папка на диске, которая указывает на ту же базу кода, но находится в другой ветке. Несколько воркеров могут работать одновременно над одним репозиторием — каждый в своей папке, в своей ветке.
💡
Как создаётся worktree
⚡
Worktree создаётся за миллисекунды — копируются только рабочие файлы. Git-объекты (история) не дублируются.
Именование ветки:
С task_id: task-49/backend-opus
Без task_id: feat/orchestra/worker-name
🛡️
Защита от конфликтов
🔒
Предварительная симуляция — перед мержем Orchestra проверяет конфликты без изменения кода
⏳
Сериализованный мерж — только один мерж в момент времени через глобальный файловый лок
🔀
Параллельная работа без конфликтов — как это выглядит

🤖 Агент Backend

📁 Своя папка
🌿 Ветка: task-49/backend
✏️ Редактирует: app/api/
💾 Коммитит: свободно
🏁 Мержит первым → clean

🤖 Агент Frontend

📁 Своя папка
🌿 Ветка: task-49/frontend
✏️ Редактирует: app/static/
💾 Коммитит: свободно
🏁 Мержит вторым → clean

⚠️ Риск конфликта

❌ Оба редактируют
app/config.py
→ Конфликт при мерже
→ Pre-check поймает
→ Оркестратор решает
💡
Лучшая практика: давать агентам разные «территории» — backend меняет app/api/, frontend меняет app/static/. Меньше конфликтов = быстрее работа.
4

Граничные случаи и защита

🔀 Несвязанные истории (unrelated histories)
▼
⚠️
Проблема: Если внутри репозитория есть другой git-репозиторий (со своим .git папкой), и агент работает в нём — его коммиты идут в «чужую» историю. При попытке мержа в main оказывается, что у веток нет общего предка.
Сейчас (fallback):
🔄
Orchestra автоматически использует cherry-pick fallback — переигрывает каждый коммит. Работает, но может создавать дубли.
Рекомендуемый фикс:
🎯
Обнаружение вложенного .git при создании воркера → сразу сообщить оркестратору. Задать правильный repo_path.
🏗️ Создание worktree — защитные проверки
▼
  1. 1
    Проверка имени ветки
    git check-ref-format — убеждаемся, что имя ветки валидно (нет спецсимволов, не начинается с дефиса и т.д.)
  2. 2
    Ветка уже занята?
    _is_branch_checked_out_elsewhere — Git позволяет одну ветку держать в одном worktree одновременно. Если ветка уже занята другим воркером — reuse без -b.
  3. 3
    Авто-сохранение main
    _auto_commit_if_dirty — если в main есть незакоммиченные изменения, они автоматически коммитятся как wip: auto-save. Воркер ветвится от чистого состояния.
  4. 4
    Копирование конфигов
    CLAUDE.md, .env, .mcp.json, .worktreeinclude — копируются в worktree. Воркер сразу знает правила проекта.
🔐 Мерж — цепочка защит
▼
  1. 1
    Глобальный лок
    Файловый лок .git/orchestra-merge.lock — если два воркера пытаются мержиться одновременно, второй ждёт. Нет race conditions.
  2. 2
    Проверка чистоты
    Если в worktree есть незакоммиченные изменения — мерж отклонён с ошибкой. Агент должен сначала закоммитить.
  3. 3
    Симуляция конфликтов
    git merge-tree --write-tree — вычисляет результат мержа без изменения файлов. Если конфликты есть — возвращает список файлов, не ломая дерево.
  4. 4
    Restore в finally
    Оркестратор стеширует свои изменения → переключается на target ветку → делает мерж → возвращается на свою ветку → pop stash. Порядок критичен: сначала ветка, потом pop.
🔄 Переключение на новую задачу (switch_worker_branch)
▼
💡
После завершения задачи воркер не удаляется — он может перейти на следующую задачу в той же папке. Это быстрее, чем создавать новый worktree.
Условия для switch:
✓
Рабочее дерево чистое (все закоммичено)
✓
Текущая ветка полностью смержена в from_ref
Что происходит:
1. Создаётся ветка task-50/name
2. Мержится свежий main (auto-sync)
3. Воркер продолжает работу

Что Orchestra делает лучше
🔒
Файловый лок мержа — явная защита от race conditions. Многие инструменты надеются на порядок PR.
🌿
Per-task именование веток task-N/name — привязка к системе задач из коробки.
🔄
switch_worker_branch — воркер переходит на новую задачу без пересоздания окружения.
🚀
Что можно добавить
📦
Squash merge по умолчанию — самое важное изменение. Чистая история в main.
🗂️
Directory ownership — явная «территория» каждого агента. Структурное предотвращение конфликтов.
🧪
Pre-dispatch симуляция — проверить конфликт двух агентов до их запуска.
6

Лучшие практики

🌿
Ветки: короткие и конкретные
❌ Антипаттерн
feat/scope/worker-name
Долгоживущая ветка на воркера — накапливает задачи, расходится с main, сложно мержить. Конфликты растут пропорционально времени жизни ветки.
✅ Правильно
task-49/backend-opus
Одна ветка = одна задача. Создать → сделать → смержить → удалить (или switch). История чистая, конфликты минимальны.
🗺️
Разделение территорий между агентами
🏆
Лучший способ избежать конфликтов — структурное разделение. Каждый агент «владеет» своей частью кода.
Агент Его территория Запрещено трогать
🤖 backend-opus app/api/, app/models/ app/static/, app/templates/
🤖 frontend-sonnet app/static/, app/templates/ app/api/, app/models/
🤖 tests-haiku tests/ любой production код
🤖 docs-haiku docs/, *.md любой python/js файл
⚠️
Общие файлы (pyproject.toml, app/config.py) — источник конфликтов. Либо один агент их «владеет», либо изменения в них координируются через оркестратора.
🤖
Opus vs Sonnet vs Haiku — когда что использовать
Модель Когда использовать Не использовать Стоимость
🧠 Opus 4.7 Оркестратор (принятие решений), сложная архитектура, research, планирование задач Простые рутинные задачи — дорого $5/$25 per M
⚡ Sonnet 4.6 Реализация фич по спецификации, код по готовому плану, frontend Архитектурные решения без supervision $3/$15 per M
🚀 Haiku 4.5 Тесты, документация, простые CRUD, рутинные правки, задачи «по шаблону» Сложная логика, архитектура $1/$5 per M
💡
Принцип: На подписке Max 20x все цифры виртуальные — реальных расходов нет. Но оптимизировать стоит ради качества: Opus медленнее, зато принимает более взвешенные решения. Haiku быстрый, но делает поверхностный анализ.
📋
Чеклист запуска параллельных агентов
  1. 1
    Определить территории
    Перед спавном убедиться: какие файлы/директории будет трогать каждый агент. Перекрытие = потенциальный конфликт.
  2. 2
    Указать task_id
    Всегда передавать task_id при спавне — это создаёт правильное именование ветки task-N/name и позволяет привязать мерж к задаче.
  3. 3
    Мержить в правильном порядке
    Если агенты зависят друг от друга (B использует API от A) — сначала мержить A, потом B switch_worker_branch забирает обновлённый main.
  4. 4
    Убедиться что worktree чистый перед мержем
    Агент должен закоммитить всё перед мержем. Orchestra проверит и откажет если есть незакоммиченные изменения.
  5. 5
    Следить за вложенными репозиториями
    Если воркер работает внутри папки с собственным .git — указать правильный repo_path. Иначе коммиты уйдут «не туда».
