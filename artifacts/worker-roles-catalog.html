Orchestra — Worker Roles

Каталог ролей, pipeline, структура промптов, примеры spawn

🎯
Orchestrator
Opus
Управляет воркерами. Декомпозирует задачи, спавнит воркеров, ревьюит результаты. Каталог ролей инжектится автоматически.
✓ Управление командой, декомпозиция, одобрение планов
✗ Прямая имплементация — делегируй воркерам

Особенности

  • Получает каталог ролей из roles/*.md frontmatter автоматически
  • Видит список текущих воркеров (auto-injected)
  • Видит других оркестраторов (cross-project)
  • НЕ получает цвет, НЕ делает auto-report
  • Промпт: base.md + orchestrator.md + каталог ролей + workers list

Гейты одобрения

Для full-cycle воркеров: одобряет Research и Plan. Implementation — воркер справляется сам через Codex consensus.

🔄
Full-Cycle
Opus
Research → Plan + Codex review → Implement + Codex review. Жёсткий 3-фазный pipeline с 2 гейтами одобрения оркестратора. Все артефакты в docs/tasks/<id>/.
✓ Новая фича с неизвестным скоупом
✓ Крупный рефакторинг (5+ файлов)
✓ Интеграция с внешней системой
✗ Баг-фиксы, конфиг, имплементация по спеке

Pipeline (подробнее во вкладке «Full-Cycle Pipeline»)

  • Phase 1: RESEARCH — код, websearch, docs → research.md → ⏸️ ждёт одобрения
  • Phase 2: PLAN + Codex — план, Codex ревью до консенсуса → plan.md → ⏸️ ждёт одобрения
  • Phase 3: IMPLEMENT + Codex — код, Codex ревью до консенсуса → report.md → DONE

Документация задачи

Каждая задача создаёт docs/tasks/<task-id>/ с файлами: research.md, plan.md, codex-review-plan.md, codex-review-impl.md, report.md

Правила

  • НИКОГДА не пропускать фазу
  • НИКОГДА не продолжать без одобрения после фазы 1 и 2
  • Codex консенсус ОБЯЗАТЕЛЕН в фазах 2 и 3
  • Всё записывается в файлы — не только в чат
⚙️
Worker
Sonnet / Opus
Универсальный воркер. Выполняет задачи напрямую без pipeline гейтов. Для системных воркеров (постоянных) и одноразовых.
✓ Ясная задача для известного модуля
✓ Имплементация по детальной спеке
✓ Баг-фикс с известным repro
✗ Задачи с ресёрчем / неизвестным скоупом → full-cycle

Два подтипа

  • System worker (Opus, permanent) — знает модуль, переиспользуется. Naming: backend, frontend, taskmanager
  • Disposable (Sonnet, one-shot) — имплементация по спеке, убивается после merge. Naming: impl-*, fix-*

Workflow

  • pwd → read code → do task → pre-DONE checklist → commit → DONE report
  • Обязательный structured DONE: Files, Tests, Breaking, Notes
  • Перед началом: прочитать код, чекнуть docs/

Промпт

Frontmatter prompt: worker.md — body пустой, берёт контент из prompts/worker.md. Это fallback роль по умолчанию.

🔍
Reviewer
Opus
Ревьюит код, планы, имплементации на корректность, безопасность, качество. Выдаёт findings по severity (CRITICAL / HIGH / MEDIUM / LOW).
✓ Code review, plan review, security audit
✗ Имплементация — ревьюеры не пишут код

Фокус

  • Баги, логические ошибки, edge cases, race conditions
  • Безопасность: injection, auth bypass, path traversal, secrets
  • Обратная совместимость и безопасность миграций
  • Пробелы в тестовом покрытии

Формат вывода

Для каждого finding: file:line, что не так, предложенный фикс. Если ничего не найдено — явно сказать.

👁️
Watcher
Sonnet
Мониторит системы, логи, метрики. Репортит аномалии оркестратору. Статусы: OK / WARNING / CRITICAL.
✓ Мониторинг систем/логов/метрик, health checks
✗ Имплементация или фиксы — наблюдатели только смотрят

Фокус

  • Ошибки, краши, деградация производительности
  • Здоровье деплоя и доступность сервисов
  • Алерты при пересечении порогов

Правила

Не чинить самому — репортить оркестратору. Краткие отчёты: что случилось, когда, импакт, рекомендация.

Как строится промпт агента

🎯 Orchestrator prompt

base.md — платформа: MCP tools, communication, ограничения
orchestrator.md — workflow: decision tree, spawning rules, parallel tasks
roles catalog (auto) — из frontmatter всех roles/*.md
other orchestrators (auto) — cross-project orchestrators list
current workers (auto) — список воркеров в scope

⚙️ Worker prompt

base.md — платформа: MCP tools, communication, ограничения
roles/worker.md → worker.md — workflow: checklists, DONE format, git rules
system_prompt (custom) — от оркестратора: экспертиза, scope, constraints

🔄 Full-Cycle prompt

base.md — платформа
roles/full-cycle.md — pipeline: 3 фазы, гейты, Codex consensus
system_prompt (custom) — от оркестратора

🔍 Reviewer prompt

base.md — платформа
roles/reviewer.md — фокус, формат вывода, severity levels
system_prompt (custom) — от оркестратора

YAML Frontmatter формат

Каждый roles/<name>.md начинается с frontmatter. Manager парсит его и генерирует каталог ролей автоматически.

---
name: full-cycle # id роли для spawn_worker(role="...")
label: Full-Cycle # человеческое название
model: opus # рекомендуемая модель
when: New feature, large refactoring # когда использовать
not_for: Bug fixes, config changes # когда НЕ использовать
description: > # описание для каталога оркестратора
  Research → Plan + Codex → Implement + Codex.
prompt: worker.md # (опц.) fallback файл если body пустой
---

# Ниже — промпт для агента (если есть).
# Если body пустой и есть prompt: — берёт из указанного файла.

Как добавить новую роль

  1. Создать app/prompts/roles/my-role.md с YAML frontmatter
  2. Написать промпт для роли после --- (или указать prompt: worker.md для fallback)
  3. Рестартнуть Orchestra — оркестратор автоматически увидит новую роль в каталоге
  4. Спавнить: spawn_worker(name="my-worker", ..., role="my-role")

Примеры spawn для каждой роли

Задача: добавить swarm mode в Orchestra. Unknown scope, нужен ресёрч.

  name="feat-swarm",
  task="#23: Implement swarm mode — spawn N workers on same task, judge picks best result",
  repo_path="/mnt/data/Projects/Python/orchestra",
  task_id="23",
  role="full-cycle",
  model="claude-opus-4-8[1m]"
)
