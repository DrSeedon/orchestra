02

Целевой поток: одна истина, несколько скоростей чтения

Смысл прост: сначала зафиксировать, какой именно факт меняется и чем он доказан. Затем Git принимает каноническое изменение. Быстрые проекции догоняют этот конкретный HEAD; если не успели — система говорит об этом и читает канон напрямую.

Что типизировано

current, rejected, disputed, superseded и stale-needs-validation — не стилистические слова, а режимы запроса. У факта есть valid time, observed/recorded time, source path + anchor, commit/blob и actor/event.

Что делает поколение

После merge появляется target_head. SQLite должен синхронно дойти до него. Vector/log могут отставать: при несовпадении виден visible projection debt, а изменённая тема получает direct canonical fallback — не превращается в «факта нет».

Техническая граница, раскрыть

Стабильный fact_key задаёт кандидата на обновление внутри (project, topic, fact_key). Идентичный event — idempotent no-op; конфликт одного ключа требует явного supersedes или disputed. TTL только создаёт validation debt: истёкший refresh_after не удаляет и не объявляет факт ложным.

03

Один новый факт — четыре честных режима

Ниже синтетический walkthrough механизма, а не результат Phase 2. Представим, что исследование принесло новую проверенную находку. Сначала система находит дом темы, затем обновляет стабильный ключ и сохраняет старую дорогу.

mode = current

Что считаем правдой сейчас

fact_keymemory.index.freshness
claimПроверять нужно поколение canonical HEAD против projection HEAD; при расхождении читать изменённую тему напрямую.
evidencedocs/tasks/256/research.md §6.4 · commit/blob + anchor

Ответ получает claim, статус current, valid time и путь источника. Старая версия не исчезла — она просто не попадает в default current.

mode = rejected

Что уже пробовали и закрыли

statusrejected; причина и evidence обязательны.
claim«Усилить только prompt-контракт — достаточно» — путь закрыт измерением source-link 7/12 и current index 50.1%.
queryРежим rejected возвращает это явно, current по умолчанию его не смешивает с действующим ответом.
event = supersedes

Как старая версия остаётся видимой

old factfact_id = F-old, valid_to закрыт, superseded_by = F-new.
new factfact_id = F-new, тот же fact_key, новое evidence и явная причина замены.

Ничего не перезаписывается молча. Это спасает от повторного «открытия» уже закрытой дороги и даёт audit trail.

mode = as_of

Что было верно на выбранную дату

valid timeЗапрос отбирает факт по valid_from ≤ date < valid_to; неизвестная дата остаётся null, а не «началом времён».
resultНа дату до supersession возвращается F-old с provenance; после — F-new. Оба доступны в истории.
04

#299 помогает задачам, но не становится базой знаний

Контур задач

#299 исследует Git-canonical task records с SQLite query projection: стабильный UUID/ULID и сохранённый человекочитаемый #N, история, merge-конфликты и восстановление из клона.

В обсуждении #295 фиксируем решение пользователя: YouGile и payments из текущего планирования #299 убраны. Здесь остаётся только переносимый task store и его projection/identity вопросы.

Контур знаний

Задача — место, где лежит raw research/report и доказательство. Topic — место, где компактно живут typed conclusions. fact_key отвечает за семантическую идентичность факта, а task ID — за рабочую задачу.

Не смешиваем task state и knowledge facts в один бесформенный store: у них разные владельцы, жизненные циклы, запросы и правила удаления.

Практическая граница, раскрыть

Исследовательская задача может породить evidence ref в событии знания. Это связь provenance, а не превращение task JSON в topic. Проекция SQLite может обслуживать оба домена, но таблицы, идентичности и валидаторы должны оставаться различными.

06

Что почувствует воркер

Предложено, ещё не измерено

Меньше поиска

Компактный hot registry может убрать отдельное чтение README; один warm-запрос возвращает typed facts вместо разрозненных chunks. Это гипотеза о tool calls, не Phase 2 результат.

Понятные режимы

Запросы current, rejected и as_of не смешивают старую и новую дорогу без подписи.

Доказательство рядом

У результата есть source path, anchor и generation receipt: воркер видит, из какого канона факт пришёл и догнал ли индекс HEAD.

Ни один из этих эффектов нельзя выдавать за измеренный. #256 прямо оставляет answer utility/task success, promotion recall и A/B latency proposed path как неизвестные до реализации и разрешённого теста.

07

Доска решений для пользователя и оркестратора

Выберите по одному варианту на каждый вопрос. Кнопка внизу соберёт локальную копируемую сводку; сеть не используется. Пустой выбор разрешён — это тоже сигнал, что решение не принято.

1. Насколько строгой делать схему факта?

Рекомендуемый defaultОбязательные fact_key, status, valid time и provenance; остальное версионируется.

АльтернативаРазрешить свободную форму с постепенной типизацией.

Если ждатьPromotion recall и orphan safety останутся не измеримыми; ручная запись продолжит расходиться.

2. Кто может promote и supersede?

Рекомендуемый defaultWrite API проверяет evidence; same-key conflict не решается similarity-моделью молча.

АльтернативаДля supersede добавить отдельное человеческое подтверждение.

Если ждатьПоявится спор о праве изменения и риск collateral retirement при будущей автоматизации.

3. Когда связывать Git task store #299?

Рекомендуемый defaultСначала закрепить Git/SQLite projection, identity и head contract задач; затем переиспользовать proven boundary.

АльтернативыПараллельная работа возможна только с разными схемами и acceptance gates; knowledge-first ускорит факты, но не даст task migration seam.

Если ждатьДва проекта будут спорить о canonical/projection terminology и могут породить несовместимые поколения.

4. Как хранить private data и сколько держать историю?

Рекомендуемый defaultСначала классифицировать; private repo/access control; tombstone не называть GDPR erase.

АльтернативаВынести чувствительные поля в отдельный контролируемый store с provenance-ссылкой.

Если ждатьЛюбая схема станет опасной для платежных/клиентских данных и потребует переделки retention.

5. Какие rollout gates и rollback обязательны?

Рекомендуемый default12 promotion scenarios, 18 retrieval cases, zero false supersession, head receipts, parity и явный rebuild из Git.

АльтернативаДольше держать старый read path и сравнивать normalized responses до cutover.

Если ждатьНельзя отличить безопасный rollback от потери фактов или stale projection.
