# tool-latency — из чего состоит время вызовов инструментов

Владелец темы: `.orchestra/tasks/516/research.md` (фаза 1, ресёрч).
Все числа — замер на 2026-09-05 по `data/orchestra.db` за 2026-08-03…2026-09-05.
Это датированный срез, а не текущий конфиг: база живая и растёт.

## Established

- **Пары `tool → tool_result` соединяются по `tool_use_id`, а не по порядку `ts`.**
  Колонка появилась 2026-08-11, с 08-16 почти сплошная (77 106 из 102 255 строк `tool`).
  Для строк без неё проверенная эвристика — **LIFO внутри сессии** (результат закрывает
  самый поздний незакрытый вызов): 96.0 % верного партнёра и −0.3 % ошибки суммы времени
  на размеченной части. · search: `tool_use_id`, «спаривание tool_result», LIFO,
  `scripts/calibrate.py` · evidence: `.orchestra/tasks/516/raw/07-calibration.txt` · 2026-09-05, #516

- **Пустое `tool_name` — не класс вызовов, а строки до появления колонок телеметрии.**
  Все 24 446 таких строк лежат в 2026-08-03…08-11 плюс хвост 155 строк 08-22. Имя
  полностью восстанавливается из `content`: легаси-формат `Bash: {json}`, хвост 08-22 —
  `file: update <path>` (это `FileChange`). После восстановления безымянных пар нет.
  Уточняет `feature-usage-audit.md` («semantics before named tool_name telemetry began
  2026-08-13 remain unresolved»): для ИМЕНИ инструмента вопрос закрыт, парсер payload
  по-прежнему не написан. · search: «пустое tool_name», legacy tool rows, `FileChange`
  · evidence: `.orchestra/tasks/516/raw/01-null-toolname-shape.txt`, `02-content-samples.txt`
  · 2026-09-05, #516

- **Суммировать длительности вызовов как стенное время можно:** объединение интервалов
  внутри сессии даёт 115.58 ч против суммы 120.46 ч, перекрытие 4.0 %.
  · evidence: `.orchestra/tasks/516/raw/26-overlap-and-nonbash.txt` · 2026-09-05, #516

- **Время инструментов держит тонкий хвост, а не общая медленность.** bash-семейство:
  медиана **0.19 с**, среднее 5.64 с (завышает в 30 раз), p95 26.11 с, p99 110.44 с.
  Топ-1 % вызовов = 32.3 % времени bash, топ-5 % = 68.4 %, топ-10 % = 83.9 %.
  **1 369 вызовов из 62 350 (2.2 %) дольше 60 с держат 39.8 % всего времени инструментов.**
  Любой вывод про «медленные вызовы» без квантилей — ошибка.
  · evidence: `.orchestra/tasks/516/raw/10-bash-distribution.txt` · 2026-09-05, #516

- **Два фиксированных потолка ожидания стоят 5.83 ч (4.8 % времени инструментов).**
  `_MERGE_WAIT_SECONDS = 90.0` (`app/mcp_stdio.py:2512`) — 169 вызовов `merge_worker`
  упираются в потолок, это 4.31 ч = 56.3 % времени тула, плюс 145 вызовов-продолжений
  на 1.82 ч; в коде константа честно названа «ручкой ЧАСТОТЫ, а не корректности».
  Дефолт `timeout=30` в `_api` (`app/mcp_stdio.py:518`) — 240 вызовов на полке ~30 с,
  из них **180 (1.52 ч) заканчиваются ошибкой**: время потрачено, ответа нет.
  · search: `_MERGE_WAIT_SECONDS`, «полка 30 секунд», `_api` timeout
  · evidence: `.orchestra/tasks/516/raw/27-mcp-timeout-cliffs.txt`, `28-timeout-errors.txt`
  · 2026-09-05, #516

- **Потолок bash в harness (120 с) убивает команды и в большинстве случаев не виден
  как ошибка.** 170 вызовов на 119.5–121.9 с = 5.69 ч = 4.7 % времени инструментов;
  `is_error=1` стоит только у 51 из них, остальные приходят как обычный результат с
  обрезанным выводом. Среди убитых есть команды, просившие `timeout 600` и `timeout 900`.
  · search: «потолок 120 секунд», «убитая команда bash», harness timeout
  · evidence: `.orchestra/tasks/516/raw/31-harness-timeout-120.txt` · 2026-09-05, #516

- **13.4 % времени инструментов (3 950 вызовов, 16.19 ч) — вызовы, завершившиеся
  ошибкой.** · evidence: `.orchestra/tasks/516/raw/28-timeout-errors.txt` · 2026-09-05, #516

## Rejected

- **«Парность по `ts`» в смысле FIFO по сессии — негодное правило, ошибка ×13.**
  Строки `tool` без ответа копятся в очереди и сдвигают все последующие пары до конца
  сессии; худшие случаи дают 22 суток на вызове, реально шедшем 0.0 с. Для bash даёт
  875.13 ч вместо 74–79 ч и «дольше 60 с — 13 314» вместо ~900. Верный партнёр угадан
  в 28.2 % случаев. · evidence: `.orchestra/tasks/516/raw/04-rule-comparison.txt`,
  `05-rule-agreement.txt` · 2026-09-05, #516

- **«Полные прогоны тестов съедают время» — опровергнуто.** Полный прогон (без пути
  и без `-k`) — 419 вызовов / 4.96 ч, десятая часть класса `tests`. Основное время
  (44.50 ч из 49.91 ч) — ЦЕЛЕВЫЕ прогоны отдельных файлов.
  · evidence: `.orchestra/tasks/516/raw/23-tests-subclasses.txt` · 2026-09-05, #516

- **«`uv run` тормозит старт тестов» — опровергнуто прямым сравнением.** На целевых
  прогонах `uv run` даёт медиану 13.18 с (4 400 вызовов), прямой `.venv/bin/python -m` —
  13.30 с (1 527 вызовов). Разницы нет.
  · evidence: `.orchestra/tasks/516/raw/23-tests-subclasses.txt` · 2026-09-05, #516

- **«Целевой прогон в основном стартует, а не считает» — опровергнуто замером.**
  Пол запуска: `import pytest` 0.24 с, сбор одного файла 0.14 с, полный wall
  `--collect-only` одного файла 1.00 с. При медиане целевого прогона 12.92 с старт
  занимает <10 %; батчинг файлов в один вызов экономит ~1 с на вызов, максимум ~1.7 ч
  из 44.5 ч. Сбор ВСЕГО набора — 29.56 с, это фиксированная цена любого полного прогона.
  · evidence: `.orchestra/tasks/516/raw/24-startup-floor-measured.txt` · 2026-09-05, #516

- **«Установка зависимостей / git-операции / чтение и грепанье» как статьи расхода —
  опровергнуты.** deps 89 вызовов / 0.41 ч (0.34 %); git 10 741 вызов / 1.46 ч, p95 = 1.4 с;
  search-read 22 749 вызовов / 4.06 ч при медиане **0.01 с**; файловые тулы
  (`Read`/`Edit`/`Write`/`FileChange`) 18 867 вызовов / 0.77 ч. Самые ЧАСТЫЕ классы
  оказались почти бесплатными. · evidence: `.orchestra/tasks/516/raw/32-final-table.txt`
  · 2026-09-05, #516

- **«8 ч уходит на повторные прогоны одной команды» — снято собственной проверкой,
  верная цифра 1.66 ч.** Из 1 205 повторов 978 прогонов (6.28 ч) шли ПОСЛЕ правки файла
  в той же сессии — это проверка нового состояния, а не лишняя работа. Без единой правки
  между прогонами повторено 227 раз на 1.66 ч. Совпадение текста команды само по себе
  избыточности не доказывает. · evidence: `.orchestra/tasks/516/raw/34-repeat-without-edit.txt`
  · 2026-09-05, #516

## Gaps

- Разрыв 6.6 ч со счётом оркестратора объяснён как эффективная верхняя отсечка
  ≈250–270 с (его сумма и среднее ложатся между отсечками 240 и 300 с), но его скрипт
  не прочитан, поэтому это реконструкция, а не подтверждённая причина.
- Остаточная ошибка классификации ≈1 %: 1.17 ч внутри класса `other` содержат реальный
  запуск pytest, не пойманный из-за вложенного экранирования `bash -lc "… '"'…'"' …"`,
  где отслеживание кавычек рассинхронизируется.
- Истинная длительность полного прогона цензурирована сверху: прогоны запускались под
  `timeout 590`/`580`, поэтому распределение обрезано, а не измерено.
- Сокращаемость названа по классам, но НЕ проверена экспериментом: ни одна замена
  (ожидание по событию, снятие полок таймаута) не выполнена и не замерена. Это фаза 2.
