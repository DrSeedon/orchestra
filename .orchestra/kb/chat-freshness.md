# chat-freshness — актуальность чата в дашборде

Тема про ОДИН вопрос: откуда берётся история чата при выборе агента. Ответ зафиксирован
решением юзера 28.08.2026 и дальше не переоткрывается: **только сеть, только один свежий
snapshot, никакого локального кеша как первого источника**.

## Установлено

- **Чат — network-first: при выборе агента идёт ОДИН запрос `/api/sessions/<name>/logs`
  (`before_id=2^31-1`, `limit=_CHAT_PAGE=100`), ответ рисуется одним кадром, и только потом
  подключается SSE строго после последнего `id`** · `app/static/js/app.js:2356` (`_showChatFor`),
  `app.js:2298` (`_fetchHistory`) · 28.08.2026
- **Локальный кеш непригоден как первый источник по ПРИЧИНЕ, а не по объёму: он не может
  доказать, что после его watermark ничего не появилось, — watermark обновляется тем же
  фоновым poll, который и опаздывает.** Поэтому кешированный хвост нельзя показывать как
  актуальный даже на один кадр · комментарий-владелец `app/static/js/app.js:2356` · 28.08.2026
- **Зеркало логов в IndexedDB и фоновый `/logs/sync` удалены целиком.** Вместе с ними ушли
  константы `MIRROR_KEEP_PER_SESSION`, `_CHAT_MIRROR_DEADLINE`, `_CHAT_MIN_FROM_STORE`,
  `_CHAT_MIRROR_MAX_GAP`, `_STORE_DB` · коммит `735cf14e`, −1083/+406 строк в пяти файлах ·
  28.08.2026
- **Переключение агента отменяет предыдущий запрос через `AbortController`, а не ждёт его.**
  Отменённый snapshot освобождает сетевой слот и не может дорисоваться поверх нового агента:
  сверка идёт по `generation` (`_chatLoadGeneration`) · `app.js:2364`, `_chatLoadIsCurrent` ·
  28.08.2026
- **`stale-while-revalidate` для чата запрещён явно.** Он корректен только там, где устаревшие
  данные допустимы; в живом чате устаревший кадр — это и есть дефект, ради которого всё
  переделывалось · решение 28.08.2026
- **Свежесть принуждается с ОБЕИХ сторон: сервер отдаёт `Cache-Control: no-store`, клиент
  просит `cache: 'no-store'`.** Одной стороны мало — посредник или браузер переигрывает
  старый 200 и воспроизводит ту самую лесенку «сначала старое, потом SSE догоняет» ·
  `app/routes/sessions.py:583`, `app.js:2310` · коммиты `735cf14e`, `6de7cb70` · 28.08.2026
- **Сетевые слоты разделены по приоритету: всего 4 одновременных GET, фоновым доступно 3
  (`_API_MAX_CONCURRENT_GETS=4`, `_API_MAX_BACKGROUND_GETS=3`).** Четвёртый слот всегда
  свободен под клик юзера — запрос чата идёт с `priority: 'critical'` · `app.js:7253-7255`,
  `app.js:2308` · 28.08.2026
- **Сетевая ошибка показывает честную ошибку с кнопкой «Повторить», а не подсовывает архив
  через SSE** · `_renderChatLoadState(name, error)`, `app.js` ветка `catch` в `_showChatFor`;
  стили `app/static/css/style.css:112` · 28.08.2026
- **Один клик по агенту создаёт ровно history + context + SSE.** Повторных `/sessions`,
  `/stats`, context и sync больше нет · отчёт фронтового воркера 28.08.2026
- **Тесты после переделки: `tests/test_frontend.py` 94 passed / 1 skipped, `tests/test_logs_sync.py`
  28 passed** — прогоны мои, до мержа `735cf14e` · 28.08.2026

## Отвергнуто

- **«Зеркало в IndexedDB даёт мгновенный чат на повторном заходе» (#8, #2)** · опровергнуто
  практикой: зеркало ключевалось по имени агента, требовало собственной инвалидации по эпохе
  рендерера, и его промах давал пустой экран у редко открываемого агента (замер 21.08: 16
  узлов при пороге `_CHAT_MIN_FROM_STORE=40`). Удалено целиком 28.08.2026 (`735cf14e`)
- **«Тормоза чата — это объём зеркала»** · опровергнуто 21.08: у юзера зеркало было 1.7 МБ /
  688 строк, лечило удаление базы, а не её размер → дело было в НЕСОВПАДЕНИИ данных с кодом,
  то есть в самой идее локального первого источника
- **«Достройка кадрами на 250/1000/5000 мс — приемлемая цена за скорость»** · отвергнуто
  28.08.2026: именно эта лесенка и читалась юзером как «экскурсия по музею старых сообщений»
- **«Клиентского `cache: no-store` достаточно»** · опровергнуто необходимостью отдельного
  коммита `6de7cb70` на серверный заголовок: посредник переигрывает старый 200 мимо клиента
