# Эксперименты с задержками: ловушки измерения

## MemoryHigh: свободная RAM хоста не исключает синхронный reclaim

В опыте #3 (03.08.2026) на хосте оставалось 23,5 ГБ RAM, но service cgroup имела
MemoryHigh=2G. Наблюдались многосекундные задержки при pressure_cpu full=0 и oom_kill=0.
Искали причину в RAG, GIL и аллокаторе; решающим оказался рост memory.events/high и
pgscan_direct при pgscan_kswapd=0. По отчёту, изменение лимита в том же процессе дало
p99 3807 → 35 мс. Это один исторический опыт, не ожидаемый эффект любого изменения лимита.

Различающая проверка: найти cgroup через /proc/<pid>/cgroup и прочитать memory.high,
memory.max, memory.current, memory.events и memory.stat. В том опыте измеряющие подпроцессы
жили в той же cgroup и сами расходовали её бюджет. Неизвестно, повторяется ли это ограничение
в сегодняшнем окружении; сначала нужен новый снимок. Источник: [разбор perf, опыт #3 от 03.08.2026](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/archive/knowledge-20260909/workers/perf.md).

## py-spy --gil исключал саму дорогую работу

В том же расследовании ONNX Runtime отпускал GIL во время InferenceSession.run. Выборка
`py-spy record --gil` показывала Python-обвязку, но исключала нативный inference. Низкая доля
RAG в таком профиле не опровергала его стоимость. Различить удалось измерением вокруг
InferenceSession.run и профилем нативного стека; `_worker` из concurrent.futures отдельно
оказался queue.get(), то есть ожиданием пула. Источник: [разбор perf, опыт #3 от 03.08.2026](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/archive/knowledge-20260909/workers/perf.md).

Применимо при сравнении GIL-профиля с задержкой/загрузкой нативной библиотеки. Наличие SQLite
или ONNX в процессе само по себе ещё не определяет виновника сегодняшнего зависания.

## Улучшение на 600 мс оказалось удалённой функциональностью

В исследовании фронта пустая подмена Tailwind дала около −600 мс. Страница при этом лишилась
стилей, и подешевела сама раскладка. Такой опыт не измерял предложенную замену Play CDN
статическим CSS. Сопоставимым контролем оказался тот же сгенерированный CSS с сохранением
позиции в каскаде. При переносе style/link менялся также порядок применения правил.

В соседнем визуальном опыте контроль без изменений дал 0,00% различий, а исследуемая правка —
9,8%; сравнение getComputedStyle локализовало line-height на 432 узлах. Проценты относятся к
тому снимку страницы. Самостоятельный screenshot diff без контроля живого контента не давал
того же вывода. Источник: [разбор опытов audit-front](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/archive/knowledge-20260909/workers/audit-front.md).

## Сетевой baseline плавал без фикса

В #143 сохранены результаты базы 7/8 → 2/8 → 11/16 без изменения кода. Односторонний
прогон «до/после» на таком канале мог приписать фиксу движение среды. В #142 контрольный
хост отдал 1 МБ за 0,55 с, пока путь до исследуемого сервера обрывался на 16 КБ: это отделяло
общую проблему клиента от маршрута к конкретному серверу. Ни один адрес или скорость из
этих опытов не задаёт сегодняшний маршрут. Источник: [сохранённые наблюдения frontend](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/archive/knowledge-20260909/workers/frontend.md).

## Изоляция кодового replay V-558: /proc и незавершённый счётчик Claude

12.09.2026, Linux с Landlock ABI 4, Codex 0.153.4 / Claude Code 2.1.263:
разрешение Landlock на `/proc/self` оказалось разрешением каталога PID запускающего
процесса. Дочерний Python получил PermissionError на свой `/proc/self/fd`;
`unshare -Urnm` отказал на uid_map и в exec, и в bg. Поэтому pidfd-задача V-543
не могла честно выполняться на этом стенде; вместо ослабления границы взята backend/API
часть V-546. Её эталон прошёл одинаковые 93 теста снаружи и внутри границы.

`claude --bare` в этой версии прямо исключает OAuth, поддерживая API-key auth:
два старта дали 0 usage/$0/Not logged in. Удаление --bare при сохранённых private HOME,
пустых settings/MCP и файловой границе позволило использовать подписочный OAuth.
При остановке двух работающих Claude CLI через 600 с streaming assistant usage не
содержал завершённого output/total_cost_usd. Сохранить stdout недостаточно для полного
учёта стоимости оборванного хода; цена этих двух плеч осталась неизвестной.
Код обеих моделей на дедлайне прошёл 93/93, поэтому timeout нельзя превращать в
«не написала рабочий код». Условия, пробы, исходники и ограничения: [V-558](../tasks/V-558/report.md).

### V-560: причина отказа namespace и выбранный рабочий путь

При проверке V-560 vendor-bubblewrap найден по пути
`/usr/lib/node_modules/@openai/codex/node_modules/@openai/codex-linux-x64/vendor/x86_64-unknown-linux-musl/codex-resources/bwrap`.
Его наличие не даёт рабочую песочницу: `kernel.apparmor_restrict_unprivileged_userns=1`,
запуск возвращает `bwrap: setting up uid map: Permission denied`. Это запрет
непривилегированных user namespaces на этом хосте, а не отсутствие бинаря.
Владелец выбрал «как есть оставляй»: защиту не меняли. Поэтому локальный
`scripts.local_bench` проверяет sandbox до провайдеров и на этом хосте отказывает
с причиной и указанием использовать offline fixture-режим или другую машину.
Небезопасного provider fallback нет; положительная namespace-ветка здесь не доказана.
Проверить текущее состояние заново: `python -m scripts.local_bench doctor`.
Команда, точный отказ и 38 offline-проверок механизма: [V-560](../tasks/V-560/report.md).

## Полный `/tmp` tmpfs может потерять вывод уже выполненной команды (05.09.2026)

На измеренной машине `/tmp` был tmpfs размером 7.7 GiB и заполнен до 100%; Bash вместо
вывода уже исполненной команды вернул ENOSPC. Место занимали копии agent home, чужие
артефакты, вывод pytest, uv cache и review JSONL. Большие временные данные следует держать
на дисковом разделе, например `/mnt/data`: заполненный tmpfs ломает и канал результата,
и запись. Наблюдение сохранено в Git-коммите `779372efb`, `TODO.md`; тип mount и свободное
место перед действием нужно проверять заново.

## Находит ли замороженный модельный рецензент реальные дефекты (V-909, 17.10.2026)

Офлайн-замер Luna (`gpt-6-luna`) с промптом из замороженного `codex_review` на 49 диффах: 9 «плохих» по `.orchestra/tasks/V-905/rollback_rate.py` и 40 случайных чистых. Разметка Sonnet вслепую с доступом к последующей истории. Итог: recall на задачах, откатанных из-за дефекта кода, 1/2 (n=2, интервал 9–91%); реальных замечаний на чистых 13/28 = 46% (30–64%), но подтверждённых позднейшим исправлением того же места 6/28 = 21%; важность «высокая» у 1 из 28; цена ≈27 тыс. платных токенов и ≈30 с на дифф. Порог владельца пройден формально, на таком n не различимо. Факты, дорогие для повтора:
- Откаты не меряют ревью: из 9 откатанных/починенных задач 6 — политика (чистка «enterprise» 12–13.06, приватность changelog, правило владельца), 1 — документы, 1 — случайный мерж; запись о дефекте кода только у двух. Молчаливые дефекты (правки без отката) видны только через последующую историю: 6 из 40 чистых диффов содержали замечание, место которого потом исправили.
- `codex exec -s read-only` на этом хосте не запускает команд (`bwrap: loopback: Failed RTM_NEWADDR`): ревью выходит INCOMPLETE. Рабочий путь — `danger-full-access` в одноразовом снимке без истории (два коммита base/change), иначе рецензент видит откаты через `git log`. Из снимка нельзя вырезать весь `.orchestra/`: изменение каталога проектов лежит в нём, и рецензент отвечает «дифф не соответствует задаче».
- Один и тот же дифф при повторе: пилот дал suggestion, полный прогон — APPROVED без замечаний (n=1, но значит, что однопроходный recall шумный).
- `dynamic_workflow` с `schema` бракует валидный JSON, если модель обернула его прозой или ```json (`invalid JSON: Expecting value at line 1 column 1`), и тратит `max_calls` на повторы (47 из 70 вызовов, $9,99); результат шага не содержит ключа задачи — возвращайте `item` внутри ответа и разбирайте без schema.
Данные, скрипты и разметка: [V-909](../tasks/V-909/report.md).

## Замер ревью на тихих дефектах и workflow без файлов (V-918, 17.10.2026)

- Задача `dynamic_workflow` работает в git worktree `wf-…`, созданном на закреплённом коммите `repo`; `data/workflow-runs/<run>/workspaces/*/attempt-1` — лишь метаданные. В V-918 задачи не прочитали пакеты из `.orchestra/tasks/V-918/` даже после коммита. Причина прогоном не установлена. До V-925 эти worktree были ПОЛНЫМИ (`wf_run` не передавал конфиг worktree, `resolve_rule(None)` → без sparse), так что версия «sparse-копия без своего каталога» для V-918 неверна. Наиболее вероятно: задача видит только то, что закоммичено на `base_commit` переданного `repo`; если передан основной checkout, коммиты ветки воркера туда не входят. С V-925 worktree workflow частичные и включают `.orchestra/tasks/<id>/` своей задачи (по `ORCHESTRA_TASK_ID`). Для замеров надёжнее класть содержимое в промпт или гонять локальные `claude -p --tools ""` / `codex exec` с текстом через stdin (`.orchestra/tasks/V-918/llm.py`).
- Набор «тихих» плохих задач строится из git: `git blame -w` строк, изменённых фикс-коммитом, → коммит-источник (`.orchestra/tasks/V-918/mine.py`, 480 фиксов → 347 с источником); одного blame мало, нужен вердикт двух независимых оценщиков по паре (согласие 69%). Результат Luna-рецензента: recall 9/23 (39%, 22–59%), 65% реальных замечаний на чистых; но разница плохие/чистые не значима. Подробно: `.orchestra/tasks/V-918/report.md`.
