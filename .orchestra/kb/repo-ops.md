# Git, worktree, локальная работа и выкладка

## Рабочая копия и main

Worktree — другой checkout того же репозитория, а не новый проект. Перед удалением проверь
его собственные изменения, untracked/ignored данные и достижимость коммитов из main.
`git status` с одним untracked файлом ничего не говорит о сохранности остальных файлов
каталога; используй `git ls-files`. Не удаляй чужие данные вместе с временной копией.

## Merge, sync и запущенный код

Полномочия определены в [AGENTS.md](../../AGENTS.md). Merge в main, push origin, pull на
VPS и рестарт — разные действия. Сохраняй свежие чужие коммиты, не force-push. Не сообщай
«работает», проверив только git log: Python-сервис продолжает исполнять загруженный код.
После рестарта проверяй cut_names и восстановление срезанных работ.

## Частные данные и инфраструктура

База, окружение, исходные журналы и task Git не публикуются вместе с кодом. При переносе
фрагмента в отслеживаемый отчёт проверь секреты на границе публикации. Исходное отображение
частного журнала не меняй для решения задачи публикации.
SSH/адреса/роли проверяются по `~/.claude/docs/vps-registry.md`; proxy и туннели принадлежат
ai-proxy-manager, не Orchestra. Не записывай копию паролей и текущих маршрутов в KB.

## Проверка checkout и frozen head

RUNNING merge относится к принятой голове ветки, а не к будущим коммитам, которые воркер
добавит после запуска операции. После squash-merge не предполагай, что merge main обратно
в старую ветку будет тривиальным: один и тот же результат может иметь другую историю.

Перед восстановлением файла через git checkout/show сохрани текущую правку. Не используй
rollback для проверки гипотезы поверх чужого незакоммиченного состояния. Отсутствие branch
проверяй документированным кодом конкретной команды, а не обобщением «любой ненулевой = нет».

Имена из shell-строки нельзя надёжно выделить split/regex без учёта quoting и обёрток.
Не превращай диагностический поиск процесса/пути в широкую разрушительную команду.
