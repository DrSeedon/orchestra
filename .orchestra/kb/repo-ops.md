- **`normalize_merge_result` не должен превращать well-typed pre-merge отказ в `NO_COMMITS_MERGED` только потому, что target ref не изменился и `commits_merged=0`.** Инцидент `cradle-globe`: target checkout содержал `?? .orchestra/tasks/49/`; scratch дал raw `target working tree is dirty`, затем текущий normalizer заменил его на «verify the worker branch», а после очистки target тот же worker дал `commits_merged=1`. - **`uv run` не делает exec — он порождает ребёнка, поэтому `ExecStart=uv run …` ломает любой контракт systemd, завязанный на pid exec'нутого процесса (`LISTEN_PID`/`sd_listen_fds`, `sd_notify`, `MainPID`). В юнитах — прямой путь к интерпретатору.** Сервис при этом выглядит рабочим, расхождение вскрывается только там, где на pid кто-то опирается. Замер 18.08 (#324), обе стороны одной командой: `LISTEN_PID=$$ exec uv run --no-project python …` → `LISTEN_PID=2751595, pid=2751601, MATCH=False`; `LISTEN_PID=$$ exec .venv/bin/python …` → `2751602 == 2751602, MATCH=True`. На этом признаке висят усыновление агентов (`app/fdstore.py:92`) и гейт TG-моста (`app/tg_bridge.py:3751`): живой сервис проходит их только благодаря untracked drop-in `60-runtime-isolation.conf` с прямым exec, а трекнутый `deploy/orchestra.service` до #324 содержал `uv run` — на конфигурации из репозитория мост отказал бы молча. Отсюда же: **эффективный юнит смотреть `systemctl cat <unit>`, а не `cat` файла** (drop-in прячет фактический `ExecStart`), и расхождение «наблюдаемый процесс (`ps`) ≠ прочитанный конфиг» — это САМА находка, а не фон: автор #324 видел оба факта на экране одновременно и не спросил, почему они разные
- merge воркера не проходит на ровном месте → инжектированные `.claude/skills/` дёргают дерево → исключать через git common-dir `info/exclude`, не `.gitignore`. НО `info/exclude` бессилен против ОТСЛЕЖИВАЕМЫХ файлов: в репо, который версионирует свои `.claude/skills/*/SKILL.md`, инъекция = модификация трекнутого файла, дерево грязное навсегда. Правило общее: платформа НИКОГДА не пишет поверх файла, который репозиторий трекает (`workspace.tracked_paths`) — как и зеркало `AGENTS.md`. Untracked-копии (`.env`) при спавне сами попадают в `info/exclude`
- В `.gitignore` строка `workers/` глотает и `.orchestra/workers/` → нужен `!.orchestra/workers/` (строки 9-10, не «почистить»): иначе воркер молча теряет личную память или делает `git add -f`
- SHA в инструкции отката: `--is-ancestor` доказывает достижимость, но НЕ откатываемость → прогони `git revert --no-commit` на скретче + `--abort`. В hot-path доке лежал до-squash SHA, а рабочий давал конфликт
- **Переписал историю `main` при ЖИВЫХ воркерах (`pull --rebase`, синхронизация с другим контуром) → их ветки остались на исчезнувшей базе, и следующий `merge_worker` падает `FAILED` без деталей.** Симптом обманчив: `worker_wip` показывает пачку «незамерженных» коммитов, которые по СОДЕРЖИМОМУ давно в main — rebase выдал им новые SHA. Замер 14.08: синхронизация с ноутбуком переписала 4 коммита, у `grok-impl` мгновенно стало 4 фантомных незамерженных вместо одного настоящего. Порядок разбора: (1) проверить каждый подозрительный коммит ГРЕПОМ СОДЕРЖИМОГО в main, не хешом; (2) заморозить настоящий новый коммит ссылкой (`git branch preserve/<id>-<воркер> <sha>`), иначе его соберёт `gc`; (3) `switch_worker_branch(from_ref="main", force=True)` и поручить воркеру `git cherry-pick <sha>`; (4) требовать повторный прогон тестов НА НОВОЙ базе. Профилактика: синхронизировать контуры, когда у воркеров нет несмерженной работы
- Документируешь период → два прохода: `git log main` по датам (НЕ своя ветка, НЕ присланный список — моя цифра «93 коммита» потеряла 7) + `.orchestra/tasks/<id>/report.md` по каждому id: счётчик не покажет ОТОЗВАННЫЕ и отрицательные результаты, а они и есть суть
- Цена переноса репо = `du -sh .git` + `ls-files` + `remote -v`, НЕ `du -sh` каталога: untracked даёт 10-20× завышение (Parsing: 91 ГБ каталог, 7.5 МБ история)
- Деплой в каталог с `User=` в юните → сперва `find <dir> ! -user <юзер>`: чужие владельцы не мешают чтению и запуску, падает только ЗАПИСЬ в `.git`, посреди деплоя. `chown -R` со снимком прав
- Надо, чтобы агент ЗАБЫЛ устаревшее → `UPDATE sessions SET session_id=''` при ОСТАНОВЛЕННОМ сервисе, НЕ `compact_worker`: компакт просит сессию законспектировать саму себя, устаревшие убеждения переезжают без исходника
- **Коммитишь СЫРУЮ выгрузку как артефакт задачи (`.tsv`, `.jsonl`, `.csv`, дамп вызовов, лог инструментов) → сперва прогони её фильтром по ФОРМЕ секрета, а не по имени переменной:** выгрузка вызовов по построению содержит аргументы и заголовки авторизации целиком. Шаблоны минимум: `y0_`, `sk-or-v1-`, `ya29\.`, `gh[pousr]_`, `AIza`, `Bearer <25+>`. **Поиск по ИМЕНИ переменной даёт ложно-чистый результат** — дважды за день: `grep api_id` не находит `--api-id=`, а `grep KEY=value` не находит те же значения внутри JSON. Замер 12.08: `.orchestra/tasks/sol-efficiency/calls_strict.tsv` пролежал в ПУБЛИЧНОМ `origin` с двумя боевыми OAuth-токенами Яндекс.Директа чужого проекта, отдавался с `raw.githubusercontent.com` без авторизации. ### Дубли и рассинхрон

- **Частный случай, который бьёт беззвучно: ДОСЛОВНЫЙ перечень колонок, написанный дважды в одной функции** (`DROP` → `CREATE` → `INSERT` в коде починки дрейфа схемы). Добавил колонку в один перечень — новые значения молча обнулятся при первом же дрейфе: таблица есть, строки есть, а настройки вернулись к дефолтам, и выключенной окажется та самая фича, ради которой колонку заводили. Замер #314: `db.py:428-457`, шесть колонок `quota_controller_policy` в SELECT и в INSERT. Закрывать мутацией, а не вычиткой.
- Правило: одна мысль = один owner. Копия, снятая при создании, тихо расходится с оригиналом (`AGENTS.md`, `.claude/skills/`, словари статусов) → любой снимок обязан обновляться на реконнекте или генерироваться на лету. **Правишь правило, у которого есть файл-владелец → перечитай этот файл ЦЕЛИКОМ глазами, а не грепом по своей формулировке: греп слеп к копиям той же мысли, сформулированным иначе.** Замер: #184 — паттерн поймал автора трижды подряд в одной задаче, и все три копии нашёл ревьюер
- Новый рантайм: расход утёк в чужой пул → хвост `ELSE 'claude'` всегда баг; та же логика жила в НЕСКОЛЬКИХ SQL и фронтовых тернарниках. Цены рантайма с кеш-тарифом не класть в общий `TOKEN_PRICES` (Grok: `docs/grok-field-guide.md`)
- Состояния в дашборде «разъезжаются» → та же логика продублирована (словари статусов в `renderAgentItem` vs табы; `.tab-unread` в двух местах) → искать ВТОРУЮ копию, а не подкрашивать первую. Решение и рисование держать в одной функции
- «Мёртвый» модуль оказался живым → грепали строку, а читалось через 12 функций (fallback + дашборд) → перед удалением грепать РЕАЛЬНЫЕ импорты и fallback-пути широко (app/, tests/, static/, манифесты), проверяя не «кто ЗОВЁТ», а «кто читает ДАННЫЕ». В #65 два упоминания `system_prompt` в JS оказались про чужой payload — вайтлист по грепу убил бы всю правку. **Зеркальная ошибка (#176): греп засчитывает МЁРТВЫЕ вызовы за живые** — кластер функций может звать сам себя по кругу, не имея ни одного входа снаружи. Приговор выносить графом вызовов по AST и отдельно проверять динамическую диспетчеризацию (`getattr` с вычисляемым именем): греп дал 357 строк, AST-граф — замкнутый на себя кластер и 364 строки (43.2% пакета)
- Правило и его костыль живут в РАЗНЫХ файлах (правило в `CLAUDE.md`, `!.orchestra/workers/` в `.gitignore`) → перед удалением правила грепни костыль: жив костыль без объяснения → следующий агент уберёт костыль, а не правило
- Правило в `CLAUDE.md` и промпт роли в `.orchestra/pipelines/` расходятся → воркер слушается ПРОМПТА: `research-method.md` велел «Run in /tmp», и rag-max положил 1.6 ГБ в tmpfs=RAM вопреки доке. Правишь правило про поведение агентов — грепни `.orchestra/pipelines/*/prompts/` на ту же тему

### Воркеры и оркестрация

- Воркер игнорирует твой ответ → plain text в чате = сообщение ЮЗЕРУ, воркер его не видит → даже «ок, работай» слать через `send_message(to="worker")`
- Воркер после merge «залипает» → сработал `needs_switch` guard → `merge_worker(next_task_id=...)` одним вызовом
- Пустое падение воркера (`stop_reason=error`, no output, журнал чист) → ПЕРВЫМ делом `GET /api/usage`, не инфраструктура. Коммитить за него руками через `worker_wip`
- Объём выхлопа задаёт ФОРМУЛИРОВКА задания, а не модель: открытое «исследуй и предложи» = заказ на research; точное ТЗ (файл+строка+образец) дало 6 строк прода
- Короткая фраза юзера («добей прошлую») читается двояко и меняет ЗАДАЧУ → спросить одной строкой, а не выбирать молча; отмена — только явное «отменяю #N»

### Чужая машина (ноут юзера — рабочий, не стенд)

- Тяжёлые прогоны только последовательно и под потолком памяти: `systemd-run --user --scope -p MemoryMax=2G`, одна модель за раз, `nice -n 15`, не больше 2-3 параллельных. `nice` НЕ защищает от вытеснения по ПАМЯТИ — дважды за сутки выдавили чужое обучение сети (RSS рос 3.5→4.2 ГиБ), а ONNX-бенчмарки грели CPU до 93°C. Потолок — в ПОСТАНОВКУ задачи, не в напоминание вдогонку
- Гейт свободной памяти считать по `MemAvailable` из `/proc/meminfo`, НЕ по `free`: при page cache они расходятся в 2-3 раза
- «Занята ли машина» по ОДНОМУ срезу — не проверка: чужое обучение держало 88% CPU при RSS 0.46 ГиБ (буферы mmap на диске) и в топе по памяти было НЕВИДИМО → смотреть CPU И память, плюс `pgrep -af` по именам чужих процессов
- `/tmp` на ноуте — **tmpfs, то есть RAM**: 1.6 ГБ «файлов» физически занимали оперативку. Перед тяжёлой записью `findmnt /tmp`; большое класть на `/mnt/data`, НЕ в `~/.cache` (корневой раздел забит на 99%)
- Загружена ли ML-модель в процесс → anonymous RSS (`/proc/<pid>/smaps_rollup`) + лог загрузки, НЕ `find` по `.onnx`: ONNX читает веса в heap. Кеш по дефолту в `/tmp` — при ребуте умрёт
- `killpg` по СОХРАНЁННОМУ числовому PGID после выхода лидера убьёт чужую группу (PGID переиспользуются) → сигналить по живому handle; `pkill -f` матчит процессы всей системы
