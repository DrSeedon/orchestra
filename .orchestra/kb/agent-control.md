# Агенты: роли, промпты, личные заметки

## Источник промптов

[pipeline.yaml](../pipelines/default/pipeline.yaml) выбирает роли, модули, навыки и effort.
Тексты принадлежат `prompts/base.md`, `prompts/roles/`, `prompts/modules/`, `prompts/skills/`
в том же pipeline. [prompting.py](../../app/prompting.py) и [manager.py](../../app/manager.py)
собирают инструкции и память. Личный overlay содержит только особенности конкретного агента,
не копию общей политики. Версии в сохранённом system_prompt не доказывают актуальность
работающего native thread; проверяй сборку и жизненный цикл нужного рантайма.

## Роли и результат

`orchestrator` и `sub-orchestrator` координируют; `worker` исполняет определённую задачу;
`full-cycle` ведёт согласованный результат с исследованием при необходимости; `reducer`
собирает fan-out доклады. Точные возможности определяет pipeline, не исторический список
«постоянной команды». Все роли получают общий модуль knowledge и оглавление своего проекта.

[Создание и перенос агента](../pipelines/default/prompts/skills/orchestra-agents.md): сохраняй
его личный файл по имени и проекту. Не клонируй чужую инструкцию вместо выбора роли.
Исследование заканчивается отчётом; ни KB-запись, ни личная заметка не являются квитанцией
приёмки. Правила не предлагаются автоматически после каждой задачи.

## История после compaction/restart

Актуальные решения и незавершённая работа принадлежат текущей задаче. Статус воркеров
проверяется через платформу; старый отчёт не является live snapshot. Не создавай параллельные
суточные обзоры и обязательные сессионные хроники. Срезанные рестартом ходы проверяются
по `cut_names`; это не доказательство отказа работника выполнить задачу.

## Проверка доставки правила всем адресатам

Перед правкой общего правила найди его адресатов в pipeline.yaml/modules и собери итоговый
промпт каждой затронутой роли. Уникальное правило одной роли не надо размножать по общим
модулям. При переносе удали узкую копию, иначе агент получит две разные версии одного правила.

Проверять присутствие случайного ключевого слова недостаточно: сравни смысл, условие
срабатывания и исполняемый путь. ROLE_SYSTEM_PROMPT используется и при создании, и при
повторной сборке; проверка только нового spawn не подтверждает обновление существующего
агента. Полный пользовательский override нельзя молча принять за генерируемый шаблон.

Идентификатор строки Orchestra sessions.id отличается от native sessions.session_id.
Имя агента может изменяться: durable фоновые задания и доставки привязываются к постоянному
ID. Неправильный join по native UUID либо повторно используемому имени даёт чужую историю.

Источники консолидированных наблюдений: [prompt-engineer](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/archive/knowledge-20260909/workers/prompt-engineer.md), [kb-index-injection](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/workers/kb-index-injection.md), [report](https://github.com/DrSeedon/orchestra/blob/9a1735f1695519a445f393802c2154bd37337e38/.orchestra/tasks/82/report.md).

## Старые схемы workflow

Старая fleet-looping.png рисовала обязательную цепочку RESEARCH → PLAN/Codex review →
IMPLEMENT → VERIFY с возвратом в исследование. Она не является текущим контрактом full-cycle:
глубину выбирают по задаче, review необязателен. architecture.png также содержит прежние
модельные имена и HTMX; актуальные роли и UI проверяются по pipeline и текущему frontend.
Оригиналы доступны через history.md, не используются как новые инструкции.
