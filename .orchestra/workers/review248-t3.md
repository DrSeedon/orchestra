# review248-t3 — личные заметки

## Зонд по Orchestra-БД без pytest — `ORCHESTRA_DB_PATH`
`app/db.py:_resolve_db_path()` читает `ORCHESTRA_DB_PATH` из env. Значит любую машину
состояний (`tm`, `merge_operations`, `db`) можно гонять standalone-скриптом на свежей БД,
не изобретая фикстуры и не упираясь в autouse-гард из #235:

```
ORCHESTRA_DB_PATH=/home/kesha/orchestra/data/probe/x.db uv run python probe.py
```

Внутри — `sys.path.insert(0, <свой worktree>)`, `init_db()`, `tm.ensure_project`,
`tm.create_task`, `db.save_session`. Это дешевле и честнее, чем читать код: в #248 T3 так
получены все три блокера. Скретч убирать `trash`, не `rm -rf` (хук режет `rm -r` вообще,
включая внутри heredoc-скрипта — `shutil.rmtree` тоже лучше не звать, проще плодить
`repo0/repo1/...` и снести каталог целиком).

## Личные заметки ИМПЛЕМЕНТЕРА читать ДО диффа
`.orchestra/workers/<автор>.md` — там он честно пишет то, чего нет ни в DONE, ни в постановке
интегратора. В #248 T3 автор прямо назвал конфликт своего оракула со старым зелёным
`tests/test_mcp_stdio.py`, а в списке «известных падений» от интегратора этого теста не
было. Файл читается за 20 секунд и дал целый блокер.

## Причинность падения теста доказывать мутацией, а не датой коммита
«Тест покраснел из-за этого диффа» — гипотеза. Снять правку (`cp F F.bak` → замена →
`mv F.bak F` → `touch F`), прогнать целевой тест на обоих плечах и предъявить обе строки:
зелёную без правки и красную с ней. Считать маркер ДО прогона и ПОСЛЕ отката, уникальность
якоря проверять в той же команде.
