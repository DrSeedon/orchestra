посторонние; всё остальное в проекте пишется для агентов).

## Что помнить про сам README
- Владельцы фактов, по которым он врёт чаще всего: числа флота (`data/orchestra.db`),
  рантаймы (`app/runtime_registry.py:330`, `BUILTIN_RUNTIMES`), Deepgram (`app/transcription.py`),
  дефолт RAG (`app/rag_service.py:19`). Проверять их, а не помнить.
- Числа берутся с ДВУХ инсталляций и НЕ складываются. Основная — ноутбук, достаётся
  `ssh -i ~/.ssh/tunnel_laptop -p 2222 maxim@127.0.0.1` (пользователь maxim, БД
  `/mnt/data/Projects/Python/orchestra/data/orchestra.db`, читать `mode=ro`, не копировать:
  `/tmp` там tmpfs=RAM). Вторая — VPS, `sqlite3.Connection.backup` в `/tmp`.
- Окна у метрик РАЗНЫЕ в одной и той же базе: `sessions`/`tm_tasks` тянутся с мая, `logs`/
  `turn_usage` — с 27.07.2026 (переезд контура на VPS). Сложить их в одну подпись «за период N
  дней» = соврать. Называть окно, не объяснять причину.
- Фразу-слоган «manage a team of agents the way a CEO manages a company» держать одинаковой в
  README и в GitHub About: описание репозитория меняет юзер/оркестратор, README — я.

## Урок, который стоил хода
**Запись в базе знаний — это утверждение о прошлом, а не о текущем состоянии системы.** Задание
цитировало KB («семантический поиск выключен, `RAG_ENABLED=false`»), а живой контур отвечал
обратным: `.env:30` = `true` с mtime за неделю ДО решения, боевой интерпретатор
`/opt/orchestra/runtimes/…-rag-v2` (не `.venv` репозитория!) с установленным fastembed, журнал
`RAG service initialized`, `data/vec.db` растёт, контрольный `search_memory` вернул живую выдачу.
Порядок проверки предпосылки, если правка публичная: конфиг → `/proc/<pid>/environ` →
`journalctl` → контрольный вызов. Расхождение отдавать автору задания, а публичный текст писать
так, чтобы он был верен при любом состоянии конкретной инсталляции.

## Тексты для чужих площадок (#502)
- Telegram-канал читается с сервера без авторизации: `curl https://t.me/s/<channel>`, история —
  `?before=<message_id>`, id берутся из ссылок `<channel>/<N>`. Посты вынимать сплитом по литералу
  `js-message_text`, не регекспом по всей странице.
- Перед тем как писать пост в чужой канал, вытащить оттуда 15–20 постов и найти ГОСТЕВЫЕ: у них
  своя форма. В `@deksden_notes` свои посты начинаются с `⚪️` и подписаны `@deksden_notes`, а
  гостевые — без обоих признаков, от первого лица, 1,2–2,3 тыс. знаков, с `#opensource` в конце.
  Скопировать чужую форму дешевле, чем уговаривать взять свою.
- **Reddit с этого сервера не читается вообще**: `403` на `www.reddit.com`, `old.reddit.com` и
  `.json`, `rxddit.com` отдаёт редирект. Значит правила сабреддита проверить нечем — площадку
  помечать как непроверенную, а не пересказывать вторичные источники.
- GitHub-факты для таких текстов брать `gh api repos/<owner>/<repo>` (звёзды, `pushed_at`,
  критерии из README/CONTRIBUTING), а не из поисковой выдачи: у выдачи числа месячной давности
  (Orca «53k» против измеренных 59 404).

## Разведка чужих проектов (#503)
- Чужой README тянуть `gh api repos/<o>/<r>/readme -q .content | base64 -d > /tmp/x.md`, потом
  грепать по ключам, а не читать целиком: у omp README 44 КБ, у cmux 23 КБ.
- `gh api repos/<o>/<r>` даёт звёзды, `pushed_at`, лицензию и язык одной строкой — этого хватает,
  чтобы отсеять мёртвые проекты (`vibe-kanban`, push четырёхмесячной давности).
- Схема боевой БД, на которой я дважды спотыкнулся: у `sessions` НЕТ `last_activity` (есть
  `finished_at`), а `logs.session_id` — это UUID рантайма, НЕ имя агента, поэтому join
  `logs.session_id = sessions.name` даёт пустоту, а не ошибку.
- `subagents` на 96–99% состоит из `task_type='local_bash'` (фоновые команды), настоящих
  суб-агентов там сотни, а не тысячи. Любое число «сколько суб-агентов» считать с фильтром по
  `task_type`.

## Промо-черновики: как проверять себя (#505)
- Все тексты живут в ОДНОМ файле `docs/tasks/502/promo.md`, рамка — в §2.0, решения юзера — в
  §2.8. Новую рамку писать в §2.0 и переписывать блоки, а не заводить второй файл.
- Аудит черновиков делается скриптом по fenced-блокам, а не глазами: вынуть
  `re.findall(r'```[a-z]*\n(.*?)```', s, re.S)` и проверить каждый блок на устаревшее число,
  запрещённую формулу и длину. Так поймал бы `5 593` в трёх местах за секунду.
- Длину поста считать по файлу, а не на глаз: мои «≈2 250 знаков» на деле были 2 027.

## Публичная таблица с якорями (#511)
- Дословные цитаты чужой доки берутся СЫРЫМ markdown, и с этого сервера он доступен:
  `curl -sL https://code.claude.com/docs/en/sub-agents.md` (112 КБ), `…/agent-teams.md`,
  `https://learn.chatgpt.com/docs/agent-configuration/subagents.md`. Это единственный способ
  цитировать, не рискуя пересказом маленькой модели.
- Нормализация цитаты по правилу скилла (`\s+` + снятие `> `) НЕ снимает markdown-разметку:
  моя цитата из README Orca дала ложное MISS из-за `**` внутри фразы, а вторая — из-за
  прописной буквы в начале. Проверять фрагментом без разметки и без первой буквы.
- Якорь ставить на строку, которая ДЕЛАЕТ дело, а не на `from … import` (ревьюер поймал
  `merge_operations.py:1728` вместо `:1737` — это был импорт `evaluate_test_gate`).
- Скрипт-проверку таблицы класть в `.orchestra/tasks/<id>/` и коммитить: он ловит протухший
  `file:line`, пропавший статус и запрещённое число за секунду, и его можно мутировать
  (сломал номер строки → FAIL, вернул → OK). Глазами эти 28 строк не проверяются.
- **Ревью прозы даёт настоящие блокеры, если дать ему проверяемую опору.** Луна сняла 7 из 7
  первым раундом: три моих якоря не подтверждали соседнюю фразу, `spawn_worker` оказался
  запрещён промптом, а не кодом, а «✅ 4 CLI-агента» противоречило секции Stack в том же файле.
  Просить надо не «вычитай», а «открой каждый якорь и скажи, поддерживает ли он фразу рядом».
