# orchestra-cleanup — личная память

## `rg -rn` — это НЕ «рекурсивно с номерами»
В ripgrep `-r` = `--replace`. `rg -rn "app\.ia\.knowledge"` подставляет `n` вместо каждого
совпадения, и вывод выглядит как настоящий код: `from n.knowledge import KnowledgeService`.
Я чуть не процитировал этот несуществующий импорт как file:line в отчёте.
Рекурсия в rg включена по умолчанию — нужен просто `rg -n`.

## Где на самом деле лежит живое состояние базы знаний
`~/.local/state/orchestra/knowledge-v1/` (не в `data/`, не в репозитории):
- `runtime-state.json` → `active_owner` (`canonical` открывает ветку `app/routes/memory.py:40`);
- `project-knowledge-owner.json` → свой `active_owner` (`project-local` включает чтение
  `.orchestra/kb/records/`) и `project_heads` по проектам;
- `scope-registry.json` → соответствие scope → `repository_root` и `canonical_project_id`.
Два независимых гейта: чтобы понять, читается ли путь, надо посмотреть ОБА, код по одному
файлу ответа не даёт.

## Проверять «читается ли это» вызовом, а не только грепом
Быстрее всего доказать живой путь чтения дёрнув `curl -s -X POST
http://127.0.0.1:8888/api/memory/search -d '{"scope":"<repo>","query":"...","limit":3}'` —
read-only, отвечает за секунды и сразу показывает, из какого хранилища пришёл ответ
(`source_class`, `source_path`). Грепом это заняло час.

## `du` врёт на каталогах из тысяч мелких файлов
`.orchestra/kb/records` — 51 МБ по `du` и 7.6 МБ реального JSON: 12 759 файлов по ~600 Б,
каждый занимает блок 4 КiB. Прежде чем называть размер в отчёте, суммируй полезную нагрузку
(`find -printf '%s'` или проход парсером), а `du` подавай отдельно как «на диске».

## В этом репозитории 18+ worktree'ев одного дерева
Любой тяжёлый каталог под git умножается на их число: те же `records` весят 665 МБ по всем
worktree'ям. Считая экономию от удаления — считай оба числа, иначе занизишь в двадцать раз.
`git worktree list` даёт актуальный счёт.
