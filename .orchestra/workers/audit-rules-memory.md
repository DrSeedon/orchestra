# audit-rules-memory — личная память

Профиль: аудит поведения агентов по логам. Читаю много, пишу мало, вывод обязан висеть
на числе. Ниже — только то, что стоило мне времени и понадобится снова.

## `scope` в БД ≠ репозиторий воркера (#188)
`sessions.scope` и фактический репозиторий worktree могут расходиться, и по имени каталога
worktree этого не видно. Замер: `seo-cro` имел `scope=/home/kesha/projects/seedon`, а его
worktree принадлежал `seedon/site/.git`; `infra` — `seedon/infra/.git`. Из-за этого
`load_worker_memory` 8 суток читал несуществующий путь, а агент отчитывался «Memory: updated».
**Перед любым выводом про пути сверяй:**
```bash
git -C <worktree> rev-parse --path-format=absolute --git-common-dir   # → <repo>/.git
```
и сравнивай `dirname` с `sessions.scope`. Из 30 живых воркеров расходились 3 — то есть это
не экзотика. Имя каталога worktree (`home-kesha-projects-seedon-site`) намекает на репозиторий,
но НЕ является доказательством: `scope` пишется отдельно и может указывать на родителя.

## Удаляешь по признаку «этого нет в БД» — перечитай БД ПЕРЕД удалением (#188)
Анализ идёт по снимку (`Connection.backup`), а снимок стареет за часы. Замер: по снимку 11:54
файл `docs/workers/tg-readability.md` попадал в список «агента не существует», а в свежей копии
через два часа агент был (103 имени → 107). Удалил бы живую память по устаревшему списку.
**Правило: снимок — для счёта, свежая копия — для приговора.** И сверяться надо с ДВУМЯ
источниками: живая БД И холодный архив `/home/kesha/orchestra-archive/`.

## Хоронишь правило — трассируй до КОНЦА, а не до первого подтверждения (#188)
Объявил мёртвым правило «alias `opus` в сохранённой модели не использовать», потому что нашёл
`ALIASES["opus"]` в `app/models.py`. Ошибся: алиасы применяет только `resolve_model()` на ВХОДЕ,
а сохранённую модель читает `get_model_spec()`, которая на `'opus'` бросает `ValueError`.
Правило защищало реально падающий путь, находку пришлось отзывать публично.
**Признак опасности: правило говорит про КОНКРЕТНУЮ ветку («в сохранённой модели», «на резюме»,
«при откате»), а я проверяю существование символа вообще.** Существование ≠ достижимость по той
ветке. Проверка на 10 секунд, которая бы спасла: не `grep`, а прогон по той самой ветке —
`python3 -c "from app.models import get_model_spec; get_model_spec('opus')"`.
Отсюда общее для аудита: **перед публикацией списка «на удаление» прогнать каждый пункт
исполнением, а не чтением.** Моя доля ложных срабатываний при чтении — 1 из 7 (14%).

## Шум метрики split-half считается ТОЛЬКО по до-периоду (#188)
Считал по объединённому пулу до+после — эффект попадал в оценку «шума». Направление ошибки
несимметрично: для «есть прирост» это консервативно, а для «эффекта нет» — либерально,
поэтому ложным получается именно вывод об отсутствии эффекта. После пересчёта запрет,
который я объявил сработавшим, порога не прошёл. Правило уехало в `CLAUDE.md` (`93409db`),
здесь держу причину ошибки, чтобы не повторить в другой форме.

## p-value по дням при n≈8 — не доказательство
Перестановочный тест требует обменности дней при нулевой гипотезе; при тренде, меняющемся
составе агентов и разном дневном объёме её нет. Что работает вместо него и не разваливается
на ревью: контрольная группа (проект/агенты БЕЗ правила), плацебо-разрезы фиктивными датами
внутри до-периода, шум по до-периоду. Все три пережили два раунда Codex; p-value — нет.

## Корпус логов: как собирать
Живая БД `/home/kesha/orchestra/data/orchestra.db` (только `mode=ro` + `Connection.backup`)
даёт ~15 суток; глубже — только холодный архив `/home/kesha/orchestra-archive/*.json`
(по файлу на сессию, `{session:{...}, logs:[{ts,type,content}]}`). Вместе ≈80 тыс. записей.
Формат `logs.content` для `type='tool'`: `ToolName: {json}` — парсится как
`re.match(r'^([A-Za-z_]\w*):\s*(\{.*)$', content, re.S)`. Скелет корпуса, который переживёт
следующую задачу, — `/tmp/corpus.py` в этой сессии; при новом заказе воссоздать за 5 минут,
не изобретая парсер заново.
