## (a) ГЛАВНЫЙ ВОПРОС — gzip против `RequestCensusMiddleware`. **Опровергнуто, дефекта нет**

### Что утверждал автор
gzip добавлен последним → стоит самым внешним → Census видит `http.response.start` раньше
и придерживание кадра его не касается.

### Что проверено на РЕАЛЬНОМ `app.main` (не на стенде)

**1. Фактический порядок стека — из построенного приложения, а не из рассуждения:**

```
uv run python -c "from app.main import app; app.build_middleware_stack()"
0 ServerErrorMiddleware
1 starlette.middleware.gzip.GZipMiddleware      <- внешний
2 app.main.AuthMiddleware
3 app.main.RequestCensusMiddleware              <- внутренний
```

Census — ВНУТРЕННИЙ. Значит его `send_wrapper` является аргументом `send` для gzip: Census
получает кадр от приложения ПЕРВЫМ и передаёт наверх. Придерживание кадра в gzip физически
не может сдвинуть классификацию. Обоснование автора верно.

**2. Живой сокет + настоящий SSE-роут `/api/sessions/{name}/stream`** (не синтетический
эндпойнт стенда), настоящий `drain_mutating_requests()`, два плеча — gzip и nogzip.
Скрипт: `/tmp/t197probe/probe_real_sse_drain.py`.

| Наблюдение | gzip | nogzip |
|---|---|---|
| SSE сжат? | `false` | `false` |
| Первые байты видны в открытом виде (инкрементальность) | `true` | `true` |
| Census во время SSE | `mutating=0, streams=1` | `mutating=0, streams=1` |
| Держащий мутирующий запрос в полёте | `mutating=2, streams=1` | `mutating=2, streams=1` |
| После закрытия потока | `mutating=0, streams=0` | `mutating=0, streams=0` |

**Плечи побайтно совпадают.** Реклассификация «мутирующий POST → поток» по `content-type`
работает при активном gzip; утечки счётчика нет.

**3. Контрольное плечо разрешающее, а не отказное** (требование методики): без gzip провод
даёт 40 020 Б, с gzip — 115 Б на том же теле; на статике 574 223 → 143 330 Б. Плечи
различимы, значит проба меряет предмет, а не саму себя.

**4. Три прогона на плечо** (асинхронный код): `counter_while_inflight=1`,
`counter_after=0`, `sse_counter_after=[0,0]` — одинаково во всех шести прогонах.

**Оговорка о честности пробы.** В моих прогонах `drained: false` — это АРТЕФАКТ пробы:
эндпойнт `/api/probe_drain_now` сам является мутирующим и считает себя
(`is_mutating_path('POST','/api/probe_drain_now') == True`), поэтому изнутри счётчик не
достигает нуля никогда. Настоящий `/api/restart` из счёта исключён
(`_CENSUS_EXEMPT_PATHS`, проверено вызовом: `is_mutating_path('POST','/api/restart') ==
False`). Доказательством служат САМИ СЧЁТЧИКИ, а не булев ответ дренажа.

**5. Оракул автора не вакуумный.** `test_production_app_registers_gzip_middleware` читает
настоящий `app.main`, а не стенд. Мутация (gzip перенесён внутрь, регистрацией первым):

```

grep -c маркера ПОСЛЕ отката = 1
зелёный повтор всей сьюты -> 6 passed
```
Откат в той же команде, `touch` файла сделан. Оракул ловит дефект.

## НАХОДКИ

### [suggestion] Оракул сжатия зелен на фикстуре, которая жмётся в 72 раза лучше живого файла

**Файл:** `tests/test_static_compression.py:36-39, 85`

Фикстура — повторяющаяся строка:
```python
PlainTextResponse("function orchestraDashboard() { return 42; }\n" * 4000, ...)
```
Замер (`gzip.compress(level=9)`):

| тело | до | после | коэффициент |
|---|---|---|---|
| фикстура стенда | 180 000 | 608 | **296.1×** |
| настоящий `app/static/js/app.js` | 442 704 | 107 392 | **4.1×** |

Ассерт всего лишь `wire_gz < wire_plain / 2`. Между 296× и 2× — три порядка запаса,
поэтому тест останется зелёным при ЛЮБОЙ деградации сжатия вплоть до почти полной.
Это ровно грабля из `CLAUDE.md` («293× против 5.1 у настоящего текста»).

**Сценарий отказа:** кто-то поднимает `minimum_size` выше размера `app.js`, или ставит
`compresslevel=0`, или добавляет `application/javascript` в исключения — реальная статика
перестаёт сжиматься, пользователь снова везёт 574 КБ по каналу с 17% потерь, а
`test_static_is_gzipped_and_shrinks_over_the_wire` печатает `passed`.

**Чем закрыть (1 строка):** отдавать в фикстуре настоящий
`Path("app/static/js/app.js").read_text()` и требовать `wire_gz < wire_plain / 3`. Тогда
порог (3×) стоит рядом с фактическим значением (4.1×), а не в трёх порядках от него.

*Смягчающее:* сама фича работает — измерено мной независимо сырым сокетом на реальных
ассетах: 574 223 → 143 330 Б (**4.01×**), что согласуется с заявкой автора (829 751 →
227 573, 3.6×). Дефект в ОРАКУЛЕ, не в реализации.

### [suggestion] Не-SSE потоки теряют инкрементальность под gzip

**Файл:** `app/main.py:476` (`GZipMiddleware`), проявляется на `app/routes/system.py:1735`

Starlette освобождает от сжатия только `text/event-stream`. Любой другой
`StreamingResponse` буферизуется дефлятором: замер на 40-кусковом `text/markdown`-потоке,
искусственно придержанном посередине —

| | ранние байты | виден ли `chunk-0000` |
|---|---|---|
| gzip | 253 (только заголовки) | **нет** |
| nogzip | 3 210 | да |

То есть первый кусок не доезжает до клиента, пока генератор не закончит.

**Сценарий отказа (сегодня отсутствует, завтра вероятен):** появляется потоковый роут с
долгим генератором и не-SSE типом — например, выгрузка журнала `text/plain` или
построчный отчёт, — и он начинает отдавать всё одним куском в конце вместо построчного
вывода. Пользователь видит «висит», а не «идёт».

**Почему НЕ blocking:** потоковых роутов в проде ровно два (`grep -rn "StreamingResponse"
app/routes/`): SSE (исключён Starlette) и `/api/report_bug` — конечный документ, который
никто не потребляет инкрементально, и он приходит целиком (проверено выше). Живого
потребителя у дефекта нет.

**Чем закрыть, если решите:** явно расширить исключения
(`GZipMiddleware` не принимает свой список в 1.1.0 — потребовалась бы обёртка), либо просто
знать об ограничении и не добавлять долгих не-SSE потоков. Я бы сегодня НЕ трогал: код
ради несуществующего потребителя противоречит философии проекта.
