# V-779 — загрузка дашборда и аналитика

## Что задерживало запросы

Аналитика не входит в начальный bootstrap: `app.js` запускает список сессий и полосу расхода, а `analytics.js` запрашивает `/api/usage/analytics` при открытии модалки. По замерам оркестратора `/api/usage` занимал 0.15 с, `/api/sessions` — 0.8–1.5 с, аналитика — 38 с без параметров, 21 с при `days=1` и более 60 с для присланного `period=7d`. Endpoint принимает параметр `days`; `period=7d` игнорируется и фактически использует default `days=7`. Начальная отрисовка списка ждёт `Promise.all` для `/api/sessions` и `/api/stats`. У `usage_analytics_endpoint` синхронный `build_usage_analytics()` выполнялся прямо в `async`-обработчике, поэтому длинная аналитика занимала event loop и задерживала чат/SSE и другие API. Запрос не занимал общий executor: раньше он вообще не использовал executor.

Источник основного времени — `_retention()` в `app/usage_analytics.py`: `MIN(ts), MAX(ts)` по всем `status`-логам с `content LIKE '%turn ended%'`. До правки план на живой БД показывал `SCAN logs USING INDEX idx_logs_status`; индекс начинается с `session_id`, поэтому запрос без `session_id` просматривал все строки этого status-индекса. Выражения `date(column)` также обходили raw timestamp-индексы на `turn_usage`, `subagents`, `tool_errors` и `voice_costs`. Запрос по `tm_tasks` использует существующий статусный индекс и занимал около 0.04 с после индексирования основных путей; дополнительный индекс для него не добавлялся.

Тот же проход по status-логам был в начальном `/api/sessions`: `manager.list_sessions()` вызывает `get_last_turn_map()` при каждом обновлении списка, а запрос вычислял последний ход по всей истории `logs`. Для исходного запроса план тоже показывал скан `idx_logs_status`. `/api/sessions` уже исполняется через `asyncio.to_thread`, как и `/api/stats`; причина задержки сессий была в повторном SQL-проходе, а не в блокировке event loop. Аналитика, напротив, блокировала event loop до изменения.

Изменения V-761/V-760 не объясняют 55 секунд профиля. На актуальном `main` профиль `model_speeds` читал `turn_usage` через существующий timestamp-индекс; после индексирования helper занимал 0.002–0.003 с. Цены кэша не пересчитываются внутри агрегатора аналитики: он суммирует уже сохранённый `cost_usd`. Замер `/api/usage` оркестратора также был 0.15 с.

Дополнительный профиль начального `/api/stats` на той же backup-копии показал 3.960 с в `get_stats()`. Запрос `COUNT(*)` по `logs` использовал покрывающий `idx_logs_session`, но всё равно проходил все события всех сессий. По указанию владельца поле `total_logs` и этот COUNT удалены. После удаления оставшаяся агрегация полей сводки заняла 0.025 с на копии. Поиском `rg` просмотрено 22,038 Python/JS/TS/HTML/shell/config-файлов под `/home/kesha/projects` и `/home/kesha/orchestra/scripts`; чтения `total_logs` не найдено (`total-logs-callers.log`, `rg_exit=1`). В найденных ссылках на `/api/stats` были тесты PhotoServer/kiosk, тестовая transport-probe (она читает свои `rows`, `integrity`, WAL и reconnect-поля), readiness probe, игнорирующая тело ответа, и blueprint DnD. Namespace `/demo/groom/api/stats` у groom-demo-bot — другой маршрут. Скан включал все обычные source/config-файлы этих каталогов, исключал VCS, кэши, данные и build outputs; удалённые артефакты в старом `.uv-cache` вызвали ошибки в более широком проходе, поэтому caller-аудит опирается на source-only результат без таких ошибок. Файлы с результатом: [callers-source-search-final.log](callers-source-search-final.log), [total-logs-callers.log](total-logs-callers.log), [bootstrap-helpers.log](bootstrap-helpers.log), [bootstrap-helpers-after.log](bootstrap-helpers-after.log).

## Изменение и жизненный цикл

`db.init_db()` идемпотентно создаёт шесть expression/partial индексов и на существующей схеме v3, и на новой. `idx_logs_turn_end_day` покрывает аналитику: ключи `date(ts), session_id, ts` обслуживают временные окна и всю историю terminal-turn строк. Отдельный `idx_logs_last_turn(session_id, ts)` использует точный prefix-фильтр `turn ended%` из `get_last_turn_map()`, исключая повторный проход по чужим status-строкам. Остальные индексы соответствуют фильтрам `date(ts)` для `turn_usage`, `subagents`, `tool_errors` и `voice_costs`. `/api/stats` сохраняет session/cost/token агрегаты, но больше не считает и не возвращает `total_logs`; аудит не нашёл читателей этого поля в других проектах или scripts. Числа и границы оставшихся метрик аналитики не меняются.

`/api/usage/analytics` теперь выполняет SQLite-снимок в отдельном однопоточном executor. Соединение SQLite остаётся локальным одному расчёту и закрывается при выходе из `build_usage_analytics`; сессия не разделяется между запросами. Новый regression-тест подтверждает, что медленный stub не блокирует event loop и что запрос передаётся не в default executor. Query-plan тесты проверяют фактическое использование индексов, без порога времени в CI.

Перезапуск не выполнялся, live SQLite не изменялась. Все изменения — Python/SQLite; они начнут действовать только после следующего перезапуска, инициированного владельцем. JS/CSS не менялись. Следующий запуск построит log-индексы на существующих данных; измерено 88.652 с + 1.048 с на backup-копии при одновременном тестовом CPU load.
