# V-1191 — ложная post-fix тревога после V-1174

Дефект подтверждён на исходном коде и исправлен минимально. Живые данные,
provider CLI, сбросы, сервисы и рестарты не использовались.

## Причина и изменение

Запрос с `failed` в URL проходит фильтр слов ошибок в `collect_journal_events`,
даже если ответ успешный. V-1174 уже распознаёт полный исходный journal access
record как `successful HTTP access log`: `aggregate` правильно отправляет его
в шум. Но `post_fix_verdict` исключал лишь отдельные другие классы шума.
Поэтому старая запись в `fixes` приводила к ложному повторению независимо
от отсутствия новых кандидатов на тревогу.

На синтетическом примере получается ровно сигнатура из задания:

```text
INFO: <N>.<N>:<N> - "GET <PATH> HTTP/<N>" <N> OK
```

В `app/error_watch.py` существующий набор исключений post-fix переименован
из `_EXPECTED_HUB_NOISE` в `_POST_FIX_EVENT_NOISE` и дополнен одним классом:
`successful HTTP access log`. Используется прежний `_event_noise`, проверяющий
источник `journalctl` и полное исходное сообщение. Нормализатор, HTTP regexp,
порог тревоги и формат состояния не менялись.

Остальные классы шума не исключаются автоматически из наблюдения фикса.
Ошибки и отказы продолжают считаться; исключать всю нормализованную сигнатуру
нельзя: даже `500 OK` и `200 OK` превращаются в один ключ после замены чисел.

## Регрессии и состояние

Добавлены 14 синтетических проверок в `tests/test_error_watch.py`:

- Реальная цепочка journal JSON → фильтр → нормализация → агрегация → scan →
  post-fix → сохранение и повторная загрузка состояния. Подменён только запуск
  journalctl; SQLite создаётся тестами, ссылки на задачи подменены.
- Старый ключ фикса V-1174 и старое уведомление в `alerts`; открытое и завершённое
  окно; присутствующий и отсутствующий старый `recurrence_reported`.
- Успешные записи не дают повторения; завершение окна сообщает отсутствие
  повторения ровно один раз; dry-run не меняет файл состояния. Пропадание записей
  из окна сохраняет метаданные фикса и не вызывает уведомления.
- Настоящая journal-ошибка `500 OK` с той же сигнатурой и два варианта явно
  помеченной ошибки из БД (исходный access log / нормализованный ключ) дают
  post-fix count=1, затем достигают порога 10, без примеси успешных запросов.
- HTTP 404/500, добавленный traceback, префикс ошибки, отказ после access log,
  ERROR вместо INFO и самостоятельный отказ обнаруживаются и повторно
  не уведомляют после загрузки сохранённых флагов.

Старые флаги ложного повторения намеренно не сбрасываются: исправлена
классификация новых наблюдений, без редактирования живого состояния.

## Фактическая проверка

Каждый Python-запуск использовал provisioned uv **0.11.28**, PATH из задания,
`--frozen` и стандартную `.venv`; lock и зависимости проекта не менялись.
Тесты работали офлайн. Вспомогательный запуск направляет pytest tmp в папку
задачи. Импортированный `app` — каталог `app/` внутри этой копии
(путь относительно корня копии; абсолютный путь хаба не публикуется).

- Обязательная команда `uv run --frozen python -m pytest tests/test_error_watch.py -q`
  завершилась с кодом 2 при collection: `ModuleNotFoundError: No module named 'app.db'`.
  В этой исходной копии отсутствуют также `app.secret_mask`, `app.hub_activity`.
- Для доступной проверки добавлен явно включаемый
  `.orchestra/tasks/V-1191/run_source_checks.py`. Он подставляет только отсутствующие
  import-time зависимости: неиспользуемый тестами `DB_PATH` и identity
  `mask_secrets`. Проверяется настоящий `app/error_watch.py`, а не его копия.
  Это вспомогательный прогон, **не штатный acceptance gate**.
- До изменения production-кода первоначальные 13 новых случаев:
  **5 failed, 8 passed**, 240 deselected, 1.63 с. Падения показали ложные
  уведомления и неверный ненулевой count при завершении окна.
- После исправления и добавления контроля journal `500 OK`:
  **238 passed, 16 deselected**, 4.02 с, код 0. В этот прогон входят все
  **14 новых случаев**, остальные доступные прежние проверки, настоящие
  synthetic SQLite, formatting aiohttp/Python без сетевого I/O.
- 16 исключённых случаев: 15 используют fixture `hub_finish_row`, требующий
  отсутствующий `app.hub_activity`; один проверяет credentials/URL/email
  masking и исключён из-за подменённого `app.secret_mask`. Штатные тесты не
  ослаблены и не помечены skip: исключения существуют только в явно включаемом
  вспомогательном runner.
- `uv run --frozen python scripts/run_tests.py` завершилась с кодом 2:
  в частичной копии отсутствует сам `scripts/run_tests.py`.

Повторить доступный прогон:

```bash
export PATH="$HOME/.local/share/orchestra/tools/uv/0.11.28/bin:$PATH"
export TMPDIR="$PWD/.orchestra/tasks/V-1191"
uv run --frozen python .orchestra/tasks/V-1191/run_source_checks.py --stub-missing-imports
```

Полный gate, реальные app imports, secret masking и интеграция HubActivityStream
остаются непроверенными; их требуется прогнать в полном checkout. Зелёный
вспомогательный прогон не доказывает работу Python в живом процессе.
