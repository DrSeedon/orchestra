## 1. Webhook-вход с подписью и дедупом

**Мера.** (а) сколько раз внешнее событие будили агента через опрос, а не пуш; (б) во что обходится опрос; (в) что уже есть в коде. Источник: вызовы `mcp__orchestra__bg_create` в таблице `logs` с 2026-08-03 по 2026-10-21 (N = 5 606), таблица `bg_jobs` хранит только последние сутки и для этого не годится.

**Числа.** Из 5 606 `bg_create`: `run` 4 590, `command` 396, `timer` 361, `file` 70, `cron` 69, `idle` 68, `cron_command` 59. Среди 455 опросных `command`/`cron_command` по содержимому: GitHub CI/PR (`gh run`, `gh-clean`) **127**, ssh/прочее 208, локальный процесс или файл 98, HTTP 22. Медиана интервала опроса 90 с (для `gh` — 120 с, последние — 30–60 с). Опрос выполняет сервер без модели, агент просыпается один раз по совпадению: всего таких пробуждений от фоновых задач 6 376 за период. То есть **опрос не стоит токенов**: пробуждающий ход нужен при любом механизме, пуш его не отменяет. Запросов к GitHub API при 127 ожиданиях по 5–15 минут при интервале 90–120 с — порядка тысячи за 80 дней, ничтожно против лимита 5 000/час. Выигрыш пуша — только задержка обнаружения, в среднем половина интервала: 127 × ~45–60 с ≈ 1,6–2,1 агентских часа суммарно за 80 дней, причём агент в это время простаивает и ничего не тратит.

**Что уже есть.** `POST /api/webhook/github` (`app/routes/system.py:3167–3300`): проверка `X-Hub-Signature-256` через `hmac.compare_digest`, разбор `workflow_run`, маршрут в оркестратор по `GITHUB_REPO_SCOPE_MAP`, с логом упавшего джоба. Но не включён: `gh api repos/DrSeedon/orchestra/hooks` вернул `[]`, в `.env` нет ни `GITHUB_WEBHOOK_SECRET`, ни `GITHUB_REPO_SCOPE_MAP`. Нет дедупа по `X-GitHub-Delivery` (GitHub повторяет доставки). Других внешних источников, ждущих входа, не нашёл: упоминаний «вебхук» в сообщениях владельца 1 (пересланный пост), задача про webhook 1 (чужая, про MAX-бота).

**Примеры.** (1) 2026-09-05 — три подряд `gh run view <id> --json status,conclusion` с интервалом 90 с для ожидания CI. (2) 2026-10-19 — `gh-clean run list --commit <sha>`, интервал 30 с. (3) cron-напоминания о торгах V-274 (28.10) — это время, а не внешнее событие, webhook не нужен.

**Контрдоказательства.** Единственный внешний источник — GitHub CI; остальные «ожидания» локальные (pgrep, файл-лог) и webhook не заменяет.

**Вердикт.** Универсальный webhook-вход с подписью/дедупом **не брать**: нет внешнего источника, кроме CI, и тот закрыт уже написанным эндпоинтом. Если владельцу важна секундная реакция на упавший CI, цена — включить имеющееся (создать хук, секрет и карту репозиторий→scope в `.env`; ≈ 30 минут руками владельца) + добавить дедуп по `X-GitHub-Delivery` (≈ 15–20 строк и тест). Ожидаемая выгода: минуты задержки на CI-цикл, ноль токенов. **Не измеряется:** сколько реальных красных CI проходит мимо — письма о падении (владелец 06.10: «28 писем за сутки») идут по почте, не через агентов.

## 2. Учёт расхода по локальной истории провайдера

**Мера.** По дням и по группам рабочих каталогов сравнить сумму токенов из jsonl Claude (последнее сообщение по `message.id`, поля `output_tokens`, `cache_creation_input_tokens`) с `turn_usage` (`runtime='claude'`), потому что на подписке платят выход и запись кеша, чтение ≈0 (KB V-660). Окно **07.10–21.10 12:00** (14,5 суток): раньше история Claude на диске неполная — до ~21.09 отношение jsonl/`turn_usage` < 1 (файлы удаляются), ровно с 22.09 оно ≥1.

**Числа (окно 07–21.10).** jsonl: выход 62,4 М, запись кеша 457 М. `turn_usage`: выход 47,7 М, запись кеша 360 М. Не видно нам: **14,7 М (24%) выхода и 97 М (21%) записи кеша**; в долларах API-эквивалента — порядка 20% от $6 935 учтённого Claude-расхода окна, ≈ $1,4–1,6 тыс. (экстраполяция по доле токенов, по моделям не пересчитывал). Разложение разрыва по каталогам:

| Группа | выход, М | запись кеша, М | доля разрыва (выход / запись) |
|---|---|---|---|
| `data/*`, `~/bench`, `/tmp` (замеры V-656, V-758, V-45) | ≈7,2 | ≈21 | 49% / 22% |
| `/opt/cog-second-brain` (личные сессии Кеши) | 2,0 (2,11 против 0,09 учтённых) | 55 (59,3 против 4,1) | 14% / 57% |
| воркеры в `worktrees/*` (разрыв после учёта осиротевших `turn_usage`) | ≈3,7 | ≈16 | 25% / 16% |
| прочее (оркестраторы, мелкие проекты) | ≈1,8 | ≈5 | остаток |

(Оркестраторы сходятся с учётом на 80–90%.) Крупнейшая «невидимая» статья по квоте — не замеры, а личные сессии Кеши: 55 М записи кеша ≈ 33 п.п. недели по нашей оценке 0,6 п.п./М.

**Объясняет ли невязки квоты.** Окна 5-часовой квоты Claude с 22.09 по рядам `turn_usage` (монотонный участок `quota_five_hour_pct`, ≥5 ходов, рост ≥3 п.п.): **188 окон**, суммарный рост 3 420 п.п. Регрессия роста на (запись кеша, выход) только по `turn_usage`: R² = 0,80, RMSE 8,1 п.п. На всех токенах из jsonl подгонка **хуже** (R² = 0,74, RMSE 9,2): рядом попадают и ходы чужого аккаунта/профиля, и шум по времени сообщений. Но остаток модели по `turn_usage` коррелирует с невидимой записью кеша (r = 0,36, наклон 1,7 п.п./М), а в 7 окнах, где невидимого > 30% и > 5 М, среднее необъяснённое превышение **+14,6 п.п. при общем RMSE 8,1**. Вывод: часть неопознанных скачков — это именно невидимый расход, но не всё; ряд подтверждает связь, а не закрывает её (поправка: это остаток одной модели на 188 окнах, не независимая проверка).

**Codex.** Не измеряется этим способом: за дедупликацией по thread id в уцелевших rollout-файлах 16,8 Г входных токенов против 26 Г в `turn_usage`, т.е. локальная история покрывает ~65% (каталоги `codex-home` чистятся, осталось 49), а 17% уцелевших потоков не сопоставились с нашими session id (цепочки компакции и подмены). Судить о «невидимом» расходе Codex по этому нельзя.

**Примеры.** 14.10 15:00 — окно, где `turn_usage` дал 3,36 М выхода, а в jsonl 4,31 М (+28%). 08.10: jsonl 12,35 М выхода против 5,81 М (×2,1) — день с замерами V-758/V-656. 29.09: ×4,5 по выходу (бенчмарки).

**Контрдоказательства.** (1) Сама квота измеряется провайдером напрямую (`quota_*_pct`), невидимый расход виден как рост процента — теряется атрибуция («кто сжёг»), а не знание о нём. (2) Подгонка на jsonl-суммах не лучше. (3) Нужно ли считать личные сессии Кеши в расход Orchestra — вопрос владельца; у бота приоритет.

**Вердикт: брать для Claude, S.** Ценность: перестаёт теряться атрибуция ~20% Claude-расхода, а главное, **данные скоропортящиеся** (Claude чистит историю: до 21.09 уже частично потеряно). Реализация: ежедневный проход по `~/.claude/projects` с записью агрегата (день × каталог × модель) в нашу БД — прототип замера это ~40 строк; учёт Codex отдельно не обещаю. Цена S (≤ 1–2 дня воркера с тестом на разбор формата).

Просьб владельца «откати/верни как было» агенту про файлы: **0** (слово «откат» встречается 16 раз: про лимиты, «откатить на стенде» при выкладке экспоната, баг отмены в рисовалке).

**Не измеряется:** время, потерянное на ручной откат, и случаи тихой потери, о которых никто не написал.

**Вердикт: не брать.** Ожидаемая выгода: по замеру ≈ 0 у файлов в git (откат — 1 вызов, ≈ секунды) и 0 у файлов вне git (чекпоинт их не видит). Цена M. Если когда-нибудь появится реальный случай «агент затёр незакоммиченное», вернуться — доказательств такого за 80 дней нет.

## 4. Форк разговора воркера с нативной историей

**Мера.** Сколько раз одну и ту же работу гоняли дважды или сравнивали подходы, и сколько это стоило; нужен ли был при этом именно форк с общим префиксом.

**Числа.** Задач, у которых в названии «сравн/benchmark/бенчмарк/A-B/замер/абляц/эксперимент» (N = 98 из 2 487, созданных с 01.08): 65 из них имеют ходы в `turn_usage`, 2 303 хода, **$2 026 API-эквивалента из $15 673 (13%)** по всем задачам с учётом. Сами замеры вне учёта — сессии в `data/v656-*`, `data/v758-*`, `~/bench`: 256+511 сессий, выход 11,6 М, запись кеша 31,5 М за 29.08–21.10, то есть ≈4% записи кеша всего Claude (≈19 п.п. недели суммарно по 0,6 п.п./М, ≈2,5 п.п. в неделю). Задач с ≥2 воркерами: 23 из 129 с привязкой в таблице сессий (остальные 106 — один воркер). Просьб владельца о форке разговора («форк» без репозиториев, «скопируй сессию», «два варианта подхода воркеру»): **0**; в таблице `runtime_handoffs` 5 передач с 19.08.

**Примеры.** V-758 и V-656 — одинаковые сценарии (steer, stall, ident, costbase, pidfd) на нескольких моделях и с повтором `-r2`: каждый прогон — чистая сессия с коротким промптом, общего длинного разговора нет. V-45 — корпус из 169 коротких сессий.

**Почему форк почти не выиграет.** Деньги в подписке — запись кеша и выход (чтение ≈ бесплатно). Форк экономит только повторную запись общего префикса. При префиксе 200 тыс. токенов это 0,2 М × 0,6 = **≈0,12 п.п. недели** на каждую ветку; длинные общие префиксы у сравнительных прогонов отсутствуют. Остальное (выход, инструменты) форк не уменьшает.

**Контрдоказательства.** T3 Code применяет форк для переключения провайдера/модели в треде; у нас это закрыто `change_worker_model` (внутри рантайма сессия продолжается, между Claude и Codex — `chat_history_v1`). Нативный fork в нашем `app/` не используется (`rg fork_session|thread/fork` — 0). Возможная потребность «попробовать оба варианта с общим контекстом оркестратора» из данных не видна.

**Вердикт: не брать.** Ожидаемая выгода ≤ 0,1–0,2 п.п. недели на форк, спроса нет. Цена M.

**Не измеряется:** качество Gemini и других CLI в нашей роли воркера; какие агенты из реестра ACP поддерживают подписку без ключа.

**Вердикт: не сейчас, решение за владельцем.** Если нужен третий пул (Google AI Pro уже куплен) — сначала дешёвая проверка из #249 (запустить Gemini CLI воркером на одной нашей задаче с замером), и только потом выбирать, делать ли ACP-слой или отдельный бэкенд. Цена ACP-входа M–L; ожидаемая выгода в единицах (доля недельной ёмкости третьего пула) не оценима без этого замера.
