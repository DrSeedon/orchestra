# V-921 — глобальные OOM 17.10.2026

## Вывод

Все три случая были **глобальными OOM хоста**: ядро пишет `constraint=CONSTRAINT_NONE` и `global_oom`, swap хоста был исчерпан (16 GiB всего, 0 свободно). Сначала каждый раз погибал Python главного процесса Orchestra в `orchestra-api`; во втором эпизоде после него погибли ещё четыре процесса в `agents/workers`.

В OOM-дампах крупнейшие резидентные потребители — процессы `ffmpeg`: четыре процесса с суммарным RSS около 17.3 GiB в первом эпизоде, четыре с 17.1–19.2 GiB во втором и три с 18.6 GiB в третьем. Дамп ядра не записывает cgroup каждого PID, поэтому приписать каждый `ffmpeg` конкретному worker PID нельзя. По БД и инструментальным логам наиболее близкие по времени тяжёлые работы — рендеры видео `video-platforma` (V-200), `research-video-style` (V-904), затем серия `finish.sh`/`ffmpeg` у `rilsy` (V-193); перед третьим эпизодом одновременно шёл также Playwright-заказ `gamelab-bots` (сессия V-269, рабочие файлы V-261).

V-919 §1 фиксирует пик `orchestra.service` 14 GiB RAM и 12 GiB swap. В этих же событиях ядро видит 0 свободного из 16 GiB swap хоста: память вне сервиса добавила остальное давление, и OOM стал глобальным.

Лимит свопа V-897 уже действовал: при рестарте 17.10 в 07:07:44 CEST процесс Orchestra создал `agents/memory.swap.max=1 GiB` в 07:07:45.587 CEST. Это за 2 ч 13 мин до первого OOM. Лимит ограничивал только `agents`; для `orchestra.service` и дочернего `orchestra-api` своп оставался `max`. В каждом OOM дампе у крупнейших `ffmpeg` по отдельности было более 1 GiB swap — они не могли находиться внутри `agents` с этим лимитом. Поэтому V-897 снизил потенциальный ущерб от части агентских процессов, но **не ограничил тяжёлые локальные background-run и SSH-задачи и не предотвратил эти глобальные OOM**.

## Почему убивало основной процесс

Убитые процессы главного Python в трёх эпизодах имели `oom_score_adj=800`, как и задано политикой Orchestra. Ядро маркирует все три события как `global_oom`; при выборе жертвы учитывает оценку badness, основанную в том числе на памяти и swap процесса, а затем добавляет `oom_score_adj`. Поэтому 800 резко повышал риск для главного Python. В первом снимке он имел 337.7 MiB RSS + 209.6 MiB swap, тогда как ближайшие видимые `MainThread` в `agents/workers` — около 135–138 MiB RSS и 3–91 MiB swap. Во втором снимке у главного Python было 129 MiB RSS + 285 MiB swap; у четырёх процессов из `agents/workers`, убитых следом (три `MainThread` и один `claude`), было 195–279 MiB RSS и 47–61 MiB swap. В третьем главный Python имел 143 MiB RSS + 436 MiB swap. Больший учтённый footprint при одинаковом высоком `oom_score_adj` согласуется с повторным выбором API-процесса первым.

Это не было только убийством главного процесса: во втором эпизоде ядро затем убило четыре процесса из `agents/workers`, тоже с `oom_score_adj=800`. Значение 800 намеренно делает Orchestra уязвимой раньше процессов с низкой оценкой и защищает бота Кеши; оно не означает, что все агенты имеют меньший score. Точные баллы `oom_score` на момент OOM журнал не сохраняет, поэтому объяснение выбора по сравнению `RSS + swap` — согласованный с kernel badness heuristic вывод, а не прямой замер `oom_score`. Документация ядра: [oom_score_adj и heuristic badness](https://docs.kernel.org/7.0/filesystems/proc.html), [состав kernel task dump](https://docs.kernel.org/6.6/admin-guide/sysctl/vm.html).

## V-897: применился, но не охватил нагрузку

Рестарт начался в 07:07:32 CEST, процесс Python стартовал в 07:07:45, а mtime `agents/memory.swap.max` — 07:07:45.587 CEST. В момент инцидента это соответствовало `agents.memory.swap.max=1 GiB`; лимит был установлен после рестарта, задолго до OOM. Текущий снимок после инцидента показывает `orchestra.service/memory.max=16 GiB`, `memory.swap.max=max`; `agents/memory.max=14 GiB`, `memory.swap.max=1 GiB`; у `orchestra-api` оба лимита — `max`. Код V-897 пропускает запись файла, если значение уже совпадает, поэтому сохранённое время отражает первое применение лимита.

В четырёх процессах `ffmpeg` первого дампа `swapents` составляет 1.2–3.5 GiB **на процесс**, а во втором и третьем — до 4.1 GiB. Ни один такой процесс не мог находиться в иерархии `agents` с общим swap-потолком 1 GiB. Kernel dump не содержит cgroup этих `ffmpeg` PID, и к моменту расследования процессов уже не было; конкретную внешнюю cgroup для каждого установить нельзя. Но источник задач согласуется с обходом лимита: локальные `bg_jobs` по умолчанию запускаются с `agent_workload=False` (`app/bg_jobs.py:453,586,1255`), значит наследуют cgroup API-процесса; `ssh localhost` запускает удалённую часть в отдельной пользовательской сессии. В V-200/V-193 были локальные run-команды, в V-904 и V-193 — SSH-команды. У выбранных локальных job config поля `host` и `agent_workload` отсутствуют ([DB-снимок](logs/db-selected-jobs.txt)); эти пути не ограничивались `agents/memory.swap.max`.

## Предложения

1. **Охватить cgroup-лимитом agent-owned background runs.** Для `bg_jobs` типа `run`, созданных worker-сессиями, передавать `agent_workload=True` либо задавать его по владельцу job; сейчас конфиг соответствующих jobs не содержал этого поля, а default в `app/bg_jobs.py:453,586,1255` — `False`. Тогда прожорливый локальный run будет ограничен `agents` (14 GiB memory / 1 GiB swap), а API останется за пределами этой cgroup. Цена: такой run или его worker может быть OOM-killed раньше и вернёт ошибку вместо завершённого результата.
2. **Отдельно ограничить SSH-пути.** Локальный cgroup не ограничивает удалённые процессы, созданные через `ssh localhost`; V-904 и V-193 реально используют этот путь для FFmpeg/prep/render. Если тяжёлые job остаются на SSH, удалённый launcher должен помещать их в ограниченную transient cgroup либо запускать через контролируемый агентский runner. Иначе одна локальная квота не защищает от того же глобального исчерпания.
3. **Ограничить число параллельных видео-рендеров.** Перед OOM `rilsy` запустил четыре `finish.sh` одновременно, а kernel последовательно фиксировал несколько `ffmpeg` с RSS от 2 до 9 GiB и общим RSS группы до 19.2 GiB. Лимит параллелизма (например, один-два рендера) снижает пиковую память; цена — более длинная обработка. Из-за отсутствия cgroup-меток у исторических PID это средство уменьшения риска, а не доказательство, что именно каждый из этих четырёх процессов принадлежал указанному запуску.

Сервисы, юнит, лимиты и процессы во время исследования не менялись. Запросы к live БД были `SELECT` через `sqlite3 -readonly`; cgroup-файлы только читались.
