# V-1195 — agent-desktop для Orchestra и тендерного браузера

**Статус:** исследование, без установки, запуска на ноутбуке или внедрения. Проверены исходник agent-desktop на GitHub, пост Telegram, код текущей Orchestra и локальный отчёт Seedon V-246. Код — checkout текущей рабочей ветки на 01.11.2026. V-246 — ручной прототип от 14.10.2026, а не проверка текущего состояния ноутбука.

## Вывод

`agent-desktop` — системный desktop CLI/FFI над OS accessibility tree; это не MCP-сервер, не браузерный драйвер и не средство изоляции. Он может добавить осмысленное управление доступными элементами нативных Linux-приложений, чего не даёт CDP, если окно КриптоПро действительно видно AT-SPI. Эта конкретная совместимость не проверена. Поддержка Linux нацелена прежде всего на Ubuntu 24.04+/GNOME 46 с графической пользовательской сессией; Wayland ограничивает указатель и управление окнами.

Для просмотра публичных страниц, поиска и заполнения web-форм уже есть более доказанный маршрут V-246: Playwright → CDP отдельного профиля Яндекса на ноутбуке через SSH-туннель. Прототип прочитал публичную карточку РТС, выполнил поиск и загрузил файл; он не проверял вход с ЭП, PIN, подпись или подачу. `agent-desktop` потенциально дополняет этот маршрут для нативных окон, но сейчас нет доказательства, что закроет пробел КриптоПро или улучшит параллельность/токены.

Для тендеров подходит только как возможный помощник чтения и подготовки. Нужны отдельные проверки AT-SPI на конкретных окнах КриптоПро и площадках. Подписание, PIN и финальную подачу следует оставить человеку: не выдавать агенту команду/инструмент для этих действий. В V-246 предложенная схема допускала клик агента по кнопке подачи после согласия в чате; это предложение не было испытано и слабее заданной здесь обязательной защиты.

## Что подтверждает первоисточник

README описывает Rust CLI и C-библиотеку: программа возвращает JSON accessibility tree с ref-идентификаторами, агент выполняет действие и читает новый snapshot. Ref привязан к snapshot; устаревший ref отклоняется. Доступны также отдельные команды клавиатуры/мыши, окон, буфера, трассировки и скриншотов. Действия по ref в штатном headless-режиме идут через accessibility API и не двигают указатель и не забирают фокус; это не значит, что команда явного `focus` либо физический ввод фокуса не меняют. CLI позволяет подключить навык с инструкциями, но сам не содержит LLM.

Документированная матрица Linux:

| Механизм | Заявленная поддержка | Ограничение / доказательство |
|---|---|---|
| Дерево доступности | AT-SPI, X11 и Wayland | Нужны `at-spi2-core` и переменные/шина текущей GUI-сессии; из обычной TTY/SSH без GUI-среды приложения не видны. |
| Семантические действия | Через AT-SPI на X11 и Wayland | Работают по refs без движения указателя/захвата фокуса в headless-режиме. Это не проверка CryptoPro. |
| Клавиатурный ввод | X11 через XTEST; Wayland — GNOME Mutter RemoteDesktop | Wayland-зависимый механизм; нужно учитывать разрешение/сессию GNOME. |
| Указатель | X11 в headed-режиме | На Wayland ввод указателем отказывается работать. Независимых виртуальных курсоров в Linux-документации не найдено. |
| Скриншоты | X11-окна; Wayland portal | Скриншот остаётся отдельным действием и может раскрывать данные. |
| Окна | запуск/список; управление окнами X11 | На Wayland native window control не поддерживается. |
| Платформа | Ubuntu 24.04+ / GNOME 46 — основная цель, glibc ≥2.35 | Документация прямо отмечает проблему ATK bridge Ubuntu 22.04 (`Action.GetActions`). |

Матрица подтверждается README и `docs/install.md`; более полная таблица перед запуском предлагается командой `agent-desktop skills get linux`. Официальный upstream не заявляет Linux-поддержку каждой комбинации дистрибутива, среды и приложения.

### Многопользовательский и параллельный доступ

README описывает namespace/session для snapshot/ref; FAQ поясняет, что refs в namespace требуют соответствующего `--session`. Это разделение идентификаторов и контекста, не OS-песочница и не блокировка действий. CLI и FFI дают агенту операции над общей сессией ОС. Параллельные команды могут одновременно менять один интерфейс; найденная документация не задаёт арбитраж, блокировки или владение окном между агентами. Headless actions по refs обходят физический pointer, поэтому высказывание поста про «свой курсор каждому агенту» как минимум не подтверждено и не описывает этот режим. Для X11 headed-ввод остаётся общим физическим указателем. Не включать несколько управляющих агентов на одной сессии без внешней сериализации.

## CryptoPro, Яндекс и V-246

В локальном отчёте Seedon [`V-246/report.md`](/home/kesha/projects/seedon/.orchestra/tasks/V-246/report.md) зафиксированы ручные пробы отдельного профиля Яндекса с Playwright/CDP: живые расширение CryptoPro и native messaging host, ответ цепочки плагина/CSP, просмотр публичной карточки и поиск РТС, а также загрузка файла с VPS. Изоляция профиля была намеренной: копия без cookies, паролей и истории; автор также проверил DNS allowlist против открытия стороннего домена. Прототип запускал браузер в Xvfb для невидимой подготовки либо планировал отдельный видимый режим Wayland; последний не проверен.

Ключевая граница теста: при вызове CryptoPro `Store.Open` появилось отдельное native-окно `xcpui_app`, которого не было в DOM и которое CDP не мог нажать. Автор отменил запрос в Xvfb; PIN и подпись не вводились, на площадку с ЭП не входили, заявка не отправлялась. Wayland-режим и окно PIN оставлены непроверенными; поведение других площадок и необходимость дополнительных CryptoPro/Rutoken host-компонентов также не проверялись. Поэтому утверждение «CDP не видит native окно» доказано для наблюдавшегося окна в том тесте; возможность agent-desktop работать с ним через AT-SPI остаётся гипотезой до пробы на точно таком окне.

Текущая Orchestra не содержит browser/desktop MCP-инструмента в `app/mcp_stdio.py`. В `app/limits_card.py:553–610` Playwright используется для рендера карточки лимитов в отдельном headless Chromium; это не браузерная автоматизация пользователя. `app/runtime_registry.py:130–164, 250–269` умеет загружать внешние MCP-серверы из конфигурации scope и пробрасывать их в runtime, то есть есть общий механизм подключения, но не конкретный desktop control. Спец-инструмента, сериализующего desktop-команды или запрещающего подачу, в текущем коде не найдено. V-246 — отдельный прототип Seedon, не интеграция Orchestra.

## Разрешения, изоляция и секреты

- Утилита должна исполняться в той же Linux GUI-сессии, чьи окна читает; SSH-клиент без display/bus/runtime среды их не обнаружит. Доступ к accessibility API — доступ в пользовательскую сессию, не изоляция по приложениям. `--app` ограничивает выбранную цель команды, но не является границей безопасности.
- Semantic refs уменьшают зависимость от пикселей и физического указателя, но не блокируют ввод данных, выбор сертификата или нажатие кнопок. Набор команд включает `click`, `press`, `type`, `focus`, `mouse-*`, `close-app` и команды clipboard. Один CLI/skill сам по себе не запрещает подпись/подачу.
- Источник явно предупреждает, что accessibility snapshots, заголовки окон, clipboard, уведомления, скриншоты, вывод команд и trace/debug-артефакты могут содержать приватные данные; traces могут сохранять артефакты даже при редактировании структурированных полей. Их нельзя отправлять в публичные логи/хаб без разрешённого потока обработки.
- Отдельный профиль Яндекса из V-246 ограничивает ущерб, если CDP доступен процессам того же пользователя; SSH-туннель сам по себе не ограничивает полномочия CDP внутри браузера. Профиль без паролей/cookies и сетевой allowlist снижает поверхность доступа, но не превращает браузер в OS sandbox. В V-246 агентский профиль был отдельным каталогом около 586 МБ — это стоимость конкретной копии, не измерение agent-desktop.
- Для тендеров безопасная граница: по умолчанию read-only; после проверки площадки — ограниченный ввод полей и загрузка подготовленных файлов; не давать агенту кнопку подписи/подачи, не вводить PIN в агентский ввод и не делать автоподтверждение CryptoPro доверенным сайтом. Человек лично подтверждает native CryptoPro prompt, выбирает сертификат, вводит PIN и сам выполняет финальную подачу. Считать отправку успешной только по документированному статусу/квитанции площадки после ручного действия.

## Варианты интеграции

| Вариант | Что получится | Цена и ограничения |
|---|---|---|
| Только skill/инструкция для существующего CLI | Агент знает цикл snapshot → ref action → повторный snapshot и платформенные ограничения. | Быстрее всего для ограниченной пробы; не даёт Orchestra нового API и не обеспечивает hard gate. Инструкция не является защитой от подписи/подачи. |
| Локальный CLI через выделенную команду / existing shell | Доступны все штатные команды и JSON-ошибки; можно пробовать в изолированной GUI-сессии и получать результат в агенте. | Мало интеграционного кода, но широкий интерфейс и права процесса; нельзя пускать сырой CLI в тендерный профиль без ограничений. Каждый отдельный вызов запускает CLI; FFI существует, но его встраивание дороже и пока не нужно обосновывать. |
| Новый узкий MCP wrapper в Orchestra | Типизированные операции snapshot/ref, read-only по умолчанию, allowlist приложений/команд, сериализация и видимая ручная остановка; все возвращаемые данные можно локально маркировать/ограничивать. | Наибольшая разработка и поддержка. Политика должна быть в исполняемом wrapper, а не только prompt. Wrapper не может гарантировать PIN/нативное подтверждение, если ОС/драйвер допускают ввод или окно не различено; запрет подачи нужно валидировать в самом интерфейсе инструмента и оставить owner-only ручное действие. |

CLI/FFI выпущены под Apache-2.0; сам проект не требует удалённого model API. Для использования без нового поставщика токенов подходящий маршрут — локальный CLI/MCP, где snapshots и команды остаются локально. Но при передаче вывода в hosted/hub-агент защита нарушается независимо от локальности бинарника; следует использовать локального исполнителя/модель и не пересылать UI-содержимое на хаб. Добавление скилла к модели не имеет измеренной токенной экономии.

## Стоимость и измерения

- Лицензионная стоимость agent-desktop: нулевая по Apache-2.0; остаются инженерные часы, сопровождение Linux/AT-SPI/Wayland, дисковое место профиля и эксплуатация локального GUI. Денежная сумма/часы не измерялись.
- В `docs/install.md` upstream приводит только собственный запуск CLI: около 21 мс на вызов с нативным launcher и около 146 мс, если блокирован postinstall и работает Node launcher. Это не замер сценария тендера, не сравнение с Playwright/CDP и не токены.
- Ни V-246, ни доступный пост не содержат сравнимого измерения токенов/стоимости agent-desktop против browser Playwright/CDP на одинаковой задаче. Пост называет экономию токенов, но не приводит данные или методику. Качественно accessibility snapshot может быть короче скриншота плюс визуального описания, однако стоимость будет зависеть от дерева, отбора узлов, prompt и модели; утверждать выигрыш нельзя.
- Результаты V-246 — функциональные пробы нескольких действий, не замер задержки, токенов, параллельности или устойчивости к изменениям страницы.

## Предложение и проверка перед любым внедрением

Сначала отдельная локальная проба без подписи и без изменения ноутбука: Linux/X11 или выделенный тестовый GUI-профиль, где допустимо; снимок доступности обычного окна и CryptoPro native confirm; установить, появляется ли окно/контролы в AT-SPI, может ли `snapshot` их прочесть и какие конкретно ref actions проходят. На Wayland — отдельно проверять клавиатурный ввод и отказ указателя, не обещать полноценное управление окнами. Это исследование не запускало эти проверки.

Если native окно доступно, сравнить на одной заранее выбранной read-only форме agent-desktop и Playwright/CDP: выполненные наблюдения/действия, корректность, число retries, wall-clock и фактические input/output tokens одного и того же локального агента с тем же prompt/model. Несколько агентов — отдельный тест на конфликт двух параллельных чтений и на сериализацию изменений; независимо направленные курсоры не считать существующей функцией. Перед внедрением — владелец определяет разрешённые площадки, профиль, и ручные stop points; обязательны запрет на PIN/подпись/финальную подачу и проверка того, что инструмент не может обойти его через общий shell/raw CLI.

Пока практичнее считать Playwright/CDP+отдельный профиль уже доказанным вариантом для web-подготовки, а `agent-desktop` — кандидатом на отдельную проверку нативного окна. Никакое изменение или подключение не выполнялось.
