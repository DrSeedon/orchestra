# #213 — эффорт по рантайму: развести нельзя, и ключ нужен другой

Основание — `docs/tasks/208/research.md` (`da029a6e`). Файлы: `pipelines/default/pipeline.yaml`,
`pipelines/default/prompts/modules/model-routing.md`. `app/` не трогал.

## 1. Ответ на вопрос: манифест этого не умеет, И «по рантайму» недостаточно

`RoleSpec.effort` — скаляр `str | None` (`app/pipeline.py:201`), он же в `ResolvedRole` (`:274`),
пробрасывается в манифест-резолв (`:388`). При спавне читается плоско:
`manager.py:660-662` берёт `getattr(rr, "effort")` и кладёт в сессию.

**Важнее другое: разделение по РАНТАЙМУ не решает поставленную задачу.** Целевые значения —
Sol `xhigh`, Luna `high`, — но обе модели дают один и тот же рантайм:

```
claude-opus-5[1m]   -> claude
gpt-5.6-sol         -> codex
gpt-5.6-luna        -> codex
gpt-5.3-codex-spark -> codex
gpt-5.6-terra       -> codex
```
(`backend_for_model`, `app/models.py:623`). Ключом обязана быть **модель**, иначе Sol и Luna
неразличимы и правка не сделает того, ради чего задумана.

### Что нужно от кода (не реализовывал, отдаётся отдельно)

1. `app/pipeline.py`: `RoleSpec.effort` / `ResolvedRole.effort` принимают `str | dict[str, str]`,
   где ключ — id модели, плюс необязательный ключ `default`. Валидатор: значения из известного
   набора эффортов; неизвестный ключ — пропуск с warning (`validation: fail-open`, как у модулей).
2. `app/manager.py:660-662`: выбирать по модели спавна. Данные уже под рукой — `model` в
   аргументах, `bt = backend_for_model(model)` посчитан строкой выше (`:659`). Порядок разрешения:
   точный id модели → рантайм → `default` → `None`.
3. Обратная совместимость: скаляр остаётся валидным, остальные роли и пайплайны не трогаются.
4. Тесты: маппинг разрешается по модели; скаляр ведёт себя как раньше; незнакомая модель падает
   в `default`.
5. Знать при внедрении: живые сессии значение НЕ подхватят — при восстановлении эффорт берётся из
   строки БД (`manager.py:1202`, `:1518`), из манифеста он читается только при спавне.

Целевые значения, когда поле появится: Opus `high`, Sol `xhigh`, Luna `high`. Spark не мерился —
оставить дефолт.

## 2. Что сделано без кода

**Манифест — запись ограничения** комментарием над `roles:` (6 строк): почему `high` у рабочих
ролей верен для их дефолтного Opus и не подходит Sol, какие целевые значения, почему ключом должна
быть модель, и что до правки в коде Sol-воркеры недополучают ступень. Комментарий явно ограничен
`worker`/`full-cycle` и заканчивается «Это запись ограничения, не задание» — обе оговорки появились
после ревью (см. ниже). Значения эффорта не менял: `high` верен для Opus, а Opus — дефолтная модель
всех рабочих ролей.

**Блок маршрутизации — два уточнения.**

- Пункт Sol: «**There is no discount route through Sol**: its returns keep climbing to the top of
  the effort ladder with no inflection (+1.7 / +1.7 / +1.9 index points per step, #208), so
  cheapness is not available here at all — a task you would only fund at a discount goes to Luna,
  not to Sol.» Единственное предписание здесь — выбор МОДЕЛИ; про ступень эффорта не сказано
  ничего, потому что спавнящий агент её не выставляет.
- Пункт Luna: «Measured: on 3 closed single-turn tasks (N=1 per cell) it did the same work as Sol
  at 20.5× less (#199), and on one real bug both scored 5.0 of 6.0 against pre-registered checks,
  Luna at 13.2× less (#208). One closed ticket at a time — long multi-turn work on Luna we have
  never measured, so do not stretch a ticket into a session there.» Ограничение объёма стоит
  ПОСЛЕ выигрышей по цене, чтобы «дешевле в 13 раз» не читалось как разрешение сажать Luna на всё.

## 3. Чего НЕ вписал и почему

В постановке была ещё одна оговорка про Luna: «независимые отчёты — теряет инструкции на длинных
сессиях; один замер даёт 14× по времени против Terra». Не вписал. Наш собственный `#204`
(`research.md:704`) прямо помечает числа этого происхождения как непроверяемые SEO-цифры и пишет
«не цитировались и цитировать не надо»; в репозитории источника с атрибуцией нет. Вчерашняя задача
#207 была ровно про это — вычистить из промпта число без источника. Поэтому осторожность
сформулирована через то, что у нас есть: «мы этого не мерили». **Если у тебя есть атрибутированный
источник — дай ссылку, впишу цифру.**

## 4. Ошибка, которую поймала проверка первоисточника

Я написал в промпт «tied with Sol 5.0/5.0». В `#208` (`research.md:19`, таблица `:323`) счёт —
**5.0 из 6.0 у обоих** (по A3 оба получили ноль, и это отдельно разобрано в их отчёте после
ревью). «5.0/5.0» читается как безупречный результат, то есть я усилил бы вывод при переносе.
Исправлено на «both scored 5.0 of 6.0 against pre-registered checks».

Отсюда же — почему в этих двух утверждениях теперь стоят `#199` и `#208`: число в промпте без
адреса первоисточника мы уже один раз вычищали (MRCR, #207). Ссылка на задачу стоит шесть байт и
делает цифру проверяемой.
