## Что реализовано

`app/owner_activity.py` содержит чистое ядро: 60-секундные presence-интервалы,
оконную оценку message/voice, детерминированную аллокацию перекрытий и группировку
сессий по календарю Красноярска. Presence имеет приоритет над message; при равном
приоритете побеждает самое позднее событие, затем стабильный `tab_token/event_id`.
Так сумма scope всегда равна глобальному union и не зависит от порядка replay.

Для вопроса «в каком проекте сижу» presence сфокусированного dashboard считается
сильнее одновременного TG-сообщения другого scope; TG получает время своего scope,
когда dashboard-presence в этот момент нет.

`owner_activity_events` хранит все raw-события бессрочно. Событие вкладки содержит
случайный `tab_token` из `sessionStorage`, scope, timestamp, visible/focused и
`last_input_at`; текста, DOM, URL, IP и user-agent в таблице нет. `db.add_log`
атомарно добавляет только длину owner-сообщения, scope, subtype и найденную
длительность voice. Startup backfill однократно превращает старые owner messages в
`estimated=true` и использует тот же метод.

API: `POST /api/owner-activity/events` (idempotent по event_id),
`GET /api/owner-activity/sessions` и `GET /api/owner-activity/summary`. Ответы
содержат UTC start/end, день `Asia/Krasnoyarsk`, scope, секунды/часы, source и
estimated. Python-роутер подключён в `app/main.py`; dashboard отправляет focus,
blur, scope-switch, visibility, input и heartbeat; input ограничен переходом из
idle или не чаще одного раза в 60 секунд. До рестарта текущий процесс не
видит новые Python-маршруты и startup backfill — это ожидаемое ограничение.

## Что проверено в коде

### 1. Сообщения и происхождение

В `app/schema.sql:104-117` `logs` хранит `ts`, тип, `origin` и JSON
`origin_detail`, а `sessions` хранит `scope`, `name`, `role` и
`is_orchestrator` (`app/schema.sql:318-345`). В текущем срезе 15 сообщений
`origin='user'` пришли из worker/full-cycle сессий; остальные 2 474 — из
orchestrator-сессий. Фильтр владельца должен быть не просто
`type='user_message' AND origin='user'`, а также `sessions.is_orchestrator=1`.
Ответы/доставки между агентами не следует считать работой владельца: у них есть
провенанс `agent`/`background_task`, а `message_deliveries` отдельно описывает
источник и цель.

Dashboard `POST /api/sessions/.../send` принимает `channel='dashboard'`
(`app/routes/sessions.py:245-256`). Для обычного сообщения без `sender` он ставит
`origin='user'` только если валидна auth cookie; без неё сообщение всё равно
доставляется, но получает `origin='unknown'` (`app/routes/sessions.py:997-1015`).
Поэтому `http_send` не является автоматически «dashboard»: это смешанная
транспортная метка. В срезе безопасно брать только `origin='user'`, а
`subtype` хранить для разрезов. Сообщения с `sender` — `origin='agent'` — в часы
владельца не попадают.

Telegram-мост ставит `subtype='telegram'` в `_flush_batch`
(`app/tg_bridge.py:573-620` и путь отправки около 430), но сообщения, пришедшие
в течение 5 секунд, объединяются в один лог, а ожидание media может длиться до 30
секунд. Поэтому 900 строк — число доставленных логических батчей, не обязательно
число нажатий Send.

**Вердикт пункту (1): частично подтверждён.** Канал и scope извлечь можно, но
нужно явно исключить workers, учитывать auth semantics, batching и отсутствие
текста между сообщением и ответом. Приписывать `http_send` к dashboard без
`origin='user'` нельзя.

### 2. Присутствие в dashboard

В `app/static/js/app.js:1035-1037` `_pollCanRun()` проверяет только
`document.hidden` и `navigator.onLine`; `app/static/js/app.js:1114-1125` при

### 5. Telegram: что видно и что нет

Код обрабатывает text, voice, video note, photo, document, video, audio, sticker
и fallback (`app/tg_bridge.py:3785-3979`). Для voice уже есть отдельная таблица
стоимости: с 1 по 23 сентября — **330 записей, 13 760,7 секунд**; это полезный
metadata-сигнал длительности аудио, но не доказательство времени чтения/говорения
владельца и не всегда совпадает с моментом доставки транскрипции.

В текущем bridge нет `edited_message`, `message_reaction` или
`message_reaction_count` observer. Официальный Bot API описывает edited updates и
реакции; реакции требуют явного `allowed_updates` и администраторских прав для
чата ([Bot API](https://core.telegram.org/bots/api)). Поэтому реакции и правки
можно добавить как отдельные события, но это будет новый ingestion path. Bot API
не присылает боту факт того, что человек прочитал сообщение; это остаётся
невидимым без другого клиента/протокола. Даже если ловить реакцию, она означает
действие, а не момент чтения.

## Реализация и план сопровождения

### Сигналы

1. `message`: существующий `user_message` после фильтра `origin='user'` и
   `is_orchestrator=1`; сохранять transport subtype и session/scope.
2. `dashboard_presence`: браузер раз в 60 секунд, только при `visibilityState`
   visible, `document.hasFocus()` и недавнем локальном activity. Передавать scope,
   случайный tab token, observed timestamp, last-input age и версию схемы; не
   передавать текст, DOM, URL за пределами scope, IP или user-agent.
3. `dashboard_activity`: локально обновлять last-input на pointer/keyboard/scroll
   событиях, но отправлять только агрегированное время и heartbeat.
4. `telegram_media`: использовать существующие длительности voice/video-note как
   отдельный сигнал с меньшей уверенностью; не приписывать длительность всей
   сессии автоматически.
5. `telegram_reaction/edit`: отдельные metadata-only events, если владелец выберет
   расширение Bot API ingestion; reaction — активность, но не read receipt.

### Схема хранения (реализовано)

Фактическая модель — бессрочная таблица raw-событий:

- `owner_activity_events`: `event_id`, `kind`, `event_type`, UTC `ts/start_ts/end_ts`,
  `scope`, `tab_token`, `visible`, `focused`, `last_input_at`,
  `content_length`, `voice_duration_sec`, `source`, `estimated`; уникальность по
  `event_id`; содержимого сообщения нет.
- Поминутная таблица не нужна: сессии пересчитываются из бессрочного raw-источника
  на запросе, поэтому алгоритм можно исправить без потери событий.

Хранить timestamp в UTC. «День» для линейки должен иметь выбранную timezone и
показывать её в API/HTML; молча использовать локальную timezone сервера нельзя.

### Алгоритм

1. Нормализовать входы по UTC и dedupe по event id. Сообщение даёт timestamp,
   heartbeat — активную минуту/точный интервал, media — отдельный confidence.
2. Внутри `(tab_token, scope)` объединить пересекающиеся heartbeat intervals.
3. По всем вкладкам объединить их в глобальное множество; вкладки не складывать.
4. Для каждого атомарного отрезка выбрать presence вместо message; внутри одного
   источника выбрать последнее событие, затем стабильный token/event id. Это даёт
   ровно один scope на секунду и сохраняет сумму scope равной глобальному union.
5. Склеить соседние участки с gap `<= 5 мин` в `owner_sessions`; сохранить raw
   start/end и алгоритм, чтобы повторный расчёт был воспроизводим.
6. Для истории до внедрения строить только `estimated=true` из сообщений; методы
   V-57/30m и старый message_think_10m остаются сравнительными числами и не
   подменяют новый источник.

### API и файлы

Затронуты `app/schema.sql`, `app/db.py`, `app/main.py`,
`app/owner_activity.py`, `app/routes/owner_activity.py`,
`app/static/js/owner-activity.js`, `app/static/js/app.js`,
`app/templates/dashboard.html` и `tests/test_owner_activity.py`.

Минимальный API:

- `POST /api/owner-activity/events` — authenticated, idempotent, metadata-only;
- `GET /api/owner-activity/sessions?from=&to=&scope=` — сессии и источники;
- `GET /api/owner-activity/summary?from=&to=` — часы по дням/scope и confidence;
- retention job отсутствует: raw events хранятся все и навсегда по решению владельца.

### Тесты ядра

Проверять не формулировки UI, а механику, от которой зависит себестоимость:

- пересекающиеся интервалы одной вкладки считаются один раз;
- две вкладки одного scope не удваивают глобальные часы;
- два scope получают deterministic winner, сумма по scope равна глобальному множеству;
- gap ровно 5 минут и 5 минут + epsilon дают разные границы;
- duplicate event id не меняет результат;
- порядок событий и перезапуск процесса не меняют проекцию;
- отсутствующий `last_input_at`/невалидный scope отклоняется или попадает в
  `unknown`, но не создаёт часы владельца;
- worker `origin='user'` не попадает в owner-only отчёт;
- timezone/day boundary и неполный текущий день явно тестируются;
- из лога/пинга в тестовую таблицу не попадает message content.

### Приватность и цена

Новый сигнал metadata-only. Random tab token — идентификатор вкладки, не fingerprint
устройства; он хранится бессрочно вместе с raw event по решению владельца. Не
сохранять IP, user-agent, текст, DOM, URL страницы или содержимое Telegram. Доступ
к ingest и отчёту — та же аутентификация, что и dashboard; агрегаты могут быть видны
только владельцу.

Платный API не требуется. При одном ping/минуту одна вкладка даёт 1 440 событий
в день; пять вкладок за 30 дней — 216 000 raw событий. Это планировочная верхняя
оценка объёма, не замер размера SQLite. Трудозатраты были planning estimate
порядка 2–4 инженерских дней без Telegram reaction path; эту ветку не расширяли,
поскольку владелец запретил reactions/edits.

## Архитектурные развилки — решения владельца 23.09

| развилка | ветка A | ветка B | цена/последствие |
|---|---|---|---|
| источник | raw events + пересчёт сессий | только minute buckets | Выбрано A: бессрочная история дороже по SQLite, зато сохраняет replay и исправление алгоритма; отдельная minute projection не нужна |
| идентичность | random per-tab token | без token | Выбрано A: токен нужен для union вкладок, хранится бессрочно вместе с raw |
| присутствие | видимость + focus + last input ≤5 мин | только visible/focus | A меньше ложного времени чтения в фоновой вкладке; B меньше JS-событий, но завышает idle reading |
| Telegram | messages + voice metadata | добавить edits/reactions | Выбрано A: edits/reactions не ловим; read receipt всё равно не появляется |
| split scope | deterministic winner, presence > message, latest event | равные доли / `unattributed` | Выбрано A: exact scope-switch и сумма scope = global union; это модель только для редкого реального overlap |
| история | message-only с `estimated=true` | не показывать историю до heartbeat | Выбрано A: полезная линейка до запуска, но явно оценочная |
| день | UTC | timezone владельца Asia/Krasnoyarsk | Выбрано B: хранение UTC, календарь и API day — UTC+7 |

Решения приняты; реакции и правки TG намеренно не добавлялись.

Фактический выбор поверх исходной сравнительной таблицы: raw events бессрочно;
random token; одновременно visible+focus+last-input≤5 мин; сообщения и voice без
edits/reactions; перекрытие получает deterministic winner (`presence > message`,
последнее событие, затем стабильный id); история `estimated`; хранение UTC и день
Красноярска. Поминутная projection не создаётся, сессии считаются из raw.

## Ограничения и риски

- Текущие `logs.content` содержат содержимое сообщений, но этот отчёт его не
  читает и не копирует. Для новой телеметрии это отдельный запрет, а не надежда на
  маскирование.
- Message timestamp — момент принятия/доставки батча, не обязательно начало
  печати, чтения или voice recording.
- Dashboard может быть открыт в нескольких вкладках/устройствах, но текущая БД
  не наблюдает это. Число 9 активных orchestrator-сессий — число серверных
  сессий, не число вкладок.
- Сигнал «последний assistant text» не покрывает чтение ответа без следующего
  сообщения и не знает, кто именно читал Telegram.
- 23 сентября — неполный день; ранние дни до 03 сентября и работа вне Orchestra
  отсутствуют.
