# V-699: spawn latency and V-695 recovery

## Измерение

Исторические записи боевой SQLite читались через `mode=ro`; запросы не читали текст логов и не меняли БД. Пять перечисленных в задаче первых вызовов `spawn_worker` заканчиваются `ReadTimeout` примерно на 30 секундах. У четырёх из пяти на момент первого таймаута ещё нет строки начальной доставки; у `dz-vznaniya` доставка появилась только после повторного вызова. Это подтверждает, что клиент не дошёл до POST начальной доставки, а таймаут пришёл из создания сессии.

Ступени измерены на реальных текущих Git-репозиториях целевых проектов в одноразовых клонах `--shared --no-checkout`; рабочие деревья создавались в каталоге измерения, без боевой БД и сервиса. Запускал текущий `app.workspace.create_worktree` с worktree-конфигом `default`, отдельно замерил сборку промпта по фактическим scope проектов.

| Репозиторий | Файлов в Git | Сумма размеров Git blob | `git worktree add --detach` | Весь `create_worktree` | `assemble_prompt` |
|---|---:|---:|---:|---:|---:|
| seedon | 4 767 | 1 247 867 967 | 38.223 с | 38.847 с | 0.184 с |
| katya-work | 3 341 | 2 031 504 235 | 105.617 с | 107.359 с | 0.449 с |

Основное время уходит на материализацию tracked-файлов при `git worktree add --detach`; все остальные команды настройки worktree заняли менее двух секунд. Сборка промпта заняла менее половины секунды. Медленный Git checkout был причиной 30-секундного `ReadTimeout`; повторы прежней длительности не требуются, если HTTP и MCP host deadlines превышают подготовку worktree и начальную доставку.

## Другой дефект V-695

`spawn_resume_verdict` теперь отдельно отказывает с `SPAWN_TASK_MISMATCH`, когда совпадает `delivery_id`, но изменён текст задачи, и с `SPAWN_DELIVERY_ID_MISMATCH`, когда имя воркера занято другим `delivery_id`. Тест проверяет изменённый даже одним пробелом текст и чужой id, а также тексты отказов с дальнейшим действием. Это устраняет ситуацию, когда повтор задачи seedon отличался от исходной на 49 символов и выглядел как сбой идемпотентности.

## Проверка клиентских дедлайнов и исправление

OpenAI config reference задаёт `mcp_servers.<id>.tool_timeout_sec` как число и указывает default 60 секунд; верхний предел там не задан. Сгенерированный Codex `orchestra` MCP server теперь получает 360 секунд: [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference).

Claude Code MCP docs задают per-server tool timeout в миллисекундах, показывают 600000 мс как десятиминутный пример и описывают его как жёсткий wall-clock дедлайн. Верхний предел в документации не указан. При незаданном `MCP_TOOL_TIMEOUT` default — около 28 часов; timeout для stdio также не ограничивается HTTP first-byte таймером. У текущего процесса Orchestra `MCP_TOOL_TIMEOUT` не задан, поэтому этот default действует на Claude Agent SDK/CLI. Источник: [Claude Code MCP docs](https://code.claude.com/docs/en/mcp).

Вариант 0 реализован: только `POST /api/sessions` внутри `spawn_worker` получает HTTP timeout 300 секунд; остальные вызовы `_api` сохраняют 30 секунд. В Codex конфиг добавляет `tool_timeout_sec = 360` только для `orchestra`, чтобы оставить запас на создание, начальную доставку и формирование результата.

Повторный одиночный checkout seedon выполнен после сообщения о восстановлении свободного места. Он занял **147.702 с** на `git worktree add --detach`, при `nice=15`. Во время этого замера параллельно шёл ещё один Git checkout в seedon, поэтому значение включает конкурирующую I/O нагрузку и не является чистым замером только влияния свободного места. Повторять checkout по условию задачи не стал. Единственная созданная временная папка немедленно перемещена через `trash`; в корзине она занимает около 1.2 ГБ, поэтому место физически освободится после окончательной очистки корзины.

Наиболее долгий измеренный checkout seedon укладывается в HTTP deadline 300 с с запасом примерно 152 с; host Codex настроен на 360 с, Claude default существенно выше. Проверка: `/home/kesha/orchestra/.venv/bin/python -m pytest tests/test_spawn_resume_695.py tests/test_mcp_stdio.py::test_spawn_passes_base_branch tests/test_backend_codex.py::test_mcp_config_rendered_into_config_toml_not_argv tests/test_backend_codex.py::test_mcp_config_supports_url_only_servers -q` — **8 passed**. Импортированный модуль: `/home/kesha/orchestra/worktrees/home-kesha-orchestra/fix-spawn/app/__init__.py`.

Мутации проверены после коммита `ad3a8a37` с новыми тестами: возврат `SPAWN_CREATE_TIMEOUT_S` с 300 до 30 с сделал `test_spawn_passes_base_branch` красным (`expected 300`, получил `30.0`); возврат Codex `tool_timeout_sec` с 360 до 60 сделал оба теста сгенерированного host-конфига красными. Производственный код восстановлен после каждого замера мутации.

Оркестратор 05.10 выбрал вариант 0 как достаточный; отдельного pending-состояния и изменения поведения `get_worker_info` / `delivery_status` не делаем. В штатном последовательном потоке вызывающий ждёт ответ `spawn_worker`, поэтому не опрашивает сессию во время создания. Если Claude Code отводит вызов в фон после двух минут, событие о завершении всё равно приносит ответ. Повтор после неоднозначного исхода безопасен с тем же `delivery_id` и исходным точным текстом благодаря `spawn_resume_verdict`; иной текст/ID теперь получают разные отказы.
