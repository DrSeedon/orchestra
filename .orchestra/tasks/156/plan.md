# #156 — план: автотриггер пробуждения после лимита

Основано на `research.md`. Механизм исправен, отсутствует ОДИН вызов. План — минимальный:
вызов из idle-safe точки + дебаунс. `limit_wake.py` не перерабатываем.

## Решение в одну фразу

Когда ход завершился на subscription-лимите и статус агента уже выставлен (`IDLE`/`WAITING`),
Orchestra сама вызывает существующий `schedule_wake_after_reset()`, не чаще раза в
`WAKE_AUTO_DEBOUNCE_SECONDS`.

## Точка врезки — измерена, не угадана

`app/session_turns.py`, метод `after_turn_idle_actions` (строка 344 в текущем файле).

Почему именно он — три факта из кода:
1. Он вызывается СТРОГО ПОСЛЕ `finish_turn_status()` (`session_turns.py:342-343`), а тот уже
   выставил `AgentStatus.IDLE` либо `WAITING` и сделал `_persist()`. Условие оркестратора
   «агент к моменту вызова должен быть УЖЕ idle» выполняется структурно, а не по договорённости.
2. Флаг `subscription_limited = s._session_limit_hit` уже вычислен в этом же обработчике
   (`session_turns.py:248`) — новый детектор не нужен, передаём готовое значение параметром.
3. Рядом уже живут аналогичные post-turn действия (`fire_auto_report`, `_hibernate.schedule`),
   то есть это штатное место для «что сделать после хода», а не новый семафор.

**Что НЕ трогаем:** `session.py:1038/1066` — там лимит только распознаётся, статус агента в
этот момент ещё `RUNNING`. Врезка туда разбудила бы агента посреди хода. Разрешение править
`session.py` от оркестратора получено, но по факту правка в `session.py` **не требуется** —
seam оказался в `session_turns.py`. Сообщаю явно: это уточнение, а не самовольное сужение.

## Дебаунс — обязателен (условие оркестратора)

Модуль-владелец: `app/limit_wake.py`. Причина размещения там же, где планировщик — одна мысль,
один owner: дебаунс защищает `schedule_wake_after_reset` и обязан работать для любого будущего
вызывающего, а не только для этого одного.

Механика: модульный `_last_auto_schedule: datetime | None` + константа
`WAKE_AUTO_DEBOUNCE_SECONDS = 60`. Новая функция `schedule_wake_auto()`:
- прошло меньше окна с прошлого автозапуска → выходим, ничего не делая (лог `debug`);
- иначе фиксируем отметку **до** запуска и зовём `schedule_wake_after_reset()`.

Отметка ставится до вызова, а не после: залп из десяти агентов приходит в один event-loop tick,
и отметка после `await` пропустила бы все десять. Ручной вызов кнопкой дебаунс **не трогает** —
человек нажал осознанно.

Почему 60 секунд: приёмка допускает «около минуты» задержки, а `run_wake_job` при открытой
ёмкости стартует с `delay=0.1s`. Дебаунс режет только повторные планирования внутри залпа;
первый агент залпа планирует когорту, а `_load_limit_stopped_agents()` внутри планировщика
собирает ВСЕХ остановленных, включая тех, кто упёрся секундой позже — их подберёт та же когорта.

## Известная цена (зафиксирована, не дефект)

При открытой базовой ёмкости и закрытом monthly gate агент будет разбужен немедленно
(`available_now`), потратит один холостой ход и снова упрётся. `run_wake_job` поймает это
(`limit_turn_id > target`, `limit_wake.py:621-628`) и остановит когорту. Один ход против
ручного пинка каждый раз — принято оркестратором как цена.

## Tickets

### T1 — дебаунс-обёртка `schedule_wake_auto()` в `limit_wake.py`
- Files: `app/limit_wake.py` (+~20 строк), `tests/test_limit_wake.py`
- Что: константа `WAKE_AUTO_DEBOUNCE_SECONDS = 60`, модульная отметка `_last_auto_schedule`,
  async-функция `schedule_wake_auto()`, вызывающая существующий `schedule_wake_after_reset()`.
  Отметка ставится ДО вызова. Исключения наружу не выпускаем (пробуждение — не критический
  путь хода): ловим, логируем `logger.warning`, ход агента не ломаем.
- AC:
  - два подряд вызова `schedule_wake_auto()` внутри окна → `schedule_wake_after_reset`
    вызван РОВНО один раз;
  - вызов после истечения окна (подменённое время) → второй вызов проходит;
  - десять параллельных `asyncio.gather(schedule_wake_auto())` → ровно один проход;
  - исключение внутри `schedule_wake_after_reset` не пробрасывается наружу;
  - прямой вызов `schedule_wake_after_reset()` (кнопка) дебаунсом НЕ блокируется.
- blocked-by: none

### T2 — автовызов из idle-safe точки
- Files: `app/session_turns.py` (+~6 строк), `tests/test_limit_wake.py`
- Что: `after_turn_idle_actions` получает флаг `subscription_limited: bool = False`;
  вызывающий (`handle_turn_end`) передаёт уже вычисленное значение со строки 248.
  При `True` → `s._spawn_bg(schedule_wake_auto())` (импорт внутри функции — так же, как
  сделаны соседние `from app.bg_jobs import bg_manager`, чтобы не тянуть цикл импортов).
- AC:
  - ход завершился с `_session_limit_hit=True` → `schedule_wake_auto` вызван, и на момент
    вызова `s.status` уже НЕ `RUNNING` (проверяется в тесте записью статуса из подменённой функции);
  - обычный ход (`_session_limit_hit=False`) → `schedule_wake_auto` НЕ вызван;
  - авто-report и hibernate после правки продолжают работать (существующие тесты зелёные);
  - **(добавлено самопроверкой)** ход с `_session_limit_hit=True` НЕ уходит в раннюю ветку
    auto-continue (`session_turns.py:277-287`), то есть seam достижим. Замер, а не допущение:
    ветка требует `stop_reason in (error_max_turns, max_turns)` и `ok=True`, а лимит даёт
    `stop_sequence` — но проверяем фактом, а не рассуждением.
- blocked-by: T1

## Риски правки

- **Цикл импортов** `session_turns → limit_wake → session`. `limit_wake.py:18` уже импортирует
  из `app.session` на верхнем уровне, поэтому импорт в `session_turns` делаем **внутри функции**.
  Проверка на T2: `python -c "import app.main"` должен пройти.
- **Тесты, приколоченные к сигнатуре** `after_turn_idle_actions`. Новый параметр — с дефолтом
  `False`, существующие вызовы не ломаются. Перед правкой грепнуть тесты на имя метода.
- **Мутационная проверка** (моя же грабля): после зелёных тестов T1/T2 убрать вызов
  `schedule_wake_auto` из `session_turns.py` и убедиться, что тест T2 КРАСНЕЕТ. Зелёный тест
  без мутации ничего не доказывает — на прошлых задачах fallback дважды маскировал дефект.
