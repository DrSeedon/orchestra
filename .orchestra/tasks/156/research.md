# #156 — агент, срезанный лимитом, не просыпается сам

Фаза 1. Все три кандидата из постановки **опровергнуты замером**. Настоящая причина —
четвёртая, в постановке не рассматривалась.

## Question

### Context
`app/limit_wake.py` (712 строк) умеет классифицировать агентов, остановленных на
subscription-лимите, планировать `bg_jobs`-таймер на момент разблокировки и доставлять
пинок с проверкой ёмкости провайдера. Живой инцидент 05.08.2026: воркер `merge-contours`
срезан на `monthly spend limit`, ушёл в idle и не вернулся после восстановления квоты.
`bg_list()` в момент инцидента не показывал ни одного задания на пробуждение.

### Change under test
Почему для `merge-contours` не было создано задание на пробуждение, и что нужно изменить,
чтобы агент, срезанный **любым** видом лимита, возвращался к работе сам.

### Baseline
Текущее поведение: возврат агента выполняет человек — вручную пинает или жмёт кнопку
«Разбудить после сброса» на дашборде.

### Outcome (measurable)
Для воспроизведённого состояния «срезан месячным лимитом» задание на пробуждение
существует в `bg_jobs`, и после открытия ёмкости агент получает ход.

## Hypotheses considered

| # | Гипотеза | Фальсификатор | Вердикт |
|---|---|---|---|
| H1 | `monthly` намеренно исключён из планирования (нет `resets_at`) | прогнать планировщик на данных инцидента: если вернёт schedule — H1 ложна | **REFUTED** |
| H2 | Задание создаётся, но не переживает рестарт/hibernate | найти в `bg_jobs` хоть одну запись `wake-limit-*` в истории | **REFUTED** |
| H3 | Условие создания требует полей, которых у месячного лимита нет | тот же прогон планировщика на реальном снимке | **REFUTED** |
| H4 | Механизм не имеет автоматического триггера — вызывается только человеком | найти вызов `schedule_wake_after_reset` из кода, не из HTTP-ручки/тестов | **CONFIRMED** |

## Findings

### F1 — Детектор лимита сработал штатно. CONFIRMED
Тир 1 (прямое измерение по БД, read-only копия `data/orchestra.db`).
Сессия `merge-contours` = `d8291c34-f2b5-4269-bcc6-608db72331d2`, статус `idle`.
Хвост лога дословно:

```
420469|2026-08-05T14:02:48|text|You've hit your monthly spend limit · raise it at claude.ai/settings/usage?from=cc_cli_limit_message
420470|2026-08-05T14:02:48|error|⏳ subscription limit — ждём сброса квоты. НЕ ретраим
420473|2026-08-05T14:02:48|status|turn ended (stop_sequence, 65 turns, $4.66 turn ...) | 5h:99% reset 0h17m 7d:45% reset 5d16h
```

`_subscription_limit_kind` (`app/session.py:39-43`) на этой фразе возвращает `"monthly"`;
`app/session.py:1038` ставит `_session_limit_hit`, `:1066` печатает «НЕ ретраим».
Детект и защита от слепого ретрая работают ровно как задумано.

### F2 — Заданий на пробуждение не существовало НИКОГДА. CONFIRMED, опровергает H2
Тир 1. `SELECT id,type,status,created_at FROM bg_jobs WHERE id LIKE 'wake-limit-%'` →
**0 строк** при 15 записях в таблице всего. Задание не «не дожило» — оно не создавалось
ни разу за всю историю базы. H2 отпадает: нечему было умирать на рестарте.

Масштаб проблемы: `type='error' AND content LIKE '%subscription limit%'` с 01.07.2026 →
**102 срабатывания**. Топ пострадавших с 20.07: `intent-hunter` 16, `Orchestra-orchestrator` 9,
`feat-mccfr-scale` 8, `COG-second-brain-orchestrator` 8, `terrain-dev` 7, `seedon-orchestrator` 7.
То есть 102 раза агент вставал и 0 раз система планировала возврат.

### F3 — Планировщик поставил бы monthly-агента в очередь НЕМЕДЛЕННО. CONFIRMED, опровергает H1 и H3
Тир 1 (исполнение продового кода на снимке инцидента, `/tmp/probe156.py`).
Вход — ровно те окна, что напечатаны в логе строки 420473 (`5h:99% / 7d:45%`),
агент с `limit_kind="monthly"`:

```
readiness(anthropic, live 5h=99%): {'state': 'available', 'reason': 'base capacity is open'}
plan schedules: [{'provider': 'anthropic', 'reason': 'available_now', 'reset_at': None,
                  'agents': [{'id': 'd8291c34', 'name': 'merge-contours', ...}]}]
plan manual: []  unavailable: []
```

Три следствия, каждое убивает по кандидату:
1. `build_wake_plan` **не смотрит на `limit_kind` вообще** — `monthly` не исключается
   (H1 ложна). Классификация идёт от ТЕКУЩЕЙ ёмкости провайдера, а не от текста лимита.
   Это результат #98: терминальный текст перестал быть приговором.
2. Никаких недостающих полей не потребовалось (H3 ложна) — план построен целиком.
3. `reason=available_now` → `delay=0.1s` (`limit_wake.py:414-418`). Агент был бы разбужен
   через долю секунды, а не «после сброса».

Важная деталь: базовое окно на момент среза было **99%, то есть открыто**. Месячный
spend limit — это отдельный gate доплат, он режет ход, не трогая 5h/7d. Поэтому «ждать
сброса» тут вообще не нужно было: ёмкость подписки уже была.

### F4 — У механизма нет автоматического триггера. CONFIRMED — это и есть причина
Тир 1 (полный grep вызовов по репозиторию, исключая worktrees):

```
tests/test_limit_wake.py:406,456,513,567,620,656,707,814  → тесты
app/routes/system.py:1053  → @router.post("/api/usage/wake-after-reset")
app/static/js/analytics.js:284 → кнопка на дашборде
```

Других вызовов `schedule_wake_after_reset` нет. Путь ровно один:
**человек открыл дашборд → нажал кнопку → POST → план**. В `app/session.py:1038/1066`,
где лимит распознан, вызова планировщика нет; в `app/bg_jobs.py:607` находится только
исполнитель уже созданного задания (`run_wake_job`), не создатель.

Это согласуется с историей: #87 ставил задачу именно как «кнопка на дашборде», #97/#98
чинили её классификацию. Автоматизации никто не заказывал — она отсутствует by design,
а не сломана.

### F5 — Слепого ретрая при автотриггере не будет: защита уже встроена. CONFIRMED
Тир 1 (чтение `run_wake_job`, `limit_wake.py:588-615`). Перед КАЖДОЙ доставкой:
`current_provider_usage(provider, force_refresh=True)` → `provider_readiness` →
`if readiness["state"] != "available": break`. Плюс проверка «агент снова упёрся»
(`limit_turn_id > target`, `:621-628`) и dedupe по токену (`_wake_token_seen`).
Грабля из постановки («не бить в стену») закрыта существующим кодом — автотриггеру
не нужно изобретать проверку готовности, только позвать готовый вход.

### F6 — Есть штатный durable-механизм отложенного вызова. LIKELY
Тир 2 (первичный источник — код). `bg_jobs` переживает рестарт (таблица в SQLite,
`expires_at`/`trigger_at`), `bg_manager.create(..., replace_key=...)` идемпотентен по ключу
`wake-limit-<provider>`, `_schedule_lock` защищает от гонки параллельных планирований
(тест `test_limit_wake.py:814`). LIKELY, а не CONFIRMED: восстановление конкретно
wake-задания после рестарта я не воспроизводил — записей в БД для этого не было (F2).

## Counter-evidence и риски

- **Против «просто позвать планировщик на каждом лимите»:** `schedule_wake_after_reset`
  атомарно ЗАМЕНЯЕТ таймеры провайдера (`replace_key`). Если десять агентов упрутся в
  лимит подряд, десять вызовов подряд перепланируют одну и ту же когорту. Гонку держит
  `_schedule_lock`, но каждый вызов делает `force_refresh` usage — это сетевой запрос к
  провайдеру. Нужен дебаунс, иначе на массовом лимите (а он массовый: 102 события)
  получим шквал refresh'ей.
- **Против автопинка вообще:** агент, срезанный на монтли-лимите, будет разбужен
  немедленно (F3, `available_now`), потратит ход — и может снова упереться в тот же
  monthly gate, если базовая ёмкость открыта, а доплаты закрыты. `run_wake_job` это
  ловит постфактум (`hit the limit again`) и останавливает когорту, но один холостой ход
  на агента будет потрачен. Это цена, а не дефект; альтернатива — не будить вовсе.
- **Гипотеза, не проверенная:** переживает ли уже созданное `wake-limit-*` задание
  рестарт сервиса. Проверять на живой системе, а не на пустой таблице.
- **Не проверено:** поведение при провайдере `codex` — `provider_readiness` для
  не-anthropic идёт другой веткой (`limit_wake.py:180-211`). Инцидент был на anthropic.

## Affected files

- `app/limit_wake.py` — точка входа для автотриггера + дебаунс. Владелец логики.
- `app/session.py:1038,1066` — место, где лимит уже распознан; **общий рантайм**,
  правка только с разрешения оркестратора. Минимально — один вызов-хук.
- `app/bg_jobs.py` — трогать, скорее всего, не нужно: исполнитель готов.
- `tests/test_limit_wake.py` — существующий каркас тестов (1055+ строк) переиспользуем.

## Edge cases

- Лимит ловится в обработчике `text` ДО `turn_end` — хук должен вешаться так, чтобы
  агент уже был `idle`, иначе разбудим сами себя посреди хода.
- Оркестратор и воркер оба попадают в выборку `find_limit_stopped_agents`.
- Агент, убитый/заархивированный после лимита: `ensure_loaded` вернёт None — уже обработано.
- Пользователь вручную пнул агента раньше таймера → `limit_turn_id` разойдётся,
  доставка пропустится (`:648-650`). Уже обработано.

## Вывод для гейта

Чинить нечего — механизм исправен и безопасен. Не хватает ОДНОГО: автоматического вызова
`schedule_wake_after_reset` в момент, когда агент встал на лимите. Это правка на единицы
строк плюс дебаунс, а не переработка `limit_wake.py`.

## Приложение — независимая перепроверка F4 (второе мнение)

Codex как рецензент недоступен: квота исчерпана до 08.08. Вместо внешнего вердикта —
исчерпывающий поиск по всем путям, включая динамическую диспетчеризацию (`grep -rn "wake"`
по всему `app/`, без фильтра по имени функции). Результат: единственная ветка, ведущая к
пробуждению, — `bg_jobs.py:387` `config["action"] == "wake_subscription_limited"` →
`_run_wake_timer` → `run_wake_job`, то есть ИСПОЛНЕНИЕ уже созданного задания.
Создателя, кроме HTTP-ручки, нет. Это self-review, а не внешний вердикт — так и фиксирую.

Побочная находка, усиливающая опровержение H2: `bg_reset_wake_triggering` (`app/db.py:1434`,
вызывается `bg_jobs.py:460` на старте) специально восстанавливает wake-задания, прерванные
рестартом. Устойчивость к рестарту не просто есть — она отдельно запрограммирована.
