## Часть 1 — хрупкость кеша в `/tmp`

> **СТАТУС ПОСЛЕ ПРОВЕРКИ БОЕМ (11:23):** шаг 1 выполнен оркестратором (561 МБ скопированы
> в `/home/kesha/.cache/fastembed`, симлинков 5 к 5, владелец `kesha`). Ребут состоялся,
> кеш в `/tmp` уцелел → срочности НЕТ, окно «48 часов» неактуально.
> Шаги 2-4 остаются как плановая гигиена, делать при согласовании с владельцем без спешки.
> Прогноз «гарантированная потеря» был неверен — разбор ниже.

### Почему это выглядело назначенной аварией (прогноз, оказавшийся неверным)

Проверено на VPS:

| Факт | Проверка | Значение |
|---|---|---|
| `D /tmp 1777 root root 30d` | `/usr/lib/tmpfiles.d/tmp.conf` | `D` = **очистить каталог при загрузке**; `30d` = плюс чистка по возрасту |
| `systemd-tmpfiles-clean.timer` | `is-active` → **active** | правило 30d живое, не декоративное |
| atime блоба | `2026-08-03 06:59:17` | обновляется при каждом старте бота → 30d сам по себе не сработает |
| `/` смонтирован `relatime` | `findmnt -no OPTIONS /` | atime обновляется, но это спасает только от 30d, **не от ребута** |
| `/tmp` — не tmpfs | `findmnt /tmp` пусто, `df` = `/dev/sda1` | переживает работу, но `D` всё равно чистит на boot |

Итого: 30-дневное правило не сработает (atime свежий), но **`D` при загрузке снесёт кеш
гарантированно**. Contabo Live Migration (тикет 16240351353, окно 48 ч) = ребут.
После него бот на старте качает 561 МБ через прокси из РФ — на машине, которая только что
мигрировала, с высокой вероятностью неудачи и краша RAG-инициализации.

### ⚠️ ПРОВЕРКА БОЕМ: прогноз «гарантированная потеря» ОПРОВЕРГНУТ (2026-08-03 11:23)

Ребут состоялся — Contabo мигрировал VPS в 11:23 (стало 8 ядер / 24 ГБ).
**Кеш в `/tmp` пережил его: 561 МБ на месте**, mtime 11:23:28.

Разобрал причину, потому что «не сработало» без механизма — бесполезная запись.
Я ошибся не в том, ЧТО делает `D`, а в том, как на него влияет поле возраста:

| Что я утверждал | Что на самом деле |
|---|---|
| `D` = безусловная очистка каталога при загрузке; `30d` — отдельное дополнительное правило | Поле возраста **квалифицирует** `D`. Удаляется только содержимое СТАРШЕ 30d |

Первоисточник, `man 5 tmpfiles.d` на самой машине:
- `D` — «the contents of the directory will be removed **when `--remove` is used**»;
- раздел *Age* — «The age field **only applies to lines starting with d, D, e, v, q, Q, C**…
  If a file or directory is older than the current time minus the age field, it is deleted»;
- «When the age is set to zero, the files are cleaned unconditionally» — то есть
  безусловная очистка была бы при `D /tmp 1777 root root 0`, а у нас `30d`.

Boot-юнит `--remove` действительно передаёт (`ExecStart=systemd-tmpfiles --create --remove
--boot --exclude-prefix=/dev`, отработал `status=0/SUCCESS` в 11:23:14), так что механизм
запустился — просто кеш не подпадал под возраст. atime блоба обновляется при каждом старте
бота (`/` смонтирован `relatime`), поэтому 30 дней он не наберёт, пока бот живёт.

**Вывод меняется существенно:** авария не «назначена на ребут», а наступает только если бот
не стартует дольше 30 дней (тогда atime протухнет) либо кто-то поставит `0` / запустит
`systemd-tmpfiles --clean` вручную. Риск из высокого становится низким, но НЕ нулевым —
и защита от него уже сделана бесплатно (шаг 1 выполнен, копия в `/home/kesha/.cache/fastembed`).

**Урок метода:** я прочитал `D` в конфиге и остановился на подтверждающей строке man,
не проверив, как на директиву влияет соседнее поле. Классическое подтверждение гипотезы:
искал «что делает D», а надо было «при каких условиях D НЕ срабатывает».
Прогноз оказался сильнее реальности — фиксирую как ошибку, а не как «повезло».

### Что делать: перенести кеш в постоянный каталог

Владелец `/opt/kesha-bot` — чужой, выполняет оркестратор после согласования.
Бот работает под `User=kesha`, `Environment=HOME=/home/kesha`, `EnvironmentFile=/opt/kesha-bot/.env`.

**Целевой каталог:** `/home/kesha/.cache/fastembed` — тот же владелец `kesha`, тот же диск
(`/dev/sda1`, 109 ГБ свободно), переживает ребут и правило 30d не действует.

**Почему НЕ шарить каталог с копией Orchestra** (`/home/kesha/orchestra/data/models`):
соблазнительно (сэкономит 561 МБ диска), но это связывает два проекта общим состоянием
ради диска, которого не жалко — свободно 109 ГБ. Дефицит у нас **память, а не диск**.
Общий каталог экономит 0 байт RAM. Отклонено осознанно: цена — скрытая связанность
чужого проекта с нашим, выигрыш — ноль по дефицитному ресурсу.

### Команды (выполняет оркестратор; сам не выполняю — VPS read-only + чужой проект)

Шаг 1 — перенести кеш БЕЗ повторного скачивания (не трогает работающий бот):

```bash
# от root, кеш принадлежит kesha — сохранить владельца
mkdir -p /home/kesha/.cache/fastembed
cp -a /tmp/fastembed_cache/. /home/kesha/.cache/fastembed/
chown -R kesha:kesha /home/kesha/.cache/fastembed
du -sh /home/kesha/.cache/fastembed   # ожидается 561M
```

`cp -a` сохраняет симлинки blobs→snapshots (структура HF-кеша на них держится) и владельца.
`/tmp` пока НЕ удалять — страховка на случай отката.

Шаг 2 — прописать переменную:

```bash
grep -n FASTEMBED_CACHE_PATH /opt/kesha-bot/.env || \
  echo 'FASTEMBED_CACHE_PATH=/home/kesha/.cache/fastembed' >> /opt/kesha-bot/.env
```

Шаг 3 — применить (рестарт бота, окно ~30 c; согласовать с владельцем):

```bash
systemctl restart kesha-bot-vps
journalctl -u kesha-bot-vps -f --since -2min | grep -iE "embedder loaded|error|download"
```

**Критерий успеха:** в журнале `RAG embedder loaded (shared): AlpEge/bge-m3-onnx-int8`
без строк о скачивании, и:

```bash
ls -la /proc/$(systemctl show -p MainPID --value kesha-bot-vps)/cwd
tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value kesha-bot-vps)/environ | grep FASTEMBED
```

Шаг 4 — только после успешного шага 3, освободить `/tmp`:

```bash
rm -rf /tmp/fastembed_cache   # ⚠️ деструктивно, ТОЛЬКО после подтверждённого шага 3
```

### Откат

Убрать строку из `.env` → `systemctl restart kesha-bot-vps`. Кеш в `/tmp` цел (шаг 4 не выполнен).

### Если согласовать с владельцем до миграции не успеваем

Минимальная страховка **без** рестарта и без правки чужого `.env` — только копия:
шаг 1 в одиночку. Тогда после ребута кеш в `/tmp` исчезнет, бот скачает заново — но
у нас будет локальная копия для мгновенного восстановления вместо загрузки через прокси.

## Часть 2 — вариант А (общий эмбеддинг-сервис): честная оценка

### Рекомендация: НЕ ДЕЛАТЬ

Оркестратор просил оценить честно, стоит ли отдельная задача ради 3.7% памяти. Считаю — нет.

**Арифметика после апгрейда.** 0.89 ГиБ из 24 ГБ = **3.7%**. До апгрейда это было 11% на
машине, где swap забит — там дублирование было настоящей болью (SwapPss 1.74 ГиБ у процесса
Orchestra, load 31.7). После апгрейда исчезает не сам расход, а **механизм ущерба**:
своп перестаёт быть горячим, и второй экземпляр из причины деградации становится просто
неаккуратностью.

**Цена варианта А, честно:**
- изменение `rag.py` в **чужом** `/opt/kesha-bot` + координация с владельцем;
- новый долгоживущий сервис: сокет, протокол, батчинг, обработка недоступности,
  автозапуск, наблюдаемость;
- новая точка отказа: сейчас падение RAG у бота не задевает Orchestra и наоборот.
  Общий сервис делает их зависимыми — за 3.7% памяти мы покупаем общий SPOF;
- тесты на два проекта сразу.

**Прецедент.** #113 отклонил близкий по механике вариант (эмбеддер отдельным процессом):
0 ГиБ активного выигрыша, IPC не окупился. Там причина отклонения была другая (не экономился
второй экземпляр), поэтому переносить вывод автоматически я в research.md отказался.
Но инженерная часть — IPC, живучесть, батчинг — та же самая, и она уже один раз была
признана не окупающейся.

**Что делает вариант А осмысленным снова** (триггеры для переоткрытия):
- апгрейд не состоялся или памяти снова не хватает (`SwapPss` растёт, load держится высоким);
- появляется третий потребитель эмбеддингов — тогда экономится 2×0.89 ГиБ и меняется баланс;
- обе системы переходят на общий корпус (сейчас корпуса разные: у бота сообщения,
  у копии Orchestra — файлы).

**Что сделать вместо** — ноль строк кода, часть 1 уже это и делает: убрать хрупкость
(`/tmp`) и лишнюю копию на диске. Память после апгрейда перестаёт быть дефицитом,
а «гигиену» покупать ценой SPOF между двумя проектами — плохая сделка.
