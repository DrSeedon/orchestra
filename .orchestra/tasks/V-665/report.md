# V-665: анимированные объяснения в HTML-артефактах

Запрос владельца (29.09): анимации и моушн в HTML-артефактах — с пояснениями, с пуском, паузой,
перемоткой, как можно удобнее; выбрать техники, на которые LLM тратит меньше токенов и которые
надёжны.

## Итог

- Добавлен новый скилл `.orchestra/pipelines/default/prompts/skills/html-motion.md`: правила
  и готовый каркас плеера на 65 строк. Скилл подключён всем ролям через `defaults.skills` в
  `pipeline.yaml`. В `base.md` одна фраза объявляет его спутником `html-artifacts`: иначе
  действующее правило «only the html-artifacts skill» уводило бы агентов мимо нового скилла.

  (`tests/test_prompting.py::TestHtmlArtifactsSkillInvariants::test_budget`), на HEAD там 15986,
  то есть запас 14 байт. Раздел с каркасом весит 12.5 КБ. Встроить его значило бы поднять

  «приложить» к скиллу: `inject_skills_to_worktree_report` (`app/prompting.py:297`) копирует в

  индексе скиллов (200 символов).
- Два рабочих примера: `task-path.html` (путь задачи владелец → оркестратор → воркер → мерж →
  рестарт) и `weekly-limit.html` (недельный лимит Claude 22–29.09 по реальным снимкам
  `usage_snapshots`). Кадры лежат в `shots/`, MP4 — в `video/`.

## Замер техник (одна сцена, одинаковые возможности плеера)

Сцена: три узла, точка идёт по двум рёбрам, узлы меняют цвет, в конце меняется текст статуса;
4 шага по 2 с. У всех вариантов одинаковые функции: пуск/пауза, шаги, ползунок, скорость,
клавиши, главы, подписи. Файлы лежат в `bench/`, размеры считает `bench/build.py`
(`bench/sizes.json`). Токены посчитаны токенизатором `o200k_base` (tiktoken). Это
приближение: токенизатор Claude не публичен.

| Вариант | Сцена: байт / строк / ток. | Плеер: байт / ток. | Файл: байт | Офлайн | Пауза = перемотка | Конец = перемотка в конец |
|---|---|---|---|---|---|---|
| A. Состояния шагов + чистая `render(t)` (выбран) | 1983 / 17 / **668** | 3011 / 1091 | 7 082 | да | 0 px | 0 px |
| B. Web Animations API (`element.animate`) | 2608 / 23 / 893 | 1954 / 671 | 6 627 | да | 0 px в прогоне offline; расхождение 131 px в первом прогоне | **1684 px** |
| C. GSAP-таймлайн, CDN | 2311 / 20 / 784 | 1650 / 582 | 6 095 | **нет**: `gsap is not defined` | — | — |
| C'. GSAP, встроен в файл | 2311 / 20 / 784 | 1650 / 582 | **78 976** | да | 0 px | 0 px |
| D. Canvas + `draw(t)` | 2054 / 16 / 741 | 1671 / 586 | 5 955 | да | 0 px | 0 px |

Как проверялось (`bench/check.py`, Chromium headless, контекст `offline=True`): «пауза =
перемотка» — снимок сцены, поставленной на паузу во время проигрывания, против снимка после
`P.seek(8)` → `P.seek(t_паузы)`. «Конец» — естественный конец при скорости 2 против
`P.seek(P.T)`. Отличающимся считается пиксель с разницей больше 8 по любому каналу. Перемотка
назад (`seek(8)` → `seek(3)` против `seek(3)`) дала 0 px у всех работающих вариантов.
WebKit не проверен: у Playwright 1.x на VPS нет `libgtk-4.so.1`.

Причины у B, подтверждены отдельной пробой:
- `Animation.pause()` применяется асинхронно: сразу после вызова `currentTime` = 733.3 мс
  (`pending=true`), через два кадра — 750.0. Время, прочитанное на паузе, и показанный кадр
  расходятся на кадр. Отсюда нестабильность: 131 px в первом прогоне, 0 px во втором.
- `play()` у завершённой анимации перематывает её в 0. После `seek(6.5)` + `play()` анимации
  шагов 1–3 (уже завершённые) проигрались заново: 5 анимаций стояли на 1633 мс, 3 — на 8000 мс.
  Воспроизводится стабильно (1684 px).
- WAAPI не анимирует текст, поэтому смену подписи в сцене всё равно пришлось писать вручную.

Почему основной — A:
- Сцена декларативная: шаг перечисляет только то, что меняется (`set`). Сцена стоит 668
  токенов — меньше всех. В B, C и D время каждого изменения приходится вычислять вручную:
  задержки, позиции на таймлайне, `p(i)` в Canvas.
- Детерминизм по построению: кадр — функция от `t`, состояние не накапливается.
- Один файл, без зависимостей, текст остаётся настоящим SVG — наведение и доступность
  работают.
- Плеер дороже, чем в B/C/D (1091 против 582–671 токена), но его не пишут: он вставляется
  из скилла готовым. Если у агента есть shell, каркас копируется командой `awk` из `SKILL.md`,
  и перепечатывать его не нужно вовсе. Проверено: извлечённый шаблон открывается без ошибок,
  кадры на 0 / 2 / 3.5 / 4.9 / 5 с верны.

Запасной вариант — D (Canvas) на **том же плеере**: шаги без `set`, рисование в хуке
`draw(i,p,t)`. Он тоже детерминирован (0 px), но теряет DOM (наведение, доступность, выделение
текста), вдобавок в сцене нужно вручную учитывать `devicePixelRatio` и расписание `p(i)`.
Он нужен, когда объектов слишком много для SVG. Порог числа объектов здесь не измерялся.

GSAP отклонён: с CDN артефакт офлайн пустой, а встроенный весит +73 КБ (`gsap.min.js`
3.15.0, 72 927 байт) при том же детерминизме, что у A. Текст в сцене GSAP всё равно пришлось
синхронизировать руками. Сторонний `gsap.min.js` и собранный `c-gsap-inline.html` не
закоммичены (`.gitignore` в папке задачи); `bench/build.py` скачивает их для повторения замера.

## Каркас (что в него входит)

27 строк JS плеера и 11 строк CSS; вместе с HTML управления это около 1.7 тыс. токенов.
Модель заполняет только SVG с `id` и массив `STEPS`:
`{d, t: что происходит, x: почему, set: {id: {attr: value}}, w: {id: [от, до]}, e}`.
- Числа и `#rrggbb` интерполируются, строки переключаются, `[a,b]` задаёт значение «от a к b»,
  `text` меняет текст, `along/at` ведёт элемент по SVG-пути.
- `w` — окно внутри шага. Появилось после проверки первого примера: подпись «+1 коммит» у main
  появлялась раньше, чем туда доходил `squash`; `w:[.75,1]` исправил это, `[.2,.5]` и `[.6,.9]`
  дали очерёдность двух коммитов.
- `draw(i,p,t)` — хук для вычисляемого (подпись курсора графика, Canvas).
- Плеер: пуск/пауза, ⏮ ⏭ до конца шага, ползунок, скорость 0.5/1/2, пробел/←/→/Home/End,
  главы кликом, `prefers-reduced-motion` (шаг сразу в итоговом состоянии), печать без
  контролов, ссылка `#t=12.5`, `window.P` для проверки.
- `$` объявлен через `function`, а не `const`: сцена графика вызывает `$` раньше кода плеера,
  и `const` дал бы ReferenceError (TDZ).

Сборка: `build_examples.py` берёт стиль, управление и плеер **прямо из
`skills/html-motion.md`** (одна копия каркаса) и собирает `src/*.src.html`. Проверка —
`check_examples.py` (Chromium, `offline=True`, `check_examples.json`).

| Проверка | task-path | weekly-limit |

| Ошибки JS и консоли | нет | нет |

| Узкий экран 390 px: переполнение страницы | 0 px (сцена прокручивается в своём блоке) | 0 px |

Кадры: `shots/*-start.png`, `*-mid.png`, `*-end.png`, `*-paused.png`, `*-narrow.png`.

По ходу проверки найдены и исправлены четыре дефекта:
1. На ширине 390 px панель управления переполняла страницу на 49 px → `flex-wrap`.
2. SVG ужимался до нечитаемых подписей → сцена в `.stg` с `min-width:680px` и локальной
   прокруткой.
3. Подпись из двух строк сдвигала кнопки во время проигрывания → `min-height:4.4em`.
4. Маркер события на графике появлялся раньше, чем до него доходила линия (прозрачность
   плавно росла весь шаг) → маркеры под тем же `clipPath`, что и линия.

Числа графика. Источник: `data/orchestra.db`, таблица `usage_snapshots`, открыта только на
чтение (`mode=ro`); поле `seven_day_pct`. Запрос и точки сохранены в
`weekly-limit-data.json`: 2025 снимков, из них 35 без данных квоты (разрыв линии).
Прореживание — первый снимок в каждом 20-минутном интервале плюс снимки событий, итого 511
точек. События посчитаны по полным данным: первый снимок ≥ порога. Подпись курсора в конце
каждого шага совпала с событием: 1 / 25 / 50 / 75 / 90 / 100 %. Факты из подписей:
- 50% за 3467.9 мин = 2.41 суток;
- максимум опережения — +25.0 п.п. (74% при равномерных 49.0%, 25.09 17:21 UTC);
- 50→75% прошли за 34.2 ч, 75→90% — за 55.1 ч;
- в минимуме расход отставал от равномерного на −4.5 п.п. (93%, 29.09 02:44 UTC);
- 100% — 29.09 06:31:54 UTC, за 28 мин до сброса в 07:00 UTC.

Время на графике — красноярское (UTC+7).

Видео: `record.py` пишет его через Playwright `record_video_dir` и перекодирует в H.264
(`ffmpeg -crf 28`). Получилось `video/task-path.mp4` (445 КБ, 27.4 с) и
`video/weekly-limit.mp4` (438 КБ, 23.5 с). Запись одного примера занимает около 30 с.
