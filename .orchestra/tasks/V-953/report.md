# V-953 — после сброса 5-часового лимита агенты не продолжили работу

## Что произошло на самом деле (БД и журнал, 18.10 UTC)
Гипотеза «таймер не создан из-за usage 99% и debounce» не подтвердилась: таймеры создавались. В `bg_jobs` за 10:10–10:26 шесть заменяющих друг друга джобов `wake_subscription_limited` (`reason=base_reset`, `reset_at=10:30:00`), финальный `bg-e8c34b9740` с 8 агентами (GM-orchestrator, ai-table-worker, fix-api, gamelab, gamelab-content, gamelab-ui, seedon-orchestrator, tender-cards). Идентификатор у них не `wake-limit-*`: это `replace_key`, а id обычный `bg-…`, поэтому по префиксу их не нашли. Джоб сработал в 10:30:00.001 и закончился: `last_output = "stopped: anthropic: base capacity has no timed reset"`, `deliveries` пусты.

Причина: `run_wake_job` в момент срабатывания принудительно обновляет usage; снимок Anthropic в первую долю секунды после сброса ещё показывал `utilization=100` с `resets_at=10:30:00` (уже ≤ now). `provider_readiness` трактовал любое окно с `reset <= now` как «нет времени сброса» → state `manual` → цикл прерван, джоб `triggered`, повторных попыток нет. К 10:36 usage был 0%, но будить было уже некому.

## Почему в 11:05 кандидатов было только двое
Остальные шестеро (tender-cards, gamelab-ui, gamelab-content, gamelab, sales, seedon-orchestrator) к 11:05 уже были подняты вручную оркестраторами (user_message «лимит сброшен, продолжай» около 11:00:34–11:00:49, дальше нормальные ходы). Поэтому `_latest_limit_turn` их справедливо не считает остановленными: после хода есть сообщение не от `limit_wake`. Фильтр здесь не виноват.

## Отдельный дефект кандидатов: sales
`sales` не попал ни в один план (проверено на логах на моменты 10:15:08 и 10:26:54). Лог: `provider_limit` → `error` → `turn ended` (10:15:03) → ещё один `turn ended` (10:15:06, без собственных строк). Окно «последнего хода» брало отрезок между двумя `turn ended` и не видело `provider_limit` → кандидатом не был. Orchestra-orchestrator выпал из планов 10:25:37 и 10:26:54 по причине, которую я не установил (на ровных логах до 10:26:54 он кандидат; статус сессии в момент вызова неизвестен) — **не подтверждено**.

## Исправления (`app/limit_wake.py`)
1. `provider_readiness`: окно с `resets_at <= now` считается сброшенным (не `manual`); окно без `resets_at` по-прежнему `manual`/`unavailable`; окно с будущим сбросом ждёт его.
2. `run_wake_job`: если ёмкость выглядит закрытой, неразбуженные цели перепланируются (`_rearm_wake`: таймер 120 с, `attempt` растёт, после 5 попыток отказ с записью в `last_output`). Раньше джоб молча заканчивался.
3. Отказ провайдера с `resets_at` — доказательство лимита вне зависимости от процента usage: `limit_reset_at` кандидата задаёт нижнюю границу таймера (usage 99% → всё равно `base_reset` на этот момент, не `available_now`).
4. `_latest_limit_info`: пустой дубликат `turn ended` сливается с предыдущим окном; SQL в `_load_limit_stopped_agents` захватывает четыре последних завершения хода.

Не изменено: ручная остановка и штатно завершённый ход агента не будятся (условие «после хода есть сообщение не от limit_wake» и отсутствие `provider_limit` остались). Debounce 60 с остаётся; пачка отказов в одну минуту даёт один пересчёт всей когорты, а один таймер на провайдера — одно пробуждение на агента (`replace_key`, проверка `deliveries`).
