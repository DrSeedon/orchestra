# V-1186 — read-only диагностика reset cron

Проверка выполнена 2026-11-01 около 10:25 UTC. Действующий reset-скрипт не запускался. Из provider/account RPC был вызван только `account/rateLimits/read`; `initialize` / `initialized` использовались лишь как handshake app-server. Не вызывались consume, генерация, авторизационные изменения и рестарты. Сырые account-данные и идентификаторы кредитов в отчёт не копировались.

## Сбой

Журнал cron содержит три почти одновременные доставки одного результата (10:23:25 UTC): `REDEEM_FAILED initialize: unexpected app-server EOF`, exit code 1. Эти близкие по времени записи не доказывают три отдельных запуска. В том же временном окне другой cron завершил запись с `OSError: [Errno 28] No space left on device`.

В активной копии `/home/kesha/.cache/canary-scripts/codex_reset.py` `AppServer.request()` выдаёт EOF, когда `os.read(stdout)` возвращает пустой блок (строки 127–138; тот же код в `scripts/codex_reset.py`). Это означает, что app-server закрыл stdout/завершился до ответа на `initialize`. Скрипт затем вывел `REDEEM_FAILED` и вернул 1. Его `Popen` направляет stderr дочернего app-server в `subprocess.DEVNULL` (строки 184–187), поэтому stderr не сохраняется; внешний `2>&1` в cron этого не меняет. Код выхода самого дочернего процесса не записан. Следовательно, ENOSPC подтверждён как одновременная ошибка записи на хосте и сильное объяснение отказа старта, но конкретный внутренний syscall/текст ошибки app-server восстановить нельзя.

## Кредит, лимиты и диск

Свежий `account/rateLimits/read` вернул одну недельную запись: использовано **95%**, reset **2026-11-05 08:32:34 UTC**. В списке два кредита, оба `available`; ближайший истекает **2026-11-06 22:47 UTC**, следующий — **2026-11-30 20:13 UTC**. Поскольку ошибка произошла на `initialize`, до запроса лимитов и до `consume` выполнение не дошло. Свежее состояние подтверждает, что оба кредита доступны на момент проверки; расход именно этим неуспешным запуском исключён по порядку вызовов.

Активная копия скрипта содержит `WEEKLY_RESET_THRESHOLD = 99`, inclusive-проверку `used >= threshold` и отдельную expiry-ветку `< 9 минут` (строки 20, 72–91). Сейчас 95% ниже порога, а ближайший срок дальше пяти дней: оба условия ложны, ожидаемый результат нормальной проверки — `no action`.

Текущий `df`: `/dev/sda1`, 290G всего, 280G занято, **9.8G доступно (97%)**; inode заняты на 7%. `/tmp` на той же файловой системе. Сейчас ENOSPC по этому mount не наблюдается. Журнал также содержит более ранние `No space left on device` при git/worktree-записях 1 ноября в 03:00, 08:43 и 08:46 CET.

`bg-7d176f2fd9` остаётся активным `cron_command` с расписанием `*/5 * * * *` UTC и вызывает отдельную live-копию скрипта через `timeout 60 python3 -I ...`; Orchestra active. Safe read-only запуск app-server с тем же `initialize` и последующим `account/rateLimits/read` сейчас завершился успешно. Вместе с активным job и текущим свободным местом это подтверждает техническую способность выполнить следующие read-проверки, но не является запуском следующего cron tick.

Последний зарегистрированный результат задания — EOF выше. Поиск логов user-message за 30 октября — 1 ноября просмотрел 511 записей, без усечения; позже этого результата успешный/no-action результат не найден. Обычный проход `no action` не обязательно создаёт сообщение, поэтому время последнего успешного poll неизвестно.

У текста задания есть устаревшие указания: он всё ещё называет порог 95% и говорит «This job just spent one», хотя live-скрипт уже обновлён на 99%, а EOF на `initialize` не мог вызвать consume. Это может дать неверное уведомление/направить расследование к consume.

## Безопасная процедура изменения текста уведомления

Штатного in-place update для активного cron нет: MCP предоставляет `bg_list`, `bg_create`, `bg_cancel`; HTTP API имеет только GET/POST/DELETE `/api/bg/jobs` (`app/routes/bg.py:306,386,392`). `bg_update_config()` обновляет строку только при `status='triggering'` и используется внутренним limit-wake flow (`app/db.py:2400–2407`), поэтому не подходит для активного reset cron. Внутренний `bg_replace_job()` атомарно заменяет задания с `replace_key` (`app/db.py:2251–2278`), но текущий публичный create-вызов не передаёт такой ключ для существующего job; прямое изменение БД не является поддержанным интерфейсом.

Уже проверенная процедура замены cron (зафиксирована в `.orchestra/tasks/V-1184/report.md`): сначала сохранить полный текущий config, message, target и идентичность; отменить старый job и подтвердить `cancelled`; затем создать один job с теми же командой, расписанием, matcher, timeout и target, изменив только message; после этого read-only проверить, что активен ровно один корректный job. При ошибке создания восстановить старый config; при неоднозначном результате сначала перечитать активные jobs, не повторять create вслепую. Создание нового до отмены старого запрещено этим сценарием: два потребителя могли бы одновременно попасть в условие кредита. Между cancel и create будет короткий пропуск cron tick; операция не выполнялась в рамках этой задачи.

Скрипт, расписание и live job не менялись. Тесты не запускались: задача была read-only и ограничивалась отчётом и проверкой поддержанного интерфейса. Рабочее дерево до добавления отчёта было чистым.
