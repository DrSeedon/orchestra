Путь задачи через оркестратор

Задача идёт по одному маршруту: пользователь → оркестратор → воркер в своём worktree → ревью → squash-мерж в main. Отклонений ровно два, и оба — циклы, а не тупики: ревью не прошло возвращает работу тому же воркеру, воркер упал возвращает управление оркестратору, который подбирает незакоммиченный WIP.

основной путь ветка отказа — возврат в цикл, задача не теряется

Что происходит в каждом узле

Пользователь
Формулирует задачу текстом. Дальше он в маршруте не участвует до отчёта.
Оркестратор
Разбирает задачу, выбирает модель, зовёт spawn_worker. Orchestra заводит воркеру git worktree и ветку task-<id>/<worker>.
Воркер
Правит файлы только внутри своего worktree, коммитит в свою ветку. Не трогает main и не мержит сам.
Ревью
Cross-LLM codex_review или самопроверка плюс прогон тестов. Здесь маршрут ветвится.
Мерж в main
merge_worker — squash-мерж, один коммит на задачу. Единственный, кто пишет в main, — оркестратор.
Ревью не прошло
Замечания уходят воркеру через send_message. Сессия и worktree живы, воркер продолжает с того же контекста — цикл повторяется до зелёного ревью.
Воркер упал
Ход оборван (stop_reason=error, пустой выхлоп). Оркестратор смотрит worker_wip — незакоммиченные файлы и неслитые коммиты, — коммитит WIP и резюмит либо респавнит воркера.

Что схема гарантирует

  • ИзоляцияОдин воркер — один worktree — одна ветка. Параллельные задачи не видят чужих правок до мержа.
  • Один писатель в mainВоркер физически не мержит. Любая работа попадает в main только через оркестратора.
  • Отказ не терминаленОбе красные ветки возвращаются в основной цикл. Потерять можно только незакоммиченное — поэтому воркер коммитит до отчёта.
  • Готово = чистое деревоПризнак завершения — пустой git status и коммит в ветке, а не сообщение «сделал».
