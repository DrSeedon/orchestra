История диалогов агента: SQLite, JSONL или вектор-стор

Три варианта отвечают на три разных вопроса. JSONL — «покажи, что именно произошло в этой сессии». SQLite — «посчитай и отфильтруй по всем сессиям». Вектор-стор — «где мы обсуждали что-то похожее». Выбор почти никогда не про скорость записи: любой из трёх успевает за агентом, который думает секундами. Выбор — про то, каким вопросом вы придёте к этим данным через месяц, и про то, что останется после падения процесса.

Коротко

Один абзац на вариант. Детали — ниже, в разборе.

A

SQLite — таблица

Один файл, одна таблица messages, индекс по сессии и времени

Компромисс по умолчанию. Даёт транзакции, фильтры, агрегаты и полнотекст (FTS5), не требуя ни сервера, ни сети, ни денег. Расплата — единственный писатель на базу и то, что данные больше нельзя посмотреть без клиента.

B

JSONL — файлы на диске

Файл на сессию, строка на сообщение, только дозапись в конец

Самый дешёвый и самый прозрачный вариант: tail -f, jq, git diff работают сразу. Битый хвост после падения отбрасывается одной строкой. Расплата — любой вопрос сложнее «покажи эту сессию» превращается в полный скан.

C

Вектор-стор — внешний

Чанки + эмбеддинги, поиск по близости, приблизительный по своей природе

Единственный, кто отвечает на вопрос «о чём похожем мы уже говорили» — тот самый, ради которого историю обычно и хранят. Но он производный: у него нет ни порядка сообщений, ни гарантий, ни исходного текста, если вы его туда не положили отдельно.

Пять критериев

Оценка — «для этой задачи», а не абсолютная: у истории диалогов запись редкая и мелкая, а чтение — пачками.

Сравнение SQLite, JSONL и вектор-стора по пяти критериям
Критерий SQLite JSONL Вектор-стор
Скорость записи Достаточно Коммит на сообщение упирается в fsync; пачка в одной транзакции снимает вопрос. Писатель на базу один. Лучшая Открыть на дозапись и писать. Дешевле уже не бывает — но без fsync строка живёт в page cache. Худшая Каждая запись — эмбеддинг плюс сеть плюс правка индекса. На порядки дороже двух других и может отказать.
Скорость поиска Точный — мгновенно По индексу — за микросекунды, по словам — FTS5. Смысловой поиск недоступен в принципе. Линейно Своя сессия — открыть файл. Любой вопрос «по всем» — прочитать и распарсить всё; растёт вместе с архивом. Единственный по смыслу Отвечает там, где два других молчат. Ответ приблизительный: ANN отдаёт не гарантированный топ, а близкий к нему.
Цена Только диск Ни сервиса, ни трафика. Текст сжимается плохо, зато не платится дважды. Только диск, дешевле Старые файлы жмутся и уезжают в архив по одному, без перестройки чего-либо. Плата за токены и за RAM Эмбеддинги оплачиваются за каждый токен — и повторно при смене модели. Индекс держится в памяти: цена ≈ объём.
Восстановление после сбоя Даётся даром WAL и журнал делают крэш-консистентность сами. Обратная сторона: повреждение одного файла бьёт по всей истории. Проще некуда Обрыв портит последнюю строку — парсер её отбрасывает. Зато между двумя файлами нет ни транзакции, ни порядка. Только переиндексацией Как производное — восстанавливается из источника целиком. Это часы работы и повторный счёт за эмбеддинги.
Удобство отладки Нужен клиент, зато SQL Вопрос «сколько ходов у воркера X за вторник» — одна строка. Глазами в файл не заглянешь, diff нечитаем. Лучшая tail -f, jq, grep, обычный diff. Инцидент разбирается тем же, чем читается лог. Чёрный ящик «Почему не нашлось» проверяется только повторным прогоном эмбеддинга. Числа в индексе ничего не говорят человеку.

Выбор за два вопроса

Дерево устроено так, что вектор-стор никогда не оказывается листом в одиночку. Причина — в разборе ниже.

Что именно ломается

По варианту: где выигрывает, обо что спотыкается на практике, какой порядок величин закладывать.

SQLite

Запись идёт в WAL, коммит стоит одного fsync. Пачка сообщений в одной транзакции амортизирует его до нуля на сообщение.

  • Выигрывает: вопросы вида «все ходы воркера за неделю дороже N» — один запрос вместо скрипта.
  • Спотыкается: писатель на базу ровно один. Десять агентов, пишущих одновременно, сериализуются, и при коротком таймауте вы получите database is locked вместо ожидания.
  • Спотыкается: соблазн выключить synchronous ради скорости. Это ровно та ручка, которая делает крэш-консистентность необязательной.
  • Порядок: запись — доли миллисекунды на строку в пачке; выборка по индексу — микросекунды; размер ≈ размеру текста плюс индексы.

JSONL

Дозапись в конец файла, открытого в режиме append. Ни схемы, ни миграций, ни блокировок между сессиями — файлы независимы.

  • Выигрывает: разбор инцидента. Читаете тем же, чем читаете логи, и видите ровно то, что видел агент.
  • Спотыкается: «покажи все сессии, где встречалось X» — это полный скан. На гигабайте архива вопрос перестаёт быть интерактивным.
  • Спотыкается: нет транзакции между файлами. Обновили сообщение в одном и счётчик в другом — падение между записями оставит расхождение, и починить его сможет только отдельный скрипт.
  • Порядок: запись — единицы микросекунд без fsync; поиск — линейно по объёму архива.

Вектор-стор

Текст режется на чанки, каждый превращается в вектор, индекс отвечает на «ближайшие к запросу» приблизительно — точный ответ здесь стоил бы полного перебора.

  • Выигрывает: ровно один запрос — «мы это уже решали?». Ни SQL, ни grep на него не отвечают.
  • Спотыкается: как источник правды он не годится. Порядок сообщений, точные значения, повтор одного и того же ответа — всё это теряется на чанковании, а вернуть исходник можно только из того, что вы сохранили отдельно.
  • Спотыкается: смена модели эмбеддингов обесценивает индекс целиком — старые и новые векторы несравнимы. Это переиндексация всего архива, оплаченная заново.
  • Порядок: запись — десятки-сотни миллисекунд на пачку (эмбеддинг + сеть); один вектор на 1536 измерений — около 6 КБ, и он лежит в оперативной памяти, а не на диске.

Как решить

Один агент, история нужна для чтения глазами — JSONL. Не усложняйте: файл на сессию закрывает всё, пока архив измеряется сотнями мегабайт, а отладка стоит одной команды.

Несколько агентов, нужны счётчики и фильтры — SQLite. Момент перехода узнаётся по симптому: вы начали писать скрипты, которые читают все JSONL, чтобы что-то посчитать.

Нужен смысловой поиск — вектор-стор, но исключительно как производный индекс поверх первых двух. Источник правды остаётся локальным и переживает и потерю индекса, и смену модели эмбеддингов. Обратная схема — «вектор вместо базы» — ломается на первом же вопросе, требующем точного ответа, и чинится только тем, что вы в неё не заложили.

Числа в тексте — порядки величины для локального NVMe и типового API эмбеддингов, а не измерения на вашей нагрузке. Если выбор между вариантами упирается в них — меряйте на своих объёмах: разрыв между JSONL и SQLite по записи почти всегда меньше, чем разница в том, как вы будете это читать.
