# V-910: находит ли агент запись в KB/отчётах при перефразированном вопросе, и даёт ли гибридный поиск выигрыш

Основа: V-898 §3, §6. Протокол, эталон и прогноз зафиксированы коммитами до запусков (`protocol.md`, `questions.py`, `reference.json`, `prediction.md`, `corpus_manifest.sha256`). Сырьё: `raw_a/` (160 прогонов A), `b_results.json`, `grades_s.json`, `analysis.txt`, скрипты рядом.

## Вердикт
**Порог не достигнут, слой не нужен.** На 28 перефразах B (bge-m3 + FTS5 + RRF, top-5) попадает в 60,7 %, сегодняшний путь A (агент с индексом тем и `rg`, ≤3 поисковых вызова) — в 81,2 %. B − A = **−20,5 п.п.** (95 % ДИ [−41,1; 0,0], односторонний sign-flip p = 0,97 для гипотезы «B лучше»). Требовалось ≥ +20 п.п. при p < 0,05. Прогноз заранее был «+10…+20, порог ~35 %» — результат хуже прогноза: я недооценил A.

## Что мерили
Корпус: снимок 789df54d, `.orchestra/kb/*.md` (10) + `.orchestra/tasks/*/report.md` (303), 5,3 МБ, 4179 чанков. 40 вопросов: 28 перефразов (P), 7 прямых (D), 5 про заменённые выводы (S). Цели взяты seed-случайно по разделам (`sample.py`), обобщённые разделы пропускались по порядку выборки. Отступление от «30, половина перефразы»: P поднят до 28 ради мощности (для +20 п.п. мощность ≈ 0,9). Допустимое множество файлов на вопрос = все файлы корпуса, где есть строка `gold` (README исключён); попадание — на уровне файла. Лексический контроль перефразов (`check_q.py`, общие основы ≥5 букв с df ≤ 8): у P в среднем 0–1 общая основа.

A: Luna и Sonnet 5.5, по 2 повтора, подписка. Промпт: индекс тем (`kb_index_block`) + фраза из модуля knowledge про `rg` + вопрос + правило «≤3 поисковых вызова (rg/grep/Grep/Glob/ls/find), чтение найденного файла бесплатно». hit_strict = названный файл в допустимом множестве И поисковых вызовов ≤3. B: `rag.py` Кеши импортирован только на чтение в её venv, `RagMemory` на отдельной БД (`/home/kesha/bench910/b/`), индексация вне cgroup платформы, hit = допустимый файл среди 5 лучших чанков.

## Почему B проиграл (интерпретация, не замер)
1. Метрика top-5 **чанков**, а не файлов: несколько чанков одного большого файла вытесняют остальные; top-10 даёт 0,786 ≈ A. Это штатное поведение `rag.search` (chunk-level), мы его не меняли.
2. Нейтральный по номерам вопрос про «отчёт задачи» чанки не знают, из какого файла они: чанк не несёт пути или номера задачи, а у A есть индекс тем и прямой `rg` по числам и идентификаторам.
3. FTS5 с prefix-OR по всем словам вопроса (`_expand_query`) на русской морфологии даёт шум; vec-only (0,714) лучше hybrid (0,607) — RRF с шумным FTS-списком тянет вниз.
4. A — агент с несколькими попытками и чтением; B — один запрос без переформулировки.

## Ограничения
- B измерен как чистый поиск, не как инструмент в руках агента (с переформулировкой и чтением). Выигрыш такого сочетания не измерен; но порог задан для B как поиска, и он не пройден с запасом.
- Файловый уровень попадания, допустимое множество строится по строке `gold` — могла пропустить законные файлы с тем же фактом другими словами (занижает оба плеча одинаково).
- Один автор вопросов (я); цели выбраны seed-случайно, но формулировки мои. Лексический контроль только по основам.
- Luna работала с `danger-full-access` и `network=True` (в `read-only` песочнице bwrap ломает любую команду: `loopback: Failed RTM_NEWADDR` — в KB есть), сети в промпте запрещены; web_search не встречался, подозрительных путей вне каталога не найдено (флаги загрязнения пусты на 160 прогонах). Sonnet имел только Read/Glob/Grep. Шесть прогонов Sonnet упали из-за инфраструктуры (`no stdin data received`) и перезапущены; три прогона-пилота исключены (`raw_a_pilot/`).
- Корпус на момент замера: 313 файлов; 303 отчёта — часть задач держит факты только в `research.md`/`plan.md`, их в корпус не включали.
- Мощность: ловили бы +20 п.п.; разницы порядка ±10 п.п. не различаем. Здесь знак обратный и существенный.

## Рекомендация
Индекс «как инструмент поиска для агентов» не предлагать. Если когда-нибудь вернуться: сначала проверить дешёвые улучшения B, не требующие слоя поверх `rg` (путь файла в тексте чанка, дедупликация по файлу, vec-only), и измерить агентный сценарий; для A слабое место — отчёты задач без индекса (P/reports 0,735), там помогла бы строка-описание в самих отчётах или общий указатель, а не вектор.
