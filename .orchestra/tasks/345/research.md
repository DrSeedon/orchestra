## Часть 1. Сам скилл/хук

### 1.1 Что это физически

Полное содержимое репозитория (`git log --all --diff-filter=A --name-only`, 3 коммита,
создан 2026-08-17, MIT, 25 звёзд, 1 форк):

```
README.md  RULESET.md  injected-instruction.md  EXPECTED-RESULTS.md
SHA256SUMS.txt  LICENSE  .github/CODEOWNERS
hooks/sessionstart.sh  assets/{benji.png,savings.svg,tokens.svg}
```

`sha256sum -c SHA256SUMS.txt` → 8/8 OK. Никакого кода, кроме однострочного `cat`.

**На какой хук садится.** Claude Code `SessionStart`, matcher `startup|resume|clear|compact`.
Комментарий в самом хуке называет причину матчера дословно: *«re-injects after /clear and
compaction — the two events that silently wipe injected context»*. Хук ничего не вычисляет —
он печатает статический текст в контекст сессии.

**Цена.** `injected-instruction.md` = 2 996 байт, заявлено ~745 токенов. `RULESET.md` (3 487 Б) —
тот же текст плюс YAML-фронтматтер для формата скилл-папки.

**Что делает в момент срабатывания.** Пять правил (дословно из `injected-instruction.md`):

1. **Recon in one pass** — собрать все независимые факты одним шагом: цепочка проб через `;` с
   размеченными секциями (`echo == layout ==; ls -la; echo == deps ==; head -30 requirements.txt`)
   либо несколько tool-вызовов в одном сообщении. Копируешь конвенцию — смотри ДВА примера, не один.
2. **Look through a keyhole** — инспектирующая команда заканчивается ограничителем (`| head -50`,
   `grep -m 20`, `wc -l` перед содержимым, Read с offset/limit). Явная оговорка: правило
   действует на ИНСПЕКЦИЮ и никогда на ingestion — «truncating data you will transform corrupts output».
3. **Probe the environment once** — все зависимости одной пробой, доустановка одной командой.
4. **Green means the task's own check** — если задача называет команду проверки, она и есть
   определение готовности; «падение по среде — тоже твоё падение»; та же проверка упала дважды →
   подход неверен, назови альтернативу. Прошло — остановись, «no victory laps».
5. **Polling is a step** — ждать слайсами ≥30 с; никаких пере-опросов раз в секунду и пустого ввода
   ради подглядывания. Где исполнение блокирующее — правило бесплатно.

Плюс общий хвост: не строить проверочный харнесс, которого задача не просила; «efficiency never
outranks correctness».

Ключевая формулировка механизма — первый абзац: *«Every request you send re-reads the whole
conversation so far. The bill is steps × context, not words.»* Это заявка на то, что экономия
берётся из СОКРАЩЕНИЯ ШАГОВ, а не из краткости формулировок.

### 1.2 На чём стоят 22% — и что из этого проверяемо

Заявленное число из README: **«up to −18% cost and −22% tokens per task, quality unchanged»**.
Уточнение: 22% — это **total tokens (−21.9%)**, а не деньги; деньги — 17.9%. Юзер процитировал
«до 22% токенов» — формулировка автора корректна, слово «up to» стоит в оригинале.

Головной замер (`EXPECTED-RESULTS.md`, job `bp6-final`, 2026-08-16):

| метрика | медиана paired | p | totals |
|---|--:|--:|--:|
| cost | −17.9% | 0.005 | −16.7% |
| turns | −20.0% | 0.001 | −18.9% |
| total tokens | −21.9% | 0.001 | −25.0% |
| cache reads | −23.9% | 0.001 | −25.9% |
| output tokens | −21.2% | 0.007 | −14.3% |
| code written | −13.3% | 0.006 | −19.2% |
| wall-clock | −15.6% | 0.018 | −8.3% |
| fresh input | −7.8% | **0.125** | −3.0% |
| quality | 7↑/5↓/68 tie | sign 0.77 | mean 0.362→0.392 |

**Стенд:** 80 парных задач SkillsBench, Claude Code 2.1.201 (пиннут в обеих ветках), Sonnet 5,
effort low, Docker-песочницы. Статистика — Wilcoxon по парным дельтам, знаковый тест по наградам.

**Что в этом сделано хорошо** (проверено чтением `EXPECTED-RESULTS.md`, не README):

- **Парный дизайн, одна и та же задача в обеих ветках.** Единственное различие — инжектируемый текст.
- **Механическая проверка, что лечение вообще доехало:** payload дошёл до модели в **80 из 80**
  прогонов лечения и **0 из 80** контрольных (`trajectory.json`). Это ровно та проверка, отсутствие
  которой у нас записано в граблях как «проверял артефакт, а не рассказ».
- **Симметричные исключения:** 2 заведомо сломанные задачи (seismic/earthquake) упали одинаково в
  обеих ветках и выброшены симметрично; 4 односторонних RuntimeError (3 контроль, 1 лечение)
  переигрывались по заранее объявленному house rule.
- **Медиаторы адопции опубликованы:** размеченные цепочки проб 10 → 102 команд, батченные пробы
  зависимостей 7/80 → 22/80 trials, Read с offset/limit 20% → 28%, **всего Read-вызовов 144 → 57**.
  То есть автор показал не только исход, но и что поведение реально изменилось в предсказанную сторону.
- **Автор сам публикует неудобное.** Раздел «Honesty note on effect size»: предыдущая версия v5 в
  тот же день дала **−10.0% cost при p=0.169, то есть НЕЗНАЧИМО**; между днями контрольная ветка
  уехала на +10.5%, а ветка лечения осталась плоской. Прямая формулировка: «its measured saving
  scales with how expensive the baseline happens to run». И у v5 totals по стоимости были **+0.6%**
  при медиане −10.0% — расхождение медианы и суммы автор объясняет хвостом трудных задач.
- **Раскрыты срезанные углы:** «bp2/bp4/bp5 smokes ran the treatment arm only against bp1's control —
  fine for gating, not quotable».
- **Заявка о качестве ограничена самим автором:** «not powered as an equivalence test — large
  effects ruled out, small ones not».

**Где число хрупкое:**

1. **Все скрипты замера и сырые прогоны НЕ ОПУБЛИКОВАНЫ.** `EXPECTED-RESULTS.md` ссылается на
   11 артефактов; проверено — в репозитории нет ни одного, и ни одного не было ни в одном коммите:
   `gen_instruction.py`, `compare.py`, `adoption.py`, `mediators.py`, `run_ab.sh`, `run_full.sh`,
   `LAB-NOTES.md`, `winning-strats.md`, `dist/benjamin-plus/SHA256SUMS.txt`,
   `skill/benjamin-plus/SKILL.md`, `runs/`. Раздел «Reproducing» перечисляет команды, которые
   выполнить нечем. **Перепроверить 22% по опубликованному невозможно** — доступна только сводка
   чисел, написанная автором.
2. **k=1 на задачу в головном прогоне.** Автор это раскрывает и опирается на 66-68/80 ничьих и на
   отдельную стадию k3x10. Но шум самой метрики (split-half по до-периоду) не измерен и не показан —
   у нас это отдельное правило в `CLAUDE.md`, здесь его эквивалента нет.
3. **Эффект и дрейф базы одного порядка.** Разница между v5 (−10.0%, p=0.169) и v6 (−17.9%, p=0.005)
   объясняется в том числе дрейфом КОНТРОЛЯ на +10.5% между днями. То есть величина суточного дрейфа
   сопоставима с величиной эффекта. Парность внутри дня это гасит, но диапазон «−10% … −18%»
   означает, что одно число называть нельзя, и автор его и не называет одним.
4. **Заявка о качестве — не доказательство эквивалентности.** 68 ничьих из 80 при k=1 означают, что
   верификатор на большинстве задач не различает ветки вовсе; sign p=0.77 отвергнуть деградацию не может.
   Это ровно граница, которую автор проговаривает сам.
5. **`fresh input` −7.8% при p=0.125 — единственная незначимая строка в таблице**, и это
   содержательно: экономия идёт не из новых входных данных, а из cache reads (−23.9%) и turns (−20.0%).

**Самая важная цифра для нас — не 22%, а перенос.** Автор отдельно приводит внешний замер на
другом бенчмарке и другом рантайме: **Java SWE-bench, Codex CLI, gpt-5.6-luna, 675 парных реплик →
cost −4.4% [−7.5, −1.5], p=0.003; solve rate без изменений (p=0.22); tool calls −20%.**
Эффект по деньгам **сжался вчетверо** относительно домашнего бенчмарка, при том что сокращение
tool-вызовов сохранилось (−20%). Это и есть честная внешняя валидность.

### 1.3 Отдельная находка: способ доставки решает больше, чем текст

Замер автора, названный им decisive: на Java SWE-bench (Codex CLI, 225 инстансов × 3 реплики)
**инжектированный** benjamin — единственная ветка со значимой экономией (−4.4%, p=0.003), а тот же
самый текст, положенный **скилл-папкой**, не сэкономил ничего (**−0.5%, n.s.**), потому что
доставание `SKILL.md` стоило медианно 3 шага при **73% промахов по пути**.

Вывод автора: «The distribution is now hooks/injection ONLY». Это утверждение не про benjamin, а
про механику скиллов вообще: дискаверабельный скилл платит за себя поиском.

## Часть 2. Метод авторесёрча

### 2.1 Из чего он состоит у автора

Описание в README дословно: *«Mine ~1,200 old agent traces for where the money actually goes, draft
rules, run a paired A/B, read the failing trajectories, revise, run again. Six versions later, only
the rules that survived the evidence were left.»*

Развёрнутый след цикла — таблица «The ladder — five versions in one day» в `EXPECTED-RESULTS.md`:

| стадия | версия | результат | урок |
|---|---|---|---|
| smoke10 k=1 | v1 (713 tok) | cost −11.7%, reward 0/4/6 — провал | диагностика трасс 4 агентами: 2 падения — дисперсия, 2 вызваны скиллом через недоопределённый «check» |
| smoke10 k=1 | v2 (+строгость check) | syzkaller починен; out_tok **+52%** | конструирование проверок = кит по выходным токенам |
| k3x10 (60 trials) | v3 (+check-to-file) | totals +7.4% против медиан −8.9% | экономия при k=1 была миражом; гарды под задачу X вредят задаче Y |
| smoke10 k=1 | v4 (cap harness) | киты выжили | у «супа из правил» нет нетто-положительной конфигурации |
| smoke10 k=1 | **v5 = LEAN** (632 tok) | cost −13%, reward паритет | оставлены только правила с чистым доказательством |
| 82 задачи | v5 → v6 | головной замер | — |

Главный вывод автора о самом методе, дословно: **«quality guards are not free»** — каждый гард,
добавленный ради одного класса падений, порождал «verification whales», съедавшие экономию в
другом месте. **«The winning configuration deleted more rules than it added.»**

Стоимость программы автор публикует: bp1 $14.94 · bp2 ~$8.6 · bp3 $49.04 · bp4 $9.08 · bp5 $6.83 ·
bp-final $64.40 ≈ **$153 за 254 оплаченных прогона**, шесть версий за примерно сутки.

### 2.2 Что нужно, чтобы поднять такой контур у нас

Проверено обращением к первоисточникам, не по памяти:

| компонент | статус | доказательство |
|---|---|---|
| **Harbor** — харнесс прогона агентов в контейнерах | публичный, Apache-2.0, живой | GitHub API: `harbor-framework/harbor`, 4 396 звёзд, `pushed_at=2026-08-19`, не архивирован |
| поддержка НАШИХ рантаймов | есть | `/tmp/harbor/src/harbor/agents/installed/claude_code.py:107` — параметр `append_system_prompt`, CLI-флаг `--append-system-prompt` |
| **SkillsBench** — набор задач с детерминированными верификаторами | публичный, Apache-2.0 | GitHub API: `benchflow-ai/skillsbench`, 1 692 звезды; статья arXiv 2602.12670 |
| скрипты статистики (`compare.py`, `mediators.py`, `adoption.py`) | **отсутствуют** | см. §1.2 п.1; Wilcoxon по парным дельтам — вызов `scipy.stats.wilcoxon`, переписывается за час |
| «шахтёрство по 1 200 трассам» | **не воспроизводимо** | `winning-strats.md` не опубликован |
| драйвер цикла (агент, который читает результат и правит конфиг) | у нас **есть** заготовка | `bg_create(type="run")` + `send_message` + full-cycle роль |

То есть покупать или изобретать нечего: две несущие детали (харнесс и набор задач) — открытые
Apache-2.0 проекты, третья (статистика) тривиальна, четвёртая (агент в цикле) у нас уже работает
в другом виде. **Отсутствует у нас именно то, чего у автора и не опубликовано: дисциплина
предрегистрации и парного прогона, зашитая в скрипт, а не в голову исполнителя.**

### 2.3 Чего в его цикле НЕТ — и что мы обязаны добавить

Метод автора решает задачу «подобрать текст правила под метрику». Три вещи, которые у нас в
`CLAUDE.md` записаны замерами, а у него не видны:

1. **Собственный шум метрики.** У нас правило: намерил улучшение на фиксированной выборке →
   померь split-half по ДО-периоду (#135: лучший арм +0.031 при медианном шуме 0.105). У автора
   роль шума играет парность и повтор в другой день — слабее.
2. **Далёкая предметная область.** У нас: прогони 1-2 задания из ДАЛЁКОЙ области, прежде чем
   объявлять эффект (#119). У автора весь тюнинг шёл на SkillsBench, и ровно на переносе эффект
   и сжался вчетверо — то есть наш собственный урок здесь подтвердился на чужих данных.
3. **Замороженный оракул.** Цикл, где агент правит конфиг и перезапускает евал, — это ровно тот
   контур, в котором у нас записан #223: правка оракула после RED делает невозможным любой реплей.
   У автора между версиями менялся ТЕКСТ ПРАВИЛА (предмет замера), а не верификатор — это законно;
   но автоматизируя цикл у себя, мы обязаны запретить агенту трогать верификатор, иначе он
   оптимизирует проверку, а не поведение.

## Часть 3. Применимость к Orchestra

### 3.1 Предпосылка benjamin проверена на НАШИХ данных — и подтвердилась

Заявка benjamin: «The bill is steps × context, not words». Проверил на живой БД (read-only,
`file:...?mode=ro`), 14 дней, `turn_usage`:

```
claude   turns=2220  cost=$4285.18  tokens=6468.6M  cache_read=97.4%  output=0.32%  cost/turn=$1.930
codex    turns=2121  cost=$3848.30  tokens=11518.7M cache_read=49.1%  output=0.18%  cost/turn=$1.814
tool calls=61027  turns=4341  →  14.06 tool-вызовов на ход
```

Доли `cache_read` по рантаймам НЕ сравниваются между собой: у Anthropic cached не входит в
`input_tokens`, у OpenAI входит (#175) — знаменатели разные.

Декомпозиция расхода Claude по классам токенов, прайс-лист `TOKEN_PRICES` (`app/models.py`,
единственный владелец), множители Anthropic cache_read=0.1×input, cache_create=1.25×input:

| класс | $ за 14 дней | доля |
|---|--:|--:|
| **cache_read** | 3 149 | **68.6%** |
| cache_create | 911 | 19.9% |
| output | 510 | 11.1% |
| fresh input | 19 | 0.4% |

Реконструкция даёт $4 590 против записанных SDK $4 285 — расхождение 7%, поэтому **абсолютные
доллары считать приблизительными**; доли устойчивы, так как множители сдвигают только вес внутри
классов. Независимое подтверждение: цифра 68% уже стояла в `CLAUDE.md` из #178, полученная другим
способом и на другом периоде; сейчас на свежих 14 днях вышло 68.6%.

**Что это значит.** 88.5% нашего расхода на Claude (cache_read + cache_create) — это плата за
ПЕРЕДАЧУ КОНТЕКСТА, а не за новые рассуждения. Output — 11.1%. Отсюда прямое следствие, объясняющее
всю серию замеров JetBrains: скиллы вроде caveman, которые сжимают ФОРМУЛИРОВКИ, бьют по 11%-й доле
и потому дают −8.5%; benjamin бьёт по 69%-й доле через сокращение числа шагов и потому даёт −18%.
При 14.06 tool-вызовах на ход у нас есть на что действовать.

### 3.2 Садится ли на наш контур как есть

**Хук — нет. Текст — да, и вставлять его надо в другое место.**

- Наши Claude-воркеры поднимаются через **`claude-agent-sdk`** (`app/backend_claude.py:1`:
  «wraps claude-agent-sdk for persistent agent sessions», `ClaudeSDKClient` на 869-945), а не через
  Claude Code CLI, читающий `~/.claude/settings.json`. Инструкция установки из README
  (`"hooks": {"SessionStart": ...}` в settings.json) **к нашим воркерам неприменима вовсе**.
- Хуки у нас уже используются программно и другим типом: `HookMatcher(matcher="Bash", ...)`,
  `PreToolUse` (`app/backend_claude.py:368-419`). `SessionStart` в коде не встречается.
- IDE-рантайм JetBrains **не нужен**: см. опровержение H4 — исполняемого кода в репозитории 459 байт `cat`.
- Наш законный маршрут доставки описан в самом README последним пунктом: *«Any other agent — append
  `injected-instruction.md` to the system prompt»*. У нас это модуль в
  `pipelines/default/prompts/modules/` + строка в `modules:` роли, то есть **правка одного файла и
  одной строки манифеста**, без хуков и без рестарта ради самого текста.
- Побочная выгода: проблема, ради которой автору нужен матчер `clear|compact`, у нас закрыта
  архитектурно — системный промпт перечитывается с диска при re-injection на resume/compact (#137,
  зафиксировано в `docs/kb/prompt-delivery.md`).
- Цена payload при нашем профиле: 745 токенов × 2 220 ходов Claude = 1.65M токенов cache_read
  ≈ **$0.83 за 14 дней**. Пренебрежимо.

### 3.3 Что из пяти правил у нас УЖЕ есть — построчно

Проверено сборкой промпта, а не грепом по файлам:
`build_system_prompt(DEFAULT_PIPELINE, role)` интерпретатором главного чекаута (метод из
`docs/kb/prompt-delivery.md`). Контекст каждого совпадения открывался — совпадения по ключевым
словам оказались обманчивыми в двух случаях из пяти.

| правило benjamin | у нас | доказательство |
|---|---|---|
| **1. Recon in one pass** | **НЕТ** | все 3 вхождения `parallel` в full-cycle — про параллельных ВОРКЕРОВ и git-каталоги; `one message` — про отчёт воркера. Батчинг tool-вызовов приходит только из встроенного промпта харнесса Claude Code («Independent tool calls can run in parallel in one response»), у нас своего правила нет. Правила «два примера перед копированием конвенции» нет вовсе |
| **2. Keyhole** | **ЧАСТИЧНО** | есть половина про Read: `base.md:53` «grep/search BEFORE full Read — … Read with offset+limit». Половины про шелл-ограничители нет: `head -` в собранном промпте full-cycle **0 вхождений** |
| **3. Probe env once** | **НЕТ** | все вхождения `dependenc` — про `blocked-by` цепочки тикетов; единственное `one probe` — из #237 про прод-подобный рантайм, другая мысль |
| **4. Green = task's own check** | **ЕСТЬ, сильнее** | весь контракт RED-оракула в `full-cycle.md`: «the named test command stays red → escalate, never retry», immutable-оракул, AC |
| **5. Polling is a step** | **ЕСТЬ, сильнее** | `base.md:33` «Never sleep or poll … End the turn»; `worker.md:11,51`; `full-cycle.md:147». У нас не «ждать 30 с», а «закончить ход» — Orchestra будит агента событием |

Итого: **2 правила из 5 есть и в более сильной форме, 2 отсутствуют полностью, 1 наполовину.**
Причём отсутствуют ровно те два, что относятся к разведке в начале задачи, — а именно разведка и
даёт медиатор «Read calls 144 → 57» в замере автора.

### 3.4 Конфликты с нашими правилами

Один кандидат, при проверке — мнимый. `CLAUDE.md:242`: «Правишь правило, у которого есть
файл-владелец → перечитай этот файл ЦЕЛИКОМ глазами, а не грепом» (#184, паттерн поймал автора
трижды в одной задаче). Формально противоречит keyhole. Фактически правило 2 benjamin само содержит
изъятие: «Read a file whole only when you are about to edit it or copy from it verbatim» — правка
файла-владельца попадает в изъятие. **Риск не в тексте, а в применении**: агент, применивший
keyhole небрежно, поломает урок #184. Если внедрять — изъятие надо назвать нашими словами и с
нашей ссылкой, а не полагаться на английскую формулировку автора.

Второй, более серьёзный: правило 5 в редакции benjamin («жди слайсами по 30 с») **слабее нашего**
(«закончи ход, тебя разбудят») и для Codex прямо опасно — у нас записан замер, что Codex жжёт время
в `sleep` (74 сна на 1 579 вызовов) и что формулировку «просто подожди» он читает буквально.
Внедрять правило 5 дословно **нельзя** — оно откатит наше более сильное правило.
