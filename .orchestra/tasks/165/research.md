## Эксперимент — критерии заданы ДО прогона

Стенд: ЖИВОЙ локальный инстанс `127.0.0.1:8888` (рестарта НЕ было — на нём в этот момент
работали соседние воркеры). Скретч-скоуп `/mnt/data/tmp165/scope165` на ext4 (НЕ `/tmp`:
там tmpfs = RAM). Боевой Contabo не трогался — на нём только read-only проверки.

Критерии, зафиксированные заранее:

1. `POST /api/sessions` с `is_orchestrator=true` создаёт сессию на живом сервере И она живёт
   В ПАМЯТИ процесса, а не только в БД. **Доказательство различающее:** сессия отвечает на
   `send_message`. Ручной `INSERT` этот тест провалил бы — сервер о строке не знает.
2. Переданный `mcp_servers` сохраняется в `mcp_servers_custom`.
3. `docs/workers/<имя>.md`, положенный на диск ДО вызова, попадает в `system_prompt`.
4. Транскрипт: ни один эндпоинт не принимает чужой `session_id` → ожидаемый ПРОВАЛ.

`tg_topic` выставился в `true` сам: `manager.py` — «root orchestrators get a dedicated TG
topic». Запрашивать не пришлось.

**Различающая проверка живости** — `send_message(to="migrate-probe-165")` и через 45 с в

Агент реально запустился, отработал ход и получил СВОЙ свежий `session_id`. Рестарта не было.

**(2) `mcp_servers_custom` — ПАС.**

```sql
SELECT mcp_servers_custom, pipeline, role, is_orchestrator, tg_topic
  FROM sessions WHERE name='migrate-probe-165';
→ {"probe165": {"command": "/bin/true", "args": ["--probe-165"]}}|default|orchestrator|1|1
```

Колонки `mcp_servers` в таблице НЕТ вовсе — эффективный конфиг собирается в рантайме
(`_make_mcp_config`, `manager.py:648`). То есть «прописать MCP» = передать `mcp_servers` при
создании, ничего больше.

**(3) Личная память — ПАС.** Заранее положен файл с маркером:

```
/mnt/data/tmp165/scope165/docs/workers/migrate-probe-165.md
  → "MARKER-WORKERMEM-165: this line proves docs/workers travels as a plain file."
```

Проверка по ПОЛНОМУ prompt из БД (не по API-ответу — см. «Контр-свидетельства»):

```
system_prompt: 43596 байт
grep -c MARKER-WORKERMEM-165 → 1     ← память вшита
grep -c MARKER-CLAUDEMD-165  → 0     ← CLAUDE.md в prompt НЕ вшивается
```

`CLAUDE.md` ноль — и это не дыра: его читает сам CLI из каталога скоупа в рантайме. Ему
достаточно лежать на диске, что и обеспечивает `git clone`.

**(4) Worktree воркера — ПАС (не ожидал).**

```
POST /api/sessions {"name":"probe165-worker","use_worktree":true,
 "repo_path":"/mnt/data/tmp165/scope165","base_branch":"master",
 "parent_name":"migrate-probe-165"}
→ 201
  worktree_path=/mnt/data/Projects/Python/orchestra/worktrees/mnt-data-tmp165-scope165/probe165-worker
  branch=feat/mnt-data-tmp165-scope165/probe165-worker  base_branch=master
```

Платформа сама посчитала слаг от repo root и создала git worktree — ровно то, что скрипт
делает руками в `migrate_git` (:366) через `git bundle` + `worktree add`.

**(5) Транскрипт — ПРОВАЛ, как и ожидалось.** Мутирующих эндпоинтов сессии 17
(`grep '@router.post|put|patch' app/routes/sessions.py`); ни один не принимает чужой
`session_id`. Ближайший, `POST /api/sessions/{name}/rollback-session` (:493), выбирает
ТОЛЬКО из `session_id_history` уже существующей сессии:

```python
entry = session.session_id_history[index]   # :503
session.session_id = entry["session_id"]    # :508
```

У новой сессии история пуста (`{"current_session_id":null,"history":[]}` — замерено на пробе
до первого хода). Подсунуть `<session_id>.jsonl` с чужого хоста через API нельзя.

**Уборка.** Обе пробы удалены (`DELETE /api/sessions` → `{"ok":true}`), git worktree снят
платформой (`git worktree list` в скретче показывает только сам репозиторий), строки
`sessions`/`logs`/`inbox` вычищены (`SELECT count(*) WHERE name LIKE '%probe165%'` → 0),
скретч-каталог отправлен в корзину через `gio trash`. Живой сервис не рестартился.

## Ответ на главный вопрос — покрытие по пунктам

| Что переносит `migrate_agent.py` | Природа | Эквивалент без рестарта | Уверенность |
|---|---|---|---|
| строка `sessions` (~20 полей) | БД | `POST /api/sessions` — все поля выставляет сама платформа | **CONFIRMED** — замер (1) |
| `mcp_servers_custom` | БД | параметр `mcp_servers` того же вызова | **CONFIRMED** — замер (2) |
| `docs/workers/<имя>.md` (`copy_scope_files`, :470) | **файл** | положить в скоуп до вызова; едет с `git clone`, если закоммичен | **CONFIRMED** — замер (3) |
| `CLAUDE.md` скоупа (`copy_scope_files`, :470) | **файл** | едет с `git clone` | **CONFIRMED** — замер (3): в prompt не вшивается, читается с диска |
| worktree воркера (`migrate_git`, :549) | git + БД | `use_worktree=true` + `repo_path` — платформа создаёт worktree сама | **CONFIRMED** — замер (4) |
| ветка воркера с работой | git | обычный `git push` ветки; `create_worktree` (`workspace.py:522-535`) ПЕРЕИСПОЛЬЗУЕТ существующую ветку вместо создания | **LIKELY** — прочитан код ветвления, отдельным замером на непустой ветке не проверял |
| `logs` (`build_children_copy`, :449) | БД | **нет** — новая сессия начинает с пустым логом | **CONFIRMED** — эндпоинта нет |
| `inbox` | БД | **нет**; но непрочитанный инбокс на момент переезда = пустой (агент idle) | **CONFIRMED** — эндпоинта нет |
| `subagents` | БД | **нет** — статистика субагентов, не рабочее состояние | **CONFIRMED** — эндпоинта нет |
| транскрипт `<session_id>.jsonl` (`copy_transcript`, :308) | файл + БД | **нет** — цена API-пути | **CONFIRMED** — замер (5) |

**Вывод: без рестарта переезжает ВСЁ, кроме истории диалога** (транскрипт + логи + inbox +
subagents — все четыре суть «прошлое», а не «рецепт»). Всё, что определяет, КАК агент
работает — промпт, роль, модель, MCP, личная память, `CLAUDE.md`, worktree воркеров, —
воспроизводится на живом сервере одним HTTP-вызовом плюс `git clone`.

Ровно это и есть та цена, которую скилл уже назвал верно и своими словами:

> «Историю диалога везти не надо и вредно — переезжает рецепт (промпт, роль, файлы), а не
> транскрипт.»

То есть API-путь не отнимает ничего, что скилл считал нужным везти. Он отнимает ровно то,
что скилл называл ВРЕДНЫМ, и взамен снимает рестарт.

## Нужны ли два пути? — НЕТ, но развилка одна

Единственный сценарий, где скрипт даёт то, чего API не даёт: **надо, чтобы агент проснулся
С ПАМЯТЬЮ ДИАЛОГА**. Это не переезд проекта, а клонирование конкретной живой сессии
(например, «дожать на сервере ровно тот разбор, что шёл на ноуте»). Для штатного переезда
проекта это анти-цель: скилл сам предупреждает «не строй планов на „он забудет“».

Поэтому в скилле — не два равных пути, а один основной (API) и одна явная сноска про
скрипт с честным критерием: нужен транскрипт → скрипт → тогда и только тогда рестарт, и
не своей рукой.

## Дополнительно проверено на VPS (read-only, боевые агенты не тронуты)

Чтобы API-путь не оказался локальной привилегией:

```
ssh root@158.220.127.161:
  app/routes/sessions.py:172 → @router.post("/api/sessions", status_code=201)   # тот же код, та же строка
  grep -c mcp_servers app/routes/sessions.py → 2                                 # параметр принимается
  systemctl show orchestra -p User -p LoadState → User=kesha / LoadState=loaded
  /proc/<MainPID>/environ → USER=kesha HOME=/home/kesha
  ALLOWED_ROOTS в .env → не задан
  ls -d /home/kesha/projects → существует
```

`_is_safe_path` (`app/routes/system.py:179`) пускает `cwd` только внутрь
`_get_allowed_roots()`, куда входит `str(Path.home())` — **home процесса Orchestra**, а не
того, кто вызывает. На VPS это `/home/kesha` → путь `/home/kesha/projects/<name>`
разрешён. Проверено по `/proc/<pid>/environ`, а не по логину ssh (мы заходим как root, и
`~` у нас указывало бы на `/root` — та же ловушка, что описана в `copy_transcript`).

Запрещённые части пути (`_DENIED_PARTS`, `_DENIED_HOME_PARTS`: `.env`, `.git`, `.ssh`,
`.claude`, `.config` …) в `/home/kesha/projects/<name>` не встречаются.

Дашборд VPS доступен по HTTPS с кукой (`POST /login` → 302, замерено), то есть вызов
`POST /api/sessions` выполним и удалённо — прямо из скилла `vps-orchestra`.

## Контр-свидетельства и то, что чуть не увело в ложный вывод

1. **API-ответ обрезает `system_prompt` до 500 символов.** Первая проверка маркера памяти по
   ответу `GET /api/sessions/{name}` дала `False` — и это выглядело как «память не
   подхватилась». Ложь: `to_dict()` режет поле. Проверка по ответу API давала бы ОДИНАКОВЫЙ
   `False` и когда память есть, и когда её нет — то есть не была проверкой (правило проекта).
   Ground truth — полное поле из БД: 43 596 байт, маркер найден.
2. **`mcp_servers` в ответе нет, потому что колонки нет.** Первый `SELECT ... mcp_servers`
   упал с `no such column`. Это не дыра в API, а архитектура: эффективный конфиг собирается
   в рантайме из `mcp_servers_custom`. Вывод «MCP не переносится» был бы артефактом
   неправильного запроса.
3. **Ветка воркера — самое слабое место таблицы.** `create_worktree` переиспользует
   существующую ветку (`workspace.py:522-535`), но имя ветки платформа считает САМА:
   `task-<par>/<name>` при `task_id`, иначе `feat/<repo-slug>/<name>`. Совпадёт имя воркера
   и `task_id` — совпадёт и ветка; не совпадёт — платформа заведёт новую от `base_branch`, и
   коммиты воркера останутся в стороне, ВЫГЛЯДЯ при этом здоровым worktree. Помечено
   LIKELY, а не CONFIRMED: замер делался на свежей ветке. Практический вывод для скилла —
   не полагаться на это, а мержить работу воркеров ДО переезда.
4. **Правило «ручной INSERT нельзя» остаётся верным и API его не нарушает.** Опасение из
   задания («проверь, что API не имеет той же болезни») снято замером (1): сессия ответила
   на сообщение, значит она в `manager.sessions`, а не только в файле БД. Болезнь ручного
   INSERT ровно в том, что живой процесс о строке не знает и затирает её из памяти;
   `create_session` идёт ЧЕРЕЗ процесс, поэтому затирать нечего.
5. **Скрипт делает одну вещь, которой у API нет и которая не в списке задания:** гейт
   `assert_idle` (:302) — отказ мигрировать, пока кто-то `running`. При API-пути этот гейт
   исчезает вместе со скриптом. Компенсируется тем, что API создаёт НОВУЮ сессию и ничего не
   перезаписывает: гасить исходную — отдельный осознанный шаг, он и так был в скилле.

## Риски и краевые случаи

- **Скилл не должен звать API вслепую по HTTP-примеру.** Локально агент вызывает
  `mcp__orchestra__spawn_worker`; на VPS — `curl` с кукой из `vps-orchestra`. Один
  результат, два транспорта — в скилле нужен явный выбор транспорта, иначе агент попробует
  локальный MCP против удалённого инстанса (грабля «локальный MCP их не видит»).
- **`is_orchestrator=true` + пустой `parent_name`** → платформа сама включает `tg_topic`.
  Это желаемое поведение (юзер пишет оркестратору из TG), но означает НОВЫЙ топик в группе —
  стоит упомянуть, чтобы не выглядело сбоем.
- **Имя.** Логика скилла (переезд → то же имя, дубль → `<имя>-vps`) остаётся в силе и
  становится ВАЖНЕЕ: память подхватывается по имени файла `docs/workers/<имя>.md` в момент
  создания. Ошибся именем — память молча не подхватится, а сессия будет выглядеть здоровой.
- **`git clone` должен пройти ДО вызова API:** `cwd` валидируется на существование каталога
  (`sessions.py:143` + `manager.py:518`). Пустого каталога мало для памяти — нужен
  закоммиченный `docs/workers/<имя>.md`, иначе его надо положить руками.
- **Порядок для воркеров:** сперва оркестратор (он `parent_name` для остальных), потом
  воркеры. При обратном порядке `_find_orchestrator_name` не найдёт родителя.
