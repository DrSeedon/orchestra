# #473 — владение воркеров переживает переезд раскладки `docs/` → `.orchestra/`

## Установленный факт, ради которого задача существует

**Владение воркера хранится в ДВУХ местах, и починка одного не чинит ничего.**

- колонка `sessions.owned_dirs` — JSON-список, читается при загрузке сессии
  (`app/manager.py:_load_from_db` → `parse_owned_dirs`);
- блок `## Directory ownership` внутри сохранённого промпта — `sessions.prompt_overlay`
  и `sessions.system_prompt` (`app/manager.py:_ownership_prompt`).

Что именно видит агент, решает `assemble_prompt` (`app/manager.py`): при
`stored_overlay is not None` промпт собирается как `base + prompt_overlay`, и колонка
`owned_dirs` в этой ветке НЕ читается вовсе.

**Доказательство, а не чтение кода.** Скармливаем `assemble_prompt` РАЗНЫЕ `owned_dirs`
при одном и том же сохранённом overlay и сравниваем результат:

```bash
ORCHESTRA_DB_PATH=/tmp/probe473.db .venv/bin/python - <<'EOF'
from app.manager import SessionManager
m = SessionManager()
overlay = "\n\nTASK" + SessionManager._ownership_prompt(["docs/tasks/88"])
a, _ = m.assemble_prompt(pipeline="default", role="worker", scope="/tmp", is_orch=False,
                         name="w", owned_dirs=["docs/tasks/88"], branch="b",
                         stored_overlay=overlay, old_prompt="")
b, _ = m.assemble_prompt(pipeline="default", role="worker", scope="/tmp", is_orch=False,
                         name="w", owned_dirs=[".orchestra/tasks/88"], branch="b",
                         stored_overlay=overlay, old_prompt="")
print("identical prompts despite different owned_dirs:", a == b)
print("prompt still points at the OLD path:", "- docs/tasks/88/" in a)
print("prompt never mentions the NEW path:", ".orchestra/tasks/88" not in a)
EOF
```

Вывод:

```
identical prompts despite different owned_dirs: True
prompt still points at the OLD path: True
prompt never mentions the NEW path: True
```

То есть исправленная колонка на промпт не влияет НИКАК: агент продолжает читать старый
путь. Это и есть главная ловушка задачи — починка одной колонки выглядела бы успешной
(`select owned_dirs` показывает новый путь) и не чинила бы ничего.

Второе плечо — что эта ветка действительно та, по которой пойдут все 13 строк:

```bash
sqlite3 -readonly data/orchestra.db \
  "select count(*), sum(prompt_overlay is not null) from sessions
   where owned_dirs like '%docs/%' and status in ('idle','running','waiting')"
```

→ `live rows with legacy ownership: 13; of them prompt_overlay NOT NULL: 13`. Ни одной
строки с NULL-overlay нет, то есть ветка «читаем `owned_dirs`» не сработает ни у кого.

## Применять руками не нужно — починит рестарт

`migrate_registered_project_layouts()` вызывается в `app/main.py:393`, то есть ДО
`auto_resume_all()`. Раскладка у всех пяти проектов уже `current`, поэтому
`migrate_project_layout` уходит в ветку `already_current` — и она теперь тоже зовёт
`migrate_session_ownership`. Значит первый же штатный рестарт чинит все 12 строк до
того, как сессии загрузятся в память. Команда `--repair-ownership` остаётся ручным
аварийным входом (и для проектов, до которых миграция не доехала).

Применять на живом сервере СЕЙЧАС нельзя: менеджер держит сессии в памяти и
перезаписывает строку из неё (тот же механизм, что переписывает `sessions.model`
при `auto_resume`), — прямой UPDATE был бы молча откачен.

## Найденный в собственном коде дефект: отказ починки роняет СТАРТ платформы

Найден при самопроверке по вопросу оркестратора «что при частичном отказе на середине
списка проектов». Ответ оказался хуже, чем частичный отказ.

`migrate_registered_projects` изолирует только `LayoutMigrationError`
(`except LayoutMigrationError as exc`). Вызовы `migrate_session_ownership` на ветках
`already_current` и journal-only стоят ВНЕ большого `try`, который превращает всё
остальное в `ORCHESTRA_LAYOUT_GIT_ERROR`. Значит сырой `sqlite3.OperationalError` —
а `database is locked` тут достижим, БД держит живой сервер, `busy_timeout` 5 с —
уходил бы из `migrate_registered_project_layouts()` прямо в `lifespan`
(`app/main.py:393`) и **валил старт Orchestra целиком, для всех проектов**, из-за
косметической починки, которая бесплатно повторяется на следующем старте.

Хуже всего то, что боевая конфигурация идёт ИМЕННО по этой ветке: раскладка у всех пяти
затронутых проектов уже `current`, то есть в проде сработал бы именно незащищённый путь.

Лечение — `_isolated_session_ownership`: отказ логируется (`logger.error`) и попадает в
результат как `ownership.status == "failed"` с текстом исключения, а миграция файлов и
остальные проекты продолжаются. Это не молчание: отказ виден и в журнале, и в JSON.

Гранулярность применения внутри одного проекта при этом транзакционная: SELECT и все
UPDATE идут внутри одного `with _conn() as connection`, а контекст-менеджер соединения
sqlite3 коммитит при успехе и откатывает при исключении. Значит «часть строк переписана,
часть нет» внутри проекта невозможно; между проектами частичность возможна и безопасна —
повтор идемпотентен.

## Про перепроверку статуса под локом — окна нет, и это проверяемо

`AgentSession.send()` берёт `_lifecycle_lock` (`app/session.py:1296`) и держит его через
`self.status = AgentStatus.RUNNING` (`app/session.py:1530`) до `finally: release()`
(`app/session.py:1644`). Роут держит ТОТ ЖЕ лок и над перепроверкой статуса, и над
записью, поэтому переход `idle → running` между ними невозможен: `send()` заблокируется.
Порядок «проверил → записал колонку → переписал промпт» окна не образует ещё и потому,
что колонка и промпт пишутся ОДНИМ `save_session(snapshot)`, а не двумя записями.

## ОБЩИЙ ДЕФЕКТ, шире этой задачи: загрузчик сессии читает строку ДО взятия лока

Найден ревью (Sol, раунд 2, R2-1 в его нумерации → мой R2-2) и подтверждён по коду.
К владению он отношения не имеет — под ним лежали ВСЕ писатели строки сессии.

**Механика, две точки:** `SessionManager.ensure_loaded` читает строку на
**`app/manager.py:1867`** (`db_row = get_session_by_name(name, scope)`), а лок сессии
берётся только внутри `_ensure_loaded_row` на **`app/manager.py:1900`**; в
`_load_from_db` дальше уходит та самая строка, прочитанная ДО лока. Между этими двумя
точками есть окно, и любая запись в строку, попавшая в него, в живую сессию не
доезжает: объект собирается из устаревшего словаря.

**Почему это не косметика.** Живая сессия позже сохраняет себя из памяти: `_persist_loop`
собирает ПОЛНЫЙ снимок строки (`snapshot = self._to_db_dict()`,
**`app/session.py:5237`**) и отдаёт его в `save_session`, а тот делает
`INSERT … ON CONFLICT DO UPDATE` по всем колонкам. Поэтому устаревшее значение не просто
не видно — оно ЗАПИСЫВАЕТСЯ ОБРАТНО поверх нового. То есть успешно применённая правка
через некоторое время исчезает из БД сама, без единой ошибки в журнале.

**Класс жалоб, который это объясняет:** «поменял, ответ 200/ok, а потом снова старое».
Под окном были описание и системный промпт (`update_session_fields`), модель, привязка
задачи и владение — всё, что правит строку сессии, пока её кто-то грузит.

**Лечение — одна строка, перечитать под локом:**
`return await self._load_from_db(get_session(session_id) or db_row)`.
Оно чинит окно для всех писателей сразу, а не только для смены владения. Закреплено
`test_loader_rereads_the_row_under_the_lock`; мутация обратно на `db_row` его роняет.

**Общее правило, которое отсюда следует:** снимок, прочитанный ДО взятия лока, внутри
лока уже недействителен — под локом его надо перечитать, а не использовать. Захват
«прочитал → подождал лок → применил прочитанное» выглядит корректным ровно потому, что
лок в нём есть; проверять надо не наличие лока, а то, что данные прочитаны ПОСЛЕ него.
