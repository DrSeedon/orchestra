# #147 — ужесточить фильтр правил в промптах

## Вопрос (Step 0)

- **Контекст:** `pipelines/default/prompts/modules/self-improvement.md` инжектится во все роли;
  агенты предлагают `📝 RULE`, оркестратор триажит вручную.
- **Change under test:** более жёсткий фильтр общности, отсеивающий локальную конкретику
  У АВТОРА, до предложения.
- **Baseline:** текущий тест «would this help an agent on a COMPLETELY DIFFERENT task next month?»
  + 4 примера ✅/❌.
- **Измеримый исход:** доля предложений с локальным триггером; и — главное — даёт ли новая
  формулировка ДРУГОЙ вердикт на реальных примерах, чем старая.

## Гипотезы (Step 1)

- **H1 (ведущая):** фильтр слаб, потому что спрашивает про ПОЛЬЗУ («поможет ли»), а польза
  всегда воображаема — автор только что получил эту пользу сам, и отвечает «да».
  Falsifier: если бы дело было в пользе, отбраковка шла бы по доменности; но доменных мало.
- **H2 (конкурирующая):** агенты просто не читают фильтр / он теряется в длинном модуле.
  Falsifier: тогда доля мусора была бы равномерной по типам, а не сконцентрированной в триггерах.
- **H3 (от оркестратора):** нужен счётчик «2 независимых случая».
  Falsifier: если принятые правила выведены из ОДНОГО случая — критерий вредный.

## Замеры (Step 5) — read-only копия живой БД

Снимок: `cp data/orchestra.db /mnt/data/rule-audit-snap.db` (на реальный диск, не в tmpfs).

**Замер 1. Триаж почти не отбраковывает.**
Только `type='user_message'` (настоящие сообщения агентов, без Bash-эха):

| вердикт | шт |
|---|---|
| TAKE | 42 |
| REJECT | 1 |
| прочее (без явного слова) | 6 |

**CONFIRMED** (прямой запрос к живой БД). Из 317 упоминаний `📝 RULE` в логах — 123 реальных
предложения. Ручной триаж, который в постановке задачи считается работающим барьером
(«я отбраковываю руками, часть просачивается»), фактически говорит TAKE в 42 случаях из 43.
Барьера нет — есть штамп. Это меняет постановку: чинить надо не «часть просачивается»,
а «не отбраковывается почти ничего».

**Замер 2. Доменного мусора мало — значит, старый фильтр НЕ сломан, он просто узкий.**
Классификация 112 предложений по маркерам:

| категория | шт | доля |
|---|---|---|
| явно доменные (лес/LOD/НК/бухгалтерия/CSS-grid) | 10 | 8% |
| чистый workflow | 42 | 37% |
| «прочее» — workflow по форме, локальные по триггеру | 60 | 55% |

**CONFIRMED** (счёт по корпусу). Существующие ❌-примеры (вода, растительность) ловят
именно эти 8%. Основная масса брака — 55% в середине, и текущий фильтр про них молчит.

**Замер 3. Что общего у брака — ТРИГГЕР, а не действие.**
Разбор «прочего» показывает устойчивый паттерн: **действие** сформулировано обобщённо и
выглядит переносимым, а **триггер** описывает ситуацию, которая физически возможна только
в этом проекте:

- «Когда делаешь визуал для ленты биржи/маркетплейса → проверять уменьшенным до размера карточки»
- «When визуальный прототип рассчитан на монитор 60 Гц → gate average ≥90, 1% low ≥60»
- «Когда льгота зависит от перечня в пункте НК/ПП → читать пункт до последнего абзаца»
- «Когда бухгалтерский статус влияет на платёж → подтверждать первичным документом»

Автор проверяет действие («полезно? да») и не проверяет триггер («а он вообще где-нибудь ещё
возникнет?»). Отсюда H1 подтверждается, H2 отклоняется: фильтр читают, но он спрашивает не то.

**Замер 4 (falsification, Step 4). Критерий «2 независимых случая» вреден.**
Проверил его на трёх правилах, которые оркестратор и юзер приняли как лучшие за 04.08:

| правило | случаев в основании | судьба при критерии «2 случая» |
|---|---|---|
| `git log -S` перед планированием правки | 1 (#114) | ЗАРУБЛЕНО |
| `git check-ignore` до начала работы | 1 (#134) | ЗАРУБЛЕНО |
| померь собственный шум метрики (split-half) | 1 (#135) | ЗАРУБЛЕНО |

**REFUTED** — критерий отсекает ровно то, что мы хотим сохранить. Один яркий случай с замером
даёт отличное правило; повторяемость коррелирует не с общностью, а с тем, как часто мы
натыкались на грабли (то есть с возрастом правила, а не с его качеством).
Рекомендую **не вводить** счётчик случаев. Пункт 2 задачи закрываю отрицательным результатом.

## Найденный дискриминатор

Разделяет обе группы без ошибок (3/3 принятых, 5/5 отбракованных):

> **Тест триггера:** назови проект, в котором твой ТРИГГЕР не может возникнуть.
> Назвал — правило локальное. Не можешь назвать — кандидат в общий свод.

Почему работает: у принятых триггер — свойство самого ЗАДАНИЯ («задача описывает симптом»,
«в задании указан путь файла», «намерил улучшение на выборке»). Такое бывает в любом проекте.
У отбракованных триггер — свойство предметной области (биржа, 60 Гц, НК, платёж).
Тест объективный: ответ проверяется называнием конкретного проекта, а не ощущением пользы.

## Три адреса (пункт 3 задачи)

Агенты путают, потому что нигде не сказано, ЧЕМ адреса отличаются по смыслу:

| адрес | что туда | тест на выбор |
|---|---|---|
| `docs/workers/<name>.md` | моя привычка//грабля | «это про то, как *я* работаю?» → сюда, порог НИЗКИЙ |
| проектный `CLAUDE.md` | правило этого репозитория | «триггер возникает только в этом проекте?» → сюда |
| глобальный `~/.claude/CLAUDE.md` | правило для всех проектов | «сработало минимум в ДВУХ разных проектах» → только сюда |

Формулировка про два проекта взята из ответа оркестратора пограничному воркеру и применяется
ТОЛЬКО к глобальному файлу — там цена ошибки максимальна (читают все агенты всех проектов),
а откат дороже всего. К проектному своду счётчик случаев не применяется (см. замер 4).

## Две планки, которые нельзя слипать (пункт 4)

- **Личная память — порог НИЗКИЙ.** Файл читает один агент, лишняя запись стоит нисколько,
  проверка перед DONE остаётся обязательной и без критериев общности.
- **Общий свод — порог ВЫСОКИЙ.** Читают все, протухшее правило дороже отсутствующего.
- Риск слипания реален: обе планки живут в одном модуле в 20 строках друг от друга.
  В правке они разнесены явными заголовками и в личной памяти сказано «фильтр общности
  здесь НЕ применяется».

- Тест требует от автора назвать проект — агент может назвать неубедительно и пропустить.

## ПРИЁМКА: где новая формулировка даёт ДРУГОЙ ответ

Прогон обеих формулировок по реальным предложениям из корпуса:

| правило | старый фильтр | новый (тест триггера) | итог |
|---|---|---|---|
| `git log -S` перед планированием (#114) | ДА → предложить | не назову проект → предложить | тот же |
| `git check-ignore` до работы (#134) | ДА → предложить | не назову → предложить | тот же |
| шум метрики split-half (#135) | ДА → предложить | не назову → предложить | тот же |
| лес/LOD обрывается (polus) | НЕТ, домен → не предл. | polus → не предл. | тот же |
| растительность в масштабе человека | НЕТ, домен → не предл. | polus → не предл. | тот же |
| визуал для ленты биржи → смотреть в размере карточки | **ДА, полезно → ПРЕДЛОЖИЛ** | seedon → не предл. | **ДРУГОЙ** |
| прототип на 60 Гц → gate avg≥90 | **ДА, полезно → ПРЕДЛОЖИЛ** | polus → не предл. | **ДРУГОЙ** |
| льгота в пункте НК → читать до конца | **ДА, полезно → ПРЕДЛОЖИЛ** | бухгалтерия → не предл. | **ДРУГОЙ** |
| бухстатус → подтверждать первичкой | **ДА, полезно → ПРЕДЛОЖИЛ** | бухгалтерия → не предл. | **ДРУГОЙ** |
| иллюстрация+текст → независимые grid-области | **ДА, полезно → ПРЕДЛОЖИЛ** | лендинг → не предл. | **ДРУГОЙ** |
| пограничный: фикстура load-bearing → удалять элемент целиком | ДА → в общий свод | триггер общий, но 1 проект → **проектный** `CLAUDE.md` | **ДРУГОЙ** |

**Вердикт изменился в 6 случаях из 11.** Совпадение на пяти — не слабость формулировки:
три принятых правила обе версии пропускают (и должны), два явно доменных обе режут (и должны).
Разница ровно там, где старый фильтр отвечал «полезно → значит общее».

Пограничный кейс решается адресом, а не отказом: действие переносимое, но оплачено одним
проектом → проектный `CLAUDE.md`, в глобальный только после второго проекта. Это совпадает
с решением, которое оркестратор принял вручную, — теперь оно выводится из промпта, а не из его памяти.
