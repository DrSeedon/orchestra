## Summary

The plan has the right product shape for MVP: a native skill, small prompt hooks, Tier-1 worker memory only, and Tier-2 prompt/pipeline changes as proposals. The scientific constraint is also present in the skill requirements: retro findings must be anchored to concrete signals, not open-ended self-critique.

However, there is one wiring assumption that makes the plan non-functional as written: adding `self-analysis` to `pipeline.yaml` is not enough for native skill injection in the current code. There are also trigger/gate holes: the design calls the gate deterministic, but relies on the worker to notice and count its own history with no hard check.

## Findings

blocking: `T2` wires the skill only in `pipeline.yaml`, but `inject_skills_to_worktree()` still reads skill names from `pipelines/default/prompts/roles/<role>.md` frontmatter, not from the resolved pipeline role. In this branch, role prompt files are intentionally frontmatter-free (`tests/test_default_pipeline.py:274-281`), while `app/manager.py:543-549` only uses `get_role(...).skills` to decide whether to call injection, then calls `inject_skills_to_worktree(role, wt.path)`. The injector then does `parse_role_frontmatter(role_path.read_text())` and `meta.get("skills", [])` (`app/prompting.py:183-190`), so `worker.md` / `full-cycle.md` produce an empty list and no `.claude/skills/self-analysis/SKILL.md` is copied. Fix the plan by adding a wiring ticket before/with T2: pass resolved skill names into the injector, or make the injector resolve `pipeline.yaml` itself. Add an AC that a temp worktree actually contains `.claude/skills/self-analysis/SKILL.md` after injection.

blocking: The verification AC would not catch that bug. `skills_catalog()` lists every file in `prompts/skills/*.md` regardless of whether a role can use it (`app/prompting.py:103-115`), so the T2/T4 catalog checks can pass while the worker never receives the skill. The "confirm `inject_skills_to_worktree` would find `skills/self-analysis.md`" check is also too weak; current code can find the file path and still never select the skill name. Replace this with an actual copy assertion and a test for both `worker` and `full-cycle`.

suggestion: The ticket slicing is checkable but not really vertical. T1 creates the skill, T2 attaches config, T3 adds prompts; none of those independently ships an end-to-end behavior. For this small prompt/config change that is not fatal, but the current `T1 -> (T2, T3) -> T4` order hides the injector problem. A cleaner minimal slice is: T0 fix/verify native injection from pipeline role skills; T1 worker end-to-end (`self-analysis.md` + worker skill attach + worker trigger + injection assertion); T2 full-cycle attach/trigger/artifact tree; T3 verification.

suggestion: The gate is described as deterministic, but the implementation is prompt-driven and self-reported. `>=10 tool calls`, "user corrected/rephrased", and "single command retried >=3x" are not collected by code, and the plan explicitly says "no metrics API needed" because the worker "knows" (`plan.md:51-53`). That is a best-effort prompt convention, not a deterministic gate. Either relabel it as best-effort MVP, or make the role prompt invoke the skill before DONE and let the skill immediately skip unless it can cite concrete signals. The latter costs one lightweight skill check per task but closes the missed-trigger path.

suggestion: T3 keeps the gate list only in the skill to avoid duplication, but that creates a trigger chicken-and-egg. If the role prompt only says "if any gate is met", the worker must already know the gate before loading the skill. Native skill metadata may help, but it is not a hard contract. Either include the short gate list in the role prompt, or phrase the hook as "run `self-analysis`; it must skip if no gate is met." The current two-line limit is less important than making the trigger observable.

suggestion: The scientific grounding is mostly enforced for retro entries, but not clearly for worker-memory writes. The plan says problem entries need "no signal => no entry" (`plan.md:63-65`) and memory gets "distilled lessons" (`plan.md:36-37`), but it does not say memory may only be written from an anchored retro entry. Add an AC: every appended/merged worker-memory lesson must cite the source retro and concrete signal, must be generalizable, and must be skipped for n=1 weak observations unless it is worker-scoped and directly actionable. This keeps Huang 2024 / "Knowledge to Noise" constraints from leaking through the memory side channel.

suggestion: Tier-2 proposal behavior is appropriately conservative, but per-task Tier-2 prompt proposals from n=1 can still generate noise. The research says durable prompt edits should come "almost exclusively" from Mechanism B / recurring patterns. Keep the Tier-2 table, but make the default row status "logged, not promoted" unless the signal is severe (for example Codex HIGH on a prompt-caused failure) or recurrence is already known.

question: Do we actually want to attach this to generic `worker` immediately? The plan's blast radius is small in code, but prompt self-triggering on every substantial worker task can create noisy `retro.md` files and memory edits. If the goal is MVP learning, consider starting with `full-cycle` only for one cycle, because full-cycle already has task artifacts, Codex reviews, and report structure. Add `worker` after the first real retros prove useful.

## Verdict

Do not implement exactly as written. The core concept is sound and simple enough, but the plan needs a wiring fix and stronger verification before it is shippable. After changing injection to consume pipeline role skills and tightening the gate/memory AC around concrete signals, this is a reasonable MVP.
