# Proxy ↔ VPN independence — research

**Дата:** 2026-07-01
**Статус:** research only, ждёт approval
**Проблема:** SSH-туннели к прокси-VPS шли через `tun0` (Reality VPN юзера). VPN off → tun0 down → туннели дохнут → Orchestra падает. Прокси должны быть ЗАМЕНОЙ VPN, а зависели ОТ него.

---

## TL;DR (что подтверждено экспериментально)

1. **Contabo (158.220.127.161) и Fornex (89.127.206.225) РАБОТАЮТ напрямую с домашнего РФ-WiFi без VPN.** SSH-баннер отвечает, `curl -x :12343 https://api.anthropic.com/v1/messages` → HTTP 405 (= API живой). РКН их не блокирует.
2. **Ёжик (194.87.250.243) и Timeweb (147.45.101.84) недостижимы** — и через tun0, и напрямую (TIMEOUT + ICMP fail). Это НЕ про VPN: серверы либо лежат, либо firewall режет SSH с неизвестных IP. Отдельная проблема.
3. **Автономность реальна.** Достаточно одного незаблокированного VPS (Contabo). VPN не нужен вообще.
4. **Замкнутый круг не в блокировке, а в routing hijack** от Reality VPN (xray/sing-box TUN-режим) + в **stale ssh-процессах**, которые не пересоздаются при смене сети.

## 1. Root cause: почему при включённом VPN маршрут к VPS шёл через tun0

VPN у юзера — **xray в TUN-режиме** (`/usr/local/bin/xray run`, процесс `nobody`) под управлением **Hiddify** (`/usr/bin/sudo hiddify`). TUN-режим перехватывает ВЕСЬ трафик через policy routing, а не через изменение default route в main-таблице.

### Механизм (`ip rule` + table 2022)

При VPN ON `ip rule list` содержал (приоритеты — чем меньше, тем раньше):

```
9000: from all to 172.19.0.0/28 lookup 2022        # tun subnet
9001: from all lookup 2022 suppress_prefixlength 0 # ← ГЛАВНОЕ
9002: not from all dport 53 lookup main suppress_prefixlength 0
9003: not from all iif lo lookup 2022
9003: from 172.19.0.0/28 iif lo lookup 2022
...
32766: from all lookup main                         # обычный маршрут (default via WiFi gw)
```

`table 2022` = `default via 172.19.0.2 dev tun0`.

**Как это заворачивает VPS-трафик в tun0:**
- Пакет к `158.220.127.161` доходит до правила **9001** `from all lookup 2022`.
- `suppress_prefixlength 0` отбрасывает из решения только маршруты с префиксом ≤ 0 (т.е. `default 0.0.0.0/0`). Но VPS-IP матчится на `default via tun0` — это префикс 0, значит по идее должен быть suppressed и провалиться в main.
- **НО** на практике `ip route get 158.220.127.161` стабильно возвращал `via 172.19.0.2 dev tun0 table 2022`. Значит фактический перехват идёт либо через кэш маршрута, либо xray добавляет доп. маршрут/fwmark. Точный механизм suppress не важен для фикса — **важен наблюдаемый результат**: весь исходящий трафик (кроме DNS и tun-подсети) попадал в tun0.

**Ключевой контр-тест (доказывает, что фикс возможен):**
```
ip route get 158.220.127.161 from 10.199.164.73   # source = физ. IP
  → via 10.199.164.194 dev wlp4s0   (НАПРЯМУЮ, мимо tun0!)
```
Правило `9003: from 172.19.0.0/28 ...` и source-based правила означают: **если задать source = физический IP, маршрут идёт через WiFi-gateway, мимо VPN.** Именно поэтому `nc -s 10.199.164.73 158.220.127.161 22` получал SSH-баннер даже при поднятом tun0.

> ⚠️ `ssh -b <phys_ip>` в тесте молча зависал (пустой вывод), хотя `nc -s` работал. Причина не докопана — возможно ssh резолвит/бандит иначе или ловит IPv6. Для рекомендации это не блокер (правильный фикс — `ip rule`, а не bind), но если пойдём в `BindAddress` — надо перепроверить.

### Почему круг замыкался
- VPN ON → tun0 UP → правило 9001 гонит VPS-трафик в tun0 → SSH-туннели живут (VPN сам ходит наружу).
- VPN OFF → tun0 down → правила 9000-9003 (ссылающиеся на tun0/2022) становятся невалидны, default падает на main (`via 192.168.1.1 dev wlp4s0`). **Маршрут к VPS восстанавливается сам** — но старые ssh-процессы, которые уже установили TCP-сессию через (ныне мёртвый) tun0, зависают в `ServerAlive`-лимбе и не переподключаются мгновенно.

**Вывод:** проблема НЕ в том, что «без VPN нет маршрута». Маршрут есть. Проблема в (а) при VPN ON туннели цеплялись за tun0 и (б) stale ssh-процессы при переключении сети.

## 2. Почему Contabo работает без VPN, а Ёжик/Timeweb нет

Проверка (VPN OFF, домашний РФ-WiFi 192.168.1.11), `nc -w6 <ip> 22`:

| VPS       | IP               | Провайдер | Прямой SSH без VPN | Вывод |
|-----------|------------------|-----------|--------------------|-------|
| Contabo   | 158.220.127.161  | Contabo DE| ✅ SSH-баннер OK   | НЕ заблокирован РКН |
| Fornex    | 89.127.206.225   | Fornex NL | ✅ SSH-баннер OK   | НЕ заблокирован РКН |
| Ёжик      | 194.87.250.243   | (свой VPN)| ❌ TIMEOUT + ICMP fail | недостижим |
| Timeweb   | 147.45.101.84    | Timeweb   | ❌ TIMEOUT + ICMP fail | недостижим |

**Это НЕ про блокировку РКН по стране.** Contabo (DE) и Fornex (NL) — оба европейские дата-центры, оба доступны. Ёжик и Timeweb недоступны и через tun0 тоже (проверено `nc` без source-bind → тоже TIMEOUT). Причины:
- **194.87.250.243 (Ёжик)** — это сам VPN-сервер юзера (Marzban VLESS+Reality). Порт 22 наружу, вероятно, закрыт firewall'ом / SSH слушает нестандартный порт / сервер down. Reality-порт (443) работает, SSH — нет.
- **147.45.101.84 (Timeweb)** — VPS клиента (orchestra.zahoron.ru). Вероятно, SSH ограничен по source-IP (allowlist), домашний РФ-IP не в списке.

> Discrepancy: в тексте задачи Fornex указан как `93.127.202.23`, но в `.env` реальный `SSH_TUNNELS` → `fornex|12342|89.127.206.225|3128`. Тестировал по фактическому IP из .env.

**Fornex `:12342` даёт HTTP 000 хотя SSH до него достучался.** Причина: туннель форвардит на remote `127.0.0.1:3128` (squid), а **squid на Fornex, похоже, лёг** — SSH-слой жив, а прокси-демон за ним мёртв. Отдельная remote-side проблема, не связанная с routing.

## 4. Варианты решения

### Вариант A — «Быстрый»: сделать Contabo дефолтом + health-check автопереключение
**Что:** зафиксировать Contabo (`:12343`) как основной прокси (уже так в `.env`). Довести до ума `scripts/check-proxies.sh` (он уже написан, логика верная) и повесить его на смену сети (NetworkManager dispatcher hook) + периодический таймер.

- ➕ Ноль изменений в сети/routing. Работает уже сейчас.
- ➕ `check-proxies.sh` перебирает кандидатов, находит живой, переключает Orchestra+Codex+TG.
- ➖ Не решает root cause (при VPN ON туннель снова уйдёт в tun0). Но т.к. Contabo достижим и через tun0, и напрямую — на практике всегда работает.
- ➖ Требует рестарт Orchestra при смене прокси (sed в .env).

### Вариант B — «Правильный»: policy routing — VPS всегда мимо tun0
**Что:** добавить `ip rule` с приоритетом < 9000 для IP прокси-VPS → main-таблица (физ. gateway). Тогда даже при ВКЛЮЧЁННОМ VPN SSH-туннели идут напрямую, не через tun0.

```bash
# для каждого прокси-VPS (пример Contabo + Fornex):
ip rule add to 158.220.127.161/32 lookup main priority 8000
ip rule add to 89.127.206.225/32  lookup main priority 8000
```

- ➕ Решает root cause: туннели независимы от VPN на уровне ядра.
- ➕ Split-tunnel: VPN для юзера остаётся, прокси-трафик вынесен.
- ➖ Хрупко: Hiddify/xray **перезаписывают `ip rule` при каждом старте/reconnect VPN** — наши правила надо переставлять после каждого toggle VPN (hook на up/down tun0).
- ➖ Требует root (rule add). Orchestra бежит от `maxim`, не может сам. Либо systemd-unit с CAP_NET_ADMIN, либо NM-dispatcher скрипт от root.
- ➖ `main` gateway меняется при смене WiFi (192.168.1.1 дома, 10.199.164.194 в другой сети) — правило `lookup main` это переживает (main всегда актуальна), ок.

### Вариант C — «Автономный» (рекомендуемый): B-lite через прямой outbound, БЕЗ ip rule
**Что:** вообще убрать зависимость от tun0 для туннелей, привязав ssh к прямому маршруту через **source binding + доведённый health-check**. Комбинация:

1. **Health-driven failover (из A)** — `check-proxies.sh` как источник истины. Один рабочий прокси гарантирован, пока жив хоть один незаблокированный VPS.
2. **Убрать мёртвые VPS из ротации** — Ёжик/Timeweb недостижимы → в `PROXY_LIST`/`SSH_TUNNELS` держать первыми Contabo и Fornex (реально доступные). Мёртвые — в конец или убрать.
3. **Починить zombie-процессы в `ssh_tunnel.py`** — при старте `start_tunnel()` делать `pkill -f "ssh -N -L <port>:"` для своих портов перед спавном (или трекать PID в файле). Иначе дубли копятся.
4. **Опционально** добавить `ip rule` из B ТОЛЬКО если юзер хочет держать VPN включённым одновременно с прокси. Если сценарий «VPN off дома» — B не нужен вообще (маршрут и так прямой).

## Рекомендация

**Вариант C (A + чистка + опционально B).** Обоснование:

- Root cause «нет маршрута без VPN» — **ложный**. Маршрут прямой работает (доказано). Реальные боли: (1) stale ssh-процессы, (2) мёртвые VPS в ротации, (3) кэш статусов в дашборде.
- Полноценный `ip rule` policy routing (B) — оверинжиниринг для сценария «выключил VPN дома»: там tun0 нет, перехватывать нечего. B нужен ТОЛЬКО если юзер хочет VPN + прокси одновременно (напр. VPN для браузера, прокси для Orchestra). Это отдельный кейс — спросить юзера.
- Дешёвый надёжный фикс: гарантировать живой прокси через health-check + убрать паразитов.

### Конкретные правки (для approval, НЕ реализовано)

## Отдельные находки (баги/проблемы)

1. **Zombie ssh-процессы** — `ssh_tunnel.py` не убивает старые процессы при рестарте/смене сети. Дубли копятся (сейчас 7 живых ssh на 4 туннеля). → правка #1.
2. **Дашборд кеширует статусы прокси** — `proxy_manager.py._cache` заполняется только при явном `check_proxy`/`check_all`, никогда не инвалидируется. Юзер видит старое «✅ работает» когда прокси уже мёртв. **Рекомендация:** (а) TTL на кэш (напр. 60с), (б) фоновый `check_all` по таймеру + push через SSE, (в) кнопка «refresh all» в UI. Минимум — TTL, чтобы не показывать stale «зелёный».
3. **Fornex squid (3128) лежит** — SSH до Fornex есть, но remote-прокси не отвечает (HTTP 000). Нужно поднять squid на 89.127.206.225 или убрать Fornex из активной ротации.
4. **Ёжик/Timeweb недостижимы по SSH** (194.87.250.243, 147.45.101.84) — TIMEOUT и через VPN, и напрямую. Мёртвый груз в конфиге. Проверить порты SSH / firewall allowlist или выкинуть из `SSH_TUNNELS`.
5. **`ssh -b <ip>` зависает, `nc -s` работает** — если пойдём в source-binding, перепроверить поведение ssh (возможно нужен `AddressFamily inet` / другой синтаксис). Для рекомендованного варианта не блокер.

## РЕАЛИЗОВАНО (2026-07-01, Вариант C, approved)

Сценарий юзера подтверждён: VPN **или** прокси, не одновременно → **#5 (ip rule split-tunnel) SKIP**.

- **#1 zombie cleanup** (`app/ssh_tunnel.py`):
  - `_kill_stale(port)` — `pkill -f "ssh -N -L {port}:127.0.0.1:"` перед стартом каждого туннеля (once, в `start_tunnel`, НЕ в reconnect-loop). Паттерн якорён на `{port}:127.0.0.1:` → 12340 не матчит 123400. Протестировано на реальном ssh-процессе: убивает.
  - `stop_tunnel` + CancelledError handler: `terminate()` → `wait_for(KILL_GRACE=3s)` → `kill()` (SIGKILL) если завис на мёртвом маршруте.
- **#2 .env порядок**: `SSH_TUNNELS` = contabo, fornex (живые) → ezhik, timeweb (мёртвые). PROXY_LIST уже поправлен оркестратором (Direct, Contabo первыми).
- **#4 дашборд TTL** (`app/proxy_manager.py`): `CACHE_TTL=60s`, каждый cache-результат штампуется `_ts`. `list_proxies` дропает stale (>60s) → фронт рисует ⚪ (unknown) вместо ложного 🟢. + `refresh_loop()` (bg task в `main.py`) перепроверяет все прокси каждые 60с → дашборд самозаживает. Протестировано: fresh keep / stale drop.
- **#3 NM hook**: `scripts/99-orchestra-proxy` (dispatcher-скрипт, реагирует на up/down/vpn-up/vpn-down/connectivity-change → дёргает `check-proxies.sh`). Требует root для установки в `/etc/NetworkManager/dispatcher.d/` — **инструкция по установке в шапке файла**, юзер ставит сам (safety: не sudo-инсталлю).
- **check-proxies.sh**: кандидаты переупорядочены (Contabo, Fornex, Hiddify, Timeweb, Ezhik).

### Осталось юзеру (root/ручное)
1. Установить NM hook: `sudo cp scripts/99-orchestra-proxy /etc/NetworkManager/dispatcher.d/ && sudo chmod 755 ...` (команды в шапке файла).
2. Прибить legacy root-zombie `ssh ... 12338` (owned by root, наш pkill от maxim не достаёт): `sudo pkill -f "ssh -N -L 12338:"`.
3. (Опц.) поднять squid на Fornex (89.127.206.225:3128) или оставить как fallback.
4. Разобраться с Ёжик/Timeweb SSH (firewall allowlist / down) если нужны в ротации.
