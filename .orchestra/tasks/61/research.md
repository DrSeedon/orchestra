# #61 — исследование: возврат на ветку, смерженную сквошем

## Вопрос

- **Контекст**: `merge_worker` мержит СКВОШЕМ. После этого предок теряется, и возврат воркера
  на ту же задачу идёт через `switch_worktree_branch`, где существующая ветка выкачивается и
  в неё вливается база (`app/workspace.py:2010` — `git merge <from_ref>`).
- **Проверяемое утверждение**: возврат на смерженную сквошем ветку всегда падает конфликтом,
  `force=True` не помогает.
- **Измеримый исход**: воспроизвести и назвать признак, по которому платформа имеет право
  пересоздать ветку от базы вместо слияния.

## Замер: воспроизведено, но НЕ всегда

Стенд — настоящий репозиторий: воркер поработал, ветка смержена сквошем, воркер уехал на
`adhoc-*`, затем возврат.

**Случай A — после сквоша main не трогал те же строки:**
```
branch_content_status: content_merged=True, reason=content-noop
switch_worktree_branch(force=True) → {'ok': True, 'branch': 'task-61/worker'}
```
Сегодня это **работает**. То есть «всегда падает» — не так; починка нужна не всему пути.

**Случай B — main после сквоша правил те же строки (боевой случай):**
```
--is-ancestor(работа воркера, main): НЕТ
branch_content_status: content_merged=False, reason=conflict
switch_worktree_branch(force=True) → {'ok': False,
  'error': "merge with main failed: CONFLICT (add/add): Merge conflict in feature.txt",
  'conflicts': ['feature.txt']}
ветка после попытки: adhoc-1-1/worker        ← откат отработал, дерево не испорчено
```
Руками лечится мгновенно и без потерь:
```
git checkout -B task-61/worker main → rc=0
ветка: task-61/worker; чужой коммит на месте: True; своя работа на месте: True
```

## Главное: критерий, который ты предложил, в этом случае НЕ работает

«Содержимое доказано в base через `branch_content_status`» — верный инструмент для #27, но
здесь он даёт `content_merged=False, reason='conflict'` **ровно в том случае, который
падает**. Причина в природе проверки: `merge-tree` сравнивает деревья, а main после сквоша
изменил те же строки — значит слияние конфликтует, и по этому признаку ветка выглядит
несмерженной. `--is-ancestor` тем более говорит «нет» (сквош убивает предка).

Иначе говоря: **git после сквоша не может доказать, что работа ветки уже в main**, если main
успел эту работу доработать. Признак нужно брать не из git.

## Признак есть, и он у нас уже записан

`merge_operations` (`app/db.py:255`) хранит по каждой операции: `scope`, `worker_name`,
`accepted_worker_branch`, `accepted_worker_head`, `state`, `commit_point`. Успешная запись —
это наше собственное доказательство «ветка X с головой H слита в base», не зависящее от
того, что git может вывести из истории.

Правило-кандидат для плана: **ветка существует, по ней есть операция мержа `SUCCEEDED` с
`commit_point=REACHED`, и её `accepted_worker_head` совпадает с текущей головой ветки →
работа уже в базе, ветку можно пересоздать от базы** (`git checkout -B <branch> <from_ref>`).
Голова разошлась с записью → на ветке появилось что-то ПОСЛЕ мержа, это не безобидный
случай.

Это ложится в словарь #17: `SAME` / `BENIGN` / `FATAL` — только доказательство берётся из
durable-записи, а не из git-предка.

## `force=True` сегодня не значит ничего

`force` проверяется ровно в одном месте (`app/workspace.py:1699`) — можно ли ПОКИНУТЬ
текущую ветку с неподтверждённым содержимым. До ветки «целевая ветка существует» он не
доходит вовсе: замер выше сделан с `force=True`, и он не изменил ничего.

Вариант для плана: дать `force` смысл именно здесь — «пересоздать целевую ветку от базы,
даже если доказательства мержа нет». Тогда получается честная пара: без `force` платформа
пересоздаёт только доказанное, с `force` — берёт ответственность человек/оркестратор.

## Риски

1. **Пересоздание ветки от базы уничтожает коммиты ветки.** Если доказательство неверно —
   потеряна работа. Поэтому доказательство обязано быть точным (совпадение головы), а не
   «похоже, мержили».
2. **Старые ветки без записи в `merge_operations`** (смерженные до появления таблицы или
   вручную) не получат доказательства — для них останется сегодняшнее поведение или `force`.
3. **Политика в роуте, механизм в workspace** — придётся протащить явный параметр; риск,
   что кто-то вызовет workspace напрямую и получит старое поведение (это и есть замысел:
   без политики — без пересоздания).

## Чего я НЕ проверял

- Не проверял, есть ли в живой БД записи `merge_operations` для веток, на которые реально
  возвращались (то есть насколько часто доказательство будет доступно).
- Не проверял случай, когда после мержа воркер продолжил коммитить в ту же ветку — по
  правилу это FATAL, но живьём не гонял.
- Не проверял поведение при удалённой ветке (`origin/...`) — у нас локальный мерж, но путь
  формально существует.

## Вердикта Codex нет

Codex недоступен до 08.08. Самокритика: вывод «признак нужно брать не из git» опирается на
один сценарий конфликта (add/add по одному файлу). Возможны случаи, где `merge-tree` даёт
чистое слияние даже после доработки — тогда сегодняшний путь сработает и без изменений,
а мой критерий просто не понадобится. Это не отменяет дефекта, но сужает его: чинится
не «возврат на смерженную ветку», а «возврат на смерженную ветку, которую база успела
доработать».
