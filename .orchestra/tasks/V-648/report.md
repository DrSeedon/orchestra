## Что делает listener и почему сообщение не доказывает аварию

`_activate_backend_tasks()` запускает постоянный listener для runtime с `event_stream == "persistent"`; в остальных потоках `_turn_event_loop()` запускается после `backend.send()`. Есть такой же запуск после отправки ожидающих сообщений через `_flush_pending()`. См. [app/session.py:2011](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2011), [app/session.py:2523](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2523), [app/session.py:1492](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:1492).

`_turn_event_loop()` потребляет события backend, передаёт их обработчику и при `turn_end` учитывает результат хода. `TurnManager.handle_turn_end()` записывает usage и `finish_turn_status()` ставит `IDLE` либо `WAITING` ([app/session.py:2389](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2389), [app/session_turns.py:283](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session_turns.py:283), [app/session_turns.py:452](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session_turns.py:452)). После этого конечный per-turn event stream может штатно исчерпаться без исключения.

`_on_task_done()` отдельно обрабатывает отмену (возврат при `CancelledError`) и необработанное исключение. Любое другое завершение `Task` без исключения, включая обычный `return`, логируется предупреждением с текстом `silent death`. При этом warning печатает текущий статус уже после завершения корутины ([app/session.py:2548](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2548)). Поэтому запись `status=IDLE` сама по себе совместима со штатным концом per-turn потока и не говорит, что ответ пропал.

Есть ещё прямой штатный источник таких warning: per-turn и persistent loop ловят `asyncio.CancelledError` и делают `return` ([app/session.py:2170](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2170), [app/session.py:2252](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2252)); listener явно отменяется, например, перед compact ([app/session.py:2794](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2794)). Поскольку корутина подавила `CancelledError` и вернулась нормально, `Task.exception()` вернёт `None`, и callback напечатает `silent death`. Python 3.12 документация подтверждает, что task считается отменённой, только если корутина передала `CancelledError` наружу, а `exception()` для нормально завершившейся корутины возвращает `None` ([asyncio Task cancellation and exception](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)). Это основание считать заметную долю предупреждений плановым lifecycle шумом, хотя долю без полной таблицы измерить нельзя.

Есть и неоднозначность противоположного знака: в `finally` per-turn listener переводит сессию из `RUNNING` в `IDLE`, если Codex не сообщил об отсутствии активного turn id ([app/session.py:2257](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2257)). Так же происходит при раннем нормальном исчерпании потока до `turn_end`. Тогда callback видит уже `IDLE` и не вызывает `_finish_failed_running_turn()`. Для Claude ветка также переводит состояние в `IDLE`. Следовательно, `status=IDLE` не отличает штатный конец после `turn_end` от преждевременного конца без итогового события. Пойманное внутри `_turn_event_loop()` исключение тоже превращается в обычное завершение корутины: оно записывается отдельно как `turn error`, затем выполняется `finally`, а done callback может добавить предупреждение “silent death”.

Постоянный loop сам имеет штатные возвраты: backend отсутствует; event stream закончился, когда сессия `IDLE` (код прямо помечает это как нормальное при остановке/рестарте); loop отменён. При завершении stream во время работы он, в зависимости от состояния backend, фиксирует провал хода или пытается переподключиться; лимит повторов — пять ([app/session.py:2139](/home/kesha/orchestra/worktrees/home-kesha-orchestra/research-silent-death/app/session.py:2139)). Внешний done callback всё равно маркирует нормальный выход как `silent death`, даже если loop имел ожидаемую причину возврата.

## Проверка боевой БД

Проверен один конкретный сохранённый сбойный ход, который БД связывает с listener termination: сессия `seo-cro`, 24 сентября 08:38:04 UTC. В `logs` есть точное содержимое ошибки `listen task exited unexpectedly while RUNNING`; рядом записаны пользовательское сообщение и ошибка в пределах одной секунды. В `turn_usage` есть два результата `ok=0, stop_reason='interrupted'` в 08:38:04 и 08:38:08 UTC. Это доказывает, что как минимум один ход не завершился обычным успешным turn result.

В том же окне в БД есть одно адресованное этой сессии сообщение от `seedon-orchestrator`: состояние `SUBMITTED`, `error_json` отсутствует. Позже для сессии появляется `text` в 08:40:22 UTC; до этого после сбойной отметки итогового `text` нет. Значит, в этом случае сообщение доставки не осталось в состоянии ошибки, а сессия возобновила выдачу примерно через две минуты. Сопоставить поздний текст с конкретным приватным содержимым сообщения без чтения самого сообщения нельзя, поэтому это свидетельство восстановления активности, не доказательство ответа на каждый запрос. Текущий снимок `sessions.backend_type` для этой сессии — `claude`, тогда как обе строки `turn_usage.runtime` — `codex`; backend в таблице сессий нельзя считать исторической истиной для этого события.

Это один подтверждённый незавершённый ход, а не выборка нескольких случаев из 829 строк. Без журнала нельзя надёжно выбрать остальные конкретные timestamps и соединить их с `logs`, `turn_usage` и `message_deliveries`. Общая проверка статусов доставок за период не заменяет такой join: запись со статусом `SUBMITTED` не устанавливает, что все пользовательские ответы были сформированы или доставлены.

## Причина и оценка

1. **Много предупреждений, вероятно, ожидаемый шум конечных event streams.** Это непосредственно следует из сочетания per-turn listener, обработчика `turn_end`, переводящего сессию в `IDLE`/`WAITING`, и callback, который считает любое нормальное завершение `Task` подозрительным. Предыдущий замер V-646 показывает большой кластер `IDLE` для одной сессии. Он не позволяет оценить долю этого объяснения среди новых 829 строк.
2. **Есть реальный риск раннего окончания listener до фиксации turn_end.** Код нормализует состояние в `IDLE` в `finally`, поэтому предупреждение не различает нормальное исчерпание после итогового события и преждевременное завершение. Один точный marker в SQLite плюс два `interrupted` usage подтверждают, что незавершённые ходы случаются. По этой выборке нельзя установить, что именно вызвало завершение listener, или оценить частоту.
3. **Ранжировать внешнюю первопричину нельзя.** Возможны закрытие потока backend-ом, преждевременное завершение event iterator или ошибка, пойманная самим listener; прямых доступных журналов для проверки распределения причин нет. Это гипотезы по коду, не установленные диагнозы.

Итого: **сам warning в основном выглядит как дефект классификации/уровня логирования, а не доказательство 829 потерянных ходов. Обычное завершение, намеренная отмена и ранний выход не разделены одним сообщением. Ранний выход может оборвать ход, а текущий статус `IDLE` способен скрыть это различие.** На конкретном проверенном случае БД показывает interrupted ход и последующую активность; недоставленного сообщения в статусе `FAILED_BEFORE_SUBMIT` или `DELIVERY_UNKNOWN_ORPHANED` у выбранной доставки нет.

## Предложение

Предлагаю отдельно учитывать обработанный `turn_end`, намеренную отмену и исчерпание потока при незавершённом ходе. Обычное окончание и запланированную отмену не маркировать как смерть; неожиданный выход фиксировать до сброса `RUNNING` в `IDLE`, с session, backend, последним типом события и наличием terminal `turn_end`. Затем повторить выборку по журналу и SQLite, чтобы установить, сколько из 829 записей относится к каждому исходу и сколько ранних выходов повторяются/теряют ответ. Это предложение к последующей реализации; в рамках V-648 код не менялся.

## Метод и ограничение

Изменений кода нет. SQLite открыта `mode=ro`; запрошенные session logs, usage и delivery status читались выборочно, без содержимого сообщений. Журнал не читался из-за отсутствующего доступа `systemd-journal` и запрета повышения привилегий в окружении. Для полной таблицы и нескольких временных срезов потребуется выполнить тот же read-only запрос из контекста с доступом к `journalctl -u orchestra`, сохранив правило дедупликации выше.
