# #2 — задержка при переключении агента в дашборде

## 1. Из чего складывалась задержка (замер ДО)

Метод: Playwright + живой сервер :8888, версия app.js подменяется через
`page.route('**/static/js/app.js')` — так одна и та же страница гоняется на «до» и «после».
`addChatEntry` обёрнут таймером, `EventSource` — сабклассом, который метит первое и
последнее SSE-событие. Скрипты: `/tmp/measure_switch.py`, `/tmp/verify_cache.py`.

Сеть отдельно, curl по тому же запросу, что делает первичный бурст
(`/api/sessions/<agent>/logs?before_id=…&limit=100`), 3 прогона на агента:

| агент | размер | время |
|---|---|---|
| Orchestra-orchestrator | 74 КБ (70 строк) | 13–59 мс |
| back | 112 КБ (100 строк) | 11–16 мс |
| frontend | 39 КБ (23 строки) | 7–14 мс |

Переключение целиком (6 переключений, повторные заходы):

| | ДО |
|---|---|
| контент на экране | 579–1331 мс (медиана 826) |
| первое SSE-событие | 62–229 мс |
| перерисовано сообщений | 100 каждый раз |
| из них внутри `addChatEntry` | 172–446 мс |
| `after_id` в запросе | всегда 0 |

**Вывод: узкое место — рендер, не сеть.** Сеть отдаёт всю пачку за ~15 мс, а
`marked.parse` + `DOMPurify.sanitize` + `hljs` на 100 сообщений стоят 170–450 мс.
Плюс SSE шлёт историю по одному событию на сообщение, и каждый `onmessage`
синхронно рисует и дёргает `scrollTop = scrollHeight` (форс layout), поэтому
доставка бурста растягивается до 0.6–1.3 с.

Отсюда решение: **кеш сетевых ответов проблему бы не решил** — распарсить JSON заново
дёшево, дорого его отрисовать. Кешируем готовый DOM.

## 2. Где держать кеш

Выбран **in-memory на время вкладки** — `Map` с открепёнными `DocumentFragment`.

- `localStorage` (~5 МБ) и `sessionStorage` хранят только текст → при возврате всё равно
  пришлось бы рендерить, то есть платить ровно ту цену, ради которой всё затевалось.
  Плюс сериализация 112 КБ JSON на каждое переключение.
- `localStorage` вдобавок переживает рестарт сервера и пересоздание сессии — максимальный
  риск показать протухшее.
- DOM в памяти вкладки: закрыл вкладку — кеш исчез, окно протухания ограничено сверху.

Ограничения: 8 агентов (LRU), в каждом ≤ `MAX_CHAT_NODES` = 500 узлов — потолок и так
держит существующая обрезка чата.

## 3. Инвалидация (важнее самого кеша)

| ситуация | что делаем |
|---|---|
| воркера убили и подняли заново под тем же именем | ключ валидности — `session.id` из `/api/sessions` (кладём в `_sessionIds` при каждом `renderAgentList`, раз в 3 с). Не совпал → кеш выбрасываем, грузим с `after_id=0` |
| сессию пересоздали, пока агент **не был выбран** (id чужого scope обновляется только при заходе в него) | после `await refreshSessions()` и **до** `connectSSE()` — `_dropStaleRestoredDom()`: id разошёлся → чат стираем, `lastId` сбрасываем в 0 |
| переключение оркестратора (scope) | ключ кеша = `_chatPositionKey(scope, name)`, тот же, что у read-receipts. Имена агентов в разных scope не пересекаются |
| смена compact/normal режима | весь кеш отрисован в прежнем режиме → `_chatDomCache.clear()` |
| ушли посреди стрима | черновик стрима (`streamBubble`) выкидываем из DOM перед укладкой в кеш: финальный `text` придёт строкой лога с id > lastId и нарисуется заново. Иначе был бы дубль |
| ушли, не дождавшись подтверждения своего сообщения (`localMessages` не пуст) или финал стрима отложен выделением текста (`_streamDeferredFinal`) | чат **не кешируем вовсе**: какой пузырь чей — надёжно не определить, а ошибка стоит либо дубля, либо потери. Состояние живёт секунды |
| логи старше 7 дней вычистил `cleanup_old_logs` | в кеше остаются реальные сообщения, просто их уже нет на сервере. Не протухание |

## Грабли, на которые наступил

- **Живой :8888 отдаёт статику из основного чекаута, а не из worktree воркера.** Правки JS
  в своей ветке на живом фронте не видны — `typeof _stashChatDom → undefined`, при этом
  никакой ошибки, просто «фикс не работает». Проверять правки фронта надо, подменяя файл
  через `page.route('**/static/js/app.js', route.fulfill(body=…))`, а «до/после» брать как
  `git show HEAD:путь` против рабочей копии.
- **Искусственный тест хвоста врёт.** Попытка сэмулировать «пока нас не было, пришли
  сообщения», удалив последние узлы из DOM и откатив `lastId`, дала лишний узел: удалённым
  оказался compact-tool-line, к которому досылаемый `tool_result` должен был приклеиться
  (`_findLastBefore`). Артефакт вырезания, не кеша.
