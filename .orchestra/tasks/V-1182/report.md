# V-1182 — авто-сброс Codex при исчерпании лимита

Замер проведён **2026-11-01 07:27 UTC** (08:27 CET). Живой источник — локальный Codex app-server `codex-cli 0.166.0`, только RPC `account/rateLimits/read`; запросов на inference или расход кредита не было.

## Текущее состояние

- План в ответе API: `prolite`. Недельное окно: **92%**, `windowDurationMins=10080`; обычное следующее обновление указано на **2026-11-05 08:32:34 UTC (09:32:34 CET)**.
- API вернул только `rateLimitsByLimitId.codex.primary` (10080 минут). `secondary` отсутствует, других limit ID нет. Поэтому текущий 5-часовой процент и его время обновления этим источником **не установлены**; это не означает доказанного отсутствия 5-часового лимита.
- В последнем снимке dashboard БД (`usage_snapshots`, **2026-11-01 07:22:25 UTC**) общие `five_hour_pct` и `seven_day_pct` были `NULL`; в сохранённом объекте Codex оба окна тоже пусты, хотя `availableCount=2`. Снимок не годится для проверки текущих процентов. Прямой ответ API новее и содержит недельные 92%.
- Живой API перечислил два доступных кредита `Full reset`, `resetType=codexRateLimits`:

| Кредит | Выдан | Сгорает | Статус при замере |
|---|---|---|---|
| 1 | 2026-10-07 22:47:42 UTC | 2026-11-06 22:47:42 UTC | available |
| 2 | 2026-10-31 20:13:19 UTC | 2026-11-30 20:13:19 UTC | available |

Первый кредит сгорает **после** ближайшего обычного недельного обновления. Если недельное окно не достигнет автоматического порога раньше 5 ноября, обычный сброс наступит раньше срока кредита.

## Что делает автоматизация

Задание `bg-7d176f2fd9` — активное `cron_command`, расписание `*/5 * * * *` UTC. Оно запускает `/home/kesha/.cache/canary-scripts/codex_reset.py` через `timeout 60`; установленная копия побайтно совпала с [scripts/codex_reset.py](../../../scripts/codex_reset.py). В базе задания `status=active`, `error=NULL`; последнее сохранённое завершение команды — `no action`, а сохранённые значения кредита и времени недельного сброса совпадают с живым ответом API. Вызов Orchestra `bg_list` также показал задание активным.

Точные условия в коде ([`scripts/codex_reset.py`](../../../scripts/codex_reset.py#L34)):

1. Через `account/rateLimits/read` ищется ровно одно недельное окно на 10080 минут. 5-часовое окно не подставляется вместо него.
2. Список доступных кредитов фильтруется по `status=available` и сортируется по ближайшему `expiresAt`.
3. Если доступных кредитов нет, команда ничего не делает. Иначе она использует самый близкий к сгоранию кредит при **недельном расходе ≥95%** либо когда до его сгорания осталось **меньше 9 минут**. Ровно 9 минут под expiry-условие не попадает.
4. Расход выполняется отдельным RPC `account/rateLimitResetCredit/consume` с idempotency key `orchestra-<credit id>`, затем код повторно читает лимиты. Ошибки печатают `REDEEM_FAILED`; успешное действие — `REDEEMED`.

Значит **95% — порог автоматизации, а не 100%**: кредит может быть потрачен до исчерпания. При 100% условие `≥95%` тоже истинно, и при работающем задании/провайдере следующий запуск по расписанию должен попробовать расходовать доступный кредит. Плановый интервал — до пяти минут ожидания следующего запуска; это не гарантия немедленного сброса. При отсутствии кредита или ошибке API/consume автоматического успешного сброса не подтверждается: ошибка даст `REDEEM_FAILED`, а последующие запуски повторят проверку по расписанию. При штатном обновлении 5 ноября кредит не расходуется.

Использование досрочного кредита отличается от обычного обновления: оно вызывает consume и тем самым расходует один отдельный бонус. Историческая локальная хроника ранних Codex reset-ов фиксировала перенос следующего недельного срока примерно на «момент сброса + 7 суток»; поэтому ранний кредит может отодвинуть обычную дату. Это историческое наблюдение, а не повторно проверенная гарантия провайдера. См. [.orchestra/kb/models-and-quotas.md](../../kb/models-and-quotas.md#банкованные-досрочные-сбросы-codex-13-штук-за-08-08--19-09-и-чем-они-видны-20-09-2026).

## Работоспособность и границы доказательства

На момент проверки `systemctl show orchestra` показывал `ActiveState=active`, PID `3752461`, запуск процесса **2026-10-31 21:30:03 UTC**. В журнале после этого есть `bg_jobs: restored 26 jobs, expired 0`; код восстановления поднимает все активные неистёкшие задания из БД (`app/bg_jobs.py:685-767`). Состояние конкретного задания при чтении было active без сохранённой ошибки.

За весь доступный в журнале период с создания задания 21 октября фильтр по его ID дал запись о создании и два совпадения шаблона **22 октября 18:30 и 18:35 UTC**. Журнал сообщает только о совпадении `REDEEMED|REDEEM_FAILED`, а не различает результат операции. Код задания не пишет каждый обычный проход в журнал. В БД сохраняется `last_output` без времени выполнения; текущее `no action` совпадает с показаниями API, но по нему нельзя установить время последнего прохода. Следовательно, активное состояние, восстановление заданий после старта и согласованный последний вывод поддерживают вывод, что задание настроено и работает; точный факт успешного 5-минутного опроса непосредственно перед замером этими журналами не доказуем.

5-минутные проходы и журнал проверены только для Orchestra на этой машине. Подписка могла расходоваться другой сессией/устройством между чтением API и очередным запуском. Без использования кредита нельзя экспериментально проверить, какие конкретно окна провайдер обнуляет, как быстро это видно всем клиентам и сохраняется ли дата обновления после очередного раннего consume.
