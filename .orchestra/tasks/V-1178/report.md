# V-1178 — Read-only diagnosis of seven laptop resume warnings

## Finding

The seven startup lines were failed attempts to load persisted worker sessions, not seven cut turns. The restart receipt had `cut_names=[]`; all seven rows were `idle` before and after the restart, and the current read-only check still finds them `idle`. The saved native session IDs are identical before restart, after restart, and now for all seven. The session rows remain readable through the API (7/7 HTTP 200). The route returns a detached data-only object when a session was not loaded; this proves metadata availability, not an active worker runtime.

The startup cause matches the normal strict layout refusal at the worker-worktree level. Current layout classification is `current` for all seven base project scopes and `missing` for all seven stored worker worktrees. The project-scope `layout.json` files predate the restart. The `ORCHESTRA_LAYOUT_MISSING` exception rewrites its reported repository to the worktree's base checkout, which explains why the journal names a base that currently has a layout file. `load_worker_memory` uses the worktree repository path when available and refuses a missing worktree layout if either it or its base has managed state. `SessionManager.auto_resume_all` catches the load failure; only rows previously `running` or `interrupted` enter `not_continued` and receive restart-cut recovery. These seven were already idle, so no cut notification or retry was issued. Source inspected in the startup-era revision: `app/manager.py::SessionManager.auto_resume_all`, `app/prompting.py::load_worker_memory`, and `app/orchestra_layout.py::{LayoutMigrationError,migrate_worker_worktree}`.

If any of these sessions must execute future work, a separate authorized task must select a per-worktree reconciliation path after reviewing its preserved changes. No resume, message, repair, model turn, restart, or deletion was performed.

## Recovery feasibility on isolated copies

The worktree Git graph gives a concrete, non-code migration plan. Five worker heads are ancestors of their project base; all five worktrees are dirty only in `.serena/project.yml`. Three of those bases do not change `.serena/project.yml` on the way to the layout-introduction commit; the other two do. The `.orchestra/layout.json` blob is tracked in each base and absent from all seven worker branch trees. A standard fast-forward to the layout-introduction commit would bring the layout and managed paths without changing a session row or native ID.

Two dirty ancestor worktrees have upstream changes to `.serena/project.yml`, but their saved local bytes exactly match the pinned layout commit's version. The three-way YAML previews are clean; five semantic keys changed on both sides and have the same merged values. A synthetic dirty-file FF still refuses because the index/worktree differs from HEAD. A WIP preservation commit followed by an ordinary merge to the layout commit is a viable Git path and passed a synthetic check; it is a live history write and needs project-owner approval. Three other dirty ancestor worktrees have no upstream change to `.serena`; synthetic `--ff-only` preserved their local file. Two clean worktrees are not fast-forwardable: one is 1 commit ahead / 48 behind, the other 30 ahead / 11 behind. An isolated shared-object clone previewed merging each to its minimal layout-introduction commit: the first has one content conflict; the second merges cleanly and retains both histories. Exact paths, keys, commits, and per-worktree associations remain private.

The synthetic exercise used current `migrate_project_layout`, `migrate_worker_worktree`, and `load_worker_memory` functions. A clean old-layout linked worktree migrated and loaded its original memory. A missing-layout worktree returned `None` from `migrate_worker_worktree`; both the loader and `migrate_project_layout(repair=True)` refused it with `ORCHESTRA_LAYOUT_MISSING`, leaving its HEAD and status unchanged. A dirty missing-layout branch also kept its file and status unchanged. Normal Git fast-forward moved a clean missing-layout branch to current and restored memory; a dirty non-overlapping `.serena` edit was preserved; if upstream changed that file to a different value, fast-forward failed without changing HEAD or file bytes. A separate synthetic commit-then-merge proved the two Sensar `.serena` versions can be preserved as a WIP commit and merged without conflict when their bytes already match upstream. The first same-file synthetic setup stopped before merge because its relative worktree destination resolved under the synthetic base; the corrected absolute-path run is the result above. The merge previews used an isolated `--shared --no-checkout` clone in the laptop's temporary directory; merge-tree wrote only to that clone, and no live refs, index, or worktree were changed. Synthetic runners and receipts are `.orchestra/private/V-1178/verify_layout_recovery.py`, `synthetic-layout-recovery-result.json`, and `synthetic-serena-preservation.py` with `synthetic-serena-preservation/result.json`.

Initial recovery plan: fast-forward the three non-overlapping ancestor branches to their layout-introduction commit, preserving `.serena`; resolve the two same-file `.serena` overlaps explicitly; merge the two divergent histories after reviewing the one reported content conflict. This is an existing Git path and needs per-project authorization for live worktrees. Extending `migrate_worker_worktree` to initialize arbitrary `missing` states would change its contract and is not necessary for this one-time plan; it needs a separate owner decision. After branch reconciliation, `GET /api/sessions/{name}/session-history` is the existing lazy-load path: `ensure_loaded` reconstructs the session with its saved native ID and calls `AgentSession.start()` without an initial message, which sets/persists `idle` and does not generate a model turn. It changes in-memory/session persistence state, so it was not called in the initial read-only audit.
