# V-653 — три небольших дефекта платформы

## Результат

1. `SessionManager.remove()` отменяет ожидающий таймер предкомпакта до отключения backend и удаления worktree. После входа в `_fire_precompact_timer()` ссылка на задачу очищается, чтобы последующие отмены из самого компакта (например, при `DeferredContext`) не оборвали его. Поведенческий тест `test_remove_cancels_pending_precompact_timer` помечает сессию выгруженной (`loaded=False`), удаляет её во время ожидания таймера и подтверждает, что таймер не вызывает compact. После `remove()` ожидание явно отпускается, поэтому тест падает при удалении отмены из `SessionManager.remove()` вместо зависания.
2. Таймаут `cron_command` по-прежнему сохраняется в `last_output` и теперь отправляет цели задания уведомление с id, командой, лимитом 600 секунд и рекомендацией проверить запуск. Последовательные таймауты дают одно уведомление; успешное выполнение сбрасывает это состояние, и следующее превышение лимита снова сигналится. Тест `test_timeout_wakes_once_until_a_successful_run` проверяет последовательность таймаут → таймаут → успех → таймаут.
3. Миграция V-576 создаёт `attention_events` через `CREATE TABLE IF NOT EXISTS` при переходе v2→v3 и восстанавливает таблицу на существующей базе v3. Если таблица уже была создана вручную, DDL идемпотентен. Тест `test_v3_database_missing_attention_events_is_repaired` удаляет таблицу после миграции, проверяет восстановление и повторный идемпотентный запуск.

Описание таймаута в `bg_create` и раздел `Unreleased / Fixed` обновлены. TODO фиксирует, что миграцию нужно проверить при следующем рестарте владельцем, поскольку эта ветка сама Orchestra не перезапускает.
