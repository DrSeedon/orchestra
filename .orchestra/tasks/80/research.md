# #80 — исследование: залипание на PARTIAL и игнор нового `operation_id`

## Вопрос

- **Контекст**: `merge_worker` — durable-операция. git-часть прошла, привязка задачи упала
  (`task '18' not found`) → операция осталась `PARTIAL`; все последующие вызовы, включая
  вызовы с НОВЫМ `operation_id`, возвращают результат первой операции (старая ветка,
  старый `worker_head`).
- **Проверяемое утверждение**: новый `operation_id` обязан создавать новую операцию;
  вторичный провал привязки не должен блокировать успешную git-часть.
- **Измеримый исход**: воспроизвести залипание и назвать переход, которого не хватает.

## Гипотезы и фальсификаторы

**H1 — дедупликация по `operation_id` схлопывает разные вызовы.**
*Фальсификатор*: если блокирует не сам id, а что-то другое — H1 неверна.
**Итог: ОПРОВЕРГНУТА.** Блокирует не id: запись с новым id вообще не создаётся.

**H2 — незакрытая операция сессии блокирует любые новые.**
*Фальсификатор*: найти код, который снимает эту блокировку (закрывает операцию).
**Итог: ПОДТВЕРЖДЕНА, и фальсификатор дал главное: снимающего кода НЕ СУЩЕСТВУЕТ.**

## Замер: воспроизведено (стенд на уровне операций)

```
1) состояние после провала привязки: PARTIAL, commit_point=REACHED
   next_action: FINALIZE_SAME_OPERATION — Finalize this operation; do not repeat or
                manually apply the Git merge.

2) новый operation_id=9bc9edb2…, ветка task-80/worker, голова b…
   создана новая операция: False, http=200
   вернулся operation_id: ada07477… (ПЕРВОЙ операции)
   ветка в ответе: task-17/worker, голова: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa

3) кто-нибудь пишет resolved_at: НИКТО
```

Все три пункта репорта подтверждены на одном прогоне.

## Механика — три места, и одно из них пустое

1. **Блокировка** (`app/merge_operations.py:234-243`): перед созданием операции ищется
   «активная» по сессии —
   `WHERE session_id=? AND resolved_at IS NULL AND state IN ('PENDING','RUNNING','PARTIAL','UNKNOWN')`.
   Нашлась → возвращается ЕЁ результат, новая запись не создаётся. Отсюда и «переданный
   UUID в ответе не появляется»: он нигде не сохраняется.
2. **Источник PARTIAL** (`:529-531` и `:564-565`): провал привязки задачи кладётся в
   `stage_failures` как `TASK_LINK_PARTIAL`, а любое непустое `stage_failures` при
   `commit_point == "REACHED"` даёт `state = "PARTIAL"`. То есть **успешный и необратимый
   git объявляется частичным из-за вторичного шага**.
3. **Выход** — его нет. `finish_operation` (`:630-636`) пишет `state`, `commit_point`,
   `finished_at`, но **`resolved_at` не пишет никогда**; поиск по всему `app/` не находит
   ни одного `SET resolved_at`. Колонка есть (`db.py:291`), индекс по ней есть (`db.py:302`),
   писателя нет.

**Корень:** в машине состояний есть состояние, которое блокирует работу, и нет перехода
наружу. Дверь в одну сторону.

## Блокировка ЗАДУМАНА — и это меняет форму правки

`tests/test_merge_operations.py:303` —
`test_unresolved_partial_blocks_new_key_even_when_snapshot_drifted`: тест прямо закрепляет,
что незакрытая PARTIAL блокирует новый ключ ДАЖЕ при изменившемся снимке. То есть это не
недосмотр, а сознательная защита от повторного мержа поверх недоделанной операции.

Значит правка не «убрать блокировку», а **дать ей выход**: пока выхода нет, защита
превращается в ловушку, и репортёру пришлось нарушить `next_action` («do not merge
manually»), чтобы не потерять три коммита.

## Что можно менять, а что нельзя (для плана)

**Нельзя потерять**: гарантию «не мержим второй раз поверх незавершённой операции». Она
защищает от двойного применения git — самого дорогого класса ошибок в этом коде.

**Варианты выхода** (решать оркестратору, я их не выбирал):

| вариант | суть | цена |
|---|---|---|
| A. явное закрытие | тул/эндпоинт «операция разобрана, закрыть» → пишет `resolved_at` | ещё одна ручка у оркестратора, зато решение остаётся человеческим |
| B. авто-закрытие вторичных провалов | если `commit_point=REACHED` и все провалы вторичные (привязка, RAG) → операция терминальна и `resolved_at` ставится сразу | ловушка исчезает без новых ручек; риск — «вторичный» надо определить точно |
| C. новый снимок = новая операция | блокировать только при СОВПАДАЮЩЕМ снимке; другая ветка/голова → новая операция | прямо отвечает пункту 2 репорта, но ослабляет защиту из теста `:303` |
| D. привязка к несуществующей задаче — WARNING | `task '18' not found` не попадает в `stage_failures` вовсе | пункт 3 репорта; сам по себе не лечит залипание, только его частый повод |

Моя рекомендация — **D + B, и A как страховка**: D убирает самый частый повод (ссылка на
несуществующий номер — ошибка вызывающего, а не мержа), B делает состояние проходимым для
уже случившихся, A оставляет человеку рычаг для действительно неясных случаев (`UNKNOWN`).
Вариант C трогает инвариант, закреплённый тестом, — его я бы не брал без явного решения.

## Аддитивность контракта (окно мерж→рестарт)

Новый MCP против старого роута в памяти: любые новые поля ответа (`resolved`, причина
закрытия) должны ДОБАВЛЯТЬСЯ, а отсутствие поля означать «старый сервер», а не «не
закрыто». Новых обязательных полей запроса не вводить: старый роут их проигнорирует, и
клиент решит, что закрыл операцию, когда он её не закрыл.

## Риски

1. **Ослабить блокировку — значит рискнуть двойным мержем.** Любой вариант обязан оставлять
   недоделанную операцию блокирующей, пока её не закрыли явно или автоматически по правилу.
2. **`UNKNOWN` — не то же самое, что `PARTIAL`.** UNKNOWN означает «git-исход неизвестен»;
   авто-закрывать его нельзя ни при каких условиях, только человеком.
3. **Общий рантайм четырёх проектов.** Ошибка здесь ломает мерж всем сразу.

## Живой факт: прямо сейчас заблокирован один воркер

Проверка живой БД (read-only) после написания разбора:

```
незакрытых операций сейчас: 1
PARTIAL | REACHED | sales | adhoc-1785832953-25/sales
```

То есть у воркера `sales` **любой `merge_worker` сейчас возвращает результат этой операции**
и мержа не делает — независимо от того, какой `operation_id` передан. Это не гипотеза о
будущем, а текущее состояние: залипание уже случилось второй раз, у другого воркера.

Как только выход появится (любой из вариантов A/B/D), эту запись надо закрыть — и это же
первый настоящий сценарий для проверки после выката.
