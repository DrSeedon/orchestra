Причина провала цели — не драйвер, а распределение: при отборе по записанному правилу и условиях «симптом без литералов» задачи Luna либо решает всегда, либо не решает; середины мало (см. «Что это значит»). ## Отбор кандидатов (правило, не вкус)

Источник — `.orchestra/tasks/V-914/index.jsonl` (400 F2P). Скрипт `select.py` (seed 923) применяет правило:

* базовое: F2P=true; на родителе красный не по `ImportError`/`has no attribute`/`cannot import` (нельзя решить, не угадав новое имя); коммит не из 20 пилотных задач V-914 → 264 коммита;
* **плечо A («несколько файлов»)**: `priv_names ≤ 6`, `mock_count ≤ 12`, коммит меняет ≥2 файлов в `app/ scripts/ pyproject.toml`, 15 ≤ изменённых строк ≤ 500 → пул 63;
* **плечо B («случайная выборка для оценки смещения»)**: из остальных 264−63 с мягким критерием `priv_names ≤ 4`, `mock_count ≤ 8` → пул 52. Порядок в обоих пулах — `random.Random(923).shuffle`.

Все 115 кандидатов (63 + 52) получили черновик условия; отбор кандидатов по «описуемости» вручную не делался. Черновик писал Sonnet (dynamic_workflow, 2 запуска, ≈ $2,5 API-эквивалента, подписка) по входу из сообщения коммита, диффа `app/` и диффа тестов, с правилами: симптом и ожидаемое поведение словами; можно назвать один главный файл (с наибольшим числом изменённых строк), но **никаких имён функций/констант/полей и литералов, которые проверяет тест**; не называть, какие несколько файлов менять; иначе `reject` с кодом (LITERAL/DOCS_PROMPT/ENV/TRIVIAL/OTHER) и списком скрытых литералов. Вердикты — `drafts.json`.

Результат: из 115 принято 35 (**A 11 из 63 = 17%; B 24 из 52 = 46%**), остальные 80 отклонены (почти все LITERAL). Вывод о смещении: правило «несколько файлов» отсеивает как раз задачи с неугадываемыми новыми именами — мультифайловые изменения чаще вводят новый интерфейс; среди принятых это 10 задач из 34 (C02 исключена). Принятые условия я прочёл целиком; правка вручную не делалась.

**Контроль скоринга** (`control.jsonl`, `run2.py control`): родитель красный, эталон коммита зелёный — 34 из 34. C02 исключена (коммит удаляет свой тестовый файл, тестов нет). Три предварительных «красных эталона» оказались артефактами драйвера (`tail -40` вырезал итоговую строку pytest при шуме asyncio; `database is locked` при параллельном запуске) — драйвер исправлен (итог ищется grep'ом), контроль C09/C15/C35 повторён: зелёные.

## Метод прогона

`run2.py`: фикстура — `git archive <коммит>^ app scripts pyproject.toml`; Luna (`tools=all`, сеть включена, один проход, `Semaphore(3)`); скрытые тесты — тестовые файлы коммита, в полном дереве коммита (`git init`, ветка `main`) с `app/scripts/pyproject` модели; принято = все тесты зелёные. Вне cgroup (`ssh kesha@localhost`, `nice 15`), venv отдельный. Метка **`no_edit`** = пустой дифф `app/scripts/pyproject` относительно фикстуры: такая попытка не скорится, не входит в знаменатель, попытки добавляются (до +3 на задачу). Остановка: первые 3 попытки с правкой дали 3/3 → «потолок», 0/3 при реальном падении тестов → «пол»; иначе до 10 попыток с правкой. Доверительный интервал — Wilson 95%. Платные токены — `max(0, вход − cache_read − cache_create) + cache_create + вывод` (чтение кеша не считается, KB V-660).

## Что это значит

1. **Распределение двухмодальное.** Из 34: потолок 17 (50%), пол 8 (24%), середина-ish 9 (26%), в том числе строго в окне 30–60% — 2. Ранняя остановка по 3 повторам усечёт и часть задач в окне (задача с p=0,6 даёт 3/3 с вероятностью 22%; p=0,5 — 12,5%), так что окно недооценено — но не настолько, чтобы дать 20.
2. **Полы не равны «трудно».** C07, C10, C11, C18, C19, C26, C27, C34: тесты падают по существу (не «нет правки»), но я не разбирал по каждой, решаема ли она по условию; по названиям упавших тестов (содержимое не разбиралось) в нескольких тест, по-видимому, проверяет точные значения/маркер, которые условие намеренно не раскрывает (C18 — точный маркер «тихого хода», C19 — декодирование `\xff`→`\ufffd`, C26 — «слепой артефакт»). Это дефект «условие без литералов» — задача неразрешима угадыванием, а не трудна. Для набора различения такие 8 задач бесполезны (всегда 0).
3. **Условия вышли длинными и порой близкими к спецификации** (черновики от модели при правиле «симптом, а не требование»); это поднимает потолок. Правило «один главный файл назван» оставлено из пилота; без него пол вырос бы.
4. **Плечи**: средняя принимаемость сопоставима (A 65%, B 62% по всем попыткам), но состав остановок разный: B даёт 14 потолков из 24 (58%), A — 3 из 10. Мультифайловость (A) чуть чаще даёт середину (4 из 10 дошли до 10 попыток против 5 из 24), по малым числам — наблюдение, не вывод.

## Контаминация и ограничения

* Флаг `contamination_flag` срабатывает на тексты внутри самой фикстуры (`git log `, `/home/kesha/orchestra`, `github.com` в коде/скриптах): у C05, C08, C24, C33 — почти в каждой попытке (фикстура содержит эти строки), у остальных почти никогда. Доля принятых: флаг 29/50 (58%), без флага 79/121 (65%) — признака накачки нет, но сырой лог попыток не сохранён (в отличие от V-914), так что обращения за пределы каталога **не исключены поштучно**. Недочёт драйвера; для постоянного набора нужен лог и жёсткий запрет чтения вне каталога (песочница).
* `persist_turn_usage` во внешнем окружении падает (`no such table: turn_usage`): учёт в БД платформы для этих запусков не записан; цифры здесь — из `runs.jsonl`.
* Один провайдер/модель/плечо; нет Sonnet и нет сравнения «deeper» (контраст не делался: набор не получился, бюджет не оправдывал).
* Черновик условий писала модель; полной ручной проверки неразрешимости по условию нет (см. п. 2).
* Знаменатель — только попытки с правкой; `no_edit` суммарно 6 из 171 (3,5%), заметно меньше, чем в пилоте V-914 (2 из 20).

## Что дальше (предложение, решение владельца)

Чтобы получить ≥20 задач в окне, нужна не доводка отбора по виду коммита, а **калибровка на более широком пуле по дешёвому первому проходу** и другой генератор условий: брать условия с уровнем детализации «симптом + подсказка места», но проверять неразрешимость (скрытые литералы) до прогонов, а не после; кандидатов при выходе середины ~25% нужно ≈ 80 для 20 задач (≈ 80 × 3 × 24 тыс. ≈ 5,8 млн плюс добор). Без этого набор «по правилу» годится максимум как 6–9 задач с 3/10…8/10: C04, C17 (+ C05, C08, C09, C12, C24 как верхняя половина).
