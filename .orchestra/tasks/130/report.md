# #130 — детектор целых > 2^53 в аргументах tool-вызова

Страховка по итогам разбора #129 (`docs/tasks/129/research.md`): округляет JS-слой CLI,
до Python, поэтому у себя мы можем только сделать следующий случай различимым за один греп.

## Что сделано

`app/backend_claude.py`:
- `_oversized_ints(value, path)` — рекурсивный обход дикта/списка, отдаёт `(json-путь, значение)`
  для каждого `int` с `abs(v) > 2**53`. `bool` отсекается явно (в Python это подкласс `int`).
- В ветке `ToolUseBlock`, рядом с уже существующим `_json.dumps(block.input, ...)` — по строке
  `logger.warning` на каждое найденное значение: имя тула, путь до поля, само значение.

Смотрим на ЗНАЧЕНИЕ, а не на ответ сервера — поэтому ловится и тихий сценарий, где схема тула
допускает `number` и правка молча уходит в чужой объект (в #129 нас спас `z.string()` у чужого MCP,
второй раз может не спасти).

## Стоимость на tool_call — измерено, ограничений не ставил

Выборка — **11 876 реальных тел аргументов** из живой БД (read-only копия), обход каждого 200 раз:

| что | время |
|---|---|
| медиана по реальным аргументам | **1.33 µs** |
| максимум по реальным аргументам | **3.76 µs** |
| самый большой реальный аргумент (157 697 B) | **2.20 µs** |
| для сравнения: `json.dumps` того же аргумента, который уже делается в этой же строке | **390 µs** |
| патологический случай: список из 10 000 чисел | 5 166 µs |

Обход стоит **в 177 раз дешевле сериализации**, которая и так выполняется на каждый tool_call.
Цена пропорциональна числу ЭЛЕМЕНТОВ контейнеров, а не байтам: аргумент на 157 КБ (почти всё —
одна строка) обходится за 2 µs.

Поэтому **ни глубина, ни размер не ограничены**. Патологический случай в 11 876 реальных
аргументов не встретился ни разу (максимум 3.76 µs — это на три порядка ниже), а любой лимит
завёл бы молчаливое слепое пятно: обход, который тихо не досмотрел до поля, хуже отсутствующего.
Если такой аргумент когда-нибудь появится, 5 мс на tool_call — всё ещё не та величина, ради
которой стоит терять полноту проверки.

## Слепые пятна детектора (самопроверка)

- **Значение, приехавшее как `float`, не ловится.** Практически недостижимо: JS
  `JSON.stringify` печатает целочисленный double без экспоненты вплоть до 1e21, поэтому Python
  разбирает его в `int`. Экспоненциальная запись начинается с 22 цифр — таких ID в природе нет.
  Чинить нечего, но знать стоит.
- **Флуда не ограничивал:** аргумент с сотней больших ID даст сотню строк. В реальных данных
  максимум — 3 ID в массиве (`moderate_ads`), поэтому лимит был бы преждевременной абстракцией.
- **Глубина рекурсии не ограничена.** Риск симметричен уже существующему `_json.dumps` строкой
  выше: обе рекурсии тратят один и тот же стек, и если dumps на этом объекте выжил, выживет и обход.

Гипотеза (НЕ проверена): `serde_json` разбирает целое в `i64`, 19 цифр < 2⁶³ проходят точно,

**Важно для решения о страховке на codex-пути — она нужна при ЛЮБОМ исходе, и вот почему:**
- Codex округляет → мы видим округлённый `int` > 2⁵³ → детектор срабатывает;
- Codex не округляет → мы видим ТОЧНЫЙ `int` > 2⁵³, и он будет округлён на последнем хопе в
  любом MCP-сервере на JS, чего мы уже не увидим → детектор становится единственным
  предупреждением, то есть нужнее, чем в первом случае.

Условие срабатывания (`abs(v) > 2**53`) в обоих случаях одно и то же. Точка вставки на
codex-пути — `_tool_arguments_json` (`app/backend_codex.py:240`), туда же приходят аргументы
после нашего точного `json.loads`. Правку не делал: расширение объёма — решение оркестратора.
