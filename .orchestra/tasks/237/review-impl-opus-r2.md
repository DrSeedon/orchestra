## 2. B2 — закрыт; арифметику пересчитал сам

`_ADMISSION_WATCHDOG_S = _DRAIN_DEADLINE_S + _WATCHDOG_MARGIN_S` = 900 + 120 = **1020 с**
(`app/routes/system.py:1766-1767`), токен попытки `_restart_attempt` (`:1772`, проверка `:1788`),
снятие сторожа при отказе — `_disarm_watchdog_if_aborted` (`:1918`).

**Проверено пробой, что сторож снимается ТОЛЬКО при отказе** (полный поток `restart_server`,
`_abort_restart` обёрнут счётчиком):

```
# попытка отказывает на ~0.5 с, бюджет сторожа 1.0 с
aborts: ['3 mutating call(s) still in flight']            → ровно 1, сторож не выстрелил

# сигнал ушёл, процесс жив (os.kill замокан), бюджет 0.6 с
aborts: ['no restart within 0.6s of a successful preflight']   http allowed: True
```

Второе плечо — то самое, ради чего сторож существует, и оно осталось живым: гейты
переоткрыты, флот возвращён. Замечание автора про `test_t6_admission_reopens_if_the_restart_
never_happens` подтверждаю — этот оракул подменяет `_restart_service_after_response` двойником,
возвращающим `{"ok": True}`, поэтому «отменять сторожа при любом завершении» его роняет.

**Пересчёт бюджета (моя арифметика, не авторская).** Худший ход попытки:
`sleep(0.5)` + `drain_mutating_requests` (≤ `MUTATING_DRAIN_BUDGET_S` = 120 с,
`app/main.py:53`) + цикл дренажа ходов (≤ 900 с) + подготовка флота. Формально
`0.5 + 120 + 900 = 1020.5 > 1020` — то есть запас в 120 с целиком съедается вторым
дренажом. На практике второй дренаж мгновенен, и это доказуемо: `/api/restart` входит в
`_CENSUS_EXEMPT_PATHS` (`app/main.py:98-103`), а приём мутирующих закрыт префлайтом, поэтому
`inflight_mutating_count()` уже 0 и `drain_mutating_requests` возвращает True на первой
итерации (`app/main.py:216-219`). Значит реальный худший ход ≈ `0.5 + 900 + подготовка`, и на
флот остаётся ≈119 с — при 24 живых Codex-процессах на машине и `drain_budget_s=1.0` на
сессию этого хватает с запасом. Вывод: бюджет достаточен, но его достаточность держится на
цепочке из трёх фактов, ни один из которых не записан рядом с константой. См. S-a.

## R2-B1. Гейт активации в ранбуке не видит НИ ОДНОГО живого CLI — он зелен всегда

`docs/tasks/237/window-runbook.md:49` (шаг 2, гейт активации) и
`docs/tasks/237/window-runbook.md:166` (ежесуточная проверка деградации).

Обе строки ищут процессы шаблоном `pgrep -f 'codex app-server'`. **Такой подстроки в argv
наших CLI нет.** Реальный argv:

```
node /usr/bin/codex -c model_reasoning_effort="xhigh" -c features.multi_agent=false \
     -c web_search="live" app-server --stdio
```

между `codex` и `app-server` стоят три `-c`-опции. Замер на этой машине прямо сейчас:

```
pgrep -f 'codex app-server'      →  1 совпадение, и это МОЙ СОБСТВЕННЫЙ bash
                                    (3873140 /bin/bash -c … шаблон попал в argv проверяющего)
pgrep -fc 'codex .*app-server'   →  41
ps -eo args | grep -c 'node /usr/bin/codex .*app-server --stdio'   →  24   (обёртки = cli_pid)
ps -eo args | grep 'vendor.*bin/codex ' | grep -c 'app-server --stdio' → 24 (дети обёрток)
```

**Сценарий отказа, дословно по ранбуку.** Ночь, окно активации. Оператор выполняет шаг 2 «до
сигнала A» — `pre-A-inventory.txt` получается ПУСТЫМ (или содержит одну строку про его же
шелл). После рестарта A цикл `while read pid st; …` не делает ни одной итерации, строк
`UNRESOLVED` нет по построению. Ранбук говорит: «Пусто → гейт пройден». Оператор объявляет
активацию успешной, а 24 старых CLI могли остаться жить — и после #258 неопознанный сирота
**не убивается** (сигнал только по доказанной identity), то есть он останется висеть молча,
ровно как сам ранбук и предупреждает двумя абзацами ниже.

Ежесуточная проверка ломается симметрично и в ту же сторону: `pgrep -fc 'codex app-server'`
печатает 0–1 при 24 живых процессах. Ранбук велит бить тревогу при «расхождении вверх», а
получается вечное расхождение ВНИЗ, про которое не сказано ничего, — то есть накопление сирот
не будет замечено никогда.

Это ровно тот класс, который в `CLAUDE.md` назван первым: проверка, дающая одинаковый вывод при
успехе и при провале, и врущая в сторону «дефекта нет». Стоила бы она одного дословного
прогона — правило «правишь документацию с командами → выполни её тело на живой системе»
существует и не было применено.

**Что нужно.** Шаблон, который (а) действительно матчит наши процессы, (б) не матчит сам себя,
(в) явно решает, считает он обёртки (`cli_pid`, их 24), детей (тоже 24) или оба семейства —
иначе ежесуточное сравнение «процессы против числа codex-сессий» будет расходиться вдвое даже
после починки. Плюс положительный контроль в самом ранбуке: инвентарь обязан быть НЕПУСТЫМ до
сигнала, иначе гейт не пройден, а не пройден вхолостую.

Severity: **blocking** — но только для ранбука, код не затронут. Если оркестратору удобнее,
это чинится одной строкой отдельным коммитом и мержится вместе; блокировать мерж КОДА этой
находкой оснований нет, блокировать ОКНО — есть.

# Suggestions

### S-a. Достаточность бюджета сторожа держится на трёх незаписанных фактах
`app/routes/system.py:1766-1767`. Комментарий обосновывает 120 с как «fleet quiesce + store +
the outcome write». Но внутри попытки, ДО начала отсчёта дренажа ходов, лежит ещё
`drain_mutating_requests` с бюджетом 120 с (`app/main.py:53`) — арифметически
`0.5 + 120 + 900 = 1020.5` уже больше `_ADMISSION_WATCHDOG_S`. Спасает только то, что этот
второй дренаж мгновенен (`/api/restart` в `_CENSUS_EXEMPT_PATHS`, приём закрыт префлайтом).
Либо вывести бюджет как `_DRAIN_DEADLINE_S + MUTATING_DRAIN_BUDGET_S + margin`, либо назвать
эту зависимость в комментарии. Сейчас изменение `MUTATING_DRAIN_BUDGET_S` или появление
второго не-exempt мутирующего пути молча вернёт B2.

### S-b. Отмена сторожа не покрыта ни одним оракулом
`app/routes/system.py:1918`. Доказано мутацией M5: no-op вместо всей функции → `65 passed`.
Ветку «попытка отказала → сторож снят» я проверил пробой, но в замороженном наборе её нет.
Достаточно теста, который прогоняет `restart_server` с быстрым отказом и бюджетом сторожа
меньше времени наблюдения, и требует ровно одного `_abort_restart`.

### S-c. Инвариант «quiesce вернул False ⇒ не квиесцирован» нигде не записан, а он несущий
`app/manager.py:2216-2225`. Обе ветки выхода вызывающего (`if not await quiesce()` и
`except Exception`) не возобновляют backend. Это корректно ровно потому, что
`quiesce_for_handover` сама гарантирует: False = либо флаг не ставился, либо уже вызван
`resume_after_aborted_handover`. Одна строка комментария у `quiesce_for_handover` (и,
по вкусу, `assert not self._handover_quiescing` перед обоими `return False`) закрывает целый
класс будущих регрессий — именно этот инвариант и был сломан в B1.

### S-d. Инвентарь в ранбуке и его описание в отчёте расходятся
`report.md` («First activation») требует снять `(pid, /proc starttime, argv)`; команда в
`window-runbook.md:47-52` пишет только `(pid, starttime)`. Argv — единственное, что позволит
отличить сироту-обёртку от сироты-бинаря при разборе. Мелочь, но чинится в той же строке, что
и R2-B1.

# Что проверено и претензий не имеет

- Удаление `abort_handover` — полное: ноль вхождений в `app/`, `tests/`, `scripts/`.
- `_rollback_handover` идемпотентен: `rollback_restart_handover` сначала обменивает
