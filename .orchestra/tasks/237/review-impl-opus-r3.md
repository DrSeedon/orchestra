# Blocking

### B1. Шаг 4 ранбука требует `cli_pid`, которого в этот момент не существует ни у кого

`docs/tasks/237/window-runbook.md:121-127`:

> Требуется одновременно: `STARTED` на диске, `status=running`, `backend_type=codex`,
> **непустой `cli_pid`**. Записать `cli_pid` и его `/proc` starttime:
> `PID=<cli_pid>; echo "$PID $(awk '{print $22}' /proc/$PID/stat)" > …/subject-identity.txt`

Колонка `sessions.cli_pid` пишется РОВНО одним вызовом — `save_handover_state`
(`app/db.py:2783-2794`), единственный вызывающий `app/manager.py:2233` внутри
`_hand_over_backend`. То есть она заполняется только В ХОДЕ передачи, уже после сигнала на
рестарт. Шаг 4 исполняется ДО сигнала B и по построению видит ноль.

Живой замер сейчас (read-only копия боевой БД):

```
$ sqlite3 'file:…/orchestra.db?mode=ro' \
  "SELECT COUNT(*), SUM(CASE WHEN cli_pid IS NOT NULL AND cli_pid!=0 THEN 1 ELSE 0 END)
     FROM sessions WHERE finished_at IS NULL;"
46|0
```

46 живых сессий, непустых `cli_pid` — **ноль**.

**Сценарий отказа.** Ночью, в затишье, оператор доходит до шага 4. Обязательное разрешающее
плечо («требуется одновременно») не выполняется никогда: `cli_pid` = 0. Дальше два исхода, оба
плохие:

* оператор останавливается — окно затишья, которого ждали с 13.08 и которое зависит от сброса
  пула Codex 20.08, потрачено впустую;
* оператор идёт дальше и подставляет `PID=0`. Тогда `subject-identity.txt` содержит `0` и пустой
  starttime, а шаг 6 признак 2 (`awk '{print $22}' /proc/$PID/stat 2>/dev/null`) печатает
  пустоту при любом исходе рестарта. Это ложное отрицание в сторону «CLI не выжил, механизм не
  работает» — ровно та проверка, которая даёт один и тот же ответ независимо от истины, и
  единственный признак, ради которого весь замер B и затевался.

**Отдельно: ранбук противоречит сам себе.** На строках 207-212 того же файла этот факт записан
дословно и правильно — «колонка пишется только при передаче … в покое она нулевая у всех», и
именно поэтому проверка по `cli_pid` СОЗНАТЕЛЬНО выброшена из суточного блока. Автор применил
находку к суточной проверке и не применил к шагу 4, где она несущая.

**Минимальная правка, закрывающая блокер** (проверена на живой машине, разрешающее плечо есть —
на существующих агентах команда даёт ровно один pid): брать identity из `/proc`, а не из БД.

```bash
W=/home/kesha/orchestra/worktrees/home-kesha-orchestra/seamless237
PID=$(python3 scripts/cli-inventory.py snapshot | awk '$3=="node"{print $1}' \
      | while read p; do [ "$(readlink /proc/$p/cwd)" = "$W" ] && echo "$p"; done)
test "$(echo "$PID" | wc -w)" = 1 || { echo "ОТКАЗ: субъект не опознан однозначно"; }
echo "$PID $(python3 scripts/cli-inventory.py snapshot | awk -v p="$PID" '$1==p{print $2}')" \
  > /home/kesha/orchestra-scratch/237/liveB/subject-identity.txt
```

Проверка на живых агентах (`feat-runtime-switch`, `quota-policy`, `quota-routing`): у каждого
ровно пара процессов с cwd = его worktree, верхний из пары — `node` (это и есть `backend.pid`,
тот же процесс, который целит `terminate_cli_process`). Из требований шага 4 убрать «непустой
`cli_pid`»; `STARTED`, `status=running`, `backend_type=codex` оставить — они выполняются
(запрос из шага 4 исполняется, `exit=0`).

### 2. Тест на отмену сторожа — краснеет в ОБЕ стороны

`tests/test_hot_apply.py:503-556`. Прогнал ровно ту пробу, которую просил оркестратор, плюс
зеркальную:

| мутация `_disarm_watchdog_if_aborted` | результат |
|---|---|
| целиком no-op (`return` первой строкой) | **`1 failed`** — `test_guard_aborted_attempt_disarms_its_watchdog_but_a_signalling_one_does_not` |
| безусловный `watchdog.cancel()` в начале | **`3 failed`** — тот же охранник + `test_t6_admission_reopens_if_the_restart_never_happens` + `test_t9_…` |

В раунде 2 первая из этих мутаций давала `65 passed`. Дефект первой версии теста, о котором
пишет автор, действительно снят: двойник висит на `sleep(3600)` и не может завершиться до
отмены, а такт цикла после `.cancel()` дожидается перехода в `cancelled()`. Направление «успешный
сигнал НЕ снимает сторожа» покрыто второй мутацией — без него исчез бы единственный случай,
ради которого сторож существует.

Заодно: подмены в тестах переведены с `_ADMISSION_WATCHDOG_S` на `_watchdog_budget_s`
(`test_fd_adopt.py:1059`, `test_hot_apply.py:468,576`). Это существенно: `monkeypatch.setattr(…,
raising=False)` на исчезнувшее имя молча создал бы атрибут, и три теста ждали бы по 1140 с
вместо 0.01 — то есть висли бы, а не падали. Проверено, что имя действительно используется:
мутация формулы покраснила именно эти пути.

### 3. Инвариант «`False` ⇒ не квиесцирован» — признак наблюдаемый

`app/backend_jsonrpc.py:126-132` (докстринг) + `tests/test_seamless_restart.py:877-929`. Тест
после каждого отказа ПИШЕТ кадр в pipe со стороны CLI и ждёт, пока он доедет до
`_notifications` — это наблюдаемо и требует одновременно живого reader-таска и не поставленного
на паузу транспорта. По флагу такое не проверяется в принципе: флаг снимался и при живом
дефекте B1.

Мутация — восстановление формы B1 (в ветке отказа по сериализации заменить
`await self.resume_after_aborted_handover()` на `self._handover_quiescing = False`) → **`1
failed`**, маркер до 1, после отката 0, повтор зелёный (`16 passed`).

Оба отказных пути покрыты: путь 1 (незавершённый JSON-RPC запрос) возвращает `False` ДО любой
мутации состояния, путь 2 (несериализуемое событие) чинится через `resume_after_aborted_handover`.
Клауза инварианта про возврат перенесённых событий в очередь покрыта отдельно и раньше —
`tests/test_seamless_restart.py:681-693` проверяет порядок `[1, 2]` с недописанным кадром.

### 4. `scripts/cli-inventory.py` — на живой машине, три плеча

| плечо | команда | результат |
|---|---|---|
| разрешающее | `check` по снимку 40 живых | `checked 40 entries, 40 still alive`, **`exit=1`**, 40 строк `UNRESOLVED` |
| отрицательное | `check` по несуществующему pid | `checked 1 entries, 0 still alive`, `exit=0` |
| подделка | `check` по живому pid с чужим starttime | `checked 1 entries, 0 still alive`, `exit=0` |
| счёт | `count` | `processes=40 clis=20 survived_a_restart=0` |

Полнота матча по хвосту проверена независимо от скрипта: `ps -eo pid,args | grep -F "app-server
--stdio"` даёт те же 40 pid, и сверка хвоста `/proc/<pid>/cmdline` у каждого из них не дала ни
одного расхождения — то есть скрипт не пропускает ни одного процесса, который поймал бы поиск по
подстроке. Собственный шелл не ловится: хвост argv у проверяющего — текст скрипта. Прежний
`pgrep -f 'codex app-server'` перепроверил дословно: **1 совпадение**, блокер раунда 2 был
настоящим.

Разбор `/proc/<pid>/stat` в скрипте честный: `stat[stat.rindex(")") + 2:].split()[19]` — это
поле 22 (индекс 0 = state, поле 3), `_ppid` — поле 4. Оба устойчивы к пробелам и скобкам в
`comm`.

Единственная граница, которую стоит знать: скрипт видит только CLI Codex (хвост `app-server
--stdio`). Claude-агенты Orchestra под этот шаблон не попадают. Сейчас это не дыра — рестарт
передаёт только Codex, а Claude-ход рестарт БЛОКИРУЕТ (`_blocking_runtimes`), и на машине
прямо сейчас ни одного Claude-CLI Orchestra нет (два найденных `claude` принадлежат
`kesha-bot`). Но докстринг скрипта говорит «live agent CLI processes» шире, чем матчит; если
Claude когда-нибудь научится переживать рестарт, гейт останется к нему слеп молча.

# Вердикт

**BLOCKING — один блокер, снова в ранбуке, а не в коде.**

* **Код дельты — APPROVED.** Формула бюджета выведена из слагаемых, второго владельца нет,
  обе новые проверки краснеют на подсунутых им дефектах, обе — в обе стороны. Замечания S4/S5 и
  граница по Claude-CLI не требуют правок сейчас.
* **Ранбук исполнить дословно нельзя** из-за B1: обязательное разрешающее плечо шага 4 требует
  величины, которой в этот момент не существует ни у одной сессии, и при попытке пройти дальше
  превращает центральный признак замера в вечное «CLI не выжил».

**Минимальное изменение, закрывающее блокер:** в шаге 4 `window-runbook.md:121-127` убрать
требование «непустой `cli_pid`» и брать identity субъекта из `/proc` по cwd worktree (команда
выше, проверена на трёх живых агентах). Правки кода не требуется. Заодно дешёво закрыть F2
одной строкой (`MainPID` до B) — обе правки в одном файле и не трогают ничего исполняемого.
