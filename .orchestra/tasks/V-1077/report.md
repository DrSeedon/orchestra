# V-1077 — что из Agent Skills применимо к Orchestra

Исследование от 25.10.2026 UTC. Изменены только материалы этой задачи; skills, приложение, тесты, промпты и конфигурация не исправлялись. Модели, provider CLI, SSH и платные API не запускались. Число установок, размер skill и зелёные механические тесты здесь не используются как доказательство качества.

Практический вывод: сохранить существующие source owner и progressive loading; при отдельно согласованном улучшении взять парные evals с наблюдаемыми результатами и контроль обобщения исправлений. Не делать массовое переписывание семи skills, обязательное начало description одной фразой, механическое сокращение до размера или автоматическое пополнение gotchas.

**Host-gap закрыт полученной квитанцией root:** worker прочитал семь полных canonical pipeline-файлов и три references; root отдельно прочитал все семь destination `.codex/skills/*/SKILL.md`, все три references и полный `pipeline.yaml`. По [обезличенной квитанции](sources/host-readback.json#L1) destination-файлы совпадают с canonical/inventory побайтно, canonical 7/7 tracked, destinations 0/7 tracked, reference destinations также untracked; живой `CLAUDE.md` — симлинк на `AGENTS.md`. Хеши и роль-слияние сверены локально. Эти host-наблюдения получены от root, не изображаются повторным доступом worker к host. Фактическая активация моделью и A/B-качество не измерялись; coverage и ограничения перечислены в разделе 10. Дополнительный HOME/readback не нужен. Отсутствующие здесь manifest/symlink — свойства урезанной private copy, не регрессия продукта.

## 3. Что является контрактом

Обязательны каталог с `SKILL.md`, YAML frontmatter, непустые `name` и `description`. Имя 1–64 characters, lowercase alphanumeric/hyphen, без крайних и последовательных дефисов, совпадает с именем каталога. Description 1–1024 characters. Unicode допускается формулировкой текущего spec и проверкой `isalnum()`/NFKC в reference validator; правило поста про только латиницу строже. У наших семи имён эта неоднозначность не проявляется.

Опциональны `license`, `compatibility` (если задана — 1–500 characters), string→string `metadata`, экспериментальный `allowed-tools`. `references/`, `assets/`, `scripts/` и `evals/` не обязательны. В body нет обязательных названий разделов. Обязательного literal `Use when...` нет. Лимиты 500 строк и <5000 tokens находятся в рекомендациях по disclosure, не в проверке размеров body у pinned validator ([spec](sources/agentskills--agentskills--docs--specification.mdx#L216)).

`_read_skill_index_entry` Orchestra проверяет string/nonempty name/description и однострочное имя, но не 1024-character предел: offline проверены оба значения **1024 и 1025**. Это наблюдение границы helper, не автоматически дефект permissive discovery. Нужна отдельная авторская format-проверка, если её решат ввести; нельзя путать её с изменением runtime parser.

Особенность `grill-me`: top-level `roles` и `integrations` находятся вне ALLOWED_FIELDS pinned reference validator. Orchestra index их игнорирует; manifest владеет выбором ролей. Это конкретный portability gap при строгом validator, а не доказательство, что все CLI отвергнут файл или что эти поля реально активируют web-search.

## 4. Source owner и путь доставки Orchestra

1. Список skills роли — `defaults.skills` ∪ `roles.<role>.skills`, со значением `all`, поглощающим списки: [`_merge_list`/`resolve_role`](../../../app/pipeline.py#L532). Владелец — `pipeline.yaml`, не `roles:` внутри отдельного skill. Хотя manifest в копии отсутствует, его полный host readback теперь известен: effective counts **7/6/4/4/3** для orchestrator/sub-orchestrator/worker/full-cycle/reducer. Точные списки и отдельная проверка существующей функции слияния — в разделе 10; состав не выведен из ожиданий тестов.
2. Payload injector — [`_SKILLS_DIR`](../../../app/prompting.py#L24) в `.orchestra/pipelines/default/prompts/skills`. [`inject_skills_to_worktree_report`](../../../app/prompting.py#L356) превращает `<name>.md` в `<cwd>/.claude|.codex/skills/<name>/SKILL.md`, копирует `<name>/references/**`. `scripts/`, `assets/` и `evals/` этим helper не переносятся. Поэтому просто добавить evals рядом с canonical skill недостаточно для их доставки к агенту.
3. Project-owned tracked destination сохраняется, даже если отличается от canonical; symlink entrypoint/skill directory не затирается; Git error даёт безопасный отказ. `_copy_skill_file` использует временный файл и rename. `written` считает изменённые entrypoints, а не repaired references: **0 не означает, что references не обновлялись**. Это проверено поведением.
4. [`AgentSession._refresh_skills`](../../../app/session.py#L1787) вызывается перед connect; берёт `worktree_path or cwd`, `_SKILL_HOME_DIRS` допускает только Claude/Codex. `skills == all` означает оставить native discovery, а не скопировать все canonical файлы. Это отдельная семантика от `build_codex_skills_index(..., "all", ...)`, который glob-ит pipeline files для fallback.
5. Claude: [`_make_client` настройка](../../../app/backend_claude.py#L1212) выбирает user/project/local либо local по `inherit_claude_md`; `options.skills` не задаётся. Filesystem delivery не доказывает, что выбранные setting_sources и фактический SDK активировали файл. Здесь реальный CLI не проверялся.
6. Codex: native project discovery предполагается кодом; [`_codex_factory`](../../../app/runtime_registry.py#L214) по умолчанию не добавляет второй индекс. Ручной `ORCHESTRA_CODEX_SKILL_INDEX` или file-conflict fallback включает каталог. Автоматический fallback ограничен 16000 chars; validation profile его отключает. Самого discovery capability probe здесь нет.
7. В fallback [`_read_skill_index_entry`/`build_skills_index`](../../../app/prompting.py#L631) модель получает **имя + whitespace-normalized description + абсолютный путь**, не body и не references. Required pipeline metadata ломает построение при ошибке; optional project metadata пропускается с предупреждением; совпадение name сохраняет первый required entry. Дополнительные project files берутся из **tracked clean HEAD `.claude/skills`**, см. [`_project_skill_files`](../../../app/prompting.py#L679). Это отдельная precedence от native CLI. Canonical fallback path ведёт на `<name>.md`: контекст references с соседним `<name>/references` требует внимания при исполнении; реальное разрешение моделью здесь не проверено.
8. Hub не наследует эту доставку автоматически: [`BLOCKED_DIRS`](../../../app/hub_workspace.py#L80) исключает `.claude/.codex/.grok`; [`plan_upload`](../../../app/hub_workspace.py#L377) дополнительно ограничен scope и checked-out files. [`hub_preamble`](../../../app/backend_hub.py#L74) строит сокращённый worker prompt, а не переносит весь pipeline. Generic host skills этого T3 thread — отдельный provider/hub слой, их наличие не доказывает перенос семи repo skills. Canonical `.orchestra/...` может прийти как scoped source (как в этой задаче), что ещё не есть discoverable skill.
9. Grok/Harness не входят в `_SKILL_HOME_DIRS`; их factories не вызывают этот injector/index. Из этого можно утверждать отсутствие **данного механизма**, но нельзя утверждать отсутствие любой другой поддержки в их внешнем runtime. Наличие пустого `skill_index` в history schema — тоже не свидетельство активации.

Следствие для переданного HOME-наблюдения: шесть отсутствующих глобальных файлов и отличающийся глобальный `laptop-access` **не определяют действующий источник**. Host receipt подтверждает project-local файлы и их ownership; поддерживаемый кодом owner здесь согласуется с наблюдением, а оснований исправлять глобальный HOME нет. Наличие файлов всё ещё не заменяет наблюдение native catalog/активации.

## 7. Три конкретных примера, включая контрпример

**HTML: conditional reference уже есть, но исполнимая инструкция указывает неверный источник.** [`html-artifacts.md:151`](../../../.orchestra/pipelines/default/prompts/skills/html-artifacts.md#L151) ведёт в animation только для нужного вида объяснения. В [`animation.md:20`](../../../.orchestra/pipelines/default/prompts/skills/html-artifacts/references/animation.md#L20) `awk` извлекает fenced scaffold из `<path-to-this-SKILL.md>`, хотя fence хранится в **reference**. Offline запуск той же программы на canonical entrypoint даёт **0 bytes**, на reference — **11236 bytes** ([inventory](inventory.json#L161), `test_animation_extraction_observed_source_mismatch`); root отдельно повторил эти результаты на host и включил в квитанцию. Это конкретный дефект пути, а не оценка качества prose; Git-история переноса здесь недоступна, причина возникновения не доказана. Кандидат исправления — указать путь к reference и проверять непустой runnable output; ничего не исправлено в рамках research-only.

**Laptop: возможный split, но не вырезание диагностик.** В 132 строках соединены исполнимый маршрут, authority boundary и датированный список каталогов. Последний нужен при поиске конкретного checkout, а не при проверке соединения; его можно изучить как кандидат на conditional reference. Сохранить различия `ss` success+empty / failed check, refused/timeout / permission denied: от одного отказа нельзя вывести sleep или разрешение restart. Команды и домашние каталоги владельца не проверялись и не выгружались; source snapshot не выдаётся за live state. Механический delivery test подтвердил, что обе project-local копии получают canonical bytes, **не** что SSH работает или global HOME сломан.

**VPS deploy — контрпример размерной оптимизации и автоматическим gotchas.** Этот файл всего 55 строк, но оставшиеся строки задают точную авторизацию, ff-only, сохранность чужих правок, проверку нового PID и recovery после restart. Убирать их потому, что агент якобы и так знает systemd, нельзя. Root rules дополнительно владеют текущей политикой idle watcher; skill не расширяет полномочия. В этой задаче ни один такой маршрут не запускался. Отрицательное условие будущего eval — вопрос о необходимости рестарта после merge не должен превращаться в действие; наличие `active` без нового PID/health/recovery не доказывает завершённый restart.
