# V-981 — Auto Mode classifier и Jev

## Вердикт

Новость в основном подтверждена: `CLAUDE_CODE_AUTO_MODE_MODEL` появился в Claude Code 2.1.302 и выбирает модель **клиентского** Auto Mode classifier. Это не переключает server-side review и не является универсальным API-плагином. `autoMode.classifyAllShell` тоже поддерживается: в Auto Mode он отправляет shell-команды на проверку независимо от узких allow-правил, добавляя проверку/задержку на каждый shell-вызов.

Jev нельзя подставить в переменную напрямую: Claude Code ожидает полный model ID, который умеет обслужить текущий provider; TypeSafe Jev принимает отдельный типизированный запрос `POST /v1/systemone` и не реализует протокол модели Claude Code. Для связки потребовался бы самостоятельный adapter или интеграция за gateway, а также новый платный API-класс. Такой путь не исследовался и не запускался.

## Что проверено локально

- Глобально установлен Claude Code 2.1.303; отдельный локальный canary-каталог содержит 2.1.304. В bundle обеих версий найдены строки `CLAUDE_CODE_AUTO_MODE_MODEL` и `classifyAllShell`.
- `/home/kesha/.claude/settings.json` существует, но `permissions.defaultMode` не задан и блока `autoMode` нет. Активную интерактивную сессию и значение `Auto mode server` через `/status` не проверял.
- Orchestra создаёт `ClaudeAgentOptions` с `permission_mode="default"` и собственным `can_use_tool=_make_auto_approve(...)`; этот callback разрешает вызовы, кроме локально заблокированных инструментов. Bash дополнительно проходит собственный `PreToolUse` классификатор в `backend_claude.py`. Поэтому Auto Mode classifier не является текущим контуром разрешений воркеров Orchestra, и настройка его модели сама по себе не заменит наши правила.
- В исследовании V-639 уже проверялся Jev как закрытый hosted API для типизированных вопросов (`noul`, `choice`, `score`), не генеративная модель. Реальное качество классификации для нашей конкретной задачи там не измерялось.
- Никакие настройки не изменялись; запросы к TypeSafe/Jev не отправлялись и платные вызовы не делались.

## Что именно делают настройки

Официальные release notes Claude Code 2.1.302 сообщают, что `CLAUDE_CODE_AUTO_MODE_MODEL` меняет модель, используемую клиентским Auto Mode classifier, но не меняет server-side Auto Mode. В официальной документации переменная задаётся полным model ID; если провайдер не поддерживает выбранную модель, проверки classifier завершаются отказом и действие блокируется. Поддерживается диагностика по `classifier_request_started` в debug-логе. Документация также называет случаи, когда выбранная модель игнорируется: среди них Opus 5 / Sonnet 5.5 / Opus 5.5 и запрет модели организационной политикой.

`autoMode.classifyAllShell: true` при включённом Auto Mode приостанавливает все Bash и PowerShell allow rules, чтобы classifier проверял команды вместо немедленного разрешения по allowlist (кроме критических удалений, которые идут по отдельному пути). Официальная документация прямо предупреждает о дополнительной задержке и о том, что каждый shell-вызов становится classifier call. Это расширяет покрытие, но не превращает classifier в детерминированный механизм и не удаляет обязательные правила `permissions.ask`/`deny`.

Соннет 5 — обычная модель classifier по умолчанию, независимо от выбранной через `/model` модели, с провайдерными/организационными исключениями и fallback. Поэтому первая часть пересланного сообщения правильная. Изменение переменной относится к клиентской проверке; когда сессию обслуживает server-side review, переменная её не перенастраивает.

## Jev и стоимость

Официальный Auto Mode интерфейс не обещает совместимость с произвольной моделью через внешний decision API: переменная задаёт model ID для Claude Code, а Jev принимает структуру `state + questions` на `api.typesafe.ai/v1/systemone` и возвращает структурированные ответы. Это разные контракты и семантика: простой проброс `jev-latest` не делает Jev backend для Claude Code. Нужен адаптер, который преобразует запросы classifier в TypeSafe typed decisions, а также экспериментальная оценка безопасных разрешений/блокировок; цена и качество такого решения пока не установлены.

TypeSafe является внешним hosted API. В V-639 зафиксирована заявленная стоимость на момент исследования, но текущий тариф здесь повторно не проверялся и в расчёт не включён. Любой вызов с TypeSafe API потребует отдельного согласования нового платного расхода. Без отдельного разрешения предложение остаётся исследовательской идеей.

## Рекомендация

- **Брать переменную как штатную настройку для выбора поддерживаемой модели** — только если есть конкретная Claude-модель, доступная используемому provider, и сессия использует клиентский classifier. Для Orchestra workers практической пользы сейчас нет: их решения проходят через собственные callbacks/hooks.
- **Рассмотреть `classifyAllShell` для интерактивного Auto Mode** как усиление покрытия, если владелец хочет, чтобы команды не проходили только по narrow allow rules. Цена — дополнительный classifier вызов/задержка на каждую shell-команду; настройка не включалась и не измерялась.
- **Не брать Jev как drop-in classifier.** Для реальной интеграции нужен adapter/gateway и новый API-расход; пользы на наших данных пока не показано. Никакой платной пробы не проводил.
