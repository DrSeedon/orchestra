# V-576 — один каталог проектов вместо двух слоёв: как сделать и где схема ломается

Исследование, 15.09.2026. Продуктовый код не менялся, боевая БД читалась read-only
(`sqlite3 -readonly "file:/home/kesha/orchestra/data/orchestra.db?mode=ro"`, путь взят из
`/proc/1016880/environ` живого процесса). Orchestra и telegram-bot-api не трогались.
`app/routes/sessions.py` не правился (в параллели #V-575).

---

## 0. Ответ одним абзацем

Сущностей не две, а три, и «портфель» — не вторая из них, а третья, мёртвая.
Реально работают: **scope сессии** (путь на диске) и **namespace задачи** (`project_id`
внутри Git-хранилища задач, оно же `tm_projects.canonical_id`). Портфель
(`portfolio_*`, 9 таблиц, 1919 строк кода, 1844 строки тестов) за всё время своего
существования не получил **ни одного** вызова `project_goal`/`project_wait` в проде и
содержит 0 проектов, 0 целей, 0 ожиданий — это чистое удаление, а не миграция. Но вместе
с ним сносится `notify_user`, который **живой** (17 вызовов, последний 11.09), потому что
его durable-путь лежит внутри `app/portfolio.py`. Каталог файлом — правильное решение и
он получается почти даром: сегодня `tm_projects` **уже** не источник истины, а проекция,
которую машина пересобирает из Git-репозитория задач. А вот «у задачи список тегов вместо
проекта» ломается на измеренном факте: **424 ссылки вида `#N` конфликтуют внутри
предлагаемых тегов, это 857 задач из 1755 (48.8%)** — номер задачи уникален только в паре
с namespace. Вывод: namespace остаётся (невидимый, неизменяемый, выдаёт номер), теги
ложатся поверх него как отдельный слой без полномочий. При таком разделении миграция
задач не нужна вообще — ни один файл задачи не переписывается, `V-575` остаётся `V-575`.

## 2. Проверка двух «жёстких» ограничений

### (1) «Счётчик обязан остаться в SQLite, иначе два агента получат один номер» — **опровергнуто**

Счётчика в SQLite нет и не было. В `app/` ровно три `INSERT INTO tm_tasks/tm_projects`
(`app/task_runtime.py:65,97`, `app/tm.py:211`) — все проекционные, ни один не вычисляет
номер. Номер выдаётся в `app/task_store.py:233` как `max(...)+1` по JSON-файлам, под
`flock` (`:108-124`), и результат фиксируется git-коммитом раньше, чем SQLite вообще
увидит задачу.

Требование за ограничением — **настоящее**: два агента не должны получить один номер. Оно
уже выполняется, просто другим механизмом. Перенос счётчика в SQLite не нужен и был бы
регрессом: он сломал бы синхронизацию с ноутбуком (номер должен переживать `git merge`
чужих задач, `app/task_store.py:316-321`).

Побочный факт, который надо знать: `flock` гарантирует уникальность **внутри пары
(проект, origin)**, а не глобально. Отсюда следует всё, что в §3.

### (2) «`task_create` без аргументов знает проект из scope, подстановку надо сохранить явно» — **подтверждено**

`app/tm.py:1594-1612`: пустой `project_id` → `_project_for_session_scope(conn, scope)` →
проект обязан иметь непустой `scope`, иначе ошибка со списком разрешённых. Это единственное
место подстановки, и оно же — единственное место, где `tm_projects.scope` работает как
допуск («какие проекты вообще могут принимать новые задачи»). При переходе на теги обе
функции надо сохранить явно, и каталог — естественный их владелец:
`scope → write_namespace` (куда пишем номер) и `scope → default_tags` (чем помечаем).

## 3. Где предложенная схема ломается

### 3.1 Главный слом: номер задачи не переживает слияние проектов в тег

Измерено по боевой БД. Если склеить историю одного человеческого проекта в один тег:

| тег | конфликтующих ссылок `#N`/`V-N` | задач в конфликте |
|---|---|---|
| orchestra | **231** | 469 |
| seedon | **149** | 300 |
| comfy-image-pipeline | 20 | 40 |
| kesha-tg-bot | 13 | 26 |
| vpn-service | 8 | 16 |
| cog-second-brain | 2 | 4 |
| university | 1 | 2 |
| **итого** | **424** | **857 из 1755 (48.8%)** |

Это не теоретическая коллизия. `#1` в `/home/kesha/orchestra` — «Usage и Proxy-панель
скрыты на VPS…», `#1` в `git:orchestra` — «test». `#161` есть в обоих, и в теле задачи
`161` из `home-kesha-orchestra-8b68cd9600cc` лежит git-коммит с темой
`«#161: отказ фильтра опознаётся по телу события…»` — ссылка уже записана в историю git.

Отдельно: **`V-` тоже не глобален.** `V-1` существует в трёх проектах (dnd-game-master,
katya-work, seedon), `V-9` — в трёх (dnd-game-master, cog-second-brain, seedon), `V-2`…`V-8`
и `V-10` — в двух. `V-` — это не «VPS-нумерация», это `origin` записи; каждый проект ведёт
свой счёт `V-`. Требование «`V-575` обязан остаться `V-575`» выполняется только потому, что
`V-575` разрешается **через scope сессии**, а не сам по себе.

**Следствие, обязательное для любого варианта:** сущность, выдающая и разрешающая номер,
должна остаться ровно одна на задачу и не может быть списком. Тег списочный → тег не может
быть этой сущностью.

### 3.2 Второй слом: проект зашит в путь файла задачи

`app/task_store.py:147-148`: `projects/<project_id>/tasks/<uuid>.json`, и
`_validate_records` (`:178`) падает `«task identity does not match its file»`, если файл
лежит не там. Если «проект» становится списком тегов, файл теряет однозначное место. Любая
схема, где тег определяет расположение, требует перенести 1755 файлов и переписать
`_path`/`_validate`/`_records`/`_tree_records`/`sync`. Namespace, оставленный на месте,
делает эту работу нулевой.

### 3.3 Третий слом: форма записи задачи закрыта на точное равенство ключей

`app/task_store.py:61`: `if set(record) != required or record['schema_version'] != 1`.
Добавить в запись поле `tags` «просто так» нельзя: либо переписываются все 1755 файлов с
`schema_version: 2` (и ноутбук со старым кодом перестаёт читать хранилище — `_validate`
бросит исключение на всём), либо валидатор ослабляется до «обязательные ключи + явный
белый список необязательных». Второе дешевле и совместимо в обе стороны, но это осознанное
ослабление единственной проверки формы — назвать владельцу, а не протащить молча.

### 3.4 Четвёртый слом: «фантомные `git:*`» нельзя вычистить удалением строк

`git:orchestra` — 375 задач, `git:seedon` — 202, `git:scope-mnt-…-comfy` — 113,
`git:cog-second-brain-…` — 82. Это не мусор, это локальные привязки к каталогам Git-хранилища
(`app/task_runtime.py:58-67`). `DELETE FROM tm_projects WHERE id LIKE 'git:%'` вернёт их
обратно на первом же `refresh()` — и с **другим** случайным `prefix`. Мусор здесь — не сами
строки, а то, что автогенерация делает из canonical-id локальный id вместо того, чтобы
спросить каталог. Чинится каталогом, а не `DELETE`.

Настоящий мусор в этих 30 строках — 4 дубля-зомби: `Orchestra` (1 задача),
`orchestra` (5), `Seedon` (2), плюс `git:university` и `git:university-9d38443e2220` как
две половины одного университета. И отдельная ловушка: строка с id `orchestra` указывает на
canonical `vps-orchestra` (5 задач), а canonical `orchestra` (375 задач) висит на строке
`git:orchestra`. `resolve_project_selector('orchestra')` вернёт **не тот** проект, который
имеет в виду человек.

### 3.5 Пятый слом: снос портфеля уносит живой `notify_user`

`mcp__orchestra__notify_user` → `POST /api/portfolio/attention` (`app/mcp_stdio.py:2188-2190`)
→ `app/routes/portfolio.py:386` → `app/portfolio.py:1165` → `portfolio_attention_events`, а
`app/tg_bridge.py:188` читает событие обратно, чтобы отличить настоящий durable-тег от текста,
который модель могла сочинить. Вырезать портфель целиком, не тронув это, — значит уронить тул,
которым владелец пользуется.

### 3.6 Шестой слом: у SQLite нет пути миграции

`app/db.py:67-73`: если `user_version` не равен `SCHEMA_VERSION` и таблицы уже есть —
`RuntimeError('database schema needs offline migration before starting Orchestra')`.
Живая БД: `user_version = 1`, 9 портфельных таблиц. Значит `DROP TABLE` для них — это
**оффлайн-операция на остановленном сервисе**, а останавливать/перезапускать Orchestra может
только владелец. Дешёвая альтернатива в §7.

## 4. Минимальная схема, которая закрывает задачу

Три слоя вместо нынешних трёх, но с честным разделением полномочий.

### 4.1 `namespace` — остаётся, становится невидимым

Это сегодняшний `record['project_id']` (он же `tm_projects.canonical_id`). Ровно один на
задачу, неизменяемый, уже защищён `app/task_runtime.py:72-74` и `app/task_store.py:317`.
Его работа и только она:

* выдать номер (`max+1` под `flock`);
* разрешить `#N` / `V-N` обратно в задачу;
* определить путь файла задачи.

Человеку не показывается никогда. Выбирается один раз, при создании, по scope сессии.

### 4.2 Каталог — файл в `.orchestra/`

`.orchestra/projects.yaml` в репозитории Orchestra. YAML, потому что это уже формат
`pipeline.yaml` (`app/pipeline.py:18,428`), `pyyaml` уже в зависимостях
(`pyproject.toml:19`), и корень резолвится так же:
`Path(__file__).parent.parent / '.orchestra'` — у живого процесса это
`/home/kesha/orchestra/.orchestra/` (проверено: `cwd` процесса 1016880 = `/home/kesha/orchestra`).

```yaml
version: 1
projects:
  orchestra:
    name: Orchestra
    scope: /home/kesha/orchestra
    write_namespace: home-kesha-orchestra-8b68cd9600cc
    namespaces: [orchestra, vps-orchestra, orchestra-15ebb64920a9,
                 mnt-data-projects-python-orchestra-13dc8d0cd9fb]
  seedon:
    name: Seedon
    scope: /home/kesha/projects/seedon
    write_namespace: vps-seedon
    namespaces: [seedon, seedon-ab14b1ec414e]
  university:
    name: Университет
    archived: true
    namespaces: [university, university-9d38443e2220]
```

Правила файла, каждое со своей причиной:

* **ключ = тег.** Одно слово, оно же в UI, оно же в `task_list(tags=…)`.
* **`scope`** — необязателен и уникален. Есть → проект принимает новые задачи из этого
  каталога (замена `tm_projects.scope` как допуска, §2.2) и попадает в
  `_registered_project_roots()` вместо SQL-запроса `app/orchestra_layout.py:1144`.
* **`write_namespace`** — куда уходит номер новой задачи. Обязателен, если есть `scope`.
* **`namespaces`** — все остальные исторические пространства этого проекта, для показа и
  фильтра. Именно этот список убивает `git:*`: `app/task_runtime.py:58-67` больше не
  выдумывает локальный id, а спрашивает каталог.
* **`archived: true`** — проект не предлагается, задачи видны только по явному фильтру.

Полная таблица «30 namespace → 18 записей каталога» — в `namespace-map.md` рядом.
Сумма задач по ней сходится: 1755.

### 4.3 Теги задачи — и здесь самое дешёвое место

**Тег по умолчанию не хранится в задаче вообще.** Он вычисляется:
`tags(task) = catalog.tag_of(task.namespace)`. Для всех 1755 существующих задач это даёт
правильный тег без единой правки файла, без `schema_version: 2`, без переноса файлов и без
риска для `V-575`.

Хранить надо только *дополнительные* теги — ровно то, ради чего задача «может относиться к
нескольким проектам». Это необязательное поле `extra_tags: []` в записи задачи; у всех
существующих записей оно просто отсутствует. Валидатор `app/task_store.py:58-62` меняется с
`set(record) != required` на `required ⊆ set(record) ⊆ required ∪ {'extra_tags'}` — узкое,
явное, обратимое послабление (это и есть цена из §3.3, но в минимальном объёме).

В проекции: одна колонка `tm_tasks.tags TEXT NOT NULL DEFAULT '[]'`, заполняется в
`app/task_runtime.py:80-92` как «тег namespace + extra_tags». Фильтр —
`EXISTS (SELECT 1 FROM json_each(tm_tasks.tags) WHERE value=?)`; JSON1 в сборке есть
(проверено: `sqlite_version 3.45.1`, `json_each` работает и в CLI, и в `python3 -m sqlite3`).
Индекс не нужен: 1755 строк.

### 4.4 Что остаётся в БД и почему именно это

| Остаётся | Почему |

## 10. Что может оказаться дороже, чем кажется

1. **«Убрать теги из задачи» — не бесплатно, если поле попадёт в запись.** `extra_tags`
   пишется в JSON, а JSON лежит в git-репозитории задач: 174 МБ на 1755 файлов и 2313
   коммитов. Каждая правка тега — отдельный коммит с `fsync` и `flock` на всём хранилище
   (`app/task_store.py:265-299`), то есть блокирует создание задач во всех проектах на время
   записи. Пометить сотню старых задач задним числом = сто коммитов. Если теги будут править
   часто — хранить их в проекции, а не в записи.

2. **Синхронизация с ноутбуком.** `TaskStore.sync` (`:301-326`) делает `git merge` с
   `task-sync.git`. Пока на ноутбуке старый код, послабление валидатора должно быть
   **односторонне совместимым**: новый код читает старые записи (да), старый код читает
   новые (`set(record) != required` → **нет**, если там появился `extra_tags`). Практически:
   первая же задача с дополнительным тегом, доехавшая до ноутбука, положит ему всё
   хранилище целиком — `_validate_records` падает на первой битой записи и роняет `list()`.
   Либо теги не едут в записи (п.1), либо ноутбук обновляется раньше VPS.

3. **`tm_projects` выглядит изолированной, но её `scope` — допуск на создание задач.**
   `app/tm.py:1599`: проект без `scope` не может принять задачу. Если каталог по недосмотру
   не перенесёт `scope` для какого-то проекта, `task_create` в нём начнёт падать с
   «project is not registered» — и это заметят агенты в середине работы, а не тесты.
   Отдельно: `/home/kesha/projects/University` — живая сессия, scope есть, проекта в
   `tm_projects` нет; в каталоге его тоже не окажется, если генерировать каталог только
   из `tm_projects`.

4. **`resolve_task_ref` — узкое место, через которое проходит весь мерж.**
   `resolve_scoped_task_identities` (`app/tm.py:542`) разбирает номера из **сообщений
   коммитов** при `merge_worker`. Там уже есть шрам: `skip_unknown` появился после того, как
   коммит `#110` в проекте с нумерацией от `#3` уронил всю операцию с `NO_COMMITS_MERGED`
   и заблокировал трёх воркеров (комментарий `app/tm.py:551-558`). Любая ошибка в том, какой
   namespace достаётся сессии из каталога, воспроизведёт ровно этот отказ — не в списке
   задач, а в мерже.

5. **Снимок роутов под гейтом.** Удаление 21 роута меняет
   `tests/route_surface_snapshot.json`, а `app/merge_test_gate.py:102-107` требует прогона
   `tests/test_routes_surface.py` при касании этого файла. Это не проблема, но это
   обязательный прогон, который легко забыть запланировать.

6. **Фронтовый CSS не изолирован.** В блоке `style.css:1069-1334` первая же строка (`:1070`)
   — общее правило `#file-panel { transition: … }`, не портфельное. Удаление «блока целиком»
   сломает анимацию файловой панели.

7. **Цена «ещё раз спросить» выше цены ошибки в каталоге.** Каталог — 18 строк, которые
   человек пишет руками один раз. Если в нём перепутать `write_namespace`, новые задачи
   поедут в чужое пространство номеров, и откатить это будет нельзя: `number` неизменяем
   (`app/task_store.py:317`). Единственная защита — сверить каталог до шага 2, на живых
   данных (`namespace-map.md`).
