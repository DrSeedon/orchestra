# #239 — Инцидент 12.08.2026 — `orc.seedon.ru` не отвечал ~2 часа

**Статус:** решено (симптом снят). Причина-первопричина НЕ найдена — см. §5, это открытая работа.
**Кто расследовал:** локальный Orchestra-orchestrator (ноут) + Кеша (на Contabo).
**Для кого этот файл:** оркестратор Orchestra на VPS — чтобы не копать заново закрытое и взяться за §5.

## 1. Итог одной строкой

Uvicorn на Contabo задыхался в IO-голоде из-за 6 процессов `ugrep` (~8 ГБ RSS, load average 49.78
при 8 ядрах). Сеть и nginx-релей были ни при чём. После `pkill` — `/login` по loopback
**20 000 мс → 3.5 мс**.

опровергнут этим замером окончательно.

## 3. Что оказалось НЕ причиной (закрыто, не перепроверять)

- **Сеть / ТСПУ / фильтрация по SNI.** Опровергнуто: пробы с SNI `orc.seedon.ru`,
  с чужим SNI и вовсе без SNI вели себя одинаково; при этом TLS-хендшейк завершался
  полностью (сертификат `*.seedon.ru` валиден, ALPN согласован), а рвалось уже на
  прикладных байтах. Плюс контрольные TLS-хосты (`1.1.1.1`, `seedon.ru`) отвечали нормально.
- **Исчерпание nginx worker_connections.** Опровергнуто: 22 и 16 открытых fd при лимите 768,
  5 established-соединений. Насыщения не было.
- **Падение nginx на релее.** Опровергнуто: `nginx -t` успешен, `:80` и `:8080` отвечали
  мгновенно всё время инцидента.
- **Ребут сервера.** Не делали и не требовалось: хост был полностью доступен (SSH, `:80`, `:2053`).

## 4. Разгадка «Host-раскола» (важно — тут я ошибся, диагноз исправлен)

Симптом, который сбил с толку: на **один и тот же IP** Contabo в один момент времени
`Host: orc.seedon.ru` → 200 за 210 мс, а `Host: orchestra.seedon.ru` → таймаут.
Выглядело как «одно приложение в двух состояниях».

**Правильное объяснение (Кеша):** в nginx на Contabo **нет vhost для `orc.seedon.ru`**.
Есть только `orchestra.seedon.ru`. Запрос с первым Host падает в default server и получает
мгновенный 404/200 от самого nginx — **до Orchestra он не доходит вообще**. Второй Host —
единственный маршрут, реально идущий в uvicorn, потому только он и стоял.

Два Host = два разных vhost, а не один сервер в двух настроениях. При IO-голоде и должен
был стоять ровно один — тот, что ходит в бэкенд.

## 5. ОТКРЫТО — кто плодит `ugrep` (главное, что осталось)

Симптом снят, причина жива и повторится.

**Известно:**
- 6 процессов `ugrep`, старшему **49 минут**, один жрал **3.3 ГБ** — на grep по одному
  файлу `oai_sol_card.md`. 49-минутный grep по одному `.md` — это не «долгая задача», это
  утечка/патология в чьём-то тулинге.
- Рядом крутилось 16 процессов Codex.

**Проверено в локальном контуре (ноут), чтобы сузить поиск:**
- `grep -rn "ugrep" app/ scripts/ pipelines/` → **пусто**
- `ugrep` в скиллах, `CLAUDE.md`, `docs/`, `.codex/`, `.claude/` → **пусто**
- `which ugrep` на ноуте → **не установлен**
- `oai_sol_card.md` локально → **не найден**

Вывод: источник **не в нашем локальном коде и не в наших промптах**. Искать надо на самом
Contabo — кто именно порождает `ugrep` (кандидат №1: тулинг Codex/Sol-воркеров, т.к. рядом
16 процессов Codex и файл `oai_sol_card.md` похож на артефакт карточки модели OpenAI).

**Что сделать на VPS:**
1. Найти живой источник: `pgrep -a -x ugrep`, затем по PPID подняться до родителя
   (`ps -o ppid,cmd -p <pid>`) — чей это процесс, какого агента/воркера.
2. Проверить, не идёт ли `ugrep` из MCP-сервера (например, serena/индексатора) или из
   собственного тулинга Codex-рантайма.
3. Поставить дешёвый предохранитель: лимит по времени/памяти на такие вызовы, иначе
   через неделю повторится.

## 6. Побочные наблюдения (не причина, но чинить стоит)

- **Polling-шторм:** московский релей долбит `/api/logs/sync` по 6 раз в 5 секунд. Сам по себе
  не причина, но добавлял нагрузку в момент, когда сервер уже задыхался.
- **Цикл рестартов `telegram-bot-api`:** Orchestra перезапускала его, т.к. health-probe не
  проходил по таймауту — следствие перегруза, а не причина.
- **`https://orchestra.seedon.ru/` снаружи → 404** — это конфиг релея, отдельно от нагрузки.
- **Косяк при зачистке (Кеша):** `pkill -f "ugrep -G"` заодно прибил собственный bash —
  паттерн совпал с командной строкой шелла. Правильно: `pkill -x ugrep`.

## 7. Методологический урок (стоил ~2 часов)

Три раза за расследование я измерил **прокладку** и отчитался за **пункт назначения**:

1. Первые пробы шли через `HTTPS_PROXY` — TCP-коннект «к удалённому IP» за 0.14 мс
   (физически невозможно) вскрыл, что мерю прокси.
2. «404 за 287 мс → ориджин жив» — это была собственная страница nginx-релея, 162 байта.
   До uvicorn запрос не доходил.
3. «200 OK за 210 мс на `Host: orc`» — снова ответ nginx за себя (см. §4).

Общее у всех трёх: **код ответа + латентность подделывает любая прокладка**. Живость бэкенда
доказывает только байт, который может произвести ТОЛЬКО бэкенд.
