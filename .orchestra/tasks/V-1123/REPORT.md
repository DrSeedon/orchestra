# V-1123: isolate quota admission collection from SQLite

Изменения приняты после проверки оркестратором в полном worktree. Сбор и параллельный
прогон прошли; новая регрессия падает при возврате исходного e2e-модуля. Ниже сохранены
ограничения первоначальной source-only проверки, затем результаты host-приёмки.

## Изменение

- `tests/test_quota_admission_e2e.py`: вычисление константы Claude явно передаёт
  `policy_history=[]`. Существующий API `line_limit` использует пустую историю
  без вызова `_claude_policy_history` / SQLite. Временное окно, текущая политика,
  пороги обеих сторон, тела тестов и их реальные DB/pipeline-фикстуры сохранены.
- `tests/test_quota_admission_collection.py`: отдельный процесс выполняет настоящий
  `pytest --collect-only` исходного e2e-модуля. Python audit hook запрещает каждую
  попытку `sqlite3.connect` до открытия БД; список попыток проверяется даже если
  приложение подавит исключение. Проверяются успешный сбор и присутствие тестов
  допуска выше/ниже линии. Функции приложения и SQLite не подменяются.
  Свежий процесс исключает ложный успех из-за кеша импортов. Вложенная collection
  явно использует `-n0`, чтобы аудит оставался в процессе, выполняющем collection;
  внешний прогон `-n2` не меняется.
- `app/quota_gate.py`, `app/db.py`, production DB guard, hub-only guard V-1119,
  политики квот и CHANGELOG не менялись.

## Фактическая проверка

Использован предоставленный uv **0.11.28**, CPython **3.12.3**, стандартная `.venv`,
не системный uv-диспетчер и не другой интерпретатор. Установка 76 зависимостей
из frozen lock прошла успешно. Подмены отсутствующих модулей не делались.
Импорт `app` даёт namespace package этой копии; импорт `app.quota_gate`
останавливается на отсутствующем `app.models`.

В каждой оболочке тестов устанавливались:

```sh
export PATH="$HOME/.local/share/orchestra/tools/uv/0.11.28/bin:$PATH"
export TMPDIR="$PWD/.orchestra/tasks/V-1123/scratch"
```

Ниже общая часть команды: `uv run --frozen python -m pytest`.
Каждому прогону также передан отдельный `--basetemp` внутри `scratch`.

не воспроизведена; детерминированный RED/GREEN новой регрессии тоже не получен.

## Что передавалось на проверку в полной копии

- Новая регрессия должна падать на исходном e2e-модуле именно из-за audit-события
  SQLite и проходить после добавления пустой истории. При RED аудит блокирует
  соединение до доступа к данным, поэтому не требуется трогать общую БД.
- Повторить collection и обычный прогон обоих модулей, включая `-n2`, со всеми
  исходниками `app`, настоящим default pipeline и его prompts. В этой копии
  `.orchestra/pipelines/default` также отсутствует.
- Проверить реальные тела допуска с временной БД и существующие проверки истории
  квот / production DB guard. Их поведение и восстановление старых данных здесь
  не проверены. Изменение не касается формата БД, WAL, блокировок или восстановления.

Не следует принимать ошибки импорта за исходный CI-дефект или заявлять, что CI
исправлен, до прогона в полной копии. Сервисов, живой БД, env-файлов, токенов,
моделей и платных вызовов задача не касалась.
