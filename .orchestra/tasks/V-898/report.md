# V-898: Hy Memory 2.0 (Tencent Hunyuan) — разбор по первичным источникам

Класс B, только чтение. Модель не скачивалась и не запускалась; запрошены только метаданные HF/GitHub API и тексты README/docs/arXiv. Дата проверки 2026-10-16, релиз вышел 10.2026, так что всё ниже — свежие данные без отзывов сообщества (у модели на HF 0 скачиваний, 23 лайка).

## 1. Что реально выпущено

Три разных артефакта в одной лицензии (Apache-2.0 для кода и для весов; сторонние компоненты — со своими лицензиями; ограничений на коммерцию нет).

### 1.1 SDK `hy-memory==2.0.1` (каталог `hy_memory/`, ~139 файлов)

Это не «модель с памятью», а Python-движок, которому нужны два внешних OpenAI-совместимых эндпоинта: LLM и эмбеддер (`MEMORY_LLM_*`, `MEMORY_EMBEDDER_*`). Модель памяти — одна из подставляемых LLM.

- Что извлекается (сцена `chat`, иерархия L0–L7): L1 сырой диалог (append-only), L2 атомарные факты (версионируемые, неизменяемые), L3 сводки сессий, L6 схемы («ментальные модели», в графе), L7 намерения с TTL (по истечении разжалуются в обычные факты). L4/L5 зарезервированы. Режимы: `lite` — чистый векторный RAG без LLM; `pro` — LLM-извлечение + reconcile; `ultra` — плюс «System 2» (индукция схем и cross-domain sweeper по вызову `evolve()`).
- Сцены `working` и `coding`: из сессии с tool-call трассой получается ровно 1 факт (что сделано) плюс 0..N «опытов» (experience: task, search_keys, solution, boundary_envs, confidence), прошедших порог ценности; факты и опыты перекрёстно связаны. В `coding` дополнительно «diff chain» (`hy_memory/coding/chain_store.py`): реальные диффы каждой версии кода хранятся без LLM — аргумент авторов: откатанная версия не лежит ни в HEAD, ни в факте.
- Хранение: ChromaDB по умолчанию (Qdrant/FAISS опционально), граф Kuzu (Neo4j опционально), метаданные working/coding в SQLite, опциональный MySQL-кэш.
- Достаётся: `search()` отдаёт каналы profile/normal/proactive; `default` — без LLM-вызовов, `agentic` — классификация сцены, переписывание запроса, разбор временного окна; кандидаты — вектор + BM25 (аддитивное слияние); опциональный локальный cross-encoder rerank.
- Кто решает, что забыть: решает LLM-reconciler (`hy_memory/agent/reconciler.py`). Для каждой новой записи ищутся кандидаты (вектор+BM25, min_score 0.4), одним LLM-вызовом выдаются операции `ADD` (с `supersedes=[id]` — запись о противоречии уходит в «цепочку эволюции») и `DELETE` (логическое: `status=SHADOW, is_latest=False`, «слияние-поглощение»). Физического забывания/затухания по времени нет; единственный срок годности — TTL у L7. Данные не удаляются, а перестают возвращаться.

### 1.2 Модель Hy-Memory-30B-A3B

- `HYV3ForCausalLM` (`hy_v3`), MoE 30,06 B параметров / ~3 B активных, hidden 2048, контекст 262 144, 51 шард safetensors, **60,1 ГБ** (BF16 + немного F32). Квантованных версий у авторов нет, на HF их ещё нет (поиск «Hy-Memory» → один репозиторий, 0 скачиваний). Заявленный способ запуска — vLLM 0.31.0 / SGLang в Docker; требований к железу не указано.
- Роль: «писатель» памяти — заменяет LLM внутри Mem0, MemOS, Hy-Memory (то есть выполняет extract + reconcile по протоколу каждого фреймворка). Не ретривер и не отвечающая модель.
- Обучение (arXiv 2610.22196, 15.10.2026, 128×H20): (1) on-policy distillation протоколов записи, (2) RL «attributed» — плотные пробы ответимости по чанкам, межчанковая атрибуция награды, штраф за over-storage, GRPO.

### 1.3 MemHub (`memhub/`, v1.0.0, ~1500 файлов, Electron + FastAPI + SQLite, npm `memhub-cli`)

- Локальный демон («Runtime») + CLI (`memhub serve/install/doctor/…`) + Web UI + Electron. В релизе v1.0.0 лежат: macOS arm64 DMG (318 МБ), Linux x64 zip (263 МБ), Linux arm64 zip (257 МБ). Windows нет. Linux ставится как systemd user service.
- Поток: `Evidence (сырой источник, сохраняется до обработки) → Hy Memory → Governance → Matters/Wiki`. Разрешения разделены на три границы: чтение источника, отправка содержимого модели, чтение памяти хостом. Есть версионирование, коррекция и каскадное удаление.
- «10+ инструментов» — по `memhub/docs/harness-support/README.md` их 10 строк: Hermes, Cursor, Claude Code, Codex, WorkBuddy, OpenCode, Qwen Code, Pi, OpenClaw (заморожен, не работает), DeepSeek Harness (исключён, баг). Реально открыты 8.
- Как цепляется (на примере Claude Code, `claude-code.md`): запись MCP-сервера `one-memory` в `~/.claude.json`; skill `~/.claude/skills/memhub-recall/SKILL.md`, говорящий модели когда звать; три capture-хука в `~/.claude/settings.json` (`UserPromptSubmit`, `Stop`, `SubagentStop` → `one-memory capture claude-code`); плюс фоновое сканирование `~/.claude/projects` (история сессий). Codex — TOML MCP + skill + хуки `UserPromptSubmit`/`Stop` + скан `~/.codex/sessions`. Cursor — MCP+skill+хуки; OpenCode — JS-плагин; Qwen Code — MCP+skill без хуков (только скан). Автоматического prefetch перед промптом нет: модель должна сама вызвать MCP-инструмент (`om_recall`, `om_conversations`, `om_diagnostic_trace`). Два независимых переключателя: «одним кликом подключить recall» и «синхронизировать чтение сессий».
- Файлов правил (AGENTS.md/CLAUDE.md) MemHub не правит — ни в одном описанном способе подключения их нет.

## 2. Бенчмарки и что значит «обходит Opus 5»

Источник цифр: model card и arXiv 2610.22196 (HTML v1, приложение A, таблицы 7–10). Независимых воспроизведений нет.

- «№1 на 4 бенчмарках» в первичном источнике — **4 харнесса (фреймворка памяти), не 4 бенчмарка**: Mem0, Hy-Memory, MemOS и EverMemOS (последний не участвовал в обучении). Оценка каждого харнесса — среднее шести метрик: LoCoMo (LLM-judge), LongMemEval, PersonaMem-v2, Travel SPS, Shopping PS, CMB (Code Memory Bench, авторский, под ревью ICLR 2027).
- Режим: фиксированные 20%-подвыборки каждого набора, один детерминированный прогон, без доверительных интервалов; сами авторы пишут, что разницы 0,01–0,02 пункта недостоверны, повторные сиды — «future work». Отвечающая модель заморожена; в оценке упомянут эндпоинт DeepSeek V4.1 Flash, кто именно судья — не указано.
- «Обходит Opus 5» = **Opus 5 в роли писателя памяти внутри того же харнесса** (подменена только запись; промпты, ретривал, отвечающая модель и судья те же). Opus не использовался как конечный ассистент и не сравнивался как «память против памяти».
- Цифры (модель / Opus 5), среднее по харнессам: **55,49 / 54,62** (разница 0,87 пп.). По харнессам: Mem0 54,02/53,43; Hy-Memory 60,55/60,53; MemOS 50,51/50,50; EverMemOS 56,89/54,04. Т.е. на трёх из четырёх харнессов — ничья в пределах шума, заметный отрыв только на held-out EverMemOS (+2,85), и он в основном из метрик Travel SPS (+10,7) и CMB (+13,7).
- По отдельным метрикам Opus 5 нередко лучше: LoCoMo на Mem0 69,47 против 59,54 у Hy; LongMemEval на MemOS и EverMemOS (79,4 и 80,4 против 73 и 76); CMB на Hy-Memory 75,70 против 70,73. Модель выигрывает Travel SPS и LongMemEval на Mem0.
- Чего нет: сравнения с другим Claude (5.5), с тривиальным базисом (`lite`/RAG без LLM-записи в тех же метриках), стоимости записи, латентности, проверки на отмене/опровержении фактов.

Оценка надёжности: для узкой формулировки («после дообучения 3B-активный writer на их харнессах не хуже Opus 5 в пределах шума») доказательств достаточно как для заявки авторов; для «лучше Opus» — нет (одна 20%-подвыборка, нет CI, судья не раскрыт, авторский CMB).

## 4. Реалистичность запуска модели на нашем VPS

Измерено: 8 ядер AMD EPYC (виртуалка), `free` показывает 23 ГБ всего, 13 занято, ~9 доступно (в момент проверки; бот Кеши и Orchestra уже в этой цифре), swap уже сегодня переполнялся. cgroup агента `memory.max = max` (потолок платформы 14/16 ГБ из задачи).

Данные авторов/сообщества:
- BF16: 60,1 ГБ — не помещается ни при каких условиях.
- Готовых GGUF/AWQ для Hy-Memory-30B-A3B пока нет. Та же архитектура `hy_v3` есть у Tencent Hy-MT2-30B-A3B (переводческая модель); её GGUF-кванты — ориентир по размеру: APEX-I Nano 11,5 ГБ, Compact 14,0, Quality 19,0, Balanced 20,8 ГБ; поддержка `hy_v3` в llama.cpp с сборки b9993 (HF `alphaZimuth/Hy-MT2-30B-A3B-APEX-GGUF`; в llama.cpp был feature request #24702 на `hy_v3`; статус не проверял). Т.е. разумный Q4 ≈ 17–19 ГБ; более низкие кванты ≈ 11–14 ГБ ценой качества, которое для Hy-Memory-30B никто не мерил.
- Скорость: единственные числа — для Hy-MT2 на Intel i7-12700H + RTX 3060 12 ГБ (GPU с выгрузкой экспертов на CPU): prompt 463–1224 ток/с, генерация 29–72 ток/с. **CPU-only данных нет ни у авторов, ни в сообществе.** Моя оценка (не замер): при 3 B активных и Q4 ≈ 1,7 ГБ на токен генерация упирается в пропускную способность памяти виртуалки, порядка единиц–десятков ток/с, обработка промпта десятки ток/с на 8 vCPU; для записи памяти (промпт в тысячи токенов на сессию) это минуты на сессию.
- Вывод по железу: Q4 (~18 ГБ) при ~9 ГБ свободных не помещается без вытеснения бота или Orchestra, а в условиях приоритета бота и сегодняшнего инцидента со свопом запускать нельзя. Запуск возможен только на другой машине (ноутбук владельца с GPU, не VPS) или через платный хостинг.

## 6. Минимальный замер, который изменил бы вердикт (не запускался)

Вывод «векторный/агентный слой над KB не нужен» зависит от неизмеренного: находит ли агент с `rg` + индексом нужную запись, когда формулировка запроса не совпадает с лексикой записи.

1. Взять 30 вопросов, на которые ответ однозначно лежит в `.orchestra/kb/*.md` или `.orchestra/tasks/*/` (записать эталон `файл:раздел`). Половину сформулировать перифразом без слов из записи (русско-английский микс, синонимы), 5 — на отменённые/заменённые выводы (какой вариант действует сейчас).
2. Условие A: сегодняшний путь — агент с индексом тем и `rg` (метрика: нашёл ли нужную запись за ≤3 вызова, число токенов). Условие B: `rag.py` Кеши (bge-m3 + FTS5 + RRF), проиндексировавший `.orchestra/`, top-5 (метрика: попадание в top-5; без LLM-записи, бесплатно, отдельная копия индекса вне боевых БД).
3. Решение: если B даёт ≥ +20 пп. по перифразам на вопросах, где A промахивается, — предлагается индекс как инструмент поиска (не как писатель памяти). Иначе слой не нужен. Для отмен B не поможет: нужен отдельный контроль заменённых записей из #454.
4. Проверка самой модели возможна только после появления CPU-замера Q4 (или на ноутбуке с GPU): прогнать корпус #454 с её ловушками (отмена, условие) через модель и сравнить с эталоном из `.orchestra/tasks/454/`.
