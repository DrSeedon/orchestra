# #224 — секреты MCP в argv: как передать иначе, не сломав оба рантайма

Дата: 12.08.2026. Фаза 1 (ресёрч). Значения секретов в этом файле не приводятся нигде —
все замеры сделаны по ИМЕНАМ ключей и счётчикам, маскирование стоит внутри самих команд.

## Вопрос (Step 0)

- **Контекст.** Orchestra передаёт MCP-конфиг рантаймам Claude CLI и Codex CLI при коннекте
  бэкенда. Блок `env` со значениями секретов оказывается в argv живого процесса.
- **Проверяемое изменение.** Передавать конфиг так, чтобы значения не попадали в argv.
- **База сравнения.** Текущее поведение: inline JSON (`--mcp-config {…}`) у Claude,
  inline TOML (`-c mcp_servers.X.env={…}`) у Codex.
- **Измеримый исход.** (1) argv живого процесса не содержит значений; (2) MCP-сервер
  по-прежнему стартует и отдаёт тулы — на ОБОИХ рантаймах.

## Гипотезы и их фальсификаторы (Step 1)

| # | Гипотеза | Что её опровергнет | Итог |
|---|---|---|---|
| H1 | Оба CLI принимают ПУТЬ к файлу конфига | один из них отвергает путь / не стартует сервер | **частично REFUTED** — см. F1/F3 |
| H2 | Достаточно положить секреты в env самого CLI: MCP-ребёнок его унаследует | ребёнок не видит переменную | **REFUTED для Codex** (F4) |
| H3 | Обёртка-скрипт (`command=wrapper`, env внутри файла 600) работает на любом рантайме | ребёнок не получает env / CLI не стартует сервер | **ЧАСТИЧНО: CONFIRMED под `codex exec`, LIKELY под `app-server`** (F5) |
| H4 | У Codex есть ДРУГОЙ файловый маршрут, кроме профиля | `app-server` не читает базовый конфиг | **CONFIRMED** (F14) — найдено внешним ревью, см. «Что изменил ревью» |

Ведущая гипотеза постановки была H1 («Claude CLI принимает и путь, и JSON-строку»). Она
верна для Claude. Для Codex ответ оказался двухступенчатым: профильный маршрут закрыт (F3),
но базовый `$CODEX_HOME/config.toml` читается и в `app-server` (F14) — то есть файловый
маршрут у Codex ЕСТЬ, просто не тот, который напрашивался.

## Находки

### F1. Claude CLI принимает путь к файлу; SDK пропускает его как есть — CONFIRMED (измерение)

`claude --help`: `--mcp-config <configs...>  Load MCP servers from JSON files or strings`.
SDK: `mcp_servers: dict[str, McpServerConfig] | str | Path`
(`claude_agent_sdk/types.py:1762`); для не-dict значение уходит в argv дословно
(`_internal/transport/subprocess_cli.py:391-393`), для dict — `json.dumps` (там же, 384-390).
Именно вторая ветка и есть наш дефект.

Прогон (probe-сервер `docs/tasks/224/probe/probe_mcp.py`, конфиг 600):

```
claude -p "…" --mcp-config /tmp/probe224/cfg2.json --strict-mcp-config
→ exit=0
→ ps: "--mcp-config /tmp/probe224/cfg2.json"      (в argv ТОЛЬКО путь)
→ probe-дамп создан                               (сервер реально запущен из файла)
```

Патч SDK не нужен: тип уже допускает `str | Path`.

### F2. MCP-ребёнок Claude НАСЛЕДУЕТ env процесса CLI — CONFIRMED (измерение), но путь отвергнут

В конфиге был только `PROBE_OUT`; `PROBE_FROM_CLI_ENV` экспортирован в шелле перед запуском.
Дамп ребёнка: `{"PROBE_FROM_CLI_ENV": "MARKER_CLI_ENV", "PROBE_OUT": "…"}` — наследование есть.

**Этот путь всё равно не годится**, и это не вкусовщина: положив сюда ключи чужих проектов,
мы отдадим их каждой Bash-команде агента (env наследуется вниз), то есть первый же `env` или
`printenv` в выводе агента запишет их в логи — ровно та авария, которую задача чинит.
Годится только для собственных переменных Orchestra, и то без выигрыша.

### F3. У Codex `--profile` НЕ применяется к `app-server` — CONFIRMED (измерение)

⚠️ Первая редакция этого пункта делала из него вывод «файловый маршрут для Codex закрыт».
**Вывод неверен и снят** — см. F14. Сам замер ниже верен, неверно было обобщение с одного
механизма на все.

Профильный маршрут Codex — `-p <name>` + `$CODEX_HOME/<name>.config.toml`.
Он работает и несёт `mcp_servers` целиком, включая `env`:

```
codex exec -p probe224 …            → exit=0, probe-дамп создан,
                                      env из файла доехал до ребёнка
```
Имя профиля с дефисом тоже находится (проверено файлом с заведомо битым
`model_provider` — ошибка пришла из СОДЕРЖИМОГО файла, значит файл прочитан).

Но Orchestra запускает Codex как `codex … app-server --stdio`
(`app/backend_codex.py:413`), а там флаг отвергается дословно:

```
codex -p orchestra-probe-abc app-server --stdio
→ Error: --profile only applies to runtime commands and `codex mcp`:
  `codex`, `codex exec`, `codex review`, `codex resume`, `codex archive`,
  `codex delete`, `codex unarchive`, `codex fork`, `codex mcp`, `codex sandbox`,
  and `codex debug prompt-input`.
```

Ответ на вопрос постановки «если один из них путь не принимает — скажи»: **путь принимают оба,
но разными механизмами.** Claude — прямым аргументом `--mcp-config <файл>`; Codex — только
через каталог `$CODEX_HOME` (F14), профильный аргумент в его режиме отвергается.

### F4. MCP-ребёнок Codex НЕ наследует env процесса CLI — CONFIRMED (измерение)

Тот же экспорт `PROBE_FROM_CLI_ENV`, дамп ребёнка под Codex:
`{"PROBE_FROM_CONFIG": "MARKER_CONFIG_ENV", "PROBE_OUT": "…"}` — переменной CLI нет.
Значит для Codex «просто перенести в окружение» невозможно в принципе: env обязан
приехать из конфига. Вместе с F3 это выбивает оба очевидных решения.

### F5. Обёртка-скрипт работает: argv содержит только путь — CONFIRMED (измерение)

`command` указывает на скрипт 700, секреты экспортируются ВНУТРИ него, `exec` на настоящий
сервер. Для CLI обёртка непрозрачна — это просто команда.

```
codex exec -c 'mcp_servers.probe.command="/tmp/probe224/wrap.sh"' \
           -c 'mcp_servers.probe.enabled=true' …
→ exit=0
→ probe-дамп: {"PROBE_FROM_WRAPPER": "MARKER_WRAPPER_ENV", "PROBE_OUT": "…"}
```

Проверено под `codex exec`. Под `app-server` не проверялось — **LIKELY, не CONFIRMED**:
механизм спавна MCP общий, а обёртка для Codex неотличима от обычной команды, но
разница между режимами у нас уже стреляла (F3), поэтому в Фазе 3 это обязан закрыть
прогон на настоящем бэкенде, а не рассуждение.

**Отдельный дефект самого механизма, найденный ревью:** генерация shell-скрипта из значений
означает интерполяцию произвольной строки в исполняемый текст. Кавычка, перевод строки,
`$(…)` или обратный апостроф в значении ломают скрипт или исполняются. Marker-пробник этого
не ловит by design — маркеры были буквенные. Если обёртка всё же понадобится, генерировать
надо не shell, а `execve` без интерполяции (например, крошечный Python-загрузчик, читающий
JSON-сайдкар 600 и делающий `os.execve`). Это ещё одна причина, по которой обёртка ниже
понижена до запасного варианта.

### F14. У Codex ЕСТЬ файловый маршрут: `app-server` читает `$CODEX_HOME/config.toml` — CONFIRMED (измерение)

**Эту находку принёс Codex-ревью, и она опровергает вывод первой редакции.** Проверено не
рассуждением, а прогоном настоящего `app-server` с JSON-RPC-хендшейком
(`initialize` → `initialized` → `thread/start`, драйвер `docs/tasks/224/probe/drive_appserver.py`):

```
CODEX_HOME=/tmp/probe224/codexhome codex app-server --stdio
config.toml (600) в этом каталоге:  [mcp_servers.probe] + [mcp_servers.probe.env]
→ PROBE LAUNCHED FROM $CODEX_HOME/config.toml:
  {"PROBE_FROM_CODEX_HOME": "MARKER_CODEX_HOME", "PROBE_OUT": "…"}
```

Каталог был свежий: `auth.json` симлинком, БЕЗ единой записи `trust_level` — MCP всё равно
поднялся. Значит отсутствие унаследованного списка доверенных путей спавну серверов не
мешает (полный ход модели при этом не гонялся → для самого хода это LIKELY, не CONFIRMED).

**⚠️ Здесь первая редакция F14 содержала ошибку, найденную во втором раунде ревью.**
Было написано: «`app/backend_codex.py:1534` УЖЕ читает `CODEX_HOME`, значит учёт токенов
поедет за каталогом сам, без правок». **Это неверно.** Проверено по коду:

```python
# app/backend_codex.py:1534, внутри _runtime_context()
root = Path(os.environ.get("CODEX_HOME", str(Path.home() / ".codex"))).expanduser()
```

`os.environ` здесь — окружение ДОЛГОЖИВУЩЕГО процесса Orchestra, а не то `env`, которое
`connect()` отдаёт `create_subprocess_exec` (строки 415-443) для дочернего процесса.
Установка `CODEX_HOME` в дочернем env `os.environ` родителя не меняет, поэтому поиск
rollout продолжит идти в общий `~/.codex/sessions`, ничего там не найдёт и вернёт `None`.
**Последствие — молчаливая потеря учёта токенов и context% у всех Codex-воркеров**, причём
`None` неотличим от «данных ещё нет»: отказ выглядит ровно как норма. Это тот самый класс
проверки, что даёт одинаковый ответ при успехе и при провале.

Требование к Фазе 2: `CodexBackend` обязан хранить свой codex-home полем и использовать
ЕГО и в дочернем env, и в `_runtime_context()` — а не читать `os.environ`.

**Цена маршрута — измерена, и она не нулевая.** Живой `~/.codex/config.toml` (222 строки)
содержит, помимо секретов: `project_doc_max_bytes` (тот самый потолок обрезки `AGENTS.md`),
~70 записей `[projects."<путь>"] trust_level`, глобальный MCP `yandex-direct` (с
`YANDEX_DIRECT_TOKEN`) и HTTP-сервер `openaiDeveloperDocs`. Свой `CODEX_HOME` на агента
всего этого НЕ унаследует.

**Вторая ошибка первой редакции, тоже найденная ревью:** отсюда был сделан вывод
«генерировать конфиг на коннекте ИЗ ЖИВОГО БАЗОВОГО». Так делать нельзя — копирование
базового файла затащило бы `mcp_servers.yandex-direct` (вместе с его токеном) и
`openaiDeveloperDocs` в конфиг КАЖДОГО воркера, в обход осознанного отбора серверов в
`runtime_registry.py:230-245`. То есть починка argv восстановила бы кросс-проектную выдачу
секретов через другой канал — прямо против цели задачи.

Правильная форма: **не копия, а сборка по белому списку.** Переносить из базового только
нужные скалярные настройки (`project_doc_max_bytes` и то, что реально требуется), MCP-блок
писать ТОЛЬКО из `context.mcp_servers` этого воркера, `[projects.*]` и чужие серверы не
клонировать вовсе.

Про расхождение копии: уточнение ревью справедливо — расходится не «конфиг», а каталог.
`config.toml` регенерируется на коннекте и потому не дрейфует; а вот `sessions/`, `history`
и записанные Codex'ом `trust_level` — отдельное состояние, которое обязано ПЕРЕЖИВАТЬ
реконнект, иначе перестанут находиться thread-id для resume. Значит каталог на агента
должен быть стабильным (по session_id), а не временным.

И ещё одно ограничение, замеренное в том же прогоне: каталог **не должен лежать в `/tmp`** —
```
WARNING: proceeding, even though we could not create PATH aliases:
Refusing to create helper binaries under temporary dir "/tmp"
```

### F8. Куда ещё утекает та же строка (пункт 3 задачи) — CONFIRMED

- **Дашборд.** `AgentSession.to_dict` (`app/session.py:2904-2936`) MCP-конфиг НЕ отдаёт —
  в браузер он как поле сессии не попадает. Но логи отдаются целиком
  (`/api/sessions/{name}/logs`, SSE `stream_session_logs`, `/api/logs/{id}`), поэтому всё,
  что уже записано в `tool_result`, в браузере видно. Экспозиция реальна, но её носитель —
  логи, а не конфиг.
- **RAG-индекс.** Индексируются только `user_message` и `text` (`app/rag.py:103`).
  В `vec.db` 4 чанка упоминают `--mcp-config` и **0 несут значение токена** (проверено
  регуляркой по `log_chunks.text`). Главный носитель (`tool_result`) не индексируется —
  этот путь распространения чист.
- **БД сессий.** `sessions.mcp_servers_custom` хранит кастомные серверы со спавна:
  3 записи с `OPENROUTER_API_KEY`. Это отдельное хранилище значения, argv не касается,
  наружу не отдаётся — но в перечень «где лежит секрет» входит.
- **Картиночные блобы** (`app/blobs.py`) выносят только base64-изображения; текст
  `tool_result` остаётся в `logs.content`.

### F9. `db.add_log` — единственный шов ПЕРСИСТЕНЦИИ, но НЕ единственный шов ВЫДАЧИ — CONFIRMED

`app/db.py:1353` — единственный INSERT в `logs`, и это зафиксированный инвариант в его
докстринге. `session._log` (`app/session.py:2781`) — не единственный вызывающий:
`app/notify.py:108` и `app/tg_bridge.py:402` пишут мимо него. **Маскировать надо в
`add_log`**, иначе два пути записи останутся открытыми — классический «правишь одно,
ищи второе» из `CLAUDE.md`.

**Поправка после ревью (я этого не увидел, увидел ревьюер).** Формулировка первой редакции
«единственный шов» была слишком широкой: она верна для записи в БД и неверна для выдачи
наружу. Рядом живёт ВТОРОЙ канал — `app/live_broker.py`, в который `session._handle_event`
публикует напрямую, минуя `add_log`, четырьмя вызовами:

```
app/session.py:1434  stream            app/session.py:1453  thinking_stream / tool_stream /
app/session.py:1440  subagent_stream                        tool_patch / turn_diff
                                       app/session.py:1482  subagent_event
```

Комментарий в коде честно называет их эфемерными: «Live partials: push to in-memory broker
for SSE fan-out, NEVER persist». Для нашей задачи это значит: маскирование в `add_log`
закрывает БД, дашбордную выдачу СОХРАНЁННЫХ строк, RAG и историю, но **живой поток в
браузер во время хода остаётся немаскированным** — включая `tool_stream`, по которому
вывод команды идёт до её завершения. Это не отменяет шов `add_log`, а добавляет второй.
Правильный вывод для плана: маскирующая функция — общий leaf-хелпер, вызываемый ОБОИМИ
путями (`add_log` и `broker.publish`), а не встроенный в один из них.

Это меняет объём Фазы 2: швов два, а не один. Мой замер 0.40% (F10) снят по строкам БД и
эфемерный поток не покрывает — площадь по нему не измерена вовсе.

### F10. Правило маскирования: замерена и площадь, и ложные срабатывания

Правило-кандидат (по имени ключа, значение ≥12 символов) прогнано по всем 80 880 строкам:

```
строк, которые правило тронет:  323 (0.40%)   вхождений: 581
по типам: tool_result 273, tool 46, user_message 2, subagent_start/end 2
```

Верхние совпавшие ИМЕНА: `TOKEN` 149, `INTERNAL_TOKEN` 66, `OPENROUTER_API_KEY` 63,
`DEEPGRAM_API_KEY` 39, `PASSWORD` 31, `YANDEX_DIRECT_TOKEN` 31, `_TEMPLATE_HASH` 19,
`SECRET` 14, `TEMPLATE_HASH` 14, `BY_TOKEN` 13, `YOUGILE_API_KEY` 12,
`GOOGLE_OAUTH_CLIENT_SECRET` 12, `DASHBOARD_PASSWORD` 11, `GROK_TOKEN` 11,
`TELEGRAM_BOT_TOKEN` 9, `RECEIVED_REQUEST_HASH` 2.

Два вывода, которых не было в постановке:
1. **`*_HASH` суффиксом брать нельзя.** Крупнейший класс ложных срабатываний —
   `TEMPLATE_HASH`/`_TEMPLATE_HASH` (33 вхождения) и `RECEIVED_REQUEST_HASH`: это хеши
   содержимого, не секреты. `api-hash` Telegram закрывать явным списком, а не суффиксом.
2. **Суффиксы не ловят половину пары кредов.** `YANDEX_DIRECT_LOGIN` (x3 в живом argv) не
   подходит ни под один суффикс. Явный список, о котором говорит постановка, обязателен.

**Что именно означают эти 0.40% (уточнено после ревью).** Это площадь ПОВРЕЖДЕНИЯ — сколько
строк правило вообще тронет, то есть верхняя граница риска испортить полезные данные. Это
НЕ мера полноты и не мера безопасности: сколько секретов правило ПРОПУСКАЕТ, отсюда не
следует. Замечание ревью справедливо в том, что первая редакция подавала одно число как
общий вердикт; и оценивать повреждение стоит по типу записи, а не только по её доле —
две задетые `user_message` весят иначе, чем двести `tool_result`.

**Полнота, измеренная отдельно — и пересчитанная после ревью.** Первая редакция сравнивала
323 совпадения из одного снимка (80 880 строк) с 17 совпадениями из другого (81 207 строк) и
подавала разницу как «+17». **База живая и растёт между запросами, а множества пересекаются**,
поэтому такая арифметика неверна. Оба правила перепрогнаны в ОДИН проход по ОДНОМУ снимку,
с честной разностью множеств по `logs.id`:

```
строк в снимке                                   81 433
базовое правило                                     323  (0.40%)
доп. формы (COOKIE|CREDENTIAL|PRIVATE_KEY|…)         17
   из них НОВЫХ, которых нет у базового               9
'Bearer <токен>' / 'Basic <токен>'                   29
   из них НОВЫХ                                      19
объединение всех трёх                               351  (0.43%)
```

Настоящий вклад пропущенных форм — **9 строк, а не 17**: восемь из семнадцати базовое
правило и так ловило. Плюс 19 строк формы `Bearer …`, которые достаются переиспользованием
готового `_AUTH_VALUE` из `runtime_history.py` (F11), а не новой регуляркой. Итог: пробел
реальный, но узкий (351 против 323 строк), список ключей расширить дёшево, перекраивать
подход не нужно.

### F11. Готовый санитайзер в репозитории уже есть, но не на том пути

`app/runtime_history.py:114-155` — `_sanitize` с `_PEM_PRIVATE_KEY`, `_AUTH_VALUE`,
`_NAMED_SECRET`, base64. Применяется в `_normalize_history` (рендер истории обратно в CLI),
к записи в `logs` отношения не имеет. `_NAMED_SECRET` формально накрыл бы
`"INTERNAL_TOKEN": "…"` (в паттерне нет `\b` слева, `TOKEN` матчится хвостом имени), но
заменяет на `[redacted]` — без длины и хвоста, которых требует задача. Кандидат на
переиспользование регулярок, не самой функции.

### F12. `telegram-bot-api.service` — CONFIRMED

`-rw-r--r-- 1 root root /etc/systemd/system/telegram-bot-api.service`, в `ExecStart`
стоят `--api-id=` и `--api-hash=` значениями. Мало того что юнит world-readable — эти же
значения попадают в argv процесса (в БД уже 14 строк с `--api-hash=`, 4 сессии).
Лечится `EnvironmentFile=` 600 и независимо от всего остального.

### F13. `/proc` без `hidepid` — CONFIRMED

`findmnt -no OPTIONS /proc` → `rw,nosuid,nodev,noexec,relatime`; `/proc/1/cmdline` имеет
режим `-r--r--r--`. Человеческий uid на машине один (`kesha`, 1001), но cmdline читает
процесс ЛЮБОГО uid, включая сервисные (tinyproxy, nginx). Для сравнения `/proc/<pid>/environ`
читает только владелец — то есть env строго лучше argv против чужих uid, и строго не лучше
против агента-соседа под тем же uid. Настоящий выигрыш фикса не в изоляции uid, а в том,
что секрет перестаёт попадать в вывод рутинных команд.

## Контр-доводы и то, что фикс НЕ закрывает

- **Маскирование в `add_log` не защищает контекст модели.** Агент, запустивший `ps`, увидит
  значение в своём `tool_result` — маскируется то, что уходит в БД, дашборд, RAG и TG-зеркало.
  Чтобы закрыть и контекст, шов пришлось бы двигать в бэкенды, на границу возврата
  tool-результата, а это ломает легитимные сценарии (агент читает свой `.env`). Считаю
  правильным размен, но он обязан быть назван вслух, а не подразумеваться.
- **Обёртка не спасает HTTP-серверы с заголовками.** Токен в `headers` останется в argv.
  Сейчас таких серверов нет (F6), но завтра появятся — файловый маршрут Claude их накрывает,
  обёртка нет.
- **Кросс-проектное чтение под одним uid остаётся.** Файл 600 и обёртка 700 принадлежат
  `kesha`; агент соседнего проекта работает под тем же uid и может их прочитать, если
  специально захочет. Устраняется случайная утечка, не злонамеренная.
- **Уже записанное остаётся записанным.** Санитизация БД и ротация — вне задачи, по прямому
  указанию. Пока рестарта нет, поток новых записей продолжается.
- **Codex молча игнорирует отсутствующий профиль.** `codex exec -p <несуществующий>` не
  ругается и стартует дальше (проверено: прогон дошёл до таймаута, а не до ошибки). Класс
  ошибки общий: пропавший файл конфига даёт воркера с НУЛЁМ тулов Orchestra и без единой
  жалобы. Любой файловый маршрут обязан иметь fail-loud проверку, что конфиг применился.

## Рекомендация (на решение гейта)

**Рекомендация переписана после ревью.** Первая редакция предлагала обёртку для Codex,
потому что считала файловый маршрут закрытым. F14 это опроверг: у обоих рантаймов есть
ШТАТНЫЙ файловый механизм, то есть решение получается однородным, а не составным.

| Рантайм | Механизм | Основание |
|---|---|---|
| Claude | `options.mcp_servers = <путь к файлу 600>` | F1: SDK и CLI это уже умеют, правка ~строка; накрывает ВСЕ серверы разом, включая чужие из `.mcp.json` (F6) и будущие HTTP-заголовки |
| Codex | свой СТАБИЛЬНЫЙ `CODEX_HOME` на агента, `config.toml` 600, **собираемый по белому списку** (не копия базового); `-c mcp_servers.*.env=` уходит из argv | F14: штатный путь платформы, без генерации исполняемых файлов и без интерполяции значений |
| оба | маскирование общим leaf-хелпером, вызываемым И из `db.add_log`, И из `broker.publish` | F9: швов два — персистенция и живой SSE |

Два обязательных условия для Codex-ветки, без которых она ломает работающее (оба найдены
ревью, оба проверены по коду — детали в F14):
1. **Конфиг собирается, а не копируется.** MCP-блок — только из `context.mcp_servers`
   воркера. Иначе глобальный `yandex-direct` с токеном разъедется по конфигам всех агентов.
2. **`CodexBackend` хранит свой codex-home полем** и использует его и в дочернем env, и в
   `_runtime_context()` (`backend_codex.py:1534` сейчас читает `os.environ` РОДИТЕЛЯ).
   Иначе молча ломается учёт токенов и context%.

Маскирование применять к полю `content`, а не к payload целиком: `type`, `subagent_id`,
`tool_use_id`, `item_id` и структура патчей обязаны остаться нетронутыми, иначе поедет
разбор на фронте.

Обёртка-скрипт (F5) остаётся **запасным** вариантом: она не трогает базовый конфиг Codex
и потому дешевле по миграции, но вносит интерполяцию значений в исполняемый текст, поэтому
годится только в `execve`-виде без shell. Брать её, если генерация `config.toml` из базового
окажется дороже, чем выглядит.

**Границы того, что этот набор даёт.** Он устраняет попадание значений в argv и, значит, в
вывод рутинных команд, в БД, в дашборд и в RAG. Он **НЕ** даёт изоляции между проектами:
все агенты работают под одним uid `kesha` и могут прочитать и файл конфига 600, и каталог
`CODEX_HOME` 700, если станут это делать намеренно (F13). Первая редакция назвала набор
«минимальным полным», не оговорив, для какой именно цели он полон, — формулировка
исправлена: полон для случайной утечки, не для злонамеренного чтения соседом.

**Открытый вопрос для Фазы 2:** жизненный цикл файлов. Конфиг обязан существовать всё время
жизни процесса CLI (сервер может быть перезапущен рантаймом позже), значит удаление — на
`_disconnect_backend`, а каталог — приватный (700) вне рабочего дерева и вне `/tmp` (F14),
иначе он попадёт в `git status` и заблокирует мержи (граблю с `report_bug`/`BUGS.md` уже
проходили). Плюс fail-loud проверка, что конфиг применился: Codex молча стартует без
пропавшего конфига, отдавая воркера с нулём тулов Orchestra.

## Окно применения (явно, как просила постановка)

Правка в `app/` вступает в силу только после рестарта Orchestra — рестарт здесь НЕ
предлагается и не запрашивается, окно назначает владелец. Ниже — только то, каким будет
состояние после разрешённого запуска, чтобы его можно было проверить.

Первая редакция утверждала, что у уже подключённых воркеров argv останется прежним до
реконнекта. **Замер показал обратное, и это существенно лучше:**

```
systemctl show orchestra -p KillMode  →  KillMode=control-group
cgroup процессов агентов              →  0::/system.slice/orchestra.service
                                         (проверено на живых claude и codex)
```

То есть CLI-процессы агентов лежат в cgroup самого юнита и при рестарте гибнут вместе с
ним; переподключаясь, они соберут argv уже по-новому. Отдельного «окна доживания» для
процессов Orchestra нет — есть обычная плата за рестарт (оборванные активные ходы).

**Чего рестарт Orchestra не чинит.** Среди живых процессов с `--mcp-config` нашлись два,
принадлежащих ДРУГОМУ юниту — `kesha-bot-vps.service` (`/opt/kesha-bot/bot.py`, PPID 2433318,
cgroup `0::/system.slice/kesha-bot-vps.service`). Это чужой сервис на том же хосте, который
запускает Claude тем же дефектным способом. Наша правка его не касается вовсе; он останется
источником тех же строк в `ps` и требует отдельного решения владельца.

Ротацию секретов (решение юзера) осмысленно делать после того, как выполнены оба условия:
код перезапущен И живые сессии переподключены.
