# #160 — после рестарта воркеры «просто айдл висят»

Фаза 1. Корень найден и **воспроизведён на изолированном инстансе** (живой сервис не
рестартился). Дефект ровно там, где симптом: механизм пробуждения существует и работает,
но при ШТАТНОМ рестарте он не получает данных, по которым решает, кого будить.

## Question

### Context
`app/manager.py:1646 auto_resume_all()` при старте поднимает сессии из SQLite и для тех,
кто на момент рестарта был `running`, шлёт «пинок» — `_inject_restart_notice`
(`manager.py:1706`). Уточнение юзера дословно: «просто айдл висят и всё» — то есть запись
сессии восстанавливается, агент виден в списке, но хода не получает.

### Change under test
Почему воркер, прерванный рестартом на середине хода, не получает пробуждающее сообщение.

### Baseline
Ожидаемое поведение (и то, что написано в `CLAUDE.md`): «после разрешённого рестарта
SQLite-сессии и idle workers восстанавливаются; активные turns прерываются» — прерванные
должны быть разбужены пинком.

### Outcome (measurable)
Для воркера со статусом `running` на момент рестарта после `auto_resume_all` существует
доставленный restart notice. Критерий зафиксирован ДО прогона.

## Hypotheses considered

| # | Гипотеза | Фальсификатор | Вердикт |
|---|---|---|---|
| H1 | Сессия отбрасывается фильтром `session_id IS NOT NULL` (находка из #35) | воспроизвести: если сессия ЕСТЬ в списке — H1 ложна | **REFUTED** — сессия восстанавливается всегда |
| H2 | Пинок шлётся, но не запускает ход (теряется в доставке) | посчитать вызовы `send` после resume | **REFUTED** — вызовов ноль, терять нечего |
| H3 | Пинок не шлётся, потому что к моменту чтения статуса он уже не `running` | сравнить статус в БД до рестарта и на старте | **CONFIRMED** |
| H4 | Никто не будит вообще, механизма нет | код `_inject_restart_notice` существует | **REFUTED** — механизм есть и в hard-kill работает |

## Findings

### F1 — Корень: `shutdown_all()` стирает `running` из БД ДО того, как старт его прочитает. CONFIRMED
Тир 1 (прямое измерение, продовый код на временной БД: `docs/tasks/160/repro_restart.py`).

Цепочка, вся в проде:
1. `app/main.py:127` на остановке зовёт `manager.shutdown_all()`.
2. `manager.py:1757-1761` вызывает `session.stop()` для КАЖДОЙ сессии.
3. `session.py:1718 stop()` → `self.status = AgentStatus.IDLE` (`:1724`) → `_persist()` (`:1725`).
4. Следующий старт `auto_resume_all` (`manager.py:1649`) читает
   `SELECT id FROM sessions WHERE status = 'running'` → **пусто**.
5. `was_running` пуст → ветка `elif row["id"] in was_running` (`:1700`) не берётся →
   `_inject_restart_notice` не вызывается ни для кого.

Ключевая деталь: `stop()` не различает «юзер нажал стоп» и «сервер выключается». Обе
ситуации пишут в БД одно и то же значение `idle`, и информация «этот агент был прерван
на середине хода» уничтожается безвозвратно — это ровно тот случай из постановки, когда
прерванный ход «молча выглядит как завершённый».

Замер, 3 полных прогона подряд, результат побитово одинаковый (асинхронный код — одного
прогона мало; 4-й срезан моим шелл-таймаутом, не падением):

```
A graceful restart (systemctl restart)
  status before restart      : running
  status seen by auto_resume : idle
  session restored into list : True
  restart notices sent       : 0  -> FAIL — sits idle, nobody wakes it

B hard kill (SIGKILL/OOM)
  status before restart      : running
  status seen by auto_resume : running
  session restored into list : True
  restart notices sent       : 1  -> PASS — woken
```

**Инверсия и есть суть бага: чем «чище» остановлен сервис, тем гарантированнее теряется
работа.** `systemctl restart` (штатный сценарий обновления VPS из постановки) попадает
в арм A. Пробуждение сохраняется только когда процесс убит жёстко и `stop()` не успел
отработать — то есть механизм из #35/#87 живёт лишь на аварийном пути.

### F2 — Симптом «айдл висят» объясняется полностью и точно. CONFIRMED
Тир 1 (тот же прогон). `session restored into list : True` при `notices sent : 0` — это
дословно «присутствует в списке, статус idle, хода нет». Ни одна другая гипотеза такой
комбинации не даёт: H1 убрала бы агента из списка, H2 дала бы ненулевые вызовы.

### F3 — Живая БД подтверждает: пробуждение почти никогда не срабатывало. CONFIRMED
Тир 1 (read-only запрос к `data/orchestra.db`).

| маркер | всего |
|---|---|
| `⏹️ stopped (manual interrupt)` (то, что печатает `stop()`) | 1785+ за 27.07–05.08, по 64–542 в день |
| `Orchestra server restarted` (доставленный пинок) | **16 за всю историю**, максимум 8 в день |

Кроме того: запрос «≥3 сессии остановлены в одну секунду» (сигнатура пакетного
`shutdown_all`) даёт **0 строк**. То есть на живой машине массового graceful-стопа в логах
не видно — при `TimeoutStopSec=30` (проверено `systemctl cat orchestra`) часть остановок
доходит до SIGKILL. Это объясняет, почему баг выглядит как «НЕ ВСЕ воркеры» (дословная
формулировка первой постановки), а не «никто»: **разделяющий признак — успел ли
`stop()` данной сессии дописать `idle` в БД до того, как systemd убил процесс.** Кто успел —
потерян, кто не успел — разбужен. Отсюда и недетерминированность, которую видел юзер.

### F4 — Второй, независимый дефект: очередь сообщений не переживает рестарт. CONFIRMED
Тир 1 (чтение `_to_db_dict`, `session.py:1817-1849`). `_pending_messages`
(`session.py:254`) — поле только в памяти, в снимок для БД не попадает. Сообщения,
поставленные в очередь на строках `:686`, `:694`, `:707` (компакт идёт / бэкенд без
mid-turn inject / инжект упал), при рестарте исчезают молча. Находка совпадает с P1 из
`docs/tasks/35/review-reliability.md` — за прошедшее время не починена.

Это отдельная потеря: даже если разбудить агента (F1), адресованные ему сообщения уже не
восстановятся. Чинить надо обе, но F1 — блокер, F4 — усугубление.

### F5 — Механизм пробуждения сам по себе исправен. CONFIRMED
Тир 1 (арм B даёт `notices sent : 1`). `_inject_restart_notice` с джиттером
`3 + random(0,12)` (`manager.py:1710`) работает, доставка через `manager.send` работает.
Чинить его не нужно — нужно не уничтожать вход, по которому он принимает решение.
Согласуется с выводом #156: «механизм пробуждения исправен, отсутствует автотриггер».

## Counter-evidence и риски

- **Против H1 (моя стартовая гипотеза по памяти #35).** Фильтр `session_id IS NOT NULL`
  (`manager.py:1656`) реально способен отбросить сессию, пойманную посреди `compact()`.
  Но к ЭТОМУ симптому он отношения не имеет: в обоих армах сессия восстановилась. Держу
  как известный отдельный риск, не как причину #160.
- **Арм B — не «правильное» поведение.** Hard kill будит агента, но теряет всё, что
  `stop()` делает штатно (отключение бэкенда, отмена таймеров). Вывод «давайте не звать
  `shutdown_all`» был бы неверным прочтением замера.
- **Чего я НЕ мерил.** Живой `systemctl restart` не запускался (запрещено постановкой),
  поэтому доля graceful/SIGKILL на реальной машине оценена косвенно — по отсутствию
  пакетных стоп-бурстов в логах, а не прямым замером. На вывод о корне это не влияет:
  арм A воспроизводится детерминированно и покрывает штатный сценарий обновления VPS.
- **`was_waiting` — та же болезнь.** Ветка `:1695` про `waiting` читает статус из того же
  затёртого источника, плюс требует живых `bg_jobs`. Отдельно не воспроизводил.

## Направление фикса (НЕ реализовано — гейт)

Суть: различить «остановлен человеком» и «прерван выключением сервера», и сохранить это
различие в БД, а не в памяти. Требования к фиксу:
- отдельный устойчивый признак прерванности (колонка/статус), выставляемый на shutdown,
  а не вывод по `status='running'`, который сам же shutdown и затирает;
- fail-closed в ОБЕ стороны (грабля `_verify_mcp_isolation`): «не разбудили того, кто
  работал» — такой же дефект, как «разбудили того, кто честно закончил»;
- проверка обязана различать успех и провал — красный тест на арме A до фикса.
