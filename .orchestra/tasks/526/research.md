# #526 — формальные промпты: выигрыш есть, универсальной замены прозе нет

Проверено **2026-09-07**. Только исследование; предложенные изменения не реализованы. Перед началом выполнен `git fetch origin main`: HEAD, local main и origin/main совпали на `789e96a9cc22480f4d5108e270e56eb61ec6257b`. Платные модельные API, локальный inference и дополнительные модельные сессии не запускались.

## Question

**Контекст:** Orchestra управляет подписочными CLI, инструментами, ревью и merge; интерпретация поручена модели, дорогие ошибки должны отсекаться кодом. **Изменение:** типизированные промпты, ограниченный декодер или программная оркестрация вместо свободного текста. **База:** существующие промпты и гейты. **Исход:** меньше неверных допусков и ложных отказов при сохранении качества задач; отдельно — валидность формы, правильность значений, согласованность повторных решений, токены, задержка и стоимость успешной задачи. Accuracy одного прогона не измеряет повторяемость решения.

## Hypotheses considered

| Гипотеза и механизм | Что опровергает | Итог |
|---|---|---|
| H1: DSL делает решение детерминированным, поскольку устраняет неоднозначность | Два разных допустимых значения либо ошибка при валидной структуре | Общая гарантия отвергнута: схема допускает несколько ответов; эмпирически форма и значение расходятся [1,5,9] |
| H2: формализация полезна на машинных границах, поскольку устраняет парсинг прозы | У нас нет таких границ либо типизация лишь переносит тот же непроверяемый текст | Два действующих шва найдены; наблюдаемое поведение парсеров воспроизведено [L1]. End-to-end выигрыш будущей замены не измерен |
| H3: оптимизация промпта повышает качество через поиск примеров/инструкций по метрике | Нет улучшения на независимом holdout или расходы выше выигрыша | Есть внешние положительные и отрицательные результаты DSPy [4]; наша окупаемость неизвестна |
| H4: ограничение формата всегда ухудшает reasoning | Рост качества при том же backbone | Универсальный тезис отвергнут [1]; обратный тезис «всегда помогает» тоже [2,3,5] |

## Findings: что именно формализуется

1. **Форма:** грамматика ограничивает допустимые токены; JSON Schema описывает структуру и часть ограничений значений. Это практическая гарантия для поддерживаемой схемы и завершённой генерации, а не обещание успешного ответа при отказе, обрыве или лимите. Просто «отвечай JSON» такой гарантии не даёт. **CONFIRMED — tier 2, документация провайдеров [9–11].**
2. **Смысл:** `approved: bool` исключает опечатку, но допускает и ошибочное `true`, и ошибочное `false`. Проверяемый предикат в коде может гарантировать конкретное свойство — например, совпадение SHA; произвольную истинность заключения из этого получить нельзя. Детерминированное ветвление по неверному предикату лишь повторяет ошибку. **CONFIRMED — логическое следствие контракта; наличие ошибок значений измерено [1,5].**
3. **Исполнение:** IF/LOOP в Python или интерпретируемом DSL фиксирует порядок вызовов и счётчик итераций. Строка `ЦИКЛ(СКИЛЛ, пока хорошо)` внутри промпта не создаёт исполняемого цикла; `пока хорошо` остаётся суждением модели. Кеш ответа возвращает сохранённое решение, включая ошибку; кеш префикса экономит вычисления, не выбирает ответ. Переносимый файл не обеспечивает равное поведение разных моделей. Это различение механизмов, не отдельный benchmark.

DSPy решает статистическую оптимизацию, SGLang — в том числе производительность; оценивать их только как JSON-валидаторы тоже неправильно.

На GSM8K accuracy: LM only **80.1%**, Guidance **83.8%**, Outlines **81.6%**, XGrammar **83.7%**. **LIKELY:** выигрыш в указанной конфигурации; независимого повторения и измерения сегодняшних версий здесь нет.

**RANLP’25, Schall/de Melo [3], независимая академическая работа, tier 2.** На SQuAD EMIN Mistral-7B-Instruct **81.1→73.7%** при constraints (**−7.4 п.п.**); Llama3-8B Base **42.5→59.6%** (**+17.1 п.п.**). IFEval strict instruction compliance Llama3-8B-Instruct **84.1→52.6%** (**−31.5 п.п.**). Последнее — соблюдение пользовательских инструкций, не валидность JSON. **CONFIRMED как опубликованные результаты; LIKELY как переносимый риск**, не оценка нашего Astra/Luna. Ограничение пространства меняет не только синтаксические ошибки; эффект зависит от задачи и модели.

**Tam et al., EMNLP Industry 2024 [2], tier 2, независимая от библиотек работа.** В Table 1 GPT-3.5 Turbo без схемы: Text **75.99**, JSON **74.70**; с дополнительной схемой JSON **49.25**. Последнее часто неверно пересказывают как универсальный штраф native JSON mode. Авторы отдельно обнаружили в Last Letter JSON-mode размещение `answer` перед `reason` в **100%** ответов GPT-3.5: меняется порядок решения. Ответ dottxt [8] оспаривает prompting/chat-template и постановку; dottxt заинтересован в Outlines. **LIKELY: схема способна навредить; REFUTED: эти числа доказывают неизбежную цену любого constrained decoder.**

**Capacity, Not Format (июнь 2026), tier 2, препринт [5].** На отдельном MATH-Hard опыте GPT-4o-mini (100 задач):

| Режим | Accuracy | Tokens, как указано в Table 3 |
|---|---:|---:|

Для API JSON разница **−9 п.п., p=0.12**, статистически незначима. Меньше токенов здесь не значит больше решённых задач. В основном опыте JSON задавался подробной инструкцией, это **не** чистая изоляция стоимости token masking. **LIKELY:** полезное свежее контрдоказательство, ограниченное выборкой/методикой; повторения у нас нет. Не пересчитываю токены в доллары подписки.

Численной единой «наценки constrained decoding» нет. Claude документирует дополнительный system prompt, оплачиваемые входные токены, компиляцию и кеш грамматики **24 часа** [11]; число добавленных токенов/миллисекунд не указано. Формула сравнения для нас: весь расход настройки + все успешные и неуспешные попытки, делённые на число **правильно** завершённых задач. Числитель для нашей новой схемы не измерен, поэтому экономию не заявляю.

## Counter-evidence и пределы вывода

- **Формализация хуже свободного текста**, когда преждевременно закрывает пространство ответа. Измеренный пример — падение Mistral-Instruct на SQuAD [3]; механизм порядка `answer/reason` наблюдался отдельно [2]. В нашем открытом исследовании обязательный `winner: enum[DSPy,LMQL,Guidance]` сделал бы честный ответ «нет достаточных данных / ни один» непредставимым. Это наш логический контрпример, не модельный эксперимент.
- **Смысловая ошибка и недетерминизм не одно и то же.** Модель может ошибаться одинаково всегда. Приведённые accuracy не дают коэффициента согласия повторных решений; такой замер в нашем контуре не выполнен. Грамматика не является доказательством повторяемости.
- **Независимость не бинарная печать качества.** JSONSchemaBench имеет связь с Guidance; ответ dottxt заинтересован; LMQL/SGLang дают авторские результаты. Minho и RANLP дают внешние проверки, но на других моделях. Найденный SOB’26 [19] также имеет конфликт: авторы Interfaze оценивают Interfaze. Его лидерборд не использован для выбора поставщика.
- **Свежесть инструмента не обновляет старый benchmark.** LMQL не признан «мёртвым» только по PyPI, а нынешний Outlines не обвиняется в задержках старой версии. CFGzip’26 [20] сообщает до **7.5×** ускорения относительно constrained baseline на сложных CFG — авторский результат, не преимущество перед свободным текстом и не измерение нашего CLI.
- **«Меньше параметров» не следует из грамматики.** Для такого решения нужен отдельный опыт: малая модель + формализация против большой на одной проверке качества, с полной стоимостью. У найденного DSPy case study перенос на дешёвую модель как раз не помог [4]. Ни уменьшение файла промпта, ни валидный JSON не являются таким опытом.

## Предложение, не мандат

Не вводить общий «язык промптов» по имеющимся данным. Наиболее обоснованный следующий предмет — **протокол результата ревью**, потому что его парсер уже воспроизводимо путает наличие заголовка с наличием вердикта. Второй — **provenance лимитных событий**, где новый prompt DSL вообще не нужен. Это уточняет существующую границу «код для дорогих ошибок», а не предлагает заменить её.

Если владелец отдельно разрешит проверку решения: взять реальные обезличенные артефакты обоих исходов, заранее зафиксировать ожидаемые решения; сравнить существующий parser, строгую квитанцию и свободный анализ с финальной квитанцией. Метрики: false accept, false reject, незавершённые ответы, правильность содержимого, согласие повторов, полный расход и latency. Обязательные случаи: пустота, отказ, обрыв, локализованный заголовок, отрицание вердикта, корректное чистое ревью, неподходящий SHA, старый запуск. Число повторов и бюджет определить по пилоту 2–3 случаев; автоматическую модельную оценку не использовать как единственный oracle. Сначала проверить передачу схемы по **настоящему** runtime; API-demo не доказывает эту цепочку.
