# V-997 — T3 Code: что это, лучше ли Orchestra, что взять

Источники: клон `github.com/pingdotgg/t3code` (read-only, /tmp/t3/src, HEAD от 21.10.2026), README, docs/, release notes v0.1.0 и v0.1.1 (через `gh api`), код `apps/server`, `packages/*`. Сравнение с нашим кодом — `/home/kesha/orchestra/app`. Платных вызовов нет. Не запускал T3 Code, поэтому оценки «как работает» — по документации и коду, не по прогону.

## 0. Главное

1. **Версии «1.0.0» у апстрима нет.** Теги: …`v0.0.45` (02.10), **`v0.1.0` (15.10)**, `v0.1.1` (20–21.10), дальше nightly `v0.1.2-*`. Скорее всего разработчик Multicast называет «1.0» релиз **v0.1.0 = «Orchestrator V2»** (мобильное приложение при этом идёт как «T3 Code 2.0»). «Форк 0.4» — вероятно 0.0.4x (сентябрь–начало октября) либо буквально 0.0.4 (март 2026); уточнить у них. От этого зависит размер скачка (п.4).
2. T3 Code — не конкурент Orchestra по назначению, а **соседний класс**: интерактивная «панель управления агентами» одного разработчика (десктоп/веб/мобайл поверх Claude Code, Codex, Cursor и др.). Orchestra — автономная многопроектная фабрика с трекером задач, квотным допуском, мерж-конвейером и Telegram. Пересечение есть (воркеры, worktree, чат, делегирование), но оси разные.
3. Лучше нас T3 Code в: нативном мобильном/десктопном клиенте, числе провайдеров, event-sourcing с идемпотентными командами, форке/переключении провайдера в треде, серверной очереди сообщений, scheduled tasks/webhooks, usage-экране по всем провайдерам. Хуже/нет: задачи и пайплайны, квотный допуск и учёт подписочных пулов, многопроектный оркестратор с иерархией ролей, мерж-гейты и приёмка, правила/KB, Telegram.

**Как ведёт агентов** (по коду `apps/server/src/provider`, `packages/*`):
- Claude Code — через официальный `@anthropic-ai/claude-agent-sdk` (TS) — то же, что делаем мы (`app/backend_claude.py`, python-SDK).
- Codex — через **app-server JSON-RPC** (`packages/effect-codex-app-server`) — то же, что наш `app/backend_codex.py` + `backend_jsonrpc.py`.
- Cursor — официальный `@cursor/sdk` (раньше CLI); Grok Build, OpenCode (1.x и 2.x, свой сервер на инстанс), Pi (RPC-режим), Muse Code, Antigravity (с собственным установщиком и профилем аккаунта) и **ACP Registry** (любой агент из реестра Agent Client Protocol: Devin, Cline, Kimi, Droid…).
- «Инстанс» провайдера = отдельный аккаунт (несколько аккаунтов Codex/Claude параллельно, изоляция HOME/keychain).
- Не API-ключи, а CLI/подписки пользователя — как и у нас.

## 3. Что делает лучше нас, что мы делаем, а он нет

**Лучше (с доказательствами из репо):**
- *Надёжность команд.* Event log + receipts + outbox в одной транзакции: «подтверждение команды = намерение зафиксировано, не исполнено» (`docs/internals/overview.md`, раздел Durable intent). У нас эквивалент размазан по `message_deliveries`/`initial_deliveries`/`merge_operations`.
- *Версионированный контракт клиент↔сервер.* RPC-схема `packages/contracts/src/rpc.ts`, дескриптор окружения с capability-флагами (напр. `threadPullRequests`), правило «персистентные события обязаны декодироваться при replay». У нас такого слоя нет — клиент и сервер деплоятся вместе.
- *Широта провайдеров и мульти-аккаунт* (8+ драйверов, инстансы с изоляцией кредов).
- *Нативные клиенты и relay без проброса портов.*
- *Очередь сообщений и steer* на сервере; fork треда; чекпоинты на ход.
- *Тестовая культура:* replay-фикстуры провайдеров (`record:claude-replay`, `record:cursor-replay`), perf-тесты wire-протокола.

**У нас и нет у него:** квотный допуск по пулам подписок (его «Limited» — реакция, наш `quota_gate` — предупреждение); задачи/пайплайны/роли/приёмка; иерархия оркестраторов и фабричная работа над несколькими проектами; мерж-гейт и diff-бюджет; KB, правила, temp rules; Telegram как основной канал; учёт стоимости по подписочной формуле (у них — API-эквивалент, прямо оговорено «not your subscription bill»); защита от runaway/stall (`runaway_guard.py`, `stall_signals.py`).

**Честная оговорка:** «лучше» — это сравнение по доке и структуре кода, а не по прогону. Заявленное качество (скорость, память) не проверял; их же issue-трекер (2 611 открытых) и пометки «rawish» от Multicast говорят, что V2 свежий.

## 4. Скачок 0.0.4x → v0.1.0 (V2) для форка

Прямой diff v0.0.45→v0.1.0: 15 909 файлов, +1,88 млн/−0,53 млн строк (от v0.0.4: 28 319 файлов, 4 740 коммитов). Практически другая система. Что известно из release notes v0.1.0:

- **V2 оркестратор переписывает ядро**: запуск/остановка/очередь/resume ходов, субагенты, история. Для форка с правками в оркестрации V1 слияние = ручной перенос, не `git merge`.
- **БД: односторонняя копия.** При первом старте V2 копирует старую БД и импортирует треды; V1 хранит свою копию, изменения не синхронизируются. Откат на V1 теряет всё сделанное после миграции.
- **Протокол несовместим**: V2-сервер и V1-клиент не работают друг с другом; нужно обновить все серверы (включая фоновые сервисы и удалённые машины), все десктоп-приложения и мобильное (2.0).
- **Минимальные версии CLI**: Codex 0.159+, Claude Code 2.1.280+, Grok 1.0.13+, OpenCode 2.0.18+ (1.x ограниченно), Pi 0.80.5+. Старые установки Codex/Claude у Multicast придётся обновить.
- **Убрано/изменено**: профиль браузера десктопа новый (повторный логин на сайтах), отдельная панель агентов удалена (lineage), контролы Workspace/Git/scripts переехали в «thread details», настройка токен-за-токеном стриминга удалена, у Grok нет Auto-accept edits, субагентные треды read-only, Cursor перешёл с CLI на SDK, смена провайдера в треде — lossy.
- **Новое, что надо ревьюить в форке**: `delegate_task` и T3 Code MCP дают агентам управление тредами — для корпоративного форка это новая поверхность (самоодобрение прав запрещено, но проверить); «Continue threads after restarts» включается настройкой.
- v0.1.1 (20.10) — исправления/рефакторинг мобильного дизайна-системы и CI; ломающего в нём не вижу в заметках.
- Нестабильность: ветка `main` ежедневно выпускает nightly/preview; для форка разумно ориентироваться на tag `v0.1.1`, не на main.

Для Multicast: **так как у них форк, лицензия MIT, а апстрим перерабатывает ядро**, цена будущих слияний выше, чем у обычного форка; разумно держать свои правки на границе (провайдер-драйверы, UI-тема), а не в `orchestration-v2`.

## 5. Что взять (кандидаты, не решения)

Это предложения для владельца; ничего не реализовано (исследование).

1. **Чекпоинт + откат на ход** — понятная пользовательская ценность, независима от остального. M.
2. **Fork треда с нативной историей** (Codex/Claude native fork) — для сравнительных попыток. M.
3. **Чтение локальной истории провайдеров** для учёта расхода вне наших сессий. S–M.
4. **ACP-вход** как универсальный адаптер — расширяет набор моделей без бэкенда на каждого. M; архитектурный — выбор за владельцем.
5. **Webhook-триггеры с проверкой подписи/дедупом** поверх `bg_jobs`. S–M.
6. **Контракт клиент↔сервер с capability-флагами** — только если появятся независимо обновляемые клиенты. Сейчас не нужен.

Не брать: нативные мобильные клиенты, встроенный терминал, source-control за пределами GitHub, замену хранения на event sourcing (архитектурный форк, требует решения владельца до любой реализации).
