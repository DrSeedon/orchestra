## Правило «можно удалить без потери» (`app/worktree_cleanup.py`)
Файл удаляется, только если выполнены все условия:
1. Копия чистая: `git status --porcelain` пуст (нет изменённых и неотслеживаемых-неигнорируемых файлов), не идёт merge/rebase/cherry-pick/revert, и ни один процесс не работает внутри (cwd) и не держит в ней открытый файл (`/proc/*/cwd`, `/proc/*/fd`).
2. Файл игнорирует `.gitignore`, отслеживаемый в самом репозитории (`git check-ignore -v`). Файлы, игнорируемые через `info/exclude` или глобальный excludes, не трогаются: там Orchestra и пользователь помечают то, что подложили сами (`.claude/`, `AGENTS.md`, `codex_sessions.json`).
3. Это не файл, который Orchestra копирует в каждую копию (`CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `.env`, `.worktreeinclude`), и он не внутри каталога окружения (`.venv`, `venv`, `node_modules`, `.git`). Они совпадают с основной копией по построению, и их удаление сломало бы воркера.
4. Его содержимое есть в другом месте, и это проверено:
   - `in_target_branch`: blob-id файла (`git hash-object`) входит в дерево целевой ветки — файл восстанавливается из git;
   - `in_main_checkout`: тот же путь в основной копии — обычный файл с теми же байтами (побайтное сравнение; так katya-work переносит результаты в основную копию перед закрытием воркера);
   - `cache`: файл внутри `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache` — пересоздаётся инструментами.

Неотслеживаемый результат, которого нет ни в целевой ветке, ни в основной копии, не удаляется. Перед удалением копия проверяется ещё раз (условие 1), а у каждого файла — размер и mtime. Изменившийся после плана файл остаётся. Удаляются только сами файлы и каталоги, опустевшие от этого удаления; основная копия не меняется. Удаление идёт через `unlink` проверенных файлов: корзина не освободила бы место, потому что лежит на том же диске.

## Где срабатывает
- **После каждого успешного `merge_worker`**: `_run_operation` вызывает `_clean_worktree_after_merge` после того, как результат операции записан. Поэтому очистка не задерживает и не меняет исход мержа, а ошибка только пишется в лог (`post-merge worktree cleanup …`). Цель сравнения — целевая ветка мержа, основная копия — корень репозитория копии.
- **Разовый или повторный проход**: `uv run --frozen python scripts/worktree_cleanup.py [--apply] [--root <каталог worktrees>] [<worktree> …]`. Без `--apply` — пробный прогон, вывод — одна JSON-строка на копию.

## Ограничения
- Проверка процессов видит только процессы пользователя `kesha` (чужие `/proc/*/fd` не читаются); воркеры работают от `kesha`.
- Если после мержа CLI воркера ещё жив с cwd в копии, очистка этого мержа откажет («process(es) use it») и сработает при следующем мерже или ручном проходе. Во время замера ни у одной простаивающей копии, кроме моей, процессов не было.
- После мержа между проверкой и удалением воркер может начать следующую задачу. Перепроверка процессов и mtime сужает это окно, но не закрывает до нуля. Даже тогда удаляется только то, что лежит в целевой ветке или в основной копии.
- `.venv`, `node_modules` и уникальные результаты правилом не освобождаются. Это и есть основная масса места в копиях; удалить её можно только решением владельца по конкретным каталогам.
