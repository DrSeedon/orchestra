# V-939 — ролик «когда серверу не хватает памяти»

`video/scene.mp4`, 88,1 с, стиль «бумага», TeraTTS m1, фоновая музыка по умолчанию. Открывает сцена `cafe`, потому что инцидент был утром (09:20–09:46 CEST). Закрывает сцена `board`: на доске итоговая схема очков. Сборка: `python3 build_scene.py <animation.md> > scene.html`, затем `run.sh`. Скрипт запускает make.py через `ssh` под `choom -n 1000`.

## Откуда числа
- **Три OOM за 26 минут**: 09:20:53 → 09:46:52 CEST, V-921.
- **Память сервера 24 ГБ**: в дампе 6291320 страниц RAM, своп 16 ГБ, свободно 0 кБ (`V-921/logs/kernel-oom-0920.txt`).
- **Четыре ffmpeg первого дампа**: 7,47 + 3,91 + 3,86 + 2,03 = 17,3 ГБ RSS. Отрезки полосы и счётчик построены по этим значениям.
- **Надбавки на момент OOM**: у ffmpeg `oom_score_adj 0` (все три дампа), у Orchestra и агентов 800. Это поле есть в таблице процессов дампа; в отчёте V-921 его не было, я взял его из логов.
- **«800 = будто съел 80 % всей памяти»**: формула ядра badness = память + adj/1000 · (RAM + своп). Это документация ядра, на которую ссылается V-921.
- **Очки**: у рендера 9,6 ГБ (7,47 RSS + 2,16 своп у крупнейшего ffmpeg), у Orchestra 0,5 ГБ (337,7 МиБ RSS + 209,6 МиБ своп). У агента 0,3 ГБ — это порядок величины из второго дампа (195–279 МиБ RSS + 47–61 МиБ своп).
- **После исправления (V-924)**: процессы агентов получают 1000. `ssh kesha@localhost` без `choom -n 1000 --` блокирует правило `ssh_agent_oom_priority` (`app/shell_policy.py`). У группы agents 14 ГБ памяти и 1 ГБ свопа при 16 ГБ у сервиса (`memory.max` и `memory.swap.max`, прочитаны 17.10).
- **Живая проверка 17.10 (сам)**: у моего процесса `oom_score_adj` 1000, cgroup `orchestra.service/agents/workers`. У API (MainPID) 800, cgroup `orchestra-api`.

ГБ на экране — двоичные гибибайты, как в дампах.

## Честный минус в ролике
- Первым теперь гибнет работа агента, и её придётся запускать заново.
- Запуски через ssh только помечены, а не ограничены лимитом группы, поэтому память всё ещё может кончиться.
