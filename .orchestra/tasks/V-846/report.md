# V-846 — pre-execution shell policy

## Decision and basis

V-844 inspected 522 shell-call candidates over 2026-10-07–14; 404 had a recognized shell sleep, totaling 4.786 hours of numeric pauses. Process/log polling accounted for 248 calls and 4.128 hours; waiting for subagent output files accounted for 23 calls and 0.417 hours. Only six calls were short process-completion checks, totaling 0.002 hours; examples used `sleep 1`, while the report also records a bounded 5-second restart check. The guard therefore allows sleeps through 5 seconds and blocks longer or unparseable durations. A `timeout` wrapper is measured by its effective bound for a sleep: `timeout 5 sleep 60` is permitted, while `timeout 30 sleep 60` is blocked.

The search threshold follows the equal-result replays in V-844: a scoped workflow path search took 1.64 seconds with `find` and 0.28 seconds with `rg --files` (83% faster), and a skill-path search took 5.70 seconds with `find` and 0.84 seconds with `rg --files` (85% faster). The `find | head` comparison was not counted because ordering changed the returned paths. Plain `grep` remains permitted, including as a pipe filter. Recursive `find` is blocked for path/name/type searches; commands using metadata, time, output-format, tree-control, or action semantics that `rg` cannot replace pass this performance guard (`-newer`, `-mtime`, `-delete`, `-exec`, `-printf`, depth and permission predicates). `find -delete` still hits Claude's pre-existing destructive-command guard; this task does not expand that separate rule to the other runtimes.

## Implementation

`app/shell_policy.py` is the sole owner of the 5-second threshold, shell parsing, exception list, and refusal text. It recognizes shell separators and loops, `timeout`, environment/command wrappers, nested `sh -c`, heredocs, and guarded commands inside `find -exec`; shell scripts supplied only by path are opaque to this command-text classifier. V-844 also found 23 Python heredoc AST candidates for `time.sleep`/`asyncio.sleep`, but the report could not establish execution for those calls, so this shell-utility guard does not reject Python code based on unexecuted AST candidates.

Claude always installs its existing Bash `PreToolUse` hook, regardless of `CLAUDE_BASH_HOOK_ENABLED`, and that hook invokes the shared classifier. Codex 0.160.0's app-server PreToolUse hook did not intercept shell execution nested inside code-mode `exec` (`tools.exec_command`): a live run showed `sleep 10` and `find` executing despite the configured hook. The backend now prepends a private per-session `CODEX_HOME/policy-bin` to the app-server PATH. Each wrapper checks `/proc` process ancestry and classifies only when the caller is the Codex `app-server` itself or a shell chain reaching that app-server. A process-tree trace showed direct `sleep` as an app-server child and the `find` pipeline as its `bash -c` child; a Python `subprocess.run` child was parented by Python, and a shell-script sleep by `/bin/sh ./x.sh`. Those application/script children pass through to the real executable. A process chain containing Python, Node, make, or a script interpreter stops classification. If `/proc` cannot establish the Codex caller chain, the wrapper passes through to avoid changing unrelated programs. Codex keeps `approvalPolicy=never`; it does not depend on interactive command approvals.

Grok's launch previously passed `--always-approve`, which bypassed per-tool permission requests. That flag is removed. ACP permission requests now inspect the shell call before execution, select a one-time allow for permitted shell commands, and select a reject option for policy violations; the rejection reason is attached to the resulting tool error and the permission handler queues a session violation event immediately. Non-shell permissions retain the existing approval behavior. Orchestra's harness checks the same policy before built-in Bash dispatch.

The session event handler writes each policy refusal as a `policy_violation` log entry with the rule, tool, and explanation; the associated `tool_result` remains in the transcript. Codex derives the event from its wrapper's refusal output, independent of the shell pipeline exit code; Grok emits one directly from the permission callback. Each row is one occurrence, so totals and per-agent/per-rule counts can be grouped from `logs` (`type='policy_violation'`) by session and the JSON `rule` field. The entry is visible in the session log.

The general prompt now has one English instruction directing agents to `bg_create` for long waits and `rg` for recursive search. Enforcement does not depend on that prompt.

## Remaining boundary

Claude, harness, and Grok's permission callback classify submitted command text; Codex's PATH wrappers additionally catch direct tool-shell invocations through ordinary PATH lookup, including commands inside `find -exec`. Application subprocesses and shell scripts pass through. An absolute utility path or replacement PATH remains outside the measured Codex coverage. Grok's live behavior remains unverified without credentials. Python changes require an Orchestra restart before live sessions load this enforcement; only the owner may initiate it.
