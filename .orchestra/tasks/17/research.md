# #17 — исследование: почему мерж падает на «worker HEAD changed» и «session branch changed»

## Вопрос

- **Контекст**: `merge_worker` — durable-операция: снимок личности воркера (ветка + HEAD)
  принимается один раз, потом исполняется, причём между принятием и git-работой стоит
  ожидание чужого хода (замер из #16: 58.3 с у payroll; git-работа при этом занимает 0.13–0.73 с).
- **Проверяемое утверждение**: оба падения — «worker HEAD changed before merge» и
  «session branch changed before merge» — одна болезнь: состояние снимается заранее и к
  моменту действия протухает.
- **База сравнения**: они могут быть двумя разными дефектами, у которых совпал симптом.
- **Измеримый исход**: воспроизвести оба падения в тесте и показать, лечит ли одно
  изменение оба, или нужны два разных.

## Гипотезы и их фальсификаторы

**H1 — «пин до ожидания».** HEAD фиксируется до `_wait_for_merge_idle`, воркер коммитит
за время ожидания, равенство HEAD ломается.
*Фальсификатор*: если бы merge перечитывал HEAD после ожидания, либо падение приходило бы
из другого места — H1 неверна.
**Итог: ПОДТВЕРЖДЕНА** (замер A ниже + код).

**H2 — «одна болезнь на двоих».** Второе падение (`session branch changed`) — тот же
протухший снимок.
*Фальсификатор*: если во втором сценарии нет никакого ожидания и починка H1 его не лечит —
H2 неверна.
**Итог: ОПРОВЕРГНУТА в узком смысле, ПОДТВЕРЖДЕНА в широком** — см. раздел «Одна ли это
болезнь». Ожидания там нет вовсе; общее у них другое.

**H3 — «БД разъезжается с git сама по себе».** Рассинхрон возникает без чужого вмешательства.
*Фальсификатор*: если в коде нет пути, где git уже переключён, а запись в БД не состоялась.
**Итог: ПОДТВЕРЖДЕНА**, путь найден дословно (`persistence_failed`, `routes/sessions.py:1143`).

## Замеры: оба падения воспроизведены

Тест-стенд — настоящий git-репозиторий и настоящий worktree, ожидание хода подменено
функцией, которая делает ровно то, что делает живой воркер: коммитит.
Сырой выхлоп (`pytest -s`, стенд-файл в Phase 1 не коммичу — он станет тестом в Phase 3):

```
A: False | worker HEAD changed before merge: expected fd71d3f121168b028957a6344e27047430b3321d,
                                             found e9834b0feb7ad6490729b401bbbb2fd7c2f7364f
A: head0 fd71d3f1 head1 e9834b0f потомок: True

B: ремонт → False | worker is already on branch 'task-18/worker'
B: в БД task-17/worker | в git task-18/worker
B: мерж → False | session branch changed before merge: expected task-18/worker, found task-17/worker

2 passed
```

Строка `потомок: True` — главная в этом замере: новый HEAD **является потомком**
запиннённого, ветка та же. То есть отвергается не расхождение истории, а обычный коммит
воркера, сделанный ровно в то окно, пока мерж ждёт его же хода.

## Механика A (`worker HEAD changed`)

1. `merge_operations._session_snapshot()` (строка 345) читает ветку и HEAD **из git**
   и кладёт в `accepted_worker_head` при приёме операции.
2. `_run_operation` → `_verify_accepted_snapshot` (строка 358) сверяет снимок с git ещё раз —
   всё ещё **до** ожидания.
3. `execute_merge_session` (`routes/sessions.py:720`) пиннит `pinned_head = expected_head`
   на строке 806 и только на строке 843 зовёт `_wait_for_merge_idle`.
4. Ожидание — `session.wait_for_turn_completion()`, десятки секунд.
5. После ожидания `merge_worktree_to_main` сверяет `expected_worker_head` с живым HEAD
   (`workspace.py:1075`) и падает.

Между шагами 3 и 5 у воркера полный ход, в течение которого он ОБЯЗАН коммитить —
это прямое требование его же промпта («ALWAYS commit before reporting DONE»). То есть
система штрафует воркера за выполнение собственного правила.

Диагностика: сообщение `worker HEAD changed before merge: expected X, found Y` не отличает
«воркер дописал коммит поверх» от «историю переписали» — оркестратору не за что зацепиться.

## Механика B (`session branch changed`)

Тут два источника правды сравниваются на равенство:

| что сравнивается | откуда берётся |
|---|---|
| `expected_branch` (снимок операции) | **git**, `inspect_worktree_identity` (`merge_operations.py:345`) |
| `row_branch` | **БД**, `sessions.branch` (`routes/sessions.py:752`) |

Пока они совпадают, всё работает. Разъезжаются они на одном конкретном пути:
`switch_branch` (`routes/sessions.py:1136`) сначала делает git-переключение, потом пишет в БД;
если запись падает, возвращается `state: "persistence_failed"` — **git уже на новой ветке,
БД на старой**.

Дальше система запирается:

- `switch_worktree_branch` отказывается чинить: `if original_branch == new_branch:
  return {"ok": False, "error": "worker is already on branch ..."}` (`workspace.py:1693`);
- поскольку `ok=False`, вызывающий код не доходит до `persist_lifecycle` — БД остаётся
  старой (`routes/sessions.py:1143`, `manager.py:751`);
- `merge_worker` отказывается мержить: `session branch changed before merge`.

Ремонтный инструмент отказывает **именно потому, что git уже в нужном состоянии**.
Идемпотентность (повтор безопасен) перепутана с ошибкой (повтор запрещён).

## Одна ли это болезнь

Честный ответ: **разные дефекты одного семейства, и чинить надо оба, но одним понятием.**

- Общее: и там, и там система держит ЗАПОМНЕННУЮ личность воркера и сверяет её с ЖИВЫМ git
  на строгое равенство, не имея ни одного пути, который бы их **сводил обратно**. Есть
  «совпало» и «отказ»; «расхождение безобидно, подтягиваю» не существует как состояние.
- Различие: в A расхождение создаёт время (пин до ожидания), в B — сбой записи; ожидания в
  сценарии B нет вовсе. Починка A (перечитать HEAD после ожидания) **не лечит** B — это и
  есть фальсификатор H2, он сработал.

Отсюда: две правки, но обе — про одно недостающее понятие «примирение личности». Класс
расхождения должен называться явно: `БЕЗОБИДНОЕ` (та же ветка, новый HEAD — потомок
запиннённого) против `ФАТАЛЬНОГО` (другая ветка, не-потомок: rebase, reset, чужая сессия).

## Риски и края

1. **Пин существует не просто так.** `accepted_worker_head` — часть durable-контракта:
   повторный вызов с тем же `operation_id` обязан слить то же самое. Если после ожидания
   молча брать новый HEAD, повтор операции сольёт БОЛЬШЕ, чем было принято. Поэтому
   «перечитать» — это не «забыть пин», а «принять дрейф и записать оба значения в результат».
2. **Быть потомком мало для безопасности.** Воркер за время ожидания может закоммитить
   мусор или WIP. Но это ровно то, что произойдёт и при повторном `merge_worker` секундой
   позже, — отказ не защищает, а только заставляет оркестратора повторять.
3. **`already on branch` как успех** снимает единственную защиту от «переключить на ту же
   ветку, но с другой базы»: `from_ref` при этом игнорируется. Ответ должен различать
   «уже там и база совпадает» (успех) и «уже там, но просят другую базу» (отказ).
4. **Гонка после ожидания.** Воркер может начать новый ход сразу после `idle` (входящее
   сообщение, bg-job). Перечитывание после ожидания сужает окно, но не закрывает его —
   значит классификация дрейфа нужна в любом случае, это не «на всякий случай».
5. **Общий рантайм.** Правки лежат в merge/session/worktree — по правилам проекта это
   зона обязательного ревью; Codex недоступен до 08.08, вердикта не будет.

## Чего я НЕ проверял

- Не воспроизводил падение на живой системе (только на стенде с настоящим git).
- Не измерял, как часто это случается в проде: замеры 58.3 с / 0.13 с взяты из описания
  задачи (разбор #16), сам я их не перепроверял.
- Не проверял, есть ли другие места, где снимок личности сверяется на равенство после
  долгого ожидания (`stop_worker`, `kill_worker`, авто-switch на `send_message`) —
  если фикс делать системно, это стоит грепнуть до плана.

## Вердикта Codex нет

Codex недоступен до 08.08 — второе мнение по исследованию не запрашивалось.
Самокритика:
1. Стенд подменяет ожидание функцией, которая коммитит мгновенно; в реальности между
   пином и коммитом проходят десятки секунд. На механику это не влияет (проверяется
   равенство, а не время), но «58 с» в моём замере не участвуют.
2. Вывод «разные дефекты одного семейства» держится на том, что в B нет ожидания. Если
   окажется, что в живом инциденте `switch` тоже стоял за ожиданием, границу придётся
   пересматривать — я не видел журналов того инцидента, только описание оркестратора.
3. Классификация дрейфа как «потомок = безобидно» — моё предложение, а не измеренная
   истина. Ему нужен отдельный контр-пример в Phase 2: воркер, который за время ожидания
   сделал `git commit --amend` (потомком не будет) и воркер, который сделал два коммита.
