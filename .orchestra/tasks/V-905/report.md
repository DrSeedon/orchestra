# V-905: пост Anthropic «Solving code review» против нашего контура

Класс B, только чтение. Код и промпты не менялись. Скрипт: `rollback_rate.py`, вывод: `rollback_rate.out.txt` (в этой же папке).

## 1. Первоисточник против пересказа

Источник: https://claude.dev/blog/solving-code-review-at-anthropic/ (WebFetch отдаёт пересказ страницы, не дословный текст; цифры ниже оттуда, картинка с поста прочитана: «Layers, not one gate», шесть слоёв: verification, required CI, AI review, security review, human approval, merge queue + flags, под ними fast rollback).

Что подтвердилось: Claude пишет ~90% кода Claude Code; смёрженных PR с июня по сентябрь больше чем вдвое, доля откатанных упала больше чем на 40%.

Что пересказ потерял или сгладил:
- **«Откат» не определён.** Статья говорит только «сломанные сборки откатываются» и называет revert/incident rate *предохранителем*: если растёт, человеческое время лишь переехало, а не сэкономлено. Знаменатель (все смёрженные PR) и окно наблюдения не названы. «−40%» это относительное падение доли, абсолютных значений нет.
- **Уровни риска:** низкий (доки, тексты, внутренние фичи, аддитивное под флагом) — без человека, когда зелёные автопроверки и security-ревью; средний (обычные изменения плюс чувствительные зоны: кеш, автообновление, системные промпты) — один человек; высокий — двое. Уровень ставит *классификатор по изменению, не по автору*; второй классификатор проверяет, нужен ли человек всё равно. Файлы CI-workflow и чувствительные пути всегда требуют человека. Одобрение агента не считается человеческим; тот, кто поставил задачу агенту, считается обязательным ревьюером; одобрение действует на один коммит. Слабый пункт: circuit breaker (ужесточать допуск при росте откатов) пока не сделан.
- **Кто проверяет проверяющих:** найденные ошибки голосует отдельная группа агентов (постится только при достаточном согласии, ранги Important/Nit/Pre-existing; стиль и cleanup отсекаются). Шум меряют реакцией авторов (исправлено/неверно/намеренно/не важно) и прогоном на заведомо чистых PR. Ежедневный eval: набор из прошлых инцидентов и откатов, подтверждённый экспертами; изменение промпта/инструмента/модели остаётся, только если балл вырос.
- **Сходимость:** один PR прошёл 50+ раундов ревью за ночь; 59% повторных замечаний — код, существовавший до первого прохода. Лечение: потолок 3 раунда, повторное ревью только по диффу, флаг на класс бага, без повторов. На внутренних PR: «проходит за один раунд» 65%→78%, «пять и больше раундов» 8,9%→1,5%, среднее число ревью 2,08→1,32.
- **Модели и стоимость: не названы, цифр стоимости нет.** Это прямой ответ на вопрос задачи: пост не позволяет посчитать цену по подписке или API.
- Метрики человеческого времени: одобрений на PR (медиана и p95), комментарии, время ожидания человека; время считают вместе с откатами/инцидентами (это и есть «разбор последствий»).

## 2. Как у нас сейчас

- **Тест-гейт merge_worker:** `app/merge_test_gate.py`. Подмножество `tests/test_<stem>.py` для изменённых `app/*.py` (плюс `test_routes_surface.py` для routes/main), не полный сьют; `live_probe` отключены; таймаут на узел; убитый бюджетом прогон с уже напечатанным FAILED считается красным. Признанная дыра: модуль без одноимённого теста не проверяется.
- **Мутационный гейт:** `evaluate_mutation_gate` (там же, ~839–985). Меняет только исходники на состояние цели, гонит изменённые тесты в одноразовом дереве и контрольно на ветке; `PASSED/guarded_source_change` только если узел зелёный в контроле и красный на мутации, `FAILED/tests_not_guarding_source`, если тест не заметил дельту. Это проверка «тест краснеет», сделанная механизмом (правило code-quality.md: «a mutation proves nothing unless the test it reddens is COMMITTED»). Не охватывает: изменения без тестов, промпты, конфиги, документы.
- **acceptance_command:** `app/acceptance.py`, платформа запускает команду приёмки, а не воркер; без шелл-синтаксиса, таймаут 180 с по умолчанию.
- **Оркестратор:** `modules/orchestration.md` («Acceptance rests on the diff, the tests and your own mutation check», `merge_worker(expected_head, acceptance_note)`). Единственное «одобрение» — решение оркестратора; человек (владелец) в каждом мерже не участвует, то есть у нас фактически «низкий риск без человека» для всего, плюс владелец сам решает рестарт и платные траты.
- **Модельное ревью:** заморожено владельцем 20.09.2026, коммит `643d4721` (`#V-597`). Дословная причина из комментария в `app/mcp_stdio.py:3973`: «заморозь чтобы никто не мог вызвать убери тул закоменти и в промптах тоже закоменти»; пояснение там же: ревью своей работы воркером Codex «стоило целого фонового прогона и ничего не решало». Тул снят с регистрации, тело функции и тесты оставлены (вернуть = декоратор + строки про `codex-debate`). Решение владельца, не результат замера; отчёта V-597 в `.orchestra/tasks` нет, в KB про причину заморозки записей нет (`rg` по `.orchestra/kb`, `.orchestra/tasks`: 40+ файлов с совпадениями, все про упоминания в промптах/отчётах, ни одного замера эффективности).
- **Что реально лежит в БД** (`review_receipts`, read-only): 1098 строк, из них 73 — настоящие ревью (`runtime=codex`: implementation 47, exec 17, review 5, skip 2…) с 03.09 по 20.09, ни одной после заморозки; остальные 1025 — `task_run`-квитанции жизненного цикла, не ревью. Из 73: completed 64, failed 9; у 64 завершённых вердикт-классификация по тексту: approve/ACK 29, changes 29, без вердикта 15 (классификация по подстроке, грубая); рецензент почти всегда gpt-5.6-luna (70 из 73); среднее время завершённого 2,1 мин (макс 7,4). То есть «целый фонов прогон» по времени не подтверждается (2 мин); возможно, имелась в виду цена слота/контекста воркера или токены — это не измерено, а общий пул нельзя делить на ревьюеров (KB models-and-quotas: «Дельта общего пула не была расходом выбранных агентов»). Валидность замечаний (сколько из 29 «changes» были реальными дефектами) нигде не размечена.

## 3. Наш аналог метрики

**Правило (записано до подсчёта, закреплено в шапке `rollback_rate.py`).** Единица: коммит первой линии `main` с префиксом задачи (`#N:`, `V-N:`, `#V-N:`, опц. `WIP`), группировка по ключу задачи (`V-N` и `N` — разные ключи). Откат: позднейший коммит `Revert "…"`/`revert`/`откат` в начале темы или `This reverts commit <sha>`, цель определяется по sha, цитируемой теме или явной ссылке на задачу. Починка: позднейший коммит ДРУГОЙ задачи в пределах 14 дней от последнего коммита исходной, явно называющий её (`#N`/`V-N`) и с «fix/исправ/чин/регресс/hotfix/follow-up/доработ» в теме. Задача «плохая», если любой её коммит откачен или починен. Задачи младше 14 дней от конца истории исключены (цензурирование справа). Срез: 30.04–17.10.2026, 2787 коммитов первой линии, 693 задачи, 481 допустимая.

**Вывод по шуму: сравнение до/после 20.09 ничего не показывает.** Точный тест Фишера 8/439 против 0/42: p=1,0. Верхняя 95%-граница при 0/42 по «правилу трёх» ≈7%, то есть ниже 1,8% опустить нельзя. Плохие события сидят в одном июньском кластере (5 откатов 12–13.06, эпоха клиентских инстансов и экспериментов с дашбордом) — в сентябре их два: `V-600` (откат правила «один AGENTS.md» 19.09, до заморозки, политика владельца) и `V-621` (откат случайно влитой миграции каталога, ошибка слияния, не дефект кода). Ни одно из событий после июня не похоже на баг, который нашло бы код-ревью. Объём и тип задач за период менялись: задач на 14 дней 49 (06.09), 55 (20.09), 198 (04.10), в последнее окно сильно выросла доля исследований/отчётов (V-8xx), по которым «откат» теряет смысл. Метрика грубая: ловит только явные откаты и явные ссылки; тихие правки без ссылки не видны, поэтому 0,5–1,8% — нижняя оценка. Их «−40%» и наше «0 против 1,8%» несравнимы: у нас пол ~1%, у них масштаб 30 000 изменений в день.

## 5. Возвращать ли ревью

**Мой вердикт: владельцу не предлагать возврат ни в каком виде, пока нет замера; предложить только замер.** Опора: (а) решение владельца 20.09 и его слова, а не данные, — данных против него нет; (б) наш пол откатов ≈1%, у 8/439 против 0/42 различий нет (p=1,0), улучшать почти нечего; (в) то, что мы откатывали, в основном политические и случайные события, не дефекты кода; (г) у Anthropic ревью работает как многоуровневая система с голосованием и ежедневным eval — у нас был один рецензент и ни одной разметки полезности; (д) пост не даёт цены.

Что вообще сомнительно в моём выводе: тихие дефекты (исправлены без ссылки и без отката) метрика не видит; 29 из 64 завершённых ревью требовали изменений (≈45%), это сигнал, что рецензент находил что-то, но реальность замечаний не размечена.

**Минимальный замер (не запускался).** Офлайн-воспроизведение, без возврата тула в рабочий контур:
1. Выборка: 9 «плохих» задач из `rollback_rate.py --list` плюс ~40 случайных чистых, смёрженных ≥14 дней назад (дифф берётся из `git`, слепая разметка).
2. Рецензент: один проход Luna в read-only песочнице на каждый дифф, потолок 3 раунда, diff-only (их приёмы).
3. Разметка: для каждого замечания «реальный дефект / шум / предсуществующий код» — вручную или независимо вторым прогоном по воспроизводимому тесту; на 5–10 заметных «changes» из 29 существующих квитанций сделать то же ретроспективно (они уже есть в БД, `artifact_path`).
4. Метрики: recall на 9 плохих, доля реальных замечаний на чистых, платные токены (запись кеша + вывод) на дифф, а не процент пула.
5. Решающее правило, зафиксировать заранее: возврат обсуждать, только если recall ≥ половины на плохих задачах и ≥30% замечаний на чистых реальные; иначе вопрос закрыт данными, а не мнением. Объём: порядка 50 прогонов по 2 мин ≈ 100 мин машинного времени; платный остаток по подписке не вычислен (пул не делится, KB models-and-quotas).

Что не проверялось: тела `review_receipts` (текстов замечаний не читал), сама статья дословно (WebFetch даёт пересказ малой моделью; числа по нему, при расхождении верить оригиналу), стоимость токенов ревью по подписке.
