# V-1049 — служебная private-ссылка в проверках чистоты

Исправлено в рабочей копии. Push, рестарт и изменение живых сервисов не выполнялись.

## Причина и границы доказательства

Причина исходного инцидента в kesha-tg-bot **не подтверждена**: затронутая рабочая
копия удалена, её файлов и журнала переходов нет. Подтверждён дефект механизма:
проверки чистоты принимали Git status дословно, хотя игнорирование созданной
платформой ссылки зависело от локального неверсионируемого файла.

Воспроизведён конкретный путь в настоящем временном Git-репозитории:

1. Корневой `.gitignore` повторно включает `.orchestra/**` и перекрывает общий
   `info/exclude`. `ensure_private` создаёт ссылку и локальный `.orchestra/.gitignore`
   с `/private` и `/.gitignore`; рабочая копия чистая.
2. В новой базе появляется **версионируемый** `.orchestra/.gitignore` без `/private`.
3. `switch_worktree_branch` выполняет `reset --hard` к базе. Git заменяет локальный
   игнорируемый файл версионируемым. Ссылка остаётся, Git показывает
   `?? .orchestra/private`; прежняя финальная проверка смены ветки отказывает.
4. Повторный `ensure_private` не может исправить версионируемый ignore: существующий
   запрет на его изменение сохраняется. Sparse checkout/reapply проблему не устраняет.

Отдельный тест показал: обычные `plan_upload` → `write_tar` → `apply_changes` не
удаляют созданный локальный ignore, потому что он не входит в upload manifest.
Поэтому считать обычный hub sync-back установленной причиной инцидента нельзя.

## Исправление

`app/private_folder.py:filter_worktree_status` исключает ровно запись
`?? .orchestra/private`, только если это симлинк из рабочей копии на существующий
общий private-каталог **того же репозитория**, вычисленный через git-common-dir.
Состояние проверяется заново при каждом вызове, без кеша и изменения файлов.

Изменения отслеживаемых файлов, staged-ссылки, реальные каталоги/файлы, ссылки на
другие цели, сломанные ссылки и ошибки проверки не скрываются. NUL-парсер сохраняет
исходные имена rename/copy, даже если имя похоже на отдельную status-запись.

`app/workspace.py:_worktree_status` применяет этот контракт к WIP, merge, смене
ветки и их проверкам восстановления. Обработчик удаления в `app/routes/sessions.py`
использует тот же фильтр, сохраняя прежний таймаут Git status. Все эти чтения запрашивают
`--untracked-files=all`, чтобы служебная ссылка и пользовательский файл внутри одного
неотслеживаемого каталога проверялись раздельно.

Фильтр выбран потому, что локальный ignore нельзя сделать надёжным при произвольных
правилах проекта и замене файла через checkout/reset. Существующий `ensure_private`
и восстановление локального ignore сохранены. Hub upload/sync-back не менялись.

В `tests/test_workspace.py` заглушка ошибки Git status теперь распознаёт команду
с дополнительными флагами; проверяемый отказ и утверждения теста сохранены.

## Фактические проверки

- Штатный целевой запуск был предпринят:
  `uv run --frozen python -m pytest tests/test_private_symlink_dirty_v1049.py tests/test_workspace.py tests/test_hub_workspace.py -q`.
  Он **не выполнен**: имеющийся `uv` — shim, сообщивший
  `uv: not found on the hub and not inside a Mutagen-synced project (cannot forward via on-remote)`.
  У доступного Python 3.12.3 также отсутствуют pytest и FastAPI. Зависимости не устанавливались.
- Офлайн-замена:
  `TMPDIR="$PWD/.orchestra/tasks/V-1049/tmp" PYTHONDONTWRITEBYTECODE=1 nice -n 15 python3 -m unittest discover -s tests -p test_private_symlink_dirty_v1049.py -v`.
  **15 прошли, 1 пропущен** из 16: пропущен импорт полного обработчика с FastAPI.
  Это не штатный прогон uv/pytest. Лог: `unittest.log`.
- Прошли реальные временные репозитории с re-include, отсутствующим и версионируемым
  вложенным ignore, заменой через reset при смене ветки, sparse reapply,
  hub upload/apply/commit_sync и последующим `merge_worktree_to_main`.
  Проверены отрицательные случаи с пользовательским файлом, неверной целью ссылки,
  реальным private-каталогом, staged/отслеживаемой ссылкой, ошибкой Git и восстановлением ignore.
- Проверка чувствительности: при отключённом фильтре **все четыре** положительных
  регрессионных сценария падают с `.orchestra/private`; исключений окружения нет.
  Исходники при этом не менялись. Лог ожидаемых отказов: `reversion-check.log`.
- `route_guard_probe.py` исполнил **тело настоящего** `delete_session`, извлечённое
  через AST, с подставным менеджером и настоящим Git. Разрешена только служебная
  untracked-ссылка; пользовательский файл, неверная цель и staged-ссылка блокируются.
  Отключение фильтра возвращает ошибочный отказ. Лог: `route-guard.log`.
  Это проверка тела обработчика, **не HTTP-интеграция** и не импорт всего приложения.
- Все изменённые Python-файлы проверены на синтаксис, хвостовые пробелы и формы
  секретов; найденных секретов нет. Изменённые участки просмотрены вручную.
  `.git` в предоставленной копии отсутствует, поэтому Git diff и историю исходного
  checkout здесь проверить невозможно. Модули импортировались из этой копии `app/`;
  абсолютные пути среды не включены в отчёт согласно ограничению задачи.

## Что осталось и нужен ли рестарт

Оркестратору нужно запустить штатные целевые pytest-тесты, включая существующие
workspace/hub/sparse/merge-тесты и тест полного обработчика удаления. Полный набор
`uv run --frozen python scripts/run_tests.py` и контракт инструкций не запускались:
помимо недоступного uv, каталога `scripts/` в выданной копии нет.

Изменён серверный Python: **для применения исправления нужен штатный рестарт Orchestra
после принятия/выкладки**. Здесь рестарт не выполнялся. Исходный исторический инцидент
остаётся неподтверждённым; подтверждены описанный путь дефекта и исправленное поведение
во временных репозиториях.
