# #141 — tool-сообщения в TG доходят все

Жалоба юзера: «настрой чтобы тулы в ТГ видны были все». В топик приходила
малая часть вызовов тулов.

## Диагноз: молчаливая перезапись при коалесцировании, НЕ TTL

Исходная гипотеза в задании — три механизма про время и перегрузку:
`_TG_TELEMETRY_MAX_AGE = 15.0`, `_TG_TELEMETRY_CALL_TIMEOUT = 2.0` + `attempts = 1`,
и отсутствие `important=True` у `_send_expandable`.

**Замер эту версию не подтвердил.** На пачке из 30 вызовов тела терялись, а
счётчики дропов стояли на нуле:

```
telemetry_dropped:   0 -> 0
optional_dropped:    0 -> 0
telemetry_coalesced: 0 -> 29     ← вот куда всё уходило
```

Реальная причина — в `_tg_call_safe`. Все тулы одного агента шли с ОБЩИМ
ключом `telemetry_key = (thread_id, orch_name)`. При совпадении ключа очередь
делает:

```python
current.call_factory = factory   # фабрика следующего вызова затирает предыдущую
current.count += 1
```

Фабрика замыкает СВОЙ `text`, поэтому уезжает только последний вызов пачки плюс
приписка «N events coalesced». Потеря учитывается как `telemetry_coalesced`, а не
`dropped` — по счётчикам дропов её не видно, что и сбивало диагностику.

Существующий тест это фиксировал как штатное поведение:
`test_thousand_same_topic_tools_use_one_coalesced_entry` — 1000 тулов → 1
сообщение, выживает `tool-999`.

## Почему отвергнуты уникальные ключи (замером, не рассуждением)

Первая попытка — уникальный `telemetry_key` на каждый вызов, чтобы ничего не
схлопывалось. Схлопывание исчезло, но появилось:

```
TG send_message dropped: rate slot unavailable
```

Telegram даёт **20 сообщений на 60 секунд** в группу
(`_TG_GROUP_WINDOW_MAX = 20`, `_TG_GROUP_WINDOW_SECONDS = 60.0`). «Каждый тул =
отдельное сообщение» физически недостижимо: потеря просто переезжает из
коалесцирования в rate-лимит. Вариант отброшен.

## Решение: батчинг тел

Тела копятся в `batch_bucket` (список на пару `(thread_id, orch_name)`) и при
фактической отправке склеиваются в ОДНО сообщение через `\n\n`. Ключ
коалесцирования остался общим: схлопывание продолжает работать как клапан
перегрузки, но перестало терять содержимое.

**Инцидент с lock contention не воскрешён.** `important` не менялся вообще —
тулы остались косметикой (`important=False`, `wait_for_slot=False`) и не делят
очередь и retry-путь с текстом юзера. Правило «косметика и доставки не делят
очередь» соблюдено. Подтверждено замером: во время пачки из 200 тулов ответ
юзеру важным классом проходит за 2.1 мс, `reliable_overflow=0`.

## Замеры

| сценарий | было | стало |
|---|---|---|
| 30 тулов, потеряно тел | **28 из 30** | **0** |
| 30 тулов, сообщений в TG | 1 | 1 (бюджет rate-лимита не вырос) |
| 200 тулов | — | 0 потерь, 2 сообщения, `dropped=0`, `pending=0` |
| 200 тулов, ответ юзеру | — | 2.1 мс, не заблокирован, `reliable_overflow=0` |
| 20 тулов по 900 символов | — | 5 сообщений, 0 потерь, ни одного >4096 |

Счётчики снимались через `_tg_delivery_snapshot` до и после.

## Баги, найденные самопроверкой в собственной правке

Все четыре закрыты до сдачи, каждый — тестом.

1. **Склейка перерастала лимит 4096.** TG отбил бы сообщение целиком, то есть
   потерялась бы ВСЯ пачка вместо одного тула. Добавлена нарезка по лимиту.
2. **Хвост застревал в bucket навсегда** (16 из 20 тел): очередь этот вызов уже
   отработала, повторной отправки не было. Добавлен дослыл.
3. **Одно тело длиннее лимита уходило неразрезанным** — склейка ограничивала
   только объединение, но не размер одного body. Теперь режется `_split_message`.
4. **Исключение при отправке съедало вынутые тела.** Пачка уже вынута из bucket,
   при падении исчезала молча. Теперь возвращается в bucket и уезжает со
   следующим вызовом — для косметики это верный компромисс: без retry-шторма и
   без тихой потери.

Отдельно: при склейке сбрасываются `entities` — их offsets посчитаны под один
body и в объединённом тексте указывают не туда.

## Правка существующего теста — осознанная, не подгонка

`TestSendDiffImage::test_send_message_tool_text_uses_cosmetic_lane` пинил старую
форму ключа `(42, "orch", "send_message", 0)`. После фикса ключ стал
`("tool", 42, "orch")` — `chunk_index` в ключе больше не нужен, содержимое
копится в bucket.

**Смысловая проверка теста сохранена и усилена:** утверждение
`important is False` (тул остаётся косметикой и не лезет в reliable-полосу —
ровно то, что защищает от инцидента с deadlock) осталось на месте, к нему
добавлено `batch_bucket is not None`. Ослабления контракта нет: изменилась форма
ключа, а не гарантия.

Тест `test_thousand_same_topic_tools_use_one_coalesced_entry` НЕ трогался и
проходит — клапан перегрузки работает по-прежнему.
