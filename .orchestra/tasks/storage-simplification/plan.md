# Git-задачи и одна SQLite-проекция

Разрешено владельцем: упростить хранение, обеспечить офлайн-работу двух узлов с Git sync, включить V- для новых задач VPS и удалить старые слои. Уточнение при интеграции fe507ac6: старые пользовательские номера сохраняются.

Рабочая ветка: simplify/storage-and-task-prefixes. Worktree: /mnt/data/Projects/Python/orchestra-storage.

## Реализовано

- Один файл на задачу в приватном Git, одна проекция tm_tasks в основной SQLite. Git-коммиты принимают изменения; SQL восстанавливается после прерванной проекции. CAS проверяет локальную ревизию, namespace и UUID.
- Создание, чтение, обновление, привязка коммитов, назначение, архивация и финализация используют одного владельца. Порядок блокировок: Git, затем SQLite. Чужие транзакции не закрываются; собственные соединения закрываются явно.
- Префикс хранится в ref_prefix. Новые задачи VPS получают V-, обычные задачи сохраняют номера. Счётчики независимы, занятые каталоги evidence пропускаются. Git sync проверяет будущий merge до изменения ветки и отказывает при конфликте/утрате/смене идентичности.
- Схема версии 1 в app/schema.sql. Убраны повторяемые исторические миграции при старте. Старую БД нужно явно перенести офлайн; запуск её не переделывает.
- Удалены старый task adapter, девять модулей IA, RAG и ML-зависимости, переходные скрипты, /api/knowledge, /api/memory/reindex и /api/tm/repair-shadow-drift. Поиск читает Markdown и исходные журналы SQLite.
- Сохранены действующие архивы истории, merge receipts и защитные механизмы доставки. Результаты удалённых форматов остаются в Git-истории и исходных SQLite-снимках.

## Перенос данных на копиях

Подготовлены инструменты:

- python -m scripts.migrate_task_storage — новый приватный Git/SQLite-комплект; исходники не изменяются.
- python -m scripts.join_task_stores — объединение подготовленных историй с проверкой отсутствия коллизий.
- python -m scripts.sync_tasks — обычный Git sync с обновлением локальной проекции.

896 задач ноутбука и 749 задач VPS соединены в 1645 записей. Обе проекции приняли полный набор; 896 и 749 исходных локальных ID соответственно сохранились. Проверка внешних ключей после переноса: 0 нарушений на каждой копии.

Старые SQL-таблицы jobs, inbox, tm_clients, tm_payments, tm_payment_allocations, tm_sync_log и tm_task_create_requests сохранены в приватной Git-истории миграции и удалены из новой рабочей базы. Остальные таблицы, включая таблицы подсистем квот, перенесены с проверкой количества строк. Исходный SQLite backup() сохранён отдельно.

Обнаружены 33 коллизии UUID старого генератора: UUID зависел от project_id и SQL row_id без идентичности узла. У всех 33 различаются название, пользовательский номер и время создания; формула прежнего генератора проверена. Для VPS подготовлена детерминированная карта новых технических UUID, исходники сохранены. В исходном снимке нет ссылок на эти UUID из portfolio_task_links, portfolio_waits и review_receipts. Миграция откажет, если перед применением появятся необработанные ссылки.

Пересекающиеся исторические проекты VPS отделены; их пользовательские номера не меняются. Scope-привязки остаются локальными. Импортированный проект не получает выдуманный локальный путь. Рабочие проекты двух узлов не объединяются по одному лишь названию или пути.

Приёмочный контракт берётся из исполняемой SQL-записи вместе с аудитом: на VPS найден реальный случай, где SQL требовал проверку, а старый Git-снимок её не требовал. Оба исходных представления сохранены. Остальные переносимые бизнес-поля берутся из прежнего канона; расхождения отражены в приватных отчётах.
