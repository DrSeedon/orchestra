# V-1071. Folding subagents: исследование применимости к Orchestra

**RESEARCH DONE, 24.10.2026.** Здесь собраны факты, ограничения и материал для решения root. Архитектурная ветка не выбрана. Делегирование, модельный review, приложение, prompts/config и правила не менялись. Новое постоянное правило или отмена действующего из статьи не следуют.

## Что установлено и что остаётся решением владельца

Опубликованный kit можно исследовать и частично использовать как набор офлайн-инструментов без Claude Code, API и новых зависимостей. Это мы действительно сделали: 48 upstream tests, два smoke по 19 задач, ручной sample tools и пересчёт сохранённых real runs. Его управляющий workflow в основном является инструкцией модели. Он сам не находит архитектуру, не выполняет безопасную автоматическую миграцию и не обеспечивает правила Orchestra.

У статьи есть два разных вида свидетельств: непроверяемый снаружи рассказ о клиенте и открытый небольшой учебный пример. **Заявленные клиентские 2× нельзя переносить на нас.** У доступного примера fold улучшил среднее время, но потерял один ранее проходивший исход; as-tool не дал стабильного выигрыша во всех проверенных срезах. Источники и собственный пересчёт ниже позволяют root принять решение, не полагаясь на пересказ.

Для применимости нужна не метка роли «специалист», а наблюдаемый обмен: зависимые последовательные шаги, которым действительно нужен общий контекст, против независимого fan-out, крупного локального чтения, отдельных прав, веток и долгоживущего состояния. В Orchestra часть механики статьи уже существует: full-cycle исполняет этапы в одном контексте, skills/KB подгружаются выборочно, workers вызываются через tools и возвращают результат родителю. Но это не доказывает ни полезность, ни бесполезность какого-либо конкретного fold.

## Проверенные границы самого toolkit

`exemplar/edge_cases.py` реально вызвал неизменённые K scripts на трёх маленьких fixtures; `evidence/edge-cases.stdout` содержит полный вывод.

1. **Coupling не доказывает зависимость.** Два независимых читателя стартуют в каждом trace с перекрывающимися интервалами. K сортирует начала и предлагает merge с coupling100%. Он не анализирует parent-child edges/перекрытие: start timestamp sorting превращает fan-out в видимую последовательность. Для Orchestra нужен export с dependency/payload edges; временная близость сама не разрешает merge.
2. **Coverage может быть ложным.** В production fixture a→b; у единственного eval task rep0 вызвал только a, rep1 только b. K union по task показывает chain covered, exit0, хотя ни один повтор не прошёл всю цепь. Порядок a/b также не кодируется `by_agent`. Отсюда требуется проверка каждого trace/обязательных данных и конечного эффекта, не только зелёный coverage status.
3. **Exit0 compare не означает отсутствие регрессий.** Один safety-case pass→fail компенсирован ordinary-case fail→pass. Даже `--fail-if-worse` возвращает0 при равном среднем и печатает предупреждение про ухудшенный task. Значит CLI нельзя взять готовым автоматическим safety gate. Кроме того `actions` сравнивает имена writes, не параметры/порядок; равное имя не доказывает равные эффекты. Сравнение common tasks и пропуск error rows не заменяют явный полный план N×R.

Это ограничения использования отчётов, **не исправления и не реализация** kit. Upstream source оставлен неизменным. Advisory verdict модели или наличие TODO-заглушек в стороннем scaffold не является политикой Orchestra.
