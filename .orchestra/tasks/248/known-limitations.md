# #248 — известные ограничения (осознанные, не недосмотр)

Этот файл существует, чтобы следующий читатель не принял взвешенное решение за пропущенный

## 1. `POST /api/sessions/{name}/merge` без `operation_id` идёт по v2-lifecycle без журнала

**Что происходит.** Роут (`app/routes/sessions.py:1702`) прокидывает тело запроса в
`execute_merge_session`. Если тело содержит `merge_schema_version: 2` и `task_outcome`, то
платформенный lifecycle отработает (задача закроется), но `operation_id` пуст → журнала
операции нет, `PREPARED`-payload не сохраняется, трейлер `Orchestra-Operation:` в коммит не
попадает, восстановление по трейлеру для такого мержа невозможно в принципе.

Найдено внешним ревью T3 (`review-impl-t3-opus.md`, suggestion).

**Почему НЕ чиним — два независимых основания.**

1. **Живых вызывающих нет.** `app/mcp_stdio.py` в `main` ходит только в
   `/api/merge-operations` (`operation_id` там обязателен и генерируется клиентом);
   вызовов из дашборда нет вовсе (`grep` по `static/` — пусто). Единственное историческое
   использование этого роута MCP-клиентом относится к эпохе до появления журнала операций
   (коммиты `daa9191b`, `273e13db`). То есть сегодня по этому пути не ходит никто, кроме тестов.

2. **Загейтить нельзя, не покрасив замороженный оракул.** Очевидная защита — «v2 требует
   `operation_id`, иначе отказ» — невозможна: тесты T3 в `tests/test_task_tracker_integration.py`
   (заморожен на `b7ad6c76`, неприкосновенен) сами зовут `execute_merge_session` с
   `merge_schema_version: 2` и БЕЗ `operation_id` — например
   `test_t3_complete_merge_atomically_links_and_closes_current_task`. Fail-closed здесь
   означал бы правку неприкосновенного файла.

**Статус: латентная ловушка для БУДУЩЕГО вызывающего, а не сегодняшний путь мимо учёта.**
Опасность реализуется только если кто-то напишет нового клиента, который шлёт
`merge_schema_version: 2` в этот роут вместо `/api/merge-operations`. Правильное лечение в
этот момент — не гейт в роуте, а перевод нового клиента на журнальный путь.

Решение принято оркестратором 13.08.2026 после оценки радиуса; отклонение зафиксировано
здесь намеренно, по правилу «удалил очевидное решение — запиши отвергнутый вариант и причину».
