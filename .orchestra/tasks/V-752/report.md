# V-752 — VeriHarness: что переносится в Orchestra

Исследование выполнено 2026-10-07; код и README проверены на `google-research/veriharness` `main`, commit [`0f10db9818920f8d79641b23d9311c4877f67702`](https://github.com/google-research/veriharness/commit/0f10db9818920f8d79641b23d9311c4877f67702), от 2026-10-02. Статья — arXiv v1 `2610.00972`, подана 2026-10-01. В репозитории лицензия Apache-2.0. Ниже помечаю результаты статьи отдельно от выводов о переносе.

## Что в действительности утверждают статья, код и сайт

VeriHarness получает десять независимых rollout одного и того же агента на задачу. Затем идут четыре модельных хода в трёх изолированных контекстах: параллельный disagreement resolver проверяет альтернативные утверждения по данным среды; consensus challenger ищет ошибку или пропуск в общем для всех ответе; свежий adjudication контекст получает задачу, rollouts и обе записи, выбирает базовый артефакт и план корректировок; delivery в том же контексте меняет выбранный артефакт и сохраняет запись о ремонте. Проверки и выбор остаются решениями модели, а программный gate в README описан как content-blind проверка сохранности файлов базового bundle.

В `harness/skills/` действительно 18 skills четырёх типов: `evidence-*`, `resolve-*`, `falsify-*`, `repair-*`; часть содержит исполняемые скрипты для чтения/сверки PDF, DOCX, PPTX, XLSX, bundles и patch. Это не просто «18 автоматических тестов»: skill задаёт процедуру проверки, а скрипты помогают получить/сопоставить свидетельства. Важно различать эволюцию библиотеки в исследовании от runtime: эксперимент формирует предложения skills по ошибкам development-наборов и фильтрует ответы/идентификаторы; наборы, на которых подбирали эти навыки, не являются независимым held-out тестом для самой библиотеки. Проверка held-out score проводится отдельно. В просмотренном runtime-репозитории нет общего механизма, который самовольно переписывает skills на каждой задаче.

Постовые числа совпадают с таблицей статьи: для Claude Opus 4.8 средний score `49.6 → 56.1`, APEX-Agents `35.8 → 47.5`; сайт визуализирует ту же таблицу. Статья также сообщает средний выигрыш над средним одиночным rollout `+6.4` пунктов для Opus и `+6.2` для Gemini 3.5 Flash; это benchmark score points, не проценты вероятности правильности.

Тезис «треть ответов, где сошлись все десять попыток, неверна» требует важной оговорки: в статье это 34% **claim-level consensus values** в десяти-rollout пулах Claude Opus 4.8 на APEX-Agents, размеченных по rubric. Это не доля целых ответов/артефактов, которые неверны целиком. В том же анализе у 74% спорных утверждений был хотя бы один корректный кандидат, а самое частое значение было корректно лишь в 47% случаев. Эти claim-level результаты сами по себе не дают вероятности ошибки для иной модели, проекта или типа задачи.

Совместимость с CLI тоже подтверждена, но формулировать её точно: таблица статьи запускала протокол и skills внутри Gemini CLI 0.46.0, Claude Code 2.1.246 и Codex 0.149.1; результаты зависели от runtime и benchmark. Публичный же harness использует pi coding-agent runtime как основной runner. README не означает, что репозиторий является нативной реализацией трёх CLI.

### Расход VeriHarness

На задачу paper использует `N=10` rollout одного model/scaffold; это в десять раз больше генераторных rollout, чем baseline из одного запуска, прежде чем считать проверки. Сверх них VeriHarness делает четыре verifier model turns — resolver, challenger, adjudication и delivery. Суммарные токены и стоимость конкретной задачи не фиксированы простым множителем: объём контекста, чтения workspace, вызовы инструментов и длина ответов меняются. Для опубликованного пула примерно из 26 тысяч rollout авторы указывают стоимость генерации более `$100,000` (грубая нижняя граница — около `$3.85` на один rollout, если поделить `$100,000` на 26,000; число приблизительное, и это не цена одного запуска harness или verifier).

Отдельная строка для нашего Codex Plus: точное число процентных пунктов без входных/выходных токенов этих запусков не вывести. `.orchestra/kb/models-and-quotas.md` сообщает локальный Plus-замер Luna 26–29.09 — около **32.3 млн input+output tokens на 1 п.п.** недельного окна. Следовательно, если фактически измерить все десять candidate runs и четыре verifier turns, оценка для этого замера будет `sum(input + output) / 32.3M` процентных пунктов. Десять rollout сами по себе означают 10× генераторных запусков относительно одиночного baseline; verifier добавляет четыре отдельных модельных хода. Это не значит, что общий расход ровно 14×: контексты и длины ходов различаются. У статьи нет token/$ отчёта на одну задачу; её `$100k+` — суммарная историческая цена примерно 26k выпущенных rollout, не Codex Plus rate card. Наш плюс-замер — одно окно, поэтому даже формула остаётся приблизительной.

## Сопоставление с Orchestra

Сопоставление — по текущим `app/` и pipeline prompt modules, а не по названиям. Цены переноса ниже — качественная оценка объёма/новых расходов, не замер реализации.

| Механизм VeriHarness | Что уже делает Orchestra | Вердикт | Цена переноса |
|---|---|---|---|
| Десять независимых кандидатов той же модели на одну задачу | `dynamic_workflow` уже умеет параллельные списки задач, цепочки и многоэтапные fan-out/fan-in; есть явные `budget_usd`, `max_calls`, `max_concurrency`, но это общий инструмент, не генераторная политика и не обязательный повтор каждого задания. Обычная работа идёт через выделенного воркера и acceptance. | Уже есть примитив; **не брать как default** для каждой задачи. | Малый кодовый перенос, но примерно 10× кандидатной генерации плюс verifier расход и больше приёмочной нагрузки на одну задачу. На Plus это напрямую расходует общий quota pool. |
| Disagreement resolver с проверкой конкурирующих утверждений по данным среды | Приёмка связывает оценку с конкретным `worker_head`, диффом, assignment и `acceptance_note`. `app/acceptance.py` запускает заданный acceptance oracle; тесты проверяют изменение кода, но не выводят автоматически claim-by-claim disagreement между вариантами. | **Не брать** как постоянный общий слой; есть частичные аналоги по объективным результатам. | Высокая: сопоставление альтернативных артефактов/утверждений, извлечение свидетельств и provenance по каждому решению. Для конкретных решений, где есть проверяемые факты, стоимость может оправдаться, но универсальность не показана. |
| Consensus challenger: целенаправленно искать общий скрытый дефект/пропуск | Mutation gate выполняет именно негативную проверку защиты: после зелёной выборки тестов временно накладывает изменённые тесты на target-source tree; если тесты остаются зелёными на исходном коде, gate сообщает `tests_not_guarding_source`. Однако он срабатывает для изменённых source+test файлов и проверяет кодовый delta, а не общий вывод нескольких агентов. | **Уже есть узкая более строгая кодовая проверка;** не переносить отдельный LLM challenger. | Запуск уже встроен в merge-gate; расширение на утверждения и не-код потребует новой схемы проверяемых claims, oracle и дополнительного модельного расхода. |
| Evidence ledgers из независимых расследований | Acceptance и merge operation сохраняют результат oracle, выбранный commit/HEAD и состояние test/mutation gates; диагностический вывод и diff остаются проверяемыми. Нет обязательного универсального журнала «claim → проверка → источник → вывод» для каждого исправления. | **Частично уже есть** в код-приёмке; полный ledger не брать как обязательный для всех задач. | Средняя/высокая: формат, сбор источников и поддержка разных типов artefact. Добавочная схема без реального пользователя ухудшает сигнал/шум. |
| Свежий adjudication: выбрать базу, план исправлений и нерешённые пункты | У оркестратора уже есть единая приёмка `worker_wip` с просмотром точного HEAD и фактических проверок перед `merge_worker`; dynamic workflows передают структурированные результаты следующих стадий. Это выбирает и принимает одну предложенную работу, но не проводит турнир десяти кандидатов. | **Уже есть** для обычной делегированной задачи; не добавлять второй acceptance authority. | Низкая для разового judgement, высокая при N кандидатов: сравнение всех версий, extra verifier turn и риск повторения merge/test costs. |
| Delivery с revision plan и repair record | Исполнитель исправляет свою ветку в рамках назначенной задачи; приёмка может вернуть конкретные вопросы/дефекты. `merge_operations` прогоняет platform acceptance и test gate перед продвижением. | **Уже есть** рабочий цикл edit → проверка → возврат/merge, но без VeriHarness-specific claim ledger. | Низкая для существующего цикла; дополнительный запуск редактора увеличит стоимость/задержку и повторяет штатную работу воркера. |
| Programmatic gate на сохранность всех файлов артефакта | В нашем случае главным артефактом является Git-изменение: snapshot/identity checks, acceptance oracle, mapped pytest subset и mutation gate. Удалённые/переименованные файлы тоже видны в diff; кодовые тесты содержательно сильнее простого bundle completeness. | **Уже есть аналог, другой предмет проверки.** | Переносить их file-preservation gate дословно не нужно; для кода он не заменяет текущие gates. |
| Reusable skills с текстом и скриптами по типу артефакта | Orchestra имеет pipeline modules/roles, test suites и проектные инструменты. У нас уже были поведенческие выводы о качестве промптов и свободе метода (V-548/V-550, V-666); правило owner запрещает буквальные tests на формулировки, а #490 показывает ценность проверки механики доставки prompt module. Это не библиотека, которая сама переписывает общие инструкции. | **Уже есть частично** как специализация промптов и исполняемые тесты; не переносить 18 офисно-документных процедур в общий pipeline. | Если вводить, каждый новый script требует поддержки сред/версий, тестов и включения только релевантным ролям; общий текст/skills увеличивают prompt и расход каждого затронутого хода. Раздельные узкие инструменты дешевле универсальной копии. |
| Эволюция skills по ошибкам с отбором на development и проверкой held-out | Сбои и подтверждённые выводы сохраняются в tasks/KB; изменения постоянных prompt rules принадлежат владельцу правил. Статья сама предупреждает, что learned-skill библиотека сформирована из development failures, а не проверена независимо на тех же задачах. | **Не брать** автоматическую само-модификацию prompt/skills. Сохранение экспериментального evidence уже есть, а принятие общего правила — намеренно отдельное решение. | Очень высокая: новые состояния библиотек, процедуры filtering, регрессии на held-out задачах и дополнительный compute; риск утечки специфического ответа или overfit на development. |
| Модельное review всех вариантов | Отдельное Codex/model review заморожено owner decision 20.09.2026. Текущая приёмка опирается на diff, tests и собственный mutation check. Это не означает, что любые возможные независимые verifier calls уже выполняются. | **Не брать** в обход замороженного решения; текущий gate остаётся авторитетом. | Новые ходы, цена/задержка, контекст и отдельная интеграция; сначала изменилось бы действующее owner rule. |

## Границы переноса

VeriHarness оценён на пяти long-horizon workspace benchmarks: профессиональные документы и наборы файлов (APEX-Agents, Workspace-Bench Lite), spreadsheets, multi-file/web workspace и code tasks. Результаты агрегируют их собственные grader scores; unanimous-error statistic ещё уже — claim rubric одного benchmark/model. У Orchestra доминируют кодовые изменения в живом репозитории и платформенные контракты: здесь есть source tree, executable acceptance, mapped tests, rollback/mutation check и Git identity. Значит, похожее название «проверка согласия» не гарантирует одинаковый эффект; office skills и benchmark point gains напрямую переносить нельзя. Это граница применимости по различию предмета и oracle, не утверждение, что метод не сможет работать на коде.
