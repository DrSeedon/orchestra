# V-1040 — восстановление MCP-сессии и WATCHING

Исправлено в `app/multicode_client.py`, `app/backend_hub.py`; добавлены регрессии в
`tests/test_multicode_client.py` и `tests/test_backend_hub.py`. Остальные исходники,
конфигурация, зависимости проекта и существующие тесты не изменены.

## Поведение

- HTTP >= 400 показывает статус и первые 300 символов тела после `_redact`.
  Маскирование выполняется до обрезания: иначе на границе мог остаться префикс токена.
- Если исходный запрос нес `Mcp-Session-Id`, HTTP 404 либо HTTP 400 с `session` /
  `not initialized` сбрасывает `_session_id` и `_initialized`. Клиент заново выполняет
  initialize + notifications/initialized и один раз повторяет исходный запрос,
  включая тот же JSON-RPC id. Повторный отказ возвращает безопасное тело ошибки;
  повторный session-отказ также оставляет клиент без устаревшего session id.
- Handshake не запускает рекурсивное восстановление самого себя. Ошибка нового
  handshake возвращается вызывающему коду; WATCHING может повторить безопасное чтение.
- `MultiCodeError.retryable` классифицирует RemoteProtocolError, ReadError, ConnectError,
  httpx TimeoutException, HTTP 5xx и отказ по переданной сессии. Обычный HTTP 400,
  авторизация, ошибки JSON/JSON-RPC и ошибки инструмента не получают этот признак.
- WATCHING повторяет wait/read до пяти попыток с задержками 1, 2, 4, 8 секунд и
  общим пределом 60 секунд на операцию, включая запросы и повторный handshake.
  После исчерпания возвращается последняя безопасная ошибка. Cancellation не перехватывается.
  Для activity poll сохранена прежняя возможность потерять live detail без потери turn;
  чтение итогового ответа тоже имеет ограниченное восстановление.
- Send/launch не получают транспортных повторов. Устранены существовавшие опасные
  fallback: повторный launch после неопределенного результата send и постановка
  неопределенно доставленного steer в очередь для повторной отправки. Любой явный
  отказ send/configure с `retryable=False` допускает создание замены, включая error,
  archived и отказ конфигурации; восстановление не ограничивается `thread not found`.
  При `retryable=True` ошибка передается вызывающему коду без нового треда.
  Отсутствующий `runId` в
  результате send теперь возвращает ошибку без повторной доставки.

## Что выяснилось

`HubBackend._mc` переживает несколько turns, а `_initialized=True` раньше навсегда
сохранял однажды выданный session id. Поэтому сброс сессий hub ломал и следующие
turns того же backend. Основной тест использует один клиент: первый tool_call
успешен, сервер забывает его сессию, следующий tool_call успешно восстанавливается.

Добавление тела HTTP-ошибки выявляет дополнительное взаимодействие:
`_workspace_lost` ищет `not found` в строке. Ответ `session not found` нельзя принимать
за потерю проекта и запускать работу заново. Поэтому transient/session-ошибки
исключены из этой ветки; это проверено отдельной регрессией.

## Фактическая проверка

Финальный прогон после замечания родителя: **59 passed, 1 deselected**; см. `tests.log`.
Все HTTP-вызовы тестов выполняются через `httpx.MockTransport`, реальные серверы,
БД, SSH, CLI провайдеров и учетные данные не используются. `asyncio.sleep` заменен
в тестах backoff; ограничение времени проверено коротким timeout без ожидания 60 секунд.
Также проверена компиляция четырех измененных Python-файлов (`environment.log`).

В приватной копии переданы только два файла `app`, поэтому для импорта backend
`run_sparse_tests.py` подставляет import-only stand-ins отсутствующих workspace,
activity, outbox, events и usage модулей. Сами исправленные MultiCodeClient и
HubBackend настоящие; их wait/read/start/send и HTTP-транспорт не подменены.
Единственный исключенный существующий тест —
`test_multicode_run_is_registered_in_orchestra_mcp`: отсутствует `app.mcp_stdio`.
Его код оставлен без изменений. Полный набор проекта здесь запустить нельзя.

Исходный `uv` оказался shim без установленного исполняемого файла. Для проверки
временно установлены инструменты в каталог задачи; использован существующий
Python из `/opt/whisper/venv`, без изменения его пакетов. Среда: Python 3.12.3,
httpx 0.28.1, pytest 9.1.1, pytest-asyncio 1.4.0, uv 0.13.5. Это проверка на доступных
пакетах, а не установка полного окружения `uv.lock`; поэтому использован `--no-sync`.
Временные runtime/tmp после проверки удалены.

Выполненная команда (окружение и установка инструментов отражены выше):

```sh
UV_CACHE_DIR="$PWD/.orchestra/tasks/V-1040/runtime/cache" \
UV_PROJECT_ENVIRONMENT=/opt/whisper/venv \
PYTHONDONTWRITEBYTECODE=1 \
PYTHONPATH="$PWD/.orchestra/tasks/V-1040/runtime:$PWD" \
nice -n 15 .orchestra/tasks/V-1040/runtime/bin/uv run --offline --frozen --no-sync \
python .orchestra/tasks/V-1040/run_sparse_tests.py \
tests/test_multicode_client.py tests/test_backend_hub.py -q -p no:cacheprovider \
-k 'not test_multicode_run_is_registered_in_orchestra_mcp'
```

В полном checkout для приемки нужен обычный прогон без stand-ins и исключения:

```sh

```

`<hub-workspace>`.

## Остаточная проверка

Уточнение родителя перед вливанием: первоначальная защита в `_start` была слишком
узкой и сохраняла fallback только для `_workspace_lost`. Заменено одно условие:
`if exc.retryable: raise`; все остальные MultiCodeError снова разрешают новый тред.
Проверены HTTP 400/403/409/422 на send (error/archived/отказ принять сообщение) и
HTTP 400/409 на configure. Все шесть новых случаев краснели до правки
(`followup-before.log`: 6 failed, 7 passed), а семь случаев неопределенной доставки
и отсутствующего runId сохраняли запрет launch. В числе transient проверены
ReadError, RemoteProtocolError, ConnectError, ReadTimeout и HTTP 500/503.
Тест с обычным 400 перемещен из запрета launch в разрешающий сценарий согласно
уточненному контракту; замороженных приемочных тестов нет.
