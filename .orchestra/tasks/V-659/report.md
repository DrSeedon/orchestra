# V-659: как измеряют effort и стоимость агентных моделей

Дата среза источников: 29 сентября 2026. Вопрос исследования: как независимые и первичные источники сравнивают уровни `low`–`max`, расход токенов и стоимость агентной работы, и какие элементы их методик полезно перенести в наши замеры. Основной внешний количественный источник — Artificial Analysis (AA); для причинных выводов о токенах и стоимости — две статьи arXiv; для поведения интерфейса — документация Anthropic. Числа ниже не сводятся в общий рейтинг: эти источники решают разные задачи и используют разные benchmarks.

## Короткий ответ

1. **Effort нужно сравнивать на одинаковых задачах, в одном harness и с независимой проверкой успеха.** Одна величина вроде output tokens не показывает, окупилась ли дополнительная работа. [Наш V-656](V-656/report.md) прогнал две задачи по одному разу на effort; предельная метрика из двух статей — billed cost per successful task, а latency, trajectory и token breakdown нужны рядом, чтобы объяснить изменение.
2. **Токены и стоимость надо учитывать отдельно по категориям.** У Anthropic кэш-чтение, запись с TTL 5 минут или 1 час, uncached input и output имеют разные цены. Thinking — часть оплачиваемого output; в API usage оно также показывается как отдельная детализация. В текущих сырых V-656 все cache writes помечены как TTL 1 час, поэтому сравнение `costUSD` с одним тарифом cache write `$2.50/M` было неравным: это ставка 5-минутной записи. По тарифу 1 час `$4/M` CLI `costUSD` всё ещё выше реконструкции примерно в 1,5–1,7 раза, но исходная оценка «около 1,8 раза против `$2/$10/$0.20/$2.50`» завышает величину разницы.
3. **Эффект усилия зависит от задачи и harness.** AA показывает сильный рост среднего индекса с усилием на смеси общих оценок. Набор hard SWE-bench в статье Weinberger/Hozez на более ранних Opus 5/Sonnet 5 обнаружил полезный high для Sonnet, но не Opus; более высокий расход не гарантировал лучшее решение. В V-656 обе задачи ограничены ясными критериями и не выявили роста качества при увеличении effort; это полезный локальный результат, но один прогон на условие не оценивает вариативность.

## Источники и что они фактически измеряют

### Artificial Analysis: Intelligence Index и стоимость задачи

AA публикует пять effort-конфигураций Sonnet 5.5 и Opus 5.5 с отдельными score и weighted cost per Intelligence Index task. Индекс v4.3.2 объединяет десять оценок: AA-Briefcase, GDPval-AA, AutomationBench-AA, Terminal-Bench 4.0, SciCode, Humanity’s Last Exam, GDP.pdf, CritPt, AA-Omniscience и AA-LCR. Поэтому итоговая строка — взвешенное среднее по разнородным задачам, а не средняя цена прогона единственного coding harness. AA явно описывает cost/task как стоимость input, cache hits, cache writes, reasoning и answer tokens, делённую на число задач в оценке и взвешенную весами индекса. В описании output/task — output с reasoning и answer; расчёт нормирует на число задач, исключая повторы. См. [страницы Sonnet 5.5](https://artificialanalysis.ai/models/releases/claude-sonnet-5-5), [Opus 5.5](https://artificialanalysis.ai/models/releases/claude-opus-5-5) и [методику индекса](https://artificialanalysis.ai/methodology/intelligence-benchmarking).

AA запускала каждую модель при всех пяти уровнях с включённым fallback; для Sonnet 5.5 fallback происходил примерно в 0,1% заданий, преимущественно Terminal-Bench, на Sonnet 5. В опубликованном релизе отмечен pre-release build с известным дефектом structured outputs, способным ухудшить результат; AA ожидала небольшое или нулевое влияние и планировала повторить релевантные оценки. Это влияет на переносимость абсолютных score. AA-профиль не даёт одного общего числа повторов на все оценки: их методика задаёт повторы отдельно по benchmark. Например, Terminal-Bench 4.0 — 66 задач, три повтора, `mini-swe-agent`, pass@1, максимум 500 шагов; задачи GDP.pdf делались по пять раз. Значит, нельзя трактовать индекс как, например, пять одинаковых прогонов одной задачи на каждой конфигурации. [Описание Terminal-Bench и GDP.pdf в методике AA](https://artificialanalysis.ai/methodology/intelligence-benchmarking).

Это не значит, что любой клиентский процесс выигрывает при low: метрика использует собственные benchmark задачи и цены; цена на графике логарифмическая. Важный контрпример внутри того же набора — FrontierCode: Sonnet 5.5 score на Xhigh был 52.1%, на Max — 46.2%; Anthropic объясняет разницу склонностью Claude Code запускать многоагентный review, с таймаутами и лишними правками вне scope. [Анонс Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5), [разбор AA](https://artificialanalysis.ai/articles/claude-sonnet-5-5).

### Anthropic: карточки, effort API и Claude Code

System cards Sonnet 5.5 и Opus 5.5 дают полезный более широкий протокол сравнения результатов: в сводной capability-таблице использованы adaptive thinking на max, стандартные sampling settings и среднее пяти запусков, с отдельными исключениями. У Terminal-Bench 4.0 Sonnet указан при max и Opus при Xhigh; в system cards результаты некоторых конкурентов взяты из их опубликованных карточек, а не из совместного прогона. В release-графиках нельзя принимать каждую строку за полностью выровненную межмодельную серию. Подробная локальная выжимка и PDFs: [V-657/report.md](V-657/report.md), [Sonnet card](V-657/sonnet-5.5-system-card.pdf), [Opus card](V-657/opus-5.5-system-card.pdf). Официальная сводная таблица тарифов и усилий: [анонс Anthropic](https://www.anthropic.com/claude-sonnet-5-5).

API `output_config.effort` — **поведенческий регулятор, не фиксированный токен-бюджет**. Effort меняет весь генерируемый output, включая обычный текст, аргументы tool calls и thinking; низкий effort обычно также уменьшает длину и число вызовов инструмента. Пять уровней доступны для Sonnet 5.5 и Opus 5.5. Claude Code текущей документации ставит им default medium; текущая документация также говорит, что Sonnet 5.5 поддерживается с версии Claude Code 2.1.284+, Opus 5.5 — с 2.1.280+. Поэтому V-656 с CLI 2.1.280 запускал Opus на заявленной минимальной версии, а Sonnet 5.5 — ниже текущего документированного минимума. Это не доказывает, что конкретные вызовы Sonnet 5.5 в V-656 не исполнились: JSON показывает `canonicalModel=claude-sonnet-5-5`; однако это версия-конфигурация, способная повлиять на распознавание модели, defaults и расчёт цены, и её надо фиксировать/обновлять при повторе. [Anthropic Claude Code model config](https://code.claude.com/docs/en/model-config), [API effort](https://platform.claude.com/docs/en/build-with-claude/effort).

Для Sonnet 5.5 текущая таблица API публикует на миллион токенов: uncached input $2, output $10, cache hit $0.20, 5-minute cache write $2.50, 1-hour cache write $4.00. Для Opus 5.5 — $4, $20, $0.20, $5 и $8 соответственно. Thinking считается как output по ставке модели. Поэтому запись кэша нельзя оценивать по одному общему тарифу без TTL. Источник — [официальная документация Anthropic по cache pricing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); поведение API показывает TTL в полях `cache_creation.ephemeral_5m_input_tokens` и `cache_creation.ephemeral_1h_input_tokens` ([Messages API](https://platform.claude.com/docs/en/api/http/messages)).

### Weinberger и Hozez, arXiv: prompt, harness и effort на coding agents

Статья `Prompt-Induced Waste in Coding Agents: Reasoning, Effort, Harness Design, and End-to-End Cost` (v6) специально разбивает вопрос на причинные факторы, а не считает токены самоцелью. В основном prompt/harness опыте было 24 детерминированных coding tasks, шесть open-weight моделей и Sonnet 5, два production harness (PI.DEV и Claude Code через protocol gateway, плюс native Claude Code), скрытые deterministic evaluators, preregistered гипотезы и paired сравнения; авторы сообщают 4,644 valid runs в основной серии и отдельные holdout/replication этапы. Сравнение эффекта effort на hard tasks вынесено отдельно: frozen slice из 25 SWE-bench Verified заданий с крупными patch, две кампании и 150 paired model-task-effort cells; Claude Code 2.1.220, Sonnet 5/Opus 5, `low`, `high`, `xhigh`; judge — официальный SWE-bench Docker evaluator. Effort перед запуском проверяли manipulation check-ом: он действительно менял объём output в этом стеке. [Статья и описание протокола, Appendix N](https://arxiv.org/html/2608.01347v6).

На hard slice Opus 5 решал 17/25 при low, 18/25 high и 16/25 xhigh; cost per resolved task был $0.75/$1.89/$3.62. У Sonnet 5 результаты были 12/25, 19/25, 17/25, а cost per resolved — $1.76/$2.32/$3.00: high улучшил success относительно low в этом наборе, но xhigh оказался дороже и слабее high. Три из шести xhigh «спасений» Sonnet воспроизвелись на повторе; шесть из десяти расходящихся задач решились при обоих уровнях во втором прогоне, указывая на существенную вариативность. Для Opus 5 ни одна из discordant пар не воспроизвелась во втором повторе. Авторы не экстраполируют эти результаты на 5.5: прямое доказательство относится к версиям 5.0. [Appendix N статьи](https://arxiv.org/html/2608.01347v6).

Отдельно основной эксперимент показал, что просьба сравнить несколько подходов увеличивала reasoning tokens в 2.4–7.4 раза без доказуемого прироста успеха; общий «think deeply» — в 1.6–2.2 раза. Та же модель, задача и prompt могли обходиться в 5–30 раз дороже per success в Claude Code, чем в PI.DEV, главным образом из-за крупнее фиксированного prefix и большего числа ходов. Это не эффект сравнения Sonnet 5.5 effort, а доказательство, почему нельзя переносить стоимость между harness и промптами. Для адекватного accounting статья рекомендует сохранять success, реальный billed cost, task/difficulty, effort, harness/version/config, turns/tools, reasoning и output tokens, cache read/write и uncached input, compaction, retries/timeouts, subagents, latency и подтверждение, что заданная настройка действительно активировалась. [Результаты и benchmark recommendations](https://arxiv.org/html/2608.01347v6).

### Weinberger и Hozez, arXiv: Token Reduction Is Not Cost Reduction

Эта работа не сравнивает все effort уровни 5.5, но даёт прямое доказательство, почему измерять надо не только output tokens. Основная paired кампания: 103 задачи, семь репозиториев, три модели, четыре arms, 2,908 Claude Code runs (2,848 анализировались), до пяти effort значений в кампании; каждое условие создавалось из одинаковых свежих рабочих копий, порядок arms рандомизировали. Cost брали из provider-billed `total_cost_usd`, сопоставляли с provider usage и опубликованным тарифом; успех — по frozen deterministic judges. Данные сохраняли по uncached input, cache creation, cache reads и generated output. Отдельно авторы прямо указывают: thinking tokens в этих API/телеметрии отдельно не экспонировались, поэтому восстановить их из результатов кампании нельзя. Это хорошее предостережение: разные интерфейсы могут давать thinking detail, а могут сообщать лишь aggregate output. [Статья, методика и limitations](https://arxiv.org/html/2607.12161v5).

В 2,848 анализируемых запусках cache creation составил 44.3% фактической стоимости, cache reads — 35.4%, generated output — 10.4%, uncached input — 1.3%, ещё 8.7% остались неатрибутированными телеметрией. Итого cache write/read — около 80% реального счёта, или 87% реконструированной четырёхкомпонентной суммы. В одном arm компрессия убрала 38.4% оценённых raw tool-output tokens, но paired billed cost вырос на 6.8% (95% CI +2.8%…+11.3%); связь task-level сокращения tool output со сдвигом стоимости была слабой (`r=0.15`, CI включал ноль). Здесь «token reduction» измерял слой инструментов, не output reasoning модели, но механизм применим к методике V-656: повторно отправляемый контекст, число ходов и кэш могут доминировать над объёмом финального ответа. [Cost anatomy и результаты](https://arxiv.org/html/2607.12161v5).

### Практические замеры вне AA

[ComputingForGeeks: Opus 5.5](https://computingforgeeks.com/claude-opus-5-5-released-features-benchmarks/) описывает воспроизводимую, хотя малую задачу: Opus 5.5, Fable 5.1 и Opus 5 вызвали через API на одинаковых трёх DevOps prompts; одинаковый короткий system prompt; проверка реальными pipeline-инструментами `kubeconform -strict`, `shellcheck`, `tofu validate` и `tofu fmt`; стоимость посчитана по опубликованным ставкам, thinking учтён в output. Opus 5.5 прошёл все три задания, с расходом $0.037, $0.034 и $0.019. Метод полезен как пример измерения «задача выполнена инструментом» и явного учёта thinking, но авторы не сравнивали effort уровни; число повторов в таблице трёх задач не указано (отдельно сказано, что отказ Fable на Terraform проверяли повторными вызовами, но сколько их было, не сообщается). Вывод о шкале effort из этих цифр делать нельзя.

[Vellum: Sonnet 5.5 Benchmarks Explained](https://www.vellum.ai/blog/claude-sonnet-5-5-benchmarks-explained) — в основном пересказ анонса Anthropic и его публичных evals. Собственного набора повторов, harness или token/cost ledger для effort-разреза статья не описывает, поэтому её цифры не считаю независимым замером. Это отвечает критерию запроса «включать практические источники только если дан метод»: Vellum полезен как вторичный навигатор по опубликованным графикам, не как отдельный эксперимент.

## Наш V-656 рядом с источниками

Этап effort в [V-656/report.md](V-656/report.md) — Sonnet 5.5, две реальные задачи (V-653 Python-дефекты и V-654 график), дословные исходные задания, изолированные клоны, CLI headless, явный `--effort`. Каждую задачу прогнали по одному разу на каждом из пяти уровней (10 запусков уровням; параллельно). Успех оценивался тестами по эталонному baseline и, для UI, скриншотами на живом JSON. Использовались число ходов, wall time, output tokens и CLI dollar estimate. JSON также содержит input, cache read/write, thinking detail, но отчёт V-656 не сводит их для каждого уровня в отдельную таблицу. Все эти прогоны — один репозиторий/собственный Claude Code harness; ни AA weighted index, ни hard-SWE samples не являются прямыми аналогами.

## Проверка стоимости в сырых V-656 результатах

Я пересчитал 12 result JSON для модели `claude-sonnet-5-5`: 10 явных effort-запусков и два default-этапа, применив ставки Anthropic и фактический TTL из API usage. Во всех этих JSON `cache_creation.ephemeral_1h_input_tokens` равен cache-creation total, а `ephemeral_5m_input_tokens=0`. При тарифах $2/M input, $10/M output, $0.20/M cache read и **$4/M 1-hour cache write** реконструкция составляет $0.388–$7.179 за запуск; CLI `costUSD` — $0.636–$11.630. Отношение CLI/реконструкция по отдельным запускам 1.52–1.66, среднее невзвешенных отношений 1.59; это собственное вычисление из [сырых JSON V-656](V-656/runs/), по формуле/тарифам [Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). В реконструкции `outputTokens` использовано как output с thinking; поле `thinkingTokens` — раскрытая подчасть output, поэтому отдельно второй раз не тарифицировал.

Следовательно, известная цифра «CLI примерно в 1.8 раза выше при официальных `$2/$10/$0.20/$2.50`» требует поправки: `$2.50/M` — 5-minute cache write, но наши фактические token records — 1-hour write по `$4/M`. При одинаковом контексте 1h перерасчёт сдвигает отношение к ≈1.59. Это не полностью устраняет расхождение CLI с тарифной реконструкцией; текущая официальная Claude Code документация указывает минимум v2.1.284 для Sonnet 5.5, а V-656 использовал 2.1.280, что согласуется с гипотезой неактуальной таблицы модели/цен в CLI, но само по себе не доказывает точную причину коэффициента. Нужен повтор на документированно поддерживаемом CLI и сверка с raw per-request API usage / invoice-like provider amount, не только `modelUsage.costUSD` с `costBasis=unknown`. AA показывает официальные ставки $2/$10/$0.20/$2.50 в короткой ставочной сводке Sonnet; подробная документация различает cache TTL, поэтому оба источника совместимы при явном указании, что `$2.50` — 5m. [AA Sonnet 5.5](https://artificialanalysis.ai/articles/claude-sonnet-5-5), [Anthropic pricing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Claude Code versions](https://code.claude.com/docs/en/model-config).

## Конкретные пробелы V-656 и возможные способы закрытия

1. **Вариативность модели не измерена:** по одной попытке на task × effort. Предложение: повторять каждую замороженную ячейку на нескольких независимых запусках с одинаковым task state; сравнивать paired результаты по задачам, распределения cost/turns/time и долю успеха, а не только mean. Сколько повторов нужно, должно зависеть от наблюдаемого разброса и цены прогона; AA использует число повторов, определённое конкретным benchmark, а arXiv отдельно показывает, что на hard задачи повторный запуск менял результат.
2. **Выборка не покрывает классы сложности:** обе задачи имеют чёткие acceptance criteria; на них качество оказалось близко к плато уже на low. Предложение: сформировать и зафиксировать страты bounded/easy, средних и hard/ambiguous задач, включая кейсы с известной высокой baseline failure; считать success-adjusted cost отдельно по стратам. Нельзя заключать по двум bounded задачам, что low оптимален и на открытой работе.
3. **Уровень задан, но фактическая настройка не подтверждена telemetry:** JSON подтверждает имя canonical model, однако CLI 2.1.280 младше текущей документированной поддержки Sonnet 5.5. Предложение: повторять после фиксации CLI/version и перед основными прогонами сделать manipulation check (вызов с малой фиксированной задачей): проверить переданный effort в request/runtime и проверить, что разные levels действительно меняют наблюдаемый output/think profile. Так делают в hard-effort paper; в статье также были пути, где effort ручка не меняла вычисление и результаты не принимали за управляемое вмешательство.
4. **Cost accounting смешивает неизвестную CLI оценку с tariff reconstruction:** `costBasis=unknown`; 1h writes ошибочно можно сравнить как 5m. Предложение: первичную цену считать по provider-side billed amount, отдельно хранить вычисленную стоимость по полям `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` с TTL-разбивкой и `output_tokens`; обе сравнивать. Любую сводную цену подписывать как billed/API-equivalent, фиксировать дату тарифа, TTL, provider/service tier и модель. Не складывать token total без тарификации: cache read/write имеют иную цену.
5. **Thinking учитывался неявно в V-656 отчёте:** raw JSON содержит `thinkingTokens`, а таблица показывает только aggregate `output`. В зависимости от формата usage это поле является подмножеством output либо отдельным показателем при нераскрытом в CLI cost estimate; нельзя просто добавлять его вторично к `outputTokens`. Предложение: сохранять token usage на уровне request, определить schema и billing formula для конкретной версии API/CLI, публиковать отдельно `output total`, `thinking detail` и `answer/non-thinking`, но в сумму денег включать каждый токен строго один раз.
6. **Задачи запускались параллельно:** V-656 отмечает одновременные 10 прогонов. Это могло повлиять на wall time и распределение лимитов, хотя одинаковые условия и одинаковый запускный порядок здесь не сравниваются. Предложение: измерять отдельно latency под контролируемой последовательной нагрузкой либо записывать queue/concurrency; качество и token/cost можно paired-рандомизировать по порядку, сохраняя task state и окружение. В статье по cost порядок arm рандомизирован внутри блоков и авторы отдельно проверяли cache carryover.
7. **Успеховая метрика пока не сводится к вероятности решения:** в обоих eval есть объективные проверки, но две красные группы были заранее красными baseline/контрактными mismatches, а screenshots xhigh/max не просматривались. Предложение: заранее определить oracle policy, отделять известные baseline failures от регрессий измеряемой модели, каждый effort-результат оценивать одинаковой процедурой, и вычислять `cost per successful task` вместе с raw cost/task. При неполной observability записывать missing, не называть уровень полностью прошедшим.

Для отдельного вопроса «какой effort ставить в обычном маршрутизаторе» наиболее информативен не широкий одномоментный sweep всех пяти уровней, а matched set, включающий ваши реальные распределения задач и проверяемые исходы; сначала повторяемость/точность счетчика, потом расширение выборки. Это предложение из приведённых источников, не решение владельца.

## Выводы для обсуждения

- На ограниченных задачах V-656 измерил резкий рост ресурсов без заметного улучшения зафиксированных исходов; на более трудных наборах AA и arXiv дополнительный effort иногда повышает score/success, но отдача не линейна и зависит от задачи, модели и harness.
- Число output tokens полезно как описание поведения модели; как итог эффективности оно слабее стоимости, проверенного успеха и времени. В API задачах cache traffic и повторы prefix могут составлять большую часть счёта, а `thinkingTokens` способен быть либо отдельно наблюдаемой детализацией, либо совсем недоступным.
- До интерпретации V-656 как «1.8× завышения CLI» надо скорректировать tariff base для 1h кэша и уточнить цену у поддерживаемого CLI. Предварительная пересчитанная разница остаётся значимой — около 1.6×, — но причина не установлена.
- AA — лучший источник широкой curve «effort → benchmark score, output и cost», arXiv hard-effort — лучший источник о причинной вариативности и измерении success/cost на парных coding задачах. V-656 отвечает на локальный вопрос о двух наших задачах, но пока не на общую рекомендацию по effort.
