# #504 — Model-produced free text in Orchestra control flow

## Question

- **Context:** the Orchestra platform shared by the 19 rows currently registered in `tm_projects`.
- **Change under test:** replace decisions inferred from model-produced prose with typed runtime signals.
- **Baseline:** current code, where a literal/regex match may consume assistant text, a model-authored fixed-shape artifact, or deterministic tool/provider output.
- **Outcome:** a source-traced inventory of every relevant branch in `app/`, split into A/B/C, with the first commit for every A site and executable false-trigger probes for the three highest-priority A sites.

Counting rule: one **site** is one syntactic comparison/regex branch, not one literal and not one downstream caller. Thus the two branches inside `_subscription_limit_kind` are two sites, and the duplicated `[round guard]` filters over `history` and `new_messages` are two sites. A literal helper called from three places is counted where it compares text, while the caller consequences are listed in the same row. **Phase-2 correction:** the curated inventory now contains 102 source-traced sites: **10 A, 9 B, 83 C**. Phase 1 reported 9 A because its source-to-sink closure stopped at the typed JSONL `agent_message` discriminator and failed to follow that item's inner `text` field into `app/mcp_stdio.py:3590`; row 6b below corrects the count and the closure.

## Hypotheses considered

1. **H1 — the defect is confined to compact-summary validation.** Falsifier: any non-compact branch whose input is a typed assistant text event or model-authored artifact and whose decision changes when ordinary prose contains the trigger. **REFUTED:** live limit handling, review validation, harness history cleanup, and tool-call classification all meet the falsifier [1][4].
2. **H2 — apparent text matches outside compact are only fixed-shape contracts (B) or deterministic external text (C).** Falsifier: a grammatical, ordinary model sentence that triggers the branch without intentionally emitting the contract or without an external failure. **REFUTED:** both limit branches and the blind-review branch trigger on such text [4].
3. **H3 — all consequential decisions already have a typed source that can replace prose matching without adding a new concept.** Falsifier: a branch where the current adapter erases the needed distinction. **PARTLY REFUTED:** Codex/Grok already expose structured error fields/codes, but Claude's current shared `text` event does not distinguish normal assistant prose from a provider-generated limit/refusal banner; that adapter needs an explicit typed `limit_kind`/`model_error` event [1].

## Blast tests and ranking

Executed with the current worktree modules using `/mnt/data/Projects/Python/orchestra/.venv/bin/python`; pass/fail criteria were fixed before running: a grammatical sentence with no real provider/tool failure must not select the failure/limit branch.

1. **Highest: row 2, live timed-limit classifier — false trigger confirmed.** Input: `The defect appears whenever an agent discusses the phrase session limit in its own answer.` Result: `_subscription_limit_kind(...) => timed`. An agent can produce this in ordinary work whenever the conversation concerns limits. The read-only production DB snapshot strengthens this from possibility to occurrence: among 34,923 `text` rows, 29 matched the timed vocabulary; 16 were longer than 200 characters and 19 did not start like the canonical `You've hit your ... limit` banner. Recent samples included ordinary explanations from `Orchestra-orchestrator`, `research-astra`, and `kesha-tg-bot` [3][4].
2. **Second: row 1, monthly-limit classifier — false trigger confirmed.** Input: `We are debugging a monthly spend limit false positive; the provider did not limit this turn.` Result: `_subscription_limit_kind(...) => monthly`. The snapshot contained 54 matching `text` rows; 5 exceeded 200 characters and 7 did not have the canonical provider-banner prefix, including an ordinary 345-character explanation quoting the phrase [3][4].
3. **Third: row 6, blind-review detector — self-trigger confirmed.** A syntactically valid review containing `## Verdict` and a finding that quoted `Unable to perform an evidence-backed review` returned `review artifact is blind: execution never happened`. A reviewer can naturally produce exactly that sentence while reviewing `app/bg_jobs.py` or this incident; the failure is deterministic once it does [4].

The first Luna pass supplied an end-to-end control: it produced a valid `## Verdict`, but the background job still reported `review artifact is blind: execution never happened` because its own execution output encountered the marker under study. In that live run the triggering producer was command output rather than model prose, so it is not additional A evidence; it proves the mixed free-text validator can reject a completed review through either side of its `artifact OR output` condition.

Lower priority by accidental-trigger probability: row 4 requires a summary shorter than 200 characters and at most three lines (the 121-character blast text triggered both `terminal_limit=true` and `provider_error=true`); rows 5/9 require at least two unfenced legacy XML tags; rows 7/8 require the model to begin a message with `[round guard]`; row 3 requires the exact `api error:` prefix **and** a failed turn before the destructive rewind is applied. These guards lower probability but do not change the provenance defect.

## Counter-evidence

- Compact validation is not the unguarded `kesha` predicate: current code requires `<200` characters and at most three newline characters. The guard reduces accidental triggers but the blast still proves one ordinary short summary is rejected.
- Safeguard handling additionally requires a failed turn before history rewind. This prevents the exact successful-turn incident documented in comments, but a model quote plus an unrelated failure can still satisfy both conditions.
- `_BLIND_REVIEW` has a legitimate operational purpose: it rejects known command-execution failures that previously returned exit 0. The counterexample shows only that the signal is collected from the wrong channel, not that the guard should disappear.
- Fixed `## Verdict`, finding, task-prefix, and silent-turn shapes are explicit contracts (B), not guesses. Their weakness is missing typed schema; their absence behavior is mostly loud and separately documented above.
- Historical DB counts are lower bounds on unsafe prose, not a perfect ground-truth label: `type='text'` intentionally conflates provider banners and model answers. Length and noncanonical-prefix filters demonstrate ordinary prose exists but do not label every matching row.

## Verdict

### (a) Count and most likely site

There are **10 class-A branch sites** under the stated syntactic counting rule (corrected in Phase 2 from the Phase-1 count of 9). The single site most likely to fire in ordinary work is `app/session.py:250`: any assistant answer containing common phrases such as `usage limit` or `session limit` marks the turn as terminal-limited, and production history already contains ordinary explanatory answers that match.

### (b) When it entered and whether it grew

The pattern first entered on **2026-07-01** in `1aa9c06a` — `WIP: auto-saved uncommitted changes before worker spawn (2026-07-01 11:28)` — as compact-summary garbage matching. It was temporarily removed on Jul 11, restored on Jul 24, and then grew into six additional behavior families through Aug 22. It has not gained a new family since Aug 22; the Aug 28 change was a file move of the existing dashboard classifier.

### (c) General replacement

Control decisions must consume typed events/receipts, never assistant prose:

- provider limits/refusals → `model_error`/`LimitEvent` carrying `kind`, `terminal`, `reset_at`, and source event id;
- compact validity → typed turn completion/error, with summary text treated only as payload;
- tool execution → typed `tool_use`/`tool_result` ledger;
- platform-injected history guards → structured provenance/subtype/id;
- review execution/outcome → process/JSONL receipt fields and a structured verdict/finding schema.

Class B may remain temporarily as a fail-loud serialization contract, but it should converge on the same typed envelope. Class C stays outside #504.
