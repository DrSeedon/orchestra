Механическое применение коэффициентов точечной регрессии V-660 даёт **3,17 п.п. экономии недельного пула**: +0,63 п.п. от cache-create, +3,22 п.п. от незакешированного input и −0,68 п.п. от output. Это число нельзя считать прогнозом: V-660 признаёт надёжным только cache-create коэффициент. Надёжно интерпретируемая часть — примерно **0,63 п.п.** за сокращение записи кеша; её 95% day-bootstrap диапазон по V-660, при тех же языковых допущениях, — **0,20–1,29 п.п.** Влияние перевода на input и output по этим данным не идентифицируется.

## Состав логируемого текста

Считались строки `logs` за окно из сессий с `sessions.backend_type='claude'`. Сообщения отправителей `user`, `agent`, `background_task` и `unknown` сведены вместе. В отдельную строку вынесены `platform`/`system` сообщения. Поля `system_prompt`, `prompt_overlay` и `last_summary` посчитаны по одному текущему снимку на каждую из **143 Claude-сессий**, имевших логи в окне.

Всего по этим девяти категориям — **337 971 767 оценочных токенов**, больше, чем 203,16 млн реальных платных токенов за период. Это ожидаемое ограничение метода: журнал хранит уникальные события и крупные результаты инструментов, тогда как usage учитывает каждый ход по правилам провайдера; не весь сохранённый вывод обязательно повторно попадает в контекст, системный промпт мог писаться в кеш многократно, а язык/категория в usage не записаны.

Чтобы получить оценку доли среди реально оплаченных токенов, композиция логов нормирована отдельно к наблюдаемым счётчикам: cache-create распределён между всеми категориями пропорционально оценочным токенам; output — между `text`, `thinking` и `tool`; незакешированный input отнесён к сообщениям user/agent. Получившаяся оценка русской доли по категориям — не прямой счётчик провайдера. Она чувствительна к обрезке/повторному использованию результатов инструментов и к тому, что снимок system prompt считается один раз, а фактические cache-write не размечены.

`compact_event` намеренно не прибавлен к категориям: 1 806 таких строк (7 045 717 символов) — JSON событий жизненного цикла сжатия, включая инструментальные события аудита, а не чистый transcript или точная запись содержимого провайдерского cache-write. `last_summary` выше — последний сохранённый снимок на сессию, не сумма всех сводок за период. События не дают точного количества повторных записей system prompt после compaction. Также не разбирались по языку поля `status`, `provider_limit`, `subagent_start/end`, `error`, `warning` и другие служебные типы; в основной таблице типов содержимого им соответствуют только указанные категории.

Для `tool_result` невозможно надёжно отделить код и вывод команд от других результатов инструментов только по этому типу. Символы не дедуплицировались; строки считаются в полном виде как хранятся в `logs`.

## Оценка эффекта перевода

`Платные токены` = subscription cache-create + output + незакешированный input. Русская доля получена распределением usage по категориям, описанным выше. Для каждой категории экономия токенов — 11% её оценённой русской части по суммарному образцу Claude из V-802. `% платных` — эта экономия, делённая на 203 164 186.

Для колонки п.п. использована точечная формула V-660: `п.п. ≈ 642,73×input + 0,604×cache_create + 0,00687×cache_read − 0,599×output`, токены в миллионах. Категориям содержимого в cache-create применён коэффициент 0,604; text/thinking/tool применены также к выходу; к user/agent messages отнесена доля незакешированного input. Положительное значение означает экономию по точечной формуле, отрицательное — увеличение расхода.

П.п. по категории показывают, насколько некорректно читать регрессию V-660 как тариф. У неё input = 642,73 п.п./М с 95% интервалом **−2 710,97…3 522,67**, а output = −0,599 с интервалом **−5,512…5,772**; оба интервала включают ноль и не дают отдельной ставки. Поэтому +3,17 п.п. — механический результат, в основном созданный неустойчивым input коэффициентом, а не защищаемый прогноз. Cache-create — единственный устойчивый коэффициент: экономия от этой части составляет около **0,63 п.п.** (V-660 bootstrap при нашей оценке объёма: **0,20…1,29 п.п.**). П.п. нельзя честно суммировать с неопределёнными input/output как точную ожидаемую экономию.

## Что можно переводить

Практически контролируемые категории — system prompts и KB-индекс, память, отчёты и сообщения пользователей/агентов. Код и фактический вывод команд/инструментов не контролируются как язык: они приходят из исходников, файлов, внешних программ и окружения; автоматический перевод может изменить исполняемое содержимое. По логам можно измерить общий `tool_result`, но нельзя приписать ему весь объём кода или командного вывода.

## Проверка и ограничения

Сверены схема и поля `turn_usage`/`logs`, код сборки системного промпта и хранения compaction summaries, исходный отчёт V-802 и раздел формулы V-660. Секреты и сырые тексты живых логов в отчёт не копировались. Токенизация — грубая оценка на коротких образцах; оценка русской доли — дополнительная пропорциональная модель, так как в telemetry нет языковой разбивки cache-create/output/input.
