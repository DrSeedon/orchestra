# V-955 — пробуждение по одному и отметка «лимит, проснётся ~HH:MM»

Просьба владельца (18.10, 18:21 КРС, голос), как передал оркестратор: «у всех, кого остановил лимит — флаг и таймер; когда лимит сбросится, запускать по чуть-чуть, каждого раз в 10 секунд».

## Что сделано
1. `WAKE_STAGGER_SECONDS` 30 → 10 (`app/limit_wake.py`). Пауза делается в `run_wake_job` между доставками по умолчанию; тест подменяет `asyncio.sleep` и проверяет, что между двумя пробуждениями ровно 10 с.
2. Единый источник отметки: `limit_wake_marks()` берёт кандидатов из `_load_limit_stopped_agents()` и таймеры из `_active_wake_jobs()` — те же функции, по которым работает планировщик (второго состояния нет). Для кандидата в таймере: `wake_at = trigger_at + позиция × 10 с`, текст «⏳ лимит, проснётся ~HH:MM UTC». Без таймера: «⏳ лимит, сам не проснётся: таймер ещё не создан» или «…месячный лимит, нужно ручное действие».
3. Где видно: поле `limit_wake` в `GET /api/sessions` и `GET /api/orchestrators`; карточка агента в дашборде (`createAgentItem`, время переводится в локальный пояс браузера, i18n-ключ добавлен); вывод `list_agents` и `list_orchestrators` (MCP) — строка отметки после задачи.
4. Исчезновение: отметка строится только для текущих кандидатов, а кандидатом агент перестаёт быть, когда он проснулся (идёт ход / вышел новый `turn ended` не лимитом) или получил любое другое сообщение (условие `_latest_limit_turn`). Штатно остановленный агент кандидатом не является.
5. Нагрузка (переделано после замера оркестратора: скан на холодном кеше страниц 27,3 с, повторный 1,09 с). Две меры. (а) Листинги не ждут скан: `limit_wake_marks()` возвращает последнее готовое значение, а при устаревании (15 с) пересчитывает его в фоновом потоке; первый расчёт запускается при старте (`main.lifespan` после `restore_from_db`). Ошибка расчёта не ломает список (`safe_limit_wake_marks`). (б) Сам скан стал дешёвым: `_load_limit_stopped_agents` больше не делает оконный запрос по всем `turn ended` всей таблицы `logs`, а для каждой подходящей сессии (не running/starting/archived, провайдер известен) идёт вниз по `idx_logs_session` до четырёх последних `turn ended` и читает строки хода, тело — только у типов `provider_limit/error/status`. Кандидаты те же: тест на реальной SQLite (`test_v955_index_walk_loader_...`) проверяет лимитированного, дубликат `turn ended`, штатно завершившего, running и не-Claude.

## Замер на боевой БД (read-only, `ORCHESTRA_DB_PATH=data/orchestra.db`, `/tmp/measure955.py`, 18.10)
- `limit_wake_marks(fresh=True)`, первый вызов: **0,198 с**; второй: **0,087 с** (кандидатов в этот момент 0).
- вызов, которым пользуются листинги (`safe_limit_wake_marks()`) с пустым кешем: **0,0005 с**, расчёт идёт в фоне. То есть `GET /api/sessions` и `/api/orchestrators` получают плюс доли миллисекунды, в том числе первый вызов после старта.
- Ограничение замера: холодный кеш страниц я не воспроизводил (сбросить кеш файловой системы без привилегий нельзя, а `posix_fadvise` по живой БД ударил бы по боевому процессу). Старый скан на этой же БД и в этом же состоянии кеша я не гонял, сравнение с 27,3 с / 1,09 с — по цифрам оркестратора. Листинги от холодного скана не зависят в любом случае, потому что не ждут его.
