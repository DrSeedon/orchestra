## Замеры, снятые до стопа

- **сейчас**: 68 строк с картинками = 11 002 075 б = **43.5%** всех байт журнала;
- **после выноса тел**: журнал 14.3 МБ (56.6% прежнего), картинки на диске ~8.25 МБ
  (байты вместо base64 — на четверть меньше);
- **худшая сессия**: последние 100 строк = 467 703 б gzip (677 063 распакованных) — это и
  есть тот ответ истории, ради которого всё затевалось; `cap` из #74 режет его на чтении,
  поэтому до клиента он не доезжает и сегодня;
- **покрытие рантаймов**: все строки с base64 в живой БД принадлежат `claude`
  (85 `tool_result` = 11.0 МБ, плюс мелочь в `tool`/`user_message`/`text`). У `codex`,
  `grok`, `opencode` строк с картинками нет вовсе — то есть непокрытых рантаймов сейчас
  не существует, но и проверить их форму не на чем;
- **семь субагентских строк с `base64` — НЕ картинки**: это bash-скрипты тестов, где слово
  встречается в тексте. Детектор их не тронет (требует форму `{'type': 'base64', 'data': …}`).

## Что осталось, если вернёмся

1. **Клиентская отрисовка** (frontend): формат ссылки в журнале —
   `{'type': 'image', 'source': {'type': 'blob', 'blob': '<sha256>', 'bytes': N, 'media_type': 'image/png'}}`,
   тело брать из `GET /api/blobs/{session_id}/{sha}`. Клиент обязан уметь ОБА формата
   одновременно: старые строки не мигрируются (решение ниже).
2. **Прогон полного сьюта** — делал только точечные файлы.
3. **Замер «после» на живых данных** — снимается после выката, сейчас это расчёт.
4. **Пересечение с TG-мостом** (`tg_bridge.py:3134` хранит путь к файлу) — не проверял.

## Решения, которые НЕ нужно переоткрывать

- **Старые 52 строки не мигрируем.** Инвариант неизменяемости `logs` (`db.py:974`) держит
  клиентское зеркало из #8; выигрыш был бы только в размере БД. Принято 04.08.2026.
- **Retention: блоб живёт, пока жива строка** (вариант A), плюс инвентарь без автоудаления
  (вариант C). Политики по возрасту нет: `agent history is research data, never delete it`
  (`db.py:1192`) сильнее экономии диска. Вариант B (удалять картинки старше N суток)
  рассмотрен и отклонён — это тихая потеря истории.
- **Копируем БАЙТЫ из строки, а не файл с диска.** Путь лежит в предыдущей строке журнала,
  у двух строк из 52 его нет вовсе, а рабочие копии сносятся штатно — ссылка на файл
  протухала у 18 из 50. Предпосылка проверена: усечения на пути записи нет
  (`_cap_content` работает только в `get_logs_sync`), максимальная строка в БД —
  651 726 байт, то есть тело доезжает целым.
- **Искать такие строки надо по ВЕСУ, а не по форме.** `LIKE '%data:image%'` даёт 0.5% —
  ложное опровержение: тело хранится как python-repr словаря без префикса.

## Риск, из-за которого остановка правильная

Врезка стоит в `app/session.py` на пути ЗАПИСИ журнала — том самом, который сегодня работает
у всех агентов. Любая ошибка здесь портит историю в момент её создания, а не при чтении.
Код написан так, что сбой хранилища возвращает исходное тело (тест на это есть), но
проверен он только тестами, а не живым трафиком.


## Что уехало в main без остальной работы (04.08.2026)

Вместе с `05ebad9` в main приехала половина #78: **хранилище `app/blobs.py` и чтение
`GET /api/blobs/{session_id}/{sha}`**. Путь ЗАПИСИ (`store_images` в обработчике
`tool_result`) оттуда **убран обратно** — `app/session.py` снова логирует `event.content`
как есть, это закреплено тестом
`tests/test_session.py::test_image_tool_result_is_logged_verbatim_not_as_a_blob_reference`
(проверен мутацией: с включённой записью краснеет).

Причина отката: **клиентской половины не существует** — в `app/static/js/app.js` нет ни
одного упоминания типа `blob`. Включённая запись означала бы, что первая же картинка после
рестарта уезжает в файл, а дашборд её не показывает.

**При разморозке #78 порядок такой:** сперва клиент (рендер типа `blob` через
`GET /api/blobs/...`), и только потом обратно `store_images` в `session.py`. Обратный
порядок = потерянные для глаза картинки у всех агентов.

Хранилище и чтение оставлены намеренно: без записи они инертны, а удаление создало бы
конфликт при разморозке. Оба роута внесены в `tests/route_surface_snapshot.json`.
