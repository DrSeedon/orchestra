# V-540 — стабильный системный промпт и границы доказательства кеша Claude

## Question

Контекст: только runtime `claude`, системный промпт Orchestra, `turn_usage` и native Claude JSONL. Изменение: удалить зависимость сборки от живого состояния проекта. Baseline: сборка до `ff9feeb5`. Измеряемые исходы: побайтовая стабильность сборки при изменениях БД, реальное чтение/запись кеша, доля дорогих ходов и стоимость на ход в одинаковых окнах одного агента/модели. Решение владельца о стабильном промпте действует независимо от причин расхода.

## Hypotheses considered

1. **Живые `ctx/status` меняют system на каждом ходе и обесценивают весь префикс.** Falsifier: эти поля приезжают как новое user-сообщение; после их изменения старый префикс всё ещё читается из кеша. Оба факта найдены. Формулировка опровергнута; вред при новом system-prefix в другом режиме этим не исключается.
2. **Крупная запись вызывается переподключением/компактом.** Falsifier для утверждения о необходимом условии: крупные записи внутри одного непрерывно живого CLI. Такие случаи найдены. Для утверждения о доле причины нужна полная история соединений; имеющийся журнал её не даёт.
3. **Длительная пауза исчерпывает TTL, независимо от изменения промпта.** Falsifier для универсального объяснения: крупная запись при паузе короче фактического TTL. Найден запрос с паузой между ответами 95.992 s. Поэтому TTL объясняет правдоподобно часть случаев, но не все; запросы до/после нельзя приписывать одной причине автоматически.

### F2. Реально изменён один байт, но в USER, не в SYSTEM — CONFIRMED, tiers 1/2

В native session `d32227c1-a7d1-422a-aaff-ca6ecfc79087` найдены последовательные platform-инъекции роли: [2,3]

| Поле | Предыдущее | Следующее |
|---|---|---|
| Timestamp UTC | 2026-09-08 02:40:50.092 | 2026-09-08 04:05:55.593 |
| Размер | 101757 B | 101757 B |
| SHA256 | c19ca177af7779c16866851f01243ee99dbe2d8c66b5b00fda7aeb973ff5ba7e | bd53998947d3fede7d526c40246555f34d6c697ae85a9bbfba6b025f30688c56 |
| Изменение по нулевому UTF-8 byte offset 80076 | `0x39` (`9`) | `0x38` (`8`) |

Общий префикс 80076 B, суффикс 21680 B. Это ровно `ctx:9%` → `ctx:8%`. **Это последовательные инъекции, не два смежных хода:** между ними есть запросы без пересборки. Native JSONL помечает оба сообщения `type=user`. Следующий API-ответ в 04:06:23.050: creation=35399, read=230890. Изменённый блок не уничтожил весь предыдущий кеш. [2,3]

Прямой путь в исходниках: `session.py:1448–1500` пересобирает роль при `not _prompt_injected` и добавляет её к `message`. После отправки `_prompt_injected=True`. `backend_claude.py:950–962` передаёт append системного промпта при новом разговоре/history import, но в обычной ветке `resume_id` задаёт только resume. «На каждом ходе любого воркера меняется system» из этого кода не следует. [4]

**Исторических полных API system-payload для двух соседних ходов нет в просмотренных источниках.** Доказательство изменения именно этих system-байтов не получено; выдавать сохранённый `sessions.system_prompt` или user-инъекцию за такой дамп нельзя.

### F3. Отрицательные плечи — CONFIRMED наблюдения, LIKELY TTL-причина

Две последовательные platform-инъекции 08.09 15:43:23.018 и 16:27:18.647 побайтно совпадают: 97386 B, SHA256 `a6c0faf4a3e699c76bbd47bfb7bcbc9a8a65e5b96f71ba3e63b21002c480b16e`. Следующий ответ 16:27:32.827 всё равно пишет 33492 токена и читает 611228. Последующий тёплый запрос 16:27:44.759 пишет 891, читает 644720. Стабильный блок допускает новую запись: новый суффикс разговора тоже кешируется. Строгое «стабильный блок → запись около нуля» не подтверждено как универсальное правило. [2,3,5]

PID из БД 1718130 уже отсутствовал. По точному native resume UUID в `/proc/*/cmdline` найден реально живой PID 2016230; `ps` показывает старт 08.09 18:27:14 CEST = 16:27:14 UTC. Наблюдение 09.09 14:11:13 UTC: процесс тот же, `--system-prompt` имеет нулевую длину. Это доказательство launch-аргумента, НЕ всех внутренних system-блоков Claude CLI. [3]

После старта этого процесса и последней platform-инъекции:

| API response UTC, 09.09 | Пауза между ответами, s | Cache create | Cache read |
|---|---:|---:|---:|
| 05:05:52.700 | 45462.299 | 629732 | 20790 |
| 08:17:15.111 | 7408.430 | 734094 | 0 |
| 14:00:35.567 | 20529.354 | 720312 | 20790 |

Новые platform-инъекции не встречаются; крупные записи не требуют нового CLI-процесса. У всех этих запросов creation отнесён к `ephemeral_1h_input_tokens`. Это сильное свидетельство в пользу истечения TTL после пауз, но без API cache diagnostics нельзя исключить изменения vendor-префикса. Времена — timestamps ответов, не начала запросов. [2,3,5]

В отдельном native окне 07.09 15:47:37.821–09.09 14:09:08.278: 292 уникальных assistant message id, 3915179 creation, все 3915179 в 1h, 0 в 5m, пять запросов >100000. Это другой знаменатель и другое окно, не сумма недельных 283 платформенных ходов. Для обычного Opus API запись 1h стоит 2× input, чтение 0.1×: отношение **20×**, а 12.5× относится к записи 5m. Недельную стоимость не пересчитывали по этому локальному срезу. Это API-equivalent, не счёт за подписку. [2,3,5]

### F4. Проверка reconnect/compact — UNCERTAIN для доли недельного расхода

Journal extraction охватила 170028 доступных строк с 02.09 14:03:32.592274 до 09.09 14:02:39.005112 UTC, но не нашла целевых сообщений hibernating/waking/compact/reconnect именно для Orchestra-orchestrator. Это не полный аудит соединений: journal предупреждает об ограничении видимости; обычный connect не имеет обязательного долговечного события в `logs`. [2,4]

В `logs` найдены 5 `compact started` и 3 `connect failed`. Правило join: событие строго после предыдущего завершённого Claude turn и не позже текущего. Из 41 дорогого хода 1 имеет такое событие, 40 не имеют; из 242 остальных 3 имеют, 239 не имеют. Это **наличие записи**, а не истина о reconnect. Лишь 1/41 нельзя интерпретировать как истинную частоту влияния lifecycle. Рестарт всего сервиса не является событием конкретного session в этой выборке. [3]

Контрпример TTL-only: 08.09 07:35:13.715 creation=475637/read=20702, предыдущий ответ в 07:33:37.723 (95.992 s). Причина этого быстрого промаха остаётся неизвестной. В той точке есть новая user-инъекция; её наличие само по себе не объясняет потерю префикса. [3]

Удалён поиск родителя по текущему in-memory составу из assemble_prompt. Дополнительный запрос стоит ход/токены. Автоматический повтор полного role-текста в user после resume остаётся; удалять/менять lifecycle в этой задаче запрещено. [4,6]

## Counter-evidence and risks

Промпт действительно менялся на один ctx-байт, но в user-истории и без тотального промаха. Неизменный промпт не гарантирует нулевую запись. Крупные записи бывают без нового CLI; короткий интервал не гарантирует hit. Поэтому ни гипотеза «всё workers», ни «всё reconnect», ни «всё TTL» не подтверждены. Нет оснований обещать возврат $310.63.

Legacy full overrides без компонентной границы сохраняются по прежнему контракту: стабильность генератора не означает переписывание вручную заданных system strings. Файлы памяти/KB и manifest могут законно менять текст. Изменение внешнего CLI/tools также находится вне доказанного инварианта платформенной сборки. Отсутствие живой подсказки увеличивает вероятность решения на устаревшем списке без вызова инструмента; существующие API остаются источником истины.
