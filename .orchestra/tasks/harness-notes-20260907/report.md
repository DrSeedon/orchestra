## Применимость к Orchestra

1. Goal + acceptance criteria + authority вместо управления каждым tool-call уже отражены
   в modules/orchestration.md: один accountable worker, способ выполнения выбирает он.
2. Самое полезное действие — укрепить фактические ограничения, найденные в аудите квитанций:
   настоящий бюджет попыток/раундов и проверяемое доказательство чтения вместо одного Verdict.
   MAX(round) по artifact_path в app/db.py не ограничивает число запусков. Ещё один ревьюер
   поверх этого не исправляет контракт.
3. Сохранение нативной сессии и корректный compact важны. В app/backend_codex.py уже есть
   thread/resume и проверка совпадения thread ID. Проверять надо непрерывность состояния на
   реальном пути восстановления; не обещать по ARC автоматическое ускорение нашей работы.
4. Детерминированные тесты и screenshot/DOM-проверка подходят лучше бесконечного согласования
   прозы. app/acceptance.py уже пиннит acceptance oracle. Проверять: «результат соответствует
   цели», а не только «процесс завершился/отчёт содержит заголовок».
5. Для внешних действий разделять чтение, подготовку результата и разрешённое исполнение.
   Проверять границы реально выданных полномочий у исполняющего инструмента; явно разрешённое
   действие не требует повторного вопроса. Там, где разрешения нет, результат остаётся черновиком.
6. Не переносить каждую ошибку в корень. Общие ограничения — AGENTS.md; детали — guides/KB,
   навык — skill, проверяемое свойство — код/тест. Это совпадает с существующим разделением.
7. Ничего не удалять по лозунгу «модели переросли harness». Durable задачи, очередь, авторство,
   восстановление и журнал операций остаются задачами платформы, даже если модель лучше
   планирует. Модель не стала доказанно несущественным фактором.

Рекомендация: закончить небольшие исправления допуска/верификации и сохранить native resume,
а не строить новую оркестрацию или включать fan-out из трёх ревьюеров по умолчанию.
Архитектурные изменения и модельные оценки в этой задаче не запускались.
