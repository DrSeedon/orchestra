# #268 — уведомление браузера, когда оркестратор зовёт

Строка зова — контракт `back` из #241: `type="tool"`, `content = "mcp__orchestra__notify_user: {\"reason\": …}"`.
Новых полей и нового API не потребовалось.

## Что сделано (`app/static/js/app.js`, `app/static/css/style.css`)

- `_callRowReason(row)` — признак зова по СТРОКЕ журнала, а не по узлу DOM: решение принимает
  живой поток до отрисовки. Возвращает `null` (не зов) или строку причины (возможно пустую).
- `_maybeNotifyCall(row, agent)` — создаёт `Notification`:
  - заголовок `🔔 <агент> зовёт` (имя сессии, в которой сделан вызов, — оно же имя зовущего);
  - тело — `reason`;
  - `tag: orchestra-call-<id>` — вторая защита от дубля, уже на стороне ОС;
  - `requireInteraction: true` — юзера нет у экрана, зов не должен успеть исчезнуть;
  - клик — `window.focus()` + прыжок к строке через существующий `_jumpChatTimelineNode`.
- `_notifiedCallIds` — множество id строк журнала. Один зов = одно уведомление, сколько бы раз
  строка ни приехала (реконнект потока, повтор пачки, дорисовка истории сверху).
- Проводка одна: `_maybeNotifyCall(l, targetAgent)` в `connectSSE().onmessage`. История
  (`_renderHistory`, `_prependHistory`) хука не имеет вовсе, поэтому старые зовы при загрузке
  молчат структурно, а не за счёт проверки.
- `_armCallNotifications(lastId)` в `connectSSE`:
  - `lastId > 0` (история уже на экране) → взводимся сразу: поток отдаёт только строки новее;
  - `lastId === 0` — запасной режим, когда `_fetchHistory` упал и историю везёт сам поток;
    эта пачка — архив, поэтому взвод отложен на 2 с. Иначе пришлось бы молчать до следующего
    реконнекта, то есть тихо потерять канал на весь сеанс.
- `_addNotifyPermissionBtn()` — кнопка `🔔` в полосе `#chat-timeline`, видна ТОЛЬКО пока
  `Notification.permission === 'default'`. Запрос разрешения — по её клику. Запрос на загрузке
  отклоняется один раз и навсегда: второй раз браузер не спросит.
- CSS `.chat-notify-permission` — тот же язык, что у `.chat-timeline-user-nav.is-notify-nav`.
  Скриншот: `notify-permission-button.png`.

## Границы (что НЕ сделано и почему)

- **Уведомления приходят только по ОТКРЫТОМУ агенту.** Клиент видит строки журнала лишь того
  агента, чей поток открыт; зов в чужой сессии до браузера не доезжает вовсе. Для «зовёт кто
  угодно, а я смотрю на другого» нужен серверный признак (зона `back`) — либо поле в
  `/api/sessions`, либо отдельный общий поток. То же ограничение и у клика: он прыгает к строке
  в текущем чате, переключение агента не требуется, потому что чужих уведомлений не бывает.
- **Не глушим уведомление, когда вкладка на переднем плане.** Один путь вместо двух; зовы
  редкие, а «всегда в курсе» — дословная просьба юзера.
- Новых классов Tailwind нет, `scripts/build-tailwind.sh` не нужен.
