# V-713 — как уменьшить копии Git worktree

## Ответ

Да: sparse checkout может убрать из каждого рабочего дерева крупные каталоги, сохранив обычную Git-ветку и общий объектный репозиторий. На измеренных снимках он сократил checkout Katya с 2.040 GB до 2.27 MB, Seedon — с 1.263 GB до 47.3 MB. Экономия относится только к выбранным профилям: файлы вне профиля физически отсутствуют, а конкретные задачи Katya и тест Seedon уже показывают зависимости от таких файлов. Поэтому это настройка состава worktree под роль/проект, а не безопасное глобальное исключение бинарников.

Рекомендация — рассматривать sparse checkout как следующий вариант для отдельных ролей, работающих преимущественно с кодом, и оставить полный checkout для задач, читающих или выпускающих документы, доказательства и данные. До реализации владелец должен выбрать, какие роли получают какой профиль: это архитектурная развилка, поскольку профиль меняет доступные воркеру файлы. Partial clone без sparse checkout проблему копий рабочего дерева не решает; reflink на текущей ФС недоступен; повторное использование worktree между заданиями уже есть.

## Замеры

Размер — выделенные блоки только рабочего дерева (`du -sx --block-size=1`), включая служебный `.git`-файл ссылки; объектные Git-данные в эту цифру не входят. Каждая копия создана в отдельном временном клоне с общими объектами (`git clone --shared --no-checkout`) и удалена сразу после измерения командой `/usr/bin/trash`. Замеры выполнены 05.10.2026 на `/dev/sda1`, `/` — ext4; `git worktree add` получил локальные уже имеющиеся объекты. Время — одна попытка на режим, не холодный сетевой clone. Условия не совпадают с диапазоном 38–148 с из V-699; вклад кэша и изменений дисковой нагрузки отдельно не измерялся. Стоимость миграции ниже указана качественно по числу затронутых путей/контрактов, трудозатраты и тарифы хранилищ не оценивались.

## Что показал код

`create_worktree()` вызывает обычный `git worktree add` и не включает sparse checkout. Менеджер один раз назначает путь новой сессии; перед следующей доставкой persistent-сессия переключает ветку в том же `session.worktree_path`. Значит, повторное использование дерева уже предотвращает создание копии на каждое задание, но число деревьев остаётся привязано к числу сохранённых сессий.

`cleanup_stale_worktrees()` запускается при старте и раз в 24 часа. Он оставляет пути, записанные у неархивированных сессий, и пропускает dirty worktree. Это намеренно не чистка по времени простоя: idle persistent-воркер всё ещё является владельцем пути.

## Ограничения замера

Первая попытка sparse закончилась с пустым index: создание worktree с `--no-checkout` само по себе не создало файлов. Эти два результата отброшены. Корректный повтор включал sparse-настройку и `git read-tree -mu HEAD`; в нём индекс содержал все tracked пути, checkout — только выбранные, а `git status --porcelain` был пуст. Данные первой попытки сохранены в `measurements/repo-checkouts.jsonl`; действительные sparse-цифры — в `measurements/repo-checkouts-corrected.jsonl`, полные — в исходном JSONL.

Файловая система `/` проверена командой `findmnt`: `/dev/sda1`, ext4, `rw`. Микропроба `cp --reflink=always` вернула код 1 и `Operation not supported`; назначения не создала. `/mnt/data` на этом VPS не существует. Все экспериментальные каталоги перемещены в корзину сразу после каждого замера; рабочие репозитории и живые worktree не менялись.

- [Git clone `--filter`](https://git-scm.com/docs/git-clone#Documentation/git-clone.txt---filterltfilter-specgt) подтверждает, что `blob:none` откладывает blob до востребования.
- [Git LFS](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs.adoc) хранит в Git pointer-файлы, а содержимое скачивает через smudge filter при checkout.
