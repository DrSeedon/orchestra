# #260 — регрессия exact-only lookup и её починка

P0 связывал результат с вызовом ТОЛЬКО по точному `tool_use_id` и при промахе рисовал
`⚠️ Результат без вызова`. На живом потоке Claude это дало ложные срабатывания.

## Гипотеза задачи не подтвердилась

Поставлено было: «у Claude идентификатор в событии ВЫЗОВА лежит не в том поле».
Проверено по живым данным, а не по предположению:

- БД: у `tool` и `tool_result` заполнена одна и та же колонка `tool_use_id`
  (вызов 104604 и результат 104608 — `toolu_012xaNqskZsUE1McmiCfDTyt`);
- живой API `/api/sessions/.../stream` отдаёт `tool_use_id` с обеих сторон,
  ключи ответа: `content, event_id, id, session_id, tool_is_error, tool_name, tool_use_id, ts, type`;
- в DOM 27 из 27 карточек вызова несли `data-tool-use-id`.

Данные и их доставка исправны. Причина — клиентская.

## Причина 1 (подтверждена живым замером): вызов приезжает ПОЗЖЕ результата

Инструментированный `_toolForResult` на живом дашборде записал промахи:

```json
{"id": "toolu_01G5brx7JCG8nwANkQmhc6eF", "cardInDom": false, "hasAnchor": true, "totalCards": 14}
{"id": "toolu_017hbqrPa67AHYE4EU1o8MZy", "cardInDom": false, "hasAnchor": true, "totalCards": 14}
```

`cardInDom: false` — в момент отрисовки результата карточки вызова в DOM ещё нет.
`hasAnchor: true` — идёт дорисовка страницы истории. Обе строки из одного параллельного
блока: вызовы 104197/104198, результаты 104201/104202 — граница страницы прошла между
ними, и вызовы приехали следующей, более старой страницей.

Второй источник того же: у Codex/Luna результат попадает в журнал РАНЬШЕ своего вызова
(`impl256-t1`: `tool_result exec-64698…` записан до `tool exec-64698…`).

`_findLastBefore` ищет только НАЗАД от якоря, поэтому оба случая давали вечную сироту.
Старый код это маскировал, приклеивая результат к последнему вызову — исходный дефект #260.

## Причина 2 (измерена по БД, но пользователю сейчас не видна)

63.7% строк `tool_result` во всём журнале (24 474 из 38 434) не несут `tool_use_id` вовсе —
поле появилось недавно, среди свежих строк (id > 100000) пустых 0 из 1851. Для таких строк
exact-only означал бы «Результат без вызова» на КАЖДОЙ.

Честная оговорка о достижимости: живьём я этот путь воспроизвести не смог. В активных
сессиях строки без id лежат за потолком `MAX_CHAT_NODES = 500`, а сессии, где они попали бы
на экран целиком (`perf-codex-seedon`, `audit-front`, `tg-readability`, `feat-quota-guard`),
архивированы и на дашборде не выбираются. Поэтому причина 2 закрыта браузерным тестом на
строках реальной формы, а не скриншотом прода.

## Правка

1. `_toolForResult`: результат БЕЗ идентификатора снова связывается соседством
   (`[data-last-tool]` / `[data-compact-tool]`) — дореформенное поведение, для таких строк
   единственно возможное и верное.
2. Результат С идентификатором ищет вызов по ВСЕМУ чату (`querySelector`), а не назад от
   якоря: идентификатор уникален, поэтому направление не важно, и случай «вызов ниже
   результата» тоже закрывается. Область поиска разведена по рендерерам
   (`[data-compact-tool]` против `:not([data-compact-tool])`), чтобы развёрнутая
   compact-карточка не путалась со своей строкой.
3. `_adoptOrphanResults`: когда вызов вставлен, он забирает уже нарисованную сироту с тем же
   идентификатором и результат перерисовывается на её месте.

Сирота остаётся только там, где вызова действительно нет.

### Дефект, который нашёл собственный тест

Первая версия усыновления делала `node.remove()`. `_prependHistory` держит `chat.firstChild`
якорем на весь цикл дорисовки, и если сиротой оказывался именно он, следующая вставка падала
с `NotFoundError: The node before which the new node is to be inserted is not a child of this node`.
Это ронялo всю дорисовку истории. Узел теперь не удаляется, а гасится.

## Проверка

Живой дашборд, реальный поток оркестратора:

| | сирот |
|---|---|
| main (100 строк) | 2 |
| main (+ добор истории) | 5 → 7 |
| ветка (те же условия) | **0** |

Все сироты на main были ложные: `callCardExists: true`, карточка вызова присутствовала и
предшествовала сироте. `substitutionHits=1`, ошибок в консоли ноль.

Скриншоты: [до](regression-before.png) — `📋 New: "Grok-воркер…"` и следом
`⚠️ Результат без вызова · toolu_01SyxXM4rXatT5NxB5vbnN63` с сырыми полями, ровно жалоба
юзера; [после](regression-after.png) — результаты в своих карточках.

Оракул расширен и параметризован по формату идентификатора × обоим режимам:

- `test_split_history_page_pairs_results_with_calls_that_arrive_later`
  — `toolu_*` (Claude/MCP), `exec-<uuid>` (Codex/Luna), `_codex_item_id` в теле вызова;
- `test_legacy_rows_without_tool_use_id_pair_by_adjacency` — строки без идентификатора.

Прогоны: 14 passed по набору корреляции, 30 passed по соседним tool/codex/task/compact,
14 passed по стражам глобальных имён, Tailwind и usage-истории.

### Мутации

| мутация | ожидание | факт |
|---|---|---|
| вернуть склейку «к последнему вызову» (`if (true)` в ветке без id) | красный | `2 failed` — оба режима параллельного теста |
| сломать поиск id у Claude (`toolu_` → `BROKEN_` в селекторе) | красный | `2 failed` — ровно плечи `claude-normal` / `claude-compact`, Codex зелёные |

Маркер обеих мутаций до правки и после отката: `1` и `1`. Зелёный повтор после отката: 14 passed.

## Найденная попутно проблема (не чинил)

`loadMoreLogs` при полном DOM бесполезен: `while (chat.children.length > MAX_CHAT_NODES)
chat.removeChild(chat.firstChild)` срезает ровно те старые строки, которые добор только что
дорисовал сверху. Замер: после шести нажатий «Load 500 more» число карточек вызова осталось
148, как и до них. Это не из #260 и отдельной задачи не заводил.
