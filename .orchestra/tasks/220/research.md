# #220 — можно ли убрать рестарт из цикла улучшения Orchestra

Фаза 1 (research). Живой сервис не рестартился ни разу; все эксперименты — отдельными
процессами из этого worktree и на read-only копии БД.

## Question

### Context
Orchestra — один процесс `uv run uvicorn app.main:app` (PID 2519657, uptime 51 527 с на момент
замера). В нём же живут сессии агентов: 13 прямых детей (9 `node /usr/bin/codex … app-server
--stdio`, 4 `claude`), 59 потомков всего, 1 476 МБ RSS у детей. Транспорт — stdio-пайпы,
владелец пайпа = сервер (`asyncio.create_subprocess_exec`, `backend_codex.py:437`,
`backend_claude.py:257`). `Type=simple` без `KillMode` → SIGTERM уходит всему cgroup.

### Change under test
Две РАЗНЫЕ цели, которые постановка справедливо разделяет:
- **(A)** правка применяется без перезапуска процесса;
- **(B)** перезапуск перестаёт быть больным, потому что ходы его переживают.

### Baseline
Текущее положение: правка в `app/**.py` живёт до ближайшего рестарта; рестарт убивает
активные ходы.

### Outcome (measurable)
Три числа, каждое считается по фактическим данным, а не по ощущению:
1. доля правок за месяц, требующих рестарта;
2. цена одного рестарта в убитых ходах;
3. цена ожидания (задержка выката) и цена дренажа.

---

## Hypotheses considered

| # | Гипотеза | Фальсификатор | Вердикт |
|---|---|---|---|
| H1 | `importlib.reload` даст горячее применение правок в `app/**.py` | живой объект после reload продолжает исполнять СТАРЫЙ код | **REFUTED** (E1/E2, измерено) |
| H2 | Боль — в самом рестарте (секунды простоя) | если ходы переживают рестарт, боль исчезает | **REFUTED**: боль в убитых ходах И в задержке выката, второе крупнее |
| H3 | Вынос сессий в отдельные процессы снимает боль | посчитать долю правок, которые ПОСЛЕ выноса всё ещё убивают ход | **ЧАСТИЧНО**: снимает 23.3% (до ~39% при покатной замене), оставляет 15.7% |
| H4 | Промпты и `pipelines/` уже горячие (посылка постановки) | найти место, где промпт пересобирается из файлов | **REFUTED**: пересборка только на spawn / `_load_from_db` |
| H5 | Дренаж перед рестартом дёшев | измерить время ожидания тишины | **CONFIRMED по латентности** при admission control, **REFUTED** без него; сходимость дренажа НЕ доказана (F7) |

---

## Findings

### F1 — Посылка постановки про «горячие промпты» неверна. CONFIRMED
Тир 2 (первоисточник — свой код) + тир 2 (докстринг, признающий это прямым текстом).

`ROLE_SYSTEM_PROMPT()` — единственная функция, читающая `pipelines/**/prompts/**` — имеет
ровно 4 call-site, и все они на входе в жизнь агента:
- `manager.py:608`, `manager.py:611` — spawn;
- `manager.py:1439`, `manager.py:1441` — `_load_from_db` (то есть `auto_resume_all` при СТАРТЕ сервера).

Дальше собранная строка лежит в `session._current_prompt` (`manager.py:1546`) и переинжектится
«раз на сессию» (`session.py:927`: `if self.session_id and self._current_prompt and not
self._prompt_injected`). Из файлов при этом перечитывается ТОЛЬКО личная память —
`refresh_worker_memory` (`session.py:938`), и её докстринг (`prompting.py:84`) говорит это
буквально: *«The prompt is assembled once (spawn / _load_from_db) but re-injected on every
resume and compact»*.

Следствие, которое надо назвать вслух: **правка `pipelines/default/prompts/roles/*.md` или
`modules/*.md` не доезжает до ЖИВОГО агента до перезапуска сервера** (или до респавна агента).
Горячее в этом слое — только `docs/workers/<имя>.md`.

Побочное наблюдение, НЕ проверенное экспериментом (UNCERTAIN, вынесено в «Открытые вопросы»):
`session.py:927-941` сравнивает `prompt_template_hash` (свежий хеш файлов) и печатает
«your role instructions were updated», но инжектит `self._current_prompt` — строку, собранную
раньше. Если чтение верное, агент получает уведомление об обновлении вместе со старым текстом.

### F2 — `importlib.reload` не работает на наших живых объектах. REFUTED (для H1)
Тир 1 (прямое измерение на нашем коде: `/tmp/t220_reload_exp.py`, критерии зафиксированы
ДО прогона; мутация `app/session.py` с откатом `cp`→`mv`+`utime`, контрольный зелёный
повтор после отката пройден, `grep -c` маркера = 0, `git status` чист).

```
before: _display_status() -> 'idle'
before: app.manager.AgentSession is app.session.AgentSession -> True
--- after importlib.reload(app.session) ---
E1 live instance ._display_status() -> 'idle' | FAIL
   type(inst) is new class -> False
   isinstance(inst, new AgentSession) -> False
   fresh instance from reloaded module -> 'MUTATED-220'
E2 app.manager.AgentSession is app.session.AgentSession -> False | FAIL
   manager's binding still the OLD class -> True
E3 deferred 'from app.session import AgentSession' is new -> True | PASS
CONTROL after rollback: _display_status() -> 'idle' | clean
```

Что это значит по нашему коду, в числах (AST-обход `app/`, 63 файла):
- **287** операторов `from app.X import Y`, из них **109 на уровне модуля** — каждый
  замораживает снимок. После reload в процессе живут ДВА класса `AgentSession`
  одновременно, и `manager` держит старый.
- **117** модульных синглтонов вида `name = Call(...)`, включая
  `deps.py:10 manager = SessionManager(...)` — reload `app.deps` обнулил бы реестр сессий.
- **55** мест `create_task`/`spawn_supervised` вне `session.py` и **34** долгоживущих цикла:
  запущенная корутина не переезжает в новый код никогда.
- **24** межмодульных `except <наше исключение>` — после одностороннего reload `except`
  перестаёт ловить, потому что классы разные.

Тихо ломается именно это: не падение, а два параллельных мира объектов.

**Контр-находка, снижающая мою же оценку риска.** Я ожидал, что `AgentStatus` даст массовый
тихий разъезд (65 межмодульных мест сравнения). Измерено — НЕ даёт:
```
E4 old AgentStatus.IDLE == new AgentStatus.IDLE -> True | PASS
   old is new -> False | .value equal -> True
```
`class AgentStatus(str, Enum)` (`session_state.py:10`) сравнивается по строковому значению, а не
по identity. `is`-сравнений с `AgentStatus` в коде ноль (грепнуто). Второй Enum, `_Phase`
(`tg_bridge.py:287`), — обычный, но все 8 его употреблений внутри своего модуля.

### F3 — Горячая подмена РОУТОВ работает и стоит дёшево. CONFIRMED
Тир 1 (`/tmp/t220_routeswap.py`, критерии до прогона; мутация `app/routes/proxy.py` с откатом
и контрольным прогоном).

```
before: 200
after swap: 200 {'MUTATED_220': True}
E6 handler swapped -> True | PASS
   deps.manager identity preserved -> True
CONTROL after rollback: clean {'proxies': [], 'active': ''}
```
Схема: `importlib.reload(app.routes.X)` → выкинуть из `app.router.routes` пути этого модуля →
`include_router` заново. Синглтон `deps.manager` переживает, потому что `app.deps` НЕ
перезагружается.

Почему это безопаснее, чем reload вообще:
- все 20 операторов `from app.routes… import` в коде — **отложенные** (внутри функций),
  то есть подхватывают новый модуль (E3 PASS);
- модульного изменяемого состояния в роутах почти нет: 8 из 10 файлов — ноль,
  `routes/sessions.py` — одна константа, `routes/tg.py` — одна. Исключение одно:
  **`routes/system.py` — 14 модульных объектов, из них `_usage_cache`, `_codex_usage_cache`,
  `_grok_usage_cache`**; их reload обнулит (цена — один лишний опрос провайдера), а
  `_usage_snapshot_loop`, запущенный в lifespan, останется на старом коде.

Без E5 картина была бы неверной: просто `reload` роут-модуля НЕ меняет поведение живого
приложения — надо именно пересобирать список роутов.
```
E5 app kept 8 routes; endpoints identical to reloaded module for 0/8 paths | FAIL
   (живой app продолжает указывать на СТАРЫЕ функции)
```

### F4 — Доля правок, требующих рестарта: 48.5%, а не «примерно половина на глаз». CONFIRMED
Тир 1 (замер по `git log main --since=2026-07-12`, 609 коммитов, классификация по путям).

Из 609 коммитов 137 — чистые артефакты (`docs/tasks/**`, CHANGELOG, тесты). Остаётся
**472 коммита, меняющих поведение**. Три тира по признаку из постановки — «читается с диска в
момент использования» против «зафиксировано в памяти»:

| тир | что это | коммитов | доля |
|---|---|---|---|
| **T1 горячее сейчас** | `app/static/**`, `app/templates/**`, `docs/workers/**`, `scripts/**`, `app/codex_review_artifact.py`, `pipeline.yaml` | 140 | **29.7%** |
| **T2 тёплое** — хватает реконнекта/нового спавна, рестарт сервера не нужен | `CLAUDE.md`/`AGENTS.md`, `app/mcp_stdio.py` | 103 | **21.8%** |
| **T3 холодное** — сегодня нужен рестарт | `app/**.py` + `pipelines/**/prompts/**` | 229 | **48.5%** |

Состав T3 (коммит может попасть в несколько): `core` 158, `supervisor` 74, `prompts` 59.

**Важно: `pipeline.yaml` лежит в T1, а не вместе с промптами.** Манифест кешируется по
`(mtime_ns, размер)` (`pipeline.py:369-394`), и `_apply_manifest_effort()` вызывается на
границе КАЖДОГО хода (`session.py:945`) — то есть правка эффорта в манифесте доезжает до
живого агента без рестарта. Первая версия этого раздела валила весь каталог `pipelines/`
в холодные и была неправа; поймано на ревью, пересчитано.

**Ключевая цифра для пункта 3 постановки.** Из 472 коммитов **45 (9.5%)** холодны
ИСКЛЮЧИТЕЛЬНО из-за F1 — их единственная холодная часть это markdown промптов. Они станут
горячими от одной точечной правки (пересобирать `_current_prompt` из файлов в точке
переинжекта, а не переиспользовать собранную строку).

**Проверка на единицу счёта.** Squash-коммит — это «выкат», а не «правка»: в одном может
лежать и однострочная правка промпта, и кросс-слойная фича, а смешанный коммит попадает в
свой САМЫЙ холодный путь. Поэтому то же самое посчитано ещё раз по изменённым ФАЙЛАМ
(n=1135): T1 34.1%, T2 13.3%, T3 52.6%, доля «холодно только из-за промптов» 10.5%.
Обе единицы дают одну картину — вывод от выбора единицы не зависит. Скрипт классификации
лежит рядом (`classify_commits.py`), числа воспроизводимы.

Топ холодных файлов месяца: `session.py` 47, `routes/system.py` 37, `db.py` 36, `manager.py` 35,
`tg_bridge.py` 27, `routes/sessions.py` 26, `workspace.py` 23, `backend_codex.py` 19.

### F5 — Цена одного рестарта: 2.38 убитых хода. CONFIRMED (но НЕ двумя сходящимися замерами — см. ниже)
Тир 1 (read-only копия живой БД).

*Замер 1 — реконструкция окон ходов.* Первая версия пары «`user_message` → следующая строка
`turn_usage`» была НЕВЕРНА, и это поймало ревью. `session.py:887` и `session.py:891` пишут
`user_message` и делают `return`, НЕ начиная хода: так логируются сообщения, вклиненные в
идущий ход, и сообщения, поставленные в очередь во время компакта. Наивная пара считала
каждое из них началом отдельного окна.

Исправленная реконструкция даёт ровно одно окно на строку `turn_usage` (началом считается
самое раннее `user_message` после предыдущего `turn_usage` той же сессии). **533 лишних
строки отброшено, окон стало 1 507 вместо 2 020.** Длительность хода: медиана 89 с, p75 289 с,
p90 705 с, p99 2 198 с, макс 5 207 с. Ни одно окно не превысило отсечку 7 200 с, поэтому
отсечка на результат не влияет (прогнано с ней и без неё — цифры побитово те же).

**Среднее число одновременных ходов в рабочие часы: 1.50, а не 2.17.** Ошибочная пара
завышала его на 45%. Доля занятых минут (52.2%) устояла.

*Замер 2 — фактические жертвы.* Строки `[system] Orchestra server restarted` (`type='user_message'`,
`manager.py:1824`) уходят ровно тем, кто был `running`. За 31 сутки: **13 рестартов, заставших
хотя бы один живой ход, 31 убитый ход, 2.38 хода на рестарт.**

**Заявку «два независимых замера сходятся» я снимаю.** Во-первых, оба берутся из одной БД, то
есть независимость мнимая. Во-вторых, после исправления они РАСХОДЯТСЯ: 1.50 против 2.38. И
измеряют они разное: 1.50 — среднее по всем рабочим минутам, 2.38 — условное среднее по
минутам, В КОТОРЫЕ ОПЕРАТОР РЕШИЛ рестартовать. Разрыв правдоподобно объясняется тем, что
рестартуют не в случайный момент, а после работы, когда агенты как раз заняты; проверить это
нечем — полного списка рестартов нет. Для оценки цены рестарта верна цифра 2.38 (это прямой
счёт жертв), а 1.50 описывает фон, а не жертвы.

При медианной цене хода $1.121 (среднее $2.257, p90 $6.139) один рестарт стоит примерно
$2.7 виртуальных денег; настоящая цена — сожжённая квота и потерянное состояние хода.

Масштаб в процентах: за окно после мержа #160 (2026-08-06 …) — 1 388 завершённых ходов и
9 убитых рестартом, то есть **0.65% ходов**.

Оговорка к методу, остающаяся в силе: реконструкция видит только ЗАВЕРШИВШИЕСЯ ходы — у
убитого или зависшего хода строки `turn_usage` нет вовсе, поэтому замер 1 смещён в сторону
успешных. Замер 2 этим не страдает. Список рестартов неполон по построению: рестарт, никого
не заставший, следа не оставляет — это делает F6 верхней оценкой.

### F6 — Задержка выката больше, чем цена рестарта. LIKELY (верхняя оценка)
Тир 1 по данным, но список рестартов неполон (см. F5), поэтому это ВЕРХНЯЯ граница.

От мержа холодного коммита в `main` до ближайшего рестарта: **медиана 3.3 ч, p75 22.9 ч,
p90 40.6 ч, макс 100.8 ч**. В течение часа применяется 22%, в течение 8 часов — 52%,
**дольше суток ждут 25%**.

Это и есть настоящая боль, а не секунды простоя: правка существует, протестирована, смержена —
и от четверти до половины суток не действует. Причём чинит она обычно то, на что уже
наступили.

### F7 — Дренаж дёшев по ВРЕМЕНИ (CONFIRMED), но его завершение не гарантировано (UNCERTAIN)
Тир 1 по латентности; гарантия завершения — не измерена и, по разбору кода, не следует.

Наивное «подождать тишины» — плохо: время до ближайшей минуты без единого активного хода в
рабочие часы: медиана 2 мин, но **p75 = 52 мин, p90 = 151 мин, макс 285 мин**. Агенты
подхватывают друг друга, и полная тишина наступает редко.

С admission control (перестать пускать НОВЫЕ ходы, дождаться только тех, что уже идут),
на ИСПРАВЛЕННЫХ окнах из F5:

| | p50 | p75 | p90 | p95 | p99 | макс |
|---|---|---|---|---|---|---|
| дренаж, мин | **1.2** | 11.8 | 25.2 | 38.6 | 71.5 | 87.6 |

≤5 мин в 60.8%, ≤15 мин в 79.8%, ≤30 мин в 92.4%. Числа практически не сдвинулись от
исправления пары в F5 — распределение дренажа к этой ошибке устойчиво, в отличие от
средней одновременности.

Разница между двумя строками — целиком в admission control. Сегодня его нет:
`/api/restart` (`routes/system.py:1708`) спит 0.5 с и шлёт себе SIGINT.

**Чего эта таблица НЕ доказывает — и это существенно для рекомендации.** Она измеряет
остаточное время ИСТОРИЧЕСКИ ЗАВЕРШИВШИХСЯ ходов, то есть латентность дренажа при условии,
что дренаж вообще сходится. Сходимость из неё не следует, потому что источник новых ходов
не один:
- идущий агент шлёт `send_message` другому агенту и запускает у того ход;
- воркер по завершении авто-репортит родителю — это тоже новый ход;
- компакт может отложить сообщения и слить их позже (`session.py:887`).

Гейт, закрывающий только «внешний» приём, оставит причинную цепочку живой, и дренаж может
не сойтись никогда. Значит гейт обязан быть ГЛОБАЛЬНЫМ барьером на admission (включая
agent→agent и авто-репорт), плюс безусловный дедлайн с явным «дренаж истёк, рву N ходов».
Замер латентности при таком барьере остаётся в силе; замера сходимости нет, и до его
появления «92% ≤30 мин» надо читать как «когда дренаж сходится», а не как гарантию.
Кроме того, из окон выпадают убитые и зависшие ходы (F5), поэтому максимум 87.6 мин —
не верхняя граница.

### F8 — Вынос сессий в отдельные процессы окупается хуже, чем кажется. LIKELY (сценарная оценка, не замер)
Классификация коммитов — тир 1, но граница «супервизор / ядро» назначена мной по списку
файлов, а не выведена из существующего дизайна: такой архитектуры не существует, мерить
нечего. Обе стороны арифметики могут сдвинуться, поэтому это оценка сценария, а не
измеренная выгода. Что именно может её сдвинуть — в «Counter-evidence».

Что мешает сегодня — конкретно:
- CLI-процессы это ДЕТИ сервера с stdio-пайпами; владелец пайпа умирает → CLI умирает даже
  без сигнала. Значит нужен процесс-супервизор на сессию, владеющий пайпом, и сокет вместо stdio;
- `live_broker.py:1-8` прямым текстом: *«Single process, single event loop… Not compatible with
  multi-worker uvicorn (in-memory, like the session manager)»*;
- реестр `manager.sessions` — обычный dict в памяти.

Что уже готово и удешевляет вынос: MCP-слой УЖЕ вне процесса и ходит по HTTP —
`app/mcp_stdio.py` (2 269 строк) использует **34 различных `/api/...` пути**. Контракт
«агент ↔ ядро» существует и обкатан.

Но арифметика выгоды неутешительна. Если разделить код на супервизорный (`session*.py`,
`backend_*.py`, `events.py`, `tool_call_guard.py`, `pidfd_exec.py`) и ядро:
- **110 коммитов (23.3% всех поведенческих)** перестанут убивать ходы;
- **74 коммита (15.7%)** трогают супервизорный код — это ровно самые частые файлы:
  `session.py` 47, `backend_codex.py` 19, `session_turns.py` 18, `backend_claude.py` 11.
  (Скрипт печатает «core-only 155 / 32.8%», но 45 из них — промптовые коммиты, которые
  чинит F1, а не разделение процессов. Выгода именно разделения — 110.)

То есть крупная переделка архитектуры покупает 23% правок и не закрывает даже самый
редактируемый файл проекта. Оговорка, снижающая уверенность в 15.7%: супервизор можно
менять покатно — заменять его версию, когда ЕГО сессия освободилась. Тогда часть из этих
74 коммитов тоже перестанет убивать ходы, а цена — тот же дренаж, только на сессию.
Верхняя граница выгоды (D) поэтому не 23.3%, а ближе к 39%; нижняя — 23.3%. Замерить
нечем: архитектуры не существует.

## Ответы на пункты постановки

**1. Где проходит настоящая граница.** Не по слоям, а по трём тирам из F4, и признак
именно тот, что назван в постановке: читается ли байт с диска в момент использования.
Уточнение к постановке: `pipelines/**` лежит НЕ на горячей стороне (F1).

**2. Реален ли `importlib.reload`.** Для `app/**.py` с живыми объектами — нет (F2, измерено).
Для роут-модулей с пересборкой списка роутов — да (F3, измерено), с одним известным
исключением (`routes/system.py`: три кеша обнулятся, `_usage_snapshot_loop` останется старым).

**3. Доля правок, которые могли бы стать горячими, если бы жили данными.** 9.5% всех
поведенческих коммитов (45 из 472; 10.5% при счёте по файлам) — только за счёт починки F1. Ещё
`routes/*.py` — кандидат на горячую подмену по F3. Всё остальное в T3 это механизмы
(`db.py`, `manager.py`, `session.py`, `tg_bridge.py`), а не политики: перенос их «в данные»
означал бы написать интерпретатор, то есть ту же сложность с другой стороны.

**4. Вынос сессий в отдельные процессы.** Технически возможен, контракт частично есть
(34 HTTP-пути), но покупает 23.3% правок и оставляет 15.7% (F8). Понадобятся: сокет вместо
stdio, IPC для событий вместо `live_broker`, распределённый реестр сессий вместо dict,
переживающий рестарт ядра.

**5. Что дешевле и что надёжнее — одна рекомендация.**

**Рекомендация: (B) через дренаж, плюс два точечных горячих фикса. НЕ (A) целиком и НЕ (D).**

По возрастанию цены:
1. **Пересобирать промпт из файлов в точке переинжекта** (F1). Цена — десятки строк в
   `session.py`/`manager.py`. Отдача — 10.0% всех поведенческих правок из холодных в горячие,
   и закрывает расхождение «уведомили об обновлении, прислали старое».
2. **Дренаж перед рестартом** (F7): гейт на приём новых ходов → ожидание нуля `RUNNING`
   с потолком → SIGINT. Цена — небольшой кусок в `manager` + `/api/restart`. Отдача — рестарт
   перестаёт быть разрушительным в 92% случаев ценой ≤30 мин ожидания, и снимает ВСЮ цену
   F5 (2.38 хода за рестарт) для ВСЕХ 48.5% холодных правок, а не для их части.
   Это единственный из вариантов, чья отдача не зависит от того, какой файл правили.
3. **Горячая подмена роут-модулей** (F3) — опционально, ~20% холодных правок,
   но реальный риск двух миров объектов при ошибке в границах.
4. **Вынос сессий в процессы** (F8) — не рекомендую: 23.3% отдачи (до ~39% при покатной
   замене супервизора) за переделку транспорта, событий и реестра.

Дополнительный довод, всплывший на ревью: **покатная замена супервизора в (D) — это тот же
дренаж, только с гранулярностью сессии.** То есть (B) не альтернатива (D), а его
предпосылка: механизм «дождись, пока эта единица освободится, потом подменяй» нужен в обоих
случаях. Значит порядок работ определён независимо от того, дойдём ли мы когда-нибудь до (D):
дренаж делается первым в любом сценарии.

Почему (B) выигрывает у (A): дренаж не зависит от того, какой файл правили, не создаёт
двух версий классов в одном процессе и не имеет тихого режима отказа. Ошибка в дренаже
видна сразу (рестарт не наступил / наступил рано); ошибка в reload — это `isinstance`,
вернувший False через три часа.

## Что ОСТАНЕТСЯ требующим рестарта при ЛЮБОМ решении, и почему

Обязательная строка постановки. Первая версия списка валила в кучу «физически невозможно» и
«у нас сейчас так написано»; ревью это справедливо разобрало, и список разделён на две
группы. Разница практическая: группа A закрывает вопрос, группа B — это цена, которую
кто-то должен заплатить кодом.

**A. Процессно-связанное: не чинится ничем, кроме перезапуска.**
1. **Интерпретатор и уже загруженные нативные расширения.** C-расширение отображается в
   адресное пространство один раз; выгрузки нет. Сюда же `pyproject.toml`/`uv.lock`, когда
   меняется нативная зависимость.
2. **Конфигурация самого процесса:** слушающий сокет и параметры uvicorn, свойства
   systemd-юнита, унаследованные файловые дескрипторы, переменные окружения, нужные ДО
   инициализации процесса (`EnvironmentFile` читается systemd при запуске — приложение
   может перечитать `.env` само, но не то, что уже прочитано до старта Python).
3. **Форма живых объектов — поля `AgentSession`, состояние `SessionManager`** — в той мере,
   в какой миграция экземпляров не написана. Измерено (E1/E2): существующие экземпляры
   навсегда остаются на старом классе, а `isinstance` против нового возвращает False.

**B. Решаемое в принципе, но ценой отдельного механизма — сегодня требует рестарта.**
4. **Стек middleware и объект приложения (`app/main.py`).** Starlette собирает цепочку один
   раз; пересобрать её у живого приложения можно (как в F3 пересобирается список роутов), но
   это отдельная работа и делать её надо под дренажом.
5. **Долгоживущие корутины: 34 цикла и 55 `create_task` вне `session.py`.** Запущенная
   корутина исполняет код, с которым стартовала, — но её можно отменить и пересоздать.
   Цена: у каждой своё состояние, которое надо уметь передать.
6. **Миграции схемы.** `init_db()` (86 DDL, `app/db.py:53`) вызывается на старте — это наша
   проводка, а не свойство SQLite; онлайн-миграции возможны.
7. **Код супервизора при идущем ходе** (15.7% правок за месяц). В архитектуре (D) это
   решается покатной заменой супервизора после того, как ЕГО сессия освободится, — то есть
   тем же дренажом, только на сессию, а не на весь процесс.

Итог: «всё горячо» невозможно из-за группы A и никогда не станет возможным. Всё, что можно
честно обещать, — «рестарт остаётся, но перестаёт стоить 2.38 убитых хода».

## Counter-evidence

- **Против моей же оценки риска reload:** ожидал массовый тихий разъезд по `AgentStatus`
  (65 мест) — измерение показало, что str-Enum сравнивается по значению и разъезда нет (F2).
  Риск reload ниже, чем я предполагал, но E1/E2 всё равно закрывают вопрос.
- **Против «просто дренаж»:** без admission control дренаж негоден — p90 составляет 151 мин (F7).
  Рекомендация держится ИМЕННО на admission control, без него она разваливается.
- **Против важности рестартов вообще:** 0.65% ходов убито за неделю (F5) — величина малая.
  Если бы это было единственным эффектом, задачу стоило бы закрыть как «не стоит работы».
  Вес ей придаёт F6 (задержка выката), а F6 — верхняя оценка на неполном списке рестартов.
- **Против выноса в процессы:** аргумент «MCP уже по HTTP, значит вынос дёшев» правдоподобен
  и я его проверил — 34 пути существуют. Но он не покрывает поток СОБЫТИЙ (`live_broker`,
  in-memory by design) и реестр сессий, а это и есть основная работа.
- **Сезонность:** «рабочие часы» отобраны по самим данным (UTC 04–13). Неделя измерения
  одна; при другом ритме работы дренажные проценты сдвинутся.
- **Против моей реконструкции ходов (нашло ревью, подтверждено кодом):** пара
  «`user_message` → следующий `turn_usage`» считала началом хода и вклиненные в ход
  сообщения, и поставленные в очередь при компакте (`session.py:887`, `:891` — оба пишут
  лог и делают `return`). 533 лишних окна, средняя одновременность завышена на 45%.
  Исправлено в F5; распределение дренажа устояло, «сходимость двух замеров» — нет.
- **Против моей оценки (D) в худшую сторону:** назначение файлов в «супервизор» и «ядро»
  сделано мной по списку, а не измерено; при покатной замене супервизора верхняя граница
  выгоды поднимается с 23.3% примерно до 39% (F8).
- **Против списка «останется требующим рестарта»:** первая версия объявляла процессно-
  связанным то, что таково лишь по текущей проводке (middleware, миграции, `.env`,
  долгоживущие задачи). Список разделён на A (физика) и B (цена). Группа A короче, чем я
  написал сначала, — то есть обещать можно чуть больше, но «всё горячо» по-прежнему нельзя.

## Affected files, risks, edge cases (для кода, если фаза 2 будет одобрена)

Фикс 1 (промпт из файлов при переинжекте):
- `app/session.py:927-941` — точка переинжекта; `app/manager.py:1439-1493` — сборка `current_base`.
- Риск: пересборка на каждом резюме стоит чтения файлов и ломает `prompt_overlay`/ownership,
  если восстанавливать границу компонентов неаккуратно (`manager.py:1468-1492` уже
  занимается именно этим).
- Edge case: агент с кастомным промптом (`update_worker_prompt`, `manager.py:1248`) не должен
  получить обратно шаблон.

Фикс 2 (дренаж):
- `app/routes/system.py:1699-1713` (`/api/restart`), `app/manager.py` (реестр статусов),
  TG-команда `/restart`.
- Риск: гейт на приём ходов — общий рантайм; неверный гейт остановит доставку сообщений
  вообще. Закрывать тестом в обе стороны: и «новый ход не пускается», и «висящее сообщение
  доедет после рестарта».
- Edge case: ход, который не кончается (p99 = 71.5 мин) — нужен безусловный потолок ожидания
  и явное сообщение «дренаж истёк, рву N ходов».
- Edge case: bg-джобы и мерж-операции имеют свой shutdown (`main.py:113-127`) — дренаж должен
  встать ДО них.
