# V-840 — аудит времени инструментов, спавна и диска

Срез снят 14.10.2026 около 10:02 CEST. Живой процесс PID 3753260 подтвердил `ORCHESTRA_DB_PATH=/home/kesha/orchestra/data/orchestra.db`; БД открывалась только `mode=ro`, `query_only=on`, в одной read-транзакции. Срез семи суток: `2026-10-07T08:02:16.012801Z` — последний id снимка 667698 с timestamp `2026-10-14T08:02:15.949620Z`. Проверка 2 001 id около нижней границы не нашла строк с timestamp по другую сторону cutoff ([cutoff_boundary_check.json](evidence/cutoff_boundary_check.json)). Времена ниже UTC.

## Выводы

- За окно нашлось 31 143 записи вызовов инструмента: 20 601 Claude, 10 509 Codex и 33 Harness. Положительную длительность между `tool` и следующим `tool_result` с тем же `session_id + tool_use_id` удалось посчитать для 30 260 вызовов. У 883 вызовов результат не найден к снимку БД (227 Claude, 656 Codex); отрицательных интервалов в итоговом окне нет. Процентили — nearest-rank.
- Сумма парных интервалов — 132 159,9 с. В `turn_usage` есть 2 102 завершённых хода с `turn_duration_ms`, суммарно 318 128,2 с. Отношение сумм — 41,5% (Claude 59,8%, Codex 14,4%). Это вклад сумм длительностей инструментов, не доля непересекающегося wall time: параллельные вызовы могут перекрываться. Для Claude `turn_usage.tool_union_duration_ms` не заполнялся, поэтому точную union-долю из БД получить нельзя.
- Основной измеренный провал MCP — `get_worker_logs`: один вызов за 502,5 с, хотя агент запросил три последние строки и получил 30 символов. Серверный путь прочитал и сериализовал до 5 000 последних строк (11,08 млн символов содержимого) до того, как клиент обрезал ответ до трёх.
- Новый sparse-код после рестарта работает. Пять spawn после старта текущего процесса заняли 0,94–5,95 с до возврата MCP; первая команда воркера появилась через 7,84–12,14 с. Три завершённых первых хода закончились через 143,7–177,2 с, при `api_duration_ms` 121,5–153,5 с. Наблюдаемая задержка первого хода в основном после создания копии.
- Диск гостю виден как виртуальный 300G `QEMU HARDDISK`, ext4. На обычном интервале `iostat` занятость была 0–1,3%, ожидание чтения/записи — до 1,19 мс; свободно 102G. Одновременно замерены 32 MiB direct write 719 MiB/s и read 1 511 MiB/s. Эти единичные короткие прогоны не доказывают класс физического носителя; `fio` отсутствует. Оснований покупать более быстрый диск в этом исследовании нет.

**Подтверждённая серверная проблема — `get_worker_logs`.** Для `ai-table-worker` вызов `limit=3` (`08.10 09:23:11Z`, сессия `206a85e3`) занял 502,46 с. MCP-код делает GET с `after_id=0`, потом берёт `logs[-limit:]`; HTTP endpoint для такого запроса вызывает `get_logs()` с пределом по умолчанию 5 000 строк. БД содержит 12 641 строку в этой сессии, так что запрос вернул максимальные 5 000 строк: их тексты занимают 11 075 638 символов. В MCP-результате осталось 30 символов. Это повторяемая лишняя работа на пути сервер → MCP: ещё один вызов того же воркера с `limit=5` занял 24,68 с; соседний `fix-dashboard` (2 506 строк, 13,09 млн символов) занял 33,05 с при `limit=4`. Данные в [mcp_outlier_samples.csv](evidence/mcp_outlier_samples.csv). Источник: `app/mcp_stdio.py:get_worker_logs` (строка 1842), `app/routes/sessions.py:get_session_logs` (732) и `app/db.py:get_logs` (1286).

**`merge_worker` тоже медленный в хвосте, но включает работу самого merge.** Вызов `fix-dashboard` шёл 82,38 с: операция создана через 42,84 с, `started_at`→`finished_at` заняло 38,33 с, ответ вернулся через 1,20 с после `finished_at`. Route делает session snapshot и admission до записи операции; runner затем исполняет Git, acceptance и финализацию. MCP-код намеренно ждёт терминального состояния до 90 с, либо до 60 с при фоне. Поэтому нельзя считать все 82 с чистой сетевой задержкой или экономить их отключением гейтов. Внутренних таймеров для snapshot/admission/acceptance в этом срезе нет. Код: `app/merge_operations.py:accept_merge_operation`, `app/routes/merge_operations.py:create_merge_operation`, `app/mcp_stdio.py:2398–2417`.

У `task_*` и `bg_*` медианы малы и общий объём намного ниже Bash и merge. Их данные не показывают общего торможения MCP server на типичных вызовах. `send_message` имеет редкий длинный хвост, но БД не содержит достаточной разбивки, чтобы приписать его доставке, quota wait, SQLite или HTTP.

Полная старая копия `urok-svyaz` создана до старта нового процесса; на момент проверки она занимала 4,9 GiB и `git sparse-checkout` для неё выключен. Это разные репозитории/деревья, поэтому размер не сравнивается напрямую с 33/62 MiB. Рестарт меняет путь для новых спавнов; старые копии автоматически sparse не стали. Выводы подтверждены [pre_restart_full_copy.txt](evidence/pre_restart_full_copy.txt) и [sparse_worktree_sample.txt](evidence/sparse_worktree_sample.txt).

По коду spawn проходит: HTTP `POST /api/sessions` → валидация/привязка задачи и ветки → `create_worktree` (в новой реализации `git worktree add --no-checkout`, sparse-checkout и project files) → skills/scaffold → сборка prompt → `session.start` → публикация готовой сессии. Первый ход/первый вызов модели начинается отдельно после доставки задания. Поля `sessions.created_at` возникают до завершения `prepare`, поэтому ими нельзя измерить окончание копии. В БД нет отдельных таймеров на git, sparse checkout, prompt, CLI startup и доставку; 5 послерестартовых вызовов слишком мало для вывода о стабильном p90.

В V-821 уже измерялся checkout Orchestra на том же диске: полный 324 MiB / 2,54 с, sparse с нужными KB и фикстурами около 62 MiB / 0,24 с (−2,30 с, −90,6%). Это прежний одиночный бенчмарк, а не A/B на текущем spawn. Та же работа измеряла katya-work 4 246→40 MiB и 48,0→1,39 с, seedon 1 305→99 MiB и 10,7→0,50 с. Источник: commit V-821 `4bd9c2e`, `.orchestra/tasks/V-821/report.md`, раздел «Правило cone и экономия».

## Ограничения

DB-журнал даёт итоговые `tool`/`tool_result` timestamps, но не CPU time и не внутренние этапы внешних инструментов. 883 непарных вызова — отсутствующий `tool_result` в снимке; это включает возможный незавершённый вызов и потерю/неполную запись, причины по одной паре определить нельзя. `get_worker_logs` и merge examples измерены по одной живой реализации и её логам; это диагноз конкретного пути, не контролируемый A/B. `dd` короткий и не описывает физический диск гипервизора.

Код и конфигурация `app/` не изменялись, тесты не запускались. Все выгрузки и скрипты извлечения находятся в [evidence/](evidence/).
