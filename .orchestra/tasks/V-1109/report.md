# V-1109: поиск по прошлому у оркестраторов Orchestra и у Кеши (только исследование)

Код и правила не менялись. Живая БД — `data/orchestra.db`, `mode=ro`, срез 27.10.2026 ~12:00 UTC. Личного содержимого переписки в отчёте нет.

## Коротко

1. **Идея у Кеши уже наша.** Её `search_memory` — не отдельная разработка, а результат замера Orchestra V-910/V-45 (17.10): гибрид эмбеддинги+FTS5 убрали, оставили текстовый поиск, потому что точность та же (0.83 против 0.87, внутри шума). Владелец тогда сказал «чтобы тоже так искал, как и мы». Поэтому «украсть идею» буквально нечего; красть можно три детали (regex, фильтр по роли, текст промпта-метода), и чинить нашу границу сканирования.
2. **У нас инструмент есть, но он слабее по охвату, чем кажется.** Сканируется только 10 000 самых новых строк `logs` (все типы, включая гигантские `tool_result`), а это для проекта Orchestra ≈ 3 суток, для katya-work ≈ 1 сутки. 27% реальных вызовов вернули `scan_truncated: true`.
3. **Пользуются слабо и неравномерно:** 3 оркестратора из 10 вызывали его, остальные ни разу за 14 дней; часть обходит инструмент прямым SQL к БД.
4. **Автоподмешивание не рекомендую:** на корпусе Кеши чистая выдача top-5 без цикла уточнений даёт 0.49, агент с повторными запросами — 0.83–0.87. Подмешивание — это как раз первый вариант.

## 1. Что есть у оркестраторов

**Инструменты** (MCP-сервер `app/mcp_stdio.py`):
- `search_logs(query, date_from, date_to, agent, all_projects, limit)` — `app/mcp_stdio.py:1958`; `limit` режется до 1..50 (`:1971`); по умолчанию ищет в проекте вызывающего (`scope=SCOPE`), `all_projects=true` — по всем проектам.
- `get_log_context(log_id, project, all_projects, before, after)` — `app/mcp_stdio.py:1986`; соседей до 10 в каждую сторону.
- Оба в `READ_ONLY_MCP_TOOLS` (`app/mcp_stdio.py:95-96`), доступны всем ролям, не только оркестраторам.
- HTTP-слой `app/routes/sessions.py:58` (запрос 1–200 символов, даты `YYYY-MM-DD`, `scope` xor `all_projects`) и `:90` (контекст, каждое сообщение режется до 4000 символов).

**Что и как ищется** (`app/db.py:1437` `search_logs`, `:1548` `get_log_context`):
- Хранилище — таблица `logs` в SQLite. Тип логов **не фильтруется**: ищется по всем `type` (user_message, text, tool, tool_result, thinking, status…). Голосовые расшифровки отдельного типа не имеют: это обычные `user_message` с пометкой `[voice: …]` (в БД с 20.10 таких 438); поиск по ним идёт как по любому тексту.
- Метод — **подстрока без учёта регистра** (`casefold().find(needle)`, `db.py:1494`), одна подстрока, без regex, без альтернатив, без морфологии, без FTS-индекса, **без ранжирования**: порядок строго «новые первыми» (`ORDER BY l.id DESC`).
- Границы: `LOG_SEARCH_SCAN_LIMIT = 10_000` строк на вызов (`db.py:1435`), затем остановка; ответ несёт `scanned`, `scan_truncated`, `result_limit_reached`. Фрагмент: 120 символов до и 180 после совпадения. Фильтры: `agent` (точное имя), даты (по UTC-дню `date(ts)`, использует индекс `idx_logs_day`). Фильтра по типу строки нет. В выдаче тип сведён к 4 ярлыкам: user message / agent message / assistant text / tool (под «tool» попадают также thinking, status, tool_result).
- Разделение по проектам: `s.scope = ?` (`db.py:1458`).

**Реальный охват 10 000 строк** (замер по БД): за последние 14 суток в `logs` ≈ 260 тыс. строк, из них tool+tool_result 65%, user_message+text всего 9%; `tool_result` весит 1,96 ГБ из ~2,0 ГБ текста. 10 000-я самая новая строка проекта Orchestra — 24.10 05:19 UTC (≈ 3 суток назад), katya-work — 26.10 05:02 (≈ 1 сутки), seedon — 24.10 00:56. Из 149 последних результатов `search_logs` в БД 40 (27%) помечены `scan_truncated: true`, 28 (19%) пусты. Если бы сканировались только `user_message`+`text`, 10 000 строк достигали бы 25.09 (Orchestra) и 05.10 (katya-work, seedon): ≈ 4–25× глубже, и каждая строка в сотни раз короче.

**Правило в промптах**: `.orchestra/pipelines/default/prompts/modules/knowledge.md:4-9`:
> «Before answering about a past event, conversation or decision, search the logs with `search_logs` in your own project first, then set `all_projects=true` if needed. Search voice-message transcripts too; do not rely only on Markdown files. Quote the relevant finding and include its date.» (строки 4–7) и «owner decision, 2026-10-21: Search past logs before answering from memory because conversations and voice transcripts are retained there.» (строка 9).

Это единственное место правила; в модуле нет метода («угадай слова оригинала»), нет подсказки, что искать надо в `user_message`, нет упоминания лимита 10 000 и флага `scan_truncated`.

**Автоматически или вручную.** Только вручную: ничто не подмешивает прошлые фрагменты в ход. Автоматически в оркестратор попадают лишь: системный промпт с индексом KB и модулями, файл памяти `.orchestra/workers/<имя>.md` (`app/prompting.py:167`, ограничен вручную), сводка при компакции (`[PREVIOUS CONTEXT SUMMARY…]`). Поиск по логам — решение модели.

Происхождение: 21.10 11:42 UTC владелец в чате seedon-orchestrator просил «записать, что в логах можно искать все прошлые сообщения»; первый вызов `search_logs` в БД — 21.10 13:27.

### Оценка автоподмешивания релевантных фрагментов

Как могло бы работать: перед ходом по тексту входящего сообщения запрос в `search_logs`, топ-3..5 фрагментов вставляются в контекст оркестратора.

- **Качество.** Единственный замер: у Кеши чистая выдача top-5 без агентного цикла находила нужную запись в 49% (top-10 — 66%), а агент, формулирующий запросы сам и уточняющий, — 83–87% по тем же данным. Автоподмешивание — это ровно «чистая выдача»: входящее сообщение владельца («сделай как вчера») не содержит слов оригинала. Для нашего корпуса не измерено; ожидать лучшего оснований нет. Подмешивание неверных 3–5 фрагментов на каждый ход хуже, чем ничего (ложные якоря).
- **Токены (оценка по длине, не замер).** Фрагмент ≤300 символов ≈ 100 токенов, 5 фрагментов ≈ 500–800 токенов на ход. Входящих ходов за 14 суток: ~1700–2100 у трёх активных оркестраторов → ~1–1,6 млн токенов записи в кеш на оркестратор за 14 суток (запись платная, чтение почти бесплатно — KB V-660). Если вставлять в начало контекста, ломается префикс-кеш; если в конец хода — остаётся в истории и копится. Плюс стоимость самого запроса: сейчас вызов сканирует до 10 тыс. строк с гигабайтами `tool_result`; на каждый ход это нагрузка на общую БД (6,3 ГБ), которую делит платформа.
- **Риски.** (а) Утечка между проектами/людьми: katya-work содержит личное; автопоиск по `all_projects` недопустим, даже по своему проекту подмешиваются сообщения 3-й стороны в контексте, не связанном с запросом. (б) Инъекция: в `logs` лежат результаты инструментов и тексты из веба; фрагмент в начале хода воспринимается как инструкция. (в) Ходы без нужды: 60+% входящих — фоновые задания и сообщения агентов, не вопросы о прошлом.
- **Если всё же нужно** — минимальный вариант вместо подмешивания текста: перед ходом только на сообщения владельца, содержащие маркеры прошлого («помнишь», «мы же», «как тогда», «вчера», «опять»), в промпт добавляется не фрагмент, а напоминание «проверь `search_logs`» (≈ 30 токенов). Это дешёвая страховка того же класса, что у Кеши («вызывай, когда пользователь ссылается на прошлое»), и её польза проверяема парным прогоном. Без замера не внедрять.

## Рекомендации (по убыванию важности; всё — предложение, реализации нет)

1. Фильтр по типу + тип по умолчанию user_message/text/agent в `search_logs` — убирает главный предел охвата. Без него правило «ищи в логах» на 27% вызовов отвечает по неполному окну.
2. Добавить в `knowledge.md` метод поиска (слова оригинала, сузить датой, читать контекст, обращать внимание на `scan_truncated`). Правка промпта — решение владельца.
3. Regex/альтернативы с ограничениями длины.
4. Проверить гипотезу «обход через прямой SQL»: сколько таких запросов были именно поиском прошлого, а не аналитикой (в этой работе не разделено).
5. Не делать автоподмешивание; при необходимости — только лёгкое напоминание по маркерам прошлого, после парного замера.

## Ограничения

- «Ходы» = строки `user_message` всех источников; доля «чистых» вопросов владельца ниже. У оркестраторов, начавших после 13.10, окно короче.
- Счёт обходов через SQL — по подстрокам команды, включает аналитику.
- Оценки токенов — расчёт по длине, не замер; эффект подмешивания на нашем корпусе не измерялся.
- Корпус и вывод V-45 — про Кешу (переписка в одном чате, Sonnet 5.5 вместо её Opus 5.5); перенос на журнал платформы с 65% `tool_result` не доказан.
