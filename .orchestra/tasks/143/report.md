# #143 — почему рвётся отдача с orchestra.seedon.ru: механизм

Продолжение #142. Вывод: **чинить на нашей стороне нечего.** Ни nginx, ни TLS,
ни домен, ни MTU. Теряются ретрансмиты на обратном пути VPS→клиент, внутри
российского сегмента. Это обращение к провайдеру, а не правка конфига.

## Две гипотезы, которые я проверил и ОТВЕРГ

Обе выглядели убедительно. Обе не подтвердились замером — записываю, чтобы
никто не пошёл по ним второй раз.

### 1. `ssl_buffer_size` = 16k (главная зацепка задания) — ОТВЕРГНУТА

В конфиге он действительно не задан, то есть работает дефолт 16 КБ, и обрыв
идёт ровно на 16384 байтах. Совпадение точное — но причина другая.

Опровержение прямое: **с самого VPS через тот же nginx и тот же TLS файл
скачивается целиком 5/5** (`curl -k https://127.0.0.1/ -H 'Host: ...'` → 372453
байт каждый раз). Если бы отдачу резал буфер nginx, резало бы и локально.
Не режет. 16384 — это объём, успевающий уехать в начальном окне ДО первого
потерянного пакета, а не граница буфера.

### 2. PMTU black hole — ОТВЕРГНУТА A/B-тестом

Дамп показывал дробление ретрансмитов 1448→1024→512→256, что выглядит как
классическая чёрная дыра PMTU. Проверил clamping MSS (с санкции оркестратора,
точечно на свой IP):

| конфигурация | залипло |
|---|---|
| без правила (база 1) | 7 из 8 |
| без правила (база 2, через 10 минут) | **2 из 8** |
| `--clamp-mss-to-pmtu` | 8 из 16 |
| `--set-mss 1200` | 8 из 16 |
| без правила (база 3) | 11 из 16 |

**Разброс БЕЗ всяких правок (7/8 → 2/8 → 11/16) перекрывает любую разницу
между армами.** MSS-клампинг не даёт ничего: при 1200 байтах на сегмент
залипания те же 8/16. Если бы дело было в размере пакета, форсирование 1200
вылечило бы. Не вылечило → гипотеза мертва.

Правило снято, `iptables -t mangle -S POSTROUTING` пуст, дампы с VPS удалены.

**Отдельный урок:** одиночное «до/после» на этой метрике даёт ложный результат
в любую сторону. Двусторонний тест (поставил → снял → повторил), которого
потребовал оркестратор, здесь и спас от неверного вывода.

## Что происходит на самом деле (наблюдение, tcpdump)

Залипший поток, последние пакеты. Клиент подтвердил `1759587113` и замолчал:

```
25.710338  seq 1759610281:1759613177  length 2896   ← сервер ушёл далеко вперёд
25.710404  seq 1759613177:1759614625  length 1448
25.935705  seq 1759621865:1759623313  length 1448
26.263706  seq 1759587113:1759588561  length 1448   ← РЕТРАНСМИТ старого сегмента
26.912697  seq 1759587113:1759588561  length 1448   ← он же
28.255710  seq 1759587113:1759588561  length 1448   ← он же
30.880989  seq 1759587113:1759588137  length 1024   ← ядро дробит
36.320344  seq 1759587113:1759587625  length  512
47.071804  seq 1759587113:1759587369  length  256
```

Читается так:
1. Сервер **не замолкает** — он отдал ~60 КБ и продолжает.
2. Один конкретный сегмент до клиента не дошёл.
3. **Каждый ретрансмит этого сегмента тоже не доходит** — при том, что более
   поздние пакеты долетали нормально.
4. Backoff 0.35→0.71→1.4→2.8→5.6→11.2 с. Клиент видит 16384 байта и висит.
5. Ни ICMP, ни RST в дампе нет — тишина.

Здоровый поток в том же дампе имел **10 ретрансмитов и всё равно завершился**
(408 КБ). То есть потери есть всегда, разница в том, проходит ли восстановление.

TCP-параметры сторон исправны: `mss 1460, sackOK, wscale 10` у клиента,
`wscale 7` у сервера, окно 71 КБ. Проблема не в согласовании.

По ICMP потерь нет — но теряются именно TCP-ретрансмиты крупных сегментов,
а ICMP-пробы мелкие и идут другим приоритетом. Стык — между hop 7 (Telia, DE)
и hop 8-11 (российский сегмент).

## Ответ на вопрос юзера «а без секьюр было бы быстрее?»

**Нет.** Замер, а не мнение:

| канал | шифрование | результат |
|---|---|---|
| SSH, порт 22 | есть | 369174 б, **3/3 целиком**, 2.3-3.2 с |
| HTTPS, порт 443 | есть | 372453 б, **залипает 8-11 из 16** |
| HTTPS без gzip | есть | залипает так же |

Шифрование одинаковое, результат противоположный → **дело не в TLS**.
Отключение HTTPS не помогло бы: дропается TCP-сегмент, содержимое ему безразлично.
Плюс панель управления агентами без шифрования публиковать нельзя.

Почему SSH цел, а HTTPS рвётся: SSH отдаёт мелкими блоками и не разгоняет
congestion window до полноразмерных бурстов, HTTPS-статика — наоборот.

> Client: 109.226.233.238 (Russia).

> Outbound TCP retransmissions from the server to this client are being dropped

## Границы вывода

- Проблема плавающая: за час частота менялась 7/8 → 2/8 → 11/16 без правок.
  Любой замер здесь нужно повторять, одиночный ничего не доказывает.
- Замеры сняты с ОДНОГО клиентского IP (`109.226.233.238`). Что будет с
  мобильного или другой сети — не проверено; замер оркестратора с VPN
  (3 из 6) намекает, что маршрут в РФ общий, но это не доказательство.
- `ssl_buffer_size` я не менял: гипотеза отпала до правки, трогать чужой
  работающий конфиг ради опровергнутой версии смысла не было.
- nginx не рестартовал, `proxy_buffering off` и SSE не тронуты —
  соседний `dnd-game-master` в безопасности.
