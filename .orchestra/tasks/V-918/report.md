# V-918: большой замер модельного ревью на тихих дефектах

Класс B, офлайн; боевой код и промпты не менялись. Предрегистрация (`prereg.md`, коммит до первого прогона рецензента) → отбор → 92 прогона → разметка → анализ (`analyze.py`, вывод `stats.txt`).

По правилу из `prereg.md` вердикт — **«помогает на тихих дефектах»**: recall 39% (нижняя граница 22%) и точность на чистых 65%. Но это формальный вердикт; ниже то, что его ослабляет. «Уверен на 100%» недостижимо ни при каком n: интервал 22–59% — честная форма ответа.

## Что именно найдено (сэмпл-проверка попаданий)

Я прочитал 5 попаданий: все настоящие совпадения механизма, не «тот же файл». Примеры: самоссылка кавычек `'${CUR}'` в `showTaskDetail`; жёсткое усечение строк в `diff_image.py`; `Math.min(days,7)` в аналитике по агентам; дубль маршрута `PATCH tg-topic` с `to_dict()` без `cwd/session_id` → KeyError/500; рассинхрон `parent_tool_use_id` и `task_id` у карточки субагента. То есть рецензент ловит локальные видимые из диффа механические ошибки; 14 из 23 не найдены ни в одном повторе (причины по существу не разбирал — это не проверено, список в `analyze`-выводе `stats.txt` и `match_*.json`).

## Как построено (и что от этого зависит)

- **Выборка.** `mine.py`: 480 «fix»-коммитов первой линии main, `git blame -w` строк, удалённых/изменённых фиксом, → коммит-источник (347 с источниками); с 2026-06-01, фикс ≥1 дня позже, ≥2 строк, размер 20–1500 строк кода без `.orchestra` и `*.md` → 67 кандидатов. Два независимых оценщика (Sonnet 5.5, Luna) по пакету «дифф источника + патчи фиксов»: оба «да» — 23, оба «нет» — 23, расхождение/unclear — 21 (согласие 46/67 = 69%). Плохие = 23 «оба да».
- **Чистые.** 23 коммита, не названные источником ни одного фикса, не сами фиксы, 2026-06-01..10-02 (≥14 дней экспозиции), подобраны по размеру (медианы 87 и 86 строк; в V-909 чистые были несоразмерно больше).
- **Рецензент.** Как V-909: Luna, замороженный промпт `codex_review`, калибровка = тема коммита, снимок без истории, `danger-full-access`. 2 независимых повтора на дифф, 92 прогона, rc=0 у всех, правок в снимках нет, вердикты 48 APPROVED / 43 NEEDS WORK / 1 INCOMPLETE. Медиана платных токенов 22 тыс. на плохих и 25 тыс. на чистых, ~19 с на прогон. Повторы согласны по «есть замечания/нет» в 42 из 46 диффов.
- **Разметка.** Два слепых разметчика (Sonnet 5.5, Luna), перемешанные анонимные элементы, оба видят дифф с контекстом и первые 8 последующих коммитов на те же файлы; согласие по «есть реальное замечание» 81/92. Отдельный шаг B (только плохие): описание дефекта + ревью → «попал ли». Попадание = оба «да».

## Ограничения, меняющие смысл вердикта

1. **Плохие определены задним числом.** Оценщики видели последующий фикс; «плохой» = фиксом признан дефект. Часть таких «дефектов» — разумная неопределённость дизайна. Это завышает пул «плохих» (нижняя граница recall по смыслу сильнее, чем по таблице) и не завышает recall искусственно; но выборка — не «тихие дефекты вообще», а те, что мы сами потом заметили и починили. Дефекты, которые никто не заметил, недоступны ни одному замеру.
2. **Чистые не доказанно чистые.** «Нет фикса на эти строки» ≠ нет дефектов; 57% чистых диффов получили реальное замечание — вероятно, часть из них настоящие дефекты, которые просто не починены. Поэтому разница плохие/чистые мала и не значима (p=0,21): рецензент находит реальные вещи и там, и там, а специфичности именно к «позже починенным» замер не показал.
3. **Разметчики щедрее, чем в V-909** (65% против 46% реальных на чистых): здесь они видели последующую историю inline, один и тот же класс моделей, что и рецензент (Luna размечал Luna). Доля «реальных» — верхняя оценка; по подтверждённым последующей правкой она была бы ниже (в V-909 21%). Не измерял отдельно.
4. **Рецензент без тестов и без исправлений автора**: 3 раунда с правкой и запуск тестов — не измерены. Вклад ревью в итоговый результат (исправил бы автор — да/нет) тоже не измерен: замер говорит «находит», не «ревью улучшило merged-код».
5. Первичный проход оценщиков через `dynamic_workflow` оказался недействительным: задачи workflow идут в частичном (sparse) worktree `wf-…` на закреплённом коммите, а свой каталог `.orchestra/tasks/<id>/` попадает в копию только по номеру из имени ветки `task-<id>/` (`app/sparse_worktree.py`, `task_id_from_branch`); у ветки workflow имя `feat/<scope>/wf-V-918-…`, номер не извлекается, поэтому пакеты не читались (повтор с закоммиченными пакетами дал то же; незакоммиченные не попали бы в любом случае). Часть моделей при этом отвечала правдоподобно, не прочитав файл. Каталог `data/workflow-runs/<run>/workspaces/*/attempt-1` — только метаданные, пустым рабочим каталогом он не является. Причина установлена по коду, отдельным прогоном не перепроверялась. Вердикты отброшены, оценка повторена с пакетом inline через локальные CLI (`llm.py`, `vet.py`). Для будущих замеров: содержимое — в тексте промпта.

## Что это значит для решения

Recall на тихих дефектах, видимых из диффа, — примерно каждый третий-второй (22–59%), цена ~22 тыс. платных токенов и ~20 с на дифф, шум на чистых высокий (до 2 из 3 замечаний реальны по щедрой разметке). Заранее записанное правило выполнено, поэтому **возвращать модельное ревью обсуждать разрешено; данные в пользу «узкого ревью для тихих ошибок» есть, но без доказанной специфичности и без замера эффекта на итог.** Следующий шаг, если владелец хочет большей уверенности: замер эффекта (автор исправляет по замечаниям, считаем сколько позднее-починенных дефектов не доехало до main) или расширение выборки — при n=23 разница плохие/чистые 78% против 57% потребовала бы порядка 60+ диффов на группу, чтобы быть значимой (грубая оценка, не считал точно).
