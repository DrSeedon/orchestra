## 1. Как это устроено на самом деле (минимальный контур)

Точка входа в Claude Code — плагин `loopx/claude_goal_mode/`, **всего 1492 строки** (`git ls-files

с нами; остальные 335K — их собственная предметка (квоты, бенчмарки, Lark, issue-fix).

Контур:

1. **Реестр** `.loopx/registry.json` — единственный источник истины про цель.
   Резолвится ходьбой вверх от cwd (`hooks/goal_state.py:29-40 find_registry`).
2. **«Взведено»** = в проекте есть `.claude/loop.md` (`goal_state.py:132-137 is_armed`).
   В нём маркер `<!-- loopx:armed {"goal_id":…,"agent_id":…} -->` (`scripts/goalmode_cmd.py:65`).
3. **Протокол одного тика** — текст в `.claude/loop.md`, который исполняет нативный `/loop`
   Claude Code (`scripts/goalmode_cmd.py:56-77`), дословно:
   ```
   1. Call `should_run()`. If should_run=false, say why in ONE line and STOP this iteration
   2. If should_run=true: `claim_task` the next open todo, do ONE bounded segment,
      then VERIFY it with a real check (build/test) — never claim success from
   ```

4. **MCP-тулы** `should_run / list_todos / claim_task / complete_task`

**Дефект, найденный по дороге** (свидетельство того, что края написаны машиной и не вычитаны):
`mcp/loopx_mcp.py:129-133` — тул `list_todos()` объявлен как «список открытых todo», а телом

## 2. Подозрение №1 — «границы полномочий как ДАННЫЕ». Ответ: ДА, но не там, где кажется

### 2.1 Принуждение у них есть, и это хук

`loopx/claude_goal_mode/hooks/goal_policy.py` (212 строк) — `PreToolUse` с `matcher: "*"`
(`scripts/install.py:61`). Решения (`goal_policy.py:152-212`):

| Класс вызова | Решение | Строка |
|---|---|---|
| `Read/Glob/Grep/NotebookRead/TodoWrite/WebFetch/WebSearch/ToolSearch` | `allow` всегда | `goal_policy.py:66`, `:183` |
| `should_run == false` | `deny` «quota/gate closed» | `:187` |
| зонд `should_run` недоступен | `deny` — **fail-CLOSED** | `:190` |
| `Edit/Write/MultiEdit/NotebookEdit` вне `write_scope` | `deny` | `:196-198` |
| `Bash` из денилиста `DESTRUCTIVE` | `deny` | `:203-205` |
| прочее (в т.ч. `Task`) | `{}` — обычный поток разрешений | `:206` |

Три места, где их инженерия совпала с нашими замерами, независимо:

- **Fail-closed при недоступном зонде** (`:189-190`) — против нашего fail-OPEN
  (`app/backend_claude.py:403-411`: три ветки `failed open` — таймаут классификатора,
  невалидный результат, любое исключение).
- **`Task` намеренно НЕ в списке read-only** — комментарий `goal_policy.py:62-65`: «It can
  launch a subagent that performs writes, so allowing it unconditionally would bypass the
  gate». Это ровно наш запрет встроенного `Agent` через `disallowed_tools`
  (`app/backend_claude.py:61`, комментарий «subagent launches arrive…»).
- **Bash признан дырой ими самими**, дословно `goal_policy.py:33-36`: «Limitation (by design):
  Bash is gated only by a denylist, so a determined shell command can still write outside
  write_scope or reach the network. For STRONG isolation … run Claude Code inside a dev
  container or VM». Это наш #228 (recall 39%) с той же рекомендацией и без наших цифр.

### 2.2 Разворот: у них принуждается НЕ та модель данных, которая у них есть

Богатая модель полномочий у них существует: `write_scopes` — список, нормализуется, запрещает

**И она принуждается — на ДОПУСКЕ задачи.** `control_plane/quota/task_orchestration_admission.py`:

```python

    reasons.append("write_scope_missing")          # :339-342
```

Задача, объявившая scope вне границ цели (или не объявившая его при пишущем `action_kind`),
не попадает в исполняемые дорожки: `build_adaptive_task_orchestration_contract` делит их на
blocked и eligible, и наружу идут только eligible.

**Но на записи файла её по-прежнему нет.** Хук видит другой, огрублённый scope —
`goal_state.py:118`:

```python

```

— то есть в момент `Edit/Write` сравнивается **один каталог, корень репозитория цели**.
Проверка: `grep -rn "write_scopes" loopx/ | grep -i "file_path|deny|permissionDecision|Edit"`
даёт **ноль** совпадений в проде. То есть тонкая модель работает на допуске, а на инструменте —
грубая.

**Вывод по подозрению №1, в обе стороны честно:**

- **На допуске у нас гейты аналогичные, но не одинаковые — и инвариант каждый держит свой.**
  Обе проверки отказывают ДО начала работы и обе судят по ОБЪЯВЛЕННОМУ, а не по сделанному.
  Дальше они расходятся: у них `write_scope_not_allowed` требует, чтобы объявленные scope
  задачи **лежали внутри границы цели** (вертикальное вложение); у нас `dirs_overlap`
  (`app/manager.py:585-607`) требует, чтобы каталоги двух живых воркеров **не пересекались**
  (горизонтальная развязка). Их проверка ничего не говорит о двух задачах на один каталог, наша
  — о выходе за периметр проекта. Считать их взаимозаменяемыми нельзя.
- **На инструменте у них есть точка, которой у нас нет вовсе**: `deny` на `Edit/Write` вне
  каталога (`goal_policy.py:196-198`). У нас на этом месте абзац в промпте
  (`app/manager.py:477-480`).
- **Модель данных, доехавшая до инструмента, у них беднее нашей**: один каталог против нашего
  списка `owned_dirs`.
- Значит брать надо **место, а не модель**. Наши данные + их точка.

## 3. Подозрение №2 — «хранилище подтверждений отдельно от отчёта». Ответ: ТРИ РАЗНЫХ УРОВНЯ

Это самая содержательная часть. У них не один механизм «evidence», а три, и они разного
качества. Смешивать их — и есть способ прочитать анонс неправильно.

### Уровень 1 — свободный текст (то, что видит агент в Claude Code). НЕ проверка

`complete_task(todo_id, agent_id, evidence: str, …)` (`mcp/loopx_mcp.py:139`) кладёт строку
в `--evidence`, справка CLI дословно: «Public-safe evidence pointer or short result for
complete/update» (`cli_commands/todo.py:113`). В `loopx/todos.py:781-782` она просто
записывается: `updates["evidence"] = evidence`. Валидируется только **публичная безопасность**
(нет секретов) и **непустота** на некоторых переходах
(`cli_commands/todo_argument_validation.py:207,322,350`).

То есть на этом уровне «подтверждение» = обязательное непустое поле в момент перехода
состояния. Содержимое не проверяет никто. Требование «VERIFY it with a real check (build/test)
— never claim success from reasoning» живёт в `.claude/loop.md`, то есть **в промпте**
(`scripts/goalmode_cmd.py:72-73`).

**Наш #174/#210 («Codex approved» при вердикте «Blocking findings remain») этот уровень бы не
поймал.** Он поймал бы только пустое поле.

Но одно отличие от нас всё же есть и оно не нулевое: **у нас нет даже обязательного поля.**
Доказательства живут внутри `report.md`, который пишет тот же, кто отчитывается, и переход
«задача закрыта» ничего не требует структурно.

### Уровень 2 — факт, который контрольная плоскость ПЕРЕВЫВОДИТ САМА. Настоящая проверка

`loopx/capabilities/issue_fix/repository_commit_evidence.py:85 verify_issue_fix_repository_commit_evidence`:

- проверяет, что каталог — рабочее дерево (`git rev-parse --is-inside-work-tree`, `:118`);
- что заявленный `owner/name` совпадает с реальным GitHub-remote чекаута (`:123-127`);
- резолвит три ссылки в oid своим `git rev-parse --verify <ref>^{commit}` (`:130-132`);
- требует `recovery_ref == repository_revision` (`:133-136`);
- требует `git merge-base --is-ancestor commit_oid revision_oid` (`:137-141`);
- берёт корневые коммиты (`rev-list --max-parents=0`) и печатает `sha256` отпечаток
  репозитория (`:143-170`);
- возвращает `status: "verified"` и явные `repo_path_captured/remote_urls_captured/
  raw_git_output_captured: False` — то есть доказательство **клон-стабильно и не тащит
  локальные пути** (`:181-184`).

Ключевое — **кто это вызывает**. Единственный вызывающий:
`loopx/capabilities/issue_fix/cli.py:1531`, внутри пути записи. Агент подаёт `--repo-path`,
`--repository-ref`, `--repo` и `commit_ref`; блоб доказательства **собирает контрольная
плоскость**. Проверка на подделку: `grep` по `add_argument|json.loads` для
`repository.commit.evidence` в `cli_commands/` и `capabilities/issue_fix/cli.py` — **ноль
совпадений**, то есть готовый блоб снаружи не принимается. Приёмка на другом конце
(`capabilities/issue_fix/outcome_projection.py:141-158`) отказывает, если `status != "verified"`,
если отпечаток не `sha256:`, если поля не похожи на oid, если `recovery_ref_oid !=
repository_revision`, если `commit_is_ancestor` ложно.

**Оговорка, без которой это нельзя копировать:** их `merge-base --is-ancestor` работает,
потому что у них коммит доставки реально предок закреплённой ревизии. У нас мержи squash, и
в `CLAUDE.md` уже записано, что `--is-ancestor` по SHA воркера отвечает «нет» ВСЕГДА. Копировать
надо приём (перевывести факт самому), а не команду.

### Уровень 3 — команда проверки, которую исполняет контрольная плоскость. Самое сильное

`loopx/control_plane/turn_driver/executor.py:483 build_loopx_turn_command_validator`:

```python
completed = subprocess.run(
    normalized, cwd=project,
    input=json.dumps(result, …),        # результат хода агента подаётся на stdin
    stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL,
    timeout=max(1.0, timeout_seconds), check=False)
```

- argv фиксирует оператор при старте хода: `--validation-command-json`,
  `--validation-timeout-seconds`, `--validation-failure-kind` (`cli_commands/turn.py:118-131`,
  разбор на `:415-428`);
- ненулевой код возврата → `{"status": "failed", "recovery_kind": repair_required |
  replan_required}` (`executor.py:526-533`);
- недоступность/таймаут → `{"status": "inconclusive", "recovery_kind": "repair_required"}`
  (`executor.py:518-524`) — то есть **не «прошло»**;
- эти `result_kind` дальше не дают ходу осесть как выполненному: `cli_commands/turn.py:447-461`
  на `repair_required|replan_required` требует один выбранный todo и пишет типизированный
  writeback вместо завершения;
- журнал хода — `executor.py:541 turn_journal_path`, имя файла = sha256 (`turn_key`), запись
  атомарная через `mkstemp` + переименование (`executor.py:549+`).

Докстринг называет это «trusted argv-only postcondition validator» — и это честное имя:
**команду выбирает не агент, запускает не агент, и её код возврата управляет переходом
состояния.**

**Наш аналог и чем он хуже.** Замороженный красный оракул (#210, #223) — та же идея: команда
задаётся вне исполнителя, исполнителю запрещено её трогать. Разница в исполнителе проверки:
у нас команду запускает сам воркер и **присылает вывод текстом**, а перепрогон делает
оркестратор руками по правилу роли («A child's green report is evidence, not acceptance…
rerun the exact command yourself»). То есть у нас это дисциплина, у них — код. Наш #219
измерил цену этой дисциплины: одно пробуждение родителя $0.87.

## 4. Подозрение №3 — «задача длиной в сутки с паузами и сменой модели»

### 4.1 Заявка в анонсе — честная, и README сам это говорит

`README.md:165-167` отдельно помечает четырёхсуточный прогон как **сообщение независимого

## 7. Что стоит взять — и цена

### Берём №1 — принуждать `owned_dirs` в момент записи (их `goal_policy.py:196-198`)

**Что именно.** Второй `HookMatcher` в уже существующем `PreToolUse` рядом с Bash-классификатором
(`app/backend_claude.py:415`): на `Edit|Write|MultiEdit|NotebookEdit` резолвить `file_path` и
сравнивать с `owned_dirs` сессии; вне — `permissionDecision: "deny"`. Данные брать те, что уже
лежат (`app/manager.py:585-607`), а не их одну-папку модель (§2.2).

**Цена — выше, чем выглядит, и вот из чего она складывается.** Первая оценка «~50–70 строк в
`backend_claude.py`» была занижена: **бэкенд сегодня физически не знает `owned_dirs`.** Они
живут на `AgentSession` (`app/session.py:353`), а `ClaudeBackend.__init__`
(`app/backend_claude.py:471`) их не принимает; собирается бэкенд в
`app/runtime_registry.py:178`, и фабрика хуков получает только классификатор Bash
(`app/backend_claude.py:604`). То есть работа — это проводка `session → runtime_registry →
ClaudeBackend`, а не один матчер. Плюс обязательные детали, без которых получится вред:

- разрешения `docs/tasks/<id>/` и `docs/workers/<имя>.md` обязаны быть **привязаны к текущей
  сессии** (иначе каждый воркер получит право писать в чужой отчёт и в чужую личную память —
  ровно наоборот к цели правки);
- нормализация пути: абсолютный/относительный, `..`, симлинки, корень worktree против корня
  репозитория;
- не гейтить, когда `owned_dirs` пуст (у нас владение необязательно), и писать решение в лог
  с причиной.

Честная оценка после этого: **~120–160 строк по трём файлам + тесты**, доезжает реконнектом
бэкенда/рестартом. Ревьюер прав, что без этой проводки получился бы хук, не знающий
авторитетного scope, — то есть проверка, которая всегда разрешает.

**Что это НЕ закрывает, дословно по их же признанию** (`goal_policy.py:33-36`): Bash обходит
запись мимо гейта. Наш #228 это уже померил: recall денилиста 39%, 45.2% исторических команд
многострочные. То есть берём мы **защиту от случайного выхода за периметр, а не от
намеренного**.

**Почему всё равно стоит.** Замер наш: 11.08.2026 четверо воркеров за один день уперлись в
границу владения (#175, #176, #177, #186), трое молча потеряли урок. Сегодня единственное, что
стоит между воркером и чужим каталогом, — абзац в промпте, а про промпты у нас три замера
подряд, что они не принуждаются.

### Берём №2 — приёмочную команду тикета исполняет платформа, а не исполнитель

**Что именно.** Их `build_loopx_turn_command_validator` (`executor.py:483-537`) + порядок
стадий (`transaction.py:353-360`). У нас команда тикета уже есть в плане, и правило роли уже
велит оркестратору перепрогнать её самому. Перенести это из дисциплины в код: команду
регистрируем при делегировании, платформа гоняет её в worktree ребёнка на его финальном DONE,
код возврата подшивает к отчёту, который видит оркестратор.

**Что именно гарантируется — уже, чем хочется.** Прогон на финальном DONE ребёнка доказывает
**зелень в worktree ребёнка до squash-мержа**, и только это. Он НЕ доказывает, что содержимое
доехало в `main`, пережило разрешение конфликтов и зелено в интегрированном состоянии. Это
отдельная точка приёмки после мержа, и её надо либо назначать явно, либо честно не обещать.
Формулировка гарантии в тикете обязана звучать как «валидированный worktree ребёнка».

**Цена.** ~150–250 строк + тесты; трогает shared runtime (конец хода, доставка сообщений) →
Codex-ревью обязательно, отдельный тикет, рестарт. Решения, которые придётся принять: таймаут;
что делать при `inconclusive` (у них — `repair_required`, то есть НЕ «прошло»; это правильная
сторона отказа); и **не копировать их `stdout=DEVNULL, stderr=DEVNULL`** (`executor.py:511-512`)
— у нас на выходе должен остаться не только код возврата, но и хвост вывода, иначе оркестратор
получит «красное» без единой строки диагностики.

**Почему стоит.** Наш #174: в отчёт ушло «Codex approved», а артефакт начинался словами «Unable
to perform an evidence-backed review»; по артефактам потом насчитали 17 файлов ревью из 183
(9.3%) без вердикта вовсе. #210: `report.md` честно писал «2 blocking», в DONE ушло «Codex
approved». Класс один: между «команда прошла» и «мне сказали, что прошла» стоит только
добросовестность.

**Экономии пробуждений я НЕ обещаю, и это поправка после ревью.** В первой редакции я приписал
сюда $0.87 из #219 — это цена одного пробуждения родителя вообще, а не доказательство, что
именно это пробуждение исчезнет. Оно исчезает только в ветке «команда зелёная и больше ничего
решать не надо»; красный или `inconclusive` всё равно требует агента. Сколько ходов оркестратора
уходит СЕЙЧАС именно на перепрогон и ничего кроме — не измерено. Обосновывать эту правку надо
корректностью, а не деньгами.

### НЕ берём — и почему (чтобы следующий не переписал заново)

- Цена обеих рекомендаций — оценка по прочитанному коду, не по прототипу. Рекомендация 2
  трогает shared runtime, и там оценка наименее надёжна.

**Довод против самой затеи, который стоит держать в голове.** LoopX решает задачу, которой у
нас нет: у них агент работает в чужом рантайме, куда они не имеют доступа, поэтому им пришлось
строить контроль снаружи — через хук, CLI и файлы. У нас рантайм свой, и то же самое
принуждение ставится дешевле и надёжнее внутри платформы. Поэтому копировать их АРХИТЕКТУРУ
(внешний слой рядом с агентом) было бы шагом назад; копировать стоит только две точки, где они
поставили проверку туда, где у нас стоит обещание.
