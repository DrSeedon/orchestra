# #368 — Откуда брать число запросов OpenRouter (1000/сутки, 20/мин)

Дата: 2026-08-22. Живые пробы: inference-ключ (`OPENROUTER_API_KEY`) 06:40–06:45 UTC, management-ключ (`OPENROUTER_MANAGEMENT_KEY` из основного чекаута .env, в лог не печатается) 06:55 UTC. Дополнено после выдачи юзером management key.

## Question

Context: Orchestra дергает бесплатные OpenRouter-модели через собственный harness (`app/harness/llm.py` → POST /chat/completions). Change under test: где взять число израсходованных запросов для счётчика рядом с полосами Claude/Codex/Spark. Baseline: сейчас числа нет нигде. Outcome: источник числа с известными границами вранья + явное решение по лимиту 20/мин.

## Hypotheses considered

- H1: «Число запросов можно получить от провайдера существующим ключом» — ОПРОВЕРГНУТА (F3, F4: ключ не даёт, нужен management).
- H2: «Заголовки ответа содержат состояние квоты» — ОПРОВЕРНУТА для успехов (F2), ПОДТВЕРЖДЕНА частично для платформенных 429 (F5).
- H3: «Локальный счёт HTTP-вызовов — единственный доступный сейчас путь» — ПОДТВЕРЖДЕНА как единственный БЕЗ действий юзера; с management key появляется точный провайдерский путь.
- H4 (конкурирующая): «20/мин и 1000/сутки — глобальные на аккаунт» — UNCERTAIN: доки не называют scope, мой burst-эксперимент это скорее подрывает (F7).

## Findings

### F1. Параметры лимитов подтверждены первичным источником — CONFIRMED
Официальные доки (fetch сегодня, `/docs/api_reference/limits.md`): для моделей с суффиксом `:free` — 20 запросов/мин всегда; в сутки 50 при lifetime-покупках <$10 и **1000 при ≥$10** (константы `FREE_MODEL_RATE_LIMIT_RPM=20`, `FREE_MODEL_HAS_CREDITS_RPD=1000`, `FREE_MODEL_CREDITS_THRESHOLD=10`). Наш аккаунт: куплено $77 (задача), живой `GET /api/v1/key` вернул `is_free_tier: false` → мы в тире 1000/сутки. Evidence tier: 2 (первичный источник) + живая проба.

### F2. Успешные ответы НЕ содержат X-RateLimit-* — CONFIRMED
Доки дословно: «Successful inference responses do not include X-RateLimit-* headers». Мои пробы: все 200-е ответы (chat/completions обеих моделей, GET /api/v1/key) не имели ни одного rate-limit заголовка. Совпадает с живым дампом из задачи. Tier: 2+1.

### F3. GET /api/v1/key не даёт число запросов — CONFIRMED (живой вызов сегодня)
Полный ответ: только денежные поля (`usage`, `usage_daily`=0 — деньги, бесплатные модели стоят $0), `limit_remaining`=null, `rate_limit: {requests: -1, note: "This field is deprecated and safe to ignore"}`. Числа запросов нет вообще. Упомянутый в доках совет «monitor remaining quota via GET /api/v1/key» относится к КРЕДИТНОЙ квоте, не к счётчику запросов.

### F4. Точный провайдерский путь существует — Analytics API, но нужен management key — CONFIRMED (спека)
`POST https://openrouter.ai/api/v1/analytics/query`, метрика **`request_count`**, размерность **`date__day`** → ровно нужное число по UTC-суткам ([openapi-спека](https://openrouter.ai/docs/api/api-reference/analytics/query-analytics-data), пример ответа `{date__day: '2025-01-01...', request_count: 1500}`). Требует management key: обычный inference key получает 403 (совпадает с пробой из задачи на /activity); management key не может делать inference-вызовы, только админ-чтение. Создаётся юзером вручную: https://openrouter.ai/settings/management-keys. **С появлением ключа актуальнее эндпойнт F8 — /activity проще и уже проверен живьём; analytics/query остаётся запасным (агрегации/группировки, которых у /activity нет).**

### F8. Management key открыт /activity: построчные запросы по (дата, модель, провайдер) — CONFIRMED (живой вызов 06:55 UTC)
`GET https://openrouter.ai/api/v1/activity` с management key → 200, `{"data": [...]}`, 203 строки за окно. Поля строки: `date` ("2026-08-21 00:00:00"), `model_permaslug`, `model`, `provider_name`, `endpoint_id`, **`requests`**, `prompt_tokens`, `completion_tokens`, `reasoning_tokens`, `usage` (деньги), `byok_usage_inference`, `byok_requests`. Сумма `requests` за день = расход ВСЕГО аккаунта — включая вызовы с других машин юзера, которых локальный счёт не видит.

### F9. /activity отдаёт только ЗАВЕРШЁННЫЕ сутки — CONFIRMED (живой вызов)
Сегодняшней даты (2026-08-22) в выдаче НЕТ; максимум — 2026-08-21. `GET /activity?date=2026-08-22` → 400 `"Date must be within the last 30 (completed) UTC days"`. Следствие: management key в одиночку НЕ решает исходную задачу «не упереться внезапно» — он даёт историю и чужой расход, но не текущие сутки. Окно — 30 завершённых UTC-дней.

### F5. На платформенном 429 заголовки ЕСТЬ — LIKELY (первичный источник, живьём не воспроизведён)
Доки: когда сам OpenRouter режет по платформенному лимиту, ответ несёт `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (+`Retry-After`, если провайдеры дали хинт). Какое окно описывает Remaining (минута или сутки) — в доках НЕ сказано; воспроизвести намеренно не удалось (F6/F7). Это опоздавший сигнал: виден только ПОСЛЕ упора, для превентивного счётчика не годится, но годится для само-коррекции локального счёта.

### F6. Измерено: бесплатная модель часто отвечает UPSTREAM-429 без всякой квоты — MEASURED
Burst 26 запросов к `z-ai/glm-5.2:free` (06:43 UTC): первый же — 429 `"Provider returned error" ... "temporarily rate-limited upstream"` с единственным заголовком `Retry-After: 5`, без X-RateLimit-*. Это ОТЛИЧНЫЙ от платформенного тип 429: перегруз у вышестоящего провайдера, состояния нашего счётчика он не раскрывает. Клиент в llm.py уже ретраит такие (429 → _RetryableStatus). Следствие для дизайна: нельзя считать каждый 429 признаком исчерпания суточной квоты.

### F7. Scope лимитов (аккаунт vs модель) — UNCERTAIN
Доки дают таблицу лимитов для «a free model variant», scope не называют; Tip говорит «different rate limits for different models». Мой эксперимент: ~30+ запросов за минуту суммарно (в основном с upstream-429) — затем `nvidia/nemotron-3-ultra...:free` и `stealth/ox-alpha` ответили 200 без платформенного 429. Если бы 20/мин было жёстко на аккаунт и считало каждый вызов, платформенный 429 ожидался бы. Возможные объяснения (различить не смог): upstream-429 не доходят до счётчика платформы; счёт помодельный; окно скользящее и я не попал. Влияет на интерпретацию 20/мин в UI.

## Два пути и гибрид — чем каждый врёт

### Путь А: локальный счёт на нашей стороне
Считать каждый HTTP-вызов POST /chat/completions из `OpenRouterClient.stream()` (app/harness/llm.py:217). Что это значит:
- **Единица — HTTP-вызов, не ход агента.** Harness-цикл делает один вызов на tool-раунд, потолок `MAX_TOOL_ROUNDS=50` (app/harness/loop.py:35), плюс ревьюер-сублуп `REVIEW_MAX_ROUNDS=15` (loop.py) → ОДИН ход воркера может сжечь десятки запросов. Считать «ходы» = занизить на порядок.
- **Ретраи** внутри `stream()` — отдельные HTTP-попытки; каждая 429/5xx-повторка тоже стучалась в дверь. Считать попытку = завысить (отклонённый запрос мог не попасть в счётчик провайдера — неизвестно, gap), не считать = занизить. Рекомендация: считать ВСЕ исходящие попытки — консервативнее, внезапный упор хуже лишнего пессимизма.
- Чем врёт: (1) тот же ключ с другой машины/приложения → занижение; (2) рестарт процесса без персистентности → потеря окна; лечение — SQLite (счётчик по UTC-дню); (3) upstream-429 размывают семантику «что такое потраченный запрос»; (4) сброс окна — 00:00 UTC.
- Не требует ничего от юзера. Единственный источник ТЕКУЩИХ суток в реальном времени (F9).

### Путь Б: management key → /activity (ключ уже выдан юзером)
`GET /api/v1/activity` (F8) — провайдерская правда по завершённым суткам, по всему аккаунту. Чем врёт: (1) **сегодня не показывает** (F9) — в одиночку задачу «не упереться внезапно» не решает; (2) лаг ровно сутки; (3) это креденшел уровня аккаунта — хранить в .env основного чек аута (уже там), маскировать как секрет (secret_mask.py), никогда не логировать и не отдавать в API-ответы.

### Решение: гибрид А+Б
1. **Локальный счётчик (А)** — текущие сутки в реальном времени: инкремент в llm.py, SQLite-персистентность по UTC-дню, показ в полосе (сутки + минутное окно).
2. **Сверка (Б)** — периодический (TTL-кеш, раз в час достаточно) запрос вчерашнего дня из /activity: (а) вчерашний провайдерский счёт vs вчерашний локальный = **измеренное занижение** локального счёта, а не предположение; (б) разница = чужой расход с других машин — показывать отдельно, чтобы «полоса ползёт, а мы не работали» не выглядела багом.
3. В API-ответе каждое число помечено источником (`local` / `provider`), фронт показывает пометку — при расхождении видно, чему верить.

**Калибровка масштаба (из /activity, подтверждено моим вызовом):** пик 2026-08-08 = **662** запроса/сутки (66% лимита), 2026-08-21 = **92** (из них 7 `stealth/ox-alpha`). 1000/сутки — не теоретический потолок: юзер уже подходил к двум третям. Минутный лимит 20 при tool-раундах (до ~50 HTTP-вызовов/ход) бьёт раньше суточного — показать оба.

## Решение по 20/мин (явное, как требовала задача)

ПОКАЗАТЬ. Основание: единица расхода — tool-раунд, а не ход; три параллельных воркера с активным инструментенным циклом легко делают >20 вызовов/мин и упираются в минутное окно ЗАДАННОГО раньше суточного, а минутная стена посреди мержа выглядит как «внезапно сломалось». Форма: вторая мини-полоса/число рядом с суточной, с быстрым сбросом (окно ≤60 с). При F7 (возможно помодельный счёт) полоса может оказаться пессимистичной — это приемлемо, отметить в тултипе.

## Risks / edge cases

- Рестарт бэкенда между инкрементом и сохранением — теряем доли секунды счёта; приемлемо для глаз.
- Параллельные запросы из нескольких asyncio-задач одного процесса — один event loop, достаточно обычного счётчика + периодический flush в SQLite.
- Management key = креденшел уровня аккаунта: читать только из .env, маскировать (secret_mask.py), не логировать, не отдавать наружу; в worktree его нет — тесты не должны требовать ключ (путь Б деградирует до «нет данных», как у Grok-ветки).
- Чужой расход (другие машины юзера тем же ключом): локальный счёт навсегда ≤ провайдерского; сверка за вчера делает занижение ИЗМЕРЕННЫМ и показывает чужую долю отдельно.
