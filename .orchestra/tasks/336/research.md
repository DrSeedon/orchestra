# #336 — почему тест-гейт мержа не даёт вердикта на большом наборе

Замер 18.08.2026, VPS, обычная агентская нагрузка. Интерпретатор `/home/kesha/orchestra/.venv/bin/python`,
argv и окружение как у гейта (`-q -m "not live_probe"`, `cwd=worktree`, `PYTHONPATH=worktree`).

## 1. Где задан потолок

`app/merge_test_gate.py`: `DEFAULT_TIMEOUT_SECONDS = 180.0` — ОДИН бюджет на весь гейт,
не на файл и не на батч.

- набор ≤ `MAX_TEST_FILES` (12 файлов) → ОДИН вызов pytest, `run_pytest(..., timeout=None)` → 180 с;
- набор > 12 файлов → батчи по ≤ `MAX_BATCH_TESTS` (6), общий дедлайн те же 180 с,
  каждому батчу `remaining / batches_left`.

Гейт не берёт `test_lock` и запускается внутри операции мержа (`app/merge_operations.py:1018`)
через `asyncio.to_thread`. Ограничения сверху на длительность операции нет:
вызов `merge_worker` ждёт терминала `_MERGE_WAIT_SECONDS = 90` с и возвращает
`STILL RUNNING`, оркестратор дозывает по тому же `operation_id`. То есть длинный гейт
не ломает контракт тула — он стоит оркестратору дополнительных poll-ов (~$0.13 за вызов).

## 2. Сколько реально занимает mapped-набор правки #329

Диff `1fe3cf1d` задевает `app/db.py`, `app/manager.py`, `app/pipeline.py`, `app/quota_gate.py`
и три тест-файла → mapped-набор 6 файлов, 510 тестов, путь ОДНОГО вызова (6 ≤ 12), бюджет 180 с.

Один вызов на все 6 файлов: **510 passed in 456.35s** (wall 456.4 с).

Прогресс-строки этого прогона — `14% 28% 42% 56% 70% 84% 98% 100%`; юзер видел обрыв
на 28/42/56%, то есть три отбитых мержа умирали ровно на 180 с этого самого прогона.

**456.4 с против бюджета 180 с — превышение в 2.54 раза.**

## 3. Почему балансировка (#316/#317/#322) не может это спасти — одно число

Те же файлы по одному:

| файл | тестов | wall, с |
|---|---|---|
| tests/test_manager.py | 171 | **219.5** |
| tests/test_db.py | 93 | 116.7 |
| tests/test_worker_model_policy.py | 16 | 30.5 |
| tests/test_default_pipeline.py | 101 | 12.3 |
| tests/test_pipeline.py | 97 | 11.2 |
| tests/test_quota_gate.py | 32 | 8.0 |

`tests/test_manager.py` **сам по себе (219.5 с) дороже ВСЕГО бюджета гейта (180 с)** — в 1.22 раза.
Батч не может быть меньше одного файла, значит:

- **любой дифф, задевающий `app/manager.py`, не может получить вердикт ни при какой
  раскладке батчей и ни при каком балансе.** #316 (батчи), #317 (`remaining/batches_left`),
  #322 (`[5,5,4]` вместо `[2,12]`) перераспределяли те же 180 с — предмет был выбран неверно;
- **параллельность сама по себе тоже не лечит:** идеальный 6-way `pytest-xdist` даёт
  wall = max(219.5) = 219.5 с > 180 с. Бюджет придётся поднимать в любом случае,
  то есть xdist — необязательное ускорение со своей ценой (новая зависимость в ОБЩЕМ
  `.venv` живого сервера, риск флака на общем состоянии: `test_lock` в БД, temp-sqlite,
  сессионные фикстуры Playwright — ложный FAILED хуже таймаута), а не решение.

Худший правдоподобный набор из замеренных (manager+frontend+db+session+mcp_stdio+tg_bridge)

на наборе #329 комбинированный прогон (456.4 с) оказался на 20% дороже суммы одиночных (381.1 с

а дешевле; накладные на лишний интерпретатор измерены как ≈4.3 с на вызов
(`test_pipeline`: wall 11.2 с против 6.88 с внутри pytest).

## 6. Второе требование: «красное» против «не успели»

Внутри гейта различие ЕСТЬ (`FAILED` vs `INCONCLUSIVE`, `retryable=True`), но наружу
оба приходят одинаково:

- `app/merge_operations.py:1004` — `operation_state = "FAILED"` в обоих случаях;
- `next_action` в обоих случаях `FIX_TESTS_THEN_RETRY` с текстом
  «Fix the failing merge-gate tests, then start a new merge» — при таймауте это ЛОЖЬ:
  ни один тест не покраснел;
- признак «не успели» лежит только в хвосте `output` (400 символов), который читатель
  вынужден парсить глазами.

`_merge_tool_result` (`app/mcp_stdio.py:1806`) печатает `FAILED — <message>. <action>`,
то есть первые слова у обоих отказов идентичны. Именно это и наблюдал юзер.

## 7. Что из этого следует делать

1. **Бюджет обязан зависеть от размера набора, с полом и потолком, выведенными из замера:**
   пол ≥ 1.5 × самого тяжёлого одиночного файла (219.5 с) → 330–360 с;
   потолок ≥ 1.5 × худшего правдоподобного набора (682–820 с) → 1200 с.
   Модель: `min(1200, 180 + 150 × n_файлов)` → 1 файл 330 с, 2 → 480, 6 → 1080 (2.4× от
   измеренных 456), 7+ → потолок 1200.
2. **Отказ по времени обязан отличаться от красноты в ПЕРВОЙ фразе и в `next_action`**,
   плюс перечислять файлы, которые не прогонялись, а не прятать это в хвосте вывода.
3. Не делать: накопление результатов между попытками (состояние + инвалидация по SHA;
   при потолке 1200 с худший измеренный набор укладывается на 57% — накопление не покупает
   ничего и добавляет режим отказа «устаревший кеш»), отбор по AST-затронутому коду
   (дорого, отдельная задача), правку самих медленных тестов (тест-слой, нет полномочий).

## 8. Ограничение, из-за которого п.1 нельзя сделать целиком

`tests/test_merge_test_gate.py` замораживает старую модель бюджета литералами
(тест `test_large_mapped_subset_runs_all_files_in_bounded_batches`, #322):

- строка 151: `assert [timeout for _batch, timeout in calls] == [60.0, 60.0, 60.0]`
  — общий бюджет батч-пути обязан быть РОВНО 180 с (180/3);
- строка 150: `assert 36.82 + 240.0 > gate.DEFAULT_TIMEOUT_SECONDS`
  — `DEFAULT_TIMEOUT_SECONDS` обязан быть < 276.82 с;
- строка 149: `assert sum(...) <= gate.DEFAULT_TIMEOUT_SECONDS`.

Путь ОДНОГО вызова (≤12 файлов, 100% наблюдённых отказов: медиана 2, p90 7) поднять можно
без правки тестов — `test_small_mapped_subset_stays_one_batch` проверяет только
`calls == [(tests, None)]`, то есть значение бюджета берётся внутри `run_pytest`.
Батч-путь (>12 файлов, 2 коммита из 80) поднять НЕЛЬЗЯ, не переписав строки 149–151.
Отсюда остаётся уступ: 12 файлов → 1980 с (потолок 1200), 13 файлов → 180 с.
Правка этих трёх строк требует явного разрешения оркестратора (тест-слой).
