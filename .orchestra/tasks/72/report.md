# #72 — два последних крупных ответа: 145.5 КБ → 1.2 КБ и 27.5 КБ → порции по ~8 КБ

Метод — тот же, что дал результат в #65: **пережимать живой ответ вариантами**, а не гадать.
Все цифры «по проводу» сняты через домен (`https://orchestra.seedon.ru`, nginx gzip),
оценки после правки — по копии живой БД с коэффициентом **×1.18** (nginx жмёт слабее
локального `gzip -6`: 145.5 КБ по проводу против 123.1 КБ локально на одном и том же ответе).

## 1. `/api/logs/sync` — 145.5 КБ, из которых рисовалось ~5%

Из чего состоял ответ (499 строк, 25 сессий, 489.8 КБ raw → 123.1 КБ локального gzip):

| часть | вклад в gzip |
|---|---|
| `content` | **114.2 КБ** |
| `ts` | 4.8 КБ |
| `session_id` + `id` + `event_id` | 5.9 КБ |
| `live_sessions` | 0.9 КБ |
| `type`, `trunc` | 0.7 КБ |

То есть резать поля бессмысленно — весь ответ это тела сообщений. Пережатие потиповыми
потолками показало, что и они не спасают: `tool`/`tool_result`/`status` ≤512 Б дают 74.4 КБ,
ВСЕ типы ≤256 Б — 37.4 КБ, и это ценой обрезки 221 строки из 499. Порог 15 КБ так не берётся.

**Что решено: холодная предзагрузка отменена целиком.** `tail=0` — карта сессий и отметка,
ни одной строки журнала. Основание — не вкусовое:

- предзагрузка привозила 20 строк на сессию, а чат показывает 100, поэтому **страница
  истории всё равно добиралась с сервера**: в замере на `main` первый заход к агенту даёт
  запрос `limit=80` вдобавок к 145.5 КБ синхронизации. Предзагрузка экономила не запрос,
  а один кадр отрисовки;
- зеркало живёт в IndexedDB между заходами, а наполняется тем, что юзер реально открыл.
  Это ровно те агенты, к которым он вернётся.

| | `main` | ветка |
|---|---|---|
| холодная синхронизация | **145.5 КБ** (замер по проводу) | **≈1.2 КБ** (1.0 КБ локально ×1.18) |
| строк в ответе | 499 | 0 |

**Чем платим:** первый в жизни заход к агенту, которого юзер ещё не открывал, теперь идёт в
сеть за первой порцией (~8 КБ, ~150–300 мс) вместо мгновенной отрисовки из зеркала. Заход
второй и далее, включая F5, — по-прежнему без сети: проверено, после F5 **0 запросов
истории** и те же 100 строк.

## 2. Страница истории — 100 строк одним ответом

Порция по строкам не ограничивает ответ: размер сообщения гуляет на три порядка, и
25 строк в разных чатах дают от 5.2 до 46.6 КБ. Поэтому порция ограничена **и строками
(25), и байтами** — новый параметр `max_bytes` у `/api/sessions/{name}/logs` (бюджет 24 000 Б
content на ответ; строка, которая одна перебирает бюджет, отдаётся одна — иначе пустой ответ
и вечный цикл добора).

Прогон по ВСЕМ 25 сессиям живой БД (`measurements/sweep.py`), худшая порция по проводу:

| | одним ответом | порциями (худшая) |
|---|---|---|
| 21 сессия из 25 | 9.6–65.5 КБ | **5.3–13.1 КБ** |
| `payroll`, `tax-rsv` | 64.7–65.5 КБ | 15.1–16.0 КБ |
| `seo-cro`, `dev-lead` | **1261.9 КБ**, 475.4 КБ | 507.4 КБ, 391.5 КБ |

Сотня строк сохранена: замер в браузере — 4 порции (25+25+25+24), **100 строк** нарисовано,
как и на `main`.

## Где порог 15 КБ НЕ достигнут, и чем платим

**Одно сообщение больше бюджета едет отдельным ответом своего размера.** У `seo-cro` худшая
порция — 507 КБ, у `dev-lead` — 391: это одиночные строки (base64-блобы). Порции их больше не
тащат за собой соседей — страница целиком стоила 1261.9 КБ, худший кусок теперь 507 КБ, —
но под порог такую строку можно загнать только обрезав её. Обрезать сообщение, которое юзер
открыл читать, молча нельзя, а видимой пометки «обрезано, открыть целиком» и ручки на одну
строку в интерфейсе сейчас нет. Это следующая задача, а не то, что стоит доделывать украдкой:
серверный `cap` + маркер обрезки + endpoint на одну строку.

Ещё две сессии (`payroll`, `tax-rsv`) выходят за порог на 1 КБ. Опускать бюджет ниже
24 000 Б ради них я не стал: это добавляет порций (то есть RTT) всем остальным, а на 15.1 КБ
против 15.0 разница внутри погрешности коэффициента ×1.18.

## Проверка

- **Форма запросов и целостность зеркала** (`verify-chunks.py branch|main`, живой :8888,
  `app.js` подменён из worktree, счётчик подмены печатается):

  | | `main` | ветка |
  |---|---|---|
  | холодная синхронизация | `tail=20` | `tail=0` |
  | запросов истории при первом заходе | 1 (`limit=80`) | 4 (`limit=25&max_bytes=24000`) |
  | строк нарисовано | 100 | 100 |
  | после F5: строк / запросов истории | 100 / 0 | 100 / 0 |

- **Дыра в зеркале, найденная при самопроверке.** Строки, скачанные `_fetchHistory`, в
  зеркало НЕ писались — раньше самый свежий кусок привозила холодная предзагрузка. Без неё
  в зеркале осталась бы дыра ровно на последних 25 строках, а инкремент их не принесёт
  никогда (они старше watermark). Добавлен `_storePut` в `_fetchHistory`; проверка после F5
  (100 строк, 0 запросов) — это она и есть.
- **Тесты**: `tests/test_logs_sync.py` + `test_api.py` + фронтовые → 146 passed, 16 skipped.
  Новые стражи: бюджет режет порцию по байтам; строка больше бюджета приходит одна; без
  бюджета лимита нет; склейка порций назад даёт ровный ряд без дыр и повторов; `tail=0`
  отдаёт карту без строк. Мутация (`if False and …` вместо проверки бюджета) роняет 2 из 5 —
  зелёные не по случайности.
- **Cross-LLM ревью**: вердикта нет — Codex недоступен до 08.08. Вместо него самопроверка;
  найденное ей — дыра в зеркале выше.
