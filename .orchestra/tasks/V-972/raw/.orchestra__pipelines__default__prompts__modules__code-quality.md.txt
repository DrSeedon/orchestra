    2	## Code quality
    3	
    4	**Think before coding.** Check discoverable facts and state bounded assumptions. Ask only when
    5	an unresolved choice changes scope, authority, material cost or an external contract.
    6	Prefer the simplest complete solution; challenge a faulty premise with evidence.
    7	
    8	**Simplicity first.**
    9	- Minimum code that solves the task. Nothing speculative
   10	- No features beyond request. No abstractions for one-off code
   11	- No comments except WHY (not WHAT), non-obvious decisions, docstrings on public API.
   12	  Keep their density at or below the surrounding code.
   13	- 200 lines where 50 suffice → rewrite
   14	- Before adding code, stop at the first applicable answer: should this exist at all;
   15	  does the codebase already do it; does the standard library/platform do it; can it be one line?
   16	  This simplicity check never removes the protections in the safety module.
   17	
   18	**Collect everything, filter on display (owner decision, 2026-09-29: collect the complete source
   19	record first and apply filters only when displaying it).** "Minimum
   20	code" never means minimum data. When code pulls data from an external source (API, site search,
   21	registry, feed), store every record and every field the source gives into our own storage, and
   22	apply business filters (price, keywords, region, relevance) at query/display time, where they can
   23	be changed without re-collecting. Narrowing at the source request is allowed only when the source
   24	cannot return the rest, the volume does not fit memory/disk (measure first), or the source forbids
   25	it — and then name exactly what is cut off. Measured cost of not doing this (seedon, 29.09): the
   26	EIS search filter dropped every tender above 2 mln at request time, so the database held none of
   27	them and nobody saw the gap.
   28	
   29	**Evaluating candidates (owner decision, 2026-10-16).** Judge a license by the real use, not
   30	the label: a non-commercial license does not rule out a model or tool for personal or internal
   31	use unless the project states a commercial purpose. Record the license restriction as a fact
   32	next to the candidate, not as a reason to reject it. Research on voice, images or video brings
   33	real samples produced by your own hands plus public demos; vendor scores and reviews do not
   34	replace samples. This binds whoever writes the research assignment and whoever accepts its verdict.
   35	
   36	**Surgical changes.** Touch ONLY what the task requires.
   37	- Don't "improve" neighboring code, formatting, comments
   38	- Don't refactor what isn't broken. Follow existing style
   39	- Noticed dead code → mention, don't delete unless your changes orphaned it
   40	
   41	**Diagnostic rounds.** Batch independent read-only checks into one tool round with bounded
   42	output and visible results for each check. Keep commands sequential when the next action
   43	depends on the previous result; do not batch mutations or retries merely to save a round.
   44	
   45	**`Killed` or `EXIT=137` — check your cgroup before your code.** Everything an agent launches,
   46	including `bg_create type=run`, lives inside the platform cgroup with a hard memory ceiling; the
   47	kernel can OOM-kill it while the machine still has free memory. `free` shows the wrong limit for
   48	you, and agents cannot use `dmesg`, so the symptom looks like a code or data defect. Measured on
   49	the VPS on 2026-09-19: `/proc/self/cgroup` was `orchestra.service`, `MemoryMax` was 12 GB (check the
   50	current value with `systemctl show orchestra -p MemoryMax`), and
   51	the platform already used 8.5 GB. The mistaken diagnosis cost seven successive rewrites
   52	(lowering the engine limit, splitting grouping, changing architecture, hash buckets,
   53	approximate counting, and deleting 23 GB), none of which addressed the cause. Diagnose with
   54	`cat /proc/self/cgroup` and your cgroup's `memory.max`. Run heavy work (datasets, builds, or
   55	anything needing several GB) outside the platform cgroup:
   56	`ssh -o BatchMode=yes kesha@localhost 'choom -n 1000 -- <command>'` enters the user slice where
   57	`memory.max = max`; `choom` makes the heavy workload an earlier OOM victim than Orchestra.
   58	The same script that failed seven times completed there in 47 seconds. Agents must not change
   59	`orchestra.service` limits: that infrastructure ceiling protects the platform from agent processes.
   60	
   61	**Route code intelligence by question.**
   62	- Literal text, paths, and current occurrences → `rg` first
   63	- Python reachability, decorators, registries, or dead clusters → task-local AST plus `rg`; a zero from either alone proves nothing
   64	- Known static-symbol rename → LSP/Serena is optional, then `rg` strings/comments/config/templates and run tests
   65	- Delete as unreachable only with a production-root proof and a mutation that makes the acceptance test fail
   66	- **A mutation proves nothing unless the test it reddens is COMMITTED.** A throwaway probe dies with your turn and guards nobody. Measured 25.08 (#398): a worker reported both fixes mutation-checked, and disabling one of its own fixes afterwards left the named suite green — `35 passed, RC=0` — because no test had entered the repository. Report a mutation only against a test that is in your diff.
   67	- A green regression command does not settle an unreproduced defect. Inspect the reported path,
   68	  reproduce it and add a meaningful check. Use test-first work when the contract is known;
   69	  exploratory diagnosis need not manufacture a frozen test before understanding the failure.
   70	
   71	**Test the core, never the wording (owner decision, 2026-09-06: test only stable core behavior,
   72	not prose that is deliberately rewritten).** This project changes constantly; a test that fails because we deliberately changed
   73	something is not a guard, it is a brake.
   74	- **Never assert a literal phrase of a prompt, rule, report or document.** No anchor lists of
   75	  quotes, no "this exact sentence must be present/absent". Such a test reddens when the OWNER
   76	  rewrites a rule — it reports his decision back at him as a failure. Measured 06.09: 23 such
   77	  tests were deleted at once, and not one of them had ever caught a defect; three were red at
   78	  that moment purely because the wording and the docs had legitimately moved on.
   79	- **Do test the mechanics that carry the wording**: that a module reaches every role, that one
   80	  role's prompt does not leak into another, that an index is assembled from its single source.
   81	  Those catch real loss — a role silently losing an entire layer of rules was found exactly this
   82	  way (#490).
   83	- Before adding any test, answer in one line: *what breaks in production if this is missing?*
   84	  Cannot name it → do not write the test. "It documents the current text" is not an answer.
   85	- Test the core that must not change: data integrity, authorization, money and quota accounting,
   86	  lifecycle transitions, concurrency, recovery, external contracts. Leave prose, formatting,
   87	  ordering of sections and internal naming untested.
   88	- Finding a brittle wording test while doing something else → delete it in that same change and
   89	  say so in the report. Do not "fix" it by updating the quote.
   90	
   91	**Pit of success.** Code where screwing up is hard.
   92	- Flat structure, minimal indirection. Reads top to bottom
   93	- One task = one pattern. Not two helpers for the same thing
   94	- Explicit > implicit. No magic, no hidden side effects
   95	- Make errors visible. Fail the unsafe operation; optional bookkeeping or unavailable metadata
   96	  must not crash an otherwise valid task.
   97	- 3 duplicate lines > premature abstraction
