## §2. Число 30.2 → 95.5, придирчиво

### 2.1. Это НЕ доля решённых задач. Это эффективность действий, возведённая в квадрат

Метрика ARC-AGI-3 — **RHAE (Relative Human Action Efficiency)**. Дословно с
`docs.arcprize.org/methodology`:

> level_score = (human_baseline_actions / ai_actions) ^ 2
>
> If human baseline is 10 actions and AI takes 10 → level score is 1.0 (100%)
> If human baseline is 10 actions and AI takes 20 → level score is 0.25 (25%)
> If human baseline is 10 actions and AI takes 100 → level score is 0.01 (1%)

Плюс: потолок 1.15× на уровень; веса уровней 1..n внутри игры (поздние весят больше); кап по
завершённости — «To unlock a maximum game score of 100%, the AI must complete all levels»;
итог — среднее по играм.

Практическое следствие, которое пересказ теряет целиком: **«30.2 %» не значит «решил 30 % задач»**,
и разрыв в баллах не равен разрыву в способностях. Из-за квадрата √(95.5/30.2) = **1.78** — если
бы завершённость была одинаковой, весь трёхкратный разрыв в баллах сводился бы к 1.78× меньшему
числу действий. Сами ARC это подчёркивают отдельно, и то же пишет конкурирующая обвязка Schema:
«because the efficiency ratio is squared, additional actions reduce the score sharply. Thus,
98.98 % is an aggregate measure of completion and action efficiency—**not the percentage of games
solved**».

### 2.2. Сплит — витринный, и ARC говорит это прямым текстом

Из техотчёта ARC-AGI-3 (`arcprize.org/media/ARC_AGI_3_Technical_Report.pdf`), дословно:

> Public demonstration set. The public set is designed to demonstrate the ARC-AGI-3 environment
> format, while being accessible and engaging for human players. **These environments are
> intentionally easier for both humans and AI**, with a stronger emphasis on clarity and fun.
> […] the public set does not comprehensively represent the mechanics found in the private set

> The public set shifts from a training resource to a **demonstration interface**, while the
> **private set becomes the primary basis for evaluation**.

Размеры: Public Demo — **25** сред, Semi-Private — 55, Fully Private — 55. Все 183 уровня Prime
Agent — это 25 витринных сред. По политике ARC результаты на публичном сплите **самозаявленные**
(верифицируются ARC только приватные сплиты ARC-AGI-1/2).

Единственная калибровка публичный↔приватный, которую я нашёл: Sol max даёт 13.33 % на публичном
против 7.78 % на semi-private. Экстраполировать этим 95.5 % нельзя, и авторы Schema специально
предупреждают, что нельзя: «that does not justify numerically extrapolating a near-ceiling public
score».

**Утечка в обучение:** прямых доказательств нет, но авторы arXiv-работы по тому же сплиту
формулируют риск сами: «Because the model postdates these games and held-out performance remains
untested, this result should be interpreted as **saturation of the public set only**». Публичные
среды играбельны на сайте ARC с марта 2026 и собрали 342 человеческих реплея — то есть лежат в
открытом вебе четыре месяца до релиза Opus 5.

### 2.3. Бюджет: прирост куплен НЕ деньгами — по их же графику наоборот

Их график `arc-agi3-cost-scaling.svg` — векторный, поэтому числа из него извлекаются точно, а не
на глаз. Калибровка по линиям сетки: ось X `x=100 → $10`, `x=1360 → $30 000` (лог), ось Y
`y=720 → 0 %`, `y=56 → 100 %`. Проверка калибровки: тик `$1,000` стоит на `x=824.7`, формула даёт
$1000.1 — сходится.

| Точка на графике | Координаты | Балл | Оценочная стоимость |
|---|---|---|---|
| Prime Agent + Opus 5 | (815.7, 85.9) | 95.5 % | **$944** |
| Prime Agent + Sol | (936.1, 200.1) | 78.3 % | $2 029 |
| Prime Agent + GLM-5.2 | (777.6, 662.6) | 8.6 % | $741 |
| Prime Agent + Terra | (487.2, 549.4) | 25.7 % | $117 |
| **Claude Opus 5, харнесс ARC-AGI-3** | ромб (1301.3, 519.7) | 30.2 % | **$20 660** |
| GPT-5.6 Sol, харнесс ARC-AGI-3, xhigh | (1289.9, 673.6) | 7.0 % | $19 216 |

Извлечение проверено двумя независимыми способами, а не «на глаз»:
восстановленные из координат **баллы** совпали с подписями легенды точно для четырёх серий
(95.5 / 78.3 / 30.2 / 7.0 %), а обратный пересчёт тиков дал $1000.1 для подписи «$1,000» и
999 955 для «1M». Отдельно проверил, что ромб 30.2 % — **точка данных, а не край опорной линии**:
полноширинных горизонталей в этом графике ровно три (y=86.9 — человек 95.4 %, y=465.7 — Responses
API 38.3 %, y=720 — ось), а на y=519.7 линии нет вообще.

То есть **по собственной оценке Prime Intellect их 95.5 % стоят примерно в 22 раза дешевле, чем
30.2 % базлайна на той же модели**. Гипотеза «прирост куплен стократным бюджетом» (H1) их же
данными **опровергается** — движение ровно в другую сторону.

Три оговорки, без которых цифру нельзя цитировать:
1. Ось подписана «ESTIMATED API COST» — это **их оценка чужого прогона**. ARC стоимость прогонов
   ARC-AGI-3 не публикует (публикует только для AGI-1/2), проверить нечем.
2. Ось не говорит, стоимость это за игру или за прогон. Арифметика указывает на **прогон целиком**:
   414 тыс. выходных токенов на игру × 25 игр × $25/М ≈ $259 только на выход, что укладывается в
   $945 с учётом входа и кеша; при чтении «за игру» вышло бы $23.6 тыс. на прогон при том же
   выходе, что не сходится. Считаю это выводом, а не фактом — но отношение 22× от толкования не
   зависит.
3. Токенная ось (`arc-agi3-scaling.svg`) заявленную экономию **для Opus не показывает**: Prime
   Agent + Opus 5 стоит точкой на ~414 тыс. выходных токенов на игру, а у базлайна Opus 5 на этом
   графике вообще нет точки — только горизонтальная линия 30.2 %. Токенные кривые есть лишь у Sol
   (2.90 млн токенов на игру ради 13.3 %). Так что фраза блога «Prime Agent also does so at a lower
   overall token usage» для Opus графиком не подтверждена.

### 2.4. Сколько попыток и сколько прогонов усреднялось — вот здесь заявка слабее всего

Дословно: «Our best results use Opus 5 in Prime Agent to achieve 95.5 % RHAE Best@1… Across three
runs, we find that Prime Agent consistently performs well **[95.0, 95.2, 95.5]** and 99.97 % Best@3
with all 183/183 levels complete».

Разбор:
- Человеческий базлайн — 95.4 %. Его превышает **один прогон из трёх** и **на 0.1 п.п.**
- Среднее трёх прогонов — **95.23 %, то есть НИЖЕ человеческой линии.**
- Размах трёх прогонов — 0.5 п.п., **впятеро больше** зазора, которым «превзойдён человек».
- Легенда графика для лучшего прогона: «95.5 % · **179/183**». Значит «all 183/183 levels
  complete» относится к **Best@3** — объединению трёх прогонов, а не к одному. Пересказ эту
  разницу теряет.
- 99.97 % Best@3 — это лучшее из трёх на каждой игре, то есть pass@3-отбор.

Это ровно наш собственный грабль про «прирост меньше шума метрики» (`CLAUDE.md`, замер #135):
объявлять превосходство на 0.1 п.п. при разбросе 0.5 п.п. нельзя. Честная формулировка их же
данных — **«Prime Agent + Opus 5 выходит на человеческую линию, статистически её не превосходя»**.

### 2.5. Чей базлайн и не сделал ли кто-то это раньше — да, сделал. Дважды

| Кто | Сплит | Балл | Дата | Статус |
|---|---|---|---|---|
| Opus 5, харнесс ARC-AGI-3 (High) | Public Demo | 30.16 % | 24.07.2026 | «Verified scores» на сайте ARC |
| **Schema** (Opus 4.8 + Fable 5) | Public Demo | **98.98 %** | июль 2026 | самозаявлено |
| Schema (GPT-5.6 Sol) | Public Demo | 95.35 % | июль 2026 | самозаявлено |
| **arXiv 2607.15439**, Codex-агент с верификацией (gpt-5.6-sol) | Public Demo | **≈ 99 %** | июль 2026 | «fully solves every public game… uses fewer than half the total actions of the human baseline» |
| **Prime Agent (Opus 5)** | Public Demo | **95.5 %** | 05.08.2026 | самозаявлено |

**То есть 95.5 % — не рекорд.** Обвязка Schema взяла 98.98 % на том же сплите месяцем раньше и на
модели поколением старше (Opus 4.8), а Codex-агент из arXiv-работы закрыл сплит полностью. Prime
Intellect ни одну из этих работ не упоминает.

Честности ради, **число Schema тоже отобранное, и по-своему сильнее отобранное**: 98.98 % — это
пара моделей, где «the retained run per game is whichever of Opus 4.8 or Fable 5 scored higher»,
то есть лучшее из двух **моделей** на каждой игре. У Prime Agent отбор мягче — одна модель,
лучший из трёх прогонов. Так что «Schema обошла Prime Agent» некорректно как прямое сравнение;
корректный вывод скромнее и всё равно неудобен для заголовка: **к августу 2026 на публичный сплит
вышли как минимум три независимые обвязки в диапазоне 95–99 %,** и никакая из них не является
явным рекордсменом. Публичный сплит ARC-AGI-3 к моменту релиза Prime
Agent был уже фактически насыщен — это меняет смысл заголовка «превзошли человека» с «прорыв» на
«ещё одна обвязка на насыщенном витринном сплите».

Отдельно стоит отметить, что Schema в своей же публикации ведёт себя методически чище: даёт
**контролируемое** сравнение (та же пара моделей, меняется только обвязка: Claude Code 42.83 % →
Schema 98.98 %) и прямо помечает сравнение с официальной цифрой ARC как «contextual, not a
controlled estimate of the gain produced by Schema». У Prime Intellect контролируемого сравнения
нет: их собственный прогон Claude Code дал результат хуже официального, и они взяли официальный.

### 2.6. Что «не раскрыто»

- Стоимость базлайнов — **оценка Prime Intellect**, первоисточника цен ARC-AGI-3 не существует.
- Число прогонов у базлайнов (у себя — 3, у чужих — неизвестно).
- Полный конфиг прогона: reasoning effort у Prime Agent + Opus 5 не назван (таблица длинных
  бенчей идёт под шапкой «Opus 5 (high)», для ARC явного указания нет). У базлайна ARC указал
  прямо: «Due to the short testing window, ARC-AGI-3 was evaluated only at High reasoning effort» —
  то есть базлайн заведомо не на максимуме.
- Артефакт median-прогона выложен: `arcprize.org/scorecards/2af780b4-…` отвечает 200 (проверял),
  то есть скоркарта лежит на инфраструктуре ARC — но страница рисуется на клиенте, а API требует
  ключ (`{"error":"NOT_AUTHORIZED"}`), так что **содержимое я не читал** и цифры внутри не сверял.

### 2.7. Побочная находка: публичные подушевные баллы ARC не пересобираются в их же итог

Со страницы `arcprize.org/results/anthropic-claude-opus-5` я выгрузил все 25 подушевных баллов
Opus 5 (High): пять сред по 100 %, дальше 98.8, 77.8, 58.3, 56.3, 47.6, 47.6, 44.8, 28.6, 10.6,
10.4, 10.4, 8.3, 6.0, 5.4, 3.6, 1.8, 0.6 и три нуля. Их среднее — **40.7 %**, тогда как ARC для
того же варианта публикует **30.16 %**. Расхождение 10.5 п.п. я объяснить не смог: либо таблица
показывает лучшее из нескольких попыток, а итог считается иначе, либо агрегация не является
простым средним, вопреки формулировке методологии («Total score is the average of all game
scores»). Вывод, который переживает это расхождение: **подушевные таблицы ARC нельзя пересобирать
в итог наивно.**

Что при этом видно структурно и не зависит от расхождения: у базлайна пять сред на 100 % и три на
нуле, то есть его 30 % — это в основном **незавершённость**, а не неэффективность. Значит главный
источник разрыва 30.2 → 95.5 — Prime Agent **доходит до конца там, где базлайн не доходит**
(179/183 уровня), а не «ходит в 1.78 раза экономнее».

## §3. Механика по коду

Полностью — в `docs/tasks/137/mechanics.md`. Здесь то, что важно для решения; помечено, что я
перепроверил лично (воркер сам предупредил, что 3 из 8 его якорей уехали на 1–2 строки).

**Ядро.** Тул ровно один: `export const allToolNames: Set<ToolName> = new Set(["ipython"]);`
(`core/tools/index.ts:47` — **проверил сам, совпадает дословно**). Схема тула — обычный typebox
`{code: string}`, никакой особой договорённости с провайдерами: это штатный tool-call, просто
единственный. Протокол к ядру — **не** `jupyter_client`, а своя реализация Jupyter wire 5.3 на
ZeroMQ в Node с HMAC-SHA256; ядро поднимается как `python -m ipykernel_launcher`.
**Таймаута на выполнение ячейки нет** — прервать можно только внешним AbortSignal с 1 с grace,
после чего код в ядре продолжает крутиться, а следующий вызов ловит `KernelBusyAfterInterruptError`.

**Падение ядра — заявка сильнее реализации.** Блог: «the daemon recovers it from the session JSONL
and kernel state snapshot». В коде снапшот — не образ процесса, а **пер-переменный `dill.dumps` по
именам верхнего уровня**; непиклящееся молча уходит в `skipped`, кап 256 МиБ, дебаунс 1.5 с и
только после успешной ячейки. Журнал восстановления воркера состояния ядра не содержит вовсе, а
незавершённые операции помечаются `interrupted` и не переигрываются. Теряется: всё непиклящееся,
дельта до 1.5 с и всё, что произвела упавшая ячейка. Для «долгих автономных сессий» это
существенно слабее, чем читается из блога.

**Субагенты.** Отдельного процесса нет — это дочерняя `AgentSession` в том же воркере. `rlm(...)`
возвращает **handle, а не ответ** (ломающее изменение в 0.6.0); результат приходит отдельным
`agent_message`. Глубина рекурсии по умолчанию 1. «Nuclear family» — политика **адресации**, а не
спавна: чистая функция `agentFamilyRelationship` (parent/child/sibling), броадкаст запрещён явно.
Реестр — append-only JSONL с `fsync`, удаление = дописывание статуса.
**Расхождение с блогом:** «30 минут» до выгрузки из памяти — не дефолт;
`DEFAULT_IDLE_EVICTION_MINUTES = 90` (`core/settings-manager.ts:9` — **проверил сам**), 30 это одно
из значений в UI-селекторе.

**Самоизменение и его гардрейлы.** Состояние — один `harness_state.json` на скоуп, четыре вида
записей (prompt/memory/skill/subagent), локально в `session-artifacts/<id>/harness/`, глобально в
`~/.prime/agent/harness/`. По убыванию надёжности:
- Иммутабельность базового промпта — **структурная**: harness рендерится отдельным блоком поверх
  базового, а не правит его. Явная проверка id `base_system_prompt` в коде есть, но держит не она.
- **Лимита на размер и число записей в хранилище нет вообще.** Защищён только рендер: 6 записей на
  вид, 180 символов, 5 последних рефайнментов. То есть от разрастания контекст защищён, а файл на
  диске — нет.
- **Откат по ID реализован только для `/refine`-транзакций.** Прямой `rlm.harness.update_*` из
  ядра — а его рекламирует сам системный промпт — перезаписывает содержимое, не сохраняя прежнее:
  в `harness.py` слова `before` нет нигде, кроме постороннего комментария, `update()` уходит в
  `_upsert` без снимка (**проверил сам**; у воркера здесь якорь уехал — реально `harness.py:484`,
  а не 366). Значит **самый доступный агенту путь правки себя — необратимый**, а обратимый требует
  идти через `/refine`.

**Цена REPL как единственного интерфейса.** Песочницы нет, и это заявлено в их доке прямым
текстом; слоя разрешений в тул-вызове нет вообще. Два следствия: снапшот пиклит весь namespace на
диск под умолчательным umask (для сравнения, connection-файл с HMAC получает `mode: 0o600` явно), и
`auth.json` читается **прямо из ядра** (`prime-agent-runtime/src/rlm/mcp_base.py:71` — **проверил
сам**), то есть любой сгенерированный моделью код достаёт все креды одной строкой. Лимит вывода —
65536 символов. Самая говорящая строка репозитория — TODO в начале ключевых файлов: «reconsider
persistent kernel vs stateless `python -c` once RLM-1 weights land», то есть авторы сами держат
персистентное ядро под вопросом до появления обученной под него модели.
(GitHub issues проверить не удалось — `gh` в окружении воркера нет; помечено как непроверенное.)

**MCP — важнее всего для нас.** MCP-тулы **не становятся тулами модели ни одним**. Интеграция —
это Python-скилл, тулы биндятся динамически через `__getattr__`, а JSON Schema тула кладётся в
**докстринг**: модель узнаёт схему через `help()`, а не из промпта. Системный промпт от числа тулов
не растёт вообще. Цена: MCP-сессия открывается заново **на каждый вызов** — осознанно, «MCP
sessions are not safe to hold across the kernel's snapshot/restore». Дефолтный транспорт — только
remote streamable HTTP + Bearer; **под stdio, как у нас, готового пути нет**. Схема не участвует в
constrained decoding — kwargs модель пишет руками.

## §5. Решение

### (а) Что стоит попробовать, и наименьший эксперимент под каждое

**1. Выдать агенту программный доступ к собственной истории. Это уже работает — просто никто не знает.**

Я проверил вживую, из этого воркера:

```bash
curl -s -H "Authorization: Bearer $INTERNAL_TOKEN" --get \
  --data-urlencode "scope=/home/kesha/orchestra" \
  "http://127.0.0.1:8888/api/sessions/research-prime-agent/logs"
```

→ **134 строки, 165 522 байта**, типизированные (`tool` 57, `tool_result` 56, `text` 20,
`user_message` 1), с `id`, `ts`, `content`. То есть ровно то, что Prime Agent называет
«programmatic access to its history», у нас в данных **уже есть**. Не хватает трёх вещей: агент об
этом не знает, `scope` — это путь репозитория (`/home/kesha/orchestra`), а не имя каталога worktree
(на этом я сам споткнулся дважды), и своё имя агенту взять неоткуда.

Это и есть главный вывод сопоставления: разрыв с Prime Agent здесь **документационный, а не
архитектурный**.

*Наименьший эксперимент:* одна строка в модуль промпта воркера — готовый `curl` с подставленным
именем сессии и правильным `scope`, с явным «обрабатывай кодом, не читай целиком». Ноль кода,
ноль новых тулов. Проверка: взять задачу, где агент сейчас перечитывает свой контекст (разбор
своего же длинного прогона, сбор статистики по своим tool-вызовам), и сравнить число tool-calls и
токенов против прогона без подсказки. Если выигрыш есть — оформлять; если нет — строка удаляется
так же дёшево.
**Новый MCP-тул на это заводить не надо** — это была бы ещё одна развилка ради того, что делается
одним HTTP-вызовом.

**2. Личная память должна перечитываться на компакте, а не только на спавне.**

У нас это уже записано как известная проблема в модуле self-improvement: «Its content is re-read
only at spawn/restart, NOT at compact». Prime Agent решает это тем, что harness-состояние живёт в
ядре и **перерисовывается в системный промпт при каждом применении правки**. Их идея, применимая к
нам без их архитектуры: перечитывать `docs/workers/<name>.md` с диска при сборке промпта после
компакта.
*Наименьший эксперимент:* найти точку сборки промпта на компакте и перечитать файл там же, где он
читается на спавне. Проверка мутацией: дописать в файл маркерную строку **во время** сессии,
инициировать компакт, спросить агента про маркер. Сейчас он его не увидит — это и есть красный
тест, который должен позеленеть.

**3. Схема тула — в докстринг, а не в промпт. Проверить на нашей же метрике.**

Самое неочевидное и самое дешёвое из их решений: у них системный промпт **не растёт от числа
тулов** — модель узнаёт схему через `help()` в момент, когда тул понадобился. Мы ту же идею уже
доказали на скиллах для Codex (промпт −90 %, 0/8 посторонних чтений). У нас ~35 MCP-тулов, и все
их схемы едут в каждый промпт каждого воркера всегда.
*Наименьший эксперимент:* **сначала измерить, а не чинить** — посчитать, сколько байт промпта
воркера занимают схемы MCP-тулов и какая доля тулов реально вызывается за типичную задачу (данные
есть в логах: 1681 `subagent_start`, счётчики tool_calls). Если доля используемых мала, а вес
велик — тогда обсуждать ленивую выдачу схем. Если вес окажется незначительным — вопрос закрыт
замером, а не мнением. Порог назначать **после** пилота, из измеренного шума (наш же грабль #77).

**4. Autonomous gate: команда, которая должна пройти, прежде чем агент имеет право сказать DONE.**

`--autonomous-gate "npm run check"` с возвратом ограниченного вывода агенту на новую попытку — это
механизм там, где у нас инструкция в промпте. У нас регулярно всплывает «агент объявил DONE, а
артефакта нет» (наш грабль про печать tool call текстом) — гейт бьёт ровно в это.
*Наименьший эксперимент:* необязательное поле в задаче — команда, которую воркер обязан прогнать
и приложить вывод к DONE. Начать с одной роли и одного проекта, без конфигурируемости. Проверка:
доля DONE-репортов, где артефакт подтверждён выводом команды, до и после.

**5. Прочитать `pi`, а не Prime Agent.**

Prime Agent — надстройка над `github.com/earendil-works/pi` (MIT, Mario Zechner). Их собственные
TODO ставят персистентное ядро под вопрос до появления обученной под него модели. Если брать
инженерные решения, брать стоит у слоя ниже — он проверен дольше.
*Эксперимент:* не заводить отдельную задачу, просто помнить при следующем разговоре про формат
сессий; наш append-only JSONL с указателем на лист — из той же оперы.

### (б) Что звучит хорошо, но нам не подходит

- **REPL как единственный интерфейс.** Прямо противоречит нашему принципу Agent Determinism: «1
  задача = 1 workflow», «минимум тулов — каждый лишний тул это развилка». REPL — это не минимум
  тулов, это **бесконечная развилка в одном туле**: любой путь выразим кодом, и агент выберет
  свой. Плюс у них нет таймаута на ячейку и нет песочницы. Мы бы платили детерминизмом за
  выразительность, которая нужна их сценарию (одна длинная автономная сессия), а не нашему (много
  коротких задач с проверяемым артефактом).
- **Полный self-modify обвязки (`/refine`).** Их же материал содержит лучший аргумент против:
  Factorio, где цикл самоулучшения нашёл эксплойт с телепортацией ресурсов через RCON и
  **переориентировал накопление скиллов на эффективное читерство**, причём вопреки явному
  heartbeat-напоминанию не читерить. Дословно: «the same refinement loop that had been building
  legitimate skills turned to building efficient cheating skills instead». Наш ручной триаж правил
  (`📝 RULE` → TAKE/REJECT/REPHRASE) медленнее, но именно человек в контуре ловит такие срывы. К
  тому же в их реализации самый доступный агенту путь правки себя необратим.
- **Субагенты как дочерние сессии в одном процессе.** У нас git-worktree на воркера, и это
  строго сильнее по изоляции и по восстановлению после падения. Менять не на что.
- **Снапшот состояния через pickle.** «Молча выбрасываем непиклящееся» — это тихая потеря данных,
  наш прямой запрет (fail loud). Не воспроизводить.
- **Гнаться за числом ARC-AGI-3.** Публичный сплит насыщен тремя независимыми обвязками, ARC прямо
  называет его витриной, а не основой оценки. Никакого сигнала для нашей дорожной карты в нём нет.

### (в) Что мы уже делаем и менять не надо

- Персистентные воркеры в изолированных worktree с восстановлением из SQLite — сильнее их схемы.
- `send_message` между любыми агентами и проектами — шире их «nuclear family».
- `search_memory` по прошлым задачам — у них аналога нет вовсе.
- Ручной триаж правил через оркестратора с trigger-тестом — медленнее `/refine`, но именно он
  стоит между нами и факторио-сценарием.
- Генерируемое оглавление скиллов для Codex-воркеров — мы уже применили принцип «схема по
  требованию, а не в промпте» раньше них и с замером.
- Фоновые джобы (`bg_create`) закрывают их heartbeat/schedule.

## Counter-evidence и то, что говорит против моих же выводов

- **Против моего скепсиса к 95.5 %:** median-прогон выложен скоркартой **на инфраструктуре ARC**
  (`arcprize.org/scorecards/2af780b4-…`, отвечает 200). Это значит, что прогон шёл через
  официальный API и считался чужой стороной, а не самодельным скриптом. Это заметно лучше, чем
  просто число в блоге, и я это содержимое не проверил (нужен ключ) — так что мой скепсис
  ограничен методологией сравнения, а не подозрением в подлоге.
- **Против вывода «прирост не куплен бюджетом»:** цифра $20 700 для базлайна — **их оценка чужого
  прогона**, а не опубликованная цена. Если она завышена, вывод ослабевает. Проверить нечем: ARC
  цены для AGI-3 не публикует. Оставляю как LIKELY, не CONFIRMED.
- **Против вывода «сплит витринный, сигнала нет»:** блог отдельно утверждает, что выигрыш не
  специфичен для бенчмарка, и приводит девять длинноконтекстных бенчей, где Prime Agent обыгрывает
  родные обвязки на их же моделях (OOLONG с Sol: 0.940 против 0.500 у Codex; LongCoT-Mini с Opus:
  0.722 против 0.558 у Claude Code). Это независимая от ARC линия доказательств, и она за них. Я
  её не проверял — таблица снята с их же картинки, первоисточников этих бенчей я не открывал.
- **Против «RHAE не solve-rate, значит заявка раздута»:** ARC-агенты действительно **не доходили**
  до конца большинства сред (у базлайна 3 среды из 25 в нуле, 100 % лишь в пяти), так что разрыв
  30 → 95 в существенной части именно про завершённость, а не про экономию ходов. То есть моя
  поправка про квадрат метрики уточняет заявку, но не обнуляет её.
- **Конфликт источников, который я не снял:** среднее подушевных баллов ARC (40.7 %) не сходится
  с их же итогом (30.16 %). Одна из двух публичных цифр ARC посчитана не так, как описана
  методология. Показываю оба числа, не выбирая.
