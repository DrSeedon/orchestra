# #4 — почему история usage пустая по Codex

## Короткий ответ юзеру

**История Codex за июль не испорчена и не потеряна — её никогда не писали.**
Восстанавливать нечего: этих данных нет ни в одном хранилище, и достать их неоткуда.
С 03.08 Codex пишется штатно, впредь не теряется.

## Диагноз: цифры, а не рассуждение

Замер по read-only копии живой `data/orchestra.db`.

| Период | Строк | Пустых `provider_usage` | С данными |
|---|---:|---:|---:|
| 05.07 – 02.08 | 6400 | **6400 (100%)** | 0 |
| 03.08 | 89 | 72 | 17 |

Внутри 03.08 — две **резкие** границы, а не постепенная деградация:

- **`2026-08-03T06:29:27Z`** — с этой секунды `provider_usage` заполнен в 100% строк (до неё — в 0%).
- **`2026-08-03T07:02:20Z`** — с этой секунды появляется ключ `codex` (между 06:29 и 07:02 писался только `anthropic`).

### Что это отсекает

- **Гипотеза «переезд сломал» — ИНВЕРТИРОВАНА.** Переезд на VPS не сломал запись, а **запустил** её.
  До переезда пусто было всё, после — заполнено всё. Вторая граница 07:02 — это момент,
  когда на VPS заработал Codex CLI (`_fetch_codex_usage` спавнит `CODEX_BIN app-server`).
- **Гипотеза «схема без колонки»** объясняет только строки до 18.07: `ALTER TABLE ... ADD COLUMN
  provider_usage DEFAULT '{}'` задним числом проставил `'{}'` всем старым строкам.
- **Гипотеза «код не умел»** — неверна для 18.07–02.08: writer лежит в репо с 18.07 (`5d72eb2`).
  Остаётся единственное объяснение этого окна: **живой процесс на ноуте крутил старый модуль в
  памяти** (Python-код подхватывается только рестартом, а рестарт рвёт ходы агентов — его избегали).
- **Гипотеза «`_fetch_codex_usage` падает и глушится»** — не подтвердилась как причина пустоты:
  пустым был весь `provider_usage`, включая `anthropic`, а не только codex.

### Codex на исчерпанных лимитах пишется штатно

Проверено на живом стенде (лимиты выбраны прямо сейчас): `utilization: 100`,
`resets_at: 2026-08-08T05:53:45Z`. **«Лимит выбран» ≠ «нет данных»** — 100% это ответ провайдера.

## Почему июль невосстановим

Проверил все хранилища, а не одно:

| Где | Что там | Годится? |
|---|---|---|
| `usage_snapshots.provider_usage` | `'{}'` во всех июльских строках | нет |
| `usage_snapshots.five_hour_pct/seven_day_pct` | выделенные колонки **только под anthropic** by design | нет |
| `turn_usage.quota_primary_pct` | таблица начинается с августа, 29 строк, все `runtime=claude`, `quota_primary_pct` пуст | нет |
| `data/usage_cache.json` | 2 КБ, только последнее значение, codex отсутствует | нет |
| journald 20.07–01.08 | 0 совпадений по `codex.*utilization\|rateLimits` | нет |

API провайдера отдаёт только текущее заполнение скользящего окна, историю — нет.

## Что починено в коде

Диагноз показал, что текущий writer работает. Но по дороге нашёлся отдельный дефект,
из-за которого график **врал** бы при каждом молчании провайдера.

Было: `snapshot_codex = codex_data or _codex_usage_cache.get("data")` — молчащий провайдер
получал в снимок **последнее известное значение с новым временем**. На графике это ровная
линия там, где данных не было.

Доказано дифференциально (тот же сценарий на до-фиксовом коде):

```
СТАРОЕ ПОВЕДЕНИЕ при молчащем Codex:
  08:08:41  codex=[('primary', 100)]     ← настоящий ответ
  08:08:41  codex=[('primary', 100)]     ← ВЫДУМАНО: Codex молчал, взято из кеша
```

Стало — три различимых состояния:

| Состояние | Как выглядит в `provider_usage` |
|---|---|
| не настроен (нет токена / нет бинарника) | ключа нет вовсе |
| спросили, не ответил | `{"windows": [], "status": "unavailable", "error": "RuntimeError: ..."}` |
| ответил | `windows` с числами (в т.ч. честные 100%) |

Живой прогон после фикса:

```
08:08:17.495  anthropic status=ok  [(5h,5.0),(7d,42.0)]   codex status=ok  [(primary,100)]
08:08:17.839  anthropic status=ok  [(5h,5.0),(7d,42.0)]   codex status=unavailable  windows=[]
              err=RuntimeError: Codex app-server initialization failed: limit
```

## Осталось нерешённым (не трогал сознательно)

- **График соединяет точки через разрыв.** `_renderSparklines` рисует `polyline` по всем точкам
  подряд, поэтому пропуск в сутки превращается в прямую линию между соседними замерами.
  Метка `status=unavailable` теперь в данных есть, но чтобы разорвать линию, нужен
  `app/static/js/app.js`/`usage.js` — спорный файл, вне границ задачи.
- **`codex_spark` при недоступности codex исчезает без метки** — он производный от того же
  запроса, отдельного «спросили» у него нет.
- **Выделенные колонки `five_hour_pct` при молчании anthropic пишут 0.** Это легаси-фолбэк
  только для строк до 18.07: `_usage_providers_from_row` сперва читает `provider_usage` и
  возвращает его, если он непустой. Чинить «по-настоящему» = делать колонки nullable = миграция.
