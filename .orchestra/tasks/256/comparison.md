| **Plain Markdown+Git class** [G1–G3] | Human-edited files; Git content-addressed blobs/trees/commits are snapshots and history. | No native tiers. Directory/index files can be hot by convention; all content remains cold files. | Edit → review → commit/merge. Hooks/CI can validate structure. | Git versions bytes, not facts. Supersession, TTL, contradiction and “current” selection are entirely application conventions. | Commit stores tree, parents, author/committer/time/message; old versions remain addressable. | Working tree reads own write immediately; other branches/readers see it after ref update/pull. `update-ref <new> <old>` supplies CAS, but no derived-search freshness. | Native path/history search; any FTS/vector index is external and must track HEAD. | Exact path/grep/log; semantic query is external. | Repository boundary is strong; sharing is explicit via remote/branch. | No automatic prompt use; caller controls what it reads. | Content hashes dedup bytes, not claims. | **Letta MemFS: Git-backed Markdown tiering** [L1–L3] | Per-agent Git repository of Markdown with descriptions/frontmatter. | `system/` content is always in prompt; the complete file tree is always visible; non-system contents are fetched on demand. | Agent/reflection edits files, commits and pushes; memory subagents use worktrees. Current reflection prompt says read the landscape, update an existing topic, create only when genuinely distinct. | Prompt says latest evidence wins, fix stale source, archive retired context in `ARCHIVE.md`; no typed fact identity, valid-time schema or deterministic contradiction executor. | Git version history and file path; no required per-claim evidence reference in inspected MemFS schema. | Local edits are not saved memory until commit/push; other projections update after sync. No semantic index by default. | File search by default; optional keyword/semantic/hybrid mod. Startup sync creates/deletes entries from paths. | Always-visible names/descriptions form query/discovery signposts; contents read via file tools. | One MemFS per agent; separate shared-memory feature. | Explicit tiering: small `system/`, tree/description hot, full external memory cold. | A prompt-driven memory doctor says one canonical location and no duplicates; a file created under a new path still exists until later defrag. | None measured in inspected current MemFS docs for exact/current/rejected recall or task success. | Enforcement is still model behavior; file tree grows; prompt can archive the wrong fact; no status-aware search; sync latency/conflicts; per-agent store does not directly solve project-shared truth. | Inject a compact topic registry/tree at cold entry and require “read adjacent topic before write”; keep verbose evidence cold. Do not rely on a reflection model as the only orphan/contradiction guard. |
| **SQLite relational typed-fact ledger + FTS5 class** [S1–S4] | Rows with explicit keys/constraints can be canonical; FTS5 should be a projection of those rows. | Hot current-state view/query; cold event/history/evidence tables. Tiers are schema/application choices. | One transaction can insert evidence/event, close a prior valid interval and update current-view/FTS rows. | Fully explicit if schema provides `fact_key`, status, `valid_from/to`, `refresh_after`, `supersedes_id`; `UNIQUE/CHECK/FK` can reject overlap or orphan evidence. SQLite itself supplies none of those domain rules. | Actor/task/source/commit columns plus append-only event rows; serializable ACID transaction. | Same-connection read-after-commit is immediate; a long-lived read transaction sees its older snapshot until it ends. One writer at a time. | FTS5 external-content tables require application triggers and can become inconsistent; official recovery is full `rebuild`. A content table + FTS rows can instead be updated in one transaction. | SQL exact/current/as-of filters first, FTS second; vector search remains optional derived retrieval. | Mandatory `project_id` in every PK/FK/query; authorization is application code. | Structured fact summaries can be bounded deterministically; evidence excerpts fetched on demand. | Unique `(project,topic,fact_key,version/source)` plus FKs prevent duplicate identities and source-less facts; a topic registry prevents arbitrary files. | SQLite documents ACID/serialization, not agent-memory utility. #256 local audit shows why constraints matter: 41.7% of changed research paths lacked any KB source link under prompt-only enforcement; semantic promotion recall is unmeasured. | Single-writer contention; schema migration; typed rows can become a second truth if Markdown remains independently editable; FTS trigger drift; DB alone is harder to review/port through Git. | Use SQLite as a synchronous **derived current-state/control projection**, not the sole truth. Enforce identity, status and project scope there; reconcile it to Git HEAD. |
| **Microsoft GraphRAG batch graph index** [M1–M4] | Input documents remain source; derived Documents/TextUnits/Entities/Relationships/Claims/Communities are Parquet tables; embeddings go to a vector store. | No hot task state. Query uses completed graph/community/vector artifacts; raw text units remain cold provenance. | Batch indexing: chunk → LLM extract/merge/summarize → community detection/reports → embeddings. | Optional Claims/Covariates have evaluated status/time bounds, but claim extraction is off by default and requires prompt tuning. No general incremental supersession/TTL contract in inspected docs. | TextUnits link derived items to source documents. | Query operates over completed indexes; read-after-write is batch completion, not immediate promotion. | Full configurable pipeline; current repo is in maintenance mode. Major upgrades use migrations or reindex; config init can overwrite prompts/config. | Local search combines graph and raw chunks; global search map-reduces community reports; DRIFT expands follow-up questions. | Dataset/root separation; no project authorization mechanism in the indexing model itself. | Community summaries target global questions but global search is resource-intensive. | Stable document IDs hash text; entities with same title/type are merged. This is extraction dedup, not canonical topic/orphan control. | Paper reports improved comprehensiveness/diversity over naïve RAG for global sensemaking at ~1M tokens; no Orchestra-style update/promotion benchmark. | Expensive LLM indexing; extraction ≈75% of standard indexing cost; summaries can merge contradictions; batch freshness; project now maintenance-only; much machinery for questions Orchestra rarely asks. | Graph/community projection is useful only later for cross-topic/global synthesis. It must not own current-state facts or block immediate lexical/typed retrieval. |
| **Graphiti/Zep temporal graph hybrid** [Z1–Z7] | Raw episodic nodes are non-lossy evidence; entity/fact edges and community/saga summaries are derived graph state. | Episode history + semantic facts + summaries; queries can filter group/type/time; context is bounded results. | `add_memory` enqueues an episode, extracts/resolves entities/facts, assigns temporal metadata and invalidates contradictions; `add_triplet` bypasses extraction for typed writes. | Facts carry `valid_at/invalid_at/expired_at`; old facts are retained. Group processing is sequential. Supersession/invalidation is partly LLM-decided; no safe TTL semantics for project decisions. | Fact edges list episode UUIDs; `get_episode_entities` traces provenance. Current issue #1661 shows `reference_time` stored but dropped by read paths in v0.29.1. | MCP `add_memory` explicitly returns before background processing: no immediate read-after-write guarantee. Recent code has ingest/event-time watermarks for saga summaries. | Hybrid vector/full-text/graph search; incremental episode ingestion; graph DB/index constraints. | Search facts/nodes with group/type/date filters; hybrid ranking and graph traversal. | `group_id` partitions graphs; enforcement still depends on caller/config. | Bounded fact results, but extraction/dedup prompts and graph context can grow. | Entity/fact resolution attempts dedup and contradiction invalidation; direct triplets support typed writes. No canonical topic-file guard. | Zep paper: DMR 94.8% vs MemGPT 93.4%, LongMemEval up to +18.5% and −90% latency vs baselines. Issue #1661: provenance time write-only. | Borrow bitemporal fields, raw episode→fact provenance, group isolation and explicit typed triplet write. Reject graph-first storage and all automatic retirement; supersession needs deterministic same-key checks and explicit authorization. |
| **Wikibase typed statements** [W1–W4] | Entity statements: subject + property/value + qualifiers + references + rank. Full statement nodes coexist with a derived “truthy/best-rank” view. | Hot/default: preferred, else normal statements. Cold: normal history, deprecated claims, qualifiers/references. | Editors/API add a statement, qualifiers, references and rank; multiple values can coexist. | Preferred = current/consensus default; normal = relevant/history; deprecated = erroneous/outdated belief retained and normally hidden. Correct historical facts use start/end qualifiers, not deprecated rank. No automatic TTL. | References are first-class; qualifiers can encode valid intervals/method; revision history is provided by MediaWiki. | Entity edits are authoritative; WDQS/RDF is a separate exported/indexed view and can lag. | Full vs truthy statement representations; best-rank query view. | Query default returns best rank; callers can explicitly request all ranks, qualifiers and references. | Repository/project isolation is not the public Wikidata model; a private Wikibase instance can provide it. | Best-rank projection keeps default output small while history remains queryable. | Stable statement structure and constrained properties; it permits multiple preferred values for disagreement. It does not decide topical file placement. | No cold-agent Orchestra metrics in inspected primary docs. | Rank is coarse and editorial; “preferred” can mean current or consensus; multiple preferred values require consumer handling; query-service lag; schema/ontology governance overhead. | Adopt the distinction **current / historical / rejected / disputed** and keep rejected claims so they are not re-added. Keep valid-time separate from rejection and always attach evidence. |
| **KurrentDB append-only event log + projections** [K1–K4] | Immutable append-only event log/streams are truth; query views are projections/secondary indexes. | Hot materialized/current projection; cold immutable stream; subscription checkpoints track projector position. | Append typed event to a fine-grained stream with expected revision and stable event IDs; projectors update read models. | No in-place update/TTL: append `FactSuperseded`, `FactRejected`, etc., then fold. Domain policy must decide contradictions and valid time. | Complete ordered audit with event type/body/metadata, global and stream positions. | Append returns commit position; caller can wait until an eventually consistent view reaches it. A synchronous projection can be written in the same DB transaction only in an application-owned design, not by generic async subscriptions. | Projections/secondary indexes can rebuild from stream and checkpoint. | Query the current projection; replay/as-of from events; continuous queries/subscriptions update derived views. | Stream ID can include project/topic/fact; auth is application/server policy. | Read model controls returned context; history never needs prompt injection. | Expected revision prevents lost updates; same event IDs + same checks make retries idempotent. Stream design is the orphan/ownership boundary. | Official docs give durability/ordering/idempotency guarantees, not agent-memory task metrics. | At-least-once subscriptions can duplicate/out-of-order delivery; projector lag; event schema evolution/upcasting; projection write amplification; event store is disproportionate infrastructure for one SQLite-hosted project. | Use a small append-only `knowledge_events` table and per-topic revision/CAS inside existing SQLite, not a separate Kurrent deployment. Expose projector generation and make handlers idempotent. |
| **Recommended Orchestra hybrid: Git evidence + typed fact events/current view + existing FTS/vector cold history** [D1] | Canonical: task evidence and typed topic records committed in Git. Derived: SQLite `knowledge_events`, `knowledge_facts_current`, FTS/vector projections keyed to Git HEAD. | Hot: compact generated topic registry + current task state. Warm: typed current/rejected fact summaries. Cold: full topic/task evidence/log chunks. | `kb_promote` must resolve an existing topic, validate evidence, stable `fact_key`, status/time, and explicit supersession; true new topic updates registry+README atomically. Merge projects changed facts synchronously; embedding stays async. | Statuses `current/historical/rejected/disputed/stale`; valid-time is separate. Same-key overlapping change requires explicit `supersedes`; TTL is `refresh_after` warning, never deletion. Semantic similarity may suggest a topic but may not retire a fact. | Required fact ID, task path/anchor, blob+commit SHA, measurement/URL refs, actor/session/task and event history. Search returns all of them. | Search compares projection HEAD to repo HEAD. Same merge response can read new fact from synchronous FTS projection; on projector failure it reads changed canonical topic directly and reports stale watermark. | FTS typed projection sync; existing embeddings/log backfill async with `target_head/indexed_head` and debt. Rebuild from Git and events is deterministic. | Resolve intent/mode (`current`, `rejected`, `as_of`, `all`) and topic aliases first; exact symbols/typed facts before existing hybrid fallback. Existing RRF/weights/pool remain untouched. | Mandatory server-side `project_id`; cross-project requires separate authorization, not a Boolean supplied by the model. | Default result = claim + status/time + one provenance line; raw evidence only on demand. Registry stays one line/topic; no full biography. | Unique topic slug and fact key; registry is generated/validated; new files outside registry fail delivery check; idempotency key prevents duplicate promotion; orphan audit is a merge gate. | Not yet measured. Gate is the frozen #256 holdout plus synthetic promotion/supersession suite in `metrics.md`; baseline is in `eval/*.raw.json`. | Added schema/projector complexity; Git↔SQLite cannot be one physical transaction; false typed identity can retain a stale fact; sync work on merge must stay bounded. | This is the minimum combination that covers all named metrics while preserving current evidence, audit, offline operation and bounded prompts. |
