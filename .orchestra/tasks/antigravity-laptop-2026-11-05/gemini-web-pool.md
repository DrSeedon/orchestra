# Gemini Web account pool — 2026-11-05

Источник: прямое поручение пользователя в текущем треде и два уточнения во время
реализации. Без commit/push/смены ветки. Разрешены импорт трёх Google-аккаунтов
через SSH stdin, синхронизация файлов и restart только orchestra.service.

## Принятые уточнения

- Распределять новые GeminiWebClient по аккаунтам; внутри чата сохранять аккаунт.
  Менять его только после отказа; после успешного failover оставаться на новом.
- Выбирать Google-пользователя путём /u/N/ для init и всех Gemini RPC.
  Проверять principal против разрешённого пула, чужие аккаунты отклонять.
- Проверить все четыре модели, три аккаунта, большой запрос около 110 KB,
  seedon-orchestrator и gemini-web-check-1793881789 на VPS.

## Найденные ошибки

- Пользователь сообщил воспроизводимый identity mismatch на двух боевых сессиях:
  прежний authuser=email мог оставлять выбранным дефолтный Google principal.
  До исправления helper скрывал причину за общим сообщением helper failed.
- Первая реализация round-robin на каждый запрос изменена до развёртывания:
  пользователь уточнил требование sticky-привязки.

Результаты проверок будут дописаны после фактических прогонов. Куки, ключи,
сырые ответы провайдера и полные адреса аккаунтов в артефакты не включаются.

аккаунта Opera: the…ool@gmail.com (0), max…0as@gmail.com (1), kat….ks@gmail.com (3).

## Итог реализации и проверок

- `app/gemini_web_auth.py`: старый одиночный формат сохранён; добавлен непустой
  пул с проверкой уникальных email и неотрицательного целого authuser_index,
  `read_accounts()`, маскирование credential всех аккаунтов.
- `app/harness/gemini_web.py`: новые инстансы распределяются счётчиком по пулу;
  аккаунт закрепляется по email. Повторные запросы и retarget модели сохраняют
  аккаунт. Только отказ запускает ограниченный перебор пула; успешный failover
  закрепляет нового владельца. Abort/cancel не запускают следующий аккаунт.
- `app/harness/gemini_web_worker.py`: /u/N/ применяется к init и всем Gemini RPC,
  допускаются только владельцы из разрешённого пула. Фактический principal
  возвращается клиенту для сохранения sticky-привязки. В журнал идут только
  разрешённые имена классов ошибок и фиксированные коды, без vendor-текста.
  Реальные точки входа существующего адаптера — stream и _request; методов
  chat и _run_helper у него нет, лишние обёртки не добавлялись.
