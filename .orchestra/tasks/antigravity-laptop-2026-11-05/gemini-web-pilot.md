# Gemini Web: изолированный пилот — 2026-11-05

Источник: после исследования Максим попросил попробовать на Orchestra/VPS
или сначала на ноутбуке. Выбран ноутбук: на нём уже выполнен Google-вход.
Цель — подтвердить доступ к Argon в веб-каталоге и один реальный ответ.
Боевая Orchestra и её сервисы на этом этапе не меняются.

## Подготовка

- Ресурсы хаба перед единственным браузером: около 82 ГБ available,
  cgroup memory.current ~15.2 ГБ из 52.8 ГБ, pids 453/4096.
- T3 preview успешно открыл Gemini, но профиль оказался неавторизованным.
  Вкладка закрыта; дополнительный браузер не оставлен.
- На ноутбуке найдены только метаданные двух нужных Google cookies в Opera:
  `__Secure-1PSID` и `__Secure-1PSIDTS`, зашифрованные v11, HttpOnly.
  Значения не выводились и в файлы не копировались. В Chrome этих cookies нет.
- Совпадение Google-аккаунта ещё нужно проверить перед генерацией: метаданные
  синхронизации профиля Opera не подтверждают владельца Google-сессии.

## Клиент и границы хранения

Выбран `gemini-webapi==2.1.1` из PyPI; SHA-256 wheel:
`9192455580ad3eb0c6c0600df5962cc3bd40d9e311150c3f043c8a376e69680e`.
Wheel прочитан и проверен перед использованием, основные ветви init/close
и загрузки сессии изучены.

Обнаружено важное несовпадение с правилами пользователя: библиотека по
умолчанию сохраняет cookies при close(), даже если auto_refresh выключен,
и включает значение cookie в имя кэш-файла. В пилоте такие записи необходимо
отключить в памяти процесса до первой авторизации; вывод библиотеки также
не должен раскрывать credential. Установленные файлы библиотеки не патчатся.

На ноутбуке создаётся отдельное окружение
`~/.local/share/orchestra-gemini-web-pilot/.venv`; зависимости скачиваются
одним потоком. Это окружение не является venv боевой Orchestra.
Credential из Opera допускается использовать только в RAM, без экспорта
базы браузера и без передачи значений через аргументы процессов.

Первый запуск пилота остановлен на чтении сессии в RAM с `ValueError`,
до открытия SSH и до обращения к Gemini. Единственная найденная в Secret
Service запись `Chromium Safe Storage` не дала успешно расшифровать cookie.
Проверяется, использует ли Opera другой backend хранилища (KWallet).
Cookie-кэш библиотеки к этому моменту не создавался.

Проверка двух Safe Storage записей в Secret Service не дала корректной
расшифровки. Найден правильный backend: уже открытый KWallet,
`Chromium Keys / Chromium Safe Storage`. Для этой записи PKCS#7 и SHA-256
домена в cookie v24 проверены успешно. Значения ключей/cookies не выводились.
Пилот переключён на чтение только этой записи KWallet, с собственным app id;
после чтения закрывается только его handle, а не пользовательский кошелёк.

Первый веб-init успешен: account status `AVAILABLE`, каталог показывает
Flash-Lite 3.5, Flash 3.8, Pro 3.1 и Argon 4 как available. Однако проверка
principal по `oPEP7c` не совпала с аккаунтом, использованным ранее в agy.
Запрос модели не отправлялся. Проверяется, является ли поле email и какая
именно веб-сессия выбрана, прежде чем делать canary.

Дополнительная проверка подтверждает, что principal действительно email,
но это другой аккаунт: маскированная подсказка `the…ool@gmail.com`.
В agy ранее использовался аккаунт, начинающийся на `maxim2000as`.
Каталог этой веб-сессии возвращает доступный `gemini-argon / 4 Argon`.
Генерация остановлена проверкой владельца до отправки запроса модели.
Через request_user_input_async запрошен выбор: подтвердить принадлежность
активного веб-аккаунта и разрешить один canary либо использовать только
прежний agy-аккаунт. Ответ обязателен для зависимой части пилота.

Ответ Максима: использовать только прежний аккаунт agy. В пилот добавлен
явный Google `authuser` для init и последующих запросов, при сохранении
обязательной проверки точного principal перед генерацией. Другой аккаунт
не разрешён для canary; на нём запросов модели не выполнялось.

Проверка с явным authuser успешна: principal совпал с разрешённым аккаунтом,
status `AVAILABLE`, каталог показывает `gemini-argon / 4 Argon`. Один
временный чат с явно выбранным объектом Argon вернул ровно `OK` за 6.069 с.
Клиент ModelOutput не содержит фактической атрибуции модели ответа, поэтому
подтверждены выбор Argon по каталогу и работа запроса, но независимая
проверка response details ещё не выполнена. Туннель закрыт в finally.

## Одноразовая проверка на VPS

После успешного локального запроса установлен отдельный venv
`/home/kesha/orchestra/data/gemini-web-pilot/.venv`, `gemini-webapi==2.1.1`.
Процесс не использует venv/DB боевой Orchestra и не запускает её сервис.
Две нужные cookie переданы с ноутбука по SSH stdin непосредственно в RAM
принимающего процесса. Файлы cookie/ключей на VPS не создавались.

VPS напрямую выполнил init, подтвердил точный разрешённый principal,
получил веб-каталог с `gemini-argon / 4 Argon` и ответ `OK` за 11.319 с.
Exit 0. Временный чат, автокэш и cookie refresh отключены; HTTP-сессия закрыта.
Ограничение атрибуции модели то же: ModelOutput не содержит actual model id.
Подтверждён работающий веб-путь с явно выбранным Argon, а не измерение весов
модели по независимому серверному атрибуту.

Безопасный результат без credential сохранён рядом:
`gemini-web-vps-result.json`; на VPS — в data/gemini-web-pilot/server-result.json.
Это одноразовый пилот: постоянный провайдер Gemini Web в Orchestra не добавлен,
самостоятельное обновление авторизации сервера не настроено. Production
orchestra.service и telegram-bot-api не перезапускались.
