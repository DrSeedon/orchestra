## 1. Часть 2 уже закрыта — и это надо было проверить до правки

Правило проекта «находка протухает между пакетами» сработало ровно здесь. Хронология:

То есть фикс маски приехал через час после репорта, репорт с ним никто не связал, и он пролежал
двое суток. `4b722ba` в main (`git merge-base --is-ancestor` подтверждает).

Проверка живьём, а не чтением. Репозиторий, созданный чужим пользователем (root), `main` на месте:

```
resolve_base_branch(repo, "")        → RuntimeError: cannot inspect branch 'main':
                                       fatal: detected dubious ownership in repository at '…'
branch_wip_status(repo, base_ref="") → то же самое
branch_wip_status(repo, "main")      → то же самое
```

Настоящий текст git доезжает: `_inspect_branch_ref` (`app/workspace.py:178`) различает
`show-ref` rc=1 (ветки правда нет) и любой другой rc (ошибка git) и во втором случае бросает
`RuntimeError` с текстом git. Дальше `/api/sessions/{name}/wip` кладёт `str(e)` в `error`, а

(`workspace.py:345`) теперь достижима только когда ветки действительно нет.

**Свежих масок этого класса в `app/` не осталось** — в `workspace.py` и `merge_operations.py`

## 2. Часть 1 — три дефекта, а не один

### 2.1. `chown` не покрывает `.git` целевого репозитория (главный)

`migrate_git` создаёт worktree по SSH **под root** и передаёт сервисному юзеру только
`{new_wt}` и каталог `worktrees/<slug>` (`give_to_service_user`, добавлено в `4b722ba`).
Всё, что git при этом пишет в `.git` ОСНОВНОГО репозитория цели, остаётся за root.

Модель реальной миграции (целевой репозиторий принадлежит сервисному юзеру `kesha`, ветка
воркера приезжает бандлом, worktree создаёт root) — **17 root-записей**:

```
.git/worktrees/, .git/worktrees/vanilla-frontend/{HEAD,index,gitdir,commondir,ORIG_HEAD,logs/HEAD}
.git/refs/heads/adhoc-913188/…            .git/logs/refs/heads/adhoc-913188/…
.git/objects/pack/pack-….{pack,idx,rev}   .git/FETCH_HEAD
```

Репорт называл 14 и не упоминал `objects/pack/*` — а там лежат коммиты воркера.

**Почему сегодняшний `chown` не спасает — замерено, а не выведено.** После `chown -R` на
worktree (чужих файлов 0 из 0) git из-под сервисного юзера ВСЁ РАВНО отказывается:

```
$ git status --porcelain          # внутри полностью chown-нутого worktree
fatal: detected dubious ownership in repository at '/tmp/repro55/wts/vanilla-frontend'
```

Для связанного worktree git проверяет владельца ещё и gitdir — `.git/worktrees/<name>`, а он
root'овый. Симптом из репорта воспроизводится ПОСЛЕ фикса `4b722ba` слово в слово.

**Второй, более тихий отказ.** Добавляем `chown` на `.git/worktrees` — `status` оживает,
но коммит падает:

```
$ git commit -qm probe2
fatal: cannot lock ref 'HEAD': Unable to create
  '…/.git/refs/heads/adhoc-913188/vanilla-frontend.lock': Permission denied
```

Каталог ветки в `refs/heads/` принадлежит root. То есть мигрированный воркер читает, но
**не может закоммитить** — при правиле «ALWAYS commit before reporting DONE» это ловушка хуже
отключённого гейта kill: гейт хотя бы падает громко.

Лечение проверено там же: после `chown` на `.git/worktrees` + `refs`/`logs` `status` и
`commit` из-под сервисного юзера проходят.

### 2.2. Сервисный юзер определяется по владельцу каталога, а не по юниту

`target_service_user` (`scripts/migrate_agent.py:98`) берёт `stat -c %U {to_orchestra}`.
Это догадка, а не факт: **на этом же VPS 3 августа 3021 файл в `/home/kesha/orchestra`
принадлежал root при `User=kesha` в юните** (записано в `CLAUDE.md`). В такой момент скрипт
определил бы сервисного юзера как `root`, честно выполнил бы `chown -R root` и отчитался бы
об успехе — то есть закрепил бы ровно тот дефект, который чинит.

Ground truth — юнит. Проверено на живом хосте: `systemctl show orchestra -p User` → `User=kesha`,
и в юните `User=kesha`. Но здесь ждёт ловушка ровно того класса, что `OOMScoreAdjust`:

```
$ systemctl show orchestra-nope -p User   # юнита не существует
User=
$ echo $?
0
```

Пустой `User=` и **нулевой** код возврата — то же самое, что у существующего юнита без `User=`
(там сервис и правда идёт от root). Отличать обязан `LoadState`:
`systemctl show <unit> -p LoadState` → `loaded` против `not-found`.

### 2.3. Проверка chown слепа: печатает «чисто» и когда проверить не смогла

`give_to_service_user` (`:116-127`) считает чужие файлы так:

```
find {path} ! -user {user} -printf . 2>/dev/null | wc -c
```

Замер трёх случаев:

| путь | вывод |
|---|---|
| несуществующий | `0` |
| существующий, всё своё | `0` |
| существующий, 8 чужих | `8` |

`2>/dev/null` съедает `No such file or directory`, а `wc -c` от пустого ввода даёт `0` —
и функция рапортует «owner … → user», не тронув ничего. Это тот же класс, что `systemctl show`
из п. 2.2: проверка, дающая одинаковый вывод при успехе и провале, — не проверка.

### 2.4. Остаточные маски в самом `migrate_agent.py`

- `:262` `git bundle create … 2>/dev/null || true` и `:266` `git fetch … 2>/dev/null || true` —
  причина потери коммитов воркера выбрасывается. Ниже `die` на `git worktree add` сработает,
  но покажет симптом («ref не найден»), а не причину («бандл не собрался, потому что …»).
  Это ровно та подмена, из-за которой репортёр в части 2 искал несуществующую проблему с веткой.
- `:278` при `dubious ownership` скрипт делает `git config --global --add safe.directory {to_scope}`
  **в gitconfig root'а на целевом хосте** — навсегда, без уборки. Это лечит симптом для root
  и ничего не даёт сервисному юзеру, от имени которого потом работает Orchestra.

## 3. Варианты решения

**A. Оставить работу от root и расширить `chown` (то, что просил оркестратор).**
После переноса передавать сервисному юзеру ещё и `.git` целевого репозитория; сервисного юзера
брать из юнита с гейтом `LoadState=loaded` и фолбэком на `stat -c %U` с громким предупреждением;
проверку владельцев сделать зрячей (не подавлять stderr `find`, отличать «0 чужих» от «не смог
посмотреть»). Снимок владельцев до и сверка после — как требует правило проекта.
Минимально по диффу, ничего в архитектуре не двигает.

**B. Не создавать root-файлов вовсе — выполнять git на цели от имени сервисного юзера**
(`runuser -u <user> -- git …`). Тогда не нужны ни `chown`, ни `safe.directory` в root'овом
gitconfig, и дефект закрывается конструкцией, а не уборкой. Дороже по диффу (переписываются
все удалённые git-вызовы `migrate_git`), плюс требует `runuser`/`sudo` на цели и читаемости
бандла из `/tmp` для сервисного юзера.

Рекомендую **A + одну заплату из B**: чинить `chown`, но убрать автодобавление
`safe.directory` в конфиг root'а, заменив его на явную ошибку с инструкцией. Это выполняет
поручение буквально и не оставляет на чужом хосте вечного побочного эффекта.
Если скажешь «делай B» — она честнее по сути, я просто оцениваю её как отдельную задачу.
