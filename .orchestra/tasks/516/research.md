## 1. Правило спаривания: главная методическая находка

Задание предлагало парность по `ts`. **Наивное чтение этого правила даёт ошибку в 13 раз**,
и это стоит зафиксировать отдельно, потому что цифра выглядит правдоподобно.

В `logs` есть колонка **`tool_use_id`** — точный ключ соединения. Она заполнена
у 77 106 из 102 255 строк `tool` (75 %), появилась 2026-08-11, с 2026-08-16 почти
сплошная (`raw/06-tuid-coverage.txt`). Это ground truth: 75 382 пары.

Проверка четырёх эвристик против ground truth (`scripts/calibrate.py`,
`raw/07-calibration.txt`):

| правило | верный `res_id` | сумма часов (истина 95.86) |
|---|---|---|
| H1 FIFO по всей сессии | **28.2 %** | **138 716** |
| H2 FIFO + окно 60 с | 87.0 % | 83.08 |
| H4 FIFO со сбросом на границе хода | 87.5 % | 100.32 |
| **H3 LIFO** (результат закрывает самый поздний незакрытый вызов) | **96.0 %** | **94.16** |

FIFO по сессии разваливается, потому что строки `tool` без ответа (102 251 против
100 180 `tool_result`) накапливаются в очереди и сдвигают все последующие пары до
конца сессии: худшие случаи дают длительность **22 суток** на вызове, который на
самом деле шёл 0.0 с (`raw/05-rule-agreement.txt`).

**Итоговое правило (дословно, `scripts/build.py`):** пара берётся по `tool_use_id`,
если он непуст и встречается ровно один раз с каждой стороны; все остальные строки
спариваются LIFO внутри `session_id` в порядке `(ts, id)`. Точность LIFO измерена на
размеченной части: 96.0 % верного партнёра, ошибка суммы времени −0.3 %.
Длительность = `ts(tool_result) − ts(tool)`. Отсечка `0 ≤ dur ≤ 600 с` убирает
22 пары из 100 226.

**Дыра с пустым `tool_name` закрыта.** 24 446 строк без имени — это не отдельный
класс вызовов, а строки, записанные **до появления колонок телеметрии**: все они
лежат в 2026-08-03…08-11 плюс хвост 155 строк 08-22 (`raw/01-null-toolname-shape.txt`).
Имя полностью восстанавливается из `content`, где легаси-формат — `Bash: {json}`,
а хвост 08-22 — `file: update <path>` (это `FileChange`). После восстановления
безымянных вызовов не остаётся: 24 200 пар / 26.03 ч разошлись по обычным классам.

**Суммирование длительностей корректно как оценка стенного времени:** объединение
интервалов внутри сессии даёт 115.58 ч против суммы 120.46 ч, перекрытие всего
**4.0 %** (`raw/26-overlap-and-nonbash.txt`).

## 2. Сверка трёх счётов

Оба правила названы дословно и прогнаны на одних данных (`raw/29-reconciliation.txt`).

**Счёт Кеши (47 406 вызовов bash / 78.8 ч) — воспроизведён точно.**
Его правило: `tool_name = 'Bash'` из колонки, **без верхней отсечки**.
Мой прогон того же правила: **47 481 / 79.22 ч** — расхождение 0.16 % по числу и
0.5 % по времени, объясняется ростом живой базы (только за 2026-09-05 добавилось
1 230 вызовов bash / 1.14 ч).

**Счёт оркестратора (96 975 пар / 107.1 ч; Bash 46 562 / 67.8 ч) — по заявленному
правилу не воспроизводится.** Буквальный session-FIFO с отсечкой 600 с даёт для Bash
**37 474 вызова / 875.13 ч**, медиану 21.67 с и «дольше 60 с — 13 314» против его 894.
Промах в 13 раз: значит фактически применялось не глобальное FIFO, а соседское
спаривание. При LIFO получается 47 550 / 74.38 ч. Оставшийся разрыв в 6.6 ч —
не период (при его числе пар моя сумма 117–118 ч, а не 107.1) и не верхняя отсечка
в 600 с: его сумма и среднее ложатся между отсечками 240 с (66.75 ч, среднее 5.06)
и 300 с (69.05 ч, среднее 5.23), то есть эффективный потолок был ≈ 250–270 с, а не 600.

**Что из его выводов устояло и что нет.** Форма распределения подтверждена
независимо: медиана 0.19 с против его 0.2, концентрация топ-1/5/10 %
**32.3 / 68.4 / 83.9 %** против его 33.3 / 68.3 / 84.0. Абсолютные суммы занижены:
с восстановлением легаси-имён и отсечкой 600 с честная цифра —
**62 350 вызовов bash-семейства / 97.64 ч**, а не 46 562 / 67.8 ч.

## 4. Распределение, а не среднее

Среднее по bash-семейству — 5.64 с, медиана — **0.19 с**: среднее завышает в 30 раз.
Работает не «инструменты медленные», а тонкий хвост (`raw/10-bash-distribution.txt`,
62 350 вызовов / 97.64 ч):

```
p50 = 0.19 c   p90 = 11.92 c   p99   = 110.44 c
p75 = 1.32 c   p95 = 26.11 c   p99.9 = 314.12 c

топ-1 %  (623 вызова)  = 31.56 ч = 32.3 % времени bash
топ-5 %  (3 117)       = 66.76 ч = 68.4 %
топ-10 % (6 235)       = 81.96 ч = 83.9 %

дольше 60 с: 1 369 вызовов = 47.91 ч = 49.1 % времени bash
```

**1 369 вызовов из 62 350 (2.2 %) держат 39.8 % всего времени инструментов.**
За тот же период `bg_create` вызван 525 раз — на каждую фоновую задачу приходится
2.6 блокирующих bash-вызова дольше минуты. Тренд положительный: в августе на вызовы
дольше 60 с уходило 50.3 % времени bash, в сентябре — 27.3 % (`raw/30-bg-alternative.txt`).

**Отдельно: 13.4 % всего времени инструментов (3 950 вызовов, 16.19 ч) потрачено на
вызовы, завершившиеся ошибкой** (`raw/28-timeout-errors.txt`).

## 5. Что оказалось неправдой

Проверка ожидавшихся кандидатов дала три отрицательных результата и один
опровергнутый механизм.

- **«Полные прогоны тестов съедают время» — нет.** Полный прогон (без пути к тесту
  и без `-k`) — 419 вызовов / **4.96 ч**, десятая часть класса. Основное время
  (44.50 ч) — **целевые** прогоны отдельных файлов (`raw/23-tests-subclasses.txt`).
- **«Установка зависимостей» — нет.** 89 вызовов / 0.41 ч / 0.34 % за месяц.
- **«git-операции» — нет.** 10 741 вызов / 1.46 ч, p95 = 1.4 с.
- **«Чтение и грепанье больших файлов» — нет.** 22 749 вызовов / 4.06 ч, медиана 0.01 с.
  Вместе с файловыми тулами — 4.83 ч из 120.46 (4.0 %).
- **«`uv run` тормозит старт» — опровергнуто прямым сравнением.** На целевых прогонах
  `uv run` даёт медиану 13.18 с, прямой `.venv/bin/python -m` — **13.30 с**
  (4 400 против 1 527 вызовов). Разницы нет (`raw/23-tests-subclasses.txt`).
- **«Целевой прогон в основном стартует, а не считает» — опровергнуто замером.**
  Пол запуска: `import pytest` 0.24 с, сбор одного файла 0.14 с, полный wall
  одиночного `--collect-only` 1.00 с. При медиане целевого прогона 12.92 с на старт
  приходится <10 % (`raw/24-startup-floor-measured.txt`). Батчинг файлов в один вызов
  экономит ~1 с на вызов, то есть максимум ~1.7 ч из 44.5 ч.

**Самоопровержение по ходу работы.** Первая оценка повторных прогонов дала 8.03 ч
и была бы ложным «сокращаемо». Проверка, была ли между двумя одинаковыми командами
хоть одна правка файла в той же сессии, показала: 6.28 ч приходится на прогоны
**после правки** — это не лишнее, это проверка нового состояния. Без правок повторено
только 227 прогонов на **1.66 ч** (`raw/34-repeat-without-edit.txt`). В таблице стоит
1.66 ч, а не 8.03.

## 6. Чего эта работа не даёт

- **Остаточная ошибка классификации ≈1 %.** 1.17 ч внутри `other` содержат реальный
  запуск pytest, не пойманный из-за вложенного экранирования вида
  `bash -lc "… '"'…'"' …"`, где отслеживание кавычек рассинхронизируется
  (`raw/22-class-table-v4.txt`). Влияет на границу `tests`/`other`, не на выводы.
- **Полка 120 с не всегда видна как ошибка.** Из 170 вызовов на 119.5–121.9 с только
  51 помечены `is_error=1`; остальные приходят как обычный результат с обрезанным
  выводом. То есть убитая команда в логах в большинстве случаев неотличима от
  успешной — это ограничение данных, и оно же самостоятельная находка.
- **Потолок наблюдаемости.** Полные прогоны запускались под `timeout 590`/`580`, поэтому
  истинная длительность полного набора цензурирована сверху. Прямой замер сбора:
  29.56 с только на collection, до первого ассерта.
- **Стоимость не сведена к деньгам и к ходам** — вопрос был про время инструментов.
- **Причина 6.6-часового разрыва со счётом оркестратора установлена как «эффективная
  отсечка ≈250–270 с», но не подтверждена его кодом** — самого скрипта я не видел.

## 7. Если владелец решит чинить (фаза 2, не начата)

Всего сокращаемого — 19.03 ч (15.8 %), 1 307 вызовов, объединение без двойного счёта
(`raw/35-reducible-union.txt`). Порядок по отношению «часы / риск»:

1. **wait-loop → событие** (6.63 ч, риск нулевой): проверка та же, меняется способ
   ожидания. Ничего не перестаёт проверяться.
2. **Потолок bash 120 с** (5.69 ч): сейчас команда, попросившая `timeout 600`,
   убивается на 120 с и время теряется целиком. Либо согласовать потолки, либо
   отправлять такие команды в фон.
3. **`_MERGE_WAIT_SECONDS`** (4.31 ч + 1.82 ч повторов): мерж и так durable, ответ
   «STILL RUNNING» уже нельзя прочитать как отказ. Сокращается блокировка агента,
   не длительность мержа.
4. **Дефолт `timeout=30` в `_api`** (1.52 ч чистой потери): 180 вызовов сгорают в
   таймаут без ответа.

Ни один из четырёх пунктов не трогает то, что защищает правильность: полный прогон
перед мержем (4.96 ч) и целевые прогоны после правок (6.28 ч) остаются как есть.
