## 2. Конкурентность — вот где loop сериализуется

6 параллельных клиентов на `/api/sessions`, одновременно зонд на тривиальный `/api/pipelines`:

```
idle:       /api/pipelines  n=640  p50=3ms    p95=6ms    max=16ms
под нагр.:  /api/pipelines  n=86   p50=185ms  p95=319ms  max=462ms
под нагр.:  /api/sessions   n=494  p50=188ms  p95=331ms  max=447ms
```

3-миллисекундная ручка деградирует в 60 раз. Обработчик `/api/sessions` **держит event loop
целиком**, всё остальное стоит в очереди за ним. Шесть клиентов — синтетика, но достижимая:
несколько вкладок дашборда плюс HTTP-вызовы агентов через MCP идут в тот же loop.

## 3. Атрибуция: GIL-профиль ошибается, брать надо wall-clock

`py-spy --gil` (558 сэмплов) даёт: `get_all_sessions` 21.7 % inclusive, `get_role_icons` 0.
Но **`sqlite3` отпускает GIL на времени выполнения запроса** — GIL-профиль систематически
занижает всё, что блокирует loop через SQLite. Правильный прибор здесь — обычный wall-clock:

```
py-spy record (1983 сэмпла, та же нагрузка):
  обработчик list_sessions ....... 1397 (70 %)
    ├─ get_last_turn_map ......... 1093 (55 % ВСЕГО профиля)   ← настоящий расход
    └─ get_all_sessions ..........  292 (15 %)
  сериализация ответа FastAPI ....  332 (17 %: serialize_response 7 % + encoder 10 %)
```

Прямой замер запросов по read-only копии живой БД (10 прогонов):

```
get_last_turn_map:  p50=15.3ms  (min 13.5, max 22.9)
get_all_sessions :  p50= 1.9ms  (min  1.6, max  6.5)
```

Причина: `get_last_turn_map` — `SELECT ... FROM logs WHERE type='status' AND content LIKE
'turn ended%' GROUP BY session_id`. План — `SCAN logs USING INDEX idx_logs_session`, то есть
СКАН всей таблицы: чтобы применить `LIKE`, SQLite читает `content` каждой строки. В таблице
9 685 строк и **14.4 МБ текста в `content`**, а нужных `type='status'` — 801 (8 %).
Это делается на каждый `/api/sessions`.

## 4. Правка — одна строка

```sql
CREATE INDEX IF NOT EXISTS idx_logs_status ON logs(session_id, ts) WHERE type='status';
```

Замер на копии живой БД, три варианта:

| вариант | запрос p50 | план | вставка 300 строк | размер БД |
|---|---|---|---|---|
| как сейчас | 16.0 мс | `SCAN logs USING INDEX idx_logs_session` | 12 мс | 23.65 МБ |
| `(type, session_id, ts)` | 0.6 мс | `SEARCH ... (type=?)` | 6 мс | 23.65 МБ |
| **частичный `WHERE type='status'`** | **0.6 мс** | `SCAN idx_logs_status` | 6 мс | 23.65 МБ |

Оба варианта дают одинаковый результат запроса (20 строк, идентичны) и одинаковую скорость;
взят частичный — он индексирует только 8 % строк, то есть минимально утяжеляет INSERT в
`logs` (а это самая горячая на запись таблица). Роста файла БД в пределах измеримого нет,
построение индекса — 35 мс, то есть на живой 23-МБ базе `init_db()` при следующем старте
создаст его незаметно. Отдельная миграция не нужна: `CREATE INDEX IF NOT EXISTS` в схеме
покрывает и новые, и существующие БД.

Ожидаемый эффект на `/api/sessions`: −15 мс из 37 мс блокировки loop'а на каждый запрос.

## 5. Что НЕ трогаем и почему

- **`get_role_icons`** — 0 сэмплов в обоих профилях, ручка 3 мс. Причина дешевизны неприятная:
  функция читает 4 файла ролей и **всегда возвращает `{}`**, потому что ни в одном
  `pipelines/*/prompts/roles/*.md` нет YAML-фронтматтера (все начинаются с `<role>`).
  То же касается `role_can_spawn()` — она читает тот же фронтматтер и всегда возвращает
  `None` («без ограничений»). Это вопрос корректности, а не производительности; в рамках #21
  не менял, выношу оркестратору.
- **`get_all_sessions` на event loop** — 1.9 мс. Выносить в тред ради 1.9 мс = усложнение
  без выигрыша: даже полное её устранение оставит 35 из 37 мс.
- **Сериализация ответа (17 %)** — 51 КБ JSON на каждый `/api/sessions`. Тоже на loop'е, но
  это уже про объём ответа, а не про блокирующий I/O; отдельная задача, если понадобится.

## 6. Жалоба юзера «дашборд долго грузит» (00:19) — сервер тут ни при чём

Проверил оба пути к дашборду за ночь:

```
журнал orchestra, 03.08 22:22 → 04.08 05:14:   0 строк вообще (последняя активность 19:27)
nginx access.log, 04.08 00:00–04:59:           45 строк, ВСЕ — сканеры интернета
   (15× 404 "GET /", RDP-пробы mstshash, /.git/config, /druid/index.html, /manager/html)
```

Ни одного запроса дашборда ни на nginx, ни в приложение. То есть в момент жалобы браузер
юзера **не отправлял на сервер ничего** — ни поллинга, ни SSE, ни heartbeat (`_heartbeatProbe`
бьёт раз в 3 с, его тоже нет). Серверная медленность не может быть причиной этой жалобы;
симптом клиентский — мёртвая вкладка, которая перестала опрашивать и показывает старое.
Это ровно территория #32 (frontend, «старые сообщения вместо новых»).
