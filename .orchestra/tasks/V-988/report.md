# V-988 — prompt cache OpenAI и Orchestra

Дата проверки: 21.10.2026. Только чтение и исследование; платных запросов не делал.

## Вывод

В официальной документации подтверждено изменение от 20 октября: для GPT-5.6 и новее в **OpenAI Responses API** можно запросить минимум 12 часов жизни кеша через `prompt_cache_options.ttl: "12h"`. Это не настройка ChatGPT Plus/Codex CLI. В документах о входе через ChatGPT и Codex app-server указано, что приложение само формирует запросы, не принимает произвольные параметры Responses API, а `prompt_cache_retention` среди них прямо запрещён. Официального подтверждения утверждения «кеш Codex и Work хранится бесконечно» в проверенных источниках не нашёл; более того, руководство API говорит, что кеш не бессрочен.

Для Orchestra сейчас значимо только приближение TTL в общих индикаторах Codex: оно выставлено в 30 минут. Оно не запускает компактизацию и не определяет остановку воркеров. V-979 относится к OpenRouter и к Codex не применяется. Учёт стоимости Codex уже использует сообщённое runtime число cache-read токенов; он не задаёт срок их хранения. В OpenRouter harness параметр 12h напрямую не включить: он шлёт Chat Completions в OpenRouter, а новый TTL документирован для Responses API. Перенос туда означал бы отдельный API/runtime и стоимость платных API вызовов; этот вариант здесь не предлагается.

## 1. Что выпустил OpenAI

Первичный источник — [API changelog](https://developers.openai.com/api/docs/changelog): запись **20 октября 2026**, тип Feature, продукт **`v1/responses`**. В ней говорится, что можно выбрать кеширование на 12 часов; запись кеша тарифицируется по 2,5× обычной цены input.

[Руководство Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) уточняет параметры и область:

- Для **GPT-5.6 и новее** используется `prompt_cache_options.ttl`; допустимы `"30m"` (по умолчанию) и `"12h"`. На Responses API срок 12h — минимальная гарантия доступности для чтения, а не крайний срок удаления. OpenAI может держать записи дольше, но руководство прямо указывает: кеш не хранится бессрочно.
- Для 12h запись стоит **2,5× uncached input**, для 30m — **1,25×**. Это полная ставка записи, не добавка сверх обычной цены. Чтение стоит те же **0,1×** на большинстве моделей этого поколения, **0,05× у GPT-6.1 Sol**. Поэтому 12h имеет смысл только для стабильного префикса, который будет повторно прочитан; при переходе с действующей 30m записи на 12h повторно записываемые токены оплачиваются по ставке 12h без зачёта прежней записи. Запрос может смешивать 30m и 12h breakpoint’ы.
- У предыдущих поколений другой параметр — `prompt_cache_retention`, обычно `"in_memory"` или `"24h"` в зависимости от модели. Это не новый 12h параметр и не эквивалент бессрочного хранения. Список моделей для extended retention в руководстве: GPT-5.5/5.5 Pro, GPT-5.4, GPT-5.2, ряд GPT-5.1/Codex, GPT-5, GPT-5 Codex и GPT-4.1. Для GPT-5.6+ это уже `prompt_cache_options.ttl`.
- Changelog указывает API-функцию, не план ChatGPT. Он не обещает доступность настройки на Plus. [Ограничения Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) применяют требования также к Codex app-server: сервер сам делает HTTP/SSE Responses-запросы, «не принимает произвольные Responses параметры», а `prompt_cache_retention` перечислен как неподдерживаемое поле. Следовательно, для нашего Codex CLI/app-server под ChatGPT Plus **включить 12h настройкой Orchestra нельзя** по опубликованному контракту. Не исключено, что OpenAI меняет внутреннюю политику кеша сервиса независимо от клиента, но официального подтверждения этому не найдено.

Проверил официальный API changelog, Prompt caching guide, Sign in with ChatGPT preview limitations и ChatGPT/Codex changelog. Последний не содержит сообщения о бессрочном prompt cache для Codex/Work на дату проверки. Это граница найденной документации, а не доказательство отсутствия любых скрытых rollout’ов.

## 2. Что видно в `turn_usage`

Read-only источник: `/home/kesha/orchestra/data/orchestra.db`, подключён как `sqlite3 -readonly 'file:/home/kesha/orchestra/data/orchestra.db?mode=ro'`. Таблица содержит **28 743** строк всего; временное покрытие — **2026-08-03 06:33:39 UTC — 2026-10-21 07:46:02 UTC**. Для Codex было **7 965** строк с моделями `gpt-*`; одна запись runtime=`codex` помечена моделью Claude и исключена из сравнения. Все расчёты — агрегаты, базу не менял.

Единица анализа — **первый записанный ход в рамках того же `session_id` после промежутка между соседними ходами не меньше часа**. В группу `1–12 ч` включены промежутки `>=1 h` и `<=12 h`, в `>12 ч` — строго больше 12 h. Сессии без предыдущего наблюдаемого хода исключены: их idle-gap неизвестен. Период «до» заканчивается 19 октября UTC; «после» начинается 20 октября 00:00 UTC — дата официального changelog. Для каждого хода cache-read share = `cache_read_tokens / input_tokens`: Codex сообщает input как полное число токенов, cache-read — его подмножество (так же ограничивает cached часть расчёт стоимости в `app/backend_codex.py`). Средний share — среднее по ходам; взвешенный — отношение сумм токенов.

Пост-изменение видимый период заканчивается 21 октября 07:46 UTC — менее двух дней; в нём всего 15 наблюдений после gap. В них перемешаны `gpt-6-luna` (4 и 7 ходов) и `gpt-6.1-sol` (2 и 2); до даты гораздо больше старых моделей и много больше наблюдений. Поэтому видимых скачков в доле cache-read после 12 часов нет, но выборка не позволяет проверить новый rollout или отделить его от смены модели/сессии/совпадения префикса. Кроме того, заявленный API TTL не относится к этому Codex-пути. Этот датасет **не различает** старое поведение и внутреннее бессрочное удержание, если оно действительно включено.

## 3. Последствия для Orchestra

| Область | Текущее поведение и отношение к новости |
|---|---|
| Cache warmth | V-979 (`app/static/js/app.js::_cacheWarmthHtml`) показывает только успешные ходы **OpenRouter harness**, с 10m sticky-routing границей и эмпирическим 10–30m окном; это не TTL-гарантия и не Codex-виджет. Его не менять по новости. Отдельно, общий cache pill и аналитика берут `PROVIDER_METADATA.codex.cache_ttl_seconds = 1800`, approximate=true (`app/models.py`), и показывают приблизительный 30m reference window; аналитика использует его для маркировки cold-start. Это единственное предположение о сроке Codex. Не переписывать его на «бессрочно» без официального подтверждения поведения ChatGPT-auth Codex. |
| Cost accounting | `app/backend_codex.py::_codex_cost` считает API-equivalent цену на основе полного input, фактических cache-read/write токенов и опубликованных цен; срок cache entry в формулу не входит. Для подписки это виртуальная API-equivalent оценка, не списание Plus. Новых фактических полей в Codex turn usage нет, правило менять не требуется. Если когда-либо появится прямой Responses API путь, нужно отдельно учесть повышенную ставку 12h write, а не переносить старую стоимость записи автоматически. |
| Compaction / kill workers | `compact_worker` — ручная операция; Codex компактизацию делает нативно. Автоматическая компактизация основана на контекстном пороге/окне и расписании, kill — на lifecycle gate и состоянии незакоммиченной работы; TTL prompt-cache в этих решениях не участвует. Хранение prefix не увеличивает контекстное окно и не возвращает отброшенную компактизацией историю. Действия не менять. |
| OpenRouter harness | `app/harness/llm.py` отправляет `POST {base_url}/chat/completions`, по умолчанию OpenRouter. Модели/провайдеры выбираются из каталога OpenRouter/локальных моделей. `prompt_cache_options.ttl` 12h описан OpenAI для Responses API GPT-5.6+, не для этого OpenRouter Chat Completions пути. Универсально добавить параметр сюда нельзя; сначала потребовался бы отдельный прямой OpenAI Responses runtime с поддержкой stream, tool-loop, учёта и биллинга. Такая смена добавила бы отдельный платный API расход, пока не разрешённый; текущий harness использует маршруты `:free` и разрешённый allowlist платных harness-маршрутов. |

## 4. Вердикт и цена переноса

| Элемент | Вердикт | Цена переноса |
|---|---|---|
| Подписочный Codex cache для Plus / CLI / app-server | **Не брать / сейчас не включать** | Прямого параметра для клиента нет по опубликованному контракту. Переключение на API обошло бы подписочный маршрут и создало бы отдельный платный API расход. |
| V-979 индикатор OpenRouter | **Уже корректно отделён** | 0: его 10/30m эвристика явно только OpenRouter, не Codex. |
| Общий Codex cache pill и 30m TTL в аналитике | **Оставить приближённым, не объявлять вечным** | Сейчас 0. При подтверждённой смене Codex service policy надо было бы изменить UI/аналитику и правила cold-start, но не compaction/worker-kill. Неизвестный точный новый TTL мешает корректному числу. |
| Cost accounting | **Уже учитывает cache-read фактически; менять нечего** | 0 для подписки. Для будущего Responses API маршрута — отдельная схема цены: write 2.5× для 12h, чтение модель-зависимое, новый API бюджет. |
| Compaction / worker kill | **Уже не зависит от prompt cache TTL** | 0. Увеличенное хранение кеша не заменяет живой контекст. |
| OpenRouter harness 12h API retention | **Не брать в текущий harness** | Существенная смена endpoint/runtime с OpenRouter Chat Completions на прямой OpenAI Responses; появляется отдельный оплачиваемый API-класс, цена записи 2.5× input за 12h, и работа по адаптации streaming/tool calls/учёта. Разрешения на такой расход нет. |
