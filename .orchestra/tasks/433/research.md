# #433 — provenance of `logs.type='user_message'`

## Question

- Context: Orchestra stores every input delivered to an agent as `logs.type='user_message'`; dashboard, TG mirror, RAG and runtime-history consumers currently infer authorship from `content`.
- Change under test: persist a finite origin category at delivery time and render/classify by that field; use text-prefix parsing only in a one-time history migration.
- Baseline: `chat.js` treats every non-`[from:...]` input as the user (and hides platform notes); `rag.py` independently repeats the same prefix inference.
- Measurable outcome: on the frozen live cohort `ts >= 2026-08-25`, `id <= 562928`, exactly 940/2738 rows are `user`; every `user_message` has an explicit finite origin; new production ingress cannot omit provenance; no runtime consumer parses provenance from text.

## Hypotheses considered

1. **H1: every live ingress knows enough context to assign provenance before the immutable log insert.**
   - Falsifier: a production caller reaches `AgentSession.send` with neither a trusted entry-path category nor a sender/job/platform identity.
   - Result: supported, with one structural edge: mailbox delivery can combine several agents into one provider input, so category plus a scalar sender cannot preserve “who exactly”; the provenance detail must support a sender list.
2. **H2: adding a default at `db.add_log` is enough to close writer completeness.**
   - Falsifier: a `user_message` insert bypasses `add_log`, or a known caller silently receives the default.
   - Result: refuted. `initial_deliveries.py` and `message_deliveries.py` issue direct SQL inserts, and 29 production `send` call sites carry several different origins.
3. **H3: one finite category field is sufficient for the UI contract.**
   - Falsifier: the UI must display the exact agent/job while the category remains one of a finite set.
   - Result: refuted by task requirement 5 (“с подписью кто именно”) and `chat.js:3917-3933`, which displays the exact agent name. The faithful minimum is a finite `origin` plus a non-empty sender list/source descriptor (or one structured object containing both).
4. **Alternative: retain runtime prefix parsing as a compatibility fallback.**
   - Falsifier: an explicit `unknown` can safely render left while an offline migration handles old prefixes.
   - Result: refuted as necessary. A fallback parser recreates the second owner prohibited by the task; missing/new values can fail safe as `unknown`, never as `user`.

## Findings

### F1 — the stated 2738-row baseline is reproducible, but the frozen boundary is part of the claim

The task's snapshot is exactly reproduced by the insertion-snapshot boundary `id <= 562928` and event-time lower bound `ts >= '2026-08-25'`:

```text
agent       1136
background   481
unknown      181
user         940
total       2738
```

Command shape: read-only SQLite transaction over `data/orchestra.db`; classify `[from:` as agent, `[Background job` as background, `[HH:MM]`/`[from TG:` as user, remainder as the 181-row audit set. `id` is used only to freeze the insertion snapshot, not to order events; event ordering remains by `ts` [1].

**Confidence: CONFIRMED** — direct live-DB measurement reproduces all four task-card counts exactly (evidence tier 1). The 24% figure itself is accepted task input; reconstructing its N-boundary is not a new independent prevalence estimate.

### F2 — the 181 “unknown” rows split into five real origins plus 12 genuinely unknown test artifacts

| Frozen class | Rows | Canonical origin | Evidence |
|---|---:|---|---|

| `BUG REPORT платформы:` notices | 10 | `platform` | `notify.notify_bug_report` authors the text |

| `[Cron job fired]` | 2 | `background_task` | `bg_jobs._fire_cron` |

Roll-up: `agent=68`, `background_task=2`, `platform=41`, `system=58`, `unknown=12`; sum = 181. With the already recognized prefixes the frozen post-migration distribution is therefore `user=940`, `agent=1204`, `background_task=483`, `platform=41`, `system=58`, `unknown=12`.

Three additional known producers contribute zero frozen rows: `[system wake:...] = 0`, `[Cron command matched] = 0`, and `dashboard_voice_transcriptions` contains 0 rows. They still require explicit origins for future writes: system/background_task/user respectively.

`InitialDeliveryRequest.sender` is caller-supplied and `initial_deliveries` stores no authenticated `source_principal`. The 67-row `agent` classification is operational rather than a security-principal proof: all 67 sender values match live session names in the same scope, and repository search finds only MCP spawn calling `/initial-deliveries`. Migration policy must classify a matching initial-delivery sender as `agent` and fall back to `unknown` on mismatch; unlike `message_deliveries`, it cannot prove whether an operator manually forged the sender historically. Direct-message migration can and must use `source_principal`: `operator:* → user`, `mcp:* → agent`.

**Confidence: LIKELY for the semantic split; CONFIRMED for every row count** — live rows, receipt joins and current authoring functions agree (tiers 1+2), but initial-delivery history lacks an authenticated principal [2][3]. Counterexample to content-only classification: the four visually identical fan manifests have two different origins.

### F3 — persistence has six writer seams, fed by 29 ingress calls

Low-level persistence paths:

1. `AgentSession.send` logs in compacting, running and new-turn branches (`session.py:1208,1255,1299`).
2. Compaction directly writes a platform `user_message` (`session.py:2961`).
3. Durable initial delivery directly inserts the immutable row (`initial_deliveries.py:251-253`).
4. Durable direct message delivery directly inserts the immutable row (`message_deliveries.py:285-287`).

The first three `AgentSession.send` branches are reached by 29 current `manager/session.send` call sites. The ingress categories include dashboard/TG/voice/restart-inbox user input; MCP/initial/mailbox/auto-report agent input; bg/cron/limit-wake input; platform fan/bug/undelivered/compaction notices; and system restart/retry/auto-continue/CI messages [4].

`db.add_log` is not the single writer claimed by its comment: the two durable-delivery modules bypass it intentionally to couple the immutable log with delivery state in one transaction. A default `origin='unknown'` at the low-level function would therefore both miss two SQL paths and conceal any known caller omitted from the 29-call inventory.

**Confidence: CONFIRMED** — literal writer grep plus call-site grep and code trace to the insert (tier 2). The completeness oracle must exercise/scan all six seams and require explicit provenance at the `send` boundary; counting only direct SQL strings is insufficient.

### F4 — origin already exists in one envelope but is not persisted

`InjectedMessage` already carries `origin`, `job_id`, and `event_id` (`events.py:9-16`); background terminal messages set `origin="orchestra.bg_jobs"` (`bg_jobs.py:566-572`). `AgentSession.send` currently extracts only `event_id`, converts the envelope to bare text, and discards `origin`/`job_id` before all three log branches (`session.py:1129-1133`).

This proves a structured delivery seam is viable and also shows that the existing `origin` value is not the requested finite category. A plan must either evolve this envelope into `{origin, sender/ref, ...}` for all ingress or add equally mandatory keyword parameters; optional defaults would recreate silent `unknown` on known paths.

**Confidence: CONFIRMED** — current source trace (tier 2) [5].

### F5 — runtime provenance/subtype inference has seven consumers, not one

- Dashboard: `chat.js:3911-3936` strips `[HH:MM]`, hides `[Orchestra platform...]`, parses `fromMatch`, and otherwise renders a right `chat-user` bubble.
- TG mirror: `tg_bridge.py:3285-3311` parses `[from:` to choose agent-vs-user presentation.
- RAG: `rag.py:107,257-264` parses `[from:` and otherwise classifies every `user_message` as human.
- Text-tail construction detects platform notes by text (`session.py:3217`) and should consume the field instead.
- Native runtime-history import repeats the same platform-note text filter (`runtime_history.py:1033`).
- `AgentSession.send` parses two `[system] Retrying...` strings to preserve/reset retry counters (`session.py:1195-1198`); category alone is insufficient, so structured provenance needs a system subtype.
- Limit-wake delivery finds/excludes `[system wake:<token>]` by content (`limit_wake.py:59-65,569-576`); the token should move to a structured ref/event field rather than remain a provenance parser.

`mcp_stdio.get_worker_logs` does not parse a prefix, but labels every `user_message` with the same human icon; it is another consumer of the new field (`mcp_stdio.py:1859-1875`). History and SSE already return `SELECT *` rows, so a new DB column reaches the main snapshot/SSE contract automatically; explicit projections such as `_SYNC_COLS` still need an audit [6].

**Confidence: CONFIRMED** — exact-string grep plus consumer code (tier 2). Removing only `fromMatch` would leave six runtime parsers/filters and one false-human renderer.

## Counter-evidence and limits

- The task says “field” singular, while exact agent/job labeling and a finite category list are independent data items. A single encoded string (`agent:name`) loses the finite-enum contract; a category-only field loses “who exactly”. Architecture must choose an enum plus structured detail or one validated structured object before planning.
- `session_turns._deliver_mailbox` can combine multiple senders into one delivered provider message (`session_turns.py:577-580`). No multi-sender mailbox row occurred in the frozen 2738-row cohort, but the production code permits it. Splitting log rows would diverge from the one provider input; forcing `unknown` would throw away known provenance. The lossless choice is `origin=agent` plus a non-empty sender array.
- Existing model-facing text may still contain a derived `[from:name]` so the model can see authorship. The field must remain canonical and no runtime consumer may parse the derived prefix. Removing the prefix from stored content would require a wider runtime-history/backend presentation change; this is an architecture choice, not a Phase 1 fact.
- The current live DB continued receiving rows after the task snapshot. Counts after `id=562928` are not part of the frozen 940/2738 acceptance baseline.
- The full suite is already red by task input (47 failures, terminated near 82%). Phase 1 did not run it: Phase 3 must compare exact failing node-id sets on the same command/commit, not totals.

## Recommended architecture gate for Phase 2

Preferred invariant:

- `origin` is exactly one of `user | agent | background_task | platform | system | unknown`.
- Structured provenance detail carries a non-empty `senders` array plus optional stable `subtype/ref` (agent names, job id, retry kind, wake token, platform/system label). If one physical column is mandatory, it must be a validated object containing `origin` and this detail, not a free-form string.
- Every new production delivery constructs structured provenance before `manager.send`; omission is a loud error. `unknown` is passed explicitly only when provenance is genuinely unavailable.
- UI rule is fail-safe: only `origin == 'user'` is right-aligned; missing/invalid/`unknown` is left-aligned and visibly labeled, never treated as user.
- One offline, idempotent migration uses receipt joins first, then the frozen prefix rules, then the explicit 181-class rules; all remaining rows become `unknown`. No text parser remains in application/runtime code.

This is a recommendation, not implementation approval. It requires the user's architecture choice and ownership expansion at the Phase 1 gate.
