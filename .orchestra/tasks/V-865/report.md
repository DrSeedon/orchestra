# V-865 — pilot: правило числовой калибровки

## Результат

**Не внедрять по результату пилота.** Во всех 12 парах слепой Luna-оценщик признал оба ответа правильными: 0 выигрышей B, 0 проигрышей B, 12 ничьих. Предварительный порог требовал не менее 5 discordant wins B и ни одного проигрыша; он не достигнут. Exact McNemar/sign test при нуле discordant pairs не определён — сообщать p-value нельзя. На точных контрольных C10–C12 обе arms дали правильную арифметику, новых B-only ошибок и необоснованных статистических требований судья не отметил.

Это значит, что добавка **не показала улучшения на выбранных случаях**, а не что доказано отсутствие эффекта на всех ролях/моделях/числах. Нулевой результат также не оправдывает второй этап автоматически: критерий для расширения был пройден только при ≥5 парных улучшениях без проигрышей. При новом, отдельно одобренном исследовании можно пересмотреть риск/цену и тестировать другие случаи, но этот запуск не обосновывает постоянный модуль.

## Выполнение preregistered пилота

До вызовов закоммичены [manifest.md](manifest.md), [rubric.md](rubric.md), [candidate-rule.md](candidate-rule.md) — commit `1e6dfbf2`. Manifest содержит 12 кейсов, evidence snapshot и вопросы, рандомизированный порядок A/B и псевдослепое кодирование, включая три точных отрицательных контроля. Кандидатное правило добавлялось только в arm B; основное содержимое задания совпадало внутри пары.

Dynamic workflow завершился успешно: **25/25 calls** (24 ответа A/B + один независимый blind assessor), exit 0, все на subscription billing без API credits. Эффективный model/runtime из journal — `gpt-6-luna` / `codex`. Workflow default system modules в обоих arms были `communication-style`, `user-values`, `knowledge`, `code-quality`; кандидатное правило передавалось в тексте user prompt, потому что публичный dynamic_workflow tasks interface не позволяет выбирать иной role-module bundle. Следовательно, вывод относится к этой реальной динамической workflow-сборке, а не непосредственно к каждому полному prompt-бандлу оркестратора/воркера.

Фактический `cost_usd` по журналу (API-equivalent, не счёт и не API-кредит): A/B calls — `$0.02910934`, assessor — `$0.00196958`, всего **`$0.03107892`** из разрешённого потолка `$15`. Все 25 calls завершились без таймаута и без исчерпания бюджета. Подробности: [run-ledger.md](artifacts/run-ledger.md).

## Ограничение ослепления

В assessor prompt закралась неоднозначность: общее указание называло X первой, Y второй записью в паре, а per-case random label map задавал собственную метку X/Y для позиций. Это делает X/Y subfields в judge JSON ненадёжными. Однако во всех 12 случаях judge присвоил обеим сторонам `correct=1` и `winner=tie_both_correct`; перестановка X/Y не меняет ни одной paired outcome, McNemar входа или итогового критерия. Этот конкретный результат пригоден для решения по заданному порогу, но нельзя использовать его X/Y assignment для дополнительных сравнений.

Ослепление было по условию/label mapping: assessor не получил A/B mapping или candidate-rule text. Содержание ответов могло выдать, что один arm осторожнее; это обычное ограничение blind оценивания текстовых ответов. Не использовался второй judge или human adjudicator.
