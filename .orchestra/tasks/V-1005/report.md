# V-1005 — MultiCode 1.3.2 и Orchestra: сравнение и варианты встраивания

## Рамка и источники

**Главная цель (steer владельца от 21.10, через Orchestra-orchestrator):** работать с MultiCode Hub через Orchestra откуда угодно, в том числе с телефона и без включённого ноутбука. MultiCode не должен получать доступ к ноутбуку владельца или VPS Orchestra; целевая граница для наших машин — ноль доступа. Поэтому рассматриваются только направления, где Orchestra инициирует соединение к Hub, рабочая папка доступна только на Hub, а Mutagen, PC tunnel и вызовы on-remote не нужны. Варианты, требующие обратного доступа Hub к Orchestra или ноутбуку, отмечены как несовместимые с целью.

Сравнение возможностей остаётся контекстом к этой цели: надо ли управлять тредами MultiCode или достаточно использовать его account pool как model provider — разные архитектурные ветки с разной ценой и правами.

Прочитаны целиком self-report и второй ответ MultiCode-агента о хранении/доступе к ПК, отчёты V-997/V-998, переданный draft V-325 и его raw-файлы hub-binary-context.txt и claude-hub-script-strings.txt (только чтение). Из открытого upstream T3 Code просмотрены tag v0.0.45 (сервер и MCP-контракт), а также актуальная main-документация о HTTP/WebSocket, внешнем MCP и T3 Connect; различия версий ниже явные. Скриншоты Usage — моментальный снимок от 21.10. Код Orchestra проверен в этой ветке; ссылки ниже дают актуальные file:line. После steer от 21.10 статически прочитан распакованный клиент MultiCode 1.3.2 (`/home/kesha/.cache/multicode-v325/`: desktop `main.cjs`, серверный `binCli-DRUogLaA.mjs` и helper `multicode-hub`). Из него восстановлен контракт отправки в тред, см. [re/send-recipe.md](re/send-recipe.md). Ни сам клиент, ни хаб не запускались. Ноутбук владельца не трогался.

**Калибровка:** self-report MultiCode помечен как заявление агента; V-325 подтверждает отдельные строки серверного AppImage/нативного helper и ограниченный сетевой снимок, но не проверял удалённый API, фактический MCP из внешнего клиента или полный runtime tunnel. В пакете V-325 указан T3 server 0.0.45 и hash приложения; одноимённый файл docs/user/outside-agents.md отсутствует в upstream tag v0.0.45, а соответствующее OAuth/MCP руководство есть в более новой upstream main. Поведение современной upstream main не приписывается форку MultiCode 1.3.2. Ответы на обновлённый questionnaire ещё не получены. Скриншоты показывают только один снимок остатков, не алгоритм маршрутизации.

Стоимость переноса в таблице ориентировочная: S — до 1–2 дней, M — около недели, L — больше недели или архитектурная работа (шкала V-997). Для интеграций с неизвестным API точная стоимость не оценивается до ответа.

## Варианты встраивания

### Что подтверждено в T3 Code и V-325

Upstream T3 описывает клиент-серверную границу так: один environment владеет provider processes, execution, files и durable state; web/desktop/mobile клиенты обращаются к нему по HTTP и WebSocket RPC. Обычный hosted web — клиент, который подключается напрямую к environment. T3 Connect предоставляет маршрут к environment, но не меняет execution model ([Architecture overview](https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md), [Remote architecture](https://github.com/pingdotgg/t3code/blob/main/docs/internals/remote.md)). Это основание для Orchestra как удалённого клиента к хабу, не доказательство, что кастомный MultiCode endpoint совместим.

Тег upstream v0.0.45 совпадает с версией T3 server, которую агент сообщил для MultiCode. В этом теге T3 server по умолчанию слушает 127.0.0.1 (`apps/server/src/server.ts:2598–2624`). Его `/mcp` принимает Bearer credential, разрешаемый через McpSessionRegistry; без него возвращает 401 `invalid_mcp_credential`, а текст ошибки прямо называет credential «provider-scoped» (`apps/server/src/mcp/McpHttpServer.ts:1617–1729`). У этого тега нет docs/user/outside-agents.md; проверенный MCP endpoint — internal provider tool server. Значит, наличие `mcp__t3-code__*` внутри MultiCode треда само по себе не даёт Orchestra удалённый OAuth MCP endpoint. В актуальной upstream main уже документирован внешний MCP на /mcp, read-only по умолчанию, с разрешением на thread start/message/stop и runtime-mode ceiling ([Outside agents](https://github.com/pingdotgg/t3code/blob/main/docs/user/outside-agents.md), [Environment authentication](https://github.com/pingdotgg/t3code/blob/main/docs/internals/environment-auth.md)); это более поздний путь, его наличие в MultiCode build не подтверждено. Даже текущий upstream говорит, что проект — организационная, а не filesystem граница: доступ к файлам ограничен правами серверного пользователя, а не project root (`environment-auth.md`).

V-325 подтверждает из пакета MultiCode relay-пути моделей, но их базовый адрес по умолчанию — loopback на Hub; настоящий публичный provider endpoint/внешняя авторизация не найдены. Встроенный helper `claude-hub` создаёт Mutagen two-way-resolved sync, Hub выигрывает конфликт, и настраивает обратный tunnel, через который `on-remote` обращается к PC. Self-report дополнительно заявил, что on-remote запускает команды на ПК как обычный пользователь, без sandbox и project restriction, а `~/.ssh` технически читается; эти последние факты — заявления агента, не независимая проверка wrapper. Следовательно, одно лишь «не синхронизировать папку проекта» не доказывает отсутствие доступа к ноутбуку, пока на Hub остаются зарегистрированные tunnel/shims и агент может запускать команды.

### Что подтверждено статикой MultiCode 1.3.2 (21.10)

Полный разбор с file:line лежит в [re/send-recipe.md](re/send-recipe.md). Здесь выводы, которые меняют вилку:

- Десктоп подключается к `t3 serve` на хабе как к обычному upstream «SSH environment». Хелпер `multicode-hub t3 connect` возвращает SSH-алиас хаба. Десктоп по SSH поднимает или находит сервер на `127.0.0.1:<port>` хаба (по умолчанию 3773, порт в `~/.t3/userdata/server-runtime.json`) и делает **исходящий** `ssh -L`. Дальше идут HTTP и WebSocket `/ws?orchestrationProtocol=2` с Effect RPC в JSON. Обратный туннель и Mutagen для этого пути не нужны: их ставит отдельная команда `multicode-hub setup`.
- Создать тред и отправить первое сообщение можно одним RPC `orchestration.launchThread`. Следующие сообщения идут через `orchestration.dispatchCommand` с `type:"message.dispatch"`, ответ читается из `orchestration.getThreadProjection` (`messages[].role="assistant"`) или из стрима `orchestration.subscribeThread`. Временную папку на хабе даёт `projects.ensureScratch` (`~/.t3/scratch`, вне Mutagen-синка).
- Аутентификация — обычный Bearer. Сервер содержит headless CLI `t3 auth session issue --scope … --ttl …`, поэтому можно выпустить токен **только** с `orchestration:read` и `orchestration:operate`, без терминала, файловой системы, настроек и управления доступом. Альтернатива — одноразовый pairing credential и `POST /oauth/token` (RFC 8693) с сужением scope.
- Значит, вариант 2 («Orchestra как T3 RPC client») больше не гипотеза: протокол и права известны. Остались две неизвестные. Первая: доступен ли SSH до хаба с VPS без локального прокси helper на ноутбуке. Вторая: публичный ли `host` в ссылке `multicode-hub phone pair`; если да, это путь без SSH.
- Граница безопасности уточнена. Bearer на исходящем соединении не даёт хабу доступа к VPS. Агент в созданном треде по-прежнему работает с правами пользователя хаба и, если обратный туннель ноутбука активен, теоретически дотянется до on-remote. `runtimeMode:"approval-required"` без одобряющего фактически блокирует команды и правки, но это защита приложения, а не ОС. Потолок runtime mode найден только для MCP-сессий, для bearer — нет.

### Вилка решения

1. Если «через Orchestra» означает **запускать и продолжать именно T3/MultiCode threads**, рекомендую вариант 2. После статического разбора 21.10 он уже не ждёт Multicast: транспорт, методы и scoped bearer известны, и запрашивать у Multicast remote MCP не нужно. Порядок:
   (а) владелец прогоняет [рецепт](re/send-recipe.md), цена S;
   (б) решается, как VPS достаёт хаб: свой SSH-ключ к учётке хаба или публичный pairing-host из `phone pair`;
   (в) интеграция S–M.
   Отдельно решается граница ноутбука. Пока ноутбук привязан к той же учётке хаба с обратным туннелем, агент треда теоретически может дотянуться до него; полный ноль даёт только вариант 4 (отдельная учётка или среда без привязки ПК). Наш клиент всегда шлёт `approval-required`, это снижает риск, но не убирает его. Приватные данные Orchestra в треды не отправлять.
2. Если достаточно **использовать account pool как модель для обычных Orchestra workers**, выбирается provider adapter (3). Это меньше прав и чище по машинной изоляции; в обмен нет управления MultiCode thread state. Сначала получить поддержанный external gateway URL/token/terms; текущие relay routes на loopback — не готовый provider API.
3. Если Multicast не может предоставить ни remote T3 API, ни отдельный hub-only environment, **безопасного полного thread-control варианта из известных фактов нет**. Отдельный mobile app — ручной обход вне Orchestra, а открывать доступ MultiCode к VPS или laptop противоречит цели.

У любого inbound MCP/webhook/callback от Hub к Orchestra остаточный доступ к VPS не будет нулевым; он вынесен в строку 5, не предлагается как «мост». Доступ к данным Hub и model vendor останется даже в безопасном исходящем варианте: запросы и файлы, которые Orchestra передаст в Hub, становятся данными обработки/хранения MultiCode; по заявлению агента thread JSONL включает сообщения, tool calls и stdout команд.

## Итоговые выводы

MultiCode сильнее в заявленных многопровайдерном UI с per-account balances, нативном desktop/mobile, прямом управлении тредами и scheduled runs на хабе. Его самые важные для нас неизвестные — точный account router/failover и есть ли внешний API, а не заявленная ширина инструментов.

Orchestra сильнее в предотвращении исчерпания квоты до выполнения хода, сохранённой очереди при квотном блоке, связи воркера с задачей/проектом, изоляции работы через worktree и проверяемой приёмке результата. У неё уже есть background jobs и GitHub HMAC webhook; у MultiCode не следует забирать обобщённую «похожую» механику, пока не показана разница в результате.

Из прежних решений: V-998 подтвердил «не брать» per-turn rollback и native thread fork при текущих наблюдаемых сценариях; эта оценка остаётся базовой. V-997 описал ACP и event-sourcing как возможные идеи, но V-998 показал цену поддержки отдельного backend и отсутствие подтверждённого спроса на ACP. Для V-1005 вывод — не строить универсальный провайдер/мультиаккаунт только по обещанным моделям: сначала подтвердить API, учет пула и условия использования.

Самый высокий риск всего исследования не функция MultiCode, а граница ноутбука: по заявлению агента on-remote запускает команды как обычный пользователь на ПК в full-access, не ограничиваясь workspace, а stdout входит в transcript на hub. Если это верно, любой доступ к T3 runtime со стороны внешнего orchestration превращается в доступ к пользовательской машине и выносит секреты/выводы команд в хранилище hub. Такую топологию нельзя считать безопасной для нашего owner laptop или приватных данных Orchestra до технического ограничения ОС/VM и ответов оператора.
