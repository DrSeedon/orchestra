# #340 — `handoff_pending_effect` запирал воркеров навсегда

Симптом: `change_worker_model` отвечает `http_4xx: handoff_pending_effect` на idle-воркере,
обхода нет, кроме пересоздания агента. Ниже — механизм, замеры и правка.

## 1. Механизм: `id` в `logs` — это порядок ВСТАВКИ, а не порядок событий

`_log` (`app/session.py:4649`) отправляет вставку в общий пул `ThreadPoolExecutor(max_workers=4)`
(`app/session.py:233-239`). Четыре потока пишут параллельно, поэтому autoincrement `id`
раздаётся в порядке КОММИТА транзакции, а не в порядке событий. `ts` берётся в event loop
до отправки в пул (`app/session.py:4638`) и порядок событий сохраняет.

Замер по живой БД (`sqlite3.Connection.backup`, 178 304 строки `logs`, 361 сессия с tool-строками):

| факт | число |
|---|---|
| пар `tool`+`tool_result` с обеими строками | 42 661 |
| из них `id` результата МЕНЬШЕ `id` своего вызова | 4 266 (10.0%) |
| из них `ts` результата раньше `ts` вызова | **0 из 42 661** |
| групп `(session_id, ts)` с более чем одной строкой | 0 из 178 304 |

Уточнение к таблице (внешняя проверка `rev340-opus`): наивный join по `tool_use_id` даёт не
ноль ts-инверсий, а 82 — `tool_use_id` не уникален в сессии (86 групп, 82 из них в одной
grok-сессии). На вывод это не влияет — попарное сопоставление в порядке событий не
ошибается ни на одной паре, — но неуникальность идентификатора это отдельный дефект,
заведённый отдельной задачей.

`build_runtime_state_packet` сопоставлял пары одним проходом по `id`
(`app/runtime_history.py:282,341`). Инвертированную пару такой проход не видит:
`tool_result` встречается раньше своего вызова → помечается `ambiguous`, а сам вызов
остаётся `pending` навсегда. Гейт считал блокирующим любой `status != "completed"`,
то есть обе половины одной и той же артефактной пары.

Отсюда наблюдение «pending ≈ ambiguous в каждой сессии» и вся картина отказов.
Равных `ts` в паре нет ни одного (микросекундное разрешение), тайбрейк `(ts, id)`
оставлен для детерминизма, а не потому, что он срабатывает.

## 3. Что решили и почему именно так

Гейт оставлен, но его предмет изменён: он блокирует не «непарный вызов», а
«вызов, ПОСЛЕ которого в снимке нет ни одной строки». Порог по времени не введён и не нужен.

Оговорка про силу этого предиката, важная для читателя: наличие строк после вызова НЕ
доказывает, что ход завершился — 4 615 из 43 096 живых пар (10.7%) имеют строки между
вызовом и собственным результатом. Предикат исключает ровно одно состояние: вызов, у
которого тул может исполняться ПРЯМО СЕЙЧАС, а замораживать снимок под работающим тулом
нельзя. Строгая версия («пропускать только с доказанным концом хода») проверена внешним
ревью: она блокирует те же 2 сессии и не отпускает дополнительно ни одной из 1 162.

Почему остальные (в том числе 39 «убитых рестартом») переносятся с пометкой:

- блокировка НЕ доделывает и НЕ отменяет эффект — он случился или не случился дни назад.
  Гейт решает лишь, увидит ли новый рантайм ЗАПИСЬ о нём;
- повторить вызов по пакету физически нельзя: аргументы и тела результатов в пакет не
  попадают (`payload_visible: false`, `"tool_payload_bodies": "omitted"`), у эффекта есть
  только имя, хеш и `repeat_policy: "never"`;
- цена противоположной ошибки известна и платится: 266 сессий из 361 были неперемещаемы,
  четверо воркеров заперты в двух проектах, обход — пересоздание агента с потерей контекста.

Различить «эффект завершился, а запись потеряна» и «эффект недоделан» задним числом
можно только классом A/B выше — прямого доказательства по строке нет ни у кого. Поэтому
пометка `unresolved` едет вместе с пакетом и пишется в журнал, а не молчит.

## 4. Правка

- `app/runtime_history.py` — сопоставление пар в порядке событий `(ts, id)`; `ordered`
  (порядок `id`) не тронут, на нём заморожены `snapshot_sha256`, `raw_event_refs` и
  `recent_messages` — из пяти его потребителей изменён ровно один, цикл эффектов;
- там же — терминальная классификация после прохода: `unresolved` для вызова, за которым
  в снимке есть хоть одна строка; `pending` остаётся только у хвоста снимка;
- `classify_handoff_effects` / `describe_handoff_effects` — единственный владелец решения
  и текста отказа; `session.py` больше не читает `packet["tool_effects"]` напрямую;
- `_handoff_blocked_result` — один формат отказа для обоих путей смены модели; отказ
  называет tool, `call_id`, `log_id` и `ts` каждого висящего вызова и кладёт их в
  `pending_effects` ответа (дашборд показывает `body.error`, `app/static/js/app.js:2543`);
- `unresolved_effects` пишутся в журнал ПЕРЕД возвратом на обоих путях подготовки. Первая
  версия ставила запись после `if result is not None: return result`, то есть на пути
  идемпотентного повтора, которого в штатной работе не бывает: правка, сознательно
  расширяющая класс пропускаемого, молчала бы обо всех 43 эффектах запертых воркеров
  (блокер внешнего ревью);
- удалён недостижимый дубль гейта (`app/session.py:3869` до правки): `pending_effects > 0`
  бывает только у `ok=False`, который возвращается раньше;
- `call_ts` кладётся ТОЛЬКО в незакрытые эффекты. Пакет считается против контекстного окна
  цели в preflight-манифесте (`build_model_visible_manifest`), и поле на всех эффектах стоило
  бы 68 040 байт у `direct-research` вместо нынешних 1 260.

## 7. Что заработает только после рестарта

Вся правка — Python в `app/`, живой процесс держит старый код в памяти. До
`systemctl restart orchestra` `change_worker_model` продолжит отвечать
`handoff_pending_effect` на тех же воркерах. Проверка здесь сделана из СВЕЖЕГО процесса
по строкам боевой БД, а не через MCP-тул живого сервера.
