# V-666 — техники промптов для агентов: исследование и сравнение

Дата: 29.09.2026. Только чтение и отчёт; действующие промпты не изменялись.

## Вопрос и границы

Контекст — системные инструкции и агентные промпты Orchestra. Сопоставление — опубликованные рекомендации и открытые реализации против .orchestra/pipelines/default/prompts/ и корневого AGENTS.md. Искомый результат — идеи, чья полезность подтверждена измерением или надёжной практикой, с оценкой, есть ли уже эквивалент у нас. Это исследование не доказывает, что изменение текста улучшит именно Orchestra: эффект зависит от модели, задачи и harness.

Прочитаны V-662, V-659, .orchestra/kb/prompt-engineering.md, текущие base.md, roles/full-cycle.md, modules/research-method.md, code-quality.md, worker-lifecycle.md, user-values.md, pipeline.yaml и AGENTS.md. Во внешних материалах прочитаны OpenScience Autoresearch skill, актуальные гайды Anthropic по prompting и Claude Code, OpenAI Codex agent-loop guide и prompting guide, публичный Codex prompt, Aider prompt constants и актуальная версия статьи arXiv:2608.01347 (v6, 10.09.2026). Открытые system prompts — первичные источники о конкретной реализации, но не независимое свидетельство эффективности. OpenScience skill Autoresearch помечен MIT; Apache-2.0 корневого проекта автоматически не распространяется на включённые skills (см. разбор лицензий в V-662).

## Измеренное отдельно от рекомендаций

**Техники с измеренным эффектом в arXiv:2608.01347:** ограничение области/изменения плюс критерий достаточного результата и stop condition не увеличило стоимость и уменьшило reasoning у одной модели; «сравни несколько подходов», «думай глубже» и certainty framing заметно увеличили reasoning/token/tool cost без убедимого среднего прироста успеха; в неоднозначных задачах stop-early framing ухудшил сбор evidence и hidden-test success; эффект prompt/effort существенно зависел от harness. Работа preregistered, paired, с 24 детерминированными задачами, скрытыми evaluator’ами и около 4.6k запусков по нескольким стадиям/расширениям. Это экспериментальные условия статьи, не прямой замер Orchestra.

**Практические рекомендации, не измеренный причинный эффект:** Anthropic/OpenAI предлагают конкретнее задавать исход/границы, предоставлять runnable check/repro, а OpenAI для GPT-6 советует узкие skill triggers, progressive disclosure и избегать предписания читать нерелевантные документы/повторять проверки. Anthropic также рекомендует XML-разделители для составного контекста и состояние для long-horizon задач. Эти советы могут помочь в описанных условиях, но сами по себе не доказывают причинный выигрыш для нашего runtime.

В статье дополнительный inference effort иногда повышал успех на сложных repository-scale задачах; поэтому «меньше вычислений всегда лучше» из неё не следует. Её итоговая метрика — cost per successful task, не минимум токенов или инструментальных вызовов.

**Наши измерения.** V-548/V-550: пять моделей на одной задаче; предписание способа вместе с неоднозначностью при обрезке стоило 7.5–8.8× двум моделям. Влияние двух одновременно снятых указаний нельзя разделить. Это основание не навязывать несущественный метод при проверяемой цели, но не вывод «любая инструкция вредна». #77: 20/20 соблюдений при сохранности результата 15/20. V-643: штатный compaction потерял часть чисел и незавершённых дел. Для наших решений эти локальные измерения релевантнее общих вендорских тезисов, но ограничены описанными задачами/выборками.

## Явные противоречия и их разрешение

1. **Минимум действий против полноты исследования.** Внешние данные поддерживают bounded-стратегию для ясных условий; ambiguous плечо не прочитало нужный requirements-файл и получило 3/5 hidden-test failures против 0/5. Наше условие «остановись, когда результат решаем» безопасно только вместе с проверкой фактического кода/источников и выяснением неопределённости. Глобальные квоты чтений/файлов/ходов противоречили бы evidence.
2. **Обязательные несколько планов/максимальное размышление против измеренной стоимости.** Формулировки повышали расход без убедимого прироста среднего успеха в тестовой выборке. У нас альтернативы нужны только при настоящей архитектурной развилке или для опровержения спорного утверждения, не в каждой задаче.
3. **Самопроверка против повторов.** Runnable oracle и наблюдаемое evidence рекомендованы Anthropic; certainty wording в статье приводило к повторным проверкам уже решённого. Наше требование проверить релевантные контракты и сообщить результаты, вместе с запретом повтора неизменённого зелёного прогона, точнее безусловного «проверь себя ещё раз».
4. **Пошаговый workflow против свободы метода.** OpenScience/Claude Code показывают пользу специализированных процессов для конкретных классов задач. V-548/V-550 предупреждает о цене детального предписания на bounded задаче. Процесс имеет смысл как активируемый профиль, если он сам необходим для исхода, но не как базовый текст всех ролей.

## Результат

Практически новые для нас идеи в основном уже выражены: ограниченная цель, измеримый исход, проверка реального эффекта, масштабирование усилий, сохранение состояния и свобода метода. Наиболее важный внешний вклад — количественные эффекты лишнего branching/thinking/certainty language и их зависимость от harness; он поддерживает часть локального опыта, не отменяя глубокого исследования при неопределённости. Пробел V-662 остаётся архитектурным, а не текстовым: общего ledger для долгой серии метрико-управляемых экспериментов у нас нет.

Изменения базовых правил не предлагаются: задача разрешает только исследование, а правка общего поведения требует решения владельца. Для будущего продолжения можно отдельно решить, нужен ли ограниченный пилот текущего prompt против одной bounded-efficiency формулировки на фиксированных ясных и неоднозначных coding-задачах. Замер должен включать успех/сохранность артефакта, cost per successful task, лишние проверки и пропуски evidence; это рекомендация, никакая реализация или эксперимент здесь не начинались.
