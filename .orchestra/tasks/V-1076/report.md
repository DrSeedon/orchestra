# V-1076 — native Codex compact timeout: исследование

Результат: воспроизведены механизмы в публичном Python backend, способные дать именно стадию `completion notification`, скрыть явную ошибку и показать позднее завершение при следующем пользовательском ходе. Причина конкретных host-инцидентов **не установлена**: нет их wire trace. Изменены только task-local материалы; реализации исправления нет.

Самый существенный подтверждённый дефект: после ACK последовательность `turn/started → error → turn/completed(status=failed)` без compaction item заканчивается общим timeout вместо исходной ошибки. Reader отправляет эти сообщения в отдельную compact-очередь; до compaction notification никто её не разбирает. Текущий timeout тем самым может скрывать уже полученный отказ.

Второй существенный результат: если completion действительно приходит после timeout, reader уже кладёт его в обычную очередь. Настоящие `send()` и последующее `events()` показывают `codex context compacted`, хотя старый вызов compact остался неуспешным. Это доказано отдельно для всех трёх поддерживаемых форм уведомления. Сама такая строка спустя 29 минут **не доказывает**, что завершилась прежняя операция: новый automatic compact даёт ту же строку.

## Что объясняется на host и что остаётся гипотезой

Суффикс `waiting for completion notification` означает, что локальный ACK await закончился, но до обработки timeout **общего** deadline `await future` не вернул результат в compact coroutine. Это не доказывает отсутствие wire notification: мог уже прийти error и failed terminal; без receive/scheduling timestamps нельзя исключить и задержку возобновления waiter около deadline. Изолированная потеря только terminal **после возврата из await C** даёт другую стадию — `turn lifecycle`. Эти механизмы нельзя смешивать.

У backend есть отдельный reader, поэтому отсутствие пользовательского события само по себе не останавливает чтение stdout. Зато обычный consumer для Codex имеет режим [per_turn](../../../app/runtime_registry.py#L367); следующий пользовательский ход создаёт [turn event loop](../../../app/session.py#L1780), вызывающий [events](../../../app/session.py#L2558). Поэтому доставленный позднее completion может уже лежать в памяти до следующего хода. Проба с реальными `send/events` подтверждает этот путь; полный session listener startup не моделировался. Из этого нельзя вывести, было ли на host поздним **получение** сообщения, его **показ**, или это был совершенно новый compact.

|---|---|---|---|
| Upstream compact дольше deadline | `Q A ... D ... C1 T1` | H: direct late path подтверждён, host timing/identity отсутствуют | Сопоставить receive timestamps и turn/item identity до/после timeout |

## Минимальное предложение исправления, без реализации

1. **Сначала устранить маскировку terminal failure.** Разбирать compact lifecycle/error в момент получения, а не только после C. Для своего terminal failed/interrupted сохранять исходную ошибку и завершать waiter; `willRetry=true` само по себе не обрывает ещё живую операцию. Успех — распознанный compact и успешный terminal того же turn. EOF/disconnect должен завершать waiter в обеих стадиях. Это точечное изменение владельца compact state, без нового provider-вызова.
2. **Защитить владельца до конца операции.** Отдельный operation record/lock остаётся занят до terminal/reconciliation, даже если completion future уже done. Фильтровать thread до lifecycle/usage изменений, закреплять первый допустимый compact turn, проверять C.turnId при его наличии. Сохранить три существующие формы C/K/L; для legacy без ID задать явную ограниченную политику совместимости, а не безусловно запретить старые события.
3. **Timeout/cancel означает unknown remote outcome.** Не терять запись unresolved operation, поздние notifications привязывать к ней и логировать как поздние. Не запускать повторный native compact, пока старая операция не reconciled. ACK содержит `{}`, поэтому один локальный generation-ID не отличает поздний S старой операции от S нового запроса: обещать такую корреляцию нельзя. Следующую delivery/hibernate/recovery политику согласовать с существующим session lifecycle; native interrupt требует известного compact turn. Автоматический restart/disconnect не предлагается как безусловная мера.
4. **Добавить только event metadata:** local operation/generation, стадия, времена Q/ACK/first C/terminal, method, thread/turn match, terminal.status, error-info/willRetry, reader EOF/exit, queue routing и поздний результат. Не сохранять body, summaries, prompts, пользовательские пути или секреты. Исторический timeout не переписывать в успех: поздний результат — отдельный факт.

Риски: слишком строгий matcher отрежет legacy события без ID; ранний abort на recoverable error сломает reconnect; освобождение gate на timeout снова допустит overlap, вечный unresolved gate ухудшит доступность; сохранение старой операции требует ограниченного объёма состояния и понятного owner recovery; изменение маршрутизации может потерять обычные status/error события или задвоить terminal. Решающие acceptance checks будущего fix должны включать разрешающие и отрицательные плечи матрицы: три success-формы, early notification, failed/interrupted, retryable error с последующим **успехом**, late old events при retry, cancellation/EOF во всех стадиях, сохранение обычного user turn. Текущие characterization assertions описывают дефект и должны быть осмысленно заменены ожидаемым контрактом, а не сохранены как будущая норма.

Просто увеличить 120 s недостаточно: это не исправляет скрытую ошибку, ложный успех, потерю identity и cancellation; увеличивает время занятого session и задержку обратной связи. Изменение бюджета имеет смысл только после распределения измерений ACK/C/T и проверки CLI 0.163.0 schema/ordering на host.
