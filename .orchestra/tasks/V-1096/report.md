## Как читать enforcement и аналоги

**I** — инструкция агенту. В ub-mode нет executable code, CI workflow, hook, wrapper или платформенного interceptor, который заставляет выполнить SKILL. Формулировка README об enforcement — claim README; фактические механизмы принадлежат отдельным CLI и только при их запуске. Нет подтверждения, что companions автоматически вызываются при активации skill.

## Companion mechanics: факты из кода

### Crapper: CRAP не равен проверке корректности

Формула `CC² × (1 − coverage)³ + CC` использует долю coverage 0..1. Реализация переводит проценты в долю; отсутствие coverage при `--no-coverage` даёт CRAP=None. При запрошенном coverage, но отсутствии данных конкретной функции, анализатор использует 0%. [crapper/src/crapper/crap.py:6-34](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/src/crapper/crap.py#L6-L34) [crapper/src/crapper/analyze.py:12-25](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/src/crapper/analyze.py#L12-L25)

SKILL требует **строго <10**. У CLI threshold по умолчанию None; без `--threshold` высокие числа не меняют exit status. С `--threshold 10` блокируется только **>10**, ровно 10 разрешено. Если scores отсутствуют либо вообще нет найденных source files, код возвращает 0. Граничные тесты upstream явно подтверждают равенство порогу и no-score success. [crapper/src/crapper/cli.py:294-326](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/src/crapper/cli.py#L294-L326) [crapper/tests/test_cli.py:297-310](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/tests/test_cli.py#L297-L310)

Из формулы: даже при coverage=100% CRAP=CC; функцию с CC=10 нельзя привести к строгому <10 только увеличением coverage. При coverage=0 и CC=3 CRAP=12. Это вычисление формулы, не эксперимент и не оценка времени. Покрытая строка не доказывает проверку результата; низкий CRAP не является correctness oracle.

В README перечислены шесть семейств: Clojure, Java, Go, TypeScript, Rust, Python. Реальный discovery дополнительно принимает JS/JSX/MJS/CJS как typescript-family, исключает .d.ts. Java constructors/anonymous-class methods не являются отдельными entries; Python nested functions относятся к внешней функции; TS содержит отдельные Express-callback entries; степень coverage различается (Java instructions, TS branches при BRDA, иначе lines). Сравнивать числа языков как один независимый от языка стандарт нельзя. [crapper/README.md:58-85](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/README.md#L58-L85) [crapper/src/crapper/discover.py:6-23](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/src/crapper/discover.py#L6-L23)

Важное расхождение docs/code: README обобщает ошибочный coverage-run как 0%. В Python, если после красных tests создан coverage data file, `_record_python_lcov` всё равно экспортирует LCOV и сообщает, что coverage записан; `run_coverage` для встроенных language runners возвращает 0. Значит, неверно утверждать, что любой красный baseline обязательно обнуляет Crapper coverage или блокирует CLI. Отдельный пользовательский coverage-command с nonzero подавляет чтение прежних reports. ## Реальный merge path Orchestra и пределы соответствия

`app/merges.py` в копии отсутствует. По `rg` реальный путь — `app/merge_operations.py` → `app/merge_test_gate.py` → executor в routes/sessions и workspace. Exact expected_head + непустое acceptance_note и actor проверяются при приёмке; смена HEAD отвергается. Это механизм конкретной операции, а не гарантия всех инженерных правил. Связанные разрешающие/отрицательные тесты: `tests/test_work_acceptance.py:43-83`.

Mapped subset выбирает stem tests изменённых app/*.py, route-surface test и изменённые tests/test_*.py. Это не полный suite. Неmapped source и docs-only могут дать SKIPPED; строгий mapped-контур зависит от `oracle.required`. Browser/live_probe исключаются в соответствующих Orchestra runs. Отрицательный и разрешающий path блокировки/допуска существуют в `tests/test_merge_test_gate.py:82-93,1347-1363`; эти тесты найдены/прочитаны частично и **не запускались**.

Rollback mutation gate после зелёного mapped subset собирает две disposable trees целевого commit: обе получают worker test artifacts, только control — worker source delta. Проверяются изменённые test nodes. Доказательством служит тот же node, зелёный с source change и красный после возврата target sources. Если target-source run тоже зелёный при зелёном control, `tests_not_guarding_source` делает общий gate FAILED и merge отвергается. Отрицательное и разрешающее плечо явно представлены в `tests/test_merge_test_gate.py:239-270`.

Это **не** source-operator mutation campaign, не null-output oracle и не доказательство последовательности «написал red до code». Добавленный helper/import без идентифицируемого changed test node может дать SKIPPED; test-only/source-only/нет tests/нет target/no diff/исключённые markers имеют отдельные исходы. При некоторых отказах control/rollback возникает INCONCLUSIVE.

Критичная граница: `evaluate_test_gate:1089-1092` переносит в общий status только mutation FAILED. Mutation SKIPPED/INCONCLUSIVE сохраняется в evidence, но сам по себе не меняет зелёный mapped result. `merge_operations:2071-2075` смотрит общий test_gate status; strict_mapped не делает отдельно mutation INCONCLUSIVE блокирующим. Тест `tests/test_merge_test_gate.py:403-430` прямо ожидает общий PASSED и mutation INCONCLUSIVE при timeout. Следовательно, нельзя говорить «Orchestra всегда блокирует без доказанной мутации». Здесь это факт текущего кода, не новая задача на починку.

Small changes: структурный размер diff ограничен **2000 вставками**, удаления не считаются; tracked task evidence и validated hub inputs имеют исключения. Ровно 2000 допустимо, 2001 блокируется; orchestrator/human waiver существует и worker сам его не получает. Это реальный gate размера, а не формализация «минимального edit» из R05/R11/R38/R59. `app/diff_budget.py:16-117`, `app/workspace.py:1699-1716`, `tests/test_diff_budget.py:47-114`.

Root cause vs defensive checks: code-quality требует reproducer и meaningful guard test, но разрешает exploratory diagnosis до frozen test, когда контракт ещё не понятен (:65-69). Orchestration (:54-66) оставляет проверки authorization/data integrity/irreversible writes и запрещает необязательным metadata блокировать независимый безопасный путь. Поэтому R37 не даёт основания удалять нужные проверки на границе. Установление root cause остаётся суждением агента, механического semantic oracle не найдено.

Cleanup/lifecycle: recovery-safe cleanup в worktree_cleanup не равен kill worker. Уборка выполняется после сохранения merge outcome; сохраняет уникальные файлы и env, проверяет dirty/in-progress/process holders и восстанавливаемость данных. Delete-session отдельно блокирует running/children/dirty/unmerged при force=false; force=true эти проверки обходит. Правила 72h/persistent/RESEARCH DONE из worker-lifecycle шире показанного delete guard; наличие инструкции нельзя объявлять равным платформенной проверке всех этих условий.

Локальные `rg` по app/tests/scripts/pyproject/uv.lock/prompt modules не нашли интеграцию имён crapper/dryer/mutator или CRAP. Это граница «не найден в проверенной области», а не доказательство отсутствия любой ручной мутационной проверки: собственный rollback механизм найден и разобран. Прямые shell/Git действия этим merge API не перекрыты; сам merge_test_gate docstring признаёт отсутствие полного bash-блока.

Runtime по языкам: Clojure — clj/bb и project aliases/Cloverage; Java — Maven и JaCoCo 0.8.12; Go — go toolchain и go.mod; TS/JS — npm/project scripts, coverage/Vitest/c8; Rust — cargo и llvm-cov либо tarpaulin; Python — project interpreter с pytest или unittest и coverage.py. Наличие парсера языка не означает наличие его runtime/runner или проходящий baseline. [crapper/README.md:72-85](https://github.com/unclebob/crapper/blob/6fd92c4c9bcc56efb64a2f8743d5a2993bcfd42d/README.md#L72-L85) [mutator/README.md:102-115](https://github.com/unclebob/mutator/blob/a5a0cb803b66e0cdb8bf471b3b08af701d424a41/README.md#L102-L115)

Для полного исходного цикла без re-use coverage и без кеша killed: Crapper обычно один coverage-run на затронутый project/language unit; Mutator по умолчанию генерирует coverage ещё раз, плюс baseline и M mutant test runs. Итого это **два coverage-прохода + B baseline-проходов + M mutant-проходов**, плюс Dryer/static parsing, где B — число уникальных пар command/cwd с непустым selection. Это счёт вызовов из кода, не замер и не всегда один full suite: Go mutator ограничивается package, другие команды определяет project.

Параметрическая оценка для одного набора: CPU-work ≈ C_crapper_cov + C_mutator_cov + B×T_baseline + Σ T_mutant + parser/I/O. Последовательное верхнее время mutant при N выбранных sites и одном runner timeout τ — до N×τ плюс накладные расходы; при нескольких workers идеальное деление не учитывает CPU/RAM contention и компиляцию. У coverage/baseline нет доказанного общего timeout ceiling. Поэтому **численного гарантированного лимита полного цикла нет**.

Иллюстрация, не замер: если M=1000 и каждый mutant command занимал бы ровно 1 секунду, одни mutant commands дают 1000 CPU-test-seconds (~16.7 минут последовательного времени) до coverage/baseline/setup. Это арифметический сценарий, не прогноз Orchestra и не оценка модельного бюджета. Число M в Orchestra не измерялось. Исторические ~728s полного pytest из docstring merge_test_gate не являются сегодняшним benchmark.

Companion scanners сами не содержат необходимости вызывать LLM/provider. Полный агентный remediation loop добавляет неопределённое число edits/tests/turns; из кода CLI его стоимость не выводится. Суммы в $/подписочная квота не оценивались. Default all-cores и сетевые installer fallbacks не совпадают с ограничениями согласованного offline smoke; отсутствие выполнения ниже осознанно.

Выполнены публичные HTTP GET к GitHub API/raw, чтение/нумерация первичных файлов, read-only `rg`/sed/nl локальных источников, сравнение Git blob hashes, SHA256 фиксация manifest. Поэтому offline companion smoke **не запускался**, анализ механики — по коду. Broker uv найден по предусмотренному пути и сообщил 0.11.28. Системный uv dispatcher не использовался.
