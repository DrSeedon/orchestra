Решает юзер. Факты собраны, рекомендация помечена как рекомендация.

### Почему тул `list_jobs` вообще выдан агентам
Археология: раньше `spawn_worker`/`kill_worker` были **асинхронными** — клали задание в очередь и
СРАЗУ возвращали агенту `job_id`, не дожидаясь результата:
```
$ git show e9b4e7f | grep -A8 "async def spawn_worker"
-    add_job(job_id, "spawn", args["name"], args["repo_path"])
-    await _manager.enqueue_worker_spawn(job_id=job_id, ...)
-    return {"text": f"Worker '{args['name']}' spawn queued (job {job_id}).\nCheck: list_jobs or list_workers."}
```
Тул существовал ровно затем, чтобы агент мог узнать, чем кончился его же спавн. В коммите
**e9b4e7f (2026-06-02, «#45 Fix all Codex full review findings»)** оба тула переписали на
синхронный HTTP, а инфраструктуру очереди забыли снести.

### Что сломается у агентов, если тул исчезнет: ничего
Сегодня `spawn_worker` (`mcp_stdio.py:155`) — синхронный `POST /api/sessions`, возвращающий результат
сразу: `Spawn failed: ...` либо готовый воркер. Ждать и опрашивать статус больше нечего.
`list_jobs` при этом **физически не может вернуть данные** — писателя у таблицы нет (`add_job` мёртв),
в боевой БД 0 строк (проверено тобой независимо). Агент получает `"No jobs"` всегда.
То есть у агентов уже сейчас ничего нет — исчезновение тула отнимает пустую строку.

### Дашборд: НЕ ссылается (проверено — тул не единственный конец, но второй конец чужой)
Вкладка JOBS в дашборде существует, и это ловушка: она читает **другую таблицу**.
```
$ grep -n "loadJobs" -A6 app/static/js/app.js
5769: async function loadJobs() {
5774:     const resp = await fetch(`/api/bg/jobs?scope=...`);   ← bg_jobs, НЕ jobs
```
`jobs` (`db.py:119`) и `bg_jobs` (`db.py:212`) — две разные таблицы с разными схемами. Дашборд,
`routes/bg.py` и тулы `bg_*` работают с ЖИВОЙ `bg_jobs`. У мёртвой `jobs` фронтовых потребителей **ноль**:
```
$ grep -rn "api/jobs" app/static/js/ app/templates/

```

### T2 — Fail-loud в сборщиках блоков промпта *(баг, не оверинжиниринг)*
**Риск: needs-check · ~0 строк (правка поведения, не чистка)**

- Файлы: `app/manager.py:67-90` (`_other_orchestrators_block`), `app/manager.py:92-131` (`_workers_block`).
- Суть бага: оба обёрнуты в `except Exception: return ""`. Любой сбой (БД, битая строка сессии) →
  оркестратор молча получает системный промпт **без списка воркеров и без списка других
  оркестраторов**. Он не знает, кому писать и кого переиспользовать; выглядит как «агент тупит».
- **Ключевой аргумент:** вызывающая `ROLE_SYSTEM_PROMPT` (`manager.py:182`) в своём же докстринге
  объявляет «**Fail loud:** нет манифеста или роли нет в манифесте → `ValueError`» и действительно
  бросает. Немой `except` внутри противоречит контракту собственной функции.

Что делаем (решение по каждому пункту, а не «убрать except»):
1. **Логируем:** `logger.exception(f"prompt block '<имя>' failed for scope={scope!r}")` — класс и текст
   исключения обязательны (грабли: `Send failed: network error: ` без текста).
2. **Что отдаём:** НЕ пустую строку. Возвращаем явный маркер деградации в промпт, например
   `## Your current workers\n⚠️ Worker list unavailable (internal error) — use list_agents.`
   Агент должен ЗНАТЬ, что список неполон, и иметь обходной путь, а не считать, что воркеров нет.
   Это прямо чинит опаснейший сценарий: пустой список читается как «воркеров нет» → оркестратор
   плодит дубликаты.
3. **Падаем или нет:** НЕ падаем. Сборка промпта — путь спавна/резюма; `ValueError` здесь
   положит восстановление всех сессий при единственной битой строке в БД. Деградация допустима,
   но обязана быть громкой и видимой в промпте.
4. Сузить `except Exception` до реально ожидаемого (`sqlite3.Error`, `KeyError`, `TypeError`);
   всё прочее пусть летит наверх.
- **AC:** (1) при подсунутом падающем `get_all_sessions` в логе есть `logger.exception` с классом
  исключения; (2) в промпт попадает маркер `⚠️ ... unavailable`, а не пустая строка;
  (3) на здоровой БД промпт **байт-в-байт** прежний.
- **Тесты:** новые в `tests/test_manager.py` — monkeypatch `get_all_sessions` на бросающий, проверить
  и лог, и маркер. Регресс: существующие тесты сборки промпта.
