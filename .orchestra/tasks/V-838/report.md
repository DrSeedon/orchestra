# V-838 — разбор code-modernization

## Краткий вывод

Первоисточник заметно шире пересказа: это специализированный Claude Code plugin для модернизации legacy-систем, а не единичный «агент для проверки тестов». В версии `1.0.0` есть пошаговые slash-команды, восемь специализированных агентов, исполняемые Python-скрипты проверки, JS-workflow и необязательная панель Claude Code. Главная удачная идея — повторная проверка независимым скриптом по сохранённым артефактам, а не доверие текстовому отчёту модели.

У Orchestra уже имеются близкие механизмы: пользовательский approval gate, собственный acceptance oracle задачи и merge-гейт тестов плюс проверка, что новые тесты защищают изменения кода. Но область и доказательная модель разные: наш merge mutation gate временно возвращает изменённый код к target commit, оставляя тесты воркера, а плагин намеренно вносит поведенческий дефект в новую реализацию и сохраняет запуск тестов. Сравнения двух реализаций и автоматическое формирование списка новых входов у нас нет как универсального инструмента. Это кандидаты на выборочное использование, не повод переносить весь plugin.

Проверен официальный репозиторий на commit [`8bd00f08f0b04705e610cf132fbe2cf5ec44cfe3`](https://github.com/anthropics/claude-plugins-official/commit/8bd00f08f0b04705e610cf132fbe2cf5ec44cfe3), ветка `main`, 2026-10-14. Версия из `.claude-plugin/plugin.json` — `1.0.0`; лицензия `LICENSE` — Apache-2.0. Снимок дерева перечисляет 13 команд, 8 agent-файлов, 17 Python/shell скриптов, 6 JS workflow и 29 TS/TSX/JSON файлов панели/хуков. Выбранные исходники и неизменяемые ссылки зафиксированы в [evidence/source-index.md](evidence/source-index.md).

## 1. Что действительно делает плагин

### Состав и workflow

Входная команда `/code-modernization:modernize` фиксирует intent, предлагает следующий шаг и запускает маршрут, который может остановиться на понимании системы и плане без переписывания. Основной маршрут: preflight → assess → map → extract-rules → review → brief → uplift/transform/reimagine → verify → harden. README называет не только миграцию языка, но и обновление той же платформы и перестройку архитектуры. Результаты и целевой код помещаются под `analysis/<system>/` и `modernized/`; legacy-код размещается в `legacy/<system>` (часто symlink на оригинал).

В дереве присутствуют 13 команд, включая отдельные команды для извлечения бизнес-правил, плана, преобразования, тестирования/сравнения, проверки и hardening; 8 специализированных агентов; Python/shell-инструменты для разбиения, сравнения, сборки отчёта и анализа; JS workflow для извлечения правил, оценки портфеля, uplift и scaffold; TypeScript hooks/UI для live pane. Панель опциональна: README указывает ранний доступ Claude Code function hooks, отключённых по умолчанию. Usage telemetry отдельно конфигурируется в manifest и поступает через хуки Claude Code; это дополнительная поверхность, не часть доказательства эквивалентности. Инвентарь с точными путями — в [evidence/source-index.md](evidence/source-index.md).

### Бизнес-правила, план и гейты

`business-rules-extractor` записывает правила как конкретные Given/When/Then с `file:line`, значениями параметров и уровнем уверенности; текст исходников рассматривается как данные, а не инструкции. Workflow шардирует систему по модулям, затем перепроверяет цитаты referee-агентом и применяет два судейских прохода к P0 правилам. По `modernize-extract-rules.md`, ожидаемый масштаб — 10–15 агентов на shard; в примерах 58 агентов для 4 shards и сотни агентов для большой кодовой базы. Это существенная цена, а не лёгкая «добавка к prompt».

`modernize-brief` — плановый человеческий gate перед сборкой: человек подтверждает вопросы preflight, спорные правила и brief; дальнейший шаг не считается автоматически разрешённым от факта завершения анализа. README описывает шесть точек человеческого решения, включая принятие найденных различий и подписание итогового proof. Security hardening выдаёт проверенный патч, который пользователь применяет сам.

### Сравнение реализаций, мутации и PROVEN

`scripts/compare.py` читает сохранённые выводы старой и новой реализации по одним inputs и сравнивает байты. Отличающиеся поля можно исключить только явно описанными масками; числовая tolerance требует причины и ограничена малыми величинами. Missing output или отличие — не pass. Если человек принимает отличие, оно остаётся в отчёте как approved difference. Self-check comparator отдельно меняет байт копии вывода и требует обнаружить различие.

`modernize-verify` — независимый повторный запуск, предпочтительно в новой сессии: очищает build/test output, заново запускает полные тесты, проверяет runner evidence, делает собственный code canary, заново рассматривает обычные comparison cases и создает не менее десяти новых, не использовавшихся ранее валидных inputs. При доступном legacy оба варианта исполняются на тех же новых inputs, а outputs сравниваются. Malformed cases пробуются только когда intent требует точного сохранения такой терпимости; иначе граница явно указывается как не проверенная. Для правил засчитываются только P0 IDs, привязанные к реально выполнившемуся успешному тесту, не к skipped/pending тесту или заметке.

Итоговый `proof_pack.py` строит один из трёх статусов по правилам, записанным в output, а не по мнению агента: `PROVEN` при прохождении всех применимых checks; `NOT PROVEN` при провале; `PARTLY PROVEN` при отсутствии известного провала, но неполном доказательстве. Для uplift добавляются проверки измеренного baseline, сохранности тестовых файлов и покрытия version deltas. Документация отдельно перечисляет, чего `PROVEN` не доказывает: весь input space, поведение невыявленных правил, скорость, нагрузку, безопасность и concurrency. Когда старая система не может быть запущена и есть только traces, верхний статус — `PARTLY PROVEN`.

Есть две разные мутации. (а) `compare.py` меняет байт output только для проверки, что сравнитель способен обнаружить отличие. (б) verify-команда намеренно меняет важную строку новой реализации и запускает relevant tests; proof-pack требует артефакт результата, где тесты покраснели. README приводит canary как защиту от suite, который просто проходит без проверки поведения. Это не равно одному тесту на случайную syntactic mutation: агент выбирает изменение, которое должно влиять на контракт.

### Человек, лицензия и пределы обещаний

Пересказ верно передаёт: извлечение правил, approval плана, трансформации кода, same-input comparison, свежие граничные входы, мутационный canary и трёхуровневый итоговый статус. Но опускает, что статус вычисляет скрипт из проверяемых артефактов, что человек отдельно одобряет различия и подписывает verification, что «не трогает исходник» лишь частично подкреплено workflow/permission guidance, и что proof ограничен выбранными inputs и не доказывает ряд нефункциональных свойств. Плагин не просто сохраняет оригинал неизменным: build tools могут писать в собственные output directories; shell-скрипты не покрываются file-tool permission rules.

Лицензия — Apache-2.0, она совместима с адаптацией кода и текстов при выполнении требований лицензии, сохранении применимых notices/лицензии и обозначении изменённых файлов. Вендорный Mermaid-asset имеет отдельный файл лицензии; его копирование требует учитывать именно её условия. Идеи/процессы можно описывать самостоятельно без копирования исходных файлов. Это техническая оценка, не юридическое заключение.

## 2. Сопоставление с Orchestra

| Механизм | Что есть сейчас | Существенное отличие |
|---|---|---|
| Приёмка мутацией | `evaluate_test_gate` запускает тесты, затем mutation gate на изменённых source/test paths. Он создаёт временный архив target SHA; контрольный прогон идёт с source изменений воркера, второй — с target source и оставленными тестами воркера. Если изменённые тесты проходят и на target source, изменения не защищены и gate fail. | Это автоматическая проверка диффа «тесты против отката source», а не специально спроектированное изменение реализации по одному бизнес-правилу, как plugin canary. Самостоятельную мутационную проверку оркестратора требуют orchestration prompts, но это отдельное человеческое действие. Смешивать эти два механизма нельзя. |
| Merge test gate | При merge тесты отбираются по changed paths; общий test result FAIL/INCONCLUSIVE блокирует, и strict task oracle требует общего PASS. | Не создаёт полный proof pack на каждую задачу; покрытие зависит от mapping тестов и задачи. Сам по себе `mutation_gate: INCONCLUSIVE` не меняет общий result из PASS и поэтому не блокирует merge: в `merge_test_gate.py` общий статус переключается на FAILED только при mutation FAILED. Это подтверждает `tests/test_merge_test_gate.py::test_mutation_gate_timeout_is_visible_and_not_a_false_pass`, который ожидает внешний PASS плюс видимый mutation INCONCLUSIVE. Это ограничение текущей механики, не предложение менять её в рамках этого исследования. |
| Acceptance oracle | Задача может иметь `acceptance_command`, manifest и required flag; oracle привязывается к ревизии/хэшу. При merge выполняется pinned oracle; required oracle требует PASS. | Это контракт конкретной задачи, не автоматически выведенный эквивалент legacy-реализации. Не каждая задача обязана иметь oracle. |
| Approval gate | В orchestration prompt классы A/B/C: исследование завершается `RESEARCH DONE`, реализация требует слова владельца; отдельная approval граница существует у каждого phase gate. | Уже есть и по полномочиям строже/общей области шире, чем plugin-specific brief gate. |
| Full-cycle | Pipeline role выбирается для исследования/неизвестного объёма; full-cycle выбирает глубину исследования/планирования/проверки и остаётся в пользовательской границе approval. | Общая роль не предписывает массовый fan-out или кросс-языковую модернизацию. |
| «Test the core» | Постоянное правило запрещает проверять переформулируемый текст и просит тестировать стабильное ядро; требует до добавления теста назвать конкретный production failure. | Совпадает по намерению фильтровать тесты; автоматически генерируемый boundary pack и same-input cross-implementation comparison у нас не являются стандартом. |

Подробные локальные anchors: `.orchestra/pipelines/default/prompts/modules/orchestration.md:11-42, 91-100`, `report-format.md:28-31`, `code-quality.md:50-79`, `worker-lifecycle.md:39-52`, `pipeline.yaml:96-122`; `app/merge_test_gate.py:581-620, 738-885, 896-983`, `app/merge_operations.py:1723-1895`, `app/acceptance.py:240-430`, `app/tm.py:116-153`. Статус и target SHA merge gate сохраняются в результатах merge operation/receipt; это не три литературных статуса доказательства плагина.

Важное различие о human mutation: orchestration prompt просит оркестратора принять решение по диффу, тестам и собственному mutation check; программный gate также проводит rollback-source проверку. Если этот программный mutation probe возвращает INCONCLUSIVE, общий test-gate result всё же может остаться PASS (mutation FAILED — единственный статус, который `evaluate_test_gate` явно поднимает до общего FAILED). Плагин canary требует доказательства, что внесённая мутация покраснила тесты; это не то же, что незавершённый автоматический probe. Plugin canary не заменяет review или approval. Оба подхода не делают вычисляемое PASS эквивалентом продуктового одобрения.

## Итог

Главная идея уже воплощена не в одном месте: task-specific oracle задаёт ожидаемый check; merge-time gate запускает tests; mutation sub-gate проверяет, что тесты перестали проходить на target source; оркестратор принимает работу по diff и evidence; approval gate остаётся человеческим. Отличие plugin — система сохраняет трассируемый per-module proof dossier и отдельно запускает same-input/fresh-input сравнения старого и нового вариантов. Её стоит рассматривать только для задач, где старое поведение исполнимо и является независимым oracle; без такого предмета три статуса и десять случаев не дадут дополнительного факта.

Разумные предложения владельцу, не решения: применить paired comparison + fresh cases для конкретной языковой/major-version миграции; явно зафиксировать независимую verify-фазу в её assignment; не внедрять plugin-wide rule mining, массовую adjudication и PROVEN vocabulary в каждый проект. Реализация и изменение правил/промптов не выполнялись.
