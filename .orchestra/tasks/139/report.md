# #139 — фиксированный барьер зависимостей + устойчивый снапшот маршрутов

## Главное: тест НЕ был протухшим, протухло окружение

Диагноз из #139 (и мой собственный из #114) звучал так: «starlette 1.3.1 сломал
`include_router`, тест устарел». Это оказалось неверно в решающей детали.

`uv.lock` пинит **starlette 1.1.0 / fastapi 0.136.3**. Под этими версиями старый тест зелёный,
`app.routes` содержит все 93 маршрута. В венве же стоял **starlette 1.3.1** — окружение
пере-резолвилось мимо лока. То есть пункт 3 (churn лока) был ПРИЧИНОЙ пункта 2, а не
соседней проблемой.

```
$ uv run pytest tests/test_routes_surface.py -q   # под залоченными версиями
1 passed
```

Вывод в личную память: «версия в venv» ≠ «версия в локе»; при падении «из-за старого кода»
сперва сверять установленную версию с залоченной.

## Корневая причина churn — вне репозитория

`~/.config/uv/uv.toml` на машине юзера:

```toml
exclude-newer = "7 days"
```

Скользящий барьер, глобальный на всю машину. Каждый `uv` резолвит «сегодня минус 7 дней»,
видит расхождение с коммитнутым локом и переписывает его. Поэтому снятие `[options]` из
`uv.lock` в `88a3a84` не помогло, а сделало хуже: без записи в локе uv считает барьер
«addition» и пере-резолвит гарантированно.

Формулировка задачи («в `uv.lock:14-15` рядом с `exclude-newer` стоит `exclude-newer-span`»)
на текущем дереве не подтвердилась — этих строк в репо не было вовсе, их удалил `88a3a84`.
Проверено `grep` по `uv.lock`/`pyproject.toml`/`uv.toml` + `git log -S`.

## Что перебрано и почему отвергнуто (замеры)

| Вариант | Результат |
|---|---|
| `exclude-newer` только в `pyproject.toml` | **не помогает** — uvicorn 0.48 → 0.51 всё равно |
| `frozen = true` в `[tool.uv]` | **не существует** — uv 0.9.28 ругается `unknown field 'frozen'` |
| `--frozen` / `UV_FROZEN=1` | работает, но требует, чтобы КАЖДЫЙ агент помнил флаг |
| Барьер с датой новее лока | **опасно** — следующий `uv lock` обновил ~40 пакетов |
| **`[options] exclude-newer` в обоих файлах** | **принято** |

Отдельно: дата барьера = `2026-07-09T10:16:55Z`, ровно та, что удалил `88a3a84`. Она совпадает
с содержимым лока (самый свежий пакет загружен 2026-07-08), поэтому не тянет ни одного
обновления. Проверка: `uv lock --locked` → `Resolved 99 packages`, без жалоб.

**Обоснование выбора одной фразой:** барьер сам по себе не пин (пакеты старее даты всё равно
едут вверх) — настоящий пин это `uv.lock`, поэтому чиним пассивно, записью барьера в оба файла,
чтобы защита работала без флагов и без памяти агента.

### Доказательство, что churn закрыт

```
BEFORE: 29c665ebca5359d8
$ uv run python -c "import fastapi,starlette; ..."   # БЕЗ UV_FROZEN
OK 0.136.3 1.1.0
AFTER : 29c665ebca5359d8
```

Четыре подряд `uv run` + `uv run pytest` — лок байт-в-байт. Ставятся залоченные версии.

## Снапшот маршрутов, переживающий следующий апдейт

`_collect()` спускается во вложенные роутеры по ДВУМ атрибутам: `routes` (Mount, старые
версии) и `original_router` (обёртка `_IncludedRouter` из starlette 1.3+). Имя атрибута между
версиями менялось — проверяем оба, плюс защита от циклов по `id()`.

Добавлен `test_route_surface_is_discoverable`: порог `>= 20` маршрутов. Он ловит худший случай —
когда обход «успешно» находит 4 автодок-маршрута, снапшот сходится сам с собой и guard молча
умирает.

**Поверхность не изменилась**, показывать диффом нечего: под обеими версиями обход даёт те же
93 маршрута, что и в снапшоте.

```
surface под starlette 1.3.1: 93 | snapshot: 93
IDENTICAL: True     added: []     removed: []
```

(проверено в отдельном венве `/tmp/sl13` с fastapi 0.140.7 / starlette 1.3.1; старый плоский
обход там находил 4)
