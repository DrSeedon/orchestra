# V-655 — удалено живое хранилище задач, восстановлено из SQLite

**Что случилось.** 28.09 ~11:00 UTC, во время чистки заполненного на 100% диска по слову владельца («Удаляй», «Почисти всё безопасное»), оркестратор отправил в корзину `data/storage-preflight-final-20260908` как «старую копию базы» и затем очистил корзину. Внутри лежало живое Git-хранилище задач: `ORCHESTRA_TASK_REPOSITORY=/home/kesha/orchestra/data/storage-preflight-final-20260908/tasks`. Живость проверялась только по `ORCHESTRA_DB_PATH` и открытым файлам процесса; переменную хранилища задач никто не сверил, а Git не держит файлы открытыми.

**Последствие.** С ~11:00 до ~11:40 UTC у всех проектов падали `merge_worker` (`fatal: cannot change to '…/tasks'`) и операции с задачами. Первым сообщил katya-work-orchestrator (report_bug 20260928T113122).

**Восстановление.** Копий хранилища не было: хаб `~/.local/state/orchestra/task-sync.git` устарел на 08.09, у ноутбука отдельное хранилище. Пересобрано из проекции `tm_tasks` живой базы (2010 задач, состояние на 10:56 UTC) скриптом [rebuild.py](rebuild.py): каждая запись проходит `task_store._validate`. Поля, которых нет в SQLite (`creation_key`, `creation_fingerprint`, `evidence_refs`, `acceptance.manifest_paths/required`), взяты из копии хранилища на ноутбуке для 1653 задач; для остальных 357 — синтетические `recovered-<id>` и пустые списки. Живой `refresh()` перепроектировал базу, создание задачи V-655 прошло (коммит `fae43d1` в новом хранилище).

**Что утрачено.** Git-история изменений задач VPS до 28.09 (кто и когда менял статус). Текущее состояние всех задач сохранено. Идемпотентность повторного `task_create` с прежним `request_key` для 357 задач не восстановима.

**Урок.** Перед удалением каталогов в `data/` сверять ВСЕ пути из `/proc/<pid>/environ` живого процесса (`ORCHESTRA_*`), а не только БД; чистка корзины после переноса туда данных Orchestra — только после суток работы без ошибок.
