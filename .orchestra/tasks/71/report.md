## Замер до и после — на живом ответе

```

он же без system_prompt:   1 545 б gzip ( 5 875 распакованных)
снимется: 19 804 б, останется 7.2% провода
```

«После» снято пережатием ЖИВОГО ответа без поля — на сервере код ещё старый. Это и есть
**ожидаемое число после выката: ~1 545 байт по проводу**, проверяется одной командой:

```bash
curl -s -o /dev/null -w '%{size_download}\n' -H "Authorization: Bearer $TOK" \
     -H 'Accept-Encoding: gzip' https://orchestra.seedon.ru/api/orchestrators
```

Цель «снять ~7 КБ» перевыполнена: снимается 19.8 КБ, ответ уходит глубоко внутрь
надёжного конверта (15 КБ) с запасом в десять раз.

## Что сделано

Одна строка в роуте `/api/orchestrators` (`app/routes/system.py:1430`):
`o.pop("system_prompt", None)` — внутри общего цикла, который проходит по `result`,
то есть **по обоим путям сразу**: активные сессии (`to_dict()`) и строки из БД
(`get_all_sessions()`) лежат в одном списке. Половинчатый фикс, который #65 нашёл в уже
«починенном» месте, здесь невозможен по конструкции — резать в двух местах просто негде.

Источник (`to_dict()`) не тронут: его же отдаёт `/api/sessions/{name}`, где промпт нужен.
Отдельная дверь к полному промпту работает как работала — `GET /api/sessions/{name}/prompt`.

## Второй вызов на первой загрузке — диагноз для frontend, я не трогал

Причина не в двух местах кода, а в начальном значении дросселя.

- **Место**: `app/static/js/app.js:5788` — `let _orchFreshAt = 0;`
- **Условие**: `app.js:5820` — `if (Date.now() - _orchFreshAt >= _ORCH_REFRESH_MS)`
- **Что происходит**: при старте `_orchFreshAt` равен нулю, поэтому первый же
  `refreshSessions` (через ~0.5 с после `loadOrchestrators`) считает только что полученные
  данные протухшими и тянет их заново.
- **Доказательство** (врезка в `window.fetch`, стек вызывающего в консоль):
  ```
  +0.36 с  at api <- at loadOrchestrators
  +0.85 с  at api <- at refreshSessions
  ```
- **Правка на одну строку**: в `loadOrchestrators()` (`app.js:1166`) после успешного
  ответа проставить `_orchFreshAt = Date.now();` — тогда первый `refreshSessions` попадёт
  в дроссель и не продублирует запрос.

Дальше дроссель работает: за 20 с наблюдения три вызова (0.30 / 0.72 / 18.64 с), прежнего
спама раз в 3 с уже нет.
