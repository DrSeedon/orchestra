# #50 — исследование: как доставить ФАКТ недоставки в контекст ждущего агента

## Вопрос

- **Контекст**: в #47 измерено, что запись `logs` типа `system` в контекст агента не попадает
  (`get_logs` читается только для `_build_runtime_handoff`, и там берутся только
  `user_message` и `text`). Ждущий оркестратор о недоставке не узнаёт.
- **Проверяемое утверждение**: факт можно довезти, пристроив его к СЛЕДУЮЩЕМУ успешному
  сообщению этому же агенту — это не ретрай, исходное сообщение не пересылается.
- **Измеримый исход**: текст, фактически ушедший в CLI (`backend.send`), содержит факт.

## Что измерено

**Точка врезки существует и доказана.** Стенд: настоящая сессия, мок бэкенда,
перехват `backend.send`:

```
В БЭКЕНД УЕХАЛО:
    обычное сообщение от оркестратора
ВЫЗОВОВ backend.send: 1
```

То есть в CLI уезжает ровно строка `message`; всё, что к ней приписано, агент читает как
часть входящего сообщения. **Прецедент в проде уже есть**: `app/session.py:688` точно так же
приписывает к сообщению блок `[Orchestra platform note: …]` с обновлённым системным
промптом. Механизм не новый — новым будет только источник текста.

**Путей отправки два**, и оба заканчиваются `backend.send`:
| путь | условие | строка |
|---|---|---|
| mid-turn inject | `status == RUNNING` и рантайм это умеет | `app/session.py:652` |
| обычный старт хода | `IDLE`/`WAITING` | `app/session.py:756` |

Гасить факт можно только ПОСЛЕ возврата из `backend.send` — до этого доставки не было.

**Существующая очередь для этого не годится.** `_pending_messages` (`app/session.py:251`)
живёт только в памяти; в аудите #35 это уже записано как P1 «потеря сообщений при
рестарте». Очередь фактов обязана быть durable, иначе она теряется ровно в том сценарии,
ради которого делается (недоставка → рестарт → ждущий агент так и не узнал).

## Кто производит факты

Три места, где сегодня пишется только строка в журнал/историю:

| место | событие |
|---|---|
| `app/manager.py` `_record_undelivered_auto_report` (#47) | автоотчёт воркера не доставлен оркестратору |
| `app/notify.py` `report_undelivered` (#30) | не доставлено пробуждение / результат bg-job |
| `app/notify.py` `_record_undelivered_bug` (#56) | не доставлено уведомление о баг-репорте |

Адресат у всех один и тот же — сессия, которой не удалось доставить. Это и есть ключ очереди.

## Требования, которые задают форму решения

1. **Не растёт бесконечно.** Нужен потолок на сессию (кандидат: 20 записей) и сжатие
   переполнения в одну строку «и ещё N событий», а не молчаливое отбрасывание.
2. **Не дублирует одно событие.** Нужен ключ дедупликации: у баг-репорта это `record_id`,
   у автоотчёта — id хода/сессии воркера, у пробуждения — id джоба. Повторная попытка
   доставки того же события не должна класть вторую запись.
3. **Гасится только по факту доставки**, иначе «доставили» и потеряли.
4. **Не ретрай**: в контекст едет строка «было такое-то событие, доставить не удалось»,
   а не исходное сообщение.

## Риски

1. **Врезка в `send()` — общий рантайм.** Ошибка здесь ломает доставку всем; блок должен
   собираться так, чтобы любой сбой очереди не мешал самому сообщению (факт важен, но
   сообщение важнее).
2. **Контекст агента не бесплатен.** Каждый факт — это токены в чужом ходу; отсюда потолок
   и сжатие, а не «все накопленные события».
3. **Дубли при повторной недоставке одного и того же события** — без ключа дедупликации
   очередь заполнится одинаковыми строками.

## Чего я НЕ проверял

- **Поведение при ОТКАЗЕ `backend.send`**: стенд на этом повис (внутри есть свои ретраи),
  и я его снял, чтобы не вешать сьют. Для плана важно только правило «гасить после
  возврата», но сам путь отказа надо будет пройти тестом в Phase 3.
- Не проверял mid-turn inject живьём (нужен RUNNING-агент с рантаймом, который это умеет) —
  измерен только обычный путь.
- Не смотрел, как блок факта выглядит у Codex-рантайма: у него другой формат входящего
  сообщения (`<current-user-message>` в обычном пути), и врезку надо делать до этой обёртки.

## Вердикта Codex нет

Codex недоступен до 08.08. Самокритика: «прецедент в проде» — это ОДИН механизм
(инъекция промпта), и он работает на первом сообщении после резюма. Мой случай — любое
сообщение, в том числе mid-turn; на этом пути прецедента нет, и его надо проверять
отдельно, а не считать доказанным по аналогии.
