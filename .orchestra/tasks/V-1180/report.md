### Cut-session binding and timestamp boundary — duplicate risk remains

Startup captures session IDs in `restart_cut_turns` in the same transaction that resets running/interrupted session statuses; it then calls `requeue_cut_turn_steers` only for those obligations. That function does not bind receipts to a native turn ID. It selects the `turn ended` log with greatest SQLite `id`, parses that row's `ts`, and considers every SUBMITTED `steered:` receipt for that session with `updated_at > ts` to be from the cut turn. `AgentSession._log` submits writes to a four-worker executor and returns immediately; there is no per-session ordered log queue and a hard process death can lose queued log writes.

Two synthetic SQLite outcomes establish the limitation:

- With a historical successful steer and no committed `turn ended` log (the async log was lost at process death), a session persisted as running yields `requeue_cut_turn_steers == 1`; the historical successful body is placed in the mailbox. This is the failure window already described in the candidate notes.
- I forced the actual `_log` executor wrapper to delay the earlier end-log write by 150 ms while a later end-log write completed first. SQLite then held `(id=1, ts=later)` followed by `(id=2, ts=earlier)`. Because selection is `MAX(id)` rather than max event time/turn identity, the older timestamp became the cutoff; a receipt timestamp between the two ended up in the mailbox along with the current cut receipt. The earlier receipt represented a historically successful turn and was **re-forwarded**. The delay is a controlled schedule, not a measurement of natural frequency; source code allows it because writes run concurrently and ordering is not serialized.

Therefore “do not redeliver historically successful turns” holds for persisted, insertion-ordered end logs, but is **not guaranteed** across log loss or executor reordering. This is an observed false-recovery mechanism, with frequency unmeasured. The task's requested absence check cannot be accepted as a universal property. A further unverified cut-binding edge is a process death after a steer receipt commits but before the asynchronous session-status persist commits: if DB status remains `idle` and no `restart_cut_turns` row exists, boot's cut-session query will not call recovery. I did not force this status/receipt write interleaving.

Initial-input behavior remains deliberately distinct: known initial routes are stored with the plain turn ID and are not selected by the `steered:` recovery query. This matches the prior code contract that initial inputs are not mid-turn steers. Whether the actual Codex app-server preserves an interrupted initial input across its native history is unverified; no CLI was run. The at-least-once tradeoff also remains: already-consumed but unconfirmed steers can be resent after an interrupted turn; recovery copies are hidden from chat.
