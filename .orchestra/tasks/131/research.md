# #131 — Переезд рабочего контура Orchestra с ноутбука на VPS

Дата: 2026-08-03. Фаза 1 (research). Все проверки на VPS — **только чтение**.
Codex не привлекался (квота исчерпана до 8 августа) — second opinion отсутствует, см. «Ограничения».

## Question

Целесообразен ли перенос рабочего контура Orchestra с ноутбука на Contabo VPS
`158.220.127.161`?

- **Контекст**: дома лёг проводной провайдер, юзер работает через мобильный. На VPS прямой
  интернет, HTTPS-дашборд `https://orchestra.seedon.ru` уже поднят.
- **Change under test**: VPS становится основным control plane (спавн/мерж/дашборд).
- **Baseline**: текущее состояние — ноутбук основной, на VPS протухший второй инстанс.
- **Measurable outcome**: (а) может ли оркестратор на VPS спавнить и мержить воркеров
  для 8+ живых скоупов; (б) переживёт ли тамошняя БД обновление кода до main.

## Hypotheses considered

| # | Гипотеза | Фальсификатор | Итог |
|---|---|---|---|
| H1 | Полный переезд: клонировать все репозитории на VPS, мигрировать БД | Проекты, которые физически/юридически не переносятся (диск, приватные данные, локальные сервисы) | **Частично REFUTED** — код влезает, но рабочие данные и локальные привязки нет |
| H2 | Раздельный контур: VPS ведёт то, что клонируется чисто; ноут держит остальное | Две БД/два дашборда неюзабельны на практике | **CONFIRMED как рекомендация** |
| H3 | Переезд не нужен, узкое место — сеть, лечится без миграции | VPS ходит к API чисто, ноут нет | **REFUTED** — см. F7, но не в пользу H1 |

## Findings

### F1. На VPS крутится не «пустой стенд», а боевая машина с чужими сервисами — CONFIRMED
`systemctl list-units --state=running` [измерение]: помимо `orchestra.service` там живут
`kesha-bot-vps.service`, `dnd-game-master.service`, `nginx`, `telegram-bot-api`,
`mtg` (MTProto), `hysteria-server`, `tinyproxy`, `orchestra-proxy`, `fail2ban`.

**Это тот же хост, что раздаёт прокси `Contabo DE|:12343` в `PROXY_LIST`** и обслуживает
телеграм-бота Кеши. Ресурсы: 4 ядра, 7.8 ГБ RAM (2.2 занято, 5.5 доступно), **swap = 0**,
диск 145 ГБ / 133 ГБ свободно, LA 0.17.

Риск: **swap отсутствует**. Пара тяжёлых воркеров + существующие сервисы → OOM-killer
прилетит по всему хосту, включая бота Кеши и прокси, через который ноут ходит к API.
Confidence: CONFIRMED (прямое измерение `free -h`, `df -h`, `nproc`).

### F2. Пользователь `kesha` — владелец процесса, установка одна — CONFIRMED
`systemctl show orchestra`: `User=kesha`, `WorkingDirectory=/home/kesha/orchestra`,
`EnvironmentFiles=/home/kesha/orchestra/.env`,
`ExecStart=/home/kesha/.local/bin/uv run uvicorn app.main:app --host 0.0.0.0 --port 8888`.
Аптайм процесса — с 31 июля 06:05 CEST, то есть 3 дня.

Оговорка к формулировке задачи: `kesha` — это **юзер, под которым запущено всё хозяйство**
на этом VPS (и бот, и Orchestra), а не «инстанс Orchestra, принадлежащий боту».
Confidence: CONFIRMED.

### F3. Сессий на VPS почти нет — 3 idle, все на самой Orchestra — CONFIRMED
Чтение БД через `sqlite3` модуль Python (бинарь `sqlite3` на VPS действительно отсутствует,
факт оркестратора подтверждён):

```
('Orchestra-orchestrator', '/home/kesha/orchestra', 'claude-opus-4-6[1m]', 'claude', 'idle', 'orchestrator')
('frontend',              '/home/kesha/orchestra', 'claude-opus-4-8[1m]', 'claude', 'idle', 'worker')
('back',                  '/home/kesha/orchestra', 'claude-opus-4-8[1m]', 'claude', 'idle', 'worker')
counts: [('archived', 1), ('idle', 3)]
```

**Терять на VPS нечего.** Ни одной running-сессии, ни одного скоупа кроме самой Orchestra.
Обновление кода не прервёт там никакой работы. Confidence: CONFIRMED (прямое чтение БД).

### F4. Ответ на «старые опусы тоже обновить» — CONFIRMED
Это именно про F3: на VPS сессии сидят на **Opus 4.6 и Opus 4.8**, тогда как локальный
контур давно на `claude-opus-5[1m]` (74 из 85 живых сессий). «Обновить старые опусы» =
переключить эти 3 сессии на `claude-opus-5[1m]`.

**Грабли из CLAUDE.md применимы напрямую**: `UPDATE sessions SET model=...` на живом сервере
будет перезатёрт из памяти при auto_resume. Менять только при остановленном сервисе и
перепроверять после старта. Алиас `opus` не использовать — пинить `[1m]`, иначе контекст
схлопнется до 200K. Confidence: CONFIRMED (модели прочитаны из БД; механика — известные грабли проекта).

### F5. Обновление кода: миграции БД безопасны — CONFIRMED ЭКСПЕРИМЕНТОМ
Отставание: **256 коммитов** (`git rev-list --count 41c7dc4..main` = 256; оценка «255» была
близка). Дата VPS-коммита `41c7dc4` — 17 июля 2026. `app/db.py` менялся в 13 коммитах.

Схема на VPS не содержит 5 таблиц, которые есть локально: `turn_usage`, `tool_errors`,
`merge_operations`, `improvement_rules`, `voice_costs`.

**Эксперимент** (pass/fail определён ДО запуска: PASS = `init_db()` без исключения, ни одной
потерянной строки, новые таблицы созданы). Копия боевой БД VPS прогнана через `init_db()`
текущего main в `/tmp/m131/`:

```
init_db: OK
rows lost: NONE
new tables: ['improvement_rules', 'merge_operations', 'tool_errors', 'turn_usage', 'voice_costs']
sessions before/after: 4 4
```

Причина устойчивости — `_migrate()` в `app/db.py:370` строго аддитивен: `CREATE TABLE IF NOT
EXISTS` + `ALTER TABLE ADD COLUMN` под проверкой `PRAGMA table_info`, с комментарием в коде
«Never drop columns». Ни одного `DROP`/`RENAME`.

Оговорка: копировался только `orchestra.db` без `-wal` (247 КБ несведённых данных). На
результат миграции схемы это не влияет, но при реальном переезде БД снимать корректно —
см. шаг 2 плана. Confidence: **CONFIRMED (прямое измерение, воспроизводимо)**.

### F6. `orchestra.seedon.ru` — рабочий HTTPS-фронт с авторизацией — CONFIRMED
`/etc/nginx/sites-enabled/orchestra`: `server_name orchestra.seedon.ru` → `proxy_pass
http://127.0.0.1:8888`, сертификат Let's Encrypt (Certbot), `:80` → 301 на HTTPS.
Есть `proxy_http_version 1.1` + `Upgrade`/`Connection upgrade` + `proxy_buffering off` +
`proxy_read_timeout 86400` — **SSE-стрим дашборда будет работать**, это не дефолтный конфиг.

Проверка снаружи [измерение]:
```
https://orchestra.seedon.ru/            -> HTTP 302   (редирект на логин)
https://orchestra.seedon.ru/api/agents  -> HTTP 401   (без cookie не пускает)
```
Авторизация включена (`DASHBOARD_USER`/`DASHBOARD_PASSWORD` в `.env` VPS). В журнале видны
живые запросы с `128.204.66.142` — **юзер уже сейчас ходит на этот дашборд из браузера**.
Confidence: CONFIRMED.

### F7. Прямой доступ к Anthropic API с VPS работает, прокси не нужен — CONFIRMED
```
env -u HTTPS_PROXY -u HTTP_PROXY curl https://api.anthropic.com/v1/messages
  -> HTTP 405 за 0.298s
env -u HTTPS_PROXY -u HTTP_PROXY curl https://github.com
  -> HTTP 200 за 0.201s
```
HTTP 405 (Method Not Allowed) на GET к POST-only эндпоинту — **правильный ответ живого API**,
то есть TLS и маршрут целы; это не 403-блокировка как в РФ. В `.env` на VPS строки
`HTTPS_PROXY`/`HTTP_PROXY` **закомментированы** с пометкой «not needed — VPS is in EU/Contabo».

CLI на месте: `/usr/bin/claude` версии 2.1.197, креды подписки —
`~/.claude/.credentials.json` (обновлён сегодня 02:24), API-ключей нет, что соответствует
правилу «только подписка». Confidence: CONFIRMED (прямое измерение).

**Это подтверждает мотивацию юзера**: на VPS сеть действительно здоровее. Но само по себе
это фальсифицирует H3 лишь частично — сетевую проблему ноутбука решает и текущая схема
(ноут ходит через прокси на этот же Contabo), просто менее надёжно на мобильном.

Модели живых сессий: `claude-opus-5[1m]` — 74, `gpt-5.6-sol` — 6, `claude-sonnet-5[1m]` — 2,
`gpt-5.5` — 2, `claude-sonnet-4-6` — 1. Confidence: CONFIRMED (прямые запросы к БД).

## Counter-evidence — что говорит против переезда

1. **F1 — общий хост.** Orchestra на VPS делит 7.8 ГБ RAM **без swap** с телеграм-ботом
   Кеши, DnD-сервисом и tinyproxy, который сам раздаёт прокси `:12343` ноутбуку. Перенос
   боевой нагрузки (несколько воркеров Opus) на этот хост рискует уронить сервисы, от
   которых зависит в том числе резервный сетевой путь ноутбука. Это аргумент против H1 и
   за поэтапность.
2. **F8.2 — данные не переезжают.** Для Parsing (7 сессий) и Sensar (10 сессий) предмет
   работы — неотслеживаемые 82 ГБ и 15 ГБ. Их перенос по мобильному каналу нереалистичен.
3. **F8.1 — `stargate-tactics` без remote.** 6 сессий на репозитории, существующем в одном
   экземпляре. Любой перенос требует ручного копирования и повышает риск потери истории.
4. **Против H3 (не переезжать вовсе)**: F7 показывает измеренный прямой доступ 0.3 s без
   прокси, а F6 — что юзер уже фактически пользуется VPS-дашбордом. Полный отказ от переезда
   игнорирует реальную проблему связи.
5. **Конфликт оценок**: вводные задачи давали «61 сессия» и «255 коммитов»; измерено 85 и
   256. Расхождения мелкие, но показывают, что цифры до перепроверки использовать нельзя.

## Вердикт по главному узлу (код проектов)

Ни «клонировать всё», ни «переезд нецелесообразен». Расслоение по стоимости переноса:

- **Группа A — переносится дёшево и осмысленно** (`orchestra` 32 МБ .git, `seedon` 477 МБ,
  `VPN-Service` 20 МБ, `COG-second-brain` 48 МБ): чистые git-репозитории с remote, работа
  ведётся по коду, а не по локальным данным. **33 из 85 сессий.**
- **Группа B — остаётся на ноуте** (`Parsing` 82 ГБ `_research/`, `Sensar` 15 ГБ `backup/`,
  `University` 9.8 ГБ, `stargate-tactics` без remote): предмет работы — локальные данные
  либо репозиторий без удалённой копии. **29 сессий.**
- Остальные скоупы (Aperant, kesha-tg-bot, polus, WebView и т.д.) — по мере надобности.

То есть **H2**: постоянный двухконтурный режим, а не разовая миграция. VPS — основной для
группы A и для разработки самой Orchestra; ноут — для группы B и как запасной путь.
Дашборд VPS уже доступен снаружи по HTTPS (F6), поэтому «работать через дашборд на VPS»
для группы A выполнимо без переноса локальной БД вообще.

## Risks

| Риск | Вероятность | Последствие | Митигация |
|---|---|---|---|
| OOM на VPS без swap валит бота Кеши и tinyproxy | Средняя | Падает и рабочий контур, и резервный прокси ноутбука | Добавить swap ДО нагрузки; лимит на число одновременных воркеров |
| `git pull` конфликтует по `uv.lock` (F10) | Высокая | Обновление останавливается на полпути | `git stash` перед pull; VPS-копию не считать источником правды |
| Перенос локальной БД тянет мёртвые скоупы | Высокая | Спавн падает `repo_path does not exist` (`workspace.py:239`) | НЕ переносить БД целиком; см. план, шаг 6 |
| `sessions.model` откатывается после рестарта | Высокая | «Старые опусы» остаются на 4.6/4.8 | Править при остановленном сервисе, перепроверять после старта (F4) |
| Кириллица/пробел в пути Sensar | Средняя | Ломает скрипты переноса | Группа B на VPS не переносится — риск снимается |
| Два контура расходятся по коду | Средняя | Мержи в разные стороны, конфликты | Один проект ведётся ровно в одном контуре; `origin` — единственная точка синхронизации |
| Дашборд VPS открыт в интернет | Уже реализовано | Компрометация = доступ ко всем агентам | Проверено: 302/401, авторизация есть (F6). Пароль сменить при переезде |
