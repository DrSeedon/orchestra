# #426 — почему `task_create`/`task_update` виснут на 30 с

Замер 01.09.2026, боевой процесс `orchestra` (MainPID 1514557), py-spy через ssh-хоп
(`ptrace_scope=1` не даёт снять стек из юнита напрямую).

## Что померено

| вызов | время | метод |
|---|--:|---|
| `GET /api/tm/tasks` (три подряд) | 1.36 / 1.68 / 2.04 с | curl `-w %{time_total}` |
| `POST /api/tm/tasks` | **20.84 с** | curl, задача #426 создана |
| `PUT /api/tm/tasks/426` | **19.60 с** и **18.12 с** | curl, два прогона |

Клиентский дедлайн MCP — 30 с (`app/mcp_stdio.py:514`, `kwargs.pop("timeout", 30)`).
То есть запись задачи идёт **впритык к таймауту**: обычный прогон 18–21 с, любая
дополнительная нагрузка переваливает за 30 → `transport_timeout: ReadTimeout` при уже
committed записи.

## Кто владелец времени

8 срезов стека, снятых по 2 с в течение одного `PUT` (кадры `app/`, число попаданий):

```
8  app/routes/tm.py:272          — await asyncio.to_thread(_do)
7  app/tm.py:2181                — shadow-путь записи
7  app/ia/runtime.py:156,171     — TaskStore.task_update → _changed → _head_writer
5  app/ia/runtime.py:661         — _refresh_current_projection()
2  app/ia/projections.py:30,40,168
1  app/ia/runtime.py:660         — _commit_canonical()
```

Владелец — `KnowledgeRuntime._record_task_head` (`app/ia/runtime.py:642-661`), который на
**каждую** запись задачи делает три дорогие вещи:

1. `evidence_records()` (`:893-899`) — `copy.deepcopy` кэша из **47 834** evidence-записей
   (191 МБ на диске). Вызывается не один раз: `_record_task_head` берёт её сам, и ещё
   дважды её берёт `_refresh_current_projection` через `_retained_evidence_records()`
   (`:1079` и `:1087`).
2. sha256 по всему отсортированному списку evidence.
3. `_commit_canonical()` + `_refresh_current_projection()` — git-коммит в стор из 47 834
   файлов и пересборка SQLite-проекции `current.db` размером **2.32 ГБ**.

Разложение измерено отдельным прогоном на тех же файлах (вне сервера, read-only):

| стадия | время |
|---|--:|
| `glob` по evidence | 1.87 с |
| чтение 47 834 json (один раз, потом кэш) | 50.55 с |
| `copy.deepcopy` кэша | **1.03 с** за вызов |
| sha256 по evidence | **1.01 с** |

То есть ≈4–5 с из 20 уходит на копии и хэш evidence, остальные ≈14 с — git-коммит и
пересборка проекции на 2.3 ГБ.

## Почему это раньше не находилось

`uvicorn` пишет строку access-лога в момент отправки ответа. Клиент, оборвавший запрос по
30-секундному дедлайну, строки не оставляет вовсе. Отсюда прямой признак частоты:

| день | строк `POST /api/tm/tasks` в журнале | задач создано | не дождались ответа |
|---|--:|--:|--:|
| 30.08 | 5 | 9 | 4 |
| 31.08 | 4 | 7 | 3 |
| 01.09 | 0 | 1 | 1 |

**8 из 17 созданий задач (47%) не дождались ответа**, при этом все 17 записались.
Отсюда же «исход неизвестен» в баг-репортах: запись коммитится за первые ~3 с, а ответ
уходит через 20.

**Отвергнуто:** вечное зависание корутины. Полный `py-spy dump` в покое показал все 16
потоков `idle`, ни одного кадра `app/` — незавершённых запросов в процессе нет.

## Что чинить (варианты, не решение)

- `evidence_records()` отдаёт `deepcopy` защиты ради; вызывающие внутри одной записи могли
  бы делить один снимок — снимает ≈3 с из 20 без изменения семантики.
- `_refresh_current_projection()` на каждую запись задачи пересобирает проекцию, которая
  задачам не принадлежит. Кандидат — отложить её за пределы синхронного ответа.
- Хэш головы считается по всем 47 834 evidence при изменении ОДНОЙ задачи — кандидат на
  инкрементальный пересчёт.

Ни один вариант не выбран: цена и риски не мерены, это предмет отдельного тикета.
