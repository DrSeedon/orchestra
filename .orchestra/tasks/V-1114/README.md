# V-1114 — исследовательские артефакты

Ничего в этом каталоге не подключено к Orchestra и не заменяет память или правила.
`report.md` — результат исследования с ограничениями. `prompts.md` — три sleep- и два
wake-кандидата, модельные прогоны которых пока **не выполнены**.

## Что действительно запущено

Из корня копии, с provisioned uv 0.11.28 и штатной `.venv`:

```bash
export PATH="$HOME/.local/share/orchestra/tools/uv/0.11.28/bin:$PATH"
uv run --frozen python .orchestra/tasks/V-1114/harness.py measure
uv run --frozen python -m pytest .orchestra/tasks/V-1114/test_harness.py -q
```

`measure` проверяет SHA исходных документов и не перезаписывает зафиксированный манифест
при изменении источника. Пишет результаты только рядом с собой. Сеть, БД, CLI моделей,
сервисы, ключи и app не используются. Настройка uv может получить только locked зависимости;
сами проверки выполняются офлайн. `app/` отсутствует в копии, импорт app невозможен.

`bank.json` — 40 вопросов с эталоном и проверяемыми цитатами-опорами; не давать этот файл
sleep-модели или answering-модели. Для answering отправлять `questions-public.json`.
Идентификатор Mxx — номер строки исходного файла памяти, в котором один абзац.
Это локаторы данного фиксированного снимка, не глобальный протокол памяти.

`proxy-*.md` — **механические** варианты: заголовки, заголовки с ID, первые/последние
160 символов каждого абзаца. Они не являются ответами на S1/S2/S3 и не прошли семантическую
консолидацию. `offline-measurements.json` и `offline-per-case.json` содержат точные размеры
и сохранность буквальных опор, не accuracy Claude. У каждого модельного поля `null`, n=0.
Исходный архив не дублируется: используется неизменённый `.orchestra/workers/Orchestra-orchestrator.md`
с SHA из `source-manifest.json`. Если источник изменился, для нового опыта нужен новый
отдельный снимок/каталог и переоценка эталона, не тихая замена старого SHA.

## Продолжение в окружении родителя

1. Проверить живой model ID/effort читателя памяти; не угадывать его по исторической заметке.
2. Запустить sleep-кандидаты через настоящий `dynamic_workflow`, явно `billing: "api_credit"`.
   Сверить реальную схему инструмента; готового валидированного tool payload здесь нет.
   Единственный общий лимит всех вызовов $20. Подписочный fallback запрещён.
3. Сохранить outputs, hashes, точный model ID, параметры и отдельные receipts. Заморозить
   кандидаты до открытия вопросов. Не путать proxy-файлы с полученными outputs.
4. Для full-плеча промаркировать исходные абзацы Mxx. Одинаковый канонический слой
   AGENTS+knowledge+model-routing дать всем плечам, отдельно учитывать его токены.
   Таблица размеров офлайн этого дополнительного слоя и разметки не содержит.
5. Сформировать матрицу из `prompts.md`. В W1 использовать фиксированный retriever только
   по тексту вопросов, без эталона; пакет источников размечать Mxx. На уровне блока по 10
   вопросов объединять retrieved IDs без дублей. Размеры в текущих measurements —
   на **один вопрос**; размеры блока и его API usage пересчитать отдельно.
6. Рандомизировать порядок плеч и переставлять варианты ответов с сохранением карты
   соответствия эталону. Текущий public JSON — исходный банк, не готовая рандомизация.
   Разнести фактические и поведенческие вопросы по блокам без смешения ответов с промптами.
7. Нормализовать block-responses обратно в исходные choice/ID, объединить в 40 answers
   одного плеча/повтора. Для каждой порции источников хранить список **действительно
   переданных** Mxx. Нельзя объединённый список всех источников приписывать каждому
   отдельному вопросу: проверять groundedness до объединения или оценивать блоки через
   функцию `score(response, block_cases, available_ids)`.

Для готового одного запроса на весь банк (не для смешения источников нескольких блоков):

```bash
uv run --frozen python .orchestra/tasks/V-1114/harness.py score response.json --available-evidence received-ids.json
```

В `response.json` требуется `{"answers":[{"id":"F01","choice":"A","evidence_ids":["M06"]}, ...]}`;
`received-ids.json` — список исходных абзацев, реально показанных этому вызову.
Функция `score` отдельно считает правильность выбора и наличие полного набора допустимых
source IDs. Это не семантический судья цитат и не доказательство того, что модель прочла
источник: сгенерированную память можно снабдить верным ID, исказив его содержание.
Поэтому сохранять весь переданный текст и проверять ошибки/основания вручную;
для summary-only можно измерять choice-score, но полную evidence-groundedness не приписывать.

Сырые ответы и receipts будущих Claude-прогонов складывать в новый подкаталог задачи,
не затирая `execution-status.json`, который описывает этот нулевой модельный запуск.

## Что не проверяет стенд

Это ограниченный finite-choice probe, не интеграционный агент и не имитация настоящих
команд рестарта. Не покрыты tool-use, compaction/resume, самопроизвольное извлечение KB,
параллельная запись памяти, долговременное накопление ошибок и другие оркестраторы.
Вопросы написаны автором исследования по доступной памяти; внешнего слепого набора нет.
Новый независимый набор и повтор на памяти seedon нужны для обобщения, но его файл здесь
не запрашивался и не копировался. Автоматического внедрения при зелёном score нет.
