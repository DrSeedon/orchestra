## 1. Runtime preflight и общий контракт

Для каждой модели на фактическом runtime отдельно получить без inference список допустимых effort и canonical model ID. Кандидаты для Terra/Sol — `low`, `medium`, `high`, `xhigh`, `max`; фактическую поддержку здесь не утверждаем. Luna проверяется самостоятельно. `none` включать только при явном допуске runtime. Speed modes, fast/Ultra, тарифы и названия профилей не являются дополнительными effort. `max` и `xhigh` не считать синонимами без подтверждения контракта; UI-алиасы одного фактического значения не размножать в отдельные плечи.

Пусть `E_T`, `E_S`, `E_L` — подтверждённые множества; `t`, `s`, `l` — их размеры. Зафиксировать version/runtime, источник capability metadata, requested/effective effort и все неподдержанные значения. Нельзя молча подставлять default, наследовать effort родителя или заменять модель. При отсутствии проверяемых capabilities запуск заблокирован. Если runtime фактически вернул другой effort, результат помечается несоответствием протоколу, не успехом требуемого плеча; повтор потребляет бюджет. Списки фиксируются до результатов; изменение capabilities требует новой ревизии расписания.

Внутри каждой стадии все плечи получают одинаковые задания, критерии, входы, инструменты, ограничения контекста/вывода/времени, окружение и правила кеша. Каждый запуск — чистое состояние без ответов других плеч и без доступа к эталону. Сохраняются штатные reference/negative controls, оценивание не подгоняется под модель. Результаты разных стадий не объединяются: coding не является доказательством orchestration-качества и не служит основанием убрать effort из второй матрицы.

## 2. Сначала coding

Источник заданий — неизменённые frozen synthetic fixtures V-1162 из main, существующие oracle и runner. Число fixtures `F` пока неизвестно. Плечи: `{Terra}×E_T ∪ {Sol}×E_S`; `A₁=t+s`. Полная сетка с `r` повторами: **`C₁=F×A₁×r` ячеек**. При t=s=5: A₁=10, один повтор=10F, два=20F. По одному только лимиту invocations два повтора помещаются при F≤2; F=3 означает 60 вызовов, если одна ячейка равна одному invocation.

При превышении cap предлагается coding pilot: до четырёх frozen fixtures, все подтверждённые effort обеих моделей, **один повтор вместо двух**, без Luna. Для A₁=10 и F≥4: **40 ячеек/вызовов**, условно ≤400k generated, ≤79 min 20 s с конвертом ниже. Это сокращает повторы и, если F>4, покрытие заданий. Подмножество до результатов выбирается по исходному порядку manifest; при отсутствии порядка фиксируется сортировка ID. ID/хеши и исключённые задания сохраняются на исходном хосте. Выбор не считается репрезентативным. При F≤2 возможны два повтора, но это отдельное заранее выбранное расписание.

Размер pilot не фиксирован на 40 при других capabilities: например, если обе модели допускают ещё и `none`, A₁=12 и четыре fixtures дадут 48 ячеек: ≤480k generated, но до 94 минут с условным конвертом ниже, то есть превышение прежнего wall-time cap. Размер пересчитывается по формуле ниже; effort не выкидываются ради красивого числа.

Переход к стадии 2 — после сохранения coding-результата, проверки полноты/расхода и отдельной фиксации расписания и бюджета второй стадии. Coding должен завершиться либо с полной таблицей, либо с явным статусом неполного pilot/guard-блокера. Не запускать вторую стадию параллельно или как незаметное продолжение неполного coding.

## 3. Затем orchestration: 11 приватных кейсов

Источник — приватный набор владельца **ровно из 11 кейсов**. Их содержимое, эталоны, traces и prompts хабу не передаются, не запрашиваются и не реконструируются по synthetic V-1162. Проверки и исполнение — только на исходном разрешённом хосте существующим механизмом. Локальный отчёт владельцу может содержать ID/хеши и детали; на хаб для планирования достаточно counts/capabilities и разрешённых обезличенных агрегатов. Synthetic coding fixtures не подменяют приватные orchestration cases.

Плечи: `{Terra}×E_T ∪ {Sol}×E_S ∪ {Luna}×E_L`; **A₂=t+s+l**. Размер полной матрицы: **`C₂=11×A₂×r` ячеек**. Это расчёт без доступа к содержимому кейсов:

| Условные runtime counts t+s+l | Плеч A₂ | 1 повтор: ячеек | 2 повтора: ячеек |
|---|---:|---:|---:|
| 5+5+1 | 11 | 121 | 242 |
| 4+4+4 | 12 | 132 | 264 |
| 5+5+5 | 15 | 165 | 330 |
| 6+6+6, только если `none` реально доступен всем | 18 | 198 | 396 |

Это сценарии расчёта, не подтверждённые capability lists. В частности, первая строка не предписывает Luna только high. При любом runtime A₂>5 уже один полный проход превышает 56 вызовов даже при одном invocation на ячейку. При двух повторах старый invocation cap требует A₂≤2, что не покрывает даже три модели с одним effort у каждой. Простое разбиение полной матрицы на пакеты по 56 не сохраняет прежний общий бюджет.

### Явная предлагаемая граница для полной второй стадии

**На согласование, не на запуск:** отдельная стадия 2, все 11 кейсов, все подтверждённые effort, **два повтора**, при A₂≤18: максимум **396 ячеек**. Плановый бюджет-кандидат: **396 invocations / 4 000 000 generated / 13 часов wall time**, без retries/warm-ups и дополнительных модельных судей. Это явное увеличение относительно прежних 56/500k/90min, а не уже полученное разрешение. До его одобрения действуют старые пределы; stage 2 full не допускается.

Обоснование кандидата условно: **один invocation на ячейку**, до 10k generated с reasoning и до 110 s на попытку вместе с завершением/очисткой; 360 s на preflight/scoring. Тогда максимум 396×10k=3.96M generated; 396×110+360=43 920 s = **12 h 12 min**, запас до 13 h — 48 min. Для A₂=15: 330 ячеек, 3.3M generated, **10 h 11 min**; один повтор — 165, 1.65M, **5 h 8 min 30 s**. Это арифметические пределы, не замер скорости и не рекомендация ускорять/обрезать кейсы ради соответствия.

**Критическое различие:** orchestration-кейс может содержать несколько provider invocations, работу подчинённых и retries штатного протокола. Ячейка не равна invocation по определению. Если верхняя граница на ячейку — K invocations, B generated суммарно по всем участникам и D секунд end-to-end с завершением, ресурсный расчёт для r повторов: **`I₂≤11A₂rK`, `G₂≤11A₂rB`, `W₂≤11A₂rD+H`**, где H — предельные накладные расходы. Параллельность здесь не предполагается. Например, K=2 при A₂=18/r=2 требует до 792 invocations: кандидат 396 уже не допускает полную сетку. Частичный расход, retries и дети включаются, не скрываются внутри одного case.

K/B/D/H надо определить на исходном хосте по существующему контракту и model-free проверкам без раскрытия кейсов. При неизвестных/больших границах кандидат 396/4M/13h **не гарантирует** выполнение; нужен новый явный расчёт/согласование, без изменения runner или frozen кейсов. Если runtime даст >18 уникальных effort-плеч, кандидат также пересматривается. Для реального 90-минутного cap длительный эксперимент не имитировать ожиданием или автоматическим обновлением бюджета.

### Вариант без увеличения старого cap

Для одной стадии с P полными fixture-блоками, A плечами, r повторами допустимо лишь:
**`P≤min(F, floor(56/(ArK)), floor(500000/(ArB)), floor((5400−H)/(ArD)))`**.
Для orchestration F=11. При K=1/B=10k/D=110/H=360 и одном повторе: A₂=15 → максимум **3 кейса, 45 invocations, 450k, 88 min 30 s**; A₂=18 → максимум **2 кейса, 36 invocations, 360k, 72 min**. Это отдельные пилоты на subset, не полный 11-кейсовый benchmark. Исходный хост фиксирует subset до результатов; на хаб содержимое не вывозится. При большем K/B/D покрытие ещё меньше.

**Эти числа нельзя добавлять к уже потраченному coding-бюджету.** Для общего старого cap из формулы вычитаются фактические coding invocation/tokens/time и необходимый остаточный overhead; никакого автоматического reset. Если обе стадии должны поместиться вместе, есть явный малый вариант: coding 2 fixtures ×10 плеч ×1 + orchestration 1 приватный кейс ×15 плеч ×1 = **35 вызовов / ≤350k / ≤70 min 10 s**, при тех же условных K/B/D и общем H=360 s. При A₁=12/A₂=18: 24+18=**42 вызова / ≤420k / ≤83 min**. Оба сокращают повторы до одного и сильно сокращают кейсы, поэтому дают только технический pilot. Если даже эти условия не обеспечиваются существующими guards, запуск блокируется. Выбор между полным отдельно бюджетируемым исследованием и малым общим pilot должен быть явным до запуска.

## 4. Метрики, сравнимость и статистика

Для обеих стадий отдельно сохраняются полная таблица запланированных/выполненных ячеек и статусов, requested/effective effort, model/runtime/version, repeat, fixture ID локально, расход и stop reason. Одинаковое расписание условий фиксируется до результатов; чередовать плечи по кейсам штатным способом, чтобы уменьшить дрейф времени, без изменения обязательного frozen-порядка. Не продолжать общую сессию между плечами. Reference/negative controls запускаются model-free до расходования квоты; эталон не попадает в prompt.

- **Качество:** критерии соответствующего набора без правки. Отдельно pass/fail, raw scores и infrastructure/timeout/truncation/unsupported; знаменатели planned и completed явно. В coding — парные сравнения Terra/Sol по одинаковым effort и сравнения effort внутри модели. Во второй стадии — также Luna на всех подтверждённых effort; Luna high может быть парным ориентиром, только если доступен, но не заменяет остальные Luna effort. При несовпадении effort-множеств сравнение на пересечении явно отделяется от полного отчёта.
- **Latency:** monotonic end-to-end, инструменты/дети включены; очередь/setup/cleanup отдельно. Сохранять все значения, median/range; TTFT только при штатной telemetry. Timeout — цензурированное наблюдение с указанным порогом. Не выдавать p95 на малом n за устойчивый результат и не сравнивать только успешные ответы без указания смещения.
- **Tokens:** input/cached/output/reasoning раздельно, generated без двойного сложения reasoning; все участники/повторы и сбои учитываются. Неизвестный расход не равен нулю. На подписке cache read показывается отдельно, API-equivalent цена не равна расходу квоты. Tokens на успех включают неуспешные попытки; при нуле успехов отношение не определено.

Один повтор не оценивает стабильность на одном кейсе. Два повтора не удваивают число независимых задач. Для полной второй стадии n=11 кейсов, а не 330/396 независимых задач: один изменившийся кейс сдвигает однопроходную долю на 1/11≈9.09 п.п. Малые subset pilots ещё слабее. Парные различия рассчитываются по общим кейсам, с кластеризацией по кейсу при интервалах/ресемплинге; 11 кейсов дают ограниченную точность и обобщаются только на этот фиксированный набор. Несколько effort и три модели означают множественные сравнения: не выбирать выгодные p-values, не заявлять универсальное превосходство, не объединять стадии ради увеличения n. Trials не останавливаются по выгодному качеству; остановка по budget/guard означает неполный результат. Победитель по coding не назначается победителем orchestration.
