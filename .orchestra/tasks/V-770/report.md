# V-770 — permission boundaries and backup exposure

Research only; no policy, service, config, or data was changed. The service CWD is `/home/kesha/orchestra`; its `app/backend_claude.py` and `app/backend_codex.py` match the worktree copies by SHA-256 (`9199c175a815040b1fba6753c8730459777e09cec8be85aded06bb1cf6b14fc1` and `a17059ce37194d2eb8f09af963da9ac86f135c73d8adecbf5d45cbbdeabca194`). The database queries below used SQLite `mode=ro`; no destructive command was run.

## Finding

The exact Windows/PowerShell failure shown in the supplied post is not reproducible as such here: Orchestra runs on Linux, not the author's Windows host. The underlying risk does apply. A worktree is not a filesystem jail, and the Orchestra service and its agent subprocesses run as `kesha` with write access to the user's home and project directories. Claude has a partial Bash classifier, but it fails open and does not constrain paths; Codex is explicitly launched with full filesystem access. The service cannot elevate to root (`NoNewPrivs=1`, zero effective capabilities), but root protection does not protect user-owned project data.

The supplied screenshot claims that a Windows PowerShell 5.1 quoting error changed a `cmd /c rmdir /s /q` cleanup target to the drive root; a later retry in another command form passed a prior safety check, and the command repeated. It says the session was non-admin, reports no outside access, and credits a daily Synology backup. The Telegram page could not be opened by the browser, so these remain the post author's claims, not an independently verified incident.

## 1. What each runtime can do

The current service is `/home/kesha/orchestra`, UID 1001 (`kesha`), with `NoNewPrivileges=1`, `CapEff=0`, `ProtectHome=no`, `ProtectSystem=no`, and no `ReadOnlyPaths`/`ReadWritePaths` boundaries. Its process has supplementary group 27 (`sudo`), but a read-only `sudo -n -l` attempt was rejected because of `NoNewPrivileges`; the process is not root. `/home/kesha/projects` and `/home/kesha/orchestra` are both owned by UID 1001 and writable by that UID.

| Runtime | `rm -rf ~` | Delete another project | `sudo` to root | Write outside the task worktree |
|---|---|---|---|---|
| Claude SDK / Claude Code | A direct Bash `rm -r` is denied if the managed classifier completes. It can pass when the classifier fails open; other deletion forms (`rmdir`, `find -delete`, `git clean`, Python, direct file tools) are not comprehensively denied. | Yes, for paths writable by `kesha`; the worktree path is a starting directory, not an OS boundary. | No, in the observed service process: `NoNewPrivs=1`, `CapEff=0`; `sudo -n -l` was rejected. | Yes. The PreToolUse classifier has no path confinement. The service has no systemd home/filesystem protection; SDK sandbox is unset. |
| Codex app-server | Yes. Orchestra sends `approvalPolicy: never` and `sandbox: danger-full-access` (`app/backend_codex.py:708–709`). | Yes, subject to ordinary UID/file permissions. | No, same service process/NoNewPrivileges boundary. | Yes; the explicit app-server sandbox setting is full access. The Codex backend does not wrap its command in bwrap. |
| Harness / OpenRouter | Through Bash, yes, subject to ordinary UID permissions. Direct registered file tools deny paths outside their canonical workspace (`app/harness/tools.py:102–120`). | Through Bash, yes. Direct file tools reject outside-workspace paths. | No, current service boundary as above. | Direct read/write/edit/glob/grep: no. Bash: yes unless the process is successfully run as a more restricted `ORCHESTRA_AGENT_UID`. That variable is absent from the live service environment, so current Bash runs as `kesha`.

Claude's app code sets `permission_mode="default"`, but `_make_auto_approve` returns `PermissionResultAllow` for every tool except the small blocked set (`AskUserQuestion`, `Monitor`; orchestrators also block `Agent`). Thus most calls are approved without a human prompt even though the CLI is not started with `bypassPermissions`. The hook is attached in the live service (`CLAUDE_BASH_HOOK_ENABLED=1`). On a normal successful classification it denies only recursive `rm`, `chmod 777`, `curl | sh/bash`, the measured pathological grep quantifier, and `run_in_background` (`app/backend_claude.py:347–460`). It is not a workspace-path policy. The global Claude settings file has no `sandbox` section; app code does not set `ClaudeAgentOptions.sandbox` or restricted mode. The [Claude CLI reference](https://code.claude.com/docs/en/cli-usage) distinguishes skipping permission prompts from `--restricted`, which confines built-in file tools to working directories; Orchestra does not pass `--restricted`.

The platform's worktree, ownership and “do not edit outside scope” rules reduce accidental cross-task edits only while followed. They do not stop a shell process with the same UID. `.gitignore` excludes `data/` from commits; ignore rules do not prevent deletion.

## 2. Managed Bash fail-open events

The classifier deadline is 100 ms (`_BASH_CLASSIFIER_TIMEOUT`, `app/backend_claude.py:64`), around `asyncio.to_thread(...)` (`:431–440`). On `TimeoutError`, invalid output, or any exception, the hook logs `failed open` and returns `_pretool_output()` without `permissionDecision: deny` (`:444–460`). The SDK callback then auto-approves Bash. Anthropic's [PreToolUse hook reference](https://code.claude.com/docs/en/hooks) confirms that a `permissionDecision: deny` blocks the call; no such denial is returned in the failure path.

Read-only `journalctl -u orchestra.service` counts, deduplicating the paired plain/logger-prefixed records by journal timestamp and normalized message:

| Window | Raw journal lines | Unique fail-open callbacks | TimeoutError | Other classifier errors |
|---|---:|---:|---:|---:|
| Rolling 24 hours (ending 2026-10-08 08:20 UTC) | 72 | 40 | 35 | 5 `ValueError` |
| Rolling 7 days (2026-10-01 08:20–2026-10-08 08:20 UTC) | 229 | 147 | 139 | 8 `ValueError` |

Unique callbacks by UTC day in the seven-day query: Oct 1: 3; Oct 2: 26; Oct 3: 23; Oct 4: 9; Oct 5: 42; Oct 6: 2; Oct 7: 20; Oct 8: 22. The week scan returned only timeout and `ValueError` fail-open messages; 82 of its 229 lines were duplicate renderings, not additional callbacks.

The deadline is 100 ms and the seven-day query found 139 timeouts. Sysstat was enabled and had 1,001 ten-minute host samples covering the same week on an 8-CPU VM. For each timeout I matched the nearest sample (within five minutes): 139 events mapped to 76 distinct samples. Compared with all 1,001 samples, those timeout-nearest samples had higher median run queue (8 vs 4), higher median load average (5.68 vs 1.02), and lower median CPU idle (68.73% vs 92.52%); 20/76 timeout-nearest samples had CPU idle below 20%, compared with 55/1,001 overall. This supports host load as a likely contributor to the 100 ms deadline misses. It does not establish per-request causation: samples are ten minutes apart, many events share a sample, and there is no per-process CPU, executor-queue, or command-size telemetry. Oct 5 is the largest daily burst (42 unique failures).

The database `logs` table has `session_id` and `tool_use_id` for Bash events; the journal error does not. In a ±3 s read-only join by time, 86 fail-open timestamps had exactly one nearby Bash log, 57 had multiple, and one had none. The 86 single-candidate windows included seven commands in destructive-command families and two `sudo`/`su`-family candidates; because this is only temporal matching, these counts do **not** prove those commands caused those failures.

One candidate is substantially stronger: a Bash tool row was timestamped 10 ms before a `ValueError` fail-open, was the only Bash row within three seconds, and calling the exact classifier on its stored payload reproduced `ValueError: No closing quotation`. It contained `rm -i` over relative image paths after `cd out` with a here-string answer `y`, followed by `rclone copyto` to a remote destination. The session's CWD was an Orchestra task worktree. Its tool-result row was not marked as an error; the command's redirected `rm` output means individual deletions cannot be confirmed. This is evidence that a malformed classifier input can reach a file-removal/external-copy command, not evidence of a whole-home or another-project deletion. No session/tool ID is included in the journal event, so the association is still temporal, not a definitive request ID match.

With fail-closed behavior, a classifier timeout/exception would produce a PreToolUse denial instead of allowing that Bash call. The affected command would not run; benign shell work would also stop on those failures (40 affected calls in the observed 24 hours, 147 in the week). This changes the failure mode from uninspected command execution to denied command/availability loss. Non-Bash tools are outside this hook.

## 3. Backups and recoverability

The live database path is `/home/kesha/orchestra/data/orchestra.db` (3,412,381,696 bytes at 2026-10-08 10:06 CEST); the same directory had only its active `-wal` and `-shm` companions among `orchestra.db*` files. `.gitignore:15` ignores all `data/`, and `git ls-files data/orchestra.db` confirms it is not tracked. No separate DB backup file was found in the scanned `/home/kesha/orchestra/data` tree.

The canonical task-record store is `/home/kesha/orchestra/data/storage-preflight-final-20260908/tasks`, from the live service's `ORCHESTRA_TASK_REPOSITORY`; it is a local Git repository with 2,323 task JSON records, HEAD `80f9807` committed 2026-10-08 10:01 CEST, and no Git remotes configured. `app/task_store.py:1` states that task-store operations never contact a remote. The SQLite `tm_tasks` table is a projection, not the task store's canonical copy. Deleting `data/` therefore removes both the live DB and the task store. The root repository's `data/` is ignored; no claim is made about independent off-host copies under other names.

The root repository's `.orchestra/tasks/*.md` reports are ordinary tracked project files. They can be recovered from `origin` only if their commits were pushed; a local commit or another worktree does not survive loss of the host/repository. Other user projects have the same limitation: a remote clone can restore pushed Git history, not uncommitted/untracked files or ignored data.

Coverage checked: all 22 systemd system timers; user crontab and user-systemd timer availability; mount targets/types; the three `orchestra.db*` files in live `data/`; and 1,670 regular files (max depth 6) under `/home/kesha/v37`, `/home/kesha/maxim-drive/backup-2026-09-24`, `/home/kesha/.config/getpostingboard/snapshots`, `/home/kesha/.codex/shell_snapshots`, `/home/kesha/painter-backups`, `/home/kesha/.claude/shell-snapshots`, and `/home/kesha/.claude/backups`. The filename search found no `orchestra.db*` in those trees; the dated `maxim-drive` directory also had no `orchestra` directory to depth 5. The only system timer named for a backup was OS `dpkg-db-backup`; a separate photobooth mirror-sync timer was present, but its unit definition was not inspected and it is not evidence of an Orchestra backup. `/home/kesha/maxim-drive/backup-2026-09-24` is a local directory, not a mounted NAS; no NFS/CIFS/Synology mount was visible. The user crontab query and user-systemd timer query were unavailable, so those sources are not evidence of absence. No restore drill was performed; archives under different names or off-host backups not mounted here remain unverified.

## 4. Verdicts

| Advice | Verdict | Evidence and cost |
|---|---|---|
| Claude “auto-permissions” / bypass prompts | **Already have the functional equivalent for most tools; do not add a broader bypass.** | `permission_mode` is `default`, but `can_use_tool` approves almost every tool. The Bash hook provides a narrow deny set and currently fails open; a global bypass would not fix parsing or path confinement and would remove remaining CLI permission checks. Marginal implementation cost is small; risk is broader unreviewed operations, not a backup improvement. |
| Codex Auto-review | **Do not take it as a data-safety control.** | Review cannot prevent a running session from deleting ignored files or copying data externally. Current work acceptance and merge-test checks are about code/results, not filesystem confinement or backup. Owner policy freezes the model-review route (`.orchestra/pipelines/default/prompts/roles/worker.md:37`); the `codex_review` registration is commented out in `app/mcp_stdio.py:3856`. Re-enabling automatic model reviews would spend model/quota capacity and still would not provide a restore path. |
| Automatic/project-wide backup | **No such protection was found for these targets.** | The DB and canonical task store are ignored/local under `data/`; the task-store Git repository has no remote. No confirmed external backup exists in the checked coverage. No restore cost or recovery time can be claimed without a verified backup and restore test. |
