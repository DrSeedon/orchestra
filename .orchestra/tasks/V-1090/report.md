## 3. Как оценивали и что воспроизвелось

**Выбор конвенции.** В `judge.py`:1–26, 327–359, 388–425 описан и реализован детерминированный tokenizer/regex judge. Он берёт Python-файлы из полного diff, считает net-added непустые строки, отменяет добавленную строку совпадающим stripped удалением (один к одному по diff), игнорирует комментарии и разделяет source/test/docstring scopes. TFILE смотрит имена новых тестовых файлов. Есть hits только file-side → `follow_file`, только code-side → `follow_code`; оба или ни одного → `neither`. Это не LLM-оценка правильности и не процент строк: одна task-decision получает один verdict независимо от количества совпадений. Лексическая эвристика может пропустить семантически эквивалентный путь; `neither` объединяет mixed и absent. Release хранит итог verdict, но не `a_hits`, `b_hits`, reason, возвращаемые judge.

**Упоминание конфликта.** Полный [conflict_criteria.md](evidence/stale-docs-data-fa3c8b8a3347b11e7d4faa073af2b210a1b037e3/criteria/conflict_criteria.md) требует хотя бы одного конкретного doc-vs-code несоответствия. Вагуальность, описание собственной работы, task-vs-code mismatch или task-vs-doc mismatch дают NO. Язык ответа любой. По P Appendix A финальные ответы перемешаны, получили opaque IDs; судья видел ID и reply, без metadata, task, repo и diff, по одному ответу на вызов. Возврат — YES/NO и цитата до 25 слов; timeout 600 секунд, максимум три попытки. В release осталась только label. Условие может угадываться из содержания самого ответа; «слепой» означает отсутствие явного condition/agent metadata, не устранение всех языковых признаков. Human double coding, inter-rater agreement и независимая точность judge не представлены. YES измеряет **сообщение хотя бы об одном конфликте**, а не внутреннее распознавание, полноту списка всех конфликтов или правильность их разрешения.

**Переписывание.** `more_numbers.py`:28–42 считает удалённые `-` строки существовавших `.py` (включая тесты), исключая diff headers и новые файлы; порог ≥20 суммарно на run. Это прокси объёма вмешательства, не полный semantic audit. Нетто-исправление или форматирование тоже может пересечь порог; отсутствие rewrite означает лишь отсутствие этого порога, а не отсутствие любых edits. В данных максимум удалений у non-rewrite — 18.

**Тестовый исход.** `score.py`:39–85 сначала копирует finished workspace, восстанавливает исходные test files и `pytest.ini`, добавляет held-out тест и запускает именно исходные test modules плюс held-out module. `all_pass` требует exit=0, ненулевое число исполненных тестов каждой группы и отсутствие failures в обеих; timeout 600 секунд. Вновь написанные агентом дополнительные test modules не являются отдельной обязательной группой scorer. Такой порядок препятствует засчитыванию просто переписанных старых assertions как исходного контракта. Здесь scorer только прочитан, а записи `all_pass` только агрегированы.

## 4. Проверенные выводы и недоказанные обобщения

Наблюдаемый контраст достаточен для узкого утверждения: на опубликованном наборе конфликтующих Python-конвенций добавление данного user-level prompt связано с сильным сдвигом классифицированных net-added choices, отсутствием rewrites по заданному порогу и отсутствием combined test failures в B. Арифметика этого утверждения воспроизводится. Полная причинная атрибуция именно обучению instruction hierarchy остаётся объяснением авторов: они не меняли training, не сравнивали один model в нескольких harness, не аблировали источник/порядок доставки и две части строки. Возможные альтернативы в рамках наблюдаемого дизайна — более конкретная инструкция разрешения конфликта и дополнительное требование отчётности; данные не разделяют эти вклады.

Существенные пределы, вытекающие из открытого дизайна и release:

1. **Заранее известная правильная сторона.** Нет counter-condition «документ актуален, код устарел», намеренного style migration, явного нового требования пользователя, смешанного/ошибочного baseline. Следование коду считается хорошим исходом по конструкции набора; универсальная истинность code precedence не проверена.
2. **Видимое сообщение и знание — разные измерения.** 79/80 основано на финальных ответах; traces чтения каждого файла и внутреннее обнаружение не наблюдаются в release. Успех YES даже в 160/160 не доказывает точность или полноту всех перечисленных конфликтов.
3. **Не все документальные правила являются описаниями.** §6/рис. 8 сами различают проверяемое описание кода и обязательное действие вроде запуска тестов. Строка B буквально широко говорит о documentation, но negative tests на override security/owner constraints не опубликованы. Нельзя выводить из неё разрешение отменить нормативное правило обнаруженным старым паттерном.
4. **Не 1 440 независимых репозиториев.** 1 440 choices — это 40 проектов, 320 runs и повторы тех же четырёх/пяти конвенций. Project-level bootstrap учитывает этот кластер при CI; распространённость проблемы в реальных repositories этим N не измеряется. Направления сбалансированы, но каждый type представлен только 11–12 проектами.
5. **Нет изоляции модели от CLI.** Sonnet 5.5/Claude Code и GPT-6 Sol/Codex сравниваются парами. Разные инструменты, runtime и approvals мешают трактовать расхождения как чистые свойства моделей. Другие версии, языки, подписочные маршруты Orchestra, долгие многотуровые сессии и роли здесь не тестировались.
6. **Точность автоматической разметки не воспроизведена.** Мой recount доверяет verdicts и conflict labels; он не исполняет чужой judge, не заменяет его новым и не вызывает модели. Отсутствуют сохранённые judge evidence и human validation. Семантическую корректность cannot infer из regex matches.
7. **Оригинальные тесты против общего исхода.** 17/20 combined failures и факт, что все они rewrites, пересчитаны. Что именно упало — original или held-out — неразделимо в release-поле `tests.all_pass`. Иллюстрация kanbanlite с удалённым Enum и исходными import failures показана в P рис. 7, но полный JUnit/log набора не опубликован.
8. **Запуски могли менять сами instruction files.** `doc_edited=true` у семи записей: R003 (Claude B), R004/R092/R120/R129/R148 (Claude A), R308 (Codex A). Это воспроизводимый дополнительный endpoint; данное исследование не является доказательством, что строка предотвращает правку документов. Изначальный project-doc одинаков между conditions, но в ходе run он не оставался неизменяемым во всех случаях.
9. **Нулевое число событий — только наблюдение.** B не содержит ≥20-line rewrites, но небольшие удаления встречаются; тестовый успех не измеряет безопасность, review cost, долговременную совместимость или отсутствие нежелательных эффектов.
10. **Практические предложения отдельно от измерений.** Универсальное добавление в system prompt и обучение моделей отличать описания от правил — предложения §6, не проверенные treatments этого эксперимента. Числа про частоту устаревших файлов из других работ и три timeline-примера рис. 2 не являются дополнительными model runs здесь; их underlying commits/датасеты отдельно не аудировались.

Это исследовательские границы, а не рекомендация принять или отвергнуть intervention. Реальных model/eval/API запусков, новых расходов, установки навыков и изменений текущих правил не было.

## 6. Воспроизводимость, выполненные проверки и ограничения передачи

Собственный [recount.py](recount.py) использует только стандартную библиотеку и читает JSON/diff как данные. Он не импортирует авторские modules, не применяет diff к baseline, не запускает чужой judge/scorer/tests и не обращается к сети. Проверяет уникальность runs и полную сетку 40×2×2×2, validity, длины verdicts, все 36 именованных fractions из `numbers.md` и 64 category fractions; отдельно выводит rewritten-run IDs, медианы и project coverage. [audit.py](audit.py) проверяет upstream blobs, неизменность локальных source files, синтаксис task utilities, локальные ссылки отчёта и формы секретов перед передачей. [capture.py](capture.py) — только публичная загрузка восьми figures и snapshot локальных правил; его [stdout](evidence/capture.txt) сохранён verbatim.

**Граница публикации после проверки root.** Исходный отчёт и четыре вывода с native hub paths (`audit-first.txt`, `instruction-contract.txt`, `pytest-instruction-contract.txt`, `python-environment.txt`) сохранены побайтово в ignored `private/raw/` с прежними относительными путями. Старый `artifact-sha256.json` также сохранён там, чтобы не потерять provenance первоначального набора. Их публичные пять копий явно помечены `PUBLIC DERIVATIVE`: literal пути заменены на `/home/<hub-user>/<hub-workspace>` и `/home/<hub-user>`, поэтому эти копии **не verbatim outputs**. Выводы и численные результаты не переоценивались. [preservation-manifest.json](preservation-manifest.json) содержит SHA-256 и bytes оригиналов; его идентичная private-копия находится в `private/preservation-manifest.json`. Тридцать regular fixture files и 16 symlinks перенесены целиком из публичного `pytest-tmp/` в `private/pytest-tmp/`; manifest отдельно фиксирует bytes/SHA содержимого regular files и target bytes ссылок, без публикации target text. Это воспроизводимые pytest fixtures, не исходные данные авторов. Никакие live logs не менялись. Private custody до завершения worker сохраняет root на native стороне.

Task-local `.gitignore` содержит `/private/`. Public hash/shape traversal отсекает этот каталог **до обхода** и не включает его содержимое или fixture outputs. Отдельная адресная проверка preservation receipt сверяет private originals, когда они доступны; на копии без них аудит явно сообщает этот предел. В hub нет `.git`, поэтому фактический native `git check-ignore` остаётся root. Полные 585 файлов публикационного dataset сохранены и продолжают проверяться по upstream blob hashes. [prepare_publication.py](prepare_publication.py) — выполненная одноразовая утилита сохранения/подстановки; повторный запуск отказывается перезаписывать сохранённые оригиналы.

Фактически использован provisioned **uv 0.11.28** и default `.venv`, а не system uv dispatcher или подмена интерпретатора. Locked setup установил 76 пакетов; собственные подсчёт и аудит были офлайн. [uv-version.txt](evidence/uv-version.txt) и публичная производная [python-environment.txt](evidence/python-environment.txt) сохраняют runner, Python и import probe. В `python-environment.txt` `app: None`: импортированного `app` нет, поэтому абсолютный путь импортированного `app` предоставить невозможно; ожидаемый root после публикационной подстановки — `/home/<hub-user>/<hub-workspace>/app`.
