# V-952 — `idempotency key must be 16-128…` и `Worker is waiting`

## 1. request_key
Минимум 16 введён регулярным выражением `_TASK_CREATE_REQUEST_KEY` в app/tm.py при #395 (748e81e37); обоснования нет ни в сообщении коммита, ни в KB/отчётах (поиск `rg` по .orchestra/kb и .orchestra/tasks). Что ключ реально защищает: `TaskStore.create` ищет запись с тем же `creation_key` **в том же проекте**; совпал ключ и отпечаток содержимого → возвращает существующую задачу (идемпотентность), совпал ключ при другом содержимом → `TaskCreateConflict` (громко); id задачи = uuid5(проект, origin, ключ). Нижние слои (store, тесты `request_key='one'`) короткие ключи принимают, ограничение было только на HTTP/`api_create_task` слое. То есть длина от коллизий не защищает: защита — отпечаток. Решение: 1–128 символов тот же алфавит; описание `task_create` в mcp_stdio теперь называет правило (ключ в рамках проекта, тот же ключ с другим содержимым отклоняется — на каждую разную задачу новый ключ). `delivery_id` другого рода: обязан быть UUID и это уже указано в описаниях инструментов (`message must be a UUID`), не менялся. Остаточный риск: два агента одного проекта выберут одинаковый короткий ключ для разных задач → получат конфликт (а не дубликат), понятный по тексту ошибки.

## 2. merge_worker «Worker is waiting»
Статус `waiting` ставит только `finish_turn_status()` в конце хода, если у сессии есть активные bg-задания (`has_active_jobs`). Журнал/БД по случаям:
| случай | что держало `waiting` | оценка |
|---|---|---|
| prolider 18.10 08:48 | два `cron` (`bg-5327819a41`, `bg-c8fa7ba1e9`) с expires_at +100 лет, созданные в 08:48:19–20 | дефект: напоминание само себе никогда не завершится |
| bench-evals-core 17.10 10:29 | активный `command`-watch `bg-fd7f29f8af` («V-923 run finished», до 22:06), плюс `run`-задания воркфлоу | верный отказ: воркер ждёт результат |
| urok-svyaz 15.10 09:55–13:09 | в логах сессии повторяющееся «waiting for bg jobs» (конец хода → ожидание), записи заданий к моменту проверки уже вычищены (`bg_cleanup_old` 24 ч) | по логу — ожидание результата заданий; тип не восстановить (не подтверждено) |
| ai-table-gm 15.10 | та же ситуация, задания вычищены | не подтверждено |
Побочный эффект того же дефекта: пока `waiting`, `after_turn_idle_actions` пропускает auto-report (`s.status != WAITING`), т.е. воркер с вечным cron не докладывал DONE.
Решение: (а) plain `cron` не считается ожидаемым результатом (`jobs_holding_waiting`, `_RECURRING_REMINDER_TYPES`); `cron_command`, `timer`, `run`, `file`/`command`/`ssh`, `merge` по-прежнему держат ожидание. (б) Настоящий отказ оставлен: у `waiting` воркера идут процессы заданий в его worktree, а merge делает reset worktree воркера — снимать запрет нельзя. Но отказ теперь говорит, чего ждёт воркер (`details.waiting_on_jobs`, текст), чтобы оркестратору не гадать. (в) error_watch: «Worker is waiting|running; wait until it is idle» — ожидаемый отказ (noise). Не сделано: автоматического ожидания merge до конца долгого задания (ожидание часами внутри запроса нерационально).
