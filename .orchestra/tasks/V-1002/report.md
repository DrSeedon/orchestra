## В двух словах

В доступном task store — **2 887 записей задач** в **31 техническом проектном bucket**; **2 068** имеют статус `done` или `paid`. В таблице сессий — **1 122 дочерних запуска**, включая **1 117 уникальных имён**. Это счётчики сохранившихся данных, не оценка всех когда-либо созданных сущностей после удаления/переноса исторических хранилищ.

### Как воспроизвести числа

Все SQLite-команды открывают базу строго в режиме `mode=ro`. SQL ниже исполняется через `sqlite3` по указанному URI; Q1–Q5 и Q7–Q9 были сгруппированы в одной read-транзакции для согласованности. Команды можно запускать из любой директории.

**Q1 — все задачи и пространство номеров:**

```sql
SELECT COUNT(*) AS rows,
       SUM(ref_prefix='V') AS v_prefixed,
       SUM(ref_prefix='') AS unprefixed,
       MIN(created_at), MAX(created_at)
FROM tm_tasks;
```

**Q2 — статусы по нумерации:**

```sql
SELECT CASE WHEN ref_prefix='V' THEN 'V-prefixed' ELSE 'unprefixed' END AS space,
       status, COUNT(*)
FROM tm_tasks GROUP BY space,status ORDER BY space,status;
```

**Q3 — создание по месяцам:**

```sql
SELECT substr(created_at,1,7) AS month, COUNT(*)
FROM tm_tasks GROUP BY month ORDER BY month;
```

**Q4 — buckets проектов и текущие охваты:**

```sql
SELECT p.id, p.name, p.scope, COUNT(t.id) AS tasks
FROM tm_projects p LEFT JOIN tm_tasks t ON t.project_id=p.id
GROUP BY p.id ORDER BY tasks DESC;
SELECT COUNT(DISTINCT project_id) FROM tm_tasks;
```

Для объединённых по продукту подпунктов использовались буквально перечисленные выше `project_id`; это арифметическая сумма bucket-ов, а не эвристическое слияние одинаковых имён.

**Q5 — медиана времени до завершения (SQLite окно; вычисление медианы по отсортированным результатам):**

```sql
SELECT (julianday(completed_at)-julianday(created_at))*86400 AS seconds
FROM tm_tasks
WHERE status IN ('done','paid') AND completed_at IS NOT NULL
ORDER BY seconds;
```

2 043 результата; медиана двух центральных значений равна 1 697.537 секунды, показано округлённо до ближайшей секунды.

**Q6 — история Orchestra:**

```bash
git rev-list --count main
git log -1 --format='%H %ad %s' --date=short main
```

**Q7 — дочерние сессии:**

```sql
SELECT role, COUNT(*) AS session_rows, COUNT(DISTINCT name) AS names,
       SUM(total_turns) AS session_turn_counter
FROM sessions WHERE parent_id!='' GROUP BY role;
SELECT COUNT(*), COUNT(DISTINCT name), MIN(created_at), MAX(created_at)
FROM sessions WHERE parent_id!='';
```

`session_turn_counter` приведён для воспроизводимости таблицы, но не используется как число ходов в отчёте: для биллингово-аналитического ряда берётся отдельная таблица `turn_usage`.

**Q8 — помесячные ходы и сумма API-equivalent:**

```sql
SELECT substr(ts,1,7) AS month,
       CASE WHEN lower(model) LIKE 'claude%' THEN 'Claude'
            WHEN lower(model) LIKE 'gpt-%' THEN 'Codex/GPT'
            ELSE 'Harness/other' END AS family,
       COUNT(*) AS turns, ROUND(SUM(cost_usd),2) AS api_equivalent,
       SUM(cost_usd IS NULL) AS unknown_cost
FROM turn_usage GROUP BY month,family ORDER BY month,family;
```

**Q9 — общий охват и итоги по семействам:**

```sql
SELECT COUNT(*), MIN(ts), MAX(ts), SUM(cost_usd IS NULL) FROM turn_usage;
SELECT CASE WHEN lower(model) LIKE 'claude%' THEN 'Claude'
            WHEN lower(model) LIKE 'gpt-%' THEN 'Codex/GPT'
            ELSE 'Harness/other' END AS family,
       COUNT(*), ROUND(SUM(cost_usd),2), SUM(cost_usd IS NULL)
FROM turn_usage GROUP BY family;
```

### Ядро платформы и надёжность

- **V-772/V-793 — резервное копирование данных.** Задачи хранятся в приватном Git-зеркале; SQLite копируется через backup API, доставка на ноутбук возобновляется после его появления в сети. (CHANGELOG, V-772/V-793.)
- **V-846 — правила исполнения работают через блокировку.** Shell guard отклоняет долгие паузы и рекурсивные `find`/`grep`, когда доступен `rg`; до этого V-844 нашёл 4,786 часа суммарных числовых `sleep` за неделю. Это длительность заданных пауз, а не измеренная потенциальная экономия: время готовности процесса отдельно не зафиксировано. (Отчёт V-844, §1 и §4; CHANGELOG V-846.)
- **V-915 — прекращение сиротских процессов.** При восстановлении после сбоя платформы процесс фонового задания теперь останавливается до уведомления об `INTERRUPTED`; иначе агент мог повторить работу, пока первая копия ещё писала в те же файлы. (CHANGELOG, V-915.)
- **V-982 — привязка задачи к работающему агенту.** Задача и task-run назначаются в одной транзакции с проверками владельца и состояния; ветка, HEAD, грязные файлы и работающий процесс сохраняются. (CHANGELOG, V-982.)
- **V-984 — уборка результатов в worktree после merge.** Удаляется только игнорируемый и доказуемо повторяемый результат. Один проход освободил 1.2 ГБ; 12.9 ГБ без копии в основном checkout оставили нетронутыми. (CHANGELOG, V-984.)

## Сбои, инциденты и развороты

- **Удаление task store 28.09.2026.** Владелец указал этот случай как инцидент для разбора. Доступная текущая SQLite начинается с 16.05, но сама по себе не подтверждает, какие записи были потеряны и восстановлены; в текущем `logs` точное событие не удалось надёжно выделить. Поэтому число потерянных задач и масштаб простоя здесь не утверждаются.
- **3 августа: удаление чужих worktree уборщиком.** Changelog фиксирует запуск очистки в основном checkout с тестовой БД; после этого были удалены каталоги нескольких проектов, включая семь worktree Seedon, часть которых восстановили позже. Это был реальный сбой с последствиями, а не просто красный тест. (CHANGELOG, история worktree-cleanup.)
- **Автоматические рестарты.** Правило проекта теперь запрещает агентам самостоятельно перезапускать Orchestra; Python-изменения ждут прямого разрешения владельца. Changelog V-915 отдельно фиксирует последствия прошлых рестартов: фоновые процессы могли пережить остановку родительского процесса и продолжить писать после сообщения `INTERRUPTED`.
- **Sol: маршрут туда-обратно.** V-970 открыл GPT-6.1 Sol для агентских запусков; пять запусков сожгли окно Codex с 0 до 100% примерно за 75 минут, и V-991 вернул ручной выбор только владельцу. Это измеренный расход окна, не изменение счёта API.
- **Интерфейс предложений задач отменён.** V-858 реализовал карточки, V-873 удалил их после проверки: карточки удваивали чат и список сессий. Это разворот по результату использования, а не поломка данных.
- **Полнота исторических подсчётов ограничена.** В текущем task store есть 2 887 строк, но источники показывают несколько старых и импортированных пространств. Идентичные номера и даже UUID между независимыми установками не всегда означали одну задачу; при репетиции консолидации найдено 33 совпадения UUID с разным содержимым (KB `tasks-and-projects.md`). Поэтому отчёт не складывает номера как уникальные ключи и не заявляет доказанную полноту удалённых хранилищ.
- **Spend — только API-equivalent.** `cost_usd` в `turn_usage` — оценка стоимости вызовов по API-ставкам; правила проекта запрещают читать её как платёж по подписке. У части ходов цена неизвестна, и часть периода отсутствует в таблице.

## Охват и ограничения

Текущая база открывалась только через SQLite `mode=ro`. До добавления этого отчёта в worktree команда `rg --files .orchestra/tasks | rg '/report\\.md$' | rg -v '/V-1002/' | wc -l` обнаружила 41 уже доступный task report; task archive в checkout неполон, поэтому выводы дополнены CHANGELOG, KB и сохранёнными отчётами, которые читались напрямую в Seedon и University. Факты из changelog и KB приняты как документированные выводы, а не повторно проверенные live-состояния. В других проектах task count берётся из центрального task store; Git-истории этих репозиториев для числа коммитов не агрегировались. Эмпирические траты, завершённые задачи и состав моделей могут изменяться вместе с live DB.
