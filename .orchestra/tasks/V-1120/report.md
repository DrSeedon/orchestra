Текущий текст NodeSeek содержит другой набор предположений; штрафов за Linux/Fable и признака «наблюдения» через logout в нём нет. Связь между этими публикациями по содержанию сильная, но документированной цепочки заимствования до исходного китайского эксперимента нет.

**Повторный logout — неспецифический симптом.** Anthropic документирует срок веб-сессии, глобальный выход, отзыв токенов и несколько исправлений реальных ошибок OAuth, в том числе при конкурентных CLI. Они дают обычные альтернативы «наблюдению перед баном». Нельзя ни объявить все сбросы безобидными, ни использовать последовательность logout → ban как подтверждение скрытого карантина. [Веб-сессии и отзыв](https://support.claude.com/en/articles/10310342-how-do-i-log-out-of-all-active-sessions), [официальные исправления CLI](https://github.com/anthropics/claude-code/blob/0e1f4789406477380b267a01f3ddd50b0211e5b3/CHANGELOG.md).

Для рассматриваемого случая исходным установленным обстоятельством остаётся **сообщённая Anthropic причина Supported Countries Policy; апелляция уже подана**. Это входные сведения задачи, не добытая нами переписка. Исследование не устанавливает, какие именно сигналы привели компанию к решению. Повторные сбросы логина не заменяют эту причину объяснением про Linux, расход квоты или SDK.

## 1. Метод и пределы доказательств

Разделены четыре типа материала:

1. **Первоисточник о публичных правилах/продукте** — документация, Help Center, датированные сообщения и release notes Anthropic. Это доказательства опубликованного поведения, не полный аудит закрытого антифрода.
2. **Первичное публичное свидетельство пользователя** — собственный bug report с версией, последовательностью событий и наблюдениями. Оно подтверждает наличие сообщения о проблеме, но не автоматически правильность диагноза автора.
3. **Первоисточник утверждения** — китайский пост, где автор утверждает существование баллов. Его первичность относительно слуха не делает его первичным свидетельством внутренних правил Anthropic.
4. **Пересказ/агрегатор/продвижение услуги** — годится для поиска цепочки, не считается независимой репликацией.

Для вывода о конкретном штрафе понадобились бы проверяемые внутренние правила либо сопоставимое исследование: контроль других факторов, количество аккаунтов под риском, отрицательные исходы, длительность наблюдения, версия клиента, одинаковые региональные и платёжные условия. В найденном списке этого нет. Много сообщений на форумах не заменяет контрольную группу; «не забанили» имеет неизвестный срок наблюдения и смещение выживших. Восстановление после входа тоже не исключает отдельной дальнейшей проверки.

**Временная оговорка:** на дату чтения страницы [AUP](https://www.anthropic.com/legal/aup) и [Supported Regions](https://www.anthropic.com/legal/supported-regions) уже показывают **Effective Nov 12, 2026**, то есть будущую относительно задачи редакцию. Её формулировки не выданы за действовавшие 29 октября. Для запрета обхода бана использована [архивная AUP от 15.09.2025](https://www.anthropic.com/legal/archive/22742366-2ef0-4c7a-a833-6523f10d3944), раскрытая в браузере; для регионального контекста — Help Center и [датированное сообщение 04.09.2025](https://www.anthropic.com/news/updating-restrictions-of-sales-to-unsupported-regions). Динамическая документация описывает доступный сейчас текст; она не доказывает состояние продукта в день давнего сброса логина.

## 4. Повторный logout: что действительно можно различать

Сначала необходимо различать объекты: **веб-cookie, OAuth access token, refresh token, длительный setup-token, доступ организации и ID разговора**. Истечение/сброс одного не означает того же для остальных. Возобновление разговора SDK не является OAuth refresh; `connect/disconnect` клиента не тождественны login/logout аккаунта.

| Возможная причина | На что опирается | Отличающие признаки в принципе, без запроса частных данных | Чего это не доказывает |
|---|---|---|---|
| Обычное истечение веб-сессии | A13: после входа веб-сессия длится 28 дней; при активности её срок обновляется раз в час | Длительное отсутствие активности и повторный вход только в браузере соответствуют этой модели | Частые сбросы при активной работе нельзя объяснить одним лишь 28-дневным TTL. Это правило не задаёт TTL CLI access token |
| Утрата/очистка cookie или другой профиль браузера | A3 описывает cookie, A9 включает их в troubleshooting ошибок входа | Изменение только одного браузерного профиля, приватная сессия или очистка локального состояния совместимы с локальной причиной | Нельзя без наблюдений утверждать, что именно cookie вызвала конкретный logout; рекомендация из troubleshooting не является диагнозом |
| Истёк access token; обычный refresh не сработал | A14 прямо указывает expired sign-in и невозможность refresh; A8 v2.1.117 исправляет эту ситуацию | Ошибка авторизации совпадает с границей срока, успешное штатное обновление восстанавливает работу | 401 сам по себе не говорит о причине отказа и не подтверждает антифрод-карантин |
| Конкурентное обновление/перезапись OAuth | A8 v2.1.126/129/133/136; пользовательские P1/P2/P3 | Несколько процессов, волна 400/401 при обновлении, восстановление после перечитывания актуального состояния. RFC 9700 объясняет общую опасность повторного использования уже вращённого refresh token | Конкретная серверная политика ротации Anthropic не полностью следует из RFC; наличие такого бага в прошлом не доказывает его в каждой версии и у владельца |
| Две версии CLI/IDE и разные источники авторизации | A8 v2.1.277; A14: `/login` при заданном env token меняет текущую сессию, следующий процесс снова читает env | Повторяемая разница между старым и новым процессом/клиентом, другой активный способ входа | Обновление бинарника на диске не обновляет уже работающий процесс. «Снова просит вход» не обязательно означает серверный отзыв всех сессий |
| Обычный отзыв токена или выход со всех устройств | A13: глобальный выход затрагивает в том числе CLI/setup-token; A8 v2.1.287 различает отзыв и общий 401 | Явное действие глобального выхода или сообщение `OAuth token revoked` объясняет недействительность credentials | Отзыв может иметь разные причины; сообщение не раскрывает решение антифрода и не означает автоматический бан |
| Смена метода входа, аккаунта, организации или конфигурационного каталога | A5 описывает способы входа и переключение аккаунта; A14 — org/method requirements и отдельные каталоги | Нужный аккаунт существует, но текущий процесс смотрит в другой контекст/источник credentials. Ошибка организации/метода отличается от исчерпания лимита | Переключение организации не является доказательством блокировки всего аккаунта. Удалять credentials для проверки не требуется |
| Показ приглашения входа как ошибка UI/старой версии | A14: до v2.1.290 setup мог показывать prompt и уже вошедшему пользователю | Prompt появляется при setup, при этом сохранённый вход существует | Видимый prompt нельзя без дополнительного признака считать реальной потерей серверной сессии |
| Сбой сервиса/сети | A5/A9 советуют проверять официальный status при ошибках входа | Публичный инцидент в точное время со сходной областью влияния поддерживает эту причину | Исторические времена сбросов владельца неизвестны; ни один конкретный инцидент к ним не привязан. Отсутствие записи status не исключает локальной/ограниченной проблемы |
| Проверка безопасности/приостановка организации или аккаунта | A1 описывает restricted screen/org hold; A11 — проверки целостности | Прямое уведомление о проверке/приостановке и указанное основание существенно сильнее косвенного logout | Даже реальный запрос проверки не раскрывает баллы, длительность «наблюдения» или неизбежность бана |

**Обновление OAuth обычно должно происходить незаметно.** Поэтому «обычное обновление может объяснить logout» здесь означает прежде всего **неудачу обновления, гонку или отзыв**, а не то, что каждый успешный refresh штатно разлогинивает пользователя. В [RFC 6749 §5.2](https://www.rfc-editor.org/rfc/rfc6749#section-5.2) `invalid_grant` охватывает несколько причин, включая недействительность, истечение и отзыв. По одной этой ошибке нельзя восстановить мотив сервера. [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700#section-4.14.2) объясняет, почему ротация и обнаружение повторного использования refresh token способны потребовать новую авторизацию без бана аккаунта.

### Почему logout → ban недостаточно

Одна и та же последовательность совместима как минимум с четырьмя моделями: независимая ошибка OAuth, затем региональное решение; отзыв credentials как **следствие** уже начавшегося enforcement; общая причина, влияющая на оба события; действительно отдельный этап проверки. Утверждение о «наблюдательном периоде» требует отличить их, чего найденные посты не делают. Нужны частоты событий у сопоставимых пользователей без бана и прямые основания от сервиса. Из сообщения владельца следует только факт повторения симптома, не его причина. Дополнительные личные данные в рамках этой задачи не нужны и не запрашиваются.

### Компактные выводы и дальнейшее исследование

1. **Сохранять разделение политики и техники.** Причина приостановки уже известна, апелляция уже подана. Техническая коррекция OAuth не отменит Supported Countries Policy и не является способом восстановить приостановленную организацию.
2. **Исследовать обработку авторизации штатного CLI/SDK, без запросов модели.** По доступному main проверить выбор `cli_path`, версии разных клиентов, источник credentials, различие process lifetime/credential lifetime/conversation resume. Версия SDK сама по себе не доказывает, какие исправления CLI A8 присутствуют. Не считать каждый старт SDK новым входом в аккаунт.
3. **Проверить конкурентное владение состоянием.** На синтетических credentials и подставном OAuth endpoint можно проверить перечитывание после обновления, конкурентный refresh, атомарную запись, симлинки и сохранность рабочего состояния после временной ошибки. Это возможная следующая задача; здесь её не реализовывали. Общий неподтверждённый 401 не должен автоматически превращаться в массовую очистку credentials или цикл повторных login.
4. **Проверить классификацию отказов и восстановление.** Будущие офлайн-проверки должны различать expired/revoked token, отказ доступа организации, региональную приостановку, rate limit и транспортную ошибку; успешный повторный вход не равен успешному восстановлению полномочий организации. Нужны ограниченные повторы только для действительно временных ошибок, без шторма и без тестовых модельных вызовов.
5. **Штатный CLI и сторонний продукт на SDK требуют разного вывода.** [A16](https://code.claude.com/docs/en/legal-and-compliance) явно допускает собственный вход пользователя в неизменённый Claude Code и упоминает обычное индивидуальное использование Agent SDK. Одновременно [A17](https://code.claude.com/docs/en/agent-sdk/overview) ограничивает предложение claude.ai login/подписочных лимитов сторонними разработчиками в их продуктах без согласования. Нельзя заключить «SDK всегда запрещён» или «любой SDK-wrapper автоматически разрешён». Точную схему использования Orchestra и применимость этих положений следует сверить отдельно; это не новая установленная причина текущей приостановки и не основание сейчас покупать API.
6. **Не переносить народные рекомендации в автоматические правила.** Нет основания маскировать Linux/клиент, имитировать действия в приложении, включать память ради очков, экономить фиксированные проценты квоты «для антибана», покупать Credits/новую подписку или повторять верификацию. Не предлагаются смена IP ради обхода, новые личности/документы, чужие аккаунты, прокси подписки и обход региональной политики. Проценты снижения риска не измерены и не обещаются.

**Смысл для текущего случая:** рассказ о сбросах логина теперь имеет документированные альтернативные объяснения; считать его ретроспективным подтверждением тайного наблюдения нельзя. Основание приостановки не переопределено. Инженерно полезное продолжение — проверить корректность штатной авторизации и сохранения состояния; организационное решение остаётся в уже поданной апелляции.
