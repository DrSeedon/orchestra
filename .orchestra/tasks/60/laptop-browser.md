# Открытие дашборда С НОУТБУКА ЮЗЕРА — абсолютные цифры

Наконец то, чего не хватало весь день: не доли с VPS, а миллисекунды с его машины.

## Условия

- Его ноутбук, 12 ядер, 16 ГБ. На момент прогонов loadavg 4.2–5.0, MemAvailable 5.7 ГБ,
  четыре чужих `python3` держали по ~100 % CPU — то есть **машина под его обычной рабочей
  нагрузкой**, не стенд.
- Ничего не устанавливалось: Playwright и Chromium там уже были.
- Прогон под `nice -n 15`, профили браузера в `/mnt/data/perf60/profiles` (не в `/tmp` —
  там tmpfs, то есть его RAM).
- Вход — **зеркало `https://orc.seedon.ru`**, потому что именно так он теперь будет работать.
- Два прогона по три захода (пустой профиль → F5 → F5). Сырьё: `browser-laptop-mirror.json`,
  `browser-lm2.json`.

## Цифры

| | 1-й заход | 2-й | 3-й |
|---|---|---|---|
| первый экран (FCP) | 316–336 мс | 312–328 | 296–300 |
| **список агентов** | **4297–4346 мс** | 982–1050 | 913–1002 |
| **чат на экране** | **4669–4760 мс** | 770–872 | 750–896 |
| LCP | 4684–4776 мс | 788–892 | 764–916 |
| длинные задачи, сумма | 79–131 мс | 138–153 | 151–199 |
| запросов | 32–36 | 30–34 | 30–31 |
| байт с провода | 62–67 КБ | 24–27 КБ | 21 КБ |

Для сравнения — тот же зонд с VPS (RTT≈0) в тот же день: 1-й заход чат 1002 мс,
длинные задачи 475 мс; 2-й — 435/350; 3-й — 592/475.

## Главный вывод: мы весь день считали не тот множитель

**Его машина не медленнее нашей — она в 3 раза БЫСТРЕЕ по главному потоку.**
Длинные задачи: 79–199 мс у него против 350–475 мс на VPS. Все наши оговорки вида
«абсолютные мс у юзера будут больше» верны только для сети и неверны для CPU.

Отсюда переоценка приоритетов:

- **Оптимизация главного потока для него почти ничего не даёт.** 400 мс, которые мы срезали
  на VPS (#38, #64), у него стоили бы ~130 мс, и они тонут в четырёх секундах ожидания сети.
- **Всё решают запросы на первом заходе.** Первый заход 4.7 с против 1.0 с на VPS (4.7×),
  а второй и третий — 0.75–0.9 с против 0.44–0.59 (1.5–1.7×). Разница в 4.7× живёт целиком
  в первом заходе, где зеркало ещё пустое и приходится ходить в сеть.
- Байты на повторных заходах уже маленькие (21–27 КБ) — тут работа #8/#32/#33 видна и на его
  канале.

## Открытая аномалия — назвать, но не объяснять

В ОБОИХ холодных заходах список агентов ждал один-единственный запрос:

```
/api/orchestrators   старт 306 мс → длительность 3500 мс   (прогон 1: 331 → 3506)
список агентов появился на 4297 и 4346 мс
```

Что известно: на VPS тот же эндпоинт в браузере — 24–58 мс; прямым curl с сервера сейчас
70–151 мс; сэмплером с его ноутбука через зеркало — 40 замеров, медиана 450 мс, максимум 686.
То есть **3.5 с не воспроизводятся ни curl'ом, ни на VPS, но воспроизводятся в браузере
на холодном заходе — 2 раза из 2.**

Гипотезы, ни одна не проверена: (а) ответ 21 КБ на плече «Москва → Contabo» упирается в тот же
порог, и зеркало тратит время на восстановление; (б) блокировка головы очереди в HTTP/2 при
~15 одновременных запросах холодного захода; (в) что-то в самом эндпоинте, срабатывающее
только на первый запрос контекста. Проверяется дешёвым зондом (повтор холодных заходов
с записью протокола и числа соединений) — не делал, чтобы не жечь его канал без спроса.

Практически это значит: **первый экран у него упирается не в рендер и не в объём, а в один
запрос на 3.5 секунды.** Если аномалия подтвердится, это единственная правка, которая
сократит его первый заход вдвое.

## Границы

- Два прогона, не восемь: машина рабочая, гонять её дольше без нужды не стал.
- Всё снято через зеркало. Прямой адрес с браузером не мерился — на нём к этим числам
  добавится лотерея обрывов (18 из 24 успешных попыток, см. `mirror.md`).
- loadavg 4.2–5.0 с чужими процессами: числа главного потока скорее завышены, то есть
  реальное преимущество его CPU над нашим ещё больше.

# Разбор аномалии 3.5 с: это наш собственный таймаут

**Ответ на вопрос о покрытии #70: `/api/orchestrators` идёт ЧЕРЕЗ `api()`** — `app.js:1182`,
`const allOrchs = await api('/api/orchestrators')`. Дырки в покрытии нет.

И там же объяснение «аномалии»: `_API_TIMEOUT_MS = 3500`, `_API_ATTEMPTS = 3` (`app.js:5894`).
Замеренные 3500 и 3506 мс — это **ровно наш таймаут**, а не поведение сети. Сырьё сходится:

```
wire=0Б    dur=3500 мс   ← первая попытка: соединение встало, наш api() её оборвал по таймауту
wire=2009Б dur=228 мс    ← вторая попытка: успех
```

Повтор из #70 сработал штатно. Плохо не то, что он был, а **сколько он стоил: 3.5 с
первого экрана при том, что здоровый ответ у него приходит за 0.2–0.7 с.**

## Что предлагаю поменять: 3500 → 2000 мс

Замеры с его ноутбука, самые тяжёлые ЗДОРОВЫЕ ответы:

| | через зеркало | прямой адрес |
|---|---|---|
| `/api/logs/sync` 130 КБ | 0.72–1.33 с | 0.84–1.03 с |
| `app.js` 382 КБ | 0.75–0.98 с | 0.97–1.28 с |
| обычный API-ответ | 0.2–0.7 с | 0.4–0.6 с |

Таймаут 2 с накрывает **все** здоровые ответы, что я видел, с запасом в 1.5×, и при этом:
- зависший запрос стоит 2 с вместо 3.5 (первый экран −1.5 с — это больше, чем весь выигрыш
  #38 и #64 на его машине вместе взятых);
- полностью мёртвый эндпоинт добивается за 6 с вместо 10.5 (три попытки).

## Чего доказать НЕ удалось

Сам стопор вне браузера не воспроизводится. С его ноутбука через зеркало:
- 12 запросов ПАРАЛЛЕЛЬНО на одном HTTP/2-соединении, 5 раундов — худший 0.93 с, зависаний 0;
- те же 12 ПОСЛЕДОВАТЕЛЬНО, 3 раунда — худший 0.67 с, зависаний 0;
- плюс 120 замеров сэмплера ранее — не-200 ноль.

Итого 96+120 запросов без единого стопора, при том что в браузере он случился 2 раза из 2
холодных заходов. Значит триггер связан с чем-то, чего нет в curl (свежее соединение сразу
после навигации, одновременный SSE-поток, порядок запросов). Дальше это ловится только
сетевым логом самого Chromium (`--log-net-log`) на его машине — это уже заметно более
навязчивый зонд, без отдельного разрешения не полезу.
