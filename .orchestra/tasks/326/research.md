## 1. Что Origin даёт сверх нашего расклада — по первоисточнику

Первоисточники, открытые в этой сессии:
[1] https://cursor.com/changelog/origin-code-hosting (17.08.2026),
[2] https://cursor.com/docs/origin, [3] .../origin/cli, [4] .../origin/git,
[5] .../origin/create-repository, [6] .../origin/mirror-github, [7] .../origin/pull-requests,
[8] .../origin/settings, [9] .../origin/codebase-settings, [10] https://cursor.com/docs/api/origin,
[11] https://cursor.com/pricing.

### 1.1 Что реально отгружено (early beta)

Changelog [1], дословно:

> «Origin begins rolling out today in early beta on all paid plans. We're starting with the
> essentials, designed for agent scale: repos, pull requests, code browsing, and GitHub sync.
> **Agent-native features ship soon.**»

То есть **агент-специфичного в бете нет вообще** — по собственным словам вендора. Отгружены:
репозитории, PR, просмотр кода, синк с GitHub. Docs [2] подтверждают тот же список
(«In early beta you can: Create Origin repositories… Clone, push, and pull with standard git…
Mirror a GitHub repository into Origin… Open, review, and merge pull requests…»).

**Про конфликты — единственная фраза во всей документации** [7]:

> «Origin **surfaces** merge conflicts so you can resolve them before merging.»

Surfaces, не resolves. Автоматического разрешения в отгруженной документации нет нигде
(проверено грепом по всем 14 страницам `origin` из `cursor.com/docs/sitemap.xml`).
Постановка задачи здесь совпадает с первоисточником. Про параллельных агентов, stacked PR,
merge queue — в changelog и docs НЕТ НИ СЛОВА (см. counter-evidence §6).

### 1.2 Цена и привязка к подписке

- [2]: «Origin code storage is available on **Pro, Teams, and Enterprise** plans.
  It is not available on free plans.»
- [11]: Individual **$20/мес** (Pro), Teams **$40/юзер/мес**, Enterprise — custom.
- Отдельной цены за Origin (за ГБ, за операции) не опубликовано нигде.
- **Для нас это НОВАЯ подписка:** мы платим за Claude Max 20× + Codex Pro + Grok; подписки
  Cursor у нас нет. Минимальный вход — $20/мес за то, чем сегодня пользуется ноль наших агентов.

### 1.3 API и CLI — есть, и они серьёзные

- **REST API есть**, база `https://api.cursor.com/v1/origin` [10]. Покрытие
  GitHub-подобное: repos, branches, commits/contents, git data (blob/tree/ref/tag), pull requests
  (create/update/merge/review/comments), checks (check runs/suites), webhooks, installations.
  Есть OpenAPI-спека.
- **Аутентификация приложений:** Ed25519-ключ → app JWT → installation access token.
  Git over HTTPS: `x-access-token` + installation token, **токен живёт не более 15 минут**
  («Tokens expire after at most 15 minutes»), минтить перед каждой git-операцией.
- **Rate limits** [10]: installation token — 3 000 points/мин, app JWT — 600/мин,
  user/service-account key — 600/мин, скользящее окно в минуту.
- **CLI** — отдельный бинарь `origin` (не путать с `agent`), ставится
  `curl -fsSL https://downloads.cursor.com/origin/install.sh | sh` в `~/.local/bin/origin`,
  логин `origin auth login` через браузерный флоу; логин ставит git credential helper.
  Умеет `origin repo create/delete`, `origin repo clone`, PR-команды.
- 🔴 **`curl | sh` прямо запрещён нашим глобальным правилом** (`~/.claude/CLAUDE.md`, «🛡 Безопасность»).
  Легального способа поставить Origin CLI по документации у нас нет — только распаковывать
  скрипт руками и читать его перед запуском.
- 🔴 **Ограничение, раздел «Current limitations»** [10], дословно:

  > «**Apps cannot reach a repository that Origin mirrors in from GitHub.** Origin leaves those
  > repositories out of installations, installation access tokens, and webhook deliveries.»

  и

  > «Pull request merge supports native Origin repositories. **Mirrored repositories are rejected.**»

  То есть **API недоступен для репозиториев, зазеркаленных ВНУТРЬ из GitHub (mirror-in)** —
  именно того режима, в котором GitHub остаётся источником истины. Ни API, ни вебхуков,
  ни программного мержа.

  ⚠️ **Поправка после ревью (важно, я это сперва переформулировал шире источника).**
  Направлений зеркалирования ДВА, и API-дока их различает [10, строка 294]:

  > «Neither mode covers a repository that Origin mirrors in from GitHub. An installation reaches
  > native Origin repositories **and repositories Origin mirrors out to GitHub**. A repository
  > mirrored in from GitHub stays outside the installation, so it never appears in
  > GET /installation/repos, and a request that names it returns 403.»

  Значит утверждение «API и мирроринг взаимоисключающи» — шире того, что написано у вендора.
  Существует третья конфигурация: **mirror-out** — Origin источник истины, копия при этом
  продолжает уезжать в GitHub, и installations до неё ДОСТАЮТ. В ней разом снимаются оба
  ограничения: API работает, и запись идёт сначала в Origin (то есть авария GitHub перестаёт
  блокировать push). Вердикт это не меняет — API, PR и CI мы не используем, а платить $20/мес и
  переносить источник истины на early beta по-прежнему не за что, — но формулировку надо держать
  честной. Отдельно: **способа СОЗДАТЬ mirror-out в 14 продуктовых страницах docs нет**
  (греп `mirrors out|mirror out|push mirror` по всем — ноль совпадений; строка живёт только в
  API-доке). Тир этой конфигурации — «упомянута, но без документированного пути включения».

### 1.4 Мирроринг: что именно синхронизируется

[6], дословно: «pushes to a synced repo **pass through to GitHub, which remains the source of
truth**». Included: git history, branches, tags; PR синкаются в обе стороны.
**Not included:** GitHub Issues, GitHub Actions workflows и secrets.

Предусловия миррора [6]: аккаунт с Origin на Pro/Teams/Enterprise, подключённое
**Cursor GitHub app** к орг/аккаунту, и **GitHub admin на репозитории**.

**Следствие для гипотезы H3 (формулировка уточнена после ревью).** Push в mirror-in
транслируется в GitHub, значит GitHub остаётся на пути записи. **Поведение при НЕДОСТУПНОМ
GitHub документация не описывает нигде** — греп `outage|unreachable|upstream unavailable|queued`
по [6] и [10] пуст. Поэтому корректная формулировка не «push физически не проходит», а
**«вендор не документирует, что происходит с push при мёртвом GitHub, — страховкой от аварии
GitHub такой режим считать нельзя»**. Контр-довод, играющий против меня: асинхронная машинерия у
Origin есть — эндпоинт `syncMirror` отвечает `202 pending` и продолжает работу в фоне; исключить
очередь на запись нельзя. Вывод H3 выживает в обеих версиях: недокументированное поведение —
не то, на чём строят план на случай аварии.

Выходы из mirror-in ровно два, и оба не «страховка»: `Settings → Danger Zone → Detach from GitHub`
(Origin становится источником истины, трансляция в GitHub рвётся) или mirror-out (§1.3), у
которого нет документированного пути включения.

### 1.5 Самохостинг и публичность

- **Самохостинга нет.** Слов `self-host`/`on-prem` нет ни на одной из 14 страниц docs `origin`
  и в API-доке. Адреса зашиты: `origin.cursor.com` для git, `api.cursor.com/v1/origin` для REST.
- **Публичных репозиториев нет.** Видимость при создании — только `Internal` (вся команда
  codebase) или `Private` (точечный доступ) [5][8]. Наш репозиторий публичен намеренно
  («origin — наш публичный, держать актуальным», `CLAUDE.md`); на Origin такого режима
  в документации не существует. Публичный репозиторий на Origin воспроизвести нечем.
- Privacy: «Origin follows the Privacy Mode of the namespace owner» [2]; команды на legacy
  privacy mode Origin включить не могут.
- Включение: **opt-out, а не opt-in** — [1] «rolling out… to all paid plan users starting today,
  **except enterprise orgs whose admins opt out**».

### 2.1 А что у нас РЕАЛЬНО дорого (и Origin этого не лечит)

Зафиксировано в `CLAUDE.md` (раздел про переписывание общей истории и Session notes):

1. **12.08** — утечка боевых OAuth-токенов Яндекс.Директа в ПУБЛИЧНЫЙ репозиторий
   (`docs/tasks/sol-efficiency/calls_strict.tsv`), лечение — `git-filter-repo` по всей истории
   в отдельном зеркале + force-push, отдельное операторское окно 13.08.
2. **12.08 и 13.08** — два эпизода переписывания общей истории; мой `git push --force`
   (424 коммита) **уничтожил опубликованный коммит `6fe84146`** и работу #174/#175 ноутбука.
3. **14.08** — `pull --rebase` при живых воркерах осиротил их базы: у `grok-impl` мгновенно
   стало 4 фантомных незамерженных коммита.

Все три — следствия того, что (а) один публичный remote обслуживает ДВА контура и
(б) историю переписывают. **Origin не убирает ни одну из причин.** В режиме миррора GitHub
остаётся источником истины, то есть ровно та же общая история и те же force-push. В нативном
режиме публичный репозиторий исчезает как класс (§1.5), а ноутбук приходится переводить туда же —
это переезд второго контура, а не страховка.

Чтобы упереться в неё, нам нужно вырасти на два порядка ПО ТЕМПУ ЗАПИСИ, а не по числу агентов:
20 живых воркеров дают 15 коммитов в минуту в пике, потому что коммит — это конец куска работы
модели, а не тик цикла.

**Про происхождение самого числа 22.6.** Его НЕТ ни в changelog [1], ни в docs [2]–[10].
Вторичный источник [12] (TechTimes, 24.06.2026, открыт через `r.jina.ai`) относит его к

## 4. Риски подключения

1. **Публичность истории.** Мы уже роняли боевые токены в публичный репозиторий (§2.1).
   Origin добавляет ВТОРУЮ копию всей истории у третьей стороны, причём при мирроринге —
   автоматически и постоянно обновляемую. Наш `git-filter-repo` вычистил GitHub; что происходит
   с уже засинканной копией в Origin после переписывания истории upstream, документация не
   описывает нигде. Механизма «вычистить блоб из миррора» в docs нет.
2. **Второй remote при живых воркерах.** У нас 32 worktree и 234 воркера с мержами за 15 суток.
   Каждый лишний remote — это лишний способ получить расхождение баз; замер 14.08 показал, что
   даже ОДИН remote при `pull --rebase` осиротил ветки живых воркеров. Пользы от второго remote
   в нашей схеме нет: **`merge_worker` мержит локально, push в сеть на критическом пути не стоит
   вообще** (`main` сейчас на 24 коммита впереди `origin/main`, последний fetch 16.08 — то есть
   GitHub у нас асинхронная витрина, а не рабочий инструмент).
3. **Доверие стороннему хостингу.** Условия хранения, резидентность, использование для обучения
   и субпроцессоры для Origin не опубликованы — это отмечает и [13] (VentureBeat, 17.08.2026):
   «Retention, residency, training use, subprocessors… are all unpublished, and a product page is
   not a contract». Там же — что включение сделано **opt-out**, и что Cursor, по сообщениям, стал
   подразделением SpaceX (сделка $60 млрд). Отдельно [13] напоминает про раскрытый Mindgard
   дефект исполнения подложенного `git.exe` при открытии проекта, который вендор чинить отказался.
   Тир этих утверждений — вторичный (§6), но для решения «отдавать ли приватный код» они
   релевантны как минимум как флаг «условий в письменном виде пока нет».
4. **Операционные мелочи, которые у нас уже стреляли.** Installation-токен живёт ≤15 минут и
   минтится под каждую git-операцию; `origin auth login` — браузерный флоу на headless VPS.
   Это ровно тот класс, на котором мы неделю назад обожглись с Grok `--device-auth`
   (токен без refresh, CLI сам удалял `auth.json`). Плюс запрет `curl | sh` (§1.3).
5. **Early beta.** Docs сами пишут: «The Permissions and Rules and Protections UIs are being
   redesigned; labels and layout may change during early beta» [8]; API — «Origin is in Early Beta
   and subject to change» [10]. Строить на этом автоматику оркестратора сейчас — подписка на
   переделки.

## 5. Вердикт

**НЕ НУЖНО — ни сейчас, ни в режиме «попробовать миррор».**

Обоснование стоит на трёх ногах, и после ревью они переставлены — несущая не та, что была
в первой редакции:

1. **Конфликтов 3.2% мержей, медиана восстановления 3.5 мин, и поток ЗАТУХАЕТ** — 11 из 26
   событий в первые двое суток, 1 событие за последние четверо. 54% конфликтов — по прозе.
2. **Наш пик — 15 коммитов/мин против рекламных 1 356/мин** (в 90 раз).
3. **Мы не пользуемся НИЧЕМ из того, что Origin добавляет:** PR не открываем, CI нет, GitHub API
   не зовём, мержим локально, `main` сейчас на 25 коммитов впереди `origin/main` и никто этого
   не ждёт.

Ограничение «API недоступен для mirror-in» — **поддерживающая деталь, а не несущая балка**
(в первой редакции я сделал её главной и заодно переформулировал шире источника, см. §1.3).
Ни одна из трёх наших ДОРОГИХ болей (утечка в публичный репозиторий, force-push по общей истории,
осиротевшие ветки после rebase) не лечится сменой форжа.

**Триггер пересмотра — конъюнкция, а не «посмотреть попозже»:**
Origin публикует в docs (а) автоматическое разрешение конфликтов и (б) stacked PR / merge queue
как отгруженные функции, И (в) доля CONFLICT держится выше 15% мержей **в скользящем окне
7 суток** (именно скользящем: средняя по всему окну не перейдёт порог даже в плохую неделю —
распределение фронт-нагруженное, см. §2), ИЛИ (г) мы начинаем отдавать агентам сквозной цикл
«ветка → PR → CI → мерж» вместо локального squash. Проверка (в) стоит одного SQL-запроса и не
требует ничьего решения.

**Дешёвый эксперимент с Origin — не осмыслен.** Он стоит $20/мес + установку `curl | sh` +
выдачу Cursor GitHub App админского доступа к репозиторию, а измеримого исхода у него нет:
мержим мы локально, PR не используем, CI нет, деплой не на Vercel.

### 🔴 ОТОЗВАНО: `merge=union` для `docs/workers/*.md`

Первая редакция предлагала «свой дешёвый эксперимент на 30 минут»: `.gitattributes` с
`merge=union` для `docs/workers/*.md` и `CHANGELOG.md`, «закрывает до 13 из 26 событий».
**Рекомендация снята целиком.** Независимая проверка сломала её по двум основаниям, оба
подтверждены мной пересчётом:

1. **Арифметика была не та.** Я сложил ПОПАДАНИЯ ФАЙЛОВ (8+8+3+2), а мерж падает, если конфликтует
   ХОТЯ БЫ ОДИН путь — значит союз спасает только событие, где union-покрыты ВСЕ пути. Пересчёт
   по событиям: только `docs/workers/*` — **3**, только `CHANGELOG.md` — **6**, вместе
   **9 из 26 (34.6%)**, а не 13 (50%). Смешанные события (проза + `app.js`/тесты) падали бы всё
   равно.
2. **Цель мертва.** Все 3 события `docs/workers/*` — 03.08, в первый день существования таблицы;
   6 событий `CHANGELOG.md` — 04.08 (5) и 11.08 (1), после чего ноль: пофайловые фрагменты из
   `docs/tasks/52` уже работают. За последние 14 суток union-адресуемых событий **ноль**.
3. **И это было бы ОПАСНО.** `docs/workers/<имя>.md` не просто append-only файл — он
   **перечитывается с диска и инжектится в промпт воркера** при каждом резюме. Union не только
   дописывает: когда одна сторона ПРАВИТ строку на месте, union оставляет ОБЕ версии, exit 0,
   без конфликта. Проверено ревьюером на нашем же примере — отозванное правило
   (`--device-auth`) и его исправление (`--oauth`) оказываются в промпте рядом, молча.
   Сегодня это громкий конфликт, который разбирает человек; union превращает его в тихое
   отравление памяти агента. Плохой размен при любой частоте конфликтов.

Механизм при этом работает: `git merge --squash` действительно исполняет merge-драйверы и
уважает `.gitattributes` (проверено прогоном: без атрибута `exit=1` с маркерами, с
`merge=union` — `exit=0` и обе строки). Строка §7 «UNCERTAIN» по механизму закрыта; отвергнута
рекомендация, а не механизм.

**Что осталось на месте union — и это лучше:**
- Пофайловые фрагменты вместо общего файла (`docs/tasks/52/report.md`, 0 конфликтов) — тот же
  структурный приём, применимый и к `docs/workers/`, и уже доказавший себя на `CHANGELOG.md`.
  Конфликты при нём остаются ГРОМКИМИ, а дублей не возникает.
- **Настоящая причина этих конфликтов — устаревшая база ветки, а не одновременная правка одной
  строки.** `frontend`, конфликтующий на `back.md`, — это не два агента в одном файле, это ветка,
  отрезанная до того, как `back.md` уехал в main. Значит рычаг — свежесть базы перед мержем,
  а не merge-драйвер; у нас это уже больное место (`pull --rebase` при живых воркерах, 14.08).
- **Легитимный исход — не делать ничего.** «Боль мала» — вывод, который §2 действительно
  заработал.

## 6. Counter-evidence и конфликт источников

**Конфликт №1 — автоматическое разрешение конфликтов.**
Вторичный источник [12] утверждает: «Origin's AI-powered conflict engine analyzes each agent's
modification intent and **resolves automatically in the majority of cases**». Первичная
документация отгруженной беты [7] говорит только «surfaces merge conflicts so you can resolve
them». Обе стороны показываю: похоже, что [12] описывает АНОНС с Compile (июнь), а [7] —
то, что реально отгружено 17.08. Разрешаю в пользу первички: **в отгруженном продукте
авторазрешения нет**. Постановка задачи («пока нет») этому соответствует.

**Конфликт №2 — stacked PR и merge queue.** Вторичное покрытие приписывает Origin наследие
Graphite (stacked PR, merge queue). В changelog [1] и во всех 14 страницах docs этих слов нет.
Считаю неотгруженным.

**Что говорит ЗА Origin (честно, против моего вывода):**
- Аргумент про смещение узкого места реален: [13] цитирует внутреннюю цифру Cursor — 35% мержей
  внутри Cursor открыты агентами. Если такая доля станет нормой индустрии, форжи под агентов
  станут отдельным классом инструментов, и наш вывод «не нужно» устареет по сроку годности,
  а не по ошибке.
- Мирроринг действительно дёшев для тех, у кого GitHub на критическом пути (PR-ревью, Actions).
  Он не даёт НАМ ничего именно потому, что у нас этого пути нет — мержим локально. Для проекта
  с человеческим PR-флоу вывод был бы другим.
- Rate limits Origin (3 000 points/мин на installation token) выглядят щедро относительно
  GitHub API — но мы GitHub API и не упираемся, так что это преимущество нам не адресовано.

**Слабые места моего собственного замера (не скрываю):**
- `merge_operations` существует только с 03.08 — 15 суток из 110 суток жизни проекта.
  До 03.08 конфликты не учтены нигде машиночитаемо; в 27 из 204 `docs/tasks/*/report.md`
  слово «конфликт» встречается, но при чтении контекста это в основном РАССУЖДЕНИЯ о конфликтах
  (#61, #115 — исследования поведения мержа), а не инциденты.
- Прокси «время до следующего успешного мержа» завышает цену конфликта (§2), значит настоящая
  боль ещё меньше — это не меняет знак вывода.
- Утверждения §4.3 о SpaceX, условиях хранения и дефекте Mindgard — тир 4 (одна вторичная
  статья [13]). Я их не проверял независимо и на них вывод НЕ держится: вывод держится на
  первичном ограничении «apps cannot reach a mirrored repository» и на наших собственных цифрах.
