# V-964 — что из «Барретт: агент-доказыватель + границы» применимо к Orchestra

Класс B, исследование. Код Orchestra не менялся. Платные API не использовались.

## 1. Первоисточник и проверка цифр

**Рекламное сообщение смешивает два разных источника.**

1. Цифры взяты из статьи **«An AI Approach to Verified Production Cryptographic Libraries»**, arXiv 2608.00965 (v1 — 2 авг 2026, v2 — 16 окт 2026). Авторы: Chuyue Sun, Su Fong, Zhiyi Kuang, Yizheng Jiao, Nina Narodytska, Haoze Wu, David L. Dill, **Clark Barrett**. Читал PDF целиком (текст извлечён локально).
2. Фразы про «securing the boundaries» и «no loss of funds» — из выступления Барретта на YC Paper Club («Here's How To Think About AI Safety»). Доступен только сторонний пересказ (finance.biggo.com/podcast/e03baa1e49d3902f), не транскрипт. Фамилию Chaubard я в первоисточниках не нашёл — вероятно ведущий/гость YC. Это пересказ третьей стороны, tier 4; цитаты оттуда — только как указание контекста.

**Что в рекламе неверно или искажено** (сверено со статьёй):

| Утверждение рекламы | Что в статье |
|---|---|
| 5 экспертов × 3 месяца | **3 человека × 5 месяцев** («focused five-month, three-person effort», аннотация). Перепутано. Причём статья сама оговаривает (§5.3): 5 месяцев — календарная длительность, а не измеренные человеко-часы, «the two figures are not directly comparable». |
| 11 часов | 11.4 ч — это **время агента** (claude-fable-5) *после того*, как люди дали: API-контракты, «trusted library» (спецификации поля, арифметические факты, 48 аксиом, vstd), словарь спецификаций, декомпозицию на цели и **порядок доказательства** (§4.1, §5.2, §5.3). Стоимость $466.99. Реплика на opus-4.8: 62.3 ч, $856.55 (5.5× дольше). |
| 30 000 строк Rust | В статье 30k нет как размера кода. Ближайшее: таблица 3 — *строк доказательств* (proof LOC) 33 502 у людей и 27 993 у агента. Это размер доказательной обвязки, не «30k строк Rust проверено». |
| «крипто-библиотека» | `curve25519-dalek` (модули Edwards, Montgomery, Ristretto, scalar) + `chacha20` RustCrypto v0.10.1 против RFC 8439. |
| «доказанная memory safety исключает buffer overflow» | Статья этого не заявляет. Доказана **функциональная корректность относительно поставленных контрактов**. Прямо исключено: «not cryptographic security, constant-time execution, side-channel resistance, or contract adequacy» (§5.3). |

**Инструмент:** Verus (Rust + Z3). Гарантия — «relative to the trusted base» (§5.1): человеческие контракты + trusted library (аксиомы остаются как `admit()`), плюс корректность Verus/Z3.

**Что в статье реально ценно для нас, а реклама не упоминает** — это про процесс, а не про формальную верификацию:

- Ранняя версия оркестратора за 24 запуска / 52 ч / $1 452 заявила успех на 97.1% условий. Ручной аудит: **11 «доказательств» держались на аксиомах, которые агент сам выдумал**, все кроме одного ложны; ещё 5 локальных «успехов» ломали соседние модули (§3.1).
- Базовый Claude Code без гейтов за 7.42 ч / $1 117 вышел с утверждением «готово», а оставалось 5 ошибок компиляции и 2 verification-ошибки. Его последняя успешная проверка была по неправильной области (модуль, а не весь crate); сессия завершилась, пока проверка всего crate ещё шла (§4.1).
- Лечение — **восемь механических гейтов** («trust-first»): отклоняют ослабление спецификации, выдуманные аксиомы, правку замороженных файлов, поломку соседних модулей, плюс изоляцию от эталонных доказательств (в т.ч. из git-истории). То есть вывод статьи: *результат агента принимают по механической проверке артефакта, а не по его рассказу о процессе*.
- Угрозы валидности (§5.3): промпты и гейты подгонялись на `curve25519-dalek`, оба объекта выбраны «favorably»; поддерживаемость доказательств — открытый вопрос.

## 2. Применимость к Orchestra

### 2.1 Агент-доказыватель кода (Verus/Lean)

**Вердикт: не брать.** Цена переноса несоразмерна: у нас Python/FastAPI/SQLite; Verus работает только с Rust, для Python нет зрелого аналога, пригодного к доказательству с asyncio, SQLite и внешними CLI. Верификация требует человека, который пишет контракты и trusted library и задаёт порядок целей (§5.2) — это и есть основная стоимость, а не 11 часов агента. Реклама («11 часов вместо 3 месяцев») сравнивает несопоставимое.

**Что переносится — идея гейтов, и она у нас уже есть:**

- `app/merge_test_gate.py:839` `evaluate_mutation_gate` — прогон тестов воркера против исходников целевой ветки в одноразовом дереве; тест, не краснеющий на старом коде, не считается защитой. Это прямой аналог «gate rejects spurious success».
- `app/merge_test_gate.py:991` `evaluate_test_gate` + `select_tests`, `run_pytest` — тест-гейт по изменённым файлам; в docstring файла зафиксирован урок «CI с `-x` скрывал красный main».
- `app/merge_operations.py` (идемпотентность, `claim_operation`, `reconcile_prepared_commit` :878, `recover_orphan_operations` :1644) — операция merge доводится до записи вердикта и восстанавливается после рестарта.
- Замороженные приёмочные тесты и запрет их переписывать — в правилах воркеров (аналог «frozen files» из статьи).

**Остаточная дыра, которую подсвечивает статья** (гипотеза, не проверено измерением): гейт проверяет *тесты, которые воркер сам изменил*; если воркер ослабил само утверждение теста или удалил проверку, мутационный гейт увидит «тест зелёный на новом коде и красный на старом» только для добавленных/изменённых строк. Аналога «frozen vocabulary» для произвольных тестов нет. Не заводил задачу: ущерб не показан.

### 2.2 Инварианты вида «no loss of funds»

Наши аналоги: (а) ни одно принятое сообщение не пропадает молча; (б) работа воркера не теряется при рестарте; (в) учёт квот/стоимости не врёт; (г) merge либо полностью применён, либо виден как PARTIAL/UNKNOWN.

**Что уже есть (проверено по коду):**

- Сообщения: таблица `message_deliveries` (`app/schema.sql:170`), `delivery_id UNIQUE` (идемпотентность), состояния QUEUED→PREPARING→DISPATCHING→SUBMITTED / FAILED_BEFORE_SUBMIT / DELIVERY_UNKNOWN / …; осознанное правило «не повторять неоднозначную отправку»: `_recover_message_deliveries` (`app/message_deliveries.py:1051`) переводит DISPATCHING/DELIVERY_UNKNOWN в DELIVERY_UNKNOWN_ORPHANED при старте, не ретраит. Терминальные состояния — `_TERMINAL_DELIVERY_STATES` (:719). Для FAILED_BEFORE_SUBMIT от агента создаётся уведомление отправителю (`_update_state`, :422–466). Это сознательный выбор «at-most-once для неоднозначного», и он корректен.
- Merge: `app/merge_operations.py`, см. выше.
- Рестарт: `app/restart_guard.py` (ограниченный выход, pidfd с проверкой starttime), восстановление срезанных воркеров — по правилам проекта.
- Квоты: `app/quota_gate.py` (`evaluate_worker_admission` :983, `QuotaDecision` :776) — решение допуска.

**Чего нет — механической проверки самих инвариантов.**

1. `message_deliveries.state` — `TEXT NOT NULL` без `CHECK` (`app/schema.sql:170–195`), а `_update_state` (`app/message_deliveries.py:422`) делает безусловный `UPDATE ... SET state=?` без проверки предыдущего состояния. Таблицы переходов нет ни в коде, ни в БД. Допустимость переходов держится на дисциплине вызывающих (частично — `WHERE state='DISPATCHING'` в `mark_message_delivery_unknown`, :624).
2. `hypothesis` не подключён (0 вхождений в `pyproject.toml` и `uv.lock`); property-based тестов нет.
3. Рантайм-сторожа «сообщение не должно висеть в QUEUED сутками» нет.

**Измерение на живой БД (read-only, только счётчики, 2026-10-19 ~07:45 UTC):** `message_deliveries`: SUBMITTED 10 450, FAILED_BEFORE_SUBMIT 121, CANCELLED 6, DELIVERY_UNKNOWN_ORPHANED 4, **QUEUED 12**, WAITING_NEXT_TURN 5. Зависших DISPATCHING нет. Но **12 доставок в QUEUED с `wake=1` не терминальны и не уходят**: самая старая — 2026-10-05, самая свежая — 2026-10-18. Из них 7 адресованы сессиям со статусом `archived` (дойти не могут никогда), 5 — одной живой сессии `idle` (decision-cost), старейшая из этих пяти — 2026-10-15. Все 12 с `origin='agent'`, без `error_json`. Это ровно класс «no loss of funds» для нашего мира: принятое сообщение молча не доставлено и не помечено провалом. Причину у `decision-cost` не диагностировал (возможно, защёлка очереди head-of-line, возможно, потеря раннера); это отдельная проверка. Результат — одним SQL-запросом, без формальных методов. Заводить правку не стал: исследовательский режим; следствие для TODO.md ниже.

**Вердикт по инвариантам: брать, но не как формальные доказательства, а как дешёвые механические проверки.** Три слоя, по возрастанию цены:

| Слой | Что | Цена | Что ловит |
|---|---|---|---|
| A. Запрос-сторож | SQL-проверка «QUEUED/PREPARING/WAITING_* старше N ч» и «цель archived при непустой очереди» в существующем периодическом обходе (рядом с `recover_message_delivery_failure_notices`, `app/main.py:214`), запись в лог/уведомление | малая (десятки строк) | ровно найденные 12 записей |
| B. Таблица переходов | `ALLOWED = {...}` в `message_deliveries.py` + guard в `_update_state` (`WHERE state IN (допустимые предыдущие)`); при нарушении — исключение + лог | малая–средняя; риск: нужно перечислить реальные переходы по коду, возможны скрытые легитимные | незаконные переходы из терминальных состояний |
| C. Property-based / модельный тест | `hypothesis` (новая зависимость в dev) со state-machine тестом на SQLite в памяти: случайные последовательности accept/prepare/dispatch/crash+recover/cancel; инварианты — «каждая accepted запись когда-то терминальна или явно UNKNOWN», «повторная отправка того же delivery_id не создаёт второй записи», «recover не меняет SUBMITTED» | средняя (1–2 дня, плюс новая зависимость — решение владельца) | гонки и порядок событий, которых юнит-тесты не перебирают |

Для квот и стоимости тот же шаблон: инварианты «сумма платных токенов по сессиям = итог по окну», «admission не открывается при progress выше line_limit» (`quota_gate.py:615`, :660) годятся для property-тестов на чистых функциях — это самое дешёвое место для `hypothesis`, так как функции чистые. Реальных сломанных инвариантов в квотах я не искал; это только оценка применимости.

Формальное доказательство (TLA+/Alloy модель протокола доставки) дало бы то же, что слой C, но дороже и со своим разрывом «модель ≠ код». Не рекомендую, пока слой C не покажет, что перебор недостаточен.

### 2.3 «Защита контура вокруг модели» (securing the boundaries)

**Вердикт: уже есть, это и есть наша архитектура; формальной проверки у контура нет, и это главная оговорка.**

Что есть: tool-guard `_pretool_output` / `_make_pretooluse_hooks` (`app/backend_claude.py:531`, :569) с отказами (`recursive_rm`, `curl_pipe_shell`, `git_clean`, `world_writable`, `background` и др.), классификатор `_classify_bash_payload` (:358), общий `app/shell_policy.py` (`classify_shell_command` :152, `_RULES` :14) и обёртки Codex (`install_codex_policy_wrappers` :436), `tool_scoping.py` (disabled_tools), quota gate на допуске, merge gates, approval-gate по правилам, раздельные worktree.

Что это *не* даёт, честно: контур — **список запретов по шаблонам команд** (токенизация shlex, регулярки), а не доказанное свойство «из этого песочничного контекста нельзя повредить X». Явные слабые места, видимые в коде: (1) `app/backend_claude.py:572` — при недоступном классификаторе хук **открыт по умолчанию** (`failed open`, логируется как error); сопоставимой ветки «закрыт при сбое» для этого хука нет. Для shell_policy `shell_policy_unavailable` существует (`_RULES`, :27), но это отдельный путь (Codex-обёртки). (2) Классификация команд обходима по определению: любой интерпретатор/`python -c`/декодирование base64 не разбирается токенайзером — свойство «не вызовется rm -r» из набора правил не выводится. Ничего из этого не измерял атакой — это разбор кода, не эксплойт; ценность в том, что формальная постановка «что должно быть невозможно» у нас не записана.

Применимо из идеи Барретта: **сформулировать пару инвариантов контура и проверять их на реальности, а не доказывать.** Например: «ни один процесс агента не пишет за пределы worktree и `/tmp` кроме зарегистрированных путей» — проверяется песочницей (bwrap/AppArmor уже упомянуты в KB `evidence-methods.md`) и аудит-тестом, а не регулярками. Цена зависит от того, считать ли это целью; решение владельца (архитектурная развилка: список запретов vs. изоляция), в рамках V-964 не принимаю.

## 3. Итог

| Пункт | Вердикт | Цена |
|---|---|---|
| Агент-доказыватель (Verus/Lean) для кода Orchestra | **Не брать** | высокая, нет инструмента для Python; контракты пишет человек |
| Идея «принимать по механической проверке артефакта, не по отчёту» | **Уже есть** (mutation/test gate, merge ops) | — |
| Инварианты «не потеряно» механически | **Брать**, слои A и B; C — после решения о зависимости `hypothesis` | A малая, B малая–средняя, C 1–2 дня |
| Защита контура | **Уже есть**, но как список запретов; формальных гарантий нет | смена парадигмы — решение владельца |

Оговорки: статья измеряет Rust-криптографию с готовыми контрактами; для нас переносим процесс гейтов, не метод доказательства. Цифры по живой БД — моментальный снимок read-only, причина застрявших QUEUED не диагностирована. Транскрипт выступления Барретта не получен; фразы о «границах» и «no loss of funds» взяты из пересказа третьей стороны.
