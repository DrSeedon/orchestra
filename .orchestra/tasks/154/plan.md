# #154 — план: гейт по исчерпанной квоте Codex

Основан на `docs/tasks/154/research.md` (коммит `0be2da7` + исправление раздела про `codex_review`).
Развилку по точкам гейта решил оркестратор; ниже она зафиксирована как данность, а не как выбор.

## Подход одной фразой

Ни одного нового источника состояния. Три MCP-тула перед действием спрашивают **уже
существующую** `provider_readiness()` через новый read-only HTTP-эндпоинт и отказывают
только в состоянии `reset`. Всё остальное — пропуск.

## Что решено за нас (границы)

| Решение | Источник |
|---|---|
| Гейтим ровно `spawn_worker`, `change_worker_model`, `codex_review` | оркестратор |
| `manager.send` НЕ гейтим; обход через Telegram — известная дыра, в отчёт | оркестратор |
| Fail-open жёстко: нет данных / мусор в дате / время в прошлом → пропускаем | постановка + §4.1 research |
| Проверку поведения провайдера после сброса 08.08 делает оркестратор | оркестратор |
| Баг `_provider_for_model` (лимит относится к ТЕКУЩЕЙ модели сессии) не чиним | оркестратор |

## Архитектурное решение и почему именно оно

**Вся проверка целиком на стороне MCP; сервер отдаёт только данные.**

Причина — жёсткая, не вкусовая. `app/mcp_stdio.py` запускается как отдельный процесс-скрипт
и **из `app/` импортирует ровно один модуль** — `app.errtext` (комментарий в шапке файла:
«Модуль на голой stdlib … и ничего больше из app/ не тянет»). Импортировать
`app.limit_wake.provider_readiness` оттуда нельзя: он тянет `app.db`, `app.models`,
`app.session`. Значит решение либо целиком на сервере, либо целиком в MCP поверх HTTP.

Целиком на сервере не выходит: `codex_review` не имеет своего роута — он создаёт
**обобщённую** фоновую джобу `POST /api/bg/jobs` с `type=run` и произвольной shell-командой.
Гейтить его на сервере значило бы вынюхивать `codex` в теле команды. Это ровно тот
«умный» неявный код, который запрещён.

Отсюда: **новый read-only эндпоинт + один хелпер в MCP, зовущий его из трёх мест.**

### Окно рассинхрона MCP↔route закрывается само

Грабля проекта: MCP подхватывается немедленно, `app/routes/` — только после рестарта.
То есть между мержем и рестартом новый MCP будет звать эндпоинт, которого на живом сервере
ещё нет → **404**. Специальной обработки это не требует: по политике fail-open любая ошибка
обращения = «не знаю» = пропустить. Гейт в этом окне просто не работает — ровно так же,
как он не работает сегодня. Ухудшения нет, и это единственная причина, по которой такая
правка вообще допустима без немедленного рестарта.

## Что меняется

### `app/routes/system.py` — новый эндпоинт (≈30 строк)

`GET /api/usage/readiness?model=<model>` — рядом с `/api/usage/history`, `/api/usage/analytics`.

Цепочка (никаких новых вычислений, только склейка существующих):

```
model → resolve_model()            app/models.py:611     (алиасы: "sol" → "gpt-5.6-sol")
      → _provider_for_model()      app/limit_wake.py:35  ("codex" | "codex_spark" | "anthropic")
      → current_provider_usage()   app/routes/system.py:880, force_refresh=False → ~9 мс из кеша
      → provider_readiness()       app/limit_wake.py:123 ← ЕДИНСТВЕННОЕ решение
```

Ответ: `{"provider": str, "state": str, "reason": str, "reset_at": str | null}`.

**Эндпоинт не бросает исключений ни при каком входе.** Каждая ветка «не знаю» отдаёт
`state: "unavailable"` с внятным `reason`:

| Вход | `state` | `reason` |
|---|---|---|
| `is_owner_mode()` == False (инсталляция клиента) | `unavailable` | `owner mode is off` |
| `resolve_model` бросил `ValueError` | `unavailable` | текст исключения |
| `current_provider_usage` бросил | `unavailable` | `err_text(exc)` |
| провайдера нет в снимке | `unavailable` | из `provider_readiness` |
| данные есть | вердикт `provider_readiness` как есть |

`is_owner_mode` нужен потому, что `reset_at` + «исчерпано» — это данные о НАШЕЙ квоте,
а на клиентской инсталляции их показывать нельзя (тот же принцип, что у `/api/usage`,
`app/routes/system.py:873`). Побочно это же и правильное поведение: у клиента нет
codex-кредов, гейт обязан быть открыт.

### `app/mcp_stdio.py` — один хелпер + три вызова (≈45 строк)

```python
_CODEX_REVIEW_MODEL = "gpt-5.6-sol"   # тул этой моделью и представляется в докстринге;
                                       # важен только её лимит-id — "codex"

async def _quota_refusal(model: str) -> ApiToolError | None:
    """Отказ, если провайдер модели доказанно исчерпан. Не знаем → None (fail-open)."""
```

- зовёт `_api("GET", "/api/usage/readiness", params={"model": model})`;
- **любое** исключение / нераспознанный ответ → `None` (пропустить), с `logger.warning`,
  называющим класс исключения — молчаливых веток не оставляем;
- блокирует **только** `state == "reset"`;
- возвращает `ApiToolError` с:
  - `code="quota_exhausted"`,
  - `retryable=False` + `retry_after_seconds=<секунд до сброса>`. Именно так, а не
    `retryable=True`: у нас записан в граблях реальный случай «Codex ретраит вечно на
    исчерпанной квоте», и флаг, читающийся как «можно повторить», приглашает агента
    в цикл длиной до суток. Время до сброса при этом сохраняем — оно информативно
    и `_canonical_error` его не режет (`app/mcp_stdio.py:110`),
  - `details={"provider", "model", "reset_at"}`,
  - `message` — человекочитаемый, см. ниже.

Формат отказа (собирается в одном месте, одинаков для всех трёх тулов):

```
ОТМЕНА: квота Codex исчерпана (провайдер codex, модель gpt-5.6-sol).
Рантайм недоступен до 2026-08-08 07:53 CEST (05:53Z).
Возьми Claude-модель (claude-opus-5[1m]) или дождись сброса.
```

Локальное время — через `datetime.fromisoformat(...).astimezone()` (stdlib, системная зона),
UTC рядом в скобках, потому что именно в локальном времени формулирует отказ сам провайдер
(§2.3 research), а в UTC живут наши логи.

Точки вызова:

| Тул | Куда | Почему туда |
|---|---|---|
| `spawn_worker` (`:541`) | сразу после проверки `if not model`, **до** `POST /api/sessions` | иначе останется worktree мёртвого воркера (риск 5 research) |
| `change_worker_model` (`:1043`) | первой строкой | отказ громкий сразу, хотя провал случился бы позже |
| `codex_review` (`:1830`) | первой строкой, до резолва cwd и сборки команды | не создавать джобу, которая гарантированно упадёт |

`spawn_worker` и `codex_review` уже бросают `ApiToolError`; `change_worker_model` сейчас
возвращает строку. Бросаем везде — один паттерн вместо двух, а `retry_after_seconds`
в строке не передать.

### `app/mcp_stdio.py` — формулировка провала джобы (1 строка)

Сейчас `message="Codex {action} done. Results in {output}"` → под префиксом `_fail_notify`
читается как `[Background job FAILED] Codex exec done.` — успех на провале.

Меняем на `f"Codex {action} → {output}"`. Читается верно в обе стороны:
- успех: `Codex exec → docs/tasks/80/CODEX_REVIEW.md`
- провал: `[Background job FAILED] Codex exec → docs/tasks/80/CODEX_REVIEW.md`

Проброс причины **не трогаем** — он работает, доказано двумя живыми доставками
(исправление в research.md).

## Чего НЕ делаем

- Не трогаем `provider_readiness`, `_provider_for_model`, `_normalize_codex_usage`.
- Не тянем `rateLimitReachedType` в нормализованный контракт (§2.6 research) — это смена
  формы `provider_usage`, которую читают графики и история.
- Не схлопываем дубль `_claude_subscription_limit_active` (§1.4 research) — отдельная задача.
- Не гейтим `manager.send`, `create_session` на сервере, TG-мост.
- Не добавляем ни одной настройки: ни порога, ни выключателя гейта, ни TTL.
- Не зовём `force_refresh=True`: это 1.0–1.25 с и подпроцесс на каждый спавн, а для
  СНЯТИЯ гейта свежесть не нужна вовсе (§4.1 research).

## Риски плана

1. **Полярность `unavailable`** — у `limit_wake` «не знаю» → не действовать, у нас →
   действовать. Один и тот же `state`, противоположная трактовка. Закрывается
   комментарием на месте + T2 AC7.
2. **`hasCredits: true`** — если у аккаунта появятся кредиты, `utilization 100` перестанет
   означать «нельзя», и гейт даст ложную блокировку. Непроверяемо сегодня (`balance: "0"`).
   Принято оркестратором как известный риск; аргумент за fail-open, а не против гейта.
3. **Окно до рестарта** — §«Архитектурное решение»; закрывается самим fail-open.
4. **Известная дыра:** сообщение юзера из Telegram (`app/tg_bridge.py:377`) и любая
   доставка мимо трёх тулов гейт не проходят. Оставлено сознательно.
5. **`codex_review` привязан к провайдеру `codex`.** Сегодня это верно: в
   `~/.codex/config.toml` ключа `model` нет (проверено), и мой живой `codex exec` отказал
   по квоте, тогда как Spark на 1% — то есть `exec` доказанно ходит в бакет `codex`.
   Пропишут в конфиг `model = "gpt-5.3-codex-spark"` — гейт начнёт ложно отказывать при
   живом Spark. Усложнять код под ненаступивший случай не будем; риск записан.
6. **Имя поля в ответе эндпоинта — `reason`, не `error`.** `_api` бросает исключение на
   любом `payload["error"] is not None` (`app/mcp_stdio.py:496`), и ответ «не знаю»
   превратился бы в ложную транспортную ошибку.
