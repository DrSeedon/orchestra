## Как это работает

```
model → resolve_model → _provider_for_model → current_provider_usage(кеш) → provider_readiness
```

Закрыто **ровно одно** состояние: `reset` (исчерпано И известно будущее время сброса) и только
для провайдеров `codex` / `codex_spark`. Всё остальное — пропуск.

Anthropic в гейт не включён намеренно: при исчерпанной квоте Claude отказ «возьми другую
модель» отправил бы агента в пустоту — альтернативы нет, а спавн встал бы совсем.

## AC9 — прогон на ЖИВОЙ исчерпанной квоте (дословно)

Единственная возможность за неделю: квота Codex выбрана сейчас, 08.08 в 07:53 она вернётся.

**A. Хелпер MCP против работающего сервера** (роут ещё не поднят — Python живёт в памяти
systemd до рестарта):

```
INFO:httpx: GET http://127.0.0.1:8888/api/usage/readiness?model=gpt-5.6-sol "HTTP/1.1 404 Not Found"
WARNING:orchestra-mcp:quota gate open for gpt-5.6-sol: readiness unavailable: ApiToolError: Not Found
A) _quota_refusal против ЖИВОГО сервера: None  (0.078s)
```

Это не обход проверки, а сама проверка: **окно между новым MCP и старым роутом закрыто
живым fail-open**, а не рассуждением. Отказ назвал себя в логе.

**B. Эндпоинт против настоящих квот провайдера** (`is_owner_mode() = True`):

```
B) gpt-5.6-sol         -> {"provider": "codex", "state": "reset", "reason": "provider capacity is exhausted", "reset_at": "2026-08-08T05:53:45+00:00"}  (0.950s)
B) gpt-5.3-codex-spark -> {"provider": "codex_spark", "state": "available", "reason": "provider capacity is open", "reset_at": null}  (0.007s)
B) claude-opus-5[1m]   -> {"provider": "anthropic", "state": "unavailable", "reason": "required seven_day usage is incomplete", "reset_at": null}  (0.006s)
```

0.950 с — первый вызов в холодном процессе (поднимается `codex app-server`); дальше 0.007 с
из кеша. В живом сервере кеш греет фоновый цикл, так что гейт платит вторую цифру.

**C. Настоящий текст отказа, каждая модель резолвится сама:**

```
C) gpt-5.6-sol:
   ОТМЕНА: квота Codex исчерпана (провайдер codex, модель gpt-5.6-sol).
   Рантайм недоступен до 2026-08-08 07:53 CEST (05:53Z).
   Возьми Claude-модель (claude-opus-5[1m]) или дождись сброса.
   envelope: {"code": "quota_exhausted", "retryable": false, "retry_after_seconds": 81184}
C) gpt-5.3-codex-spark: ПРОПУСК (гейт открыт)
C) claude-opus-5[1m]:   ПРОПУСК (гейт открыт)
```

**07:53 CEST — та самая минута, которую печатает сам провайдер** в терминальном отказе
(`try again at Aug 8th, 2026 7:53 AM`). Источник и отказ сошлись на живых данных.

Первая редакция скрипта AC9 отдавала ОДИН payload на все модели, и в выводе получилось
«провайдер codex, модель claude-opus-5[1m]» — дефект стенда, не кода. Переписал так, чтобы
каждая модель шла в эндпоинт сама; в отчёт попал второй прогон.

## Мутационная проверка (T4)

Каждая мутация — отдельно, `cp F F.bak` → мутация → прогон → `mv F.bak F`, якорь проверен
на уникальность (`grep -c` = 1 у всех трёх) и маркер сверен после отката (0).

| Мутация | Ожидание | Факт |
|---|---|---|
| `state != "reset"` → `state != "никогда"` (гейт никогда не закрывается) | красная закрытая сторона | **5 failed** — spawn / change_model / codex_review / текст отказа / конверт |
| `return None` → `raise` в except (инверсия fail-open) | красный fail-open | **2 failed** — 404-до-рестарта и транспортная ошибка |
| `_provider_for_model(...)` → константа `"codex"` | красный Spark | **3 failed** — Spark, Claude, алиасы |

Третья мутация — главная: она проверяет, что блокировка вызвана ИМЕННО исчерпанным бакетом,
а не тем, что провайдер называется codex. Гейт по рантайму убил бы полностью рабочий Spark
(сейчас 1% из 100 при `codex` на 100%).

## Найденные проблемы

1. **Ошибка в моём же research, исправлена до планирования.** Я написал «причина провала
   `codex_review` до агента не доходит» — неверно. Пустой `last_output` в БД сбил с толку:
   `bg_fail_job` не пишет вывод в колонку, но `_fail_notify` кладёт хвост прямо в тело
   сообщения. Проверено по двум фактическим доставкам (`fix-mcp-schema` 06.08,
   `research-codex-html` 05.08) — оба агента получили текст лимита дословно. Из плана ушёл
   целый пункт: чинить проброс не надо. Раздел помечен как ИСПРАВЛЕНИЕ, не переписан задним числом.
2. **`_provider_for_model` берёт ТЕКУЩУЮ модель сессии** (`app/limit_wake.py:35`). Воркер
   упирается в лимит на Sol, модель переключают на Opus — и codex-овый лимит относится к
   провайдеру `anthropic`, то есть пробуждение планируется по чужому окну. Живой пример:
   `restore-pd`, 05.08, 10:41:09 лимит → 10:41:29 смена модели. Конкретно там не выстрелило
   (новое сообщение вывело сессию из кандидатов), конструкция хрупкая. **По указанию не чинил**,
   оркестратор заводит отдельно.
3. **Дубль механизма:** `_claude_subscription_limit_active` (`app/session.py:67`) — вторая
   копия «квота выбрана?» на сырых данных, anthropic-only, один потребитель (гард перед
   `compact()`). Кандидат на схлопывание в `provider_readiness`. Не трогал — отдельная задача.
4. **Известная дыра, оставлена сознательно:** гейт стоит на трёх тулах, а не на доставке.
   Сообщение юзера из Telegram (`app/tg_bridge.py:377`) идёт мимо `manager.send` в обход гейта
   и сожжёт ход. Решение оркестратора: в `manager.send` отказ некому вернуть, а одна из
   11 точек (`bg_jobs.py:608`) несёт `[Background job FAILED]` — блокировка потеряла бы
   уведомление вместо экономии хода.

## Риски, принятые осознанно

- **`hasCredits: true`** → `utilization 100` перестанет означать «нельзя», гейт даст ложную
  блокировку. Сегодня непроверяемо (`balance: "0"`). Аргумент за fail-open, а не против гейта.
- **Поведение провайдера сразу после сброса** (роняет ли он `usedPercent` или только катит
  `resetsAt`) — проверку 08.08 после 07:53 взял на себя оркестратор.
- **`codex_review` привязан к бакету `codex`.** Проверено: в `~/.codex/config.toml` ключа
  `model` нет, и живой `codex exec` отказал по квоте при Spark на 1% — значит `exec` в
  Spark-бакет не ходит. Пропишут туда Spark — гейт начнёт ложно отказывать.

## Codex-review

**Вердикта нет.** `codex exec` отвечает ровно тем отказом, ради которого написана задача
(`EXIT=1`, `You've hit your usage limit … try again at Aug 8th, 2026 7:53 AM`) — и теперь этот
вызов вообще не дошёл бы до провайдера, его перехватил бы собственный гейт. Вместо ревью —

включая снятие `retryable=True`. Ревью после сброса квоты зовёт оркестратор.

## Урок

Быстрая проверка может соврать правдоподобно: пустая колонка `last_output` выглядела как
доказательство «данные до агента не доходят», а путь доставки шёл мимо этой колонки.
Проверять надо потребителя, а не первое пустое поле по дороге.
