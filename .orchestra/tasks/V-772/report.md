## Database backup and scheduling

`scripts/orchestra_backup.py --daily` resolves both data paths from the live process environment, obtains a nonblocking per-backup lock, uses SQLite's backup API to snapshot the WAL database, runs `PRAGMA integrity_check`, records row counts for every user table in a manifest, compresses with zstd, verifies the compressed file, then atomically publishes the archive and manifest. It retains the newest two local archive/manifest pairs under `data/backups/` (already ignored by Git). The laptop destination is `/mnt/data/orchestra-backups`; transfer uses the existing SSH reverse tunnel, checks SHA-256 and zstd integrity before publishing, and retains two verified pairs. A failed laptop attempt leaves the local backup available for the next daily retry.

The laptop tunnel connected to `maxim-911aird`; `/mnt/data` had 47 GiB free. The user systemd manager is active with linger enabled, and a 2 GiB scope command was verified. Backup work runs over `ssh kesha@localhost` with `nice -n 15 ionice -c 2 -n 7`, outside the Orchestra service cgroup. The script's unit tests use a temporary WAL database and a temporary bare Git remote only.

The selected scheduler is two durable `bg_create(type="cron_command")` entries: task-store push hourly (`bg-a700fde5c1`) and database/laptop backup daily at 02:00 UTC (`bg-a5a367bedc`). They target `Orchestra-orchestrator` and match only the script's `BACKUP_FAILURE` output; successful runs produce no output and do not wake the agent. I chose `bg_create` over the user systemd timer because its command-pattern gate supplies the requested failure-only wake directly, and the job rows survive Orchestra restarts. The SSH command carries absolute script paths because bg job cwd defaults to the service directory. No Orchestra restart is required.

The initial daily run (`bg-e943a93418`) created and verified the local archive but expired after 60 minutes during laptop upload. Its remote `.partial` was 843,417,600 bytes of 1,464,034,358 bytes. A later SSH probe received `Connection timed out during banner exchange`, so the 60-minute stall was a nonresponsive tunnel, not measured low throughput. The exact orphaned Python/scp PIDs from that run were stopped. The local archive remained intact (`zstd -t` and manifest SHA passed).

For the resume test, rsync continued the existing partial. In a 40-second bounded pilot, the remote size advanced from 843,417,600 to 1,163,036,672 bytes (319,619,072 bytes; 8.0 MB/s average). A subsequent `rsync --partial --append-verify` completed the remaining archive; remote `zstd -t` passed, and local and laptop SHA-256 both equal `ae8379fbcac49c80f632b8b844b5b2fc36813c39493142bcc723f4d7491470ee`. Each transfer attempt is limited to 450 seconds plus a 5-second kill margin and uses SSH keepalives. The measured local snapshot/compress/check stage took 48.49 seconds; an existing-archive daily reconciliation took 24.94 seconds. Adding those measured stages to the 455-second transfer limit gives 528.43 seconds, about 71 seconds under the background run's 600-second limit. At 8.0 MB/s, 1.46 GB transfers in about three minutes while the tunnel responds. When a slice expires after progress, the script now emits `BACKUP_FAILURE step=laptop BackupError: incomplete, N из M байт`; the verified local archive remains. The daily archive name changes with the date, so a later day's archive does not continue the previous date's partial.

Compression comparison used the same 3,424,034,816-byte restored SQLite file, sequentially with `nice=15`, `ionice=2/7`, and one zstd thread. Existing `-3` output was 1,464,034,358 bytes. `-5` took 23.91 seconds and produced 1,437,603,705 bytes (26,430,653 bytes / 1.81% smaller). `--long=27 -5` took 24.54 seconds and produced 1,339,946,988 bytes (124,087,370 bytes / 8.48% smaller than `-3`). The new backup setting is `--long=27 -5`; its measured 8.48% reduction saves about 124 MB per retained copy. Both endpoints have zstd installed (VPS 1.5.5, laptop 1.5.7); the tested laptop backup itself is byte-identical to the local `-3` archive. Raw comparison sizes and durations are in `zstd-measurements.log`.

The full local backup phase, using the live 3.4 GB SQLite database and the new compressor, took 48.49 seconds (`daily-timing.log`) and produced a 1,349,409,592-byte archive. That normal run exposed that the temporary raw database's `-wal` and `-shm` companions survived after the database was unlinked. The backup `finally` now removes both companions, and the SQLite backup test asserts they are absent; the observed sidecars and temporary measurement archive were cleaned. The full attempt is bounded by the 450-second transfer slice plus measured local and reconciliation stages as above.
