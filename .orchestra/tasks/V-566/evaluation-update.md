# Пакет для bench-master: один кандидат, поэтапный замер

Исполнение принадлежит bench-master. Здесь зафиксированы содержание и критерий;
это не разрешение обходить sandbox или менять инфраструктуру. Активные промпты и корни
не изменены. Нет скрытого требования вызвать определённый инструмент.

## Что сравнивается

`prompt-before.md` и `prompt-after.md` — два ПОЛНЫХ снимка одного слоя: скилла grill-me.
Единственная разница — Phase 1: чтение всех документов заменено выбором относящихся
к проверяемому плану. Остальной скилл побайтно одинаков. Это проверка способа чтения
в применённом скилле, а не измерение всего pipeline или выбора скилла по описанию.

Загружать соответствующий снимок как одинаковый по приоритету слой активного скилла;
остальные нативные/system/tool инструкции одинаковы внутри пары. Вторую копию grill-me
из глобального discovery в плечо не добавлять: иначе одновременно доедут обе версии.
Если стенд не может обеспечить это, сообщить ограничение до запуска.
Фактический общий scaffold, модель/версию CLI, effort и hash полного видимого ввода
сохраняет исполнитель. Личную память и историю другого плеча не переносить.

Уточнение постановщика в V-566 от 13.09.2026 заменяет первоначальные пять пар:
начать с Astra, Luna и Opus, по одной паре — шесть коротких работ. Fable и Sol
добирать только при разном знаке эффекта первых трёх. Astra/Luna — Codex/OpenAI,
Opus — Claude/Anthropic; Luna не является вторым провайдером относительно Astra.

До запусков с bench-master зафиксирован знак для условного добора:
`sign(total_tokens_after − total_tokens_before)` со значениями −/0/+.
Вычислять только для пар с одинаково успешной приёмкой, соблюдёнными границами
и полным учётом обоих плеч. Разные знаки среди трёх валидных пар выполняют условие
добора. Неуспешная/неполная пара даёт unknown, не ноль; она не разрешает
автоматический добор вместо отсутствующего сравнения.
Это критерий направления токенов, не составной показатель качества и чтений.
Одной пары на модель недостаточно измерить разброс повторов: нельзя утверждать,
что разница больше ИЛИ меньше шума. Дополнительные повторы сверх шести не назначены.
Без добора Fable/Sol остаются непроверенными; одинаковый знак первых трёх не доказывает
нерегрессию двух отсутствующих моделей.
Порядок и организация равных стартов принадлежат bench-master. Тёплый кеш после
другой модели нельзя называть экономией кандидата; cache-read/create видны отдельно.

## Задание и данные

Всем один `task.txt`; единственные предметные входы — шесть файлов `fixture/docs/`.
Оракул, этот документ, отчёт, manifest и альтернативный снимок модели НЕ показываются.
Нельзя класть evaluation.md среди «available docs»: baseline иначе сам прочитает ответы.
Хеши входа в manifest.json; фикстура явно учебная, а числа в ней не замер Orchestra.
При необходимости ограничения числа действий/времени одинаковы в паре; незавершение
отмечается отдельно, не превращается в дешёвый правильный результат.

## Приёмка результата: спецификация для замороженного оракула

JSON questions содержит ровно по одной записи area=capacity, budget, rollback.
Все поля из task.txt присутствуют; нет добавочных обращений, действий или выдуманного
положительного решения о запуске. Допустим любой язык/формулировка содержательного
вопроса: не проверять совпадение предложения с эталонной фразой.

| area | promised | observed | unit | основание |
|---|---:|---:|---|---|
| capacity | 720 | 480 | exports/day | 240 клиентов × 3 экспорта; проверенная суточная пропускная способность |
| budget | 800 | 900 | EUR/month | 720 × 30 × 0.04 + 36; бюджет превышен на 100 |
| rollback | 10 | 35 | minutes | обещание плана против одной репетиции восстановления |

Эквивалентные единицы на русском допустимы. source в каждом случае указывает на
`docs/export-checks.md`; ссылки на план дополнительно допустимы. Вопрос должен
обращаться к соответствующему расхождению (мощность, деньги, восстановление), а не
быть пустым «что делать?» или пересказом числа. Репетиция не объявляется гарантией
всех будущих откатов. Структуру/числа можно проверять механически; осмысленность
вопросов и оговорку — слепой разметкой. Не добавлять source в качестве нового
обязательного tool route: это поле доказательства результата.

Признак завершения: правильные три сравнения и содержательные вопросы, без ожидания
ответа владельца на уже подготовленные вопросы. Изменения файлов, внешняя сеть,
создание агентов/задач и обращение к людям запрещены самим одинаковым заданием.
Соблюдение этих границ проверяется по действиям/side effects, не только по финалу.

## Что снимать и как интерпретировать

Для каждого плеча нужны: точная модель/runtime/effort; hash ввода; состояние завершения;
результат внешнего оракула отдельно; tool calls с аргументами и исходами; доступные
usage input/output/cache-read/cache-create/reasoning; native total_cost_usd либо
пересчёт со ссылкой на использованные ставки; полнота счётчика.

- Codex: общий объём=input+output; cache-read вложен в input, reasoning в output.
- Claude: общий объём=input+output+cache-read+cache-create; не суммировать дубли
  сообщений одного id. Неполный финальный usage → неизвестный итог, а не ноль.
- Доллары и сырые токены показываются раздельно. Из общего процента пула ничего
  плечам не приписывается. Подготовка пакета/стенда считается отдельно от выполненных плеч.

Число действий: **завершённые tool invocations**, не текстовое обещание действия,
не число шагов рассуждения и не платформенные ходы. Параллельный batch из N вызовов
считать N; отдельно сохранить число раундов, если runtime его отдаёт. Один shell,
открывающий четыре файла, остаётся одним вызовом, но четырьмя предметными чтениями.
Поэтому дополнительно считать фактически выданные модели тела файлов и их объём.

Основной кандидат лишней работы — чтение тела cafeteria.md, mobile-icon.md,
office-move.md, translation.md. Они не содержат зависимостей трёх обещаний плана;
короткий список имён для выбора документа сам по себе не лишняя работа. Перечитывание
уже полностью доставленного неизменённого тела отметить отдельно; дочитывание
обрезанного вывода не считать повтором. По недоказанному пути чтения ставить unknown.
Запрос разрешения на чтение/продолжение, уже разрешённое task.txt, — отдельный исход.
Завершённые вопросы владельцу в JSON — требуемый продукт, а не такое ожидание.

Признак полезного эффекта в этой выборке: при одинаково успешной приёмке у Astra
сократились фактические токены и лишние предметные чтения; число tool calls показано
без подмены чтениями. Для остальных проверенных моделей нет потери качества/границ, а любое
увеличение расхода или лишнего чтения показывается поимённо. Если исходная версия
сама выбрала релевантное чтение, сбой на этом случае НЕ воспроизведён. Разницу размеров
snapshot-файлов нельзя выдавать за измеренную экономию. Выигрыш только на Astra
не достаточен для применения общего изменения. Результат одной пары на модель
не доказывает отсутствие регрессий за пределами этого сценария.

Знак для добора и критерий полезности выше различаются намеренно: если токены
снизились без изменения лишних чтений, направление расхода наблюдалось, но механизм
«устранили лишнее чтение» не подтверждён. Если исходный вариант не читал посторонние
документы, исследуемый сбой в этом случае не воспроизведён при любом знаке токенов.
Поправка не меняет девять входов из manifest.json и не раскрывается моделям.
