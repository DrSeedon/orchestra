## Codex после рестарта

На VPS проверен painter-astra. На момент проверки он уже работал в новом треде после последовательных fresh model changes; были живой процесс Codex и свежие tool/tool_result. Его не останавливали, модель не переключали, задания для Windows из присланного лога не исполняли. Старого lock-файла уже не было, поэтому точного исторического владельца того треда ретроспективно не установили.

Обнаружены воспроизводимые дефекты восстановления, соответствующие симптому:

1. `publish_backend_fds` сохранял pipes сразу, а PID/start-time — только путь штатного handover. В БД painter-astra обнаружены `cli_pid=0`, `cli_started_at=0` при живом CLI. Теперь положительная идентичность процесса записывается до публикации pipe-пары.
2. Обновление принятого после рестарта backend не снимало копии pipes из systemd перед disconnect и проглатывало ошибку остановки. Теперь копии снимаются, а ошибка сохраняет старый backend и флаг stale; замена не запускается через неуспешный teardown.
3. Adopted Codex мог вернуть управление после закрытия транспорта до фактического освобождения writer. Теперь есть ограниченное ожидание снятия kernel flock (действующий CODEX_PROCESS_TIMEOUT_SECONDS=5); timeout виден, повторная попытка может завершиться после освобождения. Проверка не удаляет lock-файл и не сигналит найденный по нему произвольный процесс.

Проверки: запись идентичности до передачи FD, порядок снятия FD и teardown, сохранение отказа, реальный Linux flock и timeout/retry без запуска модели. Существующие тесты PID reuse, adoption, native steering и writer-conflict также прошли. Реальный рестарт VPS новым кодом не выполнялся: это остаётся проверкой после разрешённого владельцем применения.
