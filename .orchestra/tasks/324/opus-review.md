## 2. Есть ли путь, где у БОЕВОГО процесса `LISTEN_PID != os.getpid()`?

Это дорогая сторона (ложный отказ = у юзера тихо пропадает Telegram), поэтому проверял прогоном.

**2.1. Живой процесс — гард проходит.** Прочитал окружение боевого процесса, а не пересказ:

```
systemctl show orchestra.service -p MainPID   → MainPID=2577299
ps: 2577299  /opt/orchestra/runtimes/20260817-b0b72d65-py312-rag-v2/bin/python -m uvicorn app.main:app --fd 3
tr '\0' '\n' < /proc/2577299/environ | grep LISTEN_PID   → LISTEN_PID=2577299
```

Совпадает. Ни одна библиотека в venv боевого рантайма не мутирует `LISTEN_PID`
(`grep -rn LISTEN_PID .../site-packages/` → пусто), в `app/` тоже нет ни `environ.pop`, ни
`unsetenv` для этих ключей — то есть до `start_bridge` значение доживает.

**2.2. Наследование подтверждено на себе.** Мой собственный шелл воркера:
`LISTEN_PID=2577299 SYSTEMD_EXEC_PID=2577299 NOTIFY_SOCKET=/run/systemd/notify` при своём pid
2738393. Выбор признака по pid-идентичности, а не по НАЛИЧИЮ переменных, обоснован верно.

**2.3. Прецедент в проде.** `app/fdstore.py:92-94` уже применяет ровно ту же проверку
(`listen_pid != str(os.getpid()) → {}`), и на живом сервисе она проходит: `LISTEN_FDNAMES`
содержит 59 дескрипторов, то есть усыновление реально работает. Признак не выдуманный.

**2.4. `POST /api/restart` — ложного отказа НЕТ.** `app/routes/system.py:2113` заканчивается
`os.kill(os.getpid(), signal.SIGINT)`; процесс умирает, `Restart=always` поднимает новый, systemd
назначает `LISTEN_PID` заново. Само-`exec` в приложении отсутствует: единственный `os.execv`
(`app/pidfd_exec.py:142-143`) — это хелпер запуска ДЕТЕЙ, не респавн себя.

**2.5. Найденная реальная развилка: форма `ExecStart`.** Живой юнит проходит гард не потому, что
так написан трекнутый юнит, а потому что его перекрывает drop-in
`/etc/systemd/system/orchestra.service.d/60-runtime-isolation.conf` (`ExecStart=` + прямой путь к
`python`). Базовый `ExecStart` (и в `/etc/systemd/system/orchestra.service`, и в трекнутом
`deploy/orchestra.service:38`) — `uv run uvicorn app.main:app --fd 3`, а `uv run` НЕ делает exec,
он порождает ребёнка. Измерено (эмуляция контракта systemd: `LISTEN_PID` = pid exec'нутого
процесса):

```
$ LISTEN_PID=$$ exec uv run --no-project python -c "..."
exec_d_pid(LISTEN_PID)= 2739196  app_pid= 2739202  MATCH= False   ← гард ОТКАЗАЛ БЫ
$ LISTEN_PID=$$ exec /opt/orchestra/runtimes/.../bin/python -c "..."
exec_d_pid(LISTEN_PID)= 2739205  app_pid= 2739205  MATCH= True    ← текущая живая форма
```

Подтверждение из живой системы, что это не теория: `ps` показывает `uv run uvicorn
backend.server:app` (pid 767) с ребёнком-python pid 1174 — разные pid у соседнего сервиса.

Отсюда находка H1 ниже. На СЕГОДНЯШНЕЙ живой конфигурации отказа нет.

**2.6. Запуск без сокета** (`--host/--port` вместо `--fd 3`): `LISTEN_PID` не задан → гард
отказывает. Для dev-запуска это и есть замысел. Но `deploy/install.sh:86` ставит
`deploy/orchestra.service.template`, у которого `ExecStart=... uvicorn app.main:app --host
127.0.0.1 --port 8888` (строка 15) и никакой socket-активации, — а `install.sh:128` при этом
предлагает добавить `TG_BRIDGE_TOKEN` в `.env`. См. H1.

## Находки

### H1 (высокий приоритет, править в этом же коммите; не blocking для рантайма)
**Утверждение отчёта «No unit change required… `ExecStart=… uvicorn app.main:app --fd 3` уже
удовлетворяет гард» неверно для того юнита, который лежит в репозитории.** Гард удовлетворяется
untracked drop-in'ом `60-runtime-isolation.conf` (артефакт #303), а не строкой юнита; докстринг
`app/tg_bridge.py:3744-3745` цитирует ту же строку `uvicorn app.main:app --fd 3` как основание.

Сценарий отказа, конкретно:
1. Оператор ставит `deploy/orchestra.service` (его собственная шапка предписывает установку
   вручную) БЕЗ drop-in'а #303 → `ExecStart=uv run uvicorn … --fd 3`.
2. systemd назначает `LISTEN_PID` = pid `uv`; приложение живёт в ребёнке с другим pid
   (измерено: `MATCH= False`).
3. HTTP работает (fd 3 наследуется), а мост отказывает. Наружу — одна строка
   `TG bridge FAILED to start` в журнале. Юзер узнаёт по тишине в Telegram.

Тот же класс: `deploy/orchestra.service.template:15` (`--host/--port`, socket-активации нет
вовсе) — то, что реально ставит `deploy/install.sh:86`, при том что `install.sh:128` советует
завести `TG_BRIDGE_TOKEN`. На такой инсталляции мост не поднимется НИКОГДА.

Минимальное лечение (выбор за автором/оркестратором): привести `ExecStart` в
`deploy/orchestra.service` к прямой форме (путь к интерпретатору, без `uv run`), в докстринге
гарда назвать источником истины именно прямой exec и drop-in, а в `deploy/install.sh` либо
убрать совет про TG-токен, либо снабдить шаблон socket-активацией. Проверять не глазами:
`LISTEN_PID=$$ exec <ExecStart> python -c 'сравни pid'`.

Я НЕ проверял, поднят ли TG-мост на клиентском VPS: доступа к тому хосту у меня нет. Если он там
с токеном — это blocking для него, а не suggestion.

### S2 (suggestion) — `__main__` осиротел вашей же правкой
`app/tg_bridge.py:3937-3951` (`python -m app.tg_bridge <token> <group>`) теперь не может
завершиться успехом ни при каком запуске: он всегда идёт через `start_bridge`, и pid-идентичность
у ручного запуска не совпадёт никогда. Автор назвал это осознанным. По правилу проекта
(«удалять только то, что осиротили твои же правки», «никаких обёрток на всякий случай») блок стал
мёртвым по построению — его лучше снести, чем оставить дверь, которая гарантированно отдаёт
traceback. Держать его как «документацию отказа» — это второй способ сделать одно и то же.

### S3 (suggestion) — отказ громкий в журнале, но у юзера канал — Telegram
Правка меняет режим отказа с «второй поллер» на «ноль поллеров, если конфигурация уехала».
Второй режим наблюдаем только в журнале, а журнал — не канал юзера (он работает через Telegram).
Дешёвый положительный признак: на инстансе, прошедшем гард, если токен задан, а `TG bridge: ready`
не наступил за N секунд — записать это туда, где юзер увидит без Telegram (баннер дашборда /
инбокс баг-репортов). Отдельной задачей; в этом коммите не требую.

### N1 (nit, не требует действий)
Предикат «я — тот процесс, которого exec'нул systemd» теперь живёт в двух местах:
`app/fdstore.py:92-94` и `app/tg_bridge.py:3751-3757`. По правилу «одна мысль = один owner» это
кандидат на общий хелпер; по правилу «три одинаковые строки лучше преждевременной абстракции» —
терпимо. Оставляю на усмотрение: важно лишь, что при смене признака менять придётся ОБА.
