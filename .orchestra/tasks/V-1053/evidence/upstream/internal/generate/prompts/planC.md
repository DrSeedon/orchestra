## 進め方（2 つの段階を 1 回の返答の中で行う）
ツアーを書く前に、まずシニアとしての下調べをする。

### 段階 1: 下調べ
1. `lessons/README.md` と `lessons/reading.md` を読む。
2. `commits.txt` と `change.diff` をざっと見て、何のための変更か、誰が何に困らなくなるかを 1〜2 文で書く（最初の仮説）。
3. `base/` を読み、**変更前のコードが守っている約束**を書き出す。変更で触られるファイルだけでなく、それと関わる変更していないファイル（呼び出し元、バッチ、設定、接続や初期化の処理、テスト、ドキュメント、データの定義）も読む。
   - 状態や値が何を**意味する**か / 不変条件 / 失敗したときの扱いとその理由 / 既存のテストが守っている振る舞い
   - 書かれている慣習（コメント、README、同じ種類の既存のファイルに書かれた決まりと理由）
   - 接続や設定で決まる振る舞い（何かを有効・無効にしている設定や初期化）
   - その約束を、アプリのコードの手順で守っているのか、型やデータベースの制約で守っているのか
4. 次に `change.diff` と `head/` を読み、変更を 3 の約束と 1 つずつ突き合わせる。
5. 8 つの分野を 1 つずつ当てる。`lessons/1-promises.md` から `lessons/8-ai.md` までの 8 つのファイルを、兆しがなさそうな分野も含めて全部開く（索引の抜粋だけでは兆しを見落とす）。各ファイルで、項目の「兆し」を差分と照らす。兆しが見えた項目は、その「問い」を具体的な値で追い、「十分な場合」に当たるかを確かめる。分野ごとに「兆しあり（項目の番号）」「兆しなし」「十分な場合に当たる（確かめた場所）」のどれかと、その根拠を 1 行で書く。
6. `lessons/judgment.md` を読み、見つけたことを、重さ（必須 / 提案 / Nit / 問い）を付けて全部書き出す。一番大きな問題が見つかったあとも、ほかの分野を当て続ける。修正案を考えたら、その案で本当に防げるかを、別の失敗との組み合わせや入れ替え中の状態まで、具体的な値で確かめる。
7. その中から、手順を厚く使う数個を選び、選んだ理由を書く。読者が気にしそうだが気にしなくてよいもの（確かめた場所とともに）と、良くできているところ、選ばなかった設計との比較も書く。
8. それぞれに、根拠となるファイルと行番号（base か head か）を添える。確かめたことと推測を分ける。

### 段階 2: ツアー
`lessons/teaching.md` を読んでから、下調べの結果を核にして、ツアーの JSON を書く。7 で選んだものに手順を厚く使い、6 のほかの項目も落とさず短く挙げる。最初の仮説がどう確かめられ、どう直ったかが、ツアーの流れになるようにする。
