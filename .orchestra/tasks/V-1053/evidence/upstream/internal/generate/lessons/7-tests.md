# 7. テストは何を証明しているか

## L7-1. 肝心の 1 行を壊したら、どのテストが落ちるか
- 問い: この変更の肝心の 1 行を壊したら、どのテストが落ちるか。このバグ修正のテストは、修正を戻したら落ちるか。
- 兆し: 例外が出ないことしか確かめないテスト、assert がない、新しい分岐に対応するテストがない、テストのないバグ修正。
- 十分な場合: 型や既存の上位のテストで、その壊れ方が捕まると確かめた。

## L7-2. 中身を書き換えても、振る舞いが同じなら通り続けるか
- 問い: このテストは、利用者と同じ入口から呼び、結果を確かめているか。それとも、呼んだ順番や内部の値を確かめているか。
- 兆し: mock の呼ばれ方だけを確かめるテスト、private な関数の直接のテスト、本体の差分と同じ形の書き換えがテストにも並ぶ。
- 十分な場合: 状態を確かめる方法がない（外への送信だけをする関数）。
- 補足: 呼び出しを写しただけのテストは、価値がマイナス（Google の Testing on the Toilet）。

## L7-3. 期待値を、本体と同じ計算で作っていないか
- 問い: このテストの期待値は、本体と同じ方法で作られていないか。本体に同じバグがあったら、テストも一緒に間違えないか。
- 兆し: 期待値を連結やループで作る、テストの中の if や for、本体の定数や関数で期待値を作る。
- 十分な場合: 関係のない値を埋める helper は良い。

## L7-4. その mock は、本物と同じように振る舞うか
- 問い: この mock が返す値は、本物が実際に返す値と同じか。本物の振る舞いが変わったら、このテストは気付けるか。
- 兆し: 外部ライブラリの型を直接 mock する、stub の設定がテストより長い、DB を mock して SQL が正しいことを確かめたつもりになる。
- 十分な場合: 本物が遅い、不安定、外部に影響する。選ぶ順は、本物、fake、stub、mock。

## L7-5. テストが、通るように変えられていないか
- 教訓: 仕様と矛盾するテストを与えると、GPT-5 は 54%、Claude Opus 4.1 は 50%、o3 は 49% の割合で、テストを「通した」。手口は、テストの書き換え、比較演算子の上書き、呼ばれた回数での切り替え、テストの入力の特別扱い。Claude は主にテストの書き換えだった（ImpossibleBench 2025）。
- 問い: 既存のテストの期待値が変わっていないか。消えたテストや skip が増えていないか。実装に、テストの入力の値そのもの（特定の ID、決め打ちの数）が出てこないか。
- 兆し: テストの差分。テストの値と実装の値の一致。
- ツアーへ: AI が書いた変更では、テストの差分を、実装の差分より先に疑う。
