# 判断

見つけたことを、どこまで気にするかを決める。直すべきか、細かい好みか、これで十分か。教訓同士がぶつかったら、どちらを取るか。
シニアらしさは、教訓を知っていることより、この判断にある。

## J1. 完璧かではなく、良くなったかで決める
- 完璧でなくても、システム全体のコードの健全さを確かに良くしているなら通す。悪くしているなら、小さくても止める。完璧なコードはなく、より良いコードがあるだけ（Google のレビューの基準）。
- ツアーへ: まとめでは、指摘の羅列で終わらせず、「全体として良くなったか」を先に言う。

## J2. 指摘には重さがある
- 必須（止めるべき）、提案（任意）、Nit（細かい好み）、問い（確信がないので聞く）、良い点を分ける。理由を添え、人ではなくコードに向ける（Google のガイド、Conventional Comments）。
- 重さの目安:
  - 必須: お金、データ、権限、戻せない変更、利用者の操作だけで起きる誤り。**このリポジトリの中の事実だけで**、壊れる具体的な入力を示せる。
  - 提案: 壊れはしないが、次の変更や運用を苦しくする。
  - Nit: 好み。このリポジトリの規約に書かれていないもの。
  - 問い: 外部の仕様や本番のデータしだいで正否が変わり、渡されたファイルからは決められないもの。影響が大きくても、決められないなら必須にしない。影響の大きさは問いの中で言い、マージの前に誰が何を確かめればよいかを書く。
- 見つけたことは、重さを付けて全部挙げる。手順を厚く使うのは、一番効く数個にする。残りは落とさず短く挙げる。

## J3. 事実と規約は、好みに勝つ
- 自分の好みを欠陥として言わない。根拠が「このリポジトリの規約」「壊れる具体的な入力」にあるものと、好みを分ける。
- ツアーへ: 好みは `opinion` として出し、欠陥として扱わない。

## J4. 良いところを言う
- 良くできているところを、なぜ良いかとともに言う。
- ツアーへ: 問題が見つからない変更でも、ツアーは成り立つ。問題を作り出さない。良い設計の理由を見せることも、シニアの読み方の手本である。

## J5. 防御や汎用化は、起きうる問題に見合っているか
- 100% の信頼性を目指すのは、ほぼ常に間違い。必要な水準を超えた防御は、他に使える資源を食う（Google SRE）。影響の小さい処理に、何重もの再試行やフォールバックは要らない。やりすぎも指摘の対象になる。

## J6. 意図して借りる負債は、妥当な取引になりうる
- 期限のために、分かったうえで借りる近道は、正しい判断でありうる。ほとんど変更されないコードなら、返さなくてよいこともある。返すなら、いつ、どの条件でかを残す。

## J7. まず単純に動かしてから育てる
- うまく動く複雑なシステムは、うまく動く単純なシステムから育ったもの（Gall の法則）。新しい技術を足すたびに、運用の手間がずっと続く。

## J8. なぜをコードに残させる
- 書いた人の口頭の説明で納得せず、その理由をコメントか、もっと単純なコードとして残させる。コードは将来の開発者の先生になる。

## J9. レビューの価値の多くは、理解と知識の共有にある
- レビューは欠陥探しだけでなく、変更を理解し、その理解をチームに広げる場（Bacchelli & Bird 2013）。
- ツアーへ: ツアーは「欠陥がない」で終わらず、「この変更を読んで、このコードベースの何を学んだか」を残す。

## J10. 十分だと言うなら、その根拠を示す
- 「気にしなくてよい」「今の規模なら問題ない」「ここは安全」は、それ自体が判断であり、根拠が要る。
- 根拠は、このリポジトリの中で確かめた場所（上限の検査、制約、設定、呼び出し元の全部、テスト）で示す。一般論（「普通は小さい」「たぶん使われない」）だけで十分と言わない。
- 示せないなら、十分とも問題とも言わず、何を確かめれば決まるかを問いとして出す。

## J11. 修正案は、本当に防げるかを確かめてから出す
- 直し方を示すなら、その案で問題が本当に防げるかを、具体的な値で追って確かめる。
- 別の失敗との組み合わせ（ある失敗が、あとの別の失敗に隠れる、など）や、入れ替え中の状態（古いコードと新しいコードが同時に動く、すでに書かれた古いデータ）でも防げるかを見る。
- 防げない場合が残るなら、そう書く。

## J12. 確かめられないことを重く言わない。確かめられることは確かめる
- 外部のサービスやライブラリの仕様しだいで正否が変わる点は、必須にせず、確かめるべき問いとして出す。fact にしない。
- ただし「外部しだい」と言う前に、こちらのコードで決まる部分を切り分ける。外部の振る舞いに見えても、実際にはこちらの catch や変換が複数の場合を 1 つの値にまとめている、既定値を決めている、境界を引いている、ということが多い。そこはコードを読めば決まるので、追って確かめ、fact として言う。本題はたいてい、外部の仕様ではなく、こちらのコードがそれをどう扱うかにある。
- 外部の仕様しだいの部分が残るなら、どこまでがこちらで決まり、どこからが外部しだいかの境目を示す。

## J14. 判定は、指摘の重さと合わせる
- 変更全体の判定（良くしたか）は、必須の指摘があるかで決める。問いや提案が残っていても、コードベースを良くしているなら「良くした。ただしマージの前にこれを確かめる」と言える。
- 良い変更を、外部しだいの懸念や好みで「悪くしている」と言わない。修正案が変更の利点を打ち消すなら、その案は採らない。
- 逆に、ありえない懸念を残さない。同時実行や規模の心配は、その処理が本当に並ぶか（同期の処理か、1 本のワーカーか）をコードで確かめてから出す。

## J13. 選ばなかった設計と比べる
- この変更の設計を、ありえた別の設計（制約で守る、データの持ち方を変える、責任を別の場所に置く）と比べ、何を得て何を払ったかを書く。比べることで、この設計の理由が読者に見える。

## ぶつかる教訓と、決め方
教訓は互いにぶつかる。ぶつかったら、どちらを取るかを、この変更の事情で決めて見せる。

| | ぶつかるもの | 決める軸 |
|---|---|---|
| T1 | 重複をなくす ⇔ 誤った共通化を避ける ⇔ テストは読みやすさ優先 | 重複しているのは知識か形か。変わる理由は同じか。共通化の後に呼び出し元の都合の分岐が増えていないか。実例はいくつか。テストか本番か |
| T2 | いま作らない ⇔ 変更に備えた設計 | 機能を作るのか、変えやすくするのか。決定を隠すことは機能を作らない。後で足す手間を想像する |
| T3 | 小さな関数 ⇔ 深いモジュール | 分けた片方を、もう片方を読まずに理解できるか。新しい関数のインターフェースは中身より単純か |
| T4 | 可用性のために通す ⇔ 安全のために止める | 誤って通したときの損害と、誤って止めたときの損害のどちらが大きいか。その選択がコードに明示されているか |
| T5 | リトライ ⇔ 過負荷 | 失敗の種類（一時的な失敗か、「減らしてくれ」の合図か）で分けているか。全体の予算があるか |
| T6 | 代わりの経路を避ける ⇔ 機能を縮退して動き続ける | 代わりの経路が他の共有資源に負荷を移すか、手元のもので済むか。普段から動いて試されているか |
| T7 | 未知を通す寛容さ ⇔ 定義外を拒む厳しさ | 内部の版の違いには「未知を保持して通す」。信頼の境界での検証には「定義外を拒む」 |
| T8 | 広い catch で止めるな ⇔ 想定外は落ちて再起動 | 落ちる範囲。1 件や 1 ワーカーに閉じるなら落ちてよい。全体が同時に落ちるなら障害の増幅 |
| T9 | 段階的に出す ⇔ 新旧が共存する危険 | 共存しても安全か、戻すことが安全かを、先に確かめたか |
| T10 | 詳しく残す ⇔ 計測のラベルに入れるな | 矛盾ではなく道具の違い。ログやトレースには残し、時系列のメトリクスのラベルには入れない |
| T11 | 自分のコードへの厳しさ ⇔ 他人の変更を止めない | 書くときは複雑さを許さない。レビューでは、悪くしているなら止め、良くしているなら通し、残りは Nit |
| T12 | 今すぐ整理する ⇔ 今は出す | 次に触る予定があり、整理で次の変更が小さくなるなら先に整理する |
| T13 | 割れ窓を直す ⇔ 差分を小さく ⇔ 周りに合わせる | 指摘はするが、この差分には混ぜない。悪い形を真似たなら、一貫性のためか、気付かなかったのかを問う |
| T14 | コメントを書く ⇔ コードで語る | 名前で表せることは名前で。理由、単位、境界、他との依存はコメントで |
| T15 | 本物を使う ⇔ 切り離して速く | 本物、fake、stub、mock の順。本物との一致はテストから見た約束で測る |
