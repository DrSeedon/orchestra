# 6. 次に変える人は楽か（設計）

## L6-1. この変更のあと、頭に入れておくことは増えたか、減ったか
- 教訓: 複雑さは行数ではなく、次に変える人が、どれだけ多くの場所を直し、どれだけ多くを頭に入れ、何を知らずに踏むかで測る。複雑さは小さな差分の積み重ねでできるので、「小さいから」は見逃す理由にならない（Ousterhout）。
- 問い: 動くことはわかった。この差分は、次の変更を楽にしたか、苦しくしたか。
- 兆し: 1 つの概念を足すのに多くのファイルに同じ形の変更が散る、「これを変えたらあれも変える」がどこにも書かれていない、「とりあえず」の分岐。
- 十分な場合: めったに触らない場所で、インターフェースが単純。

## L6-2. 深いか、浅い包み直しか
- 教訓: 良いモジュールは、小さいインターフェースの裏に多くを隠す。中身とほとんど変わらないインターフェースの関数やクラスは、覚えることを増やすだけ。引数をそのまま下に渡す層も同じ。
- 問い: この新しい関数やクラスを使う人は、中身を読む代わりに何を覚えればよいか。それは中身より本当に少ないか。この層を消したら、呼び出し側は何を失うか。
- 兆し: 1〜3 行を包むだけの関数やクラス、同じシグネチャで素通しする層、「init を呼んでから load」のような順番の制約。
- 十分な場合: 分けた片方を、もう片方を読まずに理解できる。名前が付くことで意図が読める。外部の型を包んで差し替え可能にする層。

## L6-3. 変わりそうな決定は、1 か所に隠れているか
- 問い: この決定（データの形式、外部 API の形、保存先、ID の付け方）が変わったら、何か所を直すか。
- 兆し: 外部 API の形や列の名前が、呼び出し側の何層も上まで出てくる。read → parse → save と手順で分かれ、同じ形式を両側が知っている。
- 十分な場合: 変わる見込みがない単純な決定。小さなスクリプト。

## L6-4. その共通化は、同じ知識をまとめたものか、形が似ているだけか
- 教訓: DRY は「同じ知識を 2 か所に書かない」ことで、見た目の重複の話ではない。逆に、形が似ているだけのコードをまとめると「誤った抽象」になり、重複よりずっと高くつく。共通の関数に、呼び出し元ごとの引数と分岐が増え始めたら、その兆し（Sandi Metz）。
- 問い: 片方の決まりが変わったら、必ずもう片方も変わるか。共通の関数に足された引数と分岐は、呼び出し元ごとの事情を持ち込んでいないか。この共通化は、いくつの実例を見て作られたか。
- 兆し: 共通の関数への真偽値の引数や mode の追加、`if (type === "x")`。同じ定数や検証の規則が、フロントとバックエンド、コードとマイグレーションに別々にある。呼び出し元が 1〜2 個の新しい共通の helper。
- 十分な場合: 分岐が呼び出し元の都合ではなく、扱うデータの性質による場合分け（通貨ごとの丸め）。

## L6-5. いま要らないものを作っていないか（YAGNI）。ただし、変えやすさのための作業は別
- 教訓: 予想した必要のための機能（拡張点、設定項目、使われない引数）は、作る、遅れる、抱え続ける、作り直す、の 4 つの費用がかかる。ただし YAGNI は、変えやすくするための整理やテストには当てはまらない（Fowler）。
- 問い: この引数、設定、拡張点、interface を、今の呼び出し元のどれが使っているか。後で足すとしたら、今と比べてどれだけ高くつくか。
- 兆し: 実装が 1 つしかない interface、誰も渡していない省略可能な引数、「将来のために」というコメント、plugin の仕組み。
- 十分な場合: 後で足すのが極端に高くつくもの（公開 API の形、保存形式）は先に考える。

## L6-6. この機能をやめるとき、きれいに消せるか
- 問い: この機能をやめることになったら、どこを消せば済むか。消すとき、他の機能のコードを直す必要があるか。このコードはどれだけ長く使われそうか。
- 兆し: 新機能のための分岐が既存の共通関数の中に入り込んでいる。新機能が既存のモジュールの内部の状態に直接触れる。
- 十分な場合: 長く残ると分かっている中心の部分。
- 補足: コードが長く使われるほど、「巧妙」は褒め言葉ではなく非難になる（Software Engineering at Google）。

## L6-7. 整理と振る舞いの変更が、混ざっていないか
- 問い: この差分のうち、振る舞いが変わる行はどれか。それ以外は本当に振る舞いを変えていないか。「リファクタリング」なのに、テストの期待値が変わっていないか。
- 兆し: 名前の変更や移動の中に、条件の変更が 1 行だけ紛れている。refactor と名乗るコミットでの assert の変更。
- 十分な場合: 小さく、読む人が両方を一度に追える。
- 補足: リファクタリングでテストが変わったら、振る舞いが変わったか、テストの層が間違っているかのどちらか（Software Engineering at Google）。

## L6-8. 名前とコメントは、コードから読み取れないことを伝えているか
- 問い: この名前を見て、中身を読まずに正しく推測できるか。同じ名前が別の意味で使われていないか。一番分かりにくいこと（なぜこの値か、なぜこの順番か、ほかにどこを直す必要があるか）は書いてあるか。逆に、コメントがコードを言い換えているだけではないか。
- 兆し: data、result、handle のような名前、単位のない数値、名前と中身のずれ（`get` なのに書き込む）、理由のない sleep や決め打ちの数字、AI のコードに多い「〜に修正」という経緯のコメント。
- 十分な場合: 範囲の狭い一時変数。名前で表せることは名前で表している。

## L6-9. 周りの書き方に揃っているか
- 問い: 同じ種類の既存のコード（ハンドラ、テスト、設定、エラーの扱い）はどう書かれているか。この差分だけ違うなら、意図的か。既にある helper を使わず、同じものを新しく書いていないか。
- 兆し: 既存と違うエラーの返し方やログの出し方、似た名前の既存の関数。
- 十分な場合: 既存の書き方が明らかに悪く、新しい書き方の理由を書き、揃える変更は別に提案している。好みの違いは Nit に留める。

## L6-10. 割れた窓を真似て広げていないか
- 問い: この差分は、既存の悪い前例を真似て広げていないか。警告や失敗するテストを「いつものこと」として扱っていないか。
- 兆し: 既存の握りつぶしやグローバル状態のコピー、skip や flaky の印の追加、警告を消す設定。
- 十分な場合: 一貫性のために真似たと書き、直すのは別の変更として提案している。

## L6-11. 書き直しで、元のコードが扱っていた場合を落としていないか
- 問い: この書き換えで、元のコードが扱っていた場合（境界、エラー、古いデータ）をすべて扱えているか。
- 兆し: ファイルや関数を丸ごと置き換える差分、「シンプルに書き直した」、元にあった分岐が新しいコードにない。
