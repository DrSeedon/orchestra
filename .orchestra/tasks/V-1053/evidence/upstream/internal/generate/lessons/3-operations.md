# 3. 出したあとどうなるか（運用と変更の安全）

## L3-1. 少しずつ出せるか、何で気付くか、どう戻すか
- 教訓: 障害の約 70% は変更から起きる（Google SRE）。Cloudflare の 2019 年の障害は、段階的な配布を通らない WAF のルールが数秒で世界に配られ、27 分間、トラフィックの約 80% が失われた。
- 問い: この変更は一部にだけ出せるか。出したあと、何を見れば効いた、壊れたとわかるか。戻すのに何が要るか。
- 兆し: 機能フラグなしの振る舞いの変更、全体に一度に効く設定、戻すときにデータの変換が要る変更。
- 十分な場合: 利用者がいない段階、内部ツール、すぐ戻せて被害が小さい。少なくとも戻し方がわかっている。

## L3-2. 設定の変更は、コードの変更と同じくらい危ない
- 問い: この設定値は、どこで、いつ、誰の手で変わるか。間違った値が入ったら、起動時に弾かれるか、本番で初めて気付くか。
- 兆し: 新しい設定キーや環境変数、既定値の変更、読み込みに失敗したら黙って既定値を使う、値の検査がない。
- 十分な場合: 読み込み時に型と範囲を検査し、不正なら起動を止める。
- 根拠: Dan Luu が公開の障害報告を探した範囲では、全面的な障害の約半分が設定の変更だった（個人の非公式な集計）。

## L3-3. 戻せる変更か、戻せない変更か
- 問い: この差分のうち、出したあとに戻せないものはどれか（データの削除や書き換え、公開した API の形、保存形式、外に送ったメールや課金）。
- 兆し: DROP、TRUNCATE、一括の UPDATE、外部への送信、公開 API の変更。
- 十分な場合: 内部の実装や、フラグの後ろの機能は戻せる。深く議論するより、出して確かめるほうが安い。
- 根拠: Bezos の 2015 年の株主への手紙の one-way door と two-way door。

## L3-4. 新しいデータを、古いコードは読めるか（配布の途中と、戻したあと）
- 問い: 配布の途中で、新しい版が書いたものを古い版が読んだら何が起きるか。今すぐ戻したら、すでに書かれた新しい形式のデータはどうなるか。
- 兆し: 直列化の形式、キャッシュの値、メッセージ、DB の JSON の形を変える。enum に値を足して書き始める。
- 十分な場合: 書かれたデータが短命で、戻しても自然に消える。
- 根拠: AWS は「新しい形式も読める版」を全台に配ってから「新しい形式で書く」を有効にする 2 段階を勧める。

## L3-5. 使う側を一度に変えられない変更は、広げて、移して、縮める
- 問い: この差分は「広げる、移す、縮める」のどこに当たるか。古い形を使う側は全部移ったか。縮める予定はあるか。
- 兆し: 列や API の改名や型の変更を 1 回で、読み手と書き手を同じ差分で同時に変える。
- 十分な場合: 使う側が同じリポジトリにあり、同時に配られ、新旧が同時に動かない。ローリング更新なら同時に動く。

## L3-6. 消したものの名前や番号を、別の意味で使い回さない
- 教訓: Knight Capital（2012）は、2003 年から使っていない機能のフラグを新機能に使い回した。8 台のうち 1 台に新しいコードを入れ忘れ、その 1 台で古い機能が動き、約 45 分で約 4.6 億ドルを失った（SEC の命令書）。
- 問い: この値、フラグ、列、enum に、昔は別の意味がなかったか。それを読む古いコードがどこかに残っていないか。
- 兆し: 既存のフラグや enum の値の意味を変える、protobuf でフィールドを消して reserved にしない、番号の付け替え。
- 十分な場合: 一度も外へ出していない定義。古い意味の値を読む場所がないことを確かめた。それでも新しい名前のほうが安い。

## L3-7. 本番の大きな表へのスキーマ変更は、ロックで読む
- 問い: この表は本番で何行あり、どれだけ書かれているか。この文はどのロックを、何秒取るか。既存の全行の検査や書き直しを、同じ文でしていないか。
- 兆し: 型の変更、NOT NULL や制約の追加、索引の作成（CONCURRENTLY なし）、マイグレーションの中の全件の UPDATE、lock_timeout がない。
- 十分な場合: 小さな表、まだ本番で使われていない新しい表。行数の見当をどこで確かめたかを見せる。

## L3-8. 本番でおかしくなったとき、後から調べられるか（観測）
- 問い: この新しい処理が本番でおかしくなったら、どの利用者の、どの入力で、どのバージョンで起きたかを、ログから絞り込めるか。新しい警報は、鳴ったとき人が何をすればよいかわかるか。遅延を平均で測っていないか。
- 兆し: 文脈のないログ、要求 ID を引き継がない非同期処理、新しい分岐に計測がない、原因（CPU など）に付けた警報、平均だけの計測、メトリクスのラベルに利用者 ID。
- 十分な場合: リポジトリの既存のログの作法に従っている。小さなプロジェクトでは、エラーに識別子を付けるだけでも大きく違う。

## L3-9. 誰も見ていない通知は、警報ではない
- 教訓: Knight Capital では、始業前に警告のメールが 97 通届いていたが、誰も見ていなかった。GitLab（2017）では、バックアップは空で、その失敗を知らせるメールは受信を拒否されていた。
- 問い: この失敗の知らせは、誰に、どこに届くか。届かなかったら誰が気付くか。消える、上書きされるデータは、どこから、何分で戻せるか。
- 兆し: 失敗時にメールを送るだけ、送信の失敗を無視、バッチやバックアップの成否を監視していない、データを消すスクリプト。
- 十分な場合: 既存のオンコールの仕組みにつながっている。再生成できる派生データ。

## L3-10. リトライやフォールバックが常に起きていても、気付けるか
- 問い: このリトライやフォールバックが毎回起きるようになっても、誰か気付くか。
- 兆し: 新しいリトライ、フォールバック、既定値への切り替えに、計測やログがない。

## L3-11. 使わなくなったものは消す。いつ誰が消すかを決める
- 問い: このフラグ、暫定の実装、二重書き込みのコードは、いつ、誰が消すか。フラグの両方の経路がテストされているか。古いほうはいつ消せるようになるか。
- 兆し: 期限や消す計画のない新しいフラグ、「deprecated」と書いただけ、コメントアウトされたコード、使われていない引数。

## L3-12. 運用の手作業や、ドキュメントの更新が要らないか
- 問い: この変更は、デプロイ後に手で流すコマンドや、手で直すデータを増やすか。README、設定の例、運用の手順は、この変更に追いついているか。
- 兆し: 新しい環境変数やコマンドがあるのに、ドキュメントが変わっていない。
- 根拠: Claude Code が出した PR で、人が加えた修正の 29% は、ドキュメントの不足だった（Watanabe ら 2025）。
