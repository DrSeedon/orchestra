# 8. AI が書いたコードで特に見ること

AI のコードの危うさは、L1〜L7 の特別な場合である。ここでは、AI だから起きやすく、根拠のあるものを挙げる。根拠の強さを〔強〕〔中〕〔弱〕で示す。

## L8-1. 形は典型的でも、中身が合っているとは限らない〔中〕
- AI のコードは、見慣れた形がそろっていて正しそうに見える。熟練者でも、見慣れた形には形どおりの意味を読み込む（R5）。形ではなく、具体的な値で追う（R6）。

## L8-2. 存在しない API やパッケージを使っていないか〔強〕
- 16 の LLM で 57.6 万件のコードを作らせると、存在しないパッケージ名が、商用のモデルで少なくとも 5.2%、オープンなモデルで 21.7% あった（Spracklen ら 2024）。
- 問い: 新しく増えた import や依存、初めて呼ぶ関数の定義は、どこにあるか。リポジトリの外のものは、版とドキュメントで確かめるべきだと言う（fact にしない）。

## L8-3. 動くコードに、安全の穴が紛れる〔強〕
- Copilot が書いた 1,689 のプログラムの約 40% に脆弱性があった（Pearce ら）。AI の助手を使った人は、使わない人より安全でないコードを書き、しかも安全だと信じた（Perry ら 2023）。
- 問い: 外からの入力が入る場所を 1 つは辿ったか（L4）。

## L8-4. 既にある helper を使わず、書き直していないか〔弱〜中〕
- コピーされた行の割合が増え、整理の行が減っているという報告がある（GitClear。相関のみ）。Claude Code の PR で、人が加えた修正の 27% は整理（重複を除く、分割する）だった（Watanabe ら 2025）。
- 問い: 新しく足した関数、定数、型と同じことをする既存のコードはないか（L6-9）。

## L8-5. 頼まれていないものと、足りないもの。防御は両方の向きを見る〔弱、根拠が割れている〕
- Anthropic の手引きは、Opus 4.5 と 4.6 に、要らない抽象、余分なファイル、起こりえない場合への防御を足す傾向があると書く。一方、独立の研究には、AI のコードは防御が足りず単純だという結果もある。向きはモデルと場面で変わると扱う。
- 問い: この try/catch、設定項目、interface は、何を守る、何のためのものか。守る相手（呼び出し元、入力の出どころ）は実在するか。逆に、境界での検証が足りていないか。

## L8-6. エラー処理が、回復できる失敗とできない失敗を区別しているか〔中〜弱〕
- Claude Code の PR で人が加えた修正の 48% はバグ修正で、その中に「回復できる状態とできない状態を区別しないエラー処理」があった。「AI はエラーを黙って握りつぶしがち」という一般の主張は、一次の研究で数として確かめられなかった〔未確認〕。
- 問い: 各 catch は、何を、どこへ伝えるか（L2-1）。

## L8-7. 頼まれた範囲を越えて、大きくなっていないか〔中〜弱〕
- AI エージェントの PR だけに現れる却下の理由に、「大きすぎる」「複雑さを増やす」があった。
- 問い: 頼まれた目的に関係しない変更はどれか。分けて出すべきものはどれか（L6-7）。

## L8-8. 説明を鵜呑みにしない（ツアー自身も含めて）〔強〕
- 熟練の開発者は、AI を使うと作業時間が 19% 増えたのに、20% 短くなったと見積もった（METR 2025）。生成 AI を使った初心者は、実際より上手くできたと思い込んだ（Prather ら 2024）。
- ツアーへ: 確かめたことと推測を basis で分け、読者が AI の説明を鵜呑みにしない手本にする。
