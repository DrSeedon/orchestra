# 2. 失敗したらどうなるか

## L2-1. エラーを受けたあと、システムはどの状態にいるか
- 教訓: 深刻な障害の多くは、エラー処理の誤りから起きる。致命的な障害の 92% が、ソフトウェアが知らせた致命的でないエラーの扱いの誤りから起き、25% はエラーを無視していただけだった（ログを出すだけも無視に数える）。35% は、空のハンドラ、広すぎる catch で全体を止める、TODO の残ったハンドラ、の 3 つの単純な型だった（Yuan ら OSDI 2014）。
- 問い: この catch や `if err != nil` のあと、呼び出し元は失敗を知るか。知らないまま次の処理が進んで困らないか。
- 兆し: 空の catch、ログだけ、`_ = f()`、err を受けて `return nil`、エラーを既定値に変える `?? []`、ハンドラ内の TODO。
- 十分な場合: 失敗しても結果が変わらない処理（計測の送信、キャッシュの温め）で、無視してよい理由がコメントにある。

## L2-2. その catch は、実際に何を受けるか
- 問い: この catch が受ける例外の集合の全部で、「止める」「全体を中断する」が正しいか。
- 兆し: `catch (Exception)`、`except:`、recover のあとの exit。
- 十分な場合: 落ちる範囲が 1 件の要求や 1 つのワーカーに閉じていて、監督する仕組みが戻す。
- 実例: HDFS で、特定の例外のための exit を上位の型で受けていたため、一時的な不調で全 datanode が落ちた。

## L2-3. めったに通らない失敗の経路は、試されていない
- 問い: この差分で増えた失敗の経路を、どのテストが通しているか。
- 兆し: 新しい失敗の分岐に対応するテストがない。mock が常に成功を返す。
- 十分な場合: 失敗の経路がエラーをそのまま上へ返すだけで、状態を変えない。
- 根拠: 障害の 77% は単体テストで再現できた（Yuan ら）。

## L2-4. 外への呼び出しは、いつか返ってこない
- 問い: 呼び出し先が 30 秒黙ったら、こちらの何が待たされ、何が使い尽くされるか。待つ時間の上限はどこで決まっているか。
- 兆し: タイムアウトを指定しない HTTP クライアントや DB の呼び出し、締め切りを引き継がない外部呼び出し、根拠のない丸い数字のタイムアウト。
- 十分な場合: 呼び出し元の締め切りが確実に伝わっている。待っても他の利用者を巻き込まないバッチ。

## L2-5. リトライは負荷を増やす。1 か所で、間隔を広げ、上限を付ける
- 教訓: 5 層がそれぞれ 3 回試すと、DB への負荷は 243 倍になる（AWS）。原因が過負荷なら、リトライは相手にとどめを刺す。
- 問い: この上や下の層にも、別のリトライはないか。相手が過負荷のとき、このリトライは助けるか、とどめを刺すか。
- 兆し: 固定間隔のループ、上限なし、jitter なし、SDK の既定のリトライの上に自前のリトライ、429 と 503 を他のエラーと同じに扱う。
- 十分な場合: 利用者も相手も 1 つ（ローカルの CLI）。SDK の実装を使い、その設定を確かめた。

## L2-6. 2 回届いても壊れないか（冪等性）
- 教訓: 「処理は成功したが、返事の前に接続が切れた」がありうる。リトライやキューの再配信で、同じ操作は 2 回届く。
- 問い: この操作が 2 回届いたら何が起きるか。2 回目は、1 回目が成功したかを知る手段があるか。
- 兆し: 課金、送金、メール、在庫の減算、外部への POST にリトライを足す。冪等キーのない作成の API。キューやイベントの新しい受け手。
- 十分な場合: 操作がもともと冪等（同じ値での上書き、削除）。`x = x + 1` や「作成」は冪等ではない。

## L2-7. 片方だけ成功する（DB の書き込みと外への送信）
- 問い: コミットのあと、送信の前に落ちたらどうなるか。送信のあと、コミットの前に落ちたら、存在しないデータの通知が飛ぶか。
- 兆し: トランザクションの中での送信や HTTP 呼び出し、コミット直後の送信。
- 十分な場合: 失われても次の定期処理で埋まる程度の重要度。お金、在庫、権限には必要。

## L2-8. 同時に 2 回、途中で落ちる、新旧が同時に動く
- 問い: 同時に 2 回呼ばれたら、同じ入力で 2 回呼ばれたら、途中で落ちたら、入れ替えの途中で古いコードと新しいコードが同時に動いたら、何が起きるか。
- 兆し: 状態の更新、ジョブ、マイグレーション、複数の手順にまたがる処理。
- 十分な場合: 直列化されている場所、巻き戻される範囲を見せられる。
- ツアーへ: ジュニアが自分からは立てない問いなので、問いの手順に向く（P2）。

## L2-9. 代わりの手段（フォールバック）は、本番で初めて動く
- 教訓: 失敗のときだけ動く代わりの経路は試されておらず、しかも負荷を他へ移しうる。Amazon.com で、キャッシュが落ちたとき全 Web サーバが DB を直接引き、DB が固まり、サイト全体が止まった（2001 年ごろ）。
- 問い: この代わりの経路は普段どれくらい動くか。本当に失敗したとき（全台同時、過負荷のさなか）、どこに負荷が行くか。
- 兆し: catch の中で別の DB や API に切り替える、キャッシュのミスや障害で元を直接引く。
- 十分な場合: 代わりの経路が手元のもので済む（固定の既定値、古いキャッシュ）。それは段階的な機能の縮退として良い。

## L2-10. 依存先が落ちたとき、どこまで巻き込まれるか
- 問い: この依存先が遅くなったら、何のプール（スレッド、接続）が埋まり、それを他の誰が使っているか。一部の機能を落として、残りを動かし続けられるか。要求が今の 3 倍来たら、何を最初に使い切り、どこで早く断るか。
- 兆し: 補助的な機能を主要な要求の同期経路に足す、共有の接続プール、上限のないキューや並列数。
- 十分な場合: 入口で同時数やレートを制限している。タイムアウトが短い。

## L2-11. 失敗したら閉じる側に倒す（fail closed）
- 問い: 認可、署名の検証、不正の判定の呼び出しが例外やタイムアウトになったら、要求は通るか、止まるか。
- 兆し: 検証の失敗時に `return true`、catch で `allowed = true`、外部の判定がタイムアウトしたら素通り。
- 十分な場合: 可用性を優先すると決めた機能で、通しても損害が限られ、その意図が書かれている（T4）。
