# シニアが学んできたこと（参考資料）

このディレクトリは、経験を積んだエンジニアが書き残してきた「コードの変更をどう読み、何を問い、どう判断するか」を、ツアーを書くための参考資料にまとめたもの。
本や研究、公開された障害の報告を読んで整理した。ツアーの「シニアなら」は、ここに書いてあることに基づかせる。

## 使い方
1. まずこのファイルを最後まで読む。下の索引の「兆し」を、差分に当てはめる。
2. 兆しが見えた分野のファイルを開き、その項目の「問い」を差分に当て、「十分な場合」に当たるかを確かめる。兆しが見えなかった分野も、索引の問いを一度は当てる。
3. 見つけたことの重さを決める前に `judgment.md` を読む。ツアーを書く前に `teaching.md` を読む。
4. ここに書いた教訓を、そのままツアーに貼らない。このコードで問題（または良さ）を見せ、最後に教訓の名前を添える。
5. ここにある数字や事故の例は、ツアーで出してよいが、basis は `opinion` にする。ここにない数字を作らない。

## 各項目の形
- **教訓**: シニアが学んできたこと
- **問い**: 差分を読みながら立てる問い
- **兆し**: 差分のどこにこれが見えたら、問いを立てるか
- **十分な場合**: 当てはめなくてよい場合。シニアらしさは、ここを見分けることにある。十分だと言うときは、このリポジトリのどこでそれを確かめたかを示す。示せないなら「十分」と言わず、問いとして出す

## 索引

### 読み方（`reading.md`）
| | 教訓 |
|---|---|
| R1 | 意図から読む。行を読む前に、何のための変更かを言葉にする |
| R2 | 中心から読む。表示の順に読まない |
| R3 | 処理が流れる順に飛ぶ |
| R4 | 差分の外を見に行く |
| R5 | 見慣れた形はまとめて読み、形からのずれで止まる |
| R6 | 具体的な値で追う |
| R7 | 本番で壊れたら、誰が何で気付くかを問う |
| R8 | 次の変更を想像する |
| R9 | 時間をリスクに比例させる |

### 問い（8 つの分野）
| | 教訓 | 兆し（抜粋） |
|---|---|---|
| **1. 約束を守っているか**（`1-promises.md`） | | |
| L1-1 | 変更前の約束を、変更も守っているか | 状態の追加や意味の変更、条件の変更、既存のテストの期待値の変更 |
| L1-2 | 約束していない振る舞いにも、誰かが頼っている | ORDER BY の削除や追加、エラーの文言、null と空の入れ替え、既定値 |
| L1-3 | 消されたものは、何を守っていたか | 消された条件、再試行、null の確認、ソート、ロック、テスト |
| L1-4 | 手順で守る約束を、型や制約で守れないか | 互いに関係する bool、状態と nullable の列、同じ確認が複数の層に |
| L1-5 | 確かめてから書く隙間に、別の要求が入らないか | `if !exists { insert }`、ロックなしの SELECT → UPDATE |
| L1-6 | 宣言しただけで効いていると思い込まない | 外部キー、トランザクション、タイムアウト、キャッシュ、ログの設定に頼る |
| L1-7 | たまたま動いているのか、保証されて動いているのか | map の反復順、sleep での待ち合わせ、文書にない振る舞い |
| L1-8 | 現実のデータは思い込みより複雑（時刻、お金、文字、名前） | タイムゾーンなしの時刻、日付の区切り、金額の float、`VARCHAR(n)` |
| **2. 失敗したらどうなるか**（`2-failure.md`） | | |
| L2-1 | エラーを受けたあと、システムはどの状態にいるか | 空の catch、ログだけ、エラーを既定値に変える、ハンドラ内の TODO |
| L2-2 | その catch は、実際に何を受けるか | `catch (Exception)`、`except:`、広い catch で全体を止める |
| L2-3 | めったに通らない失敗の経路は、試されていない | 新しい失敗の分岐にテストがない、mock が常に成功 |
| L2-4 | 外への呼び出しは、いつか返ってこない | タイムアウトのない HTTP や DB の呼び出し |
| L2-5 | リトライは負荷を増やす | 固定間隔、上限なし、jitter なし、二重のリトライ |
| L2-6 | 2 回届いても壊れないか（冪等性） | 課金、送信、在庫、外部への POST、キューの新しい受け手 |
| L2-7 | 片方だけ成功する（DB と外への送信） | トランザクションの中やコミット直後の送信 |
| L2-8 | 同時に 2 回、途中で落ちる、新旧が同時に動く | 状態の更新、ジョブ、マイグレーション、複数の手順の処理 |
| L2-9 | 代わりの経路は、本番で初めて動く | catch の中で別の DB や API に切り替える |
| L2-10 | 依存先が落ちたとき、どこまで巻き込まれるか | 補助的な機能を主要な経路に同期で足す、共有のプール |
| L2-11 | 失敗したら閉じる側に倒す | 検証や認可の失敗時に通す、判定のタイムアウトで素通り |
| **3. 出したあとどうなるか**（`3-operations.md`） | | |
| L3-1 | 少しずつ出せるか、何で気付くか、どう戻すか | フラグなしの振る舞いの変更、全体に一度に効く設定 |
| L3-2 | 設定の変更は、コードの変更と同じくらい危ない | 新しい設定キー、既定値の変更、読めなければ黙って既定値 |
| L3-3 | 戻せる変更か、戻せない変更か | DROP、一括の UPDATE、外部への送信、公開 API の変更 |
| L3-4 | 新しいデータを、古いコードは読めるか | 直列化の形式、キャッシュの値、enum に値を足して書き始める |
| L3-5 | 一度に変えられない変更は、広げて、移して、縮める | 列や API の改名を 1 回で、読み手と書き手を同時に変える |
| L3-6 | 消したものの名前や番号を、別の意味で使い回さない | 既存のフラグや enum の値の意味を変える |
| L3-7 | 本番の大きな表へのスキーマ変更は、ロックで読む | 型の変更、NOT NULL の追加、索引の作成、マイグレーション内の全件 UPDATE |
| L3-8 | 本番でおかしくなったとき、後から調べられるか | 文脈のないログ、新しい分岐に計測がない |
| L3-9 | 誰も見ていない通知は、警報ではない | 失敗時にメールを送るだけ、バッチの成否を監視しない |
| L3-10 | リトライや代わりの経路が常に起きていても、気付けるか | 新しいリトライやフォールバックにログや計測がない |
| L3-11 | 使わなくなったものは消す。いつ誰が消すかを決める | 消す計画のないフラグ、コメントアウト、使われない引数 |
| L3-12 | 運用の手作業や、ドキュメントの更新が要らないか | 新しい環境変数やコマンドがあるのに文書が変わっていない |
| **4. 信頼の境界**（`4-trust.md`） | | |
| L4-1 | その値はどこから来て、誰が書き換えられるか | 入力の検査がない新しいハンドラ、Webhook やキューの中身を信じる |
| L4-2 | 他人の ID を渡したら、他人のデータが返らないか | URL やボディの ID でそのまま取得、利用者で絞らないクエリ |
| L4-3 | 要求の中身を、そのままモデルに流し込まない | `update(req.body)`、`Object.assign(x, body)`、スプレッド |
| L4-4 | 利用者の値が、SQL やコマンドの構文になる経路 | 文字列の連結で作るクエリやコマンド、ORDER BY に利用者の値 |
| L4-5 | 利用者が指定した URL をサーバが取りに行く | 利用者の入力を fetch に渡す |
| L4-6 | 秘密や内部の情報を、ログや応答に出さない | 要求を丸ごとログ、`err.message` や stack を応答に |
| L4-7 | 利用者の入力に当てる正規表現 | 入れ子の量指定子、入力の長さの上限なし |
| L4-8 | 新しい依存は、自分たちと同じ権限で動く他人のコード | 新しいパッケージ、`^` や `latest` |
| L4-9 | 誰から届くか（公開の範囲） | listen するアドレス、CORS、認証の外にあるルート |
| **5. 規模が大きくなったら**（`5-scale.md`） | | |
| L5-1 | 測る前に、速くするための工夫を入れない | 根拠のないキャッシュ、並列化、読みにくい最適化 |
| L5-2 | データ量に比例して重くなる場所は見逃さない | ループの中のクエリ、LIMIT のない取得、全件を配列に |
| L5-3 | 並列に問い合わせると、まれな遅さがよくある遅さになる | 1 回の要求で待つ相手が増える |
| L5-4 | キャッシュが空になった瞬間、下は耐えられるか | 新しいキャッシュ、キーの形式の変更 |
| L5-5 | 要求の数ではなく、使う資源で考える | エクスポートや集計を、既存と同じ扱いで足す |
| **6. 次に変える人は楽か**（`6-design.md`） | | |
| L6-1 | 頭に入れておくことは増えたか、減ったか | 1 つの概念のために多くのファイルに同じ形の変更が散る |
| L6-2 | 深いか、浅い包み直しか | 数行を包むだけの関数やクラス、素通しの層 |
| L6-3 | 変わりそうな決定は、1 か所に隠れているか | 外部の形や列名が上の層まで出てくる |
| L6-4 | 共通化は、同じ知識か、形が似ているだけか | 共通の関数への bool の引数や mode、呼び出し元ごとの分岐 |
| L6-5 | いま要らないものを作っていないか | 実装が 1 つの interface、誰も渡さない引数、「将来のため」 |
| L6-6 | この機能をやめるとき、きれいに消せるか | 新機能の分岐が既存の共通関数に入り込む |
| L6-7 | 整理と振る舞いの変更が、混ざっていないか | 名前の変更や移動の中に条件の変更が 1 行 |
| L6-8 | 名前とコメントは、読み取れないことを伝えているか | data や result、単位のない数、名前と中身のずれ |
| L6-9 | 周りの書き方に揃っているか | 既存と違うエラーの返し方、似た名前の既存の関数 |
| L6-10 | 割れた窓を真似て広げていないか | 既存の握りつぶしのコピー、skip の追加 |
| L6-11 | 書き直しで、元が扱っていた場合を落としていないか | 丸ごとの置き換え、元にあった分岐がない |
| **7. テストは何を証明しているか**（`7-tests.md`） | | |
| L7-1 | 肝心の 1 行を壊したら、どのテストが落ちるか | 例外が出ないことだけを確かめる、新しい分岐にテストがない |
| L7-2 | 中身を書き換えても、振る舞いが同じなら通り続けるか | mock の呼ばれ方だけを確かめる |
| L7-3 | 期待値を、本体と同じ計算で作っていないか | 期待値をループや本体の関数で作る |
| L7-4 | その mock は、本物と同じように振る舞うか | 外部の型を直接 mock、DB を mock して SQL を確かめたつもり |
| L7-5 | テストが、通るように変えられていないか | 既存のテストの期待値の変更、skip、テストの値が実装に出てくる |
| **8. AI が書いたコードで特に見ること**（`8-ai.md`） | | |
| L8-1 | 形は典型的でも、中身が合っているとは限らない | 見慣れた形がそろっていて、正しそうに見える |
| L8-2 | 存在しない API やパッケージ | 新しい import、初めて呼ぶ関数 |
| L8-3 | 動くコードに、安全の穴が紛れる | 外からの入力が入る場所 |
| L8-4 | 既にある helper を使わず、書き直していないか | 新しい関数や定数 |
| L8-5 | 頼まれていないものと、足りないもの | 守る相手のいない try や設定、境界での検証の不足 |
| L8-6 | 回復できる失敗とできない失敗を区別しているか | すべての失敗を同じに扱う catch |
| L8-7 | 頼まれた範囲を越えていないか | 目的に関係しない変更 |
| L8-8 | 説明を鵜呑みにしない | コメントやコミットメッセージの主張 |

### 判断（`judgment.md`）
J1 完璧かではなく良くなったか / J2 指摘には重さがある / J3 事実と規約は好みに勝つ / J4 良いところを言う / J5 防御は問題に見合っているか / J6 意図して借りる負債 / J7 単純に動かしてから育てる / J8 なぜをコードに残させる / J9 レビューの価値は理解と共有にある / J10 十分だと言う根拠を示す / J11 修正案は本当に防げるか確かめる / J12 確かめられないことを重く言わず、確かめられることは確かめる / J13 選ばなかった設計と比べる / J14 判定は指摘の重さと合わせる。ぶつかる教訓（T1〜T15）と決め方。

### ジュニアに届ける形（`teaching.md`）
P1 全体を 1 文で言う / P2 予測させてから確かめさせる / P3 飛ぶ理由を言う / P4 時間の配分を見せる / P5 分からなさの種類で見せ方を変える / P6 名前を信じすぎないことを見せる / P7 原則の名前は問題を見せたあとに出す / P8 問いの答えを先に漏らさない
