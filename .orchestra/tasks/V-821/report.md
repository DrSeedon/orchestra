## Где хранится настройка и почему
В манифесте пайплайна, `defaults.worktree.sparse` (рядом с уже существующими `copies`/`symlinks`), общее правило и `projects:` — переопределения по glob корня репозитория (`"*/katya-work"`, `"*/orchestra"`). Обоснование: (1) манифест уже читается при каждом спавне и перечитывается по mtime, поэтому смена правила не требует рестарта; (2) политику ведёт Orchestra, и править репозитории katya-work и seedon ради настройки не нужно (это чужие проекты); (3) в `app/` нет констант: пустая модель = правило выключено. Отключение: `enabled: false` в общем правиле или в записи проекта. Альтернативу «файл в самом репозитории» отверг: он требует влить файл в чужой main и привязывает правило к версии репозитория в момент спавна. Если владельцам проектов позже понадобится управлять правилом самим, это добавляется отдельным слоем.

Правило по умолчанию: `exclude: [artifacts, .orchestra/tasks]`; `own`: `.orchestra/tasks/{id}`, `artifacts/{id}`, `artifacts/task-{id}`, `artifacts/{id}-*`, `artifacts/task-{id}-*` (`{id}` — номер задачи вида `V-821`); `resources/` и всё остальное остаются в копии. Переопределения: katya-work `include: [artifacts/task-2/tooling]`; orchestra `reference_scan: [.orchestra/kb, tests, scripts]` — каталоги, на которые ссылаются KB и тесты (`.orchestra/tasks/224`, `../tasks/V-2/report.md`, `".orchestra" / "tasks" / "224"`), находятся `git grep` на базовом коммите при спавне и включаются автоматически; новая фикстура в чужом каталоге задач попадает в копию без правки списка. Правило копии сохраняется в её файле шаблонов (строка `# rule=`), поэтому смена задачи пересчитывает по тому же правилу.

## Чтение прошлых задач из основной копии (уточнение владельца)
Подсказка (`git-workflow.md`, раздел «Partial worktree») велит читать отсутствующее из основной копии проекта, а `sparse-checkout add` оставляет исключением — только когда воркер собирается изменить файл вне копии. Путь воркер получает сам: корень основной копии — родитель каталога `git rev-parse --git-common-dir`, выполненного в его worktree. Выбрано вместо подстановки пути в системный промпт: git сам выдаёт путь именно этого репозитория, перепутать проект нельзя даже при спавне в чужой `repo_path`, а восстановление промпта (`assemble_prompt`) не нужно менять. Запасной способ без пути — `git show main:<path>` и `git grep <шаблон> main -- <каталог>` из его worktree.

Запрета чтения основной копии у воркеров нет (по коду): Claude — `permission_mode="default"` с `can_use_tool`, разрешающим всё, кроме списка блокируемых инструментов (`app/backend_claude.py:173–180, 1092`); Codex — `"sandbox": "danger-full-access"` (`app/backend_codex.py:715`); Grok — `--always-approve`, изоляция касается только MCP (`app/backend_grok.py:41, 431`). Подтверждение на деле: эта же сессия (Claude-воркер) читала `/home/kesha/katya-work`, `/home/kesha/projects/seedon` и `/home/kesha/orchestra` из чужих worktree. **Исключение: бэкенд harness (OpenRouter)** — его файловые инструменты отвергают пути вне рабочей папки (`app/harness/tools.py`, `_resolve_in_workspace`), поэтому для него подсказка дублирует `git show main:<path>`; через shell-инструмент это работает, но саму harness-ветку на реальном воркере я не запускал.

## Тихая потеря закрыта механизмом
Проверено на коде: перед мержем `merge_worktree_to_main` вызывает `_clean_worktree_error(wt, "worker")` (`app/workspace.py`, перед записью `child_error`), а он запускает `git status --porcelain`. Правка отслеживаемого файла вне cone показывается там как ` M`, поэтому мерж и раньше останавливался статусом `WORKER_DIRTY` (маршрутизация по подстроке «worker working tree is dirty» в `app/merge_operations.py`), но совет был «commit or discard first» — воркер ходил бы по кругу, потому что `git add -A` возвращает 0 и ничего не стейджит. Теперь к тексту добавляется причина и команда: «N of them lie outside this worktree's sparse checkout … Run `git sparse-checkout add /artifacts/V-9/`, then git add and commit the files again». Какие пути «вне cone», решает сам git (`git add -n -- <путь>` отказывает с упоминанием sparse), поэтому правила не дублируются в коде. Новый файл вне cone ловится так же. Тест `test_change_outside_the_copy_blocks_merge_with_the_way_out` идёт через настоящий `merge_worktree_to_main`: отказ, затем выполнение совета и успешный мерж. Оставшаяся дыра: между правкой и мержем воркер может молча не заметить пустой коммит — но мерж дальше не пройдёт, потерянной правки в main нет.

## Существующие worktree: безопасный перевод
`convert_worktree_to_sparse(path, cfg, apply=False, allow_busy=False)` / `scripts/sparse_convert.py`. Отказывает и ничего не меняет, если: есть изменённые или неотслеживаемые файлы (любые, кроме игнорируемых), идёт merge/rebase/cherry-pick/revert, внутри работает процесс (`/proc/*/cwd`; обойти — `--allow-busy`), правило выключено для проекта, копия уже sparse. С `--apply` убирает с диска только закоммиченные отслеживаемые файлы вне правила; игнорируемые и неотслеживаемые остаются, каталоги с ними выводятся в `left_on_disk_mb` — это не освобождённое место. Откат: `git sparse-checkout disable` в той копии вернула 4404 МБ (проверено на копии katya-work в /tmp, статус чистый).

Пошаговый план после рестарта (выполняет оркестратор):
1. Влить ветку, рестарт. Проверить новый спавн: в новой копии `git sparse-checkout list` показывает строки правила, `du -sm` порядка десятков–сотен МБ.
2. Для каждого проекта получить список worktree: `git -C <repo> worktree list --porcelain`.
3. Пробный прогон: `uv run --frozen python scripts/sparse_convert.py <wt1> <wt2> …` — по каждой копии `would_convert` (с размерами исключаемых каталогов) или `refused` с причиной.
4. Сначала простаивающие копии с чистым деревом: `… --apply <wt>`. Проверить `status_clean: true` и `left_on_disk_mb`.
5. Копии с отказом «modified or untracked» не трогать: воркер сначала коммитит или убирает файлы; повторить позже. Занятые (`process(es) work inside`) — после остановки воркера или с `--allow-busy` по решению оркестратора (воркер продолжит работать, закоммиченное из исключённых каталогов читается из основной копии).
6. Место: `df` до и после; игнорируемые результаты (в katya-work, например, неотслеживаемые `artifacts/V-124/decks`) удаляются отдельной очисткой после мержа, перевод их не трогает.
7. Откат отдельной копии: `git sparse-checkout disable` в ней.
Для чужих проектов (katya-work, seedon) перевод запускает оркестратор по этому плану, я массово ничего не запускал.

Тихая потеря — отдельная проверка (`/tmp` клон orchestra, файл `.orchestra/tasks/108/plan.md`, отслеживаемый и вне cone, воркер перезаписал его):

Правка выглядит как изменение, но в коммит не попадает. Все 22/25/9 «тихих» случаев — это изменение (M) или удаление (D) уже отслеживаемого файла вне cone. Что после такого `git status` остаётся грязным — это видно воркеру и, по коду `merge_operations` (статус `DIRTY`), должно останавливать мерж; **это второе я по коду не проверял**.

Без свежего `git add -A` рабочей рукой воркер этого не заметит, если скрипт сам пишет в `artifacts/<чужая_задача>/` (katya) или в `resources/…` (seedon): путь существует после записи, `git status` показывает M, коммит пуст.

### 2.3 Слияние
`evidence/merge.py`: по 15 случайным коммитам на проект, отстающим от `main` ≥15 коммитов; ветка B воссоздана в sparse-клоне (дерево совпало с деревом C в 44 из 45 случаев), затем (1) `git merge main` в ветку, как делает воркер при конфликте, (2) `git merge --squash B` на `main`, как делает оркестратор; всё то же в полном клоне.

Результат: **45 из 45** — код возврата, список конфликтных файлов и итоговое дерево в sparse и в полном клоне совпали. Конфликтов было 8 (katya), 10 (seedon), 5 (orchestra) из 15; среди конфликтных путей были вне cone (seedon: 36 файлов в `.orchestra/tasks`, 16 в `resources`; katya: 12 в `artifacts`) — git подтягивает их в рабочую копию сам, результат тот же. ## 4. Что сломается, как догрузить, что менять

**Что сломается.**
1. Новый файл вне cone → `git add` отказывает громко (текст выше); воркеру нужно `git sparse-checkout add /путь/` и повторить.
2. Правка уже отслеживаемого файла вне cone → тихая потеря (раздел 2.2). Это главный риск.
3. Задачи-доработки (katya 29%, seedon 24% без resources, orchestra 6%): предыдущий результат отсутствует в копии. Воркер увидит «нет файла», если читает; скрипт, который пишет по старому пути, получит пункт 2.
4. Тесты orchestra, читающие фикстуры из чужих задач и проверяющие ссылки KB (раздел 2.4); новый тест со ссылкой на каталог задач сломается в sparse-копии, пока каталог не добавят в cone.
5. `extensions.worktreeConfig=true` пишется в общий конфиг репозитория при `git sparse-checkout init` в linked worktree. На временном клоне orchestra проверено: у основной копии `core.sparseCheckout` не появился, 323 каталога задач на месте, `git status` чистый, у worktree есть свой `config.worktree`. Риск: инструменты и git старше 2.20, не знающие этого расширения.
6. Перед `kill_worker` оркестратор katya переносит gitignored-файлы из `artifacts/` worktree (AGENTS.md katya, строки 376–377): файлы лежат на диске независимо от cone, поэтому должно работать, но не проверял.

**Как догружать.** `git sparse-checkout add /artifacts/V-137/` (мгновенно для медианы 11 МБ; для 462 МБ по скорости checkout katya ≈ 10 с — оценка, не замер). Подсказка воркеру одной строкой в системном промпте: «если `git add` пишет про sparse-checkout или `git status` показывает M, но коммит пуст — выполни `git sparse-checkout add <каталог>` и повтори».

**Что менять (предложение, не мандат).**
- `app/workspace.py:657–668` (`git worktree add`): `--no-checkout`, затем `sparse-checkout set --no-cone --stdin` с правилом проекта и своими каталогами по номеру задачи, затем checkout. Правило проекта (список исключаемых каталогов) нужно держать в конфиге проекта, не в коде: сейчас нужны три разных.
- `switch_worker_branch` (смена задачи в том же worktree): шаблоны «своей» задачи нужно заменить; **не проверялось**.
- Проверка перед мержем: пустой `git status --porcelain` уже есть по смыслу; добавить явное сообщение «правки вне sparse-cone не попали в коммит» — **не проверялось, по коду `merge_operations` статус DIRTY существует**.
- Промпт воркера: подсказка выше. Проектные AGENTS/CLAUDE: указать, какие каталоги в cone по умолчанию.
- Acceptance-команды задач (`acceptance_command`), которые читают чужие каталоги: не обследованы. Для orchestra сейчас известны только перечисленные выше фикстуры.
- Стоимость: оценка (не замер) — одна задача на `workspace.py` и тесты, порядка нескольких часов воркера Sonnet; основной риск — поведение `switch_worker_branch`, `kill_worker` и тихая потеря.
