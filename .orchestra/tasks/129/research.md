# #129 — на каком слое теряется точность больших чисел в аргументах tool-вызова

Дата: 06.08.2026. Источник: инбокс-репорт `20260806T074825.847165Z-f705f1b9a2e64495acb41bb1eeb19a03.md`
(проект seedon, воркер `direct-research`) + логи сессии `direct-research` из
`data/orchestra.db` (read-only копия через `file:...?mode=ro`, живая БД не трогалась).

## Ответ

**Мы не теряем точность нигде — ни в передаче, ни в логах.** Округление происходит в
**JavaScript-слое Claude Code CLI**, до того как значение попадает в Python. Наш Python-слой
физически не способен округлить целое: `json.loads` без `parse_int` даёт `int` произвольной
точности, а SQLite хранит `logs.content` как TEXT.

**Недетерминированности нет.** Разделяет вызовы не порядок, а форма аргумента, которую
сгенерировала модель: **6 из 6 вызовов с числом без кавычек отвергнуты, 2 из 2 со строкой в
кавычках прошли.** Это разделение полное, исключений в логах нет.

Дефект — на слое **генерации аргумента моделью** (кавычки), проявляется на слое **JSON.parse
в Node**. Оба вне нашего кода. Лечится описанием схемы у владельца MCP-тула; у себя мы можем
только сделать следующий такой случай различимым за одну команду.

### Поправка к репорту

В репорте сказано «ПЕРВЫЙ вызов с тем же значением прошёл успешно». По логам порядок обратный:
**отказ, отказ, успех**, потом ещё три отказа. Успех коррелирует не с порядком вызова, а с
кавычками. «Зависит не только от значения» — верно; зависит от формы, и полностью.

## 2. Кто именно округлил — отпечаток формата

Значение в нашей БД: `1917704623170653200`. Это **не** результат ни одной операции Python.

```
exact double value  : 1917704623170653184     ← int(Decimal(float(x))), точное значение double
python repr(double) : 1.9177046231706532e+18  ← json.dumps(float) напечатал бы это
shortest-repr expand: 1917704623170653200     ← кратчайшая десятичная запись того же double
в нашей БД          : 1917704623170653200
```

```
$ node -e 'console.log(JSON.stringify(JSON.parse("{\"ad_id\": 1917704623170653147}")))'
{"ad_id":1917704623170653200}

$ python -c 'import json; print(json.dumps(json.loads("{\"ad_id\": 1917704623170653147}")))'
{"ad_id": 1917704623170653147}
```

Разбор:
- Если бы округлял Python, в логе было бы `1.9177046231706532e+18` (`json.dumps` float'а) или
  `1917704623170653184` (`int(float(x))`). Ни того, ни другого нет.
- `...200` — это **кратчайшая round-trip запись** double, то есть формат `Number.prototype.toString`
  в JS. Node печатает ровно эту строку. Python такой текст не производит ни одним путём.
- Значит в Python пришёл уже текст `1917704623170653200`, и Python разобрал его в точный `int`.

Округление произошло в JS **до** нашего процесса. Наш слой донёс округлённое значение без искажений.

## 3. Карта слоёв: где JSON становится объектом и обратно

| # | Слой | Операция | Точность |
|---|---|---|---|
| 1 | Модель → текст аргумента (`input_json_delta`, внутри API) | генерация текста | кавычки ставит/не ставит модель — **источник дефекта** |
| 2 | Claude Code CLI (Node) | `JSON.parse` накопленного текста | **ПОТЕРЯ**: number → float64 |
| 3 | CLI → stdout stream-json | `JSON.stringify` | печатает `...200` (shortest repr) |
| 4 | `claude_agent_sdk/_internal/transport/subprocess_cli.py:105` | `json.loads(line)` | точно: `parse_int` не задан → `int` |
| 5 | `app/backend_claude.py:400` | `_json.dumps(block.input, ensure_ascii=False, indent=2)` | точно |
| 6 | `logs.content` (SQLite TEXT) | — | точно |
| 7 | Дашборд, generic-тул (`app/static/js/app.js:3933-3946`) | `JSON.parse(body)` | достаёт только строковые поля (`description`, `to`, `name`, `pattern`) и `percent`; сырое тело живёт в `dataset.toolContent` строкой и копируется как есть → **отображение потери не добавляет** |
| 8 | CLI → MCP-сервер (`yandex-direct`, node) | JSON-RPC, снова JS | number остаётся number → zod `-32602` |

Проверено грепом: `parse_float` / `parse_int` / `parse_constant` не задаются **нигде** в `app/`
(0 вхождений) — то есть везде дефолт, а дефолт Python как раз точный для целых. Опасен обратный
случай (float), но целые ID под него не попадают.

**Единственное место в нашем коде, где большое целое реально округлится при показе:**
`app/static/js/app.js:1086` — просмотр `.json`-файла делает
`JSON.stringify(JSON.parse(raw), null, 2)`. Открытый в дашборде JSON-файл с 19-значным ID
покажет округлённое значение. Это косметика (файл на диске не меняется), но при копировании
значения из этого окна юзер получит неверный ID. Кандидат на отдельную мелкую задачу, не часть #129.

### Наш собственный MCP

`app/mcp_stdio.py`: параметры типа `int` — `limit`, `percent`, `price`, `amount`,
`delay_seconds`, `interval_seconds`, `timeout_seconds`, `priority`, `status`. Ни один не может
достичь 2⁵³ в осмысленном сценарии (рубли, секунды, счётчики). Идентификаторы у нас строковые
(`par: str`, `name: str`). Класс дефекта к тулам Orchestra не применим.

## 4. Чего мы увидеть НЕ можем

Различитель, который просил dev-lead — «сырой текст JSON аргументов ДО разбора» — **в нашем
стеке недостижим**. SDK отдаёт `ToolUseBlock.input` уже как разобранный объект (шаг 4 таблицы),
а текст до разбора существует только внутри CLI (шаги 1–2). Добавить логирование сырого текста
у себя нельзя: его к нам не присылают.

Поэтому строго по логам «модель напечатала число» и «CLI сам привёл строку к числу» неразличимы.
Разделяет их **контрольный случай 33004**: та же сессия, тот же тул, то же значение, кавычки
сохранились до сервера Директа (`'Id': '1917704623170653147'` в ответе). Механизма, который
приводил бы строку к числу в одних вызовах и не приводил в других, нет — ни у нас, ни в zod
(dev-lead проверил: `z.string().regex(...)`, без `coerce` и `union`). Остаётся генерация.

Непроверенное, помечаю честно:
- Внутренности `@anthropic-ai/claude-code` не читал — «шаг 2» назван по отпечатку формата, а не
  по исходнику CLI.
- Codex-бэкенд не проверял. Гипотеза (НЕ проверена): Rust `serde_json` разбирает 19-значное
  целое в `i64` точно, поэтому на шаге 2 потери не будет, но последний хоп в JS-MCP-сервер
  округлит ровно так же. Проверяется одним вызовом Codex-воркера к тулу с большим ID.

## 5. Почему отказ — благоприятный исход, и чем страхуемся

Согласен с репортом: `-32602` громкий. Тихий сценарий — MCP-тул, где ID объявлен `number` или
без строгой схемы: округлённый ID может СУЩЕСТВОВАТЬ, и правка молча уедет в чужой объект.
19-значные ID — норма для Яндекс.Директа, Telegram, Discord snowflake, X.

Замер экспозиции по всей БД (33 232 лога): тул-вызовов, у которых в аргументах есть целое
> 2⁵³, — **ровно 6**, и все шесть — этот инцидент. Все шесть уже округлены; ни одного точного
значения > 2⁵³ в аргументах не встречалось никогда. То есть база редкая, но детектируемая.

**Предложение (правку не делал, как договаривались):** в `app/backend_claude.py:400`, там где
уже сериализуется `block.input`, пройти по значениям и при `isinstance(v, int) and abs(v) > 2**53`
писать одну заметную строку в лог — имя тула, путь до поля, значение. Стоимость — обход дикта
на tool_call; срабатывание — 6 раз за всю историю. Выгода: следующий такой случай виден одним
грепом, а не четырьмя ходами диагностики. Детектор ловит и тихий сценарий тоже: он смотрит на
значение, а не на ответ сервера.

Чего этот детектор НЕ даёт: он не отличит «модель напечатала число» от «CLI округлил строку» —
см. §4, для этого нужен доступ к сырому тексту, которого у нас нет.

**Что чинится по-настоящему** — на стороне владельца тула: в `description` параметра явно
написать, что ID передаётся строкой в кавычках. Это единственный слой, который в нашей власти
влияет на шаг 1.
