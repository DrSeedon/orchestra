> «Пустой реестр тоже обязан ронять: если `db` пуст (БД не открылась), `actual` станет»

Это утверждение не обеспечено кодом. Если БД не открылась, `sqlite3.connect(...mode=ro)` действительно бросит исключение. Но если БД успешно открылась и таблица `sessions` пуста, `db == set()`; скрипт продолжит работу. Если все оставшиеся memory-файлы входят в архив, то `actual` может ровно совпасть с `EXPECTED`, после чего будут удалены все 17 файлов.

Нужен явный fail-closed guard перед вычислением `actual`, например `if not db: sys.exit("REFUSE: empty live registry")`. Именно пустота реестра должна считаться отсутствием знания независимо от результата set arithmetic.

### NEW BUG — suggestion: AC количества строк несовместимы при последовательном выполнении билетов

### NEW BUG — suggestion: инструкция восстановления T4 может вернуть не ту версию

> «Остаточный риск — агент, спавненный ровно в это окно и ровно с одним из 17»

До коммита `git rm` нужно отменять из `HEAD`, а не из `HEAD^`. Команда `git checkout HEAD^ -- <path>` восстановит родительскую версию файла и может потерять изменения, уже находящиеся в текущем `HEAD`. После коммита удаления `HEAD^` уместен только при уверенности, что именно этот commit является удаляющим.

План использует варианты `<sha>^` и `HEAD^` без фиксации стадии операции. Безопаснее явно разделить:

- до коммита: восстановить из `HEAD`;
- после коммита: восстановить из конкретного родителя commit удаления.
