## Часть 2. Воркфлоу оркестратора под апрув

Требование юзера (с уточнениями): реализация — только по явному «да»; ресёрчи — автономны и
не режутся; крит-баг, блокирующий работу здесь и сейчас, чинится сам с отчётом после;
всё остальное — объяснение «как CEO» и ожидание.

### 2А. Новый блок `<approval-gate>` — в начало `modules/orchestration.md`, ПЕРЕД `<decision-tree>`

Предлагаемый текст (владелец мысли — только этот блок; всё, что ниже перечислено как «снять»,
удаляется, чтобы не осталось второго источника):

```
<approval-gate>
## Ничего не реализуется без слова юзера

Определи класс ДО любого действия и назови его вслух в ответе. Классов три.

A. БЛОКИРУЕТ СЕЙЧАС — автоапрув, чини немедленно, отчитайся после.
   Тест допуска: назови агента, канал или процесс, который ОСТАНОВЛЕН или ПОРТИТ данные
   в эту минуту (спавн/мерж не проходит, мост TG молчит, дашборд не отвечает, креды
   пропали, живой процесс пишет мусор). Не можешь назвать — это не класс A.
   НЕ класс A: «сломается позже», «хрупко», «жжёт квоту», «тесты красные»,
   «ветка не смержена», «доки протухли».
   После починки — одна строка юзеру: что сломалось, что сделал, чем проверил.

B. РЕСЁРЧ — спавнишь без спроса, глубину выбираешь сам.
   Заканчивается `RESEARCH DONE` + дописанной темой в базе знаний (2В).
   Ресёрч НИКОГДА не перетекает в реализацию: вывод «надо сделать X» — это класс C.

C. ВСЁ ОСТАЛЬНОЕ — реализация, рефакторинг, чистка, инфраструктура, чужие ветки,
   тест-гейт, доки, тулинг. Пишешь юзеру бриф на 3–5 строк и ЗАКАНЧИВАЕШЬ ХОД.
   Бриф — для CEO, не тикет:
     • что не так — в последствиях для дела, не в именах файлов;
     • цена бездействия — что будет, если не делать никогда;
     • что предлагаю — одно предложение;
     • цена — примерно, из чьего пула.
   Ни `spawn_worker`, ни `task_create`, ни ветки до ответа. Ожидание — нормальное состояние.

Ты не заводишь работу себе сам. Нашёл проблему по ходу другой задачи → одна строка юзеру
и строка в `TODO.md`. `task_create` по ней — только после его ответа.
Молчание юзера не является согласием ни в одном классе, кроме A.
</approval-gate>
```

### 2Г. Что промптом НЕ удержится (правило «оба направления отказа безвредны»)

- **Класс A** — не удержится. Забыл правило → лишний вопрос юзеру (безвредно); применил слишком
  широко → реализация без спроса, то есть ровно запрещённое действие. Промпт тут даёт только
  мягкую границу. Жёсткая версия — гейт в коде на `spawn_worker`/`merge_worker`, требующий
  признака апрува в последнем сообщении юзера, по образцу `app/quota_gate.py`. Замеры проекта на
  эту тему однозначны: три провала промпт-принуждения (#198, #216, #227) против одного законного
  случая. **Рекомендую: промпт сейчас, гейт в коде — отдельной задачей с апрувом.**
- **«Не заводить себе задачи»** — удержится. Забыл → ничего не происходит; перестарался → юзера
  лишний раз спросили. Но если нужна гарантия, она дешёвая: параметр `approved_by` у `task_create`.
- **Ревью-необязательность** — удержится. Забыл → ревью всё-таки прогнали (деньги, но не ущерб);
  перестарался → ревью нет вовсе, что юзер и разрешил.
- **Структура базы знаний (2В ниже)** — удержится. Забыл → ресёрч остался только в
  `docs/tasks/<id>/` (сегодняшнее состояние); перестарался → лишние строки в теме.

### 2Д. Дыра, которую надо закрыть заодно
Тул `notify_user` не описан ни в одном промпте (P11). Под новое требование ему место в
`<approval-gate>`: класс C с ценой бездействия «сейчас» и любой откат ранее сказанного — дёргать
юзера тегом; статусы и «воркер начал/закончил» — нет (это уже записано в описании самого тула,
дублировать не надо, нужна только строка «зови его при бриф-классе C»).

## Часть 2В. База знаний по темам (новое требование)

Сегодня: 353 каталога `docs/tasks/*`, из них 209 с `research.md`, 54 МБ. Найти можно только
`search_memory` и только если угадал формулировку. Тем нет, пробелов нет, отозванные выводы
лежат вперемешку с живыми.

Предлагаю минимум, который переживёт спешащего агента:

```
docs/kb/README.md          — оглавление: одна строка на тему
docs/kb/<тема>.md          — один файл = одна тема = один владелец
```

Тема — подсистема или повторяющийся вопрос, а не номер задачи. Стартовый набор виден из того,
что мы уже исследовали: `quotas-and-pools`, `prompt-delivery`, `review-routing`,
`measurement-method`, `tg-bridge`, `sessions-and-compact`, `worker-lifecycle`, `test-harness`,
`runtimes` (codex/grok/claude).

Каждый файл темы — ровно четыре раздела, строка = один факт:

```markdown
# <тема>

## Установлено
- <утверждение> · <доказательство: файл:строка | команда + число | ссылка> · <дата, #задача>

## Отвергнуто
- <во что верили / что пробовали> · <чем опровергнуто> · <дата, #задача>

## Пробелы
- <вопрос, оставшийся без ответа> · <что помешало> · <дата, кто спрашивал>

## Источники
- docs/tasks/<id>/research.md — <одна фраза, о чём он>
```

Правила (в `modules/research-method.md`, владелец — он):
1. Ресёрч не считается законченным, пока не дописал **минимум одну строку** в тему (или не завёл
   тему и строку в `README.md`). `RESEARCH DONE` называет файл темы и дописанные строки.
2. **Дописывать, не переписывать.** Устаревшее не удаляется: к строке приписывается
   `ОТОЗВАНО <дата> #<задача> — <чем>`, и она остаётся. Это прямо лечит наш случай с ценой пула,
   которая жила в двух местах и разошлась (P3).
3. `docs/tasks/<id>/research.md` остаётся сырым артефактом задачи и НЕ пересказывается в теме —
   в теме живёт вывод и доказательство, в задаче полный текст.
4. **«Пробелы» — единственный законный источник будущих ресёрчей.** Оркестратор берёт следующий
   ресёрч оттуда, а не выдумывает. Это же и есть «заполнять пробелы в научной базе».
5. Тема без владельца не заводится: строка в `README.md` обязательна, иначе появится вторая тема
   про то же самое — ровно тот дефект, который эта задача чинит в `CLAUDE.md`.

Проверяемость (нужна, иначе правило станет пожеланием): приёмка ресёрча оркестратором —
`git diff` задачи трогает `docs/kb/`. Не трогает → ресёрч не принят.

Разовая работа по переносу 209 существующих `research.md` в темы — отдельная задача, не эта;
предлагаю переносить лениво: тема заводится тогда, когда в неё пишет очередной ресёрч.
