## Главные выводы

1. Точный продукт установлен: **SentinelX MCP**, разработчик **PensaInfra / Pensa Software**, GitHub **pensados**. Официальный сайт: <https://sentinelx.app/>. Основной агент: <https://github.com/pensados/sentinelx-cloud-core>. Его нельзя смешивать с одноимёнными security-проектами, Chrome-расширениями и AIGet API gateway.
2. Есть **настоящая публичная карточка OpenAI**: [SentinelX plugin](https://openai.com/business/plugins/sentinelx/), с разработчиком PensaInfra, сайтом sentinelx.app и кнопкой установки. Она ведёт на [ChatGPT plugin](https://chatgpt.com/plugins/plugin_asdk_app_69f63e01766881919640f03b5e7912a5). Старый адрес [ChatGPT app](https://chatgpt.com/apps/sentinelx/asdk_app_69f63e01766881919640f03b5e7912a5) также указан в публичных инструкциях проекта. Это подтверждает регистрацию в публичном каталоге, но не проверку подключения конкретного аккаунта, текущих инструментов или каждой разрешённой автоматизации.
3. Это **host tools bridge через MCP и сторонний cloud hub**. Локально работает Python-агент, принимающий задания по исходящему WebSocket. Модель и интерфейс находятся у выбранного LLM-провайдера. Доказательств, что облачный SentinelX превращает ChatGPT web в OpenAI-compatible inference API, не найдено.
4. **«Не расходует Codex» и «безлимитно» не подтверждены.** Текущие официальные инструкции OpenAI показывают использование MCP-плагина в **ChatGPT Work**, а Work и Codex делят лимиты. Обычный Chat имеет другие модели и ограничения, но название веб-сайта ChatGPT не устанавливает используемый продукт. Воспроизведения старой форумной сессии, данных usage и точной модели нет. Источники: [Plugins quickstart](https://developers.openai.com/plugins/quickstart), [Work admin FAQ](https://learn.chatgpt.com/docs/enterprise/work-admin-faq), [pricing](https://learn.chatgpt.com/docs/pricing), [models](https://learn.chatgpt.com/docs/models).
5. **Allowlist не является универсальной песочницей.** В актуальном агенте список команд ограничивает `exec`, но отдельный `script_run` выполняет произвольный скрипт с правами ОС агента и опциональным sudo. Нужны ограничения всех путей, а не только списка команд. Свежий Linux installer по умолчанию не выдаёт sudo, но сохраняет существующий sudoers; включение `NOPASSWD: ALL` делает агента эквивалентом root. Windows service работает как LocalSystem. Подробности и ссылки на строки ниже.
6. Для Orchestra полезны узкий контролируемый bridge и некоторые механизмы восстановления результатов. SentinelX не заменяет самостоятельный оркестратор: не установлены управление полным жизненным циклом задач, долговечная история рассуждений, автономное продолжение модели и надёжное возобновление всех выполнявшихся работ после рестарта агента.

## 2. End-to-end: что где выполняется

```text
Пользователь: браузер ChatGPT, Chat или Work — различать явно
  → модель и tool orchestration OpenAI
  → MCP Streamable HTTP + OAuth → mcp.sentinelx.app/mcp/mcp
                                    [закрытый SentinelX cloud hub]
  ← ответы и состояние ← маршрутизация host/user ←→ WSS /agent/connect
                                                      ↑ исходящее соединение
                                                Python agent на хосте
                                                  → exec / scripts / files / services
                                                  → опциональные Unix-socket / stdio APIs
```

**В браузере**: интерфейс диалога, подключение/авторизация плагина и показываемые ChatGPT подтверждения. Браузер не становится shell-процессом и в найденной cloud-схеме не перехватывает ChatGPT cookies. Инструментальные запросы исходят из инфраструктуры выбранного LLM-клиента к MCP hub, а не из JS страницы напрямую к файловой системе хоста. Во время первоначального enrollment возможен временный callback HTTP server на loopback; это отдельный этап, не постоянный входящий Internet-порт.

**У OpenAI**: модель выбирает инструменты и обрабатывает ответы. SentinelX не задаёт единственную модель. Утверждение «это именно такая-то reasoning-модель» без выбранного surface/model или trace не установлено. Ни Apache-лицензия агента, ни HTTP endpoint MCP не дают доступ к весам/вычислению модели.

**У Pensa**: hub обслуживает MCP, вход пользователя, привязку host, маршрутизацию, dashboard и заявленный аудит. Этот компонент закрыт. Транспортные команды и их результаты проходят через него в читаемом для сервиса виде; WSS/HTTPS защищают транспорт, но не создают end-to-end шифрование от оператора hub.

**На хосте**: агент принимает операции, проверяет свою policy, запускает subprocess/интерпретатор или выполняет структурированную работу с файлами. Возвращаются stdout/stderr, exit code, файлы или состояние. Политика модели OpenAI, scopes hub и policy агента — разные уровни. OS sandbox OpenAI не охватывает произвольный внешней MCP-командой управляемый хост.

**Дополнительные стороны**: identity provider (Google/GitHub по privacy), GitHub/PyPI при установке, инфраструктура публичного hub, явно разрешённые URL загрузок и интеграции. Каждый новый адрес в конфиге расширяет набор получателей. Нет основания обещать, что все данные остаются только на своей машине.

### Кто технически имеет доступ

Пользователь SentinelX и аккаунты, которым host разрешено разделять; ChatGPT/иной авторизованный MCP client от их имени; оператор/компрометация cloud hub в пределах доступных agent operations; администратор локальной ОС. Даже если terms обещают не использовать доступ самостоятельно, агент принимает запросы от hub и не проверяет отдельную криптографическую подпись владельца на каждую мутацию. Это архитектурный вывод из клиента и dispatch, не обвинение оператора в фактическом доступе.

[Privacy policy](https://sentinelx.app/privacy), с актуальной датой редакции **2026-10-18** (Last updated: October 18, 2026), прочитанная 29 октября, заявляет: сохраняются account/host metadata и audit arguments (включая текст edit/скрипта), status/error/timing/response hash; command output и прочитанные файлы проходят через hub без постоянного хранения. Для входа пользователя и исходящего подключения агента определяется приблизительная страна по IP; согласно политике сохраняется страна, а не IP-адрес. Дата первой публикации не установлена. Следовательно, записанный через edit код может сохраняться как **аргумент**, даже при обещании не сохранять «filesystem contents». Сама политика не проверяет production retention и доступ сотрудников. [Terms](https://sentinelx.app/terms), обновлены 2026-10-18: сервис без гарантии доступности/безошибочности; обещание не обращаться к серверам самостоятельно — договорное, не криптографическая граница. Локальный audit и pending-result файлы также могут содержать чувствительные данные.

### Старые данные, протокол и восстановление: конкретные границы

* [Protocol RequestMessage:173–198](https://github.com/pensados/sentinelx-cloud-protocol/blob/00169f8fddbab11082f7ff0f24ef5c7e321c9a47/python/sentinelx_protocol/messages.py#L173-L198): typed op/id/payload/deadline/opaque_ref, extra fields forbidden. Это корреляция и schema checking, не подпись конечного пользователя. Старый агент может отбросить незнакомое поле и не ответить; capability negotiation с закрытым hub не проверен live.
* [Policy migration:794–873](https://github.com/pensados/sentinelx-cloud-core/blob/b4207d6149d95f2d3cc9b219d4e617c365b76fda/src/sentinelx_core/policy.py#L794-L873): старый `allowed_read_paths` становится read-only; непустой новый `paths` выигрывает. В коде стоит truthiness-check: `paths: []` вместе с оставленным legacy key попадает в legacy fallback, а не обязательно в deny-all. При переносе такого конфига нужно проверять effective capabilities; это статическое наблюдение, не выполненная миграция или исправление.
* Existing Linux sudoers сохраняется: обновление новым installer само по себе не отбирает прежнее root-equivalent разрешение. Прочитанные исторические playbooks также не доказывают текущих grants/ограничений. Аккаунтные ограничения и конфиг старого installed agent неизвестны.
* Готовый pending-result и работающий процесс — разные состояния. Проверены кодом atomic record/rename, TTL/лимит числа результатов, replay после reconnect и удаление после send. Crash/reboot, fsync/durable hub ACK, дедупликация фактических side effects и конкурентные изменения файлов runtime-пробой не проверялись.

Эти случаи включены в отчёт как потенциальные регрессии callers/старых конфигов/восстановления; внешние acceptance tests не запускались и не менялись.

## 4. Квоты, продукт и проверка обещаний

**Отдельный обычный Chat существует.** [Текущая официальная справка о моделях ChatGPT](https://help.openai.com/en/articles/20001354-gpt-6-and-other-models-in-chatgpt) прямо разделяет usage/credit rules Chat и Work/Codex. В Chat выбор GPT-6/Instant/Thinking/Pro не тождествен моделям Work. [Каталог моделей Work/Codex](https://learn.chatgpt.com/docs/models) отдельно относит GPT-6.1 Sol/Terra к этим поверхностям; Terra недоступна в обычном Chat. Назвать модель исходной дискуссии нельзя: trace и выбранный surface отсутствуют.

**Но web ChatGPT может быть Work.** [Quickstart MCP plugins](https://developers.openai.com/plugins/quickstart) явно предлагает переключить Chat → Work; [официальная карточка SentinelX](https://openai.com/business/plugins/sentinelx/) также предлагает Work/Codex. [Документация MCP](https://learn.chatgpt.com/docs/extend/mcp) при этом допускает tools в Chat и Work после установки. Поэтому неверны оба безусловных вывода: «любая работа SentinelX расходует Codex» и «любая работа SentinelX не расходует Codex». Решает **реальный surface и его учёт**, а не бренд плагина.

**Work и Codex делят usage.** Это прямо сказано в [Work admin FAQ](https://learn.chatgpt.com/docs/enterprise/work-admin-faq); [pricing](https://learn.chatgpt.com/docs/pricing) описывает зависимость расхода от модели, сложности, context/tools, возможные weekly limits и fair use. Отсутствие пятичасового лимита у нынешнего Pro не обещает бесконечный ресурс. [Sign in with ChatGPT](https://learn.chatgpt.com/docs/sign-in-with-chatgpt) для внешних inference-apps также использует существующее Work/Codex allowance; разрешение приложению не создаёт новую квоту. ### OpenCode, cookies и API proxy

OpenCode-compatible provider принимает сообщения и возвращает model inference; MCP принимает `tools/list`/`tools/call`. Указание MCP URL как inference baseURL само по себе не работает. При OpenCode + SentinelX reasoning продолжает обслуживать настроенный provider, а SentinelX даёт инструменты. Это не «ChatGPT web subscription как API».

Поисковый индекс AIGet содержит старые заявления о SentinelX API и распределении нагрузки по аккаунтам. Открытые 29 октября [AIGet homepage](https://aiget.tech/en) и [terms, 26 октября](https://aiget.tech/en/terms) описывают иной prepaid gateway. Старый сниппет противоречит текущей странице; это отдельный кандидат, не подтверждение принадлежности исходной истории. Контракты с upstream, происхождение пула и разрешённость чужих аккаунтов не установлены.

В просмотренных cloud-core/installer путях не найдено извлечения ChatGPT cookies, чтения браузерного профиля или подмены ChatGPT клиента. Scope отрицательного вывода — выбранные файлы и деревья, не закрытый hub и не все одноимённые продукты. Если неизвестный OpenAI-compatible proxy просит экспортировать приватную браузерную session cookie, это **другая схема**: передача действующего session credential посреднику, возможный доступ от имени аккаунта и неподтверждённые условия использования. Наличие OAuth у SentinelX этого не оправдывает. Способы извлечения, подмены/ротации аккаунтов и обхода региональных запретов не реализовывались и здесь не приводятся.

## 6. Архитектурная развилка: bridge к Chat или самостоятельная Orchestra

**Вариант A — обычный Chat + минимальный MCP/local tools bridge.** Человек остаётся владельцем диалога и последовательности «попросил → посмотрел → продолжил». Модель в Chat может использовать инструменты, если они доступны этому аккаунту/режиму; квота тогда определяется Chat, не самим bridge. На нашей стороне нужны ограниченные действия и durable operation records, иначе закрытая вкладка/timeout оставят неоднозначность. Это удобно для коротких inspect/read/propose операций. Полный spawn_worker/restart/git merge не следует автоматически открывать во внешний plugin.

**Вариант B — Work + тот же bridge.** Даёт агентный интерфейс с multi-step execution, но Work/Codex usage общий. Переезд shell tool на свой host сам по себе не делает model inference бесплатным и не снимает context/tools limits.

**Вариант C — обычный Chat как пульт Orchestra.** Chat вызывает разрешённое создание задачи/получение статуса, а durable job, workers, квоты и продолжение принадлежат Orchestra. Параллельность обеспечивают независимые workers и серверный job manager; endpoint возвращает operation id и последующий результат. Здесь Continue может понадобиться для новой реплики/получения результата в Chat, но не должен быть условием выполнения уже принятой серверной задачи. Все запуски моделей Orchestra продолжают использовать собственный разрешённый backend и его квоту. Это не способ превратить Chat-подписку в inference API.

**Вариант D — внешний OpenAI-compatible inference provider для harness/OpenCode.** Это смена model transport и учёта, а не tools bridge. Нужны документированные auth, модель, API compatibility и право/цена использования. Никакие cookies/региональные обходы не являются частью предложения.

**Сохранение состояния и timeout.** Следует различать HTTP/MCP response timeout, жизнь shell-процесса, жизнь job record, доставку result, историю модели и её следующий turn. SentinelX решает часть middle layers, Orchestra уже решает многие из них. Надёжный контракт: операция принята один раз с id, состояние читается после reconnect, мутации без receipt не повторяются вслепую, законченный результат доставляется отдельно. Automatic Continue без знания terminal status способен повторить побочный эффект.

**Параллельность.** В SentinelX коде есть concurrent async handlers, но не установлен публичный production concurrency SLA/планировщик. У Orchestra harness tools одного response sequential; межзадачная параллельность — отдельные сессии/workers/bg jobs. Не найдено оснований переносить чужое обещание «много команд одновременно» в обещание неограниченного количества независимых агентов.

**Возврат после обрыва.** SentinelX pending-results хранит уже сформированные ответы до отправки; running async task может пережить WebSocket reconnect, но не гарантированную смерть процесса. Инсталлятор `KillMode=process` может оставить дочерний процесс жить, однако это не восстанавливает Python task и результат автоматически. В Orchestra bg restore и delivery state нужно использовать как владельцев восстановления, а не заводить второй конкурирующий реестр.

Здесь описаны варианты. Выбор facade, trust boundary и доступных mutations — архитектурное решение владельца; реализация, подключение и эксплуатация не разрешены этим исследованием.
