     1	# Threat Model — sentinelx-cloud-core
     2	
     3	This document describes the threat model the agent is designed against. It's
     4	the "deeper" companion to [`SECURITY.md`](./SECURITY.md), aimed at people
     5	auditing the code, integrating SentinelX into their stack, or evaluating it
     6	for compliance review.
     7	
     8	The structure is roughly:
     9	  1. What we're protecting (assets)
    10	  2. Who we're protecting it from (adversaries)
    11	  3. Where the trust boundaries are (architecture diagram)
    12	  4. Specific threats and how we mitigate them
    13	  5. Residual risks we accept
    14	
    15	
    16	## 1. Assets
    17	
    18	The agent sits on a host belonging to the operator. The assets it could
    19	plausibly leak or damage:
    20	
    21	| Asset | Where it lives | Loss impact |
    22	|---|---|---|
    23	| Host filesystem (read) | `/`, `/etc`, `/var`, user homes | Confidentiality of secrets, configs, code |
    24	| Host filesystem (write) | Same, gated by sudo + allowlist | Integrity / availability — files modified, services downed |
    25	| Service control | systemd units listed in `services:` | Availability — services stopped or restarted at attacker timing |
    26	| Cloud metadata credentials | `169.254.169.254` (AWS/GCP/Azure) | If the host is in a cloud, IAM credentials can pivot to cloud account compromise |
    27	| Internal network | RFC1918 routes the host can reach | Lateral movement (DBs, internal admin panels, VPN-reachable corp networks) |
    28	| The agent's JWT identity | `/etc/sentinelx/identity.json` | Impersonation of this host to the hub |
    29	| The hub's trust in this host | `host_id` registered at hub | Could let attacker route hub-bound queries to a different host |
    30	| Operator credentials transiting through tools | e.g., `cat ~/.aws/credentials` if allowed | Direct credential theft |
    31	
    32	
    33	## 2. Adversaries
    34	
    35	We model three concrete adversary personas. The agent's defenses target the
    36	first two; the third is mostly out-of-scope and noted for completeness.
    37	
    38	### A1 — Compromised hub (or hub operator turned malicious)
    39	
    40	The hub at `mcp.sentinelx.app` is operated by Pensa (project owner). An
    41	attacker who compromises the hub — or an insider who turns malicious — has
    42	full control over what messages reach each agent. The agent **must defend
    43	itself against its own hub**, because:
    44	
    45	  - If a hub compromise meant total host compromise, the failure mode of
    46	    the entire SentinelX system would be unbounded.
    47	  - Reviewers (Anthropic, OpenAI) need to be able to assert that an agent
    48	    install does not give Pensa root on the user's box.
    49	
    50	**Capabilities of A1:**
    51	  - Send arbitrary WebSocket messages to the agent
    52	  - Choose any operation the protocol supports
    53	  - Provide attacker-controlled values for any parameter
    54	  - Observe responses
    55	  - Time tool invocations
    56	
    57	**NOT capabilities of A1:**
    58	  - Forge another host's identity (each host has its own JWT)
    59	  - Bypass TLS to the agent (cert pinning at hub URL)
    60	  - Read or write the host's local filesystem outside what tools expose
    61	  - Execute commands not in the operator's allowlist
    62	
    63	
    64	### A2 — Compromised LLM client / malicious tool client
    65	
    66	The MCP client (Claude.ai, ChatGPT, or any other) calls tools through the
    67	hub. A compromised LLM or a malicious user driving the LLM to do harm is
    68	indirectly an adversary against the agent. They can invoke any tool the
    69	operator's allowlist permits, with any argument.
    70	
    71	**Capabilities of A2:** same as A1 in practice — the hub forwards their
    72	calls to the agent. The agent does not distinguish hub-originated from
    73	client-originated calls; both are treated as untrusted input.
    74	
    75	**The defense is identical to A1's:** allowlist, parameter validation,
    76	SSRF allowlist.
    77	
    78	
    79	### A3 — Local attacker on the host (out of scope)
    80	
    81	If an attacker already has a shell on the host, the agent's defenses are
    82	moot — they can read `identity.json`, modify `config.yaml`, install a
    83	keylogger in `/usr/bin`, etc. We don't attempt to defend against this.
    84	
    85	The reasonable thing to do if you suspect host compromise is to revoke the
    86	host's enrollment from the hub admin panel, then reinstall.

    89	## 3. Trust boundaries
    90	
    91	```
    92	                                        Trust boundary 1: TLS + WebSocket
    93	                                                       │
    94	   ┌────────────────────────────────┐                  │     ┌────────────────────────────────────┐
    95	   │  Hub (mcp.sentinelx.app)       │   outbound WSS   │     │  Host running this agent            │
    96	   │  Operated by Pensa             │ ◄────────────────┼───► │                                     │
    97	   │                                │                  │     │  ┌─────────────────────────────┐    │
    98	   │  - Receives MCP from clients   │                  │     │  │  agent (sentinelx user)     │    │
    99	   │  - Authenticates via Keycloak  │                  │     │  │                             │    │
   100	   │  - Routes messages to agents   │                  │     │  │  • allowlist enforcement   ◄─── Trust boundary 2:
   101	   │                                │                  │     │  │  • SSRF check on file_url  ◄─── allowlist + safe_path
   102	   │  ASSUMED HOSTILE in this model │                  │     │  │  • path-traversal rejection │    │
   103	   └────────────────────────────────┘                  │     │  │                             │    │
   104	                                                       │     │  └──────┬──────────────────────┘    │
   105	                                                       │     │         │ subprocess.run             │
   106	                                                       │     │         │ (sudo NOPASSWD for         │
   107	                                                       │     │         │  vetted binaries only)     │
   108	                                                       │     │         ▼                            │
   109	                                                       │     │  ┌─────────────────────────────┐    │
   110	                                                       │     │  │  OS / kernel / sudo binary  │    │
   111	                                                       │     │  │  ASSUMED TRUSTED            │    │
   112	                                                       │     │  └─────────────────────────────┘    │
   113	                                                       │     └────────────────────────────────────┘
   114	```
   115	
   116	**Boundary 1 (network):** the agent uses TLS with hostname verification
   117	and the hub's domain pinned in the agent's config. The agent will not talk
   118	to a different hub even if DNS lies. If the TLS cert chain fails to
   119	validate, the connection is dropped.
   120	
   121	**Boundary 2 (process):** the agent is a single Python process running as
   122	the unprivileged `sentinelx` user. Operations that require root go
   123	through `sudo` for a small set of binaries explicitly listed in the
   124	sudoers fragment installed by `install.sh`. **The allowlist sits on top
   125	of this** — even if `sudo` is misconfigured wider than intended, the
   126	allowlist still constrains what the agent can ask sudo to run.
   127

   129	## 4. Threats and mitigations
   130	
   131	We use a STRIDE-style enumeration. Each threat has: severity, attack
   132	vector, mitigation, and residual risk.
   133	
   134	### 4.1 — Tampering with command via crafted payload
   135	
   136	| | |
   137	|---|---|
   138	| **STRIDE category** | Tampering / Elevation of Privilege |
   139	| **Attacker** | A1, A2 |
   140	| **Vector** | Send `exec` op with `command="../../../bin/rm -rf /"` or a command with shell metacharacters meant to escape |
   141	| **Severity** | High if exploitable |
   142	| **Mitigation** | `exec` runs the command string through a shell (`bash -lc`; PowerShell on Windows), and what it may run depends on the host's `exec_mode`. In `allowlist` (the default) `allowed_commands` matches whole words, and every command in the line must be covered, not only the first: the line is split outside quotes on `;`, `\|`, `&&`, `\|\|`, `&` and newlines; the inside of `$(...)`, backticks, `<(...)`/`>(...)`, `$((...))` and unquoted here-doc bodies is checked by the same rules; shell grammar words and a few side-effect-free builtins are skipped; read-only filters (`grep`, `head`, `sort`, `cut`, ...) are allowed after the first command only without a file operand and without their write/execute options; and anything that cannot be analysed with certainty (a `case` statement, unbalanced quotes, parentheses or backticks) is refused. A command preceded by an assignment (`VAR=value cmd`) is matched as written, so a variable such as `LD_PRELOAD` cannot ride on an allowed command. `strict` additionally refuses newlines, command/process substitution and file redirections (formerly `exec_strict: true`). `unrestricted` runs any command line under the agent's identity, as `script_run` does, for trusted development hosts. On Windows only the whole-word match applies. Until agent 0.23.22 the match was a prefix over the whole string and the per-command check was opt-in (GHSA-r2h3-76g7-m95x). |
   143	| **Residual risk** | `allowed_commands` is a boundary only for `exec`, and only as far as its own entries allow: an entry such as `bash`, `sh`, `python3`, `php` or `node` lets a quoted payload (`bash -lc '...'`) run anything, because the payload is one argument. `script_run` runs arbitrary scripts as the agent's user and is not governed by `allowed_commands`: with it enabled, or with `exec_mode: unrestricted`, the real boundary is the agent's OS account (dedicated user, sudoers, file permissions, namespaces). Operators who need `allowed_commands` to hold set `disabled_ops: [script_run]` and keep `exec_mode` at `allowlist` or `strict`. On Windows the chain check does not model PowerShell grammar. SentinelX does not offer a shell-free argv exec mode. |
   144	
   145	### 4.2 — Path traversal in upload / edit / mutation target
   146	
   147	| | |
   148	|---|---|
   149	| **STRIDE category** | Tampering |
   150	| **Attacker** | A1, A2 |
   151	| **Vector** | `upload_file` with `target_path="../../../etc/passwd"`, or `edit`/`move`/`copy`/`delete`/`chmod`/`chown` with a `path` (or `src`/`dst`) that escapes the allowlist via `..` or a planted symlink |
   152	| **Severity** | Critical (arbitrary write/destroy as `sentinelx`, then `sudo` if applicable) |
   153	| **Mitigation** | Two layers. (1) `executor_engine.py::safe_path_under()` resolves the candidate path against the upload base, walks symlinks, and rejects escapes — applied to upload handlers. (2) The unified r/rw path model: `Policy.resolve_path()` canonicalizes symlinks *before* the prefix check and is called with `need_write=True` by every mutating op. `edit` (both `handle_edit` and `edit_upload_complete`) and the five destructive ops (`move`/`copy`/`delete`/`chmod`/`chown`) all funnel every path argument through it; for `move`/`copy` BOTH `src` and `dst` are checked independently, so a copy cannot exfiltrate to an unlisted destination. A path that is only `access: r` (not `rw`), outside the allowlist, or that resolves outside it, is rejected with `path_not_allowed`. Tests: `test_handlers_upload.py::test_upload_file_rejects_path_traversal`, `test_policy.py` (traversal/symlink-escape/prefix-not-substring), `test_handlers_edit.py` (edit path-enforce), `test_handlers_fsmutate.py` (traversal escape defeated, dst-outside-rw refused, src-in-readonly refused). |
   154	| **Residual risk** | TOCTOU: if the operator's `upload_base` itself is a symlink an attacker can swap, the check could be bypassed. We don't defend against attackers with prior write access (see §4.7). The rw model is only as good as the operator's `file_ops.paths` — see §5.1. |
   155	
   156	### 4.2.1 — `sudo` does not lift the rw allowlist on `edit` (carve-out removed in 0.11.18)
   157	
   158	| | |
   159	|---|---|
   160	| **STRIDE category** | Elevation of Privilege |
   161	| **Attacker** | A2 (compromised LLM / tool client) |
   162	| **History** | Until 0.11.17, `edit`/`edit_upload_complete` with `sudo=true` skipped the file_ops rw check, on the assumption that the installer's sudoers fragment bounded what a sudo edit could touch. The installer granted `NOPASSWD:ALL`, so no such bound existed: any request could write any file as root, including the agent's own `/etc/sentinelx/config.yaml`. An agent that can rewrite its own allowlist does not have one. Reported by OpenAI Security; removed in 0.11.18 (2026-09-08), on both the single-call and the chunked-upload path. |
   163	| **Today** | The rw verdict applies to every edit, with or without sudo; `sudo` only changes which user performs a write the policy already allows. Paths are canonicalized as before (symlinks and `..` resolved). The agent's config is not rw by default, so the agent cannot change its own policy: `edit` of `/etc/sentinelx/config.yaml` is refused with `path_not_allowed`. |
   164	| **Policy administration** | The owner changes the policy outside the assistant: as root over SSH, or with Edit config on the host's card in the dashboard, then restarts the agent. The current `add_allowed_command` / `add_allowed_read_path` playbooks have the assistant show the exact lines and leave applying them to the owner. Configs written by older installers can still carry the old playbook text describing a sudo edit of the config; those steps now fail by design (seen 2026-10-06, sxrep_FA72D2Y86WCR). An owner who wants the agent to maintain its own policy can declare the config file in file_ops with `access: rw`, which makes it a visible choice in their config rather than a property of a flag. |
   165	| **Residual risk** | (1) Declaring `/etc/sentinelx` (or `/`) as rw reopens policy rewriting; that is an explicit owner decision. (2) The rw model governs `edit`; it does not bound `script_run`, which runs arbitrary bash as the agent's user (with sudo when the sudoers allows it) and is not gated by `allowed_commands`. An owner who wants a narrow allowlist to mean something must also disable `script_run` (`disabled_ops: [script_run]`) and keep the sudoers fragment narrow (see §4.7, §5.1). Tests: `test_handlers_edit.py::{test_edit_sudo_does_not_bypass_the_rw_gate, test_edit_sudo_upload_path_is_gated_too}`. |
   166	
   167	### 4.3 — SSRF via `file_url`
   168	
   169	| | |
   170	|---|---|
   171	| **STRIDE category** | Information Disclosure / Spoofing |
   172	| **Attacker** | A1, A2 |
   173	| **Vector** | `upload_file` with `file_url=https://169.254.169.254/...` (cloud metadata), or `https://10.0.0.5/admin` (LAN service), or `https://attacker.com` (recon) |
   174	| **Severity** | Critical on cloud hosts (IAM credential theft); High on others (LAN recon / pivot) |
   175	| **Mitigation** | Layered, in `handlers/upload.py::_validate_fetch_url`: <br>1. https-only scheme. <br>2. Hostname must be in `security.trusted_fetch_hosts` allowlist (default empty). <br>3. Resolved IP must pass `_is_safe_ip()` — rejects loopback, RFC1918, link-local, multicast, reserved. <br>4. Redirects disabled via `_NoRedirectHandler`. <br>5. Default timeout reduced to 15s. <br>Tests cover each bypass attempt. |
   176	| **Residual risk** | DNS rebinding between the validation lookup and urllib's lookup is theoretically possible; in practice it requires the attacker to also be in `trusted_fetch_hosts`, which already requires operator opt-in. |
   177	
   178	### 4.4 — Unauthorized service control
   179	
   180	| | |
   181	|---|---|
   182	| **STRIDE category** | Denial of Service / Tampering |
   183	| **Attacker** | A1, A2 |
   184	| **Vector** | `service stop docker` to disrupt the host; `restart sshd` to lock the operator out |
   185	| **Severity** | Medium-High |
   186	| **Mitigation** | `services:` block in `config.yaml` is an allowlist not just of unit names but of which **actions** are permitted per unit. Stopping `sshd` is impossible unless the operator listed it. The agent's `service` handler (in `handlers/service.py`) checks both the unit and the action against the spec. |
   187	| **Residual risk** | Operator misconfiguration. Default starter config doesn't include `sshd`. |
   188	
   189	### 4.5 — Identity replay / forgery
   190	
   191	| | |
   192	|---|---|
   193	| **STRIDE category** | Spoofing |
   194	| **Attacker** | A1, A2, network observer |
   195	| **Vector** | Stolen `identity.json` used to impersonate the host |
   196	| **Severity** | High (ranks alongside host compromise) |
   197	| **Mitigation** | `identity.json` is signed by the hub at enrollment. Agent presents it on connect, hub validates. File permissions: owned by `sentinelx`, mode 0600. Stolen identity = compromised host (see A3 — out of scope). On compromise: revoke from hub admin panel, re-enroll. |
   198	| **Residual risk** | No automatic revocation if the host goes silent — operator must notice. |
   199	
   200	### 4.6 — Information disclosure via error messages
   201	
   202	| | |
   203	|---|---|
   204	| **STRIDE category** | Information Disclosure |
   205	| **Attacker** | A1, A2 |
   206	| **Vector** | Crafted inputs designed to elicit verbose errors that reveal local paths, env vars, or internal state |
   207	| **Severity** | Low |
   208	| **Mitigation** | `executor.py::HandlerError` is the only exception type that reaches the wire. Other exceptions are caught and logged locally; the wire-level response is a generic `internal_error` with a short, sanitized message. Stack traces stay in `/var/log/sentinelx/core.log` on the host only. |
   209	| **Residual risk** | Some `HandlerError` messages do include path fragments (e.g., `"file exists: /var/lib/sentinelx/uploads/foo"`). This is an intentional UX trade-off and considered low severity given how `upload_base` is structured. |
   210	
   211	### 4.7 — Local privilege escalation via the agent
   212	
   213	| | |
   214	|---|---|
   215	| **STRIDE category** | Elevation of Privilege |
   216	| **Attacker** | A3 (already on the host as a non-root user) |
   217	| **Vector** | A regular host user finds they can talk to the agent's local files and pivot through the agent's `sudo` |
   218	| **Severity** | Considered out of scope (see §2 — A3) |
   219	| **Mitigation** | The agent doesn't expose any local socket or named pipe. There is no IPC for local users to abuse. `identity.json` is mode 0600 and `config.yaml` is mode 0644 (readable but writes need sudo). The sudoers fragment is locked to specific binaries (`pensa-safe-edit`, listed services), not a wildcard. |
   220	| **Residual risk** | Acknowledged. If you don't trust the local users on a host, don't enroll that host. |
   221	
   222	### 4.8 — `local_api` with transport stdio runs a declared binary (0.23.31)
   223	
   224	| | |
   225	|---|---|
   226	| **STRIDE category** | Elevation of Privilege / Tampering |
   227	| **Attacker** | A1, A2; A3 for the binary-replacement vector |
   228	| **Vector** | (1) Craft `params` so they reach the binary's argv or a shell. (2) Replace the declared binary, or a directory entry on its path, so the agent runs something else. (3) Leave a child running after the call (a server that ignores EOF, or spawns helpers). (4) Reach tools of an MCP server the operator did not mean to expose. |
   229	| **Severity** | High if (1) or (2) were possible; Medium for (4) |
   230	| **Mitigation** | The binary is declared by the host's owner in `config.yaml` (absolute path, fixed `args`); the caller only picks an allowlisted action. (1) No shell: `create_subprocess_exec` with argv `[path, *args]`, and the call's parameters are serialized into the JSON-RPC message only. (2) `binary_problem()` refuses a binary that is, or sits in a directory that is, writable by anyone but its owner (a sticky directory and a user-private group excepted), at load (endpoint skipped) and again before every call (`unsafe_binary`). (3) One process per call, in its own session; stdin is closed after the answer, then the process group is killed after a 2 s grace, and the whole call is bounded by `timeout_s`. stdout is capped at 8 MiB, stderr kept to its last 8 KiB. The child gets a minimal environment plus the declared `env`, never the agent's. (4) Documented: the allowlist is of methods, so `tools/call` reaches every tool of that server. `run_as` goes through `sudo -n -u <user> -- <path> <args>`, which needs a sudoers rule naming that exact command. Tests: `test_local_api_stdio.py` (33, 16 sabotages caught). |
   231	| **Residual risk** | Whatever the declared binary itself does with its input is the binary's responsibility; this is the same trust the owner extends by installing it. Per-tool allowlisting inside an MCP server is not implemented. With `run_as`, the child runs as another user and the agent may not be able to signal it; it relies on the child exiting at EOF and stops waiting after a bounded grace. On Windows the permission check is skipped (ACLs are the operator's job) and helpers left by a child that already exited are not swept. |

   234	## 5. Residual risks we accept
   235	
   236	These are conscious choices, documented so reviewers know we know:
   237	
   238	  1. **Operator misconfiguration is the dominant risk.** Almost every
   239	     "what if" scenario above ends with "if the operator allowlists X,
   240	     this defense doesn't help." The mitigation is documentation
   241	     (`config.example.yaml` has extensive guidance) and conservative
   242	     defaults (empty allowlists, narrow service action lists).
   243	
   244	  2. **No sandbox.** The agent runs commands directly via `subprocess`.
   245	     A sandbox layer (firejail, bubblewrap, namespaces) would add
   246	     defense-in-depth but also installation complexity and platform
   247	     fragility. We chose the simpler model and accept that the allowlist
   248	     is load-bearing.
   249	
   250	  3. **No DoS mitigation in the agent.** The hub does rate limiting
   251	     for tool invocations per user. The agent itself does not. A
   252	     compromised hub could flood it. We accept this — a compromised
   253	     hub is already game-over for many reasons.
   254	
   255	  4. **TLS trust is bootstrapped via the OS cert store.** We don't
   256	     pin the hub's certificate fingerprint (only the hostname). An
   257	     attacker who can issue a valid cert for `mcp.sentinelx.app`
   258	     through any CA the host trusts can MITM. CT logs and the hub's
   259	     known-issuer should make this detectable post-hoc.
   260	
   261	  5. **Limited audit log on the agent side.** All operations are
   262	     logged centrally on the hub (Redis ring buffer) — that remains
   263	     the authoritative trail. Additionally, every *successful mutating*
   264	     op (`move`/`copy`/`delete`/`chmod`/`chown`) now appends one
   265	     JSON line to `/var/log/sentinelx/mutations.log` (op, paths, ts).
   266	     This is a forensic aid, NOT a security control: it is best-effort
   267	     (a write failure never blocks the operation) and an attacker who
   268	     controls the agent can also tamper with or truncate the file, so
   269	     it does not survive the very adversary (A1/A2) most relevant here.
   270	     It does help post-incident reconstruction when the hub's view is
   271	     unavailable or disputed. The agent's general logs in
   272	     `/var/log/sentinelx/core.log` are still operator-managed
   273	     (logrotate) and not protected against rotation gaps. For
   274	     high-assurance environments, ship both logs to a separate,
   275	     append-only aggregator the agent user cannot reach.
