# #367 — Аудит встроенных тулов рантайма harness (`app/harness/tools.py`)

## Вопрос

Context: рантайм harness (#365), тула́ в `app/harness/tools.py`, исполняются циклом
`app/harness/loop.py:247` (`await builtin.dispatch(...)`).
Change under test: каждый из 6 тулов (bash, read, write, edit, glob, grep) против заведомо
известного ответа; контроль — тот же вопрос через собственный тул `bash`.
Baseline: ожидание агента («тул отвечает тем, что ответил бы системный grep/ls/cat»).
Outcome: список дефектов «врёт», дефектов «неудобно/лишние ходы» и подтверждение работающего;
каждый дефект доказан парой вызовов рядом (тул + bash-контроль).

Метод: стенд на фикстурах (`/tmp/h367/stand`), вызовы через `tools.dispatch()` — тот же путь,
что боевой цикл. Все числа ниже — замеры этого стенда, не чтение кода.

## Гипотезы (до эксперимента)

- H1: дефект ox-probe — fallback-grep без `-E`: паттерн с `|` уходит в BRE, где `|` литерал,
  → пусто. Фальсификатор: если на машине с дефектом стоит rg, ветка fallback не исполнялась бы.
- H2: grep-тул молча игнорирует `glob_filter` (в коде он передаётся только в rg-ветке,
  строки 240–245: в fallback `cmd = ["grep", "-rn", pattern, "."]` фильтра нет).
  Фальсификатор: вызов с glob_filter вернул бы только отфильтрованные файлы.
- H3: синхронные `subprocess.run`/файловые операции внутри `async def dispatch` блокируют
  event loop сервера. Фальсификатор: конкурентный тик не дёргается во время grep.
- H4: `read` ложно называет UTF-8 файл бинарным, если байтовый потолок READ_MAX_BYTES режет
  многобайтный символ. Фальсификатор: такой файл читается как текст.

Все четыре подтверждены (ниже). Контргипотеза «на боевой машине стоит rg и дефект другой»
проверена: `command -v rg` на этой машине пусто; fallback — единственная ветка здесь.

## Находки — ВРЁТ (каждая доказана парой вызовов)

### D1 — grep: альтернатива `|` молча даёт «(no matches)» (дефект ox-probe) — CONFIRMED
- `[grep] {"pattern": "nemotron-3|inkling|laguna|north-mini"}` → `(no matches)`
- bash-контроль `grep -rnE 'nemotron-3|inkling|laguna|north-mini' .` → 4 совпадения.
- Причина: `rg` на машине нет (`command -v rg` пусто) → fallback `grep -rn <pattern> .`
  без `-E`; в GNU-BRE `|` — литерал. Рабочая форма воркера `a\|b` — это BRE-альтернатива.
- Замер стенда: builtin-style → rc=1 пусто; `grep -rnE` → 4 строки; `a\|b` → 4 строки.

### D2 — grep: `glob_filter` молча ИГНОРИРУЕТСЯ, тул возвращает чужие файлы под видом фильтра — CONFIRMED
- `[grep] {"pattern": "laguna", "glob_filter": "app/models.py"}` → совпадения из ТРЁХ файлов,
  включая `.hidden` и `app/sub/deep.py`. Контроль `grep -rn 'laguna' --include='*.py' .`
  → только `.py`. То есть хуже, чем пустой ответ: агент верит, что фильтр применён.
- Причина: `glob_filter` используется только в rg-ветке (tools.py:242–243).

### D3 — grep: ошибка выполнения неотличима от «нет совпадений»; stderr выбрасывается — CONFIRMED
- `[grep] {"pattern": "-laguna"}` → `(no matches)`. Реально grep упал с rc=2
  (неверная опция), stderr с текстом ошибки выброшен (capture_output, читается только stdout).
- Паттерн `--`: getopt съедает его как конец опций, `.` становится паттерном «любой символ»,
  а GNU grep с `-r` и без файловых операндов ищет по cwd → выдача затоплена всем подряд
  (замер V1, включая сырой `grep -rn -- . </dev/null` — то же). Ни `-e`, ни `--` перед
  паттерном не ставится (обе ветки). (Правка после ревью: и моя исходная формулировка
  «ищет пустую строку», и версия ревьюера «читает унаследованный stdin» опровергнуты
  замером V1/V1b — реальный симптом другой, дефект тот же: argv без защиты паттерна.)
- Цена выброшенного stderr измерена отдельно: grep по дереву с latin-1 файлом пишет
  `grep: ./latin.txt: binary file matches` в STDERR при rc=0 — совпадение в этом файле
  МОЛЧА ИСЧЕЗАЕТ из выдачи тула (замер V2: 3 файла в ответе, 4-й с реальным совпадением — нет).
  Ревьюерская гипотеза о UnicodeDecodeError-крэше на этой машине опровергнута: stdout остаётся
  валидным UTF-8, но совпадение теряется — та же ложь «совпадений нет», другой механизм.

### D4 — read: валидный UTF-8 файл объявляется бинарным — CONFIRMED
- Фикстура: 262143 × `a` + один `х` (2 байта, итого 262145 байт — валидный UTF-8 текст).
- `[read] split.md` → `[binary file, 262145 bytes — not shown]`; bash-контроль
  `python3 -c open().read()` → текст читается.
- Причина: `raw = p.read_bytes()[:262144]` режет многобайтный символ пополам →
  UnicodeDecodeError → ветка «binary». Ложь в худшую сторону: большой файл «не показан».

### D5 — read: смещение за концом файла отвечает «(empty)» — CONFIRMED
- Файл 5 строк; `[read] offset=100` → `(empty)`. Файл НЕ пуст — агент может прочитать это
  как «файл пустой». Должно быть явное «offset за EOF (в файле N строк)».

### D7 — read: offset 0-based при метках строк 1-based — молчаливая потеря строки (по ревью, подтверждено замером) — CONFIRMED
- Метки в выдаче `i+1` (1-based), а срез `start = int(offset)` (0-based): `offset=5` начинает
  со строки С МЕТКОЙ 6; запрос «с 5-й строки» молча пропускает строку 5.
- Замер V5: файл 5 строк, `[read] offset=5` → `(empty)` — запрошенная «строка 5» не показана
  вовсе. Ни схема, ни docstring базу offset не называют.

### D8 — write/edit затирают права файла до 0600 (по ревью, подтверждено замером) — CONFIRMED
- Замер V3: `chmod 755 t.py` → edit → режим файла стал `0o600`. Причина:
  `tempfile.mkstemp()` создаёт temp 0600 и `os.replace()` делает его inode финальным.
- В проде с ORCHESTRA_AGENT_UID bash работает под другим юзером → файл после write/edit
  для bash нечитаем («wrote x.sh» → следующий bash-вызов: Permission denied).

### D9 — read блокируется навечно на FIFO/спецфайле без таймаута (по ревью, подтверждено) — CONFIRMED
- Замер V4: `read("pipe")` на mkfifo не вернулся за 1 с (контроль завершён), вернулся только
  после записи в FIFO извне. `open()` блокирующий, таймаутов нет; достижимо из read-only
  ревьюера → морозит цикл (в связке с D6 — весь сервер).

### D10 — read читает ВЕСЬ файл в память до срезa (по ревью, код) — CONFIRMED по коду
- `p.read_bytes()[:READ_MAX_BYTES]` (tools.py:144): многогигабайтный файл = всплеск RSS на
  полный размер + блокирующее чтение на цикле (см. D6). Плюс тот же путь МОЛЧА обрезает
  текстовые файлы >256 КиБ без пометки об усечении (в отличие от `_cap`, который помечает).

### D6 — dispatch блокирует event loop сервера на время синхронных операций — CONFIRMED
- Проба: конкурентный `await asyncio.sleep(0.01)` во время синхронного `tools.grep(...)`
  по дереву репозитория длился **2008 мс**; контроль того же вызова через
  `asyncio.to_thread` — **10 мс**. `dispatch()` зовёт синхронные `grep/glob/read/write/edit`
  напрямую из `async` (tools.py:323–341), loop.py:247 ждёт их на боевом цикле → любой grep
  морозает ВСЕ сессии сервера до 30 c (таймаут subprocess.run).

## Находки — РАБОТАЕТ, НО ВЫНУЖДАЕТ ЛИШНИЕ ХОДЫ (цена хода)

### C1 — glob не рекурсивен по умолчанию — CONFIRMED замером
- `[glob] "*.py"` при файлах в `app/` и `app/sub/` → `(no matches)`; работает только
  `**/*.py`. Glob Клода Матчес рекурсивен; здесь агент должен знать разницу `*`/`**`,
  иначе получает ложное «нет файлов» (та же сторона лжи «проблемы нет») и второй ход.

### C2 — grep не отдаёт контекст (-A/-B/-C) — по схеме
- Схема (tools.py:283–284) принимает только `pattern` и `glob_filter`. Совпадение без контекста
  → агент идёт в `bash`+`sed` или `read` с offset — минимум один лишний ход на каждое найденное.
- Там же: `limit` есть в сигнатуре (по умолчанию 200), но в схему не вынесен — модель не может им управлять.

### C3 — edit отчитывается числом символов, а не фактом замены — CONFIRMED
- Успешный edit → `wrote t.py (6 chars)`: сколько вхождений заменено, не сказано (при
  replace_all это существенно). Мелочь, но обратная связь слабее возможной.

### C4 — glob не показывает каталоги
- `[glob] "app/*"` → только файлы, каталог `app/sub` невидим. Обходной путь — bash `ls`:
  лишний ход при исследовании незнакомого дерева.

### C5 — glob: `limit` в сигнатуре, но не в схеме (по ревью)
- Аналогично C2 для grep: модель не может управлять уже существующим параметром.

## Находки — РАБОТАЕТ КАК НАДО (проверено, не трогать)

- **bash**: exit_code всегда в ответе; stderr слит со stdout (последовательно);
  таймаут убивает ВСЮ группу процессов — проверено: `sleep 30 & sleep 60` с timeout=2
  умер в 2.0s wall, осиротевших `sleep` нет (первый pgrep-«выживший» — совпадение с
  cmdline самой проверки, ps это опроверг).
- **write**: атомарная запись (temp+rename), вложенные каталоги создаются
  (`new/dir/x.py` → ok), синтаксис-гард .py отклоняет битый синтаксис до записи.
- **edit**: неуникальный old → громкая ошибка с числом вхождений; отсутствие old → ошибка.
- **glob**: обход рабочего пространства корректен (абсолютный путь и `..` отклонены),
  симлинк-эскейп фильтруется.
- **grep** (то, что есть): скрытые файлы ищутся (`.hidden` найден), вывод `файл:строка:текст`.

## Аддендум (по заданию оркестратора): потолок MAX_TOOL_ROUNDS — что сторожит и каким быть

### Замер: сколько раундов реально жрут ходы харнес-воркеров
Источник: `data/orchestra.db`, logs всех 5 сессий с `backend_type='harness'` (22.08),
граница хода = user_message; прокси раундов = число tool_result в ходе (нижняя оценка:
раунд может пакетить несколько вызовов). В turn_usage харнес-ходов нет (runtime='harness'
туда не пишется) — считал по logs.

| сессия | ход | tool_result |
|---|---|---|
| feat-harness-bubbles (#369) | 1 | **51 → ОБОРВАЛСЯ по max_turns** |
| feat-or-quota (#368) | 2 | 36 |
| harness-tools (#367, я) | 1 / 2 | 28 / 19 |
| feat-model-catalog (#366) | 1 / 3 | 27 / 7 |
| feat-or-quota | 1 | 17 |
| feat-harness-bubbles | 2 | 14 |
| ox-probe | 1 | 9 |

n=9 ходов, медиана ~19, хвост ЦЕНЗУРИРОВАН потолком: единственный выброс доказывает
потребность >50 раундов на живой задаче в первый же день.

### Что потолок реально сторожит
- Зацикливание — да, но зацикливание видно и по стоимости.
- Суточная квота OpenRouter free (1000 req/сутки на аккаунт, 20/мин) — только ЧАСТИЧНО:
  худший случай хода = max_rounds HTTP-запросов. При 50 это ≤5% суточной квоты на ход;
  но предохранителем от выжигания суток он не является ни при каком значении: 4 воркера ×
  спокойные 20-раундовые ходы съедают 1000 запросов за ~12 ходов на всех. Настоящий
  предохранитель квоты — дневной счётчик запросов, его в цикле НЕТ (пробел, вне #367).
  llm.py ретраит 429 только до первого байта стрима (llm.py:167–200) — упёршись в 20/мин,
  ход замедлится, но не остановится.
- Контекст НЕ является ограничителем раньше раундов: статус оборванного хода #369 показал
  ctx:6% после 51 раунда (~60k токенов истории). Экстраполяция ≈ линейно: 200 раундов ≈
  240k токенов << guard 0.85×1M=850k. Для моделей с 1M-контекстом раунды бьют первыми
  всегда; `_fit_context` трепает середину истории задолго до context_limit — деградация
  качества наступает раньше любого капа и ничем не помечена.

### Решение
1. **MAX_TOOL_ROUNDS 50 → 200** (якорь — измеренный потолок claude-бэкенда,
   app/backend_claude.py:919; наблюдённая потребность >50 при n=9 не даёт собственной
   статистики хвоста).
2. **Мягкое закругление вместо обезглавливания**: за N=10 раундов до конца в историю
   дописывается системная подсказка «осталось N раундов — закругляйся, отчитайся» (+event
   в чат), повтор за 3. Терминал max_turns остаётся ok=False, но теперь наступает только
   после двух явных предупреждений — «внезапная смерть» становится исключением, а не нормой.
   Это ценнее самого числа: обрыв #369 потерял не работу (диск цела), а ОТЧЁТ.
3. REVIEW_MAX_ROUNDS=15 не трогаю: ревьюер сфокусирован и однозадачен, данных о его
   переполнении нет.

### Чем выбор плох (обязательная честность)
- **200 — паритетный якорь, не вывод из распределения**: мой замер n=9 с одним
  цензурированным хвостом. Если реальным задачам нужно >200 — увидим тот же обрыв снова,
  но уже с предупреждениями в истории и точным счётом раундов в статусе.
- **Худший случай хода при 200 = 20% суточной квоты аккаунта и ≥10 минут стены на 20/мин** —
  предохранительная функция потолка относительно квоты слабеет вчетверо. Компенсация —
  отдельный механизм (дневной счётчик), который надо заводить задачей вне #367.
- Длинные ходы тихо деградируют качеством через усечение середины истории (_fit_context)
  задолго до любого капа — ни один из лимитеров этого не помечает.
