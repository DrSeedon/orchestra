# #82 — живой прогон переименования (состояние ДО правок)

Одноразовый воркер `rn-probe` (Haiku), спавн в `/home/kesha/orchestra`, сессия
`7637a332-1b4f-4b84-b976-ff8f5a1922d2`. Сервер на момент прогона — `main` после рестарта
17:12, то есть БЕЗ правок #82: это и есть нужное «до».

## Протокол

1. Спавн `rn-probe`, дождались `готов`.
2. Создан bg-джоб `bg-cf85f52525` (timer, 120 с) на `target_name=rn-probe`,
   `target_session_id=7637a332-…` — то есть id в строке был с самого начала.
3. Переименование: `POST /api/sessions/rn-probe/rename {"new_name":"rn-probe-2"}` → `200`.
4. Воркеру (уже `rn-probe-2`) послан приказ вызвать `update_progress`, `bg_create` без
   `target` и `list_agents`.
5. Дождались срабатывания таймера.

## Сырые наблюдения

**Переименование прошло, ветка переименована, каталог worktree — нет:**
```
{"ok":true,"old_name":"rn-probe","new_name":"rn-probe-2","branch":"feat/home-kesha-orchestra/rn-probe-2"}

name        branch                              worktree_path
rn-probe-2  feat/home-kesha-orchestra/rn-probe-2  /home/kesha/orchestra/worktrees/home-kesha-orchestra/rn-probe
```
Подтверждает F7 исследования: путь остаётся старым. Ничего не сломалось — путь читается из
строки БД и нигде не вычисляется из имени заново.

**Тихий отказ №1 — живой MCP-подпроцесс представляется СТАРЫМ именем:**
```
INFO: 127.0.0.1:38702 - "POST /api/sessions/rn-probe-2/send HTTP/1.1" 200 OK
INFO: 127.0.0.1:53598 - "POST /api/sessions/rn-probe/progress HTTP/1.1" 404 Not Found
```
Сообщение доставлено уже по НОВОМУ имени (первая строка), а тул того же агента ушёл по
СТАРОМУ (вторая) — ровно потому, что `WORKER_NAME` заморожен в env подпроцесса.

**Тихий отказ №2 — пробуждение не пришло, след только в журнале:**
```
bg_job created: bg-cf85f52525 type=timer target=rn-probe
bg_job bg-cf85f52525: target rn-probe not found

id             target_name  status  error
bg-cf85f52525  rn-probe     failed  target session not found
```
Воркер всё это время был жив и idle; `target_session_id` в строке джоба указывал прямо на
него и не использовался. Наружу не ушло ничего: агент, закончивший ход в ожидании
пробуждения, ждал бы вечно.

**Громкая половина — дословный вывод тулов самого переименованного агента:**
```
1. update_progress: `http_4xx: not found`
2. bg_create:       `http_4xx: session 'rn-probe' not found in scope`
3. list_agents:     `🟢 ⚙️ **rn-probe-2** | running | claude-haik…`
```
Вторая строка — буквально симптом воркера `accountant` из чужого контура. Третья важна
отдельно: СПИСОК агентов сервер отдаёт правильный, устаревшая только собственная
идентичность процесса — поэтому со стороны выглядит, будто «агент есть, а его тулы врут».

## Что этим доказано и что нет

- **Доказано вживую:** механизм (env заморожен), оба тихих отказа, поведение worktree.
- **НЕ доказано вживую:** что правки #82 их чинят. Правки лежат в ветке
  `adhoc-1785838510-9/feat-instant` и не в памяти сервера: `app/bg_jobs.py`,
  `app/manager.py`, `app/routes/` живут в процессе systemd до рестарта. Половина «после»
  проверяется тестами (мутация: T1 4/4, T2 5/5, T3 6/6 краснеют на коде «до») и повторяется
  этим же протоколом ПОСЛЕ мержа и рестарта — шаги 1-5 воспроизводимы дословно.
