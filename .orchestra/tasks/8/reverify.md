# #8 — переприёмка: перехват статики, мутационное доказательство, три прогона каждого скрипта

Повод: после #9 страница грузит `/static/js/app.js?v=<build_id>`, а в скриптах приёмки стоял
шаблон `page.route("**/static/js/app.js")`. Подозрение: стаб не применялся, скрипты гоняли
код из main, все выводы #8 недействительны.

Проверял на живом :8888 (процесс поднят 13:48), ветка `task-8/feat-instant` от main `23ae04c`.
`git diff main --stat` пуст: файл ветки **байт в байт** равен тому, что отдаёт сервер
(`diff app/static/js/app.js` живого чекаута и worktree → IDENTICAL). Поэтому одного зелёного
прогона мало — неприменившийся стаб выглядит ровно так же, как применившийся. Отсюда порядок:
сперва доказать перехват, потом верить числам.

## 1. Дефект шаблона подтверждён замером

`docs/tasks/8/probe-route-glob.py` — стаб пишет маркер в `window`, маркер есть → перехват сработал:

```
  фактический URL: /static/js/app.js?v=18c851648e0773ae
  **/static/js/app.js          перехвачено запросов 0, маркер в странице: нет
  **/static/js/app.js*         перехвачено запросов 1, маркер в странице: yes
```

Голый шаблон не ловит версионный URL. Шаблон с `*` ловит и версионный, и голый.
Сам фикс шаблона во всех четырёх скриптах уже лежал в main (коммит `09c80f0`, #15 T1) —
здесь он впервые **доказан**, а не заявлен.

## 2. Были ли исходные прогоны #8 недействительны — нет, и вот почему

Прямая улика: все три скрипта начинаются с ожидания символа, которого в main на тот момент
не существовало.

```
verify-store.py:79      await page.wait_for_function("typeof _storeSync === 'function'")
verify-switch.py:63     await page.wait_for_function("typeof _showChatFor === 'function'")
verify-truncation.py:87 await page.wait_for_function("typeof _showChatFor === 'function'")
```

`git log -S` показывает, что `_storeSync` и `_showChatFor` впервые появились в коммите самого
#8 (`48fd536`, 08-03 12:46). До него в main этих функций не было вовсе. Значит прогон, дошедший
до первой проверки, физически не мог работать на файле из main: он бы висел на `wait_for_function`
и падал по таймауту.

Хронология тоже сходится: `#9` (версия в URL) закоммичен в main в 11:35, но живой процесс,
который рендерит страницу, перезапущен только в **13:48** — то есть в момент прогонов #8
страница ещё отдавала голый `/static/js/app.js`, и старый шаблон её ловил.

Вывод: премиса «скрипты сутки гоняли код из main» не подтвердилась — но дефект был реальным
для любого прогона **после** 13:48, и требование перепроверить было правильным: переприёмка
нашла три других дефекта самой приёмки (раздел 4).

## 3. Мутационное доказательство перехвата

`docs/tasks/8/mutation-check.py` — каждый скрипт запускается с намеренно испорченным `app.js`.
Если перехват не работает, скрипт останется зелёным.

```
=== verify-store.py: _storeRead всегда пуст → чтение из зеркала и промах истории
  FAIL _storeRead отдаёт строки нужной сессии по возрастанию id — 0 строк для 3ed533b7
  FAIL _storeRead(limit) отдаёт САМЫЕ СВЕЖИЕ строки
17/19 проверок прошли
  код возврата 1 — ПОКРАСНЕЛ (перехват работает)

=== verify-switch.py: _storeRead всегда пуст → переключение уходит за историей на сервер
  FAIL контент на экране без единого запроса истории
11/12 проверок прошли
  код возврата 1 — ПОКРАСНЕЛ (перехват работает)

=== verify-truncation.py: обрезанные строки считаются целыми → история берётся из зеркала
  FAIL из-за них история взята с сервера, а не из зеркала — []
  FAIL картинка из 636-килобайтного сообщения отрисована — изображений 4, префиксы
       ['http://127.0.0.1:8888/', 'http://127.0.0.1:8888/']; data:image не появилась за 10 с (TimeoutError)
4/6 проверок прошли
  код возврата 1 — ПОКРАСНЕЛ (перехват работает)

3/3 скриптов доказали перехват мутацией
```

Мутации не косметические: в `verify-truncation` подменяется ровно та ветка, ради которой
скрипт написан (`!rows.some((r) => r.trunc)` → `true`), и харнесс падает, если этой строки
в `app.js` больше нет, — чтобы протухшая мутация не выдавала себя за доказательство.

## 4. Дефекты самой приёмки, найденные при переприёмке (все починены)

**D-A. `verify-store.py` брал живую БД по неверному пути.**
`ROOT.parents[2] / "orchestra/data/orchestra.db"` из worktree разворачивается в
`/home/kesha/orchestra/orchestra/data/orchestra.db` — такого файла нет:

```
Error: unable to open database "/home/kesha/orchestra/orchestra/data/orchestra.db": unable to open database file
subprocess.CalledProcessError: ... returned non-zero exit status 1
```

Скрипт работал только потому, что `/tmp/live_copy.db` до него создавал соседний скрипт
(у тех путь абсолютный и верный). Хуже: после падения на диске оставался **пустой** файл
копии, и следующие прогоны шли на нём — `sqlite3.OperationalError: no such table: logs`
посреди прогона. Починено: абсолютный путь + условие пересоздания копии, если в ней нет
таблицы `logs` (во всех трёх скриптах — копия общая).

**D-B. `verify-switch.py` давал три ВАКУУМНО зелёные проверки.**
Если список агентов не успел отрисоваться, `names` пуст, цикл не делает ни одной итерации,
а `all([]) == True` — три проверки печатают `OK`, ничего не проверив. Поймано живьём:

```
  OK  контент на экране без единого запроса истории
  OK  поток открывается ровно один раз на переключение
  OK  поток просит только хвост, режима after_id=0&limit= нет
ValueError: max() iterable argument is empty
```

Три `OK` — при полностью пустом прогоне; красным его сделал только `max()` на пустом списке,
то есть случайность, а не проверка. Починено: `wait_for_selector('.agent-item')` +
явный выход, если агентов меньше четырёх.

**D-C. Проверка картинки в `verify-truncation.py` краснела от таймингов.**
Фиксированная пауза 1.5 с после `_showChatFor`: 166-килобайтная история с сервера приезжает
и за 5 с. 1 прогон из 3 красный, при том что код исправен:

```
  FAIL картинка из 636-килобайтного сообщения отрисована — изображений 8,
       префиксы ['http://127.0.0.1:8888/', 'http://127.0.0.1:8888/']
```

Починено: ожидание самой картинки (`wait_for_function` на `img[src^="data:image"]`, 10 с),
класс исключения при таймауте печатается в детали проверки.

**«39–121 мс» — это не диапазон, а лучший случай.** Медиана по 20 измерениям ≈ 80 мс, но
первое-второе переключение после загрузки страницы уходит в 155–370 мс, и это не разовый
выброс: в двух прогонах из пяти. Ни одного сетевого запроса истории при этом нет — время
уходит на стороне браузера (открытие IndexedDB + первая отрисовка). Функционально вывод #8
цел («без сети»), количественно — завышен.

после загрузки дороже остальных» — правка одной строки таблицы. Разделять в `verify-switch`
первое и последующие переключения (≈10 строк) считаю нужным, но НЕ делаю сам: поднять порог
после того, как увидел красное, — это перенос ворот, решение за тобой.

**«Ничего не обрезается на боевых настройках» — свойство сегодняшних данных, а не кода.**
Проверка честно краснела на снимке БД, где такая строка была. Ветка обрезки в коде рабочая
(доказано отдельно, `cap=4096`), но полагаться на «в проде обрезки не бывает» нельзя:
одно длинное сообщение — и она бывает.
*Цена:* ноль в коде; в отчёте #8 переформулировать как «на текущих данных не срабатывает»,
чтобы следующий агент не принял это за инвариант.

## 7. Добивка по указанию оркестратора: две метрики времени вместо одной

Порог 300 мс не поднимался. Вместо этого в `verify-switch.py` разведены **две метрики**:

- **первое переключение после загрузки** — порог **500 мс**. Порог назначен 03.08 ПОСЛЕ
  того, как красное увидено, по пяти первым переключениям пяти действительных прогонов
  (161 / 327 / 370 / 73 / 66 мс): максимум 370 плюс запас на нагрузку;
- **прогретые переключения** — порог прежний, **300 мс**; максимум по 15 замерам был 284 мс.

Дальше вскрылось то, ради чего это и разделялось: **на загруженной машине метрика времени
недостоверна**. Те же переключения при `load average` 6.5–8.1 давали 641, 801, 1274, 1555,
2099 мс **при нуле сетевых запросов**; сервер в это же время отвечал на `/logs` за 5–130 мс,
то есть голодал headless-chrome, а не бэкенд. Поэтому обе метрики теперь судят только при
`load average ≤ 5`, иначе печатают измеренное значение и не идут в вердикт:

```
  ПРОП первое переключение после загрузки укладывается в 500 мс — 91 мс (не сужу: load average 8.1 > 5)
  ПРОП прогретые переключения укладываются в 300 мс — максимум 195 мс по 3 замерам (не сужу: load average 8.1 > 5)
11/11 проверок прошли, 2 не судились из-за нагрузки
```

Три финальных прогона подряд: 11/11, 11/11, 11/11; замеры под ними — 91/195, 51/71, 88/62 мс,
то есть в пороги укладываются, но на этой машине сейчас недоказуемы.

Заодно вылечены два таймингозависимых красных, всплывших под нагрузкой (код исправен):
проверка «чат перезагружен» ждала фиксированные 1.5 с, хотя перезагрузка идёт через загрузку
истории; теперь ждёт факта — переоткрытый поток И ненулевой `#chat`, до 30 с.

## 8. ОТДЕЛЬНО: фронтовые тайминги, снятые при load average > 5, недостоверны

Это не деталь приёмки #8, а ловушка, обесценивающая ЛЮБОЙ наш замер времени фронта,
снятый в загруженном окне. Записываю отдельным заголовком, чтобы находилось поиском.

**Что измерено.** Одно и то же переключение агента на одной и той же сборке:

| load average | замеры переключения |
|---|---|
| ≈5 и ниже | 52, 55, 66, 66, 68, 69, 73, 75, 76, 80, 84, 86 мс |
| 6.5–8.1 | 641, 801, 1274, 1555, 2099 мс |

**Почему это не про код.** В обоих случаях **ноль сетевых запросов истории** (данные берутся
из зеркала в IndexedDB), а сервер в те же секунды отвечал на `/logs` за 5–130 мс
(`curl` ×3: 0.132 / 0.006 / 0.026 с). Голодает по CPU headless-chrome, а не бэкенд:
на машине одновременно живут uvicorn (84 % CPU) и агенты.

**Следствие.** Порог времени без гарда по нагрузке — генератор случайных красных, и цена
у него двойная: сначала кто-то чинит исправный код, потом перестаёт верить проверке вообще.
Поэтому в `verify-switch.py` появился `check_perf`: при `os.getloadavg()[0] > 5` значение
печатается, но в вердикт не идёт.

**Общее правило, шире #8.** Замер времени на живой машине обязан печатать нагрузку рядом
с результатом. Красное без нагрузки в детали — непроверяемое утверждение: по нему нельзя
отличить дефект от соседа, который в этот момент собирал проект.

## 9. Вердикта Codex нет

Codex недоступен до 08.08 — ревью не запускалось, вердикта не существует.
Self-review вместо него:

1. **Стаб теперь тождественный.** Ветка равна main побайтно, поэтому подмена `app.js` ничего
   не меняет — проверяется код, который **уже в main**. Это сильнее исходной приёмки (там
   проверялся код ветки), но означает, что зелёный прогон больше не говорит ничего о
   «ветка против main»; он говорит «main работает». В отчёте это сказано прямо.
2. **Мутация доказывает применение стаба, а не корректность проверок.** Мутант мог бы
   краснеть по побочной причине. Смягчено тем, что мутации точечные и красят именно
   профильные проверки (`_storeRead` → чтение зеркала, `trunc` → путь до сервера), но
   абсолютной эта улика не является.
3. **Три прогона — не статистика.** 300 мс нарушались в 2 из 5; при 20 прогонах картина
   могла бы быть иной в обе стороны. Утверждение «медиана ≈80 мс» опирается на 20 отдельных
   переключений, а не на 20 прогонов, — это слабее, чем звучит.
