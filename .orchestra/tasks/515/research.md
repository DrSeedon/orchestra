# #515 — почему CI красный и что именно в нём падает

## Вопрос (Step 0)

- **Контекст:** `.github/workflows/ci.yml`, последний шаг `uv run pytest -q --timeout=30`; за всю
  историю workflow успешен 1 прогон из 258.
- **Проверяемое изменение:** разбиение прогона на несколько процессов вместо одного.
- **База сравнения:** прогон `33893200040` — `##[error]Process completed with exit code 137` на 81%,
  60 `F` напечатано до обрыва, итоговой сводки нет вовсе.
- **Измеримый исход:** (1) доходит ли прогон до терминальной сводки; (2) пиковая память группы
  против лимита раннера; (3) полный состав падений по node id; (4) совпадает ли состав собранных
  тестов до и после разбиения.

## Findings

### F1. Одиночный процесс не проходит, шардированный проходит с запасом 53.6–76.1× · CONFIRMED (прямое измерение, тир 1); причина «накопление за прогон» — LIKELY, не CONFIRMED

Живой прогон на ветке: <https://github.com/DrSeedon/orchestra/actions/runs/33956684131>.
Все 6 шардов дошли до терминальной сводки, `RC=137` нет ни в одном.

| шард | CI: пик RSS, КБ | CI: время | локально: пик RSS, КБ | локально: время |
|---|---|---|---|---|
| 0 | 243 008 | 65.0 с | 234 848 | 359.1 с |
| 1 | 250 820 | 53.3 с | 240 972 | 184.7 с |
| 2 | 244 480 | 52.6 с | 233 352 | 158.9 с |
| 3 | 233 800 | 45.2 с | 220 560 | 162.4 с |
| 4 | 291 484 | 105.6 с | 291 440 | 313.7 с |
| 5 | 261 088 | 117.0 с | 242 160 | 283.7 с |

Числа сняты `/usr/bin/time -v` внутри самого шага (`Maximum resident set size (kbytes)`), а не
оценкой. Лимит `ubuntu-latest` для публичного репозитория — **4 CPU / 16 ГБ**
(`.orchestra/tasks/515/raw/github-hosted-runners.html`, таблица «Virtual machine / container»;
для приватных — 2 CPU / 8 ГБ, наш репозиторий `PUBLIC` по `gh repo view --json visibility`).

**Единицы названы явно, иначе запас считается двумя разными числами.** `time -v` печатает KiB
(1024 Б); «16 GB» у GitHub не уточнено. Худший шард 291 484 KiB = 298 479 616 Б, лучший
220 560 KiB = 225 853 440 Б. Отсюда запас **53.6×** при самом консервативном прочтении
(16·10⁹ Б) и **57.6×** при 16 ГиБ; по всем шести шардам **53.6–76.1×**.
Прежняя запись «57×, по диапазону 55–68×» смешивала единицы и НЕВЕРНА (поймано ревью Luna,
раунд 1).

H2 отвергнута прямо этой таблицей: если бы всю память держал один тест, его шард выделялся бы
на порядок, а разброс 1.25× этого не допускает. Но ровный профиль сам по себе НЕ доказывает
именно «накопление за прогон» — он одинаково совместим с постоянной ценой импорта и фикстур в
каждом процессе и с равномерно размазанными тяжёлыми тестами. Что подтверждено этими данными
строго: одиночный процесс не проходит, шардированный проходит, и ни один шард не приближается
к лимиту. Причинную модель «течёт накопление» считать LIKELY, а не CONFIRMED, — её фальсификатор
(профилировать рост RSS внутри одного шарда) не запускался.

### F2. Разбиение не теряет тестов; ровно 2 node id несравнимы по построению · CONFIRMED (прямое измерение)

Базовый `--collect-only` до правки — 3949 node id
(`raw/nodeids-before.txt`, `manifest.json: selected_nodes 3949`).
Объединение `--collect-only` по шести шардам новой раскладки — 3949
(`raw/nodeids-after-shards.txt`). Симметрическая разность — **2 node id**:

```
tests/test_turn_usage.py::test_cached_quota_state_returns_null_without_fresh_data[None-1788589361.5905912]
tests/test_turn_usage.py::test_cached_quota_state_returns_null_without_fresh_data[None-1788598982.427632]
```

Причина — `tests/test_turn_usage.py:104-106`: `time.time()` вычисляется прямо в
`@pytest.mark.parametrize`, поэтому node id содержит момент СБОРА и меняется при каждом запуске.
То есть по этому тесту точное сравнение множеств невозможно в принципе, а не из-за шардирования.
Раскладка проверена отдельно: 42/41/41/41/41/41 файлов, объединение равно всем 247 файлам
`git ls-files 'tests/test_*.py'`, дублей 0.

Второй, независимый признак сохранности состава — арифметика сводок. CI:
`57 failed + 3807 passed + 82 skipped + 3 xfailed = 3949`. Локально:
`33 + 3829 + 84 + 3 = 3949`. Оба равны baseline; `deselected 4` — это `live_probe`,
снятые `addopts = ["-m", "not live_probe"]` (`pyproject.toml:68`).

**A1 (8) — доказательство.** `70547310` (#488) ввёл `_load_review_project_context`
(`app/mcp_stdio.py:3716`), который через `_review_repository_root` (`:3616`) зовёт
`git rev-parse --git-common-dir` в переданном `cwd` и падает `ValueError`, если это не репозиторий.
Заглушку получили ДВА файла из 247 — `rg -l "_load_review_project_context" tests/` даёт
`tests/test_mcp_codex_review.py` (autouse-фикстура `valid_project_context_owner`, строки 27-38) и
`tests/test_project_context_review_488.py`. Прежняя формулировка «единственный файл» НЕВЕРНА и
отозвана (поймано ревью Luna, раунд 1).

Все восемь падений — в файлах БЕЗ этой заглушки, и у всех восьми причина совпадает дословно:
`grep -c "not a git repository"` по строкам этих узлов в `failed-ci-with-reason.txt` даёт **8 из 8**.
Поимённо: `tests/test_mcp_quota_gate.py::test_available_review_starts_job`,
`::test_codex_review_is_blocked_before_the_bg_job`,
`::test_review_fails_open_on_unknown_malformed_or_transport[None|answer0|answer1|answer2|answer4]`
(шесть узлов этого параметризованного теста и ещё один — итого 7 в файле) и
`tests/test_codex_bin_resolution.py::test_resolved_binary_reaches_the_shell_command`.
Все подают `tmp_path`, то есть каталог вне git, и получают
`ValueError: fatal: not a git repository (or any of the parent directories): .git`
(`cwd = '/tmp/pytest-of-runner/pytest-0/test_resolved_binary_reaches_t0'` — дословно из лога).
Это ровно правило `CLAUDE.md` «тест утверждает свойство окружения, которого сам не создал».

**A2 — ПОПРАВКА ПО ХОДУ ПОЧИНКИ: девять падений оказались не девятью причинами, а тремя
плюс утечкой глобального состояния.** Замер 05.09: `test_line_point_is_computed_server_side_for_every_pool`
и `test_gated_and_free_lanes_split_on_the_same_number` в ОДИНОЧКУ зелёные, а в прогоне файла
красные; пара «`test_rule_constants_reflect_environment_overrides`, затем `test_line_point_…`»
воспроизводит это за два теста и даёт `assert 7.5 == 5.5`, где 7.5 = `13 + (2 - 13) * 0.5` —
дословно `QUOTA_TOLERANCE_START_PP=13` и `QUOTA_TOLERANCE_END_PP=2` из соседнего теста.
Причина: откат `importlib.reload(quota_gate)` стоял ПОСЛЕДНЕЙ СТРОКОЙ ТЕЛА теста
(`tests/test_quota_map_api.py:195` до правки), а тест падал раньше неё на устаревшем ожидании —
и оставлял модуль с чужими константами всему процессу. Утечка кросс-файловая: два падения
`tests/test_usage_readiness.py` были тем же следствием и позеленели без единой правки в своём файле.
Итог по A2: **3 устаревших теста** (два про состав `rule`, один про статус выпуска),
**4 сопутствующих** (2 в `test_quota_map_api.py`, 2 в `test_usage_readiness.py`) и
**2 браузерных** с фикстурой, отставшей от контракта сервера. Отсюда общее правило, которого у
меня не было: **откат глобального состояния обязан жить в фикстуре, а не в теле теста — иначе
первое же падение делает красными чужие тесты и множит одну причину на несколько «находок».**

**A2 (9) — доказательство.** `tests/test_quota_map_api.py:167-171` требует, чтобы `payload["rule"]`

**A3 (1) — доказательство.** `app/main.py:323-329`: `_shutdown_runtime` принимает пять

### F5. Три теста #430 заморожены на коммитах, которых в этом репозитории НЕТ · CONFIRMED

`tests/test_orchestra_layout_430.py:374` сверяет
`git rev-parse <location_runtime_commit>^` с `before_ref` из `.orchestra/tasks/430/move-receipt.json`.
Оба SHA не существуют: `git cat-file -t 1f80bb50b81db380fb5f51a0894209538553087f` и
`git cat-file -t 848c8d5146909bd7d70aca9271effad5cc3a3a37` отвечают `ABSENT` при 5792 коммитах в
`--all`. Квитанция заморозила SHA ВЕТКИ воркера, а `merge_worker` мержит squash — эти коммиты в
`main` не попадали никогда. Отсюда `assert 128 == 0` и `fatal: not a tree object`.
Насколько сильно это утверждение — важно, и ревью раунда 1 правильно потребовало его сузить.
Проверено: SHA недостижимы ни из одного ref ЭТОГО репозитория, а refs тут не только свои —
`git for-each-ref` содержит `origin/main` и **407 refs удалённого `laptop`**, то есть обе ветви
контура. Отсюда строгий вывод: **ни один клон `origin` — а CI чекаутит именно его — этих
объектов не получит**, и `fetch-depth: 0` их не воскресит, потому что их нет в репозитории
вообще, а не «не скачаны». Чего проверка НЕ доказывает: что объектов нет ни на одной машине
мира — они могут лежать недостижимыми в чьём-то локальном хранилище до `gc`. Прежняя
формулировка «не может позеленеть ни на одной машине» была шире доказательства и отозвана.
Починка меняет предмет проверки — решение не моё.

### F6. Развилка: 14 тестов требуют проприетарного Codex CLI, которого на раннере быть не может · CONFIRMED по факту, решение за владельцем

2. **Пометить `live_probe`** — механизм в проекте уже есть и уже исключает 3 пробы

3. **Ставить Codex CLI на раннер** — отклонено: бинарь проприетарный, а `auth.json` — живые креды

**Перечень НЕ исчерпывающий** — ревью раунда 1 назвало ещё четыре ветки, и они не проверены:
fake-runner через инъекцию зависимости вместо стаба на диске; capability-based пропуск ровно

integration-workflow. Ни одна из них не отвергнута — просто не измерена.

Рекомендация (13 → ветка 1, `test_t4_...` → ветка 2) поэтому предварительна: контракт каждого
из 14 тестов по отдельности не разобран, разобрана причина их падения. Это архитектурное
решение, выношу его, а не исполняю.

## Counter-evidence

- **Против «шардирование и есть решение»:** оно не чинит ни одного падения — до правки состав
  падений вообще не был известен, теперь их 57. Утверждение F1 узкое: прогон стал ДОХОДИТЬ до
  конца. Зелёным CI делает работа по F4, а не F1.
- **Против «локальный прогон = CI»:** 27 из 57 падений на VPS не воспроизводятся, и 3 падения
  VPS не воспроизводятся на CI. Любой вывод «починил, локально зелено» про CI ничего не значит;
  приёмка — только живой прогон.
- **Против моей же группы D:** 19 падений я НЕ диагностировал, а лишь отделил. Называть их
  «код неверен» сейчас нельзя — из них 10 существуют только на раннере, и такой перекос обычно
  означает окружение, а не дефект. Это гипотеза, а не находка.
- **Против групп B1 и B2 нет положительного контроля.** «Нет `main` → `git show main:…` падает»

  `test_ffprobe_reads_actual_audio_duration`. До такого прогона B1/B2 — гипотезы с высоким
  правдоподобием, не находки.
- **Против выбора «6 шардов»:** число взято от прошлого протокола (#430), а не измерено.
  При 4 CPU у раннера 6 параллельных джобов всё равно исполняются на 6 РАЗНЫХ машинах, поэтому
  CPU не ограничение; но если шардов станет мало, самый длинный шард (117 с) вырастет линейно.
