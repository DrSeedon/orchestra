## Чем сделан выполнимым прогон

`.github/workflows/ci.yml` — матрица из 6 шардов, round-robin по `git ls-files 'tests/test_*.py' | sort`.
Обоснование числом, снятым `/usr/bin/time -v` внутри самого шага: пиковый RSS шарда
**233 008–291 484 KiB** против лимита `ubuntu-latest` 16 ГБ (публичный репозиторий, 4 CPU).
Единицы названы явно: худший шард 298 479 616 Б, отсюда запас **53.6×** при консервативном
прочтении «16 GB» как 16·10⁹ Б и **57.6×** при 16 ГиБ; по всем шардам 53.6–76.1×.

Две правки, которых в задании не было и которые оказались важнее ещё одного починенного теста:
- `timeout-minutes: 20` — зависание обязано становиться ПАДЕНИЕМ, а не бесконечным прогоном;
- `-v` с `PYTHONUNBUFFERED=1` — при `-q` буфер не сбрасывается, и в логе зависшего шарда
  оставался только процент без имени теста.

## B1 — доказан ОБОИМИ плечами

Утверждение: `fetch-depth: 0` нужен по существу, а не для красоты.

- **Положительное плечо.** `test_t3_repository_move_has_content_receipt_and_no_old_roots`
  выводит якорь переезда из истории (`git log <mainline> --diff-filter=A`) и на CI
  **PASSED** (прогон `34124017376`).
- **Отрицательное плечо.** В клоне `--depth 1` тот же якорь «разрешается», но указывает на
  ВЕРХУШКУ (в клоне один коммит, он добавляет все файлы), а его родителя нет:
  `fatal: Not a valid object name 7e9ad9dd…^`. То есть на дефолтном чекауте тест пройти не может.

**Отдельная находка, из-за которой B1 не доказывался несколько прогонов подряд:**
`actions/checkout` НЕ создаёт локальную ветку mainline даже при `fetch-depth: 0` — история
скачана целиком, но `main` существует только как `origin/main`, и `git log main` отвечает
`fatal: bad revision 'main'`. Лечится разрешением ссылки (`_mainline_ref`), а не глубиной.

## Дефекты `app/`, найденные по дороге

1. **`app/routes/sessions.py`: выключенная авторизация выдавала чужую личность.**
   `operator = not is_auth_enabled() or <кука>` делал человеком ЛЮБОГО безымянного вызывающего
   на контуре без `DASHBOARD_USER` — штатном пути из README. Починено: человеком остаётся
   только предъявивший куку; доставка не отвергается, теряется лишь ложное авторство.
   Мутация: возврат `not is_auth_enabled()` → красный, откат → 12 passed.
2. **`app/session.py`: отказ по оседающему ходу терял `error_code`**, хотя соседний отказ того
   же блока его несёт. Починено одной строкой, RED-оракул закоммичен отдельно.
3. **Гейт незавершённых эффектов ОБХОДИТСЯ на пути codex → claude.** Проба при заблокированном
   гейте: внутри рантайма `ok=True` (гейт не спрошен — так и задумано, переносить нечего),
   claude → codex `ok=False, handoff_pending_effect` (защита работает), **codex → claude
   `ok=True`, гейт не спрошен ни разу** — при том, что этот путь рвёт живой тред через
   `_disconnect_backend()`. Структурно: в `_change_codex_to_claude_text_tail_locked` (105 строк)
   и `_build_runtime_handoff` (53 строки) ноль упоминаний гейта. Не чинил — вынесено владельцу.

## Браузерные тесты вне блокирующего гейта

Решение владельца 07.09 «выносим их из гейта, не убиваем». Отличие — маркер `browser`,
который ставится ПО ФАКТУ запроса браузерной фикстуры (`tests/conftest.py`), а не списком
файлов: список устаревает молча. Гейт снимает их выражением
`-m "not live_probe and not browser"`; в CI они гоняются отдельной джобой с
`continue-on-error`. Состав закреплён `test_browser_inventory_is_explicit` раскладкой ПО
ФАЙЛАМ: **167 узлов из 4091**, в блокирующем наборе остаётся 3924.
Имя фикстуры `context` в набор не входит намеренно — слишком общее, оно уносило из
блокирующего набора два НЕбраузерных узла.

## Что осталось красным и почему это не наша работа

15 падений блокирующего набора. Проверено подменой: `test_merge_ref_gate`,
`test_message_provenance_review_433`, `test_review_receipt_migration_436` и
`test_search_deadline` ×3 падают одинаково с моими production-файлами и с версиями main.
`test_audit0901_session` ×2, `test_orphan_pid_identity` ×2, `test_runtime_handoff_v2` ×4 и
`test_mcp_stdio` — CI-only ещё до этой задачи либо приехали со свежим main.

Браузерная джоба зависает (~7 минут тишины при живом `chrome-headless-shell`), и зависание
КОЧУЕТ между тестами: три прогона — три разных теста, идущих через три разных стенда. Это
неустойчивость общей браузерной фикстуры, а не дефект одного теста; отдельная цель, владельцем
не открытая.

## Пре-мортем: что ломается у следующего потребителя

1. **Мерж без рестарта.** `app/routes/sessions.py` и `app/session.py` — Python, он не
   перечитывается сам. До рестарта правка провенанса не действует, и наблюдатель увидит
   старое поведение при новом коде.
2. **Новый браузерный тест уедет из-под гейта молча** — против этого стоит
   `test_browser_inventory_is_explicit`: раскладка по файлам разойдётся и тест назовёт файл.
3. **Кто-то снимет `fetch-depth: 0`** как «лишнее» — против этого стоит T3: он краснеет на
   мелком чекауте, и отрицательное плечо записано выше.
4. **Тест снова начнёт звать `git log main`** на CI — против этого `_mainline_ref` с явным
   отказом, называющим причину.
5. **Провенанс `unknown` доедет до потребителя, ветвящегося по `origin == "user"`.** Проверено
   ревьюером отдельно; в блокирующем наборе таких потребителей не нашлось.
