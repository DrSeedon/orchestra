# #151 — нативные скиллы Codex вместо нашего оглавления

## Question

- **Context** — `_codex_factory` (`app/runtime_registry.py:188`) на каждом коннекте зовёт
  `build_codex_skills_index` (`app/prompting.py:278`) и дописывает сгенерированное оглавление
  в `system_prompt`. Тело скилла агент читает сам по абсолютному пути.
- **Change under test** — заменить наш механизм на нативный: класть скиллы папками в
  `<worktree>/.codex/skills/<name>/SKILL.md`.
- **Baseline** — текущее оглавление в промпте (работает, не протухает после #149).
- **Outcome (измеримый)** — видит ли CLI 0.145.0 проектный `.codex/skills/` из рабочего
  каталога агента, и виден ли наш реальный pipeline-скилл живому воркеру нативно.

**Gate задачи:** не читает проектный каталог → закрываем отрицательным результатом.

## Hypotheses considered

- **H1: 0.145.0 читает только `$CODEX_HOME/skills` (глобальный).** Falsifier: положить скилл
  в `<proj>/.codex/skills/` и увидеть его в модель-видимом промпте. → **REFUTED** (F2).
- **H2: читает проектный каталог относительно cwd.** Falsifier: тот же скилл виден из
  постороннего каталога (значит, дело не в cwd). → **CONFIRMED** (F2, F3).
- **H3: нативный механизм ломает глобальные скиллы юзера (`pdf`, `deepgram-transcribe`).**
  Falsifier: после инъекции глобальные исчезают из списка. → **REFUTED** (F5).
- **H4: папочная доставка нужна прямо сейчас.** Falsifier: у наших скиллов есть подкаталоги.
  → **REFUTED** (F7) — все пять плоские.

## Findings

### F1 — нативный механизм существует и стабилен, справка врёт — CONFIRMED
`codex --help` скиллов не упоминает (подтверждаю наблюдение оркестратора), но:
```
codex features list | grep skill
skill_env_var_dependency_prompt   removed            false
skill_mcp_dependency_install      stable             true
skill_search                      stable             true
```
Два флага в статусе **stable**. Плюс в модель-видимом промпте есть штатный блок
`<skills_instructions>` с форматом source-локаторов (`file:`, `environment resource`,
`orchestrator resource`, `custom resource`). Это не обходной путь, а первоклассный механизм.
Урок оркестратора подтверждён и расширен: `--help` не покрывает `features list`.

### F2 — РЕШАЮЩЕЕ: проектный `.codex/skills/` читается — CONFIRMED (Tier 1, прямой замер)
Инструмент: `codex debug prompt-input` — рендерит модель-видимый промпт **локально, без
обращения к API**. Это оказалось критично: квота Codex исчерпана до 8 августа, и
`codex exec` падает на `You've hit your usage limit`, то есть поведенческий тест через
живой ответ модели был недоступен. Discovery происходит до вызова модели, поэтому
`prompt-input` доказывает ровно то, что нужно.

Проба: `/mnt/data/151-probe/proj/.codex/skills/orch-probe-skill/SKILL.md`.
```
из /mnt/data/151-probe/proj      → orch-probe-skill найден:  1
(file: /mnt/data/151-probe/proj/.codex/skills/orch-probe-skill/SKILL.md)
```
**Отрицательный контроль** (тот же бинарник, другой cwd):
```
из /tmp                          → 0
из /mnt/data/151-probe/other     → 0
```
**Вложенность:** из `<proj>/sub/deep` → 1 (обход вверх от cwd, как `.git`).

Ответ на gate: **читает**. Задача не закрывается отрицательным результатом.

### F4 — `.claude/skills/` для Codex НЕВИДИМ — CONFIRMED
В той же воркте лежат три копии из #149 (`codex-debate`, `html-artifacts`, `self-analysis`),
и нативный список не показывает **ни одной**. То есть доставка #149 работает только на Claude,
а Codex сейчас держится исключительно на нашем оглавлении. Это подтверждает F6 из #149
(«Claude читает КОПИЮ, Codex — ОРИГИНАЛ») и объясняет, почему подкаталоги не переносятся.

### F5 — глобальные скиллы юзера НЕ ломаются — CONFIRMED
После инъекции в воркти:
```
pdf                  → 1   (/home/maxim/.codex/skills/pdf/SKILL.md)
deepgram-transcribe  → 1
наш codex-debate     → 1
всего локаторов      → 25
```
Источники суммируются, а не замещаются. Требование «не ломать чужое» выполнимо.

**Обнаружен третий корень, которого не было в постановке:** `~/.agents/skills/` — 17 скиллов
юзера (`accounting`, `orchestra`, `review`, `webapp-testing`, …). Он тоже попадает в
нативный список. При выборе имён для инъекции считаться надо с ТРЕМЯ корнями, не с одним.

### F6 — коллизия имён НЕ разрешается, дублируется — CONFIRMED (риск)
Положил локальный скилл с именем `pdf` (занято глобальным). В списке оказались **ОБА**:
```
(file: /home/maxim/.codex/skills/pdf/SKILL.md)
(file: .../sensar-roadmap/.codex/skills/pdf/SKILL.md)
```
и описание локального (`COLLISION-PROBE`) показано наравне. Дедупликации по имени нет →
модель получает две записи с одним именем и разными телами.

Практический риск сейчас нулевой (наши пять имён не пересекаются с 24 чужими), но это
означает: инъекция обязана быть по СПИСКУ РОЛИ, а не «положить всё подряд», иначе однажды
имя совпадёт с пользовательским.

### F7 — мотив «доставить папкой» пока не на чем применить — LIKELY
Все пять наших скиллов — **плоские `.md`-файлы** без подкаталогов
(`ls pipelines/default/prompts/skills/` — 5 файлов, 0 директорий). Папочная структура
(`scripts/`, `agents/`) есть у скиллов ЮЗЕРА (`deepgram-transcribe`), но они и так лежат
глобально и работают. То есть выгода №2 из постановки — задел на будущее, а не текущая
починка. Формат `<name>/SKILL.md` её разблокирует, но сегодня ни один скилл её не требует.

### F8 — нестандартные поля frontmatter не мешают — CONFIRMED
`grill-me` и `orchestra-agents` несут `roles:` и `integrations:`, которых нет в
стандартной схеме. Оба загрузились нативно (по 1 совпадению), ошибок валидации в промпте нет.
Строгая проверка «Unexpected key(s) in SKILL.md frontmatter» в бинарнике относится к
упаковке плагинов (`plugin validation`), а не к discovery. Переписывать frontmatter не нужно.

## Counter-evidence / риски

- **Дублирование, если оставить оба механизма.** Наше оглавление указывает на канонические
  пути `pipelines/.../skills/*.md`, нативный список — на `<wt>/.codex/skills/*/SKILL.md`.
  Включить оба = один скилл дважды под одним именем (та же болезнь, что F6). Значит переход
  обязан быть переключением, а не добавлением.
- **`prompt-input` ≠ живой ответ модели.** Он доказывает, что скилл попал в модель-видимый
  промпт, но не то, что модель им воспользуется. Для discovery этого достаточно (нас
  спрашивали «видит ли»), но полноценная поведенческая проверка «агент применил скилл»
  требует квоты и отложена. Честно: это Tier-1 замер механизма, не Tier-1 замер поведения.
- **Версионная хрупкость.** Всё измерено на `codex-cli 0.145.0`. Проектный каталог не
  документирован в `--help`; в другой версии поведение может отличаться. Это аргумент за
  сохранение `build_codex_skills_index` как fallback, а не за удаление.
- **`.codex/` — новый артефакт в чужом репозитории.** `_WORKTREE_EXCLUDES` содержит
  `.claude/`, но НЕ `.codex/`. Без правки инъекция создаст untracked-мусор в репозиториях,
  где `.codex/` не игнорируется — ровно та проблема, что решалась в #149 для `games`.

## Рекомендация (решение за оркестратором)

**Переходить стоит, но fallback не удалять.** Одной фразой про судьбу
`build_codex_skills_index`: проектный каталог не упомянут в `--help` и проверен ровно на
одной версии CLI, поэтому оглавление остаётся страховкой на случай CLI, где discovery
отсутствует, — но включаться должно ИСКЛЮЧИТЕЛЬНО когда нативный путь недоступен, иначе
получим дубль имён (F6).

Открытый вопрос, который я не решаю сам: определять «нативный путь доступен» по версии CLI
или по факту (проверять наличие блока)? Проверка фактом требует запуска `codex debug` на
коннекте — лишний процесс на каждый спавн. Склоняюсь к простому: инъекция всегда, оглавление
под флагом/версией. Нужно твоё слово.
