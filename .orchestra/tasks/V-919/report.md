# V-919 — рестарт Orchestra без потерь

Цель (владелец 17.10, уточнение 16:17): короткая пауза на время рестарта допустима; после запуска
каждый воркер и оркестратор сам продолжает с того места, где был, без ручного разбора «прервано»,
без потери хода и без дублей фоновых заданий.

## 1. Что реально происходило 17.10 (журнал, только чтение)

Часы сервера — CEST (UTC+2); `journalctl` показывает CEST, БД — UTC.

Вывод по «зависшему graceful shutdown»: в журнале с 01.10 нет ни одного `stop-sigterm timed out` /

«рестарты», что выглядели как добитые systemd, были OOM-убийствами (SIGKILL, без shutdown вообще).
Штатный стоп укладывается в 11 с при `TimeoutStopSec=90s`. Отдельно чинить нечего; OOM — причина,
но она вне этой задачи (записано в TODO).

главного — journal 07:20:52 перечисляет десятки `Unit process … (claude|python|ssh) remains running`.

## 2. Механизмы потерь — по одному, с доказательствами

### M1. Первый ход Claude-агента пропадал целиком (живой пример — сам этот воркер)
Рестарт 09:17 UTC застал в RUNNING 5 агентов (`logs.status = '⏹️ stopped (server shutdown)'`
в 09:17:35): `kesha-tg-bot-orchestrator`, `gamelab`, `research-video-style` — с `session_id`;
`feat-lossless-restart` (я) и `bench-review-big` — **без** `session_id`. После старта
«Resumed …» и «Restart notice injected» получили ровно первые три; два первых хода молча
выпали — 40 % бежавших агентов в этом рестарте. Оркестратор вручную переслал задания обоим
в 09:18:36–37.

Причина в коде: `ClaudeBackend` присваивал `_session_id` только из `ResultMessage` (конец хода),
а `SessionManager.auto_resume_all` выбирал `session_id IS NOT NULL`. При этом транскрипт CLI
уже был на диске: `~/.claude/projects/…feat-lossless-restart/437982fb-….jsonl`, 647 КБ, последняя
запись 09:17:40 UTC — продолжить было из чего, платформа просто не знала id. Codex этим не
страдал: его `thread/started` уже сохранялся рано (`_turn_event_loop`), но только в
нестойком цикле — Claude идёт через `_persistent_event_loop`, где этой проверки не было.

### M2. Родитель получал «Turn failed» за ход, который продолжался сам
`turn_signals.record_interrupted_by_restart` (V-680) писал родителю
`stop_reason=interrupted_by_orchestra_restart … Turn failed before an explicit report` по каждому
оборванному ходу. В 09:18:01 так получил сигнал `seedon-orchestrator` от `gamelab`, а в 09:18:07 —
`Orchestra-orchestrator` от `research-video-style`; при этом оба воркера уже были подняты и через
3–15 с получили уведомление о рестарте. `seedon-orchestrator` ответил `gamelab` разбором
(«я ничего не отклонял… вероятно, команду оборвал рестарт») — ручной разбор, которого быть не должно.

### M3. Фоновые run-задания: INTERRUPTED вместо результата
`BgJobManager.shutdown` убивал процессы run-заданий; при SIGKILL/OOM они выживали
(`KillMode=process`), но их stdout был трубой в умерший процесс, и V-915 (`_reap_orphan_run`)
честно добивал их и слал `[Background job INTERRUPTED] … повторный запуск не выполнялся`.
Агенту приходилось перезапускать работу (в 09:18:01 `bench-evals-pilot` получил результат с
подсказкой «If the f2p.py process died earlier, rerun (resumable)»). Остальные типы (timer, file,
command, ssh, cron, cron_command) уже восстанавливались из БД (`restore_from_db` → `_start_task`
с остатком срока); cron без догоняющих срабатываний — это задокументированный контракт.

### M4. Команды внутри хода
Bash-вызовы самого CLI (не `bg_create`) живут внутри процесса Claude/Codex, который штатный
стоп отключает. При разрешённой владельцем паузе они просто обрываются; агент узнаёт об этом
из уведомления и проверяет результат. Держать CLI живыми через рестарт (fd-store #230,
`FileDescriptorStoreMax=256` уже в юните) владелец сделал необязательным — не трогал.

## 3. Развилки

Настоящей развилки не нашлось, поэтому реализовано сразу:
* для ходов владелец уже выбрал «пауза + автоматическое продолжение» вместо удержания CLI;
* для run-заданий `KillMode=process` уже стоит в юните — процессы и так переживают рестарт;
  не хватало только способа забрать их результат. Перезапуск команды заново отвергнут
  (повторяет побочные эффекты — прямо против требования «без дублей»). Юнит, лимиты и
  отдельный юнит для агентов не понадобились.

## 4. Что сделано

* **M1** — `ClaudeBackend._convert`: `SystemMessage(subtype="init")` отдаёт `session_id` статусным
  событием в начале хода. `AgentSession._handle_event` (общий для обоих циклов) сохраняет любой
  `status` с `session_id` через новый `SessionCost.adopt_session_id`, который сбрасывает базу
  кумулятивной стоимости новой сессии так же, как раньше делал конец хода (иначе ранняя запись
  id «съела» бы сброс и занизила стоимость первого хода — это поймал тест).
  `auto_resume_all` возобновляет и `running`/`interrupted` строки без `session_id`; для них
  `restart_notice_text` кладёт в уведомление сообщения оборванного хода (после последнего
  `turn ended`, не больше 20 000 символов).
* **M2** — сигнал родителю пишется только для хода, который не продолжится: не найден `cwd`,
  упала загрузка, не доставилось уведомление. Продолжившийся ход сам отчитается в конце.
* **M3** — run-задание пишет вывод в `data/bg_runs/<id>.out`, обёртка
  `sh -c 'rc_file=$1; shift; "$@"; rc=$?; … > rc_file; exit $rc'` записывает код в `<id>.rc`.
  `shutdown` такие процессы не трогает, отменённая при выключении задача их не убивает
  (`bg_cancel` и остановка сессии — убивают, как раньше). `restore_from_db` → `_start_task` →
  `_adopt_run`: ждёт лидера по pid + времени старта (зомби = завершён), читает код и вывод,
  доставляет обычным путём (`_finish_run`, общий с `_run_exec`, включая `success_file`),
  а при истечении срока добивает группу (`_reap_orphan_run`). Процесс умер без кода →
  INTERRUPTED, повтор не делается. Строки без `out/rc` (созданы до V-919) — прежний путь V-915.
* Текст уведомления: продолжай задачу с места остановки; фоновые задания продолжают работать.

## 5. Проверка

Тесты (реальные процессы, без боевой БД; `app` импортируется из этого worktree):
* `tests/test_restart_continuation_919.py` — 6 тестов: init-сообщение даёт id; ранний id
  сохраняется и сбрасывает базу стоимости; первый ход без id возобновляется с текстом задания;
  поднятый воркер не шлёт родителю сигнал; неподнятый — шлёт; недоставленное уведомление — шлёт.
* `tests/test_bg_run_adoption_919.py` — 5 тестов: штатный shutdown оставляет процесс живым,
  новое поколение доставляет вывод «до» и «после» рестарта; поколение в отдельном интерпретаторе
  убивается SIGKILL, новое усыновляет задание с кодом 0 и 7; процесс, убитый во время простоя,
  даёт INTERRUPTED без перезапуска; `bg_cancel` по-прежнему убивает.
* Мутации: код `app/` до правки против новых тестов — `logs/mutation-turns.txt` (5 из 6
  красные; зелёный — проверка, что неподнятый воркер по-прежнему сигналит, это охрана от
  перегиба) и `logs/mutation-bg.txt` (3 из 5 красные; зелёные — INTERRUPTED и cancel, охрана
  прежнего поведения).
* Изменённые тесты: `test_seamless_restart.py::test_t3…` — проверка вызова уведомления теперь
  с аргументом строки; `test_bg_jobs.py::test_v915…` — исполняется на строке без `out/rc`,
  то есть на тех, к кому V-915 и относится.
* Прогон 32 связанных файлов — `logs/pytest-targeted.txt`.

## 6. Ограничения и что осталось

* Первый рестарт на этот код выполняет ещё старый `shutdown` — он run-задания убьёт; со
  второго рестарта они переживают. Нужен рестарт сервиса (Python), делает владелец.
* Если процесс уже загрузил новый код, а SIGKILL пришёл до `system/init` (первые секунды хода),
  id нет — ход поднимается с пустым диалогом и текстом сообщений хода (не теряется, но
  промежуточные действия хода агент не видит).
* Bash-команды внутри хода обрываются (M4) — по решению владельца допустимо.
* OOM главного процесса 17.10 (три раза за 26 минут, пик 14 ГБ + 12 ГБ swap) — настоящая причина
  утренних «рестартов»; вне задачи, в TODO.
