# V-976 — OpenRouter vision harness

## Outcome

Catalog image capability now travels from OpenRouter `architecture.input_modalities` through the shared `ModelSpec` into `HarnessBackend.connect()` and `retarget_model()`. On image-capable OpenRouter routes, user messages containing existing Telegram `[photo: path]` or `[file: path | name]` tags are copied at request time to OpenAI-format multipart content: the unchanged original text is first, followed by one `image_url` part per image, each with a validated private `data:<mime>;base64,...` URI. The history object is not mutated, so JSONL persistence, resume, context compaction, user logs and subsequent tool rounds keep the original text tag and never store the base64 payload. Vision routes also offer a read-only `read_image` tool. It uses the existing workspace boundary and returns only a text marker such as `[workspace image: assets/logo.png]`; on the next model request, the marker's tool result stays paired with its assistant tool call, then a request-local user message sends validated image parts. The stored session keeps only the marker and tool result text. Non-vision routes omit `read_image` and pass Telegram messages through untouched.

The official [OpenRouter Image Inputs documentation](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding.md) specifies multipart `messages`, separate content entries for multiple images, recommends text before images, allows base64 data for private/local images, and lists PNG/JPEG/WEBP/GIF. I retrieved the page directly with `curl` on 2026-10-19 after the web tool returned Internal Error. It does not state a cross-model image count or common byte ceiling; provider/model limits vary. This implementation limits inline image bytes to 20 MiB across one request to bound base64 expansion and request memory, and returns an explicit error above that limit.

## Boundaries and failure behavior

Telegram image reads are limited to direct regular files inside the canonical `data/uploads` root. Local `read_image` calls resolve only inside the current workspace `cwd`, under the same boundary used by existing file tools. Traversal/out-of-root paths, missing files, symlinks that resolve outside, non-regular files, oversize images, invalid bytes and unsupported MIME all fail before POST. The file is opened with `O_NOFOLLOW`, checked with `fstat`, and read with a bounded read. Pillow `Image.verify()` validates the bytes and supplies the actual MIME, rather than trusting an extension or tag. A user-supplied marker cannot expand either root.

`finish_reason="length"` now emits a final usage/reasoning event first and then raises a clear truncation error before accumulated tool calls can be emitted. This records reasoning-only truncation (including the supplied 700-token case) without treating it as an empty completion or retrying. An empty response with another finish reason remains the existing distinct empty-completion error. The user-facing message is not claimed to be a successful answer when the provider stopped at the output limit.
