## Дефекты платформы (репорты от других проектов + свои)
- [ ] **Закрытие задачи через `merge_worker` падает `ValueError: <N> not found`, хотя запись существует** (31.08, воспроизведено на #399, #400, #410). Git-часть проходит полностью (main сдвигается, коммиты и тесты на месте), падает только пост-коммитный учёт, операция остаётся `PARTIAL` и держит воркера до ручного `resolve_merge_operation`. При этом номер ПРИСУТСТВУЕТ в `ia_task_projection` (все 274 задачи orchestra на месте), то есть данные целы — ошибается путь поиска задачи при финализации. Следствие: задачу нельзя закрыть штатно, `task_update(status="done")` запрещён платформой, остаётся только `cancelled` с пометкой «ВЫПОЛНЕНО» — статус на доске врёт. Чинить путь финализации; заодно `production_runtime_config().canonical_root` отдаёт `None`, стоит проверить, не отсюда ли растёт.
- [ ] **`merge_worker` рапортует `SUCCEEDED` при мерже ветки В САМУ СЕБЯ и нулевом переносе коммитов** (katya-work, операция `ab606af9`). `commits_merged: 0`, `target_before == target_after`, при этом успех; работы в main нет. Причина цели: после оборванного switch базой осталась адхок-ветка (`_session_base_branch`, `app/routes/sessions.py:113`). Обход: `merge_worker(target="main")`. Приёмка: (1) цель == ветка воркера → отказ; (2) `commits_merged: 0` при неизменной цели не может быть успехом; (3) ложный успех ещё и ТРАТИТ привязку при `task_outcome=complete`. Опаснее прочих: те врали «сломалось, хотя работает», этот — «сделано, хотя работа не приехала».
- [ ] **`switch_worker_branch` не атомарен: ветку переключает, привязку теряет** (katya-work, `russian-soul-luna`). `branch switched, but task assignment failed: KeyError: 'stable_id'` → `task_id=''` + `needs_switch=1`, дальше `merge_worker` отвечает `session has no bound task`, повторный switch привязку не создаёт. Круг замкнут, воркер сам не выйдет. Приёмка: инъекцией исключения в шаг привязки доказать, что сессия не остаётся в тупике.
- [ ] **`DELIVERY_UNKNOWN` во главе FIFO вешает воркера навсегда, штатного выхода нет.** Барьер сознательный (`app/message_deliveries.py:413-423`, #380 R7). Но доставка `c39339bd` встала на 25 часов, три следующих стояли `QUEUED`, отправитель получал бодрый `QUEUED`, воркер выглядел `idle`. Чинить два конца: (1) `send_message` обязан отвечать «очередь заблокирована доставкой X от <когда>»; (2) нужен явный разбор головы по аналогии с `resolve_merge_operation`.

Воркер писал файлы три минуты ПОСЛЕ «остановки»; два источника состояния соврали согласованно. Чинить: либо дождаться завершения хода, либо честно вернуть «остановка запрошена, ход идёт».
