# Локальный benchmark runner

Стенд запускает один вопрос на нескольких исполнителях, сохраняет одинаковый вход,
проверяет результат внешним оракулом и выдаёт JSON/Markdown. Он не обращается к MCP,
API Orchestra или её БД, не создаёт платформенных воркеров и не меняет сервисы.
Python 3.12+, Git; сам runner использует только стандартную библиотеку.

## Рабочий offline-пример

Из корня репозитория:

```bash
python -m scripts.local_bench plan scripts/local_bench/examples/repair/bench.json
python -m scripts.local_bench run scripts/local_bench/examples/repair/bench.json --output /tmp/bench-repair-001
```

На этой машине используйте доступный Python вместо `python`, например
`/opt/orchestra/runtimes/20260817-b0b72d65-py312-rag-v2/bin/python`.

Пример запускает три **синтетических** процесса параллельно, без CLI провайдеров.
Два исправляют `calc.total`, третий намеренно оставляет ошибку. Ожидаемый результат:
PASS/PASS/FAIL, полные синтетические счётчики, exit code **1** — отрицательный контроль
сработал. Это проверка механизма, а не измерение способностей моделей. Деньги в этом
примере — тестовые значения протокола, реальных списаний нет.

В новом `--output` находятся `report.md`, `report.json`, hashes входа/оракула, контроли
и `arms/<name>/`: исходники результата, diff, raw stdout/stderr, `accounting.json`,
`process.json`, `result.json` и независимая проверка. Существующий каталог никогда
не перезаписывается. Корень результата создаётся с доступом только владельцу и
`.gitignore`, исключающим raw-выгрузки из случайного коммита. Перед намеренной публикацией
сырые данные нужно отдельно проверить на секреты. Credential-копии после плеч удаляются.

Коды выхода: 0 — код/процесс/учёт всех плеч успешны; 1 — сравнение собрано, но есть
FAIL, лимит или неполный счётчик; 2 — ошибка конфигурации/preflight, включая отказ namespace.

## Другой вопрос — другая конфигурация

Скопируйте JSON-пример, замените только вход, задание, оракул и список исполнителей.
Пути файлов разрешаются относительно JSON; argv передаются без shell-интерполяции.

| Поле | Значение |
|---|---|
| `source.directory` + `include` | Локальная папка и явный список файлов/каталогов |
| `source.repo` + `revision` + `include` | Альтернатива: Git-снимок конкретного коммита, без его истории |
| `prompt` | Файл задания; результат и границы, без навязанного способа решения |
| `oracle.command` | Команда независимой проверки; exit 0 означает PASS |
| `oracle.files` | Mapping `путь-в-проверке: файл-с-оракулом`; модели этих файлов не видят |
| `controls.expect_baseline_failure` | Проверить, что исходный код действительно проваливает оракул |
| `controls.reference_files` | Mapping файлов принятого решения для зелёного контроля |
| `writable_paths` | Разрешённые изменения, glob-паттерны относительно checkout; по умолчанию `*` |
| `arms` | Уникальные имена и runtime: `fixture`, `codex`, `claude` |
| `timeout_seconds`, `grace_seconds` | Дедлайн попытки и время на аккуратное завершение после SIGINT |
| `budget_usd` | Общий резерв; сумма резервов provider-плеч не должна его превышать |
| `runtime_paths` | Дополнительные read-only каталоги зависимостей внутри provider sandbox |
| `preparation_cost_usd`, `preparation_cost_note` | Явная атрибуция стоимости подготовки; отсутствие — неизвестно, не ноль |

В argv поддерживаются `{python}` (интерпретатор стенда), `{workspace}` и `{config_dir}`.
Оракулу дополнительно доступны `{response}` (нормализованный ответ исполнителя) и
`{transcript}` (JSONL-поток только этого плеча). Они лежат в служебном `.bench/`
внутри проверочной копии, после завершения исполнителя. Так можно оценивать текстовые
ответы и структурированный вывод, а не только правки файлов; код стенда менять не нужно.
Путь `.bench/` зарезервирован, модель не должна создавать его в submitted checkout.
Для provider-оракула используйте файл из `oracle.files`, а не внешний `{config_dir}`:
внешняя папка не монтируется. Рабочая папка внутри namespace — `/work`, HOME —
`/home/bench`, `/tmp` — отдельная tmpfs, `/proc` — отдельное пространство PID.

Файлы оракула и reference можно брать непосредственно из закреплённого Git-коммита:

```json
"oracle": {
  "command": ["{python}", "-m", "pytest", "tests/test_feature.py", "-q"],
  "files": {
    "tests/test_feature.py": {
      "repo": "../repository",
      "revision": "FULL_ACCEPTED_COMMIT_SHA",
      "path": "tests/test_feature.py"
    }
  }
}
```

Так принятая реализация и новые тесты могут остаться в основной истории, но не попасть
в исходники, видимые модели. В `source.revision` берите снимок ДО реализации. Из корня
снимка запрещены `.git`, `.orchestra`, `.env`, AGENTS/CLAUDE, TODO и CHANGELOG; симлинки
отвергаются. Остальные входы выбирает автор вопроса — runner не умеет автоматически
определить, содержит ли произвольный документ готовый ответ.

Проверки исходного и эталонного кода заканчиваются до первого запуска плеча. Зелёный
baseline или красный reference останавливает весь запуск. Все файлы оракула замораживаются;
изменение моделью своей копии теста не изменяет независимую проверку. Оценка сравнивает
исходники с замороженным входом даже если исполнитель сам сделал Git-коммит. Bytecode
и стандартные Python-кеши не считаются изменением кода. Симлинк в результате отвергается
до исполнения оракула. У provider-оракула исходники read-only, сеть закрыта; временные
данные тесты должны писать в `/tmp`.

## Provider-режим: только при рабочей изоляции

```bash
python -m scripts.local_bench doctor
python -m scripts.local_bench run my-question.json --output /tmp/bench-live-001 --allow-provider
```

На текущем VPS непривилегированные user namespaces **запрещены**:
`kernel.apparmor_restrict_unprivileged_userns=1`. Владелец решил оставить защиту.
Provider-preflight откажет до модели: «приватный /tmp недоступен: запрещены
непривилегированные user namespaces». Снятие защиты — решение владельца. Используйте
offline-режим здесь или машину, где namespaces разрешены. Небезопасного fallback нет.

Нужны bubblewrap (ищется и в vendor-каталоге Codex), Landlock ABI 4+, libseccomp.so.2,
установленные CLI и действующий подписочный OAuth. Работоспособность `/tmp`, дочернего
`/proc` и сетевого фильтра проверяется до провайдеров. Стенд ничего не устанавливает и
не меняет sysctl/AppArmor. Полноценный provider sandbox на текущем VPS **не проверен
успешным прогоном**: проверен его честный отказ, положительная ветка покрыта контрактными
тестами и требует проверки на поддерживаемом хосте перед дорогим экспериментом.

Provider-плечо задаётся, например, так (модель — точный установленный идентификатор):

```json
{"name": "candidate", "runtime": "claude", "model": "EXACT_MODEL_ID", "effort": "high", "budget_usd": 2}
```

Для Codex замените runtime и model. В отличие от Claude, его JSON не содержит готовой
долларовой суммы: при необходимости укажите **актуальную** конфигурацию `prices` с четырьмя
ставками за миллион: `input`, `cached_input`, `cache_write`, `output`. Источник ставок
остаётся ответственностью автора конфигурации. Без ставок закрытые токены сохраняются,
стоимость отмечается `unpriced`. Это не нулевой расход. Никаких встроенных устаревающих
тарифов или импорта цен из приложения Orchestra нет.

Claude использует `CLAUDE_CONFIG_DIR/.credentials.json` (по умолчанию `~/.claude/`);
Codex — `CODEX_HOME/auth.json` (по умолчанию `~/.codex/`). `--bare` не используется,
поскольку он отключает OAuth. API-ключи вместо подписки runner не подставляет.
Настройки/MCP/память основного аккаунта не копируются. Native system/tool prompts разных
CLI всё равно различаются: результат сравнивает модель + её runtime, а не только веса.

Сеть из sandbox разрешена через CONNECT relay только к перечисленным provider hosts;
обычный Интернет и dashboard через relay закрыты. AF_UNIX/UDP-сокеты запрещены, TCP
ограничен портом relay. Read-only runtime mounts проверяются на пересечение с входными путями, Git/history,
файлами оракула/reference и выходным каталогом. Mount, раскрывающий эти данные, отвергается
до модели. Зависимости держите отдельно от защищённых исходников и эталона.

## Учёт, остановка и доля подготовки

Плечи подготавливаются до общего стартового барьера и запускаются параллельно. Ошибка
подготовки одного плеча не запускает остальные. SIGINT на дедлайне даёт CLI grace для
закрывающего события; затем TERM/KILL. Raw-поток и прогрессивный receipt записываются
сразу, финальный receipt атомарен и сохраняется также при отмене. Повторных попыток нет.

Состояния `oracle_pass`, `process.completion` и `accounting.status` независимы. После
SIGINT код может пройти проверку, процесс отмечается `deadline`, а счётчик — `complete`,
если CLI действительно выдал финальные данные. Если CLI не выдал их даже после grace,
отчёт содержит `partial`/`missing`, известные наблюдения и **null** вместо полного счёта.
Физически отсутствующее закрывающее событие не восстанавливается выдуманной ценой.
Claude `message_delta` сохраняет output завершённых ответов даже без финала всего хода;
дубли assistant-сообщений по одному id не суммируются повторно. Codex cache_read находится
внутри input и не складывается с ним второй раз.

У Claude резерв передаётся также в `--max-budget-usd`. Прогрессивная стоимость обоих
runtime, если доступна, вызывает SIGINT при достижении резерва. Это не гарантия hard cap:
CLI может сообщить usage только после дорогого запроса, а grace тоже может расходовать
токены. В отчёте видны `over_budget_observed`, неполный учёт и известная сумма; они не
доказывают соблюдение резерва при отсутствующем финальном счёте.

`preparation_seconds` измеряет подготовку snapshot/контролей/плеч отдельно от их работы.
Стоимость интеллектуальной подготовки автоматически не угадывается. При явной сумме
и пояснении выводится доля `подготовка / (подготовка + все плечи)`; если хотя бы одно
слагаемое неизвестно, доля тоже неизвестна. Для synthetic-режима это только тестовые
единицы, не расход подписок. Чтобы сравнить повторное использование, запускайте уже
готовую конфигурацию и учитывайте только действительно новую подготовку.

Проверка механизма без провайдеров:

```bash
python -m pytest tests/local_bench --confcutdir=tests/local_bench -q -p no:randomly
```

`--confcutdir` отделяет эти тесты от фикстур приложения и его БД. Примеры, oracle и
управляемые процессы дают отрицательное и разрешающее плечи без платного запроса.

Fixture-процессы — доверенные локальные тестовые программы с обычными правами пользователя.
Это не обход provider sandbox: в одном сравнении запрещено смешивать fixture и provider
runtime. Не используйте fixture для запуска модели под видом offline-проверки.

Отдельная демонстрация остановки — `examples/deadlines.json`: оба процесса оставляют
проходящий код, один выдаёт финальный счётчик после SIGINT, второй игнорирует сигналы
и остаётся с частичным receipt после KILL. У всей таблицы итоговая цена неизвестна;
отдельно показана наблюдаемая часть, а не ложный нулевой расход. Команда та же `run`,
новый JSON и новый каталог результата; ожидаемый exit code 1.

Для повторного вопроса с теми же входами используется автоматически сохранённый
`replay.json`: он ссылается на замороженные seed/оракул/reference/задание, а не на
текущий HEAD исходного проекта. Запуск: `python -m scripts.local_bench run
/прошлый-прогон/replay.json --output /новый-прогон` (для providers также требуется
явный `--allow-provider`). Стоимость старой интеллектуальной подготовки в новый прогон
не переносится. Исполняемые инструменты и внешние fixture-скрипты должны оставаться
доступны; это не контейнерный образ всей машины. `config-effective.json` сохраняет
исходную разрешённую конфигурацию отдельно от рецепта повтора.
